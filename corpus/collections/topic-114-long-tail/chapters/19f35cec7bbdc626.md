# Chapter 4: Ontological Classification of Kernel Instrumentation Entities

## 4.1 Scope and Preamble

This chapter establishes the formal ontological mapping for kernel instrumentation components within the Extended Berkeley Packet Filter (eBPF) subsystem. It provides the necessary taxonomic definitions to classify system call wrappers and tracepoints as Information Content Entities (ICEs) pursuant to the Common Core Ontology (CCO) specifications. The scope of this chapter is restricted to the `04_ebpf_kernel` family, ensuring that all designated classes are verifiable against kernel source definitions and audit requirements. The definitions herein are binding for all subsequent compliance audits and system verification protocols.

## 4.2 The Axiomatic Structure of Designative Entities

### 4.2.1 Definition of Designative ICEs

In the context of kernel observability, an entity must be formally defined to distinguish between raw data artifacts and semantic referents. The foundational axiom governing this classification asserts that any Class X, functioning as a system call wrapper or tracepoint definition, is a subclass of `cco:DesignativeICE`.

A Designative Information Content Entity is defined as an entity that "is about" something—a real-world object, process, or, in this case, a computational event. It serves as a referential anchor. Within the eBPF framework, a class such as `SysEnterOpenAt2` does not merely exist as a string or a code block; it designates a specific, bounded execution path within the kernel space. It stands for the event of a file descriptor being requested.

The formalization of this relationship is critical for maintaining the integrity of audit trails. If an entity is not designative, it cannot be reliably used to trace causality in security events. Therefore, the ontology mandates that all relevant instrumentation classes inherit from `cco:DesignativeICE`.

### 4.2.2 Axiom 1: System Call Basic Classification

The specific axiom governing this classification is expressed in Manchester syntax as follows:

**Class:** `{X:Class}` **SubClassOf:** `cco:DesignativeICE`

This axiom dictates that for any class `X` identified within the scope of kernel instrumentation, `X` must be a subclass of the Designative ICE concept. This is not merely a hierarchical relationship but a semantic constraint. It ensures that the class `X` carries the necessary properties to act as a signifier for the kernel event it represents.

To support the deterministic projection of this axiom into a relational database schema suitable for audit storage, the following structure is defined. The primary key is the unique identifier (`id`) for the axiom instance, while the foreign key structure is implicit in the class reference (`x`), which maps to the broader ontology class registry.

**Table 4-1: Relational Schema for Axiom 1 (t_syscall_basic)**

| Column Name | Data Type | Description |
| :--- | :--- | :--- |
| `id` | VARCHAR(255) | Primary Key. Unique identifier for the axiom instance. |
| `x` | VARCHAR(255) | The Class name (X) which is a subclass of cco:DesignativeICE. |

This schema supports the verification that specific instrumentation classes loaded into the kernel conform to the designative requirement. It allows auditors to query the `t_syscall_basic` table to retrieve a list of all sanctioned classes that serve as valid designative entities.

### 4.3.3 Compliance Verification

The verification protocol requires that the active eBPF programs running on a host be cross-referenced against the `t_syscall_basic` table. Any program attempting to invoke a class `X` that does not exist in this table is considered non-compliant under the governance framework.

This measure ensures that all observability data is grounded in the ontology. It prevents the introduction of arbitrary or undefined classes that could corrupt the semantic integrity of the audit logs. For instance, if a developer attempts to introduce a class named `HackyTrace` without registering it as a subclass of `cco:DesignativeICE`, the verification layer will reject the load operation.

Furthermore, the distinction between "Enter" and "Exit" entities (e.g., `SysEnterRead` vs. `SysExitRead`) is ontologically significant. While they refer to the same logical system call, they designate different *temporal* entities—the initiation of the request versus the completion of the request. The axiom `X SubClassOf cco:DesignativeICE` applies equally to both, validating their existence as separate referents within the information system.

## 4.4 Summary of Relational Projections

The mapping of the OWL ontology to the relational schema is deterministic. The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE` projects directly to the table `t_syscall_basic`. This table acts as the single source of truth for the classification of kernel instrumentation classes.

The use of a VARCHAR(255) data type for the `x` column allows for the storage of fully qualified class names, including namespaces if required by future expansions of the `04_ebpf_kernel` family. The `id` column, functioning as the primary key, ensures that each designation is unique and immutable, a necessary characteristic for forensic auditing.

By adhering to this structure, the documentation maintains a clear chain of evidence from the high-level ontological definition down to the specific rows in the compliance database. This alignment ensures that the system's semantic model is not merely theoretical but is enforced through the database constraints governing the allowable instrumentation classes.
