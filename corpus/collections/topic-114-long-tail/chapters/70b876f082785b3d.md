# Chapter 4: Ontological Classification of Kernel System Calls

**Effective Date:** October 24, 2023  
**Document Control ID:** SYS-ONT-2023-04  
**Status:** Released

## Preamble and Scope

This chapter establishes the formal ontological framework for classifying kernel system calls within the context of enterprise-grade auditing and compliance monitoring. The purpose of this text is to provide systems architects, security analysts, and compliance officers with a rigorous definition of system call entities as they pertain to the Common Core Ontologies (CCO). Specifically, this chapter details the axiomatization of system calls as *Designative Information Content Entities*, ensuring that automated logging mechanisms, such as those employed in eBPF-based tracing frameworks, adhere to a standardized semantic model. The definitions herein are binding for all subsequent chapters regarding kernel-level event mapping and audit trail reconstruction.

## 1. Designative Information Content Entities in Kernel Space

### 1.1 Axiomatic Definition

In the domain of kernel observability, precise terminology is a prerequisite for accurate auditability. We adopt the axiom that a system call is not merely a functional entry point into the kernel, but an information entity that *designates* a specific operational intent. This distinction is critical for high-fidelity logging; the audit log must capture the *designative* aspect (the name and class of the call) distinct from the *executive* aspect (the resulting state change).

The foundational axiom for this classification is defined as follows:

**Axiom 1 (template_id: syscall_basic):**
> **Class:** {X:Class} **SubClassOf:** cco:DesignativeICE

**Verbalization:**
> {X} is a designative information content entity.

This axiom asserts that any class `X` representing a category of system calls is a subclass of `cco:DesignativeICE`. In the Common Core Ontology, a *Designative Information Content Entity* is defined as an information content entity that stands for or refers to a realizable entity. In this context, the system call class (e.g., "FileReadOperation") designates the specific kernel routine that realizes the file reading action. This ontological commitment allows us to treat syscall identifiers as distinct, auditable semantic units rather than arbitrary integer constants.

### 1.2 Relational Mapping and Schema

To facilitate the storage and retrieval of these designative entities in relational databases used by Security Information and Event Management (SIEM) systems, we project the axiom onto a deterministic relational schema. The schema enforces the constraint that every recorded system call class must be explicitly identified and mapped to the designative entity superclass.

The schema for the basic system call classification is presented below. This structure serves as the master registry for valid system call classes within the auditing subsystem.

**Table 1: System Call Basic Classification Registry (t_syscall_basic)**

This table embodies Axiom 1 by listing specific classes (`x`) that are defined as subclasses of `cco:DesignativeICE`. The primary key (`id`) ensures referential integrity for audit logs that reference these designative classes.

| id | x |
|---|---|
| sc_fs_001 | FileReadOperation |
| sc_fs_002 | FileWriteOperation |
| sc_fs_003 | FileSyncOperation |
| sc_fs_004 | FileStatOperation |
| sc_fs_005 | FileDescriptorDuplication |

*Table 1 Notes:*
*   **id**: The unique identifier for the designative class within the ontology registry.
*   **x**: The class name representing the system call category, which is asserted to be a subclass of `cco:DesignativeICE`.

The data in Table 1 represents the filesystem domain of system calls. Each entry in the `x` column is a class that designates a specific type of interaction with the file subsystem. For instance, `FileReadOperation` is the designative entity that refers to the kernel's logic for reading data from a file descriptor. By populating `t_syscall_basic` with these entries, the auditing system validates that any logged event claiming to be a "FileReadOperation" corresponds to a defined ontological class.

## 2. Extension to Network and Process Control Domains

### 2.1 Domain-Specific Designation

While Section 1.1 established the general axiom, the application of `cco:DesignativeICE` extends across all kernel subsystems. The ontological framework requires that designative entities for network operations and process control be registered with the same rigor as filesystem operations. This ensures that cross-domain audit logs maintain a consistent type hierarchy.

In compliance frameworks (e.g., NIST 800-53 or PCI-DSS), the ability to distinguish between a "designative" log entry (the request to connect a socket) and the actual network traffic is vital for forensic analysis. The axiom `{X} SubClassOf cco:DesignativeICE` holds true regardless of the domain. Therefore, network-related classes such as `SocketConnectOperation` must be registered in the schema to be considered valid audit targets.

### 2.2 Registry for Network and Process Classes

The following table extends the registry defined in Section 1.2 to include critical network and process control classes. These entries are essential for monitoring unauthorized network activity or process injection attempts, which are key indicators of compromise (IoC).

**Table 2: Extended System Call Classification Registry (t_syscall_basic)**

This table continues the embodiment of Axiom 1, providing instances for network and process control classes. The schema remains identical to preserve the deterministic mapping required by the ontology engine.

| id | x |
|---|---|
| sc_net_101 | SocketCreateOperation |
| sc_net_102 | SocketConnectOperation |
| sc_net_103 | SocketAcceptOperation |
| sc_net_104 | SocketSendOperation |
| sc_proc_201 | ProcessCloneOperation |
| sc_proc_202 | ProcessExecOperation |
| sc_proc_203 | ProcessExitOperation |

*Table 2 Notes:*
*   **id**: Unique identifiers maintaining the namespace convention `sc_<domain>_<sequence>`.
*   **x**: The class name designating the specific kernel operation.

The inclusion of `ProcessExecOperation` in Table 2 is particularly significant for runtime security. As a designative information content entity, this class designates the transition of a process from its current state to a new program image. In an audit context, the appearance of this designative class in a log stream is a high-fidelity signal requiring immediate correlation with the process identity and user context.

## 3. Verification and Compliance Implications

### 3.1 Schema Validation

The integrity of the audit pipeline depends on the strict enforcement of the schema defined in Section 1.2. Any system call event captured by the monitoring agent (e.g., an eBPF program attached to the `sys_enter` tracepoint) must map its syscall identifier to a valid entry in the `t_syscall_basic` table.

If a kernel module or a custom syscall generates an event that does not have a corresponding row in `t_syscall_basic`, the event must be flagged as "Ontologically Undefined" in the compliance report. This strict validation prevents the obfuscation of malicious activity via undefined or custom syscall numbers that do not map to a recognized `cco:DesignativeICE`.

### 3.2 Audit Trail Reconstruction

For auditors, the distinction between the *designative* entity and the *data* properties of the syscall is paramount. The tables provided in this chapter (`t_syscall_basic`) define the *vocabulary* of the audit trail. When reconstructing a security incident, the analyst queries the `x` column to understand the *intent* (the designative class), while separate data tables (not shown here) would record the arguments (file descriptors, buffer addresses, etc.).

For example, referencing `sc_proc_202` (`ProcessExecOperation`) from Table 2 allows the auditor to filter all events where the designative intent was to execute a new program. This semantic filtering is far more robust than filtering on raw syscall numbers (e.g., `59` on x86_64 architectures), which may vary across hardware architectures. By anchoring the audit log to the ontological class `x`, the compliance report achieves architecture-agnostic semantic validity.
