# Chapter 4: Taxonomy of Kernel Entities in eBPF Compliance Frameworks

This chapter establishes the foundational taxonomy required for classifying kernel interactions within the extended Berkeley Packet Filter (eBPF) monitoring infrastructure. It addresses the necessity of defining system calls and kernel primitives as Information Content Entities (ICE) to facilitate automated compliance auditing, governance reporting, and security control verification. The following sections delineate the formal ontological status of these entities, providing the structural schema necessary for mapping low-level kernel events to high-level governance frameworks.

## 1. Designative Information Content Entities in System Call Architectures

In the context of kernel observability and security auditing, precise terminology is paramount for ensuring that telemetry data aligns with regulatory expectations and organizational governance policies. The fundamental unit of interaction between user-space applications and the kernel is the system call. However, for the purposes of audit trails and compliance automation, a system call must be treated not merely as a functional invocation, but as a distinct informational artifact.

### 1.1. Formal Definition and Ontological Status

To integrate kernel-level telemetry with semantic audit layers, we adopt the axiom that specific classes of system calls function as **Designative Information Content Entities**. A Designative ICE is an entity that serves to refer to or identify a specific process, function, or object within a system. By classifying system calls under this ontology, we transform raw execution vectors into structured data points that can be queried, validated, and reported against compliance standards.

The formalization of this relationship is expressed through the following axiom: the class of a specific system call (denoted as {X}) is a subclass of `cco:DesignativeICE`. This classification asserts that the informational content representing the system call serves a designative role, specifically identifying the requested kernel operation. This distinction is critical for audit logs; it ensures that the record signifies the *intent* of an operation (the designation) rather than merely recording its execution footprint.

### 1.2. Audit Implications of Designative Classification

Treating system calls as Designative ICEs allows auditors to construct queries based on the semantic meaning of an event rather than its binary signature. For instance, in a data governance framework, an auditor may require a report of all "designative entities pertaining to file modification." By querying the subclass hierarchy where `x` represents file-modification operations (such as `SyscallWrite`), the system can isolate relevant records without complex regular expression parsing of raw hex dumps.

This approach facilitates the generation of compliance artifacts required by frameworks such as NIST 800-53 or GDPR. When an automated audit tool encounters a log entry corresponding to `sys_uuid_004` (`SyscallWrite`), it understands that this entry designates a write operation. Consequently, the system can automatically cross-reference this event with data access policies to verify that the write operation was authorized against the specific data object in question.

### 1.3. Verification of Entity Designations

To maintain the integrity of the audit trail, the mapping between the kernel identifier and the designative class must be deterministic. The eBPF verification process ensures that the loaded program does not crash the kernel, but the governance layer must ensure that the program correctly classifies the events it observes.

When a probe triggers, the associated data structure must populate the `x` field with the canonical class name defined in the ontology. Any deviation from the taxonomy defined in Table 1.1 constitutes a data integrity failure in the compliance report. For example, if a probe detects a `bind` operation but erroneously classifies it as `SyscallConnect`, the audit trail becomes semantically invalid, potentially masking unauthorized network listening activities.

### 1.4. Implementation in eBPF Programs

In the implementation of eBPF observability tools, the `t_syscall_basic` table structure serves as the blueprint for the map definitions used within the kernel space. Developers utilizing the `bpf_syscall` helpers must ensure that the keys passed to BPF maps correspond to the `id` values established in the schema.

For example, when a `SyscallOpen` event is intercepted, the eBPF program should utilize the `sys_uuid_001` identifier as the key in a BPF hash map. This ensures that when the map is read to userspace for report generation, the data aligns perfectly with the relational schema expected by the compliance engine. This strict adherence to the schema prevents "schema drift" between the kernel-level data collection and the database-level reporting, ensuring that the "evidence" remains legally defensible and technically accurate throughout the data lifecycle.
