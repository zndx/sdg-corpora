# HIPAA Safeguard Directives in Audit-Trail Schemas

This chapter defines three classes of HIPAA safeguard directives as subclasses of cco:DirectiveICE and shows how each class is represented by a dedicated relation. The relations store only the class-valued slots required by the axioms; cross-table queries recover multi-hop chains such as “which administrative directive safeguards the same asset that a given technical directive also protects.”

## 1. Administrative Safeguard Relation

Axiom 1 states that any instance of a subclass X of cco:DirectiveICE stands in the hipaaSafeguard relation to a class Y. Table t_hipaa_safeguard_admin materializes exactly those two slots. Column id is the primary key that uniquely identifies each directive instance; columns x and y hold the URIs of the respective classes. Because y values recur across rows, a reader can group by y to obtain all administrative directives that protect a given asset class.

```sql
CREATE TABLE t_hipaa_safeguard_admin (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 2. Physical Safeguard Relation

Axiom 2 likewise populates a subclass of cco:DirectiveICE together with its safeguarded class, now under the physical-safeguard template. Table t_hipaa_safeguard_physical therefore re-uses the identical column layout. Its primary key id again isolates each directive; the foreign-key semantics are implicit in the repeated y values that also appear in the administrative table, permitting a natural equi-join on y.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| hipaa-phys-02 | WorkstationSecurity | ehr:PatientDemographics |
| hipaa-phys-03 | DeviceMediaControl | ehr:AuditLogArchive |

## 3. Technical Safeguard Relation

Axiom 3 completes the set by capturing technical directives. Table t_hipaa_safeguard_technical follows the same deterministic schema. Its id column serves as primary key; any y value that matches a y value in either of the preceding tables yields a three-table join path from administrative through physical to technical safeguards protecting an identical asset class.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 4. Multi-Hop Query Example

Question: which technical safeguard protects the same asset class that is also protected by at least one administrative and one physical directive?

The equi-join below walks the foreign-key relationship on y:

```sql
SELECT a.y AS asset,
       a.x AS admin_directive,
       p.x AS phys_directive,
       t.x AS tech_directive
FROM   t_hipaa_safeguard_admin a
JOIN   t_hipaa_safeguard_physical p ON a.y = p.y
JOIN   t_hipaa_safeguard_technical t ON a.y = t.y;
```

Result rows include:

- asset = ehr:PatientDemographics, admin_directive = AccessAuthorization, phys_directive = WorkstationSecurity, tech_directive = AccessControlMechanism
- asset = ehr:AuditLogArchive, admin_directive = ContingencyPlan, phys_directive = DeviceMediaControl, tech_directive = AuditControl
- asset = ehr:ThirdPartyDataShare, admin_directive = BusinessAssociateContract, phys_directive = (none), tech_directive = TransmissionSecurity

Only the first two assets satisfy the “at least one of each” criterion.
