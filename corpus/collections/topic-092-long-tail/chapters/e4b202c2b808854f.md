# Chapter 4: Formalizing Compliance Artifacts and Evidence Chains

This chapter delineates the structural formalization of regulatory compliance artifacts within the enterprise governance framework. It establishes the ontological relationships between attestation processes, specific regulatory directives (specifically PCI DSS and HIPAA), and the technical controls that generate verifiable evidence. The mapping of these concepts to a relational schema ensures data integrity and supports automated auditing mechanisms, facilitating a rigorous approach to maintaining continuous compliance posture.

## 4.1 Attestation with Supporting Evidence

In the context of governance, an attestation is formally defined as a process by which an authorized entity validates that specific controls have been executed effectively. Under the axiom `attestation_with_supporting_evidence`, the class `Attestation` is a subclass of `bfo:Process`, denoting that it is an occurrent entity that unfolds in time. Crucially, this process possesses the object property `sdg:withSupportingEvidence`, which establishes a mandatory dependency relationship between the attestation event and a specific regulatory requirement class.

This relationship dictates that an attestation is not a standalone declaration but is structurally bound to the evidence derived from a requirement. For instance, a "Quarterly Compliance Review" (the attestation) is only valid if it references the evidence generated by "PCI DSS Requirement 8.2" regarding user access management. The relational projection of this axiom enforces that the evidence target (`y`) must exist within the `t_pci_dss_requirement` table, thereby preventing orphaned attestations.

The following data table illustrates instances of this axiom, demonstrating how specific attestation processes are anchored to PCI DSS requirements.

| :--- | :--- | :--- |

## 4.2 PCI DSS Requirements

The Payment Card Industry Data Security Standard (PCI DSS) requirements function as the primary directive classes within this ontology. The axiom `pci_dss_requirement` categorizes these directives as subclasses of `cco:DirectiveICE`, representing Information Control Elements. These are normative definitions that prescribe specific behaviors or configurations within the IT environment. The object property `sdg:pciDssRequirement` links the specific requirement class (`x`) to a broader control implementation class (`y`).

It is critical to note the recursive nature of the compliance framework defined here. A PCI DSS requirement does not merely exist in isolation; it must be mapped to a `control_with_evidence_requirement`. This structure ensures that every high-level mandate (e.g., "Change default passwords") is decomposed into an executable control mechanism that is capable of producing an audit trail. The foreign key constraint in the relational schema mandates that the `y` value in the `t_pci_dss_requirement` table must correspond to a valid entry in the `t_control_with_evidence_requirement` table.

The table below provides the instantiation of these requirements, mapping the standard's textual mandates to specific control identifiers.

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_08_02 | Req_8.2_User_Access_Management | CTRL_EVID_ACCESS |
| PCI_REQ_12_01 | Req_12.1_Security_Policy | CTRL_EVID_POLICY |
| PCI_REQ_02_02 | Req_2.2_Config_Standards | CTRL_EVID_CONFIG |

*Table 4.2: Decomposition of PCI DSS requirements. The `x` column denotes the specific requirement identifier, while `y` references the control class responsible for fulfilling the directive and generating necessary evidence.*

## 4.3 Controls with Evidence Requirements

The operational backbone of the compliance framework is the `control_with_evidence_requirement`. This axiom defines a class of directives that are specifically engineered to produce verifiable artifacts. As a subclass of `cco:DirectiveICE`, it represents the active enforcement of a policy or technical standard. The property `sdg:requiresEvidence` indicates that the execution of this control must result in a tangible or digital record (e.g., a log file, a configuration snapshot, or a signed document).

In the relational model, this table serves as a junction that often links back to the regulatory requirements. The schema defines a foreign key reference from `t_control_with_evidence_requirement` to `t_pci_dss_requirement`. This circular dependency (Requirement $\to$ Control $\to$ Requirement) allows for complex mapping scenarios where a single control may satisfy multiple requirements, or where a requirement necessitates a chain of controls. For example, the control "Vendor Default Removal" (Control) satisfies "Req 2.2" (Requirement), but the evidence of this control is also necessary to satisfy "Req 10.2" (Audit Trails).

The following table details the control classes and their associated evidence requirements, demonstrating the linkage back to the PCI DSS requirements.

| id | x | y |
| :--- | :--- | :--- |
| CTRL_EVID_ACCESS | User_Access_Review_Control | PCI_REQ_08_02 |
| CTRL_EVID_POLICY | Policy_Distribution_Control | PCI_REQ_12_01 |
| CTRL_EVID_CONFIG | System_Hardening_Control | PCI_REQ_02_02 |

*Table 4.3: Control classes and their evidence outputs. Column `x` identifies the specific control mechanism, and column `y` links this control back to the PCI requirement it validates, closing the evidence loop.*

## 4.4 HIPAA Physical Safeguards

While the previous sections focused on payment card security, the governance framework must accommodate multi-regulatory environments. The axiom `hipaa_safeguard_physical` addresses the Physical Safeguards provisions of the Health Insurance Portability and Accountability Act (HIPAA) Security Rule. This axiom classifies physical security measures as `cco:DirectiveICE` subclasses, utilizing the property `sdg:hipaaSafeguard` to define the scope of the protection.

In this unified model, HIPAA safeguards are not treated as isolated silos but are integrated into the broader evidence architecture. The relational schema dictates that the `y` slot in `t_hipaa_safeguard_physical` must reference a `t_control_with_evidence_requirement`. This design enforces the principle that physical safeguards (e.g., facility access controls, workstation security) must be implemented as formal controls with auditable evidence, rather than merely procedural suggestions. For instance, a "Facility Access Log" is not just a security measure; it is a control instance that must be mapped to an evidence requirement to satisfy the governance framework.

The table below maps specific HIPAA physical safeguards to their underlying control implementations.

*Table 4.4: Mapping of HIPAA Physical Safeguards. The `x` column represents the HIPAA-specific safeguard class, which is implemented via the control class referenced in column `y`.*

## 4.5 HIPAA Technical Safeguards

Complementing physical measures, the `hipaa_safeguard_technical` axiom formalizes the Technical Safeguards required by HIPAA. These controls involve the technology and the policies and procedures for its use that protect electronic protected health information (ePHI) and control access to it. Like the physical safeguards, this axiom maps the technical directive (`x`) to a control with an evidence requirement (`y`).

This structural alignment ensures that technical safeguards such as encryption, audit controls, and authentication mechanisms are treated as auditable directives within the ontology. By referencing the `t_control_with_evidence_requirement` table, the framework ensures that technical controls are subject to the same rigorous evidence collection standards as PCI DSS controls. This allows the organization to leverage a single control infrastructure to satisfy distinct regulatory obligations (e.g., an Access Control mechanism may serve both PCI DSS Requirement 8 and HIPAA Technical Safeguard 164.312(a)(1)).
