# Chapter 4: Governance Frameworks and Evidence-Based Compliance Mapping

## 4.1 Scope and Preamble

This chapter delineates the structural relationships between governance directives, compliance requirements, and the evidentiary artifacts necessary for validation within a regulated environment. It establishes a formal ontology for mapping high-level attestations to specific control implementations across regulatory frameworks, specifically focusing on the intersection of PCI DSS and HIPAA Security Standards. The content herein provides a deterministic schema for linking abstract directives to concrete evidence requirements, ensuring that compliance postures are both auditable and operationally grounded. Readers will be guided through the hierarchical decomposition of attestation processes, requirement specifications, and safeguard implementations, supported by relational data models that enforce referential integrity across these domains.

## 4.2 Attestation with Supporting Evidence

In the context of formal governance, an attestation is defined not merely as a declaration of compliance, but as a distinct process (`bfo:Process`) that substantiates its claims through rigorous evidentiary support. The axiom `attestation_with_supporting_evidence` posits that for any attestation entity {X} to be valid, it must possess a supporting evidence relationship with a specific requirement class {Y}. This relationship transforms the attestation from a subjective assertion into an objective, verifiable artifact within the audit trail.

The operationalization of this concept requires that organizations maintain a traceable link between the act of attestation—such as a signed annual report or a third-party audit certification—and the specific regulatory or internal control requirements it seeks to validate. Without this binding, the attestation lacks the necessary "evidence anchor" required by professional standards. The structure of this relationship is hierarchical; the attestation serves as the container or wrapper for the evidence, which in turn points to the underlying requirement.

The following table illustrates the instantiation of this axiom, mapping specific attestation processes to the PCI DSS requirements they validate. The primary key (`id`) uniquely identifies the attestation event, while the foreign key (`y`) ensures that the attestation is explicitly linked to a valid requirement identifier.

**Table 4.1: Attestation with Supporting Evidence Mappings**

| id | x | y |
| :--- | :--- | :--- |
| ATT-2023-Q3 | Third-Party PCI Assessment | PCI_REQ_8.2.5 |
| ATT-2023-04 | Internal Control Self-Assessment | PCI_REQ_1.2.3 |
| ATT-2023-05 | Physical Security Review | PCI_REQ_9.2.1 |
| ATT-2023-06 | Wireless Network Audit | PCI_REQ_1.2.6 |
| ATT-2023-07 | Change Management Verification | PCI_REQ_6.4.1 |

In this schema, `x` represents the specific attestation class or instance (the process), while `y` represents the requirement class serving as the evidence anchor. This structure ensures that every attestation event recorded in the governance framework is mathematically bound to a specific control objective, thereby eliminating orphaned compliance claims.

## 4.3 PCI DSS Requirements

The Payment Card Industry Data Security Standard (PCI DSS) provides a canonical set of directives that function as `cco:DirectiveICE` (Information Control Element) classes. The axiom `pci_dss_requirement` formalizes the relationship between a specific directive {X} and its requirement definition {Y}. This mapping is critical for translating the broad language of the standard into actionable control objectives within an organization's governance architecture.

A PCI DSS requirement is not merely a textual statement; it is a governance node that must be integrated into the broader compliance fabric. The axiom asserts that {X} (the directive) is a type of entity that "pci dss requirement" {Y}. This implies a dependency where the operational validity of the directive is contingent upon the correct interpretation and implementation of the requirement. In practice, this means that when a system identifies a directive such as "Require strong authentication," it must explicitly map this to the specific PCI DSS clause (e.g., Requirement 8.2.5) to ensure semantic accuracy in reporting and auditing.

The relational projection of this axiom demonstrates a bidirectional linkage with control implementations. As shown in the schema below, the requirement table references the control table, creating a tightly coupled loop where requirements define controls, and controls validate requirements.

**Table 4.2: PCI DSS Requirement Directives**

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_8.2.5 | Multi-Factor Authentication Directive | CTRL_EVID_AUTH_01 |
| PCI_REQ_1.2.3 | Inbound Traffic Control Directive | CTRL_EVID_NET_01 |
| PCI_REQ_9.2.1 | Media Access Control Directive | CTRL_EVID_PHYS_01 |
| PCI_REQ_1.2.6 | Wireless Configuration Directive | CTRL_EVID_NET_02 |
| PCI_REQ_6.4.1 | Change Management Directive | CTRL_EVID_DEV_01 |

Here, the column `x` denotes the specific PCI DSS directive class, while `y` references the control with evidence requirement that fulfills it. This foreign key relationship (`y` -> `t_control_with_evidence_requirement`) enforces the rule that a requirement cannot exist in isolation; it must be assigned to a specific control mechanism capable of generating the necessary evidence.

## 4.4 Controls with Evidence Requirements

At the operational layer of the governance framework lies the `control_with_evidence_requirement`. This axiom addresses the "how" of compliance by defining {X} as a directive that "requires evidence" {Y}. This is a critical distinction in audit readiness: a control is only effective if it produces retrievable, verifiable evidence that it is functioning as intended.

The axiom `control_with_evidence_requirement` establishes that {X} (a control directive) is a subclass of `cco:DirectiveICE` and possesses a property `sdg:requiresEvidence` pointing to {Y}. In a mature governance environment, this means that controls are not passive configurations but active generators of audit logs, configuration snapshots, or other artifacts. The relationship defined here is reciprocal to the PCI DSS requirements; while the requirement defines *what* must be achieved, the control defines *how* it is achieved and *what proof* is provided.

The data structure for this concept reveals the circular dependency inherent in compliance frameworks: controls satisfy requirements, and requirements validate controls. The table below populates this relationship, showing how specific control directives map back to the PCI requirements they fulfill.

**Table 4.3: Control with Evidence Requirements**

| id | x | y |
| :--- | :--- | :--- |
| CTRL_EVID_AUTH_01 | Identity Management Control | PCI_REQ_8.2.5 |
| CTRL_EVID_NET_01 | Firewall State Management | PCI_REQ_1.2.3 |
| CTRL_EVID_PHYS_01 | Physical Media Handling | PCI_REQ_9.2.1 |
| CTRL_EVID_NET_02 | Wireless Encryption Control | PCI_REQ_1.2.6 |
| CTRL_EVID_DEV_01 | Production Change Control | PCI_REQ_6.4.1 |

In this table, `x` represents the specific control directive (e.g., "Identity Management Control"), and `y` represents the PCI DSS requirement ID that serves as the evidence target. The foreign key constraint ensures that every control is linked to a valid requirement, enforcing the logic that evidence generation must always be purpose-driven and aligned with a specific compliance obligation.

## 4.5 HIPAA Physical Safeguards

While PCI DSS provides a commercial framework for payment data, the Health Insurance Portability and Accountability Act (HIPAA) mandates specific protections for Protected Health Information (PHI). The `hipaa_safeguard_physical` axiom categorizes a specific class of directives {X} that implement "hipaa safeguard" {Y}, focusing on physical access controls.

Under this axiom, {X} is a subclass of `cco:DirectiveICE`, representing the physical security measures enacted by an organization. These measures are distinct from technical controls in that they involve tangible barriers, personnel security, and facility management. The relationship `sdg:hipaaSafeguard` links the directive to the specific safeguard definition {Y}, which in this relational model maps to the broader control evidence requirements. This mapping allows organizations to demonstrate that a single physical control (e.g., a badge reader) can satisfy multiple regulatory frameworks (PCI DSS and HIPAA) simultaneously, a concept known as "compliance unification."

The following table details the implementation of physical safeguards, mapping specific HIPAA directives to the underlying control evidence requirements. This illustrates how physical security protocols are integrated into the centralized evidence repository.

**Table 4.4: HIPAA Physical Safeguard Directives**

| id | x | y |
| :--- | :--- | :--- |
| HIPAA_PHY_01 | Facility Access Control | CTRL_EVID_PHYS_01 |
| HIPAA_PHY_02 | Workstation Use Policy | CTRL_EVID_PHYS_01 |
| HIPAA_PHY_03 | Device and Media Control | CTRL_EVID_PHYS_01 |
| HIPAA_PHY_04 | Security Awareness Training | CTRL_EVID_AUTH_01 |
| HIPAA_PHY_05 | Contingency Operations | CTRL_EVID_NET_01 |

The column `x` identifies the specific HIPAA physical safeguard directive (e.g., "Facility Access Control"), while `y` references the ID from the control evidence table. This structure validates that the physical safeguard is not an abstract policy but a directive that generates the evidence required by the control framework (e.g., logs of entry, video surveillance records).

## 4.6 HIPAA Technical Safeguards

Complementing physical safeguards, the `hipaa_safeguard_technical` axiom defines the automated mechanisms used to protect electronic PHI (ePHI). Similar to the physical safeguards, this axiom classifies {X} as a directive that "hipaa safeguard" {Y}, but the instances of {X} are inherently technical in nature—encryption, access control software, and audit mechanisms.

The axiom asserts that these technical safeguards are `cco:DirectiveICE` entities, meaning they are formalized instructions or configurations within the IT infrastructure. By mapping these technical directives to the control evidence requirements, the organization establishes a clear line of sight from the technical configuration (e.g., "AES-256 encryption enabled") to the compliance obligation (e.g., "Addressable implementation of Encryption"). This granularity is essential for technical audits and penetration testing, where the absence of a specific technical configuration can be directly correlated with a compliance failure.

The table below provides the relational mapping for HIPAA technical safeguards, demonstrating how specific technical controls align with the evidence requirements established in previous sections.

| HIPAA_TECH_03 | Automatic Logoff | CTRL_EVID_AUTH_01 |
| HIPAA_TECH_04 | Encryption and Decryption | CTRL_EVID_NET_02 |

In this schema, `x` represents the technical safeguard directive (e.g., "Unique User Identification"), and `y` links to the control evidence requirement. This linkage confirms that the technical implementation of user IDs is the mechanism by which the Identity Management Control generates evidence to satisfy PCI_REQ_8.2.5, thereby demonstrating the convergence of HIPAA and PCI DSS requirements through a unified control framework.
