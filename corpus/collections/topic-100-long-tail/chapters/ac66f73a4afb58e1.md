# Chapter 4: Unified Governance Ontology for PCI DSS and HIPAA Compliance

## 4.1 Scope and Preamble

This chapter establishes the formal ontology governing the intersection of Payment Card Industry Data Security Standards (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA) Security Rule. In environments where Protected Health Information (PHI) and cardholder data (CHD) coexist—such as healthcare payment processing systems—compliance officers must navigate a complex web of directives, processes, and evidence artifacts. The following sections delineate the relational mapping between specific regulatory requirements, the attestation processes that validate them, and the safeguard implementations that satisfy both frameworks. The structure provided herein adheres to a deterministic schema where every directive is anchored to a specific evidentiary process, ensuring auditability and traceability across the governance lifecycle.

## 4.2 PCI DSS Requirements and Directive Governance

The foundational element of this ontology is the PCI DSS requirement, defined formally as a subclass of the Information Control Element (DirectiveICE). In this context, a PCI DSS requirement is not merely a textual mandate but a governance object that imposes a specific control upon the enterprise environment. The axiom `pci_dss_requirement` establishes that a directive (X) necessitates a specific requirement (Y), which is structurally realized through an attestation process.

To maintain a rigorous compliance posture, organizations must map high-level directives to specific PCI DSS controls. For instance, a directive regarding network perimeter security must be explicitly linked to the requirement for firewall configuration. This linkage is not merely semantic but structural; the requirement entity serves as a foreign key bridge to the evidence that validates it. The relational schema for this concept enforces that every requirement identifier must correspond to a valid attestation record, thereby preventing the existence of "orphan" controls that lack verification mechanisms.

## 4.3 Attestation with Supporting Evidence

The attestation process acts as the verification engine for the governance framework. Defined by the axiom `attestation_with_supporting_evidence`, this concept represents a process (X) that possesses or generates supporting evidence (Y). In the context of this ontology, the "evidence" is formally linked back to the PCI DSS requirement it validates. This creates a recursive validation loop: a directive mandates a requirement, which is validated by an attestation, which in turn generates evidence that substantiates the original requirement.

This formalization is critical for audit readiness. When an auditor reviews a control, they are reviewing the attestation process—the "who, what, when, and how" of the verification. The schema dictates that the evidence slot (`y`) within the attestation table must reference a valid PCI DSS requirement. This constraint enforces the principle that evidence is always evidence *of* something specific; untargeted documentation is insufficient for compliance verification.

| `ATT_NET_001` | `Process:QuarterlyFirewallReview` | `PCI_REQ_001` |
| `ATT_ENC_001` | `Process:AnnualCipherAudit` | `PCI_REQ_002` |

The data in Table 4.2 demonstrates the bidirectional nature of the compliance framework. For example, `Process:QuarterlyFirewallReview` (`ATT_NET_001`) generates the evidence that satisfies `PCI_REQ_001`. This rigorous mapping allows compliance officers to trace a finding from a high-level directive down to the specific log files or audit reports that constitute proof of adherence.

## 4.4 HIPAA Administrative Safeguards

While PCI DSS focuses on cardholder data, HIPAA introduces the requirement for Administrative Safeguards to protect electronic PHI (ePHI). The axiom `hipaa_safeguard_admin` defines a directive (X) that implements a specific HIPAA administrative safeguard (Y). In this unified ontology, the administrative safeguard is not an abstract concept but a concrete implementation that relies upon the attestation processes defined in Section 4.3.

This approach allows for a unified control framework. A single directive, such as a Security Management Process, can function as an administrative safeguard for HIPAA while simultaneously leveraging the attestation evidence used for PCI DSS. The relational schema requires that the safeguard (`y`) reference an existing attestation record. This implies that HIPAA safeguards are validated through the same rigorous evidence-gathering processes as PCI controls, promoting efficiency and reducing audit fatigue.

**Table 4.3: HIPAA Administrative Safeguard Implementation**
This table embodies the `hipaa_safeguard_admin` axiom. It maps organizational directives to specific administrative safeguards, validated via the attestation framework.

| id | x | y |
| :--- | :--- | :--- |
| `HIPAA_ADMIN_01` | `Directive:RiskAnalysisProtocol` | `ATT_NET_001` |
| `HIPAA_ADMIN_02` | `Directive:SanctionPolicyEnforcement` | `ATT_AC_001` |
| `HIPAA_ADMIN_03` | `Directive:SecurityAwarenessTraining` | `ATT_AM_001` |

For instance, `Directive:RiskAnalysisProtocol` (`HIPAA_ADMIN_01`) utilizes the evidence generated by the `Process:QuarterlyFirewallReview` (`ATT_NET_001`) to satisfy its administrative safeguard requirements. This illustrates how network security controls serve a dual purpose in a hybrid compliance environment.

## 4.5 HIPAA Technical Safeguards

Technical Safeguards under HIPAA involve the technology and the policy and procedures for its use that protect electronic health information and control access to it. The axiom `hipaa_safeguard_technical` formalizes this as a directive (X) that enforces a technical safeguard (Y). Similar to administrative safeguards, technical safeguards are grounded in the attestation processes defined earlier.

The distinction between administrative and technical safeguards often blurs in practice; however, this ontology maintains a strict separation at the directive level while allowing for shared evidence at the attestation level. The foreign key constraint ensures that every technical safeguard is backed by a specific, documented process. This is particularly relevant for controls like access control and audit controls, which are heavily emphasized in both PCI DSS and HIPAA.

**Table 4.4: HIPAA Technical Safeguard Implementation**
This table embodies the `hipaa_safeguard_technical` axiom. It links directives to technical safeguards, ensuring that automated controls are formally attested.

| id | x | y |
| :--- | :--- | :--- |
| `HIPAA_TECH_01` | `Directive:UniqueUserIdentification` | `ATT_AC_001` |
| `HIPAA_TECH_02` | `Directive:EmergencyAccessProcedure` | `ATT_NET_001` |
| `HIPAA_TECH_03` | `Directive:TransmissionSecurity` | `ATT_ENC_001` |

In Table 4.4, `Directive:TransmissionSecurity` (`HIPAA_TECH_03`) leverages the `Process:AnnualCipherAudit` (`ATT_ENC_001`) to verify that encryption controls are functioning correctly. This data demonstrates that the technical implementation of encryption serves both the PCI DSS requirement for data protection and the HIPAA requirement for transmission security.

## 4.6 HIPAA Physical Safeguards

The final component of the HIPAA Security Rule addressed in this chapter is Physical Safeguards. These are measures to physically protect electronic information systems and related buildings and equipment from natural and environmental hazards, as well as unauthorized intrusion. The axiom `hipaa_safeguard_physical` defines a directive (X) that enforces a physical safeguard (Y).

Physical safeguards often involve facility management, such as badge readers, security guards, and workstation usage policies. By mapping these directives to the central attestation table, the ontology ensures that physical security is not treated as a siloed operational concern but as an integral part of the information security governance structure. The evidence required for these safeguards—such as visitor logs or maintenance records—must be captured within the defined attestation processes.

**Table 4.5: HIPAA Physical Safeguard Implementation**
This table embodies the `hipaa_safeguard_physical` axiom. It connects facility-level directives to the broader compliance evidence framework.

| id | x | y |
| :--- | :--- | :--- |
| `HIPAA_PHYS_01` | `Directive:FacilityAccessControl` | `ATT_AC_001` |
| `HIPAA_PHYS_02` | `Directive:WorkstationSecurity` | `ATT_AM_001` |
| `HIPAA_PHYS_03` | `Directive:DeviceMediaControl` | `ATT_ENC_001` |

The mapping in Table 4.5 shows that `Directive:FacilityAccessControl` (`HIPAA_PHYS_01`) relies on `ATT_AC_001`, the biometric access log review. This reinforces the concept that physical access controls (badges/turnstiles) generate log data that must be reviewed and attested to with the same rigor as logical access controls (usernames/passwords).
