An identifier is the immutable key that anchors a record within a relational domain, enabling unambiguous reference across all associated metadata. In directive registries, identifiers such as DIRE-0001 through DIRE-0004 serve as the primary keys for records describing standards like PCI DSS v4.0 and NERC CIP-003; similarly, artifact measurements carry identifiers ARTI-0001 through ARTI-0004 for metrics including latency_p99_ms and yield_stress_test, while service traces are keyed by SERV-0001 through SERV-0004 for operations such as ci-cd-deploy-run and nightly-data-sync. These identifiers are not merely labels—they are the structural fulcrum upon which every foreign-key relationship in the schema pivots, ensuring that attribute definitions, typed values, and entity cross-references resolve to a single, canonical record.

An attribute is a named property that describes a characteristic of an entity, and its type constrains the kind of value it may hold. Attribute definitions are declared with a name and an XSD type: effective_date carries xsd:date, enforcement carries xsd:string, mandatory carries xsd:boolean, and priority carries xsd:integer within the directive domain; confidence and recorded_at are typed as xsd:decimal and xsd:dateTime respectively in the measurement domain; duration_seconds, end_time, exit_code, and host_name in the service trace domain are mapped to xsd:decimal, xsd:dateTime, xsd:integer, and xsd:string. The attr type enforces semantic discipline at the schema level, ensuring that a boolean flag such as mandatory is stored as true or false rather than an arbitrary string, and that a timestamp like 2023-05-19T07:46:35 is validated against the xsd:dateTime format rather than treated as free text.

An entity is a reference from one record to another, establishing a directed relationship that encodes organizational or causal structure. In the directive supersedes model, entity_id values such as DIRE-0001 and DIRE-0002 appear in value tables to indicate which directive record a particular attribute value belongs to, while attr_id values like DIRE-0003 and DIRE-0001 resolve back to the attribute definition that governs the value's semantics. The service trace domain similarly uses entity_id to bind typed values—such as the decimal 4381.06 or the integer 744—to the trace record SERV-0001, which itself describes the relationship between the trace ci-cd-deploy-run and the in-service component kafka-cluster-east. This entity-level indirection decouples value storage from definition, allowing a single attribute definition to be reused across many entity instances without duplication.

The misc category captures heterogeneous, unstructured, or semi-structured values that do not conform to the strict XSD typing applied to core attributes. Within the directive domain, misc values include the string "audit excerpt" and the two-character code "en" stored against attribute identifiers DIRE-0008 and DIRE-0009; in the measurement domain, misc values encompass "Dimension Kind 01", "Encoding 02", "intake form", and the language tag "fr" bound to artifact attributes ARTI-0002 through ARTI-0010; in the service trace domain, misc values include "node-b14", "Log Level 02", "initiation", and "failed" associated with attributes SERV-0004 through SERV-0010. These misc values serve as the catch-all for metadata that is essential to operational context—environmental identifiers, log levels, procedural notes, and localization codes—yet does not require the type enforcement or query semantics of structured attributes. Their presence in varchar-typed value tables reflects a pragmatic design choice: not all operational metadata is uniform, and the schema accommodates this variance without compromising the integrity of typed attributes.
