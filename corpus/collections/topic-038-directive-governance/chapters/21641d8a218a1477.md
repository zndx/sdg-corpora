# Modeling Audit Processes and Evidence Linkage

This chapter presents five relational tables that instantiate core ontological distinctions among processes, artifacts under audit, and evidence-producing or findings-bearing relations. The tables are derived directly from the supplied axioms and support cross-table joins that recover multi-hop dependencies such as “which verification process produced evidence for a dataset later referenced by an audit finding.”

## 1. Basic Audit Processes

Axiom 1 classifies any process instance as an audit activity; table t_audit_basic therefore stores only the identifier and the process class name, with id serving as the primary key that later tables may reference.

```sql
CREATE TABLE t_audit_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| AB-001 | AnnualComplianceAudit |
| AB-002 | QuarterlyDataReview |
| AB-003 | EmissionsVerification |
| AB-004 | SafetyIncidentAudit |

## 1.1 Datasets Placed Under Audit

Axiom 2 asserts that certain artifacts stand in the underAudit relation to a process. Table t_dataset_under_audit therefore records each artifact class; its id column functions as the primary key referenced by foreign keys in verification and findings tables.

```sql
CREATE TABLE t_dataset_under_audit (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| DS-101 | SolarOutputReport2023 |
| DS-102 | EmissionsLogQ4 |
| DS-103 | EquipmentCalibrationSet |
| DS-104 | PersonnelTrainingRecords |
| DS-105 | IncidentNarrativeArchive |

## 1.2 Verification Processes Requiring Evidence

Axiom 3 requires every verification process to produce at least one evidence artifact. Table t_verification_min_one_evidence therefore carries a mandatory foreign key y that must resolve to a row in t_dataset_under_audit; id remains the primary key.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_dataset_under_audit(id)
);
```

| id | x | y |
|----|---|----|
| VM-010 | DataVerificationProcess | DS-101 |
| VM-011 | DataVerificationProcess | DS-102 |
| VM-012 | CalibrationVerification | DS-103 |
| VM-013 | TrainingRecordVerification | DS-104 |

A reader can obtain the artifact class for any verification by joining on y = t_dataset_under_audit.id.

## 1.3 Classification Processes

Axiom 4 introduces classification as an independent process category. Table t_classification_basic therefore mirrors the structure of t_audit_basic, again using id as primary key.

```sql
CREATE TABLE t_classification_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| CB-020 | RiskClassification |
| CB-021 | DataSensitivityClassification |
| CB-022 | EquipmentStatusClassification |
| CB-023 | PersonnelCompetencyClassification |

## 1.4 Audits That Record Findings

Axiom 5 states that an audit process may possess findings that reference an audited dataset. Table t_audit_with_findings therefore contains a non-null foreign key y into t_dataset_under_audit; id is again the primary key.

```sql
CREATE TABLE t_audit_with_findings (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_dataset_under_audit(id)
);
```

| id | x | y |
|----|---|----|
| AF-030 | AnnualComplianceAudit | DS-101 |
| AF-031 | QuarterlyDataReview | DS-102 |
| AF-032 | EmissionsVerification | DS-102 |
| AF-033 | SafetyIncidentAudit | DS-105 |

## 2. Cross-Table Query Example

To retrieve every verification process together with the dataset it examined and any audit finding recorded against that same dataset, the following mental join path is used:

1. Start at t_verification_min_one_evidence.y  
2. Match t_dataset_under_audit.id  
3. Continue from t_dataset_under_audit.id to t_audit_with_findings.y

Execution on the populated rows yields:

- VM-010 → DS-101 → AF-030 (AnnualComplianceAudit examined SolarOutputReport2023 and recorded a finding)  
- VM-011 → DS-102 → AF-031 and AF-032 (two separate audits referenced the same EmissionsLogQ4 after verification)

No other combinations satisfy the foreign-key constraints.
