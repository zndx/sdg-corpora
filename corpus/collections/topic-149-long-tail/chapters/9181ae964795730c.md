# Chapter 4: Governance of eBPF Artifacts and Kernel Hook Constraints

This chapter establishes the formal governance framework for the deployment and management of extended Berkeley Packet Filter (eBPF) artifacts within controlled kernel environments. It delineates the structural constraints governing the attachment of eBPF programs to kernel hooks, ensuring system stability, security compliance, and operational integrity. The definitions provided herein serve as the authoritative reference for system architects, security auditors, and compliance officers responsible for validating kernel-level instrumentation.

## 1. Single-Program Attachment Constraints

The integrity of kernel execution flow relies on strict resource management and the prevention of race conditions during instrumentation. A fundamental constraint within this governance framework is the limitation of hook utilization to a single active program instance. This restriction ensures that critical execution paths within the kernel are not subjected to conflicting logic or simultaneous modification by multiple independent eBPF artifacts. The axiom `kernelhook_max_one_program_attached` formalizes this requirement, asserting that any artifact functioning as a kernel hook may possess a maximum of one attached program. This cardinality constraint is essential for maintaining deterministic behavior in kernel subsystems where order of operations is paramount.

In practice, this constraint functions as a mutex on the hook point. When a program is successfully attached to a target hook, the hook is considered "occupied." Subsequent attempts to attach additional programs to the same hook must be rejected by the verifier or the loading subsystem. This mechanism prevents the "hook stacking" problem, where multiple programs attempt to intercept or modify the same function call, potentially leading to kernel panics, data corruption, or undefined behavior. The governance model treats the hook-program pair as a singular, atomic unit of deployment.

## 2. Program-Hook Attachment Topology

For an eBPF artifact to function, it must establish a valid topological relationship with a kernel hook. This relationship is not merely functional but ontological; the program is defined by its capacity to attach to a hook. The axiom `ebpfprogram_attaches_kernelhook_xref` captures this existential dependency, asserting that any valid eBPF program artifact must, by definition, attach to some kernel hook artifact. This cross-reference ensures that floating or orphaned programs—bytecode compiled without a designated target point—are rejected as non-compliant during the static analysis phase.

This section defines the registry of valid attachment points. The topology is governed by the system call interface and internal kernel function tracepoints. Every program loaded into the kernel must reference a valid hook identifier. This reference acts as a foreign key in the broader system architecture, linking the executable bytecode to the static location within the kernel source where it will be triggered. The governance framework mandates that this linkage be explicit and verifiable before the program is loaded into the kernel memory.

## 3. Subclass Restrictions and Hook Typing

While general attachment capabilities are necessary, they are not sufficient for a granular security policy. The governance framework requires that programs be classified according to the specific types of hooks they utilize. The axiom `ebpfprogram_subclass` provides this specificity, asserting that a program artifact attaches to a specific class of hook (Y). This distinction allows the framework to differentiate between a program designed for a kprobe (dynamic kernel instrumentation) and one designed for a tracepoint (static static instrumentation). By subclassifying the attachment relationship, the system enforces type safety and ensures that programs are only loaded into environments compatible with their designated hook class.

This classification is critical for maintaining the stability of the kernel. Different hook classes have different execution contexts, API restrictions, and performance characteristics. For instance, a program written for a socket filter may not safely execute in the context of a kprobe due to differences in the memory structures available at the trigger point. The ontology formalizes this by requiring the declaration of the target hook class (Y) for every program (X). This enables automated auditing tools to verify that the program's bytecode conforms to the constraints of the specified hook class.

## 4. Strict Attachment Policies

In high-security environments, permissive attachment policies often present unacceptable risks. To mitigate these risks, the governance framework supports strict attachment policies that constrain a program to a single, specific hook type. The axiom `ebpfprogram_only_attached_to_kprobe` defines such a policy, asserting that a specific class of programs (X) attaches *only* to the Kprobe hook class (Y). This universal restriction ensures that the program cannot be repurposed or migrated to a different hook type, such as a Tracepoint or a Socket Filter, either maliciously or accidentally.

This "only" restriction is a powerful tool for confinement. It guarantees that the program's execution context is strictly bounded by the capabilities and limitations of the Kprobe infrastructure. For example, a security audit tool designed to inspect function arguments via Kprobes must be prevented from attaching to a Tracepoint, where the argument layout might differ, potentially leading to misinterpretation of data or information leakage. By enforcing this axiom, the system architect can define a security perimeter around the program, ensuring it operates exclusively within the intended instrumentation domain.
