# Chapter 4: eBPF Artifact Governance and Kernel Hook Constraints

## 4.1 Scope and Preamble

This chapter delineates the formal constraints governing the deployment, attachment, and classification of Extended Berkeley Packet Filter (eBPF) artifacts within the kernel subsystem. The definitions provided herein establish a rigid ontological framework for ensuring system stability, security compliance, and operational integrity. The text maps abstract ontology axioms to concrete relational schemas, providing the necessary evidence structures for audit verification. All kernel instrumentation activities must adhere to the cardinality and typing constraints defined in the subsequent sections to prevent resource contention and unauthorized execution flow modification.

## 4.2 Uniqueness Constraints on Kernel Hook Attachments

### 4.2.1 Definition and Rationale

The fundamental unit of kernel instrumentation is the hook, a specific point in the kernel code execution path where external logic may be injected. To maintain system stability and deterministic behavior, the governance framework mandates a strict uniqueness constraint for specific hook classes. This constraint is derived from the axiom that a Kernel Hook artifact ({X}) may have a maximum of one ({Y}) attached program at any given instance.

This restriction serves the dual function of preventing logic collisions between competing instrumentation routines and ensuring that the execution overhead at the hook point remains bounded. In the context of a compliance audit, this constraint is critical for verifying that no unauthorized "piggybacking" of programs has occurred on a secured hook. If a hook is already occupied by a valid program artifact, any subsequent attachment request must fail or trigger a specific override workflow that is logged and audited.

### 4.2.2 Relational Mapping

The uniqueness constraint is materialized in the relational schema through the table `t_kernelhook_max_one_program_attached`. This table functions as a state registry, documenting the valid pairing of a specific hook instance with a single program instance. The primary key is the identifier (`id`), while the columns `x` and `y` represent the hook artifact and the attached program artifact, respectively.

### 4.2.3 Audit Verification Procedure

Auditors must query the `t_kernelhook_max_one_program_attached` table to validate that for any given value of `x` (the hook), there is no more than one corresponding active value of `y` (the program). The presence of duplicate `x` entries with different `y` values indicates a critical violation of the kernel hook isolation policy and necessitates immediate remediation.

## 4.3 Attachment Existence and Cross-Reference

### 4.3.1 Definition and Rationale

While the previous section constrained the cardinality of attachments, this section addresses the existential requirement of the relationship. An eBPF Program artifact ({X}) is defined by its intrinsic capability to attach to a hook artifact. This is a necessary condition for the program to be considered functional within the system. A program binary that exists in storage but lacks a defined attachment target is operationally inert and, in a strict governance context, may constitute a violation of storage policies or a potential security risk (e.g., dormant code awaiting activation).

The axiom `ebpfprogram_attaches_kernelhook_xref` formalizes this by stating that the Class {X} (eBPF Program) is a subclass of Artifact that attaches to Hook some Artifact. This relationship ensures that every active program in the registry can be traced to a valid interception point within the kernel.

### 4.3.2 Relational Mapping

The cross-reference is maintained in the `t_ebpfprogram_attaches_kernelhook_xref` table. This schema acts as a directory of all programs that possess the capability and authorization to attach to a hook. Unlike the attachment state table in Section 4.2, this table represents the *potential* for attachment defined by the program class and configuration.

### 4.3.3 Compliance Validation

During a compliance audit, the `t_ebpfprogram_attaches_kernelhook_xref` table is used to verify that no "orphan" programs exist—programs that are loaded into the kernel verification subsystem but lack a defined target hook. Furthermore, this table serves as the foreign key source for validating the `y` column in the attachment state tables described in Section 4.2. A program appearing in the active state tables must possess a corresponding entry in this cross-reference table to be considered compliant.

## 4.4 Class-Level Attachment Definitions

### 4.4.1 Definition and Rationale

The governance framework distinguishes between specific instances of hooks and programs and their taxonomic classes. This section defines the structural relationship between the class of the eBPF Program ({X}) and the class of the Hook ({Y}) to which it attaches. The axiom `ebpfprogram_subclass` posits that {X} is a subclass of Artifact that attaches to hook {Y}.

This abstraction allows the security policy to govern broad categories of instrumentation rather than individual instances. For example, a policy may dictate that "All Kprobe Programs" (Class X) must attach to "Kprobe Hooks" (Class Y). This class-level typing prevents type mismatches, such as attempting to attach a network socket filter to a tracepoint designed for scheduling events. Enforcing these class constraints ensures that the kernel's Application Binary Interface (ABI) contracts are respected, preventing kernel panics or undefined behavior resulting from improper context access.

### 4.4.2 Relational Mapping

The logical structure of these class relationships is captured in the `t_ebpfprogram_subclass` table. This table maps the program class (`x`) to the specific hook class (`y`) it is designed to engage with. The `NOT NULL` constraint on the `y` column enforces the requirement that every program class must have a defined target hook class.

The following data matrix exhibits the valid class mappings currently enforced by the system's runtime verification engine.

| `map_002` | `TracepointProgram` | `TracepointHook` | v1.2 | Standard |

### 4.4.3 Policy Enforcement

The data in `t_ebpfprogram_subclass` is utilized by the kernel's verifier module. When a program of class `X` attempts to load, the verifier consults this table to ensure the target hook is of class `Y`. If a program of class `SocketFilterProgram` attempts to attach to a hook of class `KprobeHook`, the operation is rejected, and a violation event is logged. This strict typing is essential for maintaining the integrity of the kernel's internal API surface.

## 4.5 Restricted Attachment Targets

### 4.5.1 Definition and Rationale

The final constraint layer introduces the concept of exclusivity in attachment targets. The axiom `ebpfprogram_only_attached_to_kprobe` asserts that a specific Program Class ({X}) attaches *only* to a specific Hook Class ({Y}). This is a more restrictive form of the definition provided in Section 4.4.

This constraint is typically applied to high-security contexts where a program class must be isolated from the broader kernel surface. For instance, a specific class of security auditing programs might be restricted to attaching *only* to Kprobe hooks and explicitly forbidden from attaching to Tracepoints or Socket hooks, even if those other hooks technically offer compatible data contexts. This limitation reduces the attack surface of the instrumentation framework itself, ensuring that powerful program classes cannot be repurposed for unintended instrumentation points.

### 4.5.2 Relational Mapping

The `t_ebpfprogram_only_attached_to_kprobe` table enforces this exclusivity. It identifies program classes (`x`) that are legally bound to a single, specific hook class (`y`). The relational integrity of this table ensures that if a program class is listed here, no other hook class relationships may exist for that program class.

### 4.5.3 Governance and Audit

For governance purposes, the `t_ebpfprogram_only_attached_to_kprobe` table acts as a deny-list for all hook classes not explicitly named in column `y`. During an audit, the system must confirm that for every entry in this table, no attachment records exist in the active state tables (Section 4.2) where the program class `x` is associated with a hook class other than `y`.
