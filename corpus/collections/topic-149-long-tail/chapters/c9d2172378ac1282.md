# Chapter 4: Kernel Artifact Attachment Constraints and Hook Governance

## 4.1 Scope and Preamble

This chapter delineates the structural governance of eBPF artifacts within the kernel subsystem, specifically addressing the ontological constraints governing program attachment to kernel hooks. The definitions provided herein establish the formal boundaries for artifact interaction, ensuring that kernel instrumentation adheres to strict safety and isolation protocols. We examine the cardinality limitations between hooks and programs, the existential requirements for valid attachment, and the taxonomic classifications that dictate permissible hook types. These constraints are not merely theoretical; they represent the operational reality of a secure kernel environment, where improper attachment can lead to system instability or security violations. The following sections detail the specific axioms governing these relationships, supported by relational schema projections that serve as the evidence base for compliance verification.

## 4.2 Kernel Hook Cardinality and Single-Program Attachment

The first constraint governing kernel instrumentation addresses the cardinality of the relationship between a kernel hook and an attached eBPF program. In a secured environment, a specific kernel hook instance must not serve as a conduit for multiple concurrent eBPF programs. This restriction, defined by the axiom `kernelhook_max_one_program_attached`, is critical for preventing race conditions and ensuring deterministic execution paths within the kernel. When a hook is triggered, the execution flow must be predictable; allowing multiple programs to attach to a single hook instance could result in stack corruption, undefined return value modifications, or uncontrolled latency spikes.

The axiom formally states that for any Class X, which is a subclass of `cco:Artifact`, the relationship `sdg:hasAttachedProgram` must have a maximum cardinality of 1 for Class Y. This implies that while a hook may exist in a dormant state without an attached program, it may never host more than one active program instance simultaneously. This governance model treats the hook as a dedicated resource, singularly allocated to a monitoring or modification task.

The `x` column represents the hook artifact instance (the holder), and the `y` column represents the program artifact instance (the attached entity). The data illustrates a 1:1 mapping, confirming that no hook identifier is repeated with a different program identifier.

## 4.3 Existential Attachment Requirements

Moving beyond cardinality, the governance framework mandates that valid eBPF program artifacts must demonstrate an active attachment to a kernel hook. An eBPF program that is loaded into the kernel but remains detached from any hook is functionally inert and consumes memory resources without contributing to the observability or security posture. The axiom `ebpfprogram_attaches_kernelhook_xref` establishes this existential requirement: Class X (a subclass of `cco:Artifact`) must possess the property `sdg:attachesToHook` with a value of some `cco:Artifact`.

This axiom serves as a validation check for the utility of the artifact. If a program is defined as an eBPF program, it *must* attach to something. This relationship is existential; it asserts the existence of a connection without specifying the nature or type of the target hook beyond its classification as an artifact. In the context of system auditing, this ensures that "orphan" programs—those loaded but not attached—are flagged for removal or reconfiguration.

The column `x` contains the identifier of the program artifact. This table functions as a cross-reference list, confirming that the listed program instances are actively bound to the kernel's execution path.

As evidenced in Table 4.2, each program instance listed (e.g., `kprobe_do_sys_open`) is confirmed to have an established attachment relationship. From a governance perspective, the absence of a program from this table—despite its presence in the system's object file inventory—would indicate a deployment failure or a misconfiguration in the loader logic. The `ebpfprogram_attaches_kernelhook_xref` table provides the necessary evidence that the artifact is not merely resident in memory but is operationally integrated into the kernel subsystem.

## 4.4 Taxonomic Classification of Hook Attachments

While the previous section established that a program must attach to a hook, this section refines the governance model by defining the taxonomic constraints of that attachment. Not all programs are compatible with all hooks; specific program classes are designed to interface with specific hook classes. The axiom `ebpfprogram_subclass` formalizes this by stating that Class X (a subclass of `cco:Artifact`) attaches to a hook of Class Y. This is a specialization constraint that dictates the permissible topology of the instrumentation landscape.

For example, a program designed to intercept network packets at the socket layer (a `SocketFilter`) is structurally incapable of attaching to a kprobe (a `Kprobe`). The ontology enforces this by defining the `sdg:attachesToHook` relationship with a specific target class Y. This classification is essential for automated validation tools, which can prevent a program from loading if its target hook class does not match the available hook points in the kernel. It reduces the risk of runtime errors where a program attempts to read memory structures or context data that are specific to a different hook type.

Table 4.3 illustrates the instantiation of this subclass axiom. The primary key is `id`. The column `x` represents the Program Class, and the column `y` represents the Hook Class to which programs of type X are permitted to attach. The foreign key structure here is conceptual; the values in `x` and `y` refer to class definitions defined elsewhere in the ontology.

**Table 4.3: eBPF Program Subclass Hook Compatibility**

| id | x | y |
| :--- | :--- | :--- |
| CLASS-MAP-201 | KprobeProgram | KprobeHook |
| CLASS-MAP-202 | TracepointProgram | TracepointHook |
| CLASS-MAP-203 | SocketFilterProgram | SocketHook |
| CLASS-MAP-204 | CgroupSkbProgram | CgroupSkbHook |
| CLASS-MAP-205 | RawTracepointProgram | RawTracepointHook |

The data in Table 4.3 provides the schema-level rules for attachment compatibility. The row with `id` `CLASS-MAP-201` asserts that the `KprobeProgram` class attaches to the `KprobeHook` class. This mapping is deterministic. If a system auditor encounters an instance of `KprobeProgram` attempting to attach to a `TracepointHook`, they can reference this table to confirm the violation of the `ebpfprogram_subclass` axiom. This level of formal definition allows for static analysis of eBPF bytecode before it is loaded into the kernel, ensuring that the program's attachment logic aligns with the structural definitions of the target environment.

## 4.5 Exclusive Attachment Constraints

The final constraint addressed in this chapter pertains to the exclusivity of attachment. While the previous section defined which classes *can* attach, this section defines which classes *must only* attach to specific targets. The axiom `ebpfprogram_only_attached_to_kprobe` utilizes a universal quantification (`only`) to state that Class X attaches to hook Class Y exclusively. This is a stricter constraint than the subclass relationship; it implies that if a program belongs to Class X, it is forbidden from attaching to any hook that is not an instance of Class Y.

This constraint is vital for security isolation. Certain program types may operate with elevated privileges or access sensitive data structures that are only safe within the context of a specific hook type. By restricting the attachment scope, the system limits the attack surface. For instance, a program designed to function strictly within a Kprobe context should not be allowed to attach to a generic tracepoint, as the memory context and safety guarantees may differ, potentially leading to information leakage or kernel panics.

Table 4.4 represents the relational schema for this exclusive attachment axiom. The primary key is `id`. The column `x` denotes the Program Class, and `y` denotes the Hook Class. This table serves as a negative constraint list; it defines the boundary of the program's operational domain.

**Table 4.4: eBPF Program Exclusive Attachment Constraints**

| id | x | y |
| :--- | :--- | :--- |
| EXCL-301 | KprobeProgram | KprobeHook |
| EXCL-302 | UprobeProgram | UprobeHook |
| EXCL-303 | SockOpsProgram | SockOpsHook |
| EXCL-304 | SkMsgProgram | SkMsgHook |
| EXCL-305 | LircMode2Program | LircHook |

Reviewing Table 4.4, the constraint `EXCL-301` dictates that `KprobeProgram` attaches *only* to `KprobeHook`. This means that while a `KprobeProgram` is a subclass of artifact that attaches to a hook, its attachment universe is restricted solely to `KprobeHook`. It cannot attach to `TracepointHook`, `SocketHook`, or any other class. This axiom is crucial for maintaining the semantic integrity of the eBPF verifier logic. By enforcing these exclusive relationships, the governance framework ensures that the behavioral expectations of a program class are never mismatched with the execution environment of a disparate hook class.
