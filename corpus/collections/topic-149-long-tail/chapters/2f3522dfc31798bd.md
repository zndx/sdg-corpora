# Chapter 4: Ontological Constraints for eBPF Kernel Instrumentation

This chapter establishes the formal constraints governing the interaction between eBPF programs and kernel artifacts within a compliant system. It defines the structural relationships and cardinality rules that must be enforced to ensure system stability and security integrity. The provisions herein detail the attachment protocols, subclass restrictions, and exclusive binding requirements for kernel-level instrumentation.

## 1. Kernel Hook Single-Program Attachment Constraints

The integrity of kernel instrumentation relies heavily on the strict enforcement of attachment cardinality. To prevent race conditions and resource contention, specific kernel artifacts designated as hooks must adhere to a singular attachment policy. This policy ensures that at any given moment, a specific hook instance is monopolized by a single eBPF program instance, thereby isolating the execution context and deterministic behavior of the instrumentation.

The governing axiom for this constraint is defined as `kernelhook_max_one_program_attached`. It posits that for any artifact `X` acting as a kernel hook, the number of attached programs `Y` must not exceed one. This restriction is critical for maintaining the atomicity of system calls and tracepoints where concurrent modification by multiple agents could result in undefined behavior or kernel panics.

## 2. Program-Hook Attachment Existence Requirements

For an eBPF program to be considered valid and executable within the kernel subsystem, it must demonstrate a verifiable attachment to a recognized kernel hook. This requirement ensures that no "orphan" programs—bytecode loaded into the kernel without a designated trigger point—can consume system resources or execute in an uncontrolled manner. The existence of an attachment relationship is a prerequisite for the activation of any eBPF artifact.

This relationship is captured by the axiom `ebpfprogram_attaches_kernelhook_xref`. It asserts that any class `X` representing an eBPF program must be a subclass of an artifact that attaches to some kernel hook. This existential quantification (`some`) guarantees that the program has a defined purpose and a valid execution context within the kernel's trace infrastructure.

The table below illustrates the `ebpfprogram_attaches_kernelhook_xref` schema. The primary key is `id`, which serves as the unique reference for the attachment record. The column `x` functions as a foreign key referencing the specific eBPF program class that satisfies the attachment requirement.

## 3. Specific Hook Class Binding Protocols

While general attachment establishes that a program is connected to a hook, precise governance requires the definition of *which* specific class of hook a program is designed to engage. This level of specificity is necessary for type checking and compatibility verification during the loading phase. A program intended for a network socket hook, for instance, must not be erroneously attached to a tracepoint designed for file system events.

The axiom `ebpfprogram_subclass` formalizes this by stating that a program class `X` is a subclass of artifacts that attach to a specific hook class `Y`. This relationship allows the system to enforce type safety, ensuring that the program's interface matches the hook's expected signature. It categorizes the program based on the specific family of kernel events it is instrumenting.

## 4. Exclusive Kprobe Attachment Constraints

In high-security contexts, certain instrumentation programs may be restricted to a specific type of hook to prevent misuse or privilege escalation. Specifically, programs designed for dynamic instrumentation (kprobes) may be prohibited from attaching to static tracepoints or other hook types. This restriction ensures that powerful, potentially invasive debugging tools are strictly sandboxed within their designated domain.

The axiom `ebpfprogram_only_attached_to_kprobe` enforces this by defining that a program class `X` attaches to hook class `Y` *only* if `Y` is a Kprobe. This universal quantification (`only`) restricts the range of valid attachments for `X` exclusively to the Kprobe class. Any attempt to link such a program to a non-Kprobe artifact violates the ontological constraints of the system.
