# Chapter 4: Kernel Hook Artifacts and eBPF Program Binding Constraints

This chapter delineates the structural and semantic constraints governing the interaction between eBPF program artifacts and kernel hook artifacts within the system ontology. It provides a formal analysis of the binding mechanisms, cardinality restrictions, and type-specific dependencies that enforce operational integrity. The discussion is grounded in the formal axioms defined in the `04_ebpf_kernel` family, with specific attention to the verification of attachment states and the prevention of logical conflicts in kernel-space instrumentation.

## 1. Kernel Hook Cardinality Constraints

The fundamental unit of kernel instrumentation is the hook artifact, defined formally as a subclass of `cco:Artifact`. To ensure system stability and deterministic behavior, the ontology imposes strict cardinality constraints on the attachment of program artifacts to these hooks. Specifically, the axiom `kernelhook_max_one_program_attached` asserts that any valid kernel hook instance may possess a maximum of one attached program artifact at any given temporal interval. This constraint prevents race conditions and non-deterministic execution flows that could arise from multiple programs attempting to process a single kernel event simultaneously.

In compliance with this axiom, the system enforces a mutex-like locking mechanism at the hook level. When a program artifact is bound to a hook, the hook is considered "occupied." Subsequent attachment requests targeting the same hook instance must be rejected or trigger a replacement workflow, depending on the operational policy. This ensures that the `hasAttachedProgram` property remains within the defined cardinality limit of `max 1`. ### 1.1 Operational Implications of Singular Attachment

The restriction to a single program per hook necessitates rigorous pre-deployment auditing. System architects must ensure that the logic contained within the single attached program (`y`) is comprehensive enough to handle the event signature generated by the hook (`x`). Because the ontology does not permit chaining or multiplexing at the hook layer, any requirement for complex event processing must be resolved within the program artifact itself, or by utilizing multiple distinct hooks. This design choice prioritizes kernel safety over flexibility, reducing the overhead of context switching and minimizing the attack surface exposed by instrumentation logic.

## 2. Existential Attachment Dependencies

The validity of an eBPF program artifact is contingent upon its attachment to a kernel hook. The axiom `ebpfprogram_attaches_kernelhook_xref` establishes an existential dependency, asserting that for a program artifact to be considered valid within the runtime environment, it must attach to some kernel hook artifact. This relationship is modeled as a cross-reference (`xref`) that links the program instance to the hook infrastructure. This axiom serves as a validation gate: an eBPF program that is loaded into memory but not attached to a hook is effectively an orphaned artifact and does not satisfy the criteria for an active instrumentation component.

This existential constraint ensures that resources are not allocated to program artifacts that do not contribute to the observability or security posture of the system. During the loading phase, the verifier checks the `attachesToHook` property. If this property is null or references a non-existent or invalid hook artifact, the loading operation fails. | `prog_ref_103` | `tracepoint_sched_switch` |

| `prog_ref_105` | `xdp_drop_monitor` |

### 2.1 Dependency Resolution and Lifecycle Management

Lifecycle management of eBPF programs is intrinsically linked to the lifecycle of the target hook. If the kernel module providing the hook artifact is unloaded or deprecated, any program artifact dependent on that hook via the `attachesToHook` relationship must be detached or terminated. The ontology treats this as a cascading dependency. The `ebpfprogram_attaches_kernelhook_xref` table acts as the registry for these dependencies, enabling automated compliance tools to audit the system for "dangling" references—programs that are technically loaded but have lost their binding target due to dynamic kernel changes.

## 3. Hook-Type Specificity and Subclassing

While the previous section established that a program must attach to *some* hook, the axiom `ebpfprogram_subclass` refines this by defining the specific class of hook to which a program may attach. This axiom utilizes the `some` restriction to declare that a program artifact (`x`) attaches to a hook belonging to a specific class (`y`). This is a critical distinction for type safety; it prevents a program designed for a tracepoint from being erroneously attached to a kprobe, or a socket filter from being attached to an XDP hook. The class `y` acts as a type constraint, ensuring that the program's interface matches the hook's expected signature.

This classification enables the ontology to model the diverse ecosystem of kernel hooks. By defining specific subclasses such as `Kprobe`, `Tracepoint`, or `Cgroup`, the system can enforce compile-time and load-time checks. The following table demonstrates the subclass relationships, linking specific program artifacts to their designated hook classes. The primary key identifies the specific subclassing rule, while `x` denotes the program and `y` denotes the permissible hook class.

| :--- | :--- | :--- |
| `sub_201` | `generic_kprobe_analyzer` | `Kprobe` |
| `sub_202` | `sched_switch_monitor` | `Tracepoint` |
| `sub_203` | `ingress_traffic_filter` | `Cgroup` |
| `sub_204` | `early_packet_dropper` | `XDP` |
| `sub_205` | `socket_ops_tracer` | `Sockops` |

### 3.1 Semantic Compatibility and Interface Matching

The enforcement of hook-type specificity ensures semantic compatibility. For instance, a program belonging to the subclass that attaches to `XDP` (eXpress Data Path) hooks expects a context structure (`xdp_md`) that is fundamentally different from the context structure provided by a `Kprobe` (struct `pt_regs`). The axiom `ebpfprogram_subclass` encodes this requirement at the ontological level. Auditors can query this table to verify that a program intended for high-performance packet processing (`XDP`) is not mistakenly deployed in a context where deep syscall inspection (`Kprobe`) is required, or vice versa. This classification is essential for maintaining the functional correctness of the instrumentation layer.

## 4. Universal Attachment Restrictions

The most restrictive attachment rule is defined by the axiom `ebpfprogram_only_attached_to_kprobe`. This axiom utilizes the `only` restriction to state that a program artifact (`x`) attaches to a hook *only* if that hook belongs to the specific class `y` (in this context, `Kprobe`). This is a stronger constraint than the subclassing rule; it implies a universal quantification over all possible attachments for that program. Even if the program is theoretically capable of attaching to other hook types via shared interfaces, this axiom restricts its deployment exclusively to the specified class (`y`).

This restriction is typically applied for security-sensitive programs that require strict isolation or for programs that rely on implementation details specific to a single hook type. For example, a program designed to read specific CPU registers using `Kprobe` logic may fail catastrophically or cause a kernel panic if attached to a `Tracepoint`. The table below enumerates program artifacts that are subject to this universal restriction. The schema identifies the restriction rule (`id`), the restricted program (`x`), and the sole permissible hook class (`y`).

| id | x | y |
| :--- | :--- | :--- |
| `only_301` | `kprobe_only_security_audit` | `Kprobe` |
| `only_302` | `kretprobe_return_checker` | `Kretprobe` |
| `only_303` | `raw_syscall_entry_guard` | `Syscall` |
| `only_304` | `specific_kprobe_memory_dumper` | `Kprobe` |
| `only_305` | `kprobe_latency_profiler` | `Kprobe` |

### 4.1 Enforcement and Compliance Verification

Compliance with the `only` restriction is verified during the attachment phase. The system must check that the target hook's class is identical to the class specified in the `ebpfprogram_only_attached_to_kprobe` axiom. Any attempt to attach program `x` to a hook class other than `y` constitutes a violation of the ontology and must be blocked by the verifier. This mechanism provides a robust defense-in-depth strategy, ensuring that highly privileged or unstable program artifacts cannot be repurposed or attached to arbitrary hook points by a compromised user-space process. It effectively locks the program's operational domain to a narrowly defined subset of the kernel's surface area.
