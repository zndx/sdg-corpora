# Chapter 7: Governance of Kernel-Level Artifacts and Attachment Constraints

## 7.1 Scope and Preamble

This chapter delineates the structural and logical constraints governing the interaction between extended Berkeley Packet Filter (eBPF) programs and kernel hook artifacts within the compliance framework. The definitions herein are derived from the formal ontology axioms governing the `cco:Artifact` class hierarchy, specifically addressing the cardinality, attachment, and subclassification rules for kernel-level observability and security components. The objective is to establish a verifiable baseline for auditing kernel extensions, ensuring that program-to-hook bindings adhere to strict existential and universal restrictions. All artifacts referenced in this chapter are treated as distinct entities subject to the governance protocols defined in the relational schemas appended to each section.

## 7.2 Kernel Hook Program Attachment Constraints

### 7.2.1 Definition and Axiomatic Basis

The foundational constraint for kernel hook governance is defined by the axiom `kernelhook_max_one_program_attached`. This axiom asserts that any artifact classified as a Kernel Hook (`X`) must not possess more than one attached program (`Y`) at any given instance. The formal Manchester syntax defines this as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasAttachedProgram max 1 {Y:Class}`.

In practical terms, this constraint enforces a 1:1 cardinality relationship between the hook artifact and the attached program artifact. This limitation is critical for maintaining system stability and ensuring deterministic behavior in kernel space. By restricting the attachment to a maximum of one program, the framework prevents resource contention and simplifies the forensic analysis of execution paths. The `cco:Artifact` superclass serves as the anchor, ensuring that both the hook and the program are recognized as managed entities within the configuration inventory.

### 7.2.2 Implementation and Compliance Data

To verify compliance with this axiom, auditors must examine the binding registry where hook artifacts are mapped to their associated programs. The following table, `t_kernelhook_max_one_program_attached`, represents the current state of verified attachments. The primary key is the unique identifier (`id`), while `x` represents the hook artifact and `y` represents the program artifact.

| :--- | :--- | :--- |

The governance framework mandates that any modification to these bindings must be atomic; detaching `sec_audit_exec_prog` from `sys_enter_execve_hook` must be completed before a new program can be bound.

## 7.3 eBPF Program Attachment Cross-Reference

### 7.3.1 Definition and Axiomatic Basis

The second governance concept addresses the existential requirement for program artifacts. The axiom `ebpfprogram_attaches_kernelhook_xref` establishes that a program artifact (`X`) must be subclassified as an entity that attaches to some kernel hook artifact. The Manchester syntax is expressed as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook some cco:Artifact`.

This axiom serves as a validation rule for the classification of program artifacts. It ensures that any entity registered as an eBPF program possesses the inherent capability and intention to attach to a hook. It does not specify *which* hook, but rather asserts that the relationship `attachesToHook` must exist for at least one artifact in the system. This is a critical distinction for inventory management; an eBPF bytecode blob that is not associated with a hook target fails this subclassification check and is flagged as an orphan or non-compliant artifact.

The following table, `t_ebpfprogram_attaches_kernelhook_xref`, catalogs the program artifacts that satisfy the existential quantification. The schema is simplified to reflect the program entity (`x`) and its unique identifier (`id`), as the axiom focuses on the classification of the program itself rather than the specific target in this context.

**Table 7.2: eBPF Program Attachment Cross-Reference (Existential Constraint)**

| id | x (Program Artifact) |
| :--- | :--- |
| prog_ref_101 | generic_socket_observer |
| prog_ref_102 | cpu_cycle_collector |
| prog_ref_103 | kprobe_syscall_monitor |
| prog_ref_104 | tracepoint_sched_switch |

As shown in Table 7.2, each entry in column `x` represents a distinct artifact that satisfies the condition of attaching to a hook. For instance, `generic_socket_observer` is validated as a compliant `cco:Artifact` because it possesses the `sdg:attachesToHook` property directed at some target. If an audit revealed an artifact `malicious_blob` lacking this property, it would be excluded from the class defined by `ebpfprogram_attaches_kernelhook_xref`. This registry is essential for maintaining the "White List" of active, compliant kernel extensions within the governance framework.

## 7.4 eBPF Program Subclass Specificity

### 7.4.1 Definition and Axiomatic Basis

While the previous section established the general capability to attach, this section defines the specific targeting constraints. The axiom `ebpfprogram_subclass` refines the classification by asserting that a specific program class (`X`) attaches to a specific hook class (`Y`). The Manchester syntax is: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook some {Y:Class}`.

This axiom allows for the granular typing of programs based on their target environment. Unlike the general cross-reference, this axiom creates a strict semantic link between the type of the program and the type of the hook. For example, a program designed for `TracepointHook` artifacts is semantically distinct from one designed for `KprobeHook` artifacts. This distinction is vital for policy enforcement, as it enables the governance framework to apply specific security controls based on the hook class `Y`.

### 7.4.2 Implementation and Compliance Data

The table `t_ebpfprogram_subclass` provides the evidence base for these specific subclass relationships. The schema includes the program (`x`), the target hook class (`y`), and a unique identifier. The `NOT NULL` constraint on column `y` enforces the requirement that the specific target class must be defined for the subclassification to be valid.

**Table 7.3: eBPF Program Subclass Registry (Specific Targeting)**

| id | x (Program Artifact) | y (Hook Class) |
| :--- | :--- | :--- |
| sub_201 | tc_ingress_classifier | TCIngressHook |
| sub_202 | xdp_drop_port_80 | XDPHook |
| sub_203 | raw_tracepoint_sched_switch | RawTracepointHook |
| sub_204 | socket_filter_tcp | SocketFilterHook |
| sub_205 | kprobe_do_sys_open | KprobeHook |

In Table 7.3, the row with `id` `sub_201` explicitly links the program `tc_ingress_classifier` to the hook class `TCIngressHook`. This linkage confirms that `tc_ingress_classifier` is not merely a generic artifact but a specific subclass of `cco:Artifact` designed to interact with Traffic Control hooks. Compliance auditors utilize this table to verify that programs are not deployed on incompatible hook classes. For instance, deploying `xdp_drop_port_80` (an `XDPHook` program) onto a `SocketFilterHook` would violate the semantic constraints implied by this subclassification, resulting in a runtime load failure and a policy violation.

## 7.5 Restrictive Attachment to Kprobes

### 7.5.1 Definition and Axiomatic Basis

The final concept introduces a universal restriction, limiting the attachment scope of a program artifact to a single class of hooks. The axiom `ebpfprogram_only_attached_to_kprobe` asserts that a program artifact (`X`) attaches *only* to a hook artifact of class `Y` (specifically Kprobes). The Manchester syntax is: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook only {Y:Class}`.

This axiom provides the highest level of constraint specificity. It dictates that the set of all valid attachment targets for program `X` is a subset of hook class `Y`. If `X` attempts to attach to any hook outside of class `Y`, the axiom is violated. This is particularly relevant for security-sensitive programs that must be constrained to specific, well-defined instrumentation points to prevent abuse or unintended side effects. It effectively isolates the program to a specific domain within the kernel architecture.

### 7.5.2 Implementation and Compliance Data

The table `t_ebpfprogram_only_attached_to_kprobe` documents the programs that are subject to this restrictive attachment policy. The schema maps the program (`x`) to the exclusive hook class (`y`).

**Table 7.4: Kprobe-Only Program Registry (Universal Restriction)**

| :--- | :--- | :--- |
| kpr_301 | tcp_retransmit_monitor | KprobeHook |
| kpr_302 | do_splice_direct_audit | KprobeHook |
| kpr_303 | security_bprm_check_ctx | KprobeHook |
| kpr_304 | generic_file_read_iter | KprobeHook |
| kpr_305 | ip_queue_xmit_watch | KprobeHook |

Table 7.4 illustrates the strict confinement of program artifacts. The program `tcp_retransmit_monitor` (`x`) is bound exclusively to the `KprobeHook` class (`y`). This governance rule ensures that `tcp_retransmit_monitor` cannot be dynamically retargeted to a `TracepointHook` or `SocketFilterHook`, even if such hooks exist in the system. This restriction is a key control in high-assurance environments, preventing "hook hopping" techniques that might be used to evade monitoring or escalate privileges. Any deviation from the `KprobeHook` class for the listed programs constitutes a critical security breach of the ontology-defined governance model.
