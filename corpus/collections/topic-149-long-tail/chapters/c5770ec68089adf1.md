# Chapter 4: Governance of eBPF Artifacts and Kernel Hook Constraints

## 4.1 Scope and Preamble

This chapter delineates the formal constraints governing the attachment of Extended Berkeley Packet Filter (eBPF) programs to kernel hooks within a secured operating environment. As in-kernel extensibility mechanisms, eBPF artifacts require rigorous validation to ensure system stability, security integrity, and compliance with defined governance frameworks. The following sections detail the ontological axioms that dictate the cardinality, attachment relationships, and type restrictions between eBPF programs (`cco:Artifact`) and their target kernel hooks. These definitions serve as the foundation for automated auditing tools and manual compliance verification protocols, ensuring that all loaded artifacts adhere to the strict structural requirements of the kernel subsystem.

## 4.2 Kernel Hook Cardinality Constraints

The deployment of instrumentation artifacts within the kernel space is subject to strict resource management to prevent race conditions and system instability. The primary constraint governing this relationship is defined by the axiom `kernelhook_max_one_program_attached`. This axiom asserts that any valid kernel hook artifact (Class X) must not exceed a single attached program instance (Class Y) at any given moment. This "max 1" cardinality restriction is critical for maintaining deterministic execution paths and preventing the interference of multiple logic streams on a single execution point.

From a governance perspective, this constraint ensures that hook points are not oversubscribed. When a compliance audit is performed, the artifact registry must be queried to verify that no hook identifier is associated with more than one program identifier. This relationship is modeled to enforce atomicity in the attachment process. The primary key for this verification is the unique identifier of the attachment instance, while the foreign keys reference the specific hook and program artifacts involved.

## 4.3 Cross-Reference Verification for Attachment

To establish the validity of an eBPF artifact, it must be demonstrably linked to a functional kernel hook. The axiom `ebpfprogram_attaches_kernelhook_xref` formalizes this requirement by asserting that any program artifact (Class X) must possess the property of attaching to some hook artifact. This is an existential constraint ("some"), ensuring that orphaned programs—those defined but not attached to a viable execution point within the kernel—are identified as non-compliant or dormant.

This section addresses the verification protocol for the `sdg:attachesToHook` property. In the context of a security audit, this cross-reference table serves as the master index of active instrumentation. It verifies that for every program defined in the artifact repository, there exists a corresponding hook definition. The structure of this data is simplified to focus on the program entity (`x`), as the existence of the hook is implied by the relationship's validity. The primary key (`id`) provides a unique reference for the attachment record.

## 4.4 Specific Hook Type Subclassing

While the previous sections established general attachment rules, granular governance requires defining the specific types of hooks a program class may target. The axiom `ebpfprogram_subclass` refines the relationship by stating that a specific class of eBPF programs (Class X) attaches to a specific class of hooks (Class Y). This specialization allows for the categorization of programs based on their target subsystems (e.g., networking, tracing, security) and enforces that the program logic is compatible with the hook's interface.

This distinction is vital for compliance frameworks that mandate separation of concerns. For instance, a program designed for a `Tracepoint` hook must not be erroneously classified as attaching to a `Kprobe` hook if the interface definitions differ. The relational schema captures this by linking the program class directly to its authorized hook class. The primary key (`id`) uniquely identifies the subclassing rule, while `x` and `y` denote the specific program and hook classes involved.

The mapping in Table 4.3 demonstrates that the `TCClassifierProgram` class is strictly associated with the `TcIngressHook` class. This ensures that during the compilation and loading phases, the verifier can reject any `TCClassifierProgram` instance that attempts to load against a `KprobeHook`. Such strict typing prevents interface mismatches and ensures that the program's context assumptions (e.g., register layout, argument availability) are valid for the target hook.

## 4.5 Exclusive Attachment Constraints

The highest level of restriction in the attachment ontology is defined by the axiom `ebpfprogram_only_attached_to_kprobe`. This axiom utilizes a universal restriction ("only") to assert that a specific program class (Class X) may attach *exclusively* to one specific type of hook (Class Y), and to no other. This constraint is typically applied to high-security contexts or specialized instrumentation where the program's logic is inextricably bound to the specific behavior of a single hook type, such as a Kprobe.

This constraint serves as a positive enforcement mechanism for isolation. By defining that a program attaches *only* to a `Kprobe`, the system explicitly forbids attachment to Tracepoints, Uprobes, or Socket Filters. This is particularly relevant for security modules that must not be bypassed or repurposed for other event types. The relational representation of this axiom links the program to the exclusive hook class. The primary key (`id`) identifies the constraint instance, while `x` and `y` define the exclusive relationship.

This ensures that the monitoring logic, which may rely on specific CPU register states exposed only by Kprobes, cannot be inadvertently deployed in an incompatible context, thereby preserving the reliability of the telemetry data collected.
