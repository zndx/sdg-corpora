# Chapter 4: Governance of eBPF Artifacts and Kernel Hook Constraints

## 4.1 Scope and Preamble

This chapter delineates the structural constraints governing the interaction between extended Berkeley Packet Filter (eBPF) programs and kernel hooks within the artifact ontology. It establishes the axiomatic boundaries for attachment, cardinality, and subclass relationships to ensure system stability and auditability. The definitions provided herein are derived from formal OWL ontologies and are mapped to relational schemas to facilitate rigorous compliance checking and inventory management. Administrators and security architects must utilize these constraints to validate that kernel instrumentation does not violate isolation principles or introduce resource contention.

## 4.2 Cardinality Constraints on Kernel Hooks

### 4.2.1 The Single-Attachment Axiom

To maintain kernel integrity and prevent race conditions during instrumentation, the ontology defines a strict cardinality constraint for kernel hooks. The axiom `kernelhook_max_one_program_attached` asserts that any artifact functioning as a Kernel Hook (Class X) must not have more than one attached eBPF program (Class Y). This constraint is formalized in the Manchester syntax as `SubClassOf: cco:Artifact, sdg:hasAttachedProgram max 1 {Y:Class}`.

In practical terms, this regulation mandates that a specific tracepoint or kprobe can serve as the anchor for exactly one active program artifact at any given time. This limitation is critical for deterministic behavior in high-assurance environments. Allowing multiple programs to attach to a single hook simultaneously can lead to unpredictable execution order, data corruption, or kernel panics. Consequently, the governance framework requires that any attempt to load a program onto a hook that is already occupied must be rejected by the verification layer.

### 4.2.2 Implementation and Verification

The following data table, `t_kernelhook_max_one_program_attached`, provides the relational representation of this axiom. The primary key is the identifier (`id`), while columns `x` and `y` represent the specific instances of the Kernel Hook and the attached Program, respectively. This table serves as the source of truth for audit logs verifying that the `max 1` constraint is not violated in the running kernel image.

Table 4-1: Kernel Hook Single-Attachment Registry

| id | x (Kernel Hook) | y (Attached Program) |
| :--- | :--- | :--- |
| hook-001 | sys_enter_execve | exec_monitor_sandbox |
| hook-002 | tcp_v4_rcv | net_filter_ingress_v1 |
| hook-003 | do_fork | process_creation_audit |
| hook-004 | sched_switch | cpu_latency_tracker |

As evidenced in Table 4-1, each hook instance (`x`) is mapped to a singular program instance (`y`). For instance, the hook `sys_enter_execve` is exclusively associated with `exec_monitor_sandbox`. The governance framework must query this table prior to loading new artifacts to ensure the target hook is not currently listed in column `x`.

## 4.3 Existential Dependency of Program Artifacts

### 4.3.1 The Attachment Requirement

The second foundational concept addresses the validity of the eBPF program artifact itself. The axiom `ebpfprogram_attaches_kernelhook_xref` establishes that an eBPF program (Class X) is not a valid, standalone artifact in the operational sense unless it attaches to a hook. This is expressed via the existential quantifier `attachesToHook some cco:Artifact`.

This axiom functions as a validity check. An eBPF program compiled into bytecode but not loaded onto a specific kernel hook is effectively inert and does not contribute to the runtime behavior of the system. However, within the ontology, the definition of the program class is intrinsically linked to its capability to attach. Therefore, the cross-reference table must explicitly list all program artifacts that possess the intent and capability to attach to a kernel hook. This ensures that the inventory of "active" security or monitoring components is strictly bounded by those artifacts that have successfully established a connection to the kernel infrastructure.

### 4.3.2 Registry of Active Attachments

The relational schema `t_ebpfprogram_attaches_kernelhook_xref` maintains this registry. The table is structurally simple, consisting of an identifier and the program entity (`x`). The existence of a row in this table confirms that the program artifact satisfies the existential condition of attaching to a hook.

Table 4-2: eBPF Program Hook Attachment Log

| id | x (eBPF Program) |
| :--- | :--- |
| prog-101 | socket_filter_vlan_10 |
| prog-102 | kprobe_syscall_table |
| prog-103 | trace_sched_process_exec |
| prog-104 | cgroup_skb_ingress |
| prog-105 | raw_tracepoint_sched_switch |

The entries in Table 4-2, such as `prog-101` (`socket_filter_vlan_10`), represent artifacts that satisfy the axiom `attachesToHook some cco:Artifact`. If a program artifact exists in the broader repository but is absent from this table, it is deemed detached or non-operational under the current governance policy.

## 4.4 Typed Attachment Relations

### 4.4.1 Specific Hook Binding

While the previous section established that a program *must* attach to a hook, this section refines that relationship by defining *what kind* of hook a specific class of program attaches to. The axiom `ebpfprogram_subclass` utilizes a restricted existential quantifier: `SubClassOf: cco:Artifact, sdg:attachesToHook some {Y:Class}`.

This axiom allows for the categorization of eBPF programs based on their target infrastructure. For example, a "TC Program" class is defined not just by its bytecode, but by the fact that it attaches to a "TC Hook" class. This semantic distinction is vital for automated policy enforcement. It prevents a program designed for a Tracepoint from being erroneously loaded onto a Kprobe, a mismatch that could result in context mismatch errors or invalid memory access.

### 4.4.2 Class Mapping Registry

The table `t_ebpfprogram_subclass` encodes these class-to-class relationships. The column `x` denotes the specific program class, while `y` denotes the specific hook class it targets. The `NOT NULL` constraint on `y` enforces the requirement that the program class definition must include a target hook class.

Table 4-3: eBPF Program Subclass Hook Mapping

| id | x (Program Class) | y (Hook Class) |
| :--- | :--- | :--- |
| map-01 | TCIngressProgram | TCHook |
| map-02 | SocketFilterProgram | SocketHook |
| map-03 | KprobeProgram | KprobeHook |
| map-04 | TracepointProgram | TracepointHook |
| map-05 | CgroupSKBProgram | CgroupHook |

In Table 4-3, the row with `id` `map-01` defines the `TCIngressProgram`. According to the axiom, this class is valid only if it attaches to an instance of the `TCHook` class. This mapping serves as a schema validation layer for the loading infrastructure, ensuring type compatibility between the program artifact and the target hook artifact.

## 4.5 Restrictive Attachment Domains

### 4.5.1 Universal Constraint on Attachment

The final concept introduces a restriction on the attachment domain using the universal quantifier (`only`). The axiom `ebpfprogram_only_attached_to_kprobe` asserts that a specific class of eBPF program (Class X) attaches *only* to a specific class of hook (Class Y), represented as `SubClassOf: cco:Artifact, sdg:attachesToHook only {Y:Class}`.

This is a stricter constraint than the subclass relationship defined in Section 4.4. While the subclass axiom defines a necessary condition (the program attaches to *some* Y), the restriction axiom defines a closed world. If a program class is governed by this axiom, it is forbidden from attaching to any hook class other than the one specified. This is typically used for high-security contexts where a program must be strictly confined to a specific instrumentation layer to prevent privilege escalation or bypass of security boundaries. For instance, a program designed strictly for Kprobes must be prevented from attaching to Raw Tracepoints, even if the kernel API would technically allow it.

### 4.5.2 Compliance Verification

The relational table `t_ebpfprogram_only_attached_to_kprobe` tracks these restrictive definitions. It lists the program classes (`x`) and the single, exclusive hook class (`y`) to which they are permitted to attach.

Table 4-4: eBPF Program Exclusive Attachment Constraints

| :--- | :--- | :--- |
| cons-01 | KprobeEventProgram | KprobeHook |
| cons-02 | UprobeEventProgram | UprobeHook |

| cons-04 | SkLookupProgram | SkLookupHook |
| cons-05 | LWTIngressProgram | LWTHook |

Table 4-4 demonstrates that `KprobeEventProgram` (`cons-01`) is restricted to the `KprobeHook`. Any attempt to associate an instance of `KprobeEventProgram` with a hook outside of the `KprobeHook` class constitutes a violation of the ontology and the underlying security policy.
