## 4.1 Scope and Preamble

This chapter establishes the formal governance framework for the attachment and classification of Extended Berkeley Packet Filter (eBPF) artifacts within the kernel subsystem. ## 4.2 Kernel Hook Attachment Constraints

### 4.2.1 Definition and Functional Specification

The kernel hook artifact serves the dual function of providing an execution context within the kernel and sealing the attached program logic when it is loaded. According to the axiom `kernelhook_max_one_program_attached`, any valid kernel hook artifact (Class X) must be a subclass of `cco:Artifact` and is constrained to host a maximum of one attached program (Class Y) via the `sdg:hasAttachedProgram` property. This constraint ensures that hook points are not overloaded by concurrent program logic, thereby preserving the atomicity of the instrumentation point.

The hook tool is used to align and firmly hold the program artifact inside the kernel execution context. It serves to seal the program boundary when the bytecode is injected. The tool is reusable, but the constraint `max 1` implies that while the hook instance persists, it may only possess a singular active attachment at any given temporal epoch. This limitation prevents race conditions associated with shared hook points and simplifies the verification of the system's runtime state.

## 4.3 Program-to-Hook Cross-Reference

### 4.3.1 Existential Attachment Requirements

This section details the existential constraints governing eBPF programs. The axiom `ebpfprogram_attaches_kernelhook_xref` defines that a valid eBPF program (Class X) must be a subclass of `cco:Artifact` and must satisfy the condition of attaching to a hook artifact via the `sdg:attachesToHook` property. This is a cross-reference constraint ensuring that no orphaned program artifacts exist within the system registry; every program must be demonstrably linked to a valid hook target.

The variation request for a program artifact must be completed by the kernel subsystem loader. The loader is responsible for verifying that the program class `X` fulfills the requirement of `attachesToHook some cco:Artifact`. This ensures that the program is not merely a static object but an active agent capable of binding to a kernel instrumentation point. Failure to provide a valid cross-reference entry results in a load-time rejection, as the artifact cannot be proven to serve a functional purpose within the kernel context.

## 4.5 Exclusive Attachment Constraints

### 4.5.1 Universal Restriction Definitions

The holder tool is used to align and firmly hold the program inside the kernel. It serves the dual function of restricting the program's scope and sealing the attachment surface when it is verified. The axiom `ebpfprogram_only_attached_to_kprobe` introduces a universal restriction (`only`) on the attachment property. It dictates that a specific program class (X), being a `cco:Artifact`, attaches to hook artifacts of class Y and *only* to class Y.

This constraint is critical for maintaining isolation between different kernel subsystems. For instance, a program designed for Kprobe instrumentation must be strictly prohibited from attaching to Tracepoints or Socket filters. The `only` restriction in the Manchester syntax (`sdg:attachesToHook only {Y:Class}`) provides the logical foundation for this isolation. It ensures that the set of all possible attachments for program X is a subset of hook class Y.
