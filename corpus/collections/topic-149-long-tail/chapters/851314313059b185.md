# Chapter 4: Kernel Hook and Program Attachment Constraints

This chapter establishes the formal governance framework for managing eBPF kernel artifacts, specifically focusing on the axiomatic constraints governing the attachment of programs to kernel hooks. The scope encompasses the definition of artifact capacity, the existential requirements for program attachment, and the restrictive typing of programs based on their target hook classes. The following sections detail the relational logic required to maintain kernel integrity and observability compliance, utilizing a deterministic schema to map ontology axioms to verifiable data structures.

## 4.1 Kernel Hook Capacity Constraints

The kernel hook functions as the primary interface for extending kernel functionality at runtime. It serves the dual function of intercepting execution flow within the kernel and providing a secure mounting point for eBPF programs. The tool is re-useable across different execution contexts, but the integrity of the kernel depends on strict adherence to capacity limitations.

According to the axiom defined by `kernelhook_max_one_program_attached`, any artifact classified as a Kernel Hook (X) must enforce a cardinality restriction where the number of attached programs (Y) does not exceed one. This constraint is modeled in the ontology as `sdg:hasAttachedProgram max 1 {Y:Class}`. This restriction ensures that race conditions and non-deterministic execution paths are minimized at the point of attachment. The hook is used to align and firmly hold the program instruction set inside the execution context and seal the operation boundary when the program is loaded.

This constraint is not merely a suggestion but a structural requirement of the `cco:Artifact` class within the kernel subsystem. The hook acts as a holder tool for the program, analogous to a physical mount used in manufacturing to align components. If a hook attempts to hold more than one program, the system violates the `max 1` restriction, potentially leading to resource contention or undefined behavior.

The following table illustrates the instantiation of this axiom. It lists specific kernel hook instances and the singular program attached to them. The primary key is the unique identifier of the attachment relationship, ensuring that for any given hook instance `x`, only one row exists where `x` is the holder.

## 4.2 Program Attachment Semantics

While the hook defines the capacity, the eBPF program defines the agency of attachment. The axiom `ebpfprogram_attaches_kernelhook_xref` establishes the fundamental existential nature of the eBPF program. Formally expressed as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook some cco:Artifact`, this axiom dictates that for a program to be valid, it *must* attach to at least one hook.

This verbalization implies that {X} is something that attaches to hook artifact. The program cannot exist in a valid state within the runtime system without this relationship. The `some` (existential) quantifier ensures that the class of eBPF programs is defined by their active engagement with kernel hooks. This is a critical distinction from passive artifacts; the program is an active agent that binds to the infrastructure provided by the hook.

In compliance terms, this means that during an audit, any artifact claiming to be an eBPF program must present evidence of a hook attachment. The schema for this axiom is a cross-reference table (`t_ebpfprogram_attaches_kernelhook_xref`), which serves as a registry of all active programs. The structure is simple, consisting of an identifier and the program entity, but the implication is broad: it validates the "active" status of the artifact.

## 4.3 Specific Hook Typing and Subclassing

The relationship between programs and hooks is further refined by the specificity of the target. The axiom `ebpfprogram_subclass` introduces a classification mechanism where the program type is determined by the class of the hook it targets. The Manchester syntax `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook some {Y:Class}` verbalizes to: {X} is something that attaches to hook {Y}.

This axiom allows for the categorization of programs based on their functional domain. For instance, a program attaching to a `Tracepoint` is fundamentally different in nature and capability from one attaching to a `Kprobe` or a `SocketFilter`. The ontology captures this by making the specific hook class {Y} a defining characteristic of the program subclass {X}.

The following table presents the relational mapping for this axiom. It categorizes programs based on the specific hook class they are designed to engage with. This classification is essential for governance frameworks, as different hook classes may be subject to different security policies and stability requirements.

Column `x` denotes the specific program class or instance, while `y` denotes the required hook class. The data indicates that `FunctionLatencyTracer`, for example, is defined by its attachment to the `Kprobe` class. This structure enforces type safety within the kernel extension framework.*

## 4.4 Restrictive Attachment Constraints

The final concept governing this framework is the restriction of attachment to a single, specific hook class. The axiom `ebpfprogram_only_attached_to_kprobe` utilizes the universal quantifier (`only`) to mandate that a specific class of programs may attach *exclusively* to one type of hook. The Manchester syntax is `Class: {X:Class} SubClassOf: cco:Artifact, sdg:attachesToHook only {Y:Class}`.

This verbalization, {X} is something that attaches to hook {Y}, implies a closed-world assumption regarding the attachment targets of {X}. If a program is defined under this constraint, it is forbidden from attaching to any hook that is not an instance of {Y}. This is a stricter requirement than the "some" relationship defined in Section 4.2; while "some" requires at least one, "only" permits no others.

This constraint is particularly relevant for high-security or stability-critical contexts where a program must be guaranteed not to interact with unexpected parts of the kernel. For example, a program designed strictly for `Kprobe` instrumentation must not be erroneously or maliciously attached to a `Tracepoint` or a `Socket` hook. The schema `t_ebpfprogram_only_attached_to_kprobe` enforces this by explicitly linking the program to its sanctioned target class.
