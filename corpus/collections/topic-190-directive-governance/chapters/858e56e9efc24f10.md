# Chapter 7: Ontological Foundations of Compliance Evidentiary Frameworks

This chapter delineates the structural axioms governing the generation, management, and verification of compliance evidence within distributed information systems. It establishes the formal relationships between processual traces, attestation protocols, and data artifacts as defined by the Core Common Ontology (CCO) and the Basic Formal Ontology (BFO). The principles herein are binding for all entities subject to the Digital Governance Act of 2024 and provide the necessary schema for mapping high-level regulatory obligations to low-level system observables.

## 1. Trace Support for Descriptive Claims

### 1.1. Axiomatic Definition of the Evidentiary Trace

In the context of digital forensics and continuous auditing, a "trace" is not merely a log entry but a distinct temporal entity. Under the axioms provided by `trace_supports_claim`, a trace is defined as a subclass of `bfo:0000015` (a process). This processual nature is critical; it implies that the trace has a temporal beginning and end and occupies a specific time interval. The axiom further stipulates that this process bears the specific relationship `sdg:supportsClaim` toward some `cco:DescriptiveICE` (Descriptive Information Content Entity).

Verbalized, the axiom asserts: *{X} is something that supports claim descriptive information content entity.* This establishes a directional dependency where the validity of the descriptive claim (e.g., "The transaction was authorized") is ontologically dependent on the existence of the trace process (e.g., "The authorization handshake was recorded"). In regulatory practice, this means that a compliance claim cannot be considered substantiated unless a corresponding trace process is instantiated within the system's records.

### 1.2. Implementation and Data Schema

To operationalize this axiom, compliance officers must map system logs to the relational structure defined below. The table `t_trace_supports_claim` serves as the registry for these processual entities. The primary key `id` represents the unique identifier for the specific trace instance (the process), while the column `x` denotes the class of the trace (e.g., `AccessLogTrace`, `TransactionAuditTrail`). This structure ensures that every recorded process is explicitly typed as a claim-supporting entity.

The following table embodies Axiom 1 (`trace_supports_claim`). The primary key `id` uniquely identifies the specific trace instance, while `x` categorizes the ontological class of that trace, ensuring it is classified as a process capable of supporting a descriptive claim.

| :--- | :--- |

### 1.3. Audit Implications

When an auditor reviews a system for adherence to access control policies, they query for instances of `SystemAccessTrace`. The existence of the row in the table above confirms that a process occurred which supports the claim "User access was logged." The absence of a row for a specific event time constitutes a violation of the axiom, as the descriptive claim (access occurred) lacks the necessary processual support.

## 2. Attestation and Signatory Authority

### 2.1. The Role of the Agent in Governance

Attestation represents the bridge between automated system processes and human accountability. The axiom `attestation_signed_by` formalizes this by defining a class of processes that are necessarily signed by a `cco:Person`. Unlike generic system events, an attestation process carries legal weight because it is anchored to the agency of a natural person.

The verbalization of the axiom is: *{X} is something that signed by person.* This implies that the process (the attestation) is invalid or incomplete if the `sdg:signedBy` property is not populated with a valid reference to a person entity. In governance frameworks, this prevents the "accountability gap" where actions are executed by service accounts without human oversight.

### 2.2. Registry of Attestation Classes

The relational schema for `t_attestation_signed_by` captures the class of the attestation process. It is distinct from the signature itself; rather, it catalogs the *types* of processes that require a signature. For example, a `RiskAcceptanceAttestation` is a class of process that inherently requires a signatory. By populating this table, the organization defines which business processes fall under the governance requirement of human sign-off.

The following table embodies Axiom 2 (`attestation_signed_by`). The primary key `id` serves as the unique reference for the attestation process definition, and `x` defines the specific class of attestation, ensuring it is recognized as a process requiring a human signatory.

| id | x |
| :--- | :--- |
| ATT-POL-001 | PolicyApprovalAttestation |
| ATT-POL-002 | RiskAcceptanceAttestation |
| ATT-POL-003 | AuditReportSignoff |
| ATT-POL-004 | IncidentClosureAttestation |
| ATT-POL-005 | PrivilegeGrantAttestation |

### 2.3. Compliance Verification

During a compliance audit, the verification engine checks if all instances of `PolicyApprovalAttestation` possess a valid `signedBy` property pointing to a `cco:Person`. If a process instance exists where the signatory is a `SystemAccount` (a non-person class), the axiom is violated. This structure enforces the segregation of duties and ensures that high-impact governance decisions cannot be automated away from human responsibility.

## 3. Column Lineage for Compliance Claims

### 3.1. Data Provenance as an Artifact

Modern data governance regulations, such as GDPR and CCPA, require organizations to demonstrate the provenance of data fields used in decision-making. The axiom `column_lineage_for_compliance_claim` addresses this by defining a class of artifacts (`cco:Artifact`) that support a descriptive claim. Specifically, this refers to the metadata or lineage records that track the transformation of data columns from source to target.

The axiom is verbalized as: *{X} is something that supports claim descriptive information content entity.* Here, `{X}` represents the lineage artifact. For instance, if a compliance claim states "Credit scores were calculated using only zip code and age," the supporting artifact is the column lineage record showing the transformation logic from the raw input columns to the derived score column. Unlike the "trace" in Section 1, which is a process, the lineage entity is an artifact—a dependent continuant that exists as a record of the process.

### 3.2. Lineage Metadata Schema

The table `t_column_lineage_for_compliance_claim` catalogs these artifacts. The `x` column identifies the class of the artifact (e.g., `ETLColumnLineage`, `DataDictionaryEntry`). This registry allows data governors to query which specific artifacts serve as evidence for compliance claims regarding data processing logic. It is essential for automated "right to explanation" workflows, where the system must retrieve the artifact supporting the algorithmic decision.

The following table embodies Axiom 3 (`column_lineage_for_compliance_claim`). The primary key `id` uniquely identifies the lineage artifact, and `x` specifies the class of the artifact, ensuring it is correctly categorized as an information entity supporting a descriptive claim about data transformation.

| :--- | :--- |

| LN-ART-552 | TransformationLogicArtifact |

### 3.4. Regulatory Application

When a regulator challenges the validity of a derived data field, the organization retrieves the record from `LN-ART-552` (TransformationLogicArtifact). This artifact contains the specific SQL or Python code used to derive the field. Because the axiom links this artifact to the claim "The derivation was compliant," the artifact serves as the evidentiary anchor in the defense of the algorithmic model.

## 4. Minimum Signatory Requirements in Attestation

### 4.1. Cardinality Constraints in Governance

While Axiom 2 establishes that an attestation must be signed by a person, it does not specify the quantity of signatories. Axiom 4, `attestation_min_one_signer`, introduces a cardinality constraint. It asserts that the attestation process must be signed by *min 1* `cco:Person`.

The verbalization is: *{X} is a process.* While seemingly simple, the "min 1" qualifier is a powerful logical constraint. It enforces that the set of signatories associated with the attestation process cannot be empty. In ontology-based data validation (OBDA), this constraint triggers a validation error if an attestation process reaches a "completed" state without at least one `signedBy` relation to a person instance.

### 4.2. Enforcing Quorum and Sign-off

The table `t_attestation_min_one_signer` lists the process classes subject to this cardinality rule. This is particularly relevant for "four-eyes principles" or dual-control mechanisms, although the axiom itself specifies a minimum of one. By defining classes such as `MandatoryReviewProcess`, the system enforces that a workflow cannot transition to a closed state until the cardinality constraint is satisfied.

The following table embodies Axiom 4 (`attestation_min_one_signer`). The primary key `id` identifies the specific constrained process instance, and `x` defines the class of the process, ensuring it is subject to the logical constraint of requiring at least one human signatory.

| id | x |
| :--- | :--- |
| ATT-Q-100 | SingleSignerAttestation |
| ATT-Q-101 | MandatoryReviewProcess |
| ATT-Q-102 | SupervisorApprovalProcess |
| ATT-Q-103 | ComplianceOfficerSignoff |
| ATT-Q-104 | DataStewardAttestation |

### 4.3. Workflow Integration

In an automated workflow engine (e.g., BPMN), the transition from the "User Task" node to the "Approved" node is gated by a check against this table. If the process instance `ATT-Q-102` (SupervisorApprovalProcess) attempts to close with zero signatures, the engine references the axiom `min 1 cco:Person` and blocks the transition, throwing a `CardinalityViolationException`. This ensures that governance controls are embedded directly into the execution logic of the information system.

## 5. Kernel Anomalies as Evidentiary Artifacts

### 5.1. Low-Level Artifacts in Security Claims

Security compliance often relies on evidence derived from the lowest levels of the system stack. The axiom `kernel_anomaly_supports_claim` defines a class of artifacts that support descriptive claims regarding system integrity. These artifacts are typically outputs from kernel-level monitoring, such as system call traces, interrupt logs, or memory dump analysis.

The axiom is verbalized as: *{X} is something that supports claim descriptive information content entity.* In this context, the claim is usually a negative assertion, such as "No rootkit was detected" or "The system integrity was compromised." The artifact (the anomaly record) provides the objective evidence for this claim. Because these are `cco:Artifact` instances, they are treated as information-bearing objects rather than processes.

### 5.2. Cataloging Security Evidence

The table `t_kernel_anomaly_supports_claim` maintains the registry of these security-critical artifacts. The `x` column denotes the specific class of the anomaly artifact (e.g., `KernelPanicLog`, `SyscallAnomaly`). This classification allows security information and event management (SIEM) systems to filter low-level noise and focus on artifacts that are formally defined as supporting compliance claims.

The following table embodies Axiom 5 (`kernel_anomaly_supports_claim`). The primary key `id` provides the unique identifier for the anomaly artifact, and `x` classifies the artifact type, ensuring it is recognized as a valid evidentiary object supporting a descriptive claim about system state.
