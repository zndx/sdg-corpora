# Chapter 4: Evidentiary Frameworks and Attestation Protocols in System Governance

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish verifiable links between system artifacts, governance processes, and compliance claims. In accordance with established auditing standards (e.g., ISO/IEC 27001, NIST SP 800-53), the integrity of a control environment relies upon the rigorous mapping of evidentiary data to the assertions they support. The following sections define five critical axioms governing the relationships between trace data, attestations, data lineage, and system anomalies. Each concept is presented with its corresponding relational schema to facilitate implementation within compliance metadata repositories.

## 4.2 Trace Supports Claim

### 4.2.1 Definition and Ontological Basis

The axiom `trace_supports_claim` establishes the fundamental requirement that any processual entity (specifically, a subclass of `bfo:0000015`, or "Process") must function as a supporting artifact for a Descriptive Information Content Entity (`cco:DescriptiveICE`). In practical governance terms, a "trace" is not merely a log file; it is a processual record that provides the evidentiary basis for a specific descriptive claim, such as "User access was revoked" or "Data was encrypted at rest."

The verbalization of this axiom—"{X} is something that supports claim descriptive information content entity"—mandates that the trace cannot exist in a vacuum. It must be ontologically bound to the claim it validates. This binding prevents the accumulation of "orphaned" log data that lacks audit relevance and ensures that storage resources are utilized solely for probative records.

### 4.2.2 Implementation and Evidence Correlation

To operationalize this axiom, auditors must map specific trace classes to the claims they satisfy. For instance, a `LoginSessionTrace` class supports the claim regarding user authentication. ## 4.3 Attestation Signed By

### 4.3.1 Governance and Non-Repudiation

The `attestation_signed_by` axiom defines the authority structure underlying formal attestations. An attestation, defined here as a subclass of `bfo:0000015` (Process), must bear the signature of a `cco:Person`. This requirement is foundational to the principle of non-repudiation. Without a binding to a specific individual, a processual claim lacks legal and procedural standing.

In the context of regulatory frameworks, this axiom ensures that automated processes cannot generate self-validating compliance statements without human intervention. The "signing" action represents the assumption of liability for the accuracy of the attested process. Whether the signature is digital (PKI-based) or wet-ink, the ontological structure remains identical: a link between the attestation process and the person entity.

### 4.3.2 Signatory Attribution

The implementation of this axiom requires a registry where every attestation process is explicitly linked to the class of the person signing it. While the schema below captures the class of the signer (`cco:Person`), operational deployment would typically resolve this to a specific unique identifier (e.g., Employee ID or Distinguished Name).

## 4.4 Column Lineage for Compliance Claim

### 4.4.1 Data Provenance and Transformation

As organizations rely increasingly on automated decision-making, the `column_lineage_for_compliance_claim` axiom becomes vital for data governance. This axiom asserts that a specific artifact—typically a data column or field within a larger dataset—must support a descriptive claim regarding its provenance or transformation state.

This axiom addresses the "black box" problem in ETL (Extract, Transform, Load) pipelines. By requiring that a data column (`cco:Artifact`) supports a claim (`cco:DescriptiveICE`), the ontology enforces transparency. For example, a column labeled `annual_income` in a reporting table must support the claim that it is derived from the summation of `monthly_income` columns in the source system, thereby validating the accuracy of the calculation.

## 4.5 Attestation Min One Signer

### 4.5.1 Cardinality Constraints in Governance

While Section 4.3 established the relationship between an attestation and a signer, the `attestation_min_one_signer` axiom introduces a cardinality constraint. It asserts that any attestation process must be signed by a minimum of one (`min 1`) `cco:Person`. This is a validation rule designed to prevent null-signatory states.

In database terms, this acts as a constraint check prior to the finalization of any governance record. It ensures that an attestation object cannot transition to a "valid" state unless the `signedBy` property is populated with at least one valid person reference. This axiom is particularly relevant in joint control environments where multiple signatures may be required, but a minimum threshold of one is the absolute floor for validity.

## 4.6 Kernel Anomaly Supports Claim

### 4.6.1 Low-Level Evidence Forensics

The final axiom, `kernel_anomaly_supports_claim`, bridges the gap between low-level system operations and high-level compliance reporting. A kernel anomaly (a subclass of `cco:Artifact`) represents a deviation from expected behavior in the operating system kernel, such as a panic, an oops, or an unexpected interrupt.

This axiom posits that such anomalies are not merely system errors but are evidentiary artifacts that support a descriptive claim regarding system stability, security compromise, or failure. For instance, a kernel log indicating a buffer overflow supports the claim "The system was subjected to an exploit attempt." By formalizing this relationship, the ontology allows security information and event management (SIEM) systems to classify kernel-level events as compliance-relevant evidence.
