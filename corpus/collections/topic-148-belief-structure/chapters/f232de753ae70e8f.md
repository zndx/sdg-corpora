# Chapter 4: Axiomatic Mapping of Statistical Metrics to Compliance Directives

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for integrating statistical anomaly detection metrics—specifically those derived from association rule learning—within a rigid compliance governance structure. The content herein delineates the mapping between descriptive information content entities (ICEs), which quantify transactional behaviors, and directive ICEs, which codify regulatory requirements such as the Payment Card Industry Data Security Standard (PCI DSS). As evidenced in the following sections, the relationship between raw statistical lift and regulatory mandates is not merely correlational but is structurally defined through a series of axiomatic constraints. These constraints ensure that every observed metric is anchored to a specific control requirement, thereby facilitating automated audit trails and verifiable evidence chains. The following tables and definitions provide the necessary schema for implementing this mapping within a secure data governance environment.

## 4.2 Descriptive Information Content Entities (Lift Basic)

### 4.2.1 Conceptual Definition

The foundational unit of analysis within this framework is the **Lift Basic** entity. Formally defined by the axiom `lift_basic`, this entity represents a class `X` that is a subclass of `cco:DescriptiveICE`. In the context of transactional auditing, a DescriptiveICE serves as an informational artifact that describes a state of affairs or a pattern of data without prescribing an action. The "lift" metric, borrowed from data mining, quantifies the strength of an association between two variables (e.g., a specific merchant category code and a fraud flag) relative to their expected independence.

When we assert that `X` is a `lift_basic`, we are asserting that `X` is a descriptive information content entity capable of being instantiated as a specific observation. This is distinct from a directive, which would mandate a response. The `lift_basic` entity provides the raw evidentiary basis for further governance actions. It is the "what" of the observation, devoid of the "so what" provided by the regulatory linkage.

### 4.2.2 Relational Implementation

The implementation of the `lift_basic` axiom requires a relational structure that isolates the identifier of the metric from its classification. The primary key serves as the unique reference for the specific lift calculation, while the `x` column denotes the class of the entity being described.

## 4.3 Lift with Baseline Rate

### 4.3.1 Conceptual Definition

While the basic lift entity identifies the existence of a pattern, the **Lift with Baseline Rate** entity provides the necessary context for interpretation. Defined by axiom `lift_with_baseline_rate`, this class `X` asserts that it `hasBaselineRate` some class `Y`. In statistical terms, the baseline rate represents the expected probability of an event occurring in the absence of any specific influencing factors.

Within the ontological structure defined here, the baseline rate is not merely a floating-point numerical value; it is structurally linked to a specific compliance requirement. This linkage ensures that the "normal" state of a system is defined not by arbitrary historical data, but by the specific thresholds mandated by security standards. The axiom posits that `X` (the metric) is subclass of `cco:DescriptiveICE` and possesses a property `sdg:hasBaselineRate` that points to `Y`. In the relational schema, `Y` is realized as a foreign key referencing a requirement, thereby grounding the statistical expectation in regulatory text.

### 4.3.2 Relational Implementation

The schema for `t_lift_with_baseline_rate` enforces a mandatory relationship between the observed lift and a governing requirement. The column `y` is a foreign key referencing `t_pci_dss_requirement`, ensuring that no baseline rate exists in a vacuum; it must be justified by a specific control.

## 4.4 PCI DSS Requirement Mapping

### 4.4.1 Conceptual Definition

The **PCI DSS Requirement** entity functions as the directive counterpart to the descriptive lift entities. Defined by axiom `pci_dss_requirement`, this class `X` is a subclass of `cco:DirectiveICE`, meaning it is an information content entity that prescribes specific behaviors or controls. The axiom further asserts that `X` `pciDssRequirement` some class `Y`.

This relationship creates a bidirectional link between the directive and the descriptive metrics. The requirement `Y` referenced in the schema is, in fact, the `lift_with_baseline_rate` entity. This circular dependency (where the requirement references the lift metric, and the lift metric references the requirement) creates a robust "evidence lock." It signifies that the requirement is operationalized specifically by the metric instance, and the metric instance is validated specifically by that requirement. This structure prevents the decoupling of controls from the data they are intended to monitor.

### 4.4.2 Relational Implementation

The table `t_pci_dss_requirement` serves as the registry for these directives. The foreign key constraint on column `y` ensures that every requirement listed is actively associated with a live monitoring metric (the lift baseline instance).

## 4.5 Lift with Support Count

### 4.5.1 Conceptual Definition

The final component of this framework is the **Lift with Support Count** entity. Defined by axiom `lift_with_support_count`, this class `X` is a subclass of `cco:DescriptiveICE` that `hasSupportCount` some class `Y`. The support count in data mining refers to the frequency or absolute number of times an association rule appears in the dataset.

In a governance context, the support count acts as a materiality filter. A high lift ratio (strong association) is statistically insignificant if the support count is negligible (e.g., it happened only once). By linking the support count to a PCI DSS requirement via the schema, the framework ensures that materiality thresholds are governed by compliance policies. The axiom asserts that the support count property `Y` is not a raw integer but a reference to the requirement that defines the minimum threshold for reporting or action. This ensures that low-frequency anomalies do not trigger unnecessary audit fatigue unless specifically mandated by a directive.

### 4.5.2 Relational Implementation

The `t_lift_with_support_count` table records the specific instances of metrics where support counts are tracked. The foreign key `y` links the support observation to the relevant `t_pci_dss_requirement`, enforcing the rule that materiality is defined by the directive.
