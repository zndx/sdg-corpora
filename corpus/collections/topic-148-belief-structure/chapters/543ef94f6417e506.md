# Chapter 4: Ontological Mapping of Compliance Metrics and Association Rules

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the intersection of statistical association metrics and regulatory compliance frameworks. Specifically, it addresses the integration of data mining concepts—namely "lift" and "support"—within the rigid context of the Payment Card Industry Data Security Standard (PCI DSS). The content herein is structured to provide a precise, evidence-anchored examination of four primary axioms derived from the OWL ontology. These axioms define the relationships between descriptive information content entities and directive mandates, establishing a schema for mapping quantitative security metrics to specific compliance requirements. The following sections present the relational derivations of these axioms, populated with instances representative of a high-assurance audit environment.

## 4.2 Descriptive Information Content Entities

### 4.2.1 Conceptual Framework

The foundational unit of analysis in this framework is the Descriptive Information Content Entity (ICE), denoted by the class `cco:DescriptiveICE`. In the context of the Basic Formal Ontology (BFO), such entities are generically dependent continuants that encode information about a domain of interest. Within the specific scope of this textbook, we are concerned with a subclass of these entities that represent "lift"—a metric used in association rule learning to measure the correlation between two variables, typically security events and control failures.

The axiom `lift_basic` posits that a specific class `X` is a subclass of `cco:DescriptiveICE`. This represents the most primitive form of the metric, devoid of complex attributes such as baseline rates or support counts. It serves as the ontological root for the more complex derivations that follow. In a compliance audit, these basic entities act as the raw data points upon which further statistical validation is performed.

### 4.2.2 Relational Schema and Instances

The relational projection of the `lift_basic` axiom is contained within table `t_lift_basic`. The structure is binary, consisting of a unique identifier (`id`) and the class label (`x`). The primary key (`id`) ensures referential integrity, allowing this entity to be referenced by more complex tables.

The following table enumerates specific instances of basic lift metrics identified during a hypothetical audit of network segmentation controls.

**Table 4.1: Basic Lift Metric Entities**

| id | x |
| :--- | :--- |
| LIFT_B_001 | HighRiskAccessLift |
| LIFT_B_002 | UnencryptedTransmissionLift |

*Table 4.1 Documentation:* The `id` column serves as the persistent unique identifier for the metric entity within the knowledge base. The `x` column represents the specific class name of the Descriptive ICE. These entities describe the observed correlation between specific antecedents (e.g., 'High Risk Access') and consequents (e.g., 'Security Incident').

## 4.3 Lift with Baseline Rate

### 4.3.1 Conceptual Framework

While basic lift entities describe the existence of a correlation, they lack the context necessary for risk prioritization. The axiom `lift_with_baseline_rate` extends the definition of `X` by adding the restriction `sdg:hasBaselineRate some {Y:Class}`. This verbalization asserts that entity `X` possesses a baseline rate defined by entity `Y`.

In the context of PCI DSS auditing, the baseline rate represents the expected frequency of an event in the absence of the specific condition being tested. For instance, if one is analyzing the lift of "Unauthorized Access" given "Missing Firewall Rules," the baseline rate is the general frequency of "Unauthorized Access" across the entire environment. This axiom is critical for distinguishing between genuine risk indicators and statistical noise.

### 4.3.2 Relational Dependencies

The schema for `t_lift_with_baseline_rate` introduces a foreign key constraint that anchors the metric to a regulatory requirement. The column `y` (the baseline rate) is typed as `VARCHAR(255)` and must reference a valid identifier in the `t_pci_dss_requirement` table. This structural constraint enforces the business rule that baseline rates are not arbitrary values but are derived from or defined by specific compliance mandates.

**Table 4.2: Lift Metrics Associated with Baseline Rates**

| id | x | y |
| :--- | :--- | :--- |
| LIFT_BR_001 | WirelessLiftMetric | PCI_REQ_01 |
| LIFT_BR_002 | EncryptionLiftMetric | PCI_REQ_02 |
| LIFT_BR_003 | LoggingLiftMetric | PCI_REQ_03 |
| LIFT_BR_004 | PatchingLiftMetric | PCI_REQ_04 |

*Table 4.2 Documentation:* The `id` column uniquely identifies the lift metric instance. The `x` column denotes the specific lift class. The `y` column functions as a foreign key, linking the metric to its defining baseline rate, which is stored as a PCI DSS requirement entity. For example, `LIFT_BR_001` utilizes the baseline rate defined in `PCI_REQ_01` (pertaining to firewall configuration) to calculate the statistical lift of wireless-related anomalies.

## 4.4 PCI DSS Requirements

### 4.4.1 Conceptual Framework

The directive force within the ontology is embodied by the `pci_dss_requirement` axiom. This axiom defines a class `X` as a subclass of `cco:DirectiveICE`, indicating that it is an information content entity that prescribes specific behavior or states of affairs. The axiom further stipulates that `X` has a `pciDssRequirement` relationship with class `Y`.

This section of the ontology maps the abstract statistical metrics to the concrete text of the PCI DSS standard. It establishes the governance layer, ensuring that the calculation of lift and support is not merely an academic exercise but is strictly bound to the requirements defined by the PCI Security Standards Council.

### 4.4.2 Relational Dependencies and Recursive Structure

The relational schema for `t_pci_dss_requirement` exhibits a complex, recursive dependency. The table consists of an `id`, a directive class `x`, and a requirement property `y`. The foreign key constraint dictates that `y` must reference an identifier in the `t_lift_with_baseline_rate` table.

This creates a cyclical relationship within the data model: `t_lift_with_baseline_rate` references `t_pci_dss_requirement` to establish its baseline, while `t_pci_dss_requirement` references `t_lift_with_baseline_rate` to define the specific metric context for which the directive is applicable. This structure models the interdependence of the control requirement and the measurement mechanism; the requirement defines the baseline, and the metric validates the requirement's efficacy.

**Table 4.3: PCI DSS Directive Entities**

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_01 | FirewallConfigurationDirective | LIFT_BR_001 |
| PCI_REQ_02 | CardholderDataEncryptionDirective | LIFT_BR_002 |
| PCI_REQ_03 | VulnerabilityManagementDirective | LIFT_BR_003 |
| PCI_REQ_04 | SecureCryptographyDirective | LIFT_BR_004 |

*Table 4.3 Documentation:* The `id` column provides the unique reference code for the PCI DSS requirement (e.g., "Req. 1.1.2"). The `x` column describes the nature of the directive. The `y` column references the specific lift metric (from Table 4.2) that is utilized to measure the effectiveness of this directive. For instance, the `FirewallConfigurationDirective` is inextricably linked to the `WirelessLiftMetric`, implying that compliance with this directive is measured via that specific statistical correlation.

## 4.5 Lift with Support Count

### 4.5.1 Conceptual Framework

The final axiom, `lift_with_support_count`, introduces the concept of support into the ontological framework. Support refers to the frequency with which the itemset (the combination of antecedent and consequent) appears in the dataset. The axiom defines class `X` as a subclass of `cco:DescriptiveICE` that possesses a `hasSupportCount` property relating to class `Y`.

In audit analytics, support is a vital filter. A rule may have high lift (strong correlation) but very low support (rare occurrence), which may deprioritize it relative to a high-support, moderate-lift rule. By formalizing this relationship, the ontology allows for the automated filtering of audit findings based on the prevalence of the security event.

### 4.5.2 Relational Dependencies

The schema for `t_lift_with_support_count` mirrors the structure of `t_lift_with_baseline_rate` in its complexity. It contains columns `id`, `x`, and `y`. The foreign key constraint requires that `y` reference an identifier in the `t_pci_dss_requirement` table. This design choice implies that the support count is not merely a raw number but is a value that is validated against or defined by the scope of a specific PCI DSS requirement. This ensures that the support count is relevant to the specific control environment being audited.

**Table 4.4: Lift Metrics Associated with Support Counts**

| :--- | :--- | :--- |
| LIFT_SC_001 | MalwareSupportMetric | PCI_REQ_05 |
| LIFT_SC_002 | PhishingSupportMetric | PCI_REQ_06 |
| LIFT_SC_003 | DataExfiltrationSupportMetric | PCI_REQ_07 |

*Table 4.4 Documentation:* The `id` column uniquely identifies the support metric instance. The `x` column classifies the type of support metric.
