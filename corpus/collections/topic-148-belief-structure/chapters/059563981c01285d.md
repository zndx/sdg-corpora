# Chapter 4: Ontological Mapping of Compliance Metrics to PCI DSS Directives

This chapter delineates the formal mapping between quantitative compliance metrics and the Payment Card Industry Data Security Standard (PCI DSS) requirements using a defined ontology. The scope is restricted to the structural definition of Descriptive Information Content Entities (ICE) and their relationships to Directive ICEs within a security data governance framework. We establish the axiomatic relationships between baseline rates, support counts, and specific regulatory requirements, providing a deterministic schema for audit evidence aggregation.

## 1. Descriptive Information Content Entities

The fundamental unit of observation within the security governance framework is the Descriptive Information Content Entity. As defined by the foundational axiom `lift_basic`, this class represents any information content entity that asserts a property or state of affairs without prescribing a normative behavior. In the context of an audit report, these entities function as the raw data points or log entries—such as system timestamps, traffic counts, or configuration states—that serve as the evidentiary basis for compliance analysis.

The axiom `lift_basic` posits that any instance of this class is, by definition, a subclass of `cco:DescriptiveICE`. This creates a categorical container for all non-directive data. The relational projection of this axiom is straightforward, serving as a lookup table for the specific types of descriptive artifacts collected during an audit engagement.

The following table enumerates instances of basic descriptive entities identified during a preliminary system scan. These entries represent the atomic data elements from which complex metrics are derived.

**Table 1: Basic Descriptive Information Content Entities**

## 2. PCI DSS Requirements as Directives

In contrast to descriptive observations, compliance frameworks rely on Directive Information Content Entities. These entities encode the normative rules or requirements to which an organization must adhere. The axiom `pci_dss_requirement` formalizes this by defining a relationship where a specific class (X) acts as a directive that encompasses or references a specific PCI DSS requirement (Y).

This relationship is critical for establishing traceability between the raw data (descriptive entities) and the regulatory standard. The schema enforces a complex dependency where the requirement slot (Y) must reference a valid metric entity, creating a bidirectional link between the rule and its measurement mechanism. This structure ensures that every directive cited in a report is anchored to a quantifiable or observable metric.

The table below presents specific PCI DSS directives mapped to their corresponding metric identifiers. Note the reciprocal nature of the identifiers, which enforces the integrity of the compliance mapping.

**Table 2: PCI DSS Requirements and Directives**

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_01 | DirectiveICE_FirewallConfiguration | LIFT_BASE_01 |
| PCI_REQ_02 | DirectiveICE_VendorDefaultPasswords | LIFT_BASE_02 |
| PCI_REQ_03 | DirectiveICE_StoredCardholderData | LIFT_BASE_03 |
| PCI_REQ_04 | DirectiveICE_EncryptionTransmission | LIFT_BASE_04 |

*Table 2 embodies the `pci_dss_requirement` axiom. The primary key is `id`. Column `x` denotes the directive class, while column `y` is a foreign key that references the `id` of a baseline rate entity in `t_lift_with_baseline_rate`, ensuring that every requirement is associated with a specific metric calculation.*

## 3. Baseline Rate Metrics

To determine the significance of a compliance observation, auditors must establish a baseline rate—a frequency or probability that serves as a control value against which current observations are measured. The axiom `lift_with_baseline_rate` defines a specialized DescriptiveICE that possesses a `hasBaselineRate` property. This property links the metric to a specific PCI DSS requirement context, effectively grounding the statistical baseline in the regulatory language.

This relationship allows the governance framework to differentiate between anomalous spikes and expected operational noise. For instance, a baseline rate for failed login attempts might be established as a percentage of total traffic, tied directly to Requirement 8.1.4 (Identify and authenticate access to system components). The relational structure mandates that the baseline rate entity (`y`) must correspond to a valid PCI DSS requirement entry, ensuring that the baseline is always relevant to a specific control.

The following table details the baseline rate metrics configured for the audit scope. These values define the expected "normal" operating parameters for the associated directives.

*Table 3 embodies the `lift_with_baseline_rate` axiom. The primary key is `id`. Column `x` represents the specific metric class, and column `y` is a foreign key referencing `t_pci_dss_requirement(id)`. This structure enforces that every baseline rate is strictly tied to a governing directive.*

## 4. Support Count Analysis

While baseline rates provide a normalized view, support counts provide the absolute volume of occurrences for a specific event or state. The axiom `lift_with_support_count` defines a DescriptiveICE that includes a `hasSupportCount` property. In data mining and compliance analytics, the support count is the absolute number of transactions or records that satisfy a given condition.

This metric is essential for risk prioritization. A low baseline rate with a high support count might indicate a systemic, albeit expected, issue requiring resource allocation, whereas a low support count might indicate an edge case. Similar to the baseline rate structure, this axiom links the support count entity to a specific PCI DSS requirement, ensuring that volume metrics are always interpreted within the context of a specific compliance control.
