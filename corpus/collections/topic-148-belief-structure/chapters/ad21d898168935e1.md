## 1. Scope and Preamble

This chapter delineates the formal ontological structures required to map compliance metrics—specifically those derived from Payment Card Industry Data Security Standard (PCI DSS) audits—into a rigorous descriptive framework. The content herein is not intended as a procedural guide for auditors but rather as a specification for the data architects implementing the underlying information models. We define the axioms governing "lift" metrics, baseline rates, and support counts, ensuring that every entity reference is anchored to a verifiable directive or descriptive information content entity (ICE). The following sections present the Manchester syntax axioms, their verbalizations, and the deterministic relational schemas required for storage and validation, ensuring high-fidelity data lineage in governance reporting systems.

---

## 2. Descriptive Information Content Entities (lift_basic)

### 2.1. Definition and Axiomatic Structure

The foundational unit of the compliance ontology is the **Descriptive Information Content Entity**. This concept is axiomatically defined in the ontology as the superclass for all observational data points that lack prescriptive power but describe the state of a system. The axiom `lift_basic` establishes that any entity `X` classified under this definition is inherently a `cco:DescriptiveICE`.

**Axiom 3 (lift_basic):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE`
*   **Verbalization:** {X} is a descriptive information content entity.
*   **Slot Types:** `X`: Class.

In practical terms, this axiom serves as the root node for all observational data. Whether the entity represents a log entry, a network packet capture, or a manual observation, its classification as a `DescriptiveICE` distinguishes it from `DirectiveICE`, which would imply a rule or requirement. The simplicity of this axiom belies its importance: it provides the necessary type-checking mechanism to prevent category errors in downstream reporting.

### 2.2. Instance Catalog

To instantiate this concept within a governance framework, we must populate the relational schema `t_lift_basic`. This table serves as the registry of all descriptive entities utilized in the audit. The primary key is the entity identifier (`id`), and the column `x` captures the specific class name of the entity.

**Relational Schema:**
```sql
CREATE TABLE t_lift_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DescriptiveICE"],"family":"02_observation_measurement","is_complex":false,"template_id":"lift_basic"}'
```

The following table presents representative instances of descriptive entities derived from a standard security audit. These entries illustrate the variety of classes that fall under the `DescriptiveICE` umbrella.

*Table 2.1: Registry of Descriptive Information Content Entities*

| ID (Entity Reference) | Class (X) | Description |
| :--- | :--- | :--- |
| `ent_001` | `FirewallLogEntry` | A record of a connection attempt blocked by the network perimeter firewall. |
| `ent_002` | `UserAccessRecord` | An audit trail entry documenting a user's successful authentication to the payment gateway. |
| `ent_003` | `ConfigurationSnapshot` | A point-in-time capture of system settings reflecting the state of critical services. |
| `ent_004` | `VulnerabilityScanResult` | The output of an automated scanner identifying a specific CVE on a target host. |
| `ent_005` | `PhysicalAccessLog` | A timestamped entry from a badge reader indicating entry to a restricted data center. |

Each row in Table 2.1 represents a distinct instance `X` that satisfies the axiom `lift_basic`. These entities form the evidentiary basis for calculating more complex metrics, such as lift and support counts, which will be discussed in subsequent sections.

## 3. Lift with Baseline Rate (lift_with_baseline_rate)

### 3.1. The Baseline Rate Constraint

In statistical analysis of compliance data, "lift" refers to the ratio of the observed outcome frequency to the expected outcome frequency. The axiom `lift_with_baseline_rate` formalizes this by asserting that a descriptive entity `X` (the metric) possesses a baseline rate `Y`. The baseline rate represents the expected frequency of an event under normal conditions or within a control group.

**Axiom 1 (lift_with_baseline_rate):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasBaselineRate some {Y:Class}`
*   **Verbalization:** {X} is something that has baseline rate {Y}.
*   **Slot Types:** `X`: Class, `Y`: Class.

This axiom is critical for risk assessment. By anchoring an observation `X` to a baseline `Y`, auditors can determine if the observed behavior deviates significantly from the norm. For instance, if the number of failed login attempts (`X`) significantly exceeds the established baseline rate (`Y`), this "lift" indicates a potential brute-force attack.

### 3.2. Relational Mapping to Directives

The relational projection of this axiom introduces a foreign key constraint that binds the baseline rate to a specific PCI DSS requirement. This linkage ensures that the baseline is not an arbitrary number but a metric derived from or associated with a specific compliance control.

**Relational Schema:**
```sql
CREATE TABLE t_lift_with_baseline_rate (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
)
COMMENT '{"bfo_anchor":["cco:DescriptiveICE"],"family":"02_observation_measurement","is_complex":true,"template_id":"lift_with_baseline_rate"}'
```

In this schema, `x` represents the descriptive entity (the metric), and `y` represents the baseline rate. The constraint `FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)` implies that the baseline rate `Y` is identified by the same identifier space as the requirement it supports. This creates a strong dependency: a baseline rate cannot exist in isolation; it must be sanctioned by a requirement ID.

*Table 3.1: Lift Metrics with Associated Baseline Rates*

| ID | Metric Entity (X) | Baseline Rate Reference (Y) | Interpretation |
| :--- | :--- | :--- | :--- |
| `lift_101` | `FailedAuthMetric` | `req_8.1.4` | The baseline for failed authentications is defined by Requirement 8.1.4 (User identification). |
| `lift_102` | `CipherSuiteUsage` | `req_4.1` | The baseline for acceptable encryption ciphers is defined by Requirement 4.1 (Encryption protocols). |
| `lift_103` | `PatchLatencyMetric` | `req_6.1` | The baseline for patch deployment time is defined by Requirement 6.1 (Security patching). |

In Table 3.1, the entity `FailedAuthMetric` is linked to `req_8.1.4`. This indicates that the baseline rate for this metric is not merely a statistical average but a value formally tied to the PCI DSS requirement regarding user identification management.

## 4. PCI DSS Requirements as Directives (pci_dss_requirement)

### 4.1. Directive Information Content Entities

While the previous sections dealt with descriptive entities (observations and metrics), this section addresses the prescriptive elements of the ontology: the **Directives**. The axiom `pci_dss_requirement` classifies an entity `X` as a `cco:DirectiveICE` that specifically encompasses a PCI DSS requirement `Y`.

**Axiom 2 (pci_dss_requirement):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`
*   **Verbalization:** {X} is something that pci dss requirement {Y}.
*   **Slot Types:** `X`: Class, `Y`: Class.

This axiom serves as the bridge between the abstract ontology and the specific regulatory text of the PCI DSS. By asserting that `X` is a `DirectiveICE`, we distinguish it from descriptive data, allowing the system to enforce rules based on these requirements.

### 4.2. Bidirectional Binding with Baselines

The relational schema for this axiom exhibits a circular dependency with the `t_lift_with_baseline_rate` table. Specifically, the `y` slot in `t_pci_dss_requirement` references `t_lift_with_baseline_rate`. This structure models a bidirectional relationship where a requirement defines the acceptable parameters (baseline) for a metric, and conversely, the metric validates the requirement.

**Relational Schema:**
```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_lift_with_baseline_rate(id)
)
COMMENT '{"bfo_anchor":["cco:DirectiveICE"],"family":"07_long_tail","is_complex":true,"template_id":"pci_dss_requirement"}'
```

This schema implies that for a requirement to be fully instantiated in the system, it must be associated with a lift metric that possesses a baseline rate. This enforces a "measure-by-directive" policy, ensuring that every regulatory mandate has a corresponding quantitative mechanism for validation.

*Table 4.1: PCI DSS Directives and Metric Bindings*

| ID | Directive Class (X) | Associated Lift Metric (Y) | Requirement Description |
| :--- | :--- | :--- | :--- |
| `req_8.1.4` | `AccessControlDirective` | `lift_101` | Directive requiring unique ID assignment; validated by FailedAuthMetric. |
| `req_4.1` | `EncryptionDirective` | `lift_102` | Directive requiring strong cryptography; validated by CipherSuiteUsage. |
| `req_6.1` | `VulnerabilityMgmtDirective` | `lift_103` | Directive requiring patching of security vulnerabilities; validated by PatchLatencyMetric. |

The circularity is evident here: `req_8.1.4` references `lift_101`, which in turn (per Section 3.2) references `req_8.1.4` as the source of its baseline. This closed loop ensures data integrity; a requirement cannot exist without a validation metric, and a metric cannot have a baseline without a governing requirement.

## 5. Lift with Support Count (lift_with_support_count)

### 5.1. Support Count Quantification

The final concept, `lift_with_support_count`, introduces the notion of evidence volume. In data mining and compliance analytics, the "support count" refers to the number of instances or records that substantiate a particular pattern or metric. The axiom asserts that a descriptive entity `X` has a support count `Y`.

**Axiom 4 (lift_with_support_count):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasSupportCount some {Y:Class}`
*   **Verbalization:** {X} is something that has support count {Y}.
*   **Slot Types:** `X`: Class, `Y`: Class.

While the baseline rate provides the expected frequency, the support count provides the actual volume of evidence. A high lift value with a low support count might indicate a statistical anomaly rather than a systemic issue. Therefore, `lift_with_support_count` is essential for filtering noise in compliance reports.

### 5.2. Evidence Aggregation

The relational schema for this axiom links the support count `Y` back to a PCI DSS requirement. This design choice suggests that the validity or relevance of the support count is determined by the requirement it pertains to.

**Relational Schema:**
```sql
CREATE TABLE t_lift_with_support_count (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
)
COMMENT '{"bfo_anchor":["cco:DescriptiveICE"],"family":"02_observation_measurement","is_complex":true,"template_id":"lift_with_support_count"}'
```

In this table, `x` represents the entity being measured (e.g., a specific type of security incident), and `y` represents the requirement ID that gives context to that count. This allows auditors to query, for example, "How many support records exist for Requirement 10.2.2 (Audit trails)?"

*Table 5.1: Support Counts for Compliance Metrics*

| ID | Metric Entity (X) | Requirement Reference (Y) | Support Count Value |
| :--- | :--- | :--- | :--- |
| `supp_201` | `PrivilegeEscalationEvent` | `req_8.2.1` | 14 |
| `supp_202` | `ClearTextTransmission` | `req_4.1` | 0 |
| `supp_203` | `UnpatchedSystem` | `req_6.1` | 3 |

Table 5.1 demonstrates how the ontology captures both the qualitative nature of the entity (`PrivilegeEscalationEvent`) and its quantitative context (linked to `req_8.2.1` with a count of 14). This structure facilitates the generation of audit reports that are both descriptive (what happened) and prescriptive (which requirement was implicated).
