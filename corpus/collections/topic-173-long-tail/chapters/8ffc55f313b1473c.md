# Evidence Generation and Clause Mapping in ISO 27001 Governance Frameworks

This chapter delineates the formal ontological structures governing the production of audit evidence within Information Security Management Systems (ISMS). Specifically, it addresses the intersection of generative technical processes—modeled as laboratory runs—and their resultant information artifacts, which serve as the foundation for ISO 27001 compliance verification. The text establishes a rigorous mapping between descriptive information content entities and the specific control clauses they satisfy, providing a data-centric schema for audit trail integrity.

## 1. Generative Processes and Laboratory Runs

In the context of formal ontology and audit compliance, a "Laboratory Run" is not merely a colloquial term for a test sequence; it is a spatiotemporal region defined by the execution of a specific protocol. According to the axiom `labrun_produces_measurement`, such a run is classified as a subclass of `bfo:0000015` (Process). This classification is critical for governance frameworks because it establishes that the entity in question is occurrent—it unfolds in time and has a beginning and an end—rather than being continuant, like a piece of hardware or a policy document.

The defining characteristic of this process is its capacity to produce a `cco:DescriptiveICE` (Descriptive Information Content Entity). In an audit scenario, this implies that the process must be generative; it cannot simply be a monitoring state but must actively output data artifacts that describe the state of the system at a specific point in time. For instance, a vulnerability scan executed against a server cluster constitutes a Laboratory Run. The process begins with the initialization of the scanning engine and concludes with the generation of the output file. The value of this process to the auditor is entirely dependent on the fidelity and provenance of the descriptive entity it produces.

### 1.1 Process Boundaries and Initiation
To ensure the integrity of the audit trail, the governance framework must strictly define the boundaries of the Laboratory Run. The process is initiated by a trigger event—often a scheduled cron job or a manual authorization by an accredited auditor. The ontology requires that the process be distinct from the agent that performs it. While the auditor or the automated script is the agent, the "Run" is the process itself.

### 1.2 Output Generation
The output of the Laboratory Run is the primary evidence artifact. Without the production of a `cco:DescriptiveICE`, the process holds no evidentiary value. Therefore, compliance protocols must ensure that every run terminates in a persistent, readable state. ## 2. Descriptive Information Content Entities (ICE)

The product of the Laboratory Run is the Descriptive Information Content Entity (ICE). As defined by the axiom `measurement_produced_by_run`, a `cco:DescriptiveICE` is a subclass of information content entities that are about some other entity. In the realm of ISO 27001, these are the reports, logs, and data dumps that describe the security posture of the asset under review.

The relationship between the ICE and the Run is one of production. The ICE does not exist prior to the completion of the process (in the context of the audit). This dependency is crucial for establishing the "freshness" of evidence. An audit report generated months ago, while still a document, is not the product of the current Laboratory Run and therefore cannot be used to satisfy current compliance requirements without re-evaluation.

### 2.1 Structure and Semantics
A Descriptive ICE must be machine-readable or human-readable in a standard format. Whether it is an XML file containing the output of a Nmap scan or a PDF summarizing a physical security inspection, the entity must contain descriptive data. This data is the "measurement" referenced in the ontology. It quantifies or qualifies the state of the system.

### 2.2 Provenance and Integrity
Because the ICE serves as legal evidence of compliance, its integrity must be protected. The ontology implies a direct lineage: the Run produces the ICE. Any break in this chain—such as a file modified post-generation—invalidates the ontological claim. Consequently, technical controls such as cryptographic hashing or Write-Once-Read-Many (WORM) storage are mandated for the retention of these entities.

## 3. Basic State Assertions

While Laboratory Runs are dynamic processes, they often aim to capture a static snapshot of the system: the State. The axiom `state_basic` classifies certain `cco:DescriptiveICE` entities specifically as state descriptors. These are atomic assertions regarding the configuration or status of a system at a specific moment.

A State assertion differs from a complex measurement in that it usually represents a single data point or a simple vector of data points rather than a composite analytical report. For example, the assertion "Port 443 is open" is a state. The assertion "The system is vulnerable to CVE-2023-1234" is a derived measurement, but the underlying fact "Patch level is 2022-01" is a state.

### 3.1 Atomicity in Audit Evidence
State assertions are the building blocks of compliance. When an auditor verifies that a control is in place, they are verifying one or more state assertions. The ontology treats these states as Descriptive ICE because they must be recorded and communicated. A state that exists in reality but is not recorded (described) cannot be audited.

### 3.2 Temporal Validity
States are highly temporal. The state described by "User J. Doe is disabled" may be true at 09:00 AM and false at 09:05 AM. Therefore, the governance framework requires that state assertions be tightly coupled with timestamp metadata, even though the ontology class itself focuses on the informational content.

## 4. ISO 27001 Clause Subclassification and Directive Mapping

The ultimate purpose of generating evidence through Laboratory Runs and capturing States is to demonstrate adherence to a governance framework, specifically ISO/IEC 27001. The axiom `iso27001_clause_subclass` provides the structural link between the technical evidence and the regulatory framework. It posits that a Directive Information Content Entity (`cco:DirectiveICE`) is a subclass of entities that references a specific ISO 27001 Clause.

In this schema, the Directive acts as the bridge. It is a prescriptive document or rule that mandates a specific behavior or configuration. The Clause (e.g., Annex A.9.1.1) is the normative requirement. The relationship defined here asserts that the Directive is an implementation or instantiation of that Clause.

### 4.1 The Compliance Chain
The compliance chain is linear and traceable:
1.  **Clause:** The requirement (e.g., "Access control shall be applied").
2.  **Directive:** The internal policy or configuration rule (e.g., "Mandatory Multi-Factor Authentication").
3.  **Laboratory Run:** The verification process (e.g., "Authentication Audit").
4.  **Measurement/State:** The evidence (e.g., "MFA is enforced").

The axiom `iso27001_clause_subclass` focuses on the link between the Directive and the Clause. However, the relational schema introduces a critical verification mechanism: the `y` slot (the Clause) is linked via a Foreign Key to the `id` of the Laboratory Run. This enforces the principle that a Clause is only considered satisfied or "active" in the context of a specific verification run. One cannot simply claim adherence to a Clause without referencing the specific Laboratory Run that produced the evidence validating it.
