# Chapter 4: Ontological Formalization of Compliance Directives and Evidence Chains

## 4.1 Scope and Preamble

This chapter delineates the formalization of regulatory compliance constructs within a high-fidelity ontology, specifically focusing on the intersection of Payment Card Industry Data Security Standard (PCI DSS) mandates, Health Insurance Portability and Accountability Act (HIPAA) technical safeguards, and the evidentiary requirements necessary for audit verification. The content herein maps complex governance frameworks to the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO), providing a deterministic structure for representing compliance artifacts. The objective is to establish a rigorous schema for representing how directives (specifically `cco:DirectiveICE`) necessitate specific controls, how those controls require evidence, and how attestation processes rely on these evidence chains to validate regulatory adherence. This formalization is critical for automated compliance auditing and the generation of assurance reports.

## 4.2 Attestation with Supporting Evidence

### 4.2.1 Conceptual Overview

Attestation, within the context of information security governance, is defined as a formal process (`bfo:Process`) wherein a designated authority validates the state of a system against a predefined set of controls. It is not merely a declaration of compliance but a procedural artifact that derives its validity from the existence of supporting evidence. The axiom `attestation_with_supporting_evidence` posits that for an attestation to be valid, it must be substantiated by specific evidence artifacts. This relationship ensures that compliance claims are grounded in verifiable data rather than self-referential assertions.

### 4.2.2 Formal Definition

In Manchester syntax, this relationship is expressed as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:withSupportingEvidence some {Y:Class}`

This axiom asserts that the attestation entity (`X`) is a subclass of `bfo:Process` and necessarily participates in a relationship (`sdg:withSupportingEvidence`) with an evidence entity (`Y`). The `Y` entity, in this schema, is projected to be a PCI DSS requirement, thereby linking the attestation process directly to specific regulatory standards.

### 4.2.3 Implementation and Data Structure

The following table illustrates instances where specific attestation processes are anchored to PCI DSS requirements. The primary key (`id`) uniquely identifies the attestation record, while the foreign key (`y`) ensures that the attestation is mapped to a valid, existing requirement within the governance framework.

**Table 4-1: Attestation with Supporting Evidence Mapping**

| id | x (Attestation Process) | y (PCI DSS Requirement) |
| :--- | :--- | :--- |
| ATT-2023-01 | Q3_Annual_Vulnerability_Scan_Atte | PCI_REQ_10_4 |
| ATT-2023-02 | Q4_Access_Control_Review_Atte | PCI_REQ_8_1 |
| ATT-2023-03 | Q2_Wireless_Liability_Scan_Atte | PCI_REQ_11_1 |
| ATT-2023-04 | Q1_Critical_Patch_Atte | PCI_REQ_6_1 |
| ATT-2023-05 | Q4_Data_Encryption_Verification_Atte | PCI_REQ_3_4 |

In the instance `ATT-2023-01`, the attestation process `Q3_Annual_Vulnerability_Scan_Atte` is valid only if supported by the evidence generated from `PCI_REQ_10_4` (Track and monitor all access to network resources and cardholder data). This structure prevents orphaned attestations and ensures full traceability from the audit report back to the specific control requirement.

## 4.3 PCI DSS Requirement Directives

### 4.3.1 Conceptual Overview

The PCI DSS framework is composed of numerous requirements that function as directives. These directives are modeled as subclasses of `cco:DirectiveICE` (Information Collection and Exchange Directive). The axiom `pci_dss_requirement` formalizes the relationship between a specific directive class and the requirement it represents. Crucially, this axiom establishes that a PCI DSS requirement (`X`) is a directive that necessitates a specific control with evidence requirements (`Y`). This creates a chain of custody for compliance logic: the high-level PCI requirement mandates a specific control, which in turn generates the evidence required for the attestation defined in Section 4.2.

### 4.3.2 Formal Definition

The Manchester syntax for this axiom is:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`

This structure enforces that any entity classified as a PCI DSS requirement must be a `DirectiveICE` and must be associated with a control that requires evidence. This mapping is essential for breaking down broad regulatory mandates into actionable technical controls.

### 4.3.3 Implementation and Data Structure

The table below demonstrates the mapping of PCI DSS requirement identifiers to their corresponding control classes. Note the recursive nature of the compliance model: the `y` value references a control with evidence requirement, which may itself validate the original requirement.

**Table 4-2: PCI DSS Requirement to Control Mapping**

| id | x (PCI DSS Requirement) | y (Control with Evidence) |
| :--- | :--- | :--- |
| PCI_REQ_10_4 | Network_Access_Monitoring_Req | LOG_MONITORING_CONTROL |
| PCI_REQ_8_1 | User_Access_Management_Req | USER_PROVISIONING_CONTROL |
| PCI_REQ_11_1 | Wireless_Network_Security_Req | WIRELESS_SCANNING_CONTROL |
| PCI_REQ_6_1 | Security_Patch_Management_Req | VULNERABILITY_PATCH_CONTROL |
| PCI_REQ_3_4 | Data_Encryption_At_Rest_Req | DISK_ENCRYPTION_CONTROL |

For example, `PCI_REQ_8_1` (User Access Management) is realized through `USER_PROVISIONING_CONTROL`. The directive nature of the requirement is preserved through the `cco:DirectiveICE` superclass, ensuring it is treated as an information-bearing entity with governance implications.

## 4.4 Control with Evidence Requirements

### 4.4.1 Conceptual Overview

While a PCI DSS requirement defines *what* must be achieved, the Control with Evidence Requirement defines *how* it is achieved and verified. This axiom represents the operationalization of governance. A control is a directive (`cco:DirectiveICE`) that explicitly requires evidence (`sdg:requiresEvidence`) to demonstrate its efficacy. This evidence is the tangible output—logs, screenshots, configuration files—that auditors review during the attestation process.

### 4.4.2 Formal Definition

The axiom is defined as:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:requiresEvidence some {Y:Class}`

Here, `X` represents the control mechanism, and `Y` represents the evidence requirement. The relational schema projects `Y` as a reference back to a `t_pci_dss_requirement`. This circular dependency (Requirement -> Control -> Evidence -> Requirement) models the iterative nature of compliance management: a control is implemented to satisfy a requirement, and the evidence generated by that control is used to validate the requirement.

### 4.4.3 Implementation and Data Structure

The following table details the specific controls and the evidence requirements they satisfy. The foreign key constraint ensures that every evidence requirement is tied back to a governing PCI DSS requirement, closing the loop on the compliance chain.

**Table 4-3: Control and Evidence Requirement Specification**

| id | x (Control Class) | y (PCI DSS Requirement) |
| :--- | :--- | :--- |
| LOG_MONITORING_CONTROL | System_Log_Aggregation | PCI_REQ_10_4 |
| USER_PROVISIONING_CONTROL | Identity_Management_System | PCI_REQ_8_1 |
| WIRELESS_SCANNING_CONTROL | Wireless_Intrusion_Detection | PCI_REQ_11_1 |
| VULNERABILITY_PATCH_CONTROL | Automated_Patch_Mgmt | PCI_REQ_6_1 |
| DISK_ENCRYPTION_CONTROL | Full_Disk_Encryption_Soft | PCI_REQ_3_4 |

In this schema, `LOG_MONITORING_CONTROL` (System Log Aggregation) requires evidence that satisfies `PCI_REQ_10_4`. This confirms that the operational activity of log aggregation is directly aligned with the strategic goal of network access monitoring.

## 4.5 HIPAA Technical Safeguards

### 4.5.1 Conceptual Overview

The Health Insurance Portability and Accountability Act (HIPAA) mandates specific safeguards to protect Electronic Protected Health Information (ePHI). This chapter focuses specifically on Technical Safeguards (`hipaa_safeguard_technical`). Like PCI DSS requirements, these safeguards are modeled as directives (`cco:DirectiveICE`). However, they are distinct in their regulatory origin and specific application to healthcare data. The axiom establishes that a HIPAA safeguard (`X`) is a directive that implements a specific control with evidence requirements (`Y`), thereby integrating HIPAA compliance into the broader evidence-based governance framework.

### 4.5.2 Formal Definition

The Manchester syntax is:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`

This definition allows the organization to map HIPAA-specific controls (such as access control or audit controls) to the same underlying evidence infrastructure used for PCI DSS, promoting a unified compliance model.

### 4.5.3 Implementation and Data Structure

The table below maps HIPAA technical safeguards to the control infrastructure. This mapping demonstrates how a single control (e.g., an encryption mechanism) can serve multiple regulatory masters (PCI DSS and HIPAA) by satisfying the evidence requirements of both.

**Table 4-4: HIPAA Technical Safeguard Mapping**

| id | x (HIPAA Safeguard) | y (Control with Evidence) |
| :--- | :--- | :--- |
| HIPAA_TECH_01 | Access_Control_Unique_User | USER_PROVISIONING_CONTROL |
| HIPAA_TECH_02 | Transmission_Security | DISK_ENCRYPTION_CONTROL |
| HIPAA_TECH_03 | Audit_Control_Mechanism | LOG_MONITORING_CONTROL |
| HIPAA_TECH_04 | Integrity_Control | VULNERABILITY_PATCH_CONTROL |
| HIPAA_TECH_05 | Person_Authentication | USER_PROVISIONING_CONTROL |

For instance, `HIPAA_TECH_01` (Access Control Unique User) is satisfied by `USER_PROVISIONING_CONTROL`. This indicates that the operational control managing user identities is sufficient to meet the HIPAA requirement for unique user identification, provided the requisite evidence is collected.

## 4.6 Requirement Equivalence and Target Specification

### 4.6.1 Conceptual Overview

The final axiom, `requirement_equiv_specifies_target`, introduces the concept of logical equivalence and scoping. It asserts that a requirement (`X`) is equivalent to a directive that specifies a mechanism (`Y`) and applies to a specific target (`Z`). This is a complex axiom that defines the boundary conditions of a compliance directive. It answers not only *what* must be done (the specification) but *to whom* or *what* it applies (the target).

### 4.6.2 Formal Definition

The axiom is expressed as:
`Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`

This structure requires three components: the requirement itself (`X`), the specification it dictates (`Y`), and the target system or entity (`Z`). The relational schema links `Y` back to a PCI DSS requirement, reinforcing the hierarchical nature of the governance model.

### 4.6.3 Implementation and Data Structure

The table below provides instances of requirements that are defined by their specifications and their targets. This level of granularity is essential for automated compliance scanning, as it allows the system to evaluate a specific target against a specific specification.

**Table 4-5: Requirement Equivalence and Target Specification**

| id | x (Requirement) | y (Specification) | z (Target) |
| :--- | :--- | :--- | :--- |
| REQ_EQUIV_01 | Data_Transmission_Policy | PCI_REQ_4_1 | Cardholder_Data_Environment |
| REQ_EQUIV_02 | Server_Hardening_Policy | PCI_REQ_2_2 | Production_Database_Servers |
| REQ_EQUIV_03 | Wireless_Access_Policy | PCI_REQ_1_2 | Corporate_LAN_WLAN |
| REQ_EQUIV_04 | Logging_Monitoring_Policy | PCI_REQ_10_2 | Security_Information_Event_Mgmt |
| REQ_EQUIV_05 | Physical_Access_Policy | PCI_REQ_9_1 | Data_Center_Facility |

In `REQ_EQUIV_01`, the `Data_Transmission_Policy` is equivalent to a directive that specifies `PCI_REQ_4_1` (Use strong cryptography) and applies specifically to the `Cardholder_Data_Environment`. This precise definition prevents the misapplication of controls to irrelevant systems and ensures that audit scopes are strictly defined.
