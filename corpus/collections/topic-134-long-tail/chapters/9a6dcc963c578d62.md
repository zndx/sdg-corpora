# Chapter 4: Directive Governance and Evidence Correlation in Compliance Frameworks

This chapter delineates the formal relationships between governance directives, evidentiary requirements, and compliance frameworks within a regulated enterprise architecture. It establishes the ontological structures necessary to map regulatory mandates—specifically the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA)—to technical controls and audit artifacts. The following sections provide a granular analysis of these relationships, supported by relational data schemas that enforce referential integrity across compliance domains. The objective is to define a rigorous, evidence-anchored approach to maintaining audit readiness and governance posture.

## 1.0 Attestation with Supporting Evidence

In the context of formal governance, an attestation is defined not merely as a statement of fact, but as a process-dependent entity that derives its validity from the existence of supporting artifacts. Ontologically, this is modeled by asserting that a specific class of attestation (X) is a subclass of a process (bfo:0000015) which necessitates the presence of supporting evidence (Y). This relationship ensures that any attestation logged within the governance framework is intrinsically linked to a verifiable evidentiary state, preventing the existence of orphaned or unverified compliance claims.

The implementation of this axiom requires a relational structure where the attestation record explicitly references the evidence requirement it fulfills. The primary key serves as the unique identifier for the attestation event, while the foreign key constraint enforces the dependency on the PCI DSS requirement table, ensuring that no attestation can exist without a valid regulatory basis.

## 2.0 PCI DSS Requirements as Directives

The PCI DSS framework is operationalized through a series of directives that mandate specific security behaviors and configurations. Ontologically, a PCI DSS requirement (X) is modeled as a subclass of an Information Control Element (cco:DirectiveICE), which serves as the directive vehicle for a specific requirement class (Y). This distinction allows the framework to separate the *directive* (the mandate to act) from the *requirement* (the abstract definition of the control), facilitating a more granular mapping of regulatory text to system configuration.

The relational schema for this axiom establishes a direct link between the requirement directive and the control evidence requirement. This structure ensures that every PCI DSS directive is immediately associated with the technical control that generates the necessary evidence for compliance. The foreign key constraint linking to the control table enforces a bottom-up validation, ensuring that directives are only issued where implementable controls exist.

## 3.0 Controls with Evidence Requirements

While directives define the *what* of compliance, controls define the *how*. A control with an evidence requirement (X) is a directive that explicitly necessitates the generation of artifacts (Y) to prove its operation. This axiom is foundational to the auditability of the system, as it posits that a control is only valid if it produces the requisite evidence. This class is also a subclass of cco:DirectiveICE, maintaining consistency with the directive hierarchy.

The relational representation of this concept introduces a recursive dependency in the context of the broader ontology, where the evidence required by a control often maps back to a specific PCI DSS requirement definition. This circularity is intentional and reflects the iterative nature of compliance: controls generate evidence to satisfy requirements, and requirements define the evidence that controls must generate. The schema enforces this by linking the control's evidence output back to the PCI requirement table.

## 4.0 HIPAA Safeguards (Technical)

Technical safeguards (X) are modeled as directives (cco:DirectiveICE) that implement specific HIPAA safeguard classes (Y). This axiom allows the organization to map HIPAA requirements to the same control infrastructure used for PCI DSS, promoting a unified compliance framework.

The relational schema for HIPAA technical safeguards links the safeguard directive to the control with evidence requirements. This foreign key relationship demonstrates that HIPAA compliance is achieved through the same technical controls that generate evidence for other frameworks. By mapping HIPAA safeguards to existing controls, the organization reduces redundancy and ensures a single source of truth for technical evidence.

## 5.0 Requirement Specification and Targeting

The final axiom defines the equivalence class for requirements that specify a directive and apply to a specific target. A requirement (X) is equivalent to a directive that specifies a requirement (Y) and applies to a target (Z). This structure captures the full context of a compliance mandate: it defines what must be done, the regulatory basis for the action, and the specific asset or system (the target) to which the action applies.

The relational schema for this axiom is complex, incorporating both the specification of the requirement and the application to a target. The foreign key constraint ensures that the specified requirement is a valid PCI DSS requirement, grounding the directive in the regulatory framework. The inclusion of the target (Z) allows for granular scoping of compliance efforts, ensuring that directives are applied precisely where needed within the IT infrastructure.
