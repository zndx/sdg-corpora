# Chapter 4: Governance Frameworks and Evidence-Based Compliance Directives

## 4.1 Scope and Preamble

This chapter delineates the structural relationships between regulatory compliance frameworks, specifically focusing on the intersection of Payment Card Industry Data Security Standards (PCI DSS) and Health Insurance Portability and Accountability Act (HIPAA) technical safeguards. The text establishes a formal ontology for mapping governance directives to evidence requirements, ensuring that control implementations are verifiable through audit trails. It is intended for compliance officers, information security auditors, and data governance architects who require a rigorous schema for validating the alignment between organizational policies and statutory mandates. The following sections define the axiomatic relationships between attestations, requirements, controls, and safeguards, supported by relational data models that enforce referential integrity across these domains.

## 4.2 Attestation with Supporting Evidence

### 4.2.1 Conceptual Definition

Within the context of formal governance, an attestation is defined not merely as a declaration of compliance, but as a process (bfo:0000015) that is intrinsically dependent on the existence of verifiable artifacts. The axiom `attestation_with_supporting_evidence` posits that for an attestation entity {X} to be valid, it must possess a relationship `withSupportingEvidence` to a specific requirement class {Y}. This relationship ensures that high-level compliance claims are anchored in granular, demonstrable proofs. In practice, this prevents "rubber-stamping" by mandating that every attestation event—whether it is a quarterly review or an annual audit—must reference specific, satisfied control requirements.

### 4.2.2 Implementation and Verification

When an organization undergoes a compliance audit, the auditor examines the attestation records. These records serve as the primary interface between the organization's governance board and the technical implementation of controls. The integrity of this relationship is maintained through a foreign key constraint, ensuring that an attestation cannot exist in the system unless it points to a valid, defined PCI DSS requirement. This enforces a strict bottom-up verification flow: evidence must exist before a requirement is met, and a requirement must be met before an attestation can be signed.

## 4.3 PCI DSS Requirements

### 4.3.1 Conceptual Definition

The PCI DSS framework is operationalized through a hierarchy of directives. The axiom `pci_dss_requirement` classifies a directive {X} as a subtype of `cco:DirectiveICE` (Information Control Element) which mandates a specific requirement {Y}. This axiom establishes the "long tail" of compliance governance, where high-level standards are decomposed into actionable mandates. The verbalization "{X} is something that pci dss requirement {Y}" implies that the directive is the realization of the abstract requirement within the organization's control environment.

### 4.3.2 Dependency on Control Evidence

A critical aspect of this ontology is the recursive nature of compliance dependencies. The relational schema for `t_pci_dss_requirement` dictates that every PCI requirement must reference a `control_with_evidence_requirement`. This creates a chain of custody for compliance logic: the PCI requirement defines *what* must be achieved, while the referenced control defines *how* it is achieved and *what evidence* proves it. For instance, the requirement to "maintain a vulnerability management program" is realized only when specific controls, such as "periodic vulnerability scans," are implemented and evidenced.

## 4.4 Control with Evidence Requirement

### 4.4.1 Conceptual Definition

The operational unit of compliance is the control. The axiom `control_with_evidence_requirement` defines a control {X} as a directive that explicitly `requiresEvidence` of type {Y}. This axiom bridges the gap between theoretical policy and operational reality. It asserts that a control is not merely a configuration setting or a procedural step; it is a directive that generates evidence. This evidence must be distinct and attributable to the control's execution.

### 4.4.2 The Evidence Cycle

In the relational schema, the `t_control_with_evidence_requirement` table exhibits a complex dependency structure. The evidence required ({Y}) by a control is, in fact, another PCI DSS requirement. This circular dependency (where a PCI requirement points to a Control, and a Control requires evidence pointing back to a PCI requirement) models the iterative nature of compliance maturity. A control is implemented to satisfy a requirement, and the validity of that control is verified by evidence that satisfies another requirement (often related to monitoring or logging).

For example, a "Firewall Configuration Control" is implemented to satisfy the "Firewall Requirement" (PCI_REQ_1_1). However, the *evidence* that this control is functioning correctly (e.g., a configuration backup) is mandated by a different requirement, such as "Data Retention" (PCI_REQ_3_1).

## 4.5 HIPAA Safeguard Technical

### 4.5.1 Conceptual Definition

While PCI DSS governs payment card data, HIPAA mandates the protection of electronic Protected Health Information (ePHI). The axiom `hipaa_safeguard_technical` categorizes a directive {X} as a `cco:DirectiveICE` that functions as a `hipaaSafeguard` for a specific control requirement {Y}. This mapping allows organizations to harmonize their governance frameworks by identifying where a single technical control can satisfy the evidence requirements of multiple regulatory regimes.

### 4.5.2 Cross-Framework Harmonization

The relational schema for `t_hipaa_safeguard_technical` links the HIPAA safeguard directly to the `control_with_evidence_requirement`. This structure implies that the technical safeguard is the mechanism by which the control generates its required evidence. For instance, a HIPAA "Access Control" safeguard (Technical Safeguard standard) may be the specific implementation of a generic "Access Control Log" control required by PCI DSS. By mapping these entities, auditors can verify that a single technical configuration (e.g., Active Directory lockout policies) serves as the evidence source for both PCI access requirements and HIPAA technical safeguards.

## 4.6 Requirement Equivalence (Requirement Specifies Target)

### 4.6.1 Conceptual Definition

The final axiom, `requirement_equiv_specifies_target`, provides the semantic context for the directives. It defines a class {X} as equivalent to a `cco:DirectiveICE` that both `specifies` a requirement {Y} and `appliesTo` a target {Z}. This axiom resolves the ambiguity of *where* and *what* a directive governs. It ensures that every requirement is not an abstract floating concept but is tied to a specific target environment (e.g., a database, a network segment, or a user group).

### 4.6.2 Targeted Governance

The relational schema for `t_requirement_equiv_specifies_target` enforces that the specified requirement {Y} must be a valid PCI DSS requirement. The target {Z} is typically an information asset class. This structure is essential for scoping audits. It allows the governance framework to query, "Show me all directives that apply to the 'Cardholder Data Environment' (Target) and specify 'Encryption' (Requirement)."
