# Chapter 4: Governance Frameworks and Evidence-Based Compliance Mapping

## 4.1 Scope and Preamble

This chapter delineates the structural relationships between governance directives, compliance requirements, and technical safeguards within a multi-regulatory environment. It provides a formal methodology for mapping organizational controls to the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA) Security Rule. The focus is on the ontological alignment of attestation processes, evidence collection, and the specification of technical targets. By establishing a rigorous schema for these relationships, organizations can ensure that their compliance posture is not only documented but also structurally sound and auditable. The following sections detail the axiomatic definitions of these relationships, supported by relational data models that demonstrate the practical application of these concepts in a controlled audit context.

## 4.2 Attestation with Supporting Evidence

### 4.2.1 Conceptual Framework

In the context of formal governance, an attestation is defined as a process—a temporal entity that extends through time—whereby a governing body validates the state of compliance. Axiomatically, we define an Attestation with Supporting Evidence as a subclass of `bfo:Process`. This process is characterized by the property `sdg:withSupportingEvidence`, which links the attestation event to a specific class of evidence or requirement. This relationship ensures that every attestation is not merely a declarative statement but is anchored to tangible, verifiable artifacts. The integrity of the audit lifecycle depends on this linkage; without a binding reference to supporting evidence, an attestation lacks the necessary evidentiary basis to withstand regulatory scrutiny.

### 4.2.2 Operational Implementation

When an internal audit committee or an external assessor issues a formal report, they are engaging in this attestation process. For example, the "Annual PCI DSS ROC Attestation" is a process that substantiates compliance by referencing specific PCI requirements, such as firewall configuration or encryption standards. The process entity (the attestation) serves as the primary vehicle for communication to stakeholders, while the `withSupportingEvidence` property provides the traceability required for forensic review of the compliance claim.

## 4.3 PCI DSS Requirement Directives

### 4.3.1 Conceptual Framework

The PCI DSS Requirement is modeled as a subclass of `cco:DirectiveICE` (Information Control Element). This axiom establishes that a requirement is not merely a passive text string but an active directive within the compliance ontology. The relationship `sdg:pciDssRequirement` links a high-level organizational directive to a specific, granular control requirement. This mapping is critical for translating external regulatory mandates into internal governance artifacts. It allows the organization to treat a PCI requirement as a first-class object within its own directive hierarchy, facilitating automated enforcement and monitoring.

### 4.3.2 Operational Implementation

Consider the organizational directive "Secure Network Architecture." This directive is implemented by satisfying the specific PCI DSS Requirement 1.1.2 (often related to firewall rules). In this model, the directive (`X`) is the internal policy or governance object, while the PCI requirement (`Y`) is the external standard being satisfied. This separation allows the organization to maintain its own taxonomy of directives while maintaining a strict, queryable mapping to the external PCI framework.

## 4.4 Control with Evidence Requirement

### 4.4.1 Conceptual Framework

The axiom `control_with_evidence_requirement` further refines the governance model by defining a specific type of `cco:DirectiveICE` that mandates the production of evidence. This class utilizes the object property `sdg:requiresEvidence` to link a control directive to the specific evidence artifact that must be generated. This relationship is foundational for auditability; it moves the organization from a "state of compliance" (intent) to a "demonstrable compliance" (verification). The axiom posits that for a control to be effective, it must generate a specific class of evidence that can be inspected.

### 4.4.2 Operational Implementation

For instance, a "User Access Review" control requires evidence in the form of "Manager Approval Logs." The control is the directive (`X`), and the evidence is the output (`Y`). This structure ensures that controls are not designed in a vacuum; they are defined by their output. In the context of the relational schema, this creates a recursive or cyclical dependency with the PCI requirements table, reflecting the real-world feedback loop where PCI requirements dictate controls, and controls generate the evidence that satisfies the PCI requirement.

### 4.4.3 Relational Mapping

The following table operationalizes the `control_with_evidence_requirement` axiom. It lists specific controls and the evidence they require. The foreign key constraint linking `y` back to the PCI requirement table enforces the logic that evidence requirements are ultimately derived from the compliance standards they serve.

## 4.5 HIPAA Safeguard Technical Specifications

### 4.5.1 Conceptual Framework

While PCI DSS governs payment card data, healthcare entities must simultaneously adhere to HIPAA. The axiom `hipaa_safeguard_technical` defines a class of `cco:DirectiveICE` specifically for HIPAA technical safeguards. This axiom utilizes the property `sdg:hipaaSafeguard` to map a technical implementation (such as encryption or access control) to the broader control requirements established in the previous section. This mapping facilitates a unified compliance framework where a single technical control can satisfy multiple regulatory regimes (e.g., encryption satisfying both PCI Requirement 4 and HIPAA §164.312(a)(2)(iv)).

### 4.5.2 Operational Implementation

A "Transmission Security Mechanism" is a technical safeguard under HIPAA. In a unified framework, this mechanism can be mapped to the "Encryption Key Rotation Control" defined in the general control framework. By linking the HIPAA safeguard (`X`) to the control requirement (`Y`), the organization demonstrates that its investment in technical controls has a dual compliance utility, thereby optimizing governance resources and reducing redundancy in control implementation.

### 4.5.3 Relational Mapping

The table below illustrates the `t_hipaa_safeguard_technical` schema. It maps specific HIPAA safeguards to the control requirements they fulfill. The foreign key ensures that the safeguard is anchored to a valid control requirement that exists within the organization's governance inventory.

## 4.6 Requirement Specification and Targeting

### 4.6.1 Conceptual Framework

The final axiom, `requirement_equiv_specifies_target`, provides the granular definition of a scoped requirement. It asserts that a class `X` is equivalent to the intersection of a `cco:DirectiveICE`, a specification (`sdg:specifies`), and an application target (`sdg:appliesTo`). This axiom is crucial for scoping. It moves beyond the abstract definition of a control and defines exactly *what* is being controlled (the specification) and *where* it is being applied (the target). This is the mechanism by which a generic policy is transformed into a specific, enforceable rule for a specific system asset.

### 4.6.2 Operational Implementation

Consider a "Server Hardening Directive." This is a generic concept. However, the axiom allows us to define a specific requirement instance: "The Server Hardening Directive specifies SSH Configuration and applies to the Production Web Server Farm." This triple relationship (Directive + Specification + Target) eliminates ambiguity during an audit. It answers the questions: What is the rule? What does it detail? Who or what must follow it?
