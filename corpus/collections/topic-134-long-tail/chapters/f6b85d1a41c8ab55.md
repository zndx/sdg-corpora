# Governance Frameworks: Evidence, Attestation, and Compliance Mapping

This chapter delineates the structural relationships between regulatory directives, technical controls, and the evidentiary artifacts required to demonstrate compliance. It provides a formal analysis of how governance frameworks—specifically those pertaining to PCI DSS and HIPAA—are operationalized through ontology-backed mappings. The discussion focuses on the logical derivation of compliance postures, where abstract requirements are decomposed into verifiable controls and supporting evidence. By defining the relational schema between attestation processes, specific requirements, and technical safeguards, this text establishes a data-centric model for audit readiness and regulatory reporting.

## 1. Attestation with Supporting Evidence

In the context of formal governance, an attestation is not merely a declaration of compliance but a process-oriented verification mechanism. As defined by the foundational axioms of the ontology, an attestation represents a specific type of process (bfo:Process) that is intrinsically dependent on supporting evidence. This relationship ensures that any assertion made by a governing body is anchored to verifiable data artifacts, thereby mitigating the risk of non-compliance and enhancing the integrity of audit reports.

The structural integrity of an attestation relies on the bidirectional linkage between the act of attesting and the evidence cited. When a Lead Member or a Compliance Officer updates a Select Committee, they are effectively instantiating a process where the validity of the update is contingent upon the existence of specific, referenced artifacts. This prevents "harmful downloads" of unverified assertions and ensures that all reported metrics—whether related to Adult Social Care or Information Security—are grounded in reality.

From a relational perspective, this concept is embodied by the mapping of an attestation class to a requirement class. The primary key of the attestation record serves as the unique identifier for the verification event, while the foreign key establishes a rigid dependency on the evidence requirement. Without the corresponding evidence record, the attestation is logically null and void.

**Exhibit 1: Mapping of Attestation Processes to PCI DSS Evidence Requirements**

| ID | Attestation Process (X) | Supporting Evidence Requirement (Y) |
| :--- | :--- | :--- |
| ATT-2023-Q1 | Q1 External Vulnerability Assessment | PCI_REQ_11_3 |
| ATT-2023-04 | Annual Password Policy Review | PCI_REQ_8_2 |
| ATT-2023-05 | Wireless Network Configuration Audit | PCI_REQ_1_2 |
| ATT-2023-06 | Firewall Rule Set Review | PCI_REQ_1_1 |
| ATT-2023-07 | Incident Response Plan Test | PCI_REQ_12_10 |

As illustrated in Exhibit 1, each attestation process (e.g., the "Q1 External Vulnerability Assessment") is formally linked to a specific PCI DSS requirement that generates the necessary evidence. This structure ensures that the governance framework is not merely a collection of policies but an active, evidence-based system of record.

## 2. PCI DSS Requirement

The Payment Card Industry Data Security Standard (PCI DSS) functions as a critical directive within the governance ontology. A PCI DSS requirement is modeled as a subclass of the Information Control Element (cco:DirectiveICE), representing a mandate that must be implemented within the environment. The ontology posits that these requirements are not isolated; rather, they possess a recursive relationship where a specific requirement may encompass or necessitate further control requirements.

This hierarchical structure allows for the decomposition of broad mandates into actionable sub-requirements. For instance, a high-level directive regarding encryption necessitates specific control implementations regarding key management and cryptographic protocols. The relational schema enforces this by linking a requirement entity to a control entity, ensuring that the directive is always operationalized through a concrete mechanism.

In practical terms, when an audit report identifies a failure in a specific area, it traces the failure through this hierarchy. The requirement ID serves as the anchor for the finding, while the link to the control requirement identifies the specific gap in implementation. This mapping is essential for the "post-COVID recovery" of compliance postures, as it allows organizations to systematically address control failures that lead to requirement breaches.

**Exhibit 2: PCI DSS Requirements and Associated Control Implementations**

| ID | PCI DSS Requirement Class (X) | Control Implementation (Y) |
| :--- | :--- | :--- |
| PCI_REQ_2_2 | System Configuration Standards | CTRL_CONFIG_HARDENING |
| PCI_REQ_3_4 | Render PAN Unreadable | CTRL_ENCRYPTION_AT_REST |
| PCI_REQ_4_1 | Use Strong Cryptography | CTRL_CRYPTO_PROTOCOLS |
| PCI_REQ_6_1 | Secure Development Process | CTRL_PATCH_MGMT |
| PCI_REQ_7_2 | Restrict Access by Need to Know | CTRL_RBAC_ENFORCEMENT |

Exhibit 2 demonstrates the decomposition of PCI DSS requirements into their constituent controls. The ID `PCI_REQ_3_4`, referring to the rendering of the Primary Account Number (PAN) unreadable, is directly supported by the control `CTRL_ENCRYPTION_AT_REST`. This relationship confirms that the directive is satisfied only when the underlying control is active and verified.

## 3. Control with Evidence Requirement

A control, in the lexicon of governance frameworks, is a directive designed to modify behavior or system states to achieve a compliance objective. However, the existence of a control is insufficient for audit purposes; it must generate evidence of its operation. The ontology defines a "Control with Evidence Requirement" as a directive that explicitly requires the production of evidence artifacts, which are in turn validated against the original PCI DSS requirements.

This creates a closed-loop verification system. The control is implemented (X), it generates evidence (Y), and that evidence is mapped back to the requirement that necessitated the control. This circular dependency—where the control points to the requirement and the requirement points to the control—is a feature of the complex governance ontology, reflecting the continuous nature of compliance monitoring.

For example, a "Firewall Configuration" control must produce "Configuration Logs" as evidence. These logs are then reviewed to satisfy the "Review Firewall Rules" requirement. The relational schema captures this by linking the control record to the requirement record, ensuring that every control has a defined evidence output and every requirement has a defined evidence input.

**Exhibit 3: Controls and Their Evidence Generation Requirements**

| ID | Control Directive (X) | Evidence Requirement (Y) |
| :--- | :--- | :--- |
| CTRL_LOG_MONITORING | Security Log Monitoring | PCI_REQ_10_1 |
| CTRL_AV_DEPLOYMENT | Anti-Virus Software Deployment | PCI_REQ_5_1 |
| CTRL_DATA_BACKUP | Secure Data Backup Procedures | PCI_REQ_3_2 |
| CTRL_PHYSICAL_ACCESS | Physical Access Control Mechanisms | PCI_REQ_9_1 |
| CTRL_WIRELESS_SCANNING | Wireless Intrusion Detection System | PCI_REQ_11_1 |

The data in Exhibit 3 highlights the operational necessity of evidence generation. The control `CTRL_PHYSICAL_ACCESS` is not merely a lock on a door; it is a directive that requires evidence (PCI_REQ_9_1) such as visitor logs or badge access records to prove that the physical security posture is maintained.

## 4. HIPAA Safeguard Technical

While PCI DSS governs payment data, the Health Insurance Portability and Accountability Act (HIPAA) mandates the protection of electronic Protected Health Information (ePHI). The ontology extends the governance framework to include HIPAA Technical Safeguards, classified here as directives that implement specific safeguards. These safeguards are mapped to the same control structures used for PCI DSS, illustrating the concept of "common controls"—a single technical implementation that satisfies multiple regulatory frameworks.

A HIPAA Technical Safeguard, such as access control or encryption, is modeled as a directive that references a control with an evidence requirement. This alignment allows organizations to streamline their compliance efforts. By mapping a HIPAA safeguard to an existing control (e.g., mapping the HIPAA Access Control standard to the existing Role-Based Access Control (RBAC) system), auditors can verify the efficacy of the safeguard through the evidence already generated for PCI DSS compliance.

This cross-walking is critical for comprehensive governance. It prevents the duplication of effort and ensures that the "long tail" of regulatory requirements is managed through a unified set of technical controls. The relational schema enforces this by linking the HIPAA safeguard entity to the control entity, ensuring that the safeguard is realized through a tangible, evidence-generating mechanism.

**Exhibit 4: HIPAA Technical Safeguards Mapped to Unified Controls**

| ID | HIPAA Safeguard Class (X) | Mapped Control (Y) |
| :--- | :--- | :--- |
| HIPAA_TECH_164_312_a1 | Unique User Identification | CTRL_RBAC_ENFORCEMENT |
| HIPAA_TECH_164_312_c1 | Mechanism to Encrypt EPHI | CTRL_ENCRYPTION_AT_REST |
| HIPAA_TECH_164_312_d | Audit Controls | CTRL_LOG_MONITORING |
| HIPAA_TECH_164_312_e2 | Transmission Security | CTRL_CRYPTO_PROTOCOLS |

Exhibit 4 provides a clear mapping of HIPAA Security Rule standards to the unified control environment. The safeguard `HIPAA_TECH_164_312_c1`, addressing the encryption of ePHI, is satisfied by `CTRL_ENCRYPTION_AT_REST`, demonstrating how a single technical control can serve distinct regulatory compliance objectives.

## 5. Requirement Equivalence Specification

The final concept in this chapter addresses the granular application of requirements to specific targets. A requirement is formally defined as equivalent to a directive that specifies a particular control and applies to a specific target entity (Z). This axiom moves the framework from abstract governance to concrete asset management.

In this model, a requirement is not satisfied globally; it is satisfied relative to a specific target, such as a database server, a network segment, or an application. The "specifies" relationship links the requirement to the control mechanism, while the "applies to" relationship links the requirement to the asset. This tripartite structure (Requirement—Control—Target) is essential for precise audit scoping.

For instance, a requirement for "Two-Factor Authentication" may specify a "RADIUS Token Control" but applies only to the "Cardholder Data Environment" and not to the general corporate network. This distinction prevents the over-application of controls and ensures that audit resources are focused on high-value targets. The relational schema captures this by including a foreign key to the requirement and a field for the target, creating a definitive record of what must be secured, how it must be secured, and where it is located.

**Exhibit 5: Requirement Specifications and Target Applications**

| ID | Requirement Specification (X) | Specifies Control (Y) | Applies to Target (Z) |
| :--- | :--- | :--- | :--- |
| REQ_SPEC_001 | Database Access Encryption | CTRL_ENCRYPTION_AT_REST | PROD_DB_CLUSTER_01 |
| REQ_SPEC_002 | Wireless Network Segmentation | CTRL_WIRELESS_SCANNING | GUEST_WIFI_VLAN |
| REQ_SPEC_003 | Admin Session Logging | CTRL_LOG_MONITORING | ADMIN_JUMP_SERVER |
| REQ_SPEC_004 | Web App Firewall Implementation | CTRL_WAF_DEPLOYMENT | PUBLIC_FACING_WEB_APP |
| REQ_SPEC_005 | Endpoint Malware Protection | CTRL_AV_DEPLOYMENT | ENDPOINT_POOL_WIN10 |

As shown in Exhibit 5, the requirement `REQ_SPEC_001` specifies the use of encryption controls but explicitly applies it to `PROD_DB_CLUSTER_01`. This level of granularity is characteristic of high-quality audit reports and compliance handbooks, ensuring that directives are not only theoretically sound but practically enforced against the correct assets.
