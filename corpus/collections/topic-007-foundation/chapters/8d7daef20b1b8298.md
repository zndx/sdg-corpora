# Directive Governance in Laboratory Compliance Systems

This chapter introduces five core ontological patterns for modeling regulatory directives, requirements, and verification processes. The patterns are illustrated with a relational schema drawn from clinical laboratory information management. The five tables capture directive equivalence, verification evidence requirements, attestation linkages, policy scoping, and non-obsoleteness constraints. Primary and foreign key relationships permit multi-hop queries that reconstruct compliance chains from policy to result.

## 1 Ontological Patterns and Table Structures

### 1.1 Requirement Equivalence and Target Specification

Axiom 1 states that a requirement class is equivalent to a directive that specifies a target class and applies to a further class. The corresponding table records these three participants. Column `id` is the primary key. Columns `y` and `z` function as foreign-key references to class identifiers used elsewhere in the schema, enabling joins that recover the full specification chain.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.2 Verification Requiring Minimum Evidence

Axiom 2 classifies a verification process as a subtype of bfo:Process that must produce at least one evidence instance. The table records the process class and the required evidence class. Column `id` is the primary key; column `y` references evidence classes that appear as targets in attestation records.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| VER-001 | RT-PCRVerification | AmplificationCurveEvidence |
| VER-002 | RT-PCRVerification | CycleThresholdEvidence |
| VER-003 | ELISAVerification | OpticalDensityEvidence |
| VER-004 | CultureVerification | ColonyCountEvidence |
| VER-005 | SequencingVerification | ReadAlignmentEvidence |

### 1.3 Attestation Supported by Evidence

Axiom 3 defines an attestation process as one that occurs with supporting evidence. The table links the attestation class to its required evidence class. Column `id` is the primary key; column `y` again references evidence classes, permitting direct join to verification records.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

|----|---|---|
| ATT-001 | ResultAttestation | AmplificationCurveEvidence |
| ATT-002 | ResultAttestation | OpticalDensityEvidence |
| ATT-003 | ResultAttestation | ColonyCountEvidence |
| ATT-004 | ResultAttestation | CycleThresholdEvidence |
| ATT-005 | ResultAttestation | ReadAlignmentEvidence |

### 1.4 Policy Equivalence with Jurisdiction and Scope

Axiom 4 states that a policy class is equivalent to a directive possessing both a jurisdiction and a governed scope. The table records these three participants. Column `id` is the primary key; columns `y` and `z` serve as references to jurisdiction and scope classes used in requirement specifications.

```sql
CREATE TABLE t_policy_equiv_jurisdiction_and_scope (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.5 Directive Non-Obsoleteness Constraint

Axiom 5 asserts that a directive class is a subtype of cco:DirectiveICE and is not identical to an obsolete class. The table records the directive and the class it must not equal. Column `id` is the primary key.

```sql
CREATE TABLE t_directive_not_obsolete (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 2 Cross-Table Query Example

To determine the attestation supporting evidence for a requirement governed by a given policy, join on shared evidence classes. Consider the multi-hop question: “Which attestation supports evidence for the requirement that specifies SARS-CoV-2-RNA on NasopharyngealSwab under the CLIA2020Policy?”

Start with row REQ-001 in `t_requirement_equiv_specifies_target` (y = SARS-CoV-2-RNA). Join `t_verification_min_one_evidence` on y = AmplificationCurveEvidence (VER-001). Join `t_attestation_with_supporting_evidence` on the same evidence class (ATT-001). The resulting joined row is:

REQ-001 | MolecularAssayRequirement | SARS-CoV-2-RNA | NasopharyngealSwab  
VER-001 | RT-PCRVerification | AmplificationCurveEvidence  
ATT-001 | ResultAttestation | AmplificationCurveEvidence

The chain confirms that ResultAttestation (ATT-001) supplies the required supporting evidence for the verification of the original requirement under the policy scope.
