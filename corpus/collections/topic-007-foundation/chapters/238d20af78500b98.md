# Directive Governance in Compliance Auditing

This chapter defines five ontological patterns for representing directives, policies, verifications, and attestations. Each pattern is projected to a relation whose columns correspond directly to the axiom slots. The resulting schema supports cross-table joins that recover multi-hop governance facts such as “which non-obsolete policy governs the scope verified by a given attestation.”

## 1 Requirement Specification

Axiom 1 states that a requirement is a directive that specifies a target class and applies to another class. The relation therefore stores three class references; its primary key identifies the equivalence axiom instance while the two NOT NULL columns function as foreign keys into any table that enumerates the classes used elsewhere in the schema.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 1.1 Verification Producing Evidence

Axiom 2 classifies a verification as a process that must produce at least one evidence item. The relation therefore links a verification class to an evidence class; the primary key identifies the subclass axiom while the evidence column acts as a foreign key to any table holding evidence instances.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 1.2 Attestation Supported by Evidence

Axiom 3 defines an attestation as a process that occurs with supporting evidence. The relation records the attestation class and its required evidence class; the primary key identifies the subclass axiom and the evidence column again serves as a foreign key.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
```

## 2 Policy Jurisdiction and Scope

Axiom 4 states that a policy is a directive whose jurisdiction and governed scope are both specified. The relation therefore contains three class references; its primary key identifies the equivalence axiom while the two NOT NULL columns act as foreign keys to jurisdiction and scope classes used throughout the schema.

```sql
CREATE TABLE t_policy_equiv_jurisdiction_and_scope (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 2.1 Non-Obsolete Directives

Axiom 5 asserts that a directive is not an obsolete class. The relation records the directive class and the obsolete class it must not instantiate; the primary key identifies the subclass axiom.

## 3 Cross-Join Example

To determine the result of an attestation performed on a sample using a method governed by a non-obsolete policy, join four tables on the shared class references:

```sql
SELECT
  r.z AS sample,
  r.y AS method,
  a.x AS attestation,
  p.x AS policy
FROM t_requirement_equiv_specifies_target r
JOIN t_attestation_with_supporting_evidence a ON a.y = r.y
JOIN t_policy_equiv_jurisdiction_and_scope p ON p.z = r.z
JOIN t_directive_not_obsolete d ON d.x = p.x
WHERE r.z = 'LaboratorySample'
  AND d.y IS NOT NULL;
```

The query returns one row:

- sample = LaboratorySample
- method = TestMethod
- attestation = MethodAttestation
- policy = ISO17025Policy
