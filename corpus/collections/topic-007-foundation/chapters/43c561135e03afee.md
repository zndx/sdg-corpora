# Governance Frameworks: Directive Ontology and Evidence Verification

## 1.0 Preamble and Scope

This chapter establishes the formal ontological structures governing the definition, verification, and lifecycle management of compliance directives within the enterprise architecture. It delineates the precise relationships between regulatory requirements, policy jurisdictions, and the evidentiary artifacts necessary for audit readiness. The content herein is grounded in the axiomatization of the `cco:DirectiveICE` class hierarchy and its interaction with process-oriented verification mechanisms. Readers will be guided through the logical mapping of abstract governance concepts to concrete relational data structures, ensuring that compliance artifacts are both machine-readable and audit-proof. The following sections detail five core axioms that define the equivalence classes for requirements and policies, the production of evidence through verification processes, and the exclusionary criteria for directive obsolescence.

## 2.0 Requirement Specification and Target Mapping

In the context of governance ontology, a Requirement is not merely a textual desideratum but a formal equivalence class defined by specific structural constraints. According to Axiom 1 (`requirement_equiv_specifies_target`), a Class `X` is semantically equivalent to a `cco:DirectiveICE` if and only if it satisfies two existential conditions: it must specify a standard or methodology (`Y`), and it must apply to a specific target entity or scope (`Z`). This definition ensures that every requirement encoded in the system is actionable and bound to a governed object.

The distinction between the specification (`Y`) and the target (`Z`) is critical for audit traceability. The specification represents the "what"—the technical standard, control framework, or specific parameter being mandated. The target represents the "where" or "whom"—the asset, user group, or operational domain subject to the mandate. This separation allows governance engines to query all requirements applicable to a specific asset or to trace all mandates deriving from a specific standard.

### 2.1 Relational Representation of Requirements

To operationalize this axiom, the relational schema `t_requirement_equiv_specifies_target` is utilized. The primary key `id` serves as the unique identifier for the requirement instance. The columns `x`, `y`, and `z` correspond to the Requirement Class, the Specification Class, and the Target Class, respectively. The `NOT NULL` constraints on `y` and `z` enforce the axiom's existential quantification; a requirement cannot exist in the database without a valid specification and a defined target.

The following table illustrates this mapping, demonstrating how specific governance classes (e.g., `EncryptionRequirement`) are instantiated as directives specifying technical standards (e.g., `AES256Standard`) and applying to operational domains (e.g., `CustomerData`).

## 3.0 Verification Processes and Evidence Production

Verification constitutes the operational backbone of compliance assurance. Axiom 2 (`verification_min_one_evidence`) posits that a Class `X` (a Verification Process) is a subclass of `bfo:0000015` (a Process) and is characterized by the mandatory production of at least one instance of Class `Y` (Evidence). This axiom introduces a cardinality constraint (`min 1`) on the `sdg:producesEvidence` property, formally prohibiting the existence of a verification process that yields zero evidentiary output.

This constraint is fundamental to the principle of "audit by design." It ensures that every compliance check, whether automated or manual, is intrinsically linked to an artifact that proves the check occurred. The ontology distinguishes the process of verification (the act of checking) from the evidence itself (the record of the check). By anchoring `X` to the BFO (Basic Formal Ontology) Process class, we align the governance model with upper-level ontological standards, facilitating interoperability between compliance systems and enterprise architecture frameworks.

### 3.1 Evidence Generation Constraints

The schema `t_verification_min_one_evidence` captures these relationships. The column `x` identifies the verification process class, while `y` identifies the class of the evidence produced. The enforcement of this relationship within the database ensures that workflow definitions for verification tasks are always associated with a defined output format or artifact type.

In practice, this means that a process defined as `PenetrationTest` must be configured to produce a `VulnerabilityReport`. If the process were defined without a corresponding evidence output, it would violate the axiom and fail schema validation. The table below provides instances of verification processes and their mandatory evidence outputs.

## 4.0 Attestation and Supporting Evidence

While verification focuses on the generation of new evidence through active processes, attestation is concerned with the validation of state based on existing artifacts. Axiom 3 (`attestation_with_supporting_evidence`) defines a Class `X` (Attestation) as a subclass of `bfo:0000015` (Process) that possesses the property `sdg:withSupportingEvidence`, referencing some Class `Y`. The verbalization "{X} is something that with supporting evidence {Y}" highlights the dependency of the attestation act on pre-existing data.

Attestation is typically a declarative act, often involving a human or a system agent asserting that a condition has been met. Unlike verification, which *produces* the proof, attestation *relies on* proof. This distinction is crucial for maintaining the chain of custody in compliance records. An attestation is only as valid as the supporting evidence it references; therefore, the ontological structure mandates a link between the attestation process and the evidence class that supports it.

### 4.2 Attestation Linkage Schema

The relational table `t_attestation_with_supporting_evidence` formalizes this dependency. The `x` column represents the attestation process class, and the `y` column represents the class of evidence required to support that attestation. This structure allows auditors to query an attestation record and immediately retrieve the class of the supporting document, facilitating rapid verification of assertions.

For instance, an `InternalControlAttestation` cannot stand alone; it must be supported by a `ControlTestWorkbook`. Similarly, a `VendorComplianceAttestation` requires a `VendorCertificate`. The table below details these mappings, ensuring that every attestation process is defined with its requisite evidentiary foundation.

## 5.0 Policy Jurisdiction and Governance Scope

Policies differ from requirements in their breadth and authority. Axiom 4 (`policy_equiv_jurisdiction_and_scope`) defines a Class `X` (Policy) as equivalent to a `cco:DirectiveICE` that possesses a specific jurisdiction (`Y`) and governs a specific scope (`Z`). This axiom separates the concept of a policy from a technical requirement by anchoring it to legal or organizational authority (Jurisdiction) and the domain of influence (Scope).

The `sdg:hasJurisdiction` property links the policy to the authority that mandates it, such as a legal body (e.g., GDPR, HIPAA) or an internal governing board. The `sdg:governsScope` property defines the subject matter of the policy. This dual constraint ensures that policies are not vague statements of intent but are formally anchored to a governing authority and a specific domain of application. This structure is essential for conflict resolution when multiple directives apply to a single asset; the jurisdiction property allows the system to determine precedence based on the hierarchy of authorities.

### 5.1 Jurisdictional Schema Implementation

The `t_policy_equiv_jurisdiction_and_scope` table implements this axiom. Columns `y` (Jurisdiction) and `z` (Scope) are mandatory, enforcing the axiom's requirement that a policy must have both a defined authority and a defined subject matter. This structure supports complex regulatory mapping, allowing the organization to matrix its policies against external regulations and internal operational domains.

The following table demonstrates how policies are instantiated. For example, the `DataResidencyPolicy` is mapped to the `EU_GDPR` jurisdiction and governs `PersonalData`. This explicit mapping allows for automated gap analysis, where the system can identify if a specific jurisdiction's requirements are fully covered by the defined policy scope.

## 6.0 Directive Lifecycle and Obsolescence

The final axiom addresses the temporal validity of directives. Axiom 5 (`directive_not_obsolete`) asserts that a Class `X` (Active Directive) is a subclass of `cco:DirectiveICE` and is explicitly *not* a member of Class `Y` (Obsolete Directive). This negative constraint (`not {Y:Class}`) is a powerful mechanism for lifecycle management, ensuring that the active set of governance directives is mutually exclusive with the set of retired or superseded directives.

In a dynamic regulatory environment, directives are frequently updated, superseded, or retired. Without an explicit axiom handling obsolescence, query engines might return both active and obsolete versions of a directive, leading to compliance confusion. By defining the active class through the negation of the obsolete class, the ontology creates a strict partition. This facilitates automated "sunset" processes, where a directive is transitioned from the active class to the obsolete class, automatically invalidating it for all active compliance checks.

### 6.1 Exclusionary Logic in Relational Systems

The table `t_directive_not_obsolete` captures the instances of active directives and the obsolete class from which they are excluded. While relational databases do not natively support "NOT" constraints in the same way description logics do, this table serves as a manifest of valid, non-obsolete directives. The `x` column lists the active directive classes, while the `y` column references the `ObsoleteDirective` class, formally documenting the exclusion.

This table acts as a whitelist for the governance framework. Any directive class appearing in column `x` is certified as current and valid. The reference to `ObsoleteDirective` in column `y` serves as a constant reminder of the exclusionary logic maintaining the integrity of the active directive set.
