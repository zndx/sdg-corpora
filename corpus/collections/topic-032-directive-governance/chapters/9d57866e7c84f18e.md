# Chapter 7: Formal Ontologies of Audit Governance and Compliance Verification

This chapter delineates the structural framework for mapping audit processes to relational data models using the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO). It provides a rigorous examination of five core axioms that define the lifecycle of a regulatory audit, from the identification of the artifact under examination to the final reporting of findings. The content is intended for systems architects and compliance officers seeking to implement evidence-anchored governance frameworks within enterprise resource planning (ERP) systems. Each section includes a verbalization of the ontology axiom, a definition of the corresponding relational schema, and practical instances derived from simulated audit scenarios.

## 1. Dataset Under Audit

The foundational entity in any audit engagement is the artifact or dataset subject to examination. In accordance with the axiom `dataset_under_audit`, the target of the audit is defined as a subclass of `cco:Artifact`, which is specifically undergoing a `bfo:0000015` (Process) denoted as "under audit." This distinction is critical for governance frameworks; it separates static data repositories from the dynamic process of their verification. The entity must be distinct, identifiable, and possess a persistent identity throughout the audit lifecycle.

The relational projection of this axiom is contained within table `t_dataset_under_audit`. This table serves as the central registry for all artifacts subject to the organization's compliance mandate. The primary key (`id`) ensures referential integrity, allowing other process tables to link specific audit actions to these immutable data artifacts. The column `x` represents the specific class or instance of the artifact being audited.

**1.1 Relational Schema and Implementation**

The schema below enforces the constraint that every dataset entry must be uniquely identifiable. In practice, this table is populated prior to the commencement of audit planning, serving as the "scope" definition.

```markdown
| id                | x                                |
|-------------------|----------------------------------|
| DAT-FIN-2023-Q3   | General_Ledger_Q3_2023           |
| DAT-HR-ACCESS-09  | Employee_Access_Logs_Sep         |
| DAT-ENV-EMISSIONS | Stack_Emissions_Data_YTD         |
| DAT-VENDOR-MASTER | Third_Party_Risk_Database        |
```

*Table 1: Instantiation of `t_dataset_under_audit` illustrating diverse artifact classes.*

The data in Table 1 demonstrates the variety of artifacts captured under this axiom. Row 1 represents a financial ledger, a typical target for fiscal audits. Row 2 represents security logs, pertinent to information technology (IT) governance audits. By populating `x` with descriptive class names, the system maintains semantic clarity while adhering to the strict structure of the relational model.

## 2. Audit For Period

An audit process is temporally bounded; it does not exist in a vacuum but is performed *for* a specific audit period. The axiom `audit_for_period` posits that the audit process (Class X) is a subprocess of `bfo:0000015` and possesses the object property `sdg:forAuditPeriod`, which links it to a specific temporal class or dataset (Class Y). In regulatory reporting, such as the Independent Auditors' Report for the Fiscal Year Ended June 30, 2020, this linkage is mandatory. The audit report is invalid without a clear definition of the timeframe it covers.

The table `t_audit_for_period` implements this relationship. It is crucial to note the Foreign Key constraint: column `y` must reference a valid identifier in the `t_dataset_under_audit` table. This structural dependency enforces the rule that an audit period cannot be defined independently of the dataset it contextualizes. In many implementations, the "Period" is treated as a dataset artifact (e.g., a time-series summary) to satisfy this schema constraint.

**2.1 Temporal Binding and Referential Integrity**

The following table demonstrates how specific audit engagements are bound to their respective reporting periods. The foreign key relationship ensures that the period (`y`) corresponds to a valid dataset entry established in Section 1.

```markdown
| id          | x                      | y                |
|-------------|------------------------|------------------|
| AFP-001     | FY2023_Financial_Audit | DAT-FIN-2023-Q3  |
| AFP-002     | Q3_Security_Review     | DAT-HR-ACCESS-09 |
| AFP-003     | Annual_Env_Comp_Check  | DAT-ENV-EMISSIONS|
```

*Table 2: Instantiation of `t_audit_for_period` linking audit processes to dataset-defined periods.*

In Table 2, the row with ID `AFP-001` links the process "FY2023_Financial_Audit" to the dataset "DAT-FIN-2023-Q3." This implies that the financial audit process is specifically scoped to the data contained within that quarterly ledger. This structure prevents ambiguity regarding the timeframe of the audit findings, a common deficiency in ad-hoc compliance reviews.

## 3. Audit Conducted By

Governance frameworks require the clear assignment of responsibility. The axiom `audit_conducted_by` establishes that an audit process (Class X) is a `bfo:0000015` (Process) that is `sdg:conductedBy` an instance of `cco:Person`. This axiom traces the agency of the audit, ensuring that there is always a responsible natural or legal person associated with the procedural execution. In the context of an Independent Auditors' Report, this maps to the signature block of the Certified Public Accountants (CPA) or the responsible audit firm partner.

The relational schema `t_audit_conducted_by` captures this association. While the schema provided is simplified—containing only the process identifier—it functions as a registry of auditable processes that have been assigned ownership. The presence of a row in this table asserts that the process `x` is valid and active, having been instantiated by an agent.

**3.2 Assignment of Audit Responsibility**

The table below lists audit processes that have been formally initiated and assigned. In a full expansion of this schema, a join to a `Person` table would be effected, but per the provided axiom, we list the process instances themselves.

```markdown
| id          | x                      |
|-------------|------------------------|
| ACB-001     | FY2023_Financial_Audit |
| ACB-002     | Q3_Security_Review     |
| ACB-003     | Vendor_Risk_Assessment |
```

*Table 3: Instantiation of `t_audit_conducted_by` listing active audit processes.*

The processes listed in Table 3, such as `FY2023_Financial_Audit` (ID `ACB-001`), are now formally recognized as conducted by an authorized agent. This status is a prerequisite for the process to generate findings. Without this entry, any subsequent outputs would lack the necessary authority to be considered valid audit evidence.

## 4. Audit Subclass

The scope of an audit is often defined by the specific controls or directives it targets. The axiom `audit_subclass` refines the audit process (Class X) by asserting that it `sdg:auditsControl` some `cco:DirectiveICE` (Information Content Entity). This means the audit is not merely a generic process but a specific subclass of investigation designed to verify adherence to a directive, policy, or control framework. For example, an audit might be specifically subclassed as a "SOC 2 Type 2 Audit" or an "ISO 27001 Surveillance Audit," each targeting different directive sets.

The table `t_audit_subclass` categorizes these processes. By populating this table, the governance framework distinguishes between a generic review and a formal compliance audit targeting specific internal controls.

**4.1 Control Directives and Audit Typology**

The following table illustrates how specific audit processes are categorized based on the directives they assess. This allows for the aggregation of audit results by control framework (e.g., grouping all audits related to "Information Security").

```markdown
| id          | x                      |
|-------------|------------------------|
| ASC-001     | FY2023_Financial_Audit |
| ASC-002     | Q3_Security_Review     |
```

*Table 4: Instantiation of `t_audit_subclass` identifying audits targeting specific directives.*

In Table 4, both the Financial Audit and the Security Review are identified as subclasses of auditing processes. The `x` column contains the process name, which, via the ontology, implies the existence of a relationship to a specific `DirectiveICE` (e.g., "IFRS Accounting Standards" for the Financial Audit, or "NIST 800-53" for the Security Review). This semantic linkage is vital for automated compliance reporting.

## 5. Audit With Findings

The ultimate output of the audit process is the generation of findings. The axiom `audit_with_findings` formalizes this by stating that the audit process (Class X) `sdg:hasFindings` some {Y:Class}. These findings are not free-text notes but structured entities, often linked back to the dataset under audit. The relational schema `t_audit_with_findings` enforces a link between the audit process and the finding entity (`y`), which is constrained to be a valid entry in the `t_dataset_under_audit` table.

This structure ensures that findings are evidence-based. A finding cannot exist in isolation; it must be attached to both the audit process that discovered it and the dataset artifact that contains the proof. This is the cornerstone of "evidence-anchored" documentation, allowing regulators to trace a reported issue directly back to the source data.
