# Regulatory Audit Ontologies in Relational Form

This chapter defines five core ontological patterns that structure audit processes over datasets and demonstrates each pattern through a deterministic relational schema. The schemas support primary-key and foreign-key joins that answer multi-hop questions about audit periods, conducting agents, control subclasses, and findings.

## 1 Ontology-to-Schema Mapping

The five axioms are realized as tables whose column types and foreign-key constraints are fixed by the slot signatures. Each table is introduced by a one-sentence statement of the axiom it embodies, followed by its primary-key/foreign-key structure and an example join path.

### 1.1 t_dataset_under_audit

Axiom 2 states that a dataset is an artifact placed under an audit process. The table therefore contains only an identifier column that serves as the primary key; every other table references this key when it must name a dataset that is being audited.

```sql
CREATE TABLE t_dataset_under_audit (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.2 t_audit_for_period

Axiom 1 states that an audit process exists for a specific audit period realized by a dataset. The table therefore carries a foreign key (y) that references t_dataset_under_audit.id; the primary key (id) uniquely identifies each period-qualified audit instance.

```sql
CREATE TABLE t_audit_for_period (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_dataset_under_audit(id)
);
```

A reader can obtain the dataset name for any given audit period by joining on y.

### 1.3 t_audit_conducted_by

Axiom 3 states that an audit process is conducted by a person. The table therefore records the person identifier in column x; its own primary key (id) allows other tables to reference the conducted-by fact without repeating the person value.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.4 t_audit_subclass

Axiom 4 states that an audit process audits a control directive information content entity. The table therefore stores the directive identifier in column x; its primary key permits later linkage to findings or periods.

```sql
CREATE TABLE t_audit_subclass (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.5 t_audit_with_findings

Axiom 5 states that an audit process yields findings that are themselves datasets. The table therefore carries a foreign key (y) that references t_dataset_under_audit.id; the primary key (id) distinguishes each finding instance.

```sql
CREATE TABLE t_audit_with_findings (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_dataset_under_audit(id)
);
```

## 3 Multi-hop Query Example

Question: Which person conducted the audit that produced findings on the dataset whose period is “Fiscal_Year_Ended_June_30_2020”?

Resolution path:  
1. Locate the period row in t_audit_for_period where x = “Fiscal_Year_Ended_June_30_2020”; its foreign key y yields DS-001.  
2. Locate the finding row in t_audit_with_findings where y = DS-001; its primary key is AF-400.  
3. The conducted-by table supplies the person for the same audit identifier (cross-referenced via shared process context).  

Joined result row:  
(AP-100, Fiscal_Year_Ended_June_30_2020, DS-001, AF-400, Material_Weakness_in_Internal_Control, AC-200, JARRED_GILMORE_PHILLIPS_PA)
