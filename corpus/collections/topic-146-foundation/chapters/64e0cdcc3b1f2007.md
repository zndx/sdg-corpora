# Chapter 7: Artifact Classification and Brand Attribution Protocols

## 7.1 Scope and Compliance Framework

This chapter establishes the mandatory protocols for the classification of physical entities within the centralized supply chain governance model. It details the axiomatic requirements for defining artifacts and the immutable rules governing the attribution of commercial brands to these entities. The guidelines provided herein are essential for maintaining data integrity, ensuring traceability, and facilitating automated compliance reporting across all regulated inventory systems. Adherence to these semantic structures is a prerequisite for all downstream auditing activities and regulatory submissions.

## 7.2 The Ontology of the Artifact

In the context of enterprise resource governance, the term "Artifact" is not merely a descriptive label for a physical object but a formal ontological classification derived from the Common Core Ontology (cco). An Artifact is defined as a distinct, continuant entity that has been produced by an agent through a process of manufacture or creation. Within our compliance framework, the designation of an entity as an Artifact triggers a specific set of data capture requirements, most notably the necessity to establish a provenance link to a manufacturing entity.

To operate a successful governance strategy, organizations must recognize that not all physical objects fall under the strict purview of this classification. However, for any object subject to warranty, safety regulation, or inventory valuation, the classification as a `cco:Artifact` is the foundational step. This classification serves as the antecedent for all subsequent property assertions, specifically those regarding brand identity.

### 7.2.1 The SubClassOf Axiom

The structural integrity of our data model relies on the SubClassOf axiom. We assert that any entity classified as a specific product type (X) is inherently a subclass of `cco:Artifact`. This is not a loose association; it is a logical entailment. If an entity is removed from the class of Artifacts, it ceases to be a product within the system and must be reclassified as waste, raw material, or an abstract concept.

This hierarchical structure ensures that all products inherit the properties of Artifacts. Consequently, any data validation rule applied to the generic class of Artifacts—such as the requirement for a unique identifier or a physical location status—automatically propagates to the specific product subclasses. This inheritance mechanism is critical for maintaining consistency across diverse inventory lines, ranging from office supplies to heavy machinery.

## 7.3 Brand Attribution and the `hasBrand` Property

The attribution of a brand to an artifact is a critical compliance control point. The `sdg:hasBrand` property serves as the semantic link between the physical object (the Artifact) and the legal or commercial entity responsible for its production and market identity. In formal ontology terms, this relationship is governed by an existential restriction: for a product to be validly classified, it *must* have a brand.

### 7.3.1 The Manchester Syntax Axiom

The formal logic governing this relationship is expressed in the Manchester Syntax axiom as follows:

`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasBrand some {Y:Class}`

This axiom asserts three necessary conditions for compliance:
1.  **Class Identity:** The subject X must be a defined Class.
2.  **Artifact Status:** X must be a subclass of `cco:Artifact`.
3.  **Brand Existence:** There must exist at least one relationship (some) between X and a Brand Class Y via the property `sdg:hasBrand`.

The verbalization of this axiom is: "{X} is something that has brand {Y}." This simple statement underpins the entire brand governance strategy. It prohibits the existence of "orphan" products—artifacts within the inventory database that lack a clear commercial origin. In audit scenarios, the absence of a valid `Y` (Brand) for any `X` (Product) constitutes a immediate data integrity failure.

### 7.3.2 Operational Implications

Operational teams must ensure that the Brand entity (Y) is defined within the approved vendor registry before any Product entity (X) can be introduced into the system. The relationship is directional and distinct; the Brand has the Product, not the other way around. This distinction is vital for liability tracing. In the event of a product recall, the system must be able to query the `sdg:hasBrand` property to instantly identify all artifacts associated with the implicated Brand Class.

## 7.4 Relational Mapping and Data Integrity

To implement these ontological axioms within a relational database management system (RDBMS), we project the logical structure into a deterministic schema. This translation ensures that the high-level semantic rules are enforced at the database layer through constraints and data types.

### 7.4.1 Schema Structure for `t_schemaorg_product_brand`

The primary vehicle for capturing the Artifact-Brand relationship is the table `t_schemaorg_product_brand`. This table embodies the axiom defined in Section 7.3.1. Its primary key is a surrogate key (`id`), ensuring that every specific product-brand pairing is unique and immutable.

The schema utilizes `VARCHAR(255)` data types for the `x` (Product Class) and `y` (Brand Class) columns to accommodate the standardized naming conventions used in the global taxonomy. The `NOT NULL` constraint on the `y` column enforces the existential restriction of the axiom; a row cannot be committed to the database without a valid Brand reference.

**Relational Schema Definition:**

```sql
CREATE TABLE t_schemaorg_product_brand (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:Artifact"],"family":"07_long_tail","is_complex":true,"template_id":"schemaorg_product_brand"}'
```

In this structure, `x` represents the specific subclass of the Artifact (e.g., "IndustrialCentrifuge"), and `y` represents the Brand Class (e.g., "SiemensEnergyAG"). The `id` serves as the internal reference code for the specific attribution record.

## 7.6 Audit and Verification Procedures

Regular audits of the `t_schemaorg_product_brand` table are required to ensure ongoing compliance with the ontology axioms. Auditors should verify the following:

1.  **Class Consistency:** Ensure that every value in column `x` is a recognized subclass of `cco:Artifact`. Any values that do not resolve to a defined class in the ontology must be flagged for remediation.
2.  **Brand Existence:** Verify that no values in column `y` are NULL or empty strings. Furthermore, confirm that the Brand Class referenced actually exists in the broader corporate ontology.
3.  **Cardinality Validation:** While the schema allows a Product to be associated with multiple Brands (via multiple rows with different `id`s but the same `x`), specific product lines may have a cardinality restriction of 1:1. Auditors must cross-reference the specific business rules for the product line in question.

Failure to maintain the integrity of these relationships compromises the traceability of the supply chain and exposes the organization to regulatory risk. By strictly adhering to the axiom that {X} is something that has brand {Y}, the organization ensures that every physical asset under its control is accounted for and traceable to its source.
