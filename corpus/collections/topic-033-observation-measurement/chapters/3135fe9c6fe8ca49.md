# Chapter 4: Ontological Formalization of Audit and Compliance Directives

This chapter delineates the structural and semantic framework governing audit processes, regulatory directives, and attestation protocols within a compliant enterprise architecture. The content herein establishes a formal mapping between OWL ontology axioms—specifically those derived from the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO)—and their corresponding relational schema implementations. The primary objective is to define the precise data structures required to evidence compliance with the Payment Card Industry Data Security Standard (PCI DSS) and related governance frameworks. Each section provides a rigorous definition of the ontological concept, followed by the relational schema necessary to support audit trails, verification logs, and periodic reporting.

## 4.1 Audit Conducted By

The foundational unit of governance is the audit process, formally defined as a `bfo:Process`. In accordance with Axiom 1, an audit is not a static entity but a temporal occurrence that necessitates an agent. The axiom `audit_conducted_by` establishes that any instance of an audit class (`X`) must be conducted by a person (`cco:Person`). This relationship ensures that every processual entity within the governance framework is attributable to a responsible agent, thereby establishing the chain of custody and accountability required for high-assurance environments.

The relational projection of this axiom isolates the audit instance (`x`) as the primary entity. The schema `t_audit_conducted_by` is designed to catalog these process instances. While the ontology links the process to a person, the relational schema presented here focuses on the enumeration of the audit events themselves, serving as the index for the broader governance record. The primary key (`id`) ensures that each audit process is uniquely identifiable within the system, preventing ambiguity in reporting.

## 4.2 PCI DSS Requirement

Governance directives are operationalized through specific regulatory requirements. Axiom 2, `pci_dss_requirement`, formalizes the relationship between a governing directive (`X`) and a specific PCI DSS requirement (`Y`). Here, `X` is a subclass of `cco:DirectiveICE` (Directive Information Content Entity), representing the textual or normative mandate, while `Y` represents the specific control objective derived from the PCI DSS framework. This axiom is critical for mapping high-level corporate policy to specific regulatory controls, ensuring that directives are not merely aspirational but are anchored to verifiable compliance standards.

The schema `t_pci_dss_requirement` implements this mapping. It is noteworthy that this table contains a foreign key constraint referencing the verification table (`t_requirement_min_one_verification`), establishing a dependency where a requirement must be associated with at least one defined verification method. This enforces the principle that a requirement without a verification mechanism is structurally invalid within this system.

*Table 4.2 maps Directive Information Content Entities (`x`) to specific PCI DSS requirements (`y`). The column `y` functions as a foreign key referencing the verification method, ensuring that every requirement is verifiable.*

## 4.3 Requirement Min One Verification

To ensure the efficacy of a directive, Axiom 3, `requirement_min_one_verification`, mandates that any directive (`X`) must be verified by a minimum of one verification method (`Y`). This axiom utilizes a "min 1" cardinality constraint, asserting that the absence of verification constitutes a violation of the governance model. The verification method (`Y`) acts as the procedural or technical instrument used to assess compliance with the directive.

The relational schema `t_requirement_min_one_verification` captures this relationship. In a strict implementation of the provided ontology, this schema exhibits a circular dependency with `t_pci_dss_requirement`; the verification method (`y`) in this table references the requirement ID in the requirement table. This structure implies that the verification method is inextricably linked to the requirement it validates, creating a tight coupling between the control objective and its assessment procedure.

*Table 4.3 details the verification methods (`id`) applicable to specific directives (`x`). The column `y` references the originating requirement ID, enforcing the integrity of the compliance verification loop.*

## 4.4 Requirement Only Satisfied By

Axiom 4, `requirement_only_satisfied_by`, introduces a restriction on the satisfaction of directives. It asserts that a directive (`X`) is satisfied *only* by specific classes of entities or procedures (`Y`). This is a universal restriction in the ontology, meaning that if a satisfaction mechanism is not of class `Y`, it cannot satisfy `X`. This axiom is essential for preventing "control drift," where organizations might attempt to satisfy a security requirement using an inappropriate or unapproved method.

The schema `t_requirement_only_satisfied_by` enforces this restriction by linking the directive to its sanctioned satisfier. The foreign key constraint again references the PCI DSS requirement table, indicating that the valid satisfiers are defined in the context of the specific regulatory requirement. This ensures that the evidence of compliance is strictly relevant to the control being assessed.

**Table 4.4: Sanctioned Satisfiers by Requirement**

| :--- | :--- | :--- |

| SAT-CTRL-02 | NetworkAccessControlPolicy | DIR-002 |

| SAT-CTRL-04 | VulnerabilityManagementProgram | DIR-004 |

*Table 4.4 defines the entities (`id`) that are permitted to satisfy the directives (`x`). The reference to `y` ensures that the satisfaction mechanism is aligned with the specific PCI DSS requirement logic.*

## 4.5 Attestation At Period

The final concept, defined by Axiom 5 (`attestation_at_period`), grounds the audit process in time. An attestation (`X`), which is a subclass of `bfo:Process` (specifically a process of asserting validity), must occur within a specific attestation period (`Y`). This axiom facilitates temporal indexing of compliance activities, allowing the organization to report on the status of controls at discrete points in time (e.g., quarterly, annually).

The schema `t_attestation_at_period` links the attestation process to the relevant requirement period. By referencing the PCI DSS requirement table, this schema ensures that attestations are performed within the cadence required by the specific directive. This is crucial for maintaining continuous compliance and for generating the time-stamped evidence required by auditors and regulators.
