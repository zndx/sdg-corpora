# Modeling Directive Governance in PCI DSS Compliance Audits

This chapter presents five relational tables that instantiate OWL axioms for directive information content entities, processes, and verification constraints within PCI DSS compliance auditing. The tables support cross-table joins that resolve multi-hop queries over conducted-by relations, requirement satisfactions, and attestation periods.

## 1 Ontology-to-Relation Mapping

The axioms define five table structures. Each table uses an opaque identifier as primary key. Foreign-key columns encode the existential and universal restrictions stated in the Manchester syntax.

### 1.1 Audit Conducted By

Axiom 1 projects processes that must be conducted by a person. The primary key `id` uniquely identifies each conducted-by assertion; the column `x` holds the process class identifier. No foreign key is present because the person reference is external to this schema.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.2 PCI DSS Requirement

Axiom 2 states that a directive information content entity carries at least one PCI DSS requirement. The primary key `id` identifies the directive; `x` names the directive class; `y` is a foreign key to the verification table required by the existential restriction.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_requirement_min_one_verification(id)
);
```

### 1.3 Requirement Minimum One Verification

Axiom 3 asserts that every directive must be verified by at least one entity. The primary key `id` identifies the directive; `x` repeats the directive class; `y` is a foreign key back to the PCI DSS requirement table, closing the mutual existential constraint.

```sql
CREATE TABLE t_requirement_min_one_verification (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

### 1.4 Requirement Only Satisfied By

Axiom 4 restricts satisfaction to a single class of entity. The primary key `id` identifies the directive; `x` names the directive class; `y` is a foreign key to the PCI DSS requirement table.

```sql
CREATE TABLE t_requirement_only_satisfied_by (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

### 1.5 Attestation at Period

Axiom 5 binds a process to an attestation period. The primary key `id` identifies the attestation event; `x` names the process class; `y` is a foreign key to the PCI DSS requirement table.

```sql
CREATE TABLE t_attestation_at_period (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

## 3 Cross-Join Demonstration

Join path:  
t_attestation_at_period.y = t_pci_dss_requirement.id  
t_pci_dss_requirement.y = t_requirement_min_one_verification.id  
t_audit_conducted_by.x = t_pci_dss_requirement.x (via shared class name)
