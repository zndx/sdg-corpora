# Chapter 4: Ontological Mapping of Compliance Directives and Audit Processes

This chapter delineates the formal ontological structures required to map compliance directives—specifically within the Payment Card Industry Data Security Standard (PCI DSS) framework—to relational database schemas suitable for audit reporting. The scope of this text is restricted to the precise definition of five core axioms governing the relationship between audit processes, requirements, verification methods, satisfaction criteria, and attestation periods. The content herein provides the necessary semantic grounding for generating evidence-anchored documentation, ensuring that all data entities are traceable to their ontological definitions and that relational integrity is maintained across foreign key constraints.

## 4.1 Audit Conducted By

The foundational unit of governance is the audit process, formally defined within the Basic Formal Ontology (BFO) as a processual entity (`bfo:0000015`). An audit is not a static object but a temporally bounded event that occurs within a specific span of time. To establish agency and accountability, the ontology asserts that any audit process (`X`) must be conducted by a person (`cco:Person`). This axiom, `audit_conducted_by`, ensures that procedural activities are never orphaned; they must be attributable to a responsible agent with the capacity to act.

In the context of relational schema implementation, this axiom is projected onto the table `t_audit_conducted_by`. The structure is straightforward: a primary key (`id`) and the class reference to the audit process (`x`). While the axiom implies a relationship to a person, the schema provided for this specific axiom isolates the process entity. This design choice facilitates the listing of defined audit types before linking them to specific personnel records in a broader join operation.

Consider the following data instances representing distinct audit processes defined within an institutional governance framework. These entries serve as the processual backbone for subsequent compliance mapping.

**Table 4.1: Audit Process Registry**

| id | x |
| :--- | :--- |
| `AUD-2024-Q1` | `QuarterlyAccessAudit` |
| `AUD-2024-ANN` | `AnnualSystemReview` |
| `AUD-2024-INC` | `IncidentResponseAudit` |
| `AUD-2024-VEND` | `VendorRiskAssessment` |

*Table 4.1 enumerates specific audit process classes. The primary key `id` serves as the unique identifier for the process instance, while `x` denotes the specific class of the audit being conducted, consistent with the `bfo:Process` constraint.*

The registration of these processes is a prerequisite for any compliance activity. For instance, the `QuarterlyAccessAudit` (ID: `AUD-2024-Q1`) is established as a process that must be executed by a qualified individual. The ontology does not merely record that an audit happened; it structures the definition of the audit itself, ensuring that when a person is assigned, the assignment is semantically valid. This prevents the assignment of a person to a non-processual entity, such as a policy document, thereby maintaining logical rigor in the governance model.

## 4.2 PCI DSS Requirement Mapping

Compliance frameworks are composed of directives, which are Information Content Entities (ICE) defined in the Common Core Ontologies (`cco:DirectiveICE`). The second axiom, `pci_dss_requirement`, formalizes the relationship between a governing directive (`X`) and a specific requirement class (`Y`). The verbalization "{X} is something that pci dss requirement {Y}" indicates that the directive encompasses or mandates the requirement.

This relationship is critical for decomposing complex standards like PCI DSS into manageable, auditable components. The relational schema `t_pci_dss_requirement` captures this mapping. It consists of a primary key (`id`), the directive class (`x`), and the requirement class (`y`). A critical constraint in this schema is the foreign key requirement: `y` must reference an existing identifier in the `t_requirement_min_one_verification` table. This creates a dependency where a requirement cannot exist unless it is verifiable, enforcing the principle that untestable requirements are invalid within this governance framework.

The following table illustrates the mapping of high-level security directives to specific PCI DSS requirements. Note that the `y` values (Requirement IDs) correspond to verification entries defined in the subsequent section (4.3), satisfying the foreign key constraint.

**Table 4.2: Directive to Requirement Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `REQ-001` | `NetworkSecurityPolicy` | `VER-001` |
| `REQ-002` | `DataEncryptionStandard` | `VER-002` |
| `REQ-003` | `VulnerabilityManagementProgram` | `VER-003` |
| `REQ-004` | `AccessControlMechanism` | `VER-004` |

*Table 4.2 maps directive classes (`x`) to requirement classes (`y`). The column `y` acts as a foreign key to the verification table, ensuring that every requirement `REQ-001` through `REQ-004` has a corresponding verification method defined by `VER-001` through `VER-004`.*

For example, the directive `NetworkSecurityPolicy` (`REQ-001`) is linked to the requirement `VER-001`. In a fully populated system, `VER-001` would represent the specific technical or procedural control (e.g., "Firewall Configuration Review") that satisfies the policy. This structure allows auditors to trace the lineage from a high-level strategic document down to a specific, verifiable control point. The deterministic derivation of this schema from the ontology ensures that the "long tail" of compliance requirements is systematically captured and linked to verification protocols.

## 4.3 Requirement Verification Protocols

The axiom `requirement_min_one_verification` addresses the necessity of evidence. It asserts that a directive information content entity (`X`) must be verified by a minimum of one verification method (`Y`). The Manchester syntax `sdg:verifiedBy min 1 {Y:Class}` enforces a cardinality constraint, ensuring that compliance is not self-declared but is substantiated by a distinct verification activity.

The corresponding relational schema, `t_requirement_min_one_verification`, establishes a bidirectional link with the requirement table. While the requirement table references the verification table via its `y` column, this table references the requirement table via its `y` column. This circular dependency models the real-world coupling of a control and its test: a requirement defines the scope of a verification, and a verification validates a specific requirement.

The data below demonstrates the verification methods associated with the requirements introduced in the previous section. The `y` column in this table references the `id` from the requirement table, closing the loop.

**Table 4.3: Verification Method Registry**

| id | x | y |
| :--- | :--- | :--- |
| `VER-001` | `FirewallRuleSetReview` | `REQ-001` |
| `VER-002` | `CryptographicKeyAudit` | `REQ-002` |
| `VER-003` | `QuarterlyScanProcess` | `REQ-003` |
| `VER-004` | `UserAccessLogReview` | `REQ-004` |

*Table 4.3 details the verification classes (`x`) and links them back to their parent requirements (`y`). The entry `VER-001` (FirewallRuleSetReview) is the method used to verify `REQ-001` (NetworkSecurityPolicy), satisfying the `min 1` cardinality constraint.*

This structure is essential for audit planning. When an auditor prepares to assess the `NetworkSecurityPolicy`, the system retrieves `VER-001`, indicating that a `FirewallRuleSetReview` is the mandatory procedure. The constraint `min 1` guarantees that there is no null state; every directive in the system is inherently tied to an active verification mechanism. This eliminates the risk of "zombie" policies—directives that exist in documentation but have no assigned validation method.

## 4.4 Satisfaction Criteria

While verification defines *how* a requirement is checked, the axiom `requirement_only_satisfied_by` defines *what* constitutes a successful outcome. It asserts that a directive (`X`) is satisfied *only* by a specific class of artifact or state (`Y`). The use of the "only" restriction in the ontology (`sdg:satisfiedBy only {Y:Class}`) is a strong logical constraint: it implies that no other class of entity can validly claim to satisfy the directive.

In the relational schema `t_requirement_only_satisfied_by`, this is represented by linking the satisfaction criteria (`y`) to the requirement (`x`). The foreign key constraint ensures that the satisfaction criteria are anchored to a valid PCI DSS requirement (referencing `t_pci_dss_requirement`). This enforces a strict validation hierarchy: satisfaction is not a free-floating concept but is strictly bound to the requirement it fulfills.

The following table defines the specific evidence or state that satisfies the requirements mapped in Section 4.2.

**Table 4.4: Satisfaction Criteria Definition**

| id | x | y |
| :--- | :--- | :--- |
| `SAT-001` | `CompliantConfigurationState` | `REQ-001` |
| `SAT-002` | `StrongEncryptionEvidence` | `REQ-002` |
| `SAT-003` | `AcceptedRescanReport` | `REQ-003` |
| `SAT-004` | `PrivilegedAccessJustification` | `REQ-004` |

*Table 4.4 specifies the classes (`x`) that are accepted as proof of satisfaction. The `y` column links these to the requirement IDs. For instance, only a `CompliantConfigurationState` (`SAT-001`) is accepted to satisfy `REQ-001`.*

This axiom prevents the substitution of evidence. An auditor cannot accept a generic "system check" as proof for `REQ-001` (NetworkSecurityPolicy); the ontology dictates that only a `CompliantConfigurationState` is valid. This precision is vital for automated compliance systems and rigorous manual audits alike, as it reduces ambiguity and the potential for subjective interpretation of compliance status.

## 4.5 Attestation Periods

The final axiom, `attestation_at_period`, introduces the temporal dimension to the governance framework. It asserts that a process (`X`), specifically an audit or review process, occurs *at* a specific attestation period (`Y`). This links the processual entity (`bfo:0000015`) to a temporal class, anchoring the audit in time.

The schema `t_attestation_at_period` links the attestation record (`x`) to the requirement (`y`) via a foreign key. This design implies that the attestation is performed *against* a specific requirement during a defined period. It ties the "when" (the period) to the "what" (the requirement), ensuring that attestations are not vague temporal markers but are explicitly associated with the compliance controls being validated.

The table below provides instances of attestation periods linked to the specific requirements they govern.

**Table 4.5: Attestation Period Schedule**

| id | x | y |
| :--- | :--- | :--- |
| `ATT-2024-H1` | `FirstHalfAttestation` | `REQ-001` |
| `ATT-2024-H1` | `FirstHalfAttestation` | `REQ-002` |
| `ATT-2024-Q3` | `ThirdQuarterAttestation` | `REQ-003` |
| `ATT-2024-ADHOC` | `AdHocAttestation` | `REQ-004` |

*Table 4.5 maps attestation periods (`x`) to requirements (`y`). The `FirstHalfAttestation` (`ATT-2024-H1`) covers both `REQ-001` and `REQ-002`, indicating that these requirements are attested to on a semi-annual basis, while `REQ-003` follows a quarterly schedule.*

This temporal mapping allows the organization to generate compliance reports based on time slices. For example, a query for all attestations in `ATT-2024-H1` would return the network security and encryption requirements, confirming that they have been reviewed and signed off within that specific window. This is the final step in the audit trail, moving from the definition of the process to the specific, time-bound confirmation of compliance.
