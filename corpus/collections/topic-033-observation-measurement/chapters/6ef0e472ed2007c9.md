# Chapter 4: Governance Frameworks and Compliance Verification Protocols

## 4.1 Scope and Preamble

This chapter delineates the structural relationships governing audit processes, Payment Card Industry Data Security Standard (PCI DSS) requirements, and attestation periods within an enterprise ontology. The content herein establishes formal definitions for directives, verification mechanisms, and the specific role of personnel in conducting audits. It is grounded in the Basic Formal Ontology (BFO) and utilizes the Common Core Ontologies (CCO) to ensure semantic interoperability between governance artifacts. The following sections provide a rigorous analysis of five core axioms that define the compliance landscape, supported by relational data tables that instantiate these concepts. These protocols are essential for maintaining the integrity of information security governance and ensuring that all directive information content entities are traceable to specific verification actions and responsible agents.

## 4.2 Audit Conducted By

### 4.2.1 Ontological Definition

The foundational unit of governance oversight is the audit process. In accordance with the axiom `audit_conducted_by`, an audit is formally defined as a subclass of `bfo:0000015` (Process). This process is not autonomous; it is axiomatically dependent on the existence of an agent that executes it. Specifically, the audit process is realized through the `sdg:conductedBy` object property, which necessitates a relationship with a `cco:Person`.

This relationship establishes a chain of custody and responsibility for the audit activity. It ensures that every process labeled as an "Audit" within the system is anchored to a human agent, thereby preventing the existence of orphaned or automated processes without accountable oversight. The ontology asserts that {X}, representing the Audit class, is something that is conducted by a person. This distinction is critical for regulatory frameworks that require human sign-off on compliance assessments.

### 4.2.2 Relational Implementation

The relational schema for this axiom is encapsulated in the table `t_audit_conducted_by`. The primary key is the identifier (`id`), while the column `x` represents the specific instance of the Audit class. The structure enforces that every entry in this table corresponds to a distinct process event initiated by a recorded individual in the broader personnel registry.

**Table 4.1: Audit Process Log (t_audit_conducted_by)**

| id | x |
| :--- | :--- |
| AUD-2023-001 | QuarterlyAccessReview |
| AUD-2023-002 | AnnualPenetrationTest |
| AUD-2023-003 | FirewallConfigurationAudit |
| AUD-2023-004 | IncidentResponseDrill |
| AUD-2023-005 | PhysicalSecurityAudit |

The data presented in Table 4.1 illustrates a log of audit events. Each `id` serves as a unique reference for the governance record, while the `x` value denotes the specific class or instance of the audit process being conducted. For instance, `AUD-2023-001` tracks the `QuarterlyAccessReview`, a process mandated by internal governance policies. The existence of this record implies, via the underlying axiom, that a specific `cco:Person` is assigned as the conductor of this audit, satisfying the `sdg:conductedBy` requirement.

## 4.3 PCI DSS Requirement

### 4.3.1 Directive Information Content Entities

Compliance frameworks are operationalized through Directives. The axiom `pci_dss_requirement` classifies these directives as subclasses of `cco:DirectiveICE` (Information Content Entity). These entities are not physical artifacts but rather prescriptive statements or requirements that dictate specific behaviors or configurations within the information system.

The axiom establishes a relationship `sdg:pciDssRequirement` linking a Directive {X} to a specific Requirement Class {Y}. This mapping allows the ontology to distinguish generic policy statements from specific regulatory obligations derived from the PCI DSS framework. It creates a granular layer of governance where high-level directives are decomposed into verifiable requirement components.

### 4.3.2 Dependency and Verification

A critical aspect of this axiom is its relational dependency. The schema for `t_pci_dss_requirement` includes a foreign key constraint linking the requirement entity (`y`) to the verification table `t_requirement_min_one_verification`. This enforces a database-level rule that a PCI DSS requirement cannot exist in isolation; it must be associated with at least one defined verification method. This structure embodies the compliance principle that "a requirement is only as good as its test."

**Table 4.2: PCI DSS Requirement Mapping (t_pci_dss_requirement)**

| id | x | y |
| :--- | :--- | :--- |
| DIR-PCI-01 | NetworkSegmentationPolicy | VER-SEG-01 |
| DIR-PCI-02 | DataEncryptionStandard | VER-ENC-01 |
| DIR-PCI-03 | AccessControlMechanism | VER-ACC-01 |
| DIR-PCI-04 | VulnerabilityManagementProgram | VER-VULN-01 |
| DIR-PCI-05 | LoggingMechanism | VER-LOG-01 |

In Table 4.2, the column `x` identifies the Directive (e.g., `NetworkSegmentationPolicy`), while column `y` contains the identifier of the verification protocol (`VER-SEG-01`). The foreign key constraint ensures that `VER-SEG-01` is a valid entry in the verification registry. This linkage guarantees that for every directive classified as a PCI DSS requirement, there is a pre-existing, defined procedure for verifying that requirement. The `id` column (`DIR-PCI-01`) provides the unique handle for the directive entity itself.

## 4.4 Requirement Min One Verification

### 4.4.1 Verification Constraints

The axiom `requirement_min_one_verification` introduces a cardinality constraint to the governance model. It asserts that a Directive Information Content Entity {X} must be verified by a minimum of one Verification Class {Y}. This is expressed in Manchester syntax as `sdg:verifiedBy min 1 {Y:Class}`.

This constraint prevents the creation of "zombie" requirements—directives that are mandated but have no mechanism for checking compliance. It enforces a one-to-many or one-to-one relationship where the directive is the subject and the verification method is the object. The ontology treats the verification process as a distinct class of entity, allowing for different types of verification (e.g., automated scans, manual inspections, log reviews) to be categorized and applied to different directives.

### 4.4.2 Reciprocal Referential Integrity

The relational schema for this concept, `t_requirement_min_one_verification`, exhibits a circular dependency with the `t_pci_dss_requirement` table. The `y` column in this table, representing the Verification entity, contains a foreign key reference back to `t_pci_dss_requirement(id)`.

This circularity is intentional and models the tight coupling between a requirement and its verification. It implies that a verification method is defined *in the context of* a specific requirement instance. While in pure normalization this might suggest a merge, in a compliance ontology, it preserves the distinct identity of the "Verification" as a process or artifact while binding it irrevocably to the "Requirement" it serves.

**Table 4.3: Minimum Verification Protocol (t_requirement_min_one_verification)**

| id | x | y |
| :--- | :--- | :--- |
| VER-SEG-01 | NetworkSegmentationVerification | DIR-PCI-01 |
| VER-ENC-01 | CryptographicValidator | DIR-PCI-02 |
| VER-ACC-01 | PrivilegedAccessReview | DIR-PCI-03 |
| VER-VULN-01 | QuarterlyScanAssessment | DIR-PCI-04 |
| VER-LOG-01 | LogIntegrityCheck | DIR-PCI-05 |

Table 4.3 demonstrates the implementation of the minimum verification constraint. The row with `id` `VER-SEG-01` represents the verification class `NetworkSegmentationVerification`. The column `x` links this verification to the broader directive class, while column `y` references the specific PCI DSS requirement instance `DIR-PCI-01`. This data structure confirms that the directive `NetworkSegmentationPolicy` (from Table 4.2) has a defined, mandatory verification procedure, satisfying the `min 1` cardinality rule.

## 4.5 Requirement Only Satisfied By

### 4.5.1 Satisfaction Restrictions

The axiom `requirement_only_satisfied_by` adds a layer of restriction to the compliance model. It states that a Directive Information Content Entity {X} is satisfied *only* by a specific Class {Y}. The use of the "only" (universal restriction) in the ontology implies that if an instance of {X} is considered satisfied, the entity that satisfied it must necessarily be an instance of {Y}.

This is a powerful construct for governance frameworks because it limits the scope of acceptable evidence. For example, a requirement regarding "two-factor authentication" might be restricted to being satisfied *only* by a "Hardware Token" class, thereby excluding "Knowledge-based answers" as a valid satisfaction method, even if the latter technically provides two factors. This axiom enforces rigor in how compliance is demonstrated.

### 4.5.2 Schema and Data Consistency

The relational table `t_requirement_only_satisfied_by` captures this restriction. Similar to the verification table, it relies on a foreign key constraint where the satisfaction method (`y`) references the primary requirement ID in `t_pci_dss_requirement`. This design reinforces the concept that the valid methods for satisfying a requirement are properties inherent to the requirement's definition itself.

**Table 4.4: Satisfaction Constraints (t_requirement_only_satisfied_by)**

| id | x | y |
| :--- | :--- | :--- |
| SAT-SEG-01 | RouterACLConfiguration | DIR-PCI-01 |
| SAT-ENC-01 | AES-256EncryptionModule | DIR-PCI-02 |
| SAT-ACC-01 | LDAPDirectoryService | DIR-PCI-03 |
| SAT-VULN-01 | ASVScanTool | DIR-PCI-04 |
| SAT-LOG-01 | SIEMAggregator | DIR-PCI-05 |

In Table 4.4, the `x` column defines the specific class or configuration that is permitted to satisfy the requirement. For the requirement `DIR-PCI-02` (Data Encryption), the only valid satisfier is listed as `SAT-ENC-01`, which corresponds to the `AES-256EncryptionModule`. The `y` column links this satisfaction rule back to the parent requirement ID. This structure ensures that any compliance report claiming `DIR-PCI-02` is satisfied must reference an instance of `AES-256EncryptionModule`; any other encryption method would violate the "only satisfied by" constraint encoded in this table.

## 4.6 Attestation At Period

### 4.6.1 Temporal Binding of Processes

The final axiom, `attestation_at_period`, addresses the temporal dimension of governance. It classifies the attestation process as a `bfo:0000015` (Process) that occurs at a specific `sdg:atAttestationPeriod`. This binds the act of attestation—where an auditor or responsible party formally asserts that a requirement is met—to a defined time window.

In compliance frameworks, attestations are not timeless; they are valid only for specific durations (e.g., Q3 2023, Fiscal Year 2024). This axiom allows the system to query for "attestations valid for Period Y" or to flag attestations that have expired because their associated period has concluded. It links the process of attestation directly to the temporal context of the requirement being verified.

### 4.6.2 Period-Requirement Linkage

The schema for `t_attestation_at_period` links the attestation process (`x`) to a period identifier (`y`). Consistent with the other tables, the `y` column references the `t_pci_dss_requirement` table. This design choice suggests that the "Period" is often defined relative to the specific requirement cycle or that the attestation is specifically targeting the validity of a requirement within a certain timeframe.

**Table 4.5: Attestation Period Registry (t_attestation_at_period)**

| id | x | y |
| :--- | :--- | :--- |
| ATT-Q3-23 | Q3_2023_SecurityAttestation | DIR-PCI-01 |
| ATT-Q3-23 | Q3_2023_SecurityAttestation | DIR-PCI-02 |
| ATT-Q4-23 | Q4_2023_SecurityAttestation | DIR-PCI-03 |
| ATT-Q4-23 | Q4_2023_SecurityAttestation | DIR-PCI-04 |
| ATT-ANNUAL | FY2024_AnnualReview | DIR-PCI-05 |

Table 4.5 records the attestation events. The `id` `ATT-Q3-23` represents the attestation process `Q3_2023_SecurityAttestation`. The `y` column links this attestation to specific requirements, such as `DIR-PCI-01` and `DIR-PCI-02`. This indicates that during the Q3 2023 period, formal attestation was provided for both the Network Segmentation Policy and the Data Encryption Standard. The data model supports multiple attestations for different requirements within the same period, or distinct attestations for different periods, as seen in the `FY2024_AnnualReview` entry. This structure provides a precise audit trail of *when* compliance was formally asserted.
