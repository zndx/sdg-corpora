# Compliance Artifact Ontologies in PCI DSS Reporting Systems

This chapter defines five relational tables that instantiate ontological axioms for artifacts supporting compliance claims. The tables capture class-level entities whose instances participate in claim-support relations, PCI DSS directives, and tax identification assertions. Data rows are drawn from a payment processor audit environment and are structured for cross-table verification of multi-hop regulatory queries.

## 1 Schema Overview

The schema consists of five tables, each corresponding to one axiom. Primary keys are the `id` columns. Columns named `x` and `y` hold class references that function as join keys when values match identifiers in other tables. No additional columns are introduced.

### 1.1 t_trace_supports_claim

This table embodies AXIOM 1. Column `id` is the primary key. Column `x` stores the class that supports a descriptive claim. A reader can join `x` values to identifiers appearing in `t_pci_dss_requirement` to retrieve the directive satisfied by a given trace.

| id | x |
| id | x |
| trace_001 | LineageTrace |
| trace_002 | EventLogTrace |
| trace_003 | NetworkFlowTrace |
| trace_004 | AccessLogTrace |
| trace_005 | BatchProcessTrace |

### 1.2 t_kernel_anomaly_supports_claim

This table embodies AXIOM 2. Column `id` is the primary key. Column `x` stores the artifact class that supports a claim. Values in `x` may be joined to `y` values in `t_schemaorg_org_taxid` when an anomaly record is used to substantiate an organizational assertion.

| id | x |
| id | x |
| anomaly_001 | KernelPanicRecord |
| anomaly_002 | MemoryCorruptionRecord |
| anomaly_003 | DriverFaultRecord |
| anomaly_004 | SchedulerAnomalyRecord |
| anomaly_005 | InterruptStormRecord |

### 1.3 t_column_lineage_for_compliance_claim

This table embodies AXIOM 3. Column `id` is the primary key. Column `x` stores the lineage artifact class. A join on `x` to matching `x` values in `t_trace_supports_claim` yields the combined evidence set for a single compliance claim.

| id | x |
| id | x |
| lineage_001 | ColumnMappingArtifact |
| lineage_002 | TransformationLogArtifact |
| lineage_003 | SchemaEvolutionArtifact |
| lineage_004 | DataProvenanceArtifact |
| lineage_005 | QueryRewriteArtifact |

### 1.4 t_pci_dss_requirement

This table embodies AXIOM 4. Column `id` is the primary key. Column `x` stores the directive class; column `y` stores the required claim class. The `y` column acts as a foreign-key reference to claim-supporting classes in the three preceding tables.

| id | x | y |
| id | x | y |
| req_001 | PCI_DSS_3_4 | EncryptionClaim |
| req_002 | PCI_DSS_8_2 | AccessControlClaim |
| req_003 | PCI_DSS_10_2 | AuditTrailClaim |
| req_004 | PCI_DSS_12_10 | IncidentResponseClaim |
| req_005 | PCI_DSS_6_5 | SecureDevelopmentClaim |

### 1.5 t_schemaorg_org_taxid

This table embodies AXIOM 5. Column `id` is the primary key. Column `x` stores the organization class; column `y` stores the tax identifier class. Values in `x` serve as join targets for `y` references appearing in `t_pci_dss_requirement` when an organization-level claim must be verified.

| id | x | y |
| id | x | y |
| org_001 | AcmePayments | EIN_47-1234567 |
| org_002 | VertexData | EIN_52-9876543 |
| org_003 | NorthGateSecure | EIN_38-4567890 |
| org_004 | LedgerForge | EIN_61-2345678 |
| org_005 | CipherTrust | EIN_29-8765432 |

## 2 Cross-Join Example

To determine which tax-identified organization supplies the kernel anomaly record supporting PCI DSS requirement req_003, perform the following joins:

- Start with `t_pci_dss_requirement` row where `id = 'req_003'` (`y = 'AuditTrailClaim'`).
- Locate `t_kernel_anomaly_supports_claim` rows whose `x` matches a supporting class for that claim.
- Join the resulting `x` value to `t_schemaorg_org_taxid` on `y` to retrieve the tax identifier.

The joined result row is:

`req_003 | AuditTrailClaim | anomaly_002 | MemoryCorruptionRecord | org_001 | EIN_47-1234567`
