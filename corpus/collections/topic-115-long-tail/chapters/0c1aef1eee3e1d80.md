# Chapter 4: Ontological Mapping of Audit Evidence and Compliance Artifacts

## 4.0 Scope and Preamble

This chapter establishes the formal ontological framework required to map discrete data artifacts to compliance claims within a regulated digital environment. The definitions provided herein are grounded in the BFO (Basic Formal Ontology) and CCO (Common Core Ontologies) upper-level structures, ensuring that audit evidence is not merely collected but is structurally validated against specific regulatory axioms. The following sections detail five distinct conceptual mappings—ranging from trace evidence to regulatory directives—necessary for establishing a defensible chain of custody and logical verification in automated audit systems. Each section includes a relational schema projection to facilitate the implementation of these concepts within SQL-based governance repositories.

## 4.1 Trace Supports Claim

### Area of Focus #1
**The Audit Trail, Faced With High-Volume Transaction Logs, Requires Formal Definition to Ensure That Every Traceable Event Is Capable of Substantiating a Specific Descriptive Claim, Thereby Preventing Unsubstantiated Data Accumulation.**

**COMPLIANCE RIGHTS IMPACTED**
■ ■ The Right to Verifiable Evidence
■ ■ The Right to Data Provenance

In the context of formal ontology, a "trace" is not merely a log entry; it is an entity that must satisfy the axiom `trace_supports_claim`. This axiom asserts that a Class X acts as a processual entity (`bfo:0000015`) which functions to support a `cco:DescriptiveICE` (Descriptive Information Content Entity). For an audit trail to be valid, it must demonstrate that the recorded trace (X) provides the informational substrate required to validate a specific claim about the system state or user action.

The verbalization of this axiom—"{X} is something that supports claim descriptive information content entity"—mandates that no trace exists in isolation. Every trace identified in the system must be queryable as evidence for a proposition. For instance, a database transaction log entry is not simply a row in a table; it is an entity of Class `TransactionLogEntry` that supports the claim "User A modified Record B at Timestamp T."

The relational projection of this axiom isolates the trace entity (X) to facilitate the joining of evidence records with the claims they substantiate. The primary key (`id`) ensures referential integrity, while the column `x` classifies the nature of the trace artifact.

## 4.2 Kernel Anomaly Supports Claim

### Area of Focus #2
**System Instability Events, Specifically Kernel-Level Anomalies, Must Be Classified as Artifacts That Support Claims Regarding System Integrity or Security Incidents.**

**GOVERNANCE STANDARDS IMPACTED**
■ ■ NIST SP 800-53 (Incident Response)
■ ■ ISO/IEC 27001 (Availability)

While general traces provide broad support for system claims, kernel-level anomalies represent a specific subset of evidence defined by the axiom `kernel_anomaly_supports_claim`. This axiom refines the general trace concept by restricting Class X to be a subclass of `cco:Artifact`. Unlike a processual trace, an artifact is a distinct, persistable entity generated by a process. In this case, the artifact is the anomaly record itself (e.g., a core dump or a kernel panic log), which serves to support a `cco:DescriptiveICE` regarding a failure state.

The verbalization—"{X} is something that supports claim descriptive information content entity"—remains structurally similar to the previous axiom; however, the restriction of X to `cco:Artifact` implies that the evidence is a discrete object (a file, a binary blob, or a structured error report) rather than a transient process signal. This distinction is critical for forensic analysis, as artifacts can be hashed, stored, and independently verified, whereas transient process signals may require real-time capture.

The schema for `t_kernel_anomaly_supports_claim` mirrors the trace table but enforces the semantic understanding that the values in column `x` refer specifically to artifact classes capable of being archived as immutable evidence.

## 4.3 Column Lineage for Compliance Claim

### Area of Focus #3
**Data Transformation Pipelines Must Generate Lineage Artifacts That Explicitly Support Compliance Claims, Ensuring That Derived Data Fields Can Be Traced to Their Source for Regulatory Validation.**

**REGULATORY REQUIREMENTS**
■ ■ GDPR Article 30 (Records of Processing Activities)
■ ■ CCPA/CPRA (Right to Know)

In complex data ecosystems, the validity of a compliance claim often rests on the ability to prove how a data column was populated or transformed. The axiom `column_lineage_for_compliance_claim` addresses this by defining Class X as an `cco:Artifact` that supports a `cco:DescriptiveICE`. Here, the artifact X is specifically a lineage record—such as a SQL transformation script, an ETL mapping document, or a DAG (Directed Acyclic Graph) definition—that substantiates the claim "Column C is correctly derived from Source S."

The verbalization—"{X} is something that supports claim descriptive information content entity"—is applied here to bridge the gap between technical implementation and regulatory requirement. The lineage artifact (X) is the evidence that allows an auditor to verify the claim (DescriptiveICE) that data handling procedures were followed. Without this ontological linkage, lineage data remains technical documentation rather than legal evidence.

The relational schema `t_column_lineage_for_compliance_claim` captures these artifacts. The `x` column denotes the class of the lineage artifact, which supports the claim that the data transformation was compliant.

## 4.4 PCI DSS Requirement

### Area of Focus #4
**Organizational Directives Must Be Formally Mapped to Specific PCI DSS Requirements to Ensure That Internal Policy Documents Are Directly Traceable to External Regulatory Obligations.**

**COMPLIANCE STANDARDS**
■ ■ PCI DSS v4.0
■ ■ SOC 2 Type II

The axiom `pci_dss_requirement` introduces a directive relationship between an internal control and an external regulation. It asserts that a Class X, which is a subclass of `cco:DirectiveICE` (Directive Information Content Entity), must satisfy the property `sdg:pciDssRequirement` with a specific value Y. The verbalization—"{X} is something that pci dss requirement {Y}"—establishes a direct semantic link between a governance directive (e.g., a policy document or a control procedure) and a specific requirement within the Payment Card Industry Data Security Standard (PCI DSS).

This mapping is essential for automated compliance auditing. By treating the directive (X) as an information content entity and the requirement (Y) as the object of the `pciDssRequirement` property, the organization creates a queryable graph of compliance. For example, a directive "Password Rotation Policy" (X) can be formally linked to "Requirement 8.2.3" (Y).

The relational schema `t_pci_dss_requirement` captures this binary relationship. The `x` column represents the identifier of the directive class, while the `y` column represents the specific PCI DSS requirement class or identifier it fulfills.

## 4.5 Schema.org Org TaxID

### Area of Focus #5
**Vendor and Organizational Artifacts Must Include Tax Identification Attributes to Ensure Entity Resolution and Compliance With Fiscal Reporting Obligations.**

**FINANCIAL CONTROLS**
■ ■ IRS Form 1099 Reporting
■ ■ FATCA Compliance

The final axiom, `schemaorg_org_taxid`, pertains to the identification of legal entities within the system. It asserts that a Class X, which is an `cco:Artifact` (such as a vendor profile or a corporate registration record), possesses the property `sdg:hasTaxID` with a value Y. The verbalization—"{X} is something that has tax id {Y}"—provides a mechanism for unambiguously associating an organizational artifact with its formal tax identifier.

In practice, this axiom ensures that any artifact representing an organization (e.g., a JSON-LD object describing a supplier) is ontologically bound to a specific tax identifier class or literal. This binding prevents ambiguity in entity resolution and supports downstream fiscal reporting, such as 1099 generation or VAT validation. The artifact (X) serves as the container for the identity information, while Y represents the tax ID class (e.g., `EIN`, `VATID`, `GIIN`).

The relational schema `t_schemaorg_org_taxid` implements this structure. The `x` column identifies the organizational artifact class, and the `y` column identifies the class of the tax ID associated with it.
