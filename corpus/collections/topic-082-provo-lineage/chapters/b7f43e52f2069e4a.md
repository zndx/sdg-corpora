# Chapter 7: Verification Protocols and Evidence Generation

## 7.1 Scope and Regulatory Context

This chapter establishes the mandatory protocols for verification processes within high-compliance industrial and governance environments. It delineates the formal ontological requirements for defining a verification event as a process that necessarily produces tangible evidence. The provisions herein apply to all entities subject to Audit Standard 4.2 (Process Verification) and govern the structural integrity of data recorded in compliance logs. Failure to adhere to the defined mappings between process classes and evidence artifacts shall result in non-compliance flags during automated audit trails.

## 7.2 The Ontology of Verification Processes

### 7.2.1 Definition of the Process Entity

In accordance with the Basic Formal Ontology (BFO), a verification process is formally defined as a *processual entity* (BFO:0000015). This categorization distinguishes the activity from static entities or material objects. A process is defined as an entity that unfolds in time, possesses temporal parts, and relies on one or more material participants. In the context of technical governance, a verification process is not merely an action but a bounded temporal interval during which specific operational parameters are measured, tested, and validated.

The verification process must be distinct from the system under test. For example, while a valve is a material object, the *act* of verifying the valve's integrity is a process. This distinction is critical for maintaining the fidelity of audit records. The process begins upon initiation of the test sequence and terminates only upon the generation of a conclusive result artifact.

### 7.2.2 The Evidence Production Constraint

The core axiom governing verification protocols dictates that every verification process is a subclass of processes that *produce evidence* with a cardinality of at least one (`min 1`). This constraint (`sdg:producesEvidence`) establishes a hard dependency: a verification process cannot exist in a completed state without the generation of a corresponding evidence artifact.

Evidence is defined here as a recorded output—digital, physical, or waveform-based—that captures the state of the process parameters at the moment of verification. This evidence serves as the immutable anchor for post-facto auditing. The ontology requires that the type of evidence produced be explicitly defined as a class (`Y`), ensuring that the output format is standardized and predictable.

### 7.2.3 Operational Specifications and Parameters

To ensure consistency across verification instances, specific operational parameters must be defined for each process class. These parameters dictate the physical conditions under which the process operates and the acceptable tolerances for the evidence generated. The following specification matrix details the standard operating ranges for common verification process classes deployed in field operations.

| Process Class | Media Type | Pressure Range (Bar) | Media Temp (°C) | Ambient Temp (°C) | Viscosity (cSt) Max | Mounting Position |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |

These specifications are binding. Any verification process instance falling outside the defined ambient temperature or media viscosity ranges automatically invalidates the evidence produced, rendering the verification null for compliance purposes.

## 7.3 Relational Mapping of Evidence Generation

### 7.3.1 Schema Definition and Axiomatic Structure

The logical structure linking verification processes to their required evidence is modeled through a relational schema that enforces the `verification_min_one_evidence` axiom. This schema ensures referential integrity between the process class (`X`) and the evidence class (`Y`).

The table `t_verification_min_one_evidence` serves as the registry for these mappings. The primary key (`id`) uniquely identifies the mapping rule. The column `x` stores the identifier of the verification process class, while the column `y` stores the identifier of the evidence class that the process must produce. The `NOT NULL` constraint on the `y` column enforces the ontological requirement that evidence production is mandatory; a null value would represent a process that produces no evidence, which is axiomatically forbidden in this governance framework.

### 7.3.2 Evidence Class Registry

The following table embodies the `verification_min_one_evidence` axiom. It enumerates specific verification process classes and the corresponding evidence classes they are mandated to produce. This mapping is deterministic: for every row, the existence of an instance of `x` necessitates the existence of an instance of `y`.

**Table 7-2: Verification-to-Evidence Class Mapping**

The data in Table 7-2 illustrates the application of the axiom across distinct domains. For instance, the `PressureSafetyValveTest` (a subclass of BFO Process) is formally linked to the `PressureDecayLog` (a subclass of Evidence). This linkage ensures that when an auditor queries the system for instances of `PressureSafetyValveTest`, the database can join through this mapping to retrieve the specific `PressureDecayLog` artifacts, thereby verifying compliance with the "min 1 evidence" rule.

### 7.3.3 Compliance and Non-Compliance Protocols

Pursuant to the mappings defined in Table 7-2, the following compliance protocols are enacted:

1.  **Initialization:** A verification process instance may only be initialized if a valid container for the target evidence class (`y`) exists and is writable.
2.  **Execution:** The process must capture data parameters consistent with the specifications in Table 7-1.
3.  **Finalization:** The process transitions to a "completed" state only when the evidence artifact is persisted and indexed against the process ID.

**Failure to Comply:**
If the process `x` terminates without generating the corresponding `y` artifact, the system log must record a "Constraint Violation" event. The matter of the vacancy in the audit trail will be flagged for review at the next scheduled compliance meeting. Retesting is required within 24 hours to rectify the deficiency.
