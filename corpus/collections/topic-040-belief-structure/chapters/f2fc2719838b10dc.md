# Chapter 7: Process Ontology and Verification Protocols

## 7.1 Scope and Applicability

This chapter establishes the foundational taxonomy for process governance, specifically addressing the classification of operational entities, the mandatory utilization of artifacts, and the generation of evidence through verification protocols. It delineates the structural requirements for audit processes as defined within the enterprise ontology and provides the necessary relational mappings to ensure data integrity across compliance systems. Compliance with these definitions is requisite for all reporting units, and any deviation from the prescribed schema must be authorized in writing by the Governance Committee. The provisions herein apply exclusively to the internal verification mechanisms and do not alter external regulatory obligations unless explicitly stated.

## 7.2 Basic Process Classification

### 7.2.1 Definition and Rationale

Pursuant to the foundational ontology, all operational activities within the governance framework must be classified as Processes. This classification is not merely nominal but serves as the primary structural constraint for downstream auditing and verification activities. Formally, a Process is defined as an entity that is a subclass of `bfo:0000015` (a process). This axiom ensures that every activity subject to governance is recognized as a temporal entity occurring over time, possessing distinct start and terminus points.

The classification of an entity as a Process is the prerequisite for the application of all subsequent governance rules. Without this primary classification, an entity cannot be evaluated for artifact utilization or evidence generation. Therefore, the initial step in any compliance audit involves the verification that the subject entity is properly registered within the `t_classification_basic` table.

### 7.2.2 Implementation Guidelines

All business units must inventory their operational activities and map them to the Process class. This inventory shall serve as the master index for the governance framework. The following table illustrates the requisite format for registering these basic classifications. Each entry represents a distinct process instance that falls under the scope of the ontology.

**Table 7-1: Basic Process Classification Registry**

| ID | Process Class (X) |
| :--- | :--- |
| `CLS-1001` | `IncidentResponseWorkflow` |
| `CLS-1002` | `DataSanitizationProcedure` |
| `CLS-1003` | `VendorOnboardingSequence` |
| `CLS-1004` | `QuarterlyFinancialReview` |
| `CLS-1005` | `UserAccessRevocation` |

*Note: The ID column serves as the unique primary key for all cross-referenced tables.*

### 7.2.3 Relational Schema

The data structure supporting this classification is defined by the following schema. It is imperative that the `id` field be unique and non-null, as it functions as the anchor for foreign key constraints in subsequent verification modules.

```sql
CREATE TABLE t_classification_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["bfo:Process"],"family":"03_directive_governance","is_complex":false,"template_id":"classification_basic"}'
```

## 7.3 Process Artifact Utilization

### 7.3.1 The Artifact Constraint

While the classification of an entity as a Process is necessary, it is not sufficient for full governance compliance. The ontology imposes a further restriction: a Process must utilize at least one Artifact. This is formalized by the axiom stating that a Process is a subclass of `bfo:0000015` and utilizes (`sdg:uses`) a minimum of one `cco:Artifact`.

An Artifact, in this context, refers to any discrete information object—such as a document, log file, configuration record, or database entry—that is acted upon by the Process. The "min 1" cardinality constraint ensures that no "empty" processes exist within the system. If a process is identified that does not utilize an artifact, it is either a null process requiring removal or a classification error requiring remediation.

### 7.3.2 Evidence of Utilization

To demonstrate compliance with this axiom, the governance framework requires the explicit mapping of Processes to their utilized Artifacts. This mapping is captured in the `t_process_with_min_one_artifact` table. The relationship is strictly functional; a process entry cannot exist in this table unless it is demonstrably linked to an artifact usage event.

**Table 7-2: Process-Artifact Utilization Log**

| ID | Process Class (X) |
| :--- | :--- |
| `ART-PROC-201` | `LogAnalysisProcedure` |
| `ART-PROC-202` | `RecordRetentionAudit` |
| `ART-PROC-203` | `DigitalSignatureVerification` |
| `ART-PROC-204` | `ConfigurationDriftCheck` |

### 7.3.3 Relational Schema and Integrity

The schema for artifact utilization extends the basic classification by enforcing the relationship to the `cco:Artifact` class implicitly through the verification logic. The table structure is designed to be referenced by the verification module described in Section 7.4.

```sql
CREATE TABLE t_process_with_min_one_artifact (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["bfo:Process"],"family":"01_foundation","is_complex":true,"template_id":"process_with_min_one_artifact"}'
```

## 7.4 Verification and Evidence Generation

### 7.4.1 The Verification Protocol

The Verification Protocol represents the core control mechanism within the governance framework. It dictates that specific classes of Processes, designated as Verification Processes, must produce Evidence. This relationship is axiomatically defined as: a Verification Process is a subclass of `bfo:0000015` that produces evidence (`sdg:producesEvidence`) of a minimum of one Evidence Class.

In this framework, the "Evidence" produced is not merely a static file but is itself modeled as a Process that utilizes an Artifact (referencing the structure defined in Section 7.3). This recursive structure ensures that the act of producing evidence is itself a governed, auditable activity. For instance, a "Verification Process" might be a System Audit, which produces evidence in the form of an "Audit Report Generation Process," which in turn utilizes the "Raw Log Files" as artifacts.

### 7.4.2 Mapping Verification to Evidence

The critical compliance check involves ensuring that every Verification Process is linked to a valid Evidence Generation Process. The `t_verification_min_one_evidence` table enforces this link. The foreign key constraint on the `y` column (representing the Evidence) ensures that the evidence produced is a valid, artifact-utilizing process registered in `t_process_with_min_one_artifact`.

**Table 7-3: Verification Evidence Mapping**

| ID | Verification Process (X) | Evidence Process (Y) |
| :--- | :--- | :--- |
| `VER-301` | `SystemSecurityAudit` | `ART-PROC-201` |
| `VER-302` | `ComplianceAttestation` | `ART-PROC-202` |
| `VER-303` | `CodeReviewVerification` | `ART-PROC-203` |
| `VER-304` | `InfrastructureValidation` | `ART-PROC-204` |

*Note: Column Y references the ID in Table 7-2, ensuring traceability to artifact utilization.*

### 7.4.3 Relational Schema

The schema below implements the foreign key constraint essential for maintaining referential integrity between the verification act and the evidence produced.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_process_with_min_one_artifact(id)
)
COMMENT '{"bfo_anchor":["bfo:Process"],"family":"03_directive_governance","is_complex":true,"template_id":"verification_min_one_evidence"}'
```

## 7.5 Audit Fundamentals

### 7.5.1 Definition of Audit Processes

Distinct from general verification, the Audit function constitutes a specific class of high-level governance processes. An Audit is formally defined as a subclass of `bfo:0000015`. While it shares the characteristics of a process (temporal boundedness), it is distinguished by its scope, authority, and objective. Audits are typically invasive, independent evaluations of compliance status, whereas verification may be automated and continuous.

The classification of an entity as an Audit Process triggers specific retention policies, access controls, and reporting requirements not applicable to standard processes. It serves as the top-level node in the governance hierarchy for investigative activities.

### 7.5.2 Audit Registry

All Audit processes must be registered in the `t_audit_basic` table. This registry acts as the master schedule for the governance committee, ensuring that all audit activities are tracked and authorized. The separation of this table from the basic classification table allows for granular permission management and reporting specific to audit functions.

**Table 7-4: Audit Process Registry**

| :--- | :--- |
| `AUD-401` | `AnnualFinancialAudit` |
| `AUD-402` | `Q3SecurityComplianceAudit` |
