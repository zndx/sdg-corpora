# Chapter 7: Directive Information Content Entities and Addressed Artifacts in Compliance Registries

This chapter defines five core ontological patterns for directive information content entities and their linkage to place artifacts. The patterns are realized as a five-table relational schema drawn from municipal planning records. Primary and foreign keys encode the subclass and existential restrictions stated in the source axioms, enabling direct verification of ownership, verification, enforcement, and checking relations through equijoins.

## 1. Ontology Patterns for Directives and Places

Five Manchester OWL axioms govern the schema. Each axiom asserts that a directive information content entity stands in a minimum-cardinality relation to another class. The relational projections preserve these cardinalities as NOT NULL foreign keys. All class names occupy the x or y columns; instance identifiers occupy the id columns.

### 1.1 Control Ownership Pattern

Axiom 2 states that every instance of a directive must have at least one owner. The corresponding table therefore contains one row per directive class and records the owning entity via the x column.

```sql
CREATE TABLE t_control_min_one_owner (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

The primary key id uniquely identifies each directive class. No foreign key is present because ownership is recorded directly as a class reference.

| id     | x                          |
|--------|----------------------------|
| ctrl01 | ZoningVarianceDirective    |
| ctrl02 | SpecialExceptionDirective  |
| ctrl03 | RegistrationRequirement    |
| ctrl04 | CourseCreditDirective      |
| ctrl05 | PermitFeeDirective         |

### 1.2 Place Address Attachment Pattern

Axiom 1 states that an artifact may possess a postal address. The table records the address class and links it to a controlling directive.

```sql
CREATE TABLE t_schemaorg_place_address (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_min_one_owner(id)
);
```

Column id is the primary key. Column y is a foreign key into t_control_min_one_owner, enforcing that every address is attached to a directive that possesses an owner.

| id      | x                        | y      |
|---------|--------------------------|--------|
| addr01  | GrandChuteMunicipalBldg  | ctrl01 |
| addr02  | HiltonSandestin          | ctrl02 |
| addr03  | SEAAIOfficeOwensboro     | ctrl03 |
| addr04  | MG245Classroom           | ctrl04 |
| addr05  | CommunityDevDept         | ctrl05 |

### 1.3 Requirement Verification Pattern

Axiom 3 requires every directive to be verified by at least one place. The table captures the verification link.

```sql
CREATE TABLE t_requirement_min_one_verification (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_schemaorg_place_address(id)
);
```

Primary key id identifies the requirement instance. Foreign key y references t_schemaorg_place_address, allowing a mental join that retrieves the verifying address and, transitively, the owning directive.

| id      | x                             | y      |
|---------|-------------------------------|--------|
| req01   | VarianceVerification          | addr01 |
| req02   | ExceptionSiteVerification     | addr02 |
| req03   | MemberAddressVerification     | addr03 |
| req04   | CreditLocationVerification    | addr04 |
| req05   | FeePaymentVerification        | addr05 |

### 1.4 Policy Enforcement Pattern

Axiom 4 states that a directive is enforced by at least one place. The table records the enforcement relation.

```sql
CREATE TABLE t_policy_min_one_enforcer (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_schemaorg_place_address(id)
);
```

Primary key id identifies the policy. Foreign key y again references t_schemaorg_place_address, supporting the same transitive traversal shown in the verification table.

| id      | x                          | y      |
|---------|----------------------------|--------|
| pol01   | VarianceEnforcementPolicy  | addr01 |
| pol02   | MeetingEnforcementPolicy   | addr02 |
| pol03   | RegistrationEnforcement    | addr03 |
| pol04   | CreditEnforcementPolicy    | addr04 |
| pol05   | FeeEnforcementPolicy       | addr05 |

### 1.5 Constraint Checking Pattern

Axiom 5 requires every directive to be checked by at least one place. The table materializes the checking relation.

```sql
CREATE TABLE t_constraint_min_one_check (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_schemaorg_place_address(id)
);
```

Primary key id identifies the constraint. Foreign key y references t_schemaorg_place_address, completing the set of four tables that each reference the address table.

| id      | x                           | y      |
|---------|-----------------------------|--------|
| con01   | LotSizeConstraintCheck      | addr01 |
| con02   | VenueCapacityConstraint     | addr02 |
| con03   | MailingAddressConstraint    | addr03 |
| con04   | ClassroomConstraintCheck    | addr04 |
| con05   | PaymentMethodConstraint     | addr05 |

## 2. Cross-Table Query Example

To retrieve the address that verifies, enforces, and checks the directive originally owned by ctrl01, execute the following mental equijoin path:

t_control_min_one_owner.id = ctrl01  
→ t_schemaorg_place_address.y = ctrl01 yields addr01  
→ t_requirement_min_one_verification.y = addr01 yields req01  
→ t_policy_min_one_enforcer.y = addr01 yields pol01  
→ t_constraint_min_one_check.y = addr01 yields con01

The joined row is therefore:

(ctrl01, ZoningVarianceDirective, addr01, GrandChuteMunicipalBldg, req01, pol01, con01)

This single traversal answers the multi-hop question: “Which address both verifies the variance requirement and enforces the lot-size constraint for the owned zoning directive?”
