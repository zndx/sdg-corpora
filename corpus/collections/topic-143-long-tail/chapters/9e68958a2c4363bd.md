# Chapter 4: Ontological Formalization of Belief Structures and Compliance Directives

This chapter delineates the formal ontological structures required to represent uncertainty quantification and governance directives within a semantic compliance framework. We define the axiomatic basis for Descriptive Information Content Entities (ICE) that utilize Dempster-Shafer theory, specifically focusing on mass functions and belief intervals, and establish the provenance chain for automated compliance directives. The following sections provide a rigorous definition of four primary axioms, their relational projections, and their application in a high-assurance audit environment.

## 1. Set-Theoretic Class Definitions via Intersection and Negation

In the construction of a robust compliance ontology, it is frequently insufficient to define classes solely by the presence of affirmative properties. Precise governance often requires the definition of a class $X$ as the intersection of a base class $Y$ and the logical negation of an exclusion class $Z$. This mechanism allows for the granular filtering of entities, ensuring that definitions remain strict even as the domain of discourse expands.

### 1.1 Axiom 2: Equivalent Intersection with Negation

The formal axiom for this construct is expressed in Manchester syntax as:
`Class: {X:Class} EquivalentTo: {Y:Class} and not {Z:Class}`.

Verbalized, this asserts that Class $X$ is equivalent to Class $Y$ and not Class $Z$. In the context of relational data modeling, this structure necessitates a table that captures the specific definition of $X$ by referencing its constituent components $Y$ and $Z$. The primary key serves as the unique identifier for the defined class $X$, while the foreign keys (conceptual, though not explicitly enforced in the schema provided) link to the constituent classes.

The relational schema for this axiom is presented below. It embodies the logical definition where the identity of the defined class (`x`) is derived from the intersection of the positive constraint (`y`) and the negative constraint (`z`).

**Table 1-1: Axiomatic Class Definitions via Intersection and Negation**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| def_closed_audit | ClosedAuditRecord | SubmittedRecord | PendingReview |
| def_validated_claim | ValidatedClaim | ReceivedClaim | RejectedClaim |
| def_finalized_asset | FinalizedAsset | TrackedAsset | DisposedAsset |
| def_compliant_user | CompliantUser | ActiveUser | FlaggedUser |
| def_secure_node | SecureNode | NetworkNode | CompromisedNode |

*Table 1-1 illustrates the instantiation of the `t_equiv_intersect_with_negation` schema. The `id` column represents the unique identifier for the defined class $X$. The `x` column holds the class name of the defined entity. The `y` column specifies the superclass from which properties are inherited, and the `z` column specifies the class whose instances are explicitly excluded from $X$. For instance, a `ClosedAuditRecord` is defined precisely as a `SubmittedRecord` that is not `PendingReview`.*

### 1.2 Application in Audit Trails

Consider the application of this axiom within an automated audit system. The system must distinguish between records that are merely submitted and those that are formally closed for the fiscal period. By defining `ClosedAuditRecord` through the intersection of `SubmittedRecord` and the negation of `PendingReview`, the ontology ensures that any record entering a "pending" state is automatically excluded from the set of closed records. This logical rigidity prevents ambiguity in reporting states where a record might otherwise satisfy multiple conflicting criteria.

## 2. Mass Functions and Frames of Discernment

To quantify uncertainty in evidence-based compliance, we employ the Dempster-Shafer structure of a Mass Function. A Mass Function is a specific type of Descriptive ICE that assigns a basic probability assignment (mass) to subsets of a Frame of Discernment. The Frame of Discernment represents the set of mutually exclusive exhaustive propositions relevant to the analysis.

### 2.1 Axiom 1: Mass Function Equivalence

The axiom governing this structure is:
`Class: {X:Class} EquivalentTo: cco:DescriptiveICE and (sdg:overFrameOfDiscernment some {Y:Class}) and (sdg:assignsMassTo some {Z:Class})`.

This axiom asserts that a Mass Function ($X$) is a Descriptive ICE that operates over a specific Frame of Discernment ($Y$) and assigns mass to a specific subset or hypothesis ($Z$). The relational projection of this axiom requires that the Frame of Discernment ($Y$) be a valid, previously defined class, specifically linking back to the intersection definitions established in Section 1 to ensure the frame is semantically bounded.

**Table 2-1: Mass Function Specifications**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| mf_audit_risk_01 | AuditRiskMassFunction | def_closed_audit | HighRiskHypothesis |
| mf_claim_veracity | ClaimVeracityMassFunction | def_validated_claim | FraudHypothesis |
| mf_asset_integrity | AssetIntegrityMassFunction | def_finalized_asset | DegradationHypothesis |
| mf_user_compliance | UserComplianceMassFunction | def_compliant_user | PolicyViolationHypothesis |
| mf_network_status | NetworkStatusMassFunction | def_secure_node | IntrusionHypothesis |

*Table 2-1 represents the `t_mass_function_equiv_frame_and_assignment` schema. The `id` is the unique identifier for the Mass Function instance. Column `x` denotes the specific Mass Function class. Column `y` references the Frame of Discernment (via the `id` from Table 1-1), anchoring the function to a specific domain definition. Column `z` identifies the specific hypothesis or focal element to which the mass is assigned. Note that the `y` values (e.g., `def_closed_audit`) correspond to the identifiers of the intersection definitions, ensuring the Frame of Discernment is rigorously defined by set logic.*

### 2.2 Evidence Aggregation

In practice, the `AuditRiskMassFunction` (Table 2-1, Row 1) operates over the frame defined by `def_closed_audit`. This means the function only considers evidence pertaining to records that are submitted and not pending review. It assigns a mass value to the `HighRiskHypothesis`. This structure allows the system to state, "Given the evidence from closed audit records, the probability mass assigned to the hypothesis that the process is high risk is $m$." This is distinct from Bayesian probability, as it allows for the assignment of mass to sets of hypotheses (uncertainty) rather than just single points, though the schema here identifies the specific target class $Z$.

## 3. Belief Intervals and Plausibility Bounds

While mass functions assign weight to specific hypotheses, decision-makers often require a range of uncertainty to assess risk tolerance. A Belief Interval provides this range, defined by a lower bound (Belief) and an upper bound (Plausibility).

### 3.1 Axiom 3: Belief Interval Equivalence

The formal axiom is defined as:
`Class: {X:Class} EquivalentTo: cco:DescriptiveICE and (sdg:hasBeliefLowerBound some {Y:Class}) and (sdg:hasPlausibilityUpperBound some {Z:Class})`.

This axiom defines a Belief Interval ($X$) as a Descriptive ICE possessing a lower bound derived from class $Y$ and an upper bound derived from class $Z$. The referential integrity of this axiom requires that the lower bound ($Y$) be grounded in a specific definition, again linking back to the intersection classes to ensure the bounds are calculated over the correct domain.

**Table 3-1: Belief Interval Definitions**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| bi_audit_confidence | AuditConfidenceInterval | def_closed_audit | MaxPlausibilityClass |
| bi_claim_certainty | ClaimCertaintyInterval | def_validated_claim | UpperBoundClass |
| bi_asset_reliability | AssetReliabilityInterval | def_finalized_asset | FailurePlausibilityClass |
| bi_user_trust | UserTrustInterval | def_compliant_user | RiskPlausibilityClass |
| bi_node_security | NodeSecurityInterval | def_secure_node | BreachPlausibilityClass |

*Table 3-1 depicts the `t_belief_interval_equiv_bel_and_pl` schema. The `id` uniquely identifies the interval instance. Column `x` names the Belief Interval class. Column `y` establishes the lower bound foundation by referencing the domain definition (from Table 1-1). Column `z` specifies the class defining the plausibility upper bound. For example, the `AuditConfidenceInterval` is bounded below by the evidence found in `def_closed_audit` and extends up to a `MaxPlausibilityClass`, representing the total uncertainty range.*

### 3.2 Interpreting the Interval

The `AuditConfidenceInterval` (Table 3-1, Row 1) utilizes the domain `def_closed_audit` as its basis for the Belief lower bound. This implies that the minimum confidence we have in the audit status is strictly derived from records that are confirmed closed and not pending. The upper bound, represented by `MaxPlausibilityClass`, encompasses the total belief that the hypothesis could be true, including the uncertainty mass. By separating these bounds, the framework distinguishes between "compelling evidence" (Belief) and "lack of contrary evidence" (Plausibility).

## 4. Governance Directives and Provenance

The ultimate purpose of quantifying belief and defining evidence frames is to drive action. Governance Directives are operational rules or commands triggered by the state of the information environment. These directives must have clear provenance, indicating which analytical process authored them and which operational domain they affect.

### 4.1 Axiom 4: Directive Authored and Applied

The axiom for directives is:
`Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:authoredBy some {Y:Class}) and (sdg:appliesTo some {Z:Class})`.

This defines a Directive ($X$) as a Directive ICE that is authored by an agent or process $Y$ and applies to a target $Z$. In this automated framework, the "author" is often the analytical function itself (the Mass Function), ensuring that the directive is a direct output of the uncertainty quantification process.

**Table 4-1: Directive Provenance and Application**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| dir_investigation_01 | InvestigationDirective | mf_audit_risk_01 | ComplianceOfficer |
| dir_payment_hold | PaymentHoldDirective | mf_claim_veracity | FinanceSystem |
| dir_maintenance_req | MaintenanceRequestDirective | mf_asset_integrity | LogisticsSystem |
| dir_access_review | AccessReviewDirective | mf_user_compliance | HRDepartment |
| dir_isolate_node | IsolateNodeDirective | mf_network_status | SecurityOperationsCenter |

*Table 4-1 illustrates the `t_directive_authored_and_applies` schema. The `id` is the unique directive identifier. Column `x` names the Directive class. Column `y` references the author of the directive, which is the Mass Function instance (from Table 2-1). Column `z` identifies the target entity or system to which the directive applies. For instance, the `InvestigationDirective` is authored by the `mf_audit_risk_01` Mass Function and applies to the `ComplianceOfficer`, establishing a clear chain of evidence-to-action.*

### 4.2 The Chain of Command

The integration of these axioms creates a complete audit trail. The `InvestigationDirective` (Table 4-1) does not appear in a vacuum. It is generated by `mf_audit_risk_01` (Table 2-1), which is a function operating over `def_closed_audit` (Table 1-1). Consequently, if an investigation is launched, one can trace it back to the specific definition of "closed records" (excluding pending ones) and the specific mass assignment that triggered the risk threshold. This level of traceability is critical for high-compliance environments where automated decisions must be auditable and explainable.
