# Modeling Security Compliance Directives via Relational Projections

This chapter defines five relational tables that instantiate OWL axioms for DirectiveICE subclasses under PCI DSS, HIPAA, and ISO 27001. Each table records a pair of classes (X, Y) such that X is asserted as a DirectiveICE satisfying the indicated requirement or safeguard. Primary keys ensure unique axiom instances; column Y functions as an implicit foreign key to class identifiers reused across tables, enabling cross-table verification of control inheritance.

## 1. Axiom-to-Table Mapping

The five axioms project directly onto the supplied schemas. All tables share the column signature (id, x, y) where id is the primary key for the axiom instance and y references a control class that may appear in other tables.

### 1.1 t_pci_dss_requirement
This table embodies axiom pci_dss_requirement. Column id is the primary key; column y references a PCI DSS requirement class that can be joined to equivalent Y values in the HIPAA and ISO tables.

## 2. Cross-Table Verification Example

To determine which controls satisfy both PCI DSS requirement Req-7.1 and HIPAA technical safeguard 164.312(a)(1), join on column y after selecting matching rows:

- From t_pci_dss_requirement where y = 'Req-7.1' yields x = 'AccessControlMatrix'.
- From t_hipaa_safeguard_technical where y = '164.312(a)(1)' yields the same x.
- The joined result row is (AccessControlMatrix, Req-7.1, 164.312(a)(1)).

The same X also appears in t_iso27001_annexa_subclass with y = 'A.9.1.1', confirming inheritance across three standards without additional tables.
