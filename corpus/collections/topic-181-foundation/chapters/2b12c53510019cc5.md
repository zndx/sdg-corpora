# Chapter 4: Governance of Information Security Directives and Risk Classifications

**Effective Date:** October 26, 2023, 14:00 EST  
**Reference Standard:** NIST SP 800-53 Rev. 5 / HIPAA Security Rule 45 CFR §164.308(a)  
**Status:** Release Candidate 4.2

The information contained in this chapter is current only as of the effective date stated above. This chapter provides a formal ontological mapping of regulatory directives to specific risk control classes. It is intended for use by compliance officers, information security auditors, and governance frameworks to ensure that administrative, technical, and physical safeguards are rigorously classified and cross-referenced against threat vectors and payment card industry requirements. The following sections detail the axiomatic relationships between directive classes and their respective control targets, supported by relational schema mappings for immediate integration into governance, risk, and compliance (GRC) databases.

---

## 4.1 Administrative Safeguards and Risk Mitigation

The Security Rule under the Health Insurance Portability and Accountability Act (HIPAA) requires covered entities to implement administrative safeguards to manage the selection, development, implementation, and maintenance of security measures. In the context of the ontology provided, these safeguards are formalized as directives that inherently safeguard specific classes of threats or risks. The relationship defined here is not merely associative but structural; the administrative directive exists to mitigate a specific risk class.

**Axiom 1:** `{X}` is something that hipaa safeguard `{Y}`.

This axiom asserts that for every administrative directive defined in the governance framework, there must be a corresponding threat class that it serves to safeguard. This ensures that administrative policies are not created in a vacuum but are anchored to specific, identifiable risks. The relational schema for this axiom enforces a foreign key constraint where the threat class (`y`) must be a valid entry in the control registry.

**Table 4.1: Administrative Safeguard Mapping (t_hipaa_safeguard_admin)**

| id | x | y |
| :--- | :--- | :--- |
| `ADM-001` | `WorkforceSecurityPolicy` | `CTRL-THRT-001` |
| `ADM-002` | `InformationAccessManagement` | `CTRL-THRT-002` |
| `ADM-003` | `SecurityAwarenessTraining` | `CTRL-THRT-003` |
| `ADM-004` | `SecurityIncidentProcedures` | `CTRL-THRT-004` |
| `ADM-005` | `ContingencyPlanOperations` | `CTRL-THRT-005` |

*Note: Column `x` represents the Administrative Directive Class, and column `y` represents the Threat Class ID being safeguarded. Refer to Section 4.2 for the definition of the Threat Classes referenced in column `y`.*

The implementation of these directives requires the assignment of specific security responsibilities. The `WorkforceSecurityPolicy` (ADM-001), for instance, is the primary mechanism for mitigating the `UnauthorizedAccessRisk` (CTRL-THRT-001). By formalizing this relationship in the data structure, auditors can query the database to verify that every identified threat has a corresponding administrative policy assigned to it. This mapping serves as the primary evidence for the "Administrative Safeguards" section of the HIPAA Security Rule audit.

## 4.2 Control Classes and Threat Addressing

While administrative directives provide the governance structure, the actual mitigation of risks is performed through specific control classes. This section defines the ontological relationship where a control class addresses a risk. A critical distinction in this framework is the reciprocal nature of the relationship between the control and the administrative safeguard. The control addresses the risk, but the directive governing that control is often validated by the existence of the risk.

**Axiom 2:** `{X}` is something that addresses risk `{Y}`.

This axiom establishes the core functional requirement of the security control. It posits that a control class (`X`) has the specific function of addressing a risk class (`Y`). The schema for this axiom includes a foreign key constraint referencing the administrative safeguard table, creating a dependency chain that ensures operational controls are governed by administrative policies.

**Table 4.2: Control and Threat Classification (t_control_only_addresses_threat_class)**

| id | x | y |
| :--- | :--- | :--- |
| `CTRL-THRT-001` | `UnauthorizedAccessRisk` | `ADM-001` |
| `CTRL-THRT-002` | `DataIntegrityViolation` | `ADM-002` |
| `CTRL-THRT-003` | `SocialEngineeringVector` | `ADM-003` |
| `CTRL-THRT-004` | `MalwareIntroductionEvent` | `ADM-004` |
| `CTRL-THRT-005` | `SystemAvailabilityFailure` | `ADM-005` |

*Note: Column `x` represents the Risk Class, and column `y` is the Foreign Key referencing the Administrative Directive ID (t_hipaa_safeguard_admin).*

In this configuration, the `UnauthorizedAccessRisk` (CTRL-THRT-001) is formally addressed by the controls defined under the purview of the `WorkforceSecurityPolicy` (ADM-001). This structure allows for a granular analysis of risk mitigation. For example, if a specific risk instance is identified during a breach assessment, the ontology permits the immediate retrieval of the governing administrative directive and the associated technical or physical controls. This bidirectional linkage is essential for maintaining the "defense-in-depth" strategy required by federal compliance frameworks.

## 4.3 Technical Safeguards and Encryption Mechanisms

Technical safeguards refer to the automated mechanisms and digital processes used to protect electronic protected health information (ePHI) and control access to it. Unlike administrative safeguards, which involve policies and procedures, technical safeguards involve the technology and the policy and procedures for its use that protect electronic health information and control access to it.

**Axiom 3:** `{X}` is something that hipaa safeguard `{Y}`.

In this context, the axiom applies to technical implementations. The technical directive (`X`) safeguards the system against a specific threat class (`Y`). This includes access control, audit controls, integrity controls, and transmission security. The relational projection requires that the threat class being safeguarded exists in the central control registry defined in Section 4.2.

**Table 4.3: Technical Safeguard Implementation (t_hipaa_safeguard_technical)**

| id | x | y |
| :--- | :--- | :--- |
| `TEC-001` | `UniqueUserAuthentication` | `CTRL-THRT-001` |
| `TEC-002` | `EmergencyAccessProcedure` | `CTRL-THRT-005` |
| `TEC-003` | `AutomaticLogoffMechanism` | `CTRL-THRT-001` |
| `TEC-004` | `EncryptionAndDecryption` | `CTRL-THRT-002` |
| `TEC-005` | `AuditControlMechanism` | `CTRL-THRT-004` |

*Note: Column `x` represents the Technical Control Class, and column `y` references the Threat Class ID.*

The `UniqueUserAuthentication` (TEC-001) control is a direct technical implementation safeguarding against the `UnauthorizedAccessRisk` (CTRL-THRT-001). By mapping this control to the threat class, the organization demonstrates that the technical infrastructure is actively mitigating the risks identified in the governance layer. Furthermore, the `EncryptionAndDecryption` (TEC-004) control is mapped to `DataIntegrityViolation` (CTRL-THRT-002), reflecting the requirement that encryption is not merely a confidentiality tool but a mechanism for ensuring that data has not been altered in transit.

## 4.4 Physical Safeguards and Facility Access

Physical safeguards are measures to protect physical electronic systems and related buildings and equipment from natural and environmental hazards, as well as unauthorized intrusion. These safeguards are critical in preventing unauthorized physical access to ePHI, regardless of whether the data is stored on a server, a workstation, or a portable media device.

**Axiom 4:** `{X}` is something that hipaa safeguard `{Y}`.

This axiom captures the physical manifestation of security directives. The physical directive (`X`) safeguards the environment against a threat class (`Y`). The schema enforces consistency by requiring that the threat class be previously defined in the control registry, ensuring that physical security measures are aligned with the same risk taxonomy used for technical and administrative controls.

**Table 4.4: Physical Safeguard Deployment (t_hipaa_safeguard_physical)**

| id | x | y |
| :--- | :--- | :--- |
| `PHY-001` | `FacilityAccessControls` | `CTRL-THRT-001` |
| `PHY-002` | `WorkstationUsePolicy` | `CTRL-THRT-003` |
| `PHY-003` | `WorkstationSecurity` | `CTRL-THRT-001` |
| `PHY-004` | `DeviceAndMediaControls` | `CTRL-THRT-002` |
| `PHY-005` | `DisposalProcedures` | `CTRL-THRT-004` |

*Note: Column `x` represents the Physical Control Class, and column `y` references the Threat Class ID.*

The `FacilityAccessControls` (PHY-001) directive safeguards against `UnauthorizedAccessRisk` (CTRL-THRT-001) by restricting entry to the physical premises where information systems reside. Similarly, `DeviceAndMediaControls` (PHY-004) are mapped to `DataIntegrityViolation` (CTRL-THRT-002), as the physical handling of backup media and reusable hardware is a primary vector for data corruption or loss. This mapping ensures that physical security audits are not treated as a separate domain but are integrated into the overall risk management framework.

## 4.5 PCI DSS Requirements and Cross-Framework Alignment

In environments where healthcare entities process payment card transactions, such as hospitals or clinics, the Payment Card Industry Data Security Standard (PCI DSS) applies alongside HIPAA. This section outlines the integration of PCI DSS requirements into the general risk ontology. While HIPAA focuses on Protected Health Information (PHI), PCI DSS focuses on Cardholder Data (CHD), yet the underlying controls often address the same threat classes (e.g., unauthorized access, malware).

**Axiom 5:** `{X}` is something that pci dss requirement `{Y}`.

This axiom maps a PCI DSS requirement class (`X`) to a threat class (`Y`). By utilizing the same threat class registry as the HIPAA safeguards, the ontology enables a unified view of security controls. This allows organizations to identify overlapping controls that satisfy multiple compliance obligations simultaneously, thereby optimizing resource allocation and reducing audit fatigue.

**Table 4.5: PCI DSS Requirement Mapping (t_pci_dss_requirement)**

| id | x | y |
| :--- | :--- | :--- |
| `PCI-001` | `InstallAndMaintainFirewall` | `CTRL-THRT-001` |
| `PCI-002` | `ChangeDefaultPasswords` | `CTRL-THRT-001` |
| `PCI-003` | `ProtectStoredCardholderData` | `CTRL-THRT-002` |
| `PCI-004` | `EncryptTransmissionOfCHD` | `CTRL-THRT-002` |
| `PCI-005` | `UseAndUpdateAntiVirusSoftware` | `CTRL-THRT-004` |
| `PCI-006` | `DevelopAndMaintainSecureSystems` | `CTRL-THRT-005` |

*Note: Column `x` represents the PCI DSS Requirement Class, and column `y` references the Threat Class ID.*

For instance, the requirement to `InstallAndMaintainFirewall` (PCI-001) directly addresses the `UnauthorizedAccessRisk` (CTRL-THRT-001), which is the same threat class addressed by the HIPAA `WorkforceSecurityPolicy` (ADM-001) and `UniqueUserAuthentication` (TEC-001). This alignment demonstrates that a robust firewall implementation serves as a convergent control for both regulatory frameworks. The ontology facilitates this cross-walk, providing evidence to auditors that the organization's security posture is comprehensive and mutually reinforcing across multiple regulatory domains.
