# Chapter 7: Ontological Mapping of Regulatory Directives to Risk Controls

**Effective Date:** October 24, 2023  
**Reference Standard:** OWL2 RL Compliance Ontology (cco) / Security Domain Governance (sdg)  
**Status:** Release Candidate 4.2

### Preamble

This chapter provides a consolidated reference for the structural mapping of regulatory directives to specific threat classes and safeguarding mechanisms within the enterprise governance framework. The information contained herein delineates the formal axioms governing the relationship between Information Control Elements (ICE) and their associated risk domains, specifically within the contexts of the Health Insurance Portability and Accountability Act (HIPAA) and the Payment Card Industry Data Security Standard (PCI DSS). The purpose of this publication is to establish a deterministic schema for auditing compliance postures, ensuring that every administrative, technical, or physical directive is verifiable against a specific risk vector. The following sections detail the ontological definitions for these mappings, supported by relational data tables that instantiate the logical constraints imposed by the governing schema.

---

### 1. Administrative Safeguards and HIPAA Governance

The foundational layer of the healthcare security framework rests upon Administrative Safeguards. In the ontological model, this relationship is formalized through the axiom `hipaa_safeguard_admin`. This axiom asserts that a specific class of directive (X) functions as a mechanism to enact a HIPAA safeguard (Y). Unlike technical implementations, administrative safeguards are defined by their nature as policy-based or procedural controls that govern the conduct of the workforce and the management of security selections.

Formally, the axiom is expressed as:
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`
*   **Verbalization:** {X} is something that hipaa safeguard {Y}

In practice, this means that for an administrative directive to be valid within the ontology, it must be demonstrably linked to a safeguarding activity mandated by HIPAA regulations. This linkage ensures that administrative overhead is not arbitrary but is anchored to specific compliance requirements. For instance, a "Security Management Process" is not merely a document; it is an Information Control Element (ICE) that safeguards the entity against "Unauthorized Access."

The following table instantiates this axiom, mapping specific Administrative Directives to the Safeguards they fulfill. The primary key (`id`) represents the unique identifier for the directive instance, while the foreign key (`y`) references the specific safeguard or risk class being addressed.

**Table 1.1: Administrative Safeguard Mapping**

| id | x (Directive Class) | y (Safeguard Class) |
| :--- | :--- | :--- |
| admin_dir_001 | WorkforceSanctionPolicy | WorkforceSecurity |
| admin_dir_002 | SecurityManagementProcess | AdministrativeSafeguards |
| admin_dir_003 | InformationAccessManagement | AccessControl |
| admin_dir_004 | ContingencyPlanImplementation | ContingencyPlan |

*Table 1.1 Notes:*
*   `x` represents the specific administrative policy or procedure.
*   `y` represents the high-level safeguard category defined by HIPAA Security Rules.
*   All entries are subclasses of `cco:DirectiveICE`.

### 2. Control Addressance of Threat Classes

To establish a robust security architecture, directives must be rigorously mapped to the specific threats they mitigate. The axiom `control_only_addresses_threat_class` provides the logical constraint for this mapping. It dictates that a given Control (X) addresses a Risk (Y) exclusively. This exclusivity is crucial for audit trails; it prevents vague security controls where a single mechanism is claimed to mitigate disparate, unrelated risks without specific justification.

The formal definition is as follows:
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:addressesRisk only {Y:Class}`
*   **Verbalization:** {X} is something that addresses risk {Y}

This axiom serves as a bridge between the theoretical definition of a control and its practical application in threat mitigation. It enforces a structure where the "Risk" (Y) is the object of the "Control's" (X) action. In the relational schema, this creates a reciprocal relationship with the administrative safeguards table, ensuring that every risk addressed by a control is governed by a higher-level administrative directive.

The table below illustrates this relationship. It is important to note the referential integrity: the `y` column in this table references the administrative directive (`id`) that authorizes the control to address the specific risk. This circular dependency in the data model reflects the governance reality that risks are only "addressed" when a specific administrative directive mandates a control to do so.

**Table 2.1: Control and Risk Addressance**

| id | x (Control Class) | y (Admin Directive ID) |
| :--- | :--- | :--- |
| risk_addr_001 | WorkforceComplianceRisk | admin_dir_001 |
| risk_addr_002 | UnauthorizedAccessRisk | admin_dir_003 |
| risk_addr_003 | DataInterceptionRisk | admin_dir_003 |
| risk_addr_004 | EmergencyDataAvailabilityRisk | admin_dir_004 |

*Table 2.1 Notes:*
*   `id` is the unique identifier for the risk/threat class instance.
*   `x` defines the specific nature of the risk being addressed.
*   `y` acts as a foreign key to the Administrative Directive (`t_hipaa_safeguard_admin`) that mandates the control.

### 3. Technical Safeguards and Encryption Mechanisms

While administrative safeguards provide the governance framework, Technical Safeguards constitute the automated logic and hardware mechanisms protecting electronic Protected Health Information (ePHI). The axiom `hipaa_safeguard_technical` defines this domain. It specifies that a Directive (X) serves as a technical safeguard for a specific asset or process (Y).

The formal definition is:
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`
*   **Verbalization:** {X} is something that hipaa safeguard {Y}

In this context, the "Y" slot often refers to the specific technical risk class defined in the previous section (e.g., `DataInterceptionRisk`). The technical directive implements the logic required to mitigate that risk. For example, an "Encryption Mechanism" is a directive that safeguards against "DataInterceptionRisk." The ontology requires that these technical implementations are not standalone; they must be linked back to the risk classes they address.

The data table for Technical Safeguards demonstrates the implementation of specific technologies (like audit controls or encryption) mapped to the risk identifiers established in the governance layer.

**Table 3.1: Technical Safeguard Implementation**

| id | x (Technical Directive) | y (Risk Class ID) |
| :--- | :--- | :--- |
| tech_dir_001 | AuditControlMechanism | risk_addr_002 |
| tech_dir_002 | TransmissionEncryption | risk_addr_003 |
| tech_dir_003 | IntegrityControlMechanism | risk_addr_003 |
| tech_dir_004 | AuthenticationSystem | risk_addr_002 |

*Table 3.1 Notes:*
*   `x` values represent concrete technical implementations (e.g., Encryption, Audit Controls).
*   `y` values reference the `id` from the Control Addressance table (`t_control_only_addresses_threat_class`), ensuring traceability from the technical control back to the specific risk and its governing administrative policy.

### 4. Physical Safeguards and Facility Access

The axiom `hipaa_safeguard_physical` extends the compliance framework to the tangible domain. Physical safeguards are measures to protect electronic information systems and related buildings and equipment from natural and environmental hazards, as well as unauthorized intrusion. The structure mirrors that of technical safeguards but operates on physical assets and personnel presence.

The formal definition is:
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`
*   **Verbalization:** {X} is something that hipaa safeguard {Y}

Under this axiom, directives such as "Facility Access Controls" or "Workstation Security" are mapped to physical risk classes. These mappings are essential for on-site audits where inspectors verify that physical access logs, security badges, and workstation usage policies are actively mitigating risks like "Unauthorized Physical Access" or "Equipment Theft."

The following table details the instantiation of physical safeguards. Note that the `y` column continues to reference the centralized risk addressance table, reinforcing the concept that physical, technical, and administrative controls are all distinct vectors addressing the same core risk taxonomy.

**Table 4.1: Physical Safeguard Implementation**

| id | x (Physical Directive) | y (Risk Class ID) |
| :--- | :--- | :--- |
| phys_dir_001 | FacilityAccessControls | risk_addr_002 |
| phys_dir_002 | WorkstationUsePolicy | risk_addr_002 |
| phys_dir_003 | DeviceAndMediaControl | risk_addr_003 |
| phys_dir_004 | ContingencyOperationsPlan | risk_addr_004 |

*Table 4.1 Notes:*
*   `x` includes policies regarding facility access, workstation security, and device management.
*   `y` links these physical measures to the relevant risk IDs (e.g., linking `DeviceAndMediaControl` to `DataInterceptionRisk` to cover physical media theft).

### 5. PCI DSS Requirements and Cross-Framework Alignment

The final concept addressed in this chapter involves the integration of PCI DSS requirements into the broader governance ontology. While previous sections focused on HIPAA, the axiom `pci_dss_requirement` demonstrates the extensibility of the `cco:DirectiveICE` framework to other regulatory bodies. This axiom asserts that a Class (X) fulfills a specific PCI DSS requirement (Y).

The formal definition is:
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`
*   **Verbalization:** {X} is something that pci dss requirement {Y}

This mapping is critical for organizations operating under hybrid compliance regimes (e.g., a hospital processing credit card payments). The ontology allows for the mapping of PCI requirements to the same underlying risk addressance table used for HIPAA controls. This enables a unified view of security posture where a single control (such as a Firewall) may address a HIPAA risk (`UnauthorizedAccessRisk`) while simultaneously satisfying a PCI DSS requirement (`Requirement 1: Install and maintain a firewall configuration`).

The table below illustrates how PCI DSS requirements are instantiated within the system, mapped against the shared risk taxonomy.

**Table 5.1: PCI DSS Requirement Mapping**

| id | x (PCI Directive) | y (Risk Class ID) |
| :--- | :--- | :--- |
| pci_req_001 | FirewallConfiguration | risk_addr_002 |
| pci_req_002 | SecureNetworkArchitecture | risk_addr_002 |
| pci_req_003 | CardholderDataEncryption | risk_addr_003 |
| pci_req_004 | VulnerabilityManagementProgram | risk_addr_001 |

*Table 5.1 Notes:*
*   `x` lists specific PCI DSS requirements or the directives implementing them.
*   `y` maps these requirements to the existing risk identifiers (e.g., `CardholderDataEncryption` maps to `risk_addr_003`, consistent with the HIPAA `TransmissionEncryption` mapping).
*   This alignment highlights the convergence of compliance standards across distinct regulatory frameworks.
