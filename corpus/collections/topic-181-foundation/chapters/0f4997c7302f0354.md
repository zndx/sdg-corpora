# Directive ICE Modeling for HIPAA and PCI DSS Compliance

This chapter defines five relational tables that instantiate the Manchester OWL axioms for cco:DirectiveICE subclasses. The tables capture administrative, technical, and physical HIPAA safeguards together with PCI DSS requirements, each linked to threat-addressing controls. All column values are drawn from documented compliance artifacts current as of February 4, 2021. Primary-key and foreign-key constraints enforce the slot restrictions stated in each axiom, enabling deterministic cross-table joins.

## 1. Axiom Structure and Table Projection

Each axiom projects to one table whose columns correspond exactly to the declared slots. Class-valued slots are stored as entity references; no additional columns are introduced. Foreign-key declarations implement the existential and universal restrictions present in the axioms.

### 1.1 t_hipaa_safeguard_admin

Axiom 1 states that an administrative safeguard is a DirectiveICE that hipaaSafeguard some threat class. The table therefore stores the safeguard identifier (id), the safeguard class (x), and the referenced threat class (y). Column id is the primary key; column y is a foreign key into t_control_only_addresses_threat_class.

| id          | x                          | y             |
|-------------|----------------------------|---------------|
| admin_001   | WorkforceAccessPolicy      | ctrl_010      |
| admin_002   | SanctionPolicy             | ctrl_011      |
| admin_003   | TerminationProcedure       | ctrl_012      |
| admin_004   | AccessAuthorizationForm    | ctrl_013      |

### 1.2 t_control_only_addresses_threat_class

Axiom 2 states that a control addressesRisk only a designated threat class. The table stores the control identifier (id), the control class (x), and the single permitted threat class (y). Column id is the primary key; column y is a foreign key into t_hipaa_safeguard_admin, closing the universal restriction.

| id          | x                          | y             |
|-------------|----------------------------|---------------|
| ctrl_010    | UniqueUserIdentification   | admin_001     |
| ctrl_011    | AutomaticLogoff            | admin_002     |
| ctrl_012    | EncryptionAtRest           | admin_003     |
| ctrl_013    | IntegrityControl           | admin_004     |

## 2. Cross-Join Demonstration

A multi-hop query retrieves the administrative safeguard, its controlling threat class, and the PCI DSS requirement that shares the same threat class. The join path is:

t_hipaa_safeguard_admin.y → t_control_only_addresses_threat_class.id  
t_control_only_addresses_threat_class.y → t_hipaa_safeguard_admin.id (for verification)  
t_control_only_addresses_threat_class.id → t_pci_dss_requirement.y

Example query result for threat class ctrl_010:

- admin_001 (WorkforceAccessPolicy) safeguards via ctrl_010 (UniqueUserIdentification)  
- pci_001 (InstallFirewall) also addresses ctrl_010

The joined row set therefore contains the triple (admin_001, ctrl_010, pci_001), confirming that a single threat class is addressed by both an administrative HIPAA safeguard and a PCI DSS requirement.
