# Chapter 7: Ontological Mapping of Kernel Events to Evidential Reasoning Structures

## 7.1 Scope and Preamble

This chapter delineates the formal axioms governing the relationship between low-level kernel process events and high-level evidential reasoning structures. It establishes a rigorous framework for mapping system-level thread identifiers to belief functions, ensuring that audit trails and compliance logs can be queried with semantic precision. The definitions herein are derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), providing a deterministic schema for representing uncertainty in distributed system logs. The following sections introduce the core axioms, their verbalizations, and the corresponding relational implementations required for high-assurance data storage.

## 7.2 Kernel Event Identification and Thread Association

### 7.2.1 Axiom Definition: Kernel Event with Thread ID

The foundational unit of system observation is the Kernel Event, formally defined through the axiom `kernel_event_with_tid`. This axiom asserts that a specific class of process (denoted as {X}) is a subclass of `bfo:0000015` (Process) and possesses a specific property: it is associated with a Thread ID (denoted as {Y}). 

In formal Manchester syntax, this relationship is expressed as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:withThreadId some {Y:Class}`

Verbalization: {X} is something that with thread id {Y}.

This definition is critical for audit compliance because it decouples the event occurrence from the execution context. By treating the Thread ID not merely as an integer but as a distinct class entity {Y}, the ontology allows for the threading context to carry additional semantic weight or reference external structures. In the context of this framework, the Thread ID ({Y}) serves as a bridge to evidential reasoning structures, specifically linking the process event to a mass function that quantifies the certainty of the event's properties.

### 7.2.2 Relational Schema and Implementation

The projection of this axiom into a relational schema enforces strict referential integrity. The table `t_kernel_event_with_tid` captures instances where a specific kernel event is bound to a thread identifier. The schema design mandates that the thread identifier (`y`) is not a primitive value but a foreign key referencing a distinct entity defined in the evidential reasoning layer.

The schema is defined as follows:

```sql
CREATE TABLE t_kernel_event_with_tid (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_mass_function_equiv_frame_and_assignment(id)
)
```

**Table 7.1: Kernel Event to Thread ID Mapping**
This table embodies the `kernel_event_with_tid` axiom. The primary key is `id`, representing the unique instance of the event assertion. The column `x` represents the specific Kernel Event class (a Process), and `y` represents the Thread ID class. The foreign key constraint on `y` ensures that every thread ID is actually a reference to a valid Mass Function instance, creating a dependency where the existence of a thread event implies the existence of a corresponding belief structure.

In the data presented in Table 7.1, the `ProcessSpawnEvent` (KE-2024-001) is associated with the Thread ID `MF-REF-ALPHA`. This association implies that the thread executing this process is governed by the belief structure identified as `MF-REF-ALPHA`. This linkage allows auditors to trace not just *what* process ran, but *which* uncertainty framework was active during its execution.

## 7.3 Mass Functions, Frames of Discernment, and Assignments

### 7.3.1 Axiom Definition: Mass Function Equivalence

The second axiom, `mass_function_equiv_frame_and_assignment`, provides the semantic definition for the Thread ID entity referenced in the previous section. It defines a class {X} as being equivalent to the intersection of two conditions: it is a `cco:DescriptiveICE` (Information Content Entity), it operates over a specific Frame of Discernment ({Y}), and it assigns a mass value to a specific hypothesis or focal element ({Z}).

In formal Manchester syntax, this is expressed as:
`Class: {X:Class} EquivalentTo: cco:DescriptiveICE and (sdg:overFrameOfDiscernment some {Y:Class}) and (sdg:assignsMassTo some {Z:Class})`

Verbalization: {X} is a DescriptiveICE over Frame {Y} and assigns Mass to {Z}.

This axiom is central to the implementation of Dempster-Shafer theory within the system. The "Frame of Discernment" ({Y}) represents the set of mutually exclusive propositions under consideration. The "Mass Assignment" ({Z}) represents the specific belief value allocated to a subset of these propositions. By defining {X} as a `DescriptiveICE`, the ontology ensures that these mathematical constructs are treated as first-class information artifacts, capable of being archived, hashed, and audited.

### 7.3.2 Relational Schema and Implementation

The relational projection of this axiom creates a complex dependency structure. The table `t_mass_function_equiv_frame_and_assignment` stores the definitions of the mass functions. Notably, the column `y` (the Frame of Discernment) contains a foreign key reference back to the `t_kernel_event_with_tid` table. This circular reference (Kernel Event -> Thread ID -> Mass Function -> Frame of Discernment -> Kernel Event) formalizes a closed-loop verification system: the Frame of Discernment for a belief structure is defined by the very Kernel Event that triggered the belief update.

The schema is defined as follows:

```sql
CREATE TABLE t_mass_function_equiv_frame_and_assignment (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_kernel_event_with_tid(id)
)
```

**Table 7.2: Mass Function Definitions and Assignments**
This table embodies the `mass_function_equiv_frame_and_assignment` axiom. The primary key is `id`, representing the unique identifier of the Mass Function (which serves as the Thread ID in Table 7.1). Column `x` is the DescriptiveICE (the belief function itself). Column `y` is the Frame of Discernment, referencing the Kernel Event ID that defines the context. Column `z` is the specific hypothesis or focal element receiving the mass assignment.

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| MF-REF-ALPHA | SpawnBeliefStructure | KE-2024-001 | ValidProcessHypothesis |
| MF-REF-BETA | IntegrityCheckState | KE-2024-002 | CorruptionDetected |
| MF-REF-GAMMA | MuxControlState | KE-2024-003 | ChannelActive |
| MF-REF-DELTA | AuthValidationState | KE-2024-004 | TokenRevoked |
| MF-REF-EPSILON | TelemetryState | KE-2024-005 | TransmissionSuccess |

In the data presented in Table 7.2, the Mass Function `MF-REF-ALPHA` (referenced as `y` in Table 7.1) is defined as a `SpawnBeliefStructure`. Its Frame of Discernment (`y`) is `KE-2024-001`, the `ProcessSpawnEvent`. This indicates that the scope of the belief calculation is strictly limited to the context of that specific process spawn. The mass assignment (`z`) is `ValidProcessHypothesis`, indicating that the belief function quantifies the likelihood that the process was valid.

## 7.4 Verification and Compliance Implications

The interplay between these two axioms creates a robust chain of evidence for system auditors. When a compliance officer queries the `t_kernel_event_with_tid` table, they are immediately presented with the `id` of the relevant Mass Function. By joining on this key, they can retrieve the `t_mass_function_equiv_frame_and_assignment` record, which reveals the hypothesis being tested (`z`) and the specific event context (`y`) that defined the scope of the analysis.

This structure prevents "orphan" thread IDs that do not correspond to a defined belief state, and it prevents "floating" mass functions that are not anchored to a specific system event. The circular dependency enforces a strict 1:1 mapping between the execution context (Thread) and the reasoning context (Frame), ensuring that every inference made by the system is traceable to a specific, timestamped kernel event.
