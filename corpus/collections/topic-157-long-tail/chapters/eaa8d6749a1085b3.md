# Chapter 4: Kernel Event Attribution and Evidential Mass Assignment in Audit Trails

## 4.1 Scope and Preamble

This chapter establishes the ontological framework for mapping low-level kernel telemetry to high-level evidential structures within a compliant audit environment. It addresses the critical requirement of traceability, ensuring that every discrete process event is irrevocably bound to a thread identifier and subsequently contextualized within a belief structure. The methodology outlined herein aligns with the BFO (Basic Formal Ontology) definitions of processual entities and utilizes Dempster-Shafer structures to quantify uncertainty in security event classification. Auditors must verify that the relational integrity between kernel events and their associated mass functions is maintained to satisfy the non-repudiation requirements of the governance framework.

## 4.2 Kernel Event Attribution and Thread Identification

### 4.2.1 Ontological Definition

In the context of high-assurance logging, a `Kernel Event` is not merely a timestamped entry but a distinct occurrent entity that realizes a specific process within the operating system kernel. According to the governing ontology, specifically the axiom identified as `kernel_event_with_tid`, any such event is a subclass of `bfo:0000015` (Process). The defining characteristic of this class is the possession of a specific Thread ID (`sdg:withThreadId`). This relationship is not merely correlative; it is constitutive. The event cannot exist as a recorded entity within the audit trail without this attribution.

The formalization asserts that {X} is something that with thread id {Y}. In practice, this means that the integrity of the audit log depends on the immutable binding of the event record {X} to the thread identifier {Y}. This binding serves as the primary key for all subsequent forensic analysis. If the link between the process occurrent and the thread ID is severed, the provenance of the log entry is lost, rendering the audit trail non-compliant with standards such as ISO/IEC 27001:2022 (A.12.3.1).

### 4.2.2 Relational Implementation and Evidence

To enforce this axiom within the relational database schema supporting the audit infrastructure, the table `t_kernel_event_with_tid` is utilized. This structure captures the entity reference of the event class (`x`) and binds it to a specific instance of a thread identifier (`y`). It is imperative to recognize that the `y` slot in this schema is not a primitive integer but a reference to a complex entity defined in the evidential layer (specifically, a mass function). This circular dependency ensures that the thread ID is not an orphaned value but is semantically anchored to a belief structure.

The following table provides representative instances extracted from a compliant system kernel. These rows illustrate the binding of specific event classes (e.g., `SystemCallEvent`, `InterruptHandlerEvent`) to their respective thread identifiers, which are themselves encoded as references to mass function entities.

| id | x | y |

*   **y**: The foreign key reference to the thread identifier entity, which resolves to a mass function instance (see Section 4.3).

### 4.2.3 Compliance Verification

During an audit, examiners must query the `t_kernel_event_with_tid` table to verify that no entry possesses a `NULL` value in the `y` column. Furthermore, the referential integrity constraint must be validated to ensure that every `y` value corresponds to a valid entry in the target mass function table. This verification confirms that every kernel process is not only identified but is also situated within a frame of discernment for security classification.

## 4.3 Evidential Mass Functions and Frame Assignment

### 4.3.1 Ontological Definition

While the kernel event provides the raw occurrence data, compliance requires the interpretation of this data within a framework of uncertainty. The ontology defines the class `mass_function_equiv_frame_and_assignment` to bridge this gap. This class is equivalent to the intersection of three conditions:
1.  It is a `cco:DescriptiveICE` (Information Content Entity).
2.  It is defined over a specific `sdg:overFrameOfDiscernment` ({Y}).
3.  It performs the action of `sdg:assignsMassTo` ({Z}).

This axiom formalizes the Dempster-Shafer structure within the audit system. The "Frame of Discernment" represents the set of mutually exclusive hypotheses (e.g., *Benign*, *Malicious*, *Anomalous*) that the auditor considers. The "Mass Assignment" represents the degree of belief allocated to a specific subset of this frame based on the kernel event evidence.

Crucially, the schema dictates that the Frame of Discernment (`y`) is a reference back to a `kernel_event_with_tid`. This recursive structure implies that the context for the belief calculation (the frame) is dynamically generated by the specific kernel event being analyzed. In other words, the "Frame" is not a static global list of hypotheses, but a context-specific set of possibilities derived from the thread's state.

### 4.3.2 Relational Implementation and Evidence

The implementation of this axiom is realized in the `t_mass_function_equiv_frame_and_assignment` table. This table serves as the registry for all belief calculations performed by the system. Each row represents a specific evidential packet (`x`) that interprets a kernel event (`y`) and assigns a belief mass to a target hypothesis (`z`).

The data below illustrates how the system maps the kernel events referenced in Table 4-1 to specific security hypotheses. For instance, the `SystemCallEvent` (KEVT-2024-001) is analyzed within a frame of discernment that leads to a mass assignment targeting a `Hypothesis_FileCorruption`.

*   **z**: The specific hypothesis or focal element to which the mass is assigned.

### 4.3.3 Interpretation of Assignments

The assignment of mass (`z`) is the critical output of the audit logic. It transforms the binary existence of a kernel event into a probabilistic security signal. For example, row `MF-REF-ALPHA` indicates that the evidence derived from `KEVT-2024-001` supports the `Hypothesis_FileCorruption`. The strength of this support (the numeric mass value) is managed in auxiliary property tables not shown here, but the structural linkage is mandatory.

Auditors must ensure that the `z` column contains valid references to the controlled vocabulary of hypotheses defined in the Governance Handbook. Unauthorized or null values in `z` indicate a failure of the classification engine and constitute a critical finding in the audit report.
