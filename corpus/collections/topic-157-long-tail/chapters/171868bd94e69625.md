# Chapter 7: Evidentiary Correlation of Kernel Events and Belief Structures

## Scope

This chapter establishes the formal ontology for correlating low-level kernel events with high-level evidentiary mass functions within a compliant digital forensics framework. It defines the structural requirements for mapping system processes to thread identifiers and details the application of Dempster-Shafer theory to assign evidentiary weight to specific frames of discernment. The provisions herein shall apply to all system audits requiring the reconstruction of execution paths from volatile memory artifacts.

## 1. Kernel Event Identification and Thread Correlation

### 1.1 Definition and Ontological Basis

In accordance with the Basic Formal Ontology (BFO), a kernel event is formally classified as a process, specifically denoted by the identifier `bfo:0000015`. This classification asserts that the event is an occurrent entity, unfolding in time and possessing temporal parts. To ensure traceability and non-repudiation in audit logs, every such process must be associated with a specific thread identifier. However, within this framework, the thread identifier is not treated as a primitive data type (e.g., a hexadecimal integer) but as a first-class object with its own evidentiary properties.

The governing axiom for this relationship is defined as follows: a Kernel Event (Class X) is a subclass of `bfo:0000015` and possesses a relationship `sdg:withThreadId` with a Thread Identifier (Class Y). This structure mandates that the existence of a kernel event is ontologically dependent on the existence of a thread identifier object. This dependency is critical for maintaining the integrity of the audit trail, as it prevents the logging of orphaned processes that cannot be attributed to a specific execution context.

### 1.2 Implementation and Data Provenance

The implementation of this axiom requires a relational schema where the primary key of the event record is inextricably linked to the thread identifier record. The thread identifier, in this context, serves as a proxy for the execution context, encapsulating the state of the CPU registers and memory permissions at the moment of the event's inception.

The following table, `t_kernel_event_with_tid`, embodies the axiom `kernel_event_with_tid`. The primary key `id` represents the unique identifier for the kernel event instance. The column `x` denotes the specific class of the kernel event (e.g., `SystemCallDispatch`, `InterruptHandling`). The column `y` represents the thread identifier, which, per the foreign key constraint, must reference a valid entry in the mass function table. This circular dependency ensures that the thread ID is not merely a scalar value but a complex object carrying a belief structure, as detailed in Section 2.

**Table 1.1: Kernel Event to Thread Identifier Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `evt_2023_10_alpha` | `SystemCallDispatch` | `mass_fn_ref_001` |
| `evt_2023_10_beta` | `PageFaultException` | `mass_fn_ref_002` |
| `evt_2023_10_gamma` | `NetworkPacketRx` | `mass_fn_ref_003` |
| `evt_2023_10_delta` | `ContextSwitch` | `mass_fn_ref_004` |
| `evt_2023_10_epsilon` | `IOCompletion` | `mass_fn_ref_005` |

*Note: The column `y` functions as a foreign key to the `t_mass_function_equiv_frame_and_assignment` table, enforcing referential integrity between the event and the evidentiary mass function.*

### 1.3 Compliance Verification

Auditors must verify that for every record in `t_kernel_event_with_tid`, the referenced entity in column `y` exists and is active. Any null values or dangling references in column `y` constitute a critical failure of the logging mechanism and must be flagged as a violation of the `kernel_event_with_tid` axiom. Furthermore, the class specified in column `x` must be a recognized subclass of `bfo:0000015`.

## 2. Mass Function Assignment and Frames of Discernment

### 2.1 Descriptive Information Content Entities

The assignment of probability or belief to specific hypotheses within a forensic investigation is modeled using the Dempster-Shafer structure. In this ontology, the vehicle for this assignment is a Class X that is equivalent to a `cco:DescriptiveICE` (Descriptive Information Content Entity). This entity serves as the container for the evidentiary assertion, distinct from the physical occurrence of the event itself.

The axiom `mass_function_equiv_frame_and_assignment` posits that this entity (X) operates over a specific Frame of Discernment (Y) and assigns a Mass (Z) to a hypothesis within that frame. The Frame of Discernment represents the set of mutually exclusive propositions relevant to the investigation (e.g., {Benign, Malicious, Suspicious}). The Mass Assignment represents the basic probability assignment specifically allocated to one of these propositions given the evidence.

### 2.2 Relational Structure and Circular Dependency

The relational schema for this concept, `t_mass_function_equiv_frame_and_assignment`, establishes a complex dependency structure. The column `y` (Frame of Discernment) references the `id` of the kernel event. This creates a bidirectional link: the kernel event points to a mass function via its thread ID, and that mass function points back to the kernel event as its frame of discernment.

This circularity is intentional and reflects the recursive nature of forensic analysis. The event provides the context for the belief calculation, and the belief calculation (the mass function) provides the identity (thread ID) used to index the event. In practice, this means that the "Thread ID" is actually a calculated belief vector derived from the event's properties, rather than a raw hardware value.

The table below illustrates this structure. The column `x` identifies the specific DescriptiveICE class (e.g., `BeliefStructureVector`). Column `y` links back to the kernel event ID, establishing the frame of discernment. Column `z` contains the specific hypothesis or focal element to which the mass is assigned (e.g., `Hypothesis_Injection`).

**Table 2.1: Mass Function Equivalence and Assignment**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `mass_fn_ref_001` | `BeliefStructureVector` | `evt_2023_10_alpha` | `Hypothesis_Authenticated` |
| `mass_fn_ref_002` | `BeliefStructureVector` | `evt_2023_10_beta` | `Hypothesis_Malicious` |
| `mass_fn_ref_003` | `BeliefStructureVector` | `evt_2023_10_gamma` | `Hypothesis_Unverified` |
| `mass_fn_ref_004` | `BeliefStructureVector` | `evt_2023_10_delta` | `Hypothesis_Scheduled` |
| `mass_fn_ref_005` | `BeliefStructureVector` | `evt_2023_10_epsilon` | `Hypothesis_Complete` |

*Note: Column `y` is a foreign key referencing `t_kernel_event_with_tid(id)`, ensuring the frame of discernment is anchored to a valid process instance.*

### 2.3 Interpretation of Mass Assignments

The values in column `z` (`Hypothesis_...`) represent the outcome of the evidentiary reasoning process. For instance, in the second row of Table 2.1, the mass function `mass_fn_ref_002` is analyzing the kernel event `evt_2023_10_beta` (a Page Fault). The system has assigned a mass to the hypothesis `Hypothesis_Malicious`. This implies that the thread ID associated with this event (which is `mass_fn_ref_002` itself, as seen in Table 1.1) carries a high degree of belief that the page fault was caused by malicious activity, such as a buffer overflow or an exploit attempt.

This dual-referencing mechanism allows investigators to query the system not just by "what happened" (the kernel event class X in Table 1.1) but by "what is believed to have happened" (the mass assignment Z in Table 2.1). It transforms the log from a static record of system calls into a dynamic, evidence-based assertion of system state.

## 3. Audit and Governance Framework

### 3.1 Integrity Controls

To maintain the validity of the ontological structure described above, the database management system (DBMS) must enforce the declared foreign key constraints at all times. Updates to the `t_kernel_event_with_tid` table must cascade to the `t_mass_function_equiv_frame_and_assignment` table where appropriate, or be restricted if they would orphan a mass function.

Specifically, the following integrity rules must be implemented:
1.  **Existence Check:** No row shall exist in `t_kernel_event_with_tid` where `y` does not exist in `t_mass_function_equiv_frame_and_assignment`.
2.  **Frame Validity:** No row shall exist in `t_mass_function_equiv_frame_and_assignment` where `y` does not exist in `t_kernel_event_with_tid`.
3.  **Non-Nullity:** Columns `y` and `z` in the mass function table are defined as `NOT NULL`. A mass function without a frame of discernment or a target hypothesis is semantically void and violates the axiom `mass_function_equiv_frame_and_assignment`.

### 3.2 Reporting Requirements

Quarterly audit reports must include a reconciliation of the two tables presented in this chapter. Discrepancies, such as kernel events with "unknown" thread IDs or mass functions referencing non-existent events, must be documented and remediated. The report shall quantify the "Belief Coverage," defined as the percentage of kernel events for which a mass assignment (Z) has been successfully calculated and recorded.
