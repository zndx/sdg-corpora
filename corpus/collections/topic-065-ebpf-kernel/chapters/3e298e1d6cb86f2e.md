# Chapter 4: Governance Protocols for Attestation and Evidence Verification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological structures required for validating governance artifacts within a regulated digital environment. It delineates the procedural and informational entities necessary to establish a chain of custody for organizational directives, ensuring that all attestations are rigorously signed and that all verification requirements are anchored to specific evidentiary traces. The following sections define the axiomatic relationships between processes, persons, and information content entities, providing a normalized schema for the implementation of automated compliance systems.

## 4.2 Attestation Processes and Minimum Signatory Requirements

### 4.2.1 Definition and Axiomatic Structure

In the context of governance frameworks, an attestation is formally defined as a process that must be validated by the intervention of an authorized agent. The axiom `attestation_min_one_signer` posits that for any class {X} defined as an attestation process, the entity must be a subclass of `bfo:0000015` (a process) and must possess the property `sdg:signedBy` with a cardinality of at least one (`min 1`) relative to the class `cco:Person`.

This constraint ensures that no automated or manual attestation process is considered valid within the system unless it is explicitly associated with a human agent who bears responsibility for the process's execution. The relational projection of this axiom isolates the process identifier and the class definition to enforce referential integrity at the database level.

## 4.3 Evidence Traces and Claim Support

### 4.3.1 Definition and Axiomatic Structure

The integrity of a compliance framework relies heavily on the ability to trace specific governance outcomes back to supporting evidence. The axiom `trace_supports_claim` formalizes this by defining a class {X} as a subclass of `bfo:0000015` (a process) which possesses the property `sdg:supportsClaim`. This property must assert a relationship to at least one instance of `cco:DescriptiveICE` (Descriptive Information Content Entity).

Verbalized, {X} is an entity (specifically a process of tracing or recording) that provides the foundational support for a descriptive claim. This axiom is central to the "long tail" of compliance data, where the validity of high-level reports depends on the granular availability of low-level logs and measurements. The relational schema for this axiom serves as a central junction, as the primary keys generated here are utilized as foreign keys in verification and audit period definitions.

## 4.4 Specific Signatory Assignments

### 4.4.1 Definition and Axiomatic Structure

While Section 4.2 established the *necessity* of a signatory, the axiom `attestation_signed_by` refines this by defining the specific assignment of a signatory to a process. Here, class {X} is defined as a subclass of `bfo:0000015` (a process) that is signed by some `cco:Person`.

This axiom moves from the domain of cardinality constraints to the domain of existential instantiation. It asserts that for a specific process instance, there exists a person who has executed the signing action. This distinction is vital for audit trails: the former ensures a role is filled, while the latter captures the specific identity of the individual fulfilling that role at a point in time.

## 4.5 Verification Requirements and Evidence Linkage

### 4.5.1 Definition and Axiomatic Structure

The axiom `requirement_min_one_verification` addresses the validation of directives. It defines a class {X} as a subclass of `cco:DirectiveICE` (Directive Information Content Entity) which must be verified by a minimum of one entity {Y}. Class {Y} is constrained to be a class that supports a claim (as defined in Section 4.3).

This structure creates a dependency chain where a directive (a rule or requirement) cannot be considered "verified" unless it is backed by a valid trace process. The relational schema enforces this via a foreign key constraint, ensuring that the verifying entity {Y} corresponds to a valid entry in the `t_trace_supports_claim` table. This effectively maps policy to proof.

## 4.6 Audit Periods and Temporal Scoping

### 4.6.1 Definition and Axiomatic Structure

The final axiom, `audit_for_period`, governs the temporal scoping of audit processes. It defines a class {X} (the audit process) as a subclass of `bfo:0000015` which is conducted for a specific audit period {Y}. Class {Y} is structurally identical to the verifying trace in the previous axiom; it is a class that supports a claim.

In this ontology, an "audit period" is not merely a temporal interval but is treated as an informational entity (a trace) that supports the claim of a specific time boundary. This allows the system to treat time scopes as first-class citizens that can be versioned, approved, and audited themselves. The foreign key constraint ensures that audits are only performed against formally defined and recognized period traces.
