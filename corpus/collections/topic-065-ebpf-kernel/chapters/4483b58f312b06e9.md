# Regulatory Attestation and Audit Traceability

This chapter defines a five-table relational schema that implements five OWL axioms for directive governance. The schema records attestations, supporting traces, signed processes, verified requirements, and period-bound audits. All column values are drawn from a single compliance review conducted by the Employees' Compensation Appeals Board for the Department of Homeland Security, Federal Emergency Management Agency, Denton, TX.

## 1 Schema Overview

The schema uses two entity classes—processes and descriptive information content entities—linked by foreign-key references. Primary keys are system-generated identifiers. Foreign keys enforce the minimum-cardinality and existential restrictions stated in the axioms. Cross-table joins recover multi-hop facts such as “which signer attested a requirement verified by a given trace.”

### 1.1 t_attestation_min_one_signer

Axiom 1 states that every attestation process must be signed by at least one person. The table therefore stores the attestation identifier and the class of the attested process; the primary key guarantees uniqueness of each attestation instance.

```sql
CREATE TABLE t_attestation_min_one_signer (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

|----|---|

| att-005 | AttestationProcess |

### 1.2 t_trace_supports_claim

Axiom 2 states that a trace supports at least one descriptive information content entity. The table records each trace and the claim class it supports; the primary key permits later foreign-key references from requirement and audit tables.

```sql
CREATE TABLE t_trace_supports_claim (
```

### 1.3 t_attestation_signed_by

Axiom 3 states that an attestation process is signed by a person. The table stores the attestation identifier together with the signer class; the primary key isolates each signed attestation occurrence.

### 1.4 t_requirement_min_one_verification

Axiom 4 states that a directive information content entity must be verified by at least one trace. The table therefore records the requirement identifier, the directive class, and a foreign key to t_trace_supports_claim; the foreign-key constraint enforces the minimum verification cardinality.

```sql
CREATE TABLE t_requirement_min_one_verification (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_trace_supports_claim(id)
);
```

| id | x | y |
|----|---|---|
| req-001 | DirectiveICE | trc-001 |
| req-002 | DirectiveICE | trc-002 |
| req-003 | DirectiveICE | trc-003 |
| req-004 | DirectiveICE | trc-004 |

### 1.5 t_audit_for_period

Axiom 5 states that an audit process is defined for a specific audit period. The table stores the audit identifier, the process class, and a foreign key to t_trace_supports_claim that identifies the period claim; the foreign-key constraint ensures every audit references a valid trace.

```sql
CREATE TABLE t_audit_for_period (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_trace_supports_claim(id)
);
```

| id | x | y |
|----|---|---|
| aud-001 | AuditProcess | trc-005 |
| aud-002 | AuditProcess | trc-006 |
| aud-003 | AuditProcess | trc-001 |
| aud-004 | AuditProcess | trc-002 |

## 2 Cross-Join Example

Question: Which signer attested requirement req-001, and for which audit period is that requirement verified?

Join path:  
t_requirement_min_one_verification.y → t_trace_supports_claim.id  
t_attestation_min_one_signer.id → t_attestation_signed_by.id (same attestation)  
t_audit_for_period.y → t_trace_supports_claim.id (shared claim)

Result row:  
req-001, DirectiveICE, trc-001, ComplianceClaim, att-001, Person, aud-003, AuditProcess, trc-001

The joined row shows that Person signed attestation att-001 for requirement req-001, which is verified by trace trc-001, and that the same trace anchors audit aud-003 covering the corresponding audit period.
