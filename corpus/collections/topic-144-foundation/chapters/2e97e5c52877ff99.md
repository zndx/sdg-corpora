# Chapter 4: Formal Governance Structures and ISO 27001 Control Implementation

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the implementation of information security management systems (ISMS) within the context of ISO/IEC 27001 compliance. It provides a rigorous examination of the relationships between audit processes, control classifications, and evidentiary requirements as defined by the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). The content herein is intended for compliance officers, internal auditors, and information security governance professionals who require a precise, axiomatically grounded understanding of how directive governance intersects with technical control environments. The mappings provided are deterministic, ensuring that relational data structures maintain referential integrity across the audit lifecycle.

## 4.2 Audit Conducted By

### 4.2.1 Ontological Definition and Provenance

In the domain of governance frameworks, the audit function is not merely an activity but a distinct temporal process (BFO:0000015) that requires agentive causation. The axiom `audit_conducted_by` establishes that any audit process is necessarily dependent upon the existence of a `cco:Person` who acts as the auditor. This relationship is foundational to the validity of any compliance assertion; without a valid agentive entity conducting the investigation, the process lacks the legal and procedural standing required for regulatory adherence.

The axiom asserts that the audit class {X} is a subclass of processes that are `sdg:conductedBy` some person. This implies that the instantiation of an audit event is invalid unless it is bound to a specific individual or role-bearing entity within the organizational hierarchy. In practice, this prevents the assignment of audit responsibilities to abstract organizational units without a responsible human delegate, thereby ensuring accountability chains are unbroken during forensic review.

### 4.2.2 Relational Implementation

The relational projection of this axiom simplifies the complex object property into a direct entity mapping. The table `t_audit_conducted_by` serves as a registry of audit process types. The primary key `id` ensures that each distinct audit classification is uniquely identifiable, while the column `x` denotes the specific class of the audit being conducted.

**Table 4-1: Audit Process Classification**

| :--- | :--- |
| `AUD-2023-01` | `InternalISMSAudit` |
| `AUD-2023-02` | `VendorComplianceReview` |
| `AUD-2023-03` | `AccessControlAudit` |

*Table 4-1 illustrates the instantiation of specific audit classes. Each row represents a distinct process type (X) that, by definition of the axiom, must be conducted by a person. The `id` serves as the persistent identifier for the audit process record.*

## 4.3 ISO 27001 Annex A Subclass

### 4.3.1 Control Classification and Directives

The taxonomy of controls defined in ISO/IEC 27001 Annex A represents a codified set of information security directives. The axiom `iso27001_annexa_subclass` formalizes the relationship between a governance directive (`cco:DirectiveICE`) and its corresponding Annex A control classification. Specifically, it asserts that a class {X} is a subclass of directives that implements or references a specific Annex A control {Y}.

This structure is critical for mapping high-level governance policies to specific technical controls. By asserting that {X} is a directive that has an `sdg:iso27001AnnexA` relationship to {Y}, the ontology enforces a strict mapping between organizational mandates and the standardized control objectives defined in the ISO framework. This allows for automated reasoning to determine if a specific directive satisfies the requirements of a given control objective.

### 4.3.2 Dependency on Requirement Specifications

A critical aspect of this axiom is the reliance on external requirement definitions. The relational schema enforces a foreign key constraint where the Annex A control reference ({Y}) must correspond to an entry in the requirements specification table. This creates a normalized dependency where controls cannot exist in isolation; they must be tethered to a specific requirement definition that details the operational parameters of the control.

**Table 4-2: ISO 27001 Annex A Control Mappings**

| id | x | y |
| :--- | :--- | :--- |
| `CTRL-001` | `AccessControlPolicy` | `REQ-001` |
| `CTRL-002` | `CryptographyPolicy` | `REQ-002` |
| `CTRL-003` | `PhysicalEntryPolicy` | `REQ-003` |

*Table 4-2 depicts the mapping of directive classes (X) to their Annex A equivalents. The column `y` represents the foreign key reference to the requirement specification table (`t_requirement_equiv_specifies_target`), ensuring that every control mapping is grounded in a formal requirement definition.*

## 4.4 Requirement Equivalence Specification

### 4.4.1 Tripartite Structure of Directives

The axiom `requirement_equiv_specifies_target` defines the complex equivalence class that constitutes a fully specified governance directive. Unlike simple subclass relationships, this axiom utilizes an `EquivalentTo` construct, asserting that a class {X} is equivalent to the intersection of a `cco:DirectiveICE`, a specification of some requirement {Y}, and an application to some target {Z}.

This tripartite structure—Directive, Specifies, AppliesTo—ensures that requirements are not merely abstract statements but are operationalized directives targeting specific assets or systems. The equivalence axiom implies that for an entity to be recognized as a valid requirement in this system, it must possess all three characteristics simultaneously. This eliminates ambiguity regarding whether a policy is merely a suggestion or a binding requirement; if it lacks a specified target ({Z}), it fails the equivalence test.

### 4.4.2 Bidirectional Referential Integrity

The relational schema for this axiom introduces a recursive dependency structure. The requirement {X} specifies a control class {Y}, which in turn references the requirement ID. This circular reference is intentional and models the iterative nature of compliance frameworks where requirements define controls, and controls validate requirements. The schema enforces that the `y` column (the specified control) must exist in the Annex A subclass table, maintaining a closed loop of governance definitions.

**Table 4-3: Requirement Specification and Targeting**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `REQ-001` | `MandatoryAccessControl` | `CTRL-001` | `HRDatabase` |
| `REQ-002` | `DataAtRestEncryption` | `CTRL-002` | `CustomerFiles` |
| `REQ-003` | `SecureDataCenterEntry` | `CTRL-003` | `ServerRoomA` |

*Table 4-3 details the equivalence classes for specific requirements. The column `x` names the requirement, `y` links it to the Annex A control (referencing Table 4-2), and `z` identifies the specific target system or asset to which the directive applies. This structure ensures that every requirement is actionable and bound to a target.*

## 4.5 Attestation with Supporting Evidence

### 4.5.1 The Evidentiary Standard

Attestation represents the formal assertion that a control is operating as intended. The axiom `attestation_with_supporting_evidence` posits that an attestation process {X} is a subclass of BFO processes that must include `sdg:withSupportingEvidence` some {Y}. This elevates the attestation from a subjective claim to an objective, evidence-backed verification.

In the context of an audit, this axiom mandates that a simple statement of compliance is insufficient. The attestation must be accompanied by artifacts—logs, screenshots, configuration exports, or third-party reports—that substantiate the claim. The ontology treats the evidence {Y} as a distinct class, allowing for the categorization of evidence types (e.g., `SystemLog`, `ManagerSignature`) and the tracking of their provenance.

### 4.5.2 Linking Evidence to Controls

The relational structure binds the attestation to the specific control being verified through a foreign key constraint. The evidence {Y} must reference an entry in the ISO 27001 Annex A subclass table. This ensures that attestations are not floating in a vacuum but are strictly tied to the control framework established in Section 4.3. It enforces the discipline that evidence must be collected *for* a specific control objective, rather than gathered indiscriminately.

**Table 4-4: Attestation and Evidence Registry**

| id | x | y |
| :--- | :--- | :--- |
| `ATT-EV-100` | `QuarterlyAccessReview` | `CTRL-001` |
| `ATT-EV-101` | `KeyManagementAudit` | `CTRL-002` |
| `ATT-EV-102` | `BadgeLogVerification` | `CTRL-003` |

*Table 4-4 records instances of attestation processes (X) and links them to the relevant control class (Y). The foreign key constraint on `y` ensures that the evidence provided is valid for the specific ISO 27001 control referenced in `t_iso27001_annexa_subclass`.*

## 4.6 Attestation at Period

### 4.6.1 Temporal Validity of Compliance

Compliance is not a static state but a dynamic condition that varies over time. The axiom `attestation_at_period` addresses this by defining that an attestation process {X} occurs `sdg:atAttestationPeriod` some {Y}. This temporal indexing is crucial for maintaining the currency of compliance certifications and for identifying gaps in coverage during specific reporting windows.

This axiom allows the governance framework to query the state of controls at any given point in history. By associating the attestation with a period {Y}, which is linked to the control cycle, the system can determine whether a specific asset was compliant at the time of a security incident or during a specific audit window. This is often a requirement for forensic investigations and regulatory reporting.

### 4.6.2 Periodization and Control Cycles

The relational schema treats the period {Y} as a reference to the control subclass, effectively binding the attestation period to the lifecycle of the control implementation. While seemingly counter-intuitive (linking a time to a class), in this ontology, the "period" is defined by the operational cycle of the control itself (e.g., the annual review cycle for `AccessControlPolicy`). This structure enforces that attestations are only valid within the defined operational periods of the controls they assess.

**Table 4-5: Attestation Periodicity**

| :--- | :--- | :--- |
| `ATT-PR-500` | `FY23_Q4_Audit` | `CTRL-001` |
| `ATT-PR-501` | `FY23_Annual_CryptReview` | `CTRL-002` |
| `ATT-PR-502` | `FY23_Biannual_PhysSec` | `CTRL-003` |

*Table 4-5 captures the temporal dimension of attestations. The process `x` is linked to the control cycle `y`, establishing the specific timeframe during which the attestation is valid. This linkage ensures that compliance reporting is temporally accurate and aligned with control maintenance schedules.*
