# ISO 27001 Directive Governance and Attestation Traceability

This chapter defines five core ontological templates that capture directive subclassing, requirement equivalence, audit conduct, and attestation linkage within an ISO 27001 compliance program. The templates are realized as a five-table relational schema whose primary-key and foreign-key constraints enforce the slot restrictions stated in each axiom. Cross-table joins therefore reconstruct the multi-hop chains required by the original Manchester expressions.

## 1. Requirement Equivalence and Target Specification

Axiom 5 states that a requirement class is equivalent to a DirectiveICE that both specifies an annex-A control and applies to a target class. The table below materializes this equivalence directly.

Table t_requirement_equiv_specifies_target embodies Axiom 5. Column id is the primary key. Column y is a foreign key to t_iso27001_annexa_subclass.id; column z records the target class. A reader can join on y to retrieve the annex-A subclass that the requirement specifies.

```sql
SELECT r.id, r.y, r.z, a.x
FROM t_requirement_equiv_specifies_target r
JOIN t_iso27001_annexa_subclass a ON r.y = a.id;
```

| id        | x                                      | y          | z                  |
|-----------|----------------------------------------|------------|--------------------|
| REQ-001   | A.5.1.1 Information Security Policy    | ANNEX-A5   | PolicyDocument     |
| REQ-002   | A.8.2.1 Classification of Information  | ANNEX-A8   | DataAsset          |
| REQ-003   | A.12.4.1 Event Logging                 | ANNEX-A12  | LogRepository      |
| REQ-004   | A.14.2.1 Secure Development Policy     | ANNEX-A14  | DevelopmentProject |
| REQ-005   | A.18.2.2 Compliance with Policies      | ANNEX-A18  | AuditScope         |

## 2. ISO 27001 Annex A Subclassing

Axiom 2 declares that any subclass of DirectiveICE may be further restricted by an ISO 27001 Annex A reference. The following table records these restrictions.

Table t_iso27001_annexa_subclass embodies Axiom 2. Column id is the primary key. Column y is a foreign key to t_requirement_equiv_specifies_target.id. Joining on y yields the requirement that the annex-A subclass satisfies.

```sql
SELECT a.id, a.x, a.y, r.z
FROM t_iso27001_annexa_subclass a
JOIN t_requirement_equiv_specifies_target r ON a.y = r.id;
```

| id        | x                          | y       |
|-----------|----------------------------|---------|
| ANNEX-A5  | Annex A.5 Policy           | REQ-001 |
| ANNEX-A8  | Annex A.8 Asset Management | REQ-002 |
| ANNEX-A12 | Annex A.12 Operations      | REQ-003 |
| ANNEX-A14 | Annex A.14 Development     | REQ-004 |
| ANNEX-A18 | Annex A.18 Compliance      | REQ-005 |

## 3. Audit Conduct

Axiom 1 states that an audit process is conducted by a person. The table below records the conducting person for each audit instance.

Table t_audit_conducted_by embodies Axiom 1. Column id is the primary key. No foreign key is declared; linkage to other tables occurs through shared x values that also appear as attestation identifiers. A reader can therefore correlate an audit identifier with its attestation record by equi-joining on x.

```sql
SELECT c.id, c.x, e.y
FROM t_audit_conducted_by c
JOIN t_attestation_with_supporting_evidence e ON c.x = e.x;
```

| id        | x           |
|-----------|-------------|
| AUD-1001  | ATTEST-001  |
| AUD-1002  | ATTEST-002  |
| AUD-1003  | ATTEST-003  |
| AUD-1004  | ATTEST-004  |

## 4. Attestation with Supporting Evidence

Axiom 3 asserts that an attestation process carries supporting evidence drawn from an annex-A subclass. The table below records these evidence links.

Table t_attestation_with_supporting_evidence embodies Axiom 3. Column id is the primary key. Column y is a foreign key to t_iso27001_annexa_subclass.id. A cross-join on y recovers both the annex-A control and the requirement it satisfies.

```sql
SELECT e.id, e.x, e.y, a.x AS annex_label, r.z AS target
FROM t_attestation_with_supporting_evidence e
JOIN t_iso27001_annexa_subclass a ON e.y = a.id
JOIN t_requirement_equiv_specifies_target r ON a.y = r.id;
```

| id        | x           | y         |
|-----------|-------------|-----------|
| EV-9001   | ATTEST-001  | ANNEX-A5  |
| EV-9002   | ATTEST-001  | ANNEX-A8  |
| EV-9003   | ATTEST-002  | ANNEX-A12 |
| EV-9004   | ATTEST-003  | ANNEX-A14 |
| EV-9005   | ATTEST-004  | ANNEX-A18 |

## 5. Attestation Period

Axiom 4 states that an attestation occurs at a defined period, again linked to an annex-A subclass.

Table t_attestation_at_period embodies Axiom 4. Column id is the primary key. Column y is a foreign key to t_iso27001_annexa_subclass.id. Joining on y produces the period-qualified annex-A control and its originating requirement.

```sql
SELECT p.id, p.x, p.y, a.x AS annex_label
FROM t_attestation_at_period p
JOIN t_iso27001_annexa_subclass a ON p.y = a.id;
```

| id        | x           | y         |
|-----------|-------------|-----------|
| PER-7001  | ATTEST-001  | ANNEX-A5  |
| PER-7002  | ATTEST-002  | ANNEX-A12 |
| PER-7003  | ATTEST-003  | ANNEX-A14 |
| PER-7004  | ATTEST-004  | ANNEX-A18 |

## 6. Multi-Hop Query Example

Question: Which target class is attested by ATTEST-001 during period PER-7001 and supported by evidence drawn from Annex A.5?

Execution path:
1. Start at t_attestation_at_period where id = PER-7001 → y = ANNEX-A5, x = ATTEST-001.
2. Join t_attestation_with_supporting_evidence on x = ATTEST-001 and y = ANNEX-A5 → confirms evidence link.
3. Join t_iso27001_annexa_subclass on id = ANNEX-A5 → y = REQ-001.
4. Join t_requirement_equiv_specifies_target on id = REQ-001 → z = PolicyDocument.

Result row: (ATTEST-001, PER-7001, ANNEX-A5, REQ-001, PolicyDocument).
