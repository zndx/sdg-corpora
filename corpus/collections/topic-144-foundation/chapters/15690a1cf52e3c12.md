# Chapter 4: Governance Frameworks and ISO 27001 Compliance Mapping

This chapter delineates the structural relationships between organizational directives, ISO 27001 Annex A controls, and the audit processes that verify compliance. It establishes the ontological framework necessary to map internal governance artifacts to regulatory requirements, ensuring traceability from high-level policy to specific evidence. The following sections define the core axioms governing this framework, supported by relational data schemas that enforce referential integrity across compliance domains.

## 1. Audit Conducted By

In the context of enterprise governance, an audit is formally defined not merely as a review but as a specific process (`bfo:Process`) that requires agency. The axiom `audit_conducted_by` asserts that for any audit class {X} to be validly instantiated, it must be conducted by a person (`cco:Person`). This establishes the fundamental chain of responsibility; an audit cannot exist as a disembodied event. It must be attributable to a responsible agent with the authority to inspect and verify.

This constraint is critical for maintaining the integrity of the compliance lifecycle. When an audit record is generated, the system must capture both the classification of the audit event and the identity of the auditor. The relational projection of this axiom isolates the audit class, ensuring that every audit entry is linked to a defined audit type.

## 2. ISO 27001 Annex A Subclass

Organizational directives often function as implementations of broader regulatory standards. The axiom `iso27001_annexa_subclass` formalizes this by asserting that a directive class {X} is a subclass of `cco:DirectiveICE` and specifically maps to an ISO 27001 Annex A control {Y}. This mapping is the mechanism by which internal governance documents (such as policies or standard operating procedures) gain regulatory weight. By asserting that an internal directive is a subclass of a specific Annex A control, the organization creates a formal linkage between private rules and public standards.

The complexity of this relationship lies in the requirement that the target control {Y} must be defined within the system as a valid requirement. This creates a dependency hierarchy where directives cannot reference non-existent controls. The relational schema enforces this by linking the directive entry to a specific requirement identifier.

## 3. Requirement Equivalence

To function effectively within a governance framework, a requirement must be precisely defined in terms of what it specifies and to what it applies. The axiom `requirement_equiv_specifies_target` establishes that a class {X} is equivalent to a `cco:DirectiveICE` if and only if it specifies some requirement {Y} and applies to some target {Z}. This equivalence axiom is powerful because it decomposes complex directives into their constituent parts: the rule being enforced and the object of that rule.

This decomposition allows for granular querying and reporting. For instance, an organization may query all directives that apply to a specific target class (e.g., "EmployeeRecord") to assess the total governance burden on that data type. The structure ensures that no directive is vague; every equivalent class must explicitly declare its specification and its target.

The relational projection of this axiom requires that the specification {Y} references a valid ISO 27001 Annex A entry, creating a bidirectional link between the requirement definition and the standard control. This circular dependency (where the Annex A table references the Requirement table and vice versa) ensures that controls and requirements are mutually defined and consistent.

## 4. Attestation with Supporting Evidence

Compliance is not achieved through policy alone; it requires verification. The axiom `attestation_with_supporting_evidence` addresses this by defining an attestation class {X} as a process (`bfo:Process`) that must possess supporting evidence {Y}. An attestation is a formal declaration, often signed by an officer, asserting that a control is operating effectively. However, without supporting evidence—such as logs, screenshots, or configuration exports—the attestation is unsubstantiated.

This axiom enforces the "evidence-based" nature of the compliance framework. It prevents "checkbox compliance," where attestations are filed without proof. The system requires that for every attestation record, a link to an evidence artifact is maintained. This evidence must itself be traceable back to the specific directive or control being attested.

The data structure for this concept links the attestation instance to the evidence class. The foreign key constraint ensures that the evidence provided is valid within the context of the specific ISO 27001 control being verified. This creates a rigid chain: Directive -> Control -> Attestation -> Evidence.

## 5. Attestation at Period

Finally, compliance is a temporal state. Controls that were effective last year may not be effective today. The axiom `attestation_at_period` defines an attestation class {X} as a process that occurs at a specific attestation period {Y}. This introduces the dimension of time into the governance ontology, ensuring that attestations are not perpetual but are bound to a specific validity window.

This axiom is essential for recurring compliance cycles, such as annual SOC 2 audits or quarterly ISO reviews. It allows the governance framework to query for "expired attestations" or "upcoming review periods." By linking the attestation to a period class, which itself references the underlying control, the organization can generate timeline reports showing the continuous coverage of compliance activities over time.

The relational schema for this axiom mirrors the evidence structure but substitutes the temporal period for the evidence artifact. This enforces the rule that an attestation is only valid if it is explicitly anchored to a defined time period relevant to the control's operation.
