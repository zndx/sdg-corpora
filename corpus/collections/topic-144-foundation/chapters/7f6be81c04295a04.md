# Chapter 7: Ontological Mapping of Governance Directives and Audit Processes

This chapter delineates the formal ontological structures required to map internal governance directives to the ISO/IEC 27001:2022 framework, alongside the procedural mechanics of audit and attestation. The scope of this text is restricted to the precise definition of five core axioms that govern the relationship between directive classes, control objectives, and the agents responsible for verification. The following sections establish the semantic constraints necessary for automated compliance checking and evidence traceability within a regulated environment.

## 1. Audit Execution and Agency

The foundational axiom governing any compliance framework is the attribution of agency. In the context of formal governance, an audit is not merely an event but a processual entity (bfo:Process) that necessitates a responsible agent to validate the integrity of the system. The axiom `audit_conducted_by` establishes that an audit class is a subclass of a process that is conducted by a person. This relationship ensures that every audit trail is anchored to a specific human accountable for the execution of the review, thereby satisfying non-repudiation requirements common in financial and security auditing.

The relational projection of this axiom isolates the audit entity as the primary key. The structure is designed to facilitate rapid lookup of the responsible party without embedding the full complexity of the person entity within the audit record itself.

## 2. ISO 27001 Annex A Harmonization

To achieve regulatory harmonization, internal governance directives must be formally mapped to internationally recognized control sets. The axiom `iso27001_annexa_subclass` defines a structural constraint wherein an internal directive class (X) is subclassed as a `cco:DirectiveICE` and explicitly linked to a specific control class within the ISO 27001 Annex A framework (Y). This mapping is critical for establishing the "long tail" of compliance, where granular internal policies are traced back to high-level regulatory requirements.

This relationship creates a normalized reference point for all subsequent compliance activities. By defining the directive as a subclass of `cco:DirectiveICE`, the ontology enforces that the entity possesses the properties of an informational control entity, while the link to Annex A ensures auditability against the standard.

## 3. Evidence-Based Attestation

Attestation represents the formal assertion that a control is operating as intended. However, without evidentiary support, such assertions are vacuous. The axiom `attestation_with_supporting_evidence` posits that an attestation process (X) is a process that possesses supporting evidence (Y). Within this schema, the evidence is intrinsically linked to the control mapping established in Section 2; specifically, the evidence must validate the compliance of the directive against the specific ISO control.

The foreign key constraint referencing the `t_iso27001_annexa_subclass` table enforces a rigid validation rule: evidence cannot be entered into the system unless it is explicitly tied to a valid ISO control mapping. This prevents "orphaned" evidence that does not support a specific compliance requirement.

## 4. Temporal Scope of Attestation

Compliance is a temporal state; a control valid at one moment may be deficient the next. The axiom `attestation_at_period` addresses this by defining that an attestation process (X) occurs within a specific attestation period (Y). Similar to the evidence linkage, this period is bound to the ISO control mapping, ensuring that time-bound compliance data is always associated with the specific control being evaluated.

This structure allows governance frameworks to query the historical state of compliance. By joining the attestation period to the control mapping, auditors can generate timelines showing when specific controls were tested and verified, facilitating trend analysis and gap detection.

## 5. Requirement Specification and Targeting

The final axiom defines the granularity of governance directives. A requirement is not merely a statement; it is a logical equivalence comprising three components: the directive itself, the specific control it specifies, and the target system to which it applies. The axiom `requirement_equiv_specifies_target` asserts that a Requirement Class (X) is equivalent to a DirectiveICE that specifies a control (Y) and applies to a target (Z).

This tripartite structure is essential for the deployment of governance policies. It moves beyond abstract policy documents to actionable requirements that are machine-readable and enforceable. The linkage of the specified control (Y) to the ISO mapping table ensures that the requirement is always aligned with the overarching compliance framework.
