# Chapter 7: Formal Ontology of eBPF Syscall Entities and Security Stratification

## 7.1 Scope and Preamble

This chapter establishes the formal ontological definitions required for the classification, auditing, and security stratification of extended Berkeley Packet Filter (eBPF) syscall entities within the kernel control plane. The specifications detailed herein provide the axiomatic foundation for mapping Information Content Entities (ICE) to specific subsystems, security tiers, and event triggers. These definitions are mandatory for compliance with kernel-level governance frameworks and serve as the basis for automated audit verification. The following sections delineate the relational constraints and equivalence classes that govern the behavior of designative entities in the eBPF execution environment.

## 7.2 Syscall Equivalence in Subsystem

The fundamental unit of organization within the eBPF ontology is the designation of a syscall as equivalent to a specific intersection of a Designative Information Content Entity (ICE) and a Syscall Subsystem. The axiom `syscall_equiv_in_subsystem` formalizes this by asserting that a Class X is *EquivalentTo* the intersection of `cco:DesignativeICE` and the restriction `sdg:inSyscallSubsystem some {Y:Class}`. This equivalence is not merely taxonomic but functional; it dictates that for an entity to be recognized as a valid syscall within the governance framework, it must necessarily reside within a defined subsystem boundary.

This axiom ensures that syscall definitions are not floating abstractions but are anchored to the structural reality of the kernel's modular architecture. From a compliance perspective, this allows auditors to verify that every invoked syscall maps deterministically to a subsystem owner, facilitating fault isolation and access control enforcement.

**Table 7.1** presents the relational projection of this equivalence. The primary key `id` uniquely identifies the equivalence assertion, while columns `x` and `y` represent the Syscall Class and the Subsystem Class, respectively. The `NOT NULL` constraint on `y` enforces the axiom's requirement that a valid syscall definition cannot exist outside of a subsystem context.

**Table 7.1: Syscall Equivalence Assertions by Subsystem**

| id | x (Syscall Class) | y (Subsystem Class) |
| :--- | :--- | :--- |
| equiv_001 | `BpfMapLookupElem` | `BpfMapSubsystem` |
| equiv_002 | `BpfProgLoad` | `BpfProgramSubsystem` |
| equiv_003 | `BpfRingBufSubmit` | `BpfRingBufferSubsystem` |
| equiv_004 | `BpfSkRedirectPeer` | `BpfSocketSubsystem` |
| equiv_005 | `BpfCgroupInherit` | `BpfCgroupSubsystem` |

The data in **Table 7.1** illustrates the strict mapping of high-level syscall classes to their respective functional domains. For instance, the entity `BpfMapLookupElem` is defined *equivalent* to a Designative ICE within the `BpfMapSubsystem`. This implies that any attempt to invoke this entity outside the context of the Map Subsystem violates the ontological definition and must be flagged by the runtime verifier.

## 7.3 Security Tier Stratification

To enforce the principle of least privilege and maintain kernel integrity, syscall entities are stratified into distinct Security Tiers. The axiom `syscall_at_security_tier` asserts that a Class X is a *SubClassOf* `cco:DesignativeICE` and possesses the property `sdg:atSecurityTier some {Y:Class}`. This hierarchical classification enables the governance framework to apply differential security policies based on the sensitivity and potential impact of the syscall.

The verbalization "{X} is something that at security tier {Y}" indicates that security tier assignment is an intrinsic property of the syscall class itself. This stratification is critical for audit trails, as it allows security information and event management (SIEM) systems to filter syscall logs based on risk tolerance levels. For example, syscalls residing in `Tier0_Privileged` require rigorous justification and elevated clearance for invocation, whereas those in `Tier2_Unprivileged` may be accessible to unprivileged userspace processes subject to standard verification.

**Table 7.2** documents the assignment of syscall classes to their mandated security tiers. The schema enforces that every valid syscall class (`x`) must be associated with exactly one security tier class (`y`), ensuring that no syscall exists in a security vacuum.

**Table 7.2: Syscall Classification by Security Tier**

| id | x (Syscall Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| tier_001 | `BpfProbeReadUser` | `Tier0_Privileged` |
| tier_002 | `BpfGetSmpProcessorId` | `Tier1_Safe` |
| tier_003 | `BpfKtimeGetNs` | `Tier1_Safe` |
| tier_004 | `BpfTracePrintk` | `Tier0_Privileged` |
| tier_005 | `BpfMapDeleteElem` | `Tier2_Unprivileged` |

In the context of **Table 7.2**, the classification of `BpfProbeReadUser` as `Tier0_Privileged` reflects its capability to access arbitrary user memory, a high-risk operation that necessitates strict controls. Conversely, `BpfKtimeGetNs` is categorized as `Tier1_Safe`, reflecting its read-only nature and minimal impact on system stability. These classifications are derived from the formal axiom `syscall_at_security_tier` and serve as the input for policy enforcement points within the kernel.

## 7.4 Return Type Constraints

Determinism in syscall behavior is a prerequisite for system stability and verifiability. The axiom `syscall_max_one_return` imposes a cardinality constraint on the return types of syscall entities. It asserts that a Class X is a *SubClassOf* `cco:DesignativeICE` and that the property `sdg:hasReturnType` has a maximum cardinality of 1 for Class Y.

This constraint, verbalized as "{X} is a designative information content entity" with a restricted return type, ensures that a syscall cannot ambiguously return multiple types of data structures. In the context of the eBPF Just-In-Time (JIT) compiler and the verifier, this axiom guarantees that the register state prediction following a syscall invocation is singular and well-defined. Without this constraint, the verifier would be unable to statically analyze the safety of eBPF programs, as the data flow assumptions would be non-deterministic.

**Table 7.3** provides the relational mapping of syscall classes to their singular return type classes. The structure `id`, `x`, `y` links the specific syscall to its defined output type.

**Table 7.3: Syscall Return Type Constraints**

| id | x (Syscall Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| ret_001 | `BpfMapLookupElem` | `MapValueTypePtr` |
| ret_002 | `BpfKtimeGetNs` | `UInt64Type` |
| ret_003 | `BpfCsumDiff` | `SInt32Type` |
| ret_004 | `BpfGetCurrentTask` | `TaskStructPtr` |
| ret_005 | `BpfSkRelease` | `VoidType` |

The entries in **Table 7.3** demonstrate the application of the `max 1` constraint. For instance, `BpfMapLookupElem` is strictly bound to `MapValueTypePtr`. It does not return an integer or a structure pointer in a general sense; it returns specifically a pointer to a value within a map. This precision is required for the `sdg:hasReturnType` slot to remain valid during the abstract syntax tree (AST) traversal performed by the verification engine.

## 7.5 Subsystem Hierarchies and Inheritance

While equivalence defines the necessary and sufficient conditions for a syscall's existence, the hierarchical structure of the kernel is modeled through subclass relationships. The axiom `syscall_subclass` asserts that a Class X is a *SubClassOf* `cco:DesignativeICE` and is related via `sdg:inSyscallSubsystem some {Y:Class}`. This differs from the equivalence axiom in that it allows for inheritance and broader categorization without requiring the strict identity conditions of equivalence.

This axiom facilitates the organization of syscalls into logical groupings that may share common interfaces or security policies. By defining a syscall as a subclass of entities within a specific subsystem, the ontology supports polymorphic behavior where different syscall implementations can be treated uniformly by the subsystem management code. The verbalization "{X} is something that in syscall subsystem {Y}" highlights the containment relationship essential for namespace management and modular kernel design.

**Table 7.4** illustrates the subclass relationships, grouping syscall entities under their respective subsystem domains.

**Table 7.4: Syscall Subclass Relationships**

| id | x (Syscall Class) | y (Subsystem Class) |
| :--- | :--- | :--- |
| sub_001 | `BpfSockOpsCb` | `BpfSocketSubsystem` |
| sub_002 | `BpfXdpRedirectMap` | `BpfXdpSubsystem` |
| sub_003 | `BpfSkAssign` | `BpfSocketSubsystem` |
| sub_004 | `BpfGetSocketCookie` | `BpfSocketSubsystem` |
| sub_005 | `BpfRedirectMap` | `BpfTCSubsystem` |

As evidenced in **Table 7.4**, multiple syscall classes such as `BpfSockOpsCb` and `BpfSkAssign` are subclasses within the `BpfSocketSubsystem`. This hierarchical grouping allows the governance framework to apply subsystem-wide policies (e.g., socket locking protocols) to all member classes efficiently. The `NOT NULL` constraint on the `y` column ensures that every subclass is explicitly assigned to a subsystem, preventing orphaned entities within the ontology.

## 7.6 Event Invocation Triggers

The final dimension of the ontological specification addresses the causality of syscall execution. The axiom `syscall_invoked_by_event` asserts that a Class X is a *SubClassOf* `cco:DesignativeICE` and is `sdg:invokedByEvent some {Y:Class}`. This axiom links the static definition of the syscall to the dynamic runtime events that trigger its execution.

Understanding the event triggers is paramount for forensic analysis and performance monitoring. The verbalization "{X} is something that invoked by event {Y}" establishes a dependency chain that allows auditors to trace a syscall invocation back to a specific hardware interrupt, software trap, or user-space system call entry point. This relationship is vital for constructing accurate execution graphs and for detecting anomalous syscall chains that may indicate exploit attempts or privilege escalation violations.

**Table 7.5** catalogs the mapping of syscall classes to their triggering event classes, providing the necessary evidence linkage for runtime monitoring systems.

**Table 7.5: Syscall Event Invocation Triggers**

| id | x (Syscall Class) | y (Event Class) |
| :--- | :--- | :--- |
| evt_001 | `BpfTimerSetCallback` | `TimerExpirationEvent` |
| evt_002 | `BpfSockHashCb` | `SocketReceiveEvent` |
| evt_003 | `BpfXdpCb` | `NetworkDriverRxEvent` |
| evt_004 | `BpfIterCb` | `FilesystemIteratorEvent` |
| evt_005 | `BpfCgroupInherit` | `ProcessExecEvent` |

The data presented in **Table 7.5** clarifies the operational context of the syscalls. For example, `BpfXdpCb` is invoked specifically by a `NetworkDriverRxEvent`, meaning it executes only when a network packet is received by the driver. Similarly, `BpfTimerSetCallback` is triggered by `TimerExpirationEvent`. These mappings, derived from the `syscall_invoked_by_event` axiom, enable the runtime environment to validate the preconditions for syscall execution, ensuring that syscalls are only invoked within their intended event contexts.
