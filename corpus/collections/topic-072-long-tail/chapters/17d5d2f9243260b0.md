# Chapter 4: Kernel Interface Taxonomy and Security Classification

## 4.1 Scope and Preamble

This chapter establishes the formal taxonomy for kernel system calls within the eBPF observability framework. It defines the ontological relationships between interface classes, their subsystem localization, security tiers, return type constraints, and event invocation triggers. The definitions provided herein are aligned with the `cco:DesignativeICE` (Designative Information Content Entity) upper ontology and serve as the basis for automated compliance auditing and runtime verification. Each section details a specific axiom governing system call behavior, supported by relational data mappings that enforce these constraints at the schema level.

## 4.2 System Call Equivalence within Subsystems

### 4.2.1 Axiomatic Definition
The foundational axiom for subsystem localization asserts that a specific system call class is equivalent to the intersection of being a Designative Information Content Entity and residing within a specific Syscall Subsystem. Formally, Class `X` is EquivalentTo: `cco:DesignativeICE` and (`sdg:inSyscallSubsystem` some `Y`). This equivalence relation is biconditional; it dictates that an entity is classified as `X` if and only if it is a designative entity functioning specifically within subsystem `Y`. This is distinct from a simple subclass relationship, as it precludes the existence of `X` outside the context of `Y`.

### 4.2.2 Implementation and Constraints
In practice, this axiom is utilized to strictly bind interface definitions to their functional domains. For instance, a `VirtualFileSystemOperation` is defined strictly by its existence within the Virtual File System (VFS) subsystem. It cannot be a `VirtualFileSystemOperation` if it operates within the Network subsystem. This strict typing prevents category errors in policy enforcement engines where subsystem scope is a primary filtering dimension.

The following table enumerates specific instances where this equivalence has been codified. The primary key `id` serves as the unique identifier for the equivalence assertion, while `x` represents the specific class and `y` the requisite subsystem.

**Table 4.1: System Call Equivalence in Subsystem Assertions**

| id | x | y |
| :--- | :--- | :--- |
| equiv_001 | VFSReadOperation | VirtualFileSystem |
| equiv_002 | NetSocketBind | NetworkStack |
| equiv_003 | ProcessForkEvent | ProcessControl |
| equiv_004 | IPCMessageQueue | InterProcessCommunication |
| equiv_005 | DeviceIoControl | HardwareAbstraction |

### 4.2.3 Audit Verification
During compliance audits, verification of `t_syscall_equiv_in_subsystem` ensures that no system call class has been ambiguously defined across multiple subsystems. Auditors must confirm that for every row in Table 4.1, the code implementation for `x` is fully encapsulated within the kernel module boundaries defined by `y`.

## 4.3 Security Tier Classification

### 4.3.1 Axiomatic Definition
The security tier axiom establishes a hierarchical classification of system calls based on their privilege requirements. The axiom states: Class `X` SubClassOf: `cco:DesignativeICE`, `sdg:atSecurityTier` some `Y`. This implies that every instance of class `X` must possess the property of being located at a specific security tier `Y`. Unlike equivalence, this is a subclass relationship, allowing for further specialization of `X` provided it remains within the constraints of tier `Y`.

### 4.3.2 Tier Hierarchies
Security tiers typically map to processor privilege rings (Ring 0 vs. Ring 3) or abstract capability sets (e.g., `RootOnly`, `Unprivileged`). The axiom ensures that any syscall classified as `X` is implicitly assigned the security properties of `Y`. For example, if `CriticalMemoryOperation` is defined at the `KernelMode` tier, it inherits all access control lists associated with that tier.

**Table 4.2: System Call Security Tier Classifications**

| id | x | y |
| :--- | :--- | :--- |
| tier_001 | IoplOperation | Ring0 |
| tier_002 | UserReadBuffer | Ring3 |
| tier_003 | SysctlModify | Capabilities |
| tier_004 | ModuleLoad | KernelMode |
| tier_005 | PerfEventOpen | Observability |

### 4.3.3 Governance Implications
The data in Table 4.2 is critical for governance frameworks enforcing least privilege. By querying `t_syscall_at_security_tier`, a security information and event management (SIEM) system can flag any invocation of a class `x` where the calling context lacks the credentials for tier `y`. This binding is immutable; shifting a syscall to a different tier requires a formal schema modification and re-registration of the class `x`.

## 4.4 Return Type Cardinality Constraints

### 4.4.1 Axiomatic Definition
To enforce type safety and predictability in kernel-user space communication, the ontology defines a cardinality restriction on return types. The axiom is defined as: Class `X` SubClassOf: `cco:DesignativeICE`, `sdg:hasReturnType` max 1 `Y`. This verbalizes to: `X` is a designative information content entity that has a maximum of one return type `Y`. This constraint ensures that a specific system call class cannot return polymorphic types ambiguously; it must resolve to a single, defined type `Y` or null.

### 4.4.2 Type Safety Enforcement
This axiom is particularly relevant for preventing type confusion attacks. By restricting the return type to a maximum of one class `Y`, the kernel interface guarantees that the user-space parser expects a consistent data structure. For example, a `GenericIntegerReturn` syscall is constrained to return a 32-bit signed integer; it cannot suddenly return a memory address pointer without violating the axiom.

**Table 4.3: System Call Return Type Constraints**

| id | x | y |
| :--- | :--- | :--- |
| ret_001 | GenericIntegerReturn | SignedInteger32 |
| ret_002 | PointerReturn | MemoryAddress |
| ret_003 | VoidReturn | NullType |
| ret_004 | FileDescriptorReturn | FileDescriptor |
| ret_005 | StringLiteralReturn | CString |

### 4.4.3 Schema Validation
The relational projection in `t_syscall_max_one_return` serves as a lookup table for interface generators. When a new system call is introduced, the `x` and `y` values must be inserted into this table. The `max 1` constraint in the ontology is enforced in the relational layer by ensuring that for any given `id` (representing the specific class definition), only one `y` (type) is permitted. Deviations from this schema result in a build-time failure for the kernel interface documentation.

## 4.5 Subsystem Subclass Hierarchies

### 4.5.1 Axiomatic Definition
While Section 4.2 defined equivalence, this section addresses the broader inclusion hierarchy. The axiom states: Class `X` SubClassOf: `cco:DesignativeICE`, `sdg:inSyscallSubsystem` some `Y`. This verbalizes to: `X` is something that is in syscall subsystem `Y`. This is a standard taxonomic partitioning. It allows for a generic class `X` to be categorized within subsystem `Y` without claiming that `X` is the *only* entity in that subsystem (which equivalence would imply).

### 4.5.2 Hierarchical Structuring
This axiom is used to group related system calls into functional families. For instance, `FileDescriptorManipulation` is a subclass of entities residing in the `FileManagement` subsystem. This allows for high-level policy rules that target the entire subsystem `Y` or specific subclasses `X` depending on the granularity required by the compliance rule.

**Table 4.4: System Call Subsystem Subclass Relationships**

| id | x | y |
| :--- | :--- | :--- |
| sub_001 | FileDescriptorManipulation | FileManagement |
| sub_002 | IPCSharedMemory | InterProcessCommunication |
| sub_003 | SignalDispatch | ProcessControl |
| sub_004 | SocketOptionManipulation | NetworkStack |
| sub_005 | TimerConfiguration | TimeManagement |

### 4.5.3 Impact on Access Control
The `t_syscall_subclass` table provides the structural backbone for Role-Based Access Control (RBAC) definitions within the kernel. By querying this table, a security module can dynamically construct a matrix of permissions. If a role is granted access to subsystem `y`, all classes `x` listed in Table 4.4 associated with that `y` are implicitly accessible. This hierarchical inheritance simplifies the management of complex permission sets.

## 4.6 Event Invocation Triggers

### 4.6.1 Axiomatic Definition
The final axiom governs the causality and triggering mechanisms for system calls. The axiom is: Class `X` SubClassOf: `cco:DesignativeICE`, `sdg:invokedByEvent` some `Y`. This verbalizes to: `X` is something that is invoked by event `Y`. This establishes a dependency relationship where the execution of the system call class `X` is contingent upon the occurrence of a specific event class `Y`.

### 4.6.2 Event-Driven Architecture
In modern kernel architectures, particularly those utilizing eBPF, system calls are often treated as responses to hardware or software events. This axiom maps the synchronous or asynchronous trigger to the handler. For example, an `ExceptionHandler` is a class of system call that is invoked specifically by a `HardwareTrap` event. This mapping is crucial for forensic analysis, as it links the *cause* (Event `Y`) directly to the *interface handler* (Class `X`).

When a failure occurs in class `x`, tracing back to event `y` allows engineers to determine if the root cause lies in the triggering event (e.g., a spurious interrupt) or the handler logic.
