# Chapter 4: Taxonomy of Kernel System Calls and Security Classification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for classifying kernel system calls within the eBPF observability and security architecture. The definitions provided herein are binding for all audit reporting mechanisms, compliance handbooks, and governance frameworks utilized within the kernel subsystem. The objective is to delineate the precise relationships between system call entities, their respective subsystems, security tiers, return types, and invocation events. By adhering to these axioms, security architects ensure that telemetry data is anchored in a rigorous semantic structure, facilitating automated enforcement of governance policies and high-fidelity reconstruction of system behavior.

## 4.2 System Call Equivalence within Subsystems

The foundational axiom for identifying system call entities relies on the principle of equivalence. A system call is not merely an isolated function pointer; it is formally defined as a Designative Information Content Entity (ICE) that is equivalent to the intersection of its own identity and its containment within a specific subsystem. This definition ensures that the entity cannot exist meaningfully outside the context of its designated subsystem, providing a strict boundary for namespace isolation and access control.

### 4.2.1 Axiomatic Definition

According to the axiom `syscall_equiv_in_subsystem`, a class `X` is equivalent to a `cco:DesignativeICE` if and only if it is situated within the `sdg:inSyscallSubsystem` relationship to some class `Y`. This logical constraint mandates that any instance of `X` is inherently and exclusively an instance of a designative entity operating within `Y`. In practical terms, this prevents ambiguity in audit logs where a system call might be misclassified across different functional domains, such as networking or file management.

### 4.2.2 Compliance Implications

For compliance officers, this equivalence implies that the verification of a system call's validity requires checking both its identifier and its subsystem containment. A syscall claiming to belong to the `VirtualizationSubsystem` but failing the equivalence test against the designative ICE of that subsystem must be flagged as an anomaly. This strict typing is critical for high-security environments where syscall spoofing is a potential attack vector.

## 4.3 Security Tier Assignment

Once a system call is defined within a subsystem, it must be assigned a security tier. This classification dictates the privilege level required to invoke the call and the sensitivity of the data it handles. The axiom `syscall_at_security_tier` establishes that a system call class `X` is a subclass of `cco:DesignativeICE` and possesses the property `sdg:atSecurityTier` relating to a specific security class `Y`.

### 4.3.1 Hierarchical Privilege Structure

The security tier classification is not merely a label but a structural constraint within the ontology. By asserting that `X` is at security tier `Y`, the framework implicitly restricts the execution context of `X`. For instance, calls situated at `Tier0_Privileged` are permitted to interact directly with hardware memory mappings, whereas calls at `Tier2_Userland` are sandboxed from critical kernel structures. This distinction is vital for governance frameworks that enforce the Principle of Least Privilege (PoLP).

### 4.3.2 Audit Verification

During an audit, the security tier assignment is cross-referenced with the caller's credentials. If a process running with insufficient privileges attempts to invoke a system call at a higher security tier, the eBPF observability hooks must trigger an immediate violation alert. The deterministic relationship between the call and its tier ensures that policy enforcement engines can make binary allow/deny decisions without heuristic ambiguity.

## 4.4 Return Type Constraints

To maintain type safety and predictability in kernel telemetry, system calls are subject to strict cardinality constraints regarding their return values. The axiom `syscall_max_one_return` formalizes this by stating that a system call class `X` is a subclass of `cco:DesignativeICE` and possesses a `sdg:hasReturnType` relationship with a maximum cardinality of 1 to class `Y`.

### 4.4.1 Cardinality Enforcement

The constraint `max 1` signifies that a system call may return at most one type of entity. This prohibits polymorphic return behaviors where a single syscall identifier might return an integer in one context and a pointer in another, depending on runtime state. In the context of formal verification and static analysis, this axiom allows auditors to construct precise data flow graphs. If a syscall is defined to return an `IntegerType`, any observation of a `PointerReference` in the return register constitutes a deviation from the specification.

### 4.4.2 Data Integrity Implications

This limitation is essential for automated compliance checking. When parsing audit logs, the ingestion pipeline relies on the schema definition to cast the return value correctly. Ambiguity in return types can lead to log injection attacks or misinterpretation of error codes. By anchoring the return type to a single class `Y`, the ontology ensures that the semantic meaning of the return value is invariant across all invocations of `X`.

## 4.5 Subsystem Hierarchies and Membership

Distinct from the equivalence definition, the subclass axiom `syscall_subclass` provides a mechanism for hierarchical organization. It asserts that a system call class `X` is a subclass of `cco:DesignativeICE` and is located within the `sdg:inSyscallSubsystem` relationship to class `Y`. While similar to the equivalence axiom, the subclass relationship allows for broader categorization where `X` may share properties with other entities in `Y` without being defined solely by that containment.

### 4.5.1 Taxonomic Structure

This axiom supports the construction of taxonomic trees. For example, a generic class `FileDescriptorOperation` may be a subclass of the `VFS_Subsystem`. Specific calls like `read` or `write` inherit this subsystem placement. This structure is crucial for generating governance reports that aggregate activity by subsystem. A compliance officer might query for all instances of `Y` (e.g., `NetworkSubsystem`) to review total traffic, relying on the subclass axioms to ensure all relevant `X` entities are included.

## 4.6 Event Invocation Triggers

The final dimension of the taxonomy addresses the causal mechanism of system calls: the events that invoke them. The axiom `syscall_invoked_by_event` posits that a system call class `X` is a subclass of `cco:DesignativeICE` and is `sdg:invokedByEvent` some class `Y`. This links the static definition of the call to the dynamic state of the system.

### 4.6.1 Causal Chain Analysis

Understanding the event `Y` that invokes `X` is critical for forensic analysis. It allows investigators to trace the chain of causality from a hardware interrupt or software trap up to the specific kernel function executed. For example, if `X` is a page fault handler, it is invoked by a `MemoryManagementUnitInterrupt`. If `X` is a standard I/O call, it is invoked by a `SoftwareInterrupt` (trap) initiated by a user-space application.

### 4.6.2 Governance and Monitoring

From a governance perspective, this axiom enables the creation of policies based on event types. A security framework might be configured to suppress or rate-limit syscalls invoked by `PeriodicTimerEvents` while prioritizing those invoked by `HardwareInterrupts`. This granular control ensures that system resources are allocated efficiently according to the urgency and origin of the invocation event.
