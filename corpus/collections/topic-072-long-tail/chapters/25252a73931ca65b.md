# Chapter 4: Formal Taxonomy of Kernel Interface Entities

## 4.1 Scope and Preamble

This chapter establishes the ontological framework required for the rigorous classification and auditing of Designative Information Content Entities (ICE) within the extended Berkeley Packet Filter (eBPF) and kernel syscall environment. The definitions provided herein are not merely descriptive; they serve as the structural constraints for automated compliance verification, ensuring that interface definitions adhere to strict security, functional, and subsystem boundaries. Auditors and system architects must utilize these axioms to validate that kernel interaction points—specifically system calls—are correctly categorized according to their security tier, return value constraints, and event-driven invocation contexts. The following sections detail five core axioms that govern the logical consistency of the kernel interface taxonomy.

## 4.2 Axiom 1: Syscall Equivalence in Subsystem

The first axiom addresses the fundamental identity of system calls relative to their operational context. In formal ontology engineering, distinguishing between equivalence and subclass relationships is critical for maintaining logical integrity. The axiom `syscall_equiv_in_subsystem` asserts that a given class `X` is *equivalent to* the intersection of a Designative ICE and a specific subsystem context `Y`. This means that for an entity to be considered a member of class `X`, it is necessary and sufficient that it functions as a Designative ICE within the subsystem `Y`. This is a stronger condition than simple inheritance; it defines the entirety of the class `X` based on its location and function.

This distinction is vital for audit protocols. When verifying a system call, the auditor confirms not only that the call belongs to a subsystem but that its definition is *exhaustively described* by that relationship. This prevents "orphan" interfaces that claim syscall status without a proper subsystem anchoring.

## 4.3 Axiom 2: Syscall Security Tier Classification

Building upon the foundational definitions, the `syscall_at_security_tier` axiom introduces a hierarchical classification mechanism based on privilege levels. This axiom states that a class `X` is a subclass of Designative ICE that possesses a property `atSecurityTier` with a specific value `Y`. Unlike the equivalence axiom, this is a subclass relationship, meaning `X` is a *type of* Designative ICE characterized by its security tier `Y`.

This classification is essential for governance frameworks that enforce the Principle of Least Privilege. By formally binding a syscall class to a security tier, the ontology mandates that any implementation of `X` inherits the access control constraints defined for tier `Y`. For instance, a syscall classified at a `Ring0` tier implies inherent kernel-level privileges, whereas a `Ring3` classification implies user-space restrictions. Auditors utilize this axiom to detect privilege escalation vulnerabilities where a high-security syscall is incorrectly invoked or exposed to lower-tier contexts.

## 4.4 Axiom 3: Return Type Cardinality Constraints

The `syscall_max_one_return` axiom imposes a structural constraint on the output of system calls. It asserts that a class `X` (a subclass of Designative ICE) has a return type property `hasReturnType` with a maximum cardinality of 1, typed as class `Y`. In formal terms, this means that any instance of `X` may return at most one value, and that value must belong to the type `Y`.

This constraint is critical for interface stability and predictability in kernel environments. While user-space APIs often return complex objects or tuples, kernel syscalls typically rely on a single integer return value (representing a success code, error number, or file descriptor). By enforcing `max 1`, the ontology prevents ambiguity in error handling and return value parsing. This axiom serves as a validation rule for interface specifications; if a proposed syscall definition suggests multiple return types, it violates this axiom and must be refactored.

## 4.5 Axiom 4: Syscall Subsystem Membership

While Axiom 1 defined equivalence, Axiom 4 (`syscall_subclass`) defines a looser, hierarchical membership. It asserts that class `X` is a subclass of Designative ICE that exists *in* a subsystem `Y`. This allows for broader categorization where `X` is a specific type of entity within `Y`, but not necessarily the *only* type or definitionally equivalent to the subsystem itself.

This axiom is utilized for modular auditing. It allows the governance framework to query all syscalls within a specific subsystem (e.g., "Show me all `X` in `NetworkStack`") without requiring those syscalls to be definitionally exhausted by that relationship. It supports the extension of the kernel interface; new syscalls can be added as subclasses of `DesignativeICE` within `Y` without redefining the core identity of `Y`.

## 4.6 Axiom 5: Event-Driven Invocation

The final axiom, `syscall_invoked_by_event`, introduces the dimension of causality and traceability. It states that a class `X` is a subclass of Designative ICE that is invoked by a specific event class `Y`. This links the static definition of the syscall to the dynamic runtime triggers that initiate its execution. In a compliance context, this is indispensable for forensic analysis and incident response.

By mapping syscalls to their triggering events, the ontology enables the reconstruction of call chains. If a specific security event `Y` occurs, the framework can immediately identify which syscall `X` must be examined. This axiom also aids in verifying that critical security checks (syscalls) are bound to appropriate events (e.g., ensuring a permission check is invoked by a file access event).
