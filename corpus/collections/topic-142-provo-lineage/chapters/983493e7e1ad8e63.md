# Chapter 4: Geospatial Compliance and Artifact Registration Protocols

## 4.1 Scope and Regulatory Framework

This chapter establishes the procedural framework for the geospatial registration of controlled artifacts within the facility management system. It delineates the mandatory mapping of physical assets to coordinate data structures, ensuring compliance with ISO 19115 standards and internal governance protocols regarding spatial data integrity. The documentation herein provides the axiomatic definitions and relational mappings required for audit verification, specifically addressing the intersection of physical artifacts and their digital representations in geospatial databases. As per the compliance handbook for high-value asset tracking, all artifacts subject to movement logs must be instantiated within the ontology with precise coordinate attributes. The following sections detail the implementation of these axioms, derived from the Common Core Ontologies (cco) and the Sustainable Development Goals interoperability schema (sdg), to ensure unambiguous location data reporting.

## 4.2 Geospatial Coordinate Integration

### 4.2.1 Theoretical Basis and Axiomatic Definition

The foundational requirement for asset tracking is the establishment of a definitive link between a physical object and its abstract representation in space. In accordance with the ontology defined in Section 2, we adhere to the axiom that an Artifact is a subclass of entities that possess specific geospatial coordinates. This relationship is not merely associative but existential; for an artifact to be registered as "located," it must instantiate a relationship with a GeoCoordinates class.

Formally, the axiom is expressed in Manchester syntax as:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasGeoCoordinates some {Y:Class}`

This verbalizes to: *{X} is something that has geo coordinates {Y}*. In the context of facility management, {X} represents the specific asset identifier (e.g., a medical imaging unit or a containment vessel), while {Y} represents the complex object containing the spatial data. This distinction is critical for audit trails; it separates the entity from its location attributes, allowing the location to be updated without redefining the artifact itself.

### 4.2.2 Relational Mapping and Data Integrity

To implement this axiom within a relational database management system (RDBMS), the projection follows a deterministic schema designed to preserve the one-to-many relationship potential of an artifact (an artifact may have multiple coordinate sets over time, though only one is current). The table `t_schemaorg_place_geocoord` serves as the registry for these assertions.

The table structure utilizes a surrogate primary key (`id`) to maintain referential integrity. The column `x` holds the foreign key reference to the Artifact class instance, and `y` holds the reference to the GeoCoordinates class instance. The following data table illustrates the instantiation of this axiom for a sample of high-priority facility assets.

| :--- | :--- | :--- |

### 4.2.3 Verification Protocol

Auditors must verify that for every active record in the asset inventory, a corresponding valid entry exists in `t_schemaorg_place_geocoord`. The `y` column must not be null, ensuring that the existential quantifier of the axiom is satisfied. Any artifact lacking a linked `y` instance is considered non-compliant and must be flagged for immediate field investigation.

## 4.3 Longitudinal Specification and Precision

### 4.3.1 Theoretical Basis and Axiomatic Definition

While the previous section established the aggregate coordinate object, granular compliance requires the decomposition of this object into its constituent vector components. The first of these components is the longitudinal value. Longitude defines the east-west position of a point on the Earth's surface. The ontology specifies that an Artifact is a subclass of entities that possess a specific longitude attribute.

The governing axiom is:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasLongitude some {Y:Class}`

This verbalizes to: *{X} is something that has longitude {Y}*. In this schema, {Y} is treated as a class instance representing the specific scalar value or the data node containing the value. This abstraction allows the longitude to be treated as a first-class citizen within the ontology, capable of bearing its own metadata (such as precision, datum, or collection timestamp).

### 4.3.2 Relational Mapping and Scalar Representation

The relational projection of the longitude property is captured in the table `t_schemaorg_place_longitude`. This table enforces the constraint that the longitudinal value is a mandatory property of the artifact's spatial definition. The primary key (`id`) ensures that each specific assertion of longitude is unique, preventing ambiguity in the case of duplicate readings.

The column `x` again references the Artifact, while `y` references the specific Longitude class or value instance. In the context of the following data table, `y` represents the specific longitudinal coordinate instances associated with the artifacts listed in the previous section.

**Table 4.2: Artifact Longitude Attribution**

| :--- | :--- | :--- |
| rec_101 | MRI_Scanner_Unit_A | Long_Val_MRI_A_02 |

### 4.3.3 Compliance and Precision Standards

It is mandated that the `y` instances referenced in Table 4.2 must adhere to WGS 84 datum standards. The audit protocol requires checking the precision of the `y` values; for indoor navigation assets, a precision of at least six decimal places is required. The linkage between `t_schemaorg_place_geocoord` and `t_schemaorg_place_longitude` is implicit through the shared Artifact reference (`x`), ensuring that the aggregate coordinate set contains the correct longitudinal component. Discrepancies between the timestamp of the GeoCoordinate update and the Longitude update constitute a critical data integrity failure.

## 4.4 Latitudinal Specification and Precision

### 4.4.1 Theoretical Basis and Axiomatic Definition

Complementing the longitudinal vector, the latitudinal specification defines the north-south position of the artifact. This axis is equally critical for the triangulation of assets within the facility's geospatial framework. The ontology asserts that the capacity to possess a latitude is an inherent characteristic of the Artifact class within this system.

The axiom is formally defined as:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasLatitude some {Y:Class}`

This verbalizes to: *{X} is something that has latitude {Y}*. Consistent with the treatment of longitude, {Y} represents the class instance of the latitude value. This separation of latitudinal and longitudinal data into distinct relational tables—while linked by the artifact—facilitates specialized indexing and querying, such as retrieving all assets within a specific latitudinal band regardless of their longitude.

### 4.4.2 Relational Mapping and Scalar Representation

The schema for latitude is realized in the table `t_schemaorg_place_latitude`. This structure mirrors that of the longitude table but populates the `y` slot with instances of the Latitude class. The rigorous separation of these attributes prevents data conflation and allows for distinct validation rules to be applied to each axis (e.g., latitude range validation -90 to +90).

The following table presents the latitude attributions for the monitored artifacts. Note that the `id` values are distinct from the longitude table, reinforcing the concept that these are separate property assertions.

### 4.4.3 Audit and Reconciliation

The final step in the compliance workflow involves the reconciliation of Tables 4.2 and 4.3 against the aggregate data in Table 4.1. For a given Artifact `x`, the system must verify that the active GeoCoordinate record (`y` in Table 4.1) logically encompasses the currently active Latitude and Longitude records (`y` in Tables 4.3 and 4.2 respectively).

For instance, `MRI_Scanner_Unit_A` is linked to `GeoSet_MRI_A_02` in Table 4.1. The audit query must confirm that `GeoSet_MRI_A_02` is compositionally defined by the instances `Long_Val_MRI_A_02` and `Lat_Val_MRI_A_02`. Any orphaned latitude or longitude records—those that exist in Tables 4.2 or 4.3 but are not subsumed by an active record in Table 4.1—must be archived or purged according to the data retention policy. This tripartite structure ensures that the ontology's demand for distinct, yet related, spatial properties is met with full traceability.
