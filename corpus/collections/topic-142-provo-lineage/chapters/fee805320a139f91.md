# Modeling Geo-Spatial Properties of Laboratory Artifacts

This chapter examines three OWL axioms that attach geo-spatial descriptors to artifacts and shows how the axioms project to a minimal relational schema. The schema supports joins that recover complete coordinate sets for any artifact. All tables follow the deterministic column structures derived from the axioms; primary keys identify individual assertions while the x and y columns hold class references that satisfy the SubClassOf restrictions.

## 1. Axiom Projection and Table Structure

The axioms state that an artifact class may be further restricted by existential quantification over geo-coordinate, longitude, or latitude classes. Each axiom therefore maps to one table whose rows record a single such restriction. The id column serves as primary key for the assertion; the x column references the artifact class and the y column references the coordinate class. Because multiple assertions may exist for the same artifact, joins on x recover the full set of geo-spatial properties.

### 1.1 Geo-Coordinate Table

The table t_schemaorg_place_geocoord embodies the axiom schemaorg_place_geocoord. Its primary key is id; x and y are foreign-key references to artifact and coordinate classes respectively. A reader can join this table with the longitude and latitude tables on x to obtain a three-part coordinate description for any artifact.

| id  | x                    | y             |
|-----|----------------------|---------------|
| gc1 | KnoxvilleCampus      | GeoPointKC    |
| gc2 | ManchesterFieldLab   | GeoPointMGL   |
| gc3 | NIMBioSAnnex         | GeoPointNA    |
| gc4 | TRACEArchive         | GeoPointTA    |
| gc5 | DavidDesignStudio    | GeoPointDDS   |

### 1.2 Longitude Table

The table t_schemaorg_place_longitude embodies the axiom schemaorg_place_longitude. Its primary key is id; x references the same artifact classes used in the geo-coordinate table while y references longitude classes. Joining on x yields the longitude component that completes the coordinate triple for any artifact listed in the preceding table.

| id  | x                    | y              |
|-----|----------------------|----------------|
| lo1 | KnoxvilleCampus      | LongKC         |
| lo2 | ManchesterFieldLab   | LongMGL        |
| lo3 | NIMBioSAnnex         | LongNA         |
| lo4 | TRACEArchive         | LongTA         |
| lo5 | DavidDesignStudio    | LongDDS        |

### 1.3 Latitude Table

The table t_schemaorg_place_latitude embodies the axiom schemaorg_place_latitude. Its primary key is id; x again references artifact classes and y references latitude classes. Cross-joining the three tables on x produces a complete geo-spatial record without requiring additional columns or external lookup tables.

| id  | x                    | y              |
|-----|----------------------|----------------|
| la1 | KnoxvilleCampus      | LatKC          |
| la2 | ManchesterFieldLab   | LatMGL         |
| la3 | NIMBioSAnnex         | LatNA          |
| la4 | TRACEArchive         | LatTA          |
| la5 | DavidDesignStudio    | LatDDS         |

## 2. Multi-Hop Query Example

To recover the full coordinate description for the artifact KnoxvilleCampus, select the row from each table where x equals KnoxvilleCampus and combine the three y values. The join path traverses gc1 → lo1 → la1, returning the triple (GeoPointKC, LongKC, LatKC). The same pattern applied to ManchesterFieldLab yields (GeoPointMGL, LongMGL, LatMGL). Because every x value appears in all three tables, the join is total and produces one result row per artifact.
