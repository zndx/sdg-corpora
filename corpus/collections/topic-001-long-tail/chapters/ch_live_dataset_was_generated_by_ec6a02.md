In compliance and governance frameworks, the integrity of an audit trail depends on a disciplined separation between what an entity is, what properties it carries, and how it relates to other entities. The identifier column serves as the immutable primary key for every record, whether it is a dataset such as `supply-chain-manifest` or `satellite-imagery-stack`, a HIPAA safeguard such as the `Transaction Rule` or `Breach Notification Rule`, or an LRU cache configuration such as `primary-db-cache` or `global-rate-limiter`. Each identifier—prefixed according to its domain, as in `GENE-0001`, `TECH-0001`, or `MAP-0001`—anchors the entity within the schema and provides the stable reference point that downstream relationships and attribute assignments resolve against. The entity itself is the concrete object of governance: a data asset, a regulatory control, or a system component whose lifecycle and properties must be tracked with precision.

Attributes and their types form the second pillar of this model. An attribute defines a named property of an entity—`effective_date`, `enforcement`, `mandatory`, `priority`—while the attribute type constrains the domain of permissible values to a specific schema such as `xsd:date`, `xsd:string`, `xsd:boolean`, or `xsd:integer`. This type discipline is enforced not through a single monolithic column but through a family of value tables, each dedicated to a single data type. Boolean attributes are stored in a value table where entries such as `true` and `false` are associated with their parent entity and attribute identifiers; date attributes appear in a parallel table with values like `2025-01-15` and `2023-08-04`; integer attributes carry magnitudes ranging from `2` to `784`; and string attributes hold free-form text such as `Encoding 01` or `change rationale`. This normalization by type ensures that queries can target the correct value table without resorting to ambiguous type coercion, and it mirrors the way regulatory controls are often evaluated: a boolean flag determines whether a safeguard is mandatory, a date establishes its effective window, and an integer may encode a priority or threshold.

The third pillar—relationships between entities—is expressed through junction tables that carry not only the foreign keys linking subject to target but also a role column that annotates the nature of the connection. In the dataset lineage model, for instance, the junction table records that the dataset `lab-culture-growth` (referenced by `dataset_id` `GENE-0003`) was generated by the `ml-training-runner` (referenced by `was_generated_by_id` `GENE-0003`) in a `contributor` capacity, while the same dataset was also observed by the `telemetry-collector` in an `observer` capacity. The role field is equally present in the LRU cache configuration junction, where a cache such as `prod-session-cache` is linked to a hash algorithm like `xxhash64` with the role `reviewer`, and another cache is linked to `robin-hood` as an `observer`. These roles are not decorative; they encode the provenance and accountability structure that auditors and operators need to reconstruct decision chains, assign responsibility, and trace the flow of data or configuration through the system.

Subject and target, in this context, are directional roles assigned to the foreign-key columns within a junction table. The subject column identifies the entity that initiates or owns the relationship—the dataset, the cache, the HIPAA safeguard—while the target column identifies the entity that is the recipient or counterpart of that relationship—the generation source, the hash configuration, the safeguard dependency. This distinction matters because the same pair of entities can participate in multiple relationships with different roles; a single dataset may be generated by multiple sources, each contributing in a different capacity, and a single cache may be configured with multiple hash algorithms, each serving a distinct operational purpose. The schema captures this multiplicity by allowing multiple rows in the junction table, each with its own identifier and role annotation, rather than collapsing the relationship into a single denormalized column.

The misc column, appearing in every value table, is the container for the actual attribute value. It is called misc not because it is miscellaneous in the sense of unstructured, but because it is the single column that holds the concrete datum—whether that datum is a boolean, a date, an integer, or a variable-length string—and its meaning is derived entirely from the attribute type that governs it. This design allows the schema to scale to new attribute types without altering the core entity or relationship tables: one adds a new attribute definition, registers its type, and creates the corresponding value table. The result is a governance model that is both rigid in its type constraints and flexible in its extensibility, capable of tracking the provenance of datasets like `genomic-variant-call`, the compliance posture of HIPAA safeguards like `Intrusion Detection`, and the configuration of infrastructure components like `stream-event-cache` within a single, coherent relational fabric.
