# Chapter 4: Ontological Classification of Kernel System Calls

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for classifying kernel system calls within the extended Berkeley Packet Filter (eBPF) subsystem. The primary objective is to map low-level operational primitives to high-level Information Content Entities (ICE) to facilitate rigorous auditing, compliance verification, and automated governance. By adhering to the axioms defined in the `04_ebpf_kernel` family, we ensure that every kernel interaction is traceable to a designative entity, thereby eliminating ambiguity in security telemetry and system logs. This documentation serves as the authoritative reference for system architects and compliance officers seeking to validate the structural integrity of kernel-level instrumentation.

## 4.2 The Designative Information Content Entity

### 4.2.1 Axiomatic Definition

In the context of kernel observability, it is insufficient to treat system calls merely as functional invocations; they must be modeled as distinct informational artifacts. The foundational axiom for this classification is derived from the Manchester Syntax for Web Ontology Language (OWL) representations.

**Axiom 1 (template_id: syscall_basic):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DesignativeICE`
*   **Verbalization:** {X} is a designative information content entity.

This axiom asserts that any class {X} designated as a system call within this framework is, by definition, a subclass of `cco:DesignativeICE`. A "designative" entity in this context functions as a linguistic or symbolic referent—it stands for a specific kernel operation or resource state. Unlike procedural code, which *executes* an action, the Designative ICE *represents* the concept of that action within the information space. This distinction is critical for forensic analysis, where the *record* of the call (the ICE) is often the only evidence available post-execution.

### 4.2.2 Relational Mapping and Schema

To operationalize this axiom for database storage and query execution, the ontology is projected onto a deterministic relational schema. The structure enforces that every entry in the classification table is explicitly linked to the foundational BFO (Basic Formal Ontology) anchor `cco:DesignativeICE`.

**Schema Definition:**
```sql
CREATE TABLE t_syscall_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DesignativeICE"],"family":"04_ebpf_kernel","is_complex":false,"template_id":"syscall_basic"}'
```

In this schema, the column `x` represents the specific Class {X} being defined (the system call), while `id` serves as the unique primary key for the record. The simplicity of the table—containing only the identifier and the class designation—reflects the atomic nature of the axiom: the existence of the entity is the sole requirement for its classification as designative.

## 4.3 Extended Classification and Audit Verification

### 4.3.1 Peripheral and Control Operations

While the core map and program operations define the data plane of eBPF, the control plane requires equally rigorous ontological treatment. System calls governing file descriptors, device manipulation, and peripheral interaction must be mapped to the same `DesignativeICE` superclass to maintain a consistent audit trail. This ensures that compliance frameworks scanning for "designative information" do not inadvertently exclude critical control-plane events due to schema mismatch.

The following table extends the classification to include system calls that manage the lifecycle and peripheral interactions of eBPF objects. These entities are essential for governance frameworks that track resource allocation and permission grants.

The `BpfObjPin` entity exemplifies the necessity of this classification. Pinning an eBPF object to the filesystem creates a persistent reference point. The information content entity representing this action designates the transition of a kernel object from transient to persistent state. Without the explicit classification provided in Table 4.2, an audit system might interpret the file system modification as a generic `write` operation, obscuring the specific semantic intent of persisting a kernel object.

### 4.3.2 Verification of Ontological Integrity

To maintain the integrity of the `04_ebpf_kernel` ontology, automated verification scripts must validate that every system call utilized in the kernel instrumentation codebase possesses a corresponding entry in the `t_syscall_basic` table. This process, often referred to as "Ontological Reconciliation," ensures that no "orphan" system calls—those lacking a defined status as a Designative ICE—exist in the production environment.

The reconciliation logic is straightforward:
1.  Extract all system call identifiers from the kernel trace logs.
2.  Query the `t_syscall_basic` table for the presence of these identifiers.
3.  Flag any identifier not present in the `x` column as a "Compliance Exception."

This methodology relies on the deterministic projection of the OWL axiom. Because the schema is flat and atomic (containing only `id` and `x`), the lookup operation is computationally efficient, allowing for real-time compliance checking even in high-throughput telemetry environments.

## 4.4 Governance and Compliance Implications

### 4.4.1 The Role of Designative ICE in Forensic Audits

The classification of system calls as `cco:DesignativeICE` has profound implications for forensic auditing. In the event of a security incident, investigators rely on the "evidence anchor" provided by the ontology. The axiom guarantees that every system call recorded in the audit log is an "information content entity" that "designates" a specific, bounded action.

This prevents the ambiguity often found in raw hex dumps or unstructured stack traces. For example, if a forensic analyst encounters a reference to `BpfLinkCreate` in a compromised system's journal, the ontology confirms that this entity is a Designative ICE. Consequently, the analyst understands that this entry represents the *concept* of linking a program to a kernel hook, rather than arbitrary data corruption or a generic memory access fault. This semantic layering is the cornerstone of high-quality audit reporting.

### 4.4.2 Regulatory Alignment

Regulatory frameworks, such as those governing critical infrastructure and financial transaction systems, increasingly require that telemetry data be "self-describing." The use of the `t_syscall_basic` schema, populated as per Axiom 1, satisfies these requirements by providing a machine-readable definition of the data types in use.

When a regulator requests evidence of system integrity, the organization can present the `t_syscall_basic` table as a manifest of all recognized designative entities. Any deviation between this manifest and the runtime system logs constitutes a prima facie evidence of tampering or configuration drift. Thus, the ontology serves not merely as a taxonomic exercise, but as a control mechanism for regulatory adherence.
