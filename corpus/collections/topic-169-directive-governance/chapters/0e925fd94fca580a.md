# Chapter 7: Formal Ontology of Kernel System Calls in eBPF Instrumentation

## 7.1 Scope and Preamble

This chapter establishes the formal ontological framework for classifying Linux kernel system calls within the context of extended Berkeley Packet Filter (eBPF) observability architectures. The primary objective is to define the semantic mapping between low-level kernel events and the Common Core Ontologies (CCO) definition of Designative Information Content Entities (ICE). This mapping serves as the foundational evidence base for automated audit trails, compliance verification, and security policy enforcement. By adhering to the axioms defined herein, system architects and governance officers ensure that telemetry data retains its semantic integrity across heterogeneous computing environments. The provisions detailed in this section are mandatory for all systems falling under the "04_ebpf_kernel" family classification.

## 7.2 Designative Information Content Entities

### 7.2.1 Conceptual Definition

In the realm of formal ontology and information architecture, an Information Content Entity (ICE) is defined as an entity that is generically dependent on some other entity and stands in relation to it. A specific subclass of this, the Designative ICE, functions as a sign, name, or identifier that "stands for" or designates a specific process, function, or object within a system. In the context of kernel instrumentation, a system call is not merely a binary instruction or a state change; it is a designative entity. The string identifier `execve` or the integer `59` designates the abstract concept of "execute program." Therefore, to accurately model kernel behavior for audit purposes, one must treat system calls not merely as functional triggers but as semantic tokens that designate specific operational intents.

### 7.2.2 Axiomatic Formalization

The classification of kernel system calls is governed by the following axiom, derived from the Manchester Syntax for Web Ontology Language (OWL) representations. This axiom asserts that any class defined within the system call taxonomy is a subclass of `cco:DesignativeICE`.

**Axiom 1 (template_id: syscall_basic):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DesignativeICE`
*   **Verbalization:** {X} is a designative information content entity.

This axiom implies that every specific system call class (e.g., `FileIOOperation`, `NetworkSocketOperation`) inherits the properties of a designative entity. It serves as a reference point for the semantic validity of log data. If an entity cannot be traced back to this axiom, it fails the ontological verification required for high-assurance audit logs.

### 7.2.3 Relational Schema and Registry

To implement this axiom within a relational database management system (RDBMS) or a structured log store, the following schema is mandated. This table, `t_syscall_basic`, acts as the canonical registry of valid system call classes. It ensures that every event captured by the eBPF instrumentation layer maps to a formally defined designative entity.

**Schema Definition:**
The table `t_syscall_basic` consists of two columns: `id`, which serves as the primary key and unique identifier for the class, and `x`, which holds the class name (the specific system call category). The foreign key constraints are implicit in the ontology, linking the instance data to the `cco:DesignativeICE` upper ontology.

**Table 7.1: System Call Basic Registry (t_syscall_basic)**

| id | x |

*Table 7.1 Note:* The `x` column represents the {X:Class} variable in the axiom. Each entry in this table is a distinct class that satisfies the condition `SubClassOf: cco:DesignativeICE`. This registry must be loaded into the eBPF verifier's user-space map dictionary prior to the activation of tracepoints to ensure runtime classification validity.

## 7.3 Compliance Verification and Audit Evidence

### 7.3.1 Evidence Correlation

Once the ontological classes are established in the `t_syscall_basic` registry, the next phase involves the correlation of runtime evidence with these definitions. For a compliance audit (e.g., pursuant to NIST SP 800-53 or ISO 27001), the auditor must verify that the system calls recorded in the audit trail correspond to entries in the canonical registry. This process, known as "Evidence Anchoring," ensures that the telemetry is not merely raw data but semantically enriched information artifacts.

The auditor shall extract a sample of event logs from the eBPF ring buffer and cross-reference the system call identifiers against the `t_syscall_basic` table. Any system call identifier lacking a corresponding entry in the registry must be flagged as an "Ontology Violation," indicating either a kernel version drift or a potential rootkit attempting to use undefined syscalls.

To facilitate this verification, the audit log output generated by the eBPF observability agents must adhere to a strict structure that includes the primary key of the ontological class. ### 7.3.3 Governance and Maintenance

The maintenance of the `t_syscall_basic` registry is a governance function. As the kernel evolves, new system calls may be introduced (e.g., `pidfd_open`, `io_uring_setup`). The ontology steward must evaluate these new entities to determine if they fit into existing classes (e.g., `ProcessControlOperation`) or require the creation of new designative classes. Until such a classification is formalized and added to the `t_syscall_basic` table, observability tools should treat these syscalls as `UnknownDesignativeICE` to prevent semantic pollution of the audit logs.
