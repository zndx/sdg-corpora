# Chapter 4: Designative Information Content Entities in Kernel Space

This chapter establishes the formal ontological classification of kernel-level system calls as Designative Information Content Entities (ICE) within the context of the eBPF monitoring framework. It delineates the axiomatic constraints governing these entities, provides the requisite relational mappings for compliance verification, and defines the governance structures for auditing kernel interactions. The definitions and tabular representations herein are binding for all subsequent audit procedures and system implementations.

## 1. Ontological Foundations of System Calls

### 1.1 The Designative ICE Axiom

Pursuant to the Common Core Ontologies (CCO) framework and the specific constraints of the `04_ebpf_kernel` family, system calls are formally defined not merely as functional invocations, but as distinct informational artifacts. The foundational axiom for this classification is derived from the Manchester syntax assertion: `Class: {X:Class} SubClassOf: cco:DesignativeICE`.

In this context, a Designative Information Content Entity is an entity that signifies or refers to a specific function or process within the operating system kernel. Unlike procedural code, which *does* something, the Designative ICE *designates* what is to be done. This distinction is critical for audit trails, as it separates the intent (the designation) from the execution (the process). The verbalization of this axiom asserts that any class {X} categorized under this definition is, fundamentally, a designative information content entity.

To ensure compliance with this axiom, the following relational schema is mandated for the classification of system call classes. The primary key (`id`) serves as the unique identifier for the classification record, while the column `x` represents the specific Class name that satisfies the condition of being a subclass of `cco:DesignativeICE`.

**Table 1.1: System Call Basic Classification (t_syscall_basic)**

| id | x |
| :--- | :--- |
| sc_001 | SyscallOpen |
| sc_002 | SyscallClose |
| sc_003 | SyscallRead |
| sc_004 | SyscallWrite |

The data presented in Table 1.1 illustrates the instantiation of the axiom. Each entry in column `x` denotes a specific class of system call (e.g., `SyscallOpen`, `SyscallRead`) that is axiomatically treated as a Designative ICE. This classification allows governance frameworks to track the *definition* and *intent* of kernel interactions independently of their runtime execution logs.

### 1.2 Regulatory Context and Scope

Consolidated summary for the application of the `cco:DesignativeICE` class to kernel-level entities. The following sections are amended to reflect the ontological shift from procedural to designative classification:

*   **Section 4.1.1:** All system call wrappers must inherit the properties of `cco:DesignativeICE`.
*   **Section 4.1.2:** Audit logs must distinguish between the entity (the Designative ICE) and the event (the process execution).

This classification ensures that when a security audit is performed, the analyst is querying a stable informational entity (the Class) rather than a volatile memory address. It anchors the compliance verification to the ontology rather than the implementation.

## 2. Compliance Verification and Audit Trails

### 2.2 Non-Compliance and Remediation

IMPORTANT! Read the following terms carefully before interpreting the compliance status codes. A status of "NON_COMPLIANT" indicates that the invocation of the Designative ICE did not adhere to the memory safety constraints defined in the governance framework.

In the event of a "NON_COMPLIANT" status (as seen in `log_8826`), the following remediation steps are mandatory:
1.  **Isolation:** The process ID (PID) associated with the invocation must be immediately isolated from the main memory space.
2.  **Logging:** The specific parameters passed to the `SyscallMmap` class must be serialized and stored in the secure evidence repository.
3.  **Review:** A certified governance officer must review the mapping between the instance and the `cco:DesignativeICE` class to determine if the ontology requires updating or if the implementation was faulty.

## 3. Governance Framework Implementation

### 3.1 Role-Based Access Control (RBAC) for Ontology Management

The management of the `t_syscall_basic` table and the definition of new classes under `cco:DesignativeICE` are restricted to authorized personnel. The following roles are defined within the governance framework:

*   **Ontology Architect:** Responsible for inserting new rows into `t_syscall_basic` and defining the Manchester syntax axioms.
*   **Compliance Auditor:** Responsible for querying the audit logs (Table 2.1) and verifying the `syscall_class_ref` integrity.
*   **Kernel Engineer:** Responsible for ensuring the runtime implementation aligns with the definition of the Designative ICE.

### 3.2 Evidence Anchoring and Provenance

All data tables referenced in this chapter must be stored in an immutable ledger. The `id` column in `t_syscall_basic` acts as the provenance anchor. Any modification to the definition of a class (e.g., changing the semantic meaning of `SyscallRead`) requires the generation of a new `id` and the deprecation of the old entry, rather than an in-place update. This preserves the historical accuracy of the audit logs.

For example, if the definition of `SyscallStat` is amended to include additional metadata parameters, a new entry (e.g., `sc_008: SyscallStatV2`) must be created. Existing audit logs referencing `sc_005` remain valid for the time period in which they were generated, ensuring that the evidence remains anchored to the ontological definition valid at that moment.
