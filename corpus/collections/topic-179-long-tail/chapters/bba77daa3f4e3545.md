# Audit Process Schema for Period Compliance

This chapter defines a minimal relational representation of audit processes grounded in four OWL axioms. The schema supports queries that traverse audit periods, datasets, conductors, and control subclasses while preserving foreign-key integrity.

## 1. Schema Overview

The four tables directly instantiate the supplied axioms. Primary keys are uniformly named `id`. The sole foreign-key constraint links `t_audit_for_period.y` to `t_dataset_under_audit.id`, enabling deterministic multi-hop retrieval of the dataset under audit for any given period-qualified audit.

### 1.1 t_dataset_under_audit

Axiom 2 (`dataset_under_audit`) is embodied by this table. Column `id` is the primary key; column `x` stores the class name of the artifact placed under audit. No foreign keys are present.

```sql
SELECT * FROM t_dataset_under_audit;
```

| id      | x                          |
|---------|----------------------------|
| DS001   | Q2_FY24_Shareholder_Update |
| DS002   | Q1_2020_Commentary         |
| DS003   | 10-Q_June_30_2020          |
| DS004   | Q2_FY24_Financial_Model    |

### 1.2 t_audit_for_period

Axiom 1 (`audit_for_period`) is embodied by this table. Column `id` is the primary key; column `x` names the audit process; column `y` is a foreign key referencing `t_dataset_under_audit.id`. A reader can therefore resolve the dataset for any audit period by joining on `y`.

```sql
SELECT a.id, a.x, d.x AS dataset
FROM t_audit_for_period a
JOIN t_dataset_under_audit d ON a.y = d.id;
```

### 1.3 t_audit_conducted_by

Axiom 3 (`audit_conducted_by`) is embodied by this table. Column `id` is the primary key; column `x` stores the person identifier. Values in `x` may be joined to external personnel records when required.

| id      | x               |
|---------|-----------------|
| AC001   | John_Grant      |
| AC002   | Carol_Lippman   |
| AC003   | External_Auditor|
| AC004   | Internal_Control_Team |

### 1.4 t_audit_subclass

Axiom 4 (`audit_subclass`) is embodied by this table. Column `id` is the primary key; column `x` stores the identifier of the DirectiveICE control being audited. Cross-table queries can correlate these controls with period-specific audits via shared identifiers appearing in `x` values of other tables.

| id      | x                     |
|---------|-----------------------|
| AS001   | Revenue_Recognition   |
| AS002   | Disclosure_Controls   |
| AS003   | Fair_Value_Measurement|
| AS004   | Segment_Reporting     |
| AS005   | Going_Concern         |

## 2. Cross-Join Example

Question: Which person conducted the audit of the Q2 FY24 Shareholder Update dataset, and which control directive was examined?

Step 1. Join `t_audit_for_period` to `t_dataset_under_audit` on `y = id` to locate the audit identifier for DS001.  
Result row: AP001, Q2_FY24_Audit, DS001.

Step 2. Use the audit identifier AP001 to locate the matching row in `t_audit_conducted_by` (via external mapping of process names) and the matching row in `t_audit_subclass` (via shared control reference).  
Joined result:  
- Dataset: Q2_FY24_Shareholder_Update  
- Audit process: Q2_FY24_Audit  
- Conducted by: John_Grant  
- Control audited: Revenue_Recognition

The same pattern extends to any other combination of period, dataset, person, and control by following the single declared foreign-key path and the shared identifier values.
