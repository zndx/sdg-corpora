# Chapter 4: Relational Mapping of Audit Governance Ontologies

This chapter delineates the structural implementation of a governance framework through the precise mapping of ontology axioms to relational database schemas. The focus is on the formal definition of audit processes, the artifacts subject to scrutiny, the agents responsible for execution, and the regulatory directives governing control. By grounding these conceptual entities in a deterministic relational structure, organizations ensure that compliance reporting is not only semantically rigorous but also verifiable through data integrity constraints. The following sections detail the transformation of abstract ontology classes into concrete table structures, providing the necessary evidence anchors for high-assurance audit environments.

## 1. The Dataset Under Audit

The foundational unit of any audit engagement is the artifact or dataset to be examined. In the context of governance frameworks, this entity is formally defined as an instance of an Information Content Entity that falls under the scope of a specific audit process. The axiom `dataset_under_audit` establishes that the subject of the audit (`X`) is a subclass of `cco:Artifact` and is specifically involved in an `underAudit` relationship with a process. This distinction is critical for segregating production data from audit snapshots, ensuring that the integrity of the evidence is preserved throughout the audit lifecycle.

From a relational perspective, this concept necessitates a master registry of all artifacts that have been flagged for review. The schema for this entity is designed to capture the unique identifier of the dataset and its ontological classification. By enforcing a primary key constraint, the framework guarantees that every artifact referenced in subsequent audit procedures is traceable to a single, authoritative record. This eliminates ambiguity regarding which version of a dataset—be it a ledger, a log file, or a user registry—is subject to examination.

The following table illustrates the instantiation of datasets currently under audit. It demonstrates the classification of diverse artifacts, ranging from financial transaction ledgers to access control logs, each assigned a unique identifier that serves as the foreign key target for process-related tables.

This classification allows audit engines to apply specific validation rules based on the artifact type—for instance, applying monetary integrity checks to instances of `FinancialGeneralLedger` while applying access pattern analysis to `ActiveDirectoryUserLogs`.

## 2. Audit for Period

The temporal dimension of an audit is encapsulated in the `audit_for_period` axiom. This concept asserts that an audit process (`X`) is a `bfo:Process` that is defined by its execution over a specific audit period (`Y`). In practice, this binds the procedural activities of the audit to a finite temporal window, ensuring that findings are contextualized within the correct operational timeframe. The relational projection of this axiom links the process instance to the dataset being audited, creating a dependency that enforces the scope of the investigation.

The schema for `t_audit_for_period` requires a foreign key reference to the dataset table, thereby mandating that no audit period can be established without a valid subject artifact. This referential integrity is a cornerstone of audit compliance; it prevents the creation of "orphan" audit records that lack evidentiary grounding. Furthermore, the structure supports the decomposition of complex audits into distinct periods, allowing for granular reporting on quarterly or monthly activities without conflating data across temporal boundaries.

| AUD-Q3-SEC-01 | Q3AccessCertification | DS-2023-SEC-01 |

The data in Table 2 reflects a standard quarterly cadence (Q3), illustrating how multiple processes (e.g., `Q3FinancialReview` and `Q3VarianceAnalysis`) may operate on distinct datasets within the same temporal window. The `x` column identifies the specific audit class, which determines the procedural checklist applied to the dataset `y`. This separation of concerns allows the governance framework to scale, accommodating parallel audit streams without structural interference.

## 3. Audit Conducted By

Governance frameworks must enforce accountability by explicitly linking audit processes to the agents performing them. The `audit_conducted_by` axiom formalizes this by defining an audit process (`X`) as a `bfo:Process` that is `conductedBy` a `cco:Person`. This ontological commitment ensures that every procedural step is attributable to a human agent, satisfying the fundamental requirement of non-repudiation in compliance reporting.

In the relational schema, `t_audit_conducted_by` serves as a junction that associates the audit process identifier with the responsible party. While the schema provided does not explicitly include a foreign key to a personnel table, the `x` column functions as an entity reference to the individual. In a fully normalized production environment, this would typically enforce a reference to a Human Resources directory; however, within this scope, it serves as a definitive textual or coded reference to the auditor. This linkage is essential for audit trail reconstruction, enabling stakeholders to query "who performed which audit" with precision.

## 4. Audit Subclass and Control Directives

The final concept addressed in this chapter is the specific compliance objective of the audit, defined by the `audit_subclass` axiom. This axiom posits that an audit process (`X`) is a `bfo:Process` that `auditsControl` some `cco:DirectiveICE` (Information Content Entity). This is the mechanism by which a generic audit process is specialized into a specific compliance activity, such as a SOX 404 control test or an ISO 27001 policy verification. The "Directive" represents the rule or standard against which the dataset is evaluated.

The relational schema `t_audit_subclass` captures this specialization by linking the process ID to the specific directive being audited. This allows the governance framework to categorize audit results not just by time or personnel, but by the regulatory or internal control standard being enforced. This categorization is crucial for aggregating compliance posture across an organization, as it enables the generation of reports such as "all SOX controls passed in Q3."

Table 4 illustrates the mapping of audit processes to specific control directives. These directives represent the formal logic or policy documents that govern the audit's execution criteria.

In Table 4, the `x` column contains references to specific control directives. For instance, the process `AUD-Q3-FIN-01` is explicitly linked to the `RevenueRecognition` directive. This level of granularity ensures that the audit output is not merely a binary "pass/fail" but is a structured assessment against defined governance criteria. It facilitates the automated generation of compliance matrices, where the status of the directive is derived from the execution of the linked audit process.
