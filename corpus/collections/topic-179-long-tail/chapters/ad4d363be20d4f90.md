# Chapter 4: Ontological Structures in Audit Governance Frameworks

## 4.1 Scope and Preamble

This chapter delineates the structural components of the Audit Governance Ontology (AGO), specifically focusing on the formalization of audit processes, dataset provenance, and agency attribution within a regulatory context. The definitions provided herein align with the OWL 2 Manchester syntax axioms and are projected onto a relational schema to ensure data integrity during compliance reporting. The objective is to establish a rigorous, evidence-anchored framework for representing audit events such that they satisfy both machine-readability requirements and the standards of formal governance reviews. The following sections detail the core axioms governing dataset classification, temporal scoping, agent assignment, and control verification.

## 4.2 Dataset Under Audit

### 4.2.1 Conceptual Definition

The foundational entity within any audit engagement is the object of scrutiny: the dataset. In the context of the AGO, this is formalized via the axiom `dataset_under_audit`. This axiom asserts that any entity classified as a dataset under audit is, by definition, a `cco:Artifact` (an information content entity created or modified by an agent) that stands in the relation `sdg:underAudit` to a specific `bfo:0000015` (a process).

This distinction is critical for governance frameworks. It separates passive data repositories from active subjects of compliance investigation. When a dataset is entered into the audit register, it is no longer merely a collection of records; it becomes a distinct node in the audit graph, traceable and immutable for the duration of the audit process. This formalization prevents ambiguity regarding the scope of discovery and ensures that the "system of record" is explicitly defined prior to the commencement of fieldwork.

### 4.2.2 Relational Implementation

The relational projection of this axiom creates a primary registry for all artifacts subject to review. The schema requires a unique identifier and the classification of the artifact.

## 4.3 Audit for Period

### 4.3.1 Conceptual Definition

An audit process does not exist in a vacuum; it is temporally bounded and substantively defined by the data it examines. The axiom `audit_for_period` formalizes this by defining a subclass of processes (`bfo:0000015`) that possess the object property `sdg:forAuditPeriod`. In this ontology, the "period" is not merely a temporal interval but is inextricably linked to the specific dataset instance defined in the previous section.

The verbalization "{X} is something that for audit period {Y}" indicates a dependency relationship. The audit process (X) is anchored to the period (Y). In the relational schema, this is enforced via a foreign key constraint, ensuring that an audit cannot be defined for a period that does not correspond to a recognized dataset under audit. This enforces referential integrity: one cannot audit a "period" for which no data has been captured or submitted for review.

### 4.3.2 Relational Implementation

The schema for `t_audit_for_period` links the specific audit process instance to the dataset ID that defines its scope. This ensures that the audit trail is continuous and that the "period" is effectively a proxy for the dataset snapshot.

## 4.4 Audit Conducted By

### 4.4.1 Conceptual Definition

Governance frameworks require clear lines of accountability. The axiom `audit_conducted_by` addresses the agentive dimension of the audit process. It asserts that an audit process (a subclass of `bfo:0000015`) is conducted by a `cco:Person`. This axiom links the process to the agent, establishing the "who" behind the "what."

In formal compliance terms, this axiom serves as the basis for auditor independence checks and conflict of interest screening. By explicitly modeling the relationship `sdg:conductedBy`, the system can programmatically validate that the assigned individual meets the prerequisites for the specific audit type (e.g., a CPA for financial audits or a CISSP for cybersecurity reviews). It transforms the audit from an abstract activity into a specific, attributable action performed by a legal or natural person.

### 4.4.2 Relational Implementation

The relational table `t_audit_conducted_by` serves as a log of process assignment. While the schema provided focuses on the process entity (`x`), in a full implementation, this would typically resolve to a personnel directory. For the purposes of this chapter, we focus on the process instances that have been assigned.

## 4.5 Audit Subclass and Control Verification

### 4.5.1 Conceptual Definition

The final structural component involves the specific target of the audit: the control directive. The axiom `audit_subclass` defines an audit process as one that `auditsControl` a specific `cco:DirectiveICE` (Information Content Entity). A DirectiveICE represents the rule, policy, or control requirement (e.g., "Passwords must be rotated every 90 days").

This axiom is the mechanism for granular compliance testing. It moves beyond the general "audit of HR" to a specific "audit of the Password Rotation Control." By mapping the audit process to a specific directive, the framework allows for precise gap analysis. The output of such a process is a binary or scalar determination of whether the artifact (dataset) adheres to the directive (control). This is the operational core of the governance framework: the comparison of observed reality (dataset) against required behavior (directive).

### 4.5.2 Relational Implementation

The table `t_audit_subclass` categorizes audit processes based on the specific directive they are testing. This allows the organization to report on compliance coverage across different regulatory domains (e.g., SOX, GDPR, NIST).

## 4.6 Summary of Relational Integrity

The four tables presented in this chapter are not independent lists; they form a cohesive, enforceable network of relationships. The integrity of the audit report depends on the strict adherence to these foreign key constraints.

1.  **Scope Definition:** One cannot define an `audit_for_period` (Table 4-2) without a valid `dataset_under_audit` (Table 4-1).
2.  **Agent Assignment:** An `audit_conducted_by` (Table 4-3) must reference a process that exists.
3.  **Control Mapping:** An `audit_subclass` (Table 4-4) must link a process to a valid directive.

By populating these tables with the instances provided in the Q3 FY24 data, the organization ensures that the audit narrative is supported by a deterministic, queryable data structure.
