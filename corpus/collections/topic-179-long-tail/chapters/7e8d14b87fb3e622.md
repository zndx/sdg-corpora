# Chapter 4: Ontological Mapping of Audit Governance Structures

This chapter delineates the formal ontological structures required to map audit governance processes within a regulatory compliance framework. The scope of this text is restricted to the precise definition of audit entities, their temporal bindings, the artifacts under examination, and the responsible agents. The following sections utilize the Manchester syntax of the Web Ontology Language (OWL) to define axioms, which are subsequently projected into relational schemas to ensure data integrity and auditability. This approach ensures that all governance activities are anchored to verifiable evidence structures, compliant with both administrative codes and internal control directives.

## 1.0 Temporal Scope and Periodicity

In accordance with governance standards, every audit process must be temporally bounded to ensure relevance and validity. The axiom `audit_for_period` establishes a necessary dependency between the audit process and a specific classification of time. This is not merely a timestamp but a formal classification of the audit duration, linking the process (`X`) to a defined audit period (`Y`). This relationship ensures that retrospective analysis can isolate process behaviors to specific regulatory windows, a requirement for high-quality compliance reporting.

The relational projection of this axiom enforces a strict foreign key constraint, ensuring that no audit process can be defined without a valid reference to an established period. In practice, this prevents the execution of "orphan" audits that lack a defined reporting timeframe. The table below illustrates this binding, where the `y` column represents the period identifier, which must correspond to an existing dataset entry acting as the period anchor.

**Table 1.1: Audit Process Period Mapping**

| id | x | y |
| :--- | :--- | :--- |
| AUD-FY24-Q1-001 | FinancialControlAudit | PER-FY24-Q1 |
| AUD-FY24-Q1-002 | AccessControlReview | PER-FY24-Q1 |
| AUD-FY23-Q4-005 | IncidentResponseAudit | PER-FY23-Q4 |
| AUD-FY24-Q2-010 | DataRetentionCheck | PER-FY24-Q2 |
| AUD-FY24-Q2-011 | VendorComplianceAudit | PER-FY24-Q2 |

### 1.1 Axiomatic Definition
The formal definition for this concept is expressed in Manchester syntax as follows:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:forAuditPeriod some {Y:Class}`

This verbalizes to: *{X} is something that for audit period {Y}*. Here, `X` represents the audit process, which is a subclass of `bfo:0000015` (a process). The slot `Y` represents the specific period class. The relational schema `t_audit_for_period` enforces this by requiring `y` to be a non-null field that references the primary key of the dataset table, effectively grounding the abstract concept of a "period" to a concrete record within the system.

## 2.0 Artifact Classification and Audit Status

The target of any governance process is the informational artifact. The axiom `dataset_under_audit` classifies the object of the audit inquiry. These artifacts, defined as subclasses of `cco:Artifact`, are the digital or physical records subjected to the audit process. This classification is critical for maintaining the chain of custody and ensuring that the scope of the audit is explicitly defined and immutable during the audit period.

Under this framework, an artifact cannot be considered "under audit" unless it is formally registered in the governance ledger. This registration serves as the primary key for all subsequent inquiries. The table below enumerates specific datasets that have been flagged for review, demonstrating the mapping between the system identifier (`id`) and the specific artifact class (`x`).

| PER-FY24-Q2 | Q2_Vendor_Contracts |
| PER-FY24-Q1 | Q1_Employee_Records |

### 2.1 Axiomatic Definition
The underlying ontology for this section is defined as:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:underAudit some bfo:0000015`

This verbalizes to: *{X} is something that under audit process*. The entity `X` is the artifact, and the relationship `sdg:underAudit` links it to a process. The relational schema `t_dataset_under_audit` simplifies this to a primary entity table, where the existence of the record implies the "under audit" status. The `id` serves as the anchor for the foreign keys defined in Section 1.0, creating a normalized structure where periods are inextricably linked to the specific datasets they govern.

## 3.0 Attribution of Responsibility and Conduct

Governance frameworks require clear attribution of agency. The axiom `audit_conducted_by` introduces the human element, linking the audit process (`X`) to a `cco:Person`. This axiom ensures that every automated or manual process traceable to the system must have a responsible agent identified. This is a fundamental component of directive governance, preventing the existence of autonomous or unattributed system processes that could obscure accountability during compliance investigations.

The relational mapping for this concept treats the audit process as the primary entity, with the `conductedBy` property implied by the association. The following table displays instances where specific audit processes are tied to the responsible agents, ensuring that the "who" is as rigorously documented as the "what" and the "when."

**Table 3.1: Audit Responsibility Assignment**

| :--- | :--- |
| AUD-COND-001 | SystemAudit_J_Grant |
| AUD-COND-002 | ComplianceReview_L_Bright |
| AUD-COND-003 | SafetyAudit_M_Doe |
| AUD-COND-004 | FinancialAudit_S_Smith |
| AUD-COND-005 | DataAudit_R_Roe |

### 3.1 Axiomatic Definition
The formal axiom is presented as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:conductedBy some cco:Person`

This verbalizes to: *{X} is something that conducted by person*. The structure mandates that any instance of `X` (the process) must have an associated `cco:Person`. In the relational schema `t_audit_conducted_by`, the column `x` holds the identifier for the process, which implicitly carries the constraint of the person association via the broader ontology. This design allows for rapid querying of all actions taken by a specific individual, a requirement for internal audit trails and external regulatory discovery.

## 4.0 Control Directives and Subclassing

The final concept addresses the specificity of the audit process. While previous sections defined the temporal and agent-based constraints, the axiom `audit_subclass` categorizes the audit based on the specific control directive it examines. A `cco:DirectiveICE` (Information Content Entity) represents the specific rule, law, or policy being tested. This axiom allows the governance framework to differentiate between, for example, a financial audit and a safety audit based on the directive being validated.

This granular classification is essential for reporting accuracy. It enables the generation of compliance matrices that map specific audit instances to distinct regulatory requirements. The table below provides examples of audit processes that are specifically subclassed by their target control directives, illustrating the diversity of governance activities within a single framework.

**Table 4.1: Audit Subclassifications by Directive**

| :--- | :--- |

| AUD-SUB-002 | GDPR_Article_32_Check |
| AUD-SUB-003 | ISO_27001_Access_Control |
| AUD-SUB-004 | HIPAA_Security_Rule_Audit |
| AUD-SUB-005 | NIST_800_53_Rev5_Audit |

### 4.1 Axiomatic Definition
The ontology defines this specialization as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:auditsControl some cco:DirectiveICE`

This verbalizes to: *{X} is something that audits control directive information content entity*. The entity `X` is the audit process, but it is distinguished by its relationship to a specific directive. The relational schema `t_audit_subclass` captures these instances, where the `x` column contains the specific name of the audit subclass. This structure supports the "03_directive_governance" family, ensuring that the system can report on compliance coverage across multiple regulatory bodies simultaneously.
