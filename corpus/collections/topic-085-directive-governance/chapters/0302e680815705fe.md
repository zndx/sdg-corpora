# Directive ICE Modeling in GDPR Compliance Schemas

This chapter defines five relational tables that instantiate OWL axioms for cco:DirectiveICE subclasses. The tables capture GDPR article specialization, risk-addressing constraints, mitigation relations, and priority assignments. Primary and foreign keys enforce the existential and universal quantifiers expressed in the axioms, enabling cross-table queries that reconstruct multi-hop compliance paths.

## 1 Scope and Table Construction Principles

The schemas project Manchester OWL axioms directly onto relational structures. Each table corresponds to one axiom template. Column `x` always denotes the subclass of cco:DirectiveICE; column `y` denotes the filler of the respective object property. Foreign-key constraints implement the `some` and `only` restrictions, ensuring that every asserted `y` value resolves to a valid target row.

## 1.1 GDPR Article Subclass Table

Axiom 1 (`gdpr_article_subclass`) is embodied by `t_gdpr_article_subclass`. Column `id` is the primary key; column `y` is a foreign key referencing `t_control_only_addresses_threat_class(id)`. A reader can join this table to the control-only table to retrieve every directive that both specializes a GDPR article and is restricted to addressing a single threat class.

```sql
CREATE TABLE t_gdpr_article_subclass (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

## 1.2 Control-Only Addresses Threat Table

Axiom 2 (`control_only_addresses_threat_class`) is embodied by `t_control_only_addresses_threat_class`. Column `id` is the primary key; column `y` is a foreign key referencing `t_gdpr_article_subclass(id)`. The universal restriction is realized by requiring every control row to reference exactly one threat class through this link.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_gdpr_article_subclass(id)
);
```

## 1.3 Control Addresses Risk Table

Axiom 3 (`control_addresses_risk`) is embodied by `t_control_addresses_risk`. Column `id` is the primary key; column `y` is a foreign key referencing `t_gdpr_article_subclass(id)`. The existential restriction permits a control to address one or more risks while remaining anchored to a GDPR article.

```sql
CREATE TABLE t_control_addresses_risk (
  id VARCHAR(255),
  x VARCHAR(255),

  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_gdpr_article_subclass(id)
```

## 1.4 Control Subclass Table

Axiom 4 (`control_subclass`) is embodied by `t_control_subclass`. Column `id` is the primary key; column `y` is a foreign key referencing `t_gdpr_article_subclass(id)`. The table records mitigation relations that specialize a directive toward concrete risk reduction outcomes.

```sql
CREATE TABLE t_control_subclass (
```

## 1.5 Requirement Has Priority Table

Axiom 5 (`requirement_has_priority`) is embodied by `t_requirement_has_priority`. Column `id` is the primary key; column `y` is a foreign key referencing `t_gdpr_article_subclass(id)`. The table assigns priority classes that govern sequencing of directive implementation.

```sql
CREATE TABLE t_requirement_has_priority (
```

## 2 Multi-Hop Query Example

To determine the priority of the control that addresses risk `PseudonymizationRoutine` under the article referenced by `gdpr_001`, perform the following joins:

1. Locate `ctl_risk_01` in `t_control_addresses_risk` where `x = 'PseudonymizationRoutine'`; its `y` yields `gdpr_001`.
2. Join `gdpr_001` from `t_gdpr_article_subclass` to `t_requirement_has_priority` on `y`.
3. The matching row `req_pri_02` supplies priority `Medium`.

The resulting joined tuple is:

`(ctl_risk_01, PseudonymizationRoutine, gdpr_001, Article5_1a_lawfulness, Medium)`
