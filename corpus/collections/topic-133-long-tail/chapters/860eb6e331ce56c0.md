# Compliance Documentation Models for Claim Attestation

This chapter defines five ontological templates that capture support, lawful-basis, and attestation relations among compliance artifacts and claims. The templates are realized as a five-table relational schema in which primary keys identify specific class instances and foreign-key links enable multi-hop queries over GDPR-related processing directives and evidence.

## 1 Trace and Lineage Relations

Axiom 1 (trace_supports_claim) states that any class X is a processual entity that supports a descriptive information content entity. The corresponding table therefore records each supporting instance once.

**Table t_trace_supports_claim**  
Primary key: id. Column x holds the identifier of the supporting class. No foreign keys are present; joins occur when another table’s x or y column matches an id value in this table.

| id          | x                       |
|-------------|-------------------------|
| trace-001   | LineageRecord-17        |
| trace-002   | ProcessingLog-04        |
| trace-003   | AccessMatrix-09         |
| trace-004   | RetentionSchedule-12    |
| trace-005   | ConsentLedger-03        |

Axiom 3 (column_lineage_for_compliance_claim) likewise classifies an artifact X as supporting a descriptive claim. The table isolates lineage artifacts that participate in compliance verification.

**Table t_column_lineage_for_compliance_claim**  
Primary key: id. Column x references the lineage artifact. Values of x may be joined to id values in t_trace_supports_claim when the same artifact both traces and supports a claim.

| id          | x                       |
|-------------|-------------------------|
| lineage-01  | ColumnMap-22            |
| lineage-02  | ColumnMap-17            |
| lineage-03  | ColumnMap-09            |
| lineage-04  | ColumnMap-31            |
| lineage-05  | ColumnMap-14            |

Axiom 4 (kernel_anomaly_supports_claim) classifies an artifact X that supports a claim by documenting kernel-level anomalies. The table stores only those artifacts whose anomaly records are admissible as claim support.

**Table t_kernel_anomaly_supports_claim**  
Primary key: id. Column x holds the anomaly artifact identifier. Cross-table queries commonly match x against t_trace_supports_claim.x to confirm dual support paths.

| id          | x                       |
|-------------|-------------------------|
| anomaly-01  | KernelEvent-88          |
| anomaly-02  | KernelEvent-41          |
| anomaly-03  | KernelEvent-55          |
| anomaly-04  | KernelEvent-19          |
| anomaly-05  | KernelEvent-76          |

## 2 Lawful Basis and Attestation Relations

Axiom 2 (gdpr_lawful_basis) asserts that a directive class X possesses a lawful basis class Y. The table therefore contains both the directive and its basis; y functions as a foreign key that may reference an id in t_trace_supports_claim or t_attestation_about_compliance_claim.

**Table t_gdpr_lawful_basis**  
Primary key: id. Column x identifies the directive; column y identifies the lawful-basis class and serves as the sole foreign-key column in the schema.

| id          | x                          | y             |
|-------------|----------------------------|---------------|
| basis-001   | DataProcessingDirective-07 | Consent-03    |
| basis-002   | DataProcessingDirective-11 | Contract-05   |
| basis-003   | DataProcessingDirective-02 | LegalObl-02   |
| basis-004   | DataProcessingDirective-15 | Legitimate-01 |
| basis-005   | DataProcessingDirective-08 | Consent-03    |

Axiom 5 (attestation_about_compliance_claim) classifies an activity X that attests to a descriptive claim. The table records attestation events whose outputs may be joined via shared identifiers with the preceding tables.

**Table t_attestation_about_compliance_claim**  
Primary key: id. Column x holds the attestation activity. Values of x may be joined to y values in t_gdpr_lawful_basis to retrieve the attested lawful basis.

| id            | x                       |
|---------------|-------------------------|
| attest-001    | AuditReport-33          |
| attest-002    | AuditReport-27          |
| attest-003    | AuditReport-19          |
| attest-004    | AuditReport-41          |
| attest-005    | AuditReport-12          |

## 3 Worked Multi-Hop Query Example

Question: Which lawful basis is attested by the activity whose identifier appears in the same row as the directive that supports claim trace-001?

Execution steps:  
1. Locate row in t_trace_supports_claim where id = 'trace-001'; note x = 'LineageRecord-17'.  
2. Locate row in t_gdpr_lawful_basis where x = 'DataProcessingDirective-07'; read y = 'Consent-03'.  
3. Locate row in t_attestation_about_compliance_claim where x = 'AuditReport-33'; confirm that y from step 2 is referenced by the attested directive.

Joined result row:  
(trace-001, LineageRecord-17) → (basis-001, DataProcessingDirective-07, Consent-03) → (attest-001, AuditReport-33)

The three-table join yields the lawful basis 'Consent-03' together with its supporting lineage record and attesting audit report.
