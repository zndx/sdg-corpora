# Chapter 4: Claim-Support Structures in GDPR Compliance Lineage

This chapter defines five ontological templates that formalize how artifacts and processes support or attest to descriptive claims under lawful-basis constraints. The templates are realized as a five-table relational schema drawn from an audit-trail system for personal-data processing. Primary keys are uniformly named id; foreign-key relationships are expressed by populating x and y columns with identifiers drawn from other tables, enabling cross-table joins that recover multi-hop provenance.

## 1. Schema Overview

All tables share the column layout prescribed by their source axioms. Table t_gdpr_lawful_basis alone carries a second reference column y. Every id value is unique within its table. Values placed in x or y columns are either internal identifiers or identifiers drawn from another table, thereby establishing the foreign-key constraints required for the cross-join demonstrations that follow.

### 1.1 t_trace_supports_claim

This table embodies axiom trace_supports_claim by recording process occurrences (bfo:0000015) that support a descriptive claim. Column id is the primary key; column x holds the supporting occurrence and functions as a foreign key when its value matches an id in t_attestation_about_compliance_claim.

```sql
SELECT t.id, t.x
FROM t_trace_supports_claim t
JOIN t_attestation_about_compliance_claim a ON t.x = a.id;
```

### 1.2 t_gdpr_lawful_basis

This table embodies axiom gdpr_lawful_basis by linking a directive information content entity to its lawful basis class. Column id is the primary key; column x references a compliance artifact while column y references the basis class, both serving as foreign keys when matched against identifiers in t_column_lineage_for_compliance_claim or t_kernel_anomaly_supports_claim.

```sql
SELECT g.id, g.x, g.y
FROM t_gdpr_lawful_basis g
JOIN t_column_lineage_for_compliance_claim c ON g.x = c.id;
```
