# Chapter 7: Ontological Mapping of Regulatory Directives and Evidentiary Controls

## 7.1 Scope and Preamble

This chapter delineates the structural dependencies between regulatory directives, their lawful bases, and the evidentiary artifacts required for compliance verification within distributed information systems. It establishes the ontological mappings necessary for automated governance frameworks, specifically focusing on the integration of General Data Protection Regulation (GDPR) standards with internal control mechanisms. The following sections provide a formal analysis of the axioms governing the relationships between processing directives, evidence requirements, and audit processes, supported by relational schema implementations designed to ensure referential integrity and auditability.

## 7.2 GDPR Lawful Basis and Directive Classification

### 7.2.1 Axiomatic Definition
The foundational component of any compliant data processing architecture is the establishment of a lawful basis. In the context of the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO), a lawful basis is not merely a textual justification but a distinct information content entity that must be formally linked to processing directives.

The axiom `gdpr_lawful_basis` asserts that a Class `X` (specifically a `cco:DirectiveICE`) is a subclass that possesses a lawful basis `Y`. This relationship is mandatory; without this linkage, any subsequent processing operation is ontologically invalid and non-compliant. The verbalization "{X} is something that has lawful basis {Y}" implies that the directive inherits the legal validity of `Y`.

### 7.2.2 Relational Implementation
To implement this axiom within a relational database management system (RDBMS), the table `t_gdpr_lawful_basis` is utilized. The primary key `id` serves as the unique identifier for the specific instance of the lawful basis assignment. The column `x` represents the `DirectiveICE` (the processing class), while column `y` represents the lawful basis class itself.

Crucially, the schema enforces a foreign key constraint where `y` references `t_control_with_evidence_requirement(id)`. This creates a bidirectional dependency: a lawful basis is inextricably linked to a specific control that generates the evidence supporting that basis. This ensures that the declaration of a lawful basis is not abstract but is anchored to a tangible governance mechanism.

**Table 7.1: Relational Mapping of GDPR Lawful Basis to Directives**

| id | x | y |
| :--- | :--- | :--- |
| LB-PAT-001 | ClinicalTrialProcessing | CTRL-EV-REQ-001 |
| LB-PAT-002 | EpidemiologicalDataAggregation | CTRL-EV-REQ-002 |
| LB-EMP-001 | HRPayrollProcessing | CTRL-EV-REQ-003 |

*Table 7.1 illustrates the mapping of specific processing directives (`x`) to their lawful basis identifiers (`y`). Note that the `y` values correspond to control identifiers, enforcing the axiom's requirement that a basis must be supported by a control mechanism.*

## 7.3 Control with Evidence Requirement

### 7.3.1 Axiomatic Definition
Governance frameworks must distinguish between the existence of a control and the verification of its operation. The axiom `control_with_evidence_requirement` addresses this by defining that a Class `X` (a `cco:DirectiveICE`) is a subclass that requires evidence `Y`.

The verbalization "{X} is something that requires evidence {Y}" formalizes the compliance mandate. It is insufficient to state that a control exists; the ontology demands that the control directive is structurally dependent on the production of evidence artifacts. This evidence serves as the "information content entity" that proves the control was executed effectively during a specific temporal interval.

### 7.3.2 Relational Implementation
The table `t_control_with_evidence_requirement` encodes this relationship. The primary key `id` identifies the specific control directive. Column `x` denotes the control class, while column `y` denotes the required evidence class.

The schema defines a recursive foreign key constraint: `y` references `t_gdpr_lawful_basis(id)`. This circular reference with the previous section (Axiom 1) establishes a tight coupling between the legal justification for processing and the technical proof of compliance. A lawful basis (`LB-PAT-001`) is valid only if the associated control (`CTRL-EV-REQ-001`) generates the required evidence, and conversely, the control's requirement is derived from the lawful basis it supports.

**Table 7.2: Control Directives and Associated Evidence Requirements**

| id | x | y |
| :--- | :--- | :--- |
| CTRL-EV-REQ-001 | RoleBasedAccessControl | LB-PAT-001 |
| CTRL-EV-REQ-002 | DataAnonymizationPipeline | LB-PAT-002 |
| CTRL-EV-REQ-003 | AutomatedLogRetention | LB-EMP-001 |
| CTRL-EV-REQ-004 | EncryptionAtRestStandard | LB-MKT-001 |
| CTRL-EV-REQ-005 | BiometricVerificationSystem | LB-RES-001 |

*Table 7.2 details the control directives (`x`) and the evidence (`y`) they must produce. The foreign key linkage to `t_gdpr_lawful_basis` ensures that every evidence requirement is traceable to a specific GDPR lawful basis.*

## 7.4 Attestation with Supporting Evidence

### 7.4.1 Axiomatic Definition
Attestation represents the formal validation of compliance by an authorized agent. The axiom `attestation_with_supporting_evidence` posits that a Class `X` (a `bfo:0000015`, or Process) is a subclass that includes supporting evidence `Y`.

In this context, "{X} is something that with supporting evidence {Y}" implies that the attestation process is not a standalone event but an aggregation of evidence artifacts. The attestation entity derives its validity from the completeness and integrity of the evidence `Y` it references. This is critical for audit trails, as it transforms raw data logs or system states into legally recognized compliance statements.

### 7.4.2 Relational Implementation
The table `t_attestation_with_supporting_evidence` captures this process. The primary key `id` uniquely identifies the attestation instance. Column `x` represents the attestation process class, while column `y` holds the identifier of the supporting evidence.

The foreign key constraint `y` REFERENCES `t_gdpr_lawful_basis(id)` ensures that the evidence supporting the attestation is directly tied to a valid lawful basis. This prevents "orphaned" attestations—compliance statements that do not pertain to an active legal basis for processing.

## 7.5 Audit for Period

### 7.5.1 Axiomatic Definition
Temporal scoping is a fundamental requirement in governance. Controls and evidence must be evaluated within specific timeframes to ensure continued relevance. The axiom `audit_for_period` asserts that a Class `X` (a `bfo:0000015` Process) is a subclass defined for a specific audit period `Y`.

The verbalization "{X} is something that for audit period {Y}" restricts the validity of the audit process to the defined interval. This ontological constraint prevents the application of outdated audit results to current compliance states. It ensures that the audit process is temporally bounded and aligned with reporting cycles (e.g., fiscal quarters, calendar years).

### 7.5.2 Relational Implementation
The table `t_audit_for_period` manages these temporal associations. The primary key `id` identifies the audit process. Column `x` represents the audit class, and column `y` represents the period class.

Consistent with the other evidence-based tables, the foreign key `y` REFERENCES `t_gdpr_lawful_basis(id)` links the audit period to the lawful basis. This design choice implies that the audit period is not merely a date range but is intrinsically linked to the validity period of the lawful basis for a specific processing activity.

**Table 7.4: Audit Processes Defined by Specific Periods**

| id | x | y |
| :--- | :--- | :--- |
| AUD-FY23-001 | FY2023AccessControlAudit | LB-PAT-001 |
| AUD-FY23-002 | FY2023DataRetentionAudit | LB-EMP-001 |
| AUD-Q1-24-001 | Q1_2024MarketingConsentAudit | LB-MKT-001 |
| AUD-H1-23-001 | H1_2023ResearchDataAudit | LB-PAT-002 |
| AUD-ROLL-001 | RollingSixMonthAudit | LB-RES-001 |

*Table 7.4 maps audit processes (`x`) to the lawful basis identifiers (`y`), effectively anchoring the audit timeline to the lifecycle of the data processing justification.*

## 7.6 Audit Subclass

### 7.6.1 Axiomatic Definition
The final axiom, `audit_subclass`, categorizes the audit process itself. It asserts that a Class `X` (a `bfo:0000015` Process) is a subclass that audits a `cco:DirectiveICE` (Control).

The verbalization "{X} is something that audits control directive information content entity" establishes the hierarchical relationship between the audit activity and the target of the audit. Unlike previous axioms that linked processes to evidence or periods, this axiom defines the *nature* of the audit process as a specific type of oversight mechanism targeting directive information content entities.

### 7.6.2 Relational Implementation
The table `t_audit_subclass` is structurally simpler, reflecting the classification nature of the axiom. It contains only the primary key `id` and the class column `x`. There are no foreign keys in this specific table, as it serves as a classification registry for audit types rather than a mapping table linking disparate entities.

**Table 7.5: Classification of Audit Subclasses**

*Table 7.5 lists the specific subclasses of audit processes (`x`). These classes define the methodology and scope of the audit when applied to the control directives identified in previous sections.*
