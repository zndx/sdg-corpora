# Chapter 7: Ontological Formalization of Governance and Compliance Protocols

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures governing Information Security Compliance and Audit (ISCA) within enterprise environments. It provides a rigorous examination of the axioms defining attestation, requirement mapping, and audit execution, grounded in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). The content herein is designed to establish a deterministic framework for mapping regulatory directives—specifically the Payment Card Industry Data Security Standard (PCI DSS)—to executable governance processes. Practitioners will find precise definitions for the relational instantiation of compliance artifacts, ensuring that audit trails are both semantically valid and evidentially robust. The following sections decompose these concepts into their constituent logical components, supported by data schemas that enforce referential integrity across the governance domain.

## 7.2 Attestation Signed By

### 7.2.1 Conceptual Definition
The foundational unit of trust in a governance framework is the attestation. Ontologically, an attestation is not merely a document but a process—a temporal entity that unfolds as a responsible agent validates a specific state of affairs. According to the axiom `attestation_signed_by`, any class representing an attestation event is a subclass of `bfo:0000015` (Process). This process is necessarily characterized by the `sdg:signedBy` object property, which links the attestation to an instance of `cco:Person`.

This relationship establishes the chain of custody for digital and physical records. It posits that an attestation is invalid unless it is explicitly signed by a natural person recognized within the system. The signature acts as the bridge between the process (the act of attesting) and the agent (the person attesting), thereby grounding the abstract compliance requirement in concrete legal liability.

### 7.2.2 Implementation and Evidence
In practice, this axiom is instantiated when a user completes a certification form regarding their access rights or system configuration. The system records the event as a specific class of attestation, capturing the unique identifier of the process and the identifier of the signing person. The following table illustrates the instantiation of this axiom, where the `x` column represents the specific attestation class or instance ID, and the `id` serves as the primary key for the governance record.

**Table 7.1: Relational Instantiation of Attestation Signatory Events**

| :--- | :--- |
| ATT-SIGN-001 | AnnualSecurityPolicyAttestation |
| ATT-SIGN-002 | Q3AccessControlReview |
| ATT-SIGN-003 | IncidentResponseAcknowledgement |

## 7.3 PCI DSS Requirement Mapping

### 7.3.1 Conceptual Definition
Governance frameworks often operate at the intersection of internal directives and external regulatory standards. The axiom `pci_dss_requirement` formalizes this intersection. It defines a class structure where a governance directive (subclass of `cco:DirectiveICE`) is semantically linked to a specific PCI DSS requirement via the `sdg:pciDssRequirement` property.

This mapping is critical for automated compliance auditing. It allows the system to query an internal directive and immediately retrieve the corresponding external regulatory text. The axiom asserts that for a directive to be valid within the PCI DSS scope, it must necessarily possess a requirement property that points to a defined requirement class. This creates a dependency graph where internal controls are formally anchored to external mandates.

### 7.3.2 Relational Dependencies
The schema for this axiom enforces a strict foreign key constraint. The requirement identifier (`y`) must reference an existing entry in the `t_requirement_equiv_specifies_target` table. This ensures that one cannot define a PCI DSS requirement mapping without first establishing the equivalence definition of that requirement (i.e., what it specifies and to what it applies). This circular dependency in the schema design reflects the real-world interdependence of regulatory text and its application.

**Table 7.2: Mapping of Directives to PCI DSS Requirements**

| :--- | :--- | :--- |
| PCI-REQ-101 | FirewallConfigurationDirective | REQ-EQ-101 |
| PCI-REQ-102 | VendorAccessPolicy | REQ-EQ-102 |

*Table 7.2 embodies the axiom `pci_dss_requirement`. The primary key is `id`, representing the mapping instance. Column `x` is the internal DirectiveICE class, and `y` is the foreign key referencing the requirement definition in `t_requirement_equiv_specifies_target`.*

## 7.4 Attestation Min One Signer

### 7.4.1 Conceptual Definition
While the presence of a signature is necessary, the cardinality of that signature is equally vital for process integrity. The axiom `attestation_min_one_signer` refines the definition of attestation processes by imposing a minimum cardinality constraint (`min 1`) on the `sdg:signedBy` property. This axiom asserts that any valid attestation process must be signed by at least one `cco:Person`.

This constraint serves as a validation rule within the governance engine. It prevents the creation of "orphan" attestation processes—records that have been initiated but never ratified by a human agent. In formal ontology, this distinguishes a *planned* attestation from a *completed* one. The process class `X` is only realized as a compliant governance event when the `signedBy` property is populated with one or more valid person identifiers.

### 7.4.2 Process Validation
The enforcement of this axiom ensures that audit trails do not contain gaps in authorization. For example, a background check process is technically a process, but it does not become a valid attestation of clearance until a hiring manager or security officer signs off on it. The relational representation of this axiom focuses on the process class itself, asserting its eligibility to be signed.

| ATT-MIN-002 | PrivilegeAccountReview |

| ATT-MIN-004 | NetworkChangeAuthorization |

*Table 7.3 embodies the axiom `attestation_min_one_signer`. The `id` is the unique identifier for the process definition, and `x` represents the specific class of process that requires a minimum of one signatory to be valid.*

## 7.5 Audit Conducted By

### 7.5.1 Conceptual Definition
Distinct from attestation, which is a declaration of truth or compliance, an audit is an investigative process. The axiom `audit_conducted_by` defines the relationship between an audit process and the auditor. It classifies the audit (`X`) as a subclass of `bfo:0000015` (Process) and links it via `sdg:conductedBy` to an instance of `cco:Person`.

This axiom is central to the concept of auditor independence and traceability. It ensures that every audit event recorded in the system is attributable to a specific agent with the authority to conduct such an inquiry. The "conducted by" relationship differs from "signed by" in that it implies active execution and investigation rather than mere ratification. The ontology treats the auditor as the efficient cause of the audit process.

### 7.5.2 Auditor Attribution
In the context of a compliance database, this axiom allows for the generation of auditor workload reports and conflict-of-interest checks. By querying the `t_audit_conducted_by` table, governance officers can identify which personnel are responsible for specific audit findings. The table structure below isolates the audit process identifier, serving as the base record for the audit event.

## 7.6 Requirement Equivalence Specifies Target

### 7.6.1 Conceptual Definition
The most complex axiom in this chapter is `requirement_equiv_specifies_target`. It provides an equivalence definition for a class `X` that satisfies three conditions simultaneously: it is a `cco:DirectiveICE`; it `sdg:specifies` some requirement class `Y`; and it `sdg:appliesTo` some target class `Z`. This axiom effectively decomposes a compliance directive into its semantic components: the directive itself, the specific requirement it addresses, and the target system or entity to which it is relevant.

This structure allows for granular querying. For instance, one can query for all directives that apply to a specific target (`Z`) or all directives that specify a particular type of requirement (`Y`). It bridges the gap between high-level policy (the Directive) and operational reality (the Target).

### 7.6.2 Relational Structure and Circular Dependency
The relational schema for this axiom is notable for its foreign key constraints. The `y` column (the requirement specified) references the `id` in `t_pci_dss_requirement`. Conversely, as noted in Section 7.3, the `t_pci_dss_requirement` table references this table. This circular dependency implies that a requirement definition and its PCI DSS mapping are co-dependent in this model; one cannot exist in isolation if it is to be considered valid within the compliance framework. The `z` column represents the target, grounding the directive in the infrastructure (e.g., a database, a network segment, or a personnel group).
