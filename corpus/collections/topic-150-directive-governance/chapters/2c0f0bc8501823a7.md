# Chapter 4: Directive Governance and Attestation Structures in Compliance Audits

This chapter presents five relational tables that encode the slot structures of five OWL axioms governing attestations, audits, and PCI DSS requirements. The tables support cross-table joins that resolve multi-hop queries over signed processes, conducted audits, and requirement specifications.

## 1 Scope and Table Overview

The axioms belong to the directive-governance family. Each table is introduced by its axiom, followed by its primary-key and foreign-key columns. All identifiers are drawn from formal administrative documents such as examination forms, attendance slips, and installation records.

## 1.1 Table t_attestation_signed_by

Axiom attestation_signed_by states that an attestation process is signed by a person. Column id is the primary key. Column x references the attestation class. A cross-join with t_attestation_min_one_signer on x yields the set of attestations that both carry a signature and satisfy the minimum-signer cardinality.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id          | x                          |
|-------------|----------------------------|
| asb_001     | ComplianceAttestation      |
| asb_002     | MeetingAttendanceRecord    |
| asb_003     | CandidateFormSubmission    |
| asb_004     | InstallationConfirmation   |
| asb_005     | CourtConvenedMeetingRecord |

## 1.2 Table t_attestation_min_one_signer

Axiom attestation_min_one_signer asserts that an attestation process must be signed by at least one person. Column id is the primary key. Column x again identifies the attestation class. Joining this table with t_attestation_signed_by on x confirms that every listed attestation satisfies the existential restriction.

```sql
CREATE TABLE t_attestation_min_one_signer (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id          | x                          |
|-------------|----------------------------|

| amos_002    | MeetingAttendanceRecord    |
| amos_003    | CandidateFormSubmission    |

## 1.3 Table t_audit_conducted_by

Axiom audit_conducted_by states that an audit process is conducted by a person. Column id is the primary key. Column x identifies the audit class. This table joins with t_pci_dss_requirement via shared class references to link conducted audits to the requirements they verify.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id          | x                          |
|-------------|----------------------------|
| acb_001     | PCIComplianceAudit         |
| acb_002     | AnnualSecurityReview       |
| acb_003     | AccessControlVerification  |
| acb_004     | NetworkSegmentAudit        |
| acb_005     | MerchantDataInspection     |

## 1.4 Table t_pci_dss_requirement

Axiom pci_dss_requirement asserts that a directive is a PCI DSS requirement of a specified target. Column id is the primary key. Column y is a foreign key to t_requirement_equiv_specifies_target.id. Column x names the directive class.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_requirement_equiv_specifies_target(id)
);
```

| id          | x                          | y          |
|-------------|----------------------------|------------|
| pdr_001     | Requirement8               | rest_001   |
| pdr_002     | Requirement12              | rest_002   |
| pdr_003     | Requirement3               | rest_003   |
| pdr_004     | Requirement11              | rest_004   |

## 1.5 Table t_requirement_equiv_specifies_target

Axiom requirement_equiv_specifies_target defines a directive that both specifies a class and applies to a class. Column id is the primary key. Column y is a foreign key to t_pci_dss_requirement.id. Columns x, y, and z together encode the equivalent-class expression.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

| id          | x                          | y         | z                          |
|-------------|----------------------------|-----------|----------------------------|
| rest_001    | AccessControlDirective     | pdr_001   | UserAuthenticationTarget   |
| rest_002    | PolicyDocumentation        | pdr_002   | SecurityPolicyTarget       |
| rest_003    | DataProtectionDirective    | pdr_003   | CardholderDataTarget       |
| rest_004    | MonitoringDirective        | pdr_004   | NetworkMonitoringTarget    |

## 2 Cross-Join Example

To determine which person-conducted audit verifies the PCI DSS requirement that applies to cardholder data, join t_audit_conducted_by, t_pci_dss_requirement, and t_requirement_equiv_specifies_target on the shared class references:

- Start with t_requirement_equiv_specifies_target where z = 'CardholderDataTarget' → row rest_003.
- Follow foreign key y to t_pci_dss_requirement → row pdr_003.
- Join t_audit_conducted_by on x = 'PCIComplianceAudit' → row acb_001.

The resulting joined record states that the PCIComplianceAudit conducted by a designated person verifies Requirement3, which specifies the DataProtectionDirective applying to CardholderDataTarget.
