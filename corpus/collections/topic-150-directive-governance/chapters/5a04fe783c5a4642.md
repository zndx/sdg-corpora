# Chapter 4: Formal Ontology of Governance and Compliance Mechanisms

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures underpinning the governance framework, specifically mapping OWL-derived axioms to relational data schemas utilized in compliance auditing. The focus is on the precise definition of processes, directives, and personnel interactions within the context of PCI DSS requirements. Readers will examine the logical constraints governing attestations, audit execution, and the specification of regulatory targets. The content herein is anchored in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), providing a rigorous basis for data integrity in audit reporting systems.

## 1. Attestation and Signatory Authority

### 1.1 The Ontology of Attestation

In the context of governance frameworks, an attestation is not merely a document but a temporally bounded process wherein an agent validates a state of affairs. The axiom `attestation_signed_by` provides the formal definition for this concept. It asserts that any entity classified as {X} is a subclass of `bfo:0000015` (a Process) and is specifically characterized by the property `sdg:signedBy` relating to an instance of `cco:Person`.

This distinction is critical for audit trails. It separates the *record* of the attestation from the *act* of attesting. By defining {X} as a Process, the ontology captures the event-like nature of signing, which occurs at a specific time and place, rather than treating the attestation as a static information artifact alone. The verbalization "{X} is something that signed by person" implies that the existence of the attestation process is logically dependent on the participation of a natural person.

### 1.2 Relational Implementation

The projection of this axiom into a relational schema is embodied in the table `t_attestation_signed_by`. The structure is designed to track instances of attestation processes. The primary key (`id`) ensures referential integrity for the specific event instance, while the column `x` represents the class or specific instance of the attestation process being recorded.

**Table Schema Explanation:**
The table `t_attestation_signed_by` serves as the registry for all attestation events. The `id` column acts as the surrogate primary key, uniquely identifying the attestation record. The `x` column stores the identifier for the attestation class or instance, mapping directly to the {X} slot in the ontology. This structure allows for the querying of all attestations while maintaining the link to the process-oriented definition required by the BFO.

## 2. PCI DSS Requirement Mapping

### 2.1 Directive Alignment

Compliance frameworks often require internal governance directives to map explicitly to external regulatory standards. The axiom `pci_dss_requirement` formalizes this relationship. It states that a class {X} is a subclass of `cco:DirectiveICE` (an Information Content Entity) and possesses the property `sdg:pciDssRequirement` which links it to a requirement class {Y}.

This axiom facilitates the "long-tail" of compliance governance, where specific internal controls (Directives) must be traced back to specific paragraphs or requirements within the Payment Card Industry Data Security Standard (PCI DSS). The verbalization "{X} is something that pci dss requirement {Y}" establishes a necessary condition: for an internal directive to be valid under this classification, it must be demonstrably associated with a specific PCI DSS requirement.

### 2.2 Relational Dependencies

The relational schema `t_pci_dss_requirement` encodes this mapping with a foreign key constraint that enforces referential integrity to the specification targets. The schema requires that the requirement ({Y}) being referenced must exist as a defined target in the `t_requirement_equiv_specifies_target` table. This circular dependency (where the requirement table references the target table, and the target table references the requirement table) ensures that directives are not created in a vacuum but are part of a tightly coupled definition of compliance scope.

**Table Schema Explanation:**
The table `t_pci_dss_requirement` links internal directives to external compliance mandates. The `id` is the primary key. Column `x` represents the internal DirectiveICE, while column `y` is a foreign key referencing the `id` in `t_requirement_equiv_specifies_target`. This enforces the rule that a PCI DSS requirement mapping must point to a valid, defined specification target.

## 3. Minimum Signatory Constraints

### 3.1 Cardinality in Governance Processes

While the presence of a signatory is important, governance frameworks frequently mandate a minimum threshold of participation to ensure validity and prevent unilateral authorization failures. The axiom `attestation_min_one_signer` refines the definition of an attestation process by introducing a cardinality constraint.

Formally, it asserts that {X} is a subclass of `bfo:0000015` (Process) and is related via `sdg:signedBy` to a minimum of one (`min 1`) instance of `cco:Person`. This axiom utilizes OWL restrictions to enforce that the set of signatories associated with process {X} cannot be empty. In practical terms, this distinguishes a draft process from a validly executed attestation; an attestation without at least one signatory fails to satisfy the class definition of `attestation_min_one_signer`.

### 3.2 Relational Representation

The table `t_attestation_min_one_signer` captures instances of these constrained processes. While relational databases typically enforce constraints at the row level (via NOT NULL checks) or through application logic, the existence of this specific table denotes a separate category of processes where the "min 1" rule is a primary characteristic of the entity's definition within the ontology.

**Table Schema Explanation:**
The table `t_attestation_min_one_signer` lists processes that strictly require at least one signatory to be considered valid. The `id` serves as the primary key. The `x` column identifies the specific process class or instance. This table is distinct from general attestations to isolate those processes where the cardinality of signers is a critical compliance factor.

## 4. Audit Execution and Personnel

### 4.1 The Audit Process

Auditing is a fundamental verification mechanism in governance. The axiom `audit_conducted_by` defines the relationship between the audit event and the agent performing it. It posits that {X} is a subclass of `bfo:0000015` (Process) and is characterized by the property `sdg:conductedBy` relating to some `cco:Person`.

This axiom differentiates the *audit* from the *auditor*. The audit is the process—the investigation, the evidence gathering, and the reporting. The auditor is the person. The verbalization "{X} is something that conducted by person" ensures that every recorded audit event in the system is agentive; it cannot exist without human execution (or a person-delegated agent, though the axiom here strictly points to `cco:Person`). This is vital for accountability chains in regulatory filings.

### 4.2 Data Structure for Audits

The `t_audit_conducted_by` table provides the relational instantiation of this axiom. It is a straightforward registry designed to log audit events. The simplicity of the schema (ID and Process ID) belies the importance of the constraint it represents: the linkage to a Person is handled at the ontological level, ensuring that any row in this table implies the existence of a responsible agent.

**Table Schema Explanation:**
The table `t_audit_conducted_by` records the execution of audit processes. The `id` is the unique identifier for the audit record. The `x` column represents the audit process instance or class. This table functions as a log of auditable events, ensuring that all entries conform to the definition of a process conducted by a person.

## 5. Directive Equivalence and Target Specification

### 5.1 Complex Class Definitions

The most ontologically complex axiom presented here is `requirement_equiv_specifies_target`. This axiom defines a class {X} using an `EquivalentTo` construct, meaning that {X} is exactly synonymous with the intersection of three specific conditions:
1.  It is a `cco:DirectiveICE`.
2.  It has the property `sdg:specifies` some class {Y}.
3.  It has the property `sdg:appliesTo` some class {Z}.

This creates a "necessary and sufficient" condition. For an entity to be an instance of {X}, it must be a directive, it must specify something (Y), and it must apply to a target (Z). This structure is typically used to define specific compliance rules that are only meaningful when they are actively directing a requirement towards a specific target (e.g., a directive that applies specifically to "Credit Card Data" and specifies "Encryption").

### 5.2 Relational Mapping and Circular Integrity

The relational schema `t_requirement_equiv_specifies_target` captures this tripartite definition. The schema includes a foreign key constraint where column `y` references `t_pci_dss_requirement(id)`. This creates a semantic loop: a PCI DSS Requirement (Table 2) points to a Requirement Equivalent (Table 5), and that Requirement Equivalent points back to the PCI DSS Requirement via its `y` column.

This circularity is intentional in the ontology design to represent a tight coupling between the *requirement definition* and the *directive specification*. The `z` column represents the target to which the directive applies, completing the triad.

**Table Schema Explanation:**
The table `t_requirement_equiv_specifies_target` is the central registry for directive definitions. The `id` is the primary key. Column `x` is the DirectiveICE. Column `y` is a foreign key referencing `t_pci_dss_requirement`, linking the directive to the specific PCI requirement. Column `z` represents the target system or entity class to which the directive applies. This structure enforces the ontological equivalence that a directive is defined by what it specifies and what it applies to.
