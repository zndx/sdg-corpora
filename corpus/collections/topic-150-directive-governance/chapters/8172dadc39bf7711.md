# Chapter 4: Governance Mechanisms and Attestation Protocols in PCI-DSS Compliance Frameworks

## 4.1 Scope and Preamble

This chapter delineates the formal governance mechanisms required to establish and maintain compliance within the Payment Card Industry Data Security Standard (PCI-DSS) environment. The text establishes the ontological relationships between audit processes, directive requirements, and personnel accountability. It provides a rigorous examination of the structural axioms governing conduct, attestation, and requirement specification. The objective is to define the precise conditions under which a governance framework can be considered valid, ensuring that all directives are traceable to specific personnel, processes, and regulatory targets. The following sections detail the implementation of these axioms using standardized relational schemas and evidence-based procedural documentation.

## 4.2 Audit Execution and Personnel Assignment

### 4.2.1 Definition and Axiomatic Basis

In the context of formal governance, an audit is defined not merely as a review but as a specific temporal process (bfo:0000015) that must be instantiated by a responsible agent. The foundational axiom for this section is derived from the ontology template `audit_conducted_by`. This axiom posits that for any audit process to be valid, it must be conducted by a recognized person (cco:Person). This relationship ensures that there is no ambiguity regarding the ownership of the audit activity; the process is inextricably linked to the human agent responsible for its execution.

The verbalization of this axiom asserts: "{X} is something that conducted by person." In practical terms, this means that an audit record is invalid if it lacks a designated conductor. The governance framework must enforce this relationship at the data level, ensuring that every instance of an audit process class references a valid personnel identifier.

### 4.2.2 Implementation and Evidence

To operationalize this axiom, the governance framework utilizes the relational schema `t_audit_conducted_by`. This table serves as the primary registry for audit events, linking the specific audit process instance to its unique identifier. The structure enforces that the process (X) is the central entity, with the implicit constraint that the conductor is a Person type.

When documenting audit trails, the following data structure must be utilized. The table below illustrates the registration of specific audit processes. Note that the `id` serves as the primary key, ensuring referential integrity, while `x` denotes the specific audit class or instance being recorded.

| ID | Audit Process (X) |
| :--- | :--- |
| AUD-2023-001 | QuarterlyVulnerabilityAssessment |
| AUD-2023-002 | InternalNetworkSegmentationReview |
| AUD-2023-003 | PhysicalAccessLogAudit |
| AUD-2023-004 | WirelessAccessPointScan |
| AUD-2023-005 | ApplicationCodeReview |

**Table 4.1: Audit Process Registry**

In accordance with governance protocols, every entry in Table 4.1 must be cross-referenced with the personnel roster to verify that the `conductedBy` property is populated by a valid `cco:Person`. Failure to maintain this linkage constitutes a violation of the governance axiom and invalidates the audit findings for compliance purposes.

## 4.3 PCI-DSS Requirement Integration

### 4.3.1 Directive and Requirement Mapping

The compliance framework is built upon the integration of internal directives with external regulatory standards. Specifically, the PCI-DSS framework imposes a set of mandatory requirements that must be mapped to internal governance directives. The axiom `pci_dss_requirement` formalizes this by stating that a Directive (X) is a subclass of `cco:DirectiveICE` and must possess a `pciDssRequirement` relationship with a specific Requirement Class (Y).

Verbalized, the axiom states: "{X} is something that pci dss requirement {Y}." This structure creates a dependency where the validity of the internal directive is contingent upon its correct mapping to the external PCI-DSS standard. This is not a loose association but a structural subclassing requirement; the directive *is* the implementation of the requirement.

### 4.3.2 Relational Mapping and Constraints

The schema `t_pci_dss_requirement` enforces this mapping. Crucially, this schema introduces a foreign key constraint linking the requirement (Y) to the `t_requirement_equiv_specifies_target` table. This recursive dependency ensures that requirements are not defined in isolation but are always tied to specific targets and specifications.

The following table represents the mapping of internal directives to their corresponding PCI-DSS requirement anchors. The `x` column represents the internal directive class, while `y` represents the specific requirement class identifier.

| ID | Directive (X) | PCI DSS Requirement (Y) |
| :--- | :--- | :--- |
| DIR-SEC-001 | EncryptionPolicyDirective | REQ-8.2.1 |
| DIR-SEC-002 | AccessControlProtocol | REQ-8.1.4 |
| DIR-SEC-003 | MalwareProtectionPlan | REQ-5.1.2 |
| DIR-SEC-004 | LoggingMechanismDirective | REQ-10.2.1 |
| DIR-SEC-005 | DataRetentionPolicy | REQ-10.7 |

**Table 4.2: PCI-DSS Requirement Mapping**

It is imperative that the values in the `PCI DSS Requirement (Y)` column correspond to valid entries in the requirements specification registry. This mapping allows auditors to trace a specific internal governance action (e.g., the enforcement of an encryption policy) directly back to the specific regulatory clause (e.g., Requirement 8.2.1 regarding strong cryptography).

## 4.4 Directive Specification and Target Application

### 4.4.1 Logical Equivalence of Directives

The core logic of the governance framework is defined by the axiom `requirement_equiv_specifies_target`. This axiom establishes that a Directive Class (X) is equivalent to the intersection of three conditions: it is a `cco:DirectiveICE`, it specifies a Requirement (Y), and it applies to a Target (Z). This tripartite structure ensures that directives are never abstract; they must always specify *what* is required and *who* or *what* it applies to.

The verbalization is: "{X} is something that specifies {Y} and applies to {Z}." This equivalence relation is the mechanism by which the governance framework enforces scope. A directive without a specified target is null, and a directive without a specified requirement is void.

### 4.4.2 Schema and Data Population

The relational schema `t_requirement_equiv_specifies_target` captures this complex relationship. It enforces that `y` (the requirement) must reference an entry in `t_pci_dss_requirement`, closing the loop established in the previous section. The `z` column represents the target of the directive, which could be a system class, a user group, or a data asset.

The table below details the logical decomposition of directives. Each row represents a unique directive instance, its requirement specification, and its application target.

| ID | Directive (X) | Specifies (Y) | Applies To (Z) |
| :--- | :--- | :--- | :--- |
| DIR-SEC-001 | EncryptionPolicyDirective | REQ-8.2.1 | CardholderDataEnvironment |
| DIR-SEC-002 | AccessControlProtocol | REQ-8.1.4 | PrivilegedUserAccount |
| DIR-SEC-003 | MalwareProtectionPlan | REQ-5.1.2 | PointOfSaleTerminal |
| DIR-SEC-004 | LoggingMechanismDirective | REQ-10.2.1 | SystemAuditTrail |
| DIR-SEC-005 | DataRetentionPolicy | REQ-10.7 | SecurityLogFiles |

**Table 4.3: Directive Specification and Target Registry**

In this configuration, the `Specifies (Y)` column acts as a foreign key to the requirement mapping table (Table 4.2), while `Applies To (Z)` grounds the directive in the operational reality of the infrastructure. For instance, the `EncryptionPolicyDirective` is not merely a document; it is a logical entity that specifies `REQ-8.2.1` and applies specifically to the `CardholderDataEnvironment`.

## 4.5 Attestation and Signature Authority

### 4.5.1 The Act of Attestation

Attestation represents the formalization of agreement or validation of a process state. The axiom `attestation_signed_by` defines an attestation as a process (bfo:0000015) that is signed by a person (cco:Person). This differs from the audit process in that the attestation is specifically concerned with the act of signing—validating the truth or accuracy of the preceding process.

The axiom is verbalized as: "{X} is something that signed by person." In the governance framework, this implies that no attestation process is considered complete until the digital or physical signature of a responsible person is captured and bound to the process record.

### 4.5.2 Attestation Registry

The `t_attestation_signed_by` table maintains the record of these signings. The schema is straightforward, consisting of an identifier and the attestation process class (X). The constraint is implicit: the process `X` must be of a type that supports signing, and the actor must be a valid Person entity.

The following table logs specific attestation events. These events typically occur after the completion of an audit or the implementation of a directive.

| ID | Attestation Process (X) |
| :--- | :--- |
| ATT-SIG-2023-085 | QuarterlyComplianceAttestation |
| ATT-SIG-2023-086 | VulnerabilityAcknowledgement |
| ATT-SIG-2023-087 | PolicyReviewSignOff |
| ATT-SIG-2023-088 | IncidentResponseValidation |
| ATT-SIG-2023-089 | ThirdPartyAccessAuthorization |

**Table 4.4: Attestation Event Log**

Each entry in Table 4.4 triggers a workflow to verify the credentials of the signer. The governance framework must reject the attestation if the associated Person entity lacks the authority to sign for the specific process class `X`.

## 4.6 Cardinality Constraints in Governance

### 4.6.1 Minimum Signer Requirements

To prevent the centralization of authority and ensure checks and balances, the governance framework enforces cardinality constraints on the signing process. The axiom `attestation_min_one_signer` asserts that any attestation process (X) must be signed by a minimum of one person (cco:Person). While this may appear tautological, in the context of automated workflows and role-based access control, it serves as a critical validation rule to prevent unsigned or system-generated approvals from masquerading as valid attestations.

The verbalization is: "{X} is a process." The axiom uses the restriction `sdg:signedBy min 1 cco:Person`, ensuring that the set of signers for any process X cannot be empty.

### 4.6.2 Constraint Validation

The schema `t_attestation_min_one_signer` is utilized to validate these constraints. It mirrors the structure of the attestation table but is specifically employed in query validation to enforce the "min 1" rule.

The table below lists the processes subject to this constraint. The data demonstrates that every listed process has been verified to meet the minimum signer requirement.

| :--- | :--- |

| ATT-SIG-2023-087 | PolicyReviewSignOff |

**Table 4.5: Minimum Signer Constraint Validation**

In practice, the governance engine runs a validation query against `t_attestation_min_one_signer` prior to closing any compliance period.
