# Chapter 7: Directive Governance in PCI DSS Audit Trails

This chapter defines five tables that realize OWL axioms for attestations, audits, and requirements. The tables form a minimal schema in which primary and foreign keys encode signed processes, conducted audits, and equivalences that specify targets under PCI DSS directives. All column values are instances consistent with the slot types of the source axioms.

## 1 Table Derivations from Axioms

### 1.1 t_attestation_signed_by
Axiom 1 states that an attestation is a process signed by at least one person. The table therefore stores the attestation identifier together with the signing person. Column id is the primary key; column x holds the person reference. A reader can join this table to any other attestation table on x to retrieve signatories of a given process.

| id            | x                  |
|---------------|--------------------|
| att-sb-001    | Person:DavidJeromeAlt |
| att-sb-002    | Person:TerryHartle |
| att-sb-003    | Person:AmySmith    |
| att-sb-004    | Person:KevinONeill |
| att-sb-005    | Person:JoelAllison |

### 1.2 t_attestation_min_one_signer
Axiom 3 asserts that an attestation process must have a minimum of one signer. The table records each attestation that satisfies the cardinality restriction. Column id is the primary key; column x again identifies the attestation process. Cross-table queries on x confirm that every listed attestation also appears in t_attestation_signed_by.

| id            | x                  |
|---------------|--------------------|
| att-mo-001    | PCIAttestation-12  |
| att-mo-002    | PCIAttestation-13  |
| att-mo-003    | AuditReport-07     |
| att-mo-004    | AuditReport-08     |
| att-mo-005    | ComplianceAttest-03|

### 1.3 t_audit_conducted_by
Axiom 4 states that an audit is a process conducted by a person. The table captures each audit and its conductor. Column id is the primary key; column x stores the conducting person. Joining on x with t_attestation_signed_by yields persons who both sign attestations and conduct audits.

| id            | x                  |
|---------------|--------------------|
| aud-cb-001    | Person:TerryHartle |
| aud-cb-002    | Person:KevinONeill |
| aud-cb-003    | Person:AmySmith    |
| aud-cb-004    | Person:DavidJeromeAlt |
| aud-cb-005    | Person:MarkHurd    |

### 1.4 t_requirement_equiv_specifies_target
Axiom 5 defines a requirement as a directive that is equivalent to a class specifying a target and applying to a scope. The table materializes the three slots. Column id is the primary key; columns y and z are foreign keys, the former referencing t_pci_dss_requirement. A reader can therefore traverse from a requirement equivalence through its specified target to the governing PCI DSS clause.

| id            | x                       | y             | z                  |
|---------------|-------------------------|---------------|--------------------|
| req-eq-001    | Req-12-Equiv            | pci-12-4      | Target:NetworkSeg  |
| req-eq-002    | Req-12-Equiv            | pci-12-4      | Target:AccessCtrl  |
| req-eq-003    | Req-8-Equiv             | pci-8-2       | Target:AuthMgt     |
| req-eq-004    | Req-8-Equiv             | pci-8-2       | Target:SessionMgt  |
| req-eq-005    | Req-10-Equiv            | pci-10-3      | Target:LogReview   |

### 1.5 t_pci_dss_requirement
Axiom 2 states that a directive is a PCI DSS requirement of a given target specification. The table records each directive and its linked specification. Column id is the primary key; column y is a foreign key to t_requirement_equiv_specifies_target. Joining y to that table and onward to its z column recovers the full target scope of any requirement.

| id            | x                  | y             |
|---------------|--------------------|---------------|
| pci-12-4      | PCI-DSS-Req-12     | req-eq-001    |
| pci-8-2       | PCI-DSS-Req-8      | req-eq-003    |
| pci-10-3      | PCI-DSS-Req-10     | req-eq-005    |
| pci-12-4b     | PCI-DSS-Req-12     | req-eq-002    |
| pci-8-2b      | PCI-DSS-Req-8      | req-eq-004    |

## 2 Multi-Hop Query Example

To determine which person conducted the audit whose attestation satisfies PCI DSS requirement 12.4 and specifies target NetworkSeg, begin at t_pci_dss_requirement where x equals PCI-DSS-Req-12 and y equals req-eq-001. Follow y into t_requirement_equiv_specifies_target to confirm z equals Target:NetworkSeg. The same requirement row links via its own id to any attestation table sharing the process identifier. The resulting joined row is:

pci-12-4 | PCI-DSS-Req-12 | req-eq-001 | Target:NetworkSeg | aud-cb-001 | Person:TerryHartle
