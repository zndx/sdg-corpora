# Chapter 7: Ontological Mapping for Process Audit and Artifact Verification

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish a compliant audit trail for digital process governance. It provides a rigorous examination of four primary axioms derived from the BFO (Basic Formal Ontology) and CCO (Common Core Ontologies) frameworks, specifically addressing the intersection of processual entities and informational artifacts. The objective is to ensure that all system events are not only recorded but are semantically anchored to participant artifacts and temporal indices, satisfying the evidentiary standards required for regulatory compliance and forensic review. The following sections define the relational schemata necessary to implement these axioms within a secure database environment, ensuring referential integrity and high-fidelity data lineage.

## 7.2 Axiom 1: Observation with Participant

### 7.2.1 Definition and Verbalization

The foundational unit of any audit framework is the observation. In this context, an observation is not merely a passive recording but a distinct entity that necessitates the presence of a participant artifact. The axiom is formally expressed in Manchester syntax as:

`Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`

This is verbalized as: **{X} is something that has participant artifact**.

In practical terms, this asserts that for any process or event (`X`) to be validly recorded as an observation, it must be causally connected to a specific artifact (`cco:Artifact`). The artifact serves as the "participant" in the process—the object, agent, or data structure upon which the process acts. Without this linkage, the observation lacks semantic grounding and cannot be admitted as evidence in a strict compliance context.

### 7.2.2 Relational Implementation

To enforce this axiom within a relational database management system (RDBMS), the following schema is mandated. The table `t_observation_with_participant` serves as the primary registry for all observed events. The column `x` represents the specific class or instance of the observation, while the `id` serves as the immutable unique identifier for the record.

The primary key (`id`) ensures that each observation is distinct and non-repeating. This structure prevents ambiguous references and allows for downstream foreign key constraints to validate the existence of an observation before linking temporal or processual data to it.

**Table 7.1: Observation with Participant Registry**

| id | x |
| :--- | :--- |
| OBS-2024-089 | CredentialValidationEvent |
| OBS-2024-090 | SystemAccessAttempt |
| OBS-2024-091 | DataExfiltrationBlock |
| OBS-2024-092 | ConfigurationModification |

### 7.2.3 Compliance Context

Consider the following evidence entry, modeled after the style of a formal docket:

> **AUDIT TRAIL ENTRY**
>
> **Case ID:** SEC-INV-2024-001
> **Date:** 14 October 2024
> **Time:** 09:42:15 UTC
> **Entity:** User_J_Smith
> **Artifact:** SecureToken_A77
> **Observation Class:** CredentialValidationEvent
>
> **Details:** The entity `User_J_Smith` attempted to utilize `SecureToken_A77` to access the secure ledger. The system recorded this as `OBS-2024-089`. The artifact `SecureToken_A77` is the requisite participant artifact. The observation is invalid without the artifact's hash reference.

In this scenario, `CredentialValidationEvent` (the value of `x`) is the class of the observation. The record `OBS-2024-089` cannot exist unless it is associated with a specific artifact, such as the token or the user credential file.

## 7.3 Axiom 2: Schema.org Event Start Time

### 7.3.1 Definition and Verbalization

Temporal precision is a critical component of digital forensics. The second axiom addresses the anchoring of an artifact to a specific temporal event. The Manchester syntax is defined as:

`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasEventStartTime some {Y:Class}`

Verbalized: **{X} is something that has event start time {Y}**.

This axiom establishes a relationship between an artifact (`X`) and a temporal event (`Y`). Crucially, the schema dictates that the event start time (`Y`) is not a simple literal value (like a timestamp string) but is itself an entity that references an observation. This design choice allows the "start time" to carry its own metadata, provenance, and observation context, rather than being a detached data point.

### 7.3.2 Relational Implementation

The implementation of this axiom requires the table `t_schemaorg_event_starttime`. This table links an artifact (`x`) to an observation (`y`) that signifies the start time.

The foreign key constraint `FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)` is the critical enforcement mechanism here. It ensures that the "start time" event (`y`) is a valid, previously recorded observation. This creates a strict dependency: an artifact cannot have a start time unless that start time corresponds to a legitimate observation event involving a participant artifact.

**Table 7.2: Event Start Time Mapping**

| id | x | y |
| :--- | :--- | :--- |
| EVT-START-001 | SecureSessionInstance | OBS-2024-089 |
| EVT-START-002 | AuditLogRotation | OBS-2024-090 |
| EVT-START-003 | FirmwareUpdateProcess | OBS-2024-092 |

### 7.3.3 Evidence and Usage

In the context of a governance framework, this structure allows auditors to query not just *when* something happened, but *what observation* recorded that commencement. For instance, if we examine the row with `id` `EVT-START-001`, we see that the `SecureSessionInstance` (the artifact `x`) has its start time defined by observation `OBS-2024-089`.

By referencing the observation table, the system validates that `OBS-2024-089` was indeed a `CredentialValidationEvent`. This provides a layer of semantic verification: the start of a session is inextricably linked to the validation of the credentials that authorized it.

## 7.4 Axiom 3: Process Minimum One Output

### 7.4.1 Definition and Verbalization

To validate the completion of a process, governance frameworks require evidence of output. The third axiom formalizes this requirement:

`Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasOutput min 1 {Y:Class}`

Verbalized: **{X} is a process** (that has a minimum of one output).

This axiom classifies `X` as a process (`bfo:0000015`) and imposes a cardinality constraint: it must possess at least one output (`Y`). In a compliant system, a process that executes without generating a traceable output is considered a failure or an anomaly, often indicative of data loss or obfuscation.

### 7.4.2 Relational Implementation

The table `t_process_min_one_output` records these relationships. The column `x` identifies the process class, while `y` identifies the observation that serves as the proof of output.

Similar to the previous axiom, the foreign key `FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)` ensures that the output is a verifiable observation. This prevents "ghost" outputs—claims of output that have no corresponding observation record in the system.

**Table 7.3: Process Output Verification**

| id | x | y |
| :--- | :--- | :--- |
| PROC-OUT-101 | LogRotationProcedure | OBS-2024-090 |
| PROC-OUT-102 | DataSanitizationRoutine | OBS-2024-091 |
| PROC-OUT-103 | ConfigurationBackup | OBS-2024-092 |

### 7.4.3 Audit Implications

When auditing a `LogRotationProcedure`, the examiner looks to Table 7.3. The record `PROC-OUT-101` asserts that the process `LogRotationProcedure` produced an output recorded as observation `OBS-2024-090`.

Cross-referencing this with the Observation Registry (Table 7.1), the auditor confirms that `OBS-2024-090` is a `SystemAccessAttempt` (or potentially a `LogArchiveEvent` depending on the specific instance mapping). This confirms that the process did not terminate silently; it resulted in a specific, observed state change or artifact generation.

## 7.5 Axiom 4: Process Minimum One Input

### 7.5.1 Definition and Verbalization

The final axiom in this sequence addresses the provenance of process execution. Every process must consume or act upon at least one input. The axiom is defined as:

`Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasInput min 1 {Y:Class}`

Verbalized: **{X} is a process** (that has a minimum of one input).

This ensures traceability backwards in time. By enforcing that a process has an input, the governance framework establishes a chain of custody. A process cannot manifest ex nihilo; it must be triggered by or act upon a pre-existing artifact or state.

### 7.5.2 Relational Implementation

The schema for `t_process_min_one_input` mirrors the output schema but defines the inverse direction of dependency. The table links the process (`x`) to the observation (`y`) that represents the input artifact.

The foreign key constraint `FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)` is again essential. It validates that the input claimed by the process actually exists as a recognized observation within the system's history.

**Table 7.4: Process Input Verification**

| id | x | y |
| :--- | :--- | :--- |
| PROC-IN-201 | LogRotationProcedure | OBS-2024-093 |
| PROC-IN-202 | DataSanitizationRoutine | OBS-2024-094 |
| PROC-IN-203 | ConfigurationBackup | OBS-2024-095 |

### 7.5.3 Forensic Traceability

Consider the `DataSanitizationRoutine` (`PROC-IN-202`). According to Table 7.4, this process required an input recorded as `OBS-2024-094`. In a forensic investigation, this allows the analyst to determine exactly what data was fed into the sanitization process.

If `OBS-2024-094` corresponds to a `ConfidentialFileRecord`, the chain of custody is clear: the file existed (Observation), it was input into the Sanitization Routine (Process Input), and the routine produced a `SecureWipeConfirmation` (Process Output, per Table 7.3). This end-to-end linkage satisfies the most stringent data disposal regulations.
