# Chapter 4: Ontological Structures for Operational Auditing and Process Verification

**Revision:** 4.2  
**Date:** 2023-10-27  
**Standard:** ISO/IEC 27002 & OWL 2 DL Mapping  
**Status:** Released for Implementation

This chapter establishes the formal ontological framework required to map physical and logical processes within a governance environment to relational data structures. It provides the necessary definitions for auditing workflows, ensuring that every operational event is traceable to a specific artifact, participant, and temporal anchor. The following sections detail the axiomatic derivation of four core concepts—Observation with Participant, Event Start Time, Process Output, and Process Input—and demonstrate their implementation via deterministic relational schemas. Compliance officers and system architects must utilize these definitions to maintain the integrity of the audit trail, ensuring that data inputs and outputs are rigorously validated against the underlying process logic.

## 4.1 Observation with Participant

In the context of operational auditing, an observation is not merely a passive recording of data but a distinct process (`bfo:Process`) that necessitates the involvement of a specific entity. The axiom **Observation with Participant** formalizes this by asserting that any observation process (`{X}`) must have a participant that is an artifact (`cco:Artifact`). This distinction is critical for auditability; it separates the act of measurement or monitoring from the instrument or document involved.

When an auditor verifies a system log, they are validating an observation process. The integrity of this log depends on the provenance of the participant artifact—be it a sensor, a software module, or a physical document. If the participant artifact cannot be identified or is classified incorrectly (e.g., treated as an abstract information object rather than a concrete artifact), the audit trail is compromised. The axiom ensures that for every process instance recorded, there is an immutable link to the physical or digital resource executing the role of the participant.

### 4.1.1 Relational Implementation

The relational schema for this concept, `t_observation_with_participant`, serves as the foundational table for the audit framework. It captures the identity of the observation process (`id`) and its classification (`x`). The primary key (`id`) ensures that each observation is uniquely identifiable, while the `x` column defines the ontological class of the process, restricting it to subclasses of `bfo:Process`.

This table functions as the parent entity for subsequent temporal and process-flow definitions. By anchoring the observation to an artifact participant, the schema enforces the constraint that no "orphan" processes exist within the system. Every row in this table represents a verifiable event where a specific artifact interacted with the system.

In a real-world scenario, this would correspond to a specific workflow where a temperature sensor (the artifact) is calibrated. The `id` serves as the foreign key target for other tables, ensuring that all temporal data and process inputs/outputs reference this specific calibration event.

## 4.2 Event Start Time

To establish a reliable timeline for compliance reporting, the system must anchor artifacts to specific temporal events. The **Event Start Time** axiom defines a relationship where an artifact (`{X}`) is associated with an event start time (`{Y}`). In this ontology, the concept of time is not treated as a raw literal (e.g., a timestamp string) in isolation but is modeled as a distinct class linked to the observation process.

This approach allows for granular auditing of when specific artifacts became active or relevant to the operational context. For example, a "Configuration File" (the artifact) may have an event start time corresponding to the moment it was loaded into memory during a specific observation process. By modeling the start time as a linked entity rather than a simple attribute, the system can support complex temporal queries, such as finding all artifacts that became active prior to a system failure or during a specific maintenance window.

### 4.2.1 Relational Implementation

The schema `t_schemaorg_event_starttime` implements this axiom by linking an artifact (`x`) to a specific observation instance (`y`) that represents the start time. The foreign key constraint (`y` references `t_observation_with_participant(id)`) is crucial: it dictates that a "start time" cannot exist independently of a defined observation process. This enforces the business rule that time is only relevant in the context of an event being observed.

In this structure, the `y` column effectively acts as a pointer to the temporal observation. This design facilitates the reconstruction of event sequences. If an auditor needs to determine the precise start time of a security scan, they query the `t_schemaorg_event_starttime` table using the scan's artifact ID, retrieve the observation ID (`y`), and then consult the detailed logs associated with that observation.

In Table 4.2, the row with `id` `EVT-START-101` links the artifact `SensorModule_A` to the observation `OBS-2023-001`. This indicates that the start time for the involvement of `SensorModule_A` is defined by the `ThermalCalibrationProcess` recorded in the parent table. This strict referential integrity prevents temporal ambiguity; one cannot claim a device started operating without referencing a valid, recorded observation process.

## 4.3 Process Output

A fundamental requirement of any governance framework is the ability to track the products of operational processes. The **Process Output** axiom stipulates that a process (`{X}`) must have a minimum of one output (`{Y}`). This output is modeled as an observation with a participant artifact, ensuring that the result of a process is treated as a distinct, auditable entity.

This axiom is particularly relevant for data lineage and non-repudiation. When a process executes—such as a data transformation script or a manufacturing assembly step—the output is not merely data; it is a new artifact that enters the system's inventory. By requiring that the output be linked to an observation, the framework mandates that the creation of the artifact was witnessed and recorded. This prevents "ghost data" from appearing in the system without a traceable origin.

### 4.3.1 Relational Implementation

The `t_process_min_one_output` table captures the directional flow of value from process to artifact. The structure defines the process (`x`) and its resulting output (`y`). The foreign key constraint linking `y` to `t_observation_with_participant(id)` ensures that the output is recognized as a valid observation involving an artifact.

This schema supports the "min 1" cardinality constraint of the axiom by allowing multiple rows for a single process `x` (if a process has multiple outputs) or enforcing that at least one row must exist for every active process. In practice, this table allows auditors to trace forward from a process to see exactly what artifacts were generated, facilitating impact analysis. If a specific calculation process is found to be faulty, this table immediately identifies all downstream artifacts (outputs) that may be corrupted.

**Table 4.3: Process Output Registry**

| id | x | y |
| :--- | :--- | :--- |
| PROC-OUT-500 | ThermalCalibrationProcess | OBS-2023-001 |
| PROC-OUT-501 | UserAuthenticationEvent | OBS-2023-002 |
| PROC-OUT-502 | DataIngestionRoutine | OBS-2023-003 |
| PROC-OUT-503 | NetworkPacketCapture | OBS-2023-004 |

Table 4.3 demonstrates the mapping of processes to their specific outputs. For example, the `DataIngestionRoutine` (`PROC-OUT-502`) results in the observation `OBS-2023-003`. This linkage confirms that the ingestion routine successfully produced the artifact captured in that observation. The consistency between the process names in this table and the class names in Table 4.1 highlights the deterministic nature of the ontology mapping.

## 4.4 Process Input

Complementary to the tracking of outputs is the documentation of dependencies and prerequisites. The **Process Input** axiom asserts that a process (`{X}`) requires a minimum of one input (`{Y}`). Like the output, the input is modeled as an observation with a participant artifact. This creates a complete chain of custody for every process, documenting what resources were consumed or utilized to generate the output.

From a security and compliance perspective, this is essential for verifying access controls and authorization. A process should only consume inputs that it is permitted to access. By formalizing inputs as observations, the system can validate that the artifact was present and was interacted with legally. Furthermore, this structure aids in root cause analysis; if a process fails, checking the validity and status of the linked input observations is the first step in diagnosing the issue.

### 4.4.1 Relational Implementation

The `t_process_min_one_input` table mirrors the structure of the output table but defines the inverse relationship. Here, `x` represents the consuming process, and `y` represents the input artifact observation. The foreign key constraint ensures that the input is a known, recorded entity within the system.

This schema enforces the discipline that no process operates in a vacuum. Every computational or physical action must be triggered by or dependent upon a pre-existing artifact state. In a database context, this prevents cyclic dependencies and ensures a directed acyclic graph (DAG) of process flow, which is a desirable property for reliable system architecture and clean audit trails.

**Table 4.4: Process Input Registry**

| id | x | y |
| :--- | :--- | :--- |
| PROC-IN-600 | ThermalCalibrationProcess | OBS-2023-005 |
| PROC-IN-601 | UserAuthenticationEvent | OBS-2023-003 |
| PROC-IN-602 | DataIngestionRoutine | OBS-2023-004 |
| PROC-IN-603 | NetworkPacketCapture | OBS-2023-001 |
| PROC-IN-604 | PhysicalAccessLogEntry | OBS-2023-002 |

The data in Table 4.4 reveals the interdependencies between various processes. For instance, the `UserAuthenticationEvent` (`PROC-IN-601`) utilizes `OBS-2023-003` (the `DataIngestionRoutine` observation) as an input. This might imply that user authentication relies on data structures populated by the ingestion routine. Similarly, `ThermalCalibrationProcess` (`PROC-IN-600`) takes `OBS-2023-005` (a `PhysicalAccessLogEntry`) as input, perhaps verifying that a technician was physically present in the facility before allowing the calibration to proceed. These cross-references demonstrate the power of the ontology to model complex, real-world operational constraints.
