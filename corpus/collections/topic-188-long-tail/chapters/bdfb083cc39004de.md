# Chapter 4: Ontological Constraints for Process-Artifact Interoperability in Regulated Systems

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework governing the interaction between temporal processes and material artifacts within regulated digital ecosystems. It provides a rigorous specification of the axioms that bind observational events to their participants, temporal coordinates, and requisite input/output streams. The definitions and relational schemas presented herein are binding for all compliance reporting, data lineage verification, and system interoperability protocols. Adherence to these constraints ensures that audit trails maintain referential integrity and that process execution can be reconstructed with forensic precision. The following sections detail the implementation of these axioms, supported by normalized data tables that exemplify the required structure.

## 4.2 Observation with Participant Artifacts

### 4.2.1 Definition and Compliance Rationale

The foundational unit of auditability in any technical system is the observation, defined axiomatically as a process (`bfo:0000015`) that necessitates the participation of a specific artifact (`cco:Artifact`). This relationship, codified as `observation_with_participant`, asserts that a process cannot exist in a vacuum; it must be anchored to a physical or digital entity that acts as the agent or instrument of the observation. In the context of governance frameworks, this axiom prevents the logging of "orphaned" events—processes for which the responsible instrument or software component cannot be identified.

For instance, in a laboratory information management system (LIMS), a "Calibration Check" is a process. However, for this process to be valid, it must have a participant artifact—specifically, the "Spectrophotometer Device ID 400B." Without this linkage, the observation is non-compliant because the provenance of the measurement cannot be verified. The axiom ensures that every row in a process log is traceable back to an inventory entry or a registered digital agent.

### 4.2.2 Relational Implementation

The relational schema for this axiom enforces a strict dependency where the observation is identified by a unique primary key, and the class of the participant is explicitly defined. The table `t_observation_with_participant` serves as the central registry for all process-artifact pairings. It is critical that the `x` column accurately reflects the class of the process (e.g., `QualityControlAssay`), while the `id` serves as the immutable reference for downstream temporal and material dependency mapping.

## 4.3 Event Start Time Specification

### 4.3.1 Temporal Anchoring of Artifacts

To satisfy regulatory requirements for chronological sequencing, every artifact acting as a container for event data must be associated with a specific start time. The axiom `schemaorg_event_starttime` formalizes this by asserting that an artifact (`cco:Artifact`) possesses a property `sdg:hasEventStartTime` that references a specific observation process. This is distinct from the process merely "having" a time; rather, it is the scheduling artifact or log entry that holds the temporal reference to the process instance.

In practice, this separates the *schedule* from the *execution*. The "Schedule Artifact" (an instance of a calendar or log) contains the start time data, which points to the "Observation" (the actual process). This indirection allows for the auditing of discrepancies between planned times and actual execution times. For example, a `ScheduledMaintenanceLog` artifact may indicate a start time of 08:00, referencing the `PreventiveMaintenance` observation. If the actual process log shows a different timestamp, the compliance officer can immediately identify a deviation.

### 4.3.2 Relational Implementation

The schema for `t_schemaorg_event_starttime` utilizes a foreign key constraint to link the temporal artifact (`y`) back to the primary observation registry. This ensures that a start time cannot be recorded for a non-existent process. The column `x` denotes the class of the artifact holding the time data (e.g., `ScheduleEntry`), while `y` contains the `id` of the observation process defined in Section 4.2.

## 4.4 Process Output Provenance

### 4.4.1 Traceability of Generated Entities

The axiom `process_min_one_output` addresses the necessity of provenance by mandating that any process (`bfo:0000015`) must generate a minimum of one output. In a compliant system, a process that consumes resources without producing a recordable artifact is technically a null operation and often indicates a data loss or a failure in the capture mechanism. The output (`Y`) is treated as an observation or artifact in its own right, which must be registered within the system.

Consider a `DataProcessingPipeline`. The input might be raw data files, but the axiom requires that the output—perhaps a `ProcessedDataset`—be formally declared as a product of the pipeline. This output is subsequently treated as a participant artifact for other processes (e.g., a `ValidationCheck`). This chaining of outputs to inputs creates the "chain of custody" required for high-trust environments such as clinical trials or financial auditing.

### 4.4.2 Relational Implementation

The table `t_process_min_one_output` records the generative relationship. The column `x` identifies the class of the process performing the work (e.g., `AnalysisWorkflow`), and column `y` identifies the specific output artifact by referencing the `id` from the observation registry. This recursive structure—where an output in one row can be a participant in another—enables the construction of complex directed acyclic graphs (DAGs) representing system behavior.

## 4.5 Process Input Dependency

### 4.5.1 Resource Consumption and Prerequisites

The final constraint, `process_min_one_input`, complements the output axiom by requiring that every process consumes at least one input artifact. This axiom is critical for resource accounting and dependency analysis. It prevents the initiation of processes that lack necessary prerequisites, such as a calculation running without source data or a physical assay running without a required reagent.

In the context of the `SamplePreparation` process, the input might be a `RawStockSample`. The axiom formally links the process to this stock. If the stock is later found to be compromised, the dependency graph established by this table allows auditors to immediately identify all downstream processes (the "outputs") that may be tainted by the faulty input. This is the backbone of impact analysis in risk management frameworks.

### 4.5.2 Relational Implementation

The `t_process_min_one_input` table structurally mirrors the output table but enforces the inverse semantic relationship. Here, column `y` represents the artifact being consumed. It is essential that this artifact exists in the base registry (`t_observation_with_participant`) before it can be assigned as an input. The schema enforces this via the foreign key constraint, ensuring that no process can claim to consume a non-existent resource.
