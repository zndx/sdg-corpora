# Chapter 7: Ontological Constraints for Process Audit Trails

This chapter establishes the formal ontological framework required for mapping industrial process controls to compliant audit records. It defines the structural relationships between process entities, temporal events, and material artifacts within the governance layer. The definitions provided herein are binding for all data ingestion pipelines, ensuring that every logged event adheres to the strict constraints of the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). Implementers must ensure that relational mappings reflect these axioms to maintain data integrity during forensic reconstruction.

## 7.1 Observation with Participant Artifact

The foundational unit of the audit trail is the observation, defined here not merely as a data point, but as a processual entity that involves a specific participant. In accordance with Axiom 1, an observation is a subclass of `bfo:0000015` (Process) that necessarily possesses a participant restricted to the class `cco:Artifact`. This distinction is critical for governance frameworks: it segregates human-agent interactions from machine-state readings, ensuring that automated sensor logs are ontologically distinct from operator entries.

**Axiom 1 (observation_with_participant):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`
*   **Verbalization:** {X} is something that has participant artifact.

In practice, this constraint mandates that any record classified as an observation must be traceable to a physical hardware component or a distinct software object (artifact). This prevents "orphan" data entries where the provenance of the measurement cannot be established. For instance, a temperature reading is invalid unless it is explicitly linked to the specific thermocouple (artifact) that generated the signal.

Failure to resolve this link constitutes a critical data integrity failure, rendering the observation non-compliant with ISO 8000 data quality standards.

## 7.2 Event Start Time Specification

To establish a chronological sequence of events, the framework utilizes Axiom 2, which binds an artifact to a specific start time. This relationship is modeled through the `sdg:hasEventStartTime` property. Unlike simple timestamp columns, this approach treats the "start time" as a first-class entity that references a specific observation process. This reification allows the start time to carry metadata—such as the accuracy of the clock or the timezone logic—which is essential for cross-jurisdictional compliance reporting.

**Axiom 2 (schemaorg_event_starttime):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasEventStartTime some {Y:Class}`
*   **Verbalization:** {X} is something that has event start time {Y}.

The artifact {X} represents the container of the event (e.g., a batch record or a digital log file), while {Y} represents the observation process that marked the inception of the event. By constraining {Y} to reference an existing observation (via the foreign key), the system ensures that no event can be logged without a verified, timestamped trigger from a trusted artifact.

## 7.3 Process Output Verification

A core requirement of Good Manufacturing Practice (GMP) and similar regulatory frameworks is the verification that a process has produced the required output. Axiom 3 formalizes this by defining a process {X} that must have a minimum of one output {Y}. Crucially, the output {Y} is modeled as an observation with a participant artifact. This recursive structure implies that the "output" of a process is not merely a physical product, but the *recorded observation* of that product's creation or state change.

**Axiom 3 (process_min_one_output):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasOutput min 1 {Y:Class}`
*   **Verbalization:** {X} is a process.

This axiom functions as a validation gate. A process instance cannot be closed or marked as "complete" in the database unless at least one row exists in the output mapping table linking it to a valid observation. This enforces the "no output, no process" rule, preventing the logging of ghost processes that consume resources without generating auditable evidence.

This mechanism automatically triggers quality control alerts when data generation fails.

## 7.4 Process Input Validation

Complementary to output verification is the validation of process inputs. Axiom 4 defines a process {X} that requires a minimum of one input {Y}. Similar to the output axiom, the input {Y} is restricted to be an observation with a participant artifact. This structure models the dependency of processes on prior states or material inputs, creating a directed acyclic graph (DAG) of dependencies that is essential for root cause analysis.

**Axiom 4 (process_min_one_input):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasInput min 1 {Y:Class}`
*   **Verbalization:** {X} is a process.

By enforcing input constraints, the ontology prevents processes from initiating without prerequisite conditions being met. For example, a high-pressure filling process cannot begin unless an input observation confirms that the vessel pressure is at a safe baseline. This logic moves the validation from application-layer code to the database schema layer, making it tamper-evident.
