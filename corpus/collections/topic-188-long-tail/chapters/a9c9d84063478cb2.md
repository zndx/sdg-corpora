# Chapter 4: Ontological Constraints in Process Verification and Event Logging

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish rigorous audit trails within automated industrial environments. It addresses the necessity of defining precise relationships between processes, artifacts, and temporal events to ensure compliance with regulatory frameworks such as ISO 9001 and GMP. The text provides a granular examination of four primary axioms governing observation participation, event timing, and process input/output dependencies. By anchoring these definitions to specific relational schemas, the chapter establishes a deterministic method for verifying that every manufacturing or calibration event is substantiated by physical evidence and temporal data. The following sections detail the implementation of these constraints, ensuring that data integrity is maintained through referential consistency and existential validation.

## 4.2 Observation with Participant Artifact

### 4.2.1 Conceptual Definition

In the context of high-fidelity audit logging, an observation is not merely a passive recording of data but an active occurrence (bfo:Process) that necessitates the involvement of a specific physical entity. The axiom `observation_with_participant` posits that for any observation to be valid, it must be subclassed as a process that includes a participant artifact (cco:Artifact). This distinction is critical in environments where the provenance of a measurement is as important as the measurement itself. For instance, a temperature reading is invalid if it cannot be traced back to the specific sensor (the artifact) that generated the signal. This constraint prevents the logging of "orphan" data points that lack physical grounding.

The implementation of this axiom requires that the system enforces a mandatory relationship between the event log and the inventory registry of hardware components. It is insufficient to record a generic "Temperature Check"; the system must identify "Temperature Check performed by Thermocouple ID-458." This level of granularity supports forensic analysis and non-repudiation, ensuring that every data point in the system can be audited back to a specific device or material instance.

### 4.2.2 Relational Implementation

The relational schema for `t_observation_with_participant` serves as the foundational table for this ontology. The primary key (`id`) represents the unique identifier for the observation instance, while the column `x` denotes the class of the artifact participating in the process. In practice, this maps the observation to a specific type of hardware or material entity defined in the asset catalog.

The following table illustrates instances of observations where specific artifacts are the active participants. Note that the `x` value references the class or specific instance designation of the artifact involved in the process.

| id | x |
| :--- | :--- |
| OBS-2023-001 | SpadeThermocouple_SS_A1 |
| OBS-2023-002 | FiberglassTapeSensor_ST_B2 |
| OBS-2023-003 | HoseClampAssembly_Type4 |
| OBS-2023-004 | SurfaceMeasurementProbe_X5 |

**Table 4.1:** Observation instances linked to participant artifacts. The `id` column serves as the primary key, while `x` classifies the specific artifact involved in the bfo:Process.

### 4.2.3 Technical Context and Usage

Consider the deployment of series SS and ST spade thermocouples described in technical specifications. These sensors are sandwiched between thin shims of stainless steel or fiberglass tape. When an observation is recorded—such as a surface temperature measurement—the system must capture the fact that the artifact (e.g., `SpadeThermocouple_SS_A1`) was the participant. This is not merely a metadata tag; it is a structural requirement of the observation. If the artifact is removed or replaced, the observation ID associated with that specific artifact must be archived, and a new observation ID must be generated for the new artifact. This ensures that the historical record remains immutable and tied to the physical state of the equipment at the moment of the event.

## 4.3 Event Start Time Specification

### 4.3.1 Conceptual Definition

Temporal precision is a cornerstone of compliance reporting. The axiom `schemaorg_event_starttime` extends the definition of an artifact (cco:Artifact) to include a specific property: the event start time ({Y}). This formalism asserts that any event or process artifact must possess a defined temporal inception point. In regulated environments, the absence of a precise start time invalidates the compliance record, as it becomes impossible to establish a causal timeline or verify synchronization between disparate systems.

This axiom addresses the "when" of the process. While the previous section addressed the "what" (the participant artifact), this section anchors the artifact to a specific coordinate in time. This is particularly relevant for scheduled maintenance events, calibration sequences, or batch processing runs where the duration and initiation are subject to strict service level agreements (SLAs). The start time acts as a temporal anchor against which all subsequent process outputs and inputs are measured.

### 4.3.2 Relational Implementation

The schema `t_schemaorg_event_starttime` enforces a foreign key constraint linking the event to a valid observation. This ensures that a start time cannot exist in a vacuum; it must be attached to an observation that already involves a participant artifact. The column `y` contains the temporal data, typically formatted as an ISO 8601 string, representing the start time.

The table below demonstrates the linkage between specific event artifacts and their initiation timestamps, referencing the observations established in the previous section.

| id | x | y |
| :--- | :--- | :--- |
| EVT-2023-100 | CalibrationSequence_Alpha | 2023-10-27T06:00:00Z |
| EVT-2023-101 | SurfaceMeasurement_Run1 | 2023-10-27T06:05:12Z |
| EVT-2023-102 | HoseClampSecure_Op2 | 2023-10-27T06:15:00Z |
| EVT-2023-103 | DataLogging_Session_B | 2023-10-27T07:00:00Z |

**Table 4.2:** Event start times linked to observation artifacts. Column `y` represents the precise start time, while the foreign key relationship ensures the event is grounded in a valid observation (implied by the context of `x` mapping to the observation class).

### 4.3.3 Technical Context and Usage

Referencing the style of operational notices, such as those for athletic club events or physiotherapy appointments, the precision of the start time is paramount. Just as a physiotherapist appointment requires a specific date and time (e.g., "27 May 2014, 6:00pm") to be valid, an industrial calibration event must be timestamped to the second. In the example of `EVT-2023-100`, the start time `2023-10-27T06:00:00Z` indicates the exact moment the `CalibrationSequence_Alpha` commenced. This timestamp is used to correlate the event with external factors, such as ambient temperature shifts or power grid fluctuations, which may influence the observation results. The schema ensures that for every artifact `x` acting as an event, there is a non-null `y` value, enforcing data completeness.

## 4.4 Process Output Validation

### 4.4.1 Conceptual Definition

The axiom `process_min_one_output` introduces a cardinality constraint on process definitions. It asserts that any valid process (bfo:0000015) must generate a minimum of one output ({Y}). This is an existential quantification: a process that produces no output is, by definition, null or incomplete within the system logic. This constraint is vital for manufacturing and processing industries where the "yield" or "product" is the primary measure of process efficacy.

From a governance perspective, this axiom prevents the logging of "ghost processes"—operations that ostensibly ran but produced no tangible or digital result. If a milling operation runs, it must produce a milled part; if a data scrubbing process runs, it must produce a cleaned dataset. The output `Y` is treated as an artifact that is itself a participant in a subsequent observation, creating a chain of custody and transformation.

### 4.4.2 Relational Implementation

The relational table `t_process_min_one_output` records the relationship between a process instance and its resulting output artifact. The foreign key constraint linking `y` to `t_observation_with_participant` ensures that the output is a recognized entity within the system. This structure facilitates the tracking of "genealogy" for manufactured parts, where an output of one process becomes the input of another.

The following table details process instances and their corresponding outputs, ensuring that every process entry is associated with a valid artifact ID.

| :--- | :--- | :--- |
| PROC-OUT-501 | MillingOperation_BlockA | OBS-2023-005 |
| PROC-OUT-502 | ThermalTreatment_Cure | OBS-2023-006 |
| PROC-OUT-503 | QualityInspection_Visual | OBS-2023-007 |
| PROC-OUT-504 | DataExport_Log | OBS-2023-008 |

**Table 4.3:** Process instances mapped to their required outputs. The `y` column references the ID of the observation representing the output artifact, ensuring referential integrity.

### 4.4.3 Technical Context and Usage

In the context of a machining operation, the process `MillingOperation_BlockA` is defined by its transformation of a raw material. The system validates this process only when it detects the creation of `OBS-2023-005` (the milled block). If the process completes without the registration of this output artifact, the system flags a violation of the `process_min_one_output` axiom. This triggers an audit exception, requiring operator intervention to verify if the process failed or if the output was simply not scanned. This axiom mirrors the logic of an application form where a position (process) requires a qualified applicant (output); without the applicant, the application process is incomplete.

## 4.5 Process Input Verification

### 4.5.1 Conceptual Definition

Complementary to the output constraint is the axiom `process_min_one_input`. This axiom dictates that any process (bfo:0000015) must consume at least one input ({Y}). This constraint enforces the law of conservation of information and mass within the digital twin of the industrial environment. A process cannot create something from nothing; it requires resources, materials, or data streams to initiate and sustain activity.

This axiom is crucial for inventory management and resource traceability. By mandating the recording of inputs, the system creates a debit ledger for material consumption. It allows organizations to calculate yield ratios (Output Quantity / Input Quantity) and identify sources of waste or inefficiency. Furthermore, in regulated industries like pharmaceuticals, it ensures that the specific batch of raw materials used in a process is recorded, facilitating rapid recall procedures if defects are detected later.

### 4.5.2 Relational Implementation

The schema `t_process_min_one_input` maintains the structural integrity of the input chain. Similar to the output table, it uses a foreign key (`y`) to reference an observation of a participant artifact. This artifact represents the resource being consumed. The table ensures that for every process `x`, there is a corresponding input `y`.

The table below presents a log of process inputs, verifying that each operational step is substantiated by the consumption of a specific artifact.

| id | x | y |
| :--- | :--- | :--- |
| PROC-IN-601 | MillingOperation_BlockA | OBS-2023-009 |
| PROC-IN-602 | ThermalTreatment_Cure | OBS-2023-010 |
| PROC-IN-603 | QualityInspection_Visual | OBS-2023-011 |
| PROC-IN-604 | DataExport_Log | OBS-2023-012 |

**Table 4.4:** Process instances mapped to their required inputs. The `y` column references the observation ID of the input artifact, ensuring that material or data consumption is explicitly recorded.

### 4.5.3 Technical Context and Usage

Consider the `MillingOperation_BlockA` referenced in Section 4.4. For this process to be valid, it must consume `OBS-2023-009`, which represents the raw metal stock. The relationship between `PROC-IN-601` and `PROC-OUT-501` (both describing the same process `x`) provides a complete balance sheet: the process takes `OBS-2023-009` as input and yields `OBS-2023-005` as output. This dual validation (input and output) creates a closed loop, preventing the "magic" appearance of parts. It functions similarly to the "Qualified" checkbox on an employment application; the process (hiring) is contingent upon the input (qualified candidate). Without the input artifact, the process cannot legally or logically proceed within the governed framework.
