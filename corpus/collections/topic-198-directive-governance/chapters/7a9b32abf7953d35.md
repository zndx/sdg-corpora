# Governance Structures: Directive Information Content Entities and Regulatory Compliance

## Preamble

This chapter delineates the structural axioms governing directive information content entities within a formal compliance framework. It establishes the necessary conditions for the validity, enforcement, and verification of regulatory policies and requirements. Furthermore, it defines the scope of governance artifacts and the procedural requirements for attestation. The provisions herein are derived from the foundational ontology of directive governance and are intended to serve as a normative reference for system architects and compliance officers.

## 1. Foundational Directives and Basic Policy Structure

Accordingly, the fundamental unit of governance within the framework is the Directive Information Content Entity (ICE). This entity represents the informational realization of a rule, policy, or mandate. It does not, in and of itself, constitute an action; rather, it prescribes the conditions under which actions must occur. The axiom `policy_basic` asserts that any entity classified as a Policy is, by definition, a Directive ICE. This classification is not merely semantic but serves as the primary key for all subsequent governance relations.

For a directive to be recognized as a valid policy within the system, it must be explicitly instantiated as a subclass of `cco:DirectiveICE`. This ensures that all downstream enforcement mechanisms can trace their authority to a defined informational artifact. Without this explicit classification, a directive lacks the ontological status required to trigger compliance workflows. Consequently, the system rejects any governance object that does not meet this baseline criterion, ensuring that only formally recognized policies are subject to execution.

The following table enumerates specific policy classes that satisfy the `policy_basic` axiom. These entries represent distinct categories of governance directives, each mapped to a unique identifier for reference within the compliance database.

**Table 1.1: Basic Policy Classifications**

| id | x |
| :--- | :--- |
| pol_basic_001 | DataRetentionPolicy |
| pol_basic_002 | AccessControlDirective |
| pol_basic_003 | PhysicalSecurityStandard |
| pol_basic_004 | IncidentResponsePlan |
| pol_basic_005 | ChangeManagementProcedure |

In practice, the instantiation of `DataRetentionPolicy` as a Directive ICE mandates that the system treat the document not as general text, but as a binding governance object. This distinction is critical for maintaining the integrity of the compliance framework. It prevents the conflation of advisory documentation with mandatory directives.

## 2. Enforcement Obligations and Agent Assignment

For that reason, a directive that exists solely as an information content entity is insufficient to ensure compliance. The axiom `policy_min_one_enforcer` introduces the constraint that every Policy must be enforced by a minimum of one Enforcer. This enforcer may be a specific role, an automated system, or a designated organizational unit. The relationship `sdg:enforcedBy` is mandatory; a policy lacking a defined enforcer is considered "orphaned" and is non-binding within the operational environment.

This proposed action merely proposes to validate that the assignment of enforcement responsibility is explicit and singular at a minimum. It does not preclude the assignment of multiple enforcers for complex directives. However, the cardinality constraint (`min 1`) ensures that there is no ambiguity regarding accountability. If a policy is intended to restrict access to sensitive materials, the absence of a linked enforcer—such as a `SecurityOfficer` or an `AccessControlSystem`—renders the policy unenforceable.

The relational structure below illustrates the binding between specific policy classes and their requisite enforcer classes. Note that the `y` column represents the class of the entity responsible for enforcement, ensuring that the *type* of enforcer is appropriate for the *type* of policy.

**Table 2.1: Policy-to-Enforcer Mappings**

| id | x | y |
| :--- | :--- | :--- |
| pol_enf_001 | DataRetentionPolicy | RecordsManagementManager |
| pol_enf_002 | AccessControlDirective | IdentityManagementSystem |
| pol_enf_003 | PhysicalSecurityStandard | FacilitySecurityOfficer |
| pol_enf_004 | IncidentResponsePlan | IncidentResponseTeam |
| pol_enf_005 | ChangeManagementProcedure | ChangeAdvisoryBoard |

The implication of this structure is significant. In the case of `AccessControlDirective`, the enforcement is delegated to an `IdentityManagementSystem`. This indicates that the enforcement mechanism is automated. Conversely, the `PhysicalSecurityStandard` is enforced by a `FacilitySecurityOfficer`, implying human enforcement. This distinction allows the governance framework to route compliance alerts to the appropriate subsystem—whether that be a ticketing queue for human agents or an API endpoint for automated controllers.

## 3. Scope Limitations: Governance of Artifacts

Furthermore, the framework imposes strict limitations on the scope of governance to prevent regulatory overreach. The axiom `policy_only_governs_artifacts` stipulates that a Policy may only govern entities that are classified as Artifacts (`cco:Artifact`). An Artifact, in this context, is defined as a discrete, durable object produced or acted upon by a process—this includes digital documents, source code, configuration files, and physical logs.

This restriction is not a ''significant regulatory action'' in the sense of expanding control, but rather a boundary definition. It ensures that policies do not attempt to govern abstract concepts or transient events directly. Instead, policies govern the *artifacts* that result from or record those events. For example, a `SourceCodeControlPolicy` governs the code repository (the artifact), not the act of coding itself (the process). By anchoring governance to artifacts, the framework facilitates auditability; one cannot audit an abstract thought, but one can audit the artifact that embodies it.

The following table presents policy classes that are explicitly constrained to govern artifacts. These entries demonstrate the application of the universal restriction (`only`) inherent in the axiom.

**Table 3.1: Artifact-Centric Policy Scopes**

| id | x |
| :--- | :--- |
| pol_art_001 | DocumentClassificationStandard |
| pol_art_002 | SourceCodeControlPolicy |
| pol_art_003 | ConfigurationBaselinePolicy |
| pol_art_004 | AuditLogRetentionRule |
| pol_art_005 | EvidenceStorageProtocol |

Consider the `DocumentClassificationStandard`. This policy governs artifacts such as PDFs, Word documents, and emails. It does not govern the *authors* of the documents, but rather the *documents themselves* as they exist within the storage system. This separation of concerns is essential for applying metadata tags, encryption requirements, and retention schedules to the objects under management.

## 4. Verification Mechanisms and Requirements

Accordingly, while enforcement ensures the active application of a policy, verification ensures that the policy's conditions are being met. The axiom `requirement_min_one_verification` applies to Requirements, which are a specific subtype of Directive ICE. A Requirement differs from a general Policy in that it stipulates a specific criterion that must be satisfied. To validate this satisfaction, the Requirement must be linked to at least one Verification method or entity via the `sdg:verifiedBy` property.

This distinction is critical for audit readiness. A policy might state "data must be encrypted," which is a general directive. A requirement derived from that policy might state "database fields containing PII must use AES-256 encryption." The verification of this requirement could be a script (`ConfigurationScanner`) or a manual review (`SecurityAuditor`). The axiom mandates that for every requirement, there exists a defined, executable path to verification.

The table below details specific requirement classes and the classes of verifiers responsible for confirming compliance. This structure ensures that verification responsibilities are codified alongside the requirements themselves.

**Table 4.1: Requirement-to-Verifier Assignments**

| id | x | y |
| :--- | :--- | :--- |
| req_ver_001 | EncryptionRequirement | CryptographicModuleValidator |
| req_ver_002 | AuditLogRequirement | LogAggregationTool |
| req_ver_003 | ResilienceRequirement | PenetrationTestSuite |
| req_ver_004 | PrivacyRequirement | DataDiscoveryScanner |
| req_ver_005 | AvailabilityRequirement | UptimeMonitorService |

For instance, the `EncryptionRequirement` is verified by a `CryptographicModuleValidator`. This represents a technical verification, likely automated. In contrast, a `ResilienceRequirement` might be verified by a `PenetrationTestSuite`, which involves a more complex, potentially periodic process. By defining these relationships in the ontology, the system can automatically generate verification checklists based on the active requirements within a given compliance domain.

## 5. Attestation Processes and Signatory Authority

Finally, the framework addresses the human element of compliance through the attestation process. The axiom `attestation_min_one_signer` defines an Attestation as a Process (`bfo:0000015`) that must be signed by a minimum of one Person (`cco:Person`). Attestation represents the formal declaration that a set of directives has been reviewed, understood, and adhered to. Unlike a policy, which is an information entity, an attestation is a *process* that occurs over time and culminates in a signature event.

This process is subject to strict constraints to maintain legal and regulatory validity. An attestation cannot be generated by a system alone; it requires the agency of a Person. This ensures that accountability is ultimately vested in individuals with the authority to accept responsibility for the state of compliance. The `sdg:signedBy` property links the attestation process to the specific person or persons providing their endorsement.

The following table outlines the attestation processes defined within the framework. Note that while the table lists the process class (`x`), the axiom implies the existence of a foreign key relationship to a `Person` instance in a broader database schema.

**Table 5.1: Attestation Process Definitions**

| id | x |
| :--- | :--- |
| att_sig_001 | AnnualComplianceAttestation |
| att_sig_002 | SecurityAwarenessAttestation |
| att_sig_003 | CodeOfConductAcknowledgment |
| att_sig_004 | PolicyReviewAttestation |
| att_sig_005 | IncidentReportingAcknowledgment |

The `AnnualComplianceAttestation` serves as a primary example. This process typically involves the review of all applicable policies and requirements for the fiscal year. The process is not considered complete until the `signedBy` property is populated with a valid `Person` identifier, such as a Chief Information Security Officer (CISO). This requirement prevents the generation of "ghost attestations"—compliance records that exist without human authorization.
