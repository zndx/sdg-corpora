# Chapter 4: Ontological Formalization of Uncertainty in Evidence Aggregation

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for quantifying uncertainty within the Unified Evidence Aggregation (UEA) protocol. It defines the structural requirements for representing belief functions as Information Content Entities (ICEs) within a compliant audit environment. The provisions herein detail the axiomatic mapping of Mass Functions to their respective Frames of Discernment and Focal Elements, ensuring that all probabilistic and evidentiary data are anchored to a rigorously defined schema. This framework is mandated for use in high-assurance reporting where binary logic is insufficient to capture the nuance of incomplete evidence sets.

## 4.2 The Mass Function as a Descriptive ICE

In the context of the UEA protocol, a Mass Function is not merely a mathematical distribution but is formally classified as a Descriptive Information Content Entity (`cco:DescriptiveICE`). This classification mandates that any entity functioning as a Mass Function must be a distinct, identifiable information artifact that stands in relation to the reality it describes. The axiom `mass_function_equiv_frame_and_assignment` provides the necessary and sufficient conditions for an entity to be recognized as such within the system.

According to the axiom, a Class `X` (the Mass Function) is equivalent to the intersection of three constraints:
1.  It is a `cco:DescriptiveICE`.
2.  It bears the relationship `sdg:overFrameOfDiscernment` to some Class `Y`.
3.  It bears the relationship `sdg:assignsMassTo` to some Class `Z`.

This structure ensures that a Mass Function cannot exist in a vacuum; it is inextricably bound to the domain of its definition (the Frame) and the specific hypotheses to which it allocates belief (the Focal Elements). In practice, this means that an auditor cannot define a "belief score" without explicitly referencing the set of possible outcomes (the Frame) and the specific subset of those outcomes being evaluated (the Focal Element).

### 4.2.1 Operational Definition

For the purposes of compliance reporting, the Mass Function (`X`) represents the basic probability assignment (BPA). Unlike traditional probability, which assigns likelihood to singletons, the Mass Function assigns "mass" to sets of hypotheses. The ontology captures this by requiring that `X` must `assignMassTo` a target `Z`. The target `Z` is typically a subset of the power set of the Frame `Y`.

*Example:* Consider an audit of a server's authentication status. The auditor cannot definitively prove the server is secure but has evidence suggesting it is likely so. The Mass Function is the information entity describing this distribution of belief. It is not the number 0.7 itself, but the structured object containing that number, the context of the server, and the definition of "secure."

## 4.3 Frames of Discernment

The Frame of Discernment, denoted as Class `Y` in the axiom, represents the exhaustive set of mutually exclusive hypotheses relevant to a specific audit query. The relationship `sdg:overFrameOfDiscernment` is a critical constraint that links the Mass Function to its operational domain.

The Frame of Discernment (`Y`) must be defined such that every possible state of the system under observation is represented by exactly one element within the Frame (or a union thereof). In the relational schema, the presence of `y` in the `t_mass_function_equiv_frame_and_assignment` table enforces that every Mass Function is explicitly scoped. This prevents category errors where a Mass Function defined for "Network Status" is erroneously applied to "Financial Compliance."

### 4.3.1 Governance Requirements

Regulatory guidelines stipulate that the Frame of Discernment must be established prior to the collection of evidence. Defining the Frame *post hoc* compromises the integrity of the Mass Function and renders the audit report non-compliant. The ontology enforces this by treating the Frame `Y` as a necessary class filler for the Mass Function `X`.

*Example:* In a structural integrity audit, the Frame of Discernment (`Y`) might be the class `StructuralHypothesis`, containing instances such as `Intact`, `Fatigued`, and `Failed`. The Mass Function (`X`) for a specific bridge component is defined *over* this Frame.

## 4.4 Mass Assignment and Focal Elements

The final component of the axiom involves the relationship `sdg:assignsMassTo`, which links the Mass Function (`X`) to a specific target Class `Z`. Class `Z` represents the Focal Element—the subset of the Frame to which a non-zero mass is assigned.

In evidence theory, a Focal Element is any subset of the Frame of Discernment that has a mass greater than zero assigned to it. The ontology treats `Z` as a Class to allow for the categorization of types of focal elements (e.g., `SingletonHypothesis` vs `CompositeHypothesis`). The Mass Function `X` acts as the container for these assignments.

### 4.4.1 Evidence Aggregation Rules

When multiple Mass Functions are combined (e.g., aggregating evidence from two different auditors), the resulting entity must still satisfy the axiom `mass_function_equiv_frame_and_assignment`. The aggregated Mass Function will be a new instance of `X`, operating over the same Frame `Y`, but assigning mass to potentially new, composite Focal Elements `Z` resulting from the intersection of the original evidence sets.

*Example:* Auditor A assigns mass to `Hypothesis_A`. Auditor B assigns mass to `Hypothesis_B`. The aggregated Mass Function assigns mass to the intersection `Hypothesis_A AND Hypothesis_B`. The ontology requires that this intersection be a recognized Class `Z` within the system's knowledge graph.

## 4.5 Relational Implementation of the Axiom

To enforce the axiom `mass_function_equiv_frame_and_assignment` within the audit database, the following relational schema is utilized. This table acts as the registry for all valid Mass Function definitions, ensuring that every entry corresponds to a valid Descriptive ICE that is correctly bound to a Frame and a Target.

The table `t_mass_function_equiv_frame_and_assignment` serves as the primary validation constraint. The `id` column provides a unique identifier for the specific Mass Function class or instance. The `x` column references the Mass Function itself. The `y` column enforces the link to the Frame of Discernment, and the `z` column enforces the link to the Focal Element.

**Table 4.1: Axiomatic Validation of Mass Functions**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `MF-REG-001` | `AccessControlMassFunction` | `AccessControlHypothesis` | `AuthorizedAccess` |
| `MF-REG-002` | `AccessControlMassFunction` | `AccessControlHypothesis` | `UnauthorizedAccess` |
| `MF-REG-003` | `NetworkStatusMassFunction` | `NetworkStateHypothesis` | `OperationalState` |
| `MF-REG-004` | `NetworkStatusMassFunction` | `NetworkStateHypothesis` | `DegradedState` |
| `MF-REG-005` | `CryptoComplianceMassFunction` | `KeyStrengthHypothesis` | `AdequateKeyLength` |
| `MF-REG-006` | `CryptoComplianceMassFunction` | `KeyStrengthHypothesis` | `InsufficientKeyLength` |

*Note on Table 4.1:* The rows above illustrate the binding of specific Mass Functions (`x`) to their respective Frames (`y`) and the specific Focal Elements (`z`) they address. For instance, `MF-REG-001` and `MF-REG-002` demonstrate that a single Mass Function class (`AccessControlMassFunction`) may assign mass to multiple distinct Focal Elements (`AuthorizedAccess`, `UnauthorizedAccess`) within the same Frame.

## 4.6 Registry of Focal Element Definitions

To support the foreign key constraints implied by the `z` column in the primary axiom table, a registry of defined Focal Elements is maintained. This ensures that any target of a mass assignment is a pre-validated class within the ontology. The following table details the specific classes utilized as Focal Elements in the previous section, providing their semantic definitions and hierarchical lineage.

**Table 4.2: Focal Element Class Registry**

| focal_element_id | class_name | definition | parent_frame |
| :--- | :--- | :--- | :--- |
| `FE-001` | `AuthorizedAccess` | The state where a subject successfully authenticates and possesses valid privileges for the requested object. | `AccessControlHypothesis` |
| `FE-002` | `UnauthorizedAccess` | The state where a subject attempts access but lacks valid authentication or privileges. | `AccessControlHypothesis` |
| `FE-003` | `OperationalState` | The network component is functioning within defined throughput and latency parameters. | `NetworkStateHypothesis` |
| `FE-004` | `DegradedState` | The network component is functional but operating outside optimal parameters (e.g., high latency). | `NetworkStateHypothesis` |
| `FE-005` | `AdequateKeyLength` | The cryptographic key length meets or exceeds the minimum bit-strength defined by policy (e.g., $\ge$ 256 bits). | `KeyStrengthHypothesis` |
| `FE-006` | `InsufficientKeyLength` | The cryptographic key length falls below the minimum bit-strength defined by policy. | `KeyStrengthHypothesis` |

*Note on Table 4.2:* This registry provides the semantic grounding for the `z` values found in Table 4.1. The `parent_frame` column explicitly maps the Focal Element back to the Frame of Discernment (`y`), ensuring referential integrity across the audit dataset.

## 4.7 Compliance Verification Protocol

Auditors are required to verify that all evidence entries in the final report correspond to entries in the `t_mass_function_equiv_frame_and_assignment` table. Any evidence quantification that lacks a corresponding entry in this table is considered structurally invalid under the UEA protocol.

The verification process involves the following steps:
1.  **Identification:** Extract the Mass Function identifier from the evidence log.
2.  **Validation:** Query `t_mass_function_equiv_frame_and_assignment` using the identifier.
3.  **Consistency Check:** Ensure that the Frame of Discernment referenced in the evidence log matches the `y` value in the table.
4.  **Assignment Check:** Ensure that the hypothesis being evaluated matches the `z` value in the table.

Failure to pass any of these checks results in a "Schema Violation" error, necessitating a review of the evidence collection methodology.
