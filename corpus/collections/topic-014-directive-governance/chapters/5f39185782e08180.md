# Chapter 4: Ontological Formalization of Process Anomalies and Metric Governance

## 4.1 Scope and Preamble

This chapter delineates the structural framework for governing operational anomalies, metric emissions, and alert states within high-frequency industrial data environments. The content is grounded in the axiomatic requirements of the BFO (Basic Formal Ontology) and CCO (Common Core Ontologies) upper-level structures, specifically addressing the intersection of descriptive information content entities (ICE) and processual observations. The objective is to provide a deterministic mapping between ontological constraints and relational schema implementations, ensuring that data integrity is maintained during the ingestion of telemetry, the emission of metrics, and the subsequent triggering of compliance alerts. The following sections detail five distinct axioms, providing verbalized definitions, relational mappings, and instance-level data consistent with the rigorous standards of technical audit documentation.

## 4.2 Basic Outlier Claims

### 4.2.1 Conceptual Definition
The foundational unit of observation in any governance framework is the Basic Outlier Claim. Formally, this entity is defined as a subclass of the `cco:DescriptiveICE`. In the context of real-time systems, a DescriptiveICE serves as a container for information that is about some other entity—in this case, a deviation from an expected norm. The Basic Outlier Claim does not inherently carry complex metadata regarding its causality or attributes; rather, it asserts the existence of a detectable anomaly. This distinction is critical for audit trails, as it separates the raw assertion of an event from the rich attribution that may follow during forensic analysis.

### 4.2.2 Relational Implementation
The persistence of a Basic Outlier Claim is managed through the `t_outlier_claim_basic` table. The structure is intentionally minimalistic, reflecting the axiom `Class: {X:Class} SubClassOf: cco:DescriptiveICE`. The primary key (`id`) serves as the unique identifier for the information content entity, while the column `x` represents the specific class or type of the claim being instantiated. This structure allows for high-velocity ingestion of anomaly flags without the overhead of joining complex attribute tables at the moment of detection.

**Table 4.1: Basic Outlier Claim Instances**

| id | x |
| :--- | :--- |
| `oc_basic_001` | `PressureSpikeEvent` |
| `oc_basic_002` | `FlowRateDeviation` |
| `oc_basic_003` | `TemperatureExcursion` |
| `oc_basic_004` | `ViscosityAnomaly` |

### 4.2.3 Operational Context
In a hydraulic monitoring system, for instance, the `PressureSpikeEvent` represents a raw signal processing output where the observed pressure exceeds a defined threshold. The claim itself is a static information entity stating "a spike occurred." It does not yet describe the magnitude, duration, or the specific sensor involved. This granularity ensures that the base ontology remains decoupled from the specific dimensional analysis that characterizes the event in higher-order processing.

## 4.3 Attributed Outlier Claims

### 4.3.1 Conceptual Definition
While basic claims establish the presence of an anomaly, governance frameworks require detailed context to facilitate automated response and regulatory reporting. The Attributed Outlier Claim axiom extends the basic concept by imposing a cardinality constraint: `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}`. This verbalizes to the assertion that {X} is a descriptive information content entity that possesses a minimum of one attribute {Y}. In this schema, the attribute {Y} is modeled as a reference to an alerting entity, creating a tight coupling between the observation of the anomaly and the system's reaction to it.

### 4.3.2 Relational Implementation
The `t_outlier_claim_min_one_attribute` table enforces the requirement that no outlier claim exists without at least one associated attribute. The schema defines a foreign key constraint where the attribute column `y` must reference a valid identifier in the `t_alert_triggered_by` table. This design enforces referential integrity, ensuring that every claim is substantiated by a corresponding trigger event or alert state. The primary key (`id`) remains the claim identifier, `x` holds the claim class, and `y` holds the identifier of the attribute (the alert).

**Table 4.2: Attributed Outlier Claim Instances**

| id | x | y |
| :--- | :--- | :--- |
| `oc_attr_101` | `CriticalPressureSpike` | `alert_trig_01` |
| `oc_attr_102` | `LowFlowRateAlert` | `alert_trig_02` |
| `oc_attr_103` | `HighViscosityEvent` | `alert_trig_03` |

### 4.3.3 Operational Context
Consider the `CriticalPressureSpike` (`oc_attr_101`). This is not merely a record that pressure increased, but a structured entity linking the event to `alert_trig_01`. This linkage implies that the outlier claim is "attributed" by the specific alert mechanism that fired. In compliance scenarios, this distinction is vital: it differentiates between a logged statistical deviation and a deviation that triggered a specific control action or notification workflow.

## 4.4 Alert Triggering Mechanisms

### 4.4.1 Conceptual Definition
The Alert Triggering Mechanism represents the processual aspect of the ontology, defined by the axiom `Class: {X:Class} SubClassOf: bfo:0000015, sdg:triggeredByMetric some {Y:Class}`. Here, `bfo:0000015` refers to a "Process" or an occurrent entity. The verbalization states that {X} is a process (the alert) that is triggered by a metric {Y}. This establishes a causal chain where a metric (often a value derived from a descriptive ICE) initiates a processual change in the system state—the triggering of an alert.

### 4.4.2 Relational Implementation
The `t_alert_triggered_by` table captures this dynamic relationship. The column `x` denotes the alert process class, while `y` denotes the metric or claim instance that served as the trigger. The schema includes a foreign key constraint linking `y` back to the `t_outlier_claim_min_one_attribute` table. This circular reference (Claim references Alert, Alert references Claim) models a closed-loop verification system: the claim is attributed by the alert, and the alert is substantiated by the claim. This loop is essential for root-cause analysis in audit logs, preventing "orphan" alerts that cannot be traced back to a specific descriptive claim.

**Table 4.3: Alert Triggered By Instances**

| id | x | y |
| :--- | :--- | :--- |
| `alert_trig_01` | `EmergencyShutdownProcess` | `oc_attr_101` |
| `alert_trig_02` | `FlowControlAdjustment` | `oc_attr_102` |
| `alert_trig_03` | `QualityControlHold` | `oc_attr_103` |

### 4.4.3 Operational Context
In the instance `alert_trig_01`, the process `EmergencyShutdownProcess` is triggered by the metric or claim `oc_attr_101`. This aligns with industrial safety protocols where a specific descriptive claim (e.g., "Pressure exceeded 140 Bar") necessitates an immediate processual response (e.g., "Initiate Shutdown"). The table structure ensures that the audit trail captures not just the data point, but the specific workflow process that it instantiated.

## 4.5 Metric Emission Subclasses

### 4.5.1 Conceptual Definition
To understand the origin of the metrics that trigger alerts, we must define the Metric Emission Subclass. This axiom is expressed as `Class: {X:Class} SubClassOf: bfo:0000015, sdg:emitsMetric some {Y:Class}`. It verbalizes that {X} is a process (a data source or a computational pipeline) that emits a metric {Y}. This concept is fundamental to data lineage, tracing the flow of information from the physical sensor or computational process through to the descriptive information content entity that eventually triggers alerts.

### 4.5.2 Relational Implementation
The `t_metric_emission_subclass` table documents the source of the metrics. The column `x` identifies the emitting process (e.g., a specific sensor loop or a data mining algorithm), while `y` identifies the metric or claim that is produced. The foreign key constraint directs `y` to the `t_outlier_claim_min_one_attribute` table, reinforcing that the output of an emission process is a fully attributed, structured claim ready for consumption by the alerting subsystem.

**Table 4.4: Metric Emission Subclass Instances**

| id | x | y |
| :--- | :--- | :--- |
| `emit_proc_01` | `MainLineSensorLoop` | `oc_attr_101` |
| `emit_proc_02` | `SecondaryFlowAggregator` | `oc_attr_102` |
| `emit_proc_03` | `ViscosityAnalysisJob` | `oc_attr_103` |

### 4.5.3 Operational Context
The `MainLineSensorLoop` (`emit_proc_01`) represents a continuous process reading pressure transducers. It emits the metric `oc_attr_101`. By mapping the emission process to the resulting claim, the framework provides a complete chain of custody: from the physical process (`MainLineSensorLoop`) to the informational output (`CriticalPressureSpike`) to the control response (`EmergencyShutdownProcess`). This level of detail is required for high-stakes audit reports, such as those investigating safety failures or regulatory compliance breaches.

## 4.6 Basic Aggregations

### 4.6.1 Conceptual Definition
The final concept in this chapter is the Basic Aggregation. Defined by `Class: {X:Class} SubClassOf: cco:DescriptiveICE`, this entity represents summarized or synthesized data points. Unlike the specific outlier claims which detail individual deviations, aggregations provide the statistical context—means, medians, totals—against which outliers are defined. While the ontology classifies it simply as a descriptive information content entity, its operational role is to serve as the baseline or the "norm" in governance frameworks.

### 4.6.2 Relational Implementation
The `t_aggregation_basic` table stores these summary entities. Like the basic outlier claim table, it consists of an `id` and the class `x`. This simplicity reflects the role of the aggregation as a high-level reference object. In a data warehousing context, these rows might represent the pre-calculated results of batch jobs (e.g., "Daily Average Pressure") that are used to calibrate the real-time alerting thresholds defined in the previous sections.

**Table 4.5: Basic Aggregation Instances**

| id | x |
| :--- | :--- |
| `agg_basic_001` | `HourlyPressureMean` |
| `agg_basic_002` | `DailyFlowMedian` |
| `agg_basic_003` | `WeeklyViscosityMax` |
| `agg_basic_004` | `MonthlyTemperatureStdDev` |

### 4.6.3 Operational Context
Aggregations such as `HourlyPressureMean` (`agg_basic_001`) are essential for distinguishing between signal noise and significant process anomalies. A `PressureSpikeEvent` (Section 4.2) is only meaningful when compared against a `HourlyPressureMean`. The ontology treats these as distinct classes of descriptive entities, allowing the governance system to query "all outliers deviating from Aggregation X" without conflating the observation with the baseline.
