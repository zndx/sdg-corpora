# Chapter 7: Ontological Frameworks for Anomaly Detection in Automated Compliance Systems

This chapter delineates the ontological mapping required for the persistence of anomaly detection events within a relational database management system (RDBMS), specifically tailored for high-frequency trading compliance environments. It addresses the structural derivation of OWL axioms into SQL-compliant schemas, ensuring referential integrity across descriptive entities and processual triggers. The following sections provide a comprehensive analysis of five core axiom sets, defining the logical constraints for outlier claims, alert mechanisms, metric emissions, and data aggregations. These definitions are foundational for constructing audit-ready data architectures that support both real-time surveillance and retrospective forensic analysis.

## 1. Basic Outlier Claims

### 1.1 Conceptual Definition
The foundational unit of audit evidence in any data-driven compliance framework is the Outlier Claim. Under the axiom `outlier_claim_basic`, we define a Class {X} as a subclass of `cco:DescriptiveICE` (Information Content Entity). In the context of the Common Core Ontologies (CCO), a DescriptiveICE is an entity that generically depends on some other entity or entities for its existence, typically serving as a proposition, statement, or description about the world.

In practical terms, a Basic Outlier Claim represents a raw, unelaborated assertion of deviation from a baseline norm. It does not, in this basic form, carry the specific attributes required for immediate adjudication but serves as the primary key for the observation. This aligns with the "Big Data Analytics" paradigm where initial data extraction (`Estrarre Valore Dai Dati`) involves identifying these raw signals before they are enriched with context.

### 1.2 Relational Implementation
The projection of this axiom into a relational schema isolates the identity of the claim. The primary key (`id`) ensures uniqueness of the observation, while the column `x` instantiates the specific class of the descriptive entity.

The following table embodies the `outlier_claim_basic` axiom. The primary key is `id`, which uniquely identifies the claim instance. The column `x` represents the class of the descriptive information content entity (the Outlier Claim).

| id | x |
| :--- | :--- |
| `oc_basic_001` | `PriceDeviationClaim` |
| `oc_basic_002` | `LatencyAnomalyClaim` |
| `oc_basic_003` | `SequenceViolationClaim` |
| `oc_basic_004` | `VolumeSpikeClaim` |
| `oc_basic_005` | `CrossMarketDiscrepancy` |

## 2. Attributed Outlier Claims

### 2.1 Conceptual Definition
While basic claims identify the existence of an anomaly, regulatory frameworks such as 11 NYCRR require that observations be substantiated by specific attributes. The axiom `outlier_claim_min_one_attribute` posits that Class {X} (the Outlier Claim) is a `DescriptiveICE` that must possess an attribute set (`sdg:hasAttributeSet`) with a minimum cardinality of 1 for Class {Y}.

This structure enforces the requirement that an outlier claim cannot exist in a vacuum; it must be anchored to at least one defining characteristic or attribute set. In a compliance context, this prevents the logging of "false positive" noise without supporting data vectors. The attribute set {Y} functions as the evidence packet, containing the specific metrics (e.g., timestamp, user ID, transaction value) that triggered the initial classification.

### 2.2 Relational Implementation
The schema for `t_outlier_claim_min_one_attribute` introduces a foreign key constraint that binds the attribute {Y} to an external trigger mechanism. This design ensures that the attributes defining the claim are intrinsically linked to the alert logic that surfaced them.

The following table embodies the `outlier_claim_min_one_attribute` axiom. The primary key is `id`. The column `x` is the outlier claim class, and `y` is the attribute set class. The foreign key constraint on `y` references `t_alert_triggered_by(id)`, establishing a dependency where the attribute is validated or triggered by a specific alert process.

| id | x | y |
| :--- | :--- | :--- |
| `oc_attr_001` | `HighFrequencyTradeClaim` | `alert_trig_001` |
| `oc_attr_002` | `SuspiciousIPClaim` | `alert_trig_002` |
| `oc_attr_003` | `LimitBreachClaim` | `alert_trig_003` |
| `oc_attr_004` | `AfterHoursAccessClaim` | `alert_trig_004` |

## 3. Alert Triggering Mechanisms

### 3.1 Conceptual Definition
The operationalization of a claim occurs via the Alert Trigger. Defined by the axiom `alert_triggered_by`, Class {X} is a subclass of `bfo:0000015` (a Process) that is triggered by a metric {Y} (`sdg:triggeredByMetric`). The Basic Formal Ontology (BFO) defines a process as an entity that unfolds in time and possesses temporal parts.

In this framework, the Alert Trigger is the active process—often a software agent or database procedure—that evaluates incoming data streams against defined thresholds. The relationship `triggeredByMetric` establishes the causal link: the process executes only when the specific metric conditions {Y} are met. This mirrors the logic found in occupational health monitoring (e.g., "Implementing Effective Hearing Conservation Programs"), where a biological process (hearing loss) triggers a clinical administrative process. Here, a data process triggers a compliance administrative process.

### 3.2 Relational Implementation
The relational schema for `t_alert_triggered_by` captures the dynamic nature of this process. The table links the specific alert process {X} to the metric {Y} that initiated it. Notably, the schema enforces a recursive integrity constraint: the metric {Y} must correspond to an existing Attributed Outlier Claim.

The following table embodies the `alert_triggered_by` axiom. The primary key is `id`. The column `x` represents the alert process class, and `y` represents the metric class that triggered the process. The foreign key constraint on `y` references `t_outlier_claim_min_one_attribute(id)`, ensuring that the triggering metric is a valid, attributed claim.

| id | x | y |
| :--- | :--- | :--- |
| `alert_trig_001` | `RealTimeThresholdProcess` | `oc_attr_001` |
| `alert_trig_002` | `GeoLocationValidationProcess` | `oc_attr_002` |
| `alert_trig_003` | `ExposureLimitCheckProcess` | `oc_attr_003` |
| `alert_trig_004` | `SessionTimeAuditProcess` | `oc_attr_004` |

## 4. Metric Emission Subclasses

### 4.1 Conceptual Definition
To close the loop on the audit trail, one must identify the source of the metrics. The axiom `metric_emission_subclass` defines Class {X} (a Process) as an entity that emits a metric {Y} (`sdg:emitsMetric`). This distinguishes the *source* process (e.g., a market data feed handler) from the *trigger* process (the alert logic).

The emission process is responsible for the raw generation of data points. In a consolidated summary of insurance regulations or banking standards, the provenance of data is paramount. By defining the emission process as a distinct BFO Process, the ontology allows auditors to trace a metric back to its origin system, differentiating between system-generated metrics (e.g., price feeds) and user-generated metrics (e.g., manual trade entries).

### 4.2 Relational Implementation
The schema `t_metric_emission_subclass` links the emission process to the metric it produces. The foreign key constraint ensures that the emitted metric {Y} is registered within the system as an Attributed Outlier Claim, thereby enforcing that all emitted metrics of interest are captured as potential claims.

The following table embodies the `metric_emission_subclass` axiom. The primary key is `id`. The column `x` is the emission process class, and `y` is the metric class emitted. The foreign key constraint on `y` references `t_outlier_claim_min_one_attribute(id)`, ensuring the emitted metric maps back to a specific outlier claim instance.

| id | x | y |
| :--- | :--- | :--- |
| `emit_001` | `MarketDataFeedProcessor` | `oc_attr_001` |
| `emit_002` | `AccessLogParser` | `oc_attr_002` |
| `emit_003` | `OrderBookEngine` | `oc_attr_003` |
| `emit_004` | `AuthenticationService` | `oc_attr_004` |

## 5. Basic Aggregations

### 5.1 Conceptual Definition
Finally, the ontology must account for aggregated data, which forms the baseline against which outliers are measured. The axiom `aggregation_basic` defines Class {X} as a `cco:DescriptiveICE`. Unlike the outlier claim, which describes a specific event, the aggregation describes a statistical summary (e.g., daily volume, moving averages) derived from a population of events.

Aggregations are "Descriptive" in the strictest sense; they are information content entities that describe the state of a system over a duration. In audit reports, these serve as the control groups. For instance, to prove that a "VolumeSpikeClaim" is valid, one must reference the "DailyVolumeAverage" aggregation.

### 5.2 Relational Implementation
The schema `t_aggregation_basic` is structurally simple but semantically vital. It catalogs the various types of aggregations available to the system for baseline comparison.

The following table embodies the `aggregation_basic` axiom. The primary key is `id`, and `x` is the aggregation class (a type of DescriptiveICE).

| `agg_002` | `TotalValueTraded` |
| `agg_003` | `UserSessionDurationMean` |
