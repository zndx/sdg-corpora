# Chapter 4: Ontological Structures for Operational Risk Monitoring

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish a rigorous audit trail for operational risk events within high-frequency trading environments. The definitions provided herein align with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that all descriptive information content entities (ICE) are anchored to verifiable processes and metrics. The following sections introduce five core axioms governing the classification of outlier claims, the emission of metrics, and the triggering of automated alerts, supported by relational schemas that enforce referential integrity at the database level.

## 4.2 Basic Descriptive Information Content Entities

The foundational unit of data in any governance framework is the descriptive information content entity. In this context, we utilize the `outlier_claim_basic` axiom to define the atomic elements of observation. An outlier claim is a declarative statement asserting that a specific data point or event deviates from established baselines. Unlike complex claims, which may carry attribute sets or causal dependencies, the basic claim serves as a raw, unadorned assertion of anomaly. It is essential for auditors to distinguish between these basic assertions and their enriched counterparts to maintain data provenance.

The following table instantiates the `outlier_claim_basic` schema, which consists solely of a unique identifier and the class of the descriptive entity. The primary key (`id`) ensures that each claim is distinct and traceable within the system log.

| id | x |
| :--- | :--- |
| `oc_basic_001` | `UnusualLatencySpike` |
| `oc_basic_002` | `VolumeDiscrepancy` |
| `oc_basic_003` | `CrossMarketViolation` |
| `oc_basic_004` | `FailedAuthentication` |
| `oc_basic_005` | `RegulatoryThresholdBreach` |

These basic claims act as the nodes in the broader risk graph. While they possess semantic meaning, they lack the context required for immediate automated enforcement until they are associated with specific attributes or processes. In isolation, they serve as evidence markers for post-facto analysis.

## 4.3 Attribute-Enriched Outlier Claims

To transition from passive observation to active compliance monitoring, descriptive entities must be enriched with structural metadata. The `outlier_claim_min_one_attribute` axiom posits that a descriptive ICE is defined not only by its classification but by its possession of an attribute set. This axiom is critical for filtering noise; a claim is only considered valid for automated processing if it possesses at least one defining attribute derived from the system's alerting logic.

The relational schema for this concept, `t_outlier_claim_min_one_attribute`, introduces a foreign key constraint linking the claim's attribute (`y`) to a specific alert trigger. This structure enforces the rule that an enriched claim cannot exist in a vacuum—it must be intrinsically linked to a process that validates its significance.

| id | x | y |
| :--- | :--- | :--- |
| `oc_attr_001` | `HighFrequencyQuoteStuffing` | `alert_trig_001` |
| `oc_attr_002` | `InsiderTradingPattern` | `alert_trig_002` |
| `oc_attr_003` | `SuspiciousLayering` | `alert_trig_003` |
| `oc_attr_004` | `WashTradeDetection` | `alert_trig_004` |

In the table above, the primary key is the `id` of the claim itself, while the `y` column serves as a foreign key referencing the `t_alert_triggered_by` table. This recursive dependency ensures that for every attribute-rich claim, there exists a corresponding alert process that authorizes its existence within the compliance framework.

## 4.4 Metric Emission Processes

Operational data is not static; it is generated by dynamic processes occurring within the trading infrastructure. The `metric_emission_subclass` axiom formalizes this by defining a class of processes (specifically, BFO:0000015, a processual entity) that emits specific metrics. This ontology captures the causal chain where a computational or physical process generates a data stream that is subsequently monitored for outliers.

The schema `t_metric_emission_subclass` maps the emitting process (`x`) to the metric it generates (`y`). To maintain semantic consistency, the metric emitted (`y`) is structurally defined as an attribute-enriched outlier claim. This linkage implies that the "metric" is not merely a numerical value but a semantically rich information entity capable of triggering downstream logic.

| id | x | y |
| :--- | :--- | :--- |
| `proc_emit_001` | `OrderBookDepthAnalyzer` | `oc_attr_001` |
| `proc_emit_002` | `EmployeeCommunicationScanner` | `oc_attr_002` |
| `proc_emit_003` | `TradeSequenceMonitor` | `oc_attr_003` |
| `proc_emit_004` | `CounterpartyMatchingEngine` | `oc_attr_004` |

Here, the `id` represents the unique instance of the process execution. The foreign key constraint on `y` ensures that the metric being emitted is a valid, attribute-rich claim (`t_outlier_claim_min_one_attribute`), thereby enforcing a closed loop of data provenance from process generation to claim definition.

## 4.5 Alert Triggering Logic

The core of any real-time compliance system is the mechanism by which observations precipitate action. The `alert_triggered_by` axiom defines a processual entity (the alert) that is instantiated or triggered by a specific metric. This represents the decision logic within the governance framework: the evaluation of a metric against a threshold results in the firing of an alert process.

The corresponding table, `t_alert_triggered_by`, establishes the relationship between the alert process (`x`) and the metric that caused it (`y`). Consistent with the schema definitions, the metric (`y`) must be an attribute-enriched outlier claim. This creates a tightly coupled system where alerts are triggered by enriched claims, and those claims are defined by the very alerts they trigger, forming a robust validation cycle.

| id | x | y |
| :--- | :--- | :--- |
| `alert_trig_001` | `MarketAbuseProtocol` | `oc_attr_001` |
| `alert_trig_002` | `ConductSurveillanceSystem` | `oc_attr_002` |
| `alert_trig_003` | `ManipulationDetectionBot` | `oc_attr_003` |
| `alert_trig_004` | `PreTradeRiskCheck` | `oc_attr_004` |

The primary key `id` identifies the specific alert instance. The foreign key `y` referencing `t_outlier_claim_min_one_attribute` ensures that the alert is a response to a semantically valid, attribute-rich observation. This structure prevents spurious alerts from being logged against undefined or basic claims, thereby reducing false positives in the audit log.

## 4.6 Data Aggregation Protocols

While individual claims and alerts are necessary for granular control, governance reporting often requires summarized views. The `aggregation_basic` axiom defines descriptive information content entities that serve as aggregations of lower-level data. These entities do not typically trigger alerts themselves but function as roll-up metrics for regulatory reporting (e.g., daily counts of specific outlier types or aggregate risk scores).

The `t_aggregation_basic` table is structurally simple, reflecting its role as a container for summarized descriptive data. It shares the same foundational structure as the basic claim but is semantically distinguished by its class type and usage context within the reporting layer.

| id | x |
| :--- | :--- |
| `agg_daily_001` | `DailyQuoteStuffingCount` |
| `agg_daily_002` | `DailyInsiderAlertVolume` |
| `agg_monthly_001` | `MonthlyMarketHealthIndex` |
| `agg_quarterly_001` | `QuarterlyComplianceAuditSummary` |

These aggregation entities are essential for the high-level dashboards used by Chief Compliance Officers (CCOs). They provide the "evidence-anchored" prose required for regulatory filings, ensuring that high-level statements are backed by the rigorous, axiomatically defined structures detailed in the previous sections.
