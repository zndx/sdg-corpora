# Chapter 4: Ontological Formalization of Anomaly Detection and Metric Emission in Compliance Frameworks

This chapter delineates the formal ontological structures required to model the detection, characterization, and processing of outliers within regulated data environments. It establishes the axiomatic relationships between descriptive information content entities, processual metrics, and alerting mechanisms. The provisions herein are designed to ensure that audit trails maintain referential integrity and that anomaly detection protocols are grounded in a rigorous semantic framework. Compliance officers and data architects must apply these definitions to substantiate the validity of automated governance actions.

## 4.1 Basic Outlier Claims

In the context of data governance, an outlier claim is defined as a fundamental unit of descriptive information content entity (DescriptiveICE). It represents a declarative assertion that a specific data point or aggregate observation deviates from established control thresholds. As a subclass of `cco:DescriptiveICE`, the basic outlier claim does not inherently possess complex attributes or processual dependencies; rather, it serves as the atomic evidentiary unit upon which further investigative logic is built. The identification of such claims is the primary step in any audit procedure aimed at identifying data quality irregularities or fraudulent activity.

The axiom `outlier_claim_basic` posits that any instance of this class is merely a descriptive entity. This distinction is critical for maintaining a clear separation between the observation of an anomaly and the subsequent processing of that observation. For example, a log entry noting a "Login Attempt from Non-Whitelisted IP" constitutes a basic outlier claim. It describes a state of affairs without yet invoking the complex logic of alert generation or metric correlation.

| OCB-2023-002 | DataIntegrityViolation |

## 4.2 Basic Aggregations

Alongside specific outlier claims, governance frameworks must accommodate aggregations of data points that function as descriptive entities. An aggregation, in this ontological sense, is a `cco:DescriptiveICE` that synthesizes multiple individual data points into a composite representation. This is distinct from a simple outlier claim in that it represents a statistical or logical summary rather than a singular event. The axiom `aggregation_basic` formally categorizes these entities as descriptive, ensuring they are treated as information content rather than physical processes or independent objects.

Aggregations are essential for establishing baseline behaviors against which individual outliers are measured. For instance, a "Weekly Transaction Volume Summary" is an aggregation. It does not, by itself, indicate a failure, but it provides the contextual boundary necessary to define an outlier. Without these stable descriptive anchors, the determination of variance becomes mathematically and logically unsound.

## 4.3 Outlier Claims with Attribute Sets

To facilitate granular analysis, outlier claims must be capable of possessing attributes. The axiom `outlier_claim_min_one_attribute` refines the basic definition by asserting that a valid outlier claim is a descriptive information content entity that possesses a minimum of one attribute set. This attribute set acts as a container for metadata, severity scores, or contextual tags that qualify the nature of the claim. This structural requirement moves the entity from a simple observation to a structured data object suitable for automated processing.

In practice, this means that an outlier claim cannot exist in a vacuum of descriptive properties; it must carry at least one defining characteristic. For example, an outlier claim regarding a "High-Value Transaction" must include an attribute set specifying the transaction amount, the currency, and the risk score. This axiom ensures that all actionable claims are sufficiently parameterized to trigger downstream logic.

The following table embodies the axiom `outlier_claim_min_one_attribute`. The primary key `id` uniquely identifies the claim, while `x` denotes the claim class. The column `y` represents the attribute set and is a foreign key referencing an entry in the `t_alert_triggered_by` table. This dependency enforces the rule that the attribute set is not merely a passive data object but is intrinsically linked to the alert mechanism that defines the claim's operational context.

## 4.4 Alerts Triggered by Metrics

The transition from a descriptive claim to an active compliance response is mediated by the alert mechanism. The axiom `alert_triggered_by` defines a class of entities that are processes (`bfo:0000015`) specifically triggered by a metric. This establishes a causal chain: the existence of a specific metric state precipitates a processual alert. This is a critical distinction for audit purposes, as it separates the passive recording of a value (the metric) from the active system response (the alert).

Verbalizing this axiom, we state that the alert is "something that is triggered by metric [Y]." This formulation implies that the metric is the sufficient condition for the alert's initiation. In a regulatory context, this allows auditors to trace the root cause of an automated enforcement action back to the specific metric that exceeded its threshold. For instance, a "Lockdown Process" (Alert) is triggered by a "Failed Login Count" (Metric).

The table below represents the `alert_triggered_by` structure. The `id` is the primary key for the alert instance. The column `x` identifies the class of the alert process, and `y` is the metric that triggered it. The foreign key constraint requires that `y` reference an existing outlier claim (`t_outlier_claim_min_one_attribute`), thereby closing the loop between the descriptive claim and the processual alert.

| ALT-101 | CriticalSystemAlert | OCM-102 |
| ALT-102 | WarningLevelAlert | OCM-101 |

## 4.5 Metric Emission Subclasses

Finally, the origin of the metrics themselves must be formalized. The axiom `metric_emission_subclass` describes a process that emits a metric. This is a generative relationship; a system or subprocess (the emitter) produces a measurable output (the metric). This axiom is foundational for observability architectures, as it defines the provenance of the data used in anomaly detection.

Under this axiom, the emitting process is a subclass of `bfo:0000015` (a process). The emitted metric is the output that subsequently serves as the input for alert triggers or outlier claims. For example, a "Database Audit Process" emits a "Row Modification Count" metric. This metric is then evaluated to determine if an outlier claim exists. By modeling this relationship explicitly, organizations ensure that every metric is traceable to a legitimate source process, preventing the use of orphaned or unverified data in compliance calculations.

The table `t_metric_emission_subclass` captures this relationship. The `id` is the unique identifier for the emission event or process instance. Column `x` denotes the class of the emitting process, and column `y` represents the metric emitted. The foreign key constraint links `y` to `t_outlier_claim_min_one_attribute`, signifying that the emitted metric is formally registered as an outlier claim within the system.
