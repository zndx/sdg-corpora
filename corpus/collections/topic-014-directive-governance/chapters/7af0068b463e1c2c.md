# Chapter 7: Ontological Governance of Anomaly Detection and Metric Emission

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the identification, description, and processing of outliers within high-volume data environments. It establishes the necessary axioms for defining descriptive information content entities (ICE), specifically focusing on outlier claims, alert mechanisms, and metric emission processes. The definitions provided herein are binding for all compliance audits and system governance reviews involving anomaly detection frameworks. Practitioners must ensure that all system implementations align with the relational schemas derived from these axioms to maintain data integrity and traceability. The following sections detail the specific classes, properties, and constraints that constitute the core of the monitoring ontology.

## 7.2 Basic Outlier Claims

### 7.2.1 Definition and Context

In the context of data governance and system monitoring, an outlier claim is defined as a fundamental unit of descriptive information. It represents an assertion that a specific data point or aggregation of data deviates significantly from the expected distribution or baseline behavior. According to the foundational axiom, an outlier claim is a subclass of the `cco:DescriptiveICE` (Descriptive Information Content Entity). This classification ensures that the claim is treated not merely as a raw value, but as a distinct informational entity capable of being annotated, processed, and audited.

The primary function of the basic outlier claim is to serve as a container for the observation of anomaly. It does not, in its basic form, carry the complex attributes required for immediate remediation but establishes the existence of the anomaly within the system's ledger. This separation of concerns allows for granular auditing where the existence of a claim is distinct from the processing of that claim.

### 7.2.2 Relational Implementation

The relational projection of the basic outlier claim is straightforward, designed to enforce the entity's existence without complex dependencies. The schema `t_outlier_claim_basic` serves as the registry for these entities.

## 7.3 Outlier Claims with Attribute Sets

### 7.3.1 Complex Constraints and Dependencies

While basic outlier claims establish the presence of an anomaly, governance frameworks often require that these claims be substantiated by a set of defining attributes. The axiom `outlier_claim_min_one_attribute` stipulates that a valid outlier claim must possess a minimum of one attribute set. This moves the entity from a simple observation to a structured, evidence-backed assertion.

Crucially, this axiom introduces a complex dependency within the data model. The attribute set (`y`) associated with an outlier claim (`x`) is not stored as a primitive data type but is referenced via a foreign key constraint pointing to the `t_alert_triggered_by` table. This structural decision implies that the "attributes" of an outlier are inextricably linked to the alert mechanisms that they trigger. In other words, an outlier claim cannot be fully instantiated in the system without a corresponding alert process that defines its operational parameters. This enforces a strict "no claim without alert" policy, ensuring that every identified anomaly has an associated procedural response.

### 7.3.2 Schema and Evidence

The schema `t_outlier_claim_min_one_attribute` enforces this relationship. The column `y` is mandatory (`NOT NULL`), ensuring that every claim is rigorously defined by its trigger context.

## 7.4 Alert Triggering Mechanisms

### 7.4.1 Processual Definition and Metric Triggers

An alert is formally defined as a processual entity, specifically a subclass of `bfo:0000015` (Process). It represents the active, temporal occurrence of a system responding to a specific condition. The axiom `alert_triggered_by` asserts that an alert process (`X`) is triggered by a metric (`Y`). This establishes the causal chain: the existence of a metric (which, in this schema, is represented by the outlier claim) initiates the alert process.

This section highlights the reciprocal nature of the ontology. Just as the outlier claim requires an alert to define its attributes (as seen in Section 7.3), the alert process requires a metric to initiate its execution. The schema `t_alert_triggered_by` captures this bidirectional dependency. The `y` column, representing the triggering metric, references the `t_outlier_claim_min_one_attribute` table. This circular reference (`t_outlier_claim_min_one_attribute.y` -> `t_alert_triggered_by.id` and `t_alert_triggered_by.y` -> `t_outlier_claim_min_one_attribute.id`) is a deliberate design feature to enforce tight coupling between the observation of the anomaly and the execution of the response protocol.

## 7.5 Metric Emission Subclasses

### 7.5.1 Emission Processes and Lineage

To ensure complete auditability, the ontology must account for the origin of the metrics that trigger alerts. The axiom `metric_emission_subclass` defines a process (`X`) that emits a metric (`Y`). This class is also a subclass of `bfo:0000015`, emphasizing that metric generation is an activity occurring over time.

The relational schema `t_metric_emission_subclass` links the emitting process (e.g., a sensor, a database scanner, or a log parser) to the metric it produces. The foreign key constraint on `y` references `t_outlier_claim_min_one_attribute`, reinforcing the concept that the "metric" in this governance framework is synonymous with the structured outlier claim. This traceability allows investigators to determine not only that an alert was triggered, but precisely which upstream process emitted the data that caused the trigger.

## 7.6 Basic Aggregations

### 7.6.1 Descriptive Entities for Summarization

Beyond individual outlier events, governance frameworks rely on aggregated data to assess system health and compliance trends. The `aggregation_basic` axiom defines a class of descriptive information content entities (`cco:DescriptiveICE`) that represent summarized data points, such as averages, sums, or histograms. Unlike outlier claims, which focus on deviation, aggregations focus on holistic views of the dataset.

The schema `t_aggregation_basic` is structurally simple, mirroring `t_outlier_claim_basic`. It serves as a catalog for the various types of aggregations permitted within the system. By defining these explicitly, the organization ensures that all reporting metrics are standardized and derived from approved methodologies.
