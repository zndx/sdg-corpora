# Directive Governance in Audit Management Systems

This chapter defines five core ontological patterns for representing controls, attestations, verifications, and audits. Each pattern is realized as a relation whose rows are instances of the corresponding class expressions. The relations share identifier values that function as primary and foreign keys, enabling multi-hop queries across attestations, evidence, risks, and findings.

## 1 Schema Overview

The model uses five tables derived directly from the supplied axioms. Each table contains an opaque identifier, a subject class instance (column x), and an object class instance (column y). Primary keys are the id columns. Foreign-key relationships are formed when a y value in one table equals an x or id value in another table, permitting joins that traverse the governance chain from control to risk to audit finding to supporting evidence.

### 1.1 Attestation with Supporting Evidence

This table embodies axiom 1: an attestation process is linked to a supporting evidence class. Column id is the primary key. Column y references an evidence individual that may appear as x in t_verification_produces_evidence, allowing a two-hop traversal from attestation to produced evidence.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id_a1 | QuarterlyComplianceAttestation | EvidencePacket_Q3 |
| id_a2 | QuarterlyComplianceAttestation | EvidencePacket_Q2 |
| id_a3 | IncidentResponseAttestation | EvidencePacket_INC42 |
| id_a4 | AccessReviewAttestation | EvidencePacket_AR17 |

### 1.2 Verification Produces Evidence

This table embodies axiom 2: a verification process produces an evidence class. Column id is the primary key. Column y may be joined to the y column of t_attestation_with_supporting_evidence when the same evidence packet is referenced.

```sql
CREATE TABLE t_verification_produces_evidence (
```

### 1.4 Control Addresses Risk

This table embodies axiom 4: a directive control addresses a concrete risk instance. Column id is the primary key. Column x references the same control individuals used in t_control_only_addresses_threat_class, while y references risk instances that appear as findings in t_audit_with_findings.

```sql
CREATE TABLE t_control_addresses_risk (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |

### 1.5 Audit with Findings

This table embodies axiom 5: an audit process has findings. Column id is the primary key. Column y references risk instances from t_control_addresses_risk, closing the chain from control through risk to audit outcome.


## 2 Cross-Join Example

To determine the evidence supporting an audit finding that concerns a risk addressed by a given control, perform the following joins:

- Start with t_audit_with_findings (id_f1) where y = 'Risk_2023_09_Unauth'.
- Join t_control_addresses_risk on y to obtain x = 'AccessControlPolicy'.
- Join t_attestation_with_supporting_evidence on y = 'EvidencePacket_Q3'.
- Join t_verification_produces_evidence on y to confirm the verification step.

The resulting joined row is:

AuditFinding: id_f1, Risk: Risk_2023_09_Unauth, Control: AccessControlPolicy, Evidence: EvidencePacket_Q3, Verification: LogVerification.
