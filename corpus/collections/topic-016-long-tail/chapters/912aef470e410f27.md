# Chapter 7: Directive Governance Patterns in Regulatory Audit Systems

This chapter presents five core ontological templates that formalize how directives address risks, produce evidence, and generate findings. The templates are realized as a five-table relational schema drawn from an information-security audit program. Primary keys are synthetic identifiers; foreign-key semantics arise when values in the x or y columns of one table match entity references in another, enabling two- and three-hop queries across attestations, verifications, controls, and audits.

## 1 Schema Overview

The schema comprises exactly the tables projected from the supplied OWL axioms. Each table stores class-level relationships rather than instance data; column values are therefore names of classes or named individuals that satisfy the corresponding Manchester restrictions. Four tables enforce a mandatory y column; the remaining table permits an optional y to represent universal restrictions.

## 2 Table Definitions

### 2.1 t_control_addresses_risk

This table embodies axiom 4 (control_addresses_risk). Column id is the primary key. Column x references a directive class; column y references a risk class that the directive addresses. A reader can join this table to t_audit_with_findings on y to retrieve every audit finding that concerns a risk mitigated by a given control.

```sql
CREATE TABLE t_control_addresses_risk (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 3 Cross-Join Example

Question: Which control addresses the risk underlying the finding reported by the Q4-2023-IS-Audit, and what evidence supports the corresponding attestation?

Step 1. From t_audit_with_findings select rows where x = 'Q4-2023-IS-Audit' to obtain y values 'Finding-ACL-01' and 'Finding-ENC-02'.  
Step 2. Join those y values to t_control_addresses_risk on y to retrieve x = 'AccessControlDirective' (risk 'UnauthorizedAccessRisk') and x = 'EncryptionDirective' (risk 'DataDisclosureRisk').  
Step 3. Join the risk values to t_attestation_with_supporting_evidence via the matching control classes to locate supporting evidence classes 'AccessLogEvidence' and 'KeyRotationEvidence'.  
Step 4. Confirm each evidence class appears in t_verification_produces_evidence under the corresponding verification process.

Resulting joined row (abridged):  
audit_id = awf-01, finding = Finding-ACL-01, control = AccessControlDirective, risk = UnauthorizedAccessRisk, evidence = AccessLogEvidence, verification = AccessVerification-2023.
