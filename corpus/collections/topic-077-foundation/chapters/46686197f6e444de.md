# Chapter 4: Ontological Classification of Kernel Entities and Audit Frameworks

## 4.1 Scope and Preamble

This chapter establishes the formal taxonomic structure for kernel-level information content entities within an eBPF (Extended Berkeley Packet Filter) observability context. It delineates the criteria for classifying system calls as designative entities and further distinguishes those entities subject to active auditing processes. The definitions provided herein align with the upper-level ontology of Information Content Entities (ICE) and are intended to serve as the normative reference for compliance engineers developing kernel tracing and security monitoring solutions. By grounding these classifications in formal axioms, this framework ensures that system observability data retains semantic integrity across heterogeneous execution environments.

## 4.2 Designative Information Content Entities

### 4.2.1 Definition and Ontological Status

In the context of kernel observability, an Information Content Entity (ICE) is defined as an entity that stands for some other entity or conveys meaning. Within this domain, we specifically address *Designative ICEs*, which function as identifiers or labels for specific kernel operations or states. The fundamental axiom governing this classification asserts that a specific class of system calls (`X`) acts as a designative information content entity.

Formally, this relationship is expressed through the axiom: `Class: {X:Class} SubClassOf: cco:DesignativeICE`. This implies that the system call is not merely a procedural instruction but a semantic designator that bridges the gap between user-space intent and kernel-space implementation. The designation allows for the static analysis of system behavior by treating the syscall as a discrete, nameable data point rather than a transient procedural event.

The semantic value lies in the designation itself, which anchors subsequent behavioral analysis to a defined ontological standard.

### 4.2.3 Operational Context of Designation

The utility of defining these system calls as Designative ICEs becomes apparent during forensic analysis and system auditing. When a monitoring agent captures an event, it maps the raw system call number to the designative class defined in the ontology. This mapping ensures that disparate systems—potentially running different kernel versions or architectures—converge on a unified semantic label. For example, while the raw integer for `SyscallRead` might differ between 32-bit and 64-bit architectures, the designation `SyscallRead` remains constant, facilitating cross-platform correlation of evidence.

Furthermore, the designation serves as the prerequisite for any higher-order policy enforcement. Before a policy can be applied to restrict or log an action, the action must be formally recognized as a distinct entity within the system's information model. Without this ontological commitment, audit logs would consist of unstructured numeric codes, severely limiting the automated processing of compliance evidence.

## 4.3 Audited Designative Entities

### 4.3.1 Integration of Audit Processes

While designation provides the necessary semantic labeling, it does not inherently imply observability or security enforcement. To achieve a robust security posture, specific designative entities must be linked to an audit process. This introduces a second layer of complexity: the intersection of the designative entity with a process that performs the auditing.

This relationship is governed by the axiom: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`. Here, `bfo:0000015` refers to a "Process" within the Basic Formal Ontology (BFO). The axiom asserts that for a class `X` to be considered an "Audited Designative Entity," it must not only be a Designative ICE but must also be the object of an audit process. This distinction is critical for resource-constrained environments; not every designative entity may be audited due to performance overhead, but those that are must be explicitly defined within this subclass.

### 4.3.2 The Audit Process (bfo:0000015)

The audit process referenced in the ontology is a temporal, occurring entity that monitors the state changes or invocations associated with the designative entity. In the context of eBPF, this process is typically realized as a kernel-attached tracing program or a LSM (Linux Security Module) hook. The process is not passive; it actively inspects the arguments and return values of the system call designated by `X`.

The requirement that the entity be "audited by some process" ensures that there is an active mechanism responsible for gathering evidence. This prevents "ghost" classifications where a syscall is labeled as sensitive but no actual monitoring logic is attached. The ontological structure mandates the existence of the auditor (the process) as a condition for the validity of the classification.

Because this operation fundamentally alters the execution context of the system, it is axiomatically linked to an audit process (`bfo:0000015`). In a practical deployment, this implies that an eBPF program attached to the `sys_enter_execve` tracepoint is active and functioning as the mandated auditor.

### 4.3.4 Compliance Verification and Evidence Anchoring

The differentiation between basic designative entities and audited entities forms the basis of compliance verification. When an auditor reviews a system, they can compare the running configuration against the axiomatic definitions. If `SyscallMount` is defined in the ontology as `auditedBy some Process`, the absence of log entries or trace data for mount operations constitutes a direct violation of the framework.

This evidence-anchored approach transforms abstract security policies into verifiable technical states. The ontology serves as the "source of truth," while the relational data (captured in the tables above) provides the mapping to concrete implementation details. By maintaining this strict separation between the definition of the entity (Axiom 1) and the requirements for its observation (Axiom 2), the framework ensures that system designs are both semantically rigorous and operationally enforceable.
