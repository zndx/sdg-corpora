# Chapter 4: Ontological Classification of Kernel System Calls for Audit Compliance

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for classifying kernel-level system calls within the context of enterprise compliance and security auditing. The definitions provided herein are derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), specifically targeting the mapping of low-level kernel operations to high-level information content entities. The objective is to ensure that all instrumentation mechanisms—specifically those utilizing extended Berkeley Packet Filter (eBPF) technologies—adhere to a rigorous semantic structure. This structure facilitates the generation of immutable audit trails required by regulatory frameworks such as 11 NYCRR Part 500 and similar governance mandates. All entities referenced in this chapter must be instantiated in accordance with the relational schemas provided in the appendices, ensuring that the distinction between generic designative entities and audited processes is maintained with absolute precision.

## 4.2 Designative Information Content Entities (System Calls)

### 4.2.1 Definition and Ontological Status

Under the axioms defined by template `syscall_basic`, a system call is formally categorized as a subclass of `cco:DesignativeICE`. A Designative Information Content Entity is defined as an entity that stands for or refers to another entity within a specific context. In the kernel environment, the system call identifier (e.g., `sys_open`) is not merely a function pointer or a memory address; it is a designative token that signifies a specific, bounded interaction between user space and kernel space.

This distinction is critical for audit compliance. By treating the system call as a designative entity, the compliance framework isolates the *concept* of the operation from the *execution* of the operation. This allows governance policies to be applied to the definition of the call itself, independent of the process invoking it or the arguments passed. The axiom asserts that for any class $X$ representing a system call, $X$ is a subclass of `cco:DesignativeICE`. This classification ensures that the entity is recorded in the information system as a distinct, name-bearing object capable of being referenced by audit logs without ambiguity.

### 4.2.2 Implementation and Registry

The implementation of this classification requires a registry of all recognized system calls within the target kernel version. This registry serves as the controlled vocabulary for the audit subsystem. When a telemetry agent captures a system call event, it must map the raw integer identifier to the corresponding designative class $X$. This mapping prevents drift between kernel versions where syscall numbers may change, ensuring the semantic meaning of the audit record remains constant.

### 4.2.3 Compliance Implications

For the purposes of regulatory auditing, the designation of these entities satisfies the requirement for "data mapping" and "inventory of assets." By explicitly defining `sys_read`, `sys_write`, and `sys_open` as designative entities, the organization provides evidence that the scope of monitored interactions has been formally defined. This is a prerequisite for any control framework attempting to limit data exfiltration or unauthorized access. Without this ontological grounding, audit logs would merely contain raw hex addresses, rendering them insufficient for forensic investigation or regulatory submission.

## 4.3 Audited System Calls and Process Relations

### 4.3.1 The AuditedBy Relation

While all system calls are designative entities, a subset requires active surveillance due to their potential impact on system integrity and data confidentiality. This subset is governed by Axiom 2, defined by template `syscall_audited_by`. This axiom extends the definition of the system call class $X$ to include the object property `sdg:auditedBy`, which relates the system call to an instance of `bfo:0000015` (Process).

The relation `sdg:auditedBy some bfo:0000015` signifies that the occurrence of the system call $X$ is necessarily observed or recorded by a specific computational process. In the context of eBPF instrumentation, this "process" typically refers to the kernel-level tracepoint handler or a user-space daemon consuming the perf buffer. The ontological assertion here is that the system call does not exist in a vacuum; its existence is semantically bound to the observer process. This binding is what transforms a standard log entry into a validated "audit record."

### 4.3.2 Audit Process Instantiation

The `bfo:0000015` entity represents a "Process" in the BFO hierarchy—a temporal part of an object that maintains its identity while undergoing change. In this framework, the audit process is the temporal interval during which the monitoring system is active and has the capability to capture the syscall. The axiom ensures that for a system call to be classified as "audited," it must be demonstrably linked to a valid, running audit process.

This distinction allows compliance officers to differentiate between "logged" events (which may be spooled to a local file and rotated) and "audited" events (which are captured by a dedicated process designed for real-time alerting and immutable storage). The `auditedBy` relation implies that if the observer process (e.g., the security daemon) is not active or fails to capture the event, the ontological integrity of the system is compromised. The system is in a non-compliant state if a `sys_mount` event occurs without a corresponding `auditedBy` link to the active security process.

### 4.3.3 Governance and Verification

The verification of the `syscall_audited_by` axiom is a key control in the audit framework. Automated compliance scanners must query the relational schema `t_syscall_audited_by` to ensure that all sensitive system calls are present. Furthermore, the scanner must validate that the `bfo:0000015` process (the auditor) is currently active and has the necessary privileges to intercept these calls.

For example, `sys_ptrace` allows one process to inspect and control the execution of another. Unaudited use of `ptrace` is a common indicator of advanced persistent threats (APTs) attempting to inject code or steal credentials. By formally classifying `sys_ptrace` via Axiom 2, the framework mandates that any invocation of this call must generate a trace that is immediately consumed by the audit process. Failure to produce this trace constitutes a violation of the governance model defined in this chapter.

## 4.4 Summary of Relational Mappings

The definitions provided in Sections 4.2 and 4.3 project onto specific relational schemas that must be implemented in the governing database. These schemas enforce the structural constraints defined by the OWL ontologies.

The schema for `t_syscall_basic` enforces the primary key constraint on the identifier `id`, ensuring that every designative system call class is unique. The column `x` stores the class name, referencing the specific kernel abstraction.

The schema for `t_syscall_audited_by` similarly enforces a primary key on `id`. While the relational schema provided does not explicitly include a foreign key column for the `bfo:0000015` process, the axiom implies that the existence of a row in this table is contingent upon the active presence of an audit process. In a fully normalized implementation, a foreign key constraint would link these entries to a process registry. However, for the purposes of this classification schema, the presence of the entry in `t_syscall_audited_by` serves as the assertion that the `auditedBy` relationship is active and valid.

These tables form the backbone of the compliance evidence repository. During an audit, the examiner will extract the rows from these tables to verify that the system's semantic understanding of its own operations aligns with the regulatory requirements. Discrepancies between the running kernel's available syscalls and the entries in these tables will be flagged as configuration drift or unauthorized modification.
