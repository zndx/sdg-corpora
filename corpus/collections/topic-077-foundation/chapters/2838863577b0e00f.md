# Chapter 4: Governance of Kernel-Level Information Entities and Audit Workflows

## 4.1 Scope and Regulatory Context

This chapter establishes the ontological framework for managing system-level interactions within high-assurance computing environments. It delineates the formal classification of kernel information entities, specifically focusing on the distinction between designative information content entities and those subject to active audit processes. The guidelines provided herein are intended for compliance officers, system architects, and information security auditors who must ensure that kernel observability mechanisms adhere to strict semantic standards. By mapping low-level system calls to formal ontology classes, organizations can achieve verifiable traceability and automated compliance enforcement consistent with the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO).

## 1. Designative Information Content Entities

### 1.1 Ontological Foundations

In the context of kernel observability and system governance, a fundamental distinction must be drawn between the execution of a process and the informational artifact that designates it. According to Axiom 1 (`syscall_basic`), a specific class of entity is defined as a Designative Information Content Entity (`cco:DesignativeICE`). This classification asserts that the entity in question serves as a referential token—a symbolic or linguistic construct that stands for a specific function or operation within the operating system kernel.

The designation of a system call as a `cco:DesignativeICE` is a prerequisite for any higher-level governance. It implies that the call possesses semantic properties independent of its execution state. In audit logs and compliance reports, the entity is treated not merely as a trigger for a CPU instruction, but as a bounded informational object with a distinct identity. This separation of concerns allows governance frameworks to address the *definition* and *access control* of the call separately from its *runtime behavior*.

For instance, when a compliance framework references the `open` system call, it is referencing the designative entity—the metadata and schema definition that constitutes "open-ness" within the kernel namespace. This entity exists as a persistent informational object, regardless of whether the call is invoked zero times or one million times during a reporting period.

### 1.2 Classification Schema and Registry

To maintain a rigorous audit trail, all designative entities within the kernel namespace must be cataloged in a centralized registry. This registry serves as the source of truth for automated scanning tools and compliance verification engines. The table below, derived from the relational schema projected by Axiom 1, illustrates the mandatory structure for recording these basic designative entities.

The schema `t_syscall_basic` requires a unique identifier and the class name of the designative entity. The primary key (`id`) ensures that each informational object is non-replicable and traceable across all subsystems. The `x` column denotes the specific class of the system call being designated, anchoring the entity to the `cco:DesignativeICE` superclass.

Each row corresponds to a distinct class of system call that has been formally recognized as a Designative Information Content Entity. These entries are utilized by the governance framework to validate that all observed kernel events map to a sanctioned designative definition.*

### 1.3 Compliance Implications

The accurate classification of system calls as `cco:DesignativeICE` entities is critical for maintaining the integrity of the system's semantic layer. If a kernel interface is invoked that lacks a corresponding entry in the basic registry, it constitutes a "shadow operation"—an informational entity operating outside the defined governance ontology. Compliance mandates require that such entities be immediately flagged for review.

Furthermore, this classification enables the application of metadata-based policies. Because the entity is treated as an information content entity, it can be tagged with security clearance levels, data handling restrictions, and retention schedules. For example, the `SyscallWrite` class may be annotated with a higher sensitivity rating than `SyscallStat` due to its potential to modify persistent state, thereby triggering distinct audit workflows.

## 2. Audited Designative Entities

### 2.1 Integration with Audit Processes

While the designation of an information entity establishes its semantic identity, governance frameworks must also account for the procedural oversight applied to that entity. Axiom 2 (`syscall_audited_by`) introduces a complex constraint: a designative information content entity is now subclassed to include a specific relationship to a process (`bfo:0000015`). In this context, the process represents the audit workflow or monitoring mechanism that observes, records, and verifies the entity.

The verbalization of this axiom asserts that the entity is not only a designative informational object but is also "audited by" a process. This creates a composite class where the existence of the entity is inextricably linked to the activity of an auditor. In practical terms, this means that for a system call to be compliant within this subclass, it must be actively hooked by an eBPF program, a tracepoint, or a LSM (Linux Security Module) hook that functions as the `bfo:0000015` process instance.

This distinction is vital for high-security environments (e.g., financial transaction processing or classified defense systems). It is insufficient to merely define the system call; the organization must demonstrate that a continuous, temporal process is in place to audit the call's invocation and parameters. The `auditedBy` relationship transforms the static entity into a dynamic node within the security monitoring graph.

### 2.2 Audit Process Verification

To verify that the `auditedBy` constraint is satisfied, the governance framework utilizes a secondary registry that tracks only those designative entities which have been successfully bound to an audit process. This table acts as a subset of the general registry, filtering for entities that meet the stricter compliance requirements of Axiom 2.

The relational schema `t_syscall_audited_by` mirrors the structure of the basic table but semantically restricts the population of the `x` column to those classes where the `sdg:auditedBy` object property is active and valid. The presence of a row in this table is evidence that the audit process (`bfo:0000015`) is currently engaged and generating logs for the specified entity.

| `asc-2023-102` | `AuditedSyscallClone` |
| `asc-2023-103` | `AuditedSyscallConnect` |

*Table 2.1 lists the system calls that are currently subject to active audit processes. The `x` values reflect the subclassification of the original designative entities, now modified to include the `auditedBy` restriction. These identifiers are cross-referenced in real-time audit logs to ensure that no privileged operation occurs without a corresponding process trace.*

### 2.3 Governance and Enforcement

The transition from a basic designative entity to an audited designative entity represents a elevation in the compliance status of a system call. Governance policies must dictate which specific classes of system calls require this elevation based on risk assessment frameworks.

For example, while `SyscallRead` (Table 1.1) may be a basic informational entity, the specific act of reading from a sensitive socket descriptor may require the invocation of an `AuditedSyscallRead` (if defined) or trigger a policy that maps the basic call to an audited instance dynamically. However, as shown in Table 2.1, high-impact operations such as `Execve` (process execution) and `Connect` (network socket initiation) are mandatorily classified as audited entities.

The enforcement mechanism relies on the validation of the `bfo:0000015` process. If the audit daemon fails or the eBPF probe is unloaded, the relationship `sdg:auditedBy` becomes invalid. Consequently, the system must either revert the entity to a basic state (if permissible) or initiate a fail-safe lockdown, as the entity can no longer satisfy the axiom `syscall_audited_by`. This strict adherence ensures that the "evidence-anchored" nature of the documentation is maintained; the existence of the audit record is a necessary condition for the existence of the compliant entity.

### 2.4 Reporting and Discrepancy Resolution

During an audit cycle, examiners will compare the inventory in Table 1.1 against the active inventory in Table 2.1. Any high-privilege system call present in Table 1.1 but absent in Table 2.1 must be justified as a waived or low-risk operation. Conversely, entries in Table 2.1 that lack corresponding log data in the audit repository indicate a "process-entity dissociation," a critical failure where the designative entity claims to be audited, but the `bfo:0000015` process has not generated the expected evidence.

Resolution of such discrepancies requires immediate remediation, typically involving the restart of the audit daemon or the patching of the kernel probe configuration.
