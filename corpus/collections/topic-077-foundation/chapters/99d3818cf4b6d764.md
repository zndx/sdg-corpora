# Chapter 4: Kernel Audit Semantics and Designative Information Content Entities

## 4.1 Scope and Preamble

This chapter establishes the ontological framework for classifying kernel-level system calls within an extended Berkeley Packet Filter (eBPF) observability context. It delineates the structural requirements for defining system calls as Designative Information Content Entities (ICE) and extends this definition to incorporate mandatory audit provenance. The objective is to provide a rigorous, evidence-based mapping between low-level kernel events and high-level governance data structures, ensuring that compliance frameworks can reliably ingest and interpret syscall telemetry.

## 4.2 Designative Information Content Entities

### 4.2.1 Ontological Definition and Taxonomy

In the context of kernel observability, a system call must be understood not merely as a processor instruction or a transition ring, but as an informational artifact that designates a specific intent. According to the core ontology axiom (template_id: syscall_basic), any class representing a system call is categorized as a subclass of `cco:DesignativeICE`. A Designative Information Content Entity is defined as an entity that stands for or refers to another entity—in this case, the logical operation requested by a user-space process.

The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE` asserts that the class {X} is fundamentally a carrier of information. This distinction is critical for audit trails; it separates the *record* of the action (the information entity) from the *execution* of the action (the physical process). For a compliance officer or a forensic analyst, the Designative ICE is the object of scrutiny: it is the immutable datum that asserts "Process A requested Resource B."

To implement this within a governance framework, the taxonomy must be strictly defined. We do not refer to "opening a file" in vague terms; we refer to instances of the class `SyscallOpen`, which is a Designative ICE. This semantic precision allows automated reasoning engines to infer properties about the event based solely on its class membership.

### 4.2.2 Relational Mapping of Basic Syscalls

The projection of this axiom into a relational schema ensures that every distinct syscall class is cataloged with a unique identifier. The table `t_syscall_basic` serves as the registry for these classes. The primary key (`id`) ensures referential integrity, while the column `x` holds the canonical class name.

The following data table illustrates the instantiation of this axiom. It enumerates standard system calls that have been formally classified as Designative Information Content Entities. These entries represent the foundational vocabulary of the kernel audit lexicon.

| ID | X (Class Name) |
|---|---|
| SC-1001 | SyscallOpen |
| SC-1002 | SyscallClose |
| SC-1003 | SyscallRead |
| SC-1004 | SyscallWrite |
| SC-1005 | SyscallStat |

**Table 4.1:** Registry of Basic System Call Classes as Designative Information Content Entities.

In the table above, the row with ID `SC-1001` maps to the class `SyscallOpen`. This entry asserts that `SyscallOpen` is a Designative ICE. It does not, by itself, imply that the syscall is being audited or monitored; it merely establishes its semantic nature. This distinction is the baseline for all subsequent observability logic. Without this classification, the system cannot distinguish between a raw memory address and a meaningful, designative request.

### 4.2.3 Implementation in eBPF Contexts

When deploying eBPF programs to trace these events, the loader must verify that the hook point corresponds to a valid entry in the `t_syscall_basic` table. If a trace event generates a class identifier not present in this registry, the monitoring agent must flag a taxonomy violation. This ensures that the observability pipeline remains consistent with the defined ontology. The "Designative" nature implies that the data payload associated with the event (arguments, return values) is treated as metadata describing the intent, rather than the outcome itself.

## 4.3 Audited Designative Entities

### 4.3.1 The Audit Constraint

While the classification of a syscall as a Designative ICE establishes its semantic identity, it does not guarantee oversight. In regulated environments (e.g., PCI-DSS, SOC 2), it is insufficient to merely know that an action *is* information; one must demonstrate *who* observed it and *how*. This requirement introduces the second axiom (template_id: syscall_audited_by).

The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015` extends the basic definition by adding a necessary restriction: the entity must be audited by a process. Here, `bfo:0000015` refers to a "Process" in the Basic Formal Ontology (BFO)—specifically, a temporal span of activity. In practical terms, this means the syscall class {X} is not only a Designative ICE but is also intrinsically linked to an audit trail or a monitoring process.

This ontological shift moves the entity from a passive state of "being information" to an active state of "being governed." The `sdg:auditedBy` property creates a dependency. If an instance of {X} exists, there must exist a corresponding audit process. This is the formal mechanism by which "non-repudiation" is encoded into the data model.

### 4.3.2 Relational Mapping of Audited Syscalls

The relational schema for audited syscalls, `t_syscall_audited_by`, mirrors the structure of the basic registry but represents a distinct set of classes with higher compliance requirements. The presence of a class in this table implies that the `auditedBy` restriction is active. The separation of these tables—`t_syscall_basic` versus `t_syscall_audited_by`—allows for a granular security policy. Not all Designative ICEs require auditing (e.g., benign timing calls), but those listed in `t_syscall_audited_by` mandate it.

The table below defines the classes that represent high-value or high-risk system calls, which are subject to strict audit logging.

| ID | X (Class Name) |
|---|---|
| SCA-2001 | SyscallCloneAudited |
| SCA-2002 | SyscallExecveAudited |
| SCA-2003 | SyscallSetuidAudited |
| SCA-2004 | SyscallMountAudited |
| SCA-2005 | SyscallPtraceAudited |

**Table 4.2:** Registry of Audited System Call Classes with Process Provenance.

In this table, the class `SyscallExecveAudited` (ID: `SCA-2002`) serves as the archetype for process execution monitoring. Unlike the generic `SyscallRead` in the previous table, `SyscallExecveAudited` carries the implicit constraint that any invocation of this class must trigger the creation of an audit record (the `bfo:0000015` process). This record serves as the digital evidence required for forensic investigation.

### 4.3.3 Verification and Compliance Logic

The enforcement of this axiom requires a validation layer within the eBPF verifier or the userspace controller. When a `SyscallCloneAudited` event is triggered, the system must validate that the associated audit process (e.g., writing to the audit pipe or sending a netlink message) has successfully completed. If the designative entity exists without the linked audit process, the system state is ontologically invalid, constituting a critical compliance failure.

Furthermore, the distinction between the tables allows for efficient querying. A query joining `t_syscall_audited_by` against runtime logs retrieves only those events that carry the weight of governance. This is essential for generating audit reports that satisfy regulatory bodies, which typically require evidence that specific, sensitive classes of information were actively monitored rather than passively recorded.

## 4.4 Summary of Schema Projections

The definitions provided in this chapter translate the abstract OWL axioms into concrete relational structures. These structures form the backbone of the audit database.

The table `t_syscall_basic` embodies the axiom that specific system call classes are designative information content entities. Its primary key is the unique identifier for the class definition.

The table `t_syscall_audited_by` embodies the axiom that specific system call classes are designative entities subject to audit by a process. While its column structure is identical to the basic table, its semantic content implies the `sdg:auditedBy` restriction, effectively creating a subset of high-fidelity, governed entities.
