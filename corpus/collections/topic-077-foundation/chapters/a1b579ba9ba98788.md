# Chapter 4: Formal Ontology of Kernel Audit Entities

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the classification and attribution of system-level calls within an eBPF-enabled kernel audit framework. The objective is to provide a rigorous, evidence-anchored definition of information entities that serve as the primary units of observability in compliance environments. By mapping the Common Core Ontologies (CCO) and Basic Formal Ontology (BFO) to specific kernel behaviors, this specification establishes the necessary semantic boundaries for automated audit reporting and governance verification. The definitions herein are deterministic, ensuring that any entity classified under the provided axioms satisfies the strict requirements for designative information content and process attribution.

## 4.2 Designative Information Content Entities

### 4.2.1 Theoretical Foundation

The fundamental unit of auditability in the kernel observability stack is the system call, conceptualized not as a computational action but as a discrete information artifact. Under the axiom `syscall_basic`, we define the class of system calls as a subclass of `cco:DesignativeICE`. A Designative Information Content Entity (ICE) is an entity that stands for, refers to, or denotes another entity. In the context of kernel auditing, the system call record serves as a designative token that refers to the specific, transient execution of a kernel function.

This distinction is critical for compliance reporting. The audit log does not capture the physical execution of the instruction; rather, it captures the *information content* that designates that execution. By formalizing system calls as `cco:DesignativeICE`, we establish that they are generically dependent continuants that inherit the properties of information-bearing entities. This allows the audit framework to treat kernel events as document-like objects that can be indexed, hashed, and validated against governance policies without needing to reference the volatile memory state of the executing process.

The ontological commitment to `cco:DesignativeICE` ensures that every entity processed by the auditing subsystem is, by definition, a bearer of information. This satisfies the requirement for audit trails to consist of "immutable records" rather than transient signals. The designation property implies that the system call identifier (e.g., `SYS_OPEN`) acts as a signifier for the underlying operation, creating a layer of abstraction necessary for cross-platform compliance reporting.

This semantic distinction allows the governance framework to apply metadata retention policies to the record of the event, independent of the lifecycle of the file descriptor itself.

### 4.2.3 Compliance Implications

From a governance perspective, the classification of these entities as `cco:DesignativeICE` triggers specific data handling requirements. Because they are information content entities, they are subject to integrity checks and non-repudiation controls. Audit controllers must verify that the designative relationship remains intact; that is, the log entry must accurately and unambiguously refer to the specific kernel operation it purports to represent. Any corruption or ambiguity in this designation constitutes a violation of the audit axiom and, by extension, the compliance framework relying upon it.

## 4.3 Audited Entities and Process Attribution

### 4.3.1 The AuditedBy Relationship

While the basic classification of system calls provides the foundation for the audit log, compliance frameworks require the explicit attribution of these calls to responsible agents. This is formalized through the axiom `syscall_audited_by`, which introduces an existential restriction: a system call (Class X) is not only a `cco:DesignativeICE` but is also `sdg:auditedBy` some `bfo:0000015`.

In the Basic Formal Ontology, `bfo:0000015` denotes a "Process." This is distinct from an information content entity; a process is an occurrent that unfolds in time and has temporal parts. By asserting that a system call is audited by a process, we establish a causal and observational link between the record (the designative entity) and the mechanism responsible for its capture (the auditor process).

The axiom `syscall_audited_by` therefore defines a subset of designative entities that are subject to active monitoring. The existential restriction (`some`) indicates that for every instance of such a system call, there exists at least one audit process that observes it. This does not necessarily imply a one-to-one mapping—a single audit process (e.g., an eBPF trace program running in the kernel) may audit thousands of system calls—but it guarantees that the relationship is mandatory. If a system call class cannot be proven to be audited by a process, it fails to satisfy this axiom and cannot be included in high-assurance audit reports.

### 4.3.2 High-Value Audit Targets

The distinction between a basic system call and an audited system call is functionally the distinction between standard logging and security monitoring. The `syscall_audited_by` axiom is typically applied to system calls that modify system state, alter permissions, or create new execution contexts. These are the operations that governance frameworks identify as "high-value events" requiring process-level attestation.

The following table enumerates system call classes that satisfy the `syscall_audited_by` axiom. These classes represent operations where the audit trail must include verifiable proof of observation by a kernel-level process.

**Table 4.2: Audited System Call Classification (t_syscall_audited_by)**

| id | x |
|---|---|
| sc_audit_001 | SyscallExecve |
| sc_audit_002 | SyscallClone |
| sc_audit_003 | SyscallFork |
| sc_audit_004 | SyscallPtrace |
| sc_audit_005 | SyscallMount |

In Table 4.2, the entity `SyscallExecve` (id: `sc_audit_001`) is presented as a class that is both a designative information content entity and is audited by a process. The `Execve` call, which executes a new program, is a critical control point. The axiom ensures that within the ontology, this entity is never modeled in isolation; it is intrinsically linked to the `bfo:0000015` process (the auditor) that captures its execution parameters, arguments, and return codes.

### 4.3.3 Verification and Governance

The enforcement of the `syscall_audited_by` axiom requires technical controls that verify the presence of the auditing process. In an eBPF context, this translates to ensuring that the tracepoint or kprobe associated with the system call is active and attached to a valid, running eBPF program. The governance framework must periodically validate that the `auditedBy` relationship holds true for the duration of the reporting period.

A failure in the auditing process (e.g., the eBPF program crashing or being unloaded) effectively severs the `auditedBy` relationship. Consequently, any subsequent system calls of the classes listed in Table 4.2 would no longer satisfy the axiom `syscall_audited_by`. From a compliance standpoint, this results in a "gap in coverage," which must be flagged as a material deficiency in the audit report. The ontology provides the logical structure to detect such gaps: if the entity `X` is present but the `auditedBy` relationship to `bfo:0000015` cannot be resolved, the integrity of the audit chain is compromised.

## 4.4 Summary of Schema Mappings

The definitions provided in this section map directly to the relational schema required for the persistence of these ontological structures. The following subsections detail the specific table structures that implement the axioms `syscall_basic` and `syscall_audited_by`.

### 4.4.1 Basic System Call Schema

The table `t_syscall_basic` implements the foundational classification of system calls as designative entities. The primary key is `id`, ensuring a unique identifier for each system call class. The column `x` contains the name of the class (e.g., `SyscallOpen`). This structure enforces the axiom that `X` is a subclass of `cco:DesignativeICE`.

### 4.4.2 Audited System Call Schema

The table `t_syscall_audited_by` implements the restricted classification of system calls that are subject to process auditing. While the schema structure is identical to the basic table in terms of columns (`id`, `x`), the semantic content is distinct. The rows in this table represent classes that satisfy the complex axiom including the `sdg:auditedBy` restriction. The presence of a row in this table asserts that for the class `X`, there exists a dependency on a `bfo:0000015` (Process) instance.
