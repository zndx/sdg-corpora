## 4.0 Scope and Preamble

This chapter delineates the formal ontological structures governing the classification of system calls within the eBPF kernel audit subsystem. It establishes the criteria for distinguishing between standard designative information content entities and those subject to strict auditing protocols via agent oversight. The definitions provided herein are binding for all compliance modules, security audits, and runtime monitoring frameworks deployed within the infrastructure. The objective is to ensure that every kernel primitive is mapped to a precise ontological class, thereby enabling automated reasoning over system behavior and facilitating the generation of immutable audit trails. This specification utilizes the Manchester Syntax for Web Ontology Language (OWL) definitions to enforce logical consistency across the distributed ledger of system events.

---

## 4.1 Designative Information Content Entities (Basic Syscalls)

### 4.1.1 Definition and Axiomatic Basis

The foundational unit of kernel interaction is the system call. Within the context of the Common Core Ontologies (CCO), a system call is not merely a function invocation but is formally classified as an Information Content Entity (ICE). Specifically, we address the subclass of entities that are *designative* in nature. A designative entity serves to identify or refer to a specific function or process within the operating system architecture.

The formal axiom defining this relationship is expressed in Manchester Syntax as:

**Class:** `{X}` **SubClassOf:** `cco:DesignativeICE`

**Verbalization:** {X} is a designative information content entity.

This axiom asserts that any class {X} categorized under this template is fundamentally a designation—a linguistic or symbolic token that stands for a specific kernel operation. This classification is critical for governance frameworks because it separates the *identity* of the operation from its *execution*. In audit logs, the preservation of the designative entity ensures that the intent of a process is recorded, even if the execution fails or is intercepted.

### 4.1.2 Relational Schema and Implementation

To implement this axiom within a relational database infrastructure supporting the audit framework, the following schema is mandated. This table, `t_syscall_basic`, serves as the registry for all system calls that function purely as designative entities without the immediate requirement of agent-based auditing in their base definition.

**Table 4.1: Basic Syscall Registry (t_syscall_basic)**

The primary key `id` serves as the unique identifier for the ontology class instance, while the column `x` represents the specific class name of the system call. This structure ensures that every designative entity is cataloged with a persistent reference key.

| id | x |
|---|---|
| sys_basic_001 | Syscall_Getpid |
| sys_basic_002 | Syscall_Getuid |
| sys_basic_003 | Syscall_Gettimeofday |
| sys_basic_004 | Syscall_Sched_yield |
| sys_basic_005 | Syscall_Getppid |

### 4.1.3 Compliance Profile for Designative Entities

Entities registered in `t_syscall_basic` are considered "low-risk" in terms of direct data manipulation but are "high-value" for session correlation. For instance, `Syscall_Getpid` (Process ID retrieval) does not alter the system state; however, it designates the identity of the requesting process. In compliance audits, these entities are used to construct the "actor" profile of a session.

When reviewing audit logs generated from these entities, the following fields must be present in the evidence package:
1.  **Timestamp:** Coordinated Universal Time (UTC) with microsecond precision.
2.  **Entity ID:** The `id` referenced from Table 4.1.
3.  **Return Value:** The standard integer return code, verifying the designation was resolved.

Failure to capture the designative entity accurately results in a "Broken Chain of Custody" error in forensic reconstruction, as the auditor cannot verify which process context initiated subsequent, higher-privilege operations.

## 4.2 Audited System Calls and Agent Relations

### 4.2.1 Definition and Axiomatic Basis

While all system calls are designative, a subset requires rigorous oversight due to their potential to modify system state, access protected resources, or alter security boundaries. These entities are not merely designative; they are *audited by* an independent continuant. In the Basic Formal Ontology (BFO), `bfo:0000015` denotes a "Process." In this context, it refers to the auditing agent or the monitoring process (e.g., an eBPF program attached to the kernel) that observes the syscall.

The formal axiom extending the basic definition is expressed as:

**Class:** `{X}` **SubClassOf:** `cco:DesignativeICE`, `sdg:auditedBy` some `bfo:0000015`

**Verbalization:** {X} is a designative information content entity that is audited by some process.

This axiom introduces a restriction. The class {X} is now logically dependent on the existence of an auditing process. If the auditing process (`bfo:0000015`) is not active or is compromised, the ontology dictates that the instantiation of {X} within the system is invalid for compliance purposes. This creates a hard dependency between operational execution and monitoring integrity.

### 4.2.2 Relational Schema and Implementation

The schema for audited syscalls, `t_syscall_audited_by`, mirrors the structure of the basic registry but semantically implies a join with an active process table. The presence of a row in this table indicates that the class {X} must trigger an audit event captured by a designated BFO Process.

**Table 4.2: Audited Syscall Registry (t_syscall_audited_by)**

The primary key `id` ensures referential integrity, while `x` denotes the syscall class subject to the `sdg:auditedBy` restriction. It is imperative that the monitoring daemon validates every invocation of these classes against this registry before permitting the operation to proceed to the virtual filesystem layer.

| id | x |
|---|---|
| sys_audit_001 | Syscall_Open |
| sys_audit_002 | Syscall_Connect |
| sys_audit_003 | Syscall_Execve |
| sys_audit_004 | Syscall_Mount |
| sys_audit_005 | Syscall_Chmod |

### 4.2.3 Audit Trail Specifications

For entities defined in `t_syscall_audited_by`, the audit trail must be significantly more granular than for basic designative entities. The "auditedBy" relationship necessitates the recording of the *observer* as well as the *actor*. The following data points constitute the minimum evidence requirement for a compliant audit record:

*   **Observer Process ID:** The PID of the eBPF collector or LSM (Linux Security Module) hook.
*   **Observer Timestamp:** The exact time the auditing process intercepted the syscall.
*   **Argument Vector:** A hex-encoded dump of the arguments passed to the syscall {X}.
*   **Decision Flag:** Allow/Deny, signed by the auditing process.

For example, consider `Syscall_Execve` (sys_audit_003). This syscall replaces the current process image with a new one. Because this fundamentally alters the trust boundary of the system, the axiom requires it be audited by a process (`bfo:0000015`). If the system attempts to execute a binary while the auditing process is suspended, the violation of the axiom `auditedBy some bfo:0000015` should trigger an immediate kernel panic or a halt to the execution flow, depending on the enforcement policy.

### 4.2.4 Governance and Verification

The distinction between the classes in Table 4.1 and Table 4.2 forms the basis of the "Two-Tier" governance model.

*   **Tier 1 (Basic):** Entities in `t_syscall_basic` are logged asynchronously. Their loss impacts session history but does not constitute a security breach.
*   **Tier 2 (Audited):** Entities in `t_syscall_audited_by` are logged synchronously. The execution of the syscall is blocked until the audit entry is committed to durable storage.

Verification of compliance involves sampling the audit logs and performing a join operation: `Log_Table JOIN t_syscall_audited_by ON Log_Table.syscall_class = t_syscall_audited_by.x`. Any `Syscall_Open` or `Syscall_Connect` event appearing in the raw kernel trace without a corresponding entry in the audit table generated by the auditing process constitutes a Class A Violation.

## 4.3 Summary of Ontological Mappings

The following matrix summarizes the logical progression from the generic concept of a designative entity to the specific, restricted case of an audited entity. This mapping is essential for architects implementing the eBPF control plane.

| Concept | Axiom Template | Ontological Class | Dependency |
|---|---|---|---|
| Basic Syscall | `syscall_basic` | `cco:DesignativeICE` | None (Self-contained) |
| Audited Syscall | `syscall_audited_by` | `cco:DesignativeICE` + `sdg:auditedBy` | Requires `bfo:0000015` (Process) |

In conclusion, the strict adherence to these axioms ensures that the system's behavior is not only observable but semantically grounded in a formal framework. This allows automated compliance tools to reason about system state, verify the presence of monitoring agents, and validate the integrity of the execution chain without manual intervention.
