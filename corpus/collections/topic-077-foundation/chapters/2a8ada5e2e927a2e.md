# Audit Trail Ontologies for Designative System Call Entities

This chapter defines two ontological templates that classify system-call records as designative information content entities and links them to audit processes. The templates are realized in a minimal relational schema drawn from kernel audit logs. Four tables are presented; primary keys and foreign keys are stated explicitly so that multi-table joins recover the full provenance of any audited call.

## 1. Scope and Table Overview

Two axioms govern the model. The first states that a class of system-call records is a designative information content entity. The second states that the same class is audited by a process. These axioms are projected to tables t_syscall_basic and t_syscall_audited_by. Two supporting tables, t_process and t_audit_event, supply the process instances required by the second axiom and the event context needed for cross-table queries.

### 1.1 t_process

The table embodies the bfo:0000015 process that appears in the auditedBy restriction. Its primary key is id. No foreign keys are present; every row represents an independent audit process instance.

| id | name |
|----|------|
| p1 | eBPF audit daemon |
| p2 | kernel auditd |
| p3 | seccomp tracer |

### 1.2 t_syscall_basic

The table directly implements axiom 1. Column id is the primary key. Column x holds the class name of the designative information content entity.

| id | x |
|----|---|
| s1 | sys_open |
| s2 | sys_read |
| s3 | sys_write |
| s4 | sys_close |

### 1.3 t_syscall_audited_by

The table implements axiom 2. Column id is the primary key. Column x references a row in t_syscall_basic, thereby asserting that the designative entity is audited by a process. The foreign-key relationship permits a reader to retrieve the audited class for any given audit record.

| id | x |
|----|---|
| a1 | s1 |
| a2 | s2 |
| a3 | s3 |
| a4 | s4 |

### 1.4 t_audit_event

The table supplies concrete event instances that link a process to an audited system call. Column id is the primary key. Column process_id is a foreign key to t_process.id. Column syscall_id is a foreign key to t_syscall_basic.id.

| id | process_id | syscall_id | timestamp |
|----|------------|------------|-----------|
| e1 | p1 | s1 | 2023-10-05 08:12:01 |
| e2 | p2 | s2 | 2023-10-05 08:12:03 |
| e3 | p1 | s3 | 2023-10-05 08:12:05 |
| e4 | p3 | s4 | 2023-10-05 08:12:07 |

## 2. Cross-Join Example

Question: which process audited the sys_read call recorded at 08:12:03?

Start at t_audit_event where timestamp = '2023-10-05 08:12:03'. The row yields process_id = p2 and syscall_id = s2.  
Join t_process on id = p2 to obtain name = 'kernel auditd'.  
Join t_syscall_basic on id = s2 to confirm class = 'sys_read'.  
The joined result row is therefore (e2, p2, 'kernel auditd', s2, 'sys_read', '2023-10-05 08:12:03').
