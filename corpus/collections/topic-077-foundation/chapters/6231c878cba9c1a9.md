# Chapter 4: Ontological Foundations of Kernel Audit Entities

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the identification and classification of kernel-level system calls within the context of the eBPF Monitoring Framework. The objective is to establish a rigorous, evidence-based taxonomy for information content entities (ICEs) that facilitates automated compliance auditing and real-time security governance. The definitions provided herein are derived from the upper-level ontologies of the Basic Formal Ontology (BFO) and the Information Artifact Ontology (IAO), specifically instantiated for the Linux kernel environment. The following sections present the axiomatic definitions for basic designative entities and their audited counterparts, supported by relational data schemas that serve as the canonical registry for implementation.

## 4.2 Basic Designative Information Content Entities

### 4.2.1 Axiomatic Definition

In the context of kernel instrumentation, a fundamental distinction must be made between the physical execution of a system call and the informational representation of that call. The latter is categorized as a Designative Information Content Entity (DesignativeICE). As defined by Axiom 1 (`syscall_basic`), any class {X} representing a system call is a subclass of `cco:DesignativeICE`.

The Manchester syntax for this axiom is expressed as:
`Class: {X:Class} SubClassOf: cco:DesignativeICE`

Verbalized, this asserts that the entity {X} is a designative information content entity. This means that {X} serves as a specific data structure or token that "stands for" the system call within the operating system's semantic framework. It does not denote the execution process itself (which would be a temporal process), but rather the static definition or the informational payload associated with the syscall interface. This distinction is critical for audit logs, which must record the *intent* and *definition* of an action separate from its temporal occurrence to ensure data integrity during forensic analysis.

### 4.2.2 Implementation Registry

To ensure consistency across the monitoring infrastructure, all recognized system calls are registered in the `t_syscall_basic` table. This table serves as the primary lookup mechanism for the audit daemon, mapping unique identifiers to the specific class definitions of the system calls. The primary key is the `id` field, which provides a stable, non-volatile reference, while the `x` field contains the canonical class name of the system call as defined in the kernel source headers.

The following table presents a subset of the registry, illustrating the mapping for standard file descriptor operations. These entries represent the baseline inventory of designative entities that the system is capable of recognizing.

| id | x |
|---|---|
| SYSCALL-001 | sys_read |
| SYSCALL-002 | sys_write |
| SYSCALL-003 | sys_open |
| SYSCALL-004 | sys_close |
| SYSCALL-005 | sys_stat |
| SYSCALL-006 | sys_fstat |
| SYSCALL-007 | sys_lstat |

**Table 4.1: Basic Designative Entities Registry (`t_syscall_basic`)**

The data in Table 4.1 demonstrates the application of Axiom 1. Each value in column `x` is a Class that fulfills the definition of a `cco:DesignativeICE`. For instance, `sys_read` is not merely a function address; it is a designative entity encapsulating the specification for reading from a file descriptor. The registry ensures that when an event is logged, the informational content entity referenced is unambiguously defined and traceable to this canonical list.

### 4.2.3 Governance Implications

From a governance perspective, the classification of an entity as a DesignativeICE is the prerequisite for any subsequent monitoring activity. Without this formal designation, a system call exists functionally within the kernel but remains opaque to the semantic layer of the audit framework. By populating `t_syscall_basic`, compliance officers establish the "universe of discourse" for the audit subsystem. Any system call invoked within the kernel environment that lacks a corresponding entry in this table is, by definition, excluded from the semantic audit trail, creating a potential blind spot in security monitoring. Therefore, the maintenance of this table is a key control objective for system administrators.

## 4.3 Audited Designative Entities

### 4.3.1 Axiomatic Definition and Process Constraints

While the basic designation of system calls provides the necessary taxonomy, it does not imply active monitoring. To transition from a static definition to an active compliance control, a further constraint is applied via Axiom 2 (`syscall_audited_by`). This axiom introduces a relational dependency between the designative entity and an independent process responsible for the audit.

The Manchester syntax for this axiom is:
`Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`

Verbalized, this asserts that {X} is a designative information content entity that is audited by some process. Here, `bfo:0000015` refers to the BFO class "Process." In the context of the eBPF framework, this Process represents the eBPF program or the associated userspace daemon that observes the kernel event. The axiom creates a complex restriction: a system call is only considered an "Audited Designative Entity" if there exists a realized process instance that performs the auditing action.

This distinction separates the general population of system calls (Axiom 1) from the subset subject to regulatory or security scrutiny (Axiom 2). It enforces the principle that monitoring is not inherent but must be explicitly instantiated through a process relationship.

### 4.3.2 Registry of Audited Entities

The `t_syscall_audited_by` table maintains the list of system calls that are currently subject to active monitoring by an auditing process. The structure mirrors the basic table but represents a distinct logical set. The presence of a row in this table signifies that the `sdg:auditedBy` relationship has been satisfied for that specific class of system call.

The following table details the audited entities for a standard secure baseline configuration. Note that this set is a subset of the general designative entities, focusing on operations with high security impact (e.g., process execution, privilege changes, network communication).

| id | x |
|---|---|
| AUDIT-100 | sys_execve |
| AUDIT-101 | sys_fork |
| AUDIT-102 | sys_clone |
| AUDIT-103 | sys_connect |
| AUDIT-104 | sys_accept |
| AUDIT-105 | sys_bind |
| AUDIT-106 | sys_mount |

**Table 4.2: Audited Designative Entities Registry (`t_syscall_audited_by`)**

In Table 4.2, the `x` column lists the specific classes (e.g., `sys_execve`) that are subclasses of `cco:DesignativeICE` *and* participate in the `sdg:auditedBy` relationship with a BFO Process. The `id` column provides a unique reference for the audit rule itself. For example, the entry for `sys_mount` indicates that the system call responsible for mounting file systems is not only recognized as a designative entity but is also actively monitored by a process (likely an eBPF verifier attached to the `sys_mount` tracepoint) to detect unauthorized file system tampering.

### 4.3.3 Verification and Compliance

The separation between `t_syscall_basic` and `t_syscall_audited_by` allows for granular compliance reporting. Auditors can query the schema to verify that for every high-risk operation defined in the security policy, a corresponding entry exists in `t_syscall_audited_by`. The absence of an entry for a critical syscall (such as `sys_setuid`) would constitute a finding of non-compliance, indicating that while the system recognizes the call (it exists in the basic ontology), no process is actively auditing it.

Furthermore, the reliance on `bfo:0000015` (Process) ensures that the audit trail is grounded in observable activity. The "audited by" relationship is not merely a metadata tag; it implies the existence of a running process consuming kernel events. This linkage allows the framework to correlate the *definition* of the syscall (the DesignativeICE) with the *mechanism* of observation (the Process), providing a closed loop of evidence essential for high-assurance environments.
