# Chapter 4: Taxonomy of Kernel Interfaces and Audit Control Mechanisms

This chapter establishes the formal ontology governing the classification of system calls within the secure kernel environment, specifically focusing on their designation as information content entities and their relationship to audit processes. The definitions provided herein are binding for all subsequent compliance verification reports and serve as the foundational schema for mapping kernel-level vectors to regulatory requirements. It delineates the criteria for identifying designative entities and specifies the constraints for audit-enabled interfaces, ensuring that system architecture adheres to the strictures of the Information Content Ontology (ICO) and Basic Formal Ontology (BFO).

## 1. Designative Information Content Entities in Kernel Space

The classification of kernel interfaces begins with the formal recognition of system calls as designative information content entities. In accordance with the ontology axiom `syscall_basic`, a system call is not merely a functional entry point into kernel space; it is a distinct informational entity that designates a specific process or capability. This distinction is critical for maintaining the separation between the executable code (the realization) and the symbolic identifier (the designation) within the compliance artifact. By treating these interfaces as instances of `cco:DesignativeICE`, auditors can verify that the semantic intent of the interface is preserved across version iterations without requiring analysis of the underlying binary implementation.

### 1.1 Theoretical Framework

The concept of a "Designative Information Content Entity" (DesignativeICE) posits that the entity exists primarily to "stand for" or "refer to" another entity within the system. In the context of the kernel, the class `SyscallRead` does not constitute the act of reading data itself; rather, it designates the *potential* for such an act. This ontological commitment allows for a layer of abstraction where security policies can be applied to the *designation* of the call (the name and its defined parameters) rather than the volatile memory address of the function pointer.

This abstraction facilitates rigorous static analysis. When a system call is registered within the kernel's syscall table, it is manifesting as a designative entity. The stability of this designation is a primary concern for governance frameworks. If the designation changes—meaning the syscall number or the semantic mapping of the identifier is altered—it constitutes a breaking change in the information model, triggering a requirement for re-certification under standard regulatory bodies such as the Financial Industry Regulatory Authority (FINRA) or the National Institute of Standards and Technology (NIST).

### 1.2 Implementation and Classification

To operationalize this axiom, the kernel maintains a registry of classes where each valid system call is treated as a subclass of the generic designative entity. This registry is not merely a symbol table; it is a structured compliance database. Each entry must be traceable to a requirement specification document that defines the expected behavior of the designation.

For example, the class `SyscallWrite` is defined as a designative entity that refers to the kernel's write vector. The validity of this entity is contingent upon its adherence to the defined signature (file descriptor, buffer, count). If the implementation changes to accept a memory map instead of a buffer pointer, the designation `SyscallWrite` may no longer be valid, or it may require a new class definition (e.g., `SyscallWriteV2`) to maintain ontological consistency.

## 2. Audit-Dependent Interface Classes

While the designation of system calls provides the necessary taxonomy for interface management, it does not inherently address the governance requirement for observability. In high-assurance systems, particularly those handling financial transactions or controlled unclassified information (CUI), the ability to observe and record the invocation of specific interfaces is mandated by policy. This requirement is formalized through the ontology axiom `syscall_audited_by`.

This axiom extends the definition of a system call class by adding a restriction: the entity must be audited by a process. Specifically, the axiom states that the class `{X}` is a SubClass of `cco:DesignativeICE` AND `sdg:auditedBy` some `bfo:0000015`. Here, `bfo:0000015` refers to a "Process" in the Basic Formal Ontology—a temporal sequence of events that occurs in time. Therefore, this axiom asserts that for a system call to be classified under this specific taxonomy, its invocation must trigger a distinct, temporal auditing process.

### 2.1 The Audit Process Constraint

The inclusion of `bfo:0000015` as an object property filler is significant. It moves the compliance requirement from a static classification (the name of the call) to a dynamic behavioral guarantee (the observation of the call). The "auditing process" is not merely a logging function; it is a formally defined BFO process that must have a start time, an end time, and a participant (the auditor).

In practical terms, this implies that the kernel must utilize a hooking mechanism—such as Linux Security Modules (LSM) or extended Berkeley Packet Filter (eBPF) programs—to intercept the execution of the designated class. When `SyscallClone` is invoked, the audit process (the `bfo:0000015` instance) is instantiated. This process gathers metadata (caller PID, arguments, return value) and commits it to an immutable ledger. If the kernel cannot guarantee that this process occurs synchronously with the invocation, the class `SyscallClone` cannot be validly categorized under the `syscall_audited_by` axiom.

### 2.2 Governance and Compliance

From a governance perspective, this axiom allows auditors to query the system ontology to identify which interfaces are "high-value" targets for monitoring. It provides a deterministic mapping between the interface class and the security control. If a regulatory guide specifies that "all process creation primitives must be audited," the compliance officer can verify that `SyscallClone` and `SyscallExecve` are correctly axiomatized as `SubClassOf` `syscall_audited_by`.

Failure to maintain this mapping—such as a kernel update that disables the audit hook for `SyscallOpen`—effectively breaks the axiom. The class `SyscallOpen` would still exist, but it would no longer satisfy the necessary and sufficient conditions of the `syscall_audited_by` restriction. In a formal audit environment, this would be reported as a "Control Deficiency" or "Finding."
