# Kernel Audit Ontologies for eBPF Designative Entities

This chapter defines two ontological distinctions for designative information content entities that record kernel system calls and demonstrates them in an audit-trail schema. The schema supports cross-table queries that recover the full provenance of an audited event from its identifier through its controlling process.

## 1. Designative Information Content Entities

Axiom 1 states that any class X is a designative information content entity when it functions solely to designate a kernel occurrence. The corresponding table isolates the class name so that every row is an instance of cco:DesignativeICE.

### 1.1 t_syscall_basic
Table t_syscall_basic embodies Axiom 1. Column id is the primary key that uniquely identifies each designative class. Column x holds the class name itself. No foreign keys are present because the axiom asserts only subclass membership.

| id | x |
|----|---|
| scb-01 | SyscallEntry |
| scb-02 | SyscallExit |
| scb-03 | FileDescriptor |
| scb-04 | ProcessIdentifier |
| scb-05 | MemoryMapping |

## 2. Audited Designative Entities

Axiom 2 extends the first by requiring that the designative entity be auditedBy some bfo:0000015 (process). The table therefore records only those classes that participate in an audit relation.

### 2.1 t_syscall_audited_by
Table t_syscall_audited_by embodies Axiom 2. Column id is the primary key. Column x again holds the class name, now restricted to those classes that stand in the auditedBy relation. The table therefore functions as a foreign-key target for any subsequent audit-event table.

| id | x |
|----|---|
| sab-01 | SyscallEntry |
| sab-02 | SyscallExit |
| sab-03 | FileDescriptor |

## 3. Supporting Audit Process and Evidence Tables

Two additional tables complete the minimal schema that satisfies the foreign-key requirements while remaining consistent with the axioms. Both reference the audited classes defined above.

### 3.1 t_audit_process
Table t_audit_process records the bfo:0000015 processes that perform auditing. Column process_id is the primary key. Column audited_class_id is a foreign key referencing t_syscall_audited_by.id, establishing the auditedBy link required by Axiom 2.

| process_id | audited_class_id | start_time | operator |
|------------|------------------|------------|----------|
| ap-001 | sab-01 | 2024-03-12T08:40:00 | eBPF probe 1 |
| ap-002 | sab-02 | 2024-03-12T08:41:15 | eBPF probe 2 |
| ap-003 | sab-03 | 2024-03-12T08:42:30 | eBPF probe 1 |
| ap-004 | sab-01 | 2024-03-12T09:05:00 | eBPF probe 3 |

### 3.2 t_evidence
Table t_evidence stores concrete audit records. Column evidence_id is the primary key. Column process_id is a foreign key referencing t_audit_process.process_id. Column syscall_class_id is a foreign key referencing t_syscall_basic.id, allowing a reader to confirm that only designative classes participate in evidence rows.

| evidence_id | process_id | syscall_class_id | target_pid | return_code |
|-------------|------------|------------------|------------|-------------|
| ev-1001 | ap-001 | scb-01 | 4721 | 0 |
| ev-1002 | ap-002 | scb-02 | 4721 | 0 |
| ev-1003 | ap-003 | scb-03 | 4819 | 5 |
| ev-1004 | ap-004 | scb-01 | 4902 | 0 |
| ev-1005 | ap-001 | scb-01 | 4902 | 0 |

## 4. Cross-Join Example

To recover the operator, start time, and return code for every audited SyscallEntry event, join the four tables on the foreign-key chain:

```
t_evidence
  JOIN t_audit_process ON t_evidence.process_id = t_audit_process.process_id
  JOIN t_syscall_audited_by ON t_audit_process.audited_class_id = t_syscall_audited_by.id
  JOIN t_syscall_basic ON t_evidence.syscall_class_id = t_syscall_basic.id
WHERE t_syscall_basic.x = 'SyscallEntry'
```

The join yields three rows:

- ev-1001, ap-001, eBPF probe 1, 2024-03-12T08:40:00, 4721, 0
- ev-1004, ap-004, eBPF probe 3, 2024-03-12T09:05:00, 4902, 0
- ev-1005, ap-001, eBPF probe 1, 2024-03-12T08:40:00, 4902, 0
