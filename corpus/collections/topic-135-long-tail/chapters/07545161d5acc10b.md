# Chapter 4: Quantitative Correlation of Regulatory Directives and Baseline Security Metrics

## 4.1 Scope and Preamble

This chapter delineates the formal ontological mapping between regulatory compliance frameworks—specifically the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA)—and the quantitative metrics used to assess their efficacy. The objective is to establish a rigorous, evidence-based correlation between high-level directives (DirectiveICE) and observable security phenomena (DescriptiveICE). By defining the relational structure of these concepts, we enable a deterministic audit trail where compliance requirements are anchored to statistical baselines, evidence correlation, and null-rate profiling. This approach moves beyond binary compliance checks toward a continuous, quantitative assessment of security posture.

## 4.2 PCI DSS Requirements and Directive Mapping

The foundational element of this ontology is the classification of regulatory mandates as instances of `cco:DirectiveICE`. Specifically, we examine the structural properties of PCI DSS requirements through the axiom `pci_dss_requirement`. This axiom posits that a specific requirement class (X) is a subclass of `cco:DirectiveICE` and possesses a `sdg:pciDssRequirement` relationship to a target class (Y). In practical terms, this formalizes the assertion that a specific control objective is mandated by a particular PCI DSS clause.

To illustrate this mapping, we must consider the "lift" or performance impact of a requirement. The ontology dictates that the target of a PCI requirement (Y) is not merely a static control but a measurable metric class, specifically one that involves a baseline rate. This linkage ensures that every requirement is tied to a quantifiable outcome. For instance, a requirement regarding firewall configuration is not satisfied by the existence of the configuration alone, but by the measurable reduction in unauthorized traffic flows relative to a baseline.

The following table embodies the `t_pci_dss_requirement` schema. It enumerates specific PCI requirements (X) and links them to the specific baseline metrics (Y) they are designed to influence. The primary key is the unique identifier for the requirement mapping, while the foreign key (`y`) references the specific metric instance defined in the baseline rate tables, ensuring referential integrity between the directive and the measurement.

**Table 4.1: PCI DSS Requirement to Baseline Metric Mapping**

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_01 | Requirement1FirewallConfiguration | LIFT_NET_001 |
| PCI_REQ_02 | Requirement2DefaultPasswords | LIFT_AUTH_001 |
| PCI_REQ_03 | Requirement3StoredDataEncryption | LIFT_ENC_001 |
| PCI_REQ_04 | Requirement4EncryptionTransmission | LIFT_NET_002 |
| PCI_REQ_05 | Requirement5AntiVirusSoftware | LIFT_MAL_001 |

In this schema, `PCI_REQ_01` represents the specific directive class for firewall configuration. The column `y` (`LIFT_NET_001`) acts as a foreign key pointing to the lift metric associated with network traffic. This relationship asserts that the directive is substantiated by the performance of that specific metric.

## 4.3 Baseline Rate Analysis and Lift Metrics

The concept of "lift" in this context refers to the magnitude of deviation from a standard security baseline. The axiom `lift_with_baseline_rate` defines a class (X) as a subclass of `cco:DescriptiveICE` that possesses a `sdg:hasBaselineRate` relationship with another class (Y). This structure is critical for distinguishing between raw data and actionable intelligence. A "lift" metric is meaningless without a reference point; the baseline rate provides that reference, allowing auditors to determine if a control is performing within acceptable parameters.

For example, a "Failed Login Lift" metric describes the rate at which failed login attempts exceed the established baseline. The axiom asserts that this metric class *has* a baseline rate, which might be defined as the average number of failures over a 30-day period. The relational projection of this axiom, `t_lift_with_baseline_rate`, captures the dependencies between the metric class and the evidence class that constitutes its baseline.

The table below presents the `t_lift_with_baseline_rate` structure. The primary key (`id`) identifies the specific lift metric instance. The column `x` denotes the metric class itself, while `y` (a foreign key) references the evidence class that provides the baseline data. This structure enforces the rule that a lift metric cannot exist independently of its defining evidence.

**Table 4.2: Lift Metrics and Associated Baseline Evidence**

| id | x | y |
| :--- | :--- | :--- |
| LIFT_NET_001 | InboundTrafficLift | EVID_NET_001 |
| LIFT_AUTH_001 | AuthenticationFailureLift | EVID_AUTH_001 |
| LIFT_ENC_001 | CryptoOperationLift | EVID_CPU_001 |
| LIFT_NET_002 | EgressTrafficLift | EVID_NET_002 |
| LIFT_MAL_001 | MalwareDetectionLift | EVID_FS_001 |

Here, `LIFT_NET_001` (Inbound Traffic Lift) is directly linked to `EVID_NET_001`. This linkage implies that the calculation of lift for inbound traffic is strictly derived from the evidence corpus identified by `EVID_NET_001`.

## 4.4 Evidence Correlation Mechanisms

To validate the efficacy of the baseline metrics, we must establish a correlation between observed evidence and the lift metrics. The axiom `evidence_correlated_with` formalizes this by stating that a class (X), a `cco:DescriptiveICE`, has a `sdg:evidenceCorrelatedWith` relationship with another class (Y). This creates a feedback loop within the ontology: evidence is used to establish a baseline, but that evidence is also correlated with other lift metrics, revealing systemic dependencies or causal chains in security events.

For instance, evidence of "Port Scanning" might be correlated with "Inbound Traffic Lift." The relational schema `t_evidence_correlated_with` captures these relationships. The foreign key constraint in this schema is particularly notable: the target (`y`) must reference a valid lift metric (`t_lift_with_baseline_rate`). This constraint enforces the logic that evidence correlation is not an abstract property but a specific link to a defined quantitative metric.

The following table details these correlations. The `id` serves as the unique identifier for the correlation instance. The `x` column represents the evidence class, while `y` references the lift metric ID, thereby closing the loop between observation and measurement.

**Table 4.3: Evidence Correlation with Lift Metrics**

| id | x | y |
| :--- | :--- | :--- |
| EVID_NET_001 | ExternalPortScanEvidence | LIFT_NET_002 |
| EVID_AUTH_001 | BruteForceAttemptEvidence | LIFT_AUTH_001 |
| EVID_CPU_001 | AsymmetricCryptoLoadEvidence | LIFT_ENC_001 |
| EVID_NET_002 | DataExfiltrationAttemptEvidence | LIFT_NET_001 |
| EVID_FS_001 | SuspiciousFileWriteEvidence | LIFT_MAL_001 |

In this configuration, `EVID_NET_001` (External Port Scan Evidence) is correlated with `LIFT_NET_002` (Egress Traffic Lift). This suggests that port scanning activity is statistically linked to subsequent egress traffic anomalies, providing a predictive indicator for compliance monitoring.

## 4.5 Null Rate Profiling in Compliance Data

Data integrity is a paramount concern in audit reporting. The axiom `profile_has_null_rate` addresses this by defining a class (X) that possesses a `sdg:hasNullRate` relationship with a class (Y). This axiom allows the ontology to describe the sparsity or incompleteness of data within a specific compliance profile. A high null rate in a critical log field (e.g., "User ID" in an access log) can significantly degrade the reliability of the associated lift metrics.

The relational schema `t_profile_has_null_rate` maps a specific profile class (X) to the evidence class (Y) that exhibits the null rate. The foreign key constraint requires that the evidence class (`y`) be a valid instance in the evidence correlation table. This ensures that null rates are not tracked in isolation but are associated with specific, defined evidence streams.

**Table 4.4: Profile Null Rate Associations**

| id | x | y |
| :--- | :--- | :--- |
| PROF_AUD_01 | SystemAccessLogProfile | EVID_AUTH_001 |
| PROF_AUD_02 | NetworkFlowLogProfile | EVID_NET_001 |
| PROF_AUD_03 | FileSystemChangeProfile | EVID_FS_001 |
| PROF_AUD_04 | KeyManagementProfile | EVID_CPU_001 |
| PROF_AUD_05 | DLPAlertProfile | EVID_NET_002 |

For example, `PROF_AUD_01` (System Access Log Profile) is associated with `EVID_AUTH_001`. This indicates that the null rate calculation for the access log profile is derived from the evidence stream of brute force attempts, perhaps highlighting that during such attacks, logging mechanisms may fail to capture user identifiers, resulting in null data.

## 4.6 HIPAA Physical Safeguards and Metric Integration

While the previous sections focused on logical and technical controls, physical security remains a critical component of the compliance landscape, particularly under HIPAA. The axiom `hipaa_safeguard_physical` defines a class (X) as a `cco:DirectiveICE` that implements a `sdg:hipaaSafeguard` relationship with a target class (Y). Similar to the PCI requirements, this maps a physical safeguard directive to a measurable metric.

The relational schema `t_hipaa_safeguard_physical` enforces the integration of physical controls into the quantitative framework. The foreign key (`y`) must reference a lift metric (`t_lift_with_baseline_rate`). This requirement ensures that physical safeguards, such as facility access controls, are subject to the same rigorous baseline measurement as logical controls. For example, a "Workstation Use" policy is not merely a document; it is a directive correlated with the lift metric of "Unauthorized Physical Access Attempts."

**Table 4.5: HIPAA Physical Safeguard Mapping**

| id | x | y |
| :--- | :--- | :--- |
| HIPAA_PHYS_01 | FacilityAccessControlPolicy | LIFT_AUTH_001 |
| HIPAA_PHYS_02 | WorkstationSecurityPolicy | LIFT_MAL_001 |
| HIPAA_PHYS_03 | DeviceAndMediaControlPolicy | LIFT_NET_001 |
| HIPAA_PHYS_04 | ContingencyOperationsPolicy | LIFT_ENC_001 |
| HIPAA_PHYS_05 | FacilitySecurityValidation | LIFT_NET_002 |

In this table, `HIPAA_PHYS_01` (Facility Access Control Policy) is linked to `LIFT_AUTH_001` (Authentication Failure Lift). This creates a fascinating cross-domain correlation, suggesting that the enforcement of physical access controls is statistically linked to authentication metrics—perhaps implying that physical proximity to terminals affects digital authentication failure rates.
