# Chapter 4: Ontological Verification of Audit Artifacts and Outlier Claims

This chapter delineates the formal ontological structures required to govern the identification, classification, and evidentiary support of anomalies within regulated datasets. The text provides a rigorous examination of four primary axioms—Dataset Under Audit, Trace Supports Claim, Outlier Claim Basic, and Outlier Claim Min One Attribute—establishing the necessary logical constraints for high-assurance reporting environments. It is intended that these definitions serve as the foundational schema for automated compliance engines and manual audit protocols alike, ensuring that all assertions regarding data integrity are traceable to verifiable processes.

## 1. Dataset Under Audit

### 1.1 Definition and Scope
The fundamental unit of analysis in any forensic data review is the container of the information itself, formally defined as the Dataset Under Audit. Per the governing axiom, a Dataset Under Audit is a specific subclass of an Information Content Entity (ICE) that is Artifact in nature and is currently subject to an audit process. The distinction here is critical: the entity is not merely a static repository of data (an Artifact) but is dynamically engaged in a Process (the audit). This ontological commitment ensures that governance frameworks do not merely catalog data but actively track the procedural lifecycle of that data as it moves through verification stages.

In practical terms, the classification of an entity as a Dataset Under Audit triggers specific retention and access logging requirements. The artifact must be immutable or its mutability strictly controlled while the `bfo:Process` (the audit) is active. This prevents the alteration of evidence during the examination period. The relational projection of this axiom requires a unique identifier for the dataset and a reference to the class of the artifact being examined.

### 1.2 Operational Context
When an auditor initiates a review, the first procedural step is the ingestion of the target data into the secure environment. At this moment, the system instantiates a record in the logical registry corresponding to the `t_dataset_under_audit` schema. The integrity of the audit trail relies on the accurate mapping of the physical file or database view to this logical entry.

Consider a scenario involving the review of quarterly transaction logs. The artifact is the log file itself; the process is the audit. The following table illustrates the instantiation of this axiom for three distinct artifacts currently under review. Note that the `id` serves as the primary key, ensuring that every artifact under audit is uniquely referenced within the governance framework.

| DS-2023-Q4-LED | GeneralLedger_Electronic_Copy |

**Table 1.1: Registry of Artifacts Subject to Audit Process**

The entries in Table 1.1 demonstrate that the entity `x` represents the specific artifact instance. The `id` prefix `DS` denotes the Dataset class, followed by a temporal and functional identifier. This naming convention is mandated to facilitate rapid retrieval and cross-referencing during the evidentiary phase of the audit.

## 2. Trace Supports Claim

### 2.1 The Evidentiary Link
A claim regarding data quality or compliance is vacuous without supporting evidence. The ontology defines a Trace as a specific type of process (`bfo:0000015`, a Process) that actively supports a Claim, which is itself a Descriptive Information Content Entity (DescriptiveICE). This axiom establishes the "Trace Supports Claim" relationship. It is pivotal to note that the Trace is defined as a process; it is not a static document but the act of verification, the generation of a hash, or the execution of a validation script that produces the support for the claim.

This distinction separates raw data (which might be circumstantial) from processed evidence. The Trace is the bridge between the observation of an anomaly and the formal assertion of that anomaly. In a regulatory context, this means that an auditor cannot simply assert a finding; they must point to a specific process (the Trace) that generated the support for that assertion.

### 2.2 Verification Processes
The instantiation of a Trace Supports Claim entity typically occurs after an automated or manual verification procedure. For instance, a cryptographic hash generation is a process that supports the claim that a file has not been altered. Similarly, a cross-reference check between two distinct ledgers is a process that supports the claim of consistency.

The relational schema for this concept captures the identifier of the trace process and the nature of the trace itself (`x`). The following table provides examples of trace processes instantiated during the audit of the datasets listed in Section 1.

| id | x |
| :--- | :--- |
| TR-HASH-001 | CryptographicHashVerification_SHA256 |
| TR-XREF-002 | LedgerCrossReferenceProcess_ID_Match |
| TR-MAN-003 | ManualReviewProcess_Anomaly_7B |

**Table 2.1: Log of Verification Processes Supporting Claims**

In Table 2.1, the `id` values (e.g., `TR-HASH-001`) act as the primary keys for these processes. These identifiers will later serve as foreign keys in more complex claims, linking the assertion of an anomaly directly to the specific verification process that substantiated it. The `x` column describes the class or specific type of process undertaken, ensuring that the methodology of the support is transparent.

## 3. Outlier Claim Basic

### 3.1 Descriptive Information Content Entities
The most granular level of audit finding is the Outlier Claim Basic. This axiom defines any Outlier Claim as a subclass of a Descriptive Information Content Entity (DescriptiveICE). A DescriptiveICE is an entity that is about something—it conveys meaning, asserts a fact, or describes a state of affairs. In the context of this ontology, the Outlier Claim Basic is the assertion that a specific data point or pattern deviates from the expected norm.

Unlike the "Trace," which is a process, the "Claim" is a static informational entity. It is the record of the finding. The "Basic" variant of this claim does not, in itself, contain the detailed evidence or attributes; it is merely the assertion that an outlier exists. This separation allows the ontology to distinguish between the *existence* of a finding and the *substantiation* of that finding.

### 3.2 Classification of Anomalies
When an automated system flags a transaction that exceeds a defined threshold, or when a manual auditor identifies a missing signature, an Outlier Claim Basic is generated. This claim is the formal entry into the audit register. It serves as the anchor for further investigation.

The schema for the Outlier Claim Basic is structurally simple, consisting of an identifier and the claim content (`x`). However, the semantic weight is significant. The population of this table represents the official record of identified anomalies. The table below illustrates three basic outlier claims identified during the audit period.

| id | x |
| :--- | :--- |
| OC-VAL-001 | TransactionAmountExceedsThreshold_500k |
| OC-TIM-002 | TimestampOutsideBusinessHours |
| OC-AUTH-003 | UserAuthorization_Breach_Attempt |

**Table 3.1: Registry of Basic Outlier Claims**

Each entry in Table 3.1 (`OC-VAL-001`, etc.) represents a distinct assertion. The `x` value provides a textual classification of the anomaly. These claims are "Descriptive" because they describe a specific state of the data (e.g., a value is too high). At this stage in the ontology, these claims stand alone; they have not yet been explicitly linked to the traces that support them. That linkage is the function of the next, more complex axiom.

## 4. Outlier Claim Min One Attribute

### 4.1 Complex Claims and Attribute Binding
While a basic claim asserts the existence of an anomaly, a rigorous audit requires that the claim be substantiated by attributes—specifically, traces that support the claim. The axiom "Outlier Claim Min One Attribute" defines a subclass of Outlier Claims that are DescriptiveICEs and must possess a minimum of one attribute from a defined set. In this ontological framework, the "Attribute" is structurally bound to the Trace Supports Claim entity defined in Section 2.

This relationship enforces the "min 1" constraint, meaning a claim cannot exist in this complex state unless it is associated with at least one valid trace process. This is a critical validation rule for the audit database; it prevents the logging of "unsubstantiated" outliers in the final report. Only claims that have successfully passed through a verification process (generating a Trace) are elevated to this status.

### 4.2 Relational Integrity and Foreign Keys
The relational schema for this concept introduces a dependency. The table `t_outlier_claim_min_one_attribute` contains a foreign key constraint on column `y`, which must reference the `id` of a row in `t_trace_supports_claim`. This enforces the logical axiom that the attribute (the evidence) must be a valid, registered process.

The following table demonstrates how the basic claims introduced in Section 3 are elevated to substantiated claims by linking them to the traces listed in Section 2.

| id | x | y |
| :--- | :--- | :--- |
| OC-SUB-001 | TransactionAmountExceedsThreshold_500k | TR-HASH-001 |
| OC-SUB-002 | TimestampOutsideBusinessHours | TR-XREF-002 |
| OC-SUB-003 | UserAuthorization_Breach_Attempt | TR-MAN-003 |

**Table 4.1: Substantiated Outlier Claims with Supporting Attributes**

In Table 4.1, the `id` column (`OC-SUB-001`, etc.) identifies the specific complex claim instance. The `x` column restates the nature of the claim (the DescriptiveICE). The `y` column provides the critical link: `OC-SUB-001` is valid only because `TR-HASH-001` (the hash verification process) exists and supports it. This structure ensures that every reported anomaly in the final audit output is anchored to a verifiable procedural history, satisfying the requirements for evidence-based governance.
