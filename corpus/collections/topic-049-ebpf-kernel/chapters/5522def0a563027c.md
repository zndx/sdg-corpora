# Chapter 4: Ontological Formalization of Audit Evidence and Outlier Detection

This chapter delineates the formal ontological structures required to represent audit evidence, specifically focusing on the identification and substantiation of outlier claims within regulated datasets. The content herein establishes a rigorous framework for mapping descriptive information content entities (ICEs) to their supporting processes and artifacts, ensuring compliance with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). The definitions provided are essential for maintaining the integrity of audit trails and facilitating automated reasoning over compliance datasets.

## 4.1 Basic Outlier Claims

In the context of audit governance, a fundamental requirement is the precise categorization of assertions that deviate from expected norms. The **Outlier Claim Basic** axiom provides the primary structural definition for such assertions. According to the Manchester syntax axiom `Class: {X:Class} SubClassOf: cco:DescriptiveICE`, any entity classified as an outlier claim is, by definition, a Descriptive Information Content Entity. This verbalization implies that the claim is not a physical object but a dependent entity that generically depends on some information bearer artifact.

The utility of this classification lies in its ability to segregate subjective observations from objective data records. For instance, when an automated system flags a transaction as suspicious, the flag itself is an information content entity—a descriptive assertion about the data. By constraining `X` to be a subclass of `cco:DescriptiveICE`, the ontology ensures that all subsequent processing of this claim treats it as information about information, rather than a primary data point.

## 4.2 Traces Supporting Claims

While a basic claim identifies a potential issue, it lacks evidentiary weight until it is anchored to a process that validates it. The **Trace Supports Claim** axiom formalizes this relationship. The axiom `Class: {X:Class} SubClassOf: bfo:0000015, sdg:supportsClaim some cco:DescriptiveICE` posits that the supporting entity `X` is a `bfo:0000015` (a Process) that specifically realizes the support for a DescriptiveICE.

In audit practice, a "trace" is often a lineage record or a verification procedure. By defining `X` as a Process, the ontology captures the dynamic, temporal nature of evidence generation. The claim is static (information), but the support is an occurrence (process) that happens over time. This distinction is critical for temporal auditing, where one must prove not only that a claim exists but that a valid verification process occurred to support it.

## 4.3 Outlier Claims with Attribute Sets

To increase the granularity of audit findings, an outlier claim may be required to possess specific attributes derived from evidentiary traces. The **Outlier Claim Min One Attribute** axiom refines the basic claim by imposing a cardinality constraint: `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}`. This verbalizes that the claim `X` must be associated with a minimum of one attribute set `Y`.

Crucially, the relational schema for this axiom defines `y` as a foreign key referencing the `t_trace_supports_claim` table. This structural dependency enforces a strict validation rule: an outlier claim cannot be formally recognized as having an attribute set unless that attribute set is a valid, registered trace process. In practical terms, this means that an audit finding (the claim) must be explicitly linked to a specific verification event (the trace/attribute) to be considered valid within the system.

## 4.4 Datasets Under Audit

The ontological framework must ultimately ground these information entities and processes in the physical or digital artifacts being examined. The **Dataset Under Audit** axiom provides this grounding. Defined as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:underAudit some bfo:0000015`, this axiom asserts that the dataset `X` is an Artifact (an independent continuant) that is currently undergoing a Process (`bfo:0000015`), specifically the audit process.

This distinction separates the object of scrutiny (the Artifact, e.g., a ledger file) from the act of scrutiny (the Process). In compliance frameworks, it is vital to maintain version control of artifacts. If an artifact changes, the audit process associated with the previous version may be invalidated. This ontology allows the system to track which specific version of an artifact (`X`) is linked to which specific audit process instance.
