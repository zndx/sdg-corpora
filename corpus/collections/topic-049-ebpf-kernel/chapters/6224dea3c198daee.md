# Chapter 4: Governance of Anomalous Data Assertions in Audited Environments

This chapter delineates the structural and procedural requirements for identifying, substantiating, and managing outlier claims within regulated data environments. It establishes the formal ontology governing descriptive information content entities, the process traces required to support them, and the artifacts subject to audit protocols. The guidelines provided herein ensure that all assertions of data anomalies are anchored to verifiable evidence trails, maintaining the integrity of the audit lifecycle.

## 1. Descriptive Information Content Entities

### 1.1 Definition and Scope

In the context of data governance, a Descriptive Information Content Entity (DescriptiveICE) functions as the fundamental unit of declarative information. It is not the data itself (the raw bits or the physical record), but rather the informational realization that describes a state of affairs, a specific value, or a condition within a dataset. According to the foundational axiom `outlier_claim_basic`, any entity classified as a DescriptiveICE is inherently a claim about the data—it asserts that a specific condition exists.

To qualify as a governed entity within this framework, the claim must be explicitly defined and cataloged. The assertion does not need to be true; it merely needs to be a well-formed informational content entity capable of being evaluated. This distinction is critical for audit readiness, as the governance layer manages the *claim* regarding an anomaly, distinct from the management of the anomalous data point itself.

### 1.2 Basic Claim Registration

The registration of basic claims is the first step in anomaly detection. These claims represent the identification of potential outliers without yet providing the substantiating evidence. Table 4.1 illustrates the registration of such basic descriptive entities.

## 2. Process Traces and Claim Substantiation

### 2.1 The Role of Process Traces

A claim, while identifiable, holds no regulatory weight without substantiation. The axiom `trace_supports_claim` introduces the concept of a process trace—a specific type of process (BFO:0000015) that generates or provides evidence supporting a descriptive claim. In audit terms, this is the "audit trail" or the "provenance metadata" that validates the assertion.

The process trace must be an active or historical occurrence that links the claim to reality. It transforms a mere assertion (DescriptiveICE) into a supported observation. The ontology dictates that the trace is a process entity; it is temporal and has a beginning and an end during which the supporting evidence is generated.

### 2.2 Trace Identification and Linkage

For a claim to be admissible in a compliance report, it must be associated with a valid trace. This trace might be an automated validation script, a manual review process, or a system log generation event. Table 4.2 catalogs these process traces.

**Table 4.2: Process Traces Supporting Claims (Axiom 2)**

| :--- | :--- |
| TRC-101 | AutomatedVarianceAnalysis |

| TRC-103 | SecurityAccessLogReview |
| TRC-104 | StockLevelSensorRead |

*Table 4.2 represents the `trace_supports_claim` axiom. The `id` serves as the primary key for the process trace, which will subsequently be referenced by claims requiring substantiation. Column `x` defines the specific class of the process acting as the trace.*

## 3. Attribute Set Requirements for Outlier Claims

### 3.1 Complex Claim Structure

While a basic claim identifies an anomaly, a rigorous governance framework requires that the claim be decomposed into observable attributes. The axiom `outlier_claim_min_one_attribute` posits that a valid outlier claim is not merely a simple DescriptiveICE but a complex entity that possesses a minimum of one attribute set. This attribute set must be realized by a process trace.

This structure enforces the principle of "evidence anchoring." A claim cannot exist in a vacuum; it must carry with it the reference to the trace (the attribute set) that supports it. This creates a dependency relationship where the integrity of the claim is contingent upon the validity of the referenced trace.

### 3.2 Relational Mapping of Claims to Traces

The mapping between the complex claim and its supporting trace is enforced through referential integrity. The `y` slot in the claim structure must reference a valid `id` from the trace registry. Table 4.3 demonstrates this linkage, showing how specific claims are bound to specific attribute sets (traces).

**Table 4.3: Outlier Claims with Attribute Sets (Axiom 1)**

| id | x | y |
| :--- | :--- | :--- |
| CLM-COMP-01 | RevenueDiscrepancyAssertion | TRC-101 |
| CLM-COMP-02 | LatencySpikeObservation | TRC-102 |
| CLM-COMP-03 | UserAuthenticationFailure | TRC-103 |
| CLM-COMP-04 | InventoryDepletionWarning | TRC-104 |

*Table 4.3 embodies the `outlier_claim_min_one_attribute` axiom. The primary key is `id`. Column `x` defines the claim class, and column `y` acts as a foreign key referencing `t_trace_supports_claim(id)`, ensuring that every claim is substantiated by exactly one or more attribute sets (traces).*

## 4. Artifacts Under Audit

### 4.1 Audit Scope and Artifacts

The ultimate object of governance is the data artifact itself—the dataset, ledger, or record store that is undergoing examination. The axiom `dataset_under_audit` defines an artifact (cco:Artifact) that is currently subject to an audit process (bfo:0000015). This concept delineates the boundary of the audit engagement.

An artifact under audit is distinct from the claims made about it. The artifact is the passive entity being inspected, whereas the claims and traces are the active informational and processual components of the inspection. The status of being "under audit" triggers the applicability of the preceding axioms; once an artifact is designated as such, any anomalies identified within it must be formalized as claims (Axiom 1) supported by traces (Axiom 2).
