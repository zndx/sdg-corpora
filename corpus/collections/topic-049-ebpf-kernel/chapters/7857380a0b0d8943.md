# Chapter 4: Ontological Formalization of Audit Artifacts and Anomaly Detection

## 4.1 Scope and Preamble

This chapter establishes the formal ontological structures required to govern the identification, classification, and evidentiary support of anomalies within financial and operational datasets. The definitions herein are aligned with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), providing a rigorous framework for audit professionals to map observed irregularities to verifiable data artifacts. The provisions detailed in Sections 4.2 through 4.5 delineate the specific axioms governing datasets under audit, the traces that support claims, and the hierarchical structure of outlier claims. Implementers must ensure that all relational instances adhere to the schema constraints provided, maintaining referential integrity between the asserted claims and their underlying evidentiary traces.

## 4.2 Artifacts Under Audit

### 4.2.1 Definition and Axiomatic Basis

In the context of governance frameworks, an audit is not merely a process but a dependent continuant that requires a specific object of scrutiny. The axiom `dataset_under_audit` formalizes this relationship by defining a class of artifacts that are currently undergoing a process (`bfo:0000015`). An artifact, in this sense, is defined as a `cco:Artifact`—a material entity that is the product of some realizing process, such as a digital ledger, a transaction log, or a database backup.

The Manchester syntax for this axiom is expressed as:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:underAudit some bfo:0000015`

Verbalized, this asserts: **{X} is something that under audit process.**

This definition ensures that any entity classified as a dataset under audit is intrinsically linked to an active or pending evaluative process. It distinguishes static data from data that is within the scope of a compliance review, forensic analysis, or regulatory examination.

### 4.2.2 Relational Implementation

The relational schema for `dataset_under_audit` enforces a primary key constraint on the entity identifier (`id`). The column `x` represents the class of the artifact (e.g., `GeneralLedger`, `AccessLog`). The schema is designed to catalog the specific data objects that are the subject of the auditor's scrutiny.

## 4.3 Traces Supporting Claims

### 4.3.1 Definition and Evidentiary Standards

The integrity of any audit finding relies on the existence of supporting evidence. The axiom `trace_supports_claim` defines the structural relationship between an evidentiary trace and the claim it substantiates. According to the axiom, a trace is an Independent Continuant (`bfo:0000015`) that bears the specific role of supporting a Descriptive Information Content Entity (`cco:DescriptiveICE`).

The Manchester syntax is defined as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:supportsClaim some cco:DescriptiveICE`

Verbalized, this asserts: **{X} is something that supports claim descriptive information content entity.**

In practice, a "trace" may be a specific transaction ID, a system log entry, or a digital signature. The axiom mandates that for a trace to be valid within the ontology, it must possess the capability to support a claim. This moves the audit process from subjective observation to objective dependency, where every assertion must be traceable back to an independent continuant.

### 4.3.2 Relational Implementation

The schema for `t_trace_supports_claim` is straightforward, consisting of an identifier and the class of the trace. However, its role in the wider ontology is critical, as it serves as the foreign key target for complex outlier claims. This ensures that claims cannot reference non-existent or invalid evidence.

## 4.4 Basic Outlier Claims

### 4.4.1 Definition of Descriptive Anomalies

The most granular unit of audit observation is the Basic Outlier Claim. This concept is derived from the axiom `outlier_claim_basic`, which classifies an entity strictly as a `cco:DescriptiveICE`. A Descriptive Information Content Entity is a type of information content entity that is about some thing. In the context of outlier detection, this represents a raw assertion of an anomaly without the immediate requirement for complex attribute decomposition.

The Manchester syntax is:
`Class: {X:Class} SubClassOf: cco:DescriptiveICE`

Verbalized, this asserts: **{X} is a descriptive information content entity.**

This axiom captures the initial identification of a potential issue. For example, an automated system might flag a "Revenue Spike" as a basic outlier. At this stage, it is a descriptive entity—a statement about the data—without yet being fully articulated as a complex claim supported by specific attributes. It serves as the precursor to more rigorous analysis.

### 4.4.2 Relational Implementation

The `t_outlier_claim_basic` table captures these initial assertions. It is a simple structure linking a unique claim ID to the class of the outlier.

## 4.5 Outlier Claims with Attribute Sets

### 4.5.1 Complex Claims and Attribute Constraints

To elevate a basic observation to a defensible audit finding, it must be substantiated by specific attributes. The axiom `outlier_claim_min_one_attribute` introduces a constraint that requires a claim to possess a minimum of one attribute from a defined set. This axiom is crucial for enforcing the "evidence-anchored" nature of the audit report.

The Manchester syntax is:
`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}`

Verbalized, this asserts: **{X} is a descriptive information content entity that has an attribute set containing at least one {Y}.**

In this framework, the attribute set (`Y`) is not merely a data property but a reference to a specific trace defined in Section 4.3. The constraint `min 1` ensures that a claim cannot exist in this state without at least one supporting piece of evidence. This ontological structure prevents the creation of orphaned or unsubstantiated audit claims.

### 4.5.2 Relational Implementation and Referential Integrity

The relational schema for `t_outlier_claim_min_one_attribute` implements a Foreign Key constraint linking the attribute (`y`) to the `t_trace_supports_claim` table. This enforces the axiom's requirement that the attribute must be a valid trace.

*   **Primary Key:** `id` (The unique identifier of the claim).
*   **Foreign Key:** `y` (References `id` in `t_trace_supports_claim`).

This structure guarantees that for every complex claim, there exists a verifiable trace in the evidence repository.
