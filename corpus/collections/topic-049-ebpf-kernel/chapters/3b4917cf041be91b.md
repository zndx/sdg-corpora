# Chapter 7: Ontological Frameworks for Audit Evidence and Outlier Detection

This chapter delineates the formal ontological structures governing the identification, classification, and evidentiary support of anomalies within regulated datasets. It establishes the rigorous relationships between audited artifacts, evidentiary traces, and descriptive claims, providing a standardized schema for compliance reporting. The framework provided herein is intended for use in high-assurance environments where audit trails must be machine-readable and logically verifiable against specific governance axioms.

## 1. Artifacts Under Audit

In the context of digital forensics and financial compliance, the primary unit of analysis is the Artifact. This entity represents the discrete, bounded object of scrutiny—be it a consolidated ledger, a transaction log, or a system configuration file. The axiom governing this concept asserts that an Artifact ($X$) is fundamentally defined by its relationship to a Process ($bfo:0000015$), specifically an audit process. This relationship, denoted as `underAudit`, transforms a static data object into a subject of active governance.

### 1.1 Definition and Scope

The class `dataset_under_audit` is not merely a passive container of information; it is an Artifact that is ontologically bound to an investigative process. When an auditor initiates an examination, they are instantiating a relationship between the data object and the audit methodology. This relationship ensures that the Artifact is no longer viewed in isolation but is understood through the lens of the compliance framework applied to it.

For instance, consider a "Q3 2023 Consolidated Balance Sheet." In its raw state, it is simply an Artifact. However, once it is selected for a quarterly review, it enters the state of `dataset_under_audit`. This status triggers specific retention requirements, access controls, and logging mechanisms. The ontological commitment here is that the audit process is a dependent of the Artifact's state during the examination period.

### 1.2 Operational Context

From a regulatory standpoint, identifying an Artifact as `dataset_under_audit` is the prerequisite step for any subsequent claim generation. Without this designation, no assertions regarding the data's validity or anomalies can be formally anchored. The following table illustrates instances of Artifacts that have been formally placed under audit, representing the primary keys for subsequent evidentiary chains.

## 2. Trace Supports Claim

Once an Artifact is under audit, the investigation generates evidence. This evidence is modeled not as a static datum, but as a Process—a temporal occurrence that validates or refutes a specific assertion. The axiom `trace_supports_claim` defines a class ($X$) as a subtype of a Process ($bfo:0000015$) that possesses the capability to support a Descriptive Information Content Entity ($cco:DescriptiveICE$).

### 2.1 The Nature of the Trace

A "Trace" in this ontology is an active event or a recorded process instance that provides the foundational evidence for a claim. It is distinct from the claim itself; the claim is a linguistic or logical assertion, while the Trace is the procedural or factual substrate that anchors it to reality. For example, a specific system log entry recording a login attempt at 03:00 hours is a Process (the event of logging in) that serves as a Trace supporting a claim of "unauthorized access."

The verbalization of this axiom—"{X} is something that supports claim descriptive information content entity"—emphasizes the directional flow of evidence. The Trace ($X$) is the antecedent; the Claim is the consequent. In a compliance context, the robustness of an audit finding is directly proportional to the integrity of the Trace.

## 3. Basic Descriptive Claims

The core output of the audit process is the generation of Claims. A Claim, formally defined as a Descriptive Information Content Entity ($cco:DescriptiveICE$), is a proposition that describes a state of affairs, a deviation, or a characteristic of the Artifact. The axiom `outlier_claim_basic` establishes the fundamental class of these entities, asserting simply that $X$ is a descriptive information content entity.

### 3.1 Structure of the Basic Claim

A basic claim serves as a categorical assertion. It does not, in itself, carry the weight of the evidence (that is the role of the Trace), nor does it necessarily decompose into complex attribute sets. It is the atomic unit of audit reporting. Examples of basic claims include "Revenue is recognized," "Asset is impaired," or "Variance is within tolerance."

In the context of outlier detection, a basic claim might identify the existence of an anomaly without immediately detailing its composition. For instance, the claim "Transaction 8821 is an outlier" is a valid `outlier_claim_basic`. It is a descriptive entity that classifies a specific data point. However, for the claim to be actionable, it must be linked to the underlying data and the traces that support it.

## 4. Outlier Claims with Attribute Sets

To achieve a granular level of compliance and technical detail, the ontology distinguishes between basic claims and complex claims. The axiom `outlier_claim_min_one_attribute` defines a subclass of DescriptiveICE that is structurally dependent on an AttributeSet. Specifically, the Claim ($X$) must possess a minimum of one Attribute ($Y$), where that Attribute is itself a Trace that supports a claim.

### 4.1 Complex Claim Structure

This axiom introduces a recursive dependency that enhances the audit trail's density. A complex outlier claim is not merely a statement; it is a composite object comprising a central assertion and one or more supporting attributes. Crucially, the attribute ($Y$) is not a simple literal value (like a string or number); it is a reference to an entity within the `t_trace_supports_claim` table.

This structure enforces a discipline of evidence-based auditing. One cannot assert a complex outlier claim (e.g., "Fraudulent Transfer Detected") without linking it to a specific, process-based attribute (e.g., "System Login Event: UID 9921"). The relational schema enforces this via a foreign key constraint: the $y$ column in the claims table must reference a valid $id$ in the traces table.

### 4.2 Relational Mapping and Evidence

The implementation of this axiom requires a rigorous mapping between the claim being made and the trace evidence substantiating it. The following table demonstrates how complex outlier claims are instantiated, linking the descriptive assertion ($X$) directly to the evidentiary trace ($Y$).

**Table 4-1: Complex Outlier Claims with Attribute References**

| ID | Claim (X) | Attribute Reference (Y) |
| :--- | :--- | :--- |
| CLM-CPLX-001 | Unauthorized Administrator Access | TRC-LOG-8821 |
| CLM-CPLX-002 | Suspicious Ledger Modification | TRC-LOG-8822 |
| CLM-CPLX-003 | Security Policy Circumvention | TRC-LOG-8823 |
| CLM-CPLX-004 | Automated Script Execution Detected | TRC-LOG-8824 |
| CLM-CPLX-005 | Data Exfiltration to External Host | TRC-LOG-8825 |

In Table 4-1, the column $Y$ (Attribute Reference) acts as a foreign key. For example, the complex claim "Unauthorized Administrator Access" (CLM-CPLX-001) is substantiated by the attribute "System Login Event: UID 9921 @ 03:14 UTC" (TRC-LOG-8821). This linkage satisfies the axiom's requirement that the claim `hasAttributeSet min 1` entity which is a Trace supporting a claim.

This structure allows auditors and automated compliance systems to traverse the graph of the audit. One may start with the Claim ($X$), retrieve the Attribute ($Y$) to find the specific Trace, and then examine the details of that Trace to understand the Process ($bfo:0000015$) that occurred. This end-to-end traceability is the hallmark of a mature, audit-ready ontology.
