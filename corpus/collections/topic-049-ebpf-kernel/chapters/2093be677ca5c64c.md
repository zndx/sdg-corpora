# Chapter 4: Ontological Foundations of Audit Evidence and Claim Verification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the semantic representation of audit evidence, specifically focusing on the structural relationships between descriptive information content entities, the artifacts under examination, and the process traces that substantiate compliance claims. The definitions provided herein align with the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO) to ensure interoperability across governance systems. The text delineates the necessary logical conditions for an entity to be classified as a claim, a supporting trace, or an artifact under audit, providing the relational schema required to implement these axioms within a compliance database. It is presupposed that the reader possesses a working understanding of semantic web technologies and relational database integrity constraints.

## 4.2 Basic Descriptive Information Content Entities

### 4.2.1 Definition and Axiomatic Structure

In the context of audit reporting, a fundamental unit of information is the Descriptive Information Content Entity (DescriptiveICE). According to the axiom `outlier_claim_basic`, any entity classified as such is a dependent continuant that generically depends on some independent continuant, typically a data artifact or a document. The axiom is formally expressed as:

**Class: {X:Class} SubClassOf: cco:DescriptiveICE**

This classification asserts that {X} is a descriptive information content entity. In practice, this represents the atomic level of assertion within an audit finding. It is a claim about a state of affairs, a value, or a condition, devoid of the complex evidentiary scaffolding that might validate it. The distinction between a basic claim and a verified finding is critical; the former represents the *proposition* itself, while the latter represents the proposition coupled with evidentiary support.

### 4.2.2 Relational Implementation

The relational projection of this axiom creates a table where each row represents a distinct claim identified by a unique primary key. The column `x` denotes the specific class or type of the claim being asserted.

## 4.3 Audit Traces and Claim Support

### 4.3.1 The Process of Verification

A claim, in isolation, lacks the necessary evidentiary weight to support an audit opinion. To transition from a mere proposition to a verified fact, the claim must be supported by a process trace. The axiom `trace_supports_claim` defines this relationship by invoking `bfo:0000015`, which denotes a process. The axiom is formally expressed as:

**Class: {X:Class} SubClassOf: bfo:0000015, sdg:supportsClaim some cco:DescriptiveICE**

This verbalizes to: {X} is something that supports claim descriptive information content entity. In this ontology, the "trace" is not merely a static document but the *process* or *activity* of generating, capturing, or recording evidence that substantiates the descriptive entity. This distinction is vital for audit trails; it emphasizes that the validity of a claim rests on the procedural integrity of the evidence generation process.

### 4.3.2 Relational Implementation

The schema for this axiom, `t_trace_supports_claim`, establishes the entities that act as evidentiary foundations. These traces are the processes (e.g., automated calculation, physical verification, system logging) that provide the "some" value in the Object Property Restriction `sdg:supportsClaim`.

## 4.4 Attribute-Based Outlier Claims

### 4.4.1 Complex Claims and Attribute Sets

While basic claims provide a foundation, audit anomalies—specifically outliers—require a more granular description. An outlier claim is not merely a descriptive entity; it is a descriptive entity defined by a specific set of attributes that deviate from the expected norm. The axiom `outlier_claim_min_one_attribute` formalizes this by imposing a cardinality constraint on the attribute set.

**Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}**

This verbalizes to: {X} is a descriptive information content entity that possesses a minimum of one attribute {Y}. In the context of this schema, the attribute set {Y} is projected as a foreign key referencing the trace that provides the attribute data. This structural dependency implies that an outlier claim cannot exist in a vacuum; it must be anchored to a specific trace (the source of the attribute data) that defines the anomalous characteristics.

### 4.4.2 Relational Implementation

The relational schema for `t_outlier_claim_min_one_attribute` enforces the dependency between the claim and the supporting trace. The `y` column is mandated to be `NOT NULL` and acts as a foreign key to `t_trace_supports_claim(id)`. This constraint ensures that every outlier claim is explicitly linked to a process trace that validates the attribute(s) causing the outlier status.

## 4.5 Artifacts Under Audit

### 4.5.1 The Scope of Examination

The audit process does not operate on abstract concepts alone; it examines concrete data repositories. These repositories are modeled as Artifacts (`cco:Artifact`). The axiom `dataset_under_audit` defines the relationship between these artifacts and the audit process itself.

**Class: {X:Class} SubClassOf: cco:Artifact, sdg:underAudit some bfo:0000015**

This verbalizes to: {X} is something that under audit process. Here, {X} represents the dataset or artifact, and the Object Property `sdg:underAudit` links it to a process (`bfo:0000015`). This axiom effectively scopes the audit: it defines the boundaries of the examination by linking the data objects (Artifacts) to the investigative activities (Processes).

### 4.5.2 Relational Implementation

The table `t_dataset_under_audit` catalogs the specific artifacts subject to the audit procedures. Each artifact is identified and classified. While the schema does not explicitly store the ID of the audit process in a separate column, the classification of {X} as an Artifact under audit implies the existence of the process relationship.
