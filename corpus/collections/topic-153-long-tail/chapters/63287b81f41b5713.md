# Chapter 7: Semantic Relational Mapping for Service Governance

## 7.0 Scope and Preamble

This chapter delineates the structural requirements for mapping ontological concepts regarding service processes, spatial artifacts, and quality ratings into a rigid relational schema. The objective is to ensure data lineage and referential integrity within governance frameworks, specifically where operational processes must be audited against physical locations and performance metrics. The following sections provide the formal definitions, relational implementations, and compliance data tables necessary for establishing a traceable audit trail. All entities presented herein are grounded in the axioms of the core ontology and are structured to satisfy the constraints of the `bfo:0000015` (Process) and `cco:Artifact` hierarchies.

## 7.1 Traceability of Service Processes

### 7.1.1 Conceptual Framework
The foundational axiom for service governance defines the relationship between a process and the service context in which it operates. Formally, this is expressed as: *{X} is something that in service {Y}*. In this context, the subject {X} represents a specific process class (e.g., a field audit or a data ingestion workflow), while the object {Y} represents the service location or the functional unit receiving the service.

To maintain high-fidelity audit trails, the system must distinguish between the abstract definition of a process and its instantiation within a specific service environment. This distinction is critical for regulatory reporting, where the physical or logical locus of an operation determines the applicable jurisdiction or compliance standard.

### 7.1.2 Relational Implementation
The relational schema for this concept is encapsulated in the table `t_trace_in_service`. This table serves as the primary registry for active processes, linking each process instance to its designated service endpoint.

The schema structure is defined as follows:
*   **Primary Key (`id`):** A unique identifier for the trace record.
*   **Column `x`:** The Process Class or Individual name (the entity performing the service).
*   **Column `y`:** The Service Class or Individual identifier, which acts as a foreign key referencing a valid entry in the `t_schemaorg_place_address` table. This constraint ensures that no process is recorded as operating within a non-existent or unverified location.

## 7.2 Artifact Addressability and Location

### 7.2.1 Conceptual Framework
The second axiom governs the physical grounding of artifacts within the system. It is posited that: *{X} is something that has postal address {Y}*. Here, {X} denotes an artifact—such as a compliance report, a physical record, or a storage unit—while {Y} denotes the postal address associated with that artifact.

In the context of compliance management, this axiom ensures that every tangible or documented asset is linked to a verifiable physical location. This linkage is essential for discovery processes, legal holds, and logistical operations. The relational model enforces a strict dependency where the address record (`y`) must reference a valid process trace ID (`id`) from the service traceability table, thereby creating a closed loop between the artifact, its location, and the process utilizing that location.

### 7.2.2 Relational Implementation
The schema for artifact addressability is realized in the table `t_schemaorg_place_address`. This table functions as a directory of locations, indexed by their association with specific process traces.

The schema structure is defined as follows:
*   **Primary Key (`id`):** The unique identifier for the location record.
*   **Column `x`:** The Artifact Class or Individual (the entity possessing the address).
*   **Column `y`:** The Postal Address identifier, which acts as a foreign key referencing the `id` column in `t_trace_in_service`. This reciprocal foreign key relationship validates that the address is actively employed by a registered process.

## 7.3 Review Ratings and Quality Metrics

### 7.3.1 Conceptual Framework
The final axiom addresses the evaluation of artifacts based on quality or compliance standards. The axiom states: *{X} is something that has review rating {Y}*. In this construct, {X} is the artifact undergoing evaluation, and {Y} is the assigned rating or score.

This mechanism allows the governance framework to filter artifacts by compliance status, performance grade, or audit outcome. By formalizing the rating as a distinct entity linked to the artifact, the system supports historical tracking of quality changes and facilitates automated reporting on the health of the service environment.

### 7.3.2 Relational Implementation
The relational schema for review ratings is instantiated in the table `t_schemaorg_review_rating`. This table records the outcomes of quality assurance checks and audits performed on artifacts.

The schema structure is defined as follows:
*   **Primary Key (`id`):** A unique identifier for the rating record.
*   **Column `x`:** The Artifact Class or Individual being rated.
*   **Column `y`:** The Review Rating value, which acts as a foreign key referencing the `id` column in `t_trace_in_service`. This constraint implies that ratings are context-dependent, tied intrinsically to the specific process trace under which the artifact was reviewed or generated.
