# Chapter 4: Formal Ontology of Kernel Observability and Compliance Artifacts

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework governing the classification of kernel-level observability artifacts, specifically within the context of eBPF (Extended Berkeley Packet Filter) verification and compliance auditing. The text herein delineates the axiomatic structure required to map high-level compliance directives (such as NIST 800-53) to low-level execution primitives (system calls and lab runs). The definitions provided are binding for the purposes of audit reporting and system verification. All entities referenced in the subsequent sections are defined via OWL axioms and projected into deterministic relational schemas to ensure data integrity and traceability. The implementation of these mappings shall adhere strictly to the foreign key constraints specified in the accompanying schema definitions.

## 4.2 Lab Run with Protocol

### 4.2.1 Axiomatic Definition
The foundational unit of execution within this framework is the **Lab Run**, defined formally by the axiom `labrun_with_protocol`. In Manchester syntax, this is expressed as: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:followsProtocol some {Y:Class}`. This asserts that entity `X` (a Process) follows protocol `Y`.

### 4.2.2 Relational Implementation
The projection of this axiom onto a relational schema creates a binding dependency between the execution process and the governing protocol. Notably, the schema enforces a recursive structural constraint wherein the protocol (`y`) must reference a valid system call defined at a security tier. This ensures that abstract protocols are grounded in specific, tiered system capabilities.

The following table embodies the `labrun_with_protocol` axiom. The primary key is the unique identifier (`id`) for the lab run instance. The foreign key (`y`) references the `t_syscall_at_security_tier` table, establishing that every protocol followed is explicitly defined as a system call operating at a specific security tier.

| id | x | y |
| :--- | :--- | :--- |
| `LR-101` | `Process_Audit_Log` | `SC-TIER-0` |
| `LR-102` | `Process_Mem_Scan` | `SC-TIER-1` |
| `LR-103` | `Process_Net_Filter` | `SC-TIER-2` |
| `LR-104` | `Process_File_Integrity` | `SC-TIER-0` |

### 4.2.3 Verification Context
In the context of a compliance audit, the `Lab Run` represents the specific instantiation of a verification process. For instance, `Process_Audit_Log` (LR-101) is not merely a generic logging event but a process strictly bound to the protocol defined by the system call `SC-TIER-0`. This binding prevents the execution of audit processes outside of their designated security contexts, thereby enforcing the principle of least privilege at the ontological level.

## 4.3 Syscall at Security Tier

### 4.3.1 Axiomatic Definition
The second core concept defines the **Syscall at Security Tier**, axiomatized as `syscall_at_security_tier`. The Manchester syntax is: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}`. This posits that entity `X` (a Designative Information Content Entity) is located at security tier `Y`.

### 4.3.2 Relational Implementation
This schema maps the designative intent of a system call to its security tier. The structural integrity of the model requires that the security tier (`y`) be a valid Lab Run instance. This circular dependency (referenced back to `t_labrun_with_protocol`) formalizes the requirement that a security tier is not merely a static label, but a dynamic context defined by the specific protocol execution (Lab Run) active at that time.

The following table embodies the `syscall_at_security_tier` axiom. The primary key (`id`) uniquely identifies the system call entity. The foreign key (`y`) references the `t_labrun_with_protocol` table, mandating that the security tier is defined by a specific, protocol-bound lab run.

| id | x | y |
| :--- | :--- | :--- |
| `SC-TIER-0` | `Syscall_BPF_Map_Lookup` | `LR-101` |
| `SC-TIER-1` | `Syscall_BPF_Probe_Read` | `LR-102` |
| `SC-TIER-2` | `Syscall_Socket_Ops` | `LR-103` |
| `SC-TIER-0` | `Syscall_BPF_Probe_Write` | `LR-104` |

### 4.3.3 Security Implications
The designation of `Syscall_BPF_Map_Lookup` (SC-TIER-0) at security tier `LR-101` implies that the security properties of this system call are derived entirely from the `Process_Audit_Log` lab run. This creates a verifiable chain of evidence: the syscall's security tier is auditable by tracing it back to the specific lab run protocol that defines it. Any deviation in the lab run protocol immediately invalidates the security tier classification of the associated syscall.

## 4.4 NIST 800-53 Control Subclass

### 4.4.1 Axiomatic Definition
To bridge technical implementation with regulatory compliance, the framework utilizes the **NIST 800-53 Control Subclass**. The axiom `nist80053_control_subclass` is defined as: `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:nist80053Control some {Y:Class}`. This asserts that entity `X` (a Directive Information Content Entity) implements or maps to NIST 800-53 control `Y`.

### 4.4.2 Relational Implementation
This mapping serves as the critical link between internal governance directives and federal compliance standards. The schema requires that the NIST control identifier (`y`) be grounded in a Lab Run protocol. This ensures that compliance controls are not merely theoretical assertions but are operationalized through specific, executable protocol runs.

The following table embodies the `nist80053_control_subclass` axiom. The primary key (`id`) identifies the specific directive instance. The foreign key (`y`) references the `t_labrun_with_protocol` table, ensuring the NIST control is realized through the execution of a defined protocol.

### 4.4.3 Compliance Mapping
In this schema, `Directive_Access_Enforcement` (DIR-AC-3) is mapped to the Lab Run `LR-101`. An auditor reviewing this entry can verify that the organization's implementation of Access Enforcement (AC-3) is technically enforced by the `Process_Audit_Log` protocol. This provides a deterministic path from the regulatory requirement (NIST 800-53) to the kernel-level enforcement mechanism.

## 4.5 Syscall Equivalent in Subsystem

### 4.5.1 Axiomatic Definition
The framework identifies specific system calls as functional equivalents within broader subsystems via the **Syscall Equivalent in Subsystem** axiom. The Manchester syntax is: `Class: {X:Class} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})`. This defines entity `X` as a Designative ICE that is equivalent to a syscall within subsystem `Y`.

### 4.5.2 Relational Implementation
This equivalence relation is essential for mapping legacy or proprietary interfaces to standard system calls for monitoring purposes. The schema constrains the subsystem identifier (`y`) to be a valid Lab Run, implying that the subsystem context is established by the execution environment of the protocol.

The following table embodies the `syscall_equiv_in_subsystem` axiom. The primary key (`id`) uniquely identifies the equivalent entity. The foreign key (`y`) references the `t_labrun_with_protocol` table, anchoring the subsystem definition to the active protocol run.

| id | x | y |
| :--- | :--- | :--- |
| `EQUIV-01` | `Syscall_Equiv_Netlink` | `LR-103` |
| `EQUIV-02` | `Syscall_Equiv_Cgroup` | `LR-101` |
| `EQUIV-03` | `Syscall_Equiv_Mount` | `LR-104` |
| `EQUIV-04` | `Syscall_Equiv_Signal` | `LR-102` |

### 4.5.4 Subsystem Isolation
By defining `Syscall_Equiv_Netlink` (EQUIV-01) within the context of `LR-103` (`Process_Net_Filter`), the framework ensures that netlink socket operations are only recognized as valid equivalents when they occur within the specific network filtering lab run. This prevents subsystem confusion and ensures that observability tools correctly attribute syscall-like activities to the correct logical subsystem boundaries.

## 4.6 eBPF Program Verified Safe

### 4.6.1 Axiomatic Definition
The final concept addresses the integrity of execution artifacts through the **eBPF Program Verified Safe** axiom. Formally, `ebpfprogram_verified_safe` is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:verifiedSafeBy some {Y:Class}`. This asserts that artifact `X` is verified as safe by entity `Y`.

### 4.6.2 Relational Implementation
This axiom tracks the verification status of eBPF bytecode or other kernel artifacts. The schema mandates that the verifying entity (`y`) be a Lab Run protocol. This links the artifact's safety status directly to the specific verification routine (protocol) that was executed, providing non-repudiation of the safety check.

The following table embodies the `ebpfprogram_verified_safe` axiom. The primary key (`id`) identifies the specific artifact instance. The foreign key (`y`) references the `t_labrun_with_protocol` table, ensuring the verification is tied to a concrete, auditable process.

| `ART-BPF-02` | `Artifact_XDP_Drop` | `LR-101` |
| `ART-BPF-03` | `Artifact_Kprobe_Trace` | `LR-102` |
| `ART-BPF-04` | `Artifact_Cgroup_Sock` | `LR-104` |

### 4.6.3 Safety Assurance
The entry for `Artifact_Socket_Filter` (ART-BPF-01) indicates that its safety is verified by `LR-103` (`Process_Net_Filter`). In an audit scenario, this entry serves as proof that the specific bytecode loaded into the kernel was subjected to and passed the verification protocol defined in `LR-103`. If the protocol `LR-103` is later found to be flawed or insufficient, the verification status of all artifacts linked to it (`y`) must be re-evaluated, facilitating efficient recall and re-verification.
