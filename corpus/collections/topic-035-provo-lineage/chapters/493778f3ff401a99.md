# Chapter 4: Regulatory Compliance Mapping and Control Ontologies

## 4.1 Scope and Preamble

This chapter delineates the structural mapping of the `cco:DirectiveICE` class to specific regulatory frameworks, specifically the Health Insurance Portability and Accountability Act (HIPAA) and the Payment Card Industry Data Security Standard (PCI DSS). The content herein establishes the relational dependencies between safeguard classes and the threat classes they address, providing a formal ontology for audit readiness and governance verification. The following sections define five core axioms that govern the classification of directives, ensuring that information control elements (ICE) are rigorously categorized according to their functional and compliance attributes. This approach facilitates precise evidence anchoring in compliance reports and supports the generation of automated audit trails.

## 4.2 Control Only Addresses Threat Class

The axiom `control_only_addresses_threat_class` serves as a foundational constraint within the governance ontology, asserting that a specific class of DirectiveICE (`{X}`) addresses a risk (`{Y}`) exclusively. This relationship is not merely associative but restrictive; it ensures that the control is validated only against the specific threat class defined in the ontology. In compliance frameworks, this prevents scope creep where a general control might be erroneously cited as a mitigation for a disparate risk category.

Formally, the axiom is expressed as: `{X} SubClassOf cco:DirectiveICE, sdg:addressesRisk only {Y}`. This implies that for any instance of `{X}`, the risk addressed must be an instance of `{Y}`. Within the relational schema, this creates a strict dependency where the threat class entity must reference a physical safeguard entity, establishing a bi-directional linkage between the risk definition and its physical mitigation layer.

**Table 4.1: Threat Class and Control Dependency Mapping**

| ID | Control Class (X) | Threat Class (Y) | Physical Safeguard Reference |
| :--- | :--- | :--- | :--- |
| T1 | PhysicalAccessControl | UnauthorizedPhysicalAccess | P1 |
| T2 | MediaStorageControl | DataLossTheft | P2 |
| T3 | NetworkAccessControl | NetworkEavesdropping | P1 |

*Table 4.1 illustrates the instantiation of the `control_only_addresses_threat_class` axiom. The `Physical Safeguard Reference` column denotes the foreign key constraint linking the threat class to a specific physical safeguard, ensuring that the definition of the risk is inextricably bound to a tangible mitigation asset.*

## 4.3 HIPAA Safeguard Physical

Pursuant to the Security Rule outlined in 45 CFR §§ 164.310(a)(1), physical safeguards are measures to protect electronic information systems and related buildings and equipment from natural and environmental hazards, as well as unauthorized intrusion. The ontology axiom `hipaa_safeguard_physical` classifies a DirectiveICE (`{X}`) as a mechanism that implements a HIPAA safeguard (`{Y}`).

This classification is critical for distinguishing physical controls from logical or administrative measures. In the context of the ontology, `{X}` represents the specific directive or policy (e.g., a facility access log), while `{Y}` represents the broader safeguard category (e.g., Facility Access Controls). The relational schema enforces that every physical safeguard must address a specific threat class, thereby closing the loop between the control implementation and the risk posture.

**Table 4.2: HIPAA Physical Safeguard Implementation**

| ID | DirectiveICE (X) | Safeguard Category (Y) | Threat Class Addressed |
| :--- | :--- | :--- | :--- |
| P1 | FacilityAccessControl | FacilityAccessControls | T1 |
| P2 | MediaStorageDisposal | DeviceAndMediaControls | T2 |

*Table 4.2 details the implementation of physical safeguards. The `DirectiveICE` column identifies the specific control instance, which is categorized under the `Safeguard Category` and mapped to the `Threat Class Addressed` (referencing Table 4.1), demonstrating compliance with the `hipaa_safeguard_physical` axiom.*

## 4.4 HIPAA Safeguard Technical

Technical safeguards, as defined in 45 CFR §§ 164.312, involve the technology and the policy and procedures for its use that protect electronic protected health information and control access to it. The axiom `hipaa_safeguard_technical` captures this by defining `{X}` (a DirectiveICE) as a subclass that implements a HIPAA technical safeguard (`{Y}`).

Unlike physical safeguards, technical controls are automated mechanisms, such as encryption or access control lists, that enforce security policies without requiring human intervention. The ontology requires that these technical measures be linked to a threat class, ensuring that every technological implementation is justified by a specific risk requirement. This mapping is essential for verifying that technical controls, such as unique user identification or automatic logoff, are effectively deployed to mitigate identified vulnerabilities like unauthorized electronic access.

**Table 4.3: HIPAA Technical Safeguard Registry**

| ID | DirectiveICE (X) | Safeguard Category (Y) | Threat Class Addressed |
| :--- | :--- | :--- | :--- |
| Tech1 | TransmissionEncryption | TransmissionSecurity | T3 |
| Tech2 | AuditControlMechanism | AuditControls | T3 |

*Table 4.3 provides a registry of technical safeguards. The `DirectiveICE` entries, such as `TransmissionEncryption`, are mapped to the `NetworkEavesdropping` threat class (T3), validating the axiom that the control serves to safeguard the specified asset class.*

## 4.5 HIPAA Safeguard Administrative

Administrative safeguards are the administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures to protect electronic protected health information. These activities are covered under 45 CFR §§ 164.308. The `hipaa_safeguard_admin` axiom formalizes this by defining `{X}` as a DirectiveICE that functions as an administrative safeguard (`{Y}`).

These safeguards often constitute the "soft" controls of the compliance framework, including security training, contingency planning, and risk analysis. However, in the ontology, they are treated with the same structural rigor as physical or technical controls. The schema mandates a link to a threat class, reinforcing the principle that administrative activities must be designed to address specific, tangible risks (e.g., human error leading to data loss) rather than serving as abstract bureaucratic exercises.

**Table 4.4: HIPAA Administrative Safeguard Inventory**

| ID | DirectiveICE (X) | Safeguard Category (Y) | Threat Class Addressed |
| :--- | :--- | :--- | :--- |
| Admin1 | SecurityAwarenessTraining | SecurityTraining | T2 |
| Admin2 | WorkforceSanctionPolicy | SecurityManagementProcess | T1 |

*Table 4.4 lists administrative safeguards. Note that `SecurityAwarenessTraining` (Admin1) is mapped to the `DataLossTheft` threat class (T2), illustrating how training protocols are ontologically structured to mitigate specific internal threat vectors.*

## 4.6 PCI DSS Requirement

The Payment Card Industry Data Security Standard (PCI DSS) provides a robust framework for organizations that handle cardholder data. The axiom `pci_dss_requirement` extends the `cco:DirectiveICE` class to include directives that satisfy specific PCI DSS requirements (`{Y}`). This axiom allows the ontology to map internal controls directly to external regulatory mandates, facilitating gap analysis and compliance reporting.

The structure of this axiom mirrors the HIPAA safeguards but applies to the distinct domain of payment card security. The relational schema requires that the PCI DSS requirement be linked to a threat class, ensuring that the requirement is not merely a checklist item but a functional component of the organization's risk management strategy. For instance, a firewall configuration requirement must be demonstrably linked to the threat of unauthorized network access.

**Table 4.5: PCI DSS Requirement Mapping**

| ID | DirectiveICE (X) | PCI DSS Requirement (Y) | Threat Class Addressed |
| :--- | :--- | :--- | :--- |
| PCI1 | FirewallConfiguration | Requirement 1: Install Firewalls | T3 |
| PCI2 | DataEncryptionStandard | Requirement 4: Encrypt Transmission | T3 |

*Table 4.5 maps internal directives to PCI DSS requirements. The `FirewallConfiguration` directive (PCI1) satisfies Requirement 1 and is linked to the `NetworkEavesdropping` threat class (T3), demonstrating the control's efficacy in mitigating external network threats.*
