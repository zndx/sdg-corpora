# Chapter 4: Directive ICE Subclasses in Regulatory Compliance Modeling

This chapter presents five axioms that classify DirectiveICE instances according to HIPAA and PCI-DSS safeguard patterns. The axioms are realized as a five-table relational schema whose foreign-key links permit verification of control-to-threat mappings through successive joins.

## 1. Axiom Overview and Domain Selection

The selected domain is audit-trail systems for protected health and payment-card data. In this setting each control is an instance of DirectiveICE that either safeguards a class of asset or addresses a class of risk exclusively. The five tables below are direct projections of the supplied axioms; column values are class references that satisfy the Manchester restrictions.

### 1.1 Physical Safeguard Table

Axiom 1 (hipaa_safeguard_physical) is embodied by t_hipaa_safeguard_physical. Column id is the primary key; column y is a foreign key that must resolve to an existing id in t_control_only_addresses_threat_class, thereby enforcing that every physical safeguard is paired with a control that addresses risk only.

## 2. Cross-Join Demonstration

To determine which administrative safeguard and PCI-DSS requirement both reference the same control that exclusively addresses the threat linked to the physical safeguard “MediaDisposalLocker”, perform the following joins. Start at t_hipaa_safeguard_physical where x = 'MediaDisposalLocker' (phys_saf_002). Its y value (ctrl_addr_001) is the primary key in t_control_only_addresses_threat_class. That row’s y value points back to phys_saf_002, confirming the exclusive-addresses-risk restriction. The same ctrl_addr_001 value appears as y in both t_hipaa_safeguard_admin (admin_saf_001) and t_pci_dss_requirement (pci_req_001). The joined result row is therefore:

phys_saf_002 | ctrl_addr_001 | admin_saf_001 | pci_req_001
