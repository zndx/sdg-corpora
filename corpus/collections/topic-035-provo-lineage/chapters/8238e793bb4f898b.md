# DirectiveICE Subclassing in Regulatory Control Systems

This chapter examines five axioms that locate subclasses of cco:DirectiveICE within HIPAA and PCI DSS compliance regimes. Each axiom is realized as a table whose rows instantiate the corresponding Manchester class expression. The resulting schema supports cross-table navigation that recovers which directive addresses which risk class under a given safeguard family.

## 1. Axiom-to-Table Mapping

Five tables are derived directly from the supplied axioms. Primary keys are the id columns. Foreign-key columns implement the “some” and “only” restrictions by referencing the id values of the target tables.

### 1.1 t_control_only_addresses_threat_class

Axiom 2 states that a directive addresses risk only of a designated threat class. The table therefore stores pairs (x, y) where x is a DirectiveICE subclass and y is the sole permitted threat class; the foreign key on y points to t_hipaa_safeguard_physical to close the “only” restriction.

| id | x | y |
| --- | --- | --- |
| ctl-01 | PhysicalAccessBarrier | threat-01 |
| ctl-02 | AccessLogReview | threat-02 |
| ctl-03 | EncryptionAtRest | threat-03 |
| ctl-04 | FireDamperOverride | threat-04 |
| ctl-05 | AuditTrailRetention | threat-05 |

### 1.2 t_hipaa_safeguard_physical

Axiom 1 asserts that a directive performs a HIPAA physical safeguard on a risk class. Column y therefore references t_control_only_addresses_threat_class, allowing a reader to traverse from physical safeguard to the unique threat class it is permitted to address.

| id | x | y |
| --- | --- | --- |
| phys-01 | LockedServerRoom | ctl-01 |
| phys-02 | BiometricEntry | ctl-02 |
| phys-03 | EquipmentEnclosure | ctl-03 |
| phys-04 | TamperEvidentSeal | ctl-04 |

### 1.3 t_hipaa_safeguard_technical

Axiom 3 likewise classifies technical safeguards. Its foreign key again references t_control_only_addresses_threat_class so that technical controls remain within the same threat-addressing scope.

| id | x | y |
| --- | --- | --- |
| tech-01 | TLSHandshakeEnforcement | ctl-03 |
| tech-02 | RoleBasedAccessControl | ctl-01 |
| tech-03 | SessionTimeout | ctl-02 |
| tech-04 | IntegrityChecksum | ctl-05 |

### 1.4 t_hipaa_safeguard_admin

Axiom 4 captures administrative safeguards. The same foreign-key pattern to t_control_only_addresses_threat_class ensures administrative procedures are linked to exactly one admissible threat class.

| id | x | y |
| --- | --- | --- |
| adm-01 | PolicyReviewCycle | ctl-05 |
| adm-02 | BackgroundCheck | ctl-01 |
| adm-03 | IncidentResponseDrill | ctl-02 |
| adm-04 | VendorRiskAssessment | ctl-03 |

### 1.5 t_pci_dss_requirement

Axiom 5 records PCI DSS requirements as DirectiveICE subclasses. Its foreign key again resolves to t_control_only_addresses_threat_class, permitting a single join path from any PCI requirement through the shared control table.

| id | x | y |
| --- | --- | --- |
| pci-01 | NetworkSegmentation | ctl-03 |
| pci-02 | LogMonitoring | ctl-05 |
| pci-03 | StrongCryptography | ctl-03 |
| pci-04 | QuarterlyVulnerabilityScan | ctl-02 |

## 2. Cross-Join Example

To determine which physical safeguard and which PCI DSS requirement together address threat-03, the following mental join is performed:

- Start at t_control_only_addresses_threat_class where y = threat-03 → ctl-03.
- Follow ctl-03.y into t_hipaa_safeguard_physical → phys-03 (EquipmentEnclosure).
- Follow ctl-03.id into t_pci_dss_requirement → pci-01 (NetworkSegmentation) and pci-03 (StrongCryptography).

The joined result row is therefore:

(ctl-03, EncryptionAtRest, threat-03, phys-03, EquipmentEnclosure, pci-01, NetworkSegmentation, pci-03, StrongCryptography)
