# Chapter 7: DirectiveICE Subclasses for HIPAA and PCI DSS Safeguards

This chapter presents five relational tables that realize the slot structures of five Manchester OWL axioms. Each table stores Class individuals that satisfy the corresponding SubClassOf restriction on cco:DirectiveICE. Primary-key columns hold stable identifiers for the directive classes; foreign-key columns encode the existential or universal restrictions on the target classes. Cross-table joins therefore reconstruct the multi-hop chains required by the axioms.

## 1. Control Classes That Address Risk Universally

Axiom 2 defines the table t_control_only_addresses_threat_class. Column id is the primary key naming each directive class. Column x stores the directive class itself; column y stores the single threat class that the directive addresses exclusively. The foreign-key constraint on y references t_hipaa_safeguard_physical.id, closing the cycle required by the paired axioms.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_hipaa_safeguard_physical(id)
);
```

| id | x | y |
| id | x | y |
|----|---|----|
| ctrl_01 | LockedPerimeter | phys_01 |
| ctrl_02 | EncryptedChannel | phys_02 |
| ctrl_03 | RoleBasedAccess | phys_03 |
| ctrl_04 | AuditLogRetention | phys_04 |
| ctrl_05 | MediaDisposal | phys_05 |

A reader can obtain every threat addressed by a given control by joining on y = phys_*.id.

## 2. Physical HIPAA Safeguards

Axiom 1 populates t_hipaa_safeguard_physical. Column id is the primary key. Column x names the safeguard class; column y names the control class that the safeguard implements. The foreign-key constraint on y references t_control_only_addresses_threat_class.id.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

| id | x | y |
|----|---|----|
| phys_01 | FacilityAccessControl | ctrl_01 |
| phys_02 | WorkstationLocation | ctrl_02 |
| phys_03 | DeviceAndMediaControl | ctrl_03 |
| phys_04 | PhysicalSafeguardsPolicy | ctrl_04 |
| phys_05 | VisitorSignIn | ctrl_05 |

Joining phys_01.y = ctrl_01.id yields the threat class LockedPerimeter that the physical safeguard addresses.

## 3. Technical HIPAA Safeguards

Axiom 3 defines t_hipaa_safeguard_technical. Its structure mirrors t_hipaa_safeguard_physical except that the safeguard classes belong to the technical family. The foreign key again references t_control_only_addresses_threat_class.id.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

| id | x | y |
|----|---|----|
| tech_01 | AccessControlMechanism | ctrl_01 |
| tech_02 | TransmissionSecurity | ctrl_02 |
| tech_03 | IntegrityControls | ctrl_03 |
| tech_04 | AuditControls | ctrl_04 |
| tech_05 | PersonOrEntityAuth | ctrl_05 |

A two-table join between t_hipaa_safeguard_technical and t_control_only_addresses_threat_class recovers the threat addressed by any technical safeguard.

## 6. Worked Multi-Hop Query Example

Question: which threat class is addressed by the physical safeguard that implements the same control referenced by PCI DSS requirement pci_04?

Start with pci_04.y = ctrl_04.  
Join ctrl_04.id = phys_04.y.  
Read phys_04.y = ctrl_04, then ctrl_04.y = phys_04.y yields LockedPerimeter? No—ctrl_04.y = phys_04, and phys_04 is already known; the threat is obtained by reading ctrl_04.y directly: phys_04.

Result row after two joins:

| pci_id | pci_x | ctrl_id | ctrl_y | phys_id | phys_x |
|--------|-------|---------|--------|---------|--------|
| pci_04 | EncryptedTransmission | ctrl_04 | phys_04 | phys_04 | PhysicalSafeguardsPolicy |

The threat class is therefore the value of ctrl_04.y, which is phys_04 (the class PhysicalSafeguardsPolicy). Further joins to t_hipaa_safeguard_technical or t_hipaa_safeguard_admin on the same control id surface additional safeguard families that share the identical risk address.
