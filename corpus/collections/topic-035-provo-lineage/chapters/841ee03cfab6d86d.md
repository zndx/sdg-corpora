# Compliance Directive Modeling in Relational Schemas

This chapter defines five tables that represent subclasses of cco:DirectiveICE drawn from HIPAA and PCI DSS specifications. The tables encode the axioms as foreign-key relationships, enabling verification that a given directive addresses only permitted threat classes and satisfies named safeguard or requirement slots.

## 1 Axiom grounding and table construction

Each table directly implements one axiom. Primary keys are opaque identifiers. Foreign keys enforce the existential and universal restrictions stated in the Manchester syntax.

### 1.1 Physical safeguard table

Table t_hipaa_safeguard_physical embodies axiom 1. Column id is the primary key. Column y is a foreign key into t_control_only_addresses_threat_class, ensuring every physical safeguard instance is linked to exactly one admissible threat class.

| id | x | y |
| id | x | y |
| physical-01 | Facility Access Control | threat-01 |
| physical-02 | Workstation Device Lock | threat-02 |
| physical-03 | Media Disposal Procedure | threat-03 |
| physical-04 | Visitor Escort Protocol | threat-01 |

### 1.2 Threat-addressing control table

Table t_control_only_addresses_threat_class embodies axiom 2. Column id is the primary key. Column y is a foreign key into t_hipaa_safeguard_physical, restricting the control to the listed physical safeguard.

| id | x | y |
| id | x | y |
| threat-01 | Unauthorized Physical Access | physical-01 |
| threat-02 | Unauthorized Data Access | physical-02 |
| threat-03 | Improper Media Destruction | physical-03 |
