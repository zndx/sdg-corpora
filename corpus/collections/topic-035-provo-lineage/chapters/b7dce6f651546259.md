# Chapter 4: Ontological Mapping of Regulatory Directives and Control Frameworks

## 4.0 Scope and Preamble

This chapter delineates the formal ontological structures governing the interoperability of regulatory directives within a unified compliance framework. Specifically, it addresses the integration of Health Insurance Portability and Accountability Act (HIPAA) safeguards and Payment Card Industry Data Security Standard (PCI DSS) requirements as subclasses of the Common Core Ontology (CCO) DirectiveICE. The mapping of these directives to specific threat classes and control mechanisms is established through deterministic relational schemas, ensuring that governance artifacts are auditable and logically consistent. The following sections provide a detailed analysis of five core axioms, verbalizing their semantic implications and grounding them in evidence-based data tables.

## 4.1 Physical Safeguard Implementation Protocols

### 4.1.1 Axiom Definition and Verbalization

The first axiom governing the framework is defined by the template `hipaa_safeguard_physical`. In the Manchester syntax, this is expressed as `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`. The natural language verbalization asserts that "{X} is something that hipaa safeguard {Y}". This axiom establishes a necessary condition for any physical safeguard directive: it must be a subclass of the `cco:DirectiveICE` and must exhibit the property of safeguarding a specific target entity, denoted as {Y}.

In the context of healthcare compliance, this relationship is critical for isolating physical controls—such as facility access restrictions or workstation security—from administrative or logical measures. The axiom ensures that physical directives are not merely abstract policies but are actively linked to the tangible assets or threat environments they are designed to protect.

### 4.1.2 Relational Schema and Data Population

The relational projection of this axiom is realized in the table `t_hipaa_safeguard_physical`. This table embodies the link between the specific directive class (`x`) and the safeguarded entity (`y`). The primary key (`id`) serves as the unique identifier for the directive instance, while the foreign key constraint on `y` ensures referential integrity to the control table (`t_control_only_addresses_threat_class`). This structure enforces the rule that a physical safeguard cannot exist in isolation; it must be anchored to a valid control definition that addresses a specific threat class.

The following data table illustrates instances of physical safeguards mapped to their respective control targets. These entries reflect standard facility security protocols required under HIPAA Security Rule §164.310(a)(1).

## 4.2 Control and Threat Addressing Mechanisms

### 4.2.1 Axiom Definition and Verbalization

The second axiom, `control_only_addresses_threat_class`, serves as a central node in the ontology, linking directives to the specific risks they mitigate. The Manchester syntax is defined as `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:addressesRisk only {Y:Class}`. Verbalized, this states that "{X} is something that addresses risk {Y}". The use of the "only" (universal) restriction in the object property `sdg:addressesRisk` implies that if the directive {X} addresses any risk, it must be exclusively of type {Y}. This creates a closed-world assumption regarding the risk profile of the directive, essential for precise audit scoping.

This axiom categorizes the control mechanism itself, distinguishing it based on the nature of the threat it neutralizes. It functions as the "target" for the safeguards defined in Section 4.1, creating a dependency hierarchy where safeguards implement controls, and controls define threat mitigation.

### 4.2.2 Relational Schema and Data Population

The table `t_control_only_addresses_threat_class` formalizes this relationship. The schema defines a primary key (`id`) for the control and a foreign key (`y`) that references the safeguard tables. Notably, the schema provided dictates a circular dependency where the control table references the physical safeguard table (`t_hipaa_safeguard_physical`). This recursive structure models the real-world compliance requirement that the definition of a control (addressing a risk) is often validated or instantiated by the specific physical safeguard employed to enact it.

## 4.3 Technical Safeguard Implementation Protocols

### 4.3.1 Axiom Definition and Verbalization

The third axiom, `hipaa_safeguard_technical`, mirrors the structure of the physical safeguard axiom but applies to logical and technical controls. The syntax is `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`, verbalized as "{X} is something that hipaa safeguard {Y}". In this context, {X} represents technical policies and procedures for electronic information systems, including access control, audit controls, and integrity controls as specified in HIPAA §164.312.

This distinction is vital for automated compliance auditing. While physical safeguards require manual observation, technical safeguards generate log data and system configurations that can be continuously monitored against the ontology. The axiom ensures that these technical directives are also subclassed under `cco:DirectiveICE`, maintaining a unified hierarchy for all governance artifacts.

### 4.3.2 Relational Schema and Data Population

The `t_hipaa_safeguard_technical` table shares the schema structure of the physical table, with the foreign key `y` pointing to `t_control_only_addresses_threat_class`. This linkage implies that technical safeguards are the implementation mechanism for the controls defined in Section 4.2. The data presented in Table 4.3 illustrates common technical safeguards, such as encryption and access authentication, mapped to their relevant control IDs.

These controls would define the specific risks (e.g., "Interception of Data in Transit" or "Unauthorized Logical Access") that the technical safeguards address.

## 4.4 Administrative Safeguard Implementation Protocols

### 4.4.1 Axiom Definition and Verbalization

The fourth axiom, `hipaa_safeguard_admin`, addresses the administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures. The axiom `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}` verbalizes to "{X} is something that hipaa safeguard {Y}". Here, {X} encompasses administrative standards such as Security Awareness Training, Risk Analysis, and Contingency Planning.

Administrative safeguards are often the most complex to model because they govern human behavior and organizational processes rather than static systems. By capturing these within the `cco:DirectiveICE` hierarchy, the framework allows for the correlation of policy documents (the directive) with specific operational outcomes or protected entities ({Y}).

### 4.4.2 Relational Schema and Data Population

The `t_hipaa_safeguard_admin` table provides the relational structure for these administrative directives. As with the previous safeguard types, the foreign key `y` links the administrative policy to a specific control class in `t_control_only_addresses_threat_class`. This mapping ensures that administrative requirements are not treated as vague guidelines but are tied to concrete risk mitigation controls.

## 4.5 PCI DSS Requirement Integration

### 4.5.1 Axiom Definition and Verbalization

The final axiom extends the framework beyond healthcare-specific regulations to include payment card industry standards. The axiom `pci_dss_requirement` is defined as `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`. Verbalized, "{X} is something that pci dss requirement {Y}". This axiom maps PCI DSS requirements (such as Requirement 1: Install and maintain a firewall configuration) to the same underlying control structure used for HIPAA safeguards.

This integration is crucial for organizations operating under hybrid regulatory environments (e.g., hospitals processing credit card payments). It allows the ontology to identify overlapping controls where a single directive satisfies both a HIPAA safeguard and a PCI DSS requirement, thereby reducing compliance redundancy.

### 4.5.2 Relational Schema and Data Population

The `t_pci_dss_requirement` table structurally mirrors the safeguard tables, with the foreign key `y` referencing `t_control_only_addresses_threat_class`. This design enforces the principle that PCI DSS requirements are implemented through the same fundamental control mechanisms that address organizational threats.
