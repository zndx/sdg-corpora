# Directive Governance in Regulatory Audits

This chapter specifies the relational encoding of five OWL axioms that govern audit, verification, requirement, and attestation processes. The encoding uses exactly the five tables projected from the axioms, each table serving as a deterministic container for class references and cardinality constraints. All column values are drawn from a regulatory compliance domain modelled on animal-welfare inspection procedures.

## 1 Schema Overview

The tables implement the family of directive-governance templates. Primary keys are opaque identifiers; foreign-key semantics are carried by the x, y and z columns, which hold class or individual references that may be joined across tables. Four to eight rows per table suffice to demonstrate multi-hop navigation while preserving the slot cardinalities stated in each axiom.

### 1.1 t_audit_conducted_by

This table realises AXIOM 1 (audit_conducted_by). Column id is the primary key; column x references the audit process class that must be conducted by at least one person. A reader can join x to the x column of t_attestation_min_one_signer to retrieve all attested audits performed by a given signatory.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.2 t_verification_min_one_evidence

This table realises AXIOM 2 (verification_min_one_evidence). Column id is the primary key; x identifies the verification process and y identifies the required evidence class. The NOT NULL constraint on y enforces the minimum cardinality of one evidence item. Joining y to the y column of t_requirement_only_satisfied_by yields the requirement satisfied by that evidence.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.3 t_requirement_equiv_specifies_target

This table realises AXIOM 3 (requirement_equiv_specifies_target). Column id is the primary key; x is the directive class, y the specification target, and z the subject to which the directive applies. Both y and z are mandatory, reflecting the equivalence axiom. Joining x to the x column of t_requirement_only_satisfied_by recovers the satisfaction restriction for the same directive.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.5 t_requirement_only_satisfied_by

This table realises AXIOM 5 (requirement_only_satisfied_by). Column id is the primary key; x identifies the directive and y the sole permissible satisfier class. Joining x to the x column of t_requirement_equiv_specifies_target recovers the full specification triple for that directive.

```sql
CREATE TABLE t_requirement_only_satisfied_by (
```

## 2 Cross-Join Demonstration

Consider the multi-hop question: “Which evidence class satisfies the directive that applies to AllMammals and is produced by the verification process WelfareInspection2020?”  

Begin with t_requirement_equiv_specifies_target where z = AllMammals; this yields rows req-001 and req-002, both carrying x = AnimalWelfareDirective.  
Next join on x to t_requirement_only_satisfied_by; the matching row ros-001 supplies y = PhotographicRecord.  
Finally join that y value to t_verification_min_one_evidence where x = WelfareInspection2020; the join returns rows vme-001 and vme-002, confirming that PhotographicRecord is admissible evidence.

The resulting joined tuple is therefore:

(WelfareInspection2020, AnimalWelfareDirective, AllMammals, PhotographicRecord)
