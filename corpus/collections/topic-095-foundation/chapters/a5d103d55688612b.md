# Chapter 7. Directive Governance in Compliance Audit Trails

This chapter presents five ontological templates that formalize governance processes within audit trails for registered charities and societies. The templates are realized as a fixed relational schema whose columns directly encode the slot types of each axiom. Cross-table joins on shared class references allow retrieval of multi-hop facts such as the signatory of an attestation that satisfies a requirement specifying a particular target.

## 1. Template Definitions and Table Embodiments

### 1.1 Audit Conducted By
Axiom 1 states that any instance of class X is a bfo:Process conducted by a cco:Person. The table therefore records only the identity of each such process; the person reference is carried in application data joined on the x column. The primary key is id; x functions as a foreign-key reference to process classes used in other tables.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| acb-001 | AnnualComplianceAudit |
| acb-002 | BoardElectionVerification |
| acb-003 | FinancialAttestationProcess |
| acb-004 | MembershipRegisterReview |
| acb-005 | GrantOutcomeAudit |

### 1.2 Verification Producing Evidence
Axiom 2 requires every verification process X to produce at least one evidence class Y. The table therefore contains a mandatory y column. Primary key is id; both x and y serve as join keys to process and evidence classes appearing in attestation and requirement tables.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| vme-001 | BoardElectionVerification | MeetingMinutes2023 |
| vme-002 | FinancialAttestationProcess | AuditedAccounts |
| vme-003 | AnnualComplianceAudit | PolicyRegister |
| vme-004 | MembershipRegisterReview | MemberListSnapshot |
| vme-005 | GrantOutcomeAudit | OutcomeReport |

### 1.3 Requirement Equivalent to Directive Specifying Target
Axiom 3 defines a requirement X as any cco:DirectiveICE that both specifies a class Y and applies to a class Z. The table therefore carries two mandatory reference columns. Primary key is id; y and z are foreign-key references usable in satisfaction and verification joins.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y | z |
|----|---|---|---|
| req-001 | FinancialReportingRequirement | AuditedAccounts | AnnualReport |
| req-002 | ElectionIntegrityRequirement | MeetingMinutes2023 | BoardComposition |
| req-003 | MembershipAccuracyRequirement | MemberListSnapshot | RegisteredMembership |
| req-004 | GrantComplianceRequirement | OutcomeReport | FundingAgreement |
| req-005 | PolicyCurrencyRequirement | PolicyRegister | OperationalPolicies |

### 1.4 Attestation Signed By
Axiom 4 states that an attestation process X must be signed by at least one cco:Person. The table records only the process class; signer identity is resolved through application joins on x. Primary key is id.

```sql
CREATE TABLE t_attestation_min_one_signer (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| att-001 | FinancialAttestationProcess |
| att-002 | BoardElectionVerification |
| att-003 | AnnualComplianceAudit |
| att-004 | MembershipRegisterReview |
| att-005 | GrantOutcomeAudit |

### 1.5 Requirement Satisfied Only By
Axiom 5 restricts the satisfiers of a requirement X to members of class Y. The table therefore pairs each requirement class with its sole permitted satisfier class. Primary key is id; x and y are join keys to the requirement and verification tables.

```sql
CREATE TABLE t_requirement_only_satisfied_by (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| ros-001 | FinancialReportingRequirement | AuditedAccounts |
| ros-002 | ElectionIntegrityRequirement | MeetingMinutes2023 |
| ros-003 | MembershipAccuracyRequirement | MemberListSnapshot |
| ros-004 | GrantComplianceRequirement | OutcomeReport |
| ros-005 | PolicyCurrencyRequirement | PolicyRegister |

## 2. Cross-Join Example

To determine which person-signed attestation satisfies the requirement that applies to the AnnualReport, join t_requirement_equiv_specifies_target on y to t_verification_min_one_evidence, then on x to t_attestation_min_one_signer, and finally on x to t_audit_conducted_by. One such path yields:

- req-001 (FinancialReportingRequirement) specifies AuditedAccounts and applies to AnnualReport  
- AuditedAccounts is produced by FinancialAttestationProcess (vme-002)  
- FinancialAttestationProcess is attested (att-001) and conducted by (acb-003) the same process class.

The joined row therefore records that the AnnualReport is covered by an attestation signed under the FinancialAttestationProcess that satisfies FinancialReportingRequirement.
