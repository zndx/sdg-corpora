# Chapter 4: Relational Mapping of Artifact Governance and Addressability

## 4.1 Scope and Preamble

This chapter delineates the translation of upper-level ontology axioms into a relational schema designed for high-fidelity audit trails and compliance reporting. The focus is restricted to three specific conceptual domains: the observation of participant artifacts, the ownership constraints of physical artifacts, and the postal addressability of fixed locations. The mapping process utilizes the BFO (Basic Formal Ontology) and CCO (Common Core Ontologies) frameworks to ensure semantic interoperability between the logical data layer and the physical governance domain. Implementers must ensure that all data insertions strictly adhere to the foreign key constraints defined herein, as these constraints enforce the existential dependencies required by the ontology.

## 4.2 Observation with Participant Artifacts

The foundational axiom for this governance framework is derived from the BFO definition of a process. Specifically, we utilize the axiom `observation_with_participant`, which posits that a specific class of process (X) is defined by the presence of a participant artifact. In formal Manchester syntax, this is expressed as `Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`. The term `bfo:0000015` denotes "Process," an entity that unfolds in time and possesses temporal parts, while `bfo:0000057` ("has participant") establishes a mereological connection between the process and the artifact.

In the context of a compliance audit, this table serves as the primary registry for all "observation events." An observation event is not merely a record; it is a process that must involve at least one artifact to exist. This structure prevents the logging of null or abstract events that lack physical evidence or interaction. The table `t_observation_with_participant` captures these events, where the primary key `id` serves as the immutable reference for the process instance, and the column `x` denotes the specific class or type of observation process being instantiated.

### 4.2.1 Schema Implementation

The relational projection of this axiom creates a dependency structure where the observation acts as the anchor for subsequent ownership and addressability claims. The schema is defined as follows:

```sql
CREATE TABLE t_observation_with_participant (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
```

This table embodies the axiom that an observation process is inherently dependent on the participation of an artifact. The primary key `id` ensures that each observation process is uniquely identifiable within the audit log, serving as the target for foreign key constraints from other tables that rely on the existence of this process.

## 4.3 Artifact Ownership Constraints

Building upon the registry of observations, the governance framework enforces strict ownership protocols for managed artifacts. The axiom `artifact_min_one_owner` asserts that any entity classified as an Artifact (X) must possess a minimum of one owner (Y). The Manchester syntax is defined as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasOwner min 1 {Y:Class}`. This constraint is critical for asset tracking and liability management; it ensures that there are no "orphan" assets within the system.

The verbalization of this axiom, "{X} is a artifact," implies that the entity exists as a continuous, independent entity that persists through time while maintaining its identity. The `sdg:hasOwner` property links this artifact to a responsible agent or entity. In this specific schema implementation, the "owner" is not stored as a string literal but is referenced via a foreign key to the `t_observation_with_participant` table. This design choice implies that ownership is not an intrinsic static property but is derived from a specific observation process (e.g., the process of assigning ownership or a custody transfer agreement).

### 4.3.1 Schema Implementation

The table `t_artifact_min_one_owner` enforces the `min 1` cardinality constraint through the `NOT NULL` requirement on the `y` column. The foreign key constraint ensures that an owner cannot be assigned to an artifact without a corresponding valid observation process that authorized or recorded that ownership.

```sql
CREATE TABLE t_artifact_min_one_owner (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)
)
```

This table embodies the axiom that an artifact is defined by its ownership lineage. The primary key `id` identifies the specific artifact instance, `x` denotes the artifact class, and `y` references the observation process that validates the ownership claim.

## 4.4 Spatial Addressability of Places

The final component of this chapter addresses the spatial dimension of the governance framework. While artifacts are mobile and process-dependent, places are fixed locations that require precise identification for regulatory reporting. The axiom `schemaorg_place_address` defines a Place (X) as a subclass of `cco:Artifact` (in this ontology's extension) that possesses a postal address (Y). The Manchester syntax is `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`.

This axiom ensures that any location registered as a managed site must have a verifiable postal address. The verbalization, "{X} is something that has postal address {Y}," establishes a necessary dependency between the place entity and its address attribute. Similar to the ownership model, the address (Y) is resolved through a reference to an observation process. This approach allows the system to track not just the current address, but the *verification event* that confirmed the address details, thereby providing an audit trail for compliance with zoning and delivery regulations.

### 4.4.1 Schema Implementation

The table `t_schemaorg_place_address` maps the place entity to its address verification. The foreign key linking `y` to `t_observation_with_participant` ensures that the address data is grounded in a specific verification event (e.g., a site visit or utility bill confirmation).

```sql
CREATE TABLE t_schemaorg_place_address (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)
)
```

This table embodies the axiom that a place is spatially defined by its postal address, which is validated through an observation process. The primary key `id` identifies the place, `x` denotes the place class, and `y` references the observation process that validated the address.
