## 4.0 Scope and Preamble

This chapter establishes the formal ontological framework governing the classification, interaction, and security constraints of kernel-level interfaces, specifically focusing on the extended Berkeley Packet Filter (eBPF) subsystems and system call semantics. The definitions provided herein are not merely descriptive; they constitute a prescriptive schema for auditing kernel compliance. Which aspect of kernel management is most critical? Are isolation boundaries more important than execution efficiency? Are syscall definitions more critical than the hooks that observe them? Obviously, each is important and they all interact to make a secure operating system function smoothly. However, for the purposes of this governance framework, we prioritize the *structural integrity* of the definitions. Every entity discussed is anchored to the BFO (Basic Formal Ontology) upper-level categories, ensuring that logical derivations remain consistent across distinct hardware implementations. The following sections detail the specific axioms that define syscall equivalence, return type constraints, hook-program attachment limits, and security tiering.

---

## 4.1 Syscall Equivalence within Subsystems

The first axiom of governance addresses the categorization of system calls. In a complex kernel environment, a system call cannot exist in a vacuum; it must be axiomatically defined as a `Designative Information Content Entity` (ICE). This means the syscall is not merely a function jump but a designated, information-bearing construct within the system's logical architecture. Furthermore, to ensure proper modularity and auditability, every syscall must be equivalent to the intersection of its status as a Designative ICE and its presence within a specific subsystem.

This relationship is formalized by the axiom: **Class: {X} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y})**.

In this schema, {X} represents the specific Syscall Class (e.g., `FileIOOpen`), and {Y} represents the Subsystem Class (e.g., `FileSystem`). The equivalence axiom ensures that one cannot exist without the other; a syscall is defined *by* the subsystem it inhabits. This prevents "orphan" syscalls that lack clear ownership or subsystem boundaries, a common source of compliance violations in monolithic kernel designs.

To operationalize this axiom for audit trails, we utilize the following relational structure. The primary key is the unique identifier (`id`), while the `x` and `y` columns serve as foreign keys referencing the defined Class entities.

**Table 4.1: Syscall-Subsystem Equivalence Mapping**

| id | x (Syscall Class) | y (Subsystem Class) |
| :--- | :--- | :--- |
| `map_001` | `bpf_map_create` | `BPFSubsystem` |
| `sock_001` | `socket_accept` | `NetworkSubsystem` |
| `fs_open_01` | `file_open_at` | `FileSystemSubsystem` |
| `mem_mmap_01` | `memory_map_anon` | `MemoryManagementSubsystem` |
| `proc_exec_01` | `process_execute` | `ProcessControlSubsystem` |

*Table 4.1 Note: The `id` column provides a unique reference for the equivalence assertion. The `x` column denotes the specific syscall class, while `y` denotes the requisite subsystem class. This mapping enforces the ontological constraint that the syscall is strictly defined by its subsystem context.*

## 4.2 Return Type Cardinality Constraints

While defining *where* a syscall lives is critical, defining *what* it returns is equally vital for maintaining type safety and preventing memory corruption through interface misuse. The second axiom governing this framework imposes a strict cardinality constraint on the return values of system calls.

The axiom states: **Class: {X} SubClassOf: cco:DesignativeICE, sdg:hasReturnType max 1 {Y}**.

Verbalized, {X} (the Syscall) is a designative information content entity that has a return type of {Y} with a maximum cardinality of 1. This constraint effectively prohibits syscalls from returning complex, multi-value tuples or undefined unions. In a compliant kernel, a syscall must resolve to a single, typed return value (or a void type). This simplification is mandatory for formal verification and reduces the attack surface for type confusion vulnerabilities.

The relational projection of this axiom tracks the allowable return types for specific syscall classes. The structure is straightforward: `id` acts as the primary key, `x` is the Syscall Class, and `y` is the singular Return Type Class.

**Table 4.2: Syscall Return Type Constraints**

| id | x (Syscall Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| `rt_001` | `bpf_map_create` | `FileDescriptorInteger` |
| `rt_002` | `socket_accept` | `FileDescriptorInteger` |
| `rt_003` | `process_exit` | `VoidType` |
| `rt_004` | `get_user_id` | `UIDInteger` |
| `rt_005` | `read_link` | `PathStringBuffer` |

*Table 4.2 Note: This table enumerates valid return configurations. The constraint `max 1` is enforced by the schema design, ensuring that for any given `id` and `x`, only one `y` is permissible. This aligns with the verbalization that the syscall is an entity with a single, defined return type.*

## 4.3 Kernel Hook and Program Attachment Limits

Moving from passive syscalls to active observability, we must govern the attachment of eBPF programs to kernel hooks. In modern kernels, a "hook" is an artifact—a stable, deployable piece of infrastructure within the kernel that allows external programs to attach to specific events. However, uncontrolled attachment of multiple programs to a single hook can lead to resource exhaustion (CPU throttling) or non-deterministic execution order.

Therefore, this framework adopts a restrictive axiom: **Class: {X} SubClassOf: cco:Artifact, sdg:hasAttachedProgram max 1 {Y}**.

This asserts that {X} (the Kernel Hook) is an Artifact that has an attached program {Y} with a maximum cardinality of 1. In this specific governance regime, a hook may support only one attached eBPF program at any given time. This "single-program" rule ensures that the behavior of the hook is deterministic and that the program responsible for the hook's action is clearly identifiable for audit purposes. While general-purpose kernel implementations might allow multi-program attachments (linked lists of programs), this compliance framework mandates exclusivity to guarantee strict isolation of logic.

The table below embodies this constraint. It maps specific Hook Artifacts to their attached Program Classes. The `id` is the primary key; `x` represents the Hook, and `y` represents the attached Program.

**Table 4.3: Kernel Hook-Program Attachment Registry**

| id | x (Hook Artifact) | y (Attached Program Class) |
| :--- | :--- | :--- |
| `hk_001` | `tracepoint_sys_enter_execve` | `SecurityAuditProgram` |
| `hk_002` | `kprobe_do_tcp_sendmsg` | `NetworkThroughputMonitor` |
| `hk_003` | `cgroup_skb_ingress` | `FirewallFilterProgram` |
| `hk_004` | `socket_filter` | `PacketCaptureProgram` |
| `hk_005` | `iter_task` | `ProcessEnumeratorProgram` |

*Table 4.3 Note: The `max 1` constraint is visible in the row structure; each Hook Artifact (`x`) is associated with exactly one Program Class (`y`). This registry is the canonical source for determining which program logic is active on a specific kernel artifact.*

## 4.4 Security Tiering of Syscalls

Finally, we must address the privilege levels associated with kernel operations. Not all syscalls are created equal; some manipulate fundamental hardware resources, while others merely read user-space state. To enforce the principle of least privilege, this framework assigns security tiers to syscalls.

The governing axiom is: **Class: {X} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y}**.

Verbalized, {X} is a designative information content entity that is "at security tier" {Y}. This uses an existential restriction ("some"), meaning that for a syscall to be valid in this ontology, it must be associated with at least one defined security tier. These tiers (e.g., `Ring0Privileged`, `Ring3Unprivileged`, `SecureWorld`) dictate the execution context and the requisite CPU mode (user vs. kernel) required to invoke the interface.

The following table documents the security tier assignment for various syscall classes. The primary key is `id`; `x` is the Syscall Class, and `y` is the Security Tier Class.

**Table 4.4: Syscall Security Tier Classification**

| id | x (Syscall Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| `st_001` | `bpf_map_create` | `CapableTier` |
| `st_002` | `process_execute` | `PrivilegedTier` |
| `st_003` | `get_time_of_day` | `UnprivilegedTier` |
| `st_004` | `mount_filesystem` | `SuperUserTier` |
| `st_005` | `write_memory` | `RestrictedTier` |

*Table 4.4 Note: The `y` column must not be null, as per the schema constraint `NOT NULL`. This reflects the ontological requirement that every valid syscall must inhabit a specific security tier. This mapping is essential for automated policy enforcement engines that reject syscall invocations originating from insufficiently privileged contexts.*

## 4.5 Summary of Compliance Requirements

The definitions and tables provided in this chapter constitute the evidence-anchored basis for kernel compliance auditing. It is easier to make decisions involving things than decisions involving people, but in kernel engineering, the "things" (syscalls, hooks, and tiers) are complex enough to require rigorous formalization.

To verify compliance against this framework, auditors must:
1.  Validate that every Syscall Class maps to a Subsystem Class (Table 4.1).
2.  Confirm that no Syscall Class defines more than one Return Type Class (Table 4.2).
3.  Ensure that no Kernel Hook Artifact has more than one Attached Program Class (Table 4.3).
4.  Verify that every Syscall Class is assigned a valid, non-null Security Tier Class (Table 4.4).

Failure to populate these tables as described, or deviation from the axiomatic structures defined in Sections 4.1 through 4.4, shall result in a non-compliance rating.
