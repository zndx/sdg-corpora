### 4.0 Scope and Preamble

This chapter delineates the formal ontological constraints governing the design, implementation, and auditing of kernel interfaces within the eBPF subsystem framework. It establishes the necessary and sufficient conditions for system call classification, return type cardinality, artifact attachment protocols, and security tier stratification. The definitions provided herein are binding for all compliance audits, interface verification procedures, and system hardening initiatives. Adherence to these axioms ensures that the information content entities (ICEs) residing within the kernel space maintain structural integrity and deterministic behavior, thereby mitigating risks associated with type ambiguity and unauthorized program attachment.

### 4.1 Syscall Equivalence in Subsystem

The foundational axiom for identifying valid system calls within the kernel environment is defined by the template `syscall_equiv_in_subsystem`. This axiom asserts that for a class to be recognized as a valid system call interface, it must be equivalent to the intersection of a `DesignativeICE` and a specific subsystem context. In formal terms, a class {X} is a system call if and only if it is a Designative Information Content Entity and is located within some Syscall Subsystem {Y}.

This equivalence relation serves as a primary filter for interface validation. It prevents the misclassification of general kernel functions as system calls by enforcing the requirement that the entity must possess designative properties (i.e., it must refer to or designate a specific operational directive) and exist within a bounded subsystem scope. From an auditing perspective, any entity claiming to be a system call that cannot be mapped to a specific subsystem instance fails this equivalence test and must be flagged for review.

The relational projection of this axiom, embodied in Table 4.1, catalogs the valid system call classes and their corresponding subsystems. The primary key (`id`) ensures referential integrity for each mapping instance.

**Table 4.1: System Call Equivalence in Subsystem Mappings**

| id | x (Class) | y (Subsystem Class) |
| :--- | :--- | :--- |
| rec_001 | BpfSyscall | NetworkSubsystem |
| rec_002 | ProcessForkSyscall | ProcessSubsystem |
| rec_003 | FileDescriptorSyscall | IOSubsystem |
| rec_004 | MemoryMapSyscall | VMMSubsystem |
| rec_005 | SocketBindSyscall | NetworkSubsystem |

The data presented in Table 4.1 illustrates the application of the equivalence axiom. For instance, the `BpfSyscall` (x) is validly classified as a system call because it is a `DesignativeICE` that resides within the `NetworkSubsystem` (y). Similarly, the `ProcessForkSyscall` derives its validity from its residence within the `ProcessSubsystem`. This mapping is not merely taxonomic; it is functional. The subsystem context dictates the namespace resolution and the privilege domain in which the system call operates. Consequently, any deviation from these recorded pairs—such as invoking a `MemoryMapSyscall` within the `NetworkSubsystem` context—would constitute a structural violation of the ontology.

### 4.2 Syscall Return Type Cardinality

To ensure functional determinism and prevent interface ambiguity, the ontology enforces a strict cardinality constraint on the return types of system calls. The axiom `syscall_max_one_return` stipulates that any class {X} which is a subclass of `DesignativeICE` (i.e., a system call) must possess a maximum of one return type {Y}. This constraint is critical for type safety and predictability in kernel-space execution.

In practice, this means that a system call interface cannot be polymorphic in its return type definition. While the *value* of the return may vary (e.g., an integer status code), the *class* of the return type must be singular. If a system call were permitted to have multiple return types, the calling process would lack a deterministic method for interpreting the result without runtime type inspection, which introduces unacceptable latency and complexity in the kernel path.

The enforcement of this axiom is verified through the schema defined in `t_syscall_max_one_return`. As shown in Table 4.2, each system call class is mapped to exactly one return type class. This table serves as the authoritative source for return type definitions during interface compilation and runtime verification.

**Table 4.2: System Call Return Type Constraints**

| id | x (Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| rec_006 | BpfSyscall | IntegerReturn |
| rec_007 | ProcessForkSyscall | ProcessIdentifierReturn |
| rec_008 | FileDescriptorSyscall | FileDescriptorReturn |
| rec_009 | MemoryMapSyscall | VirtualAddressReturn |
| rec_010 | SocketBindSyscall | IntegerReturn |

The entries in Table 4.2 demonstrate the restriction. The `BpfSyscall` is constrained to return an `IntegerReturn`, representing a success or error code. The `ProcessForkSyscall` is constrained to return a `ProcessIdentifierReturn` (PID). It is noteworthy that the `IntegerReturn` type is reused by `SocketBindSyscall`. This is permissible under the axiom, as the constraint applies to the cardinality of the relationship (max 1), not the uniqueness of the return type class across different system calls. However, a single system call entry, such as `ProcessForkSyscall`, must never appear in this table with a second, distinct return type class, such as `IntegerReturn`, simultaneously.

### 4.3 Kernel Hook Program Attachment

The interaction between static kernel artifacts and dynamic instrumentation programs is governed by the axiom `kernelhook_max_one_program_attached`. This axiom defines that a class {X}, which is a subclass of `Artifact` (specifically a kernel hook), may have a maximum of one program {Y} attached to it. This constraint is fundamental to maintaining the stability of the kernel execution environment.

Kernel hooks, such as tracepoints or kprobes, represent fixed points in the kernel code where external execution logic may be inserted. By limiting the attachment to a single program, the architecture prevents resource contention, stack overflow, and non-deterministic execution order that could arise if multiple programs attempted to process the same event hook simultaneously. This "single-program-per-hook" rule simplifies the audit trail, as the behavior triggered by a specific hook can be attributed to a single, verifiable program entity.

The relational schema `t_kernelhook_max_one_program_attached` tracks these attachments. The data provided in Table 4.3 represents the current authorized state of hook-to-program bindings.

**Table 4.3: Kernel Hook Attachment Constraints**

| id | x (Artifact Class) | y (Program Class) |
| :--- | :--- | :--- |
| rec_011 | SocketFilterHook | BpfFilterProgram |
| rec_012 | KprobeHook | BpfTraceProgram |
| rec_013 | CgroupDeviceHook | BpfCgroupProgram |
| rec_014 | SchedProcessExecHook | BpfLSMProgram |
| rec_015 | XdpHook | BpfXdpProgram |

In Table 4.3, the `SocketFilterHook` (x) is associated exclusively with the `BpfFilterProgram` (y). This mapping indicates that any packet interception event at the socket layer will be processed solely by the defined filter program. The axiom ensures that no secondary program, such as a logging utility, can be attached to the same `SocketFilterHook` instance. If a secondary function is required, it must be chained within the logic of the single attached program or attached to a distinct hook artifact. This constraint is rigorously enforced during the load phase of eBPF programs; attempts to attach a program to a hook already occupied result in an `EEXIST` error, thereby preserving the 1:1 cardinality mandated by the ontology.

### 4.4 Syscall Security Tier Stratification

The final structural constraint addressed in this chapter pertains to the security classification of system calls. The axiom `syscall_at_security_tier` posits that a class {X}, being a `DesignativeICE` (system call), must be situated at some security tier {Y}. This axiom facilitates the implementation of Mandatory Access Control (MAC) and privilege auditing by semantically grounding system calls within a specific security domain.

The "security tier" represents the level of privilege and trust required to invoke the system call. By axiomatically defining the tier for each system call class, the governance framework can automatically generate allow-lists and deny-lists for different security contexts (e.g., containers vs. host processes). A system call residing at a high security tier (e.g., `PrivilegedTier`) is implicitly restricted from invocation by lower-tier subjects unless explicit elevation grants are recorded.

Table 4.4 provides the classification of system calls according to their security tiers. This table is essential for compliance checking, as it allows auditors to verify that the runtime privileges of a process match the security tier of the system calls it invokes.

**Table 4.4: System Call Security Tier Classifications**

| id | x (Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| rec_016 | BpfSyscall | PrivilegedTier |
| rec_017 | ProcessForkSyscall | StandardTier |
| rec_018 | FileDescriptorSyscall | StandardTier |
| rec_019 | MemoryMapSyscall | PrivilegedTier |
| rec_020 | SocketBindSyscall | StandardTier |

The stratification evident in Table 4.4 reflects the principle of least privilege. The `BpfSyscall` is placed at the `PrivilegedTier` because it allows modification of kernel behavior and requires `CAP_SYS_ADMIN` or `CAP_BPF` capabilities. Conversely, the `ProcessForkSyscall` and `SocketBindSyscall` are classified under the `StandardTier`, as they are essential operations for standard application workloads and do not, by default, grant elevated system privileges. The `MemoryMapSyscall` is classified as `PrivilegedTier` in specific contexts where it interacts with device memory or performs executable mappings, reflecting the potential for code injection or memory corruption if misused. Compliance officers must ensure that any process attempting to invoke `rec_016` or `rec_019` possesses the appropriate credentials corresponding to the `PrivilegedTier`.
