## 4.1 Scope and Preamble

This chapter establishes the formal ontological mapping required for the auditing of Extended Berkeley Packet Filter (eBPF) kernel interactions. It defines the structural constraints governing System Calls (syscalls) and Kernel Hooks within a secure operating environment. The definitions provided herein are derived from the OWL 2 RL profile and are intended for use by compliance officers, system architects, and security auditors to verify that kernel extensions adhere to the principle of least privilege and type safety. The following sections detail four primary axioms governing the equivalence of syscalls to subsystems, return type cardinality, program attachment limits, and security tier stratification.

---

## 4.2 Syscall Equivalence within Subsystems

### 4.2.1 Definition and Axiomatic Structure

The foundational axiom for syscall identification asserts that a specific interface is formally equivalent to the intersection of two conditions: it must be a Designative Information Content Entity (ICE), and it must reside within a specific Syscall Subsystem. In formal ontology, this is expressed as:

**Class:** {X:Class} **EquivalentTo:** cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})

This equivalence relation is strict. It dictates that for an entity to be recognized as a valid syscall of type X, it is necessary and sufficient that it functions as a designative entity (a named informational construct) and that it possesses a property relationship with a subsystem Y. This prevents the misclassification of raw memory addresses or unlabeled functions as syscalls. The subsystem Y acts as a logical container or domain, ensuring that the syscall is scoped correctly within the kernel architecture (e.g., networking, file system, process control).

### 4.2.2 Implementation and Verification

During the audit phase, verifiers must ensure that every syscall invoked by a user-space process maps unambiguously to a subsystem entry. Failure to map to a subsystem implies a violation of the equivalence axiom, resulting in an "Orphaned Interface" classification.

The following table illustrates valid instances where the equivalence holds true. The primary key is the unique identifier for the specific equivalence assertion, while the foreign keys reference the defined Syscall Class (X) and the Subsystem Class (Y).

| ID | Syscall Class (X) | Subsystem Class (Y) |
| :--- | :--- | :--- |
| equiv_001 | bpf | bpf_subsystem |
| equiv_002 | socketcall | network_subsystem |
| equiv_003 | mount | filesystem_subsystem |
| equiv_004 | clone | process_subsystem |
| equiv_005 | keyctl | key_management_subsystem |

**Table 4.1: Syscall Equivalence Assertions (t_syscall_equiv_in_subsystem)**

The data in Table 4.1 demonstrates that the `bpf` syscall is defined strictly by its existence within the `bpf_subsystem`. This logical containment is the sole criteria for its classification as a DesignativeICE in this context.

## 4.3 Return Type Constraints on Syscalls

### 4.3.1 Cardinality and Type Safety

To maintain kernel stability and type safety, the ontology enforces a cardinality constraint on the return values of syscalls. The axiom governing this constraint is defined as:

**Class:** {X:Class} **SubClassOf:** cco:DesignativeICE, sdg:hasReturnType max 1 {Y:Class}

Verbalization: {X} is a designative information content entity that has a return type of maximum 1 {Y}.

This constraint dictates that any valid syscall X must not possess multiple return types. While a C implementation might use a union or a pointer to a structure to return complex data, the ontological definition requires that the *designated* return type Y be singular. This restriction is critical for static analysis tools and runtime verification environments, as it simplifies the prediction of stack state changes following a syscall exit. If a syscall were to return disparate types depending on runtime conditions without a unifying supertype Y, it would violate this `SubClassOf` restriction.

### 4.3.2 Audit Implications

Auditors must inspect the function signatures of the kernel interface. If a syscall X is found to return an integer in one success path and a pointer in another, and these are not subsumed by a single class Y in the ontology, the implementation is non-compliant. The `max 1` qualifier ensures that the relationship `hasReturnType` is functional.

Table 4.2 provides a non-exhaustive list of compliant syscall instances and their singular return types.

| ID | Syscall Class (X) | Return Type Class (Y) |
| :--- | :--- | :--- |
| ret_001 | read | ssize_t |
| ret_002 | open | int_fd |
| ret_003 | mmap | void_ptr |
| ret_004 | getpid | pid_t |
| ret_005 | gettimeofday | int_status |

**Table 4.2: Syscall Return Type Constraints (t_syscall_max_one_return)**

In the instance `ret_001`, the `read` syscall is strictly bound to the `ssize_t` class. Even though `read` may return -1 to indicate error, this value is within the domain of `ssize_t`, thereby preserving the "max 1" constraint.

## 4.4 Program Attachment Limits on Kernel Hooks

### 4.4.1 Artifact and Program Relationship

Kernel hooks serve as the anchor points for eBPF programs. Unlike syscalls, which are informational entities, hooks are treated as Artifacts—tangible components of the kernel's execution logic. The governing axiom for these artifacts is:

**Class:** {X:Class} **SubClassOf:** cco:Artifact, sdg:hasAttachedProgram max 1 {Y:Class}

Verbalization: {X} is an artifact that has a maximum of 1 attached program {Y}.

This axiom enforces a 1:1 cardinality between a specific hook instance X and the attached eBPF program Y. In the context of security governance, this limit prevents "program stacking" on a single hook instance, which can lead to unpredictable execution order, resource contention, and complex failure modes. By defining the Hook X as an `Artifact` and limiting the `hasAttachedProgram` property to a maximum of 1, the framework mandates that if multiple programs are required to observe the same event, they must be attached to distinct hook instances (e.g., different tracepoint IDs or kprobe multi-attach variations) or combined into a single monolithic program Y prior to loading.

### 4.4.2 Governance and Enforcement

Compliance checks must verify that the kernel's internal data structures reflect this limitation. If a hook X is found to reference two distinct program IDs Y1 and Y2 simultaneously, the system is in a state of violation. This axiom is particularly relevant for LSM (Linux Security Module) hooks and Tracepoints.

Table 4.3 details compliant hook-to-program bindings.

| ID | Hook Artifact (X) | Attached Program (Y) |
| :--- | :--- | :--- |
| hook_001 | tracepoint_sys_enter_execve | prog_exec_monitor |
| hook_002 | kprobe_do_tcp_sendmsg | prog_tcp_analyzer |
| hook_003 | cgroup_skb_ingress | prog_net_filter |
| hook_004 | socket_filter | prog_socket_inspector |
| hook_005 | perf_event_open | prog_profiler |

**Table 4.3: Kernel Hook Program Attachments (t_kernelhook_max_one_program_attached)**

As shown in row `hook_001`, the `tracepoint_sys_enter_execve` artifact is exclusively associated with `prog_exec_monitor`. There is no ambiguity regarding which program handles the execution event at this specific hook point.

## 4.5 Security Tier Assignment

### 4.5.1 Stratification of Designative Entities

The final axiom addresses the security classification of syscalls. It mandates that every syscall exists within a specific security context or tier. The axiom is formalized as:

**Class:** {X:Class} **SubClassOf:** cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}

Verbalization: {X} is something that is at security tier {Y}.

This utilizes an existential restriction (`some`), indicating that for a syscall X to be valid, it must be associated with at least one security tier Y. The tiers represent hierarchical levels of privilege and sensitivity (e.g., Tier 0: Critical Kernel, Tier 1: Hardware Access, Tier 2: Standard I/O). This classification allows the governance framework to apply policy rules based on the tier of the syscall being invoked. For instance, syscalls at a "Critical" tier may require additional capability checks or may be restricted entirely in unprivileged namespaces.

### 4.5.2 Classification Logic

The assignment of a tier Y is not merely metadata; it is a constraint on the operational behavior of the syscall. A syscall X lacking a defined tier Y is considered "unclassified" and must be blocked by default in a compliant enforcement engine. This ensures that all interface interactions are explicitly mapped to the security model.

Table 4.4 categorizes common syscalls by their requisite security tiers.

| ID | Syscall Class (X) | Security Tier (Y) |
| :--- | :--- | :--- |
| tier_001 | reboot | Tier_0_Critical |
| tier_002 | init_module | Tier_0_Critical |
| tier_003 | setuid | Tier_1_Privileged |
| tier_004 | mmap | Tier_2_Standard |
| tier_005 | getuid | Tier_3_Benign |

**Table 4.4: Syscall Security Tier Classifications (t_syscall_at_security_tier)**

The table illustrates the stratification logic. `reboot` and `init_module` are placed in `Tier_0_Critical`, reflecting their ability to modify the kernel state or system availability. Conversely, `getuid` is relegated to `Tier_3_Benign`, indicating it poses minimal risk and requires fewer security resources to monitor.
