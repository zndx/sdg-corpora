## 4.1 Preamble and Scope

This chapter establishes the formal ontological constraints governing the classification of kernel-level entities within the `04_ebpf_kernel` family. It delineates the axiomatic relationships between Information Content Entities (ICEs), Artifacts, and their respective security and structural attributes. The definitions provided herein are binding for all compliance audits, system verification protocols, and interface design documentation. The primary objective is to ensure unambiguous semantic mapping between kernel syscall interfaces and their logical subsystems, return types, and attachment points. Adherence to these axioms is mandatory for maintaining the integrity of the system-wide governance framework.

## 4.2 Syscall Subsystem Equivalence

### 4.2.1 Definition and Axiomatic Basis

The classification of a syscall interface is not merely a naming convention but a structural equivalence to specific subsystem domains. Under the axiom `syscall_equiv_in_subsystem`, a class `X` is formally defined as equivalent to a `cco:DesignativeICE` if and only if it exists within the scope of a specific syscall subsystem `Y`. This equivalence relation implies that the identity of the interface is inextricably bound to the subsystem it inhabits. An interface cannot be defined independently of its subsystem context; to move an interface between subsystems is to redefine the entity itself.

In formal Manchester syntax, this relationship is expressed as:
`Class: {X:Class} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})`

This axiom serves as a primary validation key for the system registry. It ensures that all designative information content entities are properly scoped, preventing namespace collisions and ensuring clear lines of responsibility for subsystem maintenance.

## 4.3 Return Type Cardinality Constraints

### 4.3.1 Definition and Axiomatic Basis

To maintain type safety and predictability in kernel-space interactions, strict cardinality constraints are imposed on the return values of designative interfaces. The axiom `syscall_max_one_return` dictates that any class `X`, which is a subclass of `cco:DesignativeICE`, may possess a maximum of one return type, denoted as class `Y`. This restriction prohibits the definition of ambiguous interfaces that might return disparate types depending on runtime state, a practice that is strictly forbidden in high-assurance systems.

The verbalization of this axiom asserts: `{X} is a designative information content entity`. The formal Manchester syntax is:
`Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:hasReturnType max 1 {Y:Class}`

This constraint is fundamental to the `04_ebpf_kernel` family's complexity management. By limiting the return type to a maximum of one (`max 1`), the ontology enforces a strict contract between the caller and the kernel. While this axiom permits the possibility of zero return types (void functions) in some interpretations of OWL cardinality, in this specific governance framework, it is interpreted as a strict upper bound to prevent polymorphic return ambiguity.

### 4.3.2 Return Type Classification

The implementation of this axiom is recorded in the system's type registry. The table below maps specific syscall classes to their sanctioned return types. The structure `id, x, y` allows for the tracing of which specific interface (`x`) is constrained to return which data type (`y`).

| :--- | :--- | :--- |
| RT-101 | `VFS_Read_Operation` | `SignedInteger64` |

### 4.3.3 Audit Implications

Compliance officers must ensure that no interface `x` is defined with multiple potential return types `y` within the same version control artifact. If an interface evolves to return a different type, it must be deprecated and a new interface with a new identifier must be created. The data in Table 4.3-A serves as the evidence base for verifying that the `max 1` constraint is not violated in the production codebase.

## 4.4 Artifact Attachment Protocols

### 4.4.1 Definition and Axiomatic Basis

While the previous sections addressed informational entities, this section governs physical or logical artifacts within the kernel environment. Specifically, the axiom `kernelhook_max_one_program_attached` regulates the binding of executable programs to kernel hooks. A kernel hook, defined as class `X` and a subclass of `cco:Artifact`, may have a maximum of one attached program, class `Y`.

The verbalization states: `{X} is a artifact`. The Manchester syntax is defined as:
`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasAttachedProgram max 1 {Y:Class}`

This limitation is critical for system stability and security. Allowing multiple programs to attach to a single kernel hook can lead to race conditions, execution order ambiguity, and complex failure modes that are difficult to audit. By enforcing a `max 1` constraint, the governance framework ensures that the behavior of the artifact `X` is deterministic and solely attributable to the single program `Y`.

**Table 4.4-A: Kernel Hook Program Attachments**

### 4.4.3 Enforcement and Governance

The `max 1` constraint enforced by this axiom requires that the runtime loader reject any attempt to attach a second program `y` to an artifact `x` if an attachment record already exists. The data presented in Table 4.4-A represents the authorized state. Any deviation detected during a system scan—such as an artifact `x` appearing with a program `y` not listed in the registry, or multiple programs attached to a single `x`—must trigger an immediate security incident response.

## 4.5 Security Tier Stratification

### 4.5.1 Definition and Axiomatic Basis

The final concept introduced in this chapter pertains to the security classification of interfaces. The axiom `syscall_at_security_tier` mandates that any class `X`, which is a `cco:DesignativeICE`, must be associated with a specific security tier `Y`. This association is existential (`some`), meaning that for an entity to be valid, it must possess at least one defined security tier property.

The verbalization is: `{X} is something that at security tier {Y}`. The Manchester syntax is:
`Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}`

This axiom facilitates the implementation of Mandatory Access Control (MAC) and audit logging policies. By stratifying designative entities into tiers, the governance framework can enforce differential handling based on the sensitivity of the operation. For instance, operations at `Tier0` may require elevated privileges and immutable logging, whereas `Tier2` operations might be permissible in less restricted contexts.

The assignment of security tiers is recorded in the compliance matrix below. The `y` column denotes the specific security tier class, which typically correlates with privilege rings (e.g., Ring 0 vs Ring 3) or abstract sensitivity levels (e.g., Critical, Standard). The `NOT NULL` constraint on `y` ensures that every designative ICE has a security classification, leaving no interface in an undefined, unmonitored state.

**Table 4.5-A: Syscall Security Tier Assignments**

| id | x (Syscall Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| SEC-001 | `VFS_Read_Operation` | `Tier0_Privileged` |
| SEC-002 | `NetLink_Bind_Operation` | `Tier0_Privileged` |

| SEC-004 | `GetTimeOfDay` | `Tier2_Unprivileged` |

### 4.5.3 Policy Implementation

The data in Table 4.5-A drives the runtime security monitor. When a syscall corresponding to class `x` is invoked, the security context is checked against the tier `y`. If the calling context lacks the credentials for `y`, the invocation is blocked, and an audit event is generated. This axiom ensures that security is not an afterthought but a defining characteristic of the entity's ontology.
