# Chapter 4: Kernel Interface Governance and Axiomatic Compliance

## 4.1 Scope and Governance Framework

This chapter establishes the formal axiomatic structure governing kernel-level interface interactions, specifically within the context of extended Berkeley Packet Filter (eBPF) and syscall subsystems. The definitions provided herein serve as the authoritative ontology for classifying designative information content entities (ICE), artifacts, and their respective security constraints. Compliance with these axioms is mandatory for ensuring system stability, maintaining namespace integrity, and enforcing privilege boundaries within the kernel runtime. The following sections delineate the logical constraints governing syscall equivalence, return type cardinality, program attachment protocols, and security tier stratification, supported by relational schema mappings for audit verification.

---

## 4.2 Syscall Equivalence within Subsystems

### 4.2.1 Axiomatic Definition
The first foundational axiom addresses the classification of syscalls based on their functional containment within specific subsystems. According to the axiom `syscall_equiv_in_subsystem`, a class `X` is formally equivalent to a `cco:DesignativeICE` if and only if it exists within the scope of a specific subsystem `Y`.

**Axiom 1 (template_id: syscall_equiv_in_subsystem):**
> Class: {X:Class} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})

This equivalence relation asserts that identity for these entities is not merely nominal but is structurally dependent on their subsystem residency. A syscall cannot be fully defined or audited without referencing its containing subsystem (e.g., `net`, `fs`, `ipc`). This prevents namespace collision and ensures that interface control points are strictly scoped to their functional domains.

### 4.2.2 Implementation and Verification
In compliance audits, verifiers must confirm that any interface designated as a `DesignativeICE` maps unambiguously to a subsystem parent. The relational projection of this axiom enforces that while the identifier (`id`) is the primary key, the subsystem (`y`) is a mandatory non-null attribute, thereby anchoring the entity to its domain.

The following table details the instantiation of syscall classes within their respective subsystems. Each row represents a distinct class `X` that satisfies the condition of being a `DesignativeICE` within subsystem `Y`.

## 4.3 Return Type Cardinality Constraints

### 4.3.1 Axiomatic Definition
To maintain strict typing and predictable behavior in kernel-space execution, the ontology enforces a cardinality constraint on the return values of designative interfaces. The axiom `syscall_max_one_return` stipulates that any class `X`, being a subclass of `cco:DesignativeICE`, may possess a return type `Y` with a maximum cardinality of 1.

**Axiom 2 (template_id: syscall_max_one_return):**
> Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:hasReturnType max 1 {Y:Class}

**Verbalization:** {X} is a designative information content entity that has a return type {Y} restricted to a maximum of one instance.

This constraint effectively prohibits multi-return dispatch patterns for standard syscalls, enforcing a singular contract for error handling or data retrieval. It ensures that the ABI (Application Binary Interface) remains stable and that consuming processes can reliably predict the register state or stack modification following a syscall invocation.

### 4.3.2 Type Safety and ABI Compliance
The enforcement of this axiom is critical for security hardening. By limiting the return type to a single class `Y`, the kernel reduces the surface area for type confusion attacks. The relational schema for this axiom tracks the specific return type class associated with each syscall class, allowing auditors to verify that no syscall is defined with void or multiple return types where a singular scalar or pointer is expected.

**Table 4.3.1: Syscall Return Type Constraints**
The table below enumerates specific syscall classes and their associated return type classes. The constraint `max 1` is implicitly satisfied by the singular assignment of `y` to `x` in each record.

| id | x (Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| `RT-001` | `BpfSyscall` | `IntegerType` |
| `RT-002` | `Openat2Syscall` | `FileDescriptorType` |
| `RT-003` | `PidfdSendSignal` | `IntegerType` |
| `RT-004` | `IoUringSetup` | `FileDescriptorType` |
| `RT-005` | `MmapSyscall` | `PointerType` |

**Compliance Check:** Auditors must validate that the class `y` is a valid primitive or complex type supported by the target architecture's calling convention.

## 4.4 Kernel Hook Attachment Protocols

### 4.4.1 Axiomatic Definition
Kernel hooks serve as the primary attachment points for dynamic tracing and instrumentation programs. The axiom `kernelhook_max_one_program_attached` governs the relationship between the hook artifact and the program payload. It defines that a class `X`, which is a subclass of `cco:Artifact` (the hook), may have a maximum of one attached program class `Y`.

**Axiom 3 (template_id: kernelhook_max_one_program_attached):**
> Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasAttachedProgram max 1 {Y:Class}

**Verbalization:** {X} is an artifact that has an attached program {Y} restricted to a maximum of one instance.

This restriction is vital for preventing resource contention and ensuring deterministic execution flow within the kernel. Allowing multiple programs to attach to a single hook instance without explicit multiplexing logic can lead to race conditions, stack overflows, and non-deterministic ordering of side effects.

### 4.4.2 Attachment Governance
In the context of eBPF and LSM (Linux Security Modules) frameworks, this axiom mandates that a specific hook instance (e.g., a specific tracepoint or kprobe) is bound to a single program logic unit. If multi-program functionality is required, the architecture must define a wrapper program (a new instance of `Y`) that aggregates the logic, rather than attaching multiple `Y` instances to a single `X`.

**Table 4.4.1: Kernel Hook to Program Attachments**
This table maps specific kernel hook artifacts to their attached programs. The "max 1" constraint is evidenced by the one-to-one mapping between the hook identifier and the program class.

| id | x (Hook Artifact) | y (Program Class) |
| :--- | :--- | :--- |
| `KH-001` | `TracepointSchedSwitch` | `SchedLatencyAnalyzer` |
| `KH-002` | `KprobeDoSysOpen` | `FileMonitorProg` |
| `KH-003` | `CgroupSockIngress` | `NetworkPolicyEnforcer` |
| `KH-004` | `SocketFilterHook` | `PacketCaptureProg` |
| `KH-005` | `LsmSocketBind` | `AccessControlVerifier` |

**Operational Impact:** Deployment scripts must verify that the target hook `X` is not already occupied by a conflicting program `Y` before attempting an attachment operation.

## 4.5 Security Tier Stratification

### 4.5.1 Axiomatic Definition
The final axiom addresses the security classification of syscalls. The axiom `syscall_at_security_tier` asserts that a class `X`, a subclass of `cco:DesignativeICE`, operates at a specific security tier `Y`.

**Axiom 4 (template_id: syscall_at_security_tier):**
> Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}

**Verbalization:** {X} is something that is at security tier {Y}.

This classification enables the enforcement of Mandatory Access Control (MAC) policies and privilege auditing. By axiomatically binding a syscall to a security tier, the system can dynamically adjust permissions based on the context of the execution environment (e.g., Ring 0 vs. Ring 3, or specific SELinux contexts).

### 4.5.2 Tier Enforcement and Auditing
The "some" (`some`) restriction in the Manchester syntax indicates that every valid instance of `X` must be associated with at least one security tier `Y`. This is a necessary condition for validity; a syscall floating without a security tier assignment represents a critical compliance violation, potentially leading to privilege escalation vulnerabilities.

**Table 4.5.1: Syscall Security Tier Assignments**
The following table provides the security tier mapping for critical syscall classes. These assignments dictate the minimum privilege level required to invoke the interface.

| id | x (Class) | y (Security Tier Class) |

| `ST-002` | `Openat2Syscall` | `UserTier` |
