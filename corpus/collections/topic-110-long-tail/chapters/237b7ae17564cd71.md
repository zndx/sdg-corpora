# Chapter 4: Formal Ontology of Kernel Instrumentation and Security Constraints

This chapter establishes the formal ontological framework governing kernel-level instrumentation, specifically delineating the classification of system calls, kernel hooks, and their associated security constraints within an eBPF context. The definitions provided herein are derived from the Common Core Ontologies (CCO) and extended to support rigorous audit trails and compliance verification for secure kernel extension frameworks. All entities referenced are treated as designative information content entities or artifacts, subject to strict cardinality constraints to ensure system stability, determinism, and security integrity. The following sections detail the axiomatic relationships between these entities, providing the necessary logical structure for implementing governance policies in high-assurance computing environments.

## 1. System Call Equivalence within Subsystems

The classification of system calls requires a precise demarcation of their functional domains. Within the kernel, a system call is not merely an entry point but a designative information content entity that is axiomatically defined by its residency within a specific subsystem. The equivalence relation asserts that a class of system calls, designated as `{X}`, is equivalent to the intersection of the class `cco:DesignativeICE` and the constraint that the call must reside within some syscall subsystem `{Y}`. This axiom ensures that system calls are not defined in isolation but are contextually bound to the kernel subsystems they service (e.g., VFS, Network, IPC).

This ontological commitment is critical for auditability. It mandates that for any instance of `{X}` to be validly instantiated, it must possess a necessary relationship to an instance of `{Y}`. In practical terms, this prevents the categorization of "orphan" system calls that lack clear subsystem ownership, thereby enforcing a strict hierarchy of responsibility within the kernel governance model.

The logical structure of this equivalence is projected into a relational schema to facilitate database storage and query verification. The primary key `id` serves as the unique identifier for the equivalence assertion, while `x` represents the specific system call class and `y` represents the parent subsystem class. The `NOT NULL` constraint on `y` enforces the axiom that a system call cannot exist without a subsystem context.

This mapping allows security auditors to trace a specific system call identifier directly to its governing kernel subsystem, facilitating fault isolation and access control enforcement.

## 2. Cardinality Constraints on Return Types

System calls function as the primary interface between user space and kernel space, and as such, they must exhibit deterministic behavior regarding their output. The axiom governing return types stipulates that any system call class `{X}` is a subclass of `cco:DesignativeICE` and possesses a return type property `sdg:hasReturnType` with a maximum cardinality of 1, restricted to class `{Y}`. This constraint, `{X} SubClassOf: sdg:hasReturnType max 1 {Y}`, formally prohibits a system call from returning multiple, disparate type instances simultaneously.

In the context of kernel security and API stability, this constraint is foundational. It ensures that a system call cannot ambiguously return, for example, both a file descriptor and a memory address pointer without a defined union or structure type. By restricting the return type to a maximum of one class `{Y}`, the ontology enforces a contract of single-point-of-return for the type definition, which simplifies static analysis and runtime type checking. This is particularly relevant for eBPF verification programs, which must predict the behavior of a system call to ensure safety; ambiguity in return types would render such verification computationally intractable or insecure.

### 2.1 Return Type Specification

The relational schema derived from this axiom captures the specific type class `{Y}` associated with each system call class `{X}`. While the `max 1` constraint is enforced at the ontology level, the relational table records the specific designated return type for each system call class.

| id | x (System Call Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| ret-001 | SyscallOpen | IntegerType |
| ret-002 | SyscallMmap | PointerType |
| ret-003 | SyscallClone | ProcessIDType |

As shown in Table 2.1, `SyscallMmap` is defined as returning a `PointerType`. The axiom ensures that no other return type class is valid for this system call. This strict typing is essential for constructing accurate data flow graphs during compliance audits, as it guarantees that the information exiting the kernel via `{X}` conforms strictly to the definition of `{Y}`.

## 3. Kernel Hook Attachment Constraints

Kernel hooks represent specific loci within the kernel code where external instrumentation, such as eBPF programs, may be attached to monitor or modify behavior. The axiom governing these hooks defines a class `{X}` as a subclass of `cco:Artifact`, representing a tangible or discrete logical component of the kernel infrastructure. Furthermore, it imposes a cardinality constraint on the `sdg:hasAttachedProgram` property, limiting it to a maximum of 1 program class `{Y}`.

The assertion `{X} SubClassOf: sdg:hasAttachedProgram max 1 {Y}` is a design choice that prioritizes isolation and determinism in kernel instrumentation. By restricting a kernel hook to a single attached program, the framework eliminates race conditions and ordering ambiguities that can arise when multiple programs contend for the same hook point. In a high-security environment, this constraint ensures that the behavior triggered by the hook is singular and attributable to a specific, verified program instance. This prevents "hook chaining" attacks where a malicious actor might attempt to attach a secondary program to intercept or alter the data flow of a legitimate security monitor.

The relational schema for this axiom links the kernel hook artifact `{X}` to the attached program class `{Y}`. This exclusivity is vital for maintaining a clear chain of custody for performance data and security events generated at the hook point.

## 4. Security Tier Stratification

To enforce a granular security policy, system calls are stratified according to their privilege requirements and potential impact on system integrity. The axiom `{X} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y}` classifies a system call `{X}` as residing at a specific security tier `{Y}`. This classification moves beyond simple user/kernel mode distinctions and allows for a multi-layered security model (e.g., Tier 0: Hypervisor, Tier 1: Kernel Critical, Tier 2: Standard Kernel, Tier 3: User-emulated).

The verbalization "{X} is something that at security tier {Y}" indicates that the security tier is an inherent property of the system call class within this ontology. This stratification enables governance frameworks to apply differential policies based on the tier. For instance, calls at `Tier1_Critical` may require mandatory multi-factor authentication approval or digital signing of the invoking binary, whereas calls at `Tier3_Standard` may only require standard capability checks. This axiom is the basis for implementing "Tiered Access Control" in compliant systems.

### 4.1 Security Tier Assignments

The relational schema for this axiom maps the system call class `{X}` to its designated security tier `{Y}`. The `NOT NULL` constraint on `y` ensures that every system call is explicitly categorized; there is no "default" or "unclassified" security tier in this strict model.

Table 4.1: System Call Security Tier Classifications

| id | x (System Call Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| tier-001 | SyscallMount | Tier1_Critical |
| tier-002 | SyscallChmod | Tier2_Standard |
| tier-003 | SyscallKill | Tier2_Standard |
| tier-004 | SyscallInitModule | Tier1_Critical |
| tier-005 | SyscallGettimeofday | Tier3_Benign |

Table 4.1 demonstrates the stratification logic. `SyscallMount` is placed at `Tier1_Critical` due to its ability to alter the filesystem namespace, a high-privilege operation. Conversely, `SyscallGettimeofday` is categorized as `Tier3_Benign`, reflecting its low security impact. This classification drives the runtime enforcement engine, ensuring that instrumentation or logging applied to `Tier1_Critical` calls is sufficiently rigorous to meet regulatory standards.
