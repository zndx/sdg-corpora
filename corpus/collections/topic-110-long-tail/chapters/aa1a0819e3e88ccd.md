### 4.0 Scope and Preamble

This chapter establishes the formal ontological framework governing the classification, behavior, and security constraints of kernel-level primitives within the eBPF (Extended Berkeley Packet Filter) infrastructure. The objective is to provide a rigorous, machine-readable schema that maps low-level system calls and kernel hooks to high-level governance artifacts. By defining these entities through strict axioms—specifically those anchored in the BFO (Basic Formal Ontology) upper ontology—this document ensures that automated audit trails can unambiguously verify the compliance of kernel extensions. The following sections detail four critical axiom sets: subsystem equivalence, return type cardinality, hook attachment constraints, and security tier classification.

### 4.1 Syscall Equivalence in Subsystem

The first axiomatization addresses the ontological definition of system calls relative to their functional containment. In the context of kernel instrumentation, a system call cannot be defined in isolation; it is ontologically equivalent to a *Designative Information Content Entity* (ICE) specifically situated within a subsystem. The axiom `syscall_equiv_in_subsystem` formalizes this by asserting that a Class X is equivalent to a `cco:DesignativeICE` only if it is located within some Syscall Subsystem Y.

This distinction is critical for governance. It prevents the ambiguous categorization of cross-cutting functions. If a system call is logically defined as `FileReadOperation`, it must be demonstrably contained within the `VirtualFileSystem` subsystem to satisfy the equivalence condition. This containment is not merely a hierarchical parent-child relationship but a necessary condition for the entity's existence within the ontology.

In the context of Table 4.1, the row with `id` SYS-1001 asserts that the class `FileReadOperation` is ontologically null unless it is realized as a Designative ICE within the `VirtualFileSystem`. This mapping allows auditors to verify that instrumentation code attached to `FileReadOperation` is correctly scoped to file-system level governance policies rather than being misapplied to generic I/O ports.

### 4.2 Syscall Return Type Constraints

To maintain strict type safety and predictable behavior in kernel-space instrumentation, the ontology enforces cardinality constraints on the return values of designative entities. The axiom `syscall_max_one_return` posits that any Class X, which is a subclass of `cco:DesignativeICE`, must possess a return type Y with a maximum cardinality of 1.

This constraint serves as a formal guarantee against polymorphic return values that could obfuscate audit logs or introduce undefined behavior in verification parsers. In a compliance scenario, if a `DesignativeICE` is observed returning multiple distinct types (e.g., an Integer and a Buffer pointer) across different execution paths, it violates this ontological definition and must be flagged for remediation. The verbalization "{X} is a designative information content entity" underscores that the entity itself is defined by this singular return contract.

**Table 4.2: Syscall Return Type Definitions**

Table 4.2 details the authorized return types for specific system call classes. The structure enforces that for any given `x` (the Syscall Class), there is exactly one permitted `y` (Return Type Class).

| id | x (Class) | y (Return Type Class) |
| :--- | :--- | :--- |
| RT-2001 | `SocketBindCall` | `IntegerErrorCode` |
| RT-2002 | `ProcessForkEvent` | `ProcessIdentifierType` |
| RT-2003 | `FileReadOperation` | `ByteCountType` |
| RT-2004 | `CapabilityCheckCall` | `BooleanPermission` |
| RT-2005 | `ClockGetTimeCall` | `TimespecStructure` |

For instance, the entry RT-2001 specifies that `SocketBindCall` is constrained to return only `IntegerErrorCode`. Any telemetry or eBPF map data derived from this syscall expecting a raw file descriptor or a pointer would be structurally inconsistent with the axiom `syscall_max_one_return`. This facilitates automated validation of parsing logic within security monitoring agents.

### 4.3 Kernel Hook Attachment Constraints

The interaction between kernel hooks and eBPF programs is governed by strict attachment rules to prevent resource contention and ensure deterministic execution flow. The axiom `kernelhook_max_one_program_attached` defines that a Class X, which is a subclass of `cco:Artifact` (representing the hook point), may have a maximum of one attached program Class Y (`sdg:hasAttachedProgram`).

This axiom reflects the operational requirement that a single tracepoint or kprobe instance should not be overloaded with multiple arbitrary programs in a way that creates race conditions or non-linear execution paths. While the kernel may technically allow chaining, this governance framework restricts the logical definition to a 1:1 mapping for the sake of auditability. If a security policy requires multiple behaviors at a single hook, the ontology dictates the creation of a composite program class rather than multiple attachments to the base artifact.

The relational schema in Table 4.3 captures the valid attachment instances. Column `x` denotes the Kernel Hook Artifact, and column `y` denotes the specific eBPF Program Class authorized for attachment.

| id | x (Class) | y (Class) |
| :--- | :--- | :--- |
| KH-3001 | `TracepointScheduler` | `LatencyAnalyzerProgram` |
| KH-3002 | `KprobeTcpV4Connect` | `ConnectionMonitorProgram` |
| KH-3003 | `Cgroup_skbIngress` | `NetworkFilterProgram` |
| KH-3004 | `SocketMapRedirect` | `LoadBalancerProgram` |
| KH-3005 | `IterateTaskFile` | `FileAuditorProgram` |

Reviewing Table 4.3, the entry KH-3002 associates the `KprobeTcpV4Connect` artifact exclusively with the `ConnectionMonitorProgram`. This ensures that the critical TCP connect path is not instrumented by conflicting monitoring logic. The `id` serves as the primary key for this relationship, ensuring that each hook-program pair is treated as a distinct, governed configuration item.

### 4.4 Security Tier Classification

Finally, the ontology mandates that all designative entities be classified according to a security tier. The axiom `syscall_at_security_tier` asserts that a Class X (a `cco:DesignativeICE`) must be situated at some Security Tier Y (`sdg:atSecurityTier some {Y:Class}`). This classification enables the enforcement of role-based access control (RBAC) and permission gating for kernel instrumentation.

The verbalization "{X} is something that at security tier {Y}" indicates that the security tier is an intrinsic property of the syscall's definition within the governed environment. Syscalls classified at higher tiers (e.g., `PrivilegedTier`) require elevated capabilities to load or trace, whereas those at lower tiers (e.g., `UnprivilegedTier`) may be accessible to observability tools running with reduced permissions. This axiom is foundational for automated policy enforcement engines that deny loading of eBPF programs if the program's target syscall's security tier exceeds the loader's clearance level.

**Table 4.4: Syscall Security Tier Assignments**

Table 4.4 provides the mapping of system call classes to their requisite security tiers. The `y` column is mandatory (NOT NULL), ensuring that every syscall defined in the system has an explicit security classification.

| id | x (Class) | y (Security Tier Class) |
| :--- | :--- | :--- |
| ST-4001 | `FileReadOperation` | `UnprivilegedTier` |
| ST-4002 | `ProcessForkEvent` | `SensitiveTier` |
| ST-4003 | `DeviceIoControl` | `PrivilegedTier` |
| ST-4004 | `SocketBindCall` | `RestrictedTier` |
| ST-4005 | `ModuleLoadRequest` | `CriticalTier` |

As evidenced in Table 4.4, `DeviceIoControl` (ST-4003) is placed at the `PrivilegedTier`. This classification signals to the governance framework that any eBPF program attempting to attach to or trace `DeviceIoControl` must possess privileged credentials. Conversely, `FileReadOperation` (ST-4001) is categorized as `UnprivilegedTier`, permitting broader observability access. This tiered structure is essential for maintaining the principle of least privilege within the kernel instrumentation layer.
