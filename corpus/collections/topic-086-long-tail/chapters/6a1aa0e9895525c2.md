# Chapter 4: Structural Governance of Artifacts and Directives

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the definition of composite artifacts and the regulatory directives that constrain them. The text establishes a rigorous framework for mapping entity classes to their constituent parts and the subsequent governance requirements applied to those entities. It is intended for systems architects and compliance officers who must implement semantic data models consistent with the Common Core Ontologies (CCO) and the BFO (Basic Formal Ontology) upper-level structure. The following sections provide a detailed analysis of four primary axioms: the intersection of artifacts with parts, the equivalence of requirements to directives, and the cardinality constraints that limit or mandate specific relationships within the governance domain.

## 4.2 Artifact Composition and Part-Whole Integration

### 4.2.1 Axiomatic Definition

The foundational concept for defining physical or informational entities in this framework is derived from the axiom `equiv_intersect_artifact_with_part`. This axiom asserts that a specific class of entity (X) is equivalent to the intersection of the general class `cco:Artifact` and the condition that the entity possesses a specific part (Y). In Manchester syntax, this is expressed as:

`Class: {X:Class} EquivalentTo: cco:Artifact and (bfo:0000051 some {Y:Class})`

This definition utilizes the BFO relation `bfo:0000051` (has part). Consequently, for an entity to be classified as X, it must fundamentally be an Artifact—defined as a material entity that is created or modified by an agent—and it must contain at least one instance of class Y as a proper part. This creates a necessary and sufficient condition for classification: an entity is an X if and only if it is an artifact with a Y.

### 4.2.2 Implementation and Relational Mapping

In a relational implementation, this intersection is captured by mapping the specific artifact class (X) to the required part class (Y). The structural integrity of the database relies on the foreign key constraint linking the part definition to a specific directive requirement, ensuring that the composition of the artifact is governed by an external rule.

The column `y` serves as a foreign key, referencing the directive that governs that specific part requirement, thereby linking physical composition to regulatory compliance.

### 4.2.3 Compliance Verification

When auditing an artifact classified as `SecureContainmentUnit` (ID: ART-2024-001), the compliance officer must verify two conditions:
1.  The entity is a discrete, man-made object (`cco:Artifact`).
2.  The entity physically contains a component classified as `BioShieldLayer`.
Failure to demonstrate the presence of the `BioShieldLayer` results in the retraction of the `SecureContainmentUnit` classification, as the intersection condition is no longer met.

## 4.3 Directive Specification and Target Application

### 4.3.1 Axiomatic Definition

The governance framework is operationalized through the axiom `requirement_equiv_specifies_target`. This axiom defines a class of requirements (X) as equivalent to a `cco:DirectiveICE` (Information Content Entity) that specifies a target (Y) and applies to a context (Z). The Manchester syntax is formalized as:

`Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`

This structure ensures that a requirement is not merely a static text but an active information entity that performs two semantic functions: it points to a specific artifact or part (the target) and it delineates the scope of application (the context). The `sdg:specifies` relation links the directive to the entity it governs, while `sdg:appliesTo` links it to the environment or operational domain.

### 4.3.2 Implementation and Relational Mapping

The relational schema for this axiom captures the tripartite nature of a directive. The table records the directive class (X), the target class it specifies (Y), and the context class (Z) to which it applies. To maintain referential integrity with the artifact definitions established in Section 4.2, the `y` column in this table references the `id` of the artifact-part intersection. This circular dependency enforces a strict governance loop: an artifact is defined by a part, and that part is governed by a directive which references the artifact definition.

## 4.4 Maximum Cardinality Constraints

### 4.4.1 Axiomatic Definition

To prevent resource exhaustion or configuration complexity, the ontology employs maximum cardinality constraints via the axiom `cardinality_max_three_generic`. This axiom restricts the number of relationships a class (X) can participate in with another class (Y) via a specific object property (p) to a maximum of three. The Manchester syntax is:

`Class: {X:Class} SubClassOf: {p:ObjectProperty} max 3 {Y:Class}`

This is a subClassOf axiom, meaning that any instance of X must obey the constraint. If an instance of X is linked to more than three instances of Y via property p, the data model is in a violation state. This is critical for limiting the number of redundant directives or components that may be attached to a single governance target.

### 4.4.2 Implementation and Relational Mapping

In the relational schema, cardinality constraints are often enforced at the application layer or through triggers, but the semantic definition is recorded here. The table `t_cardinality_max_three_generic` links the constrained class (X) to the target class (Y) of the constraint. The foreign key to the directive table indicates that these constraints are themselves governed by the specific directives identified in Section 4.3.

For the constraint `CONSTR-MAX-01`, the class `MaintenanceTeam` is restricted to having a maximum of three relationships to the target defined by `DIR-SPEC-001` (the `SecureContainmentUnit`). If the object property represents "assigned_to," this implies that no more than three maintenance teams may be assigned to a single containment unit simultaneously. This constraint ensures operational efficiency and prevents overcrowding in secure environments.

## 4.5 Minimum Cardinality Constraints

### 4.5.1 Axiomatic Definition

Conversely, the axiom `cardinality_min_two_generic` establishes a floor for relationships, ensuring that a class (X) maintains a minimum number of associations with another class (Y). The Manchester syntax is:

`Class: {X:Class} SubClassOf: {p:ObjectProperty} min 2 {Y:Class}`

This axiom is essential for redundancy requirements and safety protocols. It mandates that an instance of X must be linked to at least two instances of Y. If the count falls below two, the system is non-compliant, potentially indicating a single point of failure.

### 4.5.2 Implementation and Relational Mapping

The relational representation of minimum cardinality follows a similar structure to the maximum constraints. It identifies the class requiring the relationship (X) and the target of that relationship (Y). Again, the linkage to the directive table ensures that these minimum requirements are formally codified within the specific governance documents.
