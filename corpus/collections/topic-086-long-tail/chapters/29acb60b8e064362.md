# Chapter 4: Ontological Constraints in Artifact Governance and Directive Specification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the classification of composite artifacts and the governance directives that apply to them. In high-assurance environments, the precise definition of system components—specifically those defined as Artifacts possessing distinct parts—is a prerequisite for effective compliance auditing. The following sections detail the axiomatic structure governing these definitions, the equivalence classes for directives, and the cardinality constraints that limit or mandate specific relationships within the system architecture. Adherence to these definitions ensures that all regulatory mappings are deterministic and auditable.

## 4.2 Artifact Composition and Partonomic Intersection

The foundational unit of physical governance in this framework is the composite artifact. An entity is formally recognized as a member of the artifact class only if it satisfies the intersection of two conditions: it must be an instance of `cco:Artifact`, and it must possess a `bfo:0000051` (has part) relationship to a distinct component class. This definition, encoded by the axiom `equiv_intersect_artifact_with_part`, prevents the ambiguous classification of standalone items as composite units.

The intersection logic is critical for supply chain accountability. By defining a class `X` as equivalent to an Artifact with a part `Y`, the ontology enforces a strict dependency. If an object lacks the specified part `Y`, it cannot be classified as `X`. This allows auditors to automatically filter inventory lists based on structural completeness.

The relational schema for this axiom maps the defined class (`x`) to its required part (`y`). The schema enforces a foreign key constraint linking the part (`y`) to a directive specification, implying that parts are often the targets of specific governance requirements.

## 4.3 Directive Specification and Target Application

While Section 4.2 addressed the physical composition of artifacts, governance is enforced through Directives. The axiom `requirement_equiv_specifies_target` defines the class structure for `cco:DirectiveICE` (Information Control Element). A directive class is equivalent to the set of directives that specify a particular target (`y`) and apply to a specific scope (`z`).

This tripartite structure—Directive, Target, and Scope—ensures that mandates are never floating or unbound. A directive must explicitly articulate what it specifies (the artifact or part from Section 4.2) and the context to which it applies (e.g., a specific operational environment or security zone). This axiom is the mechanism by which abstract compliance requirements are anchored to the physical artifacts defined in the previous section.

The relational schema for this concept creates a circular dependency with the artifact definitions, reinforcing the tight coupling between physical structure and governance. The `y` value in this table (the target specified by the directive) must correspond to the `id` of an artifact definition, while the `y` value in the artifact table references this directive's ID. This mutual dependency signifies that a part is defined by the directive that governs it, and the directive is validated by the existence of the part.

## 4.4 Maximum Cardinality Constraints

In complex systems, unbounded relationships often introduce security vulnerabilities or compliance failures. The axiom `cardinality_max_three_generic` imposes a restriction on a class `X`, stating that it is a subclass of an object property `p` only if the number of relationships to class `Y` does not exceed three.

This constraint is utilized to limit the proliferation of dependencies. For instance, a specific interface class may be restricted to interacting with a maximum of three distinct directive types to prevent over-engineering or "scope creep" in compliance requirements. Alternatively, a physical component may be limited to three connection points to maintain structural integrity as defined by the governance framework.

The schema for this axiom links the constrained class (`x`) to the target definition (`y`). The target definition (`y`) must be a valid directive specification ID, linking the restriction back to the governance artifacts established in Section 4.3.

The following table defines classes that are subject to a maximum relationship constraint of three instances. These constraints prevent the over-saturation of governance targets.

| id | x | y |
| :--- | :--- | :--- |
| CARD_MAX_01 | LegacyInterfacePort | REQ_DEF_04 |
| CARD_MAX_02 | ManualOverrideSwitch | REQ_DEF_01 |
| CARD_MAX_03 | ExternalDiagnosticPort | REQ_DEF_03 |
| CARD_MAX_04 | SecondaryPowerRail | REQ_DEF_02 |

*Table 4.3 Notes:*
*   `x` denotes the Class being constrained.
*   `y` denotes the Directive ID (from Table 4.2) that defines the context of the restriction.
*   The constraint implies that instances of class `x` may participate in the relevant property `p` with instances of the class defined in `y` no more than three times.

## 4.5 Minimum Cardinality Constraints

Conversely to the restrictions defined in Section 4.4, the axiom `cardinality_min_two_generic` establishes a floor for relationships. It asserts that a class `X` is a subclass of an object property `p` only if it participates in that relationship with class `Y` at least two times.

This axiom is essential for redundancy and fail-safe requirements. In safety-critical systems, a power supply unit or a data path may be required to have at least two distinct connections or control mechanisms to ensure availability during a failure event. The governance framework uses this axiom to enforce minimum reliability standards.

The relational structure mirrors that of the maximum constraints, linking the constrained class (`x`) to a directive specification (`y`). This ensures that the redundancy requirements are not arbitrary but are tied to specific directive classes defined in the governance ontology.
