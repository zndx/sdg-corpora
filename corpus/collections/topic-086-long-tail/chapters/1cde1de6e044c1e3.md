# Chapter 4: Formal Mapping of Industrial Artifacts to Governance Directives

## 4.1 Scope and Preamble

This chapter establishes the ontological framework for mapping physical industrial artifacts to their corresponding governance directives within the enterprise compliance architecture. The definitions provided herein are derived from the formal OWL axioms governing the intersection of material entities (`cco:Artifact`) and informational entities (`cco:DirectiveICE`). The primary objective is to ensure that every physical component subject to audit is inextricably linked to a specific requirement class, thereby creating a traceable chain of evidence from the shop floor to the regulatory report. The following sections detail the logical constraints governing these relationships, supported by relational data tables that reflect the current state of the compliant inventory.

## 4.2 Artifact-Part Intersection and Composition

### 4.2.1 Conceptual Definition

The foundational axiom of this framework is defined by the template `equiv_intersect_artifact_with_part`. In formal Manchester syntax, this axiom posits that a specific Class `{X}` is equivalent to the intersection of `cco:Artifact` and the object restriction `bfo:0000051 some {Y}`. Here, `bfo:0000051` (has part) denotes a meronymic relationship where the whole (`X`) necessarily contains the part (`Y`). In the context of industrial compliance, this definition asserts that an artifact cannot exist as a compliant entity unless its constituent parts are formally recognized and classified within the ontology.

This distinction is critical for auditability. When an artifact is decommissioned or modified, the system must recursively update the status of all downstream parts. The axiom ensures that the identity of the Artifact is not merely a label but a composite structure defined by its physical and regulatory composition.

### 4.2.2 Relational Implementation

The relational schema for this concept, `t_equiv_intersect_artifact_with_part`, enforces a foreign key constraint wherein the `y` column (the Part) must reference a valid identifier in the directive requirements table. This structural dependency prevents the existence of "orphan" parts—components that are defined but not subject to any governance directive.

### 4.2.3 Compliance Verification

During the audit cycle, inspectors must verify that the physical assembly matches the records in Table 4.1. For instance, the `HolderToolAssembly` (ART-HOLDER-01) is defined by the presence of the alignment specification (REQ-SPEC-ALIGN-01). If the physical tool lacks the capability to satisfy this requirement, the artifact is deemed non-compliant. This mapping allows the governance framework to treat the physical object and the requirement as a single, intersecting entity for risk assessment purposes.

## 4.3 Directive Specification and Target Application

### 4.3.1 Conceptual Definition

The second axiom, `requirement_equiv_specifies_target`, formalizes the definition of a governance directive. The axiom states that a Class `{X}` is equivalent to `cco:DirectiveICE` that both `sdg:specifies` a target `{Y}` and `sdg:appliesTo` a scope `{Z}`. This tripartite structure is essential for precision in regulatory environments. A directive is not merely a rule; it is a rule that is explicitly bound to a target (the artifact or part) and a scope (the operational context or domain).

The use of `cco:DirectiveICE` (Information Content Entity) distinguishes the rule itself from the physical object it governs. The `sdg:specifies` property links the directive to the specific artifact component defined in the previous section, while `sdg:appliesTo` contextualizes the directive, limiting its validity to specific environments (e.g., "High-Pressure Systems" or "Clean Room Assembly").

### 4.3.2 Relational Implementation

The schema `t_requirement_equiv_specifies_target` implements this logic. The `y` column references the Artifact ID from the previous table, closing the loop between the physical object and the rule governing it. The `z` column defines the scope, ensuring that directives are not applied universally where they may be irrelevant or hazardous.

### 4.3.3 Audit Implications

The data in Table 4.2 indicates that the `AlignmentDirective` (REQ-SPEC-ALIGN-01) applies specifically to `AssemblyLineA`. If an operator attempts to apply this directive to `AssemblyLineB` without a corresponding scope entry, the action is blocked by the governance engine. This specificity prevents the misapplication of safety protocols, a common source of compliance violations in multi-line manufacturing facilities.

## 4.4 Maximum Cardinality Constraints

### 4.4.1 Conceptual Definition

To maintain operational efficiency and prevent resource saturation, the ontology employs the axiom `cardinality_max_three_generic`. This axiom asserts that a Class `{X}` is a SubClass of an object property `{p}` with a maximum cardinality of 3 for Class `{Y}`. In practical terms, this limits the number of relationships or dependencies a single entity may have. For example, a single inspection slot or a maintenance log entry may be associated with a maximum of three critical requirements.

This constraint serves as a control mechanism against complexity overload. By capping the number of applicable directives per inspection event, the framework ensures that human operators are not overwhelmed by data, thereby reducing the likelihood of error during verification procedures.

### 4.4.2 Relational Implementation

The table `t_cardinality_max_three_generic` captures these constraints. The foreign key to the requirements table ensures that the cardinality limits are applied to valid, existing directives. In the data below, the `InspectionShift` class is limited to referencing three specific requirement IDs.

**Table 4.3: Maximum Cardinality Constraint Log**
*This table records the maximum allowable associations (X) for specific requirement targets (Y). It enforces the rule that no single inspection shift may reference more than the defined limit of critical directives.*

| id | x | y |
|---|---|---|
| CON-MAX-001 | InspectionShift | REQ-SPEC-ALIGN-01 |
| CON-MAX-002 | InspectionShift | REQ-SPEC-SEAL-01 |
| CON-MAX-003 | InspectionShift | REQ-SPEC-PRESS-01 |
| CON-MAX-004 | MaintenanceLog | REQ-SPEC-MOUNT-01 |
| CON-MAX-005 | MaintenanceLog | REQ-SPEC-FLOW-01 |

### 4.4.3 Operational Impact

Under this constraint, an `InspectionShift` (CON-MAX-001 through CON-MAX-003) is permitted to address the alignment, sealant, and pressure directives. If a fourth directive were added to this shift, the system would trigger a cardinality violation. This forces the operations manager to either defer the fourth directive to a subsequent shift or escalate the matter to a separate `MaintenanceLog` event, ensuring that audit trails remain granular and manageable.

## 4.5 Minimum Cardinality Constraints

### 4.5.1 Conceptual Definition

Conversely, the axiom `cardinality_min_two_generic` establishes a baseline for thoroughness. It asserts that a Class `{X}` is a SubClass of an object property `{p}` with a minimum cardinality of 2 for Class `{Y}`. This axiom is utilized to enforce mandatory coverage. For instance, a `SafetyAudit` must encompass at least two distinct critical failure modes or requirement specifications to be considered valid.

This constraint prevents "rubber-stamping" or superficial audits where an operator might sign off on a single obvious check while ignoring deeper systemic issues. By mandating a minimum of two associations, the framework enforces a multi-vector verification process.

### 4.5.2 Relational Implementation

The schema `t_cardinality_min_two_generic` tracks these mandatory relationships. As with the maximum constraint table, the `y` column references the directive requirements. The data illustrates that a `DailyAudit` must satisfy at least two distinct requirement IDs to be compliant.

**Table 4.4: Minimum Cardinality Compliance Record**
*This table verifies that entities (X) meet the threshold of associations (Y). It ensures that audit events are sufficiently comprehensive by requiring links to multiple requirement specifications.*

| id | x | y |
|---|---|---|
| CON-MIN-101 | DailyAudit | REQ-SPEC-ALIGN-01 |
| CON-MIN-102 | DailyAudit | REQ-SPEC-SEAL-01 |
| CON-MIN-103 | WeeklyReview | REQ-SPEC-PRESS-01 |
| CON-MIN-104 | WeeklyReview | REQ-SPEC-FLOW-01 |
| CON-MIN-105 | WeeklyReview | REQ-SPEC-MOUNT-01 |

### 4.5.3 Governance Enforcement

The records in Table 4.4 demonstrate that a `DailyAudit` (CON-MIN-101 and CON-MIN-102) has successfully referenced both the alignment and sealant directives. If a `DailyAudit` record were created with only one reference, the system would flag it as "Incomplete" pending the addition of a second requirement. This logic is crucial for maintaining high standards of quality control, particularly in environments where single-point failures can have catastrophic consequences.
