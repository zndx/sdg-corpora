# Chapter 4: Structural Constraints and Relational Mapping in Governance Frameworks

This chapter delineates the formal ontological structures required to define, govern, and constrain compliance artifacts within an enterprise architecture. We examine the intersection of artifact composition and directive specification, establishing a rigorous logical framework for mapping these concepts to relational schemas. The discussion proceeds from the definition of composite artifacts to the enforcement of cardinality constraints, ensuring that the resulting data structures maintain referential integrity and reflect the axiomatic constraints of the governing ontology.

## 4.1 Artifact-Part Intersection

The foundational axiom of governance architecture is the definition of an artifact not as a monolithic entity, but as a composite structure defined intrinsically by its constituent parts. The axiom `equiv_intersect_artifact_with_part` posits that a Class `X` (the Artifact) is equivalent to the intersection of the general class `cco:Artifact` and the restriction that it must have a part `bfo:0000051` (has part) of Class `Y`. This definition ensures that one cannot exist without the other; the artifact is validated only through the presence of its specified component.

In a relational context, this mutual dependency is resolved by treating the "part" as a foreign key reference to a directive definition. The primary key `id` serves as the unique identifier for the artifact instance, while the column `y` acts as a foreign key linking the artifact to the specific directive or requirement that constitutes its part. This structure enforces the axiom that the artifact is merely the container for the regulatory directive.

## 4.2 Directive Specification and Targeting

While the artifact provides the structural container, the semantic content of governance is derived from the directives it contains. The axiom `requirement_equiv_specifies_target` defines a Class `X` (a Directive) as equivalent to a `cco:DirectiveICE` that specifies some content `Y` and applies to some target `Z`. This triadic relationship is crucial for auditability: it links the directive to the artifact it specifies (closing the loop with the previous section) and the entity (person, system, or process) to which it applies.

The relational schema for this axiom creates a central node in the governance graph. The `id` column uniquely identifies the directive instance. The column `y` is a foreign key referencing the artifact table (`t_equiv_intersect_artifact_with_part`), creating a bidirectional link where the directive specifies the artifact, and the artifact has the directive as a part. The column `z` represents the target of the directive, grounding the abstract rule in a concrete operational entity.

## 4.3 Maximum Cardinality Constraints

Governance frameworks frequently impose upper bounds to prevent resource exhaustion, administrative bloat, or excessive privilege allocation. The axiom `cardinality_max_three_generic` formalizes this by stating that a Class `X` is a subclass of an object property `p` restricted to a maximum of 3 instances of Class `Y`. This constraint ensures that no single entity may be associated with more than the specified number of target instances, enforcing a principle of least privilege or limited scope.

In the relational projection, this constraint is modeled as a distinct entity defining the rule itself. The table records the constraint definition rather than the instance data, serving as a validation rule for the system. The primary key `id` identifies the constraint rule. The column `x` represents the class being constrained, and `y` is a foreign key referencing the directive table, indicating that the constraint applies to the scope defined by that specific directive.

## 4.4 Minimum Cardinality Constraints

Conversely, robustness and redundancy in governance are often enforced through lower bounds. The axiom `cardinality_min_two_generic` asserts that a Class `X` is a subclass of an object property `p` restricted to a minimum of 2 instances of Class `Y`. This ensures that critical processes are not single points of failure; for example, requiring that a safety approval be validated by at least two distinct officers.

The relational structure mirrors the maximum constraint table but represents a lower bound logic. The `id` serves as the unique identifier for this specific constraint rule. The column `x` identifies the domain class requiring the minimum instances, and the foreign key `y` references the directive table, anchoring the redundancy requirement to the specific operational directive.
