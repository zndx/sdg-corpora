# Chapter 7: Axiomatic Formalization of Compliance Artifacts and Directives

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures required to model high-assurance compliance frameworks within relational database environments. The primary objective is to establish a rigorous mapping between abstract ontology axioms—specifically those concerning artifacts, directives, and cardinality constraints—and their concrete implementations in SQL-based governance systems. The definitions provided herein are essential for ensuring referential integrity and logical consistency in automated audit pipelines, regulatory reporting mechanisms, and directive enforcement engines. By grounding these concepts in the Ontology for Biomedical Investigations (OBI) and the Common Core Ontologies (CCO), this text provides a standardized approach to representing complex governance relationships.

## 7.2 The Intersection of Artifacts and Constituent Parts

### 7.2.1 Conceptual Definition

In the context of governance frameworks, an **Artifact** is not merely a passive object but a discrete information entity defined by its structural composition. The axiom `equiv_intersect_artifact_with_part` formalizes this by asserting that a specific class of Artifact is equivalent to the intersection of the general class `cco:Artifact` and the restriction that it must possess at least one part of a specified type. This is a critical distinction for compliance officers: it implies that the identity of the artifact (e.g., a Policy Document) is contingent upon the presence of its constituent directives (e.g., Clauses). If the constituent parts are removed or altered such that they no longer satisfy the class definition, the Artifact itself ceases to exist as a compliant instance of that class.

### 7.2.2 Relational Implementation and Evidence

The relational projection of this axiom utilizes a foreign key constraint to enforce the "has part" relationship. The table `t_equiv_intersect_artifact_with_part` serves as the registry for these composite artifacts. The primary key (`id`) uniquely identifies the artifact instance, while the foreign key (`y`) references the identifier of the directive or component that constitutes the artifact. This structure ensures that an artifact entry cannot exist in the registry without a valid, corresponding component entry, thereby enforcing the ontological axiom at the database schema level.

## 7.3 Directive Specification and Target Application

### 7.3.1 Conceptual Definition

The `requirement_equiv_specifies_target` axiom defines the operational logic of governance directives. A **DirectiveICE** (Information Content Entity) is axiomatically defined as a directive that *specifies* a particular requirement and *applies to* a specific target entity. This tripartite structure—Directive, Specification, and Target—forms the backbone of any compliance matrix. It moves beyond simple textual description by encoding the *intent* (specification) and the *scope* (application) of the directive. In practice, this allows a governance engine to query not just for "all rules," but for "all rules applying to database servers," thereby enabling automated enforcement.

### 7.3.2 Relational Implementation and Evidence

The schema for `t_requirement_equiv_specifies_target` captures this triadic relationship. The column `x` represents the Directive class, `y` represents the specification (often the artifact or clause being defined), and `z` represents the target system or process. The foreign key constraint on `y` referencing the artifact table (`t_equiv_intersect_artifact_with_part`) creates a bidirectional link: the Artifact contains the Directive, and the Directive specifies the Artifact. This circular reference models the real-world legalistic concept where a clause (Directive) defines the document (Artifact) it belongs to, while the document grants authority to the clause.

| id (Directive ID) | x (Directive Class) | y (Specification ID) | z (Target Class) |
| :--- | :--- | :--- | :--- |

| DIR-CTRL-ADMIN-02 | cco:DirectiveICE | ART-SEC-2024-01 | cco:UserAccount |
| DIR-CTRL-NET-01 | cco:DirectiveICE | ART-SEC-2024-02 | cco:NetworkSegment |

*Note: The `y` column values correspond to the Artifact IDs in Table 7.1, establishing the specification link. The `z` column defines the scope of application for each directive.*

## 7.4 Maximum Cardinality Constraints

### 7.4.1 Conceptual Definition

To prevent over-provisioning of access or excessive complexity in control mechanisms, governance frameworks must employ **Maximum Cardinality** constraints. The axiom `cardinality_max_three_generic` asserts that a specific class (X) is a subclass of an object property (p) that has a maximum of three instances of class Y. In a regulatory context, this is often used to enforce the principle of least privilege or to limit the blast radius of a specific configuration. For instance, a "Role Definition" might be constrained to have a maximum of three "Permission Assignments" to prevent the accumulation of excessive power within a single role.

### 7.4.2 Relational Implementation and Evidence

The table `t_cardinality_max_three_generic` records these constraints. While the relational schema itself does not enforce the "max 3" rule dynamically (that requires application logic or check constraints), the table serves as the evidence registry for the constraint definition. The foreign key (`y`) links the constraint to the specific Directive it governs. This allows auditors to verify that a system configuration, represented by class X, does not violate the mandated limit defined in the ontology.

**Table 7.3: Maximum Cardinality Constraints (Axiom 3)**

| id (Constraint ID) | x (Constrained Class) | y (Governed Directive ID) |
| :--- | :--- | :--- |
| CONST-MAX-3-AUTH | cco:AuthorizationRole | DIR-CTRL-ADMIN-01 |
| CONST-MAX-3-NODE | cco:ClusterNode | DIR-CTRL-NET-01 |
| CONST-MAX-3-KEY | cco:EncryptionKey | DIR-CTRL-APP-01 |
| CONST-MAX-3-LOG | cco:LogRetentionPeriod | DIR-CTRL-APP-02 |

*Note: These entries define that the `AuthorizationRole` class, governed by directive `DIR-CTRL-ADMIN-01`, must not exceed three instances of the associated property (e.g., three user assignments).*

## 7.5 Minimum Cardinality Constraints

### 7.5.1 Conceptual Definition

Conversely, **Minimum Cardinality** constraints are essential for ensuring redundancy, reliability, and the fulfillment of baseline safety standards. The axiom `cardinality_min_two_generic` stipulates that a class (X) must have a minimum of two relationships via property (p) to instances of class Y. This is frequently utilized in high-availability infrastructure governance, such as requiring a database service to have at least two replicas or requiring a signature policy to have at least two authorized signatories. This axiom ensures that critical dependencies are not single points of failure.

### 7.5.2 Relational Implementation and Evidence

The `t_cardinality_min_two_generic` table functions as the registry for these mandatory thresholds. By linking the constraint (`id`) to the governing Directive (`y`), the framework establishes a clear chain of authority: the Directive mandates the behavior, and the Cardinality Axiom defines the quantitative threshold for compliance. Automated scanning tools can query this table to generate alerts if the actual count of related entities falls below the defined minimum.

**Table 7.4: Minimum Cardinality Constraints (Axiom 4)**

| id (Constraint ID) | x (Constrained Class) | y (Governed Directive ID) |
| :--- | :--- | :--- |
| CONST-MIN-2-REP | cco:DatabaseReplica | DIR-CTRL-APP-02 |
| CONST-MIN-2-SIG | cco:AuthorizedSignatory | DIR-CTRL-ADMIN-02 |
| CONST-MIN-2-FACTOR | cco:AuthenticationFactor | DIR-CTRL-APP-03 |
| CONST-MIN-2-SITE | cco:DisasterRecoverySite | DIR-CTRL-NET-01 |

*Note: The entry `CONST-MIN-2-REP` mandates that any entity classified as a `DatabaseReplica` under directive `DIR-CTRL-APP-02` must exist in a quantity of at least two to satisfy the requirement.*
