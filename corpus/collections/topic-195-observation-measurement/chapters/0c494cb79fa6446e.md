# Chapter 7: Metric Emission Protocols and Anomaly Detection Frameworks

This chapter delineates the formal specifications governing the emission of telemetry metrics, the targeting of artifacts for outlier detection, and the subsequent triggering of alerting mechanisms within a secure observability infrastructure. The protocols described herein establish the necessary ontological relationships between low-level system events, specifically those captured via Extended Berkeley Packet Filter (eBPF) instrumentation, and high-level compliance reporting. Adherence to these structural axioms ensures that all monitored artifacts are traceable to their source processes and that any anomaly detection logic is grounded in verifiable, typed data structures.

## 1. Outlier Detection Targets Dataset

In the context of enterprise-grade monitoring, the definition of a target artifact is a prerequisite for any statistical analysis. The axiom governing the Outlier Detection Targets Dataset establishes that a specific class of process is functionally defined by its capacity to target a `cco:Artifact`. This relationship is not merely associative but constitutive; the process exists, in this operational context, to apply statistical boundaries or heuristic analysis to a specific data artifact.

The implementation of this axiom requires a rigid mapping between the monitoring process and the artifact it observes. To maintain data integrity and facilitate audit trails, the target artifacts must be registered as discrete entities within the configuration management database. The following relational schema embodies this axiom, where the primary key (`id`) serves as the unique reference for the artifact, and the column `x` denotes the specific class or instance of the process performing the targeting.

**Table 1.1: Outlier Detection Targets Registration**
This table enumerates the active processes designated to target specific system artifacts for outlier detection. The `id` column represents the unique identifier for the target artifact, which serves as a foreign key for downstream metric emission and alerting tables. The `x` column specifies the process class responsible for the observation.

| id | x |
|---|---|
| `artifact_cpu_sys_01` | `SystemCPUAnalyzer` |
| `artifact_mem_rss_02` | `MemoryResidentSetMonitor` |
| `artifact_disk_io_03` | `DiskIOLatencyTracker` |
| `artifact_net_rx_04` | `NetworkReceiveAuditor` |
| `artifact_ssl_handshake_05` | `SSLHandshakeTimer` |

The configuration detailed in Table 1.1 ensures that every artifact subject to compliance monitoring—such as CPU system time or memory resident set size—is explicitly bound to an analyzer process. This binding prevents "orphan" metrics, where data might be collected without a clear ownership or analytical context. Furthermore, by defining these targets as subclasses of `bfo:0000015` (a process), the framework acknowledges that observation is an active, temporal occurrence rather than a static state.

## 2. Metric Emission Subclasses

Building upon the foundation of established targets, the Metric Emission Subclass axiom defines the generative relationship between an emitting process and the metric itself. Formally, this is expressed as the intersection of a process (`bfo:0000015`) and the specific capability to emit a metric (`sdg:emitsMetric`). This distinction is critical for governance: it separates the passive collection of data from the active emission of a standardized metric that may be consumed by upstream alerting or dashboarding systems.

The architecture mandates that any process classified as a metric emitter must be linked to a valid target artifact. This linkage enforces a strict hierarchy where metrics cannot exist in a vacuum; they must be derived from a monitored artifact. The relational projection of this axiom captures the emitter (`x`), the specific metric emitted (`y`), and the unique identifier for the emission event or class. The foreign key constraint on `y` ensures referential integrity, mandating that the emitted metric corresponds to a valid entry in the Outlier Detection Targets Dataset.

This table details the specific processes responsible for emitting metrics and the target artifacts they are associated with. The `x` column identifies the emitting process class, while `y` references the target artifact ID (Foreign Key). | `emission_mem_profiler` | `MemoryProfilerService` | `artifact_mem_rss_02` |

As evidenced in Table 2.1, the `HostTelemetryDaemon` is explicitly configured to emit metrics regarding `artifact_cpu_sys_01`. This configuration allows auditors to verify that the data stream populating the monitoring dashboards originates from an authorized source. The use of distinct classes for the emitter (e.g., `CryptographyObserver` for SSL handshakes) allows for granular access control and policy enforcement, ensuring that sensitive telemetry is handled only by processes with the appropriate security clearances.

## 3. Alert Triggering Mechanisms

The final stage in the observability pipeline is the reaction to observed states, formalized by the Alert Triggered By axiom. This axiom defines a class of processes that are initiated or triggered by a specific metric. In practice, this translates to the automation of incident response workflows, where the breach of a threshold or the detection of an anomaly in a metric (`sdg:triggeredByMetric`) invokes a handler process.

This relationship is critical for maintaining the "control loop" of security operations. The axiom dictates that the alerting process is a subclass of `bfo:0000015`, situating it firmly within the temporal domain of system events. Relationally, this requires a mapping where the alert process (`x`) is linked to the causative metric (`y`). The schema enforces that the triggering metric must be a valid, registered target, thereby preventing alert storms based on unverified or rogue data sources.

**Table 3.1: Alert Triggering Logic**
This table maps the alerting processes to the metrics that trigger them. The `x` column denotes the alert handler class, and `y` is the identifier of the metric that acts as the trigger. This configuration ensures that automated responses are strictly bound to valid metric emissions.

| id | x | y |
|---|---|---|
| `alert_cpu_critical` | `CriticalCPUAlertHandler` | `artifact_cpu_sys_01` |
| `alert_mem_warning` | `MemoryWarningDispatcher` | `artifact_mem_rss_02` |
| `alert_io_saturation` | `IOSaturationAlarm` | `artifact_disk_io_03` |
| `alert_net_anomaly` | `NetworkAnomalyResponder` | `artifact_net_rx_04` |
| `alert_ssl_failure` | `SSLFailureInvestigator` | `artifact_ssl_handshake_05` |

The data presented in Table 3.1 illustrates the deterministic nature of the alerting framework. For instance, the `IOSaturationAlarm` is triggered exclusively by the `artifact_disk_io_03` metric. This strict binding prevents false positives that might occur if an alert handler were to subscribe to multiple, loosely defined data streams. By anchoring the alert to a specific metric ID, the framework supports precise forensic analysis, allowing investigators to trace the exact sequence of events from the initial eBPF trace to the final alert invocation.

## 4. eBPF Event Attributes

While the previous sections address the logical flow of metrics and alerts, the raw data ingestion layer is governed by the eBPF Event Attributes axiom. Extended Berkeley Packet Filter (eBPF) technology allows for the execution of sandboxed programs within the operating system kernel, providing a mechanism for deep observability with minimal overhead. The axiom asserts that any eBPF event process must possess a minimum of one `cco:DesignativeICE` (Information Content Entity).

This requirement ensures that events captured at the kernel level are not opaque binary blobs but carry structured, designative attributes necessary for correlation with higher-level metrics. An attribute might be a process ID, a user ID, a syscall name, or a file descriptor. Without these attributes, the event cannot be mapped to the logical artifacts defined in Section 1. The relational schema for this axiom is straightforward, serving as a registry of valid eBPF event classes that comply with the attribute requirement.

**Table 4.1: Validated eBPF Event Classes**
This table lists the eBPF event classes that have been validated to contain at least one designative attribute. The `x` column represents the specific event class name. These events form the foundational data layer from which metrics are eventually derived.

| id | x |
|---|---|
| `evt_sys_execve` | `ExecveSyscallEvent` |
| `evt_sys_openat2` | `Openat2SyscallEvent` |
| `evt_net_tcp_connect` | `TCPConnectEvent` |
| `evt_sched_process_exit` | `ProcessExitEvent` |
| `evt_file_read` | `FileReadEvent` |

Table 4.1 provides a registry of the low-level instrumentation points sanctioned within the system. For example, the `ExecveSyscallEvent` is guaranteed to carry attributes such as the executable path and calling PID. This structural guarantee is what allows the `SystemCPUAnalyzer` (referenced in Table 1.1) to attribute CPU usage to specific processes. The ontology ensures that there is no "data drop" between the kernel-level event capture and the application-level metric emission; the designative attributes act as the bridge across these abstraction layers.
