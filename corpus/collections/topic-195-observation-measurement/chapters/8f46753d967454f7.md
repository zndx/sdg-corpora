# Chapter 4: Kernel-Level Observability and Automated Compliance Monitoring

## 4.1 Scope and Preamble

This chapter delineates the structural framework for kernel-level observability, specifically focusing on the interaction between extended Berkeley Packet Filter (eBPF) processes, artifact targeting, and the subsequent emission of compliance metrics. The text establishes a formal ontology for describing how system processes identify specific artifacts (such as files, memory regions, or socket buffers), generate measurable data points, and trigger automated alerts based on predefined thresholds. The definitions herein are grounded in the Basic Formal Ontology (BFO) and are designed to support high-fidelity audit reporting and automated governance enforcement. Readers should interpret the following sections as a specification for the relational mapping of observability data to compliance frameworks, ensuring that all telemetry is anchored to verifiable system states.

## 4.2 Outlier Detection Targets Dataset

The identification of anomalies within a computing environment requires a rigorous definition of the targets under observation. In this context, an "Outlier Detection Target" is not merely a passive data point but is formally defined as a process that actively targets a specific system artifact. This distinction is critical for audit trails; it implies that the act of detection is an active process (bfo:0000015) directed toward an information-bearing entity.

The processes illustrated below are generally used for granular system inspection. The series of detection protocols defined in this section are instantiated as specific classes of processes that lock onto artifacts—ranging from persistent storage volumes to volatile memory structures. These processes can be attached using kernel hooks or by placing tracepoints on specific system calls. By defining the target as a process, the framework ensures that every detection event is temporally bound and causally linked to the artifact's state.

### 4.2.1 Relational Mapping of Detection Processes

The following table provides the relational schema implementation for the Outlier Detection Targets Dataset. Each row represents a unique class of process (X) designed to target a specific artifact type. The primary key (`id`) serves as the stable reference for downstream metric emission and alerting logic.

**Table 4.1: Outlier Detection Targets Dataset**

| id | x |
| :--- | :--- |
| ODT-1001 | FileIntegrityScanningProcess |
| ODT-1002 | NetworkSocketInspectionProcess |
| ODT-1003 | RegistryKeyAuditProcess |
| ODT-1004 | MemoryPageHashingProcess |
| ODT-1005 | DeviceDriverValidationProcess |

The `FileIntegrityScanningProcess`, for instance, represents a class of process that targets the file system artifact. It is distinct from a `NetworkSocketInspectionProcess`, which targets the communication buffer artifacts. This classification allows governance frameworks to apply specific retention policies and access controls based on the nature of the artifact being targeted, rather than treating all telemetry as a homogeneous stream.

## 4.3 Metric Emission Subclass

Building upon the foundation of artifact targeting, the concept of Metric Emission is introduced as a specialized subclass of process. Within this ontology, a Metric Emission Subclass is defined as a process that emits a specific metric type (Y). Crucially, the metric being emitted is structurally dependent on the Outlier Detection Target defined in the previous section. This relationship enforces a strict dependency: a metric cannot exist in isolation; it must be the output of a process that is actively targeting a system artifact.

Metric Emission Subclasses are generally used for surface-level telemetry aggregation. Unlike traditional passive logging, these processes emit metrics by reacting to the state changes detected in the target artifact. The emission is the observable effect of the detection process. For example, a process targeting a file artifact may emit a cryptographic hash metric, while a process targeting a network socket may emit a packet throughput metric.

### 4.3.1 Dependency and Relational Structure

The relational schema for Metric Emission enforces a foreign key constraint linking the emitted metric (`y`) back to the Outlier Detection Targets Dataset. This ensures referential integrity, guaranteeing that every metric emitted is traceable to a valid, defined detection process. The table below illustrates this hierarchy, where the `y` column corresponds to the `id` of the target process.

**Table 4.2: Metric Emission Subclass Registry**

| id | x | y |
| :--- | :--- | :--- |
| MES-2001 | HashGenerationSubProcess | ODT-1001 |
| MES-2002 | LatencyMeasurementSubProcess | ODT-1002 |
| MES-2003 | ConfigurationDeltaSubProcess | ODT-1003 |
| MES-2004 | BitFlipFrequencySubProcess | ODT-1004 |
| MES-2004 | SignatureVerificationSubProcess | ODT-1005 |

In this configuration, the `HashGenerationSubProcess` (X) is the specific mechanism that emits the metric, and it is inextricably linked to the `FileIntegrityScanningProcess` (Y, referenced via ODT-1001). This structure allows auditors to query the lineage of a specific metric value, tracing it back from the emission event to the original artifact targeting intent.

## 4.4 Alert Triggered By

The final stage in the observability pipeline is the generation of alerts. An alert is formally defined as a process that is triggered by a metric. This axiom completes the causal chain: Artifact Targeting leads to Metric Emission, which in turn triggers an Alert. The Alert Triggered By concept is essential for automated compliance enforcement, as it represents the transition from observation (measuring) to action (notifying or remediating).

Alerts are generally used for threshold enforcement and incident response initiation. The processes defined in this section are triggered when the metric emitted by the upstream process violates a defined condition (e.g., a hash mismatch or a latency spike). The alert process itself is a distinct entity, often involving the generation of a Designative Information Content Entity (ICE), such as a ticket ID or a syslog entry, which formally records the violation.

### 4.4.1 Alert Logic and Foreign Key Constraints

The relational schema for alerts maintains the strict dependency on the metric emission layer. The `y` column in the alert table references the `id` from the Outlier Detection Targets Dataset, effectively linking the alert to the metric source. This design facilitates complex queries, such as "Retrieve all alerts triggered by metrics associated with file integrity scanning."

**Table 4.3: Alert Triggered By Registry**

| id | x | y |
| :--- | :--- | :--- |
| ATB-3001 | SecurityViolationAlert | ODT-1001 |
| ATB-3002 | NetworkAnomalyAlert | ODT-1002 |
| ATB-3003 | UnauthorizedChangeAlert | ODT-1003 |
| ATB-3004 | MemoryCorruptionAlert | ODT-1004 |

For instance, the `SecurityViolationAlert` (X) is triggered by the metric emitted from the `FileIntegrityScanningProcess` (Y, referenced via ODT-1001). This mapping ensures that the alerting logic is not decoupled from the underlying detection mechanism. If the detection process is deprecated or modified, the foreign key constraints ensure that the dependent alert configurations are reviewed or updated, maintaining the integrity of the compliance framework.

## 4.5 eBPF Event Minimum One Attribute

While the previous sections describe the logical flow of compliance data, the raw collection of this data relies on extended Berkeley Packet Filter (eBPF) technology. An eBPF Event is defined as a process that possesses a minimum of one Designative Information Content Entity (ICE). An attribute, in this context, is a specific data point attached to the event—such as a user ID, a timestamp, or a return code—that designates the context of the event.

The eBPF events illustrated below are generally used for low-overhead, kernel-space instrumentation. These events are "sandwiched" between the kernel execution context and the user-space reporting collector. They can be attached to function entry or exit points, or to tracepoints within the kernel. The requirement for a minimum of one attribute ensures that every event collected is semantically rich enough to be actionable for audit purposes. An event with no attributes is considered noise and is filtered out by the validation layer.

### 4.5.1 Event Attribute Validation

The following table catalogs the eBPF Event classes that satisfy the axiom of possessing at least one attribute. These classes represent the fundamental units of observation that feed into the higher-level Outlier Detection and Metric Emission processes.

**Table 4.4: eBPF Event Minimum One Attribute Registry**

| id | x |
| :--- | :--- |
| EVT-4001 | SyscallOpenEvent |
| EVT-4002 | SyscallCloseEvent |
| EVT-4003 | NetworkPacketReceiveEvent |
| EVT-4004 | FileLoadEvent |
| EVT-4005 | ProcessForkEvent |

The `SyscallOpenEvent` (X), for example, is a valid process because it inherently carries attributes such as the filename, flags, and process ID. This axiom ensures that the telemetry pipeline is populated with high-value data. The `ProcessForkEvent` provides parent and child process IDs, satisfying the requirement for a Designative ICE. These raw events form the evidentiary basis for the artifact targeting described in Section 4.2, linking the lowest-level kernel activity to the highest-level compliance reporting.
