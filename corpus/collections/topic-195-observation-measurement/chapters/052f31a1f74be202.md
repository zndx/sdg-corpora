# Chapter 4: Structural Frameworks for Kernel-Level Telemetry and Compliance

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish a verifiable chain of custody for kernel-level observability data. In the context of modern governance frameworks, the integrity of audit trails relies not merely on the collection of data, but on the rigorous definition of the relationships between the observing processes, the targeted artifacts, and the resulting metrics or alerts. The following sections define the axiomatic constraints governing these relationships, specifically focusing on the interaction between extended Berkeley Packet Filter (eBPF) processes and the artifacts they monitor. The definitions provided herein are essential for ensuring that compliance reporting meets the evidentiary standards required by regulatory bodies, particularly where non-repudiation and attribution are mandatory.

## 4.2 Outlier Detection Targets

### 4.2.1 Definition and Operational Context

In the governance of system telemetry, the concept of a "target" is foundational. An outlier detection target is formally defined as a process that directs its observational capabilities toward a specific artifact. An artifact, in this ontology, refers to any discrete information object within the system state—such as a file, a network socket, or a process memory map—that is subject to compliance monitoring. The axiom governing this relationship asserts that the observing process (Class X) is a subclass of a BFO Process (bfo:0000015) and holds the specific property of targeting an artifact (cco:Artifact).

This distinction is critical for auditability. Without a formal declaration of the target artifact, telemetry data lacks the necessary context to be evaluated for anomalous behavior. For instance, a process that merely enumerates system files without a declared target artifact cannot be effectively evaluated for unauthorized access patterns. The formalization of this relationship allows auditors to map specific telemetry streams to regulated data assets, thereby satisfying the "data lineage" requirements of standards such as ISO 27001 and the NIST Cybersecurity Framework.

## 4.3 Metric Emission Subclasses

### 4.3.1 The Axiom of Emission

The transition from raw observation to governance-ready data is effected through the emission of metrics. A metric emission subclass is defined as a specific type of process (Class X) that is responsible for generating a metric (Class Y). According to the governing axiom, this process is a subclass of a BFO Process and is characterized by the object property `sdg:emitsMetric`. This relationship establishes a dependency: the existence of the metric is contingent upon the execution of the emitting process.

In practical terms, this axiom ensures that every quantitative data point used for reporting or alerting can be traced back to a specific, authorized process. This traceability is a core component of the "Control Environment" in audit engagements. When a metric indicates a deviation from the baseline (e.g., a spike in file modification rates), the auditor must be able to identify the emitting process to verify that the sensor itself has not been compromised or misconfigured.

### 4.3.2 Relational Structure and Evidence

The relational schema governing metric emissions enforces a strict link between the emitting process and the metric itself. Crucially, the metric (`y`) is structurally dependent on the target dataset defined in Section 4.2. This dependency ensures that metrics are not generated in a vacuum; they must be associated with a valid, pre-registered target process.

## 4.4 Alert Triggering Mechanisms

### 4.4.1 Logic and Determinism

The final stage in the observability pipeline is the activation of remedial or investigative workflows via alerts. An alert triggering subclass is defined as a process (Class X) that is initiated or triggered by a specific metric (Class Y). The axiom `sdg:triggeredByMetric` formalizes the causal link between the observation of a threshold violation and the operational response.

This relationship is paramount for the "Automated Remediation" controls defined in many governance frameworks. It dictates that alerts cannot be arbitrary; they must be the deterministic output of a metric evaluation. For example, an alert regarding a potential data exfiltration event must be triggered by a specific metric, such as `OutboundByteCount`, exceeding a defined threshold. This formalization prevents "alert fatigue" by ensuring that only metric-verified anomalies initiate the alert state, and it provides auditors with a clear logic path from the raw event to the notification.

### 4.4.2 Alert Configuration and Dependencies

The structural integrity of the alerting framework relies on the same referential backbone as the metric emission. The metric that triggers the alert (`y`) must correspond to a valid entry in the targets dataset. This creates a unified chain: the Target Process emits the Metric, and the Metric triggers the Alert. Disruption in this chain (e.g., an alert triggered by a non-existent metric) constitutes a configuration control failure that must be flagged during compliance audits.

## 4.5 eBPF Event Attributes

### 4.5.1 Designative Information Content Elements (ICE)

The granularity of modern telemetry is largely driven by eBPF (extended Berkeley Packet Filter) technology, which allows for the execution of sandboxed programs within the operating system kernel. An eBPF event is formally classified as a process that possesses a minimum of one attribute, specifically a `cco:DesignativeICE` (Information Content Element). The axiom `ebpf_event_min_one_attribute` mandates that for an eBPF event to be valid within the ontology, it must carry at least one designative attribute.

Designative attributes are the data fields that provide semantic context to the raw event. This includes metadata such as process IDs, user IDs, file descriptors, and timestamps. Without these attributes, an event is merely a signal with no governance value. The requirement for "min 1" ensures that the telemetry stream is parsable and attributable. In an audit context, this attribute requirement supports the "non-repudiation" principle by ensuring that every system event captured is tagged with sufficient information to identify the actor and the action.

### 4.5.2 Implementation and Attribute Constraints

The implementation of this axiom requires that all eBPF tracing programs be configured to populate specific data structures before returning events to user space.
