# Chapter 4: Ontological Structures for Observability and Anomaly Detection

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing observability processes, specifically within the context of kernel-level telemetry and automated compliance auditing. The definitions provided herein establish a rigorous framework for describing how system entities emit metrics, how detection algorithms target specific artifacts, and how alerts are instantiated based on metric thresholds. The discourse is anchored in the Basic Formal Ontology (BFO) to ensure temporal consistency and process integrity. By defining these relationships through Manchester syntax axioms and their corresponding relational projections, this chapter provides the necessary schema for implementing high-fidelity monitoring systems capable of supporting governance, risk, and compliance (GRC) requirements.

## 4.2 Metric Emission Subclasses

### 4.2.1 Conceptual Definition

The fundamental unit of observability is the metric, which serves as a quantitative representation of a system state or process. Within the ontology, the relationship between a process and the metric it generates is formalized by the axiom `metric_emission_subclass`. This axiom asserts that a specific class of process (X) is a subclass of processes that emit a specific class of metric (Y). This distinction is critical for audit trails; it is insufficient to merely record that a metric exists. The governance framework requires the provenance of the metric to be explicitly defined as a characteristic of the emitting process class.

For instance, consider a `WebServerProcess`. It is not merely a process that executes code; it is defined by its capacity to emit `RequestLatencyMetric`. The emission is not an accidental property but a defining feature of the process class within the observability ontology. This allows auditors to verify that if a process is identified as a `WebServerProcess`, it *must* be emitting the associated metrics, otherwise, the system is in a non-compliant state.

### 4.2.2 Relational Implementation

The projection of this axiom into a relational schema enforces a foreign key constraint, ensuring that the metric being emitted corresponds to a valid target artifact within the system registry. The primary key identifies the specific emission relationship instance, while the foreign key (`y`) links the metric to the broader dataset of outlier detection targets.

## 4.3 Outlier Detection Targets

### 4.3.1 Conceptual Definition

To achieve effective security monitoring and performance analysis, the system must explicitly define the targets of outlier detection algorithms. The axiom `outlier_detection_targets_dataset` formalizes this by defining a class of processes (X) that target specific artifacts (`cco:Artifact`). In the context of this ontology, the "artifact" is typically the dataset or log stream generated by the metric emission processes described in Section 4.2.

This definition separates the *act* of detection from the *source* of the data. A `NetworkAnomalyDetector` is a process class defined by its targeting of network throughput artifacts. This ontological distinction allows for modular governance: one can update the detection algorithm without altering the definition of the metric emission, or vice versa, provided the interface (the artifact) remains stable. Compliance mandates require that every detection process has a declared target; "blind" monitoring of undefined system states is considered a violation of data integrity principles in this framework.

### 4.3.2 Relational Implementation

The relational schema for this concept is deceptively simple but structurally significant. It serves as the central registry for all artifacts that are subject to analysis. The `id` column acts as the global identifier for the artifact (and, by extension, the metric class associated with it). The `x` column denotes the detection process class that utilizes this artifact.

## 4.4 Alert Triggering Mechanisms

### 4.4.1 Conceptual Definition

The transition from observation to action is mediated by alerts. The axiom `alert_triggered_by` defines a class of processes (X) that are instantiated or triggered by a specific metric class (Y). This represents the causal link in the observability pipeline: the occurrence of a specific metric state (such as a threshold breach) triggers an alert process.

In a formal audit context, this relationship must be explicit to ensure traceability. If an automated remediation process executes, the system must be able to query the ontology to identify exactly which metric triggered it. For example, a `FirewallBlockProcess` (the alert/remediation) is triggered by a `ConnectionCountMetric`. The ontology rigorously defines this dependency, preventing "orphan" alerts that are not grounded in metric data or "phantom" triggers that do not result in defined alert processes.

### 4.4.2 Relational Implementation

The schema for `alert_triggered_by` mirrors the structure of the emission table but inverts the directional logic of the process flow. Here, `x` is the alert process class, and `y` is the metric class ID that acts as the trigger. The foreign key constraint ensures that alerts can only be defined in response to valid, registered metric artifacts found in the targets dataset.

## 4.5 eBPF Event Attributes

### 4.5.1 Conceptual Definition

Extended Berkeley Packet Filter (eBPF) technologies allow for the execution of sandboxed programs within the operating system kernel. To ensure that these low-level events are meaningful for high-level auditing, the axiom `ebpf_event_min_one_attribute` is applied. This axiom mandates that any eBPF event class (X) must possess a minimum of one attribute of type `cco:DesignativeICE` (Information Content Entity).

A `DesignativeICE` refers to a data element that designates or identifies a specific property, such as a Process ID (PID), User ID (UID), or file descriptor. Without this constraint, kernel events would be raw, context-less streams of binary data, rendering them unsuitable for compliance reporting. By enforcing a minimum cardinality of 1 for designative attributes, the ontology ensures that every event captured via eBPF is self-describing to a degree necessary for forensic analysis. For example, an `ExecveEvent` must contain an attribute designating the executable path or the invoking PID.

### 4.5.2 Relational Implementation

The relational table `t_ebpf_event_min_one_attribute` serves as a registry of valid eBPF event classes that satisfy the attribute constraint. The structure is straightforward: `id` is the unique identifier for the event class, and `x` is the name of the event class. While the table itself does not list the attributes (which would be stored in a separate attribute normalization table), the existence of a row in this table asserts that the class `x` complies with the ontology's requirement for possessing at least one designative attribute.
