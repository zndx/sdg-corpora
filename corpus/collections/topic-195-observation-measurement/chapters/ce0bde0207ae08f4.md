# Observability Process Classification in eBPF-Based Monitoring Systems

This chapter defines four process classes used to structure metric handling, outlier detection, and alerting within eBPF instrumented environments. The definitions are expressed through four tables that implement the corresponding OWL axioms. Primary and foreign keys encode subclass and property restrictions so that multi-table joins recover the intended logical entailments.

## 1 Metric Emission Subclasses

Axiom metric_emission_subclass states that a process class X emits metric Y. Table t_metric_emission_subclass therefore stores pairs of class identifiers. Column id is the primary key. Column y is a foreign key that must resolve to an existing row in t_outlier_detection_targets_dataset, ensuring every emitted metric is also a declared detection target. A cross-join on y recovers every process that can emit a given target artifact.

```sql
CREATE TABLE t_metric_emission_subclass (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_outlier_detection_targets_dataset(id)
);
```

| id  | x                              | y     |
|-----|--------------------------------|-------|
| me1 | PacketLatencyEmitter           | od1   |
| me2 | CPUUtilizationEmitter          | od2   |
| me3 | MemoryAllocationEmitter        | od3   |
| me4 | DiskThroughputEmitter          | od4   |
| me5 | NetworkDropRateEmitter         | od1   |

## 2 Outlier Detection Targets

Axiom outlier_detection_targets_dataset states that a process class X targets an artifact. Table t_outlier_detection_targets_dataset therefore lists each such process class once. Column id is the primary key and the sole join target for the two foreign-key columns defined later. No additional columns are required because the axiom asserts only the existence of the targeting relation.

```sql
CREATE TABLE t_outlier_detection_targets_dataset (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id  | x                              |
|-----|--------------------------------|
| od1 | NetworkTrafficOutlierDetector  |
| od2 | ComputeResourceOutlierDetector |
| od3 | MemoryPressureOutlierDetector  |
| od4 | StorageIOOutlierDetector       |
| od5 | FilesystemEventOutlierDetector |

## 3 Alert Trigger Relations

Axiom alert_triggered_by states that a process class X is triggered by metric Y. Table t_alert_triggered_by records these dependencies. Column id is the primary key. Column y is a foreign key into t_outlier_detection_targets_dataset, guaranteeing that an alert process can be activated only by a metric that is itself a declared detection target. Joining on y yields the set of alerts reachable from any given target.

```sql
CREATE TABLE t_alert_triggered_by (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_outlier_detection_targets_dataset(id)
);
```

| id  | x                       | y     |
|-----|-------------------------|-------|
| at1 | LatencyAlertProcess     | od1   |
| at2 | CPUAlertProcess         | od2   |
| at3 | MemoryAlertProcess      | od3   |
| at4 | DiskAlertProcess        | od4   |
| at5 | DropRateAlertProcess    | od1   |

## 4 eBPF Event Attribute Requirement

Axiom ebpf_event_min_one_attribute states that a process class X must possess at least one designative attribute. Table t_ebpf_event_min_one_attribute therefore enumerates the admissible event classes. Column id is the primary key. The table contains no foreign keys because the axiom imposes only a cardinality restriction internal to the class.

```sql
CREATE TABLE t_ebpf_event_min_one_attribute (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id  | x                              |
|-----|--------------------------------|
| eb1 | SyscallLatencyEvent            |
| eb2 | PageFaultEvent                 |
| eb3 | BlockIOEvent                   |
| eb4 | NetworkPacketEvent             |
| eb5 | FileOpenEvent                  |

## 5 Cross-Join Example

To determine which alert processes can be raised by the same detector that emits packet-latency metrics, first locate the detector row (od1) in t_outlier_detection_targets_dataset. Join t_metric_emission_subclass on y = od1 to obtain emitter classes, then join t_alert_triggered_by on the same y value. The result contains two alert rows:

- at1 (LatencyAlertProcess)  
- at5 (DropRateAlertProcess)

Both alerts share the detection target od1 and are therefore reachable from any emitter that also references od1.
