# Chapter 4: Governance Directives and Evidence Integrity

## 4.1 Scope and Preamble

This chapter delineates the structural dependencies between governance directives, control mechanisms, and the evidentiary artifacts required to establish compliance within an enterprise ontology. It provides a formal examination of the axioms governing attestations, requirements, and controls, specifically focusing on the relationships between procedural classes and their supporting data. The definitions herein are essential for auditors and compliance officers seeking to validate the integrity of governance frameworks against established ontological standards. All concepts are derived from the core ontology of directive governance and are presented with the rigor required for regulatory reporting and internal audit validation.

## 4.2 Attestation with Supporting Evidence

### 4.2.1 Conceptual Definition

In the context of formal governance, an attestation is defined not merely as a declaration, but as a process (bfo:0000015) that is intrinsically dependent on the existence of supporting artifacts. The axiom `attestation_with_supporting_evidence` establishes that for an attestation to be valid, it must possess a material link to a specific class of evidence. This relationship ensures that assertions regarding system state or process execution are verifiable and grounded in empirical data rather than subjective opinion.

The verbalization of this axiom—"{X} is something that with supporting evidence {Y}"—highlights the directional dependency of the attestation upon the evidence. Without the instantiation of {Y}, the attestation {X} remains ontologically null, lacking the necessary properties to satisfy auditors or regulatory queries. This structure prevents "orphan" attestations that claim compliance without demonstrable proof.

### 4.2.2 Implementation and Data Structure

To operationalize this axiom, the governance framework must maintain a rigorous mapping between every attestation event and its corresponding evidence artifact. The following table illustrates this relationship, demonstrating how specific attestation processes are anchored to distinct evidence classes. The primary key (`id`) ensures referential integrity, while the foreign keys (`x` and `y`) enforce the constraint that no attestation may exist without a corresponding evidence type.

**Table 4.1: Mapping of Attestations to Supporting Evidence**

| id | x (Attestation Process) | y (Evidence Class) |
| :--- | :--- | :--- |
| ATST-2024-001 | QuarterlyAccessReview | SystemAccessLogs |
| ATST-2024-002 | DataResidencyCheck | GeolocationMetadata |
| ATST-2024-003 | PenetrationTestValidation | VulnerabilityScanReport |
| ATST-2024-004 | EncryptionKeyRotation | KeyManagementAuditTrail |
| ATST-2024-005 | ThirdPartyRiskAssessment | VendorComplianceCertificate |

In the instance of `ATST-2024-001`, the `QuarterlyAccessReview` process is ontologically valid only if it is substantiated by `SystemAccessLogs`. This linkage allows automated audit tools to query the evidence class directly, verifying that the logs exist, are immutable, and cover the temporal scope of the attestation period.

## 4.3 Requirement Specification and Target Application

### 4.3.1 Conceptual Definition

The axiom `requirement_equiv_specifies_target` introduces a complex equivalence class essential for the precise definition of governance requirements. It posits that a requirement ({X}) is equivalent to the intersection of three conditions: it must be a `cco:DirectiveICE` (an Information Control Element), it must specify a particular mandate ({Y}), and it must apply to a specific target scope ({Z}). This tripartite structure distinguishes a binding requirement from a general guideline or best practice.

By formalizing the requirement in this manner, the ontology eliminates ambiguity regarding the applicability of governance rules. A directive that lacks a specified target ({Z}) is merely a policy statement, whereas the presence of {Z} transforms it into an enforceable requirement with a defined domain of operation. This granularity is critical for large-scale organizations where directives must be selectively applied based on geography, data classification, or operational unit.

### 4.3.2 Implementation and Data Structure

The relational projection of this axiom requires a table structure that captures the identifier of the requirement, the directive class, the specification content, and the target entity. The data below exemplifies how specific governance mandates are decomposed into their constituent elements. This structure supports complex querying, such as "retrieve all requirements applying to the `CustomerDatabase` target."

**Table 4.2: Decomposition of Requirements by Specification and Target**

| id | x (Requirement Class) | y (Specification) | z (Target) |
| :--- | :--- | :--- | :--- |
| REQ-SEC-101 | PasswordPolicyDirective | Minimum12Characters | ActiveDirectory |
| REQ-SEC-102 | DataRetentionRule | 7YearStorage | FinancialTransactionDB |
| REQ-OPS-103 | ChangeManagementProtocol | TwoPersonApproval | ProductionEnvironment |
| REQ-HR-104 | BackgroundCheckPolicy | FederalFingerprinting | EmployeePersonnel |
| REQ-LEG-105 | GDPRComplianceMandate | RightToErasure | EUCustomerDatabase |

For example, `REQ-SEC-101` defines the `PasswordPolicyDirective`. This requirement is valid only insofar as it specifies `Minimum12Characters` and applies specifically to the `ActiveDirectory` target. If the target were changed to a legacy system incompatible with such complexity, the requirement would need to be re-evaluated or a separate equivalence class would need to be instantiated for that distinct target.

## 4.4 Attestation Periodicity

### 4.4.1 Conceptual Definition

Governance processes are temporally bounded; an attestation performed outside its designated window is considered invalid for reporting purposes. The axiom `attestation_at_period` formalizes this by asserting that an attestation process ({X}) occurs within a specific attestation period ({Y}). This temporal indexing is crucial for maintaining the currency of compliance evidence and ensuring that controls are exercised at regular, defined intervals.

The verbalization "{X} is something that at attestation period {Y}" implies a strict containment relationship. The period {Y} acts as a temporal container for the process {X}. In audit scenarios, this allows for the rapid isolation of non-compliant gaps—specifically, identifying periods where an attestation process was due but not instantiated. This axiom is foundational for continuous monitoring systems that track the "aging" of compliance artifacts.

### 4.4.2 Implementation and Data Structure

The following table encodes the temporal bounds of attestation processes. By associating a unique attestation identifier with a defined period class, the organization can generate timeline reports and calculate compliance rates over specific fiscal quarters or operational cycles.

**Table 4.3: Temporal Mapping of Attestation Processes**

| id | x (Attestation Process) | y (Attestation Period) |
| :--- | :--- | :--- |
| ATST-TMP-001 | AnnualFinancialAudit | FiscalYear2023 |
| ATST-TMP-002 | SemiAnnualSecurityReview | FirstHalf2024 |
| ATST-TMP-003 | MonthlyVulnerabilityScan | March2024 |
| ATST-TMP-004 | WeeklyLogAnalysis | Week14_2024 |
| ATST-TMP-005 | AdHocIncidentResponse | Q2_2024 |

The entry `ATST-TMP-003` links the `MonthlyVulnerabilityScan` to the `March2024` period. This precise mapping ensures that during a Q2 audit, the scanner can confirm that the process for March was executed within the correct temporal boundaries, satisfying the `attestation_at_period` constraint.

## 4.5 Control Evidence Requirements

### 4.5.1 Conceptual Definition

While attestations consume evidence, controls *require* the generation of evidence. The axiom `control_with_evidence_requirement` defines a control ({X}) as a directive that mandates the production of a specific evidence type ({Y}). This distinction is vital for the design of control frameworks: it shifts the focus from the existence of the control to the *output* of the control.

A control that does not explicitly require evidence ({Y}) is operationally invisible and cannot be audited effectively. By embedding the `requiresEvidence` property within the class definition of the control, the ontology enforces a "design for auditability" principle. It ensures that for every control implemented, there is a pre-defined mechanism for capturing the proof of its execution.

### 4.5.2 Implementation and Data Structure

The relational schema for this axiom captures the mandatory link between a control directive and the evidence it must generate. The table below provides instances of technical and administrative controls and their corresponding evidence artifacts. This mapping is used by audit teams to validate that control operations are generating the necessary documentation.

**Table 4.4: Control-to-Evidence Requirements Mapping**

| id | x (Control Class) | y (Required Evidence) |
| :--- | :--- | :--- |
| CTRL-EV-001 | NetworkFirewallConfiguration | ConfigurationBackupFile |
| CTRL-EV-002 | DatabaseActivityMonitoring | SQLQueryAuditLog |
| CTRL-EV-003 | PhysicalEntryControl | VisitorBadgeRegistry |
| CTRL-EV-004 | SourceCodeManagement | CommitHistoryAndDiff |
| CTRL-EV-005 | PrivilegedAccessSession | SessionRecordingVideo |

In the case of `CTRL-EV-002`, the `DatabaseActivityMonitoring` control is defined by its requirement to produce a `SQLQueryAuditLog`. If the monitoring system is active but fails to generate the log (e.g., due to a storage failure), the control is considered non-compliant because the requirement {Y} has not been met, regardless of the control's operational status.

## 4.6 Attestation Authorization

### 4.6.1 Conceptual Definition

The final axiom, `attestation_signed_by`, addresses the accountability dimension of governance processes. It asserts that an attestation ({X}) must be signed by a person (`cco:Person`). This requirement introduces the concept of agency and responsibility into the ontology. An attestation is not a self-validating system event; it requires the explicit endorsement of a human agent who assumes liability for the accuracy of the attestation.

This axiom serves as the bridge between technical processes and legal/organizational accountability. By restricting the `signedBy` property to the class `cco:Person`, the ontology prevents automated service accounts from signing off on compliance attestations, thereby preserving the human-in-the-loop requirement essential for high-assurance environments.

### 4.6.2 Implementation and Data Structure

The table structure for this axiom focuses on the attestation entity and its authorization status. While the schema provided focuses on the attestation class ({X}), in a full implementation, this would be joined with a personnel directory. The following table lists attestation processes that are subject to the signature requirement.

The entry `ATST-SIG-001` represents the `CEOAnnualComplianceCertification`.
