# Chapter 12: Directive Equivalence and Safeguard Projections in Compliance Schemata

This chapter defines the relational encoding of five OWL axioms that govern directive equivalence, HIPAA physical and administrative safeguards, verification evidence requirements, and attestation signing constraints. The encoding uses five tables whose primary-key and foreign-key columns directly instantiate the slot types of each axiom. All column values are drawn from instances consistent with cco:DirectiveICE and bfo:Process anchors.

## 1. Requirement Equivalence and Target Specification

Axiom 1 (requirement_equiv_specifies_target) states that a class X is equivalent to a DirectiveICE that specifies some Y and applies to some Z. The table t_requirement_equiv_specifies_target materializes this equivalence. Column id is the primary key. Columns y and z are foreign keys; y references t_hipaa_safeguard_physical.id while z carries the target class reference. A reader can join on y to retrieve the safeguard class that satisfies the specifies restriction.

```sql
SELECT r.id, r.x, p.y
FROM t_requirement_equiv_specifies_target r
JOIN t_hipaa_safeguard_physical p ON r.y = p.id;
```

|----------|----------------------------------------|------------|----------------------------|
| req-001  | PhysicalAccessDirective                | safep-001  | FacilityPerimeter          |
| req-002  | WorkstationUseDirective                | safep-002  | ElectronicWorkstation      |
| req-003  | DeviceControlDirective                 | safep-003  | PortableMedia              |
| req-004  | MaintenanceLogDirective                | safep-004  | CafeteriaEquipment         |
| req-005  | VisitorLogDirective                    | safep-005  | ReceptionArea              |

## 1.1 Physical Safeguard Instantiation

Axiom 2 (hipaa_safeguard_physical) declares that class X is a DirectiveICE that hipaaSafeguard some Y. Table t_hipaa_safeguard_physical records each such pair. Column id is the primary key. Column y is a foreign key referencing t_requirement_equiv_specifies_target.id, closing the specifies relation required by Axiom 1. A cross-join on y yields the originating requirement for any given safeguard.

```sql
SELECT s.id, s.x, r.z
FROM t_hipaa_safeguard_physical s
JOIN t_requirement_equiv_specifies_target r ON s.y = r.id;
```

| id        | x                        | y         |
|-----------|--------------------------|-----------|
| safep-001 | LockedDoorPolicy         | req-001   |
| safep-002 | ScreenPrivacyFilter      | req-002   |
| safep-003 | USBPortDisablement       | req-003   |
| safep-004 | EquipmentSerialCheck     | req-004   |
| safep-005 | SignInBadgeRequirement   | req-005   |

## 1.2 Verification Evidence Production

Axiom 3 (verification_min_one_evidence) requires that a process X producesEvidence at least one instance of Y. Table t_verification_min_one_evidence stores each verification process together with its required evidence class. Column id is the primary key. Column y is a foreign key referencing t_hipaa_safeguard_physical.id. Joining on y traces the safeguard verified by each process.

```sql
SELECT v.id, v.x, p.x AS safeguard
FROM t_verification_min_one_evidence v
JOIN t_hipaa_safeguard_physical p ON v.y = p.id;
```

| id        | x                        | y         |
|-----------|--------------------------|-----------|
| ver-001   | QuarterlyDoorAudit       | safep-001 |
| ver-002   | MonthlyScreenInspection  | safep-002 |
| ver-003   | WeeklyPortScan           | safep-003 |
| ver-004   | DailyEquipmentLogReview  | safep-004 |
| ver-005   | BadgeLogReconciliation   | safep-005 |

## 2. Administrative Safeguard Projection

Axiom 4 (hipaa_safeguard_admin) parallels Axiom 2 for administrative safeguards. Table t_hipaa_safeguard_admin records each X that hipaaSafeguard some Y. Column id is the primary key. Column y references t_requirement_equiv_specifies_target.id, permitting the same cross-table navigation used for physical safeguards.

```sql
SELECT a.id, a.x, r.z
FROM t_hipaa_safeguard_admin a
JOIN t_requirement_equiv_specifies_target r ON a.y = r.id;
```

| id        | x                              | y         |

## 2.1 Attestation Signing Constraint

Axiom 5 (attestation_min_one_signer) states that a process X must be signedBy at least one Person. Table t_attestation_min_one_signer captures each attestation process. Column id is the primary key; no foreign-key column is present because the signer restriction is satisfied by the presence of the row itself.

| id        | x                              |
|-----------|--------------------------------|
| att-001   | AnnualSafeguardAttestation     |
| att-002   | QuarterlyVerificationSignOff   |
| att-003   | IncidentReportAttestation      |
| att-004   | MaintenanceLogCertification    |
