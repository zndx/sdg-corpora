# Chapter 7: Ontological Mapping of Artifacts, Directives, and Evidentiary Traces

This chapter delineates the structural relationships between digital artifacts, regulatory directives, and the evidentiary traces required to establish compliance within a governed information system. The scope encompasses the formal definition of artifacts possessing specific attributes—such as postal addresses, pricing structures, and tax identifiers—as well as the mapping of internal directives to external regulatory frameworks like PCI DSS. Furthermore, the chapter establishes the axiomatic basis for traceability, wherein specific processes serve as the foundational evidence supporting descriptive claims made by the system.

## 7.1 Artifact Geolocation and Postal Addressing

In the context of physical and digital asset management, the precise geolocation of an artifact is a prerequisite for logistical execution and jurisdictional compliance. The axiom `schemaorg_place_address` posits that a specific class of Artifact (X) necessarily possesses a Postal Address (Y). This relationship is not merely associative but structural; the artifact cannot be fully instantiated within the system without a valid address object bound to it.

The formalization of this relationship ensures that when an artifact is queried—whether for shipping, regulatory reporting, or facility management—the system retrieves a structured address entity rather than a flat text string. This distinction is critical for maintaining data integrity during validation routines, such as verifying that a billing address matches the payment card network records.

The relational projection of this axiom treats the artifact and the address as distinct entities linked by a primary key identifier. The table structure below illustrates this binding, where `x` represents the artifact entity and `y` represents the address class entity. The primary key (`id`) ensures that each specific artifact-address pairing is unique and immutable within the record set.

**Table 7.1: Artifact to Postal Address Mappings**

| id | x (Artifact) | y (Postal Address) |
| :--- | :--- | :--- |
| aap-001 | WarehouseFacility_NY | AddressClass_100Broadway |
| aap-002 | RetailStore_London | AddressClass_221BakerSt |
| aap-003 | DataCenter_VA | AddressClass_LoudounCampus |
| aap-004 | RegionalHub_SG | AddressClass_Ayerp Rajah |
| aap-005 | Office_Berlin | AddressClass_PotsdamerPlatz |

In the preceding table, the `x` column references specific instances of the `cco:Artifact` class, such as physical facilities or retail locations. The `y` column references the corresponding address class instances. This structure allows for a single artifact to theoretically possess multiple address types (e.g., physical vs. mailing) through distinct rows, provided the primary key constraint is satisfied. The rigorous separation of the artifact from its address facilitates updates to postal data without necessitating alterations to the core artifact record, thereby preserving the historical stability of the asset registry.

## 7.2 Regulatory Frameworks and PCI DSS Requirements

Governance frameworks rely heavily on the explicit mapping of internal control directives to external regulatory standards. The axiom `pci_dss_requirement` defines that a Directive Information Content Entity (ICE) (X) must be semantically linked to a specific PCI DSS Requirement (Y). This mapping serves as the backbone of automated compliance auditing, allowing the system to verify that an internal policy or directive (X) explicitly addresses a mandate within the Payment Card Industry Data Security Standard (Y).

The `cco:DirectiveICE` represents a normative document or rule within the organization's ontology. By linking this directive to a PCI DSS requirement class, the organization creates a traceable path from the high-level standard down to the operational directive. This is essential for gap analysis; if a specific PCI DSS requirement class does not appear as a value `y` for any directive `x`, the system flags a compliance deficit.

The relational schema for this axiom enforces a mandatory link between the directive and the requirement. The table below demonstrates how internal governance documents are anchored to specific compliance controls.

**Table 7.2: Directive to PCI DSS Requirement Mappings**

| id | x (DirectiveICE) | y (PCI DSS Requirement) |
| :--- | :--- | :--- |
| pdr-101 | PasswordRotationPolicy_Draft | Req_8.2.3 |
| pdr-102 | FirewallConfigurationStd | Req_1.1.4 |
| pdr-103 | WirelessAccessProtocol | Req_1.2.3 |
| pdr-104 | LogRetentionPolicy_v2 | Req_10.7 |
| pdr-105 | MediaSanitationGuide | Req_9.6.1 |

Here, `x` denotes the specific directive identifier (e.g., `PasswordRotationPolicy_Draft`), while `y` denotes the formal requirement class (e.g., `Req_8.2.3`, referring to changing passwords at least once every 90 days). The `NOT NULL` constraint on the `y` column ensures that every directive included in this table is explicitly justified by a compliance requirement. This structure supports automated audit reporting, where a system administrator can query all directives supporting a specific PCI DSS article to demonstrate control coverage during an assessment.

## 7.3 Commercial Artifacts and Pricing Structures

The financial dimension of digital commerce is governed by the `schemaorg_product_price` axiom. This axiom asserts that an Artifact (X), typically a product or service offering, possesses a Price (Y). In this ontological view, price is treated not as a primitive numerical value, but as a distinct class entity (Y) that may encapsulate currency, tier, validity period, and taxation rules.

This abstraction allows the system to handle complex pricing scenarios where a single artifact may have multiple associated price classes depending on context (e.g., list price vs. discounted price). By modeling the price as a class linked to the artifact, the system maintains a strict separation between the item definition and its financial valuation. This is critical for audit trails, as changes to the price class do not corrupt the identity of the artifact itself.

The relational implementation of this concept requires that every artifact listed in the table must be associated with a valid price class. The following table provides instances of this mapping, illustrating how commercial artifacts are anchored to their respective pricing schemas.

**Table 7.3: Artifact to Price Class Mappings**

| id | x (Artifact) | y (Price) |
| :--- | :--- | :--- |
| spp-201 | EnterpriseLicense_SaaS | PriceClass_MonthlySub |
| spp-202 | HardwareNode_v4 | PriceClass_Perpetual |
| spp-203 | ConsultingBlock_Hr | PriceClass_RateCard_A |
| spp-204 | SupportTier_Platinum | PriceClass_AnnualFee |
| spp-205 | API_Access_Standard | PriceClass_PerCall |

In this schema, `x` identifies the commercial artifact, such as an enterprise license or hardware node. The `y` column references the specific price class, which encapsulates the complex logic of the cost (e.g., `PriceClass_MonthlySub` implies a recurring billing cycle). This structure facilitates dynamic pricing updates where the `y` value can be swapped or versioned without altering the core artifact ID `x`, ensuring that historical transaction records remain consistent with the product definition at the point of sale.

## 7.4 Organizational Identification and Taxation

For legal and fiscal compliance, it is imperative that organizational artifacts are rigorously linked to their tax identifiers. The axiom `schemaorg_org_taxid` formalizes the relationship where an Artifact (X), representing a legal entity or vendor, possesses a Tax ID (Y). This mapping ensures that financial transactions, tax filings, and regulatory reports can be accurately attributed to the correct legal entity.

The Tax ID in this context is modeled as a class (Y) to accommodate the various formats and jurisdictions involved (e.g., EIN in the US, VAT ID in the EU). By binding the artifact (the organization or vendor record) to a specific tax ID class, the system enforces data validation rules that prevent the association of incompatible tax formats with specific entity types.

The relational table for this axiom enforces that every organizational artifact must reference a tax ID class. The data below exemplifies how distinct organizational entities are bound to their respective tax identifiers.

**Table 7.4: Organizational Artifact to Tax ID Mappings**

| id | x (Artifact) | y (Tax ID) |
| :--- | :--- | :--- |
| sot-301 | Vendor_Global_Logistics | TaxID_VAT_DE123 |
| sot-302 | Subsidiary_NorthAmerica | TaxID_EIN_987654321 |
| sot-303 | Partner_Consulting_JP | TaxID_Corp_JP_4444 |
| sot-304 | Supplier_RawMaterials | TaxID_ABN_555555 |
| sot-305 | Entity_Holdings_Main | TaxID_GST_CA_777777 |

The `x` column represents the organizational artifact, such as a vendor or subsidiary. The `y` column contains the tax ID class instance. This structure is vital for cross-border transactions, where the system must automatically determine the applicable tax rules based on the `y` value associated with the vendor `x`. It prevents the common error of treating tax IDs as simple strings, instead enforcing that they belong to a recognized class of identifiers within the jurisdictional ontology.

## 7.5 Evidentiary Traceability and Claim Support

The integrity of a compliance system is predicated on its ability to support descriptive claims with objective evidence. The axiom `trace_supports_claim` defines that a Process (X), specifically a `bfo:0000015` (process), supports a Claim, represented as a `cco:DescriptiveICE`. This axiom establishes the evidentiary link between the "doing" (the process execution) and the "saying" (the descriptive claim of compliance).

In this framework, a "claim" might be a statement such as "System logs are retained for 90 days." The "process" is the actual execution of the log rotation and archival job. The axiom asserts that the process instance provides the necessary support to validate the claim. Without this linkage, claims within the system are merely assertions lacking ontological grounding.

The relational schema for this axiom is streamlined, focusing on the process (`x`) as the primary evidence provider. The claim is implicitly understood to be the `cco:DescriptiveICE` supported by the process. The table below catalogs specific process instances that serve as evidence for system claims.

**Table 7.5: Process to Claim Support Mappings**

| id | x (Process) |
| :--- | :--- |
| tsc-401 | DailyLogArchive_Job_20231025 |
| tsc-402 | UserAccessReview_Audit_Q3 |
| tsc-403 | SSLCertRenewal_Check_Auto |
| tsc-404 | DatabaseBackup_Full_Weekly |
| tsc-405 | PenetrationTest_Execution_Ext |

In this table, `x` represents the specific process instance, such as the execution of a daily log archive job or a quarterly user access review. The primary key `id` uniquely identifies the trace record. While the `y` (the claim) is not a column in this specific projection (as it is fixed to the class `cco:DescriptiveICE` in the axiom), the row existence signifies that the process `x` is the evidentiary anchor for a specific descriptive claim. For instance, the process `DailyLogArchive_Job_20231025` acts as the proof supporting the claim regarding log retention policies. This structure allows auditors to query the process logs directly when validating the veracity of the system's descriptive claims.
