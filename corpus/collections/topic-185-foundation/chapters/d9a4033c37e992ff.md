# Chapter 7: Ontological Mapping of Compliance Artifacts and Fiscal Directives

This chapter delineates the formal ontological structures required to map physical and informational artifacts to their regulatory, fiscal, and geospatial properties. It provides a rigorous framework for auditing compliance artifacts within distributed governance systems, ensuring that every entity—from a fixed asset to a procedural directive—is anchored to verifiable identifiers and descriptive claims. The following sections detail the specific axioms governing these relationships, supported by relational data schemas that facilitate automated verification and audit readiness.

## 1. Geospatial Anchoring of Artifacts

### 1.1 Overview of Addressability
In the context of asset management and regulatory compliance, the physical location of an artifact is a primary datum for risk assessment and logistical control. The axiom `schemaorg_place_address` establishes that an artifact (specifically, a subclass of `cco:Artifact`) necessarily possesses a postal address. This relationship is not merely associative but foundational; it binds the physical or legal entity to a geospatial coordinate system recognized by postal authorities.

For auditors, this mapping ensures that fixed assets, storage repositories, and operational sites can be cross-referenced against shipping manifests, insurance policies, and jurisdictional regulations. The inability to verify a valid postal address for a critical artifact often constitutes a material weakness in internal control audits.

### 1.2 Relational Implementation
The following table embodies the axiom `schemaorg_place_address`, wherein the primary key (`id`) serves as the unique transaction identifier for the relationship. The column `x` represents the specific artifact instance (e.g., a server rack, a branch office, or a document storage facility), while `y` represents the canonical postal address object. This structure allows for one-to-many mappings if a single artifact spans multiple locations, though standard practice enforces a singular primary address for liability purposes.

## 2. Alignment with PCI DSS Requirements

### 2.1 Directive Compliance Framework
The Payment Card Industry Data Security Standard (PCI DSS) imposes stringent requirements on entities handling cardholder data. The axiom `pci_dss_requirement` posits that a directive (specifically a subclass of `cco:DirectiveICE`) is defined by its adherence to specific PCI DSS requirements. In practice, this means internal governance documents—such as security policies, access control mandates, and network configuration rules—must be formally traceable to the external standard they fulfill.

This mapping is critical for maintaining a "compliance continuum." When an internal directive is updated, the corresponding relational entry must be reviewed to ensure the PCI DSS requirement reference remains valid. Conversely, during an audit, this schema allows for the rapid generation of evidence matrices demonstrating that every operational directive is grounded in a specific compliance obligation.

### 2.2 Requirement Mapping Table
The table below implements the `pci_dss_requirement` schema. The primary key (`id`) uniquely identifies the binding between the internal directive (`x`) and the specific PCI DSS requirement (`y`). This structure supports the generation of "Compliance Gap Analysis" reports by joining directive tables with requirement libraries.

## 3. Valuation and Pricing Structures

### 3.1 Financial Artifacts and Price Specification
Accurate financial reporting requires that every artifact with a commercial value be explicitly linked to a price point. The axiom `schemaorg_product_price` asserts that an artifact (`cco:Artifact`) possesses a price attribute. In technical governance, this extends beyond simple retail pricing to include licensing fees, service rates, and internal transfer costs.

The precision of this data is paramount for audit trails. Discrepancies between the listed price in the master data record and the invoiced amount are a common trigger for forensic accounting investigations. Therefore, the price attribute must be treated as a controlled value, often validated against external catalogues or contract schedules.

### 3.2 Pricing Registry
The table `t_schemaorg_product_price` illustrates the instantiation of this axiom. The artifact (`x`) is linked to a specific price value (`y`). Note that `y` is treated as a class or literal representation of the price, allowing for currency encoding within the value string or as a separate object reference depending on the localization requirements.

## 4. Organizational Identification and Taxation

### 4.1 Fiscal Responsibility and Entity Tracking
For legal and taxation purposes, organizations must be uniquely identified. The axiom `schemaorg_org_taxid` formalizes the relationship between an organizational artifact (which may be a legal entity, a vendor, or a subsidiary) and its Tax ID. This identifier serves as the anchor for all fiscal transactions, tax withholdings, and inter-company settlements.

In a globalized economy, a single organizational artifact may possess multiple Tax IDs corresponding to different jurisdictions. However, the primary relational mapping typically focuses on the Tax ID relevant to the governing jurisdiction of the transaction or the entity's headquarters. Failure to maintain accurate Tax ID mappings can result in severe regulatory penalties and operational disruptions.

### 4.2 Tax Identification Registry
The following table, `t_schemaorg_org_taxid`, records the Tax ID (`y`) associated with specific organizational entities (`x`). The primary key (`id`) ensures that each mapping is distinct, allowing for the tracking of historical changes in tax status or the addition of new jurisdictions.

## 5. Evidentiary Traceability and Claims Support

### 5.1 The Traceability Chain
The integrity of a compliance report depends on the evidentiary basis of its claims. The axiom `trace_supports_claim` defines that a process or event (specifically, a subclass of `bfo:0000015`, a "Process" in the BFO ontology) supports a specific claim encapsulated in a Descriptive Information Content Entity (`cco:DescriptiveICE`). This is the logical mechanism by which raw data is elevated to the status of "evidence."

In practice, this means that a system log entry, a transaction record, or a sensor reading (the process/event) must be formally linked to the assertion it verifies (the claim). For instance, a log of a firewall configuration change supports the claim that "access controls were modified on a specific date." Without this explicit linkage, data remains merely noise, unverified and non-compliant.

### 5.2 Traceability Matrix
The table `t_trace_supports_claim` provides the schema for these evidentiary links. The column `x` represents the process or event instance that serves as the evidence. This table is essential for automated compliance engines, which query these relationships to validate that every regulatory claim is backed by at least one verifiable trace.
