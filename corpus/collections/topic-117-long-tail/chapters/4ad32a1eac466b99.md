# Directive Classification in Regulatory Compliance Systems

This chapter defines five directive classes drawn from an OWL ontology fragment and shows how their slot structures are realized as a five-table relational schema. The schema supports multi-hop queries that traverse administrative, physical, technical, and payment-card safeguards while preserving foreign-key integrity between threat-addressing controls and safeguard instances.

## 1 Scope and Schema Overview

The ontology fragment centers on the class cco:DirectiveICE. Five Manchester axioms specialize this class by restricting the properties hipaaSafeguard, addressesRisk, and pciDssRequirement. Each axiom projects directly to one table. Primary keys are opaque identifiers; foreign keys implement the “some” and “only” restrictions as referential constraints. All column values are drawn from the same controlled vocabulary of compliance classes used in the source ontology.

## 3 Cross-Join Demonstration

Question: “Which PCI DSS requirement and which physical safeguard both address risk through the same control that is itself bounded by administrative safeguard A001?”

Step 1. Start at t_hipaa_safeguard_admin where id = 'A001'; its y value is 'C001'.  
Step 2. Locate rows in t_pci_dss_requirement where y = 'C001' → R001.  
Step 3. Locate rows in t_hipaa_safeguard_physical where y = 'C001' → P001.

Joined result row:

- administrative_safeguard: A001 (WorkforceSecurity)  
- control: C001 (AccessControlPolicy)  
- pci_dss_requirement: R001 (BuildAndMaintainSecureNetwork)  
- physical_safeguard: P001 (FacilityAccessControl)

The four values are obtained solely by following the declared foreign-key paths; no additional inference is required.
