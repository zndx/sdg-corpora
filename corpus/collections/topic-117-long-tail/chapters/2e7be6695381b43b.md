### 4.0 Preamble and Scope

This chapter provides a rigorous examination of the compliance ontology governing the Health Insurance Portability and Accountability Act (HIPAA) and the Payment Card Industry Data Security Standard (PCI DSS). It focuses on the structural mapping of directives, controls, and safeguards within the Common Compliance Ontology (cco). The following sections delineate the specific axioms that define administrative, physical, and technical safeguards, alongside their intersection with PCI DSS requirements and threat mitigation classes. The objective is to establish a deterministic schema for auditing information security controls, ensuring that every directive is anchored to a verifiable risk mitigation posture. Readers will be introduced to the relational schema underpinning these concepts, supported by data tables that reflect the instantiation of these axioms in a production environment.

---

### 4.1 Administrative Safeguards and Directives

The Security Rule under HIPAA requires covered entities to implement administrative safeguards to manage the selection, development, implementation, and maintenance of security measures. In the context of the ontology, an administrative safeguard is formalized as a subclass of the `cco:DirectiveICE` (Information Control Element). The axiom defining this relationship posits that an administrative safeguard ({X}) is a directive that specifically functions to "hipaa safeguard" a protected entity or asset ({Y}).

This relationship is not merely taxonomic but functional. The administrative safeguard acts as the governing logic that dictates how a specific control class behaves. For instance, a "Workforce Security" policy does not exist in isolation; it safeguards the "Workforce Authorization" control class. This distinction is critical for auditors who must verify that policy documents (Directives) are effectively mapped to operational controls.

The relational projection of this axiom creates a dependency where the safeguard (X) must reference a valid control class (Y). This ensures that administrative policies are not created in a vacuum but are explicitly tied to the threats they are designed to mitigate.

### 4.2 Control Classes and Threat Addressing

While administrative safeguards provide the governance layer, operational security is executed through control classes. The ontology defines a control class as a `cco:DirectiveICE` that "addresses risk" ({Y}). This axiom, `control_only_addresses_threat_class`, establishes the core mechanism of risk mitigation. It asserts that for a control to be valid, it must be associated with a specific risk or threat vector.

A critical feature of this ontology is the recursive nature of the risk definition. The schema dictates that the risk ({Y}) addressed by a control is, in fact, defined by an administrative safeguard. This creates a closed loop of governance: the Administrative Safeguard defines the scope of the Control, and the Control addresses the Risk defined by that same Safeguard. This circular dependency ensures that risks are not abstract concepts but are formally bounded by the administrative directives governing them.

For example, if the administrative safeguard is "WorkforceSecurity," the corresponding control class might be "UnauthorizedAccessControl." The risk addressed by this control is the failure of the "WorkforceSecurity" policy itself. This structure allows auditors to trace a finding from a technical failure back through the operational control to the specific administrative policy that was violated.

*In Table 4.2, the control class "UnauthorizedAccessControl" (threat_class_001) addresses the risk associated with the "WorkforceSecurity" directive (admin_001). This confirms that the control is the operational manifestation of the administrative policy.*

### 4.3 Physical Safeguards

Physical safeguards are measures to protect physical electronic information systems and related buildings and equipment from natural and environmental hazards and unauthorized intrusion. In the ontology, a physical safeguard ({X}) is a `cco:DirectiveICE that hipaa safeguard {Y}. The structure mirrors that of administrative safeguards but applies specifically to physical domains.

The distinction in the ontology is necessary because the control classes ({Y}) referenced by physical safeguards differ in nature from those referenced by administrative safeguards. A physical safeguard, such as "FacilityAccessControls," safeguards a physical control class, such as "BuildingEntrySystem." The axiom ensures that physical security policies are mapped to tangible physical assets and vulnerabilities.

The relational schema for physical safeguards enforces that the safeguarded entity ({Y}) must exist as a defined control class in the threat registry. This prevents the documentation of physical security measures (e.g., locks, guards) without linking them to a specific physical asset or zone defined in the control framework.

**Table 4.3: Physical Safeguard Implementation**
This table details the implementation of physical safeguards. The `x` column represents the physical directive, while `y` references the control class (physical asset or zone) being safeguarded.

| id | x (Physical Directive) | y (Control Class) |
| :--- | :--- | :--- |
| phys_001 | FacilityAccessControls | threat_class_001 |
| phys_002 | WorkstationUsePolicy | threat_class_003 |
| phys_003 | DeviceAndMediaControl | threat_class_003 |

*Table 4.3 shows that "FacilityAccessControls" (phys_001) safeguards the "UnauthorizedAccessControl" class (threat_class_001). This implies that the physical access controls are the primary mitigation for the general unauthorized access threat defined in the control registry.*

### 4.4 Technical Safeguards

Technical safeguards are the technology and the policy and procedures for its use that protect electronic protected health information and control access to it. The axiom `hipaa_safeguard_technical` defines these as directives ({X}) that safeguard technical control classes ({Y}).

This category encompasses the automated mechanisms used to enforce security, such as encryption, authentication protocols, and audit controls. In the ontology, technical safeguards are the specific implementations of the broader control classes defined in Section 4.2. For instance, the "UniqueUserIdentification" requirement is a technical safeguard that addresses the "UnauthorizedAccessControl" class.

The data structure requires that every technical safeguard be linked to a control class. This linkage is vital for gap analysis. If a control class exists in the registry (e.g., "AuditLogFailure"), but no technical safeguard is linked to it in the tables, the system flags a compliance gap.

**Table 4.4: Technical Safeguard Mappings**
The following table maps technical directives to their respective control classes. These mappings represent the actual configuration of systems to meet compliance objectives.

| id | x (Technical Directive) | y (Control Class) |
| :--- | :--- | :--- |
| tech_001 | AccessControl | threat_class_001 |
| tech_002 | AuditControls | threat_class_004 |
| tech_003 | IntegrityControl | threat_class_003 |
| tech_004 | TransmissionSecurity | threat_class_003 |

*As shown in Table 4.4, the "AccessControl" directive (tech_001) safeguards the "UnauthorizedAccessControl" class (threat_class_001). Similarly, "AuditControls" (tech_002) are mapped to the "AuditLogFailure" class (threat_class_004), demonstrating how technical solutions directly address specific risk vectors.*

### 4.5 PCI DSS Requirements and Cross-Framework Alignment

While HIPAA provides the baseline for healthcare data, many organizations must also comply with the Payment Card Industry Data Security Standard (PCI DSS). The ontology includes an axiom for `pci_dss_requirement`, which defines a PCI requirement ({X}) as a `cco:DirectiveICE` that fulfills a `pciDssRequirement` for a specific control class ({Y}).

This axiom facilitates cross-walking between frameworks. A PCI requirement, such as "Restrict access to cardholder data," is mapped to the same underlying control class—likely "UnauthorizedAccessControl"—that is used by HIPAA safeguards. This unified approach allows for a single control registry to serve multiple compliance frameworks, reducing redundancy and audit fatigue.

The relational schema for PCI requirements mirrors that of the HIPAA safeguards, referencing the same central table of control classes. This design highlights that while the regulatory language (the Directive X) differs between HIPAA and PCI DSS, the operational control (the Class Y) remains consistent.

**Table 4.5: PCI DSS Requirement Mapping**
This table aligns PCI DSS requirements with the established control classes. It demonstrates how a single control class can satisfy multiple regulatory obligations.

| id | x (PCI Requirement) | y (Control Class) |
| :--- | :--- | :--- |
| pci_001 | RestrictAccess | threat_class_001 |
| pci_002 | UserIdentification | threat_class_001 |
| pci_003 | AuditTrailAccess | threat_class_004 |
| pci_004 | EncryptTransmission | threat_class_003 |

*Table 4.5 illustrates that PCI Requirement "RestrictAccess" (pci_001) maps to the same "UnauthorizedAccessControl" class (threat_class_001) as the HIPAA safeguards. This confirms that the organization's access controls satisfy both HIPAA and PCI DSS obligations simultaneously.*
