# Compliance Framework Mapping: Integrating PCI DSS and ISO 27001 Annex A Controls

This chapter establishes the formal ontological relationships between regulatory directives and descriptive control measures within a unified governance framework. It provides a systematic method for mapping high-level compliance obligations—specifically the Payment Card Industry Data Security Standard (PCI DSS) and the ISO/IEC 27001 Annex A controls—to foundational descriptive entities. The objective is to enable precise audit trails and automated compliance verification by structuring these requirements as deterministic relational data.

## 1. Descriptive Information Content Entities

### 1.1 Definition and Scope

In the context of information security governance, a Descriptive Information Content Entity (DICE) serves as the atomic unit of compliance data. Formally defined as a subclass of `cco:DescriptiveICE`, this concept encompasses any textual or logical assertion that describes a state of affairs, a configuration parameter, or a procedural step within an IT environment. Unlike prescriptive directives (which mandate action), a DICE represents the *evidentiary* or *descriptive* artifact that an auditor would verify.

For instance, the statement "System clocks must be synchronized to an authoritative time source" is not itself a directive in this ontology; rather, it is a descriptive entity representing the configuration state of time synchronization services. By isolating these descriptions, the framework allows for distinct mapping of multiple regulatory frameworks to a single, underlying technical control.

### 1.2 Entity Enumeration

The following table enumerates specific instances of Descriptive Information Content Entities. These entities function as the "objects" of compliance—the specific technical states or procedures that directives seek to enforce. Each entity is identified by a unique reference code and a formal class name, which serves as the primary key for subsequent relational mappings.

**Table 1.1: Foundational Descriptive Information Content Entities**

| ID | Entity Class (X) | Description |
| :--- | :--- | :--- |
| M-001 | StrongCryptographyProtocol | Utilization of strong cryptography (e.g., AES-256, RSA-2048) for encryption of stored cardholder data. |
| M-002 | FirewallConfigurationReview | Quarterly review of firewall and router rule sets to verify necessity and accuracy. |
| M-003 | WirelessNetworkScanning | Quarterly internal or external wireless scanning to identify unauthorized access points. |
| M-004 | MaliciousSoftwareProtection | Deployment and maintenance of anti-malware software across all systems, with automatic updates. |
| M-005 | MediaSanitizationProcedure | Implementation of procedures for the secure disposal or sanitization of storage media. |
| M-006 | UniqueUserAuthentication | Assignment of a unique ID to each person with access to system components or cardholder data. |

These entities form the `t_measurement_basic` layer of the ontology. They are passive descriptors; they do not carry the weight of the regulation but define the *what* that is being regulated. In a relational database context, these rows provide the foreign key targets for both PCI DSS and ISO 27001 mappings, ensuring that a single control (e.g., cryptography) can satisfy multiple distinct regulatory obligations without duplication of effort.

## 2. PCI DSS Requirement Directives

### 2.1 Regulatory Context

The Payment Card Industry Data Security Standard (PCI DSS) imposes a strict set of requirements intended to protect cardholder data. Within the ontology, a PCI DSS Requirement is modeled as a subclass of `cco:DirectiveICE`. This classification signifies that the requirement is an *Information Content Entity* that directs action or mandates a specific state.

The axiom `{X} is something that pci dss requirement {Y}` captures the relationship between a specific compliance directive (X) and the descriptive measurement (Y) it seeks to enforce. Here, X represents the specific PCI DSS requirement text or identifier (e.g., "Requirement 1.2.3"), while Y represents the foundational DICE defined in Section 1. This structure allows the organization to query which specific PCI DSS mandates map to a given technical control, facilitating gap analysis and audit reporting.

### 2.2 Mapping to Measurement Entities

To operationalize this mapping, specific PCI DSS requirements must be anchored to the descriptive entities. The following table illustrates this projection. It demonstrates how high-level regulatory requirements (the Directive) are substantiated by specific, verifiable technical states (the Measurement).

**Table 2.1: PCI DSS Requirement to Measurement Mapping**

| ID | Directive (X) | Measurement Entity (Y) |
| :--- | :--- | :--- |
| P-001 | Requirement 4.1: Use strong cryptography | M-001 |
| P-002 | Requirement 1.1.6: Review firewall rules | M-002 |
| P-003 | Requirement 11.1: Test wireless networks | M-003 |
| P-004 | Requirement 5.1: Deploy anti-malware | M-004 |
| P-005 | Requirement 9.6: Destroy media | M-005 |
| P-006 | Requirement 8.2.3: Unique IDs | M-006 |

*Action:* Ensure that compliance matrices reference the `Measurement Entity (Y)` column when configuring automated scanning tools, as these IDs correspond to the specific technical checks required for validation.

In this schema, the `Directive (X)` column contains the formalized text of the PCI DSS requirement, acting as the mandate. The `Measurement Entity (Y)` column serves as a foreign key to the `t_measurement_basic` table. This relational integrity ensures that every PCI DSS requirement is linked to a valid, defined control mechanism. For example, the directive to "Use strong cryptography" (Requirement 4.1) is fulfilled specifically by the entity `StrongCryptographyProtocol` (M-001), thereby providing a clear audit path from regulation to implementation.

## 3. ISO 27001 Annex A Integration

### 3.1 Governance Framework Alignment

While PCI DSS provides a prescriptive set of requirements for payment card environments, ISO/IEC 27001 offers a broader Information Security Management System (ISMS) framework. Annex A of ISO 27001 contains a comprehensive list of control objectives and controls. To harmonize these standards within a single governance ontology, we model ISO 27001 Annex A controls similarly to PCI DSS requirements: as subclasses of `cco:DirectiveICE`.

The axiom `{X} is something that iso27001 annex a {Y}` facilitates this harmonization. It allows the organization to map an ISO 27001 control (X) to the same underlying descriptive entity (Y) used for PCI DSS. This convergence is critical for reducing compliance fatigue; it demonstrates that a single technical control (e.g., unique user authentication) can simultaneously satisfy a PCI DSS requirement and an ISO 27001 Annex A control.

The table below details the mapping of specific ISO 27001 Annex A controls to the foundational descriptive entities. Note the reuse of the `Measurement Entity (Y)` identifiers established in Section 1. This reuse evidences the "one-to-many" relationship between a technical control and multiple regulatory standards.

| I-002 | Annex A.13.1.1: Network controls | M-002 |
| I-003 | Annex A.13.2.1: Information transfer | M-003 |
| I-004 | Annex A.12.2.1: Malware protection | M-004 |
| I-005 | Annex A.11.2.9: Equipment disposal | M-005 |
| I-006 | Annex A.9.2.1: Access control | M-006 |

*Action:* Update the ISMS asset inventory to tag relevant assets with the `Measurement Entity (Y)` IDs. This will automatically generate the compliance status for both PCI DSS and ISO 27001 during the next internal audit cycle.

The relational structure here mirrors that of the PCI DSS table. The `Directive (X)` column references the specific ISO 27001 Annex A control clause, while `Measurement Entity (Y)` links back to the `t_measurement_basic` table. For instance, the ISO control regarding "Malware protection" (A.12.2.1) maps to entity M-004. By querying the database for all directives linked to M-004, an auditor can instantly retrieve both the PCI DSS Requirement 5.1 and ISO 27001 Annex A.12.2.1, providing a unified view of the control's efficacy across frameworks.
