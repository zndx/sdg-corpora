# Chapter 4: Mapping Governance Directives to Technical Measurement Entities

## 4.1 Scope and Preamble

This chapter establishes the formal methodology for aligning high-level governance directives with granular technical measurement entities. In the context of a comprehensive compliance framework, it is insufficient to merely cite regulatory standards; organizations must demonstrate a traceable lineage between abstract mandates (Directives) and the specific, observable states of their information systems (Descriptive Information Content Entities). The following sections delineate the ontological structures required to support this mapping, specifically focusing on the integration of PCI DSS requirements and ISO/IEC 27001 Annex A controls within a unified audit repository. This approach ensures that evidence collection is not only systematic but also semantically consistent across multiple regulatory domains.

## 4.2 Foundational Entities: Descriptive Information Content Entities

### 4.2.1 Definition and Ontological Status

The fundamental unit of audit evidence is the Descriptive Information Content Entity (DescriptiveICE). Formally, a DescriptiveICE represents a distinct, verifiable state or configuration within the target environment. Unlike abstract directives, which prescribe behavior, a DescriptiveICE describes a factual condition—such as the enabled status of a specific encryption cipher or the retention period set for an access log.

The axiom governing this entity is expressed as:
**Class: {X} SubClassOf: cco:DescriptiveICE**

In this schema, {X} represents the specific measurement or descriptive entity being cataloged. This classification is critical because it segregates observable facts from normative rules. Within the relational schema, these entities are stored in the `t_measurement_basic` table. The primary key (`id`) serves as the immutable reference for the measurement, while the column `x` holds the human-readable designation of the descriptive entity.

### 4.2.2 Role in Compliance Verification

When an auditor asserts that a system is "compliant," they are implicitly verifying that the observed values of various DescriptiveICEs match the required states defined by the governing directives. For instance, a directive may mandate "strong cryptography," but the corresponding DescriptiveICE must define "strong cryptography" in operational terms (e.g., "AES-256-CBC"). Without this foundational layer, the compliance assessment lacks the necessary granularity to be actionable or reproducible.

## 4.3 PCI DSS Requirement Integration

### 4.3.1 Directive Structure and Axiomatic Definition

The Payment Card Industry Data Security Standard (PCI DSS) functions as a Directive Information Content Entity (DirectiveICE). In this ontology, a PCI DSS requirement is not merely a text string but a structured class that asserts a relationship between a specific requirement identifier and a measurement entity.

The governing axiom is defined as:
**Class: {X} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y}**

Verbalized, {X} (the requirement) is something that PCI DSS requirement {Y} (the measurement). This structure enforces the principle that every regulatory mandate must be anchored to a specific technical control or measurement. The relational projection of this axiom is captured in the `t_pci_dss_requirement` table, where `y` acts as a foreign key referencing the `t_measurement_basic` table.

### 4.3.2 Mapping Requirements to Controls

The process of mapping PCI DSS requirements involves decomposing the standard's text into atomic directives and associating them with the IDs defined in Section 4.2. For example, PCI DSS Requirement 8.2.3 regarding secure authentication is operationalized by linking it to the `meas_auth_mfa` entity. This linkage allows automated compliance tools to query the system for the presence of MFA rather than relying on manual interpretation of the requirement text.

## 4.4 ISO/IEC 27001 Annex A Control Alignment

### 4.4.1 Directive Structure and Axiomatic Definition

Similar to PCI DSS, the ISO/IEC 27001 standard provides a set of controls via Annex A. These controls are modeled as DirectiveICEs that reference specific measurement entities. The ontological distinction here is the namespace (`sdg:iso27001AnnexA`), which allows the same measurement entity to satisfy multiple regulatory frameworks without duplication of the underlying technical definition.

The axiom is expressed as:
**Class: {X} SubClassOf: cco:DirectiveICE, sdg:iso27001AnnexA some {Y}**

Here, {X} represents the ISO Annex A control, and {Y} represents the measurement entity. This structure facilitates a unified compliance posture where a single control (e.g., encryption) can satisfy both a PCI DSS requirement and an ISO 27001 control objective simultaneously.

### 4.4.2 Harmonizing Control Objectives

The alignment of ISO 27001 Annex A controls involves mapping the control's objective to the most appropriate technical measurement. For instance, Control A.10.1.1 (Cryptography) maps effectively to the same encryption measurement used for PCI DSS. This harmonization reduces audit fatigue by presenting a single source of truth for technical implementation status.

## 4.5 Cross-Reference Analysis and Audit Implications

### 4.5.1 Convergence of Frameworks

By populating the relational schemas defined in Sections 4.2, 4.3, and 4.4, an organization can perform a cross-reference analysis to identify overlapping controls. For example, `meas_enc_aes256` is referenced by both `pci_req_02_2_3` and `iso_ctrl_a_10_1_1`. This convergence indicates that a failure in the encryption configuration constitutes a simultaneous violation of both PCI DSS and ISO 27001 standards.

### 4.5.2 Evidence Verification Protocol

Auditors are required to verify the `y` column in the directive tables against the actual system configuration. The verification protocol is as follows:
1.  Select a directive from `t_pci_dss_requirement` or `t_iso27001_annexa_subclass`.
2.  Retrieve the associated measurement ID (`y`).
3.  Locate the corresponding entry in `t_measurement_basic` to confirm the definition.
4.  Inspect the target system to validate that the state described in `t_measurement_basic.x` is active and correctly configured.

### 4.5.3 Gap Identification

If a specific directive in the PCI DSS or ISO 27001 tables cannot be mapped to an entry in `t_measurement_basic`, a compliance gap is identified. This gap indicates that the organization has defined a regulatory requirement but has not established a corresponding technical measurement to verify its implementation. Conversely, if a measurement exists but is not referenced by any directive, it may represent "shelf-ware"—technical controls implemented without a clear regulatory driver.
