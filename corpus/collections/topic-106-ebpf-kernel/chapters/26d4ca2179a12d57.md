# Chapter 7: Harmonization of Security Directives and Descriptive Metrics

This chapter delineates the formal ontological structures required to map prescriptive security directives to their constituent descriptive entities. It provides a rigorous examination of how regulatory frameworks, specifically the Payment Card Industry Data Security Standard (PCI DSS) and ISO/IEC 27001, utilize descriptive information content entities to define control objectives. The text establishes the relational dependencies between high-level compliance mandates and the granular measurements or definitions they operationalize, ensuring data integrity across cross-framework compliance audits.

## 7.1 Descriptive Information Content Entities

The foundational unit of compliance ontology is the Descriptive Information Content Entity (ICE). Within the Common Core Ontologies (CCO) framework, this entity represents a standalone piece of information that describes a state of affairs, a measurement, or a definition without necessarily prescribing an action. In the context of security governance, these entities function as the "ground truth" variables against which directives are assessed.

Formally, we define this concept via the axiom: *{X} is a descriptive information content entity*. This classification ensures that the entity is recognized as a distinct informational artifact, separate from the directives that may reference it. These entities are immutable in the context of a specific audit cycle and serve as the primary keys for linking various regulatory requirements to a single source of truth.

**7.1.1 Role in Governance Frameworks**

Descriptive ICEs are critical for eliminating redundancy in multi-framework environments. For instance, the concept of "Strong Cryptography" may be defined identically across PCI DSS and ISO 27001. By modeling "Strong Cryptography" as a `measurement_basic` entity, the governance framework avoids maintaining duplicate definitions. Instead, both frameworks reference the same descriptive entity ID.

The relational schema for this axiom is designed to store these unique definitions. The primary key (`id`) serves as the immutable reference, while the `x` slot contains the textual or URI-based definition of the descriptive entity.

**Table 7.1: Registry of Descriptive Information Content Entities**

| id | x |
| :--- | :--- |
| meas_basic_001 | Wireless Access Point Configuration Standard |
| meas_basic_002 | Audit Log Retention Policy (12 Months) |
| meas_basic_003 | Unique User Identification Credential |
| meas_basic_004 | Cryptographic Key Management Lifecycle |

*Table 7.1 enumerates the foundational descriptive entities (`t_measurement_basic`). The `id` column provides the system-wide unique identifier, while `x` represents the formal definition or name of the measurement standard. These rows act as the referential integrity anchor for all subsequent directive mappings.*

## 7.2 PCI DSS Requirement Directives

The Payment Card Industry Data Security Standard (PCI DSS) operates through a series of prescriptive requirements. In our ontology, these are modeled as subclasses of Directive ICE. A Directive ICE is an informational entity that prescribes a specific action or state. The specific relationship between a PCI DSS requirement and a descriptive entity is defined by the axiom: *{X} is something that pci dss requirement {Y}*.

This structure implies that a specific PCI DSS requirement (X) necessarily entails the existence or implementation of a specific descriptive entity (Y). The requirement acts as the container for the compliance mandate, while the descriptive entity provides the substantive definition of what must be achieved. For example, a PCI DSS requirement regarding "Logging" is not merely a label; it is a directive that formally references the "Audit Log Retention Policy" descriptive entity defined in Section 7.1.

**7.2.1 Relational Mapping and Constraints**

The relational schema for PCI DSS requirements enforces a foreign key constraint to the `t_measurement_basic` table. This is a critical design feature: it ensures that a requirement cannot exist in the system unless it points to a valid, defined measurement. This prevents "orphan" requirements—compliance mandates that lack a clear, testable definition.

The schema `t_pci_dss_requirement` includes the `id` of the requirement, the `x` slot representing the specific requirement text (e.g., "Requirement 10.7"), and the `y` slot, which is the foreign key pointing to the relevant descriptive entity.

**Table 7.2: PCI DSS Directive Mappings**

| id | x | y |
| :--- | :--- | :--- |
| pci_req_001 | PCI DSS Requirement 1.2.3 (Wireless) | meas_basic_001 |
| pci_req_002 | PCI DSS Requirement 10.7 (Retention) | meas_basic_002 |
| pci_req_003 | PCI DSS Requirement 8.2.1 (Unique ID) | meas_basic_003 |
| pci_req_004 | PCI DSS Requirement 3.5.2 (Key Mgmt) | meas_basic_004 |
| pci_req_005 | PCI DSS Requirement 9.6.1 (Destruction) | meas_basic_005 |

*Table 7.2 illustrates the `t_pci_dss_requirement` structure. The `x` column identifies the specific regulatory clause, while the `y` column establishes the mandatory link to the descriptive entities listed in Table 7.1. For instance, `pci_req_002` maps Requirement 10.7 to the "Audit Log Retention Policy" entity, formally encoding the compliance logic.*

## 7.3 ISO 27001 Annex A Subclasses

Similar to PCI DSS, the ISO/IEC 27001 standard utilizes Annex A as a comprehensive set of control objectives. To harmonize this with the PCI DSS ontology, ISO controls are modeled as Directive ICEs that reference the same underlying descriptive entities. The governing axiom is: *{X} is something that iso27001 annex a {Y}*.

This approach allows for a unified compliance view. An organization implementing a control for "Unique User Identification" does not need to implement separate controls for PCI DSS 8.2.1 and ISO 27001 A.9.2.1. Instead, they implement the single descriptive entity (`meas_basic_003`). Both the PCI DSS directive and the ISO 27001 directive point to this same implementation evidence.

**7.3.1 Cross-Framework Harmonization**

The schema `t_iso27001_annexa_subclass` mirrors the structure of the PCI DSS table, utilizing the same foreign key constraint to `t_measurement_basic`. This deterministic projection ensures that the ontology remains normalized. The complexity of managing two distinct standards is reduced to managing one set of descriptive entities and two sets of mappings (directives).

In audit scenarios, this structure facilitates efficient evidence collection. An auditor querying the `y` foreign key can instantly retrieve all directives (both PCI and ISO) that depend on a specific piece of evidence. This reduces audit fatigue and minimizes the risk of conflicting interpretations across standards.
