# Chapter 4: Formal Ontology of Compliance Directives and Measurement Entities

## 4.1 Scope and Preamble

This chapter delineates the structural mapping of regulatory compliance requirements to formal ontology axioms, specifically focusing on the intersection of the Payment Card Industry Data Security Standard (PCI DSS) and the ISO/IEC 27001 information security management framework. The objective is to provide a deterministic method for representing compliance directives as information content entities and linking them to specific descriptive measurements. This formalization enables automated reasoning over control sets, facilitates gap analysis between distinct regulatory regimes, and establishes a rigorous schema for audit evidence generation. The following sections define the core ontological classes—Measurement Basic, PCI DSS Requirement, and ISO 27001 Annex A Subclass—detailing their logical constraints and relational dependencies.

## 4.2 Measurement Basic Entities

### 4.2.1 Definition and Axiomatic Structure

At the foundational layer of the compliance ontology lies the concept of the Measurement Basic. Formally defined by the axiom `measurement_basic`, this entity represents a Descriptive Information Content Entity (ICE). In the context of the Common Core Ontologies (CCO), a Descriptive ICE is an entity that is about some other entity, functioning as a data container or observation that describes a state of affairs within a system.

The verbalization of this axiom asserts that "{X} is a descriptive information content entity." Here, {X} represents the specific class of measurement being observed. Unlike directives, which prescribe action, measurement entities describe the qualitative or quantitative attributes of a system configuration or process. These entities serve as the dependent variables in compliance equations; they are the objects against which audit assertions are evaluated.

### 4.2.2 Relational Schema and Implementation

To implement this axiom within a relational database management system (RDBMS), the following schema is utilized. The table `t_measurement_basic` acts as a lookup registry for all valid descriptive metrics utilized across the governance framework.

The primary key `id` serves as the unique identifier for the measurement class, while column `x` holds the human-readable or machine-semantic label for the measurement entity. Because this table represents the "leaf nodes" of descriptive data, it possesses no foreign key dependencies within this specific subset of the ontology, though it is referenced by higher-level directive tables.

**Table 4.1: Measurement Basic Entity Registry**

| id | x |
| :--- | :--- |
| mb_001 | WirelessEncryptionProtocol |
| mb_002 | CardholderDataStorageScope |
| mb_003 | SystemComponentInventory |
| mb_004 | AccessControlMatrix |
| mb_005 | CryptographicKeyRotationPeriod |
| mb_006 | AuditLogRetentionDuration |

*Table 4.1 enumerates the instances of the `measurement_basic` axiom. These entries represent the specific descriptive attributes (e.g., `WirelessEncryptionProtocol`) that are subject to audit observation. The `id` column provides the stable reference key used by directive tables to enforce referential integrity.*

### 4.2.3 Application in Audit Evidence

In practice, the `Measurement Basic` entity corresponds to the specific data points extracted during an audit. For instance, when an auditor verifies the configuration of a wireless access point, they are instantiating the `WirelessEncryptionProtocol` entity. The value extracted (e.g., "WPA2-Enterprise") constitutes the data property of that entity. By standardizing these entities, the ontology ensures that disparate control frameworks map to the same underlying evidentiary data, preventing redundancy in data collection and enabling cross-standard harmonization.

## 4.3 PCI DSS Requirement Directives

### 4.3.1 Definition and Axiomatic Structure

The PCI DSS Requirement axiom defines a specific subclass of Directive ICE. A Directive, in ontological terms, is an information content entity that prescribes a specific course of action or mandates a particular state of existence. The `pci_dss_requirement` axiom posits that "{X} is something that pci dss requirement {Y}."

This structure establishes a binary relationship between a Directive Class {X} (the requirement itself, such as "Requirement 1.2.3") and a Measurement Basic Class {Y} (the target state or configuration). The axiom utilizes the object property `sdg:pciDssRequirement` to link the directive to its target measurement. This linkage is critical for automated compliance scanning, as it explicitly defines *what* must be measured to satisfy a specific requirement.

### 4.3.2 Relational Schema and Implementation

The relational projection of this axiom introduces dependencies on the `t_measurement_basic` table. The schema for `t_pci_dss_requirement` enforces that every PCI directive must be associated with a valid measurement entity.

The column `y` functions as a foreign key referencing `t_measurement_basic(id)`. This constraint ensures that no directive can be entered into the system unless it points to a defined, observable metric. The column `x` represents the PCI DSS requirement identifier or class name (e.g., "PCI_DSS_Req_1_2_3").

**Table 4.2: PCI DSS Requirement Mapping**

| id | x | y |
| :--- | :--- | :--- |
| pci_001 | PCI_DSS_Req_1_2_3_Directive | mb_001 |
| pci_002 | PCI_DSS_Req_2_1_1_Directive | mb_003 |
| pci_003 | PCI_DSS_Req_3_1_Directive | mb_002 |
| pci_004 | PCI_DSS_Req_8_2_3_Directive | mb_004 |
| pci_005 | PCI_DSS_Req_3_6_4_Directive | mb_005 |

*Table 4.2 illustrates the implementation of the `pci_dss_requirement` axiom. For example, row `pci_001` links the directive `PCI_DSS_Req_1_2_3_Directive` (which mandates cryptographic protocols for wireless networks) to the measurement entity `mb_001` (`WirelessEncryptionProtocol`). The foreign key constraint on `y` ensures that the directive maps to a valid descriptive entity defined in Table 4.1.*

### 4.3.3 Compliance Logic and Verification

The mapping defined in Table 4.2 facilitates the translation of legalistic requirement text into executable verification logic. Consider `PCI_DSS_Req_3_6_4`, which requires the periodic rotation of cryptographic keys. By mapping this directive to `mb_005` (`CryptographicKeyRotationPeriod`), a compliance engine can query the configuration management database (CMDB) for the age of current keys. If the observed value exceeds the threshold defined in the policy, the directive is marked as non-compliant. This structure transforms static documentation into a dynamic, queryable knowledge graph.

## 4.4 ISO 27001 Annex A Subclasses

### 4.4.1 Definition and Axiomatic Structure

The third ontological component addresses the ISO/IEC 27001 standard, specifically the controls listed in Annex A. The `iso27001_annexa_subclass` axiom asserts that "{X} is something that iso27001 annex a {Y}."

Structurally, this mirrors the PCI DSS axiom but operates within the namespace of the ISO 27001 framework. Here, {X} represents the specific Annex A control (e.g., "A.10.1.1"), and {Y} represents the Measurement Basic entity that the control governs. This axiom is essential for organizations seeking Integrated Compliance Management, as it allows for the mapping of ISO controls to the same underlying data artifacts used for PCI DSS, thereby reducing audit fatigue.

### 4.4.2 Relational Schema and Implementation

The schema for `t_iso27001_annexa_subclass` is structurally identical to the PCI DSS table, differing only in the semantic content of the `x` column (the ISO control identifiers) and the specific `y` mappings to measurement entities.

The referential integrity is maintained via the foreign key `y`, which must correspond to an existing `id` in `t_measurement_basic`. This design enforces the principle that ISO controls, like PCI requirements, are fundamentally directives that describe specific observable states of the information system.

**Table 4.3: ISO 27001 Annex A Control Mapping**

| id | x | y |
| :--- | :--- | :--- |
| iso_001 | ISO_A_9_1_1_AccessControlPolicy_Directive | mb_004 |
| iso_002 | ISO_A_10_1_1_Cryptography_Directive | mb_005 |
| iso_003 | ISO_A_12_3_1_Backup_Directive | mb_002 |
| iso_004 | ISO_A_12_4_1_LogLogging_Directive | mb_006 |
| iso_005 | ISO_A_9_2_1_AccessControl_Directive | mb_003 |

*Table 4.3 details the instantiation of the `iso27001_annexa_subclass` axiom. Row `iso_004` maps the logging directive (`ISO_A_12_4_1_LogLogging_Directive`) to the measurement entity `mb_006` (`AuditLogRetentionDuration`). This alignment ensures that the retention of logs is measured consistently regardless of whether the audit is driven by PCI DSS requirements or ISO 27001 controls.*

### 4.4.5 Cross-Framework Analysis

A significant advantage of this ontological structure is the ability to perform intersection analysis between Table 4.2 and Table 4.3. By querying the `y` column in both tables, analysts can identify "multi-hit" measurements—entities that are targeted by both PCI DSS and ISO 27001.

For example, `mb_005` (`CryptographicKeyRotationPeriod`) is referenced by `pci_004` (PCI DSS Req 3.6.4) and `iso_002` (ISO A.10.1.1). This indicates a convergence of requirements. An organization can satisfy both standards by implementing a single control procedure regarding key rotation. The ontology explicitly highlights these overlaps, allowing governance teams to optimize their control environment and eliminate redundant testing activities.
