# Chapter 4: Event-Observation Constraints for Descriptive Entities

## 4.1 Scope and Preamble

This chapter establishes the binding ontological constraints for Information Content Entities (ICE) within the context of process-oriented governance frameworks. It delineates the specific requirements for descriptive entities—specifically Claims and Metrics—that must be anchored to temporal processes to satisfy auditability and traceability mandates. The definitions provided herein are derived from the core axioms of the Observability Ontology and are intended for use by system architects, compliance officers, and data stewards implementing high-assurance logging and telemetry systems. All entities referenced must satisfy the structural necessity of being a subclass of `cco:DescriptiveICE` and maintain a valid `sdg:observedAt` relation to a process instance (`bfo:0000015`).

## KEY TO ONTOLOGY & OTHER IMPEDIMENTA

ICE = Information Content Entity

BFO = Basic Formal Ontology

SDG = Spatial/Temporal Data and Governance

CCO = Common Core Ontologies

OBE = Observed By Event (Constraint Family)

PROCESS = bfo:0000015 (Occurrent)

## 4.2 Claims Observed by Events

### 4.2.1 Ontological Definition

A Claim, within the context of this framework, is defined as a specific subclass of `cco:DescriptiveICE`. It is not a mere data point but a declarative statement regarding the state, disposition, or outcome of a system activity. The primary axiom governing this entity is `claim_observed_by_event`, which asserts that for a Claim to possess validity within the audit record, it must be observed at a specific Process.

The Manchester syntax for this axiom is expressed as:
`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`

This structure implies that the Claim {X} cannot exist in a vacuum; it is temporally bound to an occurrent. The `bfo:0000015` (Process) acts as the validation anchor. Without this anchor, the Claim is relegated to the status of unverified assertion, failing the compliance criteria for "evidence-anchored" reporting.

### 4.2.2 Implementation in Audit Trails

In practical terms, the implementation of Claims Observed by Events requires that any assertion logged by the system be associated with a traceable transaction ID or process handle. For instance, an "Access Granted" assertion is only valid if it is observed at the process of "Authentication Attempt."

When constructing the relational schema for these entities, the primary key (`id`) serves as the unique identifier for the specific claim instance, while the `x` column denotes the ontological class of the claim being instantiated. This separation allows for polymorphic querying of the audit log while maintaining strict type adherence to the ontology.

To verify compliance with this axiom, auditors must confirm that for every entry in Table 4.1, a corresponding process record exists in the process execution logs. The `x` value must map back to a defined Class within the ontology that is a recognized subclass of `cco:DescriptiveICE`. For example, the `UserAuthenticationAssertion` (id: LOG-2024-Q3-001) must be traceable to a specific login event process. Failure to provide this link constitutes a violation of the `observedAt` constraint.

## 4.3 Metrics Observed by Events

### 4.3.1 Ontological Definition

While Claims provide qualitative assertions about system state, Metrics provide quantitative measurements. A Metric is similarly defined as a subclass of `cco:DescriptiveICE` and is governed by the `metric_observed_by_event` axiom. Like Claims, Metrics are not standalone numbers; they are measurements that are *observed at* a Process.

The Manchester syntax is identical in structure to the Claim axiom, reflecting the shared inheritance of `cco:DescriptiveICE`:
`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`

The distinction lies in the semantic nature of {X}. In this context, {X} refers to classes representing quantifiable data points, such as latency, throughput, or error rates. The `bfo:0000015` Process here represents the measurement interval or the specific operational event during which the telemetry was captured.

### 4.3.2 Telemetry and Performance Reporting

Under regulatory frameworks requiring high-fidelity performance monitoring, it is insufficient to report aggregate statistics without provenance. The `metric_observed_by_event` axiom enforces that every reported metric value must be attributable to a specific observation window or triggering event.

The relational projection for this axiom mirrors that of the Claim, utilizing `id` for the unique observation record and `x` for the metric class. This facilitates the automated generation of performance reports that can drill down from a high-level metric class to specific process instances.

### 4.3.3 Data Integrity and Lineage

The integrity of the data presented in Table 4.2 is contingent upon the `sdg:observedAt` relation. For the `CPUUtilizationPercentage` (id: TEL-SYS-A-991) to be accepted as valid evidence, the system must record the exact timestamp and process ID (the `bfo:0000015` occurrent) during which the sampling occurred. This prevents the injection of "orphaned" metrics—data points that appear valid but lack a causal connection to the system's operational history.
