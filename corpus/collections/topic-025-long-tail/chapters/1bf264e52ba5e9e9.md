# Chapter 7: Event-Driven Descriptive Entities in Compliance Auditing

## 7.1 Scope and Preamble

This chapter delineates the structural requirements for mapping descriptive information content entities (ICE) to temporal processes within a governance framework. In the context of high-assurance audit reporting and regulatory compliance, it is insufficient to merely record data points; rather, the ontological status of these data points must be rigorously defined relative to the events that generated them. The following sections introduce two fundamental axioms—`claim_observed_by_event` and `metric_observed_by_event`—which govern the semantic relationship between descriptive classes and the spatiotemporal boundaries of observational processes. Adherence to these axioms ensures that all assertions and measurements recorded in the system are traceable to specific `bfo:0000015` (process) instances, thereby satisfying the evidentiary standards required for forensic reconstruction and regulatory review.

## 7.2 The Ontology of Claims (Axiom: claim_observed_by_event)

### 7.2.1 Theoretical Underpinnings

The first ontological construct addressed in this framework is the Claim, formalized under the axiom template `claim_observed_by_event`. In Manchester syntax, this axiom is expressed as:

`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`

Verbalized, this dictates that any entity `X` classified as a Claim is a subclass of `cco:DescriptiveICE` (Descriptive Information Content Entity) and must be `observedAt` some instance of `bfo:0000015` (a process). This distinction is critical for auditability. A "Claim" in this context is not merely a string of text or a numerical label; it is a qualitatively asserted proposition about the state of a system or process. By anchoring the Claim to a process via the `observedAt` object property, the ontology prevents the existence of "orphan" assertions—claims that exist without a provenance context. This structure allows auditors to query not just *what* was claimed, but *when* and *during which specific operational process* that claim held validity.

### 7.2.2 Implementation Schema and Relational Projection

To implement this axiom within a relational database infrastructure, the class structure is projected into a simplified schema. The table `t_claim_observed_by_event` serves as the registry for these entities. The primary key is the unique identifier (`id`), while the column `x` denotes the specific Class of the claim being instantiated.

The schema definition is provided below:

```sql
CREATE TABLE t_claim_observed_by_event (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DescriptiveICE"],"family":"07_long_tail","is_complex":true,"template_id":"claim_observed_by_event"}'
```

In this structure, the `x` column functions as a type discriminator, identifying whether the row represents a specific type of claim, such as a `RegulatoryViolationAssertion` or a `PolicyComplianceDeclaration`. The constraint that `X` is a `SubClassOf` `cco:DescriptiveICE` is enforced logically by the application layer, ensuring that only valid descriptive classes are entered into this table.

## 7.3 The Ontology of Metrics (Axiom: metric_observed_by_event)

### 7.3.1 Quantitative Descriptive Entities

While claims provide qualitative assertions, governance frameworks equally require quantitative rigor. The second axiom, `metric_observed_by_event`, addresses this requirement. Structurally, it mirrors the claim axiom in Manchester syntax:

`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`

However, the semantic interpretation of `X` differs significantly. Here, `X` represents a Metric—a quantitative information content entity that describes a measurable property of a system. Like claims, metrics are `DescriptiveICE` entities, meaning they are about the system rather than physical parts of it. The `observedAt` relation to `bfo:0000015` (a process) ensures that the metric is associated with the specific temporal interval during which the measurement was taken. For example, a `ServerLatencyValue` is meaningless without the temporal context of the `ServerMonitoringProcess` that produced it.

### 7.3.2 Implementation Schema and Relational Projection

The relational projection for metrics results in the table `t_metric_observed_by_event`. This schema is structurally identical to the claims table to maintain a consistent interface for querying descriptive entities, but it is populated exclusively with classes representing quantitative data points.

The schema definition is provided below:

```sql
CREATE TABLE t_metric_observed_by_event (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DescriptiveICE"],"family":"07_long_tail","is_complex":true,"template_id":"metric_observed_by_event"}'
```

The `x` column in this context captures the specific nature of the metric, such as `ThroughputCount` or `ErrorRateRatio`. This classification allows downstream reporting systems to filter metrics by their semantic type (e.g., aggregating all `LatencyMeasurement` instances regardless of the process that observed them).

## 7.4 Summary of Ontological Compliance

The rigorous application of the `claim_observed_by_event` and `metric_observed_by_event` axioms provides a dual-layered approach to evidence management. By enforcing that all descriptive entities—whether qualitative claims or quantitative metrics—are subclasses of `cco:DescriptiveICE` and are observed at a specific `bfo:0000015` process, the framework eliminates ambiguity in audit logs.
