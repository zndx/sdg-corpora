# Chapter 4: Event-Observation Frameworks for Audit Evidence

## 4.1 Scope and Preamble

This chapter establishes the technical specifications for the ontological grounding of audit evidence within the enterprise data warehouse. It is part of the "Semantic Audit Trail Project: Translating Regulatory Compliance into Machine-Readable Provenance," conducted by the Governance Architecture Unit. The project's main objective is to ensure that every descriptive assertion utilized in financial reporting and compliance monitoring is formally anchored to a specific temporal process, thereby eliminating ambiguity regarding the time and context of observation. The following sections detail the implementation of two primary axiom templates: the Claim Observation and the Metric Observation. These constructs are mandatory for all new data ingestion pipelines effective as of the current fiscal quarter.

## 4.2 Key to Ontological Impedimenta

To ensure precise interpretation of the schema definitions and logical constraints presented herein, the following key defines the abbreviations and namespace references utilized throughout this document.

BFO = Basic Formal Ontology (Upper-level ontology)
CCO = Common Core Ontologies (Information Artifact ontology)
SDG = Semantic Data Governance (Internal namespace)
ICE = Information Content Entity
DES = Descriptive Information Content Entity
OBS = Observed At (Object property linking entity to process)

BFO:0000015 = Process (Occurrent)
CCO:DescriptiveICE = Descriptive Information Content Entity

## 4.3 Claims Observed by Events

### 4.3.1 Conceptual Definition

In the context of auditability, a "Claim" represents a declarative statement regarding the state of an enterprise asset or process at a specific point in time. To satisfy the rigorous demands of external auditors and regulatory bodies, a claim cannot exist as a free-floating text string; it must be formalized as an instance of a `cco:DescriptiveICE`. This formalization ensures that the claim is treated as a distinct information artifact, subject to versioning, access control, and integrity checks.

The critical structural requirement for a valid claim is that it must be `observedAt` a `bfo:0000015` (Process). This object property creates a deterministic link between the static information content (the claim) and the dynamic occurrent (the process or event that generated the evidence). Without this linkage, the claim lacks temporal provenance and is therefore inadmissible under the current compliance framework.

### 4.3.2 Axiomatic Structure

The logical structure of a Claim Observed by Event is defined by the following axiom template:

*   **Template ID:** `claim_observed_by_event`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`
*   **Verbalization:** {X} is a descriptive information content entity that is observed at some process.

This structure dictates that any class designated as {X} must inherit the characteristics of a descriptive entity and possess a mandatory relationship to a process event. The variable {X} represents the specific class of the claim being instantiated (e.g., `UnauthorizedAccessClaim`, `ProtocolDeviationAssertion`).

### 4.3.3 Relational Implementation

The projection of this axiom into the relational schema is managed by the table `t_claim_observed_by_event`. This table serves as the registry for all valid claim classes that conform to the observation constraint. The primary key (`id`) ensures that each claim class definition is unique and immutable within the system. The foreign key structure is implicit in the logic; while the table itself defines the valid classes, the runtime enforcement of the `observedAt` relationship requires a join with the process event logs.

The following table provides the technical specification for the currently registered claim classes.

### 4.3.4 Usage Example

Consider an audit scenario where a system administrator observes a failed login attempt. The observation is not merely a log entry; it is an instance of the class `UnauthorizedAccessClaim`. According to the axiom, this claim is a `cco:DescriptiveICE`. The `observedAt` property links this specific claim to the process instance `LoginAttempt-2023-10-27-14:30`. This structure allows an auditor to query "Show me all `UnauthorizedAccessClaims` observed at `LoginAttempt` processes," thereby retrieving a complete, temporally anchored evidence set.

## 4.4 Metrics Observed by Events

### 4.4.1 Conceptual Definition

While claims provide qualitative assertions regarding system state, Metrics provide quantitative measurements. In high-frequency trading environments, real-time monitoring systems, and resource utilization tracking, the volume of data requires a distinct yet ontologically similar approach. A Metric, in this framework, is defined as a specific type of `cco:DescriptiveICE` that encodes a numerical value or measurement vector.

Similar to claims, a Metric is devoid of context without a temporal anchor. The `metric_observed_by_event` axiom enforces the requirement that every metric class must be `observedAt` a `bfo:0000015` (Process). This distinguishes a "raw number" from a "measurement." A raw number (e.g., "45") is data; a measurement (e.g., "45 degrees Celsius observed at SensorReading-882") is an information content entity grounded in reality. This distinction is vital for root cause analysis and forensic reconstruction of system failures.

### 4.4.2 Axiomatic Structure

The logical structure for a Metric Observed by Event is defined by the following axiom template:

*   **Template ID:** `metric_observed_by_event`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:observedAt some bfo:0000015`
*   **Verbalization:** {X} is a descriptive information content entity that is observed at some process.

Although the syntactic structure mirrors that of the claim, the semantic interpretation of {X} is constrained to quantitative classes (e.g., `LatencyMeasurement`, `TemperatureReading`, `TransactionVolumeCount`).

### 4.4.3 Relational Implementation

The relational projection for metric classes is maintained in the `t_metric_observed_by_event` table. This registry enumerates the valid metric classes permissible within the reporting infrastructure. The schema enforces that every metric class entry is a subclass of the descriptive information content entity, ensuring compatibility with text-mining and semantic search tools across the data lake.

The table below details the specific metric classes currently sanctioned for use in production reporting pipelines.

**Table 4.2: Metric Class Registry (Axiom: metric_observed_by_event)**

| id | x |
| :--- | :--- |
| `METRIC-REG-001` | `CPUUtilizationPercentage` |
| `METRIC-REG-002` | `MemoryLeakRate` |
| `METRIC-REG-003` | `NetworkLatencyMs` |
| `METRIC-REG-004` | `DiskIOPSCount` |
| `METRIC-REG-005` | `TransactionThroughputPerSec` |

*Table 4.2 Notes:*
1.  **id**: The unique identifier for the metric class definition.
2.  **x**: The Class name (X) representing the quantitative metric.
3.  **Scale and Units**: While the ontology defines the class, unit definitions (e.g., milliseconds, percentage) are handled via separate attribute properties attached to the class instances, not defined in this axiom table.

### 4.4.4 Usage Example

During a stress test of the primary order management system, a monitoring tool records a spike in processing time. This recording is instantiated as `NetworkLatencyMs`. By virtue of the `metric_observed_by_event` axiom, this instance is linked to the process `StressTestExecution-Oct2023`. If the latency exceeds the defined threshold, the system generates an alert. Because the metric is ontologically anchored to the process, post-incident analysis can correlate the `NetworkLatencyMs` directly with other claims observed during the same process, such as `DatabaseTimeoutClaim`, providing a comprehensive view of the failure mode.

## 4.5 Compliance and Verification

All data models submitted for approval to the Architecture Review Board (ARB) must demonstrate compliance with the axioms described in Sections 4.3 and 4.4. Verification scripts will be run against the proposed schema to ensure that:
1.  Every class intended to store observational data is explicitly listed in either `t_claim_observed_by_event` or `t_metric_observed_by_event`.
2.  No class exists in the ontology that is a subclass of `cco:DescriptiveICE` without the `sdg:observedAt` restriction to `bfo:0000015`.

Failure to meet these criteria will result in the rejection of the deployment ticket. The evidence-anchored prose of this chapter serves as the authoritative guide for implementing these semantic constraints.
