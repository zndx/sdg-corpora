# Chapter 7: Ontological Projection of Descriptive Entities in Event-Based Auditing

## 7.1 Scope and Preamble

This chapter delineates the procedural and structural requirements for mapping high-level ontology axioms to relational data structures within the context of governance frameworks and audit compliance. It specifically addresses the instantiation of descriptive information content entities (cco:DescriptiveICE) as they are observed during discrete temporal processes (bfo:0000015). The guidelines provided herein ensure that qualitative claims and quantitative metrics are rigorously anchored to the events in which they are generated, maintaining the integrity of the audit trail. All data structures presented are deterministic projections of the underlying OWL ontology, designed to support automated validation and cross-referencing within compliance databases.

## 1. The Observation of Claims

### 1.1 Axiomatic Definition and Context

In the realm of technical auditing and compliance reporting, a "claim" represents a declarative statement regarding the state of a system, process, or entity at a specific point in time. Formally, this concept is defined by the ontology axiom `claim_observed_by_event`. The axiom asserts that any Class {X} designated as a claim is a subclass of `cco:DescriptiveICE` (Descriptive Information Content Entity) and must be `sdg:observedAt` some instance of `bfo:0000015` (a Process or Event).

This structural dependency implies that a claim cannot exist in a vacuum; it is ontologically bound to the event during which the observation was made. For instance, a claim regarding "System Integrity" is only valid when anchored to a specific "Security Audit Event." This binding prevents the detachment of assertions from their evidentiary basis, a critical requirement for high-assurance environments such as financial reporting or safety-critical system monitoring.

### 1.2 Implementation in Relational Schemas

To operationalize this axiom within a relational database management system (RDBMS), the class structure is projected into a table schema. The table `t_claim_observed_by_event` serves as the registry for these claim classes. The primary key, `id`, provides a unique identifier for the specific claim class definition, while the column `x` denotes the Class name itself.

The schema enforces the constraint that every entry in this table represents a specific type of claim—a subclass of the generic descriptive entity—that is authorized for use in event logging. The following table illustrates the instantiation of specific claim classes derived from the ontology. Note that the `x` values correspond to the specific Class names that would be defined in the ontology, while the `id` serves as the surrogate key used in the relational system.

### 1.3 Procedural Application

When an auditor or an automated monitoring system generates a record, the content of that record must be classified using one of the registered classes found in Table 1.1. For example, if an observation is made during a "Quarterly Review" (the Event) that a specific data retention policy was not followed, the record created is an instance of the `ProcessAdherenceStatement` class. The system validates this entry by ensuring `ProcessAdherenceStatement` exists in the `t_claim_observed_by_event` table, thereby enforcing the ontology's constraints at the data layer.

This rigorous classification allows downstream reporting systems to filter and aggregate claims based on their semantic type. A compliance officer may query all instances of `RegulatoryComplianceClaim` across multiple events to generate a comprehensive status report, confident that every returned record is ontologically consistent with the definition of a descriptive information content entity observed at an event.

## 2. The Observation of Metrics

### 2.1 Axiomatic Definition and Context

While claims provide qualitative assertions, metrics provide the quantitative backbone of technical documentation. The axiom `metric_observed_by_event` defines the structural requirements for these measurements. Similar to claims, a metric is defined as a Class {X} that is a subclass of `cco:DescriptiveICE`. However, the semantic distinction lies in the nature of the content; metrics represent quantifiable data points (e.g., latency, temperature, throughput) that are `sdg:observedAt` a specific event or process (bfo:0000015).

The observation of a metric is a distinct event in itself, often captured by sensors or logging instruments. The ontology mandates that the metric entity is not merely a number but a descriptive information content entity that encapsulates the measurement, its units, and its temporal context. This distinction ensures that raw data is elevated to "information" by virtue of being anchored to the process that generated it.

### 2.2 Implementation in Relational Schemas

The relational projection for metrics is encapsulated in the table `t_metric_observed_by_event`. This schema mirrors the structure of the claims registry but is populated with classes specific to quantitative measurement. The column `x` holds the Class name of the metric, which must adhere to the axiom stating it is a descriptive entity observed at an event.

The following table presents a registry of metric classes. These entries represent the valid categories of measurements that can be recorded within the system. By restricting data entry to these predefined classes, the framework prevents semantic drift—ensuring, for example, that a temperature reading is not erroneously classified as a financial metric.

**Table 2.1: Registry of Metric Classes (t_metric_observed_by_event)**

| id | x |
|---|---|
| MET-PER-001 | NetworkLatencyMetric |
| MET-ENG-002 | ThermalOutputMetric |
| MET-FIN-003 | QuarterlyYieldMetric |
| MET-ENV-004 | ParticulateMatterMetric |
| MET-SYS-005 | MemoryUtilizationMetric |

*Table 2.1 Notes:*
*   **Primary Key:** `id`
*   **Column `x`:** Represents the specific Ontology Class {X} satisfying the axiom `SubClassOf: cco:DescriptiveICE`.
*   **Usage:** These classes categorize quantitative data points captured during process execution (bfo:0000015).

### 2.3 Procedural Application and Compliance

In practice, the `t_metric_observed_by_event` table acts as a validation lookup for telemetry data ingestion pipelines. Consider a continuous integration (CI) pipeline (the Event) that executes a build process. During this execution, the system measures the time taken to run the test suite. This observation is recorded as an instance of the `NetworkLatencyMetric` or `ProcessingTimeMetric` (if defined). The ingestion engine verifies that the class type provided in the data stream exists in Table 2.1.

Furthermore, this structure facilitates complex querying required for audit compliance. An investigator may request all "Thermal Output" metrics associated with "Manufacturing Process 4B." Because the metric is ontologically linked to the event via the `observedAt` property, the system can efficiently join the event logs with the metric observations. The use of the `cco:DescriptiveICE` superclass ensures that both claims and metrics can be queried together as "information entities" when a comprehensive view of the event is required, while the subclass distinction in the tables allows for type-specific analysis.

## 3. Consolidated Reporting and Evidence Anchoring

### 3.1 Cross-Referencing Entities

The dual structure of claims and metrics provides a robust framework for evidence anchoring. In audit reports and compliance handbooks, it is often necessary to juxtapose qualitative assertions with quantitative evidence. For example, a `StructuralSafetyAssertion` (Claim) might be supported by a `ThermalOutputMetric` (Metric) recorded during the same stress test event.

The ontology allows for this relationship because both entities share the same parent class (`cco:DescriptiveICE`) and the same existential restriction (`sdg:observedAt some bfo:0000015`). In the relational layer, while `t_claim_observed_by_event` and `t_metric_observed_by_event` store the class definitions, the actual observation instances would be stored in instance tables that reference these class definitions via foreign keys. This normalization ensures data integrity and adheres to the deterministic schema requirements of high-quality technical documentation.

### 3.2 Governance and Maintenance

The maintenance of the tables provided in Sections 1.2 and 2.2 is a governance function. The addition of a new class, such as `CarbonFootprintMetric`, requires a formal update to the ontology and a subsequent insertion into the `t_metric_observed_by_event` table. This process ensures that all descriptive entities tracked by the system are formally defined and semantically consistent.

Governance frameworks must mandate that no ad-hoc class names be introduced into the `x` column. The values must correspond to the controlled vocabulary defined in the ontology axioms. Deviations from this practice result in "orphaned" data—records that cannot be semantically interpreted or validated against the core model, thereby compromising the auditability of the system.
