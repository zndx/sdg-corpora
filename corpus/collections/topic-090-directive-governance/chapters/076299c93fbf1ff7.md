# Kernel Syscall Audit Modeling

This chapter presents two ontological axioms that classify system calls as designative information content entities situated at explicit security tiers and subject to audit processes. The axioms are realized through four tables that support primary-key identification and foreign-key navigation across syscall instances, tiers, and audit events.

## 1 Scope and Table Overview

The relational representation uses the exact column structures projected from the axioms. Four tables are supplied: two directly embody the supplied axioms while two auxiliary tables supply the entity references required for foreign-key joins. All column values are drawn from kernel audit practice.

### 1.1 t_syscall Registry

This table supplies stable identifiers for syscall classes that participate in both axioms. Column `id` is the primary key; column `name` holds the conventional syscall symbol.

| id          | name   |
|-------------|--------|
| sc_001      | open   |
| sc_002      | read   |
| sc_003      | write  |
| sc_004      | mmap   |
| sc_005      | connect|

### 1.2 t_security_tier Registry

This table enumerates the security-tier classes referenced by axiom 1. Column `id` is the primary key.

| id          | name     |
|-------------|----------|
| tier_low    | TierLow  |
| tier_med    | TierMed  |
| tier_high   | TierHigh |

### 1.3 t_syscall_at_security_tier (Axiom 1)

Axiom 1 states that a syscall class is something that at security tier Y. The table therefore records the assignment of each syscall to exactly one tier. Column `id` is the primary key; columns `x` and `y` are foreign keys referencing `t_syscall.id` and `t_security_tier.id` respectively. A reader can answer “which syscalls are protected at TierHigh?” by joining on `y`.

| id          | x      | y         |
|-------------|--------|-----------|
| sat_001     | sc_001 | tier_high |
| sat_002     | sc_002 | tier_med  |
| sat_003     | sc_003 | tier_high |
| sat_004     | sc_004 | tier_low  |
| sat_005     | sc_005 | tier_med  |

### 1.4 t_syscall_audited_by (Axiom 2)

Axiom 2 states that a syscall class is a designative information content entity audited by a process. The table therefore records the audit-process linkage. Column `id` is the primary key; column `x` is a foreign key referencing `t_syscall.id`.

| id          | x      |
|-------------|--------|
| sab_001     | sc_001 |
| sab_002     | sc_002 |
| sab_003     | sc_003 |
| sab_004     | sc_005 |

## 2 Cross-Join Example

Question: return every syscall that is both placed at TierHigh and audited by a process.

Step 1. Select rows from t_syscall_at_security_tier where y = 'tier_high'.  
Result rows: sat_001 (sc_001), sat_003 (sc_003).

Step 2. Join the x values to t_syscall_audited_by on x.  
Only sc_001 appears in both sets.

Joined row:  
syscall = open, tier = TierHigh, audited = true.

The same navigation can be expressed in SQL by two inner joins across the four tables.

```json
{"tables": [{"name": "t_syscall_at_security_tier", "rows": [["sat_001", "sc_001", "tier_high"], ["sat_002", "sc_002", "tier_med"], ["sat_003", "sc_003", "tier_high"], ["sat_004", "sc_004", "tier_low"], ["sat_005", "sc_005", "tier_med"]]}, {"name": "t_syscall_audited_by", "rows": [["sab_001", "sc_001"], ["sab_002", "sc_002"], ["sab_003", "sc_003"], ["sab_004", "sc_005"]]}]}
```
