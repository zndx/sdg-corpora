# Chapter 4: System Call Classification and Audit Compliance in eBPF Architectures

## 4.1 Scope and Preamble

This chapter provides a technical specification for the classification of kernel-level system calls within extended Berkeley Packet Filter (eBPF) security architectures. The content herein defines the ontological relationships between system call interfaces, their assigned security tiers, and their audit status pursuant to the `04_ebpf_kernel` framework. It establishes the mandatory data structures required to map Designative Information Content Entities (ICEs) to security clearances and auditing protocols. The guidelines presented are intended for systems architects, compliance officers, and kernel developers responsible for enforcing governance over interface execution privileges. All mappings must be rigorously validated against the relational schemas provided to ensure consistency with the underlying ontology.

## 4.2 Security Tiering of Kernel Interfaces

### 4.2.1 Ontological Definition of Security Tiers

In the context of kernel governance, the assignment of execution privileges is not merely a configuration parameter but a structural property of the system call itself. Formally, this relationship is defined by the axiom `syscall_at_security_tier`. This axiom asserts that a specific class of system call, denoted as `{X}`, is a subclass of `cco:DesignativeICE` and possesses the object property `sdg:atSecurityTier` with a value of `{Y}`.

The designation `cco:DesignativeICE` indicates that the system call is treated as an information content entity that designates a specific function or capability within the operating system kernel. By subclassing this entity, we acknowledge that the syscall is not merely a functional entry point but a governed entity subject to classification logic. The property `sdg:atSecurityTier` maps this entity to a specific security clearance level (e.g., `Privileged`, `Restricted`, or `Unprivileged`). This mapping ensures that any invocation of `{X}` is automatically constrained by the policy definitions associated with tier `{Y}`.

### 4.2.2 Relational Implementation of Tier Mapping

To operationalize this axiom within a relational database management system (RDBMS), the schema `t_syscall_at_security_tier` is utilized. This table serves as the authoritative registry for linking system call identifiers to their mandated security tiers.

The table structure is defined by the following constraints:
*   **Primary Key (`id`):** A unique identifier for the mapping record.
*   **Entity Reference (`x`):** The specific system call class (the Designative ICE).
*   **Security Tier (`y`):** The security tier class to which the syscall is assigned.

The `NOT NULL` constraint on column `y` ensures that every system call registered in this table must have an explicit security tier assignment. This prevents the existence of "unclassified" or "orphan" interfaces within the governed kernel space.

### 4.2.4 Analysis of Tier Assignments

As evidenced in Table 4.1, the `Syscall_BPF` interface is explicitly mapped to `SecurityTier_Privileged`. This classification is consistent with the capability of eBPF to load unverified bytecode into the kernel, a process that necessitates the highest level of scrutiny. Similarly, `Syscall_Mount` is categorized at the Privileged tier due to its ability to alter the filesystem namespace.

Conversely, `Syscall_Read` and `Syscall_Write` are assigned to `SecurityTier_Unprivileged`. This reflects their status as fundamental, non-disruptive operations that are generally safe for invocation by untrusted processes. The `Syscall_Socket` and `Syscall_Unlink` interfaces occupy the intermediate `SecurityTier_Restricted` tier, indicating that while they do not require full root privileges, they are subject to stringent capability checks (e.g., `CAP_NET_RAW` or file ownership verification) before execution is permitted.

## 4.3 Audit Mandates for Designative Entities

### 4.3.1 The AuditedBy Property and Process Tracing

While security tiering restricts the *capability* to invoke a system call, the audit framework governs the *observability* of that invocation. The axiom `syscall_audited_by` formalizes this requirement. It posits that a system call class `{X}` (a subclass of `cco:DesignativeICE`) is subject to the property `sdg:auditedBy`, which references the entity `bfo:0000015`.

In the Basic Formal Ontology (BFO), `bfo:0000015` typically denotes a "process" or a temporal span of occurring. In the context of this compliance framework, it represents the specific audit logging process or the monitoring agent responsible for capturing the execution event. Therefore, any system call classified under this axiom is legally and technically mandated to generate an audit trail upon invocation. This is distinct from mere logging; it implies that the execution event is a dependent participant in the audit process.

### 4.3.2 Relational Implementation of Audit Status

The schema `t_syscall_audited_by` provides the persistence layer for the audit mandate. Unlike the security tier table, this schema does not require a foreign key to the auditor entity itself in the column definition, as the relationship is fixed to `bfo:0000015` by the ontology definition. Instead, the table functions as a registry of entities that are "opted-in" to the auditing process.

The table structure is defined by:
*   **Primary Key (`id`):** A unique identifier for the audit record.
*   **Entity Reference (`x`):** The system call class subject to auditing.

This structure allows for efficient querying of all interfaces that must trigger an audit event, enabling the kernel runtime to quickly determine if a trap into the syscall handler should result in a write to the audit log.

### 4.3.4 Compliance Verification and Governance

The data presented in Table 4.2 highlights the intersection of security governance and operational monitoring. The inclusion of `Syscall_Execve` and `Syscall_Fork` is standard practice for process tracking, ensuring that every new process creation is recorded against a parent Process ID (PID) and user context.

However, the presence of `Syscall_BPF` in this registry is of particular importance for eBPF governance. Because eBPF programs can modify system behavior without modifying kernel source code, the act of loading a program (via `Syscall_BPF`) is a critical control point. By axiomatically defining `Syscall_BPF` as `auditedBy` the audit process, the framework ensures that all program loads, regardless of their security tier, are recorded. This dual-layered protection—where `Syscall_BPF` is both `SecurityTier_Privileged` (Table 4.1) and `AuditedBy` the audit process (Table 4.2)—exemplifies the defense-in-depth strategy mandated by the `04_ebpf_kernel` family.

Furthermore, `Syscall_Connect` is audited to detect unauthorized network egress, while `Syscall_Setuid` and `Syscall_Kill` are monitored to prevent privilege escalation and denial-of-service attacks, respectively. The relational schema ensures that these definitions are machine-readable and can be automatically ingested by policy enforcement points (PEPs) within the infrastructure.
