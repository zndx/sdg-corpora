# Chapter 4: Ontological Classification of Kernel Entities and Audit Compliance

## 4.1 Scope and Preamble

This chapter delineates the formal framework for classifying kernel-level information content entities within a secure operating environment. It establishes the protocols for mapping system calls to specific security tiers and defines the mandatory audit trails required for compliance with governance frameworks. The content herein is intended for system architects, compliance officers, and security engineers who must implement rigorous controls over Information Technology (IT) assets. By adhering to the axioms defined in the underlying ontology, organizations can ensure that designative entities are properly stratified and that all privileged actions are traceable to authorized processes. This document serves as both a technical specification and a compliance handbook, providing the necessary evidence structures to satisfy internal and external regulatory audits.

## 4.2 Security Tier Stratification of System Calls

### 4.2.1 Definition of Designative Information Content Entities

In the context of kernel security management, a Designative Information Content Entity (ICE) refers to any definable unit of information that prescribes a specific behavior or function within the system. Specifically, when we examine system calls (syscalls), we are analyzing named entities that invoke transitions between user space and kernel space. According to the governing ontology, these entities are not merely functional entry points but are distinct classes of information that must be categorized based on their potential impact on system integrity.

The axiom governing this classification asserts that a system call, as a class, is a subclass of `cco:DesignativeICE`. This formalization allows us to treat software functions as objects of governance rather than abstract code constructs. By defining these entities as "Designative," we acknowledge that they serve to designate specific operations—such as file manipulation, process control, or network communication—that require varying degrees of security oversight.

### 4.2.2 The `atSecurityTier` Object Property

To enforce the Principle of Least Privilege, the ontology introduces the object property `sdg:atSecurityTier`. This property maps a specific Designative ICE (the system call) to a specific Security Tier class. The relationship is existential; that is, for a system call to be valid within the framework, it must be associated with at least one security tier. This creates a deterministic linkage where the execution of a syscall is inextricably bound to the security context of the tier at which it operates.

The verbalization of this axiom is critical for audit comprehension: "{X} is something that at security tier {Y}." In practice, this means that if a system call is designated as operating at "Tier 0" (often corresponding to Ring 0 or Supervisor Mode), it is subject to the strictest validation routines. Conversely, a syscall designated for "Tier 2" (User Mode) may have fewer execution barriers but is still logged for non-repudiation purposes.

### 4.2.3 Stratification Logic and Implementation

The implementation of this tier stratification requires a granular analysis of the kernel's syscall table. Each syscall must be evaluated based on its resource access patterns. For instance, syscalls that modify memory management tables or interact directly with hardware peripherals are invariably assigned to the highest security tiers. Syscalls that merely read environmental variables or manage non-critical file descriptors may be assigned to lower tiers.

This classification is not static; it must be reviewed in accordance with the change management protocols outlined in the organization's Information Security Management System (ISMS). Any deviation from the established mapping—such as downgrading a syscall's security tier—must be approved by the Change Advisory Board (CAB) and documented in the next revision of the technical control library.

## 4.3 Audit Mandates and Process Verification

### 4.3.1 The Audit Framework for Designative Entities

While stratification defines *where* an entity operates, the audit framework defines *how* its operation is recorded. Compliance with regulatory standards (such as NIST 800-53 or ISO 27001) requires that privileged designative entities generate immutable logs of their invocation. The ontology formalizes this through the axiom `syscall_audited_by`, which establishes a relationship between the Designative ICE and a specific auditing process.

The verbalization of this axiom is: "{X} is a designative information content entity." While seemingly tautological, in the context of the ontology, this subclassing implies that the entity `X` inherits the property of being `sdg:auditedBy` some `bfo:0000015`. In the Basic Formal Ontology (BFO), `bfo:0000015` denotes a "Process." Therefore, the axiom explicitly states that every system call falling under this classification is causally linked to an audit process. This is not a recommendation but a structural constraint of the system's design.

### 4.3.2 The Role of the Audit Process

The audit process referenced by `bfo:0000015` is an independent, temporal entity that observes the occurrence of the system call. This process is responsible for capturing the context of the invocation: the timestamp, the invoking user ID (UID), the effective group ID (GID), and the arguments passed to the syscall. By binding the syscall to this process at the ontological level, we ensure that "auditability" is a baked-in characteristic of the entity, rather than an external add-on.

This distinction is crucial for forensic investigations. If an entity is not defined as a subclass of `cco:DesignativeICE` with the `auditedBy` restriction, it theoretically exists outside the governance framework. Such "ghost" entities represent a significant compliance risk. Therefore, the registration of any new syscall into the system architecture must include the formal declaration of its audit process handler.

### 4.3.3 Compliance Verification and Evidence Generation

To verify compliance, auditors will query the system runtime to ensure that all syscalls defined in the scope are actively generating logs via the designated audit process. Discrepancies between the ontological definition and the runtime state constitute a finding. For example, if the ontology states that `Syscall_Mount` is audited by `Process_AuditD`, but runtime testing reveals that `Process_AuditD` is not receiving events for `mount`, the system is considered non-compliant.

The verification process involves cross-referencing the relational schema of the ontology with the system logs. The following table enumerates the Designative ICEs that are currently mandated to be under audit surveillance.

| ID | System Call (X) |
| :--- | :--- |
| `ab-001` | `Syscall_BPF` |
| `ab-002` | `Syscall_Mount` |
| `ab-003` | `Syscall_Execve` |
| `ab-004` | `Syscall_Kill` |
| `ab-005` | `Syscall_Setuid` |

**Table 4.2:** Registry of Designative ICEs subject to the `auditedBy` axiom. The `id` serves as the primary key for the audit rule, referencing the specific system call class `X`.

The entries in Table 4.2 represent the high-value targets for system monitoring. `Syscall_Execve`, for instance, is the mechanism by which a process is replaced by a new program. Auditing this syscall is fundamental to detecting process injection attacks or unauthorized software execution. Similarly, `Syscall_Setuid` allows a process to change its user identity; auditing this is essential for tracking privilege escalation attempts. By formally defining these relationships, the organization establishes a clear chain of evidence that can be extracted during a security incident or a regulatory audit.

## 4.4 Integration and Governance

### 4.4.1 Relational Integrity and Cross-Table Joins

The robustness of this framework relies on the relational integrity between the stratification tables and the audit tables. While Table 4.1 defines the security tier, and Table 4.2 defines the audit requirement, the effective governance of the system requires a logical join on the `x` (System Call) column.

For example, a comprehensive security policy would dictate that any syscall assigned to `Tier0_Supervisor` in Table 4.1 *must* appear in Table 4.2. It is logically inconsistent to permit a high-privilege, supervisor-mode operation to exist without an active audit trail. Database administrators and security engineers should implement foreign key constraints or application-level validation to enforce this rule. If a row exists in `t_syscall_at_security_tier` with `y = 'Tier0_Supervisor'`, a corresponding row should exist in `t_syscall_audited_by` for the same `x`.

### 4.4.2 Continuous Monitoring and Automated Enforcement

The static definitions provided in the tables above must be translated into dynamic enforcement rules. Using eBPF (extended Berkeley Packet Filter) programs attached to the kernel tracepoints, the system can automatically enforce the ontology. An eBPF program can be configured to inspect the `atSecurityTier` of an incoming syscall. If the syscall is not designated for the current security context, or if the audit process is not active, the eBPF program can return an error code (e.g., `-EPERM`) effectively blocking the operation.

This automated enforcement closes the loop between the "as-designed" ontology and the "as-implemented" system. It moves the organization from a state of periodic compliance checking to continuous compliance. The technical documentation provided in this chapter should serve as the specification for developing those eBPF control loops.

### 4.4.3 Version Control and Amendment

The ontology and its corresponding relational projections are living artifacts. As the kernel evolves and new syscalls are introduced—such as those supporting new hardware acceleration features or containerization primitives—the tables defined in Sections 4.2 and 4.3 must be updated.

All amendments must follow the strict change management workflow:
1.  **Proposal:** A kernel engineer proposes the addition of a new syscall class.
2.  **Classification:** The security office assigns the `atSecurityTier` value.
3.  **Audit Definition:** The compliance office confirms the `auditedBy` mapping.
4.  **Registration:** The new rows are added to the `t_syscall_at_security_tier` and `t_syscall_audited_by` tables.
5.  **Deployment:** The updated eBPF programs are deployed to the production fleet.

Failure to maintain the synchronization between the running kernel and the documented ontology creates "semantic drift," where the actual system behavior diverges from the documented compliance posture. This drift is a primary cause of audit failures. Therefore, the maintenance of these tables is not merely a data entry task, but a critical control activity for the organization's IT governance framework.
