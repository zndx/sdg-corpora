# Chapter 4: Ontological Formalization of Anomaly Detection and Evidence Correlation

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for describing anomaly detection processes, the generation of outlier claims, and the evidentiary correlations that support audit and compliance findings. The content herein is designed to provide a rigorous, axiomatically grounded approach to defining how descriptive information content entities (ICEs) are derived, correlated, and measured against baselines within a semantic data governance environment. The definitions provided align with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring interoperability across regulatory reporting systems. Each concept is accompanied by a relational schema projection to demonstrate how these axioms are instantiated in a physical data model, preserving referential integrity and auditability.

## 4.2 The Outlier Claim as a Descriptive Information Content Entity

### 4.2.1 Axiomatic Definition

The foundational unit of any anomaly report is the Outlier Claim. Axiomatically, an Outlier Claim is defined as a subclass of `cco:DescriptiveICE` (Descriptive Information Content Entity). In the context of technical documentation and audit trails, a `DescriptiveICE` represents a distinct informational entity that is about some portion of reality—specifically, a portion of reality that deviates from the norm. The Outlier Claim does not merely exist as a data point; it is a generically dependent continuant that asserts the existence of an anomaly.

**Axiom 3 (outlier_claim_basic):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE`
*   **Verbalization:** {X} is a descriptive information content entity.

This axiom serves as the root node for the evidentiary chain. Without the formalization of the claim itself as a descriptive entity, subsequent correlations and detection processes lack a valid semantic anchor. In practice, this entity represents the final output of a detection workflow—the "flag" or "alert" that requires human or automated adjudication.

### 4.2.2 Relational Implementation

The projection of this axiom into a relational schema treats the claim as a distinct record with a unique identifier. The table `t_outlier_claim_basic` enforces the entity's existence as a `DescriptiveICE`. The primary key (`id`) ensures that every specific claim instance is distinct and addressable within the database.

## 4.3 Evidence Correlation with Outlier Claims

### 4.3.1 Axiomatic Definition

For an outlier claim to possess evidentiary weight in a compliance framework, it must be correlated with specific data artifacts or observations. This relationship is formalized through the `evidence_correlated_with` axiom. Here, the subject (X) represents an evidentiary artifact, which is itself a type of `DescriptiveICE`. The object (Y) is the Outlier Claim defined in the previous section.

**Axiom 1 (evidence_correlated_with):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:evidenceCorrelatedWith some {Y:Class}`
*   **Verbalization:** {X} is something that evidence correlated with {Y}

This axiom asserts that evidence is not merely associated with a claim but is intrinsically correlated with it. The use of the `some` (existential) restriction in the Manchester syntax indicates that for an entity to be classified as valid evidence in this system, it *must* have at least one correlation to a recognized outlier claim. This structure prevents "orphaned" data from being treated as actionable evidence without a defined claim context.

### 4.3.2 Relational Implementation

The relational schema for `t_evidence_correlated_with` enforces a foreign key constraint linking the evidence to the claim. The column `y` references the primary key of `t_outlier_claim_basic`. This ensures that evidence cannot be entered into the system unless it is attached to a valid, pre-existing claim. This referential integrity is critical for audit trails, as it guarantees that every piece of evidence supports a specific assertion.

**Table 4.2: Evidence Correlation Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `EV_CORR_100` | `ServerLog_Entry_884` | `OCL_2023_001` |
| `EV_CORR_101` | `UserSession_Trace_992` | `OCL_2023_002` |

| `EV_CORR_103` | `NetworkFlow_Log_221` | `OCL_2023_004` |
| `EV_CORR_104` | `WarehouseManifest_771` | `OCL_2023_003` |

*Table 4.2 demonstrates the `evidence_correlated_with` axiom. The column `x` denotes the specific evidence class (e.g., a specific server log entry), while `y` contains the identifier of the outlier claim it supports. For instance, both `ServerLog_Entry_884` and `DatabaseSnapshot_445` are correlated with `OCL_2023_001`, providing multiple evidentiary sources for a single claim.*

## 4.4 Outlier Detection Processes and Claim Production

### 4.4.1 Axiomatic Definition

The generation of evidence and the subsequent identification of claims are the result of specific processes. The `outlier_detection_produces_claim` axiom formalizes the relationship between a process (X) and the evidence correlation (Y) it generates. In this ontology, the process is a subclass of `bfo:0000015` (Process), representing an occurrent that unfolds in time.

**Axiom 2 (outlier_detection_produces_claim):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:produces some {Y:Class}`
*   **Verbalization:** {X} is something that produces {Y}

It is crucial to note that the object of production is the *evidence correlation* (the instance of `t_evidence_correlated_with`), not merely the raw data. The process acts upon the environment to generate a specific informational entity that links data to a claim. This distinction allows auditors to trace not just what data exists, but *which algorithmic or manual procedure* established the link between that data and the outlier claim.

### 4.4.2 Relational Implementation

The table `t_outlier_detection_produces_claim` records the provenance of the evidence correlation. The foreign key `y` references `t_evidence_correlated_with`, creating a direct link from the process to the specific evidence instance. This structure facilitates the "re-run" requirements often found in audit scenarios, where one must identify exactly which detection process generated a specific finding.

**Table 4.3: Detection Process Provenance**

| :--- | :--- | :--- |
| `PROC_ALPHA_01` | `AutomatedHeuristicScan` | `EV_CORR_100` |

The `x` column identifies the specific process class (e.g., `AutomatedHeuristicScan`), while `y` points to the evidence correlation ID produced by that process. This indicates, for example, that the `AutomatedHeuristicScan` was responsible for producing the correlation `EV_CORR_100`.*

## 4.5 Baseline-Constrained Outlier Detection

### 4.5.1 Axiomatic Definition

Not all detection processes operate in a vacuum; many function by comparing observed behaviors against a defined baseline or normative standard. The `outlier_detection_with_baseline` axiom captures this by defining a process (X) that acts *against* a specific evidence correlation (Y). In this context, the "against" relation signifies that the evidence correlation serves as the contextual baseline or the standard of comparison for the detection process.

**Axiom 4 (outlier_detection_with_baseline):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:against some {Y:Class}`
*   **Verbalization:** {X} is something that against {Y}

This axiom is essential for "long-tail" analysis where anomalies are defined not by absolute thresholds, but by their deviation from a specific, evidentiary baseline. By referencing the evidence correlation entity, the ontology ensures that the baseline is not an abstract concept but is grounded in the same data structures as the claims themselves.

### 4.5.2 Relational Implementation

The schema for `t_outlier_detection_with_baseline` links a detection process to an evidence correlation instance via the `y` foreign key. This allows the system to query for all detection processes that rely on a specific evidentiary context as their baseline.

**Table 4.4: Baseline-Constrained Detection Processes**

| id | x | y |
| :--- | :--- | :--- |
| `PROC_DELTA_01` | `StatisticalDeviationCheck` | `EV_CORR_104` |
| `PROC_DELTA_02` | `HistoricalComparisonAlgorithm` | `EV_CORR_104` |
| `PROC_EPSILON_01` | `PeerGroupAnalysis` | `EV_CORR_101` |

*Table 4.4 illustrates the `outlier_detection_with_baseline` axiom. The process `StatisticalDeviationCheck` (x) is executed against the evidentiary context of `EV_CORR_104` (y). This implies that `EV_CORR_104` (which correlates `WarehouseManifest_771` with `OCL_2023_003`) serves as the normative baseline for this specific detection run.*

## 4.6 Lift Metrics and Baseline Rates

### 4.6.1 Axiomatic Definition

In quantitative risk assessment and fraud detection, "lift" refers to the factor by which a specific observation exceeds the expected baseline probability. The `lift_with_baseline_rate` axiom formalizes a descriptive entity (X) that possesses a baseline rate (Y). In this ontological structure, the baseline rate is not a simple floating-point number but is reified as a reference to an evidence correlation entity.

**Axiom 5 (lift_with_baseline_rate):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasBaselineRate some {Y:Class}`
*   **Verbalization:** {X} is something that has baseline rate {Y}

This approach allows for complex definitions of baseline rates. A baseline rate might be derived from a composite of multiple evidence correlations, but in this schema, it is anchored to a specific correlation instance (`t_evidence_correlated_with`). This ensures that the "lift" metric is always traceable to the specific evidentiary context from which the baseline was calculated.

### 4.6.2 Relational Implementation

The table `t_lift_with_baseline_rate` connects a lift metric entity (X) to an evidence correlation (Y). The foreign key constraint ensures that a lift metric cannot exist without a valid evidentiary basis for its baseline rate.

**Table 4.5: Lift Metrics and Baseline References**

| :--- | :--- | :--- |
| `LIFT_METRIC_50` | `FraudScoreLift_4.5x` | `EV_CORR_100` |

| `LIFT_METRIC_52` | `AccessPatternLift_3.8x` | `EV_CORR_101` |

*Table 4.5 instantiates the `lift_with_baseline_rate` axiom. The metric `FraudScoreLift_4.5x` (x) has its baseline rate defined by the evidence correlation `EV_CORR_100` (y). This creates a rigorous semantic link where the calculated lift is explicitly tied to the evidence instance (`ServerLog_Entry_884`) that established the baseline expectation.*
