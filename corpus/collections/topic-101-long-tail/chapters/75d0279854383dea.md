# Chapter 4: Ontological Mapping of Compliance Directives

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to map regulatory directives to executable compliance logic within a governance framework. It provides a rigorous examination of the relationships between designative information content entities, their subclassifications, and the attribution of priority levels to specific directives. The content herein is intended for systems architects and compliance officers seeking to implement a semantic data layer that supports automated audit trails and regulatory reporting. All definitions are derived from the core ontology axioms governing Information Content Entities (ICE) and are instantiated through relational schemas that ensure referential integrity.

## 4.2 Subclass to Designative Information Content Entity

### 4.2.1 Conceptual Definition

In the context of semantic governance, a Designative Information Content Entity (Designative ICE) serves as the foundational unit for labeling, identifying, or referring to entities within a system. The axiom `subclass_to_designative_ice` posits that specific classes of entities are, by definition, designative. This means they function as signs or symbols that stand for other entities or concepts within the compliance domain. Unlike descriptive entities, which characterize the properties of an object, designative entities act as the mechanism for reference and addressability.

The formalization of this concept is critical for establishing a controlled vocabulary. When a class is defined as a subclass of `cco:DesignativeICE`, it is axiomatic that instances of this class will function as identifiers or designators within the information system. This distinction prevents category errors where descriptive data might be mistakenly interpreted as referential keys.

### 4.2.2 Implementation and Schema

The relational projection of this axiom creates a registry of designative classes. The primary key serves as the unique identifier for the class definition, while the `x` slot contains the human-readable or machine-readable label of the designative class. This table functions as a master reference for any system component that needs to verify whether a given class possesses designative properties.

The following data exhibit illustrates the instantiation of priority classes as designative entities. These entries represent the abstract categories of urgency that will later be attributed to specific directives.

## 4.3 Designative Subclass Basic

### 4.3.1 Conceptual Definition

While the previous section established the general category of designative entities, the `designative_subclass_basic` axiom addresses the granular implementation of these entities within the foundational layer of the ontology. This axiom reinforces the principle that basic informational elements—such as system codes, unique identifiers, and classification tags—are inherently designative. It distinguishes these basic elements from complex, composite directives.

In practice, this axiom governs the creation of "basic" designative terms that are not themselves directives but are used to construct or identify them. For example, a specific compliance code or a geographical locator tag would fall under this classification. The separation of "basic" designative entities from other structural entities ensures that the ontology maintains a clear separation between the *means of reference* (the identifier) and the *object of reference* (the directive).

### 4.3.2 Implementation and Schema

The schema for this axiom is structurally similar to the general subclass registry but is semantically reserved for non-directive designative elements. It acts as a namespace for basic identifiers that support the broader compliance infrastructure.

The table below demonstrates the registration of basic designative elements used for system categorization. These are not requirements themselves but rather the "tags" or "codes" that the system uses to organize and retrieve requirements.

| :--- | :--- |
| class_tag_fiscal | FiscalCodeTag |
| class_tag_safety | SafetyProtocolTag |

*Table 4-2 Notes:*

## 4.4 Requirement Has Priority

### 4.4.1 Conceptual Definition

The axiom `requirement_has_priority` introduces a critical governance constraint: the attribution of priority to directives. Formally, it asserts that a Directive ICE (specifically a Requirement) must possess a priority property that links it to a Designative ICE (as defined in Section 4.2). This relationship is not merely optional; it is a structural necessity for the execution of compliance logic.

In a high-density regulatory environment, resources for audit and remediation are finite. Therefore, the ontology must support a triage mechanism. By defining a Requirement as a subclass of `cco:DirectiveICE` that `hasPriority` some {Y}, we create a formal pathway for automated systems to sort, filter, and escalate compliance issues. The priority value {Y} must be drawn from the registry of designative entities established in Table 4-1, ensuring that only valid, standardized priority levels are utilized.

### 4.4.2 Implementation and Schema

The relational schema for this axiom enforces a foreign key constraint, linking the requirement directly to a valid priority class. This ensures data integrity by preventing the assignment of undefined or ad-hoc priority levels. The structure supports a many-to-one relationship, where multiple requirements may share a single priority level, but each requirement must have exactly one defined priority (inherited from the existential restriction `some`).

The following exhibit details specific regulatory requirements and their formally assigned priorities. Note that the `y` column references the `id` values from the Designative Subclass Registry (Table 4-1), demonstrating the enforcement of referential integrity.

## 4.5 Identifier Unique

### 4.5.1 Conceptual Definition

The final axiom, `identifier_unique`, addresses the necessity of unambiguous reference within the governance framework. It asserts that a Designative ICE functions as an identifier for a specific entity, and crucially, that it identifies *max 1* entity. This constraint enforces singularity of reference; a single identifier string may not point to multiple distinct requirements or objects simultaneously.

This axiom is the cornerstone of auditability. In compliance reporting, it is imperative that when an identifier is queried (e.g., "REQ-101"), the result is a single, unambiguous directive. Ambiguity in identification leads to gaps in audit trails and potential regulatory non-compliance. The axiom links the identifier (a Designative ICE) to the entity it identifies (in this schema structure, the Requirement-Priority relationship).

### 4.5.2 Implementation and Schema

The schema for `t_identifier_unique` creates a mapping between a unique identifier string and a specific requirement record. The foreign key constraint linking to `t_requirement_has_priority` ensures that identifiers are only assigned to valid, existing requirements that have already been prioritized. This dependency enforces a lifecycle: a requirement must be defined and prioritized before it can be formally identified.
