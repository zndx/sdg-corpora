# Chapter 4: Governance Frameworks and Directive Mapping in Multi-Standard Compliance

## 4.1 Scope and Preamble

This chapter delineates the formal integration of disparate governance frameworks—specifically ISO/IEC 27001 and the Payment Card Industry Data Security Standard (PCI DSS)—within a unified ontology of internal controls. The objective is to establish a rigorous mapping between high-level compliance directives and granular technical controls, ensuring that organizational governance artifacts are both semantically precise and auditorily traceable. The following sections introduce five foundational axioms that define the relationships between directive classes, risk mitigation strategies, and regulatory requirements. Through the application of these axioms, organizations can derive a deterministic relational schema that supports automated compliance verification and evidence generation.

## 4.2 ISO 27001 Annex A Subclass Integration

The alignment of internal governance directives with the ISO/IEC 27001 standard is predicated on the formal subsumption of directive classes under specific Annex A control categories. The axiom `iso27001_annexa_subclass` posits that for a directive class {X} to be compliant, it must be a subclass of the Information Control Element (ICE) and must exhibit a specific relationship to an ISO 27001 Annex A control class {Y}. This relationship ensures that every internal governance artifact is logically traceable to a recognized industry standard control.

In practice, this mapping allows auditors to verify that an internal policy, such as an Access Control Directive, is not merely a procedural document but a direct implementation of a specific control objective (e.g., A.9.1.1). The relational schema derived from this axiom enforces a foreign key constraint linking the Annex A control to a specific threat-addressing class, creating a chain of evidence from the standard to the operational control.

## 4.3 Control-Specific Threat Addressing

While general directives provide the framework for compliance, the axiom `control_only_addresses_threat_class` introduces a constraint of exclusivity. This axiom asserts that a control class {X} is a subclass of the Directive ICE and addresses a risk class {Y} *only*. This logical restriction is critical for high-assurance environments where scope creep within a control's function can introduce unforeseen vulnerabilities or operational conflicts.

By enforcing the "only" (`only`) quantifier, the ontology ensures that a control designed to address "Unauthorized Physical Access" cannot be semantically interpreted as addressing "Malware Injection" without a distinct, separate classification. This precision is vital for audit reporting, as it isolates the failure domain of a specific control. The relational schema for this axiom creates a reciprocal foreign key relationship with the ISO 27001 subclass table, reinforcing the tight coupling between the standard requirement and the specific threat it mitigates.

The entries in Table 4.2 reflect the operational reality of security controls. For instance, the `PhysicalEntryControl` (id: `ctrl_threat_001`) is strictly bound to the `AccessControlPolicy` (id: `dir_iso_001`). This binding ensures that if the policy is revoked, the control's validity is inherently nullified, maintaining referential integrity across the governance framework.

## 4.4 PCI DSS Requirement Overlay

Organizations subject to multiple regulatory regimes must map their internal controls to various external standards simultaneously. The axiom `pci_dss_requirement` facilitates this by defining a class {X} as a subclass of Directive ICE that satisfies a specific PCI DSS requirement {Y}. This axiom functions as an overlay, allowing a single internal control to satisfy distinct obligations within ISO 27001 and PCI DSS frameworks.

The relational structure requires that the PCI DSS requirement (`y`) references a valid control from the threat-addressing table. This dependency ensures that compliance with PCI DSS is not merely theoretical but is anchored to an existing, implemented control that addresses a specific threat. For example, a requirement regarding the protection of stored cardholder data must map to a cryptographic control that is already defined within the ISO 27001 context.

## 4.5 Requirement Specification and Targeting

The axiom `requirement_equiv_specifies_target` provides a more complex definition of a requirement class {X}. It asserts that {X} is equivalent to the intersection of three conditions: it is a Directive ICE, it specifies a control {Y}, and it applies to a target {Z}. This equivalence axiom is used to define comprehensive requirements that are explicit about both the control mechanism and the scope of application (the target).

This structure is particularly useful for defining granular governance rules, such as "Server administrators must use two-factor authentication." Here, the requirement specifies the control (Two-Factor Authentication) and the target (Server Administrators). The relational schema enforces that the specified control (`y`) must be a valid ISO 27001 subclass, ensuring that the requirement is grounded in the broader compliance framework.

## 4.6 General Risk Addressing

In contrast to the exclusive threat addressing defined in Section 4.3, the axiom `control_addresses_risk` describes a broader, non-exclusive relationship. Here, a control class {X} is a subclass of Directive ICE that addresses a risk {Y} using the existential quantifier (`some`). This allows for controls that are multifaceted or provide defense-in-depth capabilities where a single control may mitigate multiple risks or contribute to a broader risk category.

This axiom is essential for mapping high-level security objectives to operational realities where a single directive—such as a Security Awareness Program—might address risks ranging from phishing to social engineering and physical tailgating. The relational schema links the risk (`y`) back to the ISO 27001 subclass, maintaining the connection to the primary standard while allowing flexibility in risk mitigation.

Table 4.5 demonstrates the versatility of the `control_addresses_risk` axiom. Unlike the "only" constraint in Section 4.3, this mapping allows the same control to potentially be linked to other risks in future extensions of the model, reflecting the dynamic nature of cybersecurity risk management.
