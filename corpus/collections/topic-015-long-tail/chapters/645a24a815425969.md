# Chapter 7: Formal Ontology of Governance Directives and Compliance Controls

This chapter establishes the formal ontological framework for mapping governance directives to specific control mechanisms and risk categories within the enterprise architecture. It details the structural relationships between ISO 27001 Annex A controls, PCI DSS requirements, and internal threat classifications. The definitions provided herein serve as the authoritative schema for automated compliance auditing and risk assessment protocols, ensuring that all directive classes are rigorously defined and cross-referenced according to the established axioms.

## 1. ISO 27001 Annex A Subclass Relations

The foundational axiom for information security governance within this ontology defines the subclass relationship between organizational directives and the ISO 27001 Annex A framework. This relationship asserts that a specific directive class (`{X}`) is not merely a generic policy but a subclass of the `cco:DirectiveICE` that specifically fulfills or instantiates a control objective defined in ISO 27001 Annex A (`{Y}`). This mapping is critical for maintaining traceability between high-level governance artifacts and specific compliance clauses.

The following table embodies Axiom 1 (`iso27001_annexa_subclass`), where the primary key is the directive ID (`id`) and the foreign key (`y`) references the specific threat class addressed by the control, establishing a link between the compliance requirement and the threat landscape.

**Table 1.1: ISO 27001 Annex A Subclass Mappings**

| id | x | y |
| :--- | :--- | :--- |
| `dir_iso_access_ctrl` | AccessControlPolicy | `threat_unauth_access` |
| `dir_iso_asset_mgmt` | AssetInventoryDirective | `threat_asset_loss` |
| `dir_iso_crypto` | CryptographicControlPolicy | `threat_data_exposure` |
| `dir_iso_hr_sec` | HumanResourcesSecurity | `threat_insider_threat` |
| `dir_iso_phys_sec` | PhysicalSecurityEntry | `threat_trespass` |

## 2. Control and Threat Addressing Classes

To operationalize the directives defined in Section 1, the ontology employs a specific axiom for classes that address risks exclusively. This axiom (`control_only_addresses_threat_class`) formalizes the definition of a control class (`{X}`) as a `cco:DirectiveICE` that addresses a specific risk class (`{Y}`) and no other. This "only" constraint is semantically significant, implying a strict functional boundary for the control class within the governance model.

The table below represents Axiom 2 (`control_only_addresses_threat_class`). The primary key (`id`) identifies the threat class entity, while the foreign key (`y`) creates a reciprocal reference back to the ISO 27001 Annex A subclass, ensuring that every defined threat is mapped to a specific governance control.

**Table 2.1: Control-Only Threat Addressing Classes**

| id | x | y |
| :--- | :--- | :--- |
| `threat_unauth_access` | UnauthorizedAccessClass | `dir_iso_access_ctrl` |
| `threat_asset_loss` | AssetLossClass | `dir_iso_asset_mgmt` |
| `threat_data_exposure` | DataExposureClass | `dir_iso_crypto` |
| `threat_insider_threat` | InsiderThreatClass | `dir_iso_hr_sec` |
| `threat_trespass` | PhysicalTrespassClass | `dir_iso_phys_sec` |

## 3. PCI DSS Requirement Integration

In environments where payment card data is processed, governance directives must be aligned with the Payment Card Industry Data Security Standard (PCI DSS). This axiom defines a class (`{X}`) as a subclass of `cco:DirectiveICE` that satisfies a specific PCI DSS requirement (`{Y}`). This integration allows the organization to maintain a unified view of compliance, where PCI DSS requirements are treated as specific instances of broader governance directives.

The following table illustrates Axiom 3 (`pci_dss_requirement`). The structure uses the directive ID as the primary key, with the foreign key (`y`) referencing the control-only threat class. This linkage ensures that the PCI requirement is explicitly tied to the specific threat class it mitigates within the ontology.

**Table 3.1: PCI DSS Requirement Mappings**

| id | x | y |
| :--- | :--- | :--- |
| `pci_req_7_1` | PCI_DSS_Req_7_1_AccessControl | `threat_unauth_access` |
| `pci_req_9_4` | PCI_DSS_Req_9_4_PolicyTesting | `threat_trespass` |
| `pci_req_3_4` | PCI_DSS_Req_3_4_RenderDataUnreadable | `threat_data_exposure` |
| `pci_req_12_10` | PCI_DSS_Req_12_10_AuditTrail | `threat_insider_threat` |
| `pci_req_2_1` | PCI_DSS_Req_2_1_VendorDefaults | `threat_asset_loss` |

## 4. Requirement Specification and Target Application

Complex governance directives often require the specification of control mechanisms and the definition of the entities to which they apply. This axiom defines an equivalence class (`{X}`) that is simultaneously a `cco:DirectiveICE`, a specifier of a control (`{Y}`), and an applicability rule for a target (`{Z}`). This construct is essential for granular policy enforcement, where a directive must explicitly state what it controls and who or what it affects.

The table below details Axiom 4 (`requirement_equiv_specifies_target`). The primary key (`id`) uniquely identifies the requirement, while two foreign keys are utilized: `y` references the ISO 27001 Annex A subclass (the control specified), and `z` represents the target class (the entity to which the directive applies).

**Table 4.1: Requirement Specification and Target Application**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `req_logical_access` | LogicalAccessRequirement | `dir_iso_access_ctrl` | `SystemUser` |

| `req_badge_access` | FacilityBadgeSystem | `dir_iso_phys_sec` | `DataCenter` |
| `req_hardware_inventory` | HardwareAssetControl | `dir_iso_asset_mgmt` | `ServerEndpoint` |

## 5. Control-Risk Addressing Mechanisms

The final concept in this chapter addresses the general mechanism by which a control class mitigates a risk. While Axiom 2 defines a class that *only* addresses a specific threat, this axiom (`control_addresses_risk`) is broader, defining a subclass of `cco:DirectiveICE` that addresses a risk (`{Y}`) as one of its properties. This allows for the definition of composite controls that may mitigate multiple risks or serve broader governance functions.

The following table presents Axiom 5 (`control_addresses_risk`). The primary key (`id`) identifies the control mechanism, and the foreign key (`y`) references the ISO 27001 Annex A subclass, thereby linking the specific control implementation to the broader governance framework and its associated risk definitions.
