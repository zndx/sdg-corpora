# Chapter 4: Governance Frameworks and Control Mapping in Compliance Ontologies

## 4.1 Scope and Preamble

This chapter delineates the structural relationships between information security directives, risk management protocols, and regulatory compliance standards within a formal ontology. It provides a detailed examination of how specific control classes are subclassified under ISO/IEC 27001 Annex A, how these controls address distinct threat vectors, and how they intersect with Payment Card Industry Data Security Standard (PCI DSS) requirements. The analysis is grounded in the Basic Formal Ontology (BFO) framework, specifically utilizing the *DirectiveICE* (Information Control Element) anchor to define the normative constraints of governance artifacts. The following sections present a logical decomposition of these axioms, supported by relational data tables that instantiate the mapping between abstract control classes and specific compliance obligations.

## 4.2 ISO 27001 Annex A Subclassifications

The first axiom establishes the taxonomic hierarchy for directives within the ISO/IEC 27001 framework. In this context, a control class {X} is defined as a subclass of the *DirectiveICE* and is semantically bound to a specific control objective within ISO 27001 Annex A, denoted as {Y}. This relationship ensures that any governance artifact instantiated from class {X} inherently carries the normative weight and procedural scope of the referenced Annex A control. The verbalization "{X} is something that iso27001 annex a {Y}" signifies a necessary condition: for an entity to be recognized as a valid control within this ontology, it must be traceable to a specific article within the Annex A framework.

This mapping is critical for audit readiness, as it allows automated reasoning engines to verify that a declared control set covers the requisite domains of the information security management system (ISMS). The relational schema below captures this dependency, where the primary key identifies the specific directive instance, and the foreign key enforces the link to the threat class addressed by that Annex A control.

## 4.3 Control Governance and Threat Addressing

Building upon the classification established in the previous section, the second axiom introduces a restriction on the relationship between directives and risks. Specifically, it posits that a Control Class {X} is a subclass of *DirectiveICE* that addresses a Risk Class {Y} *only* ({Y}). This "only" restriction (an allValuesFrom restriction in OWL) implies that the scope of Control {X} is exclusively limited to the mitigation of Risk {Y}. In governance terms, this means the control is not a general-purpose security measure but a targeted intervention designed for a specific threat vector.

The verbalization "{X} is something that addresses risk {Y}" encapsulates the functional purpose of the directive. However, the formal axiom imposes a stricter logical constraint: if an instance of {X} is addressing a risk, that risk *must* be an instance of {Y}, and conversely, {X} is defined solely by its capacity to address {Y}. This creates a tight coupling between the control definition and the threat ontology, preventing scope creep in control implementation. The relational schema presented below formalizes this exclusive relationship, ensuring referential integrity back to the Annex A subclassifications.

This table embodies the axiom `control_only_addresses_threat_class`. It defines the exclusive relationship where a Control Class (`x`) addresses a specific Risk Class (`y`). The foreign key constraint on `y` (referencing `t_iso27001_annexa_subclass`) enforces the logical dependency that the risk being addressed must be defined within the scope of the ISO 27001 Annex A controls.

| id | x | y |
| :--- | :--- | :--- |

## 4.4 PCI DSS Requirement Integration

In complex regulatory environments, organizations must satisfy multiple frameworks simultaneously. The third axiom addresses this by mapping the ISO-based control classes to the Payment Card Industry Data Security Standard (PCI DSS). Here, a Class {X} (representing a PCI DSS requirement category) is defined as a subclass of *DirectiveICE* that necessitates the satisfaction of specific PCI DSS requirements {Y}.

The verbalization "{X} is something that pci dss requirement {Y}" indicates that the directive {X} is the implementation mechanism for the regulatory requirement {Y}. This axiom facilitates cross-walking between the ISO 27001 ISMS and the PCI DSS compliance program. By establishing this link, the ontology allows compliance officers to identify overlapping controls and gaps between the two standards. The relational structure below maps the PCI requirements to the threat classes defined in the previous section, effectively anchoring the PCI standard to the organization's risk management taxonomy.

**Table 4.3: PCI DSS Requirement Mappings**
This table embodies the axiom `pci_dss_requirement`. It maps a PCI DSS Control Class (`x`) to a specific PCI Requirement (`y`). The foreign key on `y` references the threat class table, indicating that the PCI requirement is satisfied by the control that addresses a specific threat (e.g., PCI Requirement 7 is satisfied by the Access Control Policy which addresses Unauthorized Access).

| id | x | y |
| :--- | :--- | :--- |
| PCI_7 | RestrictAccess | THREAT_UnauthAccess |
| PCI_2 | VendorConfig | THREAT_SupplyChain |
| PCI_5 | AntiMalware | THREAT_Malware |
| PCI_3 | DataStorage | THREAT_DataLoss |

## 4.5 Requirement Specification and Targeting

The fourth axiom defines a complex equivalence class for requirements. A Class {X} is equivalent to the intersection of *DirectiveICE*, the class of entities that specify a mechanism {Y}, and the class of entities that apply to a target {Z}. This tripartite structure provides a granular definition of a compliance requirement: it is a directive that specifies *how* a control is implemented ({Y}) and defines *to what* it applies ({Z}).

This structure is essential for detailed compliance auditing. It moves beyond high-level control statements to define the specific parameters of implementation. For example, a requirement is not merely "Access Control," but "Access Control" ({X}) that specifies "Multi-Factor Authentication" ({Y}) and applies to "Privileged User Groups" ({Z}). The relational schema captures this equivalence, linking the requirement to the broader ISO taxonomy via the specification {Y}.

## 4.6 General Risk Addressing Mechanisms

While Axiom 4.3 defined an exclusive relationship between a control and a threat, the final axiom broadens the scope to general risk addressing. Here, a Class {X} is a subclass of *DirectiveICE* that addresses *some* Risk Class {Y} (a someValuesFrom restriction). Unlike the "only" restriction in Section 4.3, this axiom permits a single control to address multiple risks or allows for a more flexible mapping where the control is part of a broader mitigation strategy.

The verbalization "{X} is something that addresses risk {Y}" serves as a general-purpose predicate for connecting the governance framework to the risk register. This axiom is typically used for controls that are multifaceted or where the threat landscape is too dynamic to support the rigid exclusivity of the previous axiom.
