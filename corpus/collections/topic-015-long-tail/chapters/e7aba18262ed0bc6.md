# Chapter 4: Ontological Mapping of Compliance Directives and Risk Mitigation

This chapter provides a rigorous examination of the semantic relationships governing information security controls, specifically focusing on the alignment between ISO/IEC 27001 Annex A directives, PCI DSS requirements, and risk taxonomies. The analysis utilizes a formal ontology to define the subclass structures and equivalence classes necessary for automated compliance auditing and governance framework implementation. It establishes the deterministic links between directive classes, the specific threats they address, and the regulatory requirements they satisfy.

## 4.1 ISO 27001 Annex A Subclassifications

The foundational structure of the governance ontology relies on the precise classification of directives under the ISO/IEC 27001 Annex A framework. Axiomatically, a directive class is defined as a subclass of the `cco:DirectiveICE` and must possess a specific relationship to an Annex A control. This relationship, denoted as `iso27001AnnexA`, asserts that for any directive to be compliant within this ontology, it must be a manifestation or implementation of a specific control objective defined in the standard.

This classification ensures that governance artifacts are not merely abstract concepts but are anchored to recognized control objectives. For instance, an "Access Control Policy" directive is not a standalone entity; it is ontologically a subclass of directives that implements Annex A.9 (Access Control). The following table delineates the instantiation of this axiom, demonstrating how specific directive classes map to their corresponding Annex A control categories, which are themselves modeled as classes within the threat taxonomy.

**Table 4.1: ISO 27001 Annex A Subclass Mappings**

| ID | Directive Class (X) | Annex A Control / Threat Class (Y) |
| :--- | :--- | :--- |
| iso_sub_001 | AccessControlDirective | threat_class_001 |
| iso_sub_002 | CryptographyDirective | threat_class_002 |
| iso_sub_003 | PhysicalSecurityDirective | threat_class_003 |
| iso_sub_004 | OperationsSecurityDirective | threat_class_004 |
| iso_sub_005 | CommunicationsSecurityDirective | threat_class_005 |

In this schema, the primary key `id` represents the unique identifier for the directive class. The column `y` functions as a foreign key, referencing the identifier of the threat class that the Annex A control is designed to mitigate. This creates a dependency where the validity of the directive's classification is contingent upon the existence of the corresponding threat or control class.

## 4.2 Control-Only Addresses Threat Class

To enforce strict modularity in control design, the ontology introduces a constraint wherein certain directive classes address *only* a specific threat class. This axiom, `control_only_addresses_threat_class`, refines the broader concept of risk addressing by applying a universal quantification (`only`) to the `addressesRisk` property. This implies that instances of the directive class `X` are exclusively dedicated to mitigating the risk class `Y`, preventing scope creep or ambiguous application of security controls.

This distinction is critical for audit trails where a control must be demonstrably targeted at a specific vulnerability without implication in unrelated risk areas. For example, a directive designed solely to address "Unauthorized Access Threat" must not be ontologically structured to address "Data Exfiltration" unless explicitly reclassified. The relational integrity of this concept is maintained by a reciprocal foreign key constraint, linking the threat class back to the ISO 27001 subclass, thereby creating a closed loop of governance definitions.

**Table 4.2: Control-Only Addresses Threat Class Constraints**

| ID | Threat Class (X) | ISO Subclass Reference (Y) |
| :--- | :--- | :--- |
| threat_class_001 | UnauthorizedAccessThreat | iso_sub_001 |
| threat_class_002 | DataExfiltrationThreat | iso_sub_002 |
| threat_class_003 | PhysicalIntrusionThreat | iso_sub_003 |
| threat_class_004 | OperationalDisruptionThreat | iso_sub_004 |
| threat_class_005 | NetworkInterceptionThreat | iso_sub_005 |

The schema presented in Table 4.2 utilizes `id` as the primary key for the threat class. The column `y` references the `t_iso27001_annexa_subclass` table, ensuring that every threat class addressed by a "control-only" directive is traceable back to a specific ISO Annex A implementation. This structure supports the verification of control coverage during compliance audits.

## 4.3 PCI DSS Requirement Integration

The Payment Card Industry Data Security Standard (PCI DSS) imposes a distinct set of requirements that often overlap with ISO 27001 controls but require explicit mapping for multi-framework compliance. The ontology defines a specific subclass relationship where a directive class `X` satisfies a PCI DSS requirement `Y`. This axiom, `pci_dss_requirement`, facilitates the mapping of internal governance directives to external regulatory obligations.

By establishing `sdg:pciDssRequirement` as an object property, the ontology allows for the precise association of a directive (e.g., a firewall configuration rule) with a specific PCI requirement (e.g., Requirement 1.2.1). The relational schema dictates that the PCI requirement (`y`) must reference a valid threat class ID, reinforcing the concept that compliance requirements are fundamentally responses to identified risks. This integration enables automated gap analysis by querying directives that fail to map to necessary PCI requirements.

**Table 4.3: PCI DSS Requirement Mappings**

| ID | Directive Class (X) | PCI DSS Requirement (Y) |
| :--- | :--- | :--- |
| pci_req_001 | CardholderDataAccessDirective | threat_class_001 |
| pci_req_002 | TransmissionEncryptionDirective | threat_class_005 |
| pci_req_003 | MalwareProtectionDirective | threat_class_004 |
| pci_req_004 | PhysicalMediaAccessDirective | threat_class_003 |
| pci_req_005 | KeyManagementDirective | threat_class_002 |

As shown in Table 4.3, the foreign key constraint on `y` ensures that the PCI requirement is linked to the threat class defined in the `t_control_only_addresses_threat_class` table. This enforces the principle that regulatory requirements are instantiated to address specific, defined threats within the governance model.

## 4.4 Requirement Equivalence: Specification and Target

The ontology further refines the definition of a requirement through an equivalence axiom. A class `X` is defined as equivalent to the intersection of `cco:DirectiveICE`, the class of entities that *specify* a mechanism `Y`, and the class of entities that *apply to* a target `Z`. This axiom, `requirement_equiv_specifies_target`, provides a granular decomposition of compliance rules, separating the *specification* of the control from its *target* scope.

This decomposition is essential for attribute-based access control and policy enforcement. For example, a "Logical Access Requirement" is equivalent to a directive that specifies "Authentication Protocols" and applies to "Privileged User Groups." The relational schema captures this tripartite structure, linking the specification (`y`) back to the ISO subclass, thereby anchoring the requirement's definition in the broader compliance framework.

**Table 4.4: Requirement Equivalence Specifications**

| ID | Requirement Class (X) | Specification (Y) | Target (Z) |
| :--- | :--- | :--- | :--- |
| req_spec_001 | LogicalAccessReq | iso_sub_001 | PrivilegedRole |
| req_spec_002 | DataEncryptionReq | iso_sub_002 | CustomerDatabase |
| req_spec_003 | SiteEntryReq | iso_sub_003 | DataCenter |
| req_spec_004 | ChangeManagementReq | iso_sub_004 | ProductionEnvironment |
| req_spec_005 | VPNAccessReq | iso_sub_005 | RemoteWorkforce |

In this structure, `y` represents the specification mechanism and must correspond to an existing ISO subclass ID. The column `z` represents the target class, which is the entity or scope to which the directive applies. This allows for complex querying, such as "Retrieve all requirements that apply to 'PrivilegedRole' and specify 'Access Control'."

## 4.5 Control Addresses Risk

While Section 4.2 defined a constraint where a control addresses *only* a specific threat, the broader ontology also accommodates a more general relationship where a directive class addresses a risk class without the exclusivity constraint. The axiom `control_addresses_risk` establishes that a class `X` is a subclass of `cco:DirectiveICE` and addresses some instance of risk class `Y`.

This relationship is vital for mapping defense-in-depth strategies where a single directive may mitigate multiple facets of a risk category, or where a risk is addressed by a composite of directives. Unlike the "control-only" axiom, this allows for many-to-many mappings in the conceptual model, though the relational schema provided here enforces a link to the ISO subclass to maintain referential integrity with the core control library.

**Table 4.5: General Control-Risk Addressing**

| ID | Directive Class (X) | Risk Class (Y) |
| :--- | :--- | :--- |
| ctrl_addr_001 | AuthenticationControl | iso_sub_001 |
