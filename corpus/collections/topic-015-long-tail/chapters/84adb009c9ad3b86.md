# Chapter 4: Ontological Mapping of Governance Frameworks and Control Directives

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to map distinct governance frameworks—specifically ISO/IEC 27001 Annex A and the Payment Card Industry Data Security Standard (PCI DSS)—into a unified compliance model. The objective is to provide a rigorous, evidence-anchored methodology for defining control classes, their interrelationships with risk taxonomies, and their equivalence across regulatory domains. The definitions herein utilize the Manchester Syntax for Web Ontology Language (OWL) to ensure logical precision, facilitating automated reasoning and audit trail generation. By grounding these concepts in a deterministic relational schema, auditors and compliance officers may verify the integrity of control implementations against stated security policies.

## 4.2 ISO 27001 Annex A Subclassifications

The foundational element of the information security management system (ISMS) ontology is the classification of directives according to ISO/IEC 27001 Annex A controls. This classification is not merely taxonomic but functional, linking specific control classes to the broader governance framework. The axiom `iso27001_annexa_subclass` asserts that a control class (X) is a subclass of the `cco:DirectiveICE` (Information Control Element) and fulfills a specific requirement within ISO 27001 Annex A (Y).

In formal audit practice, this relationship ensures that every implemented control can be traced back to a specific clause in the governing standard. The ontological structure enforces a strict hierarchy where the existence of the control class is contingent upon its definition within the Annex A framework. This mapping is critical for gap analysis; if a directive cannot be mapped to an Annex A class, it falls outside the scope of the ISMS certification and must be treated as a supplementary control.

The relational projection of this axiom, `t_iso27001_annexa_subclass`, establishes a foreign key dependency on the threat-addressing capabilities of the control. This creates a circular dependency in the logical model, reflecting the real-world reciprocity between a control definition and the threat it mitigates. The table below illustrates instances where specific directive classes are subclassified under Annex A controls, referencing their corresponding threat mitigation classes.

| ID | Control Class (X) | Annex A / Threat Class (Y) |
|---|---|---|
| ISO_A_9_1 | AccessControlDirective | CTRL_ONLY_1 |
| ISO_A_8_2 | PrivilegedAccessDirective | CTRL_ONLY_2 |
| ISO_A_12_3 | DataBackupDirective | CTRL_ONLY_3 |

## 4.3 Control-Only Addresses Threat Class

To achieve a granular level of risk management, the ontology distinguishes between general risk addressing and exclusive risk addressing. The axiom `control_only_addresses_threat_class` defines a control class (X) that addresses a specific risk class (Y) to the exclusion of others. This is a stronger logical constraint than general risk association; it implies that the primary, and potentially sole, function of the control is the mitigation of threat Y.

From a compliance perspective, this distinction is vital for resource allocation and control effectiveness monitoring. If a control is designated as "only" addressing a specific threat, its failure results in a direct, high-severity exposure to that specific threat without redundancy. This axiom is modeled as a subclass of `cco:DirectiveICE`, ensuring that all entities in this domain retain the properties of information control elements.

The corresponding relational schema, `t_control_only_addresses_threat_class`, enforces a reciprocal foreign key constraint with the Annex A subclassification table. This bidirectional linkage ensures that a threat class defined in this context must map back to a valid ISO 27001 control, maintaining the closed-loop integrity of the audit evidence.

| ID | Control Class (X) | Threat Class Reference (Y) |
|---|---|---|
| CTRL_ONLY_1 | PhysicalEntryControl | ISO_A_9_1 |
| CTRL_ONLY_2 | PasswordManagementSystem | ISO_A_8_2 |
| CTRL_ONLY_3 | AutomatedBackupUtility | ISO_A_12_3 |
| CTRL_ONLY_4 | AsymmetricEncryptionModule | ISO_A_10_1 |

## 4.4 PCI DSS Requirement Integration

Organizations operating within the payment card industry must harmonize their ISMS controls with PCI DSS requirements. The axiom `pci_dss_requirement` facilitates this by defining a class (X) as a subclass of `cco:DirectiveICE` that satisfies a specific PCI DSS requirement (Y). This mapping allows for a unified view of compliance, where a single directive may satisfy obligations under both ISO 27001 and PCI DSS.

The integration of these frameworks often reveals overlaps where a single technical control (e.g., encryption) satisfies multiple distinct regulatory requirements. However, the ontology treats these as distinct axiomatic relationships to preserve the specific context of each regulation. The `pci_dss_requirement` table links the PCI DSS requirement to the "control-only" threat class, ensuring that the payment card industry requirements are grounded in the same threat-mitigation logic used for the broader ISMS.

This structure supports automated compliance reporting. By querying the ontology, an auditor can instantly retrieve all directives that satisfy PCI DSS Requirement 8 (Identify and authenticate access to system components), for instance, and verify that the underlying threat classes are adequately addressed.

## 4.5 Requirement Equivalence: Specification and Targeting

The complexity of modern governance frameworks necessitates the definition of requirements that are equivalent to the intersection of specific directives and target applications. The axiom `requirement_equiv_specifies_target` defines a class (X) that is equivalent to the intersection of `cco:DirectiveICE`, a specification (Y), and a target application (Z). In logical terms, X exists if and only if it specifies Y and applies to Z.

This axiom is particularly useful for defining system-specific policies. For example, a "Two-Factor Authentication" directive may be equivalent to the specification of "ISO_A_9_1" applied specifically to a "RemoteAccessSystem." This equivalence allows the ontology to infer that if the Two-Factor Authentication directive is present, the ISO control is satisfied for that specific target.

The relational schema for this axiom, `t_requirement_equiv_specifies_target`, includes a foreign key reference to the ISO 27001 subclassification table. This ensures that the specification component of the equivalence is always grounded in a valid control class. The table below demonstrates how specific technical requirements are decomposed into their constituent specifications and targets.

|---|---|---|---|
| REQ_EQUIV_1 | TwoFactorAuthentication | ISO_A_9_1 | RemoteAccessSystem |
| REQ_EQUIV_2 | DatabaseEncryptionAtRest | ISO_A_10_1 | CustomerDatabase |
| REQ_EQUIV_3 | LogRetentionPolicy | ISO_A_12_3 | CentralLogServer |
| REQ_EQUIV_4 | AdminSessionTimeout | ISO_A_8_2 | PrivilegedManagementConsole |

## 4.6 General Risk Addressing

While specific controls may address threats exclusively, the broader security posture relies on controls that address risks as part of a composite mitigation strategy. The axiom `control_addresses_risk` defines a general relationship where a control class (X) is a subclass of `cco:DirectiveICE` that addresses a risk class (Y). Unlike the "control-only" axiom, this does not imply exclusivity, allowing for a many-to-many relationship between controls and risks.

This generalization is essential for defense-in-depth strategies. For instance, a "NetworkFirewall" addresses the risk of "UnauthorizedAccess," but it is not the *only* control that does so; "Intrusion Detection Systems" and "Access Control Lists" may also address the same risk class. The ontology captures this through the existential quantifier (`some`), permitting multiple controls to address a single risk without logical conflict.

The `t_control_addresses_risk` table provides the evidence base for this general mapping. It links the control classes back to the ISO 27001 subclassification, ensuring that all risk-addressing activities are traceable to the primary governance framework. This table serves as a master index for the organization's risk mitigation landscape.

|---|---|---|
| CTRL_ADDR_1 | NetworkFirewall | ISO_A_9_1 |
| CTRL_ADDR_2 | IntrusionDetectionSystem | ISO_A_9_1 |
| CTRL_ADDR_3 | SecurityAwarenessTraining | ISO_A_8_2 |
| CTRL_ADDR_4 | DataLossPreventionTool | ISO_A_10_1 |
