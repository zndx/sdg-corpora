# Chapter 4: Governance Processes: Attestation and Evidentiary Traceability

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing two critical mechanisms within the regulatory compliance framework: the binding of agents to attestations and the verification of descriptive claims through evidentiary traces. The definitions herein are derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), providing a deterministic schema for mapping governance activities to relational data structures. Organizations must implement these structures to ensure that all compliance-related processes are auditable, immutable, and semantically grounded. The following sections detail the axioms governing `attestation_signed_by` and `trace_supports_claim`, providing the necessary context for data population and system validation.

## 4.2 Attestation and Personnel Accountability

### 4.2.1 Ontological Definition

In the context of governance frameworks, an attestation is not merely a signature but a distinct processual entity that serves as a formal declaration of truth or validity. The axiom `attestation_signed_by` establishes that a specific class of process (`{X}`) is a subclass of `bfo:0000015` (Process) and necessitates the participation of a `cco:Person` via the `sdg:signedBy` object property.

This relationship imposes a strict liability and accountability structure. The process is invalid unless it is explicitly signed by an authorized natural person. The Manchester syntax for this axiom is expressed as:

`Class: {X:Class} SubClassOf: bfo:0000015, sdg:signedBy some cco:Person`

Verbalized, this asserts that `{X}` is a process that is signed by a person. This distinction is crucial for audit trails; it separates automated system logs (which may be generated by agents) from legally binding attestations, which require human agency. The `cco:Person` referenced in this axiom must be a verified individual within the organization’s identity management system, possessing the requisite authority to execute the specific process class `{X}`.

### 4.2.2 Operational Context and Compliance Obligations

Important! Read the following operational parameters carefully before implementing the attestation workflow. The deployment of this ontology assumes that the organization maintains a rigorous registry of personnel credentials.

When an agent initiates an instance of class `{X}`, the system must freeze the process state until the `sdg:signedBy` property is populated with a valid `cco:Person` identifier. This is analogous to the acceptance of terms in a standard End-User License Agreement (EULA), where the act of using the software indicates acceptance. Here, the act of signing the process instance indicates the person's acceptance of responsibility for the content of the attestation.

For example, consider a `SoftwareLicenseCompliance` process. This process involves the review of installed software assets against purchased licenses. The process remains open—a draft state—until the Chief Information Officer (CIO), acting as the `cco:Person`, applies their cryptographic signature. At this moment, the process instance transitions to an "Attested" state. It is incumbent upon the governance officers to ensure that the person signing has more than three decades of experience or the equivalent certification authority, ensuring that the signatory possesses the domain knowledge required to validate the process.

Failure to link the process to a valid person results in a nullification of the audit trail. The system must flag such instances as "Orphaned Processes" and initiate an immediate remediation workflow.

### 4.2.3 Relational Representation

The relational schema for `attestation_signed_by` is designed to enforce the primary key constraints of the process instance while capturing the class definition of the attestation. The table `t_attestation_signed_by` serves as the registry for these process classes.

The primary key is the `id` column, which serves as the unique identifier for the attestation process definition. The `x` column denotes the specific Class of the attestation (e.g., `AnnualRiskAssessment`, `PolicyEndorsement`). This structure allows the governance framework to query all process classes that require human signature, facilitating dynamic form generation and workflow routing.

## 4.3 Evidentiary Traceability and Claim Support

### 4.3.1 Ontological Definition

The second pillar of the governance framework concerns the verification of assertions through evidentiary traces. The axiom `trace_supports_claim` posits that a process class `{X}` is a subclass of `bfo:0000015` (Process) which utilizes the `sdg:supportsClaim` property to reference a `cco:DescriptiveICE` (Descriptive Information Content Entity).

The Manchester syntax is defined as:

`Class: {X:Class} SubClassOf: bfo:0000015, sdg:supportsClaim some cco:DescriptiveICE`

Verbalized, `{X}` is a process that supports a claim described by an information content entity. This axiom is foundational for "long-tail" compliance, where the validity of a high-level governance statement depends on low-level, granular data traces. A `cco:DescriptiveICE` may be a textual requirement, a regulatory clause, or a specific data point (e.g., "The system logged the access at 6:00pm").

The process `{X}` acts as the bridge between the raw data and the claim. It is the active verification mechanism—such as a log scan, a hash verification, or a physical audit—that generates the proof required to uphold the `cco:DescriptiveICE`.

### 4.3.2 Evidence Standards and Audit Trails

To maintain the integrity of the governance framework, the trace process must be immutable and timestamped. The evidence generated by `{X}` must be anchored to the specific claim it supports. For instance, if the `cco:DescriptiveICE` is the statement "Venue capacity did not exceed 200 persons," the supporting process `{X}` might be `TurnstileLogAnalysis`.

This structure mirrors the precision found in operational reports and notices. Just as an event notice specifies the Date, Time, Venue, and Cost, the trace process must capture the metadata of the verification event. The system must record *who* executed the trace, *when* it was executed, and the specific *data hash* of the claim object.

Consider a scenario involving a physiotherapy service booking. The claim (DescriptiveICE) is "Body fat measurements were conducted on 27 May 2014." The supporting process `{X}` is `MeasurementDataIngestion`. This process ingests the laptop data, generates a timestamped record, and links it to the claim. If the claim is audited, the system retrieves the `MeasurementDataIngestion` process instance to prove the claim's validity.

### 4.3.3 Relational Representation

The table `t_trace_supports_claim` catalogs the process classes that function as evidentiary traces. The schema requires a unique `id` for the process class and the `x` column representing the class name itself.

This table is distinct from the attestation table in that it links to information entities rather than human agents. It is the technical backbone of the audit report, providing the lineage data necessary for forensic analysis. The `x` values in this table typically denote automated verification routines or data ingestion workflows.

## 4.4 Integration and Verification

The governance framework relies on the strict separation of concerns between attestation (human accountability) and traceability (evidentiary support). While Section 4.2 ensures that a qualified human validates the outcome, Section 4.3 ensures that the data underpinning that outcome is verifiable and grounded in process.

When an auditor reviews the system, they will query `t_attestation_signed_by` to identify the responsible parties for high-level governance decisions. Simultaneously, they will query `t_trace_supports_claim` to validate the data lineage supporting those decisions. A compliant governance entry must possess valid references in both domains; a signed attestation based on an unsupported trace is considered a violation of the framework's integrity principles.
