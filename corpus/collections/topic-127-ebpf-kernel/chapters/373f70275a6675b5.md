# Chapter 7: Directive Governance Patterns in School Authorization Systems

This chapter presents five relational tables that instantiate core axioms of directive governance. The tables capture attestations as processes, requirements as directive information content entities, and the mandatory linkages among signers, verifiers, and evidence. All column values are drawn from the domain of compiled releases and authorizations maintained by Azalea Mountain School for the 2015–16 academic year.

## 1 Axiom Instantiation and Table Definitions

### 1.1 Attestations Requiring Minimum Signers

Axiom 1 states that an attestation is a process that must be signed by at least one person. The table records each attestation instance together with its class identifier, enforcing the minimum cardinality through the presence of a non-null x value.

```sql
CREATE TABLE t_attestation_min_one_signer (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| att-001 | ParentGuardianRelease |
| att-002 | EmergencyContactAttestation |
| att-003 | MediaPermissionAttestation |
| att-004 | FieldTripAuthorization |
| att-005 | HealthRecordAttestation |

### 1.2 Requirements Requiring Minimum Verification

Axiom 2 states that a requirement is a directive information content entity verified by at least one class. The table stores the requirement identifier, its class, and the mandatory verifier class, with y serving as a foreign-key reference to verification classes.

```sql
CREATE TABLE t_requirement_min_one_verification (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| req-101 | AnnualHealthRequirement | VerificationByNurse |
| req-102 | ClubParticipationRequirement | VerificationByTeacher |
| req-103 | PEKitRequirement | VerificationByCoach |
| req-104 | SummerTermClubRequirement | VerificationByAdministrator |

### 1.3 Verifications Producing Evidence

Axiom 3 states that a verification is a process that produces at least one evidence item. The table links each verification instance to its evidence class, with y acting as a foreign-key reference usable in subsequent joins.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| ver-201 | NurseReviewProcess | SignedHealthForm |
| ver-202 | TeacherCheckProcess | ClubRosterEntry |
| ver-203 | CoachInspectionProcess | PEClothingLog |
| ver-204 | AdminAuditProcess | ClubAllocationRecord |

### 1.4 Requirements Specifying Targets

Axiom 4 defines a requirement as equivalent to a directive that specifies a target class and applies to an additional class. The table therefore contains three non-key columns, each representing a distinct ontological role.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y | z |
|----|---|---|---|
| req-301 | MediaReleaseRequirement | MediaReleaseForm | StudentRecord |
| req-302 | FieldTripRequirement | PermissionSlip | TripManifest |
| req-303 | HealthUpdateRequirement | MedicalConsent | ContactDatabase |

### 1.5 Attestations Signed by Persons

Axiom 5 states that an attestation is signed by a person. The table records the attestation class that participates in the signing relation, providing the concrete signer linkage required by the minimum-cardinality axiom.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| att-401 | ParentGuardianRelease |
| att-402 | EmergencyContactAttestation |
| att-403 | MediaPermissionAttestation |
| att-404 | FieldTripAuthorization |

## 2 Cross-Join Demonstration

A multi-hop query can retrieve the evidence produced for a given requirement by traversing the foreign-key columns. Consider the question: “Which evidence class is produced for the AnnualHealthRequirement, and which attestation class supplies the required signer?”

The path begins at t_requirement_min_one_verification (req-101), follows y to VerificationByNurse, joins to t_verification_min_one_evidence on x, then follows the attestation tables via shared class names. The resulting joined row is:

req-101 | AnnualHealthRequirement | VerificationByNurse | ver-201 | NurseReviewProcess | SignedHealthForm | att-001 | ParentGuardianRelease

This single tuple demonstrates that the health requirement is verified by a nurse review that produces a signed health form, which in turn rests on a parent-guardian release attestation.
