# Chapter 12: Directive Governance Structures in Authorization Systems

This chapter presents five core ontological templates that govern the creation, verification, and attestation of directives within authorization workflows. The templates are realized as a fixed relational schema whose rows encode instances drawn from compiled school releases and medical record access controls. Primary keys identify directive or process instances; foreign-key columns encode the signedBy, verifiedBy, producesEvidence, specifies, and appliesTo relations required by the axioms.

## 1. Attestation as a Signed Process

Axiom attestation_min_one_signer classifies an attestation as a process that must be signed by at least one person. The table therefore stores only the attestation identifier and the process class; any subsequent join on the x column recovers the required signer cardinality.

```sql
CREATE TABLE t_attestation_min_one_signer (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 1.1 Requirement Verified by a Distinct Class

Axiom requirement_min_one_verification states that every directive information content entity must be verified by at least one verification class. Column y therefore functions as a foreign key to verification instances; a join on y yields the mandated verification entity.

```sql
CREATE TABLE t_requirement_min_one_verification (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 1.2 Verification Producing Evidence

Axiom verification_min_one_evidence classifies verification as a process that produces at least one evidence class. Column y records the evidence class; joins from t_requirement_min_one_verification.y to this table’s x recover the evidence chain.

```sql
CREATE TABLE t_verification_min_one_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 1.3 Requirement Specifying Target and Applicability

Axiom requirement_equiv_specifies_target equates a directive with the conjunction of a specification class and an applicability class. Columns y and z are non-null foreign keys; a three-way join across y, z, and an attestation table answers “which directive applies to which target.”

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y | z |
| id | x | y | z |
| req-010 | ParentReleaseForm | SpecifiesSignature | AppliesToStudent |
| req-011 | HealthRecordDirective | SpecifiesAccessRight | AppliesToRecord |
| req-012 | ConventionRegistration | SpecifiesEvent | AppliesToAttendee |
| req-013 | DataAccessDirective | SpecifiesDataScope | AppliesToPatient |
| req-014 | ProcedureAuthorization | SpecifiesProcedure | AppliesToCase |

## 1.4 Attestation Signed by Person

Axiom attestation_signed_by asserts that an attestation process is signed by some person. The table records the attestation class; cross-joins with t_attestation_min_one_signer confirm the signer cardinality already required by the first axiom.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 2. Multi-Hop Query Example

Question: Which evidence supports the verification of the requirement that applies to a student record release signed by a parent guardian?

Start with t_requirement_equiv_specifies_target where x = “StudentRecordRelease”.  
Join its y to t_requirement_min_one_verification.y (y = “VerifyCustodyOrder”).  
Join that verification’s x to t_verification_min_one_evidence.x (y = “CourtDocument”).  
The resulting joined row is:

req-015 | StudentRecordRelease | VerifyCustodyOrder | Student | att-005 | ParentGuardian | ver-025 | CourtDocument
