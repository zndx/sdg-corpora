# Chapter 7: Relational Mapping of Compliance Artifacts and Information Content Entities

## 7.1 Scope and Preamble

This chapter delineates the formal ontological mapping required to integrate compliance artifacts, descriptive claims, and directive information content entities within a unified governance framework. The primary objective is to establish a rigorous data schema that supports the traceability of organizational identifiers, such as tax IDs, against descriptive information content entities (ICEs) and regulatory directives. By adhering to the axioms defined herein, auditors and systems architects may ensure referential integrity between physical or digital artifacts and the claims asserted upon them, particularly within the context of ISO 27001 compliance and financial reporting standards. The following sections provide a detailed decomposition of these mappings, supported by relational schema implementations grounded in the Common Core Ontologies (CCO) and specific domain extensions (SDG).

## 7.2 Artifact Identification and Taxation Claims

In the context of enterprise governance, an **Artifact** is defined as a distinct physical or digital entity that is the product of a design process. To establish legal and fiscal accountability, every artifact subject to audit must be linked to a formal taxation identifier. This relationship is axiomatically defined such that an Artifact (*X*) possesses a Tax ID (*Y*), where the Tax ID itself is treated not merely as a string literal but as an instance of a specific class within the ontology.

The relational projection of this axiom creates a dependency between the artifact record and a descriptive claim. This structure ensures that the assignment of a tax identifier is an auditable event, rather than a static attribute. The table below embodies the axiom `schemaorg_org_taxid`, wherein the primary key identifies the relationship, the column `x` references the Artifact, and the column `y` references the Tax ID entity. The foreign key constraint mandates that every Tax ID must correspond to a valid entry in the outlier claims table, enforcing a strict validation layer where identifiers are treated as distinct information objects.

**Table 7.1: Artifact Tax ID Mapping (t_schemaorg_org_taxid)**

| id | x (Artifact) | y (Tax ID) |
| :--- | :--- | :--- |
| rel_tax_001 | cco:Artifact_001 | tax_id_claim_alpha |
| rel_tax_002 | cco:Artifact_002 | tax_id_claim_beta |
| rel_tax_003 | cco:Artifact_003 | tax_id_claim_gamma |
| rel_tax_004 | cco:Artifact_004 | tax_id_claim_delta |
| rel_tax_005 | cco:Artifact_005 | tax_id_claim_epsilon |

The implementation of this schema allows for the differentiation between the artifact itself (e.g., a software license or a hardware component) and the administrative claim regarding its tax status. By isolating the Tax ID into a separate relational entity referenced via a foreign key, the system accommodates scenarios where multiple artifacts may share a single tax jurisdiction claim, or where a single artifact may possess multiple tax identifiers over its lifecycle due to mergers or acquisitions.

## 7.3 Descriptive Information Content Entities and Attribute Sets

A **Descriptive Information Content Entity (ICE)** is a fundamental ontological construct representing a proposition that is intended to be true about some entity. In compliance frameworks, descriptive ICEs often function as "outlier claims"—assertions that require verification against established baselines. The axiom `outlier_claim_min_one_attribute` posits that any such Descriptive ICE (*X*) must possess an AttributeSet (*Y*) containing a minimum of one attribute.

This axiom is critical for audit trails because it prevents the existence of null or empty claims. If a system records a claim regarding an artifact's compliance status, it must simultaneously record the attributes that substantiate or define that claim. The relational schema for this concept introduces a circular dependency with the Tax ID table; the AttributeSet (*Y*) of a claim is, in this specific schema topology, a reference back to a Tax ID record. This circularity models the real-world requirement that descriptive claims about an artifact (such as its origin or status) are often anchored to the artifact's registered legal identifier.

**Table 7.2: Outlier Claims and Attribute Sets (t_outlier_claim_min_one_attribute)**

| id | x (Descriptive ICE) | y (Attribute Set) |
| :--- | :--- | :--- |
| claim_001 | cco:DescriptiveICE_Audit_01 | rel_tax_001 |
| claim_002 | cco:DescriptiveICE_Audit_02 | rel_tax_002 |
| claim_003 | cco:DescriptiveICE_Audit_03 | rel_tax_003 |
| claim_004 | cco:DescriptiveICE_Audit_04 | rel_tax_004 |
| claim_005 | cco:DescriptiveICE_Audit_05 | rel_tax_005 |

In the table above, the `x` column represents the specific claim instance (e.g., "The artifact is compliant with region-specific fiscal regulations"), while the `y` column links to the Attribute Set. Given the foreign key constraint `REFERENCES t_schemaorg_org_taxid(id)`, the attribute set is effectively the Tax ID record itself. This design enforces the rule that a claim cannot exist in isolation; it must be tethered to a concrete, identifiable artifact profile.

## 7.4 Designative Attributes in Information Entities

To ensure the semantic interoperability of descriptive claims, the ontology further stipulates that a Descriptive ICE must possess at least one **Designative ICE**. A Designative ICE functions as a name, label, or identifier that signifies the entity to which the descriptive claim refers. This is distinct from the attribute set discussed in the previous section; while the attribute set provides the data content (e.g., the Tax ID string), the Designative ICE provides the semantic label required for indexing and retrieval.

The axiom `attribute_set_min_one` formalizes this requirement. The relational projection is straightforward, consisting of a primary key and the reference to the Descriptive ICE. This table serves as a validation registry, ensuring that for every descriptive claim entered into the system, a corresponding designative label exists. This prevents the "orphan record" problem where data exists but cannot be queried or referenced by human operators or downstream reporting tools.

**Table 7.3: Attribute Set Designations (t_attribute_set_min_one)**

| id | x (Descriptive ICE) |
| :--- | :--- |
| attr_set_01 | cco:DescriptiveICE_Label_01 |
| attr_set_02 | cco:DescriptiveICE_Label_02 |
| attr_set_03 | cco:DescriptiveICE_Label_03 |
| attr_set_04 | cco:DescriptiveICE_Label_04 |
| attr_set_05 | cco:DescriptiveICE_Label_05 |

The data in Table 7.3 represents the binding layer between the raw data of the claim and its representation in the governance interface. By enforcing the presence of these designative attributes, the ontology ensures that all compliance-relevant information is machine-readable and human-interpretable, a prerequisite for automated audit reporting.

## 7.5 ISO 27001 Clause Subclassifications

Governance frameworks frequently require the mapping of internal directives to external regulatory standards. The axiom `iso27001_clause_subclass` addresses this by defining a relationship wherein a Directive ICE (*X*)—an internal policy or procedural mandate—references a specific ISO 27001 Clause (*Y*). In this schema, the ISO Clause is modeled as a subclass of the Descriptive ICE, allowing the organization to attach specific metadata or audit evidence to the standard itself.

The relational structure for this axiom links the Directive to the Descriptive ICE (the Clause). The foreign key constraint ensures that the ISO clause referenced in the directive is a valid, instantiated claim within the system. This allows the organization to maintain a dynamic mapping of its internal controls to the ISO 27001 standard. For instance, an internal "Access Control Policy" (Directive) can be formally linked to "Annex A.9 Access Control" (ISO Clause) via this table.

**Table 7.4: ISO 27001 Clause Mapping (t_iso27001_clause_subclass)**

| id | x (Directive ICE) | y (ISO Clause) |
| :--- | :--- | :--- |
| iso_map_001 | cco:DirectiveICE_Access_Policy | claim_001 |
| iso_map_002 | cco:DirectiveICE_Crypto_Policy | claim_002 |
| iso_map_003 | cco:DirectiveICE_Physical_Security | claim_003 |
| iso_map_004 | cco:DirectiveICE_Ops_Security | claim_004 |
| iso_map_005 | cco:DirectiveICE_Comms_Security | claim_005 |

Note that the `y` column in Table 7.4 references the `id` from the Outlier Claims table. This implies that the ISO clauses are treated as specific instances of descriptive claims within the system's ontology. This approach provides flexibility; the organization can define the text of the ISO clause as a descriptive claim and then link multiple internal directives to that single definition, ensuring consistency across the compliance management system.

## 7.6 Product Pricing and Valuation Assertions

The final axiom addressed in this chapter, `schemaorg_product_price`, pertains to the economic attributes of artifacts. It asserts that an Artifact (*X*) has a Price (*Y*), where the Price is modeled as a specific class of entity. Similar to the Tax ID mapping, this structure treats the price not as a primitive numerical value but as a distinct information entity that can be annotated, versioned, and audited.

The relational schema links the Artifact to the Price entity, which in turn is validated against the Outlier Claims table. This validation step is crucial for financial compliance; it ensures that any price associated with an artifact is backed by a descriptive claim (e.g., a quote, an invoice, or a valuation assessment). By treating the price as a node in the graph rather than a simple property, the system can track the history of price changes and the provenance of valuation data.

**Table 7.5: Product Price Assertions (t_schemaorg_product_price)**

| id | x (Artifact) | y (Price) |
| :--- | :--- | :--- |
| price_rel_001 | cco:Artifact_001 | claim_001 |
| price_rel_002 | cco:Artifact_002 | claim_002 |
| price_rel_003 | cco:Artifact_003 | claim_003 |
| price_rel_004 | cco:Artifact_004 | claim_004 |
| price_rel_005 | cco:Artifact_005 | claim_005 |

In this configuration, the `y` column (Price) references a claim ID. This implies that the specific value of the price is stored within the descriptive claim structure defined in Section 7.3. This abstraction allows for complex pricing models, such as tiered pricing or subscription-based valuations, to be encapsulated within the claim entity while maintaining a direct link to the artifact being sold or licensed.
