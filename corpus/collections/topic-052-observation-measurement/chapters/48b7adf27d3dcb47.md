# Chapter 4: Entity Identification and Attribute Verification Protocols

## 4.1 Scope and Preamble

This chapter establishes the mandatory protocols for the identification, classification, and verification of entities within the enterprise governance framework. It delineates the formal ontological structures required to map artifacts to their regulatory and financial attributes, ensuring compliance with ISO 27001 standards and fiscal reporting requirements. The definitions herein are binding for all audit engagements and system documentation exercises. Furthermore, this chapter specifies the relational data structures necessary to maintain referential integrity between physical artifacts, descriptive claims, and directive information content entities.

## 1. Tax Identification and Artifact Classification

The foundational element of supply chain compliance is the rigorous association of `cco:Artifact` entities with their respective tax identifiers. In accordance with Axiom 1 (`schemaorg_org_taxid`), every Artifact within the inventory must be subclassified as an entity possessing a specific Tax ID. This relationship is not merely a labeling exercise but a structural assertion that the Artifact (X) is inextricably linked to a Tax ID (Y), where Y is treated as a distinct class of information content entity.

This linkage ensures that all tangible and intangible goods can be traced back to a registered legal entity for fiscal liability purposes. The ontology dictates that the presence of a Tax ID is a definitive characteristic of the Artifact class. Consequently, any system recording an Artifact without this linkage is considered non-compliant and structurally incomplete under the current schema.

### 1.1 Relational Implementation of Tax Identification

To enforce this axiom, the relational schema utilizes the table `t_schemaorg_org_taxid`. This table captures the instance-level data where the primary key (`id`) uniquely identifies the relationship between the Artifact and the Tax ID. The foreign key constraint mandates that the Tax ID (`y`) must correspond to a valid entry in the outlier claims table, thereby ensuring that the identifier itself is a verified, descriptive information content entity rather than an arbitrary string.

*This table embodies Axiom 1 (`schemaorg_org_taxid`), mapping Artifacts to their Tax IDs. The primary key is `id`, and the foreign key `y` references `t_outlier_claim_min_one_attribute(id)`, ensuring the Tax ID is a recognized claim.*

## 2. Descriptive Information Content Entities and Outlier Claims

The verification of entity attributes relies on the formalization of `cco:DescriptiveICE` (Descriptive Information Content Entity). As defined in Axiom 2 (`outlier_claim_min_one_attribute`), these entities represent assertions or claims regarding the properties of an artifact or process. A critical compliance requirement is that every DescriptiveICE must possess a minimum of one Attribute Set (`sdg:hasAttributeSet min 1`).

This structure facilitates the detection of "outlier" claims—data points that deviate from standard baselines—by requiring that every claim be substantiated by a structured set of attributes. In practice, this means that a Tax ID or a Price Claim cannot exist in a vacuum; it must be accompanied by metadata that defines its validity, scope, and origin. The ontology enforces a recursive dependency where the Attribute Set (Y) validates the Claim (X), ensuring that all descriptive data is evidence-anchored.

### 2.1 Relational Implementation of Outlier Claims

The table `t_outlier_claim_min_one_attribute` serves as the central registry for these claims. The schema enforces a circular dependency with the tax identification table to maintain data consistency: the Attribute Set (`y`) of a claim must reference a valid Tax ID relationship. This design ensures that descriptive claims are always tethered to a specific, identifiable artifact context.

**Table 2-1: Outlier Claims and Attribute Sets**
*This table embodies Axiom 2 (`outlier_claim_min_one_attribute`), defining DescriptiveICE entities with required attribute sets. The primary key is `id`, and the foreign key `y` references `t_schemaorg_org_taxid(id)`, creating a dependency loop that validates claims against tax artifacts.*

| id | x (DescriptiveICE) | y (Attribute Set Reference) |
| :--- | :--- | :--- |
| claim_taxid_998 | cco:DescriptiveICE_TaxID_US12345 | rel_tax_001 |
| claim_taxid_774 | cco:DescriptiveICE_TaxID_DE67890 | rel_tax_002 |

| claim_clause_A12 | cco:DescriptiveICE_Clause_A12 | rel_tax_003 |
| claim_attr_spec | cco:DescriptiveICE_Spec_v2 | rel_tax_005 |

## 3. ISO 27001 Directive Mapping

Governance frameworks require that internal directives be explicitly mapped to external compliance standards. Axiom 3 (`iso27001_clause_subclass`) formalizes this by defining a subclass of `cco:DirectiveICE` (Directive Information Content Entity) that specifically references an ISO 27001 Clause (`sdg:iso27001Clause`).

This mapping ensures that organizational policies are not merely abstract documents but are grounded in specific regulatory requirements. The Directive (X) is the internal implementation rule, while the ISO Clause (Y) is the external standard it satisfies. This axiom is critical for audit trails, as it allows automated verification that all necessary controls from the ISO 27001 standard have been addressed by a corresponding internal directive.

### 3.1 Relational Implementation of Directive Mapping

The `t_iso27001_clause_subclass` table records these mappings. To maintain the integrity of the compliance chain, the ISO Clause reference (`y`) must resolve to a valid DescriptiveICE. This constraint implies that the interpretation or instantiation of the ISO Clause within the system is treated as a specific type of claim or observation, subject to the same rigor as other descriptive entities.

**Table 3-1: ISO 27001 Clause Directives**
*This table embodies Axiom 3 (`iso27001_clause_subclass`), linking internal directives to ISO clauses. The primary key is `id`, and the foreign key `y` references `t_outlier_claim_min_one_attribute(id)`, identifying the clause as a specific descriptive claim.*

## 4. Attribute Set Composition

The granular definition of entity properties is governed by Axiom 4 (`attribute_set_min_one`). This axiom stipulates that any `cco:DescriptiveICE` functioning as an Attribute Set must contain at least one `cco:DesignativeICE`. A Designative Information Content Entity refers to a term, name, or label that designates a specific concept or value.

This requirement prevents the existence of empty attribute containers. In a technical audit, an Attribute Set without a Designative ICE is effectively null data. By enforcing the "min 1" constraint, the ontology ensures that every descriptive bucket contains at least one concrete, named data point. This is essential for data quality initiatives and for the automated parsing of compliance reports.

### 4.1 Relational Implementation of Attribute Sets

The table `t_attribute_set_min_one` tracks these Attribute Sets. Unlike other tables in this schema, this table operates independently regarding foreign keys, serving as a lookup for the structural composition of descriptive entities. The primary key (`id`) ensures that each Attribute Set is uniquely identifiable within the system registry.

**Table 4-1: Attribute Set Definitions**
*This table embodies Axiom 4 (`attribute_set_min_one`), listing valid Attribute Sets. The primary key is `id`. There are no foreign key constraints in this specific table, allowing it to define the fundamental building blocks of descriptive data.*

## 5. Product Pricing and Valuation

Financial compliance requires the precise tracking of valuations associated with enterprise artifacts. Axiom 5 (`schemaorg_product_price`) extends the definition of `cco:Artifact` by asserting that it has a Price (`sdg:hasPrice`). Similar to the Tax ID, the Price is modeled as a distinct class (Y), allowing for complex pricing structures, currencies, and historical valuations to be encapsulated within the entity's profile.

This axiom is vital for inventory valuation, asset depreciation calculations, and procurement auditing. By treating the Price as a linked entity rather than a simple primitive data type, the system can track the provenance of the valuation—e.g., whether the price is a list price, a negotiated discount, or a fair market value—through the associated descriptive properties.

### 5.1 Relational Implementation of Product Pricing

The `t_schemaorg_product_price` table manages the relationship between artifacts and their pricing. The foreign key `y` references the `t_outlier_claim_min_one_attribute` table, reinforcing the principle that a price is a claim about value that must be substantiated by attributes (such as currency, date, or source).
