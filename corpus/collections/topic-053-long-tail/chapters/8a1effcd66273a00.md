# Chapter 7: Formal Ontology Constraints in Audit Data Lineage

This chapter delineates the formal ontological constraints governing the generation, annotation, and processing of audit trails within distributed control systems. It establishes the necessary relationships between observational processes, their participant artifacts, and the downstream computational workflows that consume this data. Adherence to these axioms is mandatory for compliance with ISO 8000 data quality standards and ensures that the provenance of every logged entry is traceable to a physical or logical source. The following sections define the specific ontological commitments required for system certification.

## 1. Observation with Participant

### 1.1 Ontological Definition and Scope

In the context of systems governance, an observation is not merely a data point but a temporal entity (`bfo:0000015`, a Process) that necessitates the participation of an independent entity. Specifically, the axiom `observation_with_participant` asserts that any valid observation class {X} must be a subclass of a process that has as a participant a specific `cco:Artifact`. This constraint ensures that automated logging events are not orphaned in the system memory but are causally anchored to a tangible instrument, sensor, or software component.

The verbalization of this axiom—"{X} is something that has participant artifact"—serves as a validation rule for data architects. When defining a new class of observations, such as "ThermocoupleReading" or "UserLoginEvent," the system ontology must explicitly link that class to the artifact which generates or enables it. This linkage prevents the insertion of synthetic or fraudulent data that lacks a provenance chain to a recognized system component.

### 1.2 Implementation in Relational Schemas

To enforce this constraint within a relational database management system (RDBMS), the schema utilizes a primary table, `t_observation_with_participant`. This table catalogs the valid classes of observations that the system is authorized to record. The structure is deceptively simple, containing only an identifier and the class name, but it functions as a lookup registry for validation triggers.

The primary key (`id`) serves as the stable reference for the observation class, while the column `x` denotes the specific class label (e.g., "PressureTransducerLog"). The absence of an explicit "artifact" column in this specific table projection is intentional; the artifact relationship is handled at the ontology definition level (the subclass relationship to `bfo:0000057 some cco:Artifact`). However, for audit purposes, the table below represents the authorized registry of observations where the artifact linkage has been pre-validated.

### 1.3 Compliance Verification

During an audit, compliance officers must verify that for every entry in the log files, the event type maps to an entry in Table 1-1. If a log entry contains a type "SystemOverride" that does not exist in `t_observation_with_participant`, the entry is flagged as non-compliant because the system cannot guarantee that the event was generated by a recognized artifact participant. This rigid mapping is the first line of defense against data integrity attacks.

## 2. Column Tag Subclass

### 2.1 Descriptive Information Content Entities

Once an observation is captured, it must be contextualized to be useful for long-term storage and regulatory reporting. The `column_tag_subclass` axiom introduces the concept of a `cco:DescriptiveICE` (Information Content Entity). This axiom states: "{X} is something that annotates column {Y}."

In this framework, {X} represents a metadata tag or a classification schema (e.g., "Confidential," "PII," "CalibrationData"), and {Y} represents the specific data column or observation class being annotated. This relationship is critical for governance frameworks, as it automates the application of data handling policies based on the content of the log.

### 2.2 Relational Mapping and Foreign Key Constraints

The relational schema for this concept, `t_column_tag_subclass`, enforces a strict dependency between the tag and the target of the annotation. The schema includes a Foreign Key constraint linking column `y` (the annotated target) to the `id` of the `t_observation_with_participant` table.

This structural dependency ensures that one cannot annotate a column that does not correspond to a valid, artifact-participant observation. In effect, the system prevents the creation of "zombie" metadata—tags that point to non-existent data structures. This is a common failure mode in legacy systems where schema drift results in metadata referencing deprecated columns.

**Table 2-1: Annotation and Tagging Registry**

| id | x | y |
| :--- | :--- | :--- |
| TAG-001 | QualityControlMetric | OBS-2023-A |
| TAG-002 | CriticalProcessParameter | OBS-2023-B |
| TAG-003 | AuditTrailMetadata | OBS-2023-D |
| TAG-004 | SecurityLog | OBS-2023-E |
| TAG-005 | AnalyticalResult | OBS-2023-C |

*Table 2-1 defines the descriptive tags ({X}) applied to specific observation classes ({Y}). The Foreign Key constraint on column `y` ensures that tags are only applied to valid, artifact-bound observations defined in Table 1-1.*

### 2.3 Governance Implications

The use of `cco:DescriptiveICE` allows for automated compliance enforcement. For instance, if a tag "CriticalProcessParameter" (TAG-002) is applied to "ReactorTemperatureReading" (OBS-2023-B), the data retention policy engine can automatically infer that this data must be retained for 10 years and signed with a digital hash. The axiom ensures that this inference is grounded in a valid observation class, preventing policy application to arbitrary or undefined data streams.

## 3. Process Min One Input

### 3.1 Workflow Dependency and Input Validation

The final axiom, `process_min_one_input`, addresses the flow of data through the system's processing pipeline. It asserts that a processing class {X} is a process (`bfo:0000015`) that requires a minimum of one input {Y}. The verbalization, "{X} is a process," is expanded in the ontology to include the restriction `sdg:hasInput min 1 {Y}`.

This constraint is fundamental to workflow validation. It prohibits the definition of "spontaneous" processes that generate data without consuming input. In a regulated environment, every derived value must be traceable back to a source observation. This axiom enforces that traceability at the class definition level.

### 3.2 Schema Structure and Referential Integrity

The table `t_process_min_one_input` implements this logic. Like the tagging table, it relies on a Foreign Key constraint, where the input `y` must reference a valid `id` from `t_observation_with_participant`. This creates a directed graph in the database schema: Processes consume Observations, and Observations are generated by Artifacts.

By enforcing this relationship in the database layer, the system guarantees that no process definition can be instantiated unless it is linked to a valid input stream. This prevents logic errors where a calculation routine might be inadvertently disconnected from its data source.

**Table 3-1: Process Input Dependency Mapping**

| id | x | y |
| :--- | :--- | :--- |
| PROC-101 | VibrationAnalysisAlgorithm | OBS-2023-A |
| PROC-102 | ThermalLimitVerification | OBS-2023-B |
| PROC-103 | PurityCalculation | OBS-2023-C |
| PROC-104 | AccessControlVerification | OBS-2023-D |
| PROC-105 | IntrusionDetectionLogic | OBS-2023-E |

*Table 3-1 maps the computational processes ({X}) to their required input observations ({Y}). The constraint `min 1` is satisfied by the row-level insertion, ensuring every process has at least one valid input source.*

### 3.4 Audit and Verification Protocol

When auditing the system logic, reviewers query `t_process_min_one_input` to verify that all critical calculations (e.g., "PurityCalculation") are consuming the correct raw data inputs. If "PurityCalculation" (PROC-103) were pointing to a deleted or null observation, the Foreign Key constraint would fail, raising a critical schema violation alert. This ensures the integrity of the data lineage from the moment the artifact participates in the observation, through the tagging of that data, to its final consumption by a computational process.
