# Chapter 4: Verification of Process Artifacts and Input Constraints in Audit Frameworks

This chapter delineates the formal specifications for verifying process integrity within enterprise governance frameworks. It establishes the ontological definitions required to trace the lineage of observations, the application of descriptive metadata to data columns, and the validation of process inputs. The provisions herein are mandatory for systems requiring high-assurance audit trails and are designed to ensure that all process-dependent artifacts are accounted for in the relational schema.

## 1.0 Observation with Participant Artifact

### 1.1 Axiomatic Definition and Scope

In accordance with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), an observation is not merely a static data point but a temporal entity occurring over a span of time. Specifically, the class `ObservationWithParticipant` is axiomatically defined as a subclass of `bfo:0000015` (Process). This classification mandates that for an observation to be validly recorded, it must possess a participant that is an instance of `cco:Artifact`.

The verbalization of this axiom asserts that the subject entity is something that has a participant artifact. In practical terms, this distinguishes a passive recording from an active measurement process. An observation requires the involvement of a physical instrument or tool—the artifact—to capture the state of a system. This dependency is critical for audit compliance, as it anchors the digital record to a physical reality, ensuring that the data is not generated ex nihilo but is the result of a specific, artifact-mediated interaction.

### 1.2 Relational Implementation

The relational projection of this axiom is realized in the table `t_observation_with_participant`. The primary key of this table is the unique identifier `id`, which serves as the immutable reference for the specific observation instance. The column `x` denotes the class of the observation being recorded.

The structure of this table enforces the requirement that every entry represents a process involving an artifact. This table functions as the central registry for all events that generate primary data within the system. It acts as the parent entity for subsequent annotations and process dependencies, establishing the foundational layer of the audit trail.

### 1.3 Compliance and Verification Protocols

When auditing systems against this axiom, compliance officers must verify that for every row in `t_observation_with_participant`, corresponding physical evidence exists for the artifact referenced in the process definition. For instance, the `ThermocoupleCalibrationReading` (OBS-2023-001) implies the existence and utilization of a specific thermocouple device. Failure to link the digital observation to a physical asset inventory constitutes a violation of the data integrity framework.

Furthermore, the classification of `x` must be consistent with the controlled vocabulary of the ontology. Free-text entry is prohibited; values must be valid class names defined in the system ontology. This ensures that the `x` column remains queryable and semantically consistent across the enterprise data warehouse.

## 2.0 Column Tag Subclass and Annotation

### 2.1 Descriptive Information Content Entities

The second axiom governing the framework addresses the semantic enrichment of data through the use of Descriptive Information Content Entities (ICE). The class `ColumnTagSubclass` is defined as a subclass of `cco:DescriptiveICE`. Its primary function is to annotate specific data columns, thereby providing context, classification, or constraint metadata to the raw observations.

The Manchester syntax for this axiom specifies that `ColumnTagSubclass` has the object property `sdg:annotatesColumn` targeting some class `{Y}`. In the verbalization, `{X}` is something that annotates column `{Y}`. This relationship is pivotal for governance, as it allows the organization to apply regulatory tags (e.g., "Confidential," "PII," "Export Controlled") to specific data fields generated by the observation processes.

### 2.2 Relational Dependencies and Foreign Keys

The relational schema for `t_column_tag_subclass` introduces a referential integrity constraint that binds metadata to the source observation. The table consists of columns `id`, `x` (the tag class), and `y` (the target column/observation).

Crucially, the column `y` is defined as a `NOT NULL` field and establishes a Foreign Key constraint referencing `t_observation_with_participant(id)`. This dependency enforces the rule that a descriptive tag cannot exist in isolation; it must annotate a valid, pre-existing observation process. This structure prevents "orphan" metadata and ensures that the lineage of any tag can be traced back to the specific event (observation) that produced the data being tagged.

### 2.3 Governance and Data Lineage

The implementation of `t_column_tag_subclass` facilitates automated compliance reporting. By querying the `x` column, auditors can instantly isolate all observations involving sensitive or safety-critical data. For example, the `SafetyCriticalFlag` (TAG-SAFE-005) applied to `OBS-2023-003` triggers specific retention and access control policies mandated by industrial safety regulations.

It is incumbent upon data stewards to ensure that the values in `y` strictly correspond to valid identifiers in the observation table. Any attempt to insert a tag with a non-existent `y` value will result in a referential integrity violation at the database level, thereby enforcing the ontology's structural constraints at the point of data entry.

## 3.0 Process Minimum One Input

### 3.1 Process Input Validation

The third axiom defines the operational dependencies between distinct processes. The class `ProcessMinOneInput` is a subclass of `bfo:0000015` (Process), characterized by the restriction `sdg:hasInput min 1 {Y:Class}`. This axiom asserts that a process of this type cannot initiate unless it consumes at least one input of a specified class.

Verbalized, `{X}` is a process that requires `{Y}` as an input. This formalism is essential for modeling complex workflows where downstream operations are entirely dependent on the successful completion of upstream data collection or manufacturing steps. It moves the ontology from a descriptive state to a prescriptive one, defining the conditions of possibility for workflow execution.

### 3.2 Schema Structure and Referential Integrity

The table `t_process_min_one_input` encodes these dependencies. Similar to the tagging schema, it relies on a Foreign Key constraint to maintain data integrity. The columns are `id` (the unique process identifier), `x` (the class of the dependent process), and `y` (the required input).

The column `y` references `t_observation_with_participant(id)`. This linkage confirms that the input required by the process is specifically an observation event involving an artifact. In other words, the dependent process relies on the data generated by a specific observation. This circular dependency—Process requires Observation, Observation is a Process—creates a rigorous chain of evidence where every step is verifiable against the previous one.

### 3.3 Operational Impact and Workflow Control

The enforcement of the `min 1` cardinality constraint via this schema ensures that workflows cannot proceed with missing data. For instance, the `ThermalLimitAnalysis` (PROC-ANL-101) is explicitly dependent on the `ThermocoupleCalibrationReading` (OBS-2023-001). If the observation is missing, invalid, or deleted, the referential integrity constraint prevents the creation of a valid input record for the analysis process.

In operational environments, this schema supports the generation of "ready-state" reports. System architects can query `t_process_min_one_input` to determine which processes are currently stalled due to a lack of required inputs. This capability is vital for maintaining throughput in regulated environments where skipping steps constitutes a compliance breach. The strict foreign key enforcement ensures that the "input" is not a vague reference but a specific link to a recorded, artifact-mediated observation.
