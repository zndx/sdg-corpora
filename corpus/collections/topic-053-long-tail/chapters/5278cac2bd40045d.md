# Chapter 4: Semantic Provenance and Workflow Dependency Structures in Regulatory Data Systems

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish rigorous data provenance and workflow dependencies within regulated digital environments. It addresses the necessity of defining atomic observation events, the application of descriptive metadata to specific data columns, and the logical constraints governing process inputs. The definitions provided herein are derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that all data entities are anchored to a deterministic semantic framework. Compliance with these structures is mandatory for systems requiring high-fidelity audit trails, such as those found in pharmaceutical manufacturing, financial transaction logging, and environmental monitoring. The following sections provide the axiomatic definitions, relational schema implementations, and compliance verification protocols for three core concepts: Observation with Participant Artifact, Column Tag Subclass, and Process Minimum One Input.

## 4.2 Observation with Participant Artifact

### 4.2.1 Axiomatic Definition and Ontological Basis

The foundational unit of auditability in any technical system is the observation. In the context of the BFO, an observation is not merely a static data point but a temporalized occurrence—a process that unfolds over time. Specifically, we define the class of entities that are processes which necessarily involve a participant artifact. This relationship is axiomatized as follows:

**Class:** {X:Class} **SubClassOf:** bfo:0000015, bfo:0000057 some cco:Artifact

Verbalized, {X} is something that has participant artifact. Here, `bfo:0000015` denotes the class *Process*, representing an occurrent that has temporal parts and unfolds in time. The object property `bfo:0000057` (has participant) links this process to a specifically dependent continuant or an independent continuant that plays a role within the process. In this schema, the participant is restricted to `cco:Artifact`, referring to a material entity that is created or modified by some process, or which plays a role in the process.

This distinction is critical for auditability. It separates the raw event (the reading, the log entry, the scan) from the instrument or object that facilitated it. By enforcing the subclass relationship to `bfo:Process`, the system ensures that every observation record is implicitly understood as an event with a start and end time, rather than a disconnected value.

### 4.2.2 Relational Implementation and Constraints

To implement this axiom within a relational database management system (RDBMS), the following schema is utilized. The table `t_observation_with_participant` serves as the central registry for all processual events that involve an artifact.

The primary key `id` serves as the unique identifier for the specific observation instance. The column `x` denotes the class of the observation (e.g., "CalibrationReading," "SensorLog"), which must be a subclass of `bfo:Process`. The foreign key constraints implied by the broader ontology (though not explicitly visible as columns in this specific projection) ensure that the artifact referenced exists within the artifact registry.

### 4.2.3 Compliance Verification

In an audit scenario, verification of Axiom 1 involves querying the `t_observation_with_participant` table to ensure that no record exists where the `x` value is a non-processual class (e.g., a static data value or a document). Furthermore, the system must validate that the temporal boundaries of the process are recorded, consistent with the BFO definition of a process. Failure to link an observation to a specific artifact participant results in a semantic orphan—a data point that cannot be traced to a physical source, thereby invalidating the chain of custody.

## 4.3 Column Tag Subclass

### 4.3.1 Descriptive Information Content Entities (ICE)

Once an observation is instantiated, the data it generates must be categorized and annotated for retrieval and analysis. This is achieved through the application of Descriptive Information Content Entities (DescriptiveICE). These are metadata constructs that do not constitute the data itself but describe it. The axiom governing this relationship is defined as:

**Class:** {X:Class} **SubClassOf:** cco:DescriptiveICE, sdg:annotatesColumn some {Y:Class}

Verbalized, {X} is something that annotates column {Y}. In this structure, `X` represents the tag or metadata class (e.g., "UnitOfMeasure," "ConfidenceInterval," "PII_Status"), while `Y` represents the target column within a dataset structure. However, within the relational projection provided, the target `Y` is referenced via the identifier of the observation with which the column is associated. This creates a binding between the metadata and the specific observation event, ensuring that annotations are context-aware.

The use of `cco:DescriptiveICE` as a parent class ensures that the tag is an information entity—it is about something. The property `sdg:annotatesColumn` establishes the specific semantic target of this description. This mechanism allows for the creation of a "long tail" of specific, highly granular metadata tags without altering the core schema of the observation table.

### 4.3.2 Relational Schema and Referential Integrity

The relational schema for this axiom enforces a strict dependency between the tag and the observation. The table `t_column_tag_subclass` contains the tag definitions and links them to the primary key of the observation table.

### 4.3.3 Governance and Audit Implications

The implementation of `t_column_tag_subclass` allows data governance officers to query the system for specific types of metadata across all observations. For instance, selecting all rows where `x` is "Encryption_Status_Indicator" allows for an immediate audit of data security compliance across the entire dataset. The axiom ensures that these tags are not arbitrary text strings but members of defined classes (`SubClassOf: cco:DescriptiveICE`), standardizing the vocabulary used across the enterprise. This standardization is essential for automated compliance reporting and machine-readable data exchange between regulatory bodies.

## 4.4 Process Minimum One Input

### 4.4.1 Workflow Dependency and Input Constraints

Complex technical systems rarely rely on single, isolated observations. Instead, they utilize workflows where downstream processes consume and transform data generated by upstream processes. To model these workflows rigorously, we define the constraint that a specific process class must have a minimum of one input. This is expressed axiomatically as:

**Class:** {X:Class} **SubClassOf:** bfo:0000015, sdg:hasInput min 1 {Y:Class}

Verbalized, {X} is a process that has input {Y}. This axiom utilizes the Universal Quantification restriction (`min 1`) to mandate that no instance of class `X` can exist unless it is specified to have at least one input of class `Y`. In the context of the relational schema, `Y` is instantiated by referencing the `id` of an observation from `t_observation_with_participant`.

This structure effectively creates a directed acyclic graph (DAG) of data dependencies. The "input" to a process is the output (or the state) of a prior observation. By enforcing this constraint at the ontology level, the system prevents the creation of "zombie" processes—computational steps that claim to perform work but lack defined source data.

### 4.4.2 Relational Mapping and Data Flow

The table `t_process_min_one_input` records these dependencies. The column `x` identifies the downstream process class (e.g., "DataValidationRoutine," "StatisticalAggregation"), while `y` identifies the upstream observation that serves as the input.

*Table 4.3 defines the workflow logic by linking a process class (x) to its required input observation (y). The constraint `min 1` is enforced by the `NOT NULL` requirement on the foreign key column `y`, ensuring every process has a traceable data lineage.*

### 4.4.3 System Integrity and Error Handling

From a systems engineering perspective, the `process_min_one_input` axiom provides a validation layer for data pipelines. If a transformation script (Process `X`) is invoked without a valid input file (Observation `Y`), the insertion into `t_process_min_one_input` will fail due to the foreign key violation. This database-level constraint prevents the propagation of null or empty data through the workflow. Furthermore, in the event of a regulatory investigation, this table provides an immediate map of "what data fed into which decision," satisfying the "right to explanation" mandates found in data protection regulations such as GDPR.
