# Chapter 4: Semantic Data Governance and Ontological Compliance

This chapter establishes the formal protocols for integrating Basic Formal Ontology (BFO) and Common Core Ontologies (CCO) within regulated information systems. The scope of this text is restricted to the precise definition and relational mapping of three critical axiom templates: observation with participant, column tag subclass, and process input constraints. These definitions are provided to ensure data lineage, auditability, and semantic consistency across heterogeneous databases. Compliance with these mappings is mandatory for systems requiring high-fidelity evidence trails and automated reasoning over observational data.

## 1. Artifact Participation in Observational Processes

### 1.1 Conceptual Definition

In the context of semantic data modeling, an observation is not merely a static value but a temporal process (bfo:0000015) that necessitates the involvement of specific entities. The axiom template `observation_with_participant` formalizes this by asserting that any class defined as an observation must possess a participant that is an artifact (cco:Artifact). 

The Manchester syntax for this axiom is expressed as:
`Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`

Verbalized, this dictates that "{X} is something that has participant artifact." This distinction is critical for audit trails because it separates the act of measurement (the process) from the instrument or object being measured (the artifact). In compliance frameworks, failing to link a process to its participating artifact invalidates the provenance of the data, rendering it non-compliant with evidentiary standards.

### 1.2 Relational Implementation

The relational projection of this axiom is captured in the table `t_observation_with_participant`. This table serves as a registry for observational classes, ensuring that every entry is explicitly typed as a process involving an artifact. The primary key `id` ensures unique identification of the observational class definition, while the column `x` holds the class name.

The following data table illustrates instances of classes that satisfy this axiom. These entries represent distinct observational processes utilized in industrial monitoring systems.

In the preceding table, the class `ThermocoupleReadingEvent` (id: OBS-2023-001) is explicitly defined as a subclass of a process that includes a thermocouple (an artifact) as a participant. This structure allows downstream reasoning engines to infer that any instance of `ThermocoupleReadingEvent` necessarily involves an interaction with hardware, facilitating physical traceability.

## 2. Annotation of Data Columns via Descriptive ICE

### 2.1 Conceptual Definition

To achieve semantic interoperability, raw data columns within relational databases must be augmented with metadata that describes their content. The axiom template `column_tag_subclass` addresses this requirement by defining a class of Information Content Entities (ICE) that serve to annotate specific data columns. 

The Manchester syntax is defined as:
`Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:annotatesColumn some {Y:Class}`

Verbalized, this asserts that "{X} is something that annotates column {Y}." Here, {X} represents the descriptive tag or metadata class, and {Y} represents the target column or the observational class represented by that column. This relationship is foundational for governance frameworks, as it binds the definition of the data (the tag) to the instance of the data generation (the observation).

### 2.2 Relational Implementation and Dependencies

The relational schema for `t_column_tag_subclass` enforces a strict dependency on the observational artifacts defined in Section 1. The column `y` is a foreign key referencing the `id` from `t_observation_with_participant`. This constraint ensures that a descriptive tag cannot exist in isolation; it must annotate a valid, registered observational process.

The table below demonstrates the application of descriptive tags to the observational classes registered in Table 1.1. These tags provide necessary context, such as units of measure, tolerance ranges, or data sensitivity classifications.

**Table 2.1: Descriptive ICE Annotations for Observational Columns**

| TAG-UNIT-001 | CelsiusTemperatureUnit | OBS-2023-001 |

The foreign key constraint guarantees that one cannot annotate a non-existent observational process, thereby maintaining referential integrity within the governance model.

## 3. Process Input Constraints and Validation

### 3.1 Conceptual Definition

Complex workflows in technical systems are rarely isolated; they consume data or artifacts generated by preceding processes. The axiom template `process_min_one_input` formalizes the dependency of a process on at least one input. This is a crucial validation step in pipeline architecture, ensuring that a process is not initiated without requisite prerequisites.

The Manchester syntax for this constraint is:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasInput min 1 {Y:Class}`

Verbalized, this means "{X} is a process" that requires a minimum of one input {Y}. In the context of this ontology, the input {Y} is typically the observational process or artifact defined in the `observation_with_participant` axiom. This axiom allows auditors to verify that data transformation processes are grounded in valid source data.

### 3.2 Relational Implementation and Flow Control

The table `t_process_min_one_input` maps higher-level validation or transformation processes to their required inputs. Like the annotation table, this schema relies on the `t_observation_with_participant` table to validate inputs. The column `y` must correspond to a valid observational ID, ensuring that the process consumes a legitimate artifact or observation event.

The following table catalogs validation processes that require specific observational inputs. This mapping is essential for automated compliance checking, where a system may block a process if the referenced input observation is missing or invalid.
