# Chapter 12: Directive Controls Addressing HIPAA Safeguard Classes

This chapter presents four tables that encode Manchester OWL axioms for directive ICE classes. The tables capture subclass restrictions on risk-addressing behavior and on the three HIPAA safeguard categories. Primary and foreign keys implement the slot references between threat classes and safeguard classes, permitting two- and three-table joins that recover full verbalizations.

## 1 Table Definitions and Axiom Embodiment

### 1.1 t_control_only_addresses_threat_class
The table embodies AXIOM 1. Column id is the primary key for each directive class. Column x holds the subclass name; column y is a foreign key to t_hipaa_safeguard_physical.id, enforcing that the directive addresses only the referenced physical threat class. A reader can join on y to retrieve the safeguard instance that completes the verbalization “{x} addresses risk {y}”.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_hipaa_safeguard_physical(id)
);
```

| id   | x                              | y     |
|------|--------------------------------|-------|
| C001 | PhysicalAccessDirective        | P001  |
| C002 | MediaTransportDirective        | P002  |
| C003 | WorkstationLockDirective       | P003  |
| C004 | VisitorLogDirective            | P001  |
| C005 | DeviceDisposalDirective        | P004  |

### 1.2 t_hipaa_safeguard_physical
The table embodies AXIOM 2. Column id is the primary key. Column x stores the safeguard class; column y is a foreign key to t_control_only_addresses_threat_class.id. The NOT NULL constraint on y guarantees every physical safeguard participates in at least one risk-addressing directive.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

| id   | x                           | y    |
|------|-----------------------------|------|
| P001 | FacilityPerimeterClass      | C001 |
| P002 | CourierChainOfCustodyClass  | C002 |
| P003 | AutomaticLockClass          | C003 |
| P004 | SecureDestructionClass      | C005 |

### 1.3 t_hipaa_safeguard_admin
The table embodies AXIOM 3. Column id is the primary key. Column x stores the administrative safeguard class; column y is a foreign key to t_control_only_addresses_threat_class.id. The structure isolates administrative restrictions from physical and technical ones while sharing the same directive namespace.

```sql
CREATE TABLE t_hipaa_safeguard_admin (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

| id   | x                              | y    |
|------|--------------------------------|------|
| A001 | AccessAuthorizationClass       | C001 |
| A002 | TerminationProcedureClass      | C002 |
| A003 | SanctionPolicyClass            | C003 |
| A004 | BusinessAssociateContractClass | C004 |
| A005 | IncidentResponseClass          | C005 |

### 1.4 t_hipaa_safeguard_technical
The table embodies AXIOM 4. Column id is the primary key. Column x stores the technical safeguard class; column y is a foreign key to t_control_only_addresses_threat_class.id. The foreign-key graph therefore permits a single directive class to be linked simultaneously to physical, administrative, and technical safeguards.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

| id   | x                           | y    |
|------|-----------------------------|------|
| T001 | UniqueUserIDClass           | C001 |
| T002 | EncryptionAtRestClass       | C002 |
| T003 | AuditLogIntegrityClass      | C003 |
| T004 | TransmissionSecurityClass   | C004 |
| T005 | AutomaticLogoffClass        | C005 |

## 2 Cross-Join Example

To recover the complete safeguard profile for directive C001, join t_control_only_addresses_threat_class to each safeguard table on the shared y column:

```sql
SELECT c.x AS directive,
       p.x AS physical_safeguard,
       a.x AS admin_safeguard,
       t.x AS technical_safeguard
FROM   t_control_only_addresses_threat_class c
JOIN   t_hipaa_safeguard_physical p ON c.y = p.id
JOIN   t_hipaa_safeguard_admin a    ON c.id = a.y
JOIN   t_hipaa_safeguard_technical t ON c.id = t.y
WHERE  c.id = 'C001';
```

Result row:

directive: PhysicalAccessDirective  
physical_safeguard: FacilityPerimeterClass  
admin_safeguard: AccessAuthorizationClass  
technical_safeguard: UniqueUserIDClass

The row states that PhysicalAccessDirective addresses only FacilityPerimeterClass risk and simultaneously implements one administrative and one technical HIPAA safeguard.
