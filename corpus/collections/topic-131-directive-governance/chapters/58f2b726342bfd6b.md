# Chapter 7: Formal Ontology of Kernel Audit Mechanisms

## 7.1 Scope and Preamble

This chapter establishes the formal framework for mapping kernel-level system interactions to audit-compliant information entities. In the context of high-assurance computing environments, specifically those governed by the `04_ebpf_kernel` family of specifications, it is insufficient to merely log execution streams. Instead, compliance mandates that system calls be formally categorized as Designative Information Content Entities (ICE) that are intrinsically bound to audit processes. This chapter elucidates the axiom `syscall_audited_by`, providing the necessary ontological linkage between abstract syscall classes and their concrete audit workflows. The objective is to ensure that all designated kernel interactions are traceable, verifiable, and anchored to the Basic Formal Ontology (BFO) definition of a process.

## 7.2 The `syscall_audited_by` Axiom

### 7.2.1 Definition and Manchester Syntax

The foundational constraint governing the auditability of kernel interactions is expressed through the `syscall_audited_by` axiom. This axiom asserts a specific subclass relationship that binds a defined class of system calls to the necessity of an audit process. Formally, the axiom is expressed in Manchester syntax as follows:

**Class:** `{X:Class}` **SubClassOf:** `cco:DesignativeICE`, `sdg:auditedBy` some `bfo:0000015`

This logical structure dictates that for any class variable `{X}`, if `{X}` is a member of the defined set of audited system calls, it must necessarily satisfy two conditions: it must be a subclass of `cco:DesignativeICE` (Common Core Ontologies: Designative Information Content Entity), and it must possess the property `sdg:auditedBy` (Audit Data Governance: auditedBy) which relates the entity to at least one instance of `bfo:0000015` (Basic Formal Ontology: Process).

### 7.2.2 Designative Information Content Entities

The component `cco:DesignativeICE` is critical to the semantic integrity of the audit log. A Designative Information Content Entity is not merely a block of data; it is an entity that "stands for" or designates a specific real-world object or event within the system architecture. In the context of kernel auditing, the syscall class `{X}` is not treated as a transient CPU instruction, but as a persistent, designative record that signifies a specific type of interaction with the operating system kernel.

By classifying `{X}` as a `cco:DesignativeICE`, the framework ensures that the syscall is treated as an information-bearing entity capable of being referenced, indexed, and semantically queried. This distinction separates compliant audit trails from raw binary logs, allowing governance frameworks to assert that the *meaning* of the syscall (e.g., "Open File", "Process Fork") is preserved alongside its execution parameters.

### 7.2.3 The Audit Process Constraint

The second limb of the axiom, `sdg:auditedBy some bfo:0000015`, introduces the procedural mandate. The entity `bfo:0000015` represents a "Process" in the BFO top-level ontology—a temporally extended entity that unfolds over time. The object property `sdg:auditedBy` creates a dependency relationship: the existence or execution of the syscall class `{X}` is ontologically contingent upon the concurrent or subsequent execution of an audit process.

This relationship ensures that the syscall is not a "silent" operation. For a syscall to legitimately exist within the compliant system state, it must be "audited by" a process. This process may manifest as an eBPF tracepoint firing, a Linux Audit Subsystem (auditd) event, or a Secure Audit Logging (SAL) handler. The axiom does not prescribe the technical implementation of the process, only the existential necessity of the relationship.

### 7.2.4 Relational Projection and Schema

To implement this axiom within a relational database management system (RDBMS) or a structured data store, the abstract ontology must be projected onto a concrete schema. The deterministic derivation of the `syscall_audited_by` axiom results in the creation of table `t_syscall_audited_by`.

This table serves as the registry of all syscall classes that are subject to the audit constraint. The schema is defined as follows:

**Table 7.1: Schema Definition for `t_syscall_audited_by`**

| Column Name | Data Type | Description |
| :--- | :--- | :--- |
| `id` | VARCHAR(255) | The primary key, serving as a unique identifier for the specific axiom instantiation. |
| `x` | VARCHAR(255) | The class name of the system call, which must be a subclass of `cco:DesignativeICE`. |

The primary key (`id`) ensures referential integrity, allowing other compliance artifacts (such as specific audit logs or policy documents) to reference this specific definition of the audited class. The column `x` holds the string representation of the class name (e.g., `OpenSyscall`, `ExecveSyscall`), which acts as the foreign key concept to the broader ontology.

### 7.2.6 Compliance Verification Protocol

Verification of compliance with the `syscall_audited_by` axiom requires a two-step audit of the system state. First, the governance body must verify that the registry `t_syscall_audited_by` is exhaustive for the given security profile. Any system call executed by the kernel that is not represented as an instance of `{X}` in this table constitutes a violation of the axiom, as it implies an execution path that is either not a Designative ICE or is not audited by a recognized process.

Second, the audit logs generated by the system must be cross-referenced against the `id` values in the registry. For every event logged, there must exist a corresponding entry in `t_syscall_audited_by` where the event type matches the class `x`. This ensures that the "auditedBy" relationship is not merely theoretical but is actively realized in the operational data stream.

## 7.3 Summary of Ontological Constraints

The `syscall_audited_by` axiom provides the semantic backbone for rigorous kernel auditing. By mandating that relevant syscall classes `{X}` are Designative Information Content Entities (`cco:DesignativeICE`) and that they are invariably audited by a process (`bfo:0000015`), the framework bridges the gap between low-level kernel operations and high-level governance requirements. The relational schema `t_syscall_audited_by` functions as the authoritative source of truth for these definitions, ensuring that all audit trails can be traced back to formally defined classes and processes. Compliance is therefore not a matter of log volume, but of adherence to these structured ontological commitments.
