# Chapter 4: Designative Information Content Entities in Syscall Audit Trails

This chapter examines the modeling of audit records as designative information content entities within kernel-level syscall monitoring. The treatment centers on the subclass relation that positions certain entities under cco:DesignativeICE while requiring an auditedBy restriction to a bfo:0000015 process. A minimal relational schema illustrates the structure and supports multi-table joins that recover the auditor, the designated syscall, and the temporal context of each audit event.

## 1. Ontological Placement of Audit Records

The axiom syscall_audited_by states that any class X satisfying the restriction is both a designative information content entity and audited by at least one process. In an eBPF-based tracing environment this corresponds to an audit record that designates a concrete syscall invocation and is produced under the supervision of a kernel audit process. The restriction supplies the necessary existential commitment without enumerating every possible auditor.

### 1.1 Primary and Foreign Key Structure

Three tables realize the axiom. The table t_process enumerates the bfo:0000015 instances that perform auditing. The table t_syscall enumerates the designated events. The table t_syscall_audited_by records each X that satisfies the subclass axiom; its foreign-key column x references t_syscall, while an implicit link through the auditing process is recovered by joining on the process identifier carried in the audit record.

## 2. The Process Table

The table t_process embodies the range of the auditedBy property. Its primary key is the column id. No foreign keys are present because processes are treated as independent continuants.

```
CREATE TABLE t_process (
  id VARCHAR(255),
  name VARCHAR(255),
  start_time VARCHAR(255),
  PRIMARY KEY (id)
);
```

Example rows:

- id: p001, name: auditd, start_time: 2024-03-01T00:00:00Z
- id: p002, name: ebpf_tracer, start_time: 2024-03-01T00:00:00Z
- id: p003, name: seccomp_monitor, start_time: 2024-03-02T12:00:00Z

## 3. The Syscall Table

The table t_syscall supplies the individuals that are designated by the information content entities. Its primary key is id. The column pid is a foreign key referencing t_process.id, recording which process was executing when the syscall occurred.

```
CREATE TABLE t_syscall (
  id VARCHAR(255),
  pid VARCHAR(255),
  syscall_name VARCHAR(255),
  timestamp VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (pid) REFERENCES t_process(id)
);
```

Example rows:

- id: s100, pid: p001, syscall_name: openat, timestamp: 2024-03-05T08:12:03Z
- id: s101, pid: p002, syscall_name: read, timestamp: 2024-03-05T08:12:04Z
- id: s102, pid: p001, syscall_name: write, timestamp: 2024-03-05T08:12:05Z
- id: s103, pid: p003, syscall_name: connect, timestamp: 2024-03-05T08:12:06Z

## 4. The Audit Record Table

The table t_syscall_audited_by directly implements the axiom. Each row represents an X that is a designative information content entity audited by a process. The primary key is id; the column x is a foreign key referencing t_syscall.id.

```
CREATE TABLE t_syscall_audited_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (x) REFERENCES t_syscall(id)
);
```

Example rows:

- id: a001, x: s100
- id: a002, x: s101
- id: a003, x: s102
- id: a004, x: s103

## 5. Cross-Join Example

To recover the full provenance of audit record a002, join t_syscall_audited_by to t_syscall on x = id, then join t_syscall to t_process on pid = id. The resulting row is:

a002 | s101 | read | p002 | ebpf_tracer | 2024-03-05T08:12:04Z

The join traverses the foreign-key path from the designative entity through the designated syscall to the auditing process, satisfying the existential restriction of the axiom in a single traversal.
