# Chapter 4: Designative Information Content Entities for Syscall Audit Trails

This chapter defines the subclass relation that places certain kernel records under the cco:DesignativeICE category and links them via the auditedBy property to bfo:0000015 processes. The exposition is restricted to the single axiom syscall_audited_by and the relational structures that realize its slot types.

## 1. Axiom Definition and Scope

The axiom states that any class X satisfies SubClassOf: cco:DesignativeICE and sdg:auditedBy some bfo:0000015. In the eBPF instrumentation family the concrete X values are syscall designation records emitted by kernel probes. The relational projection therefore records each such designation together with its auditing process while preserving the existential restriction on the auditor.

### 1.1 Primary Relational Projection

The table t_syscall_audited_by directly encodes the axiom. Column id is the primary key that uniquely identifies each audited designation instance. Column x is a foreign key that references the identifier of the designative ICE class. A reader can therefore retrieve every process that audited a given designation by joining on x and then traversing an auxiliary process table.

```sql
CREATE TABLE t_syscall_audited_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

### 1.2 Supporting Tables for Process and Class References

Table t_bfo_processes materializes the bfo:0000015 auditor. Its primary key process_id is referenced implicitly by audit instrumentation that satisfies the existential restriction. Column start_time supplies a typed literal required for temporal qualification of the audit relation.

Table t_x_classes enumerates the admissible values for the X slot. Its primary key class_id is the target of the foreign key x in t_syscall_audited_by. Column designation_type records the cco:DesignativeICE subtype realized by each class.

Table t_audit_links supplies the concrete many-to-many association required when multiple processes audit the same designation. Its composite primary key (link_id) and foreign keys (process_id, designation_id) permit cross-table navigation from any designation to its complete set of auditors.

## 3. Cross-Join Example

Question: which process audited the designation of an open syscall that was itself audited by the ring-buffer consumer?

Walk the links: start at t_x_classes where label = 'SyscallOpenDesignation' (X001), locate matching rows in t_syscall_audited_by (A001, A002), then follow t_audit_links on designation_id to obtain process_ids P001 and P002. The ring-buffer consumer (P003) appears only for A002, confirming that P003 audited the second occurrence of the same designation class.
