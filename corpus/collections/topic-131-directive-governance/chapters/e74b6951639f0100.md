# Chapter 7: Ontological Mapping of Kernel Audit Entities

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the classification and auditability of kernel-level system calls within a secure computing environment. It establishes a rigorous mapping between low-level operating system primitives—specifically those intercepted via Extended Berkeley Packet Filter (eBPF) instrumentation—and the upper-level ontology required for compliance reporting. The primary objective is to define the axiomatic relationships between information content entities and the processes that observe them, ensuring that audit trails satisfy the evidentiary standards of modern governance frameworks. Readers will be introduced to the specific axiom `syscall_audited_by`, which serves as the logical foundation for identifying designative entities subject to surveillance. Furthermore, this chapter provides the relational schema necessary to implement these definitions within a structured audit database, facilitating automated compliance verification and forensic analysis.

## 7.2 The Designative Information Content Entity

In the context of kernel observability and security auditing, the concept of an "Information Content Entity" (ICE) must be distinguished from the physical execution of code. An ICE is an entity that is generically dependent on some other entity, typically a physical artifact or a computational process, and stands in for that entity. Within the OBO (Open Biomedical Ontologies) Foundry, specifically the Common Core Ontologies (CCO), a `cco:DesignativeICE` refers to a specific type of information content entity that serves to designate or identify a referent. When applied to system calls, this distinction is critical: the system call itself (e.g., `execve`, `open`, `read`) is not merely a function jump in memory; it is a designative entity that signifies a specific intent or operation within the governed system.

The axiom `syscall_audited_by` provides the formal constraint for this classification. It asserts that any class `{X}` representing a system call must be a subclass of `cco:DesignativeICE`. Consequently, the system call is treated as a distinct informational object that can be referenced, logged, and analyzed independently of its execution context. This abstraction allows security architects to define policies not on raw memory addresses, but on the semantic meaning of the operations performed. For instance, the class `SyscallOpen` designates the intent to access a file path, separating the *intent* from the *mechanism* of opening a file descriptor.

Furthermore, the axiom posits that `{X}` is `sdg:auditedBy` some `bfo:0000015`. In the Basic Formal Ontology (BFO), `bfo:0000015` denotes a "Process." Therefore, the axiom formally states that every designative system call entity is necessarily the object of a specific audit process. This relationship is not merely incidental but structural; the existence of the system call class within the governed ontology implies the existence of a surveillance mechanism. This ensures that the designative entity is never "orphaned" from its governance context. If a syscall is defined as a `DesignativeICE`, the ontology mandates that a process exists to capture its invocation, parameters, and return value.

### 7.2.1 Implementation in eBPF Contexts

The practical application of this axiom is most evident in modern Linux kernel tracing utilizing eBPF. In this environment, the `bfo:0000015` (Process) is instantiated as a specific eBPF program attached to a tracepoint or kprobe. The "auditedBy" relationship is the attachment link itself. When the eBPF verifier loads the program, it establishes a processual dependency: the flow of information (the syscall) is now intercepted by the audit process.

Consider the compliance requirement to monitor file access. The system call `openat2` is designated as the entity of interest. Under the `syscall_audited_by` axiom, `openat2` is classified as a `DesignativeICE`. The eBPF program loaded into the kernel acts as the `bfo:0000015` Process. The data emitted from the kernel to the user-space ring buffer constitutes the evidence of this relationship. Without the eBPF program, the `openat2` event occurs, but it is not a "DesignativeICE" in the governed sense because it lacks the `auditedBy` relationship required by the axiom. It is merely a hardware event. Only through the lens of the ontology does it become a governed, auditable entity.

## 7.3 Audit Process Governance and Control Frameworks

The `bfo:0000015` (Process) referenced in the `auditedBy` object property necessitates a rigorous governance layer. In technical documentation and compliance handbooks, the "Process" is not an abstract black box but a concrete chain of custody for data. The audit process must be defined in terms of its inputs (the syscall context), its transformation logic (filtering and redaction), and its outputs (structured logs). The ontology requires that the process be "some" `bfo:0000015`, meaning at least one such process must exist, though in complex systems, multiple processes may audit a single entity (e.g., one for real-time alerting and one for batch archival).

Governance frameworks such as NIST SP 800-53 or ISO 27001 require that the collection of audit evidence be non-repudiable and tamper-evident. The `syscall_audited_by` axiom supports this by anchoring the definition of the syscall (`x`) to the audit process. If the process fails or is terminated, the ontological relationship is severed, effectively rendering the syscall "ungoverned" within the system's logical model. This provides a powerful mechanism for health-checking: a monitoring system can validate the integrity of the governance model by verifying that for every active `x` in the registry, the corresponding `bfo:0000015` process is active and receiving events.

### 7.3.2 Verification and Attestation

The final step in the governance of these entities is the formal attestation of the axiom's validity. During an audit, an independent verifier must confirm that:
1.  The class `x` listed in `t_syscall_audited_by` is indeed a `cco:DesignativeICE` (i.e., it designates a specific, auditable event).
2.  The process `bfo:0000015` referenced by the `auditedBy` property is currently active and correctly instrumented on the kernel.
3.  The data flow from the kernel space to the persistence layer is continuous and unaltered.

This verification often involves querying the runtime state of the eBPF programs and comparing the loaded probes against the registry in `t_syscall_audited_by`. A discrepancy, such as a missing probe for `SyscallConnect`, would constitute a finding of non-compliance, as the ontological commitment (that the entity is audited) is not reflected in the physical reality of the system.

## 7.4 Summary of Relational Structures

The integration of formal ontology into kernel-level auditing provides a robust, machine-readable framework for compliance. By defining system calls as `cco:DesignativeICE` entities and explicitly linking them to audit processes via the `sdg:auditedBy` property, organizations can move from ad-hoc logging to structured evidence management. The `t_syscall_audited_by` table serves as the central registry for these definitions, ensuring that every monitored syscall is accounted for within the governance model.
