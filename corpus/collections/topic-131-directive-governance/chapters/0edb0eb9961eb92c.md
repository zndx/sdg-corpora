# Chapter 4: Ontological Foundations of Kernel Audit Frameworks

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to model kernel-level audit trails within high-assurance computing environments. It focuses specifically on the classification of system calls as designative information content entities and their subsequent relationship to the auditing processes that observe them. The content herein is intended for systems architects, compliance officers, and security engineers who must implement rigorous evidence-generation mechanisms adhering to the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO). The objective is to provide a precise, axiomatically grounded method for mapping raw kernel events to semantically rich audit records capable of satisfying regulatory scrutiny.

## 4.2 The Designative Information Content Entity

### 4.2.1 Definition and Ontological Status

In the context of kernel observability, an audit record is not merely a log entry; it is an information artifact that must be formally defined to support automated reasoning and compliance verification. We define the class of audited system calls as a subclass of `cco:DesignativeICE`. A Designative Information Content Entity (ICE) is a specific type of information entity that serves to "stand for" or designate some independent continuant (in this case, a specific system call or process event).

The distinction between the physical occurrence of a system call (a temporal process) and the record of that system call (an information entity) critical. The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE` asserts that any instance of class `X` is fundamentally a dependent entity—it exists only as a data structure or pattern within a memory space or storage medium, yet it possesses the semantic capacity to refer to the event it describes.

For example, when a process invokes the `execve` system call, the kernel executes a transition. The audit log entry generated by the Extended Berkeley Packet Filter (eBPF) program is not the transition itself; it is the `DesignativeICE` that designates that transition. This separation allows the audit infrastructure to treat the log entry as a distinct object of governance, subject to integrity checks, archival policies, and access controls, independent of the runtime process that generated it.

### 4.2.2 The SubClassOf Relationship

The formalization of this concept relies on the SubClassOf axiom. By asserting that `{X}` is a subclass of `cco:DesignativeICE`, we constrain the ontology such that no instance of `X` can exist that is not an information content entity. This prevents semantic ambiguity where a system call might be erroneously modeled as a physical action or a hardware interrupt.

Consider the class `FileReadOperation`. Under this axiom, `FileReadOperation` is not the movement of a disk head or the transfer of electrons across a bus. It is the informational designation of those events. This modeling choice is essential for audit frameworks because it allows the system to query for "all information entities designating file reads" rather than querying the physical state of the I/O subsystem, which is transient and often inaccessible post-facto.

### 4.2.3 Relational Mapping of Audited Classes

To implement this ontology within a relational database management system (RDBMS) or a structured log store, we project the ontological axiom onto a relational schema. The following table, `t_syscall_audited_by`, embodies the axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE`.

The table structure is straightforward: the primary key `id` serves as a unique identifier for the specific class definition within the system taxonomy, while the column `x` holds the class name (the `{X}` variable from the axiom). This structure allows the audit engine to enumerate all valid classes of events that are recognized as designative entities. It acts as a controlled vocabulary for the audit subsystem.

When an eBPF program attached to the `sys_read` hook triggers, it must map the captured event to this registered class. This mapping ensures that every emitted log entry is ontologically grounded, satisfying the requirement that audit trails are composed of valid designative entities rather than arbitrary string data.

## 4.3 The Audit Process and Agent Relationship

### 4.3.1 The Role of `bfo:0000015` (Process)

The second component of the core axiom introduces the `sdg:auditedBy` object property, which links the designative entity (the log entry or the event class) to an instance of `bfo:0000015`. In the Basic Formal Ontology, `bfo:0000015` denotes a "Process." A process is defined as a temporal span during which boundaries and qualities of some entity change.

In the context of this framework, the `auditedBy` relationship does not refer to a human auditor, but rather to the computational process responsible for the capture, transformation, and persistence of the audit data. This is typically a kernel-space probe (e.g., an eBPF program) or a userspace daemon (e.g., an auditd dispatcher). By formalizing this relationship, we establish a chain of custody for the information content entity. The entity `FileReadOperation` is generated *by* the `AuditCollectionProcess`.

This distinction is vital for forensic analysis. If the `auditedBy` relationship is correctly instantiated, one can query the ontology to determine exactly which software process was responsible for creating a specific log record. If the auditing process itself is compromised or behaves erratically, this relationship allows the system to identify all potentially tainted records by querying for all entities `auditedBy` the compromised process ID.

### 4.3.2 The `auditedBy` Object Property

The object property `sdg:auditedBy` is irreflexive and functional in this context. A specific instance of a designative entity (a specific log record) is audited by exactly one initiating process instance. While the process may audit many entities, the entity designates a single source of generation.

The axiom `sdg:auditedBy some bfo:0000015` utilizes the existential quantifier "some." This implies that for a class `X` to be valid (i.e., for `X` to be a registered audited syscall), there must exist at least one process that performs the auditing. This serves as a validation constraint: one cannot define a class `FileReadOperation` as an audited entity without simultaneously deploying an active auditing process capable of generating it.

This separation of duties is a common requirement in security governance frameworks, ensuring that the compromise of a standard network auditor does not automatically grant access to privilege escalation logs.

## 4.4 Verification and Compliance Protocols

### 4.4.1 Evidence Generation and Integrity

The primary utility of defining `X` as a `cco:DesignativeICE` audited by a `bfo:0000015` Process is the facilitation of automated compliance checking. A compliance engine can ingest the relational schema and the runtime logs to verify that:

1.  **Completeness:** Every system call of interest is mapped to a valid `X` in `t_syscall_audited_by`.
2.  **Provenance:** Every log entry contains a valid reference to a `bfo:0000015` Process that was active at the time of the event.
3.  **Consistency:** The `DesignativeICE` does not claim properties that violate its definition (e.g., a `FileReadOperation` should not contain network socket metadata as a primary identifier).

If the audit system generates a log entry referring to class `FileReadOperation`, but the `t_syscall_audited_by` table does not contain an entry for `FileReadOperation`, the log entry is semantically invalid according to the ontology. This validation acts as a schema-level firewall against log injection or data corruption attacks.

### 4.4.2 Audit Trail Reconstruction

In the event of a security incident, the reconstruction of the attack timeline requires traversing the `auditedBy` relationships. Investigators must isolate the `bfo:0000015` Process instances that were active during the breach window. By querying for all `DesignativeICE` instances where `auditedBy` equals the suspect Process ID, the investigator can isolate the set of records that may have been fabricated or altered by the attacker.

Furthermore, because the `DesignativeICE` is defined as a subclass of information content, it is subject to digital signature verification. The ontology supports the attachment of cryptographic hash properties to the `DesignativeICE`. The axiom structure allows for extensions such as `sdg:hasSignatureValue some xsd:hexBinary`, enabling the audit framework to prove that the `DesignativeICE` has not been modified since it was generated by the `bfo:0000015` Process.

### 4.4.3 Governance Framework Alignment

This ontological approach aligns with strict regulatory frameworks such as NIST SP 800-53 (Security and Privacy Controls for Information Systems and Organizations), specifically controls regarding Audit Record Generation (AU-3) and Audit Record Content (AU-3). By formally defining *what* constitutes an audit record (the `DesignativeICE`) and *how* it is produced (the `Process`), the organization provides mathematical proof of compliance to auditors.

The use of Manchester Syntax axioms provides a machine-readable standard (OWL) that can be directly consumed by governance tools. This eliminates the ambiguity typically found in natural language policy documents. Instead of stating "the system must log file reads," the policy asserts: `FileReadOperation SubClassOf: cco:DesignativeICE and sdg:auditedBy some bfo:0000015`. This statement is verifiable, executable, and immune to misinterpretation.
