# Chapter 4: Relational Projection of Descriptive Entities and Artifacts

This chapter delineates the formal mapping of ontology classes to relational schemas, specifically addressing the structural integrity of Descriptive Information Content Entities (ICE) and Artifacts within a governance framework. It establishes the axiomatic foundation required for data lineage, topic classification, and commercial attribute extraction, ensuring that all entity projections are compliant with the Common Core Ontologies (CCO) and relevant Schema.org extensions. The following sections provide the formal definitions, schema projections, and audit implications necessary for implementing these structures in a controlled database environment.

## 1. Topic Tagging for Descriptive ICE

The classification of tabular data requires a rigorous mechanism to assign semantic topics to ensure retrievability and regulatory compliance. According to Axiom 1, any class `X` defined as a `DescriptiveICE` must possess a `hasTableTopic` relationship to a target class `Y`. This axiom ensures that data tables are not merely stored as binary objects but are semantically indexed. The projection of this axiom into a relational database enforces a many-to-many relationship between the content entity and its semantic category, facilitating automated governance queries.

In compliance frameworks, the ability to filter tables by topic is essential for data discovery and audit readiness. For instance, a table containing financial data must be explicitly tagged as such to distinguish it from operational logs. The relational schema `t_table_topic_tag` enforces this by requiring a non-null reference to the topic (`y`) for every tag entry. The primary key (`id`) ensures that each tagging event is unique and traceable, preventing duplicate or ambiguous classifications.

The following table illustrates the instantiation of this axiom, demonstrating how specific descriptive entities are mapped to their respective semantic topics.

| id | x | y |
|---|---|---|
| tag_001 | QuarterlyEarningsTable | RevenueRecognition |
| tag_002 | QuarterlyEarningsTable | ExpenseReporting |
| tag_003 | EmployeeRosterTable | HumanResources |
| tag_004 | IncidentLog_Q3 | SecurityCompliance |
| tag_005 | InventoryManifest | SupplyChainLogistics |

In the table above, `x` represents the specific class or instance of the `DescriptiveICE` (the table itself), while `y` represents the topic class. Note that a single entity (`QuarterlyEarningsTable`) may possess multiple topic tags, reflecting the multifaceted nature of complex data sets. This structure supports granular access controls, allowing governance policies to be applied based on the sensitivity of the topic rather than the file location alone.

## 2. Provenance Sourcing in Data Governance

Provenance tracking constitutes a critical component of data governance and forensic auditing. Axiom 2 mandates that a `DescriptiveICE` (`X`) must be explicitly linked to its source table (`Y`) via the `sourcedFromTable` property. This linkage creates an immutable audit trail, essential for verifying the authenticity of data and reconstructing the lineage of information assets during regulatory investigations. Without this explicit mapping, organizations risk maintaining "orphan" data whose origins cannot be verified, leading to significant compliance liabilities.

The relational schema `t_table_provenance_source` operationalizes this axiom by storing the direct lineage of the informational entity. The constraint that `y` must be non-null ensures that every piece of descriptive information is anchored to a source. This is particularly relevant in environments where data is transformed, aggregated, or migrated; the provenance table serves as the authoritative record of the data's origin, distinct from its current location or format.

The implementation of this axiom is demonstrated in the table below, which tracks the derivation of various reporting entities from their source systems.

| id | x | y |
|---|---|---|
| src_001 | ConsolidatedBalanceSheet | GL_Subledger_2023 |
| src_002 | ExecutiveSummary_PDF | Raw_Data_Export_A |
| src_003 | RiskAssessmentReport | IncidentLog_Q3 |
| src_004 | ClientMailingList | CRM_Contact_Database |
| src_005 | TaxComplianceDoc | ERP_Finance_Module |

Here, `x` denotes the derived `DescriptiveICE`, while `y` identifies the source table or system. For example, the `ConsolidatedBalanceSheet` is explicitly sourced from the `GL_Subledger_2023`. This mapping allows auditors to trace the final report back to the original ledger entries, verifying that no data was arbitrarily introduced or omitted during the consolidation process. The `id` column provides a unique identifier for each provenance relationship, enabling the tracking of changes over time if the schema is historized.

## 3. Price Specification for Artifacts

Transitioning from informational entities to physical or digital goods, commercial attributes must be standardized to ensure accurate financial reporting and transaction processing. Axiom 3 posits that an `Artifact` (`X`) is characterized by a `hasPrice` property pointing to a value class `Y`. This projection aligns the ontology with Schema.org standards, facilitating interoperability between internal inventory systems and external e-commerce platforms. The precise definition of price is vital for tax calculations, customs declarations, and revenue recognition.

The relational schema `t_schemaorg_product_price` captures this attribute by associating an artifact with its specific price point. The schema treats the price (`y`) as a string literal to accommodate various currencies and formats, though in a strictly typed environment, this would often link to a normalized currency table. The non-null constraint on `y` ensures that every artifact listed in the system has a defined commercial value, preventing data ambiguity in sales and inventory management.

The table below provides a realistic instantiation of this axiom, listing various artifacts and their corresponding prices.

| id | x | y |
|---|---|---|
| price_001 | IndustrialPumpUnit | 1250.00_USD |
| price_002 | ServiceContract_Bronze | 500.00_USD |
| price_003 | NetworkingSwitch_48Port | 899.99_EUR |
| price_004 | ReplacementFilter_Set | 45.50_USD |
| price_005 | AnnualSoftwareLicense | 2500.00_USD |

In this dataset, `x` represents the artifact class (e.g., `IndustrialPumpUnit`), and `y` represents the price value. The inclusion of currency codes within the price string (`USD`, `EUR`) reflects the `VARCHAR` type of the column while maintaining the necessary information for financial systems. This structure allows for rapid querying of assets by price range, supporting dynamic pricing strategies and inventory valuation audits.

## 4. Brand Attribution and Asset Management

Brand attribution serves as a key identifier for asset management, warranty processing, and vendor relationship management. As per Axiom 4, an `Artifact` (`X`) must be associated with a brand entity (`Y`) through the `hasBrand` relationship. This axiom supports the enforcement of vendor compliance standards, allowing organizations to track assets by manufacturer, validate warranty entitlements, and analyze spend by supplier. In a multi-vendor environment, the explicit linkage of an artifact to a brand is a prerequisite for effective procurement governance.

The `t_schemaorg_product_brand` schema enforces this linkage, treating the brand (`y`) as a mandatory attribute of the artifact. This structure facilitates the aggregation of asset data by brand, enabling risk assessments regarding single-source dependencies or vendor-specific reliability issues. The primary key (`id`) ensures that each brand-artifact pairing is distinct, allowing for the possibility of rebranding or co-branding scenarios where necessary.

The following table exhibits the application of this axiom, mapping specific artifacts to their respective brand entities.

| id | x | y |
|---|---|---|
| brand_001 | IndustrialPumpUnit | AcmeCorp |
| brand_002 | ServiceContract_Bronze | GlobalServicesLtd |
| brand_003 | NetworkingSwitch_48Port | NanoSystems |
| brand_004 | ReplacementFilter_Set | AcmeCorp |
| brand_005 | AnnualSoftwareLicense | SoftSol_Inc |

In this example, `x` refers to the artifact, and `y` refers to the brand. Notably, both the `IndustrialPumpUnit` and the `ReplacementFilter_Set` are associated with `AcmeCorp`, allowing procurement officers to easily query all assets supplied by this manufacturer. This data is crucial for supply chain resilience, as it allows the organization to quickly identify all inventory that might be affected by a specific vendor's recall or supply chain disruption.

## 5. Postal Address Mapping for Geospatial Artifacts

Geospatial and logistical coordination relies on precise address data to facilitate shipping, regulatory reporting, and facility management. Axiom 5 stipulates that an `Artifact` (`X`), which may represent a facility, a fixed asset, or a place of business, must contain a `hasPostalAddress` relationship to a class `Y`. This ensures that physical assets are locatable within the supply chain and that legal notices or tax documents can be directed to the correct physical location.

The relational schema `t_schemaorg_place_address` encodes this relationship, requiring a non-null address (`y`) for every artifact entry. This schema supports the `cco:Artifact` class by grounding it in a physical location, which is essential for operations that involve the movement or maintenance of physical goods. The use of a `VARCHAR` field for the address allows for international address formats, which may vary significantly in structure and length.

The table below demonstrates the mapping of artifacts to their postal addresses, consistent with the requirements of Axiom 5.

| id | x | y |
|---|---|---|
| addr_001 | DistributionCenter_NY | 123 Industrial Pkwy, Newark, NJ 07102 |
| addr_002 | RegionalOffice_CA | 456 Tech Blvd, San Francisco, CA 94107 |
| addr_003 | Warehouse_Hamburg | Am Hafen 12, 20457 Hamburg, Germany |
| addr_004 | RetailOutlet_London | 78 Oxford St, London W1D 1ES, UK |
| addr_005 | ServerFarm_VA | 900 Data Center Dr, Ashburn, VA 20147 |

Here, `x` identifies the artifact (in this case, likely a facility or place), and `y` contains the full postal address. This mapping enables logistics systems to calculate shipping routes, verify tax jurisdictions, and coordinate maintenance visits. The explicit storage of the address as a linked attribute rather than embedded metadata ensures that address updates can be managed centrally without altering the core definition of the artifact itself.
