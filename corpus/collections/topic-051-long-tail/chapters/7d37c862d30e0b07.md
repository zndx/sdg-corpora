# Chapter 7: Relational Mapping of Descriptive Artifacts and Commercial Entities

## 7.1 Scope and Preamble

This chapter delineates the formal protocols for mapping high-level ontology axioms to relational database structures, specifically within the context of data governance and semantic interoperability. The content herein addresses the transformation of OWL (Web Ontology Language) constructs—specifically those pertaining to the Common Core Ontologies (cco) and the `sdg` namespace—into deterministic SQL schemas. The objective is to ensure that all descriptive information content entities (ICE) and commercial artifacts are auditable, traceable, and semantically consistent. The following sections provide a rigorous analysis of five distinct axiomatic templates, detailing their logical structure, their implementation as relational tables, and the requisite constraints that maintain referential integrity. It is mandated that all data stewards adhere to these mappings when populating the central repository.

## 7.2 Semantic Tagging of Descriptive Entities

### 7.2.1 Axiomatic Definition

The first concept addresses the classification of Information Content Entities (ICE) through the assignment of topical metadata. In the ontology, this is governed by the axiom template `table_topic_tag`. The formal Manchester syntax for this axiom is defined as: `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasTableTopic some {Y:Class}`. Verbalized, this asserts that Entity X is a subclass of DescriptiveICE and possesses a table topic denoted by Entity Y.

This relationship is critical for the retrieval and governance of unstructured or semi-structured data. By binding a specific table or data object (X) to a defined topic class (Y), the organization establishes a controlled vocabulary. Without this binding, data lakes become opaque repositories lacking semantic navigability. The axiom ensures that every instance of X is not merely a standalone artifact but is contextually anchored within the broader knowledge graph.

### 7.2.2 Relational Implementation

The projection of this axiom into a relational schema necessitates a table structure that captures the instance-level mapping between the descriptive entity and its topic. The table `t_table_topic_tag` serves this function. The primary key is the `id` column, ensuring uniqueness for every tagging event. The `x` column represents the specific DescriptiveICE instance (e.g., a specific report or data log), while the `y` column represents the Topic Class (e.g., "Financial Audit" or "Inventory Management").

The schema enforces that `y` cannot be null, as a descriptive entity without a topic violates the governance principle of findability. This structure allows for many-to-many relationships implicitly, as a single entity may have multiple topic tags across different rows, and a single topic may apply to multiple entities.

| id | x | y |
| :--- | :--- | :--- |
| tag_001 | Q3_Financial_Audit_Log | Financial_Compliance |
| tag_002 | Q3_Financial_Audit_Log | Risk_Assessment |
| tag_003 | Employee_Benefits_Summary | Human_Resources |
| tag_004 | North_District_Inventory | Supply_Chain_Logistics |
| tag_005 | Server_Room_Access_List | Physical_Security |

*Table 7.1 illustrates the instantiation of the `table_topic_tag` axiom. Note that the entity `Q3_Financial_Audit_Log` (x) is associated with two distinct topics (y), demonstrating the poly-hierarchical nature of semantic classification required for complex audit reports.*

## 7.3 Provenance and Lineage Tracking

### 7.3.1 Axiomatic Definition

Data provenance is a cornerstone of regulatory compliance. The second axiom, `table_provenance_source`, formalizes the derivation of data entities. The Manchester syntax is: `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:sourcedFromTable some {Y:Class}`. This asserts that Entity X, a DescriptiveICE, is sourced from Table Y.

In practical terms, this axiom creates a directed graph of data flow. It is not sufficient to know that a report exists; one must be able to trace the report's genesis to its source system or table. This is particularly relevant during forensic audits or data quality investigations, where the integrity of a downstream report (X) depends entirely on the validity of the upstream source (Y). The axiom enforces a dependency relationship that must be preserved in the database schema.

### 7.3.2 Relational Implementation

The relational schema `t_table_provenance_source` materializes this lineage. The structure is identical to the topic tag table in terms of column types, but the semantic load differs significantly. Here, `x` is the dependent artifact (the child), and `y` is the progenitor table (the parent).

The `id` serves as the unique identifier for the lineage link. The constraint that `y` must be `NOT NULL` ensures that every piece of data in the system has a traceable origin. Orphaned data—data with no declared source—is strictly prohibited under this data governance framework. This table facilitates recursive queries to trace lineage back through multiple generations of data transformation.

**Table 7.2: Relational Mapping of Table Provenance**

| id | x | y |
| :--- | :--- | :--- |
| prov_001 | Executive_Summary_2024 | Raw_Transaction_Log |
| prov_002 | Executive_Summary_2024 | Customer_Master_Index |
| prov_003 | Quarterly_Tax_Filing | General_Ledger_Table |
| prov_004 | Regional_Sales_Report | Global_Sales_Aggregate |
| prov_005 | Compliance_Certificate | Audit_Findings_Raw |

*Table 7.2 demonstrates the `table_provenance_source` axiom. The `Executive_Summary_2024` (x) is derived from two distinct sources (`Raw_Transaction_Log` and `Customer_Master_Index`), reflecting the common ETL (Extract, Transform, Load) practice of aggregating data from multiple upstream systems.*

## 7.4 Commercial Artifacts: Pricing Structures

### 7.3.1 Axiomatic Definition

Shifting from descriptive entities to commercial artifacts, the third axiom governs the attribution of value. The `schemaorg_product_price` axiom is expressed as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPrice some {Y:Class}`. This posits that Artifact X has a price Y.

In the context of the ontology, price is treated as a class or entity rather than a mere primitive data type, allowing for complex attributes such as currency, validity intervals, and tax inclusivity to be associated with the price entity itself. However, in the relational projection, this is simplified to a direct link between the artifact and the price value. This mapping is essential for any system involved in commerce, inventory valuation, or asset management.

### 7.4.2 Relational Implementation

The table `t_schemaorg_product_price` captures this relationship. The `x` column refers to the specific Artifact (e.g., a product SKU or a service code), while `y` contains the price value. The `NOT NULL` constraint on `y` reflects the commercial reality that an artifact listed in a sales catalog or inventory system must possess a defined price point to be considered a valid commercial offering.

This table supports high-frequency read operations during transaction processing. It serves as the junction between the physical or digital definition of a product and its economic valuation. Changes in the `y` value (price) must be audited, as they directly impact revenue recognition.

## 7.5 Brand Attribution and Governance

### 7.5.1 Axiomatic Definition

The identity of a commercial artifact is often inextricably linked to its brand. The `schemaorg_product_brand` axiom is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasBrand some {Y:Class}`. This asserts that Artifact X possesses a brand Y.

Brand attribution is a vital component of intellectual property management and marketing compliance. By formalizing the brand as a distinct class Y linked to the artifact X, the ontology allows for the aggregation of all products under a corporate umbrella or the distinction between OEM (Original Equipment Manufacturer) parts and third-party alternatives. This axiom ensures that brand identity is treated as a first-class data citizen.

### 7.5.2 Relational Implementation

The `t_schemaorg_product_brand` table implements this linkage. The `x` column denotes the Artifact, and the `y` column denotes the Brand entity. The `NOT NULL` constraint on `y` implies that the governance framework does not permit unbranded commercial artifacts within the managed inventory; every item must be attributable to a specific legal or commercial entity.

This structure facilitates brand-level reporting, such as calculating total sales per brand or assessing market share. It also prevents data ambiguity where similar product names from different manufacturers might otherwise be conflated.

## 7.6 Geospatial Location: Postal Addressing

### 7.6.1 Axiomatic Definition

The final axiom addresses the physical location of artifacts or facilities. The `schemaorg_place_address` axiom is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`. This asserts that Artifact X (which may be a building, a facility, or a fixed asset) has a postal address Y.

Accurate geospatial data is a requirement for logistics, regulatory reporting (e.g., tax jurisdictions), and operational maintenance. By treating the address as a linked class Y rather than a simple string property of X, the system can normalize address formats, validate against postal databases, and link multiple artifacts to a single location (e.g., a warehouse containing multiple assets).

### 7.6.2 Relational Implementation

The table `t_schemaorg_place_address` encodes this spatial relationship. The `x` column represents the Artifact (typically a facility or place), and the `y` column represents the standardized postal address string. The `NOT NULL` constraint on `y` ensures that the physical location of all fixed assets is known and recorded.

This table is frequently utilized in conjunction with supply chain logic to determine shipping origins or to define the boundaries of operational zones. It ensures that the "Place" concept within the ontology is grounded in verifiable postal reality.
