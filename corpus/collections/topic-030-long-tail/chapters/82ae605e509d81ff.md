# Chapter 7: Ontological Foundations for Compliance Evidence and Data Lineage

## 7.1 Scope and Preamble

This chapter delineates the structural requirements for evidentiary compliance within automated governance frameworks, specifically focusing on the intersection of process artifacts, descriptive claims, and regulatory mandates. The content herein defines the ontological relationships necessary to establish verifiable links between system-level events and high-level compliance obligations, such as those stipulated by the General Data Protection Regulation (GDPR). It provides a rigorous examination of how artifacts—ranging from kernel-level anomalies to column-level lineage mappings—function as bearers of information that support descriptive claims. Furthermore, this chapter establishes the relational schema required to persist these relationships, ensuring that audit trails are both queryable and semantically valid according to the defined axioms.

## 7.2 Trace Support for Descriptive Claims

### 7.2.1 Conceptual Definition
The foundational axiom for traceability, `trace_supports_claim`, posits that a specific class of process (`X`) functions as a dependent realization of a `bfo:0000015` (Process) entity. This entity is semantically bound to a `cco:DescriptiveICE` (Information Content Entity) via the property `sdg:supportsClaim`. In practical governance terms, this axiom formalizes the requirement that a procedural execution must generate or reference a descriptive artifact to be considered valid evidence. The process does not exist in isolation; its validity is contingent upon its capacity to support a specific claim about the state of the system or data.

### 7.2.2 Implementation and Governance
In the context of an audit, the "trace" refers to the immutable record of a process execution. For a trace to satisfy the axiom, it must be explicitly linked to a descriptive claim. For instance, a "FinancialAuditTrail" is not merely a log file; it is a process instance that supports the claim that "financial transactions have been recorded accurately." The ontological structure enforces that any instance of `X` must be capable of demonstrating this support relationship. This prevents the accumulation of "orphaned" process logs that do not contribute to compliance verification.

## 7.3 Attestation and Signatory Authority

### 7.3.1 Conceptual Definition
The axiom `attestation_signed_by` extends the definition of a process by introducing the requirement of human agency. Here, the class `X` (SubClassOf `bfo:0000015`) is constrained by the object property `sdg:signedBy`, which necessitates a relationship to a `cco:Person`. This axiom is critical for establishing non-repudiation and accountability within governance frameworks. It asserts that a specific process—typically an attestation or a sign-off event—is invalid unless it is explicitly associated with a natural person authorized to execute such an action.

### 7.3.2 Regulatory Context
Under various regulatory regimes, including GDPR and SOC 2, automated controls must often be corroborated by human oversight. The `attestation_signed_by` axiom captures this requirement by modeling the attestation not as a static document, but as a process (`bfo:Process`) that is performed by an agent. This distinction allows the system to query not just the existence of a signature, but the temporal and procedural context of the signing event itself.

### 7.3.3 Relational instantiation
The table `t_attestation_signed_by` represents the instances where a process has been signed by a person. The primary key `id` uniquely identifies the attestation event, and `x` classifies the nature of the attestation process (e.g., "ComplianceOfficerSignatory"). This structure serves as the authoritative registry of sign-off events within the system.

## 7.4 GDPR Lawful Basis Directives

### 7.4.1 Conceptual Definition
The axiom `gdpr_lawful_basis` integrates regulatory compliance directly into the ontology. It defines a class `X` (SubClassOf `cco:DirectiveICE`) which possesses the property `sdg:hasLawfulBasis`. This property relates the directive to another class `Y`, representing the specific legal grounds (e.g., Contract, Legal Obligation, Consent) underpinning a data processing activity. This axiom ensures that every directive issued within the system is semantically anchored to a valid legal justification, satisfying Article 6 of the GDPR.

### 7.4.2 Dependency and Constraints
A critical feature of this axiom is the dependency it establishes on the attestation layer. The relational schema for `t_gdpr_lawful_basis` enforces a foreign key constraint, linking the lawful basis (`y`) to an existing attestation record (`t_attestation_signed_by`). This design enforces the principle that a lawful basis is not merely a theoretical classification but must be validated and instantiated through a specific attestation process. In effect, the "lawful basis" is activated only when a responsible party (the Person from the previous axiom) attests to its applicability.

## 7.5 Kernel Anomaly Detection as Evidence

### 7.5.1 Conceptual Definition
While previous sections addressed procedural and directive-level entities, the axiom `kernel_anomaly_supports_claim` focuses on low-level system artifacts. It defines a class `X` (SubClassOf `cco:Artifact`) that supports a claim (`cco:DescriptiveICE`). Specifically, this axiom is utilized to categorize kernel-level anomalies—such as panic logs, oops messages, or hardware error reports—as evidentiary artifacts. These artifacts are distinct from general logs in that they represent deviations from expected kernel behavior and are therefore high-value indicators of system integrity or security incidents.

### 7.5.2 Evidentiary Value
In a forensic audit context, a kernel anomaly serves as an irrefutable "DescriptiveICE" that supports the claim of a system failure or an intrusion attempt. By classifying these objects as Artifacts that support claims, the ontology facilitates the automatic ingestion of low-level telemetry into high-level compliance reports. For example, a "KernelPanicArtifact" supports the descriptive claim "System availability was compromised."

### 7.5.3 Relational instantiation
The table `t_kernel_anomaly_supports_claim` catalogs these artifacts. The column `x` identifies the specific class of the anomaly artifact. This registry allows auditors to query for specific types of kernel-level evidence that support claims regarding system stability or security breaches.

## 7.6 Column Lineage for Compliance Claims

### 7.6.1 Conceptual Definition
The final axiom, `column_lineage_for_compliance_claim`, addresses the transformation of data within the information system. It defines a class `X` (SubClassOf `cco:Artifact`) that supports a claim (`cco:DescriptiveICE`). Here, `X` specifically refers to lineage artifacts—metadata that describes the transformation, derivation, or movement of data columns from source to target. This axiom is essential for verifying that data handling practices (e.g., masking, encryption, aggregation) comply with privacy policies throughout the data lifecycle.

### 7.6.2 Verification of Data Handling
Compliance frameworks often require proof that sensitive data has been handled correctly according to its classification. A column lineage artifact supports the claim that "Personally Identifiable Information (PII) was hashed prior to reporting." By formally modeling lineage as an artifact that supports a claim, the system automates the verification of data transformation rules, reducing the manual effort required during compliance audits.
