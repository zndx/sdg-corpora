# Chapter 12: Evidence Tracing and Attestation in Compliance Architectures

This chapter delineates the formal mechanisms by which digital artifacts and governance processes are mapped to regulatory compliance claims within an enterprise ontology. It establishes the structural relationships between low-level system traces, personnel attestations, and high-level data protection directives. The following sections provide a rigorous examination of the axioms governing these relationships, supported by relational schema implementations that ensure referential integrity and auditability.

## 12.1 Trace Support for Descriptive Claims

In the context of audit readiness, a "trace" is defined not merely as a log entry, but as a continuant (BFO:0000015) that functions as evidentiary support for a specific assertion. The axiom `trace_supports_claim` formalizes this by asserting that a trace entity is a subclass of processes that specifically support a `DescriptiveICE` (Descriptive Information Content Entity). This relationship is foundational for constructing defensible audit trails; without a direct, typed link between the trace artifact and the claim it substantiates, the evidentiary chain is considered broken under frameworks such as SOC 2 Type II and ISO 27001.

Operationally, this requires that any system-generated log or telemetry data be ingested into a governance repository where it is explicitly tagged with the identifier of the compliance claim it verifies. For instance, a specific database transaction log must be programmatically linked to the claim "Customer financial data is encrypted at rest." The trace acts as the proxy for the verification of that claim.

### 12.1.1 Relational Implementation

The implementation of this axiom is managed through a normalized table structure where the primary key serves as the unique identifier for the trace instance, and the `x` column denotes the specific class or instance of the trace acting as evidence.

**Table 12-1: Trace Support Mappings**

The data in Table 12-1 illustrates a variety of trace classes. Each `id` represents a specific evidentiary artifact, while `x` categorizes the nature of the trace. For example, `TRC-2023-001` represents a `SystemAccessLog`, which would typically be invoked to support claims regarding user authentication and authorization events.

## 12.2 Personnel Attestation and Authorization

Governance frameworks require that human accountability be anchored to automated processes. The `attestation_signed_by` axiom defines a process wherein a specific artifact or directive is explicitly authorized by a `cco:Person`. This moves beyond simple "user activity" logging; it creates a distinct class of process (subclassed by `bfo:Process`) that exists solely to capture the act of attestation. This is critical for high-compliance environments where manual sign-off is required for policy exceptions, risk acceptance, or access grant reviews.

The verbalization of this axiom—"X is something that signed by person"—emphasizes the directionality of the relationship. The attestation object (X) is the focal point, and the Person is the agent who imbues it with authority. In practice, this prevents the "orphaned policy" problem, where a compliance directive exists but cannot be traced back to an authorizing official.

### 12.2.1 Relational Implementation

The schema for attestation enforces that every attestation record is uniquely identified and linked to the signing entity. While the ontology defines the relationship to a `cco:Person`, the relational table captures the attestation instance itself.

**Table 12-2: Attestation Records**

| id | x |
| :--- | :--- |
| ATT-1001 | RiskAcceptanceForm |
| ATT-1002 | DataTransferAgreement |
| ATT-1003 | AccessRequestApproval |
| ATT-1004 | PolicyExceptionWaiver |
| ATT-1005 | SecurityIncidentDeclaration |

In Table 12-2, the `id` values (e.g., `ATT-1001`) serve as the persistent keys for these governance events. The `x` column specifies the class of the document or process being attested. For instance, `ATT-1004` represents a `PolicyExceptionWaiver`, a critical control in environments where strict adherence to baseline controls is temporarily impossible.

## 12.3 Lawful Basis Determination under GDPR

The General Data Protection Regulation (GDPR) mandates that any processing of personal data must be grounded in a specific lawful basis (Article 6). The `gdpr_lawful_basis` axiom formalizes this by asserting that a Directive Information Content Entity (`cco:DirectiveICE`) possesses a lawful basis (`Y`). This structure allows compliance engines to query not just *what* data is being processed, but *why* it is legally permissible.

A critical constraint in this schema is the foreign key relationship: the lawful basis (`Y`) must reference an existing attestation (`t_attestation_signed_by`). This enforces the principle that a lawful basis is not merely a static label (e.g., "Contractual Necessity") but a formally attested decision. The organization must have a record (`ATT-...`) where a responsible party has explicitly confirmed that the specific processing activity aligns with that legal basis.

### 12.3.1 Relational Implementation

The table below demonstrates how processing directives are linked to specific, attested lawful bases. The `y` column contains the foreign key pointing to the attestation table established in Section 12.2.

**Table 12-3: GDPR Lawful Basis Linkages**

| id | x | y |
| :--- | :--- | :--- |
| GDPR-LB-01 | CustomerDataProcessingDirective | ATT-1002 |
| GDPR-LB-02 | EmployeeMonitoringDirective | ATT-1001 |
| GDPR-LB-03 | MarketingAnalyticsDirective | ATT-1003 |
| GDPR-LB-04 | VendorDataAccessDirective | ATT-1002 |

In this configuration, `GDPR-LB-01` represents a directive for processing customer data. Its lawful basis is validated by the attestation record `ATT-1002` (referenced in Table 12-2 as a `DataTransferAgreement`). This linkage ensures that if the attestation is revoked or expires, the lawful basis for the directive is effectively nullified, triggering a compliance violation in automated monitoring systems.

## 12.4 Kernel-Level Anomaly Detection as Evidence

As security threats evolve, surface-level logging is often insufficient to prove the absence of compromise. The `kernel_anomaly_supports_claim` axiom addresses this by classifying kernel-level anomalies as `cco:Artifact`s that support `DescriptiveICE` claims. This is particularly relevant for forensic investigations and integrity verification (e.g., proving that a system has not been rootkitted).

Unlike standard application traces, a kernel anomaly is a distinct artifact representing a deviation from expected operating system behavior. By mapping this artifact to a descriptive claim (such as "System kernel integrity is maintained"), auditors can verify that low-level monitoring tools are active and effective. This axiom bridges the gap between abstract security posture and concrete binary evidence.

### 12.4.1 Relational Implementation

The following table catalogs instances of kernel anomalies that have been ingested by the compliance system to support specific integrity claims.

**Table 12-4: Kernel Anomaly Evidence**

| id | x |
| :--- | :--- |
| KAN-5001 | SyscallTableModification |
| KAN-5002 | InterruptDescriptorTableHook |
| KAN-5003 | HiddenProcessDetection |
| KAN-5004 | KernelModuleSignatureFailure |

Here, `KAN-5001` identifies an instance of `SyscallTableModification`. In a compliant system, the presence of this record would be linked to a claim describing the detection mechanism, or conversely, in a forensic context, it would support the claim "System integrity was compromised." The ontology treats the anomaly itself as the artifact of record.

## 12.5 Column Lineage and Data Provenance

Data governance regulations, such as BCBS 239 and GDPR Article 30, require organizations to maintain detailed provenance metadata. The `column_lineage_for_compliance_claim` axiom asserts that a data lineage artifact (specifically column-level lineage) is an `cco:Artifact` that supports a `DescriptiveICE`. This facilitates the "end-to-end" traceability of data elements from ingestion to reporting.

Column lineage is distinct from general data mapping; it tracks the transformation of specific attributes (columns) through ETL pipelines. By treating the lineage graph or metadata object as an artifact supporting a claim (e.g., "Reported revenue figures are derived from the general ledger"), organizations can automate the validation of regulatory reports. If the lineage artifact is missing or broken, the supported claim cannot be verified.
