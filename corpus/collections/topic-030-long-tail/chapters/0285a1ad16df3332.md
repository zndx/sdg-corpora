# Chapter 4. Evidence Anchoring and Compliance Provenance in Distributed Systems

## 4.1 Scope and Preamble

This chapter delineates the formal mechanisms by which technical artifacts and governance directives are anchored to descriptive claims within a compliance framework. In the context of high-assurance systems, regulatory adherence requires more than static policy declarations; it demands a traceable chain of evidence linking low-level system events to high-level legal obligations. The following sections define the ontological structures necessary to map these relationships, focusing on the intersection of processual entities, information content entities, and the actors responsible for their validation. By establishing rigorous schemas for trace support, attestation, and lineage, auditors can verify that system behaviors are consistent with declared lawful bases and descriptive claims.

## 4.2 Trace Support for Descriptive Claims

The foundational unit of auditability is the trace, defined axiomatically as a process that supports a descriptive information content entity (ICE). In practical terms, a trace serves as the evidentiary bridge between a system event and the narrative claim describing that event. For a claim to be verifiable, it must be substantiated by an antecedent process or artifact that falls within the scope of the claim's assertion.

The ontology defines this relationship through the axiom: `{X} is something that supports claim descriptive information content entity`. Here, `X` represents the class of the trace entity. This structure ensures that every descriptive claim—such as "the system processed payment card data in accordance with PCI-DSS standards"—is backed by a specific, classifiable process trace. Without this linkage, claims remain unsubstantiated assertions vulnerable to audit failure.

The classification of `X` determines the admissibility and weight of the evidence in a formal review.

## 4.3 Attestation and Signatory Authority

While traces provide raw evidence, attestations provide the governance layer necessary to validate that evidence against organizational policy. An attestation is a specific type of process that must be signed by a natural person. This requirement ensures that automated processes cannot self-validate; human accountability is injected into the verification loop.

The governing axiom states: `{X} is something that signed by person`. In this schema, `X` denotes the class of the entity or process being attested. The relational integrity of this concept is critical: the attestation is not merely a signature but a binding of a person's identity to a specific process state or artifact. This creates a non-repudiable link between the governance framework and the operational reality of the system.

| :--- | :--- |

| att_role_dpo_02 | DataProtectionOfficerRole |

For instance, the row with identifier `att_config_change_04` links the class `FirewallConfigurationChange` to a specific attestation event. This implies that an instance of a firewall configuration change cannot be considered compliant until it is recorded in this table, thereby triggering the requirement for a signatory (a Person) to validate it.

## 4.4 GDPR Lawful Basis Integration

The General Data Protection Regulation (GDPR) mandates that any processing of personal data must have a documented lawful basis. Within this ontology, a lawful basis is not an abstract concept but a distinct entity linked to a Directive ICE (Information Content Entity). The axiom formalizes this as: `{X} is something that has lawful basis {Y}`.

This structure enforces a strict dependency: a Directive (`X`) is valid only if it references a valid Lawful Basis (`Y`). Furthermore, the relational schema imposes a foreign key constraint, requiring that the Lawful Basis (`Y`) must correspond to an existing attestation record. This design choice embeds the principle that lawful bases are not merely theoretical categories (e.g., "Contractual Necessity") but must be instantiated and attested to within the system's governance records.

**Table 4.3: GDPR Lawful Basis Assignment**
The table below maps specific Directives (`x`) to their associated Lawful Basis (`y`). The `y` column functions as a foreign key referencing the attestation identifiers established in the previous section, ensuring that every lawful basis is actively attested.

| id | x | y |
| :--- | :--- | :--- |
| gdpr_processing_01 | CustomerDataProcessingDirective | att_role_dpo_02 |
| gdpr_marketing_02 | DirectMarketingConsentDirective | att_access_grant_05 |
| gdpr_payroll_03 | EmployeePayrollProcessingDirective | att_role_admin_01 |
| gdpr_analytics_04 | BehavioralAnalyticsDirective | att_audit_log_03 |
| gdpr_retention_05 | DataRetentionPolicyDirective | att_role_dpo_02 |

In the record `gdpr_processing_01`, the `CustomerDataProcessingDirective` relies on the lawful basis identified by `att_role_dpo_02`. This implies that the validity of the directive is contingent upon the attestation associated with the Data Protection Officer. If the attestation is revoked or expires, the referential integrity of the compliance claim is broken, automatically flagging the directive as non-compliant.

## 4.5 Kernel Anomaly Detection as Evidence

In security-critical environments, compliance often depends on the absence of unauthorized modifications or the presence of specific defensive measures. Kernel anomalies—deviations from expected operating system behavior—serve as high-fidelity evidence for claims regarding system integrity. The axiom defines this as: `{X} is something that supports claim descriptive information content entity`, where `X` is a subclass of Artifact.

Unlike general traces, kernel anomalies are specific artifacts generated by the system's core. They provide objective, tamper-resistant evidence that can support descriptive claims such as "the kernel enforced memory isolation" or "an unauthorized syscall was blocked." The granularity of this evidence allows auditors to move beyond policy compliance to verify technical enforcement mechanisms.

**Table 4.4: Kernel Anomaly Evidence Mapping**
This table catalogs artifact classes (`x`) that function as evidence for compliance claims. Each row represents a category of kernel-level artifact that supports a specific descriptive assertion.

| id | x |
| :--- | :--- |
| ka_panic_dump_01 | KernelPanicMemoryDump |
| ka_syscall_fail_02 | FailedSystemCallTrace |
| ka_module_load_03 | KernelModuleLoadEvent |
| ka_integrity_fail_04 | CodeIntegrityCheckFailure |
| ka_ptrace_alert_05 | PtraceAccessViolationLog |

For example, the `KernelModuleLoadEvent` (ka_module_load_03) acts as the supporting artifact for a claim regarding driver management. If a compliance claim states that "no unauthorized kernel modules were loaded during the audit period," the presence or absence of records in this class provides the definitive proof.

## 4.6 Column Lineage for Compliance Claims

Data governance frameworks require transparency regarding how data is transformed as it moves through an enterprise system. Column lineage tracks the transformation of data attributes from source to target. This is essential for validating that sensitive data is handled correctly throughout its lifecycle. The axiom expresses this as: `{X} is something that supports claim descriptive information content entity`, where `X` is an Artifact representing the lineage metadata.

By treating column lineage as a supporting artifact, the ontology allows organizations to prove that data masking, aggregation, or filtering operations were applied correctly. This supports descriptive claims such as "PII was redacted prior to reporting" or "financial figures were derived from the general ledger."
