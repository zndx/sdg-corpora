# Data Governance Ontologies for Regulatory Compliance

This chapter defines five relational tables that instantiate core ontological distinctions among claims, attestations, lawful bases, anomalies, and lineage artifacts. The tables are derived directly from the supplied OWL axioms and are intended to be queried together to resolve multi-hop compliance questions.

## 1. Attestation and Signature Structure

Axiom 2 states that a class X is a process signed by a person. Table t_attestation_signed_by therefore records each attestation instance with its primary key id and the class identifier in column x. The primary key permits foreign-key references from dependent tables; the x column supplies the ontological type required for claim evaluation.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id   | x                              |
|------|--------------------------------|
| att1 | DataProcessingConsent          |
| att2 | LegitimateInterestAssessment   |
| att3 | ContractualNecessityRecord     |
| att4 | VitalInterestsDeclaration      |
| att5 | PublicTaskAuthorization        |

## 2. Lawful Basis Linkage

Axiom 3 states that a directive information content entity X has lawful basis Y. Table t_gdpr_lawful_basis therefore stores the directive identifier in x and the required foreign key y that references t_attestation_signed_by.id. The foreign-key constraint enforces that every lawful-basis assertion is backed by a signed attestation.

```sql
CREATE TABLE t_gdpr_lawful_basis (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_attestation_signed_by(id)
);
```

| id    | x                        | y    |
|-------|--------------------------|------|
| lba1  | ConsentDirective         | att1 |
| lba2  | LegitimateInterestNotice | att2 |
| lba3  | ContractExecutionLog     | att3 |
| lba4  | PublicHealthOrder        | att5 |
| lba5  | EmergencyResponseBasis   | att4 |

## 3. Trace Support for Descriptive Claims

Axiom 1 states that a process X supports a descriptive information content entity. Table t_trace_supports_claim records each supporting trace with primary key id and the class x. No foreign key is present; linkage occurs through shared class references in x when joined with other tables.

```sql
CREATE TABLE t_trace_supports_claim (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id    | x                              |
|-------|--------------------------------|
| trc1  | ProcessingActivityLog          |
| trc2  | DataSubjectRequestRecord       |
| trc3  | RetentionScheduleAudit         |
| trc4  | CrossBorderTransferReport      |
| trc5  | SecurityMeasureVerification    |

## 4. Kernel Anomaly Support

Axiom 4 states that an artifact X supports a descriptive information content entity. Table t_kernel_anomaly_supports_claim captures anomaly artifacts under the same supports-claim pattern, again using only an id primary key and an x class column.

```sql
CREATE TABLE t_kernel_anomaly_supports_claim (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id    | x                           |
|-------|-----------------------------|
| kan1  | AccessAnomalyKernel         |
| kan2  | RetentionViolationKernel    |
| kan3  | TransferLimitKernel         |
| kan4  | ConsentWithdrawalKernel     |
| kan5  | PurposeDriftKernel          |

## 5. Column Lineage for Compliance

Axiom 5 likewise states that an artifact X supports a descriptive information content entity. Table t_column_lineage_for_compliance_claim records lineage artifacts that substantiate compliance claims, again keyed only by id and typed by x.

```sql
CREATE TABLE t_column_lineage_for_compliance_claim (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id    | x                              |

| clc4  | FinancialIdentifierLineage     |
| clc5  | BiometricTemplateLineage       |

## 6. Cross-Table Query Example

To determine the lawful basis asserted for a consent directive and the attestation that authorizes it, execute the equi-join on the foreign key:

```sql
SELECT l.id, l.x, a.x
FROM t_gdpr_lawful_basis l
JOIN t_attestation_signed_by a ON l.y = a.id
WHERE l.x = 'ConsentDirective';
```

Result row: (lba1, ConsentDirective, DataProcessingConsent). The same pattern extends to the remaining tables by matching x values across t_trace_supports_claim, t_kernel_anomaly_supports_claim and t_column_lineage_for_compliance_claim when those classes appear inside a shared compliance claim.
