# Chapter 4: Ontological Mapping of Audit Evidence and Compliance Directives

## 4.1 Scope and Preamble

This chapter establishes the formal ontological mappings required to substantiate compliance claims within a digital governance framework. It details the structural relationships between evidentiary artifacts, authoritative attestations, and regulatory directives. The objective is to provide a precise, machine-readable schema that anchors descriptive information content entities (ICE) to verifiable processes and artifacts. By adhering to the axioms defined below, auditors and compliance officers can ensure that assertions regarding data handling, system integrity, and lawful processing are grounded in irrefutable, traceable evidence. The following sections delineate five specific axioms, their verbalizations, and the corresponding relational schemas that must be utilized to generate audit-ready data structures.

## 4.2 Trace Support for Descriptive Claims

In the context of digital forensics and auditability, a "trace" is defined not merely as a log entry, but as a continuant (specifically, a process or independent continuant) that substantiates a specific claim. The axiom `trace_supports_claim` formalizes this by asserting that a specific class of entity (X) is a subclass of `bfo:0000015` (a process) and necessarily supports a `cco:DescriptiveICE`. This relationship is critical for non-repudiation; it ensures that any descriptive claim made about a system state or transaction is backed by a recorded process trace.

For example, consider a claim stating "User authentication succeeded at 09:00 UTC." The descriptive ICE is the text of the claim itself. The trace is the system process—the execution of the authentication daemon—that generated the log entry confirming the event. Without this ontological link, the claim is an unsubstantiated assertion. The schema requires that every trace instance be uniquely identified and mapped to its class definition to facilitate automated reasoning.

## 4.3 Attestation and Signatory Authority

Governance frameworks rely heavily on the concept of attestation—the formal act of declaring a process or record to be true. The axiom `attestation_signed_by` extends the definition of a class (X) by requiring it to be signed by a `cco:Person`. This creates a chain of accountability that binds a specific process or document to a responsible natural person. In compliance audits, this axiom is used to verify that critical actions, such as the approval of access controls or the validation of data integrity, were performed by authorized individuals rather than automated or anonymous actors.

The relational schema for this axiom enforces that every attestation is recorded as a distinct entity. The primary key (`id`) serves as the unique reference for the attestation event, while the `x` column denotes the class of the attestation (e.g., `PolicyAttestation`, `SignOffRecord`). This structure allows auditors to query all attestations signed by a specific person or to verify that a particular class of document requires a signature.

Consider the scenario where a Data Protection Officer (DPO) signs a Record of Processing Activities (ROPA). The instance of the ROPA signing is the attestation. The schema below captures these instances, ensuring that the class of the attestation is explicitly defined.

## 4.4 Lawful Basis and Regulatory Directives

Under data protection regulations such as the GDPR, processing activities must be grounded in a lawful basis. The axiom `gdpr_lawful_basis` defines a class (X), specifically a `cco:DirectiveICE` (a directive or information content entity prescribing action), which possesses a lawful basis (Y). Crucially, the relational schema imposes a foreign key constraint, linking the lawful basis (Y) to an existing attestation record (`t_attestation_signed_by`). This design enforces the principle that a lawful basis is not merely an abstract concept but must be substantiated by a concrete attestation—such as a signed contract or a consent record.

This structure ensures that for every directive claiming a lawful basis (e.g., "Contractual Necessity"), there exists a verifiable, signed document (the attestation) proving that the basis applies. The `x` column represents the directive class, while the `y` column references the `id` of the relevant attestation. This join operation is essential for automated compliance checks; a directive lacking a valid link to an attestation must be flagged as non-compliant.

The table below demonstrates how directives are anchored to specific attestations, thereby satisfying the requirement for a lawful basis.

## 4.5 Kernel Anomalies as Evidentiary Artifacts

System integrity monitoring often involves the analysis of low-level artifacts, such as kernel dumps or anomaly logs. The axiom `kernel_anomaly_supports_claim` posits that a class (X), defined as a `cco:Artifact` (a physical or digital object), supports a `cco:DescriptiveICE`. Unlike the "trace" defined in Section 4.2, which represents a process, an artifact represents a static object or a byproduct of a system event. In the context of security auditing, these artifacts serve as the primary evidence for claims regarding system stability, intrusion attempts, or hardware failures.

For instance, a claim that "The system experienced a buffer overflow" is supported by the artifact—the core dump file generated by the kernel. The schema distinguishes these artifacts by their class (e.g., `KernelDumpArtifact`, `MemorySnapshotArtifact`). This classification allows automated systems to apply specific retention policies or analysis routines based on the type of artifact collected.

The following table provides examples of kernel-level artifacts that serve as evidence for descriptive claims about system state.

## 4.6 Column Lineage for Compliance Claims

Data lineage is a fundamental requirement for compliance, particularly regarding the "right to be forgotten" and data accuracy mandates. The axiom `column_lineage_for_compliance_claim` defines a class (X), a `cco:Artifact`, which supports a `cco:DescriptiveICE`. Specifically, this artifact represents the metadata or transformation logic that tracks the lineage of a data column. By supporting a descriptive claim (e.g., "Column C2 is derived from Column C1"), the lineage artifact provides the proof necessary to validate that data transformations are compliant with governance policies.

This axiom treats the lineage metadata itself as an artifact. This artifact must be preserved and versioned to support historical claims about the data. The relational schema captures these lineage artifacts, categorizing them to distinguish between different types of transformations (e.g., `PIIMaskingArtifact`, `AggregationArtifact`). This granularity enables auditors to verify that sensitive data has been handled correctly throughout its lifecycle.
