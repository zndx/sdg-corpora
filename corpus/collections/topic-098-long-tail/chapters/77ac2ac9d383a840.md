# Compliance Directive Modeling in Relational Schemas

This chapter defines a minimal relational schema that instantiates five ontology axioms for administrative, physical, and technical HIPAA safeguards together with PCI-DSS requirements, each expressed as a directive that is attested with supporting evidence. The schema supports multi-hop queries that traverse primary-key and foreign-key links to retrieve the evidence associated with any given safeguard.

## 1 Schema Overview

Five tables are derived directly from the supplied axioms. Each table contains an identifier column serving as primary key, a column holding the subject class, and a column holding the object class. Foreign-key constraints enforce the “withSupportingEvidence” and “hipaaSafeguard” / “pciDssRequirement” relations required by the axioms.

## 2 Table Definitions

### 2.1 t_attestation_with_supporting_evidence

Axiom 2 states that an attestation process is something that occurs with supporting evidence. The primary key is the column id. The column y is a foreign key that must resolve to a row in t_hipaa_safeguard_admin, thereby linking each attestation to the administrative safeguard it documents. A reader can join t_attestation_with_supporting_evidence.y to t_hipaa_safeguard_admin.id to retrieve the safeguard class for any attestation.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_hipaa_safeguard_admin(id)
);
```

### 2.2 t_hipaa_safeguard_admin

Axiom 1 states that an administrative safeguard directive safeguards a target class. The primary key is the column id. The column y is a foreign key that must resolve to a row in t_attestation_with_supporting_evidence, closing the evidence loop required by the paired axioms. Joining t_hipaa_safeguard_admin.y to t_attestation_with_supporting_evidence.id yields the attestation that records the safeguard.

```sql
CREATE TABLE t_hipaa_safeguard_admin (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_attestation_with_supporting_evidence(id)
);
```

### 2.3 t_hipaa_safeguard_physical

Axiom 3 states that a physical safeguard directive safeguards a target class. The primary key is the column id. The column y is a foreign key that must resolve to a row in t_attestation_with_supporting_evidence. A cross-table query joining t_hipaa_safeguard_physical.y to t_attestation_with_supporting_evidence.id followed by t_attestation_with_supporting_evidence.y to t_hipaa_safeguard_admin.id retrieves both physical and administrative safeguards for the same attestation.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_attestation_with_supporting_evidence(id)
);
```

### 2.4 t_hipaa_safeguard_technical

Axiom 4 states that a technical safeguard directive safeguards a target class. The primary key is the column id. The column y is a foreign key that must resolve to a row in t_attestation_with_supporting_evidence. Joining through the attestation table permits retrieval of technical safeguards that share the same evidence record as any administrative or physical safeguard.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_attestation_with_supporting_evidence(id)
);
```

### 2.5 t_pci_dss_requirement

Axiom 5 states that a PCI-DSS requirement directive is linked to an attested target class. The primary key is the column id. The column y is a foreign key that must resolve to a row in t_attestation_with_supporting_evidence. A three-table join across t_pci_dss_requirement, t_attestation_with_supporting_evidence, and any HIPAA safeguard table yields all regulatory controls documented under a single attestation.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_attestation_with_supporting_evidence(id)
);
```

## 3 Cross-Join Demonstration

Consider the multi-hop question: “Which PCI-DSS requirement and which technical safeguard share the same attestation that also references administrative safeguard AS-001?”  

Start at t_pci_dss_requirement row whose y equals “AT-003”.  
Follow t_attestation_with_supporting_evidence.id = “AT-003” to obtain y = “AS-001”.  
Follow t_hipaa_safeguard_admin.id = “AS-001” to confirm the administrative safeguard.  
Continue from the same attestation row to t_hipaa_safeguard_technical.y = “AT-003” to retrieve the paired technical safeguard.  

The joined result row is:  
pci_dss_requirement = PR-002, attestation = AT-003, hipaa_safeguard_admin = AS-001, hipaa_safeguard_technical = TS-004.
