# Chapter 4: Governance Frameworks and Ontological Mapping of Compliance Directives

## 4.1 Scope and Preamble

This chapter establishes the formal ontological structures governing the intersection of healthcare data privacy and payment card security. It delineates the axiomatic relationships between administrative, physical, and technical safeguards as defined by the Health Insurance Portability and Accountability Act (HIPAA) Security Rule, and maps these controls to the Payment Card Industry Data Security Standard (PCI DSS). The content herein is intended for compliance officers, information security auditors, and data governance architects who require a rigorous, evidence-based framework for validating directive implementation. The definitions provided are anchored in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that all compliance artifacts are treated as distinct information entities with verifiable provenance and lineage.

## 4.2 Administrative Safeguards

Administrative safeguards constitute the foundational layer of the HIPAA Security Rule, representing the actions, policies, and procedures designed to manage the selection, development, implementation, and maintenance of security measures. These safeguards are not merely procedural recommendations but are formalized as *Directives*—specifically, instances of the `cco:DirectiveICE` class. In the context of our ontology, an Administrative Safeguard is defined as a class that acts as a `sdg:hipaaSafeguard` for a specific target class.

This relationship is critical for auditability: it asserts that for every administrative action (X), there must exist a corresponding object (Y) which is being safeguarded. This object is invariably an attestation or a process artifact, creating a traceable link between policy and evidence. The following axiom defines this structure:

**Axiom 1:** `{X} is something that hipaa safeguard {Y}`.

The relational projection of this axiom demonstrates that the safeguard (X) is inextricably linked to a specific evidence record (Y). The primary key of the safeguard table serves as the unique identifier for the directive, while the foreign key constraint enforces the existence of the supporting attestation record.

In practice, these administrative directives function as the governing logic for the enterprise. For instance, the *SecurityManagementProcess* (admin-001) is not a static document but a living directive that actively safeguards the integrity of the *Annual Risk Assessment Attestation* (attestation-100). This ontological distinction prevents the "zombie policy" phenomenon, where written procedures exist without active enforcement or verification. By anchoring the directive to the attestation via a foreign key, the framework ensures that the policy cannot be considered valid unless the supporting evidence exists and is current.

## 4.3 Attestation with Supporting Evidence

The attestation process represents the formal verification of compliance, categorized under the BFO class `bfo:Process`. An attestation is distinct from the directive itself; it is the act of validation that a directive has been executed effectively. In this framework, an Attestation is defined as a process that possesses `sdg:withSupportingEvidence` some Y.

This axiom introduces a bidirectional dependency within the governance model. While the Administrative Safeguard protects the Attestation, the Attestation itself is validated by evidence that loops back to the originating directive (or a related administrative control). This circular reference is intentional and mirrors real-world audit cycles: a policy (Admin Safeguard) mandates a review (Attestation), and that review is supported by the execution of the policy itself (Evidence).

**Axiom 2:** `{X} is something that with supporting evidence {Y}`.

The schema for this axiom treats the attestation as the central node of compliance verification. The primary key identifies the specific attestation event, while the foreign key (`y`) mandates that the evidence supporting this attestation must be a recognized Administrative Safeguard. This structure enforces the principle that evidence must be authoritative and derived from established governance.

The *AnnualRiskAssessment* (attestation-100) serves as a prime example of this construct. It is a process (X) that validates the security posture of the organization. However, its validity is entirely dependent on the *SecurityManagementProcess* (admin-001). Without the administrative directive defining how risk is to be assessed, the attestation process lacks the authority to exist. This tight coupling ensures that compliance activities are not performed in a vacuum but are always anchored to the governing administrative framework.

## 4.4 Physical Safeguards

Physical safeguards address the measures implemented to protect physical access to electronic information systems and the buildings housing them. Under the ontology, Physical Safeguards are modeled as `cco:DirectiveICE` entities, similar to administrative safeguards, but they are specifically concerned with the tangible environment. The axiom asserts that a Physical Safeguard (X) is a directive that acts as a `sdg:hipaaSafeguard` for a target (Y).

In the relational model, the target (Y) of a Physical Safeguard is an attestation. This reflects the operational reality that physical controls—such as door locks, security cameras, or badge readers—exist to enforce and validate specific access protocols. The physical hardware is the mechanism, but the *Directive* is the rule governing its use, and that rule safeguards the integrity of the access logs or attestation records.

**Axiom 3:** `{X} is something that hipaa safeguard {Y}`.

The schema enforces that every physical safeguard directive must be associated with a valid attestation record. This prevents the deployment of "orphaned" security controls—hardware or physical measures that are not tied to a specific compliance requirement or verification process.

This table embodies Axiom 3, mapping physical security directives (X) to the attestations (Y) they protect. The primary key is `id`, and the foreign key `y` references the attestation table, linking the physical control to the verification process it secures.

| id | x (Physical Directive) | y (Safeguarded Attestation) |
| :--- | :--- | :--- |
| phys-001 | FacilityAccessControl | attestation-104 |
| phys-002 | WorkstationUsePolicy | attestation-102 |
| phys-003 | DeviceAndMediaControl | attestation-103 |

Consider the *FacilityAccessControl* directive (phys-001). This directive governs the locking mechanisms and badge readers at the data center perimeter. Its ontological purpose is to safeguard the *PhysicalEntryLogReview* (attestation-104). If the physical directive fails (e.g., a door is propped open), the integrity of the entry log attestation is compromised, thereby breaking the compliance chain. The foreign key relationship in the data model captures this dependency, ensuring that the validity of the attestation is contingent upon the enforcement of the physical safeguard.

## 4.5 Technical Safeguards

Technical safeguards involve the technology and the policy and procedures for its use that protect electronic protected health information (ePHI) and control access to it. These are the automated mechanisms, such as encryption, authentication protocols, and audit controls. Within the ontology, these are also modeled as `cco:DirectiveICE` entities, acting as `sdg:hipaaSafeguard` for a target class (Y).

The distinction of Technical Safeguards lies in their automation and execution by information systems rather than personnel. However, the governance structure remains consistent: the technical configuration (X) is a directive that safeguards an attestation or process artifact (Y). This allows auditors to query the system for specific technical controls and immediately retrieve the compliance evidence they protect.

**Axiom 4:** `{X} is something that hipaa safeguard {Y}`.

The relational schema for technical safeguards mirrors that of physical safeguards, enforcing the link between the technical directive and the attestation. This structure is essential for vulnerability management, as it allows the organization to trace a technical finding (e.g., an obsolete encryption cipher) directly to the specific attestation record that is now considered at risk.

The *AccessControlMechanism* (tech-001) typically refers to the Identity and Access Management (IAM) system configurations, such as role-based access controls (RBAC). This technical directive safeguards the *AccessRightsAudit* (attestation-102). The logical dependency is clear: the technical mechanism enforces the rules that the audit process verifies. If the technical directive is misconfigured, the attestation of user access rights cannot be trusted. The ontology captures this by binding the technical directive's validity to the existence of the attestation it protects.

## 4.6 PCI DSS Requirements

While HIPAA provides the framework for healthcare data, the Payment Card Industry Data Security Standard (PCI DSS) imposes strict requirements on the handling of cardholder data. In environments where both healthcare and payment data are processed (e.g., hospital billing systems), these frameworks must be integrated. The ontology treats PCI DSS Requirements as `cco:DirectiveICE` entities, acting as `sdg:pciDssRequirement` for a target class (Y).

This axiom allows the organization to map PCI controls directly to the same attestation infrastructure used for HIPAA. This unified approach reduces audit fatigue and ensures that a single evidence repository can satisfy multiple regulatory frameworks. The PCI Requirement (X) is the directive, and it safeguards or requires the attestation (Y).

**Axiom 5:** `{X} is something that pci dss requirement {Y}`.

The relational schema for PCI requirements is identical in structure to the safeguard tables, utilizing a foreign key to the attestation table. This design facilitates cross-walking compliance frameworks, demonstrating that a single control (e.g., an access log) can satisfy both a HIPAA Technical Safeguard and a PCI DSS Requirement.

This directive requires the *AccessRightsAudit* (attestation-102) as proof of compliance. By sharing the attestation record with the HIPAA Technical Safeguard (tech-001), the organization demonstrates a unified control environment. The foreign key constraint validates that the PCI requirement is not merely a theoretical rule but is actively enforcing a specific, documented compliance artifact.
