# Compliance Directive Modeling in Relational Schemas

This chapter defines five tables that instantiate the supplied OWL axioms for directive ICEs, attestations, and supporting evidence. The tables capture administrative, physical, and technical HIPAA safeguards together with PCI DSS requirements, each linked through attestation records that carry evidence references. Primary and foreign keys enforce the slot restrictions stated in the axioms, enabling deterministic cross-table navigation.

## 1 Schema Overview

The relational structures directly project the Manchester axioms. Each row represents a class-level directive whose safeguard or requirement slot is filled by an attestation individual. Foreign-key columns implement the existential restrictions, while the shared id column serves as the primary key for subsequent joins.

## 2 Table Definitions

Column y is a foreign key to t_hipaa_safeguard_admin, recording the safeguard that supplies supporting evidence for the attested process. A reader can join on y to retrieve the administrative safeguard that grounds any given attestation.

## 3 Multi-Hop Query Example

To determine the administrative safeguard and PCI DSS requirement that share attestation att_001, start at t_pci_dss_requirement where y = att_001 to obtain pci_001 and x = Requirement_1_1_Firewall. Then join t_attestation_with_supporting_evidence on id = att_001 to reach y = adm_001. Finally join t_hipaa_safeguard_admin on id = adm_001 to retrieve x = WorkforceSanctionPolicy. The joined result row is (pci_001, Requirement_1_1_Firewall, att_001, adm_001, WorkforceSanctionPolicy).
