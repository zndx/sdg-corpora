# Chapter 4: Ontological Mapping of Compliance Directives and Evidence Artifacts

## 4.0 Scope and Preamble

This chapter establishes the formal ontological relationships between governance directives, specifically within the domains of Payment Card Industry Data Security Standards (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA). It details the structural dependencies between compliance requirements, control implementations, and the evidentiary artifacts necessary for audit verification. The content herein defines a rigorous mapping framework where regulatory mandates are not merely textual guidelines but are instantiated as classes with distinct properties and inter-relations. This approach ensures that compliance posture is not only declarative but is anchored in verifiable, traceable data objects that satisfy the strictures of external auditors and internal governance bodies.

## 4.1 Attestation with Supporting Evidence

### 4.1.1 Formal Definition
In the context of governance frameworks, an attestation represents a formal assertion made by a responsible party regarding the state of compliance. Ontologically, this is modeled as a process, specifically a subclass of `bfo:0000015` (Process). The validity of any attestation is contingent upon its foundation in objective reality; therefore, it must be supported by specific evidence.

The axiom governing this relationship is expressed in Manchester syntax as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:withSupportingEvidence some {Y:Class}`

Verbalized: {X} is something that with supporting evidence {Y}.

Here, {X} represents the attestation process, while {Y} represents the specific requirement or evidence class being attested. This structure prevents vacuous compliance claims by enforcing a foreign-key dependency where no attestation can exist without a referenced evidence artifact.

### 4.1.2 Operational Context
During an annual audit, the Chief Information Security Officer (CISO) must sign a Report on Compliance (ROC). This signature is the attestation. However, for the ROC to be valid, the CISO must reference specific artifacts—such as firewall configuration reviews or vulnerability scan reports—that substantiate the claim. In the ontology, the attestation instance (e.g., "FY24 Q3 Attestation") is inextricably linked to the requirement instance (e.g., "PCI DSS Req 1.2.3").

The following table illustrates instances where attestation processes are anchored to specific PCI DSS requirements, ensuring that every governance claim is backed by a corresponding regulatory mandate.

## 4.2 PCI DSS Requirement

### 4.2.1 Formal Definition
The PCI DSS framework is composed of specific requirements that function as directives. These are modeled as subclasses of `cco:DirectiveICE` (Information Control Element Directive). A requirement, in this ontology, does not exist in isolation; it is defined by its relationship to a specific control implementation that satisfies it.

The axiom is defined as:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`

Verbalized: {X} is something that pci dss requirement {Y}.

In this schema, {X} denotes the specific PCI DSS requirement (e.g., "Requirement 2.1"), and {Y} denotes the control class or instance that fulfills this directive. This mapping allows an organization to trace a high-level regulatory mandate directly to the technical or administrative control enacted to meet it.

### 4.2.2 Dependency Structure
It is critical to note that the relational schema for this concept enforces a recursive dependency structure. A PCI DSS requirement (`X`) must map to a control with evidence requirements (`Y`). This reflects the reality that compliance mandates are essentially wrappers around control activities. The requirement dictates *what* must be achieved, while the linked control defines *how* it is achieved and *what evidence* is produced.

## 4.3 Control with Evidence Requirement

### 4.3.1 Formal Definition
While the PCI requirement defines the mandate, the Control with Evidence Requirement defines the operational mechanism and its documentation needs. This entity is also a subclass of `cco:DirectiveICE`, representing a specific governance or technical control. The distinguishing characteristic is the property `sdg:requiresEvidence`, which mandates the generation of artifacts for auditability.

The axiom is expressed as:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:requiresEvidence some {Y:Class}`

Verbalized: {X} is something that requires evidence {Y}.

In this structure, {X} is the control (e.g., "Firewall Configuration Review"), and {Y} is the evidence artifact or the requirement it validates. This bidirectional linking—where a requirement points to a control, and a control points back to a requirement or evidence—creates a closed loop of verification essential for continuous compliance monitoring.

### 4.3.2 Evidence Generation and Validation
Controls are the engines of compliance. Without a control, a requirement is merely aspirational. Without the evidence requirement, a control is an invisible activity. This ontology formalizes the "Control with Evidence" as a directive that explicitly calls for the production of data. For instance, a "User Access Review" control requires the production of "User Access Logs" as evidence.

The schema enforces a foreign key constraint back to `t_pci_dss_requirement`, reinforcing the concept that controls are implemented specifically to satisfy regulatory clauses.

## 4.4 HIPAA Safeguard Physical

### 4.4.1 Formal Definition
The HIPAA Security Rule delineates specific safeguards intended to protect Electronic Protected Health Information (ePHI). These safeguards are categorized as Administrative, Physical, and Technical. This section addresses the Physical safeguards, modeled as directives (`cco:DirectiveICE`) that secure specific assets or processes.

The axiom is defined as:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:hipaaSafeguard some {Y:Class}`

Verbalized: {X} is something that hipaa safeguard {Y}.

Here, {X} represents the HIPAA safeguard specification (e.g., "Facility Access Controls"), and {Y} represents the control implementation or evidence class that enforces this safeguard. This mapping allows organizations to demonstrate cross-walks between frameworks, showing how a HIPAA physical safeguard might map to a PCI DSS physical control.

### 4.4.2 Cross-Framework Alignment
In complex environments, a single control often satisfies multiple regulatory frameworks. The `hipaa_safeguard_physical` table links HIPAA directives to the generic control definitions established in previous sections. This consolidation reduces audit fatigue by proving that a "Physical Access Control" implemented for PCI DSS simultaneously satisfies the HIPAA "Facility Access Controls" requirement.

## 4.5 Verification Produces Evidence

### 4.5.1 Formal Definition
Verification is the active process of testing, reviewing, or auditing a control to determine its operating effectiveness. Unlike the control itself (which is a directive or state), verification is a process (`bfo:0000015`). The critical output of this process is evidence.

The axiom is expressed as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:producesEvidence some {Y:Class}`

Verbalized: {X} is something that produces evidence {Y}.

In this relationship, {X} is the verification activity (e.g., "Annual Penetration Test"), and {Y} is the resulting evidence or the requirement it satisfies. This distinction is vital for audit trails: it separates the *doing* (verification) from the *state* (control) and the *proof* (evidence).

### 4.5.2 The Audit Lifecycle
The verification process is the mechanism that populates the evidence repositories referenced by the attestation processes in Section 4.1. Without a defined verification process that produces evidence, the control cannot be validated, and the attestation cannot be executed. This completes the governance chain: Requirement -> Control -> Verification -> Evidence -> Attestation.
