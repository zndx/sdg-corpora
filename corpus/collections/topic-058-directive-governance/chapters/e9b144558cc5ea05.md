# Chapter 4: Regulatory Directives and Evidentiary Verification Frameworks

This chapter delineates the structural relationships between regulatory directives, specifically within the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA), and the evidentiary mechanisms required to demonstrate compliance. It establishes a formal ontology for mapping governance directives to control requirements, physical safeguards, and the verification processes that generate audit artifacts. The text provides a rigorous examination of the data structures necessary to support automated compliance reporting and continuous monitoring in high-security environments.

## 1. PCI DSS Requirements

The PCI DSS framework functions as a set of prescriptive directives intended to secure cardholder data. Within the formal ontology, a PCI DSS Requirement is modeled as a subclass of `cco:DirectiveICE`. This classification asserts that the requirement is not merely a static text string but an executable directive within the information control environment. The relationship between the governing body and the specific requirement is captured by the object property `sdg:pciDssRequirement`, which links the directive class to the specific requirement class.

In practical terms, this structure allows an organization to map a high-level governance mandate (X) to a specific PCI DSS control objective (Y). For instance, a corporate policy regarding "Data Transmission Security" (X) serves as the antecedent for "PCI DSS Requirement 4.1" (Y), which mandates the use of strong cryptography. This mapping ensures that technical implementations are traceable back to business-level directives.

The following table illustrates the instantiation of this axiom, demonstrating how specific directive classes are mapped to PCI DSS requirements. The primary key is the unique identifier for the directive mapping, while the foreign key (`y`) establishes the link to the specific control requirement table, ensuring referential integrity across the compliance schema.

| ID | Directive Class (X) | PCI DSS Requirement (Y) |
| :--- | :--- | :--- |
| DIR-PCI-001 | NetworkSegmentationPolicy | PCI_DSS_REQ_1_2_1 |
| DIR-PCI-002 | DataEncryptionStandard | PCI_DSS_REQ_3_4_1 |
| DIR-PCI-003 | AccessControlMgmt | PCI_DSS_REQ_7_1_1 |
| DIR-PCI-004 | LoggingMechanism | PCI_DSS_REQ_10_2_1 |
| DIR-PCI-005 | VulnerabilityMgmt | PCI_DSS_REQ_11_2_1 |

## 2. Control with Evidence Requirements

While the PCI DSS requirements define *what* must be achieved, the implementation of controls defines *how* it is achieved. A Control with Evidence Requirement is defined as a subclass of `cco:DirectiveICE` that necessitates the production of proof. The axiom `sdg:requiresEvidence` establishes a critical dependency: the existence of the control (X) is contingent upon the generation and retention of evidence (Y).

This relationship is foundational for audit readiness. It posits that a control is not considered operational unless it produces the requisite evidence artifacts. For example, a "Quarterly Access Review" (X) is a directive that requires evidence (Y) in the form of "Manager Approval Logs." Without the logs, the control cannot be verified as effective.

The relational schema for this concept enforces a bidirectional link with the PCI requirements, creating a chain of custody from the regulation to the evidence. The table below encodes these relationships, where the `y` column references the specific PCI requirement ID, thereby closing the loop between the control implementation and the regulatory standard.

| ID | Control Class (X) | Evidence Requirement (Y) |
| :--- | :--- | :--- |
| CTRL-EV-001 | FirewallConfigurationReview | PCI_DSS_REQ_1_1_4 |
| CTRL-EV-002 | WirelessAccessPointScan | PCI_DSS_REQ_1_2_3 |
| CTRL-EV-003 | MediaSanitizationLog | PCI_DSS_REQ_3_3_1 |
| CTRL-EV-004 | AntiVirusLogRetention | PCI_DSS_REQ_5_2_3 |
| CTRL-EV-005 | PhysicalEntryLog | PCI_DSS_REQ_9_2_1 |

## 3. HIPAA Safeguard Physical

In environments where Protected Health Information (PHI) intersects with payment data, such as healthcare provider systems, the HIPAA Security Rule imposes additional constraints. The HIPAA Safeguard Physical axiom defines a class (X) that is a subclass of `cco:DirectiveICE` and implements a specific HIPAA safeguard (Y). The property `sdg:hipaaSafeguard` maps the organizational directive to the physical control measures mandated by 45 CFR § 164.310(a)(1).

Physical safeguards are distinct from logical controls in that they pertain to the physical access to buildings and equipment. The ontology treats these as formal directives to ensure they are audited with the same rigor as software configurations. For instance, a "Facility Access Plan" (X) implements the "Physical Access Control" safeguard (Y). This directive must be documented, enforced, and supported by evidence, linking it back to the broader evidence requirement structure defined in the previous section.

The table below details the mapping of organizational directives to specific HIPAA physical safeguards. Note that the foreign key constraint links the safeguard to the evidence requirement table, ensuring that every physical safeguard is associated with a verifiable evidence collection process.

| ID | Directive Class (X) | HIPAA Physical Safeguard (Y) |
| :--- | :--- | :--- |
| HIPAA-PHY-001 | ServerRoomAccessControl | Facility_Access_Controls |
| HIPAA-PHY-002 | WorkstationPositioningPolicy | Workstation_Use |
| HIPAA-PHY-003 | DeviceAssetTracking | Device_and_Media_Controls |
| HIPAA-PHY-004 | VisitorManagementSystem | Access_Authorization |
| HIPAA-PHY-005 | DisposalProceduresForMedia | Device_and_Media_Controls |

## 4. Verification Produces Evidence

The transition from policy to proof is mediated by verification processes. A Verification Produces Evidence is defined as a process (subclass of `bfo:0000015`) that generates an evidence artifact (Y) via the property `sdg:producesEvidence`. This axiom distinguishes the act of checking (the process) from the result of the check (the evidence).

In a mature governance framework, verification is automated and continuous. For example, a "File Integrity Monitoring Scan" (X) is a process that produces "Hash Comparison Reports" (Y). This evidence is the digital exhaust required to satisfy the evidence requirements defined in Section 2. The ontology treats verification as a first-class process entity, allowing for the scheduling, logging, and chaining of verification tasks.

The data structure below captures the output of these verification processes. The `y` column references the PCI requirement, indicating that the evidence produced by the verification process is specifically designed to satisfy a particular compliance clause.

| ID | Verification Process (X) | Evidence Produced (Y) |
| :--- | :--- | :--- |
| VER-001 | AutomatedConfigurationAudit | PCI_DSS_REQ_2_2_4 |
| VER-002 | NetworkVulnerabilityAssessment | PCI_DSS_REQ_11_2_2 |
| VER-003 | WirelessIDSAlertReview | PCI_DSS_REQ_1_2_3 |
| VER-004 | UserRightsPermissionAudit | PCI_DSS_REQ_7_2_2 |
| VER-005 | CriticalPatchLevelVerification | PCI_DSS_REQ_6_2_1 |

## 5. Attestation with Supporting Evidence

The final stage in the compliance lifecycle is attestation. An Attestation with Supporting Evidence is a process (subclass of `bfo:0000015`) that formalizes the declaration of compliance. The property `sdg:withSupportingEvidence` links the attestation act (X) to the body of evidence (Y) that substantiates it.

Attestation is not merely a signature; it is a logical assertion that the accumulated evidence satisfies the applicable directives. For example, a "Annual ROC Sign-off" (X) is an attestation that relies on the aggregate of all vulnerability scans and access logs (Y). This axiom provides the semantic link between the human-readable assertion of compliance and the machine-readable evidence trail.
