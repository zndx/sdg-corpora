# Regulatory Evidence Model for Directive Compliance

This chapter defines five core ontological patterns for representing directive governance and evidence production. The patterns are realized as a relational schema supporting cross-table queries over controls, requirements, attestations, safeguards, and verifications.

## 1 Schema Overview

The schema consists of five tables whose foreign-key relationships directly encode the slot structures of the supplied axioms. Primary keys are opaque identifiers. Foreign keys enforce the “some” restrictions expressed in each Manchester axiom.

### 1.1 t_control_with_evidence_requirement

This table embodies AXIOM 3. Column `id` is the primary key. Column `y` is a foreign key referencing `t_pci_dss_requirement(id)`, recording the evidence class required by the control.

| id | x | y |
|----|---|---|
| ctrl-001 | AccessControl | req-010 |
| ctrl-002 | EncryptionAtRest | req-011 |
| ctrl-003 | AuditLogging | req-012 |
| ctrl-004 | PhysicalAccess | req-013 |

### 1.2 t_pci_dss_requirement

This table embodies AXIOM 2. Column `id` is the primary key. Column `y` is a foreign key referencing `t_control_with_evidence_requirement(id)`, closing the mutual requirement relation between controls and PCI DSS statements.

| id | x | y |
|----|---|---|
| req-010 | 7.1 | ctrl-001 |
| req-011 | 3.4 | ctrl-002 |
| req-012 | 10.2 | ctrl-003 |
| req-013 | 9.1 | ctrl-004 |

### 1.3 t_attestation_with_supporting_evidence

This table embodies AXIOM 1. Column `id` is the primary key. Column `y` is a foreign key referencing `t_pci_dss_requirement(id)`, linking an attestation process to the requirement it supports with evidence.

| id | x | y |
|----|---|---|
| att-100 | QuarterlyAttestation | req-010 |
| att-101 | QuarterlyAttestation | req-011 |
| att-102 | AnnualAttestation | req-012 |
| att-103 | QuarterlyAttestation | req-013 |

### 1.4 t_hipaa_safeguard_physical

This table embodies AXIOM 4. Column `id` is the primary key. Column `y` is a foreign key referencing `t_control_with_evidence_requirement(id)`, associating a HIPAA physical safeguard with its controlling requirement.

| id | x | y |
|----|---|---|
| hip-200 | FacilityAccess | ctrl-004 |

### 1.5 t_verification_produces_evidence

This table embodies AXIOM 5. Column `id` is the primary key. Column `y` is a foreign key referencing `t_pci_dss_requirement(id)`, recording the evidence produced by a verification process.

| id | x | y |

| ver-300 | AutomatedScan | req-010 |

## 2 Cross-Join Example

To retrieve the verification process, the PCI DSS requirement it satisfies, and the control that requirement governs, join three tables on the foreign-key chain:

```sql
SELECT v.x AS verification, p.id AS requirement, c.x AS control
FROM   t_verification_produces_evidence v
JOIN   t_pci_dss_requirement p ON v.y = p.id
JOIN   t_control_with_evidence_requirement c ON p.y = c.id
WHERE  p.id = 'req-010';
```

Result row: verification = AutomatedScan, requirement = req-010, control = AccessControl.
