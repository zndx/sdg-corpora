# Chapter 4: Governance Frameworks and Evidence Ontology

## 4.1 Scope and Preamble

This chapter delineates the structural relationships between regulatory directives, control mechanisms, and the evidentiary artifacts required to demonstrate compliance within complex information security environments. The mapping of these concepts utilizes a formal ontology to bridge the gap between abstract governance requirements and tangible audit artifacts. By defining the precise dependencies between attestations, specific regulatory frameworks such as PCI DSS and HIPAA, and the verification processes that generate evidence, organizations can establish a rigorous, automated chain of custody for compliance activities. The following sections decompose these relationships into five primary axiomatic structures, providing a standardized schema for representing compliance data.

## 4.2 Attestation with Supporting Evidence

In the context of formal governance, an attestation is not merely a declaration of compliance but a distinct process entity that substantiates its claims through direct reference to supporting evidence. The axiom "Attestation with Supporting Evidence" establishes that an attestation (Class X) is a process that possesses or relies upon specific evidence artifacts (Class Y). This relationship is critical for audit readiness, as it decouples the act of attesting from the static evidence itself, allowing for dynamic updates to the evidence base without invalidating the attestation record.

From an ontological perspective, this structure ensures that every attestation is anchored to a verifiable truth within the system. The attestation serves as the logical wrapper for a collection of proofs, transforming raw data into a legally or regulatorily significant statement. For instance, a Chief Information Security Officer (CISO) signing off on an annual security report creates an attestation instance. This instance is semantically invalid unless it links to specific evidence, such as audit logs or configuration snapshots, that satisfy the underlying claims.

The following table illustrates the instantiation of this axiom, mapping specific attestation processes to the PCI DSS requirements they validate. Note that the `y` column serves as a foreign key to the requirement definitions, ensuring referential integrity across the governance model.

**Table 4.1: Attestation Instances Linked to PCI DSS Requirements**

| id | x | y |
| :--- | :--- | :--- |
| ATT-2023-Q3 | Third-Quarter Penetration Test Attestation | PCI-REQ-1.1.4 |
| ATT-2023-ROV | Annual Risk Assessment Verification | PCI-REQ-12.1.2 |
| ATT-2023-CRYPTO | Cryptographic Key Rotation Attestation | PCI-REQ-3.5.1 |
| ATT-2023-PHYS | Data Center Physical Access Review | PCI-REQ-9.1.1 |
| ATT-2023-WIRE | Wireless Network Vulnerability Assessment | PCI-REQ-2.1.1 |

In this schema, `ATT-2023-Q3` represents the specific event or process of the attestation. The entity `PCI-REQ-1.1.4` represents the requirement object which acts as the evidence anchor. This structure allows auditors to query the `t_attestation_with_supporting_evidence` table to immediately retrieve the scope of any signed compliance declaration.

## 4.3 PCI DSS Requirements

The Payment Card Industry Data Security Standard (PCI DSS) provides a granular set of directives designed to protect cardholder data. The axiom "PCI DSS Requirement" posits that a directive (Class X) is a subclass of the ICE (Information Control and Extension) Directive, which specifically necessitates a PCI DSS requirement (Class Y). This formalization allows organizations to map internal policies or governance directives directly to external regulatory mandates.

This relationship is fundamental to the "long tail" of compliance, where high-level governance statements must be traced down to specific, actionable control requirements. By treating the PCI DSS requirement as a distinct object within the relational schema, we enable complex querying—such as identifying all internal directives that map to a specific PCI requirement, or conversely, determining the compliance coverage of a specific directive.

The table below operationalizes this axiom. It defines specific internal directives (X) and maps them to the canonical PCI DSS requirement identifiers (Y). The foreign key constraint ensures that every mapped requirement corresponds to a valid control entry that dictates the evidence necessary for satisfaction.

**Table 4.2: Internal Directives Mapped to PCI DSS Requirements**

| id | x | y |
| :--- | :--- | :--- |
| DIR-FW-001 | Perimeter Firewall Configuration Standard | CTRL-EV-FW-01 |
| DIR-ENC-002 | Data-at-Rest Encryption Policy | CTRL-EV-ENC-01 |
| DIR-LOG-003 | Audit Log Retention and Review Procedure | CTRL-EV-LOG-01 |
| DIR-ACC-004 | User Access Management and Revocation | CTRL-EV-ACC-01 |
| DIR-VUL-005 | Quarterly Vulnerability Scanning Protocol | CTRL-EV-VUL-01 |

Here, the directive `DIR-FW-001` is the internal governance document. It satisfies the PCI DSS requirement slot by referencing `CTRL-EV-FW-01`. This intermediate reference (`CTRL-EV-FW-01`) represents the specific control mechanism that generates the required evidence, creating a necessary layer of indirection that separates policy (the directive) from implementation (the control).

## 4.4 Control with Evidence Requirement

To achieve a defensible compliance posture, an organization must define not only what controls are in place but also what constitutes proof of their operation. The axiom "Control with Evidence Requirement" defines a directive (Class X) that explicitly requires evidence (Class Y). This is a recursive and reinforcing structure within the ontology; the control itself is a directive that points to a requirement, which in turn dictates the evidence artifact.

This distinction is vital for automated compliance monitoring. A "Control" in this context is an active directive—such as a scheduled process or a configuration state—that must emit a specific signal or artifact to be considered effective. The requirement for evidence transforms the control from a static procedure into a measurable data point. For example, a "Password Complexity Policy" is merely a document until it is linked to a "System Access Log" that demonstrates the policy is being enforced.

The relational schema for this axiom, shown below, captures the dependency of the control definition on the evidence requirement. The circular nature of the foreign keys in this section (referencing `t_pci_dss_requirement`) and the previous section highlights the interdependence of controls and regulatory standards.

**Table 4.3: Control Definitions and Evidence Requirements**

| id | x | y |
| :--- | :--- | :--- |
| CTRL-EV-FW-01 | Ingress/Egress Traffic Filter Rule Set | PCI-REQ-1.1.4 |
| CTRL-EV-ENC-01 | AES-256 Database Encryption Module | PCI-REQ-3.4.1 |
| CTRL-EV-LOG-01 | Centralized Syslog Aggregation Daemon | PCI-REQ-10.1.1 |
| CTRL-EV-ACC-01 | LDAP/Active Directory Identity Sync | PCI-REQ-8.1.1 |
| CTRL-EV-VUL-01 | Automated ASV Network Scanner | PCI-REQ-11.2.2 |

In this table, `CTRL-EV-FW-01` (the firewall control) is linked to `PCI-REQ-1.1.4`. This linkage asserts that the existence and configuration of the firewall rule set are specifically intended to satisfy the PCI requirement for reviewing firewall rules every six months. The control `x` is the mechanism, while `y` represents the regulatory obligation that validates the need for the evidence produced by `x`.

## 4.5 HIPAA Safeguard (Physical)

While PCI DSS focuses heavily on technical and operational controls, the Health Insurance Portability and Accountability Act (HIPAA) imposes rigorous standards for physical access and security, particularly within the Physical Safeguards section of the Security Rule. The axiom "HIPAA Safeguard (Physical)" describes a directive (Class X) that implements a specific HIPAA physical safeguard (Class Y).

This mapping is essential for organizations in the healthcare sector that must maintain a unified control framework. It allows physical security measures—such as facility access logs, video surveillance, and workstation placement—to be integrated into the same compliance ontology as technical controls. By treating physical safeguards as directives that reference evidence requirements, the ontology ensures that physical security is audited with the same rigor as cybersecurity.

The table below demonstrates how physical security directives map to the broader control and evidence framework established in previous sections. The foreign key to `t_control_with_evidence_requirement` indicates that these physical safeguards are the mechanisms that generate the evidence required by the underlying control logic.

**Table 4.4: HIPAA Physical Safeguards Mapping**

| id | x | y |
| :--- | :--- | :--- |
| HIPAA-PHYS-01 | Facility Badge Reader and Mantrap System | CTRL-EV-ACC-01 |
| HIPAA-PHYS-02 | Restricted Area Biometric Scanner | CTRL-EV-ACC-01 |
| HIPAA-PHYS-03 | Video Surveilance of Server Room | CTRL-EV-LOG-01 |
| HIPAA-PHYS-04 | Clear Desk and Clean Screen Policy | CTRL-EV-ACC-01 |
| HIPAA-PHYS-05 | UPS and Emergency Power Generator | CTRL-EV-LOG-01 |

For instance, `HIPAA-PHYS-01` (Badge Reader) maps to `CTRL-EV-ACC-01` (User Access Management). This indicates that the physical act of badging into a facility generates the access logs that serve as evidence for the user access control directive. This cross-walking of frameworks ensures that a single physical control can satisfy multiple regulatory obligations (e.g., both HIPAA and PCI physical access requirements).

## 4.6 Verification Produces Evidence

The final concept in this ontological framework addresses the dynamic generation of compliance artifacts. The axiom "Verification Produces Evidence" defines a process (Class X) that results in the creation of evidence (Class Y). Verification differs from a standard control in that it is an active, often periodic, process designed to test or validate the state of a system.

Verification processes are the "engines" of the compliance framework. They include activities such as vulnerability scans, penetration tests, log reviews, and configuration audits. By explicitly modeling these processes as entities that produce evidence, the organization can automate the collection of audit artifacts. When a verification process runs, it should automatically populate the evidence store linked to the relevant requirement.

The following table catalogs verification processes and the specific requirement evidence they produce. This mapping is crucial for establishing the provenance of compliance artifacts; it answers the question "Who created this evidence and when?" by linking the artifact back to the process instance.

**Table 4.5: Verification Processes and Output Evidence**

| id | x | y |
| :--- | :--- | :--- |
| VER-SCAN-01 | External Network Vulnerability Scan | PCI-REQ-11.2.2 |
| VER-AUDIT-02 | Unix/Linux File Integrity Monitoring | PCI-REQ-10.5.5 |
| VER-TEST-03 | Internal Wireless Penetration Test | PCI-REQ-11.1.1 |
| VER-REV-04 | Quarterly Firewall Rule Set Review | PCI-REQ-1.1.4 |
| VER-CHECK-05 | Automated Configuration Drift Detection | PCI-REQ-2.2.1 |

In this schema, `VER-SCAN-01` (the scanning process) produces evidence that satisfies `PCI-REQ-11.2.2` (external vulnerability scanning). This relationship closes the loop on the compliance lifecycle: the directive defines the requirement, the control implements the technical barrier, and the verification process actively generates the evidence that the control is functioning as intended.
