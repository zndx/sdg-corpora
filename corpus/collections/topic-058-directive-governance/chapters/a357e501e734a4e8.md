# Chapter 4: Evidence Lifecycle and Compliance Attestation in Hybrid Regulatory Frameworks

## 4.1 Scope and Preamble

This chapter delineates the structural relationships governing the generation, collection, and verification of compliance evidence within a hybrid regulatory environment. It specifically addresses the intersection of Payment Card Industry Data Security Standards (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA) Security Rule, formalizing how high-level directives decompose into executable controls and verifiable artifacts. The content herein is grounded in a formal ontology where regulatory requirements are mapped to evidence-generating processes, ensuring that governance frameworks are not merely theoretical but anchored in auditable data structures. Readers will examine the relational schema underpinning these mappings, the recursive nature of control requirements, and the final attestation processes that validate the security posture of an enterprise.

## 4.2 PCI DSS Requirements and Control Directives

The foundational unit of compliance within the Payment Card Industry ecosystem is the PCI DSS Requirement. In the formal ontology, this is defined not merely as a textual mandate but as a specific subclass of the *Information Collection Entity (ICE)* directive. The axiom `pci_dss_requirement` establishes that for any requirement class {X}, there exists a necessary relationship to a control class {Y} via the object property `sdg:pciDssRequirement`. This relationship signifies that the abstract requirement is instantiated only through the implementation of a specific control mechanism.

From a governance perspective, this mapping is critical. It prevents the "checkbox compliance" trap where requirements are acknowledged but not operationalized. By enforcing a foreign key constraint where the requirement points to a control identifier, the framework ensures that every mandate has a corresponding executable implementation. For instance, the requirement regarding "Firewall Configuration" is meaningless without the corresponding control of "Rule Set Review."

The relational schema projected by this axiom defines the primary key as the requirement identifier and the foreign key as the control identifier. This structure allows auditors to trace backward from a specific control to the governing requirement and forward from the requirement to its implementation.

## 4.3 Control with Evidence Requirements

While the previous section established the link between requirements and controls, the axiom `control_with_evidence_requirement` addresses the *substantiation* of those controls. A control is a directive (SubClassOf `cco:DirectiveICE`), but its efficacy is proven only through the evidence it requires. The axiom formalizes this as: {X} (the Control) is something that `requiresEvidence` {Y} (the Evidence Requirement).

This introduces a recursive complexity into the compliance framework. The evidence requirement {Y} is not merely a data type but is itself mapped back to a PCI DSS Requirement ID. This circular reference—where a Control points to an Evidence Requirement, which is identified by a PCI Requirement ID—reflects the real-world audit practice where satisfying one control (e.g., "Change Default Passwords") generates evidence that satisfies another requirement (e.g., "Maintain a Vulnerability Management Program").

The relational schema for `t_control_with_evidence_requirement` utilizes the Control ID as its primary key. The foreign key constraint points back to the PCI DSS Requirement table, creating a dense graph of dependencies. This structure ensures that evidence is not generated in a vacuum; every piece of evidence must be attributable to a specific control and, by extension, a specific regulatory mandate.

For example, the control `CTRL_EVID_01` (RuleSetReview) requires evidence that satisfies `PCI_REQ_02` (VendorDefaultPasswords). In practice, this implies that the review of firewall rules must include verification that vendor default credentials have been removed. The schema enforces the logic that the evidence produced by the control is the very proof required by the linked requirement.

## 4.4 Verification Processes and Evidence Production

The static definitions of requirements and controls are activated through the verification process. The axiom `verification_produces_evidence` posits that a verification class {X} (SubClassOf `bfo:0000015`, a Process) produces evidence {Y}. This transitions the framework from a state of "being" (classes and directives) to a state of "doing" (processes and artifacts).

In the context of technical documentation, verification is the systematic examination of controls to determine their effectiveness. The ontology asserts that this examination is not passive; it *produces* the evidence object. This distinction is vital for audit trails. It is insufficient to state that a control exists; the organization must demonstrate the *act* of verifying that control, which yields the evidence artifact.

The schema for `t_verification_produces_evidence` links the Verification Process ID to the PCI DSS Requirement ID. This linkage ensures that verification activities are targeted and purposeful. A generic "security scan" is insufficient; it must be a verification process specifically designed to produce evidence for a identified requirement.

The schema enforces that the evidence produced is valid only if it maps to a recognized requirement ID.

## 4.5 HIPAA Physical Safeguards

The framework expands beyond digital controls to encompass physical security dimensions through the `hipaa_safeguard_physical` axiom. This axiom states that a HIPAA Safeguard class {X} (SubClassOf `cco:DirectiveICE`) implements a HIPAA safeguard {Y}. In the relational projection, this is mapped to the Control with Evidence Requirement table, indicating that physical safeguards are a specific type of control subject to the same evidence rigor as digital controls.

HIPAA's Security Rule explicitly requires physical safeguards to protect Electronic Protected Health Information (EPHI). These include facility access controls, workstation security, and device and media controls. By mapping these safeguards to the `t_control_with_evidence_requirement` table, the ontology integrates HIPAA compliance into the broader evidence lifecycle. A physical safeguard, such as a "Server Room Access Log," is treated as a control that must produce evidence satisfying a specific requirement.

This suggests that the physical security of workstations is verified through the review of access rules (which may include logical access controls tied to physical presence). This cross-pollination between physical safeguards and logical control evidence demonstrates a holistic approach to security governance.

## 4.6 Attestation with Supporting Evidence

The culmination of the evidence lifecycle is the attestation. The axiom `attestation_with_supporting_evidence` defines an attestation class {X} (SubClassOf `bfo:0000015`, a Process) that possesses supporting evidence {Y}. Attestation is the formal declaration by a qualified authority (e.g., a Chief Information Security Officer or an external auditor) that the controls have been implemented and are operating effectively.

Unlike verification, which is a technical act, attestation is a governance act. It consumes the evidence produced by verification processes and issues a statement of compliance. The axiom specifies that the attestation is "with supporting evidence," meaning the attestation object is invalid or incomplete without the referenced evidence artifacts.

The relational schema for `t_attestation_with_supporting_evidence` links the Attestation ID to the PCI DSS Requirement ID. This creates a direct line of sight from the final executive sign-off down to the specific technical requirement being satisfied. It prevents generic attestations (e.g., "We are secure") by forcing the attestation to be anchored to specific, evidence-backed requirements.
