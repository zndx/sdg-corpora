# Chapter 4: Formalization of Compliance Directives and Evidence Verification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for mapping regulatory compliance requirements to verifiable evidence artifacts within a governance system. The text details the structural relationships between high-level directives—specifically those derived from the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA)—and the procedural mechanisms required to validate them. By utilizing the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO), we define a rigorous schema for tracking attestations, safeguards, and verification processes. The following sections decompose these concepts into relational data structures, ensuring that every compliance claim is anchored to a specific, auditable evidence lineage.

## 4.2 Attestation with Supporting Evidence

In the context of governance, an attestation is not merely a declaration but a distinct process (BFO:0000015) that substantiates compliance through the citation of specific artifacts. The ontology defines the class `AttestationWithSupportingEvidence` as a subclass of processes that necessarily possess the property `withSupportingEvidence`. This relationship mandates that for any attestation to be valid within the system, it must reference a concrete evidence artifact or a requirement that generates such evidence. This formalization prevents "orphan" attestations—claims made without backing data—and enforces a strict dependency chain between the assertion of control and the proof of its execution.

The relational projection of this axiom establishes a direct link between the attestation entity and the PCI DSS requirement it fulfills. The primary key serves as the unique identifier for the attestation event, while the foreign key constraint ensures that the attestation points to a valid, pre-existing regulatory requirement.

## 4.3 PCI DSS Requirements

The PCI DSS Requirement class functions as a central node in the compliance ontology, bridging the gap between abstract directives and concrete controls. Formally, this class is a subtype of `cco:DirectiveICE` (Information Collection Entity), representing an information-bearing directive that prescribes specific action. The axiom `pci_dss_requirement` posits that these directives possess the object property `pciDssRequirement`, linking the general directive to a specific control class. This structure allows the governance framework to differentiate between the text of the regulation (the directive) and the technical implementation (the control) required to satisfy it.

The data schema for this concept creates a recursive dependency within the compliance framework. The `y` slot, representing the control, is validated by a foreign key referencing the control table, which in turn may reference back to the requirement table. This circularity reflects the real-world iterative nature of compliance, where requirements define controls and controls validate requirements.

## 4.4 Control with Evidence Requirement

A control is only as effective as its observability. The `ControlWithEvidenceRequirement` axiom formalizes this by asserting that any directive (`cco:DirectiveICE`) designed to function as a control must necessarily `requireEvidence`. This evidence is not merely the output of the control but the documented proof that the control operated as intended. In audit scenarios, the absence of this evidence constitutes a failure of the control itself, regardless of whether the control functioned correctly in the background. The ontology treats the evidence requirement as a mandatory component of the control's definition.

The relational schema for this axiom enforces a strict validation loop. The `y` column, representing the evidence requirement, must reference a valid PCI DSS requirement. This structure ensures that the evidence demanded by a control is explicitly tied to a regulatory mandate, preventing the collection of superfluous data that does not support compliance objectives.

## 4.5 HIPAA Safeguard (Physical)

While PCI DSS focuses on data security and cardholder environments, HIPAA introduces specific requirements regarding the physical protection of health information. The `hipaa_safeguard_physical` axiom defines a class of directives that serve as physical safeguards (`sdg:hipaaSafeguard`). These are tangible measures—facility restrictions, workstation usage policies, and device security—implemented to protect Electronic Protected Health Information (ePHI). In the ontology, these safeguards are modeled as directives that target specific control requirements, effectively overlaying physical security constraints onto the technical control framework.

The data structure for physical safeguards links the safeguard directive to a control with evidence requirements. This implies that the effectiveness of a physical safeguard (e.g., a badge reader) must be proven by the same rigorous evidence standards applied to technical controls (e.g., access logs).

## 4.6 Verification Produces Evidence

The final component of the governance framework is the verification process. The `verification_produces_evidence` axiom identifies a specific class of processes (BFO:0000015) that result in the generation of evidence. Verification differs from mere operation; it is an active, often independent, review of the system state to confirm adherence to directives. This axiom closes the loop by defining the procedural origin of the evidence artifacts referenced by the attestation and control classes.

In the relational model, the verification process is explicitly linked to the PCI DSS requirement it validates. This linkage ensures that every piece of evidence in the system can be traced back to a specific verification event, which in turn is tied to a regulatory requirement. This traceability is the cornerstone of a defensible audit trail.
