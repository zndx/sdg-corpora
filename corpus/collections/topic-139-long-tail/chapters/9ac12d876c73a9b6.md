# Chapter 4: Ontological Foundations for Kernel-Level Observability and Compliance Tracing

This chapter establishes the formal ontological framework required to audit high-frequency kernel interactions and system-level observability mechanisms. In the context of modern governance frameworks, the ability to trace a system event from a low-level syscall to a high-level compliance alert is not merely a technical convenience but a regulatory imperative. The following sections detail five core axioms that define the relationships between metric emission, protocol adherence, syscall traceability, alert triggering, and eBPF-based observation. These concepts provide the evidentiary backbone for automated audit reports, ensuring that every generated artifact is anchored to a verifiable process and a defined protocol.

## 4.1 Metric Emission Subclasses

The first pillar of the observability framework concerns the provenance of quantitative data. Within the ontology, a Metric Emission Subclass is defined as a specific type of process (`bfo:0000015`) that is causally responsible for the generation of a specific metric. This relationship is critical for auditability because it establishes the source of truth for numerical data points used in capacity planning and performance regulation. If a metric cannot be traced back to an emitting process that is itself a subclass of a recognized process, the data fails the validation checks required for compliance reporting.

Formally, the axiom states: `{X} is something that emits metric {Y}`. Here, `X` represents the process class (the emitter), and `Y` represents the metric class being emitted. This distinction allows auditors to differentiate between the process of measurement and the measurement itself, a separation that is often blurred in legacy logging systems.

## 4.2 Lab Runs with Protocol Adherence

To ensure that metric emissions are not generated in a vacuum, they must be contextualized within a formalized execution environment. A Lab Run with Protocol represents a process instance that strictly adheres to a predefined set of instructions or a protocol class. This concept is central to the reproducibility of audit findings. It mandates that any process claiming to generate compliance evidence must be an instance of a class that follows a specific protocol (`sdg:followsProtocol`).

The verbalization of this axiom is: `{X} is something that follows protocol {Y}`. In this structure, `X` denotes the lab run or the specific execution instance, while `Y` denotes the protocol class governing that execution. This relationship allows governance frameworks to query not just what data was produced, but under what exact methodological conditions it was produced.

## 4.3 Syscall Traceability

As we descend to lower levels of system abstraction, the concept of Syscall Traceability becomes paramount. In a secure environment, specific Information Content Entities (ICE) designated by the system—such as file descriptors or socket handles—must be traceable by authorized monitoring processes. This axiom defines a class of designative information entities (`cco:DesignativeICE`) that are subject to tracing by a specific process class.

The axiom is verbalized as: `{X} is something that traceable by {Y}`. Here, `X` represents the syscall or the designative entity being traced, and `Y` represents the tracing process (often the Lab Run established in Section 4.2). This relationship provides the granular audit trail required to satisfy security controls that mandate the monitoring of privileged instructions.

Consider the entry for `trace_01`: the `OpenAtSyscall` is traceable by `labrun_01`. This means that during the `NetworkStressTest`, the system is authorized to trace file opening operations. This restriction prevents unauthorized monitoring of syscalls outside the scope of the defined protocol, thereby preserving user privacy and system integrity.

## 4.4 Alert Triggering Mechanisms

The final logical step in the observability chain is the reaction to observed data. An Alert Triggered By metric is a process that activates automatically when specific metric thresholds are breached. This concept transforms passive monitoring into active governance. Within the ontology, this is defined as a process (`bfo:0000015`) that is initiated or triggered by a specific metric instance (`sdg:triggeredByMetric`).

The axiom is stated: `{X} is something that triggered by metric {Y}`. `X` represents the alert process, and `Y` represents the metric instance that serves as the trigger. This formalization is essential for automated incident response, as it explicitly encodes the causal link between a system state (the metric) and a remedial action (the alert).

| id | x | y |
| :--- | :--- | :--- |
| alert_01 | HighLatencyAlert | labrun_01 |
| alert_02 | CPUThrottlingAlert | labrun_02 |
| alert_03 | OOMRiskAlert | labrun_03 |

| alert_05 | DeadlockAlert | labrun_05 |

For example, the `HighLatencyAlert` (id: `alert_01`) is triggered by the conditions observed during `labrun_01`. This ensures that alerts are not generated in isolation; they are inextricably linked to the protocol instance that detected the anomaly, allowing auditors to reconstruct the exact sequence of events leading to the alert.

## 4.5 eBPF Event Observation

The implementation of the tracing mechanisms described above relies heavily on extended Berkeley Packet Filter (eBPF) technology. The ontology defines a specific class of processes—eBPF Events—that are capable of observing syscall information. This axiom captures the technical capability of the monitoring infrastructure to hook into the kernel and observe `cco:DesignativeICE` entities without modifying the kernel source code.

The axiom is verbalized as: `{X} is something that observes syscall designative information content entity`. This is a specialized subclass of process (`bfo:0000015`) that possesses the capability to observe low-level syscalls. It is the technological enabler for the traceability relationships defined in Section 4.3.
