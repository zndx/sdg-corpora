# Chapter 4: Ontological Foundations for Kernel Audit and Metric Compliance

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for validating kernel-level observability and compliance metrics within high-assurance environments. It delineates the structural relationships between system processes, the protocols they execute, and the metrics emitted during execution. The definitions provided herein are mandatory for any audit subsystem seeking to certify adherence to the Secure Data Governance (SDG) specifications. All entities referenced in the subsequent sections must be instantiated in accordance with the relational schemas provided, ensuring that traceability is maintained from the low-level syscall layer up to high-level alerting mechanisms. This framework is intended for systems architects, compliance officers, and security auditors who require a deterministic mapping between runtime behavior and formal ontological commitments.

## 4.2 Metric Emission Subclasses

The fundamental unit of observability in any distributed system is the metric, which serves as a quantifiable proxy for system state. In this ontology, we define a specific subclass of processes that are responsible for the generation of these metrics. Formally, we assert that a process $X$ is a subclass of `bfo:0000015` (a process) that emits a metric $Y$. This relationship is not merely causal but definitional; the existence of the process $X$ is characterized by its capacity to produce $Y$.

To maintain auditability, every metric emission event must be cataloged with a unique identifier and a reference to the specific metric class being emitted. This allows for the differentiation between, for example, a process emitting a "CPU temperature" metric versus one emitting "I/O latency," even if the underlying process class is identical. The relational implementation of this axiom enforces a strict dependency: the metric being emitted ($Y$) must correspond to a valid laboratory or execution run context, ensuring that metrics are not generated in a vacuum but are always anchored to a specific, protocol-bound execution session.

## 4.3 Laboratory Runs with Protocol Adherence

A critical component of the governance framework is the concept of the "Laboratory Run" (or LabRun), which represents a distinct, bounded execution session. Unlike a generic process, a LabRun is formally defined by its adherence to a specific protocol. We assert that a LabRun $X$ is a subclass of `bfo:0000015` that follows protocol $Y$. This protocol adherence is the binding mechanism that transforms raw execution into a verifiable, compliant activity.

The structural integrity of the audit trail relies on a recursive validation loop. The protocol followed by the LabRun ($Y$) is itself defined by the metric emission requirements established in the previous section. Consequently, the relational schema for LabRuns includes a foreign key constraint referencing the metric emission subclass. This creates a closed loop of verification: a LabRun is valid only if it follows a protocol that is itself defined by a valid metric emission subclass. This structure prevents "orphan" protocols that do not result in observable outputs and ensures that every execution run is theoretically capable of being validated against the metrics it purports to generate.

## 4.4 Syscall Traceability and Information Content Entities

To achieve granular observability, the framework must account for the lowest level of user-kernel interaction: the system call. We define a class of entities ($X$) that are subclasses of `cco:DesignativeICE` (Information Content Entity) and are traceable by a specific LabRun ($Y$). This axiom, `syscall_traceable`, provides the semantic link between the abstract data generated by a syscall and the concrete execution run that captures it.

In practice, this means that specific syscall instances—such as an `open()` or `read()` invocation carrying specific arguments—are not treated as transient events but as persistent Information Content Entities. The "traceable by" relationship ensures that these entities can be attributed to a specific LabRun protocol. This is essential for forensic analysis, where an auditor must be able to trace a specific system call back to the compliance run that was active at the time of execution. The relational schema mandates that the tracing entity ($Y$) must be a valid LabRun, thereby anchoring the syscall data to the protocol layer defined in Section 4.3.

## 4.5 Alert Triggering Mechanisms

While metrics provide continuous observability, alerts provide the reactive enforcement of governance policies. We define an alert class $X$ as a subclass of `bfo:0000015` (a process) that is triggered by a specific metric $Y$. The `alert_triggered_by` axiom formalizes the transition from monitoring to action. It ensures that every alerting process is strictly coupled to a metric emission event, preventing spurious or ungrounded alerts.

The architecture dictates that the triggering metric ($Y$) must be associated with a LabRun. This constraint is critical for maintaining the context of the alert; an alert is not merely a reaction to a number crossing a threshold, but a reaction to a specific state observed during a specific protocol execution. For instance, a "High Memory Usage" alert is only valid if it is triggered by a metric emitted during a "SecureMemoryScanRun." This filtering logic is embedded directly in the relational schema, where the metric reference ($Y$) must resolve to a valid LabRun context.

## 4.6 eBPF Event Observation of Syscalls

The final layer of the ontology concerns the mechanism of observation itself. Modern high-performance systems utilize extended Berkeley Packet Filter (eBPF) for low-overhead tracing. We define an eBPF event class $X$ as a process that observes a syscall Designative Information Content Entity. The `ebpfevent_observes_syscall_xref` axiom serves as the cross-reference linking the observation tool (eBPF) to the target entity (the syscall).

This axiom is distinct in that it does not require a foreign key dependency on the LabRun table in its primary schema definition; rather, it establishes the capability of the eBPF program. However, in the broader governance framework, the eBPF event is the *means* by which the syscall traceability (Section 4.4) is technically realized. By defining this relationship, the ontology explicitly models the instrumentation layer, ensuring that the tools used for compliance are themselves first-class entities within the system model.
