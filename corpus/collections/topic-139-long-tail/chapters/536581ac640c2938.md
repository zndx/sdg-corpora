# Chapter 7: Formal Ontologies for Kernel Observability and Compliance Auditing

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures required to establish high-fidelity audit trails within kernel-level observability frameworks. In the context of modern compliance governance—specifically regarding frameworks such as NIST 800-53 and GDPR—system telemetry must be anchored to rigorous semantic definitions. The following sections introduce a set of interlocking axioms derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), projected into a relational schema suitable for persistent storage and forensic analysis. The intent is to provide a deterministic mapping between abstract system processes (e.g., eBPF program execution) and their tangible outputs (metrics, alerts, and syscall traces), ensuring that every observable event is traceable to a validated protocol.

## 7.2 Metric Emission Subclasses

The foundational unit of observability in any audited system is the generation of telemetry data. We define this relationship through Axiom 1, which establishes the criteria for a process to be a valid emitter of metrics.

**Axiom 1 (metric_emission_subclass):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:emitsMetric some {Y:Class}`
*   **Verbalization:** {X} is something that emits metric {Y}

In this construct, the subject {X} represents a specific process instance (classified under `bfo:0000015`, a Process), while the object {Y} represents the metric being emitted. For the purposes of auditability, it is insufficient to simply record a numerical value; the system must record the *provenance* of that metric. The relational projection of this axiom enforces a strict dependency: a metric emission event is valid only if it is associated with a specific laboratory or execution run (`t_labrun_with_protocol`). This ensures that metrics do not exist in a vacuum but are the result of a controlled, protocol-driven experiment or operational run.

The following table embodies this axiom. The primary key (`id`) uniquely identifies the emission event. The column `x` denotes the process responsible for the emission, while `y` acts as a foreign key referencing the specific execution run that validates or contains the metric logic.

**Table 7.1: Metric Emission Subclass Registry**

| id | x | y |
| :--- | :--- | :--- |
| `emission_001` | `KernelTelemetryDaemon` | `labrun_001` |
| `emission_002` | `UserSpaceProfiler` | `labrun_002` |
| `emission_003` | `NetworkLatencyMonitor` | `labrun_003` |
| `emission_004` | `IOPS_Aggregator` | `labrun_004` |
| `emission_005` | `ThermalControlProcess` | `labrun_005` |

*Table 7.1 Note:* The foreign key constraint on column `y` referencing `t_labrun_with_protocol(id)` ensures that every metric emission is strictly bound to a valid execution context. In the instance `emission_001`, the `KernelTelemetryDaemon` is formally recorded as emitting data within the scope of `labrun_001`.

## 7.3 Lab Runs with Protocol

To maintain the integrity of the metrics emitted, the system must enforce that all processes operate within the bounds of a defined protocol. Axiom 2 formalizes the relationship between an execution run (a "lab run") and the protocol it adheres to.

**Axiom 2 (labrun_with_protocol):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:followsProtocol some {Y:Class}`
*   **Verbalization:** {X} is something that follows protocol {Y}

Here, {X} denotes the lab run or execution instance, and {Y} denotes the protocol class. In a compliance context, the protocol represents the governance logic, configuration, or standard operating procedure (SOP) that the run is obligated to follow. The relational schema for this axiom establishes a reciprocal dependency with the metric emission table. Specifically, the protocol followed ({Y}) is referenced by the metric emission table, creating a closed loop of verification: the emission defines the metric, the lab run executes the protocol, and the protocol validates the emission.

The table below illustrates this mapping. The `id` represents the unique identifier for the lab run. Column `x` identifies the specific run instance, and column `y` references the protocol definition (which, in this schema structure, is keyed to the metric emission ID, implying a tight coupling where the protocol is defined by the metric requirements it governs).

**Table 7.2: Lab Run Protocol Adherence**

| id | x | y |
| :--- | :--- | :--- |
| `labrun_001` | `ComplianceAuditRun_Alpha` | `emission_001` |
| `labrun_002` | `StressTestSequence_Beta` | `emission_002` |
| `labrun_003` | `NetworkBaseline_Gamma` | `emission_003` |
| `labrun_004` | `StorageThroughput_Delta` | `emission_004` |
| `labrun_005` | `EnvironmentalCheck_Epsilon` | `emission_005` |

*Table 7.2 Note:* The primary key `id` serves as the anchor for traceability. The foreign key `y` referencing `t_metric_emission_subclass(id)` ensures that the protocol followed is inextricably linked to the metric emission profile. For instance, `labrun_001` follows the protocol defined by `emission_001`, ensuring that the `KernelTelemetryDaemon` operates strictly within the parameters established for that run.

## 7.4 Syscall Traceability

A critical requirement for kernel-level auditing is the ability to trace specific system calls back to the execution runs that generated or monitored them. Axiom 3 defines the traceability of system calls, which are modeled as `cco:DesignativeICE` (Information Content Entities).

**Axiom 3 (syscall_traceable):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:traceableBy some {Y:Class}`
*   **Verbalization:** {X} is something that traceable by {Y}

In this axiom, {X} represents the system call (or the informational entity representing the syscall), and {Y} represents the mechanism or process that traces it. The schema dictates that the traceability is established via a reference to a lab run. This implies that the "traceability" is not merely a log entry but a formal relationship managed by the observability framework. The syscall is only considered "traceable" if it is formally associated with a valid lab run ID.

The following table captures these traceability links. The `id` is the unique identifier for the traceability record. Column `x` contains the specific syscall or designative entity (e.g., `SyscallOpenAt`), and column `y` contains the foreign key to the lab run that provides the trace context.

**Table 7.3: Syscall Traceability Matrix**

| id | x | y |
| :--- | :--- | :--- |
| `trace_001` | `SyscallOpenAt` | `labrun_001` |
| `trace_002` | `SyscallExecve` | `labrun_002` |
| `trace_003` | `SyscallConnect` | `labrun_003` |
| `trace_004` | `SyscallRead` | `labrun_004` |
| `trace_005` | `SyscallIoctl` | `labrun_005` |

*Table 7.3 Note:* The foreign key constraint on `y` ensures that every syscall trace is grounded in a specific execution context (`t_labrun_with_protocol`). For example, the `SyscallOpenAt` instance (`trace_001`) is traceable specifically by `labrun_001`, meaning its occurrence and parameters are recorded under the `ComplianceAuditRun_Alpha`.

## 7.5 Alert Triggering Mechanisms

Automated compliance systems rely on alerts to signal deviations from established protocols. Axiom 4 formalizes the conditions under which an alert is triggered, linking the alert event to the metric that caused it.

**Axiom 4 (alert_triggered_by):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:triggeredByMetric some {Y:Class}`
*   **Verbalization:** {X} is something that triggered by metric {Y}

The subject {X} is the alert event itself (a process), and {Y} is the metric instance that triggered the alert. Consistent with the schema design, the metric is referenced via the lab run ID. This structure allows auditors to query an alert and immediately retrieve the full execution context (the lab run) and the protocol adherence data associated with the triggering metric.

The table below catalogs these alert events. The `id` uniquely identifies the alert. Column `x` describes the alert type or instance, and column `y` references the lab run (acting as the metric proxy) responsible for the trigger.

**Table 7.4: Alert Trigger Registry**

| id | x | y |
| :--- | :--- | :--- |
| `alert_001` | `PrivilegeEscalationDetected` | `labrun_001` |
| `alert_002` | `CPUThresholdExceeded` | `labrun_002` |
| `alert_003` | `LatencyAnomalyDetected` | `labrun_003` |
| `alert_004` | `IOPS_DegradationWarning` | `labrun_004` |
| `alert_005` | `ThermalTripPointReached` | `labrun_005` |

*Table 7.4 Note:* Referential integrity is enforced by the foreign key `y` pointing to `t_labrun_with_protocol(id)`. The alert `PrivilegeEscalationDetected` (`alert_001`) is triggered by the metric conditions observed in `labrun_001`. This linkage allows forensic analysts to navigate from the alert to the specific syscall traces (`trace_001`) and protocol adherence records associated with that run.

## 7.6 eBPF Event Observation

Finally, the collection of the aforementioned data is often facilitated by extended Berkeley Packet Filter (eBPF) programs, which allow for low-overhead, dynamic tracing of the kernel. Axiom 5 defines the relationship between an eBPF event and the syscall it observes.

**Axiom 5 (ebpfevent_observes_syscall_xref):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:observesSyscall some cco:DesignativeICE`
*   **Verbalization:** {X} is something that observes syscall designative information content entity

This axiom identifies {X} as the eBPF event process. The object of the observation is a syscall, modeled as a `cco:DesignativeICE`. Unlike previous tables, this schema does not require a foreign key to the lab run table, serving instead as a cross-reference (xref) table that links the observing event directly to the syscall entity. This table is critical for mapping the raw instrumentation (eBPF) to the semantic entities (syscalls) used in the audit trail.

The table below provides the mapping for these observation events. The `id` is the unique identifier for the eBPF event, and `x` denotes the specific syscall being observed.
