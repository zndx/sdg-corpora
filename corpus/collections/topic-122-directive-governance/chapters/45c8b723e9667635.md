# Chapter 4: Ontological Formalization of Process Attribution and Traceability

This chapter establishes the formal requirements for mapping system-level events to ontological structures within a compliance framework. It delineates the specific axioms governing process attribution, artifact participation, and traceability mechanisms required for rigorous audit trails. The definitions provided herein are binding for all subsequent data ingestion pipelines and must be interpreted in accordance with the schema definitions provided in the appendices.

## 4.1 Observation with Participant

The fundamental unit of audit evidence is the observation, defined axiomatically as a process that necessarily involves a participant artifact. Under the axiom `observation_with_participant`, any entity classified as a process (X) must be substantiated by its relation to a specific artifact (cco:Artifact). This relationship ensures that abstract process flows are grounded in tangible, observable system objects, such as configuration files, binaries, or data streams. In the context of regulatory compliance, this axiom prevents the logging of "orphan" processes—those without a tangible target or input—thereby enhancing the evidentiary weight of the log data.

The relational projection of this axiom is captured in the table `t_observation_with_participant`. The primary key (`id`) serves as the unique identifier for the observation instance, while the column `x` denotes the class of the process performing the observation. It is imperative that the process class defined in `x` is a recognized subclass of `bfo:Process`. Failure to map `x` to a valid process class constitutes a schema violation and must trigger an alert in the data validation layer.

*Table 4.1: Observation with Participant Instances*

| id | x |
|---|---|
| OBS-2023-8492 | FileReadProcess |
| OBS-2023-8493 | NetworkSocketProcess |
| OBS-2023-8494 | RegistryKeyQuery |
| OBS-2023-8495 | MemoryAllocationProcess |
| OBS-2023-8496 | DeviceDriverLoad |

In Table 4.1, the instance `OBS-2023-8492` represents a `FileReadProcess`. Per the governing axiom, this entry implies the existence of an artifact (the file being read) which acts as the patient or participant in the process. While the artifact itself is not explicitly named as a column in this specific projection, its existence is a necessary condition for the validity of the row. The `id` column provides the referential anchor for all subsequent temporal and attributional data.

## 4.2 Process Operator Constraints

To maintain a strict chain of custody, the framework enforces constraints on the number of operators associated with a given process. The axiom `process_max_one_operator` stipulates that a process (X) may have at most one operator (Y). This constraint is critical for environments requiring non-repudiation; by limiting the operator count to one (max 1), the system eliminates ambiguity regarding accountability. If a process were permitted to have multiple operators simultaneously, determining the specific responsible party for a malicious or errant action would become logically impossible within the binary logic of the audit trail.

The implementation of this axiom relies on the table `t_process_max_one_operator`. The structure links a process instance to a specific observation ID (`y`), which serves as the proxy for the operator context. The foreign key constraint ensures that the operator reference is valid and grounded in a previously established observation. It is the responsibility of the ingress controller to verify that no single process identifier (`x`) is associated with more than one active operator entry in a given transaction window.

*Table 4.2: Process Operator Assignments*

| id | x | y |
|---|---|---|
| PROC-OP-1001 | AuthenticatedShell | OBS-2023-8492 |
| PROC-OP-1002 | SystemDaemon | OBS-2023-8493 |
| PROC-OP-1003 | UserApplication | OBS-2023-8494 |
| PROC-OP-1004 | BackgroundWorker | OBS-2023-8495 |
| PROC-OP-1005 | SecurityService | OBS-2023-8496 |

As evidenced in Table 4.2, the `AuthenticatedShell` process (`PROC-OP-1001`) is linked to observation `OBS-2023-8492`. The referential integrity mandated by the schema dictates that `OBS-2023-8492` must exist in the `t_observation_with_participant` table. This linkage binds the abstract concept of the "operator" to the concrete reality of the system observation. Auditors must query this table to establish the "who" behind the "what" defined in the previous section.

## 4.3 Event Start Time Attribution

Temporal precision is a cornerstone of forensic analysis. The axiom `schemaorg_event_starttime` formalizes the relationship between an artifact (X) and the initiation time of an event (Y). In this schema, the artifact (e.g., a log file, a system report, or a configuration object) is the entity possessing the property `hasEventStartTime`. Notably, the schema defines the start time (`y`) not as a literal timestamp, but as a reference to an observation instance. This design choice anchors the abstract concept of time to the specific observational event that marked the commencement of the artifact's lifecycle or relevance.

The table `t_schemaorg_event_starttime` enforces this relationship. The column `x` must contain a class reference to an `cco:Artifact`, while `y` must contain a valid foreign key referencing `t_observation_with_participant`. This structure ensures that a start time cannot exist in a vacuum; it is inextricably linked to the process observation that generated it. Compliance officers should note that any artifact lacking a corresponding entry in this table is considered "temporally unanchored" and may be excluded from the timeline of events during an investigation.

*Table 4.3: Event Start Time Mapping*

| id | x | y |
|---|---|---|
| EVT-START-500 | SystemLogArtifact | OBS-2023-8492 |
| EVT-START-501 | NetworkPacketCapture | OBS-2023-8493 |
| EVT-START-502 | ConfigurationSnapshot | OBS-2023-8494 |
| EVT-START-503 | HeapDumpFile | OBS-2023-8495 |
| EVT-START-504 | DriverManifest | OBS-2023-8496 |

In Table 4.3, the `SystemLogArtifact` is attributed the start time reference `OBS-2023-8492`. This indicates that the validity or creation of the log artifact is temporally bounded by the initiation of the observation recorded in the base table. This recursive referencing of observations allows the audit system to reconstruct a precise sequence of events without relying on potentially mutable system clocks, instead using the immutable sequence of observation IDs.

## 4.4 Trace Subclass and Spanning

Advanced monitoring environments utilize tracing to correlate low-level system events with higher-level logical processes. The axiom `trace_subclass` defines a process (X) that "spans" another process (Y). In this context, "spanning" implies a containment or duration relationship where the trace process X encompasses the lifecycle of process Y. Crucially, the schema constrains Y to be a process that is governed by the `process_max_one_operator` axiom. This constraint ensures that high-fidelity traces are only generated for processes that have a defined, single operator, thereby filtering out anonymous or multi-user system noise from the trace stream.

The relational representation `t_trace_subclass` requires that the spanned process (`y`) must correspond to an entry in `t_process_max_one_operator`. This foreign key constraint enforces the hierarchy: a Trace spans a Monitored Process, which in turn has a Single Operator. This three-tier hierarchy is essential for isolating the actions of specific users within complex, multi-threaded execution environments.

*Table 4.4: Trace Subclass Correlations*

| id | x | y |
|---|---|---|
| TRACE-800 | KernelSyscallTrace | PROC-OP-1001 |
| TRACE-801 | APICallTrace | PROC-OP-1002 |
| TRACE-802 | FunctionCallTrace | PROC-OP-1003 |
| TRACE-803 | IOPortTrace | PROC-OP-1004 |
| TRACE-804 | InterruptTrace | PROC-OP-1005 |

Reviewing Table 4.4, the `KernelSyscallTrace` (`TRACE-800`) spans the `AuthenticatedShell` process (`PROC-OP-1001`). Because `PROC-OP-1001` is linked to a specific observation and operator, the trace data contained in `TRACE-800` can be definitively attributed to the session initiated by that operator. This granular attribution is required for meeting the forensic standards set forth in compliance frameworks such as PCI-DSS and NIST 800-53.

## 4.5 eBPF Event PID Observation

The final axiom addresses the specific mechanism of kernel-level monitoring using Extended Berkeley Packet Filter (eBPF) technologies. The axiom `ebpf_event_observed_pid` defines a process (X) that observes a Process ID (PID) associated with another process (Y). This captures the act of a monitoring program (the eBPF program) hooking into the kernel to observe the execution of a target process. The schema strictly requires that the target process (Y) be a valid entry in the `t_process_max_one_operator` table. This restriction ensures that kernel-level monitoring resources are prioritized for processes involving accountable operators, rather than dissipating resources on idle or orphaned system tasks.

The table `t_ebpf_event_observed_pid` documents these hooking events. The column `x` represents the eBPF process class, while `y` references the target process with a known operator. This table serves as the registry for all active kernel-level instrumentation. During an audit, this table provides the necessary proof that monitoring controls were active and correctly targeted at the time of an incident.

*Table 4.5: eBPF Event PID Observations*

| id | x | y |
|---|---|---|
| EBPF-300 | BpfSecurityMonitor | PROC-OP-1001 |
| EBPF-301 | BpfNetworkObserver | PROC-OP-1002 |
| EBPF-302 | BpfFileSystemWatcher | PROC-OP-1003 |
| EBPF-303 | BpfMemoryGuard | PROC-OP-1004 |
| EBPF-304 | BpfExecutionTracer | PROC-OP-1005 |

In Table 4.5, the `BpfSecurityMonitor` (`EBPF-300`) is observing the PID associated with `PROC-OP-1001`. This entry confirms that the security instrumentation was actively engaged with the `AuthenticatedShell` process. The referential chain is complete: `EBPF-300` observes `PROC-OP-1001`, which references `OBS-2023-8492`, which documents the `FileReadProcess`. This chain of evidence satisfies the requirement for end-to-end traceability from the kernel hook to the user-level artifact.
