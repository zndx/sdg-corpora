# Chapter 4: Governance Framework for Process Artifacts and Operator Traces

## 4.1 Scope and Preamble

This chapter establishes the mandatory protocols for the governance of system-level processes, artifacts, and operator interactions within the enterprise observability infrastructure. The definitions provided herein serve as the ontological foundation for audit compliance, ensuring that all system events are traceable to a specific actor and temporal context. Adherence to these axioms is required for all subsystems generating logs, traces, or artifacts subject to regulatory review. The following sections detail the relational constraints and evidentiary standards for process observation, operator attribution, and event spanning.

### 4.2.1 Axiomatic Definition

The foundational unit of audit evidence is the **Observation with Participant**. Formally, this concept asserts that a process (Class X) is a specific type of occurrence (`bfo:0000015`) that necessarily involves a participant artifact (`cco:Artifact`). In relational terms, this establishes the baseline entity for all subsequent tracing. An observation cannot exist in a vacuum; it must be anchored to a tangible system component, such as a file descriptor, a socket, or a memory block.

This axiom ensures that every event logged in the system registry is associated with a concrete resource, thereby preventing the logging of abstract or orphaned processes. The primary key for this entity is the unique observation identifier, which serves as the root for foreign key relationships in downstream compliance tables.

### 4.3.1 Axiomatic Definition

To maintain strict non-repudiation, the framework enforces the **Process Max One Operator** axiom. This regulation dictates that any process (Class X) defined within the system must be associated with a maximum of one operator (Class Y). This constraint is critical for forensic analysis; it precludes the ambiguity of shared process sessions where malicious activity could be obfuscated by multiple user associations.

The operator in this context is defined via the `observation_with_participant` structure, meaning the operator themselves are treated as an artifact or entity participating in the process. The relational schema enforces this by linking the process instance directly to a specific observation record representing the operator. This creates a rigid chain of custody: a process points to one, and only one, operator observation.

### 4.4.1 Axiomatic Definition

Temporal precision is governed by the **Schema.org Event Start Time** axiom. This principle asserts that any artifact (Class X) generated or modified by the system must be associated with an event start time (Class Y). Crucially, this start time is not merely a timestamp literal but is itself derived from an `observation_with_participant` event. This recursive linking ensures that the temporal marker of an artifact is traceable back to the specific process observation that initiated it.

By defining the start time as a reference to an observation event rather than a raw date string, the ontology preserves the provenance of time data. This allows auditors to verify not just *when* an artifact was created, but *which specific observation cycle* established that temporal anchor.

## 4.5 Trace Subclass

### 4.5.1 Axiomatic Definition

The **Trace Subclass** axiom addresses the lifecycle of complex, multi-stage operations. It defines that a process (Class X) may "span" another process (Class Y). In this context, "spanning" implies a containment or duration relationship where the overarching process (X) encompasses the execution of the subprocess (Y).

To maintain the integrity of the operator constraint, the axiom mandates that the spanned process (Y) must be of the type `process_max_one_operator`. This ensures that even when a high-level process spans a subprocess, the subprocess remains strictly bound to a single operator. This prevents privilege escalation logic where a parent process might attempt to obscure the operator identity of a child process. The foreign key structure enforces that any spanned trace must point to a valid, operator-bound process.

## 4.6 eBPF Event Observed PID

**TECHNICAL SUPPLEMENT**

**KERNEL TRACE SPECIFICATIONS**

### 4.6.1 Axiomatic Definition

The lowest level of granularity in the framework is provided by the **eBPF Event Observed PID** axiom. Extended Berkeley Packet Filter (eBPF) programs are utilized to observe system behavior with minimal overhead. This axiom formalizes that an eBPF observation process (Class X) specifically observes the Process ID (PID) of a target process (Class Y).

The constraint requires that the target process (Y) be a valid instance of `process_max_one_operator`. This creates a secure loop: the kernel-level observer targets only those processes that have already been vetted and attributed to a single operator. This linkage prevents the observation of "ghost" processes that lack operator attribution and ensures that telemetry data is always correlated with an accountable entity.
