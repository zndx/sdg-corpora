# Chapter 4: Ontological Compliance Framework for Kernel Observability

## 4.1 Scope and Preamble

This chapter establishes the formal ontological structures required for high-fidelity audit trails within kernel-level observability systems. As regulatory frameworks evolve to demand granular evidence of system state changes, technical implementers must move beyond simple logging toward semantically rich data modeling. The following sections define a set of interlocking axioms derived from the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), specifically tailored to map low-level system events—such as those captured by extended Berkeley Packet Filter (eBPF)—to compliant governance artifacts. Adherence to these schemas ensures that process lineage, temporal provenance, and operator attribution are preserved with evidentiary integrity.

## 4.2 Observation with Participant

### 4.2.1 Conceptual Definition

The foundational unit of auditability is the *Observation with Participant*. In accordance with the axiom `observation_with_participant`, we define a specific class of processes that necessarily involve a participant artifact. Formally, the Manchester syntax is expressed as: `Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`.

This axiom asserts that for any process instance $X$ to be classified as a valid observation within this framework, it must bear the `bfo:has_participant` relation to an instance of `cco:Artifact`. In practical terms, this prevents the logging of "orphan" processes that lack a tangible object or data structure upon which they operate. This is critical for compliance; an audit trail must demonstrate not just that a process ran, but what specific artifact (file, socket, memory block) was acted upon.

### 4.2.2 Implementation Schema

The relational projection of this axiom is captured in the table `t_observation_with_participant`. The primary key is the system-generated identifier `id`, while the column `x` denotes the specific class of the observation process. This structure enforces the entity-centric view required by the ontology.

**Table 4-1: Observation with Participant Registry**
This table embodies the axiom `observation_with_participant`, recording the specific process classes that act upon artifacts. The `id` serves as the primary key for downstream joins.

| id | x |
| :--- | :--- |
| OBS-2023-001 | FileReadOperation |
| OBS-2023-002 | NetworkSocketBind |
| OBS-2023-003 | MemoryRegionAllocation |
| OBS-2023-004 | RegistryKeyModification |
| OBS-2023-005 | DeviceDriverLoad |

### 4.2.3 Compliance Note

Auditors must verify that every entry in the system logs maps to a defined class in Column `x`. Undefined classes represent a violation of the schema and a potential gap in the evidentiary chain. For instance, `OBS-2023-001` implies a process specifically reading a file artifact. If a process is recorded without a corresponding artifact interaction, it fails the `bfo:0000057` (has participant) constraint.

## 4.3 Event Start Time

### 4.3.1 Conceptual Definition

To establish a chronological sequence of events, the framework utilizes the `schemaorg_event_starttime` axiom. This axiom links an `cco:Artifact` (often the log entry or the record itself) to a specific temporal entity representing the start time of an observation. The Manchester syntax is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasEventStartTime some {Y:Class}`.

Here, $X$ represents the artifact persisting the record, and $Y$ represents the temporal observation. This distinction is vital: the *record* exists in the database (the artifact), but it *refers* to a time when the process actually started. By anchoring the time to the artifact via the `sdg:hasEventStartTime` property, we ensure that the metadata describing the event is inextricably linked to the event itself.

### 4.3.2 Implementation Schema

The table `t_schemaorg_event_starttime` implements this relationship. The column `y` is a foreign key referencing the `t_observation_with_participant` table. This referential integrity ensures that a start time is never recorded for a non-existent or invalid observation process.

**Table 4-2: Event Start Time Mapping**
This table embodies the axiom `schemaorg_event_starttime`. Column `y` references the observation ID (`id` from Table 4-1), ensuring temporal data is strictly anchored to valid process observations.

| id | x | y |
| :--- | :--- | :--- |
| TIME-REC-100 | SystemLogRecord_V1 | OBS-2023-001 |
| TIME-REC-101 | SystemLogRecord_V1 | OBS-2023-002 |
| TIME-REC-102 | AuditTrailEntry | OBS-2023-003 |
| TIME-REC-103 | SystemLogRecord_V1 | OBS-2023-004 |
| TIME-REC-104 | KernelMessageBuffer | OBS-2023-005 |

### 4.3.4 Validation Protocol

When querying the event timeline, the join between `t_schemaorg_event_starttime` and `t_observation_with_participant` must be performed. If `TIME-REC-100` references `OBS-2023-001`, the system validates that `OBS-2023-001` is indeed a process involving an artifact. This prevents temporal injection attacks where a timestamp might be associated with a null or fabricated process ID.

## 4.4 Trace Subclass

### 4.4.1 Conceptual Definition

In distributed systems and complex kernel interactions, a single logical operation may spawn multiple subprocesses. The `trace_subclass` axiom provides the mechanism to link these spans. The definition is: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasSpans some {Y:Class}`.

This axiom posits that a process $X$ (the parent or root trace) "has spans" $Y$. The entity $Y$ represents a subprocess or a specific segment of execution that is contained within or part of the larger process $X$. This is essential for root cause analysis and for satisfying governance requirements regarding the full scope of a system operation. It allows the auditor to view a parent process and drill down into its constituent spans ($Y$) to inspect specific execution segments.

### 4.4.2 Implementation Schema

The relational schema for `t_trace_subclass` links a parent trace (`x`) to a child span (`y`). Crucially, `y` is constrained by a foreign key referencing `t_process_max_one_operator`. This dependency implies that a span cannot exist independently; it must be associated with a valid process entity that has a defined operator (see Section 4.5).

**Table 4-3: Trace and Span Relationships**
This table embodies the axiom `trace_subclass`. It maps high-level traces to their constituent spans. The `y` column references a process ID with a defined operator, ensuring accountability at every span level.

| id | x | y |
| :--- | :--- | :--- |
| TRACE-ROOT-A | DistributedTransactionRoot | PROC-OP-10 |
| TRACE-ROOT-B | DaemonLifecycleEvent | PROC-OP-11 |
| TRACE-ROOT-C | SecurityScanSequence | PROC-OP-12 |
| TRACE-ROOT-D | DataIngestionPipeline | PROC-OP-13 |
| TRACE-ROOT-E | UserSessionFlow | PROC-OP-14 |

### 4.4.3 Structural Integrity

The `trace_subclass` relationship is directional. The entity in column `x` is the aggregator, while `y` is the component. For example, `TRACE-ROOT-A` (a distributed transaction) encompasses `PROC-OP-10`. This structure allows for recursive querying, enabling the reconstruction of complex execution trees from simple relational rows.

## 4.5 Process Max One Operator

### 4.5.1 Conceptual Definition

Accountability is a cornerstone of technical governance. The axiom `process_max_one_operator` enforces a strict cardinality constraint on process ownership. Defined as: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasOperator max 1 {Y:Class}`.

This axiom asserts that any process $X$ may have a maximum of one operator $Y$. The operator is typically the human user, service account, or system entity responsible for initiating the process. By restricting this to `max 1`, the ontology eliminates ambiguity regarding responsibility. In an audit scenario, it must be possible to point to a single record and identify a single responsible party without conflating multiple actors.

### 4.5.2 Implementation Schema

The table `t_process_max_one_operator` enforces this constraint. The column `y` holds the identifier of the operator and is a foreign key referencing `t_observation_with_participant`. This linkage ensures that the operator is associated with a valid, artifact-bound observation.

**Table 4-4: Process Operator Assignment**
This table embodies the axiom `process_max_one_operator`. It defines the singular operator for specific process instances. The `y` column links back to the observation, ensuring the operator is tied to a concrete event involving an artifact.

| id | x | y |
| :--- | :--- | :--- |
| PROC-OP-10 | ChildProcessWorker | OBS-2023-001 |
| PROC-OP-11 | SystemDaemon | OBS-2023-002 |
| PROC-OP-12 | SecurityScannerThread | OBS-2023-003 |
| PROC-OP-13 | IngestionWorker | OBS-2023-004 |
| PROC-OP-14 | LoginHandler | OBS-2023-005 |

### 4.5.3 Governance Implications

The `max 1` constraint is implemented logically at the application layer and enforced relationally by the uniqueness of the `id` in this context. If a process attempts to associate with a second operator, the insert operation must fail. This table serves as the "Responsibility Ledger." For instance, `PROC-OP-10` is operated by the entity recorded in `OBS-2023-001`. If `OBS-2023-001` defines the user "admin", then "admin" is the sole responsible party for `PROC-OP-10`.

## 4.6 eBPF Event Observed PID

### 4.6.1 Conceptual Definition

The final layer of observability involves the direct correlation of high-level logical processes to low-level kernel identifiers. The axiom `ebpf_event_observed_pid` captures this by linking a monitoring process to a specific Process ID (PID). The Manchester syntax is: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:observesPid some {Y:Class}`.

Here, $X$ represents the eBPF program or the monitoring event itself, which is a process observing the system. $Y$ represents the target PID. This axiom grounds the abstract ontological concepts in the reality of the operating system's process table. It is the mechanism by which the "logical" operator (Section 4.5) is connected to the "physical" execution thread (the PID).

### 4.6.2 Implementation Schema

The table `t_ebpf_event_observed_pid` records these observations. The column `y` references `t_process_max_one_operator`, creating a chain: eBPF Event -> Process with Operator -> Observation with Artifact. This chain provides a complete lineage from the kernel probe to the logical business artifact.

**Table 4-5: eBPF PID Observation Log**
This table embodies the axiom `ebpf_event_observed_pid`. It records the specific PIDs observed by monitoring events. The foreign key `y` ensures that the observed PID is associated with a process that has a defined, singular operator.

| id | x | y |
| :--- | :--- | :--- |
| EBP-9001 | SysEnterExecveEvent | PROC-OP-10 |
| EBP-9002 | SysConnectSocketEvent | PROC-OP-11 |
| EBP-9003 | MmapProtExecEvent | PROC-OP-12 |
| EBP-9004 | SysOpenReadEvent | PROC-OP-13 |
| EBP-9005 | CloneProcessEvent | PROC-OP-14 |

### 4.6.3 Audit Verification

When investigating a security incident, the analyst queries `t_ebpf_event_observed_pid`. For example, `EBP-9001` observes `PROC-OP-10`. By following the foreign key to `t_process_max_one_operator`, the analyst identifies the operator. Following that to `t_observation_with_participant` identifies the artifact. This full traceability satisfies the most stringent forensic requirements, proving not just *that* a PID was active, but *who* authorized it and *what* it touched.
