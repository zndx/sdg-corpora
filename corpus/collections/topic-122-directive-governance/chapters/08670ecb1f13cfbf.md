# Chapter 4: Relational Projections of Ontological Axioms in Observability Frameworks

This chapter delineates the formalization of system observability concepts through the lens of the Web Ontology Language (OWL) and their subsequent projection into relational database schemas. The mapping process described herein transforms high-level ontological assertions—specifically those derived from the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO)—into deterministic table structures suitable for audit-grade storage. The reader will examine five distinct axioms governing process interaction, operator constraints, trace spanning, and kernel-level observation, each supported by a corresponding relational schema and evidence table. These structures ensure that data ingested into compliance frameworks maintains referential integrity and semantic fidelity to the governing model.

## 4.1 Observation with Participant

The fundamental unit of behavioral analysis in any governance framework is the observation. In the context of the provided ontology, an observation is not merely a passive recording but is formally defined as a `bfo:Process` (BFO:0000015) that necessarily involves a participant. This participant is categorized as a `cco:Artifact`, representing the independent continuant that is acted upon or utilized during the process. The axiom `observation_with_participant` establishes that for any instance of Class {X}, which is a subclass of Process, there exists a relation `bfo:0000057` (has participant) linking it to an Artifact.

This distinction is critical for audit trails because it separates the event (the process) from the object of the event (the artifact). Without this separation, it becomes impossible to distinguish between the act of accessing a file and the file itself, leading to ambiguous attribution in compliance reports. The relational projection of this axiom creates a primary repository of these process instances, serving as the root node for numerous other constraints and temporal associations described in subsequent sections.

The following table embodies the `observation_with_participant` axiom. The primary key `id` serves as the unique identifier for the specific observation instance, while column `x` denotes the Class of the process being observed. This structure allows for the classification of various process types (e.g., file reads, network connections) while maintaining a strict entity-relationship model.

| id | x |
| :--- | :--- |
| obs_001 | FileReadOperation |
| obs_002 | NetworkSocketOperation |
| obs_003 | RegistryKeyModification |
| obs_004 | ProcessMemoryAllocation |
| obs_005 | ConfigurationFileEdit |

## 4.2 Process Max One Operator

To enforce accountability within the system, the ontology introduces a cardinality constraint on the relationship between a process and its operator. The `process_max_one_operator` axiom asserts that a Class {X}, defined as a Process, may have a maximum of one operator, denoted as Class {Y}. The operator is modeled as an `cco:Artifact`—typically representing a user account, a service principal, or an authentication token. This constraint is mathematically expressed as `sdg:hasOperator max 1 {Y:Class}`, ensuring that a specific process execution cannot be attributed to multiple distinct operators simultaneously.

In a compliance context, this axiom prevents the diffusion of responsibility. If a process were permitted to have multiple operators without a primary or distinct attribution, investigating security incidents or policy violations would become significantly more complex. The relational schema enforces this by linking the process record back to an observation record. The foreign key constraint ensures that the operator (the `y` value) is a valid participant in a previously defined observation, thereby maintaining the chain of evidence.

The table below illustrates the `process_max_one_operator` axiom. The `id` column uniquely identifies the process instance, `x` defines the process class, and `y` references the `id` from the observation table, effectively binding the operator (artifact) to the process. The foreign key `y` referencing `t_observation_with_participant(id)` guarantees that the operator is a recognized participant in the system's observational record.

| id | x | y |
| :--- | :--- | :--- |
| proc_001 | SystemProcess | obs_001 |
| proc_002 | DaemonProcess | obs_002 |
| proc_003 | UserSessionProcess | obs_003 |

## 4.3 Trace Subclass

Distributed tracing and longitudinal audit logs require the ability to nest processes within one another to represent parent-child relationships or causal chains. The `trace_subclass` axiom formalizes this by defining Class {X} (a Process) that spans another Class {Y} (also a Process). The object property `sdg:hasSpans` indicates that the temporal or causal extent of {X} encompasses {Y}. This is essential for constructing high-fidelity trace trees where a top-level transaction (such as an HTTP request) spans multiple sub-operations (such as database queries or cache lookups).

From a data modeling perspective, this axiom introduces a recursive relationship between processes, albeit constrained by the requirement that the spanned process ({Y}) must be of the type defined in `t_process_max_one_operator`. This implies that only processes with a defined, singular operator can be spanned within a trace. This constraint likely exists to ensure that any sub-component of a trace is already attributable to a specific actor, thereby preserving the security properties of the trace as a whole.

The table `t_trace_subclass` implements this structure. The column `x` represents the parent trace or process, while `y` represents the child process being spanned. The foreign key constraint on `y` referencing `t_process_max_one_operator(id)` ensures that the spanned process is a valid, operator-constrained entity.

| id | x | y |
| :--- | :--- | :--- |
| trace_001 | ParentTrace | proc_001 |
| trace_002 | ChildTrace | proc_002 |
| trace_003 | TransactionFlow | proc_003 |
| trace_004 | WorkflowExecution | proc_004 |
| trace_005 | JobSequence | proc_005 |

## 4.4 eBPF Event Observed PID

Modern observability platforms increasingly rely on kernel-level instrumentation to capture system behavior with minimal overhead. The `ebpf_event_observed_pid` axiom describes a specific class of Process {X} that utilizes extended Berkeley Packet Filter (eBPF) capabilities to observe the Process ID (PID) of another process, denoted as Class {Y}. The relationship is defined by the object property `sdg:observesPid`. This axiom bridges the gap between the instrumentation logic (the eBPF program itself, which is a process running in the kernel) and the target user-space process under observation.

This distinction is vital for granular security monitoring. It allows the governance framework to record not just the system calls themselves, but the metadata regarding *which* monitoring agent observed the call. This creates a "watcher-watched" relationship that can be audited to ensure that monitoring tools are functioning correctly and are not bypassed. The structure requires that the observed process ({Y}) be a valid, operator-constrained process, reinforcing the principle that all observable activity within the system must be attributable.

The table `t_ebpf_event_observed_pid` captures these kernel-level observations. Column `x` identifies the eBPF process or event class, while `y` references the specific process instance (via `t_process_max_one_operator`) whose PID was captured. The foreign key ensures that the system does not record PIDs for processes that lack valid operator attribution.

| id | x | y |
| :--- | :--- | :--- |
| ebpf_001 | KprobeEvent | proc_001 |
| ebpf_002 | TracepointEvent | proc_002 |
| ebpf_003 | UprobeEvent | proc_003 |
| ebpf_004 | SocketFilterEvent | proc_004 |
| ebpf_005 | CgroupSyscallEvent | proc_005 |

## 4.5 Schema.org Event StartTime

While the previous sections focused on the structural and causal relationships between processes and operators, the temporal dimension of these events is managed through the `schemaorg_event_starttime` axiom. This axiom defines an Artifact {X} (which could be a log file, a database record, or a digital report) that possesses an event start time property, `sdg:hasEventStartTime`, linking it to a specific observation Process {Y}. This integration of Schema.org vocabulary allows the ontology to align with standard web data models for time-indexing.

In practice, this axiom allows the system to anchor an artifact (the evidence) to a specific point in time defined by the start of an observation process. This is the mechanism by which raw data is transformed into timestamped evidence suitable for forensic analysis. The relational constraint ensures that an artifact cannot be arbitrarily timestamped; it must be linked to a valid observation process instance, thereby preventing the fabrication or backdating of log entries within the compliant system.

The table `t_schemaorg_event_starttime` documents these temporal associations. Column `x` identifies the artifact class holding the timestamp, and `y` references the `id` of the observation process from `t_observation_with_participant`. This foreign key relationship validates that the recorded start time corresponds to a legitimate, observed event.
