# Chapter 4: Ontological Foundations of System Event Tracing and Audit Compliance

This chapter delineates the formal ontological structures required to establish a rigorous, evidence-anchored framework for system event tracing. It addresses the integration of Basic Formal Ontology (BFO) process entities with Common Core Ontologies (CCO) and domain-specific extensions for security auditing. The objective is to provide a deterministic mapping between high-level governance requirements and low-level observable system states, ensuring that audit trails are not merely sequential logs but semantically rich, verifiable graphs of causal dependencies. The following sections define the core axioms governing observation, temporal anchoring, process attribution, and kernel-level tracing within a compliant architecture.

## 4.1 Observation with Participant Artifact

The fundamental unit of audit evidence is the observation, defined formally as a process that necessarily involves a participant artifact. In compliance frameworks, the integrity of an observation is contingent upon the provenance of the artifact participating in the process. We utilize the axiom `observation_with_participant` to assert that any class of observation (X) is a subclass of `bfo:0000015` (Process) and specifically bears the `bfo:0000057` (has participant) relation to some instance of `cco:Artifact`.

This structural constraint ensures that every recorded event is grounded in a material entity—a file, a configuration block, or a hardware register—rather than an abstract or ephemeral state. For auditors, this mapping provides the necessary linkage to verify that a logged action corresponds to a tangible modification or interaction within the controlled environment.

**Relational Implementation:**
The table `t_observation_with_participant` serves as the primary registry for these process entities. The primary key `id` ensures unique identification of the observation instance, while the column `x` denotes the specific class of the observation process (e.g., `ConfigurationLoad`, `LogRotation`). This table acts as a root node for subsequent temporal and relational links.

## 4.2 Event Start Time Anchoring

To establish a defensible timeline of events, audit protocols must anchor artifacts to specific temporal markers. The axiom `schemaorg_event_starttime` posits that an entity (X), classified as an `cco:Artifact`, possesses a property `sdg:hasEventStartTime` that references a specific observation event (Y). This creates a directed edge from the artifact to the process that signifies its inception or activation.

In practice, this allows compliance officers to query an artifact (such as a specific deployed binary or configuration file) and immediately retrieve the precise observation process that marked its start time. This is distinct from a simple timestamp property; it links the temporal data to a full-fledged process entity defined in Section 4.1, preserving the context of *who* or *what* observed the start.

**Relational Implementation:**
The schema for `t_schemaorg_event_starttime` enforces a foreign key constraint where `y` must reference a valid `id` in `t_observation_with_participant`. This referential integrity guarantees that no event start time exists without a corresponding, registered observation process. The column `x` represents the artifact class being temporally anchored.

## 4.3 Process Operator Constraints

Governance frameworks frequently mandate strict non-repudiation controls, requiring that specific sensitive processes be attributable to a single operator. The axiom `process_max_one_operator` formalizes this by defining a process class (X) that participates in the `sdg:hasOperator` relation with a maximum cardinality of 1 relative to class Y.

This axiom is critical for "separation of duties" enforcement. By declaring a process subclass as having `max 1` operator, the ontology explicitly prohibits shared or anonymous execution contexts for that process type. The operator is modeled as a participant in the observation, linking back to the foundational entities established in Section 4.1. This ensures that the operator is not merely a string label but an entity participating in the observed process flow.

**Relational Implementation:**
The table `t_process_max_one_operator` records the processes subject to single-operator constraints. The column `y` references the observation ID (`t_observation_with_participant`), effectively identifying the operator entity involved in that specific observation instance. The structure enforces that for the process instance `x`, the operator `y` is the singular recorded participant.

## 4.4 Trace Subclass and Spanning

Complex system behaviors are rarely isolated; they are often compositions of smaller, granular events. The `trace_subclass` axiom provides the mechanism to aggregate these events. It asserts that a class (X), which is a process, `sdg:hasSpans` some other process class (Y). This "spanning" relation allows a high-level trace (such as a full transaction lifecycle) to encompass the specific, constrained processes defined in previous sections (such as the single-operator subprocess).

In the context of a forensic investigation, the spanning relation enables the reconstruction of a complete attack chain or compliance workflow. By traversing the `hasSpans` property, an auditor can move from the macro-level trace down to the individual operator-constrained steps, verifying that each constituent action adhered to governance policies.

**Relational Implementation:**
The `t_trace_subclass` table links a parent trace process (`x`) to a child process (`y`). The foreign key constraint requires that the child process (`y`) must exist in `t_process_max_one_operator`. This dependency enforces a structural hierarchy where broad traces are composed of regulated, operator-specific subprocesses.

## 4.5 eBPF Event Observation and PID Correlation

The lowest layer of the ontology addresses the technical mechanism of observation: extended Berkeley Packet Filter (eBPF) tracing. The axiom `ebpf_event_observed_pid` defines a process class (X) that `sdg:observesPid` some target process class (Y). This bridges the gap between the logical governance model and the raw kernel telemetry.

By mapping eBPF events to the PID of the target process, we anchor the high-level traces and operator constraints to the actual runtime execution context. The target process (Y) is required to be a `process_max_one_operator` instance, ensuring that the kernel-level observation is specifically targeting those high-integrity, single-operator processes defined in Section 4.3. This creates a closed loop where kernel telemetry validates the logical compliance model.

**Relational Implementation:**
The table `t_ebpf_event_observed_pid` captures the eBPF tracing events. Column `x` identifies the eBPF observation process (the tracer), while column `y` references the ID of the target process in `t_process_max_one_operator`. This ensures that every PID observation recorded by the tracing subsystem is semantically linked to a governed process entity.
