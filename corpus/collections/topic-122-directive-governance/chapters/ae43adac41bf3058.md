# Chapter 4: Ontological Constraints for System Observability and Process Traceability

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for high-assurance system auditing and compliance monitoring. It defines the structural relationships between computational processes, artifacts, and temporal entities within a governed digital environment. The axioms presented herein provide the semantic foundation for constructing immutable audit trails, ensuring that every system event is attributable to a specific actor, artifact, and time interval. Adherence to these definitions is mandatory for systems operating under regulatory frameworks requiring non-repudiation and granular traceability.

## 4.2 Observation with Participant Artifacts

### 4.2.1 Definition and Axiomatic Structure

The fundamental unit of audit evidence is the observation of a process interacting with a discrete artifact. This relationship is formalized by the axiom `observation_with_participant`. In the Manchester Syntax, this is expressed as `Class: {X:Class} SubClassOf: bfo:0000015, bfo:0000057 some cco:Artifact`. This asserts that the entity `X` (a Process) bears the `bfo:0000057` (has participant) relationship toward an instance of `cco:Artifact`.

Verbalized, {X} is something that has participant artifact. In the context of a compliance investigation, this distinguishes a passive background process from an active agent that manipulates data objects. The artifact represents the object of the action—the file modified, the registry key altered, or the network socket accessed. Without this explicit participant link, a process entry in a log is merely a computational event without forensic context.

### 4.2.2 Implementation and Relational Mapping

The relational projection of this axiom isolates the process class `X` as the primary entity of interest. The table `t_observation_with_participant` serves as the registry for these process entities. The primary key `id` ensures that every process instance is uniquely identifiable within the audit database. The column `x` stores the class name or specific type identifier of the process, allowing for classification of events (e.g., `FileReadOperation`, `UserAuthentication`).

The following table enumerates instances of process observations that have been validated to involve a participant artifact. These entries represent the "Who" and the "What" of the audit trail, stripped of temporal data but establishing the existence of the interaction.

## 4.3 Event Start Time Anchoring

### 4.3.1 Temporal Provenance

To establish a valid timeline of events, the system must anchor artifacts to specific temporal coordinates. The axiom `schemaorg_event_starttime` defines this constraint: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasEventStartTime some {Y:Class}`. This posits that an entity `X` (an Artifact) possesses a property `sdg:hasEventStartTime` which links it to a temporal entity `Y`.

Verbalized, {X} is something that has event start time {Y}. In compliance terms, this prevents the "orphan record" problem, where an artifact exists without a known creation or initiation time. The axiom ensures that every artifact of interest is temporally bound. The structure implies that the artifact `X` is the subject of the timing, and `Y` represents the specific time instance or interval.

### 4.3.2 Relational Dependencies

The implementation of this axiom relies on a foreign key constraint that enforces referential integrity between the event and the observation. The schema defines `t_schemaorg_event_starttime`, where `y` is a foreign key referencing `t_observation_with_participant(id)`. This design choice indicates that the "Start Time" is not merely a timestamp literal but is contextually dependent on the specific observation process defined in Section 4.2.

The table below illustrates the mapping of artifacts to their initiating observations. The `x` column denotes the artifact class, while `y` links the artifact to the specific process observation ID that generated it.

## 4.4 Process Operator Constraints

### 4.4.1 Cardinality and Attribution

Governance frameworks often mandate the principle of individual accountability—the requirement that every process execution be attributable to a unique human or service operator. The axiom `process_max_one_operator` enforces this via the Manchester Syntax: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasOperator max 1 {Y:Class}`.

Verbalized, {X} is a process with a maximum of one operator {Y}. The `max 1` qualifier is a strict cardinality restriction. It prohibits shared accounts or concurrent multi-operator control over a single process instance. If a process requires multiple operators, the ontology mandates the instantiation of distinct subprocesses, each with its own singular operator attribution.

### 4.4.2 Schema and Data Integrity

The relational schema `t_process_max_one_operator` captures this restriction. While relational databases typically enforce cardinality through application logic or unique constraints, this table structure supports the axiom by linking a process `x` to an operator `y`. The foreign key constraint `FOREIGN KEY (y) REFERENCES t_observation_with_participant(id)` implies that the "Operator" is modeled as a specific type of observation—likely an authentication or session initiation event.

The following data set demonstrates the assignment of operators to processes. Note that the `y` column references the observation ID of the operator's session, effectively linking the process execution to the operator's authenticated presence.

## 4.5 Trace Subclass and Spanning

### 4.5.1 Defining the Trace

A "Trace" in systems observability is a holistic view of a transaction as it traverses multiple components. The axiom `trace_subclass` formalizes this: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:hasSpans some {Y:Class}`.

Verbalized, {X} is something that has spans {Y}. Here, `X` represents the high-level trace or workflow, and `Y` represents the individual process segments (spans) that constitute the workflow. This hierarchy is essential for root-cause analysis, as it allows investigators to collapse a distributed operation into a single identifier while retaining the ability to drill down into constituent processes.

### 4.5.2 Hierarchical Relational Mapping

The schema for `t_trace_subclass` establishes a dependency on the process operator table. The foreign key `FOREIGN KEY (y) REFERENCES t_process_max_one_operator(id)` dictates that a trace can only span processes that have defined operator attributions. This reinforces the governance model: unattributed processes cannot be part of a formalized trace.

In the table below, `x` represents the Trace ID, and `y` represents the Process ID (from Table 4.3) that is encompassed by that trace. This structure allows for a one-to-many relationship where a single Trace ID may appear multiple times, linking it to various process spans.

## 4.6 eBPF Event Observed PID

### 4.6.1 Kernel-Level Observability

For high-fidelity monitoring, particularly in security-sensitive environments, observability must extend to the kernel level. The axiom `ebpf_event_observed_pid` defines the relationship between an observation mechanism and a target process: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:observesPid some {Y:Class}`.

Verbalized, {X} is something that observes pid {Y}. This axiom models the behavior of extended Berkeley Packet Filter (eBPF) programs or similar kernel tracing utilities. The entity `X` is the tracing event itself, and `Y` is the target Process ID (PID) being monitored. This is critical for detecting anomalous behavior at the system call level, independent of application-level logging.

### 4.6.2 Linking Observations to Processes

The relational schema `t_ebpf_event_observed_pid` connects the low-level observation to the governed process layer. The foreign key `FOREIGN KEY (y) REFERENCES t_process_max_one_operator(id)` ensures that the observed PID corresponds to a process that is already registered within the operator attribution framework. This prevents "ghost" monitoring of untracked processes and ensures that kernel-level telemetry is integrated into the broader audit ontology.
