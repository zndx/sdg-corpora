# Chapter 4: Ontological Foundations for System Event Auditing and Traceability

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for mapping low-level system telemetry to high-level compliance artifacts. It delineates the structural definitions necessary to construct an immutable audit trail, ensuring that every system event is rigorously classified according to the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). The specifications herein are mandatory for any system seeking certification under the secure data governance framework, specifically addressing the intersection of process observation, temporal attribution, and operator identity verification. By adhering to these axioms, auditors and systems engineers can guarantee that log data is not merely sequential output but a semantically rich, queryable knowledge graph.

## 4.2 Observation with Participant Artifacts

### 4.2.1 Definition and Axiomatic Structure

The fundamental unit of auditability is the observation, defined not merely as a data point but as a processual entity that necessitates the involvement of a specific artifact. According to the axiom `observation_with_participant`, any class $X$ designated as an observation is a subclass of `bfo:0000015` (Process) and must bear the `bfo:0000057` (has participant) relationship to an instance of `cco:Artifact`. This distinction is critical: it separates passive data accumulation from active process monitoring. In compliance terms, this asserts that a record does not exist in a vacuum; it is the result of a process acting upon a tangible or digital entity.

### 4.2.2 Implementation and Governance

In practice, this means that logging systems must capture not only the occurrence of an event but also the direct object of that event. For instance, a "file access" log is invalid under this ontology unless it explicitly links to the specific file artifact accessed. This constraint prevents ambiguous logging where the "what" of the transaction is obscured. The following table illustrates the instantiation of this axiom, categorizing distinct observation classes that satisfy the requirement of possessing a participant artifact.

Each entry in Table 4-1 represents a specific class of process ($X$) that is ontologically bound to an artifact. The primary key `id` serves as the unique identifier for the observation instance within the governance record, while `x` denotes the specific classification of the process.

## 4.3 Process Operator Constraints

### 4.3.1 Cardinality and Accountability

To satisfy non-repudiation requirements, the framework imposes strict constraints on the relationship between a process and its operator. The axiom `process_max_one_operator` defines a class $X$ (a Process) that participates in the `sdg:hasOperator` relationship with a maximum cardinality of 1 relative to class $Y$. This formalism enforces the principle of single-point accountability: for any specific process instance within the audit scope, there may be at most one designated operator entity. This constraint is vital for forensic analysis, as it eliminates the ambiguity of shared or group credentials during the execution of sensitive processes.

### 4.3.2 Relational Mapping

The implementation of this axiom relies on a foreign key constraint linking the process record to the observation record established in Section 4.2. This linkage ensures that the operator is not merely associated with a timestamp but is intrinsically bound to the specific observation process involving the artifact. The schema enforces referential integrity, ensuring that an operator cannot be assigned to a process that does not exist as a valid observation event.

**Table 4-2: Process Instances with Max-One Operator Constraints**

| :--- | :--- | :--- |

| `proc_003` | `SystemPatchApplication` | `obs_003` |
| `proc_004` | `DataExportWorkflow` | `obs_004` |

In Table 4-2, column `x` represents the Process class, while column `y` acts as a foreign key referencing the `id` from the `t_observation_with_participant` table. This structure ensures that every privileged session or daemon initialization is traceable back to a specific root observation event involving a participant artifact.

## 4.4 Temporal Attribution of Events

### 4.4.1 Schema.org Integration

While the BFO provides the existential structure of the event, temporal precision is required for correlation and timeline reconstruction. The axiom `schemaorg_event_starttime` integrates standard web schema definitions into the core ontology. It posits that a class $X$ (an `cco:Artifact`) must possess a `sdg:hasEventStartTime` relationship with a temporal class $Y$. This bridges the gap between the physical process definition and the standardized metadata formats used in interoperability layers.

### 4.4.2 Timestamping and Synchronization

The application of this axiom requires that all artifacts generated by the system carry a machine-readable start time. This is distinct from the system clock time of the logging server; it refers to the intrinsic start time of the event artifact itself. This distinction allows for the detection of clock-skew attacks or replay attacks where an artifact's internal timestamp contradicts the observation time. The following table binds specific temporal artifacts to their parent observations, ensuring that every process is anchored in time.

The `y` column in Table 4-3 references the observation ID, creating a composite record where the process (`proc`), the observation (`obs`), and the temporal artifact (`ts`) are inextricably linked. This structure supports complex queries such as "retrieve all processes involving Artifact A that started within Time Window B."

## 4.5 Process Traceability and Spanning

### 4.5.1 The Trace Subclass

A "trace" in this framework is defined not as a static log entry, but as a process that spans other processes. The axiom `trace_subclass` designates a class $X$ (a Process) that possesses the `sdg:hasSpans` relationship with class $Y$. This recursive or hierarchical process definition allows the auditor to group granular events (such as individual system calls) into higher-level business logic traces (such as a "Complete Checkout Process"). This is essential for high-level reporting, where raw kernel events must be aggregated into meaningful compliance narratives.

### 4.5.2 Hierarchical Process Mapping

The relational implementation of this axiom links the trace entity to the constrained process entity defined in Section 4.3. By referencing `t_process_max_one_operator`, the framework ensures that any high-level trace is composed of lower-level processes that have already passed the "max one operator" validity check. This enforces consistency up the stack: a composite trace cannot be valid if its constituent processes violate operator constraints.

**Table 4-4: Trace Subclass Instances Spanning Processes**

| `trc_001` | `SystemAuditTrail` | `proc_001` |

| `trc_005` | `AccessControlMatrix` | `proc_005` |

Table 4-4 demonstrates how specific trace classes (`x`) span specific process instances (`y`). The foreign key constraint to `t_process_max_one_operator` guarantees that the trace is anchored to a process with a verified operator.

## 4.6 Kernel-Level Observation via eBPF

### 4.6.1 Low-Level Process Identification

The final layer of the framework concerns the mechanism of observation itself, specifically within modern Linux environments using extended Berkeley Packet Filter (eBPF). The axiom `ebpf_event_observed_pid` defines a class $X$ (a Process) that observes a Process ID (PID) represented by class $Y$. This axiom grounds the abstract ontological classes in the concrete reality of operating system process identifiers. It asserts that the observation process is actively monitoring a specific PID, which corresponds to the operator process defined in earlier sections.

### 4.6.2 Integrity of the Observation Loop

This axiom closes the loop between the high-level compliance definitions and the low-level kernel instrumentation. By linking the eBPF observation event to the `t_process_max_one_operator` table, the system verifies that the PID being observed is indeed the process that claims to have the single operator. This prevents spoofing, where a malicious process might attempt to claim the PID of a legitimate, authenticated operator process.

In Table 4-5, the `x` column identifies the specific eBPF hook or system call event class, while `y` references the process ID entity.
