# Chapter 7: Ontological Constraints for System Observability and Audit Trails

This chapter delineates the formal ontological structures required to establish rigorous audit trails within distributed computing environments. It defines the necessary relationships between system processes, artifacts, temporal events, and kernel-level observations to ensure compliance with governance frameworks. The following sections provide a detailed analysis of the axiom-set governing the attribution of system behaviors, ensuring that all observability data is anchored to verifiable entities and precise temporal coordinates.

## 7.1 Observation with Participant Artifacts

In accordance with the foundational axioms of system observability, any valid observation event must be intrinsically linked to a concrete participant artifact. The axiom `observation_with_participant` establishes that a class of observation is a subclass of a process (`bfo:0000015`) that necessarily involves the participation of an artifact (`cco:Artifact`). This constraint ensures that abstract system events are never orphaned; they must be grounded in a tangible interaction with a system object, such as a file, a socket, or a hardware register.

The verbalization of this axiom—"{X} is something that has participant artifact"—mandates that for any observation record generated by the system, a corresponding artifact reference must be present. This is critical for forensic auditing, where the question of "what object was accessed" is as vital as "when" or "by whom." Without this binding, audit logs fail to meet the evidentiary standards required by most compliance regimes.

To illustrate the implementation of this constraint, consider the following registry of observation classes. Each entry represents a specific type of process observation that satisfies the requirement of possessing a participant artifact.

**Table 7-1: Validated Observation Classes with Participant Artifacts**

| Observation ID | Observation Class Name |
| :--- | :--- |
| `obs_artifact_01` | `ArtifactAccessObservation` |
| `obs_artifact_02` | `ConfigurationReadObservation` |
| `obs_artifact_03` | `NetworkSocketObservation` |
| `obs_artifact_04` | `MemoryPageFaultObservation` |
| `obs_artifact_05` | `DeviceRegisterWriteObservation` |

In the table above, the `Observation ID` serves as the unique primary key for the observation instance, while the `Observation Class Name` denotes the specific classification of the event (`{X}`). Each of these classes is ontologically bound to an artifact. For instance, the `ArtifactAccessObservation` implies the existence of a file or data block that acted as the participant, whereas `NetworkSocketObservation` necessitates a socket descriptor as the participating artifact.

## 7.2 Event Start Time Attribution

Temporal precision is a cornerstone of effective governance. The axiom `schemaorg_event_starttime` refines the definition of an artifact by asserting that it must possess a specific event start time. Formally expressed as `{X} is something that has event start time {Y}`, this axiom bridges the gap between static entity definitions and dynamic execution timelines. It requires that every event artifact be annotated with a temporal marker, facilitating the reconstruction of system state sequences.

This relationship is not merely a data typing requirement but a structural dependency. The start time `{Y}` is not an isolated value; it is a reference point that anchors the event artifact `{X}` to a specific moment in the process lifecycle. In compliance scenarios, this allows auditors to correlate disparate logs—such as an authentication attempt and a resource access request—by verifying if their start times align within an acceptable threshold of causality.

The following table details the mapping of specific event artifacts to their designated start times. Note that the `Start Time Reference` corresponds to the observation identifiers established in the previous section, enforcing the foreign key constraint that links temporal data to specific observation instances.

**Table 7-2: Event Start Time Mappings**

| Event ID | Event Class Name | Start Time Reference |
| :--- | :--- | :--- |
| `evt_start_01` | `ScheduledAuditEvent` | `obs_artifact_01` |
| `evt_start_02` | `ComplianceScanEvent` | `obs_artifact_02` |
| `evt_start_03` | `IntrusionDetectionEvent` | `obs_artifact_03` |
| `evt_start_04` | `SystemBootSequenceEvent` | `obs_artifact_05` |

Here, the `ScheduledAuditEvent` (`evt_start_01`) is explicitly linked to the `ArtifactAccessObservation` (`obs_artifact_01`). This linkage ensures that the audit event is temporally anchored to the specific observation of the artifact, satisfying the schema requirement that the event artifact possesses a start time derived from the observation context.

## 7.3 Process Operator Constraints

To maintain a strict chain of custody, the system must enforce constraints on the operator associated with any given process. The axiom `process_max_one_operator` defines a process (`bfo:0000015`) that may have a maximum of one operator (`{Y}`). This constraint, verbalized as "{X} is a process," implicitly carries the restriction that the `sdg:hasOperator` property is cardinality-constrained to a maximum of 1.

This limitation is crucial for accountability. It prevents the ambiguity of shared or simultaneous operator attribution within a single process context. If a process were to allow multiple operators without distinct subprocess segregation, determining liability for malicious actions would become impossible. By enforcing a maximum of one operator, the ontology ensures that every process instance can be mapped to a single, distinct actor or system context.

The relational schema for this axiom links the process to an observation entry, treating the operator context as a participant in the broader observational framework. The table below enumerates process classes that adhere to this single-operator constraint.

**Table 7-3: Process Classes with Single Operator Constraints**

| Process ID | Process Class Name | Operator Context Reference |
| :--- | :--- | :--- |
| `proc_op_01` | `AuthenticatedSessionProcess` | `obs_artifact_01` |
| `proc_op_02` | `DaemonProcess` | `obs_artifact_03` |
| `proc_op_03` | `CronJobProcess` | `obs_artifact_02` |
| `proc_op_04` | `KernelThreadProcess` | `obs_artifact_05` |

In this configuration, `AuthenticatedSessionProcess` (`proc_op_01`) is bound to the operator context defined in `obs_artifact_01`. The constraint ensures that while the process may interact with multiple artifacts over its lifespan, the *operator* slot remains singular and distinct, referencing the specific observation that established the operator's identity.

## 7.4 Trace Subclass and Spanning

High-fidelity observability requires the ability to aggregate discrete process events into coherent traces. The axiom `trace_subclass` posits that a trace entity is a process that spans another process (`{Y}`). Verbalized as "{X} is something that has spans {Y}," this axiom defines the hierarchical relationship between a high-level trace (such as a distributed transaction trace) and the specific local process instances it encompasses.

This spanning relationship allows for the vertical integration of telemetry data. A trace might represent a user request traversing multiple microservices; the "spans" represent the individual execution units within those services. By defining the trace as a subclass of a process that spans other processes, the ontology accommodates both the macro-level narrative (the trace) and the micro-level execution (the spanned process).

The implementation of this axiom depends on the prior definition of valid processes with constrained operators. The trace must span a process that is already valid within the governance model.

**Table 7-4: Trace Hierarchies and Spanned Processes**

| Trace ID | Trace Class Name | Spanned Process Reference |
| :--- | :--- | :--- |
| `trace_span_01` | `KernelExecutionTrace` | `proc_op_01` |
| `trace_span_02` | `SystemCallTrace` | `proc_op_02` |
| `trace_span_03` | `ApplicationWorkflowTrace` | `proc_op_03` |

For example, `KernelExecutionTrace` (`trace_span_01`) spans `AuthenticatedSessionProcess` (`proc_op_01`). This indicates that the kernel-level trace captures the execution lifecycle of the authenticated session process, providing a deep-visibility layer that satisfies the spanning requirement.

## 7.5 eBPF Event Observation of PIDs

At the lowest level of the observability stack, Extended Berkeley Packet Filter (eBPF) programs provide the mechanism for raw data collection from the kernel. The axiom `ebpf_event_observed_pid` defines a process that observes a Process ID (PID) belonging to another process class (`{Y}`). Verbalized as "{X} is something that observes pid {Y}," this axiom formalizes the relationship between the instrumentation event and the target process.

This distinction is vital for security monitoring. The eBPF program itself runs as a process (or is attached to one), but its function is to observe the state of a *target* PID. The ontology separates the observer from the observed, preventing circular logic in attribution logs. The observed PID must correspond to a process that adheres to the operator constraints defined earlier, ensuring that even low-level kernel observations are eventually mapped to accountable entities.

The following table catalogs eBPF event classes and the target process PIDs they observe, linking back to the defined process instances.

**Table 7-5: eBPF Event Observations and Target PIDs**

| eBPF Event ID | Event Class Name | Target Process Reference |
| :--- | :--- | :--- |
| `ebpf_pid_01` | `SyscallEnterEvent` | `proc_op_01` |
| `ebpf_pid_02` | `ContextSwitchEvent` | `proc_op_02` |
| `ebpf_pid_03` | `FileDescriptorEvent` | `proc_op_03` |
| `ebpf_pid_04` | `NetworkPacketEvent` | `proc_op_04` |

In this schema, `SyscallEnterEvent` (`ebpf_pid_01`) observes the PID associated with `AuthenticatedSessionProcess` (`proc_op_01`). This creates a complete chain of evidence: the syscall event observes a specific process, which is constrained to a single operator, which in turn is linked to an observation involving a specific artifact, all anchored by a start time. This dense interconnectivity ensures that the audit trail is both comprehensive and resistant to tampering.
