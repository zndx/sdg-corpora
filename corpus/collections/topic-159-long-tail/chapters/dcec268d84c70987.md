# Chapter 7: Ontological Structures for Audit Evidence and Belief Representation

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures required to represent audit artifacts, specifically focusing on the generation and observation of evidence, claims, and metrics within a governance framework. The content herein defines the necessary subclasses of Information Content Entities (ICE) as prescribed by the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO). It establishes the relational integrity constraints necessary for mapping these entities to database schemas, ensuring that audit trails are both machine-readable and logically consistent with regulatory standards. The following sections provide a detailed exposition of five core axioms governing the relationship between descriptive information content entities and the temporal processes or events that observe or produce them.

## 7.2 Metric Observation by Event

In the context of systems monitoring and compliance auditing, a metric is defined not merely as a numerical value, but as a specific type of Descriptive Information Content Entity (DescriptiveICE). Axiomatically, a metric must be observed at a specific temporal boundary or occurrence. This is formalized by the axiom `metric_observed_by_event`, which asserts that any Class {X} representing a metric is a subclass of `cco:DescriptiveICE` and bears the relation `sdg:observedAt` to an instance of `bfo:0000015` (an Event). This constraint ensures that quantitative data is never treated as an abstract constant but is always anchored to a specific point in time or occurrence, thereby preserving the provenance of the measurement.

The relational projection of this axiom creates a dedicated table for storing these observations. The primary key serves as the unique identifier for the metric instance, while the column `x` captures the class or specific name of the metric entity. This structure facilitates the tracking of performance indicators against specific events, such as system failures or transaction completions.

## 7.3 Audit Evidence Generation

The audit process is fundamentally a generative activity. According to the axiom `audit_produces_evidence`, the audit process itself is a subclass of `bfo:0000015` (a Process). This process is causally linked to the production of evidence, which is categorized as a `cco:DescriptiveICE`. This distinction is critical for governance frameworks: it separates the act of auditing (the process) from the resulting artifacts (the evidence). The verbalization of this axiom posits that the entity {X} (the Audit) is "something that produces evidence descriptive information content entity."

Implementing this axiom requires a relational structure that links the process identifier to the nature of the output. The table `t_audit_produces_evidence` captures this relationship. The primary key `id` identifies the specific audit instance, while `x` denotes the class or type of audit process being executed. This schema allows compliance officers to query all evidence-producing activities and ensures that every artifact in the system can be traced back to a specific procedural origin.

## 7.4 Evidence Observation by Process

While the previous section defined the *production* of evidence by an audit, this section addresses the *observation* of that evidence. The axiom `evidence_observed_by_process` asserts that evidence, as a `cco:DescriptiveICE`, is `sdg:observedAt` a specific process. This subtle ontological difference—between production and observation—allows for complex modeling where evidence might be generated by one process but formally observed or recorded by another (e.g., a log aggregation process observing evidence generated by an application crash).

The corresponding relational schema, `t_evidence_observed_by_process`, isolates the observation event. The primary key `id` provides a unique reference for the evidence artifact, and `x` classifies the type of evidence. By separating this table from the audit production table, the framework supports a many-to-many relationship where a single audit process may produce multiple evidence items, and a single evidence item may be observed by multiple downstream processes.

## 7.5 Claim Observation by Event

In addition to raw metrics and generated evidence, audit frameworks frequently handle claims—assertions regarding the state of the world or compliance status. The axiom `claim_observed_by_event` formalizes the concept of a claim as a `cco:DescriptiveICE` that is `sdg:observedAt` an event. This ensures that claims are not treated as static facts but as assertions that are valid only relative to the specific event at which they were observed or made. For instance, a claim that "System X is compliant" is only valid relative to the compliance check event.

The table `t_claim_observed_by_event` records these assertions. The structure is identical to that of metrics and evidence observations, maintaining a consistent pattern across the ontology. The primary key `id` identifies the specific claim instance, while `x` describes the nature of the claim. This uniformity simplifies the database schema while allowing the application layer to distinguish between metrics (quantitative), evidence (documentary), and claims (assertive) based on the class value in column `x`.

## 7.6 Mass Functions and Focal Elements

The final concept introduces a layer of uncertainty and belief structure, often utilized in advanced audit scoring and Dempster-Shafer evidence theory. The axiom `mass_function_min_one_focal` defines a belief structure (a mass function) as a subclass of `cco:DescriptiveICE`. Crucially, this structure must possess `sdg:hasFocalElement` a minimum of one element {Y}, where {Y} is a Class. In this ontological mapping, the focal element {Y} is projected to be a metric, specifically an instance defined in the `t_metric_observed_by_event` table.

This relationship represents a dependency: a belief assessment (mass function) is assigned to a specific metric (the focal element). The verbalization indicates that {X} (the mass function) is a descriptive entity containing at least one focal element {Y}. The relational schema for `t_mass_function_min_one_focal` enforces this via a foreign key constraint. The primary key `id` identifies the mass function, `x` names the belief structure, and `y` (which cannot be null) references the `id` of a metric in `t_metric_observed_by_event`. This ensures that every belief assignment is anchored to a concrete, observed metric defined in Section 7.2.
