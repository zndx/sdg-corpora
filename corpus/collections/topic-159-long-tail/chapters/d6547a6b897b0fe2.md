# Chapter 4: Ontological Foundations of Audit Evidence and Metric Verification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological underpinnings for the capture, verification, and structural management of audit evidence within a distributed governance framework. It delineates the necessary relationships between descriptive information content entities (ICEs) and the temporal processes or events that generate them, ensuring that all assertions are grounded in verifiable data structures. The following sections map specific ontology axioms to relational schemas, providing a rigorous method for classifying metrics, evidence, claims, and the belief structures (mass functions) that underpin risk assessment. By adhering to these definitions, governance systems can maintain semantic consistency across distinct audit domains, facilitating automated compliance checking and high-fidelity reporting.

## 4.2 Metric Observation via Events

### 4.2.1 Conceptual Definition
In the context of systems governance, a metric is defined as a quantitative measurement derived from the state of a system at a specific moment. Axiomatically, we define a Metric Observed by Event as a specific subclass of a Descriptive Information Content Entity (DescriptiveICE). This entity is inextricably linked to an Occurrent, specifically a `bfo:0000015` (Event), via the `sdg:observedAt` object property. This relationship ensures that the metric is not merely an abstract value but is temporally anchored to a discrete occurrence, thereby providing the provenance required for forensic analysis.

### 4.2.2 Relational Implementation
The relational schema for this concept enforces that every metric entry is a primary entity with a unique identifier. The column `x` represents the class of the metric being observed (e.g., `ServerLatency`, `TransactionVolume`). This structure allows for the categorization of metrics without constraining the specific data values, which may be stored in auxiliary time-series databases. The primary key `id` serves as the stable reference for this observation instance.

### 4.2.3 Application and Analysis
When a system event occurs—such as a timeout or a security breach trigger—the corresponding metric class is instantiated in the registry. For instance, `m_004` represents the class `APIResponseTime500`, observed during a specific HTTP 500 error event. This registry acts as the foundational layer for higher-order evidence aggregation, ensuring that all subsequent analysis references a valid, temporally anchored observation.

## 4.3 Mass Functions and Focal Elements

### 4.3.1 Conceptual Definition
To move beyond simple deterministic metrics into probabilistic reasoning, we employ the Dempster-Shafer structure of belief functions. A Mass Function is defined as a DescriptiveICE that assigns a basic probability assignment (a "mass") to a set of hypotheses. The axiom `mass_function_min_one_focal` posits that any valid mass function must possess at least one focal element. In this schema, the focal element (`y`) is explicitly constrained to be a Metric Observed by Event. This creates a dependency chain where belief is assigned specifically to the verifiable metrics defined in the previous section.

### 4.3.2 Relational Implementation
The schema for `t_mass_function_min_one_focal` enforces a foreign key constraint, linking the focal element `y` to the `id` of the `t_metric_observed_by_event` table. This referential integrity is critical; it prevents the assignment of belief to non-existent or unverified metrics. The column `x` represents the Mass Function class itself (e.g., `HighLatencyBelief`), while `y` anchors that belief to a specific metric instance.

| :--- | :--- | :--- |

| mf_103 | SecurityAnomalyBelief | m_003 |

### 4.3.3 Application and Analysis
Consider the entry `mf_101`. The mass function class `CongestionBeliefStructure` assigns a degree of belief (the specific mass value is held in the associated data layer) to the focal element `m_001` (`NetworkLatencyMetric`). This structure allows an inference engine to reason about the state of the network not merely as a binary "up/down" status, but as a distribution of belief regarding congestion, grounded in the observed latency metric. The foreign key constraint (`y` references `t_metric_observed_by_event`) guarantees that the belief is always anchored to a recorded event.

## 4.4 Audit Evidence Production

### 4.4.1 Conceptual Definition
An Audit is a processual entity (`bfo:0000015`) characterized by its systematic investigation of records and controls. The axiom `audit_produces_evidence` formalizes the output of this process. It asserts that an Audit (Class `X`) is a generative process that produces Evidence, which is itself a DescriptiveICE. This distinction is vital for compliance frameworks; it separates the act of investigation (the process) from the artifacts generated (the evidence).

### 4.4.2 Relational Implementation
The table `t_audit_produces_evidence` catalogs the types of audit processes that are sanctioned within the governance framework. The column `x` stores the class name of the audit process (e.g., `QuarterlyFinancialAudit`, `AccessControlReview`). While the schema for the evidence itself is defined separately, this table serves as the registry of valid generative processes.

**Table 4.3: Audit Process Registry**
This table embodies the axiom `audit_produces_evidence`, listing the audit process classes responsible for generating descriptive evidence.

| id | x |
| :--- | :--- |
| a_201 | SOC2Type2Audit |
| a_202 | ISO27001ControlAudit |
| a_203 | InternalLogRetentionReview |
| a_204 | ThirdPartyPenetrationTest |
| a_205 | GDPRComplianceAssessment |

### 4.4.3 Application and Analysis
The entry `a_201` corresponds to the `SOC2Type2Audit` process. When this process is executed, it is axiomatically guaranteed to produce evidence entities. This registry allows the governance framework to validate that any evidence package claiming to originate from a `SOC2Type2Audit` is linked to a valid, defined process class. This prevents the introduction of "orphaned" evidence that cannot be traced back to a legitimate audit activity.

## 4.5 Evidence Observation via Processes

### 4.5.1 Conceptual Definition
While audits produce evidence, evidence is also observed naturally during ongoing operational processes. The axiom `evidence_observed_by_process` defines a subclass of DescriptiveICE that is captured passively or actively during a process (`bfo:0000015`). This differs from the audit production in that the process here is the general operational workflow (e.g., "Order Processing"), rather than a specific investigative audit.

### 4.5.2 Relational Implementation
The `t_evidence_observed_by_process` table records the specific classes of evidence entities that are generated or captured during these workflows. The column `x` identifies the evidence class (e.g., `UserAccessLog`, `TransactionSnapshot`). This classification enables the system to distinguish between raw data and structured evidence suitable for compliance reporting.

### 4.5.3 Application and Analysis
For example, `e_302` represents the `FirewallAccessLogEntry`. This evidence class is observed during the process of network traffic handling. By formalizing this as a DescriptiveICE observed at a process, the framework ensures that these log entries are treated as first-class governance objects, subject to retention policies and integrity checks, rather than transient system noise.

## 4.6 Claim Observation via Events

### 4.6.1 Conceptual Definition
In identity and access management, as well as in distributed ledger technologies, a "Claim" represents a declarative statement made by an entity about another entity. The axiom `claim_observed_by_event` defines a Claim as a DescriptiveICE that is observed at a specific Event (`bfo:0000015`). This temporal anchoring is essential for non-repudiation; a claim is only valid within the context of the event where it was asserted or verified.

### 4.6.2 Relational Implementation
The table `t_claim_observed_by_event` maintains the registry of claim classes that the system recognizes and records. The column `x` denotes the specific type of claim (e.g., `RoleAssertion`, `IdentityClaim`). Like the metric registry, this table provides the taxonomy for assertions flowing through the system.

### 4.6.3 Application and Analysis
The entry `c_401`, `AdministratorRoleClaim`, represents a specific class of privilege assertion observed during an event (such as a login attempt or a sensitive command execution).
