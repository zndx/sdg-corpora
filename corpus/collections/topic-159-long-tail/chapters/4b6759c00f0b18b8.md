# Chapter 4: Formal Ontology of Audit Evidence and Belief Structures

## 4.0 Preamble and Scope

This chapter delineates the formal ontological structures required to represent the generation, observation, and aggregation of evidence within automated audit frameworks. It establishes the necessary axioms for mapping descriptive information content entities (ICEs) to temporal processes and events, and further defines the mathematical structures required for belief aggregation. The provisions herein apply to all systems implementing high-assurance compliance logging, specifically where audit trails must be subjected to Dempster-Shafer evidential reasoning or similar probabilistic uncertainty models. The definitions provided are binding for the construction of relational schemas utilized in regulatory reporting and governance artifacts.

## 4.1 Metric Observation via Events

Pursuant to the requirements for granular telemetry, a fundamental distinction must be drawn between raw data streams and structured metrics. A metric is defined not merely as a numerical value, but as a Descriptive Information Content Entity (ICE) that is temporally anchored to a specific occurrence. This anchoring ensures that all quantitative measurements are verifiably linked to the event which generated them, satisfying the immutable traceability requirements of modern audit standards.

The axiom governing this relationship asserts that any Class representing a metric is a subclass of `cco:DescriptiveICE` and must be `observedAt` some `bfo:0000015` (an Occurrent). In practice, this means that a metric instance cannot exist in the database without a valid timestamp or event identifier. The relational projection of this axiom enforces that the primary identifier of the metric is the sole key, while the class definition provides the semantic type.

Table 4.1.1 illustrates the instantiation of observed metrics within a financial transaction processing system. Each row represents a specific metric class observed during a distinct event boundary.

In the preceding table, the column `x` denotes the specific Class of the metric observed. The entity `TransactionLatencyMetric`, for instance, is a DescriptiveICE that captures the duration of a specific transaction event. This structure allows auditors to query specific types of metrics while retaining the unique identifier (`id`) necessary for forensics. The axiom `metric_observed_by_event` guarantees that for every entry in this table, a corresponding event record exists in the broader temporal log, thereby preserving the causal chain of evidence.

## 4.2 Audit Processes and Evidence Production

The generation of evidence is not a spontaneous occurrence but the product of a deliberate, governed process. Within the ontology, an Audit is formally categorized as a process (specifically, a subclass of `bfo:0000015`) that possesses the capability to produce evidence. This distinction is critical for governance frameworks, as it separates the passive collection of logs from the active generation of compliance artifacts.

The axiom `audit_produces_evidence` posits that the Audit Class (`X`) produces a `cco:DescriptiveICE`. This relationship establishes the provenance of evidence; any evidence item utilized in a compliance report must be traceable back to a specific audit process instance. This prevents the introduction of orphaned data or fabricated evidence into the record, as all evidence must bear the signature of the process that created it.

Table 4.2.1 catalogs specific audit processes and the classes of evidence they generate. Note that the table represents the schema mapping where the process is the entity of interest.

**Table 4.2.1: Audit Process Evidence Generation Log**

| :--- | :--- |
| AUDIT-PROC-Q3 | QuarterlyAccessControlReview |
| AUDIT-PROC-Q3 | DataResidencyVerification |
| AUDIT-PROC-INC-01 | IncidentResponseForensicCollection |
| AUDIT-PROC-INC-01 | MalwareAnalysisReportGeneration |
| AUDIT-PROC-ANN | AnnualThirdPartyRiskAssessment |

The entries in Table 4.2.1 demonstrate that a single process instance (e.g., `AUDIT-PROC-Q3`) may produce multiple classes of evidence. The `x` column represents the Class of the evidence produced, which is itself a DescriptiveICE. By formalizing this relationship, the ontology ensures that the "source of truth" for any compliance artifact is the audit process itself, satisfying the "source integrity" controls found in ISO 27001 and similar frameworks.

## 4.3 Evidence Observation within Processual Contexts

While Section 4.2 defined the *production* of evidence by an audit, it is equally necessary to define the *observation* of evidence within a process. Evidence, once produced, is an information content entity that must be recorded as occurring at a specific point in a process flow. This axiom, `evidence_observed_by_process`, reinforces the temporal binding of evidence to the process timeline.

Under this axiom, the Evidence Class (`X`) is a `cco:DescriptiveICE` that is `observedAt` some `bfo:0000015`. This subtle distinction from production allows for the observation of evidence that may exist independently of the immediate audit process (e.g., legacy logs) but is being "ingested" or "observed" by the current process. This is essential for continuous monitoring systems where evidence is streamed in real-time.

## 4.4 Claim Observation at Event Boundaries

In the context of automated compliance reasoning, a "Claim" represents a hypothesis or an assertion regarding the state of the system. Unlike raw evidence, which is factual, a claim is a declarative statement that requires validation. The axiom `claim_observed_by_event` formalizes claims as DescriptiveICEs that are observed at specific events.

This structure is pivotal for rule-based auditing engines. When a system evaluates a condition (e.g., "Password complexity meets policy"), it generates a Claim. This claim is then anchored to the event (e.g., "Password Change Event"). By treating claims as information content entities, the system can store, retrieve, and evaluate them just like any other data type, enabling complex logical inference over the audit trail.

Table 4.4.1 records claims generated during a User Access Management event.

The `x` column in Table 4.4.1 denotes the Class of the claim. For example, `PrincipleOfLeastPrivilegeViolated` is a claim class indicating a specific type of failure state. The observation of this claim at a specific event ID triggers the necessary remediation workflows. This axiom allows the audit system to move beyond simple data logging to "semantic logging," where the meaning of the data is captured explicitly.

## 4.5 Mass Functions and Focal Element Assignment

The aggregation of uncertain evidence is best handled using Dempster-Shafer theory, where a "mass function" represents the degree of belief assigned to a specific set of hypotheses (the "focal element"). The axiom `mass_function_min_one_focal` provides the ontological structure for this advanced reasoning.

This axiom states that a Mass Function Class (`X`) is a `cco:DescriptiveICE` that must have `sdg:hasFocalElement` a minimum of 1 Focal Element Class (`Y`). Furthermore, the relational schema dictates that the focal element (`y`) must reference a valid entry in the `t_metric_observed_by_event` table. This foreign key constraint is logically rigorous: it mandates that belief masses (the confidence in a hypothesis) can only be assigned to metrics that have actually been observed and recorded. One cannot assign a belief probability to a non-existent metric.

Table 4.5.1 demonstrates the assignment of mass functions to specific focal elements (metrics). The `y` column contains the IDs of the metrics defined in Table 4.1.1, ensuring referential integrity.

**Table 4.5.1: Mass Function and Focal Element Assignment**

This structure enforces a high standard of evidence integrity, ensuring that all quantitative risk assessments are derived from verified, observed telemetry.
