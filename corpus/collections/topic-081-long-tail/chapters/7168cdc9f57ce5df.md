# Verification Processes and Information Content Entities

This chapter presents three OWL-derived axioms that classify processes by mandatory evidence production and that position certain entities as information content entities or descriptive information content entities. The axioms are realized in a minimal relational schema containing three tables. The schema supports cross-table joins that recover multi-hop facts such as the evidence class required by a given verification process.

## 1. Ontology Axioms and Schema Projection

The axioms are stated in Manchester OWL syntax and projected deterministically to the relational tables shown below. Column domains follow the slot types declared in each axiom; foreign-key constraints encode the existential restriction in Axiom 1.

### 1.1 Subclass Relation to InformationContentEntity

Axiom 2 states that a class X is a subclass of cco:InformationContentEntity. The corresponding table records each such class once; its single-column primary key supplies stable identifiers for foreign-key references from other tables.

Table t_subclass_to_information_content_entity embodies Axiom 2. Column id is the primary key; column x holds the class name. A reader can join this table on y to retrieve the full class record for any evidence produced by a verification process.

| id | x |
| --- | --- |
| ice01 | VerificationReport |
| ice02 | AuditLog |
| ice03 | EmissionOffsetRecord |
| ice04 | CalibrationCertificate |
| ice05 | ProtocolDeviationForm |
| ice06 | MeasurementTrace |

### 1.2 Subclass Relation to DescriptiveICE

Axiom 3 further specializes certain information content entities as descriptive. The table records only those classes that satisfy the more specific parent.

Table t_subclass_to_descriptive_ice embodies Axiom 3. Column id is the primary key; column x holds the class name. Because DescriptiveICE is itself a subclass of InformationContentEntity, every x value here also appears in t_subclass_to_information_content_entity.

| id | x |
| --- | --- |
| dice01 | VerificationReport |
| dice02 | EmissionOffsetRecord |
| dice03 | CalibrationCertificate |
| dice04 | ProtocolDeviationForm |

### 1.3 Verification Process Requiring at Least One Evidence

Axiom 1 asserts that every instance of class X is a bfo:Process that produces at least one instance of class Y, where Y is an InformationContentEntity. The table therefore stores pairs (X, Y) together with a surrogate primary key.

Table t_verification_min_one_evidence embodies Axiom 1. Column id is the primary key; column x names the process class; column y is a foreign key referencing t_subclass_to_information_content_entity.id. A mental cross-join on y recovers the concrete evidence class required by each verification process.

| id | x | y |
| --- | --- | --- |
| v01 | SiteInspection | ice01 |
| v02 | DataReview | ice02 |
| v03 | OffsetCalculation | ice03 |
| v04 | EquipmentQualification | ice04 |
| v05 | DeviationAnalysis | ice05 |
| v06 | TraceabilityAudit | ice06 |

## 2. Cross-Join Example

Consider the multi-hop question: “Which descriptive evidence class is required by the PeriodicVerification process?”  

Start at t_verification_min_one_evidence where x = 'PeriodicVerification' (row v07). Follow the foreign key y = 'ice01' into t_subclass_to_information_content_entity to obtain x = 'VerificationReport'. A second filter against t_subclass_to_descriptive_ice confirms that 'VerificationReport' also satisfies the DescriptiveICE parent. The joined result row is therefore:

(v07, PeriodicVerification, ice01, VerificationReport, dice01)

The same pattern answers any other combination of process class and required evidence class by traversing the single foreign-key link.
