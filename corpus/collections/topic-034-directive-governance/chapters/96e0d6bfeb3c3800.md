# Chapter 4: Ontological Foundations of Kernel Telemetry and Event Attribution

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework governing the attribution, observation, and alerting mechanisms within extended Berkeley Packet Filter (eBPF) observability architectures. As security telemetry moves toward kernel-level instrumentation, the precise definition of events, their causal relationships with system calls, and the derivation of security alerts require rigorous standardization. The definitions provided herein are grounded in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that telemetry data structures are not merely ad-hoc logs but semantically rich information entities suitable for audit, compliance, and automated reasoning. This specification details the structural axioms that define processual entities, designative information content entities, and their interrelations within a secure monitoring environment.

## 4.2 Processual Attribution of eBPF Events

The fundamental unit of telemetry in an eBPF-based monitoring framework is the event itself. To ensure semantic interoperability between heterogeneous agents, the event must be formally classified not as a static data object, but as a processual entity. According to the axiom `ebpf_event_min_one_attribute`, any class of eBPF event ($X$) is a subclass of `bfo:0000015` (Process). This classification is critical for audit trails because it asserts that the event occurs over a temporal interval and has a distinct beginning and end, rather than existing as a timeless state.

Furthermore, the axiom mandates that every such process possesses at least one attribute that is a `cco:DesignativeICE` (Information Content Entity). A Designative ICE is a specific type of data that "stands for" or designates a real-world entity, such as a process ID, a file path, or a network socket. In compliance frameworks, this distinction ensures that an event is never empty; it must carry sufficient context to identify the actor and the action. The separation of the event process (the occurrence) from its attributes (the designative data) allows forensic analysts to trace the lineage of an observation without conflating the observation itself with the metadata describing it.

### 4.2.1 Event Attribute Constraints

The requirement for "min 1" attribute serves as a validation constraint for telemetry ingestion pipelines. Any eBPF event stream lacking a designative attribute is ontologically invalid and must be rejected by the monitoring agent to prevent the pollution of the audit log with anonymous or unattributable process tokens. This is particularly relevant in high-frequency environments where kernel telemetry may generate millions of records per second; enforcing this schema at the edge reduces downstream storage costs and increases the signal-to-noise ratio for security information and event management (SIEM) systems.

The following table enumerates specific instances of eBPF event classes that satisfy the axiom `ebpf_event_min_one_attribute`. Each row represents a distinct class of event ($X$) that is recognized as a valid processual entity within the governance framework.

**Table 4-1: Validated eBPF Event Classes and Attributes**

| Event ID | Event Class ($X$) | Description |
| :--- | :--- | :--- |
| `EVT-2024-001` | `FileOpenEvent` | A processual entity representing the opening of a file descriptor, carrying attributes such as `pathname` and `flags`. |
| `EVT-2024-002` | `NetworkConnectionEvent` | Represents the initiation of a TCP/UDP handshake, designated by source/destination IP tuples. |
| `EVT-2024-003` | `PrivilegeEscalationEvent` | A process triggered by a change in user ID (UID) or group ID (GID), containing the `target_cred` attribute. |
| `EVT-2024-004` | `ModuleLoadEvent` | Represents the insertion of a kernel module, designated by the module name and SHA256 hash. |
| `EVT-2024-005` | `ProcessExecutionEvent` | Represents the execution of a new binary, designated by the executable path and argument vector. |

## 4.3 Alert Generation via Metric Triggers

While the capture of events is the foundation of observability, the derivation of actionable intelligence requires the generation of alerts. The axiom `alert_triggered_by` formalizes this relationship by defining an Alert Class ($X$) as a process (`bfo:0000015`) that is triggered by a specific Metric Class ($Y$). This distinction separates the raw signal (the metric) from the operational response (the alert). In a regulatory context, this separation is vital for maintaining the integrity of the audit chain; it allows auditors to verify that an alert was the deterministic result of a specific metric threshold breach, rather than an arbitrary administrative action.

The relationship is existential (`some`), meaning that for an alert to exist, there must be at least one metric that caused it. The metric, in this context, acts as the proxy for the eBPF event data. The foreign key constraint linking the metric to the event ensures that the alert is traceable back to the specific processual entity defined in Section 4.1. This structure supports the "single source of truth" principle required in standards such as ISO 27001, where security controls must be demonstrably linked to monitored activities.

### 4.3.1 Metric-to-Alert Correlation

In practice, the metric $Y$ is often a statistical aggregation or a boolean evaluation of the attributes contained in the eBPF event. For example, a `FileOpenEvent` might contain a `pathname` attribute; the metric evaluates whether this pathname matches a sensitive pattern (e.g., `/etc/shadow`). If the evaluation returns true, the metric triggers the `SecurityViolationAlert`. The governance framework requires that the identity of the triggering metric be preserved alongside the alert to facilitate post-incident forensics.

| Alert ID | Alert Class ($X$) | Triggering Metric ($Y$ | Source Event ID |
| :--- | :--- | :--- | :--- |
| `ALT-SEC-101` | `SecurityViolationAlert` | `SensitiveFileAccessMetric` | `EVT-2024-001` |
| `ALT-SEC-102` | `AnomalyDetectionAlert` | `OutboundConnectionCountMetric` | `EVT-2024-002` |

## 4.4 Syscall Invocation and Event Correlation

To understand the provenance of kernel-level activity, the monitoring framework must map high-level events to the specific system calls that materialize them. The axiom `syscall_invoked_by_event` defines a System Call ($X$) as a `cco:DesignativeICE` that is invoked by an Event ($Y$). This axiom captures the directional causality inherent in operating systems: the event (the user-space intent or kernel trigger) precipitates the invocation of the system call (the kernel interface).

By classifying the system call as a Designative ICE, the ontology acknowledges that the syscall is a "stand-in" for the specific kernel function being requested. It is not the process of execution itself (which is the event), but rather the designation of the requested operation. This granular distinction is essential for deep-dive forensic analysis, allowing investigators to reconstruct the exact sequence of kernel requests that constituted a complex attack chain, such as a race condition or a privilege escalation exploit.

### 4.2.1 Causal Linkage and Integrity

The foreign key constraint in this schema ensures that every recorded system call invocation is strictly bound to a valid eBPF event process. This prevents "orphaned" syscall records—syscall entries that cannot be associated with a specific triggering event—from appearing in the logs. Orphaned records are often indicative of rootkit activity or sensor tampering; therefore, the schema itself acts as a structural integrity check. The relationship is strictly defined as `invokedByEvent`, reinforcing that the syscall is the subordinate entity in the causal pair.

**Table 4-3: System Call Invocations Linked to Events**

| Syscall ID | Syscall Class ($X$) | Invoking Event ($Y$) | Source Event ID |
| :--- | :--- | :--- | :--- |
| `SYS-KRN-201` | `OpenAtSyscall` | `FileOpenEvent` | `EVT-2024-001` |
| `SYS-KRN-202` | `ConnectSyscall` | `NetworkConnectionEvent` | `EVT-2024-002` |
| `SYS-KRN-203` | `SetuidSyscall` | `PrivilegeEscalationEvent` | `EVT-2024-003` |
| `SYS-KRN-204` | `FinitModuleSyscall` | `ModuleLoadEvent` | `EVT-2024-004` |
| `SYS-KRN-205` | `ExecveSyscall` | `ProcessExecutionEvent` | `EVT-2024-005` |

## 4.5 Syscall Observation by eBPF Events

The final axiom in this framework, `ebpfevent_observes_syscall_xref`, closes the loop by defining the observational capability of the eBPF infrastructure. It asserts that an eBPF Event Class ($X$) is a process (`bfo:0000015`) that observes a Syscall Designative ICE. This axiom differentiates the *act* of observation (the eBPF program running in the kernel) from the *object* of observation (the syscall).

In technical terms, this axiom maps the eBPF hook point (e.g., `sys_enter` or `sys_exit`) to the specific class of syscall it is designed to monitor. This cross-reference is critical for governance documentation, as it provides a manifest of what the monitoring system is capable of seeing. It ensures that the "observes" relationship is explicitly defined for every event class, preventing scope creep or undeclared monitoring capabilities which could violate privacy policies or regulatory mandates.

### 4.5.1 Observation Manifest

The `ebpfevent_observes_syscall_xref` table serves as a manifest of the monitoring coverage. By querying this relationship, compliance officers can verify that for every critical syscall defined in the security policy, there is a corresponding eBPF event class configured to observe it. This supports the "defense in depth" strategy by ensuring that telemetry coverage is comprehensive and explicitly mapped to the kernel's attack surface.

**Table 4-4: eBPF Event Observation Capabilities**

| Observation ID | Event Class ($X$) | Observed Syscall Domain |
| :--- | :--- | :--- |
| `OBS-301` | `FileOpenEvent` | `VFSRead` and `VFSWrite` operations via `openat` |
| `OBS-302` | `NetworkConnectionEvent` | `TCPv4` and `TCPv6` connect operations |
| `OBS-303` | `PrivilegeEscalationEvent` | `Capability` and `UID` manipulation syscalls |
| `OBS-304` | `ModuleLoadEvent` | `KernelModule` initialization syscalls |
| `OBS-305` | `ProcessExecutionEvent` | `Execve` family of process spawning syscalls |
