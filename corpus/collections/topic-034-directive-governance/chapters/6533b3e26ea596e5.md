# Chapter 7: Formal Ontology of eBPF Observability and Alert Correlation

This chapter establishes the formal framework for mapping kernel-level observability events to compliance-grade audit trails. It delineates the axiomatic structure governing Extended Berkeley Packet Filter (eBPF) events, their requisite attributes, and the logical derivation of security alerts. The content herein is prescriptive, defining the minimum data structures and relational constraints required to satisfy rigorous governance standards for system telemetry. Implementers must ensure that all telemetry collection pipelines adhere to the ontological definitions provided, specifically regarding the classification of processes, information content entities, and metric triggers.

## 7.1 Event Attribution and Process Definition

The foundational unit of observability within this framework is the eBPF event, formally defined as a temporal process. According to the axioms of the Basic Formal Ontology (BFO), specifically the class `bfo:0000015`, an event is not merely a static data point but an occurrence that unfolds over time. To ensure that such processes are audit-ready, the ontology mandates that every eBPF event process must possess at least one attribute. This attribute is classified as a Designative Information Content Entity (`cco:DesignativeICE`), serving as the semantic payload that renders the process intelligible to governance systems.

The axiom `ebpf_event_min_one_attribute` asserts that a process of type `{X}` is a subclass of `bfo:Process` and bears the relation `sdg:hasAttribute` with a minimum cardinality of one. In practical terms, this constraint prohibits the logging of "empty" events—processes that lack context or descriptive metadata. For a security auditor, this ensures that every logged process is anchored to a specific, identifiable artifact, such as a file descriptor, a network socket, or a process identifier.

This structural requirement is codified in the relational schema below. The primary key `id` serves as the unique identifier for the event instance, while the column `x` denotes the specific class of the process. The axiom necessitates that every such process possesses at least one attribute, ensuring that no event is logged without semantic context.

**Table 7.1: Event Process Instances (Axiom 1)**

| id | x |
| :--- | :--- |
| evt_001 | FileOpenEvent |
| evt_002 | NetworkBindEvent |
| evt_003 | ProcessExecutionEvent |
| evt_004 | MemoryAllocationEvent |
| evt_005 | PrivilegeEscalationEvent |

In the context of a compliance audit, Table 7.1 represents the distinct classes of processes that the monitoring infrastructure is configured to detect. For instance, the `FileOpenEvent` (id: `evt_001`) represents a process wherein a file system object is accessed. The enforcement of the `min 1` attribute rule ensures that this event is inextricably linked to a Designative ICE—such as the file path or access mode—thereby providing the necessary evidence for forensic reconstruction.

## 7.2 Alert Triggering and Metric Dependency

Building upon the definition of the eBPF event, the framework formalizes the generation of security alerts. An alert is defined not as an arbitrary notification, but as a specific type of process (`bfo:0000015`) that is causally dependent on a metric derived from system activity. The axiom `alert_triggered_by` posits that an alert of class `{X}` is triggered by a metric of class `{Y}`.

This distinction is critical for maintaining the integrity of the audit trail. It separates raw observability data (the event) from the derived intelligence (the metric) and the operational response (the alert). The ontology enforces a strict dependency: an alert cannot exist without a triggering metric. This prevents the generation of spurious alerts and ensures that every compliance action is traceable back to a specific quantitative threshold or qualitative state change observed in the system.

The relational implementation of this axiom introduces a foreign key constraint, ensuring referential integrity between the alert and the underlying event process. The table `t_alert_triggered_by` records the alert class and the specific metric instance (referenced here via the event ID that generates the metric) responsible for the trigger.

**Table 7.2: Alert Triggering Logic (Axiom 2)**

| id | x | y |
| :--- | :--- | :--- |
| alt_001 | FileQuotaExceededAlert | evt_001 |
| alt_002 | UnauthorizedPortAlert | evt_002 |
| alt_003 | AnomalousExecutionAlert | evt_003 |
| alt_004 | HeapSprayDetectionAlert | evt_004 |

As evidenced in Table 7.2, the `UnauthorizedPortAlert` (id: `alt_002`) is strictly triggered by the `NetworkBindEvent` (id: `evt_002`). This linkage ensures that if the `NetworkBindEvent` is purged or modified, the integrity of the alert record is preserved through the foreign key constraint. For governance officers, this mapping provides a clear chain of custody: the alert is the effect, and the metric derived from the eBPF event is the cause.

## 7.3 Syscall Invocation and Information Content

The third layer of the framework addresses the specific mechanism of action within the kernel: the system call. While the eBPF event represents the high-level process, the system call (`syscall`) is modeled as a Designative Information Content Entity (`cco:DesignativeICE`). This classification distinguishes the syscall as a discrete unit of information—data that designates a specific kernel operation—rather than a process in itself.

The axiom `syscall_invoked_by_event` formalizes the relationship between the event process and the syscall. It states that a syscall `{X}` is invoked by an event `{Y}`. This directionality is essential for accurate root cause analysis. It posits that the informational entity (the syscall) is manifested or brought into existence by the temporal process (the eBPF event). In audit scenarios, this allows investigators to query "which syscalls were invoked by this event?" rather than simply viewing a flat list of system calls.

The schema for this axiom requires that the invoking event be a valid instance defined in the event registry. This ensures that every syscall logged is contextually anchored to a valid eBPF process, eliminating "orphaned" syscall records that lack provenance.

**Table 7.3: Syscall Invocation Registry (Axiom 3)**

| id | x | y |
| :--- | :--- | :--- |
| sys_001 | SysOpenat2 | evt_001 |
| sys_002 | SysBind | evt_002 |
| sys_003 | SysExecve | evt_003 |
| sys_004 | SysMmap | evt_004 |
| sys_005 | SysSetuid | evt_005 |

Table 7.3 demonstrates the invocation hierarchy. For example, the `SysExecve` syscall (id: `sys_003`) is invoked by the `ProcessExecutionEvent` (id: `evt_003`). By modeling the syscall as an Information Content Entity, the framework allows for rich metadata attachment—such as argument vectors or return codes—without conflating the call itself with the process of its execution. This granularity is required for high-assurance environments where the precise sequence of kernel operations must be reconstructed verbatim.

## 7.4 Observation Correlation and Cross-Reference

The final component of the ontology addresses the observational capability of the eBPF framework itself. An eBPF event is not merely a passive log entry; it is an active process that observes other entities within the system. The axiom `ebpfevent_observes_syscall_xref` defines that an event of class `{X}` observes a syscall Designative ICE.

This axiom creates a cross-reference mechanism that links the observing process (the eBPF program attached to the kernel) to the observed entity (the syscall). This distinction is subtle but vital for compliance validation. It separates the *act of monitoring* from the *act of execution*. The `ebpfevent_observes_syscall_xref` table serves as a registry of what the eBPF instrumentation is permitted or configured to see, providing a manifest of the system's transparency capabilities.

**Table 7.4: Observation Cross-Reference (Axiom 4)**

| id | x |
| :--- | :--- |
| obs_001 | FileOpenEvent |
| obs_002 | NetworkBindEvent |
| obs_003 | ProcessExecutionEvent |
| obs_004 | MemoryAllocationEvent |
| obs_005 | PrivilegeEscalationEvent |

In Table 7.4, the observation records are listed. The `FileOpenEvent` (id: `obs_001`) is the process that performs the observation of the relevant syscalls (e.g., `SysOpenat2` from Table 7.3). This cross-reference table acts as a validation index. During an audit, one can verify that the processes defined in the observation registry (Table 7.4) are indeed the same processes invoking the syscalls (Table 7.3) and triggering the alerts (Table 7.2). This closed-loop validation ensures that the telemetry pipeline is logically consistent and that the observability framework covers all critical syscall entities defined in the governance policy.
