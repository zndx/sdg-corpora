# Chapter 7: Formal Ontology of Kernel Telemetry and Event Attribution

## 7.1 Scope and Preamble

This chapter delineates the formal ontological constraints governing Extended Berkeley Packet Filter (eBPF) telemetry within the context of enterprise security observability. It establishes the necessary conditions for event validity, the causal chains linking metrics to alerts, and the precise attribution of system calls to specific process events. The definitions provided herein are binding for all downstream compliance reporting, automated response logic, and audit trails. We define the structural relationships between kernel-level processes and the information content entities they generate, ensuring that all telemetry adheres to the rigorous standards of the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO). The following sections detail the specific axioms that govern these relationships, supported by relational schema implementations designed to enforce data integrity at the database layer.

## 7.2 The Process Attribute Constraint (Axiom 1)

### 7.2.1 Ontological Definition
The foundational unit of telemetry within this framework is the eBPF event. According to the axiom `ebpf_event_min_one_attribute`, any entity classified as an eBPF event must satisfy two primary conditions. First, it must be a subclass of `bfo:0000015` (Process). Second, it must possess a minimum of one `cco:DesignativeICE` (Designative Information Content Entity). This constraint ensures that an event is not merely a raw signal but a process that carries semantic payload. A process lacking a designative attribute is considered invalid under this governance framework, as it provides no actionable intelligence or audit value.

The verbalization of this axiom states: "{X} is a process." In this context, {X} represents the specific class of the eBPF event. The requirement for at least one designative attribute guarantees that every process captured is intrinsically linked to a data artifact that describes or identifies it. This linkage prevents the accumulation of "zombie" telemetry—processes that occur but remain undefined and uncontextualized within the security information and event management (SIEM) system.

### 7.2.2 Relational Implementation
The relational schema projected by this axiom enforces the classification of the event. The table `t_ebpf_event_min_one_attribute` serves as the registry for valid event classes. The primary key is the unique identifier (`id`), while the column `x` captures the Class name of the event. This structure allows for the validation of incoming telemetry streams against a whitelist of defined process classes.

**Table 7.1: Event Attribute Registry (Axiom 1)**

| id | x |
| :--- | :--- |
| evt_001 | ProcessExecutionEvent |
| evt_002 | NetworkConnectionEvent |
| evt_003 | FileDescriptorAccessEvent |
| evt_004 | MemoryMappingEvent |
| evt_005 | CapabilityDroppingEvent |

*Table 7.1 illustrates the instantiation of valid eBPF event classes. Each row represents a specific process class {X} that satisfies the requirement of being a BFO Process. The inclusion of `MemoryMappingEvent` and `CapabilityDroppingEvent` demonstrates the framework's applicability to low-level kernel security monitoring.*

### 7.2.3 Compliance Implications
For compliance officers, this axiom translates to a strict validation rule: any log entry or telemetry record that cannot be mapped to a defined class in Table 7.1 must be rejected as non-compliant. This ensures that the observability pipeline does not become polluted with undefined or unstructured data. Furthermore, the schema comment indicates this is a "complex" template within the "observation_measurement" family, implying that these events are typically composite in nature, aggregating multiple low-level kernel signals into a single, coherent process description.

## 7.3 Metric-Triggered Alerting Logic (Axiom 2)

### 7.3.1 Ontological Definition
The generation of a security alert is not a stochastic event but a deterministic process predicated on the observation of specific metrics. The axiom `alert_triggered_by` formalizes this dependency. It asserts that an alert class {X} is a subclass of a process (`bfo:0000015`) that is triggered by a metric class {Y}. This establishes a causal chain where the metric acts as the antecedent and the alert as the consequent.

The verbalization "{X} is something that triggered by metric {Y}" emphasizes the directionality of the relationship. The metric {Y} must exist and must be observed; only then may the alert process {X} be instantiated. This is critical for forensic analysis, as it allows investigators to trace every alert back to the specific metric that violated a threshold or policy. The schema categorizes this under the "long_tail" family, suggesting that these alerts often represent edge cases or complex, multi-factor anomalies rather than simple, high-frequency threshold breaches.

### 7.3.2 Relational Implementation
The relational schema `t_alert_triggered_by` enforces the integrity of this causal link. The table includes columns for the alert class (`x`) and the triggering metric class (`y`). Crucially, a `FOREIGN KEY` constraint is placed on column `y`, requiring it to reference a valid identifier (`id`) in the `t_ebpf_event_min_one_attribute` table. This database-level constraint ensures that an alert cannot be defined for a non-existent or invalid metric class.

**Table 7.2: Alert Trigger Matrix (Axiom 2)**

| id | x | y |
| :--- | :--- | :--- |
| alt_001 | AnomalousExecutionAlert | evt_001 |
| alt_002 | SuspiciousInboundConnectionAlert | evt_002 |
| alt_003 | UnauthorizedFileAccessAlert | evt_003 |
| alt_004 | EvasionTechniqueDetectedAlert | evt_005 |

*Table 7.2 maps specific alert classes to their triggering metric classes. For instance, the `AnomalousExecutionAlert` (alt_001) is strictly triggered by the `ProcessExecutionEvent` (evt_001). The foreign key constraint ensures that `evt_001` is a valid, registered process class as defined in Table 7.1. The `EvasionTechniqueDetectedAlert` (alt_004) is triggered by `CapabilityDroppingEvent` (evt_005), illustrating how the framework captures sophisticated security behaviors.*

### 7.3.3 Audit and Verification
During an audit, the presence of the foreign key constraint provides immediate evidence of data integrity. It demonstrates that the system is architecturally incapable of generating "orphan" alerts—alerts without a traceable cause in the telemetry layer. This satisfies key requirements of governance frameworks such as NIST 800-53 regarding audit trail reliability and event correlation.

## 7.4 Syscall Invocation Attribution (Axiom 3)

### 7.4.1 Ontological Definition
System calls (syscalls) represent the primary interface between user-space applications and the kernel. Within this ontology, a syscall is modeled not as a process, but as a `cco:DesignativeICE`—an Information Content Entity that designates a specific action or request. The axiom `syscall_invoked_by_event` defines the relationship between this informational entity and the process that invoked it.

The axiom states: "{X} is something that invoked by event {Y}." Here, {X} is the Syscall Class (the DesignativeICE), and {Y} is the Event Class (the Process). This distinction is vital for granular monitoring. It separates the *action* (the syscall, e.g., `execve`) from the *context* (the eBPF event process that captured the invocation). This allows the system to treat the syscall as a data object that can be analyzed, hashed, and correlated across different host processes.

### 7.4.2 Relational Implementation
The table `t_syscall_invoked_by_event` captures this attribution. Column `x` stores the Syscall Class, while column `y` stores the Event Class. Similar to Axiom 2, a `FOREIGN KEY` constraint on `y` references the `t_ebpf_event_min_one_attribute` table. This enforces the rule that a syscall can only be invoked by a valid, registered process event. The schema places this in the "ebpf_kernel" family, highlighting its specific relevance to kernel-level instrumentation.

**Table 7.3: Syscall Invocation Log (Axiom 3)**

| id | x | y |
| :--- | :--- | :--- |
| sys_001 | ExecveSyscall | evt_001 |
| sys_002 | ConnectSyscall | evt_002 |
| sys_003 | OpenatSyscall | evt_003 |
| sys_004 | MmapSyscall | evt_004 |
| sys_005 | SetuidSyscall | evt_005 |

*Table 7.3 catalogs the specific syscalls categorized as Designative Information Content Entities. The `ExecveSyscall` (sys_001) is invoked by the `ProcessExecutionEvent` (evt_001). This mapping allows analysts to query for all events that invoked a specific syscall type, or conversely, to identify all syscalls associated with a specific event ID. The `SetuidSyscall` (sys_005) invocation by `CapabilityDroppingEvent` (evt_005) provides a concrete example of mapping privilege changes to specific kernel requests.*

### 7.4.4 Governance Context
By treating syscalls as "Designative" entities, the framework acknowledges that the syscall name or identifier is a form of data that describes the process. This is essential for compliance reporting where specific actions (e.g., "opening a file," "establishing a socket") must be explicitly logged and retained. The ontology ensures that these actions are not lost in the abstraction of a generic "event."

## 7.5 Event-Syscall Observation Correlation (Axiom 4)

### 7.4.1 Ontological Definition
While Axiom 3 establishes which event *invoked* a syscall, Axiom 4 addresses the *observation* relationship. The axiom `ebpfevent_observes_syscall_xref` asserts that an eBPF event class {X} is a process that observes a syscall designative information content entity. This creates a cross-reference (xref) layer that links the observing process directly to the informational artifact it captured.

The verbalization "{X} is something that observes syscall designative information content entity" clarifies the role of the eBPF program. The eBPF event acts as the sensor or observer. This relationship is distinct from invocation; an event might observe a syscall that it did not strictly invoke (in cases of inter-process monitoring or broader tracing scopes), or it serves to explicitly categorize the event's primary function as observational.

### 7.4.2 Relational Implementation
The table `t_ebpfevent_observes_syscall_xref` is a lookup table designed to facilitate efficient querying of this observational relationship. It consists of an `id` and the event class `x`. In a fully normalized expansion, this would link to a specific syscall table, but within the scope of this axiom, it defines the class of events capable of such observation. The schema identifies this as part of the "ebpf_kernel" family, reinforcing its role in kernel telemetry.

**Table 7.4: Event Observation Index (Axiom 4)**

| id | x |
| :--- | :--- |
| obs_001 | ProcessExecutionEvent |
| obs_002 | NetworkConnectionEvent |
| obs_003 | FileDescriptorAccessEvent |
| obs_004 | MemoryMappingEvent |
| obs_005 | CapabilityDroppingEvent |

*Table 7.4 lists the event classes that are formally recognized as observers of syscall designative entities. The entries in this table correspond directly to the process classes defined in Axiom 1 (Table 7.1). This redundancy serves a specific architectural purpose: it validates that the event class is not only a process but is *instrumented* to observe syscall data. For example, `NetworkConnectionEvent` (obs_002) is explicitly authorized to observe `ConnectSyscall` data, ensuring that the telemetry pipeline is correctly configured for this class.*

### 7.4.3 System Integrity
This cross-reference table acts as a configuration manifest. If a new event class is added to the system (Axiom 1) but is absent from this table (Axiom 4), it indicates a configuration gap where the event process exists but lacks the instrumentation to observe the necessary syscall data. This discrepancy can be flagged by automated compliance scanners to ensure full coverage of the kernel surface.
