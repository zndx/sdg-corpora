# Chapter 4: Kernel-Level Observability and Event Correlation Frameworks

## 4.1 Scope and Preamble

This chapter establishes the formal ontology governing kernel-level observability, specifically focusing on the interaction between Extended Berkeley Packet Filter (eBPF) events, system calls, and security alerts. The framework presented herein is designed to ensure compliance with rigorous audit standards, providing a deterministic schema for correlating low-level process execution with high-level security metrics. The definitions provided are anchored in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that all entities described are interoperable across heterogeneous security information and event management (SIEM) systems. Implementers must adhere to the relational constraints defined in the subsequent sections to maintain the integrity of the audit trail.

## 4.2 Process-Based Event Attributes

### 4.2.1 Ontological Definition and Compliance Requirements

In accordance with the `ebpf_event_min_one_attribute` axiom, any entity classified as an eBPF event is formally defined as a process occurring in spacetime, denoted by the BFO reference `bfo:0000015`. This classification is not merely nominal; it imposes a structural constraint on the data model: every such process must possess a minimum of one Designative Information Content Entity (ICE), referenced by the ontology class `cco:DesignativeICE`.

This requirement ensures that no event is logged without a distinct, attributable data payload. In the context of a compliance audit, this translates to the mandate that every process event—whether it be a file access, a network socket operation, or a privilege escalation—must be accompanied by metadata that designates its specific nature or target. The `DesignativeICE` serves as the semantic anchor for the event, transforming a raw process occurrence into a structured, queryable record suitable for forensic analysis.

### 4.2.2 Relational Implementation and Evidence

The relational schema for this axiom is embodied in Table 4.1, `t_ebpf_event_min_one_attribute`. The primary key `id` serves as the unique identifier for the event class instance, while the column `x` denotes the specific class of the event process. This structure allows auditors to verify that every logged event maps to a defined process class within the system ontology.

The following table presents specific instances of event classes that satisfy the axiom. These entries represent distinct process types observed within the kernel environment, each inherently capable of carrying the required designative attributes.

**Table 4.1: eBPF Event Minimum Attribute Compliance Matrix**

| id | x |
| :--- | :--- |
| evt_001 | FileOpenEvent |
| evt_002 | SocketConnectEvent |
| evt_003 | ProcessExecEvent |

*Table 4.1 enumerates valid event classes (`x`) that satisfy the requirement of being a process (`bfo:0000015`) capable of possessing designative attributes. The `id` column provides the stable reference key used in downstream correlation tables.*

### 4.2.3 Audit Verification

When verifying compliance against this section, auditors must confirm that for every unique `id` listed in the event registry, there exists a corresponding data structure capturing the `DesignativeICE`. For instance, the `FileOpenEvent` (id: `evt_001`) must be associated with attributes such as file path, flags, or mode. The absence of such attributes constitutes a violation of the `min 1` cardinality constraint defined in the governing axiom.

## 4.3 Metric-Triggered Alerting Mechanisms

### 4.3.1 Causal Dependency and Metric Correlation

The `alert_triggered_by` axiom defines a critical causal chain within the security observability framework. It posits that an alert is a specific subclass of process (`bfo:0000015`) that is instantiated only when triggered by a specific metric class. The formal Manchester syntax, `Class: {X:Class} SubClassOf: bfo:0000015, sdg:triggeredByMetric some {Y:Class}`, necessitates that the alert class (`X`) cannot exist in a vacuum; it is ontologically dependent on the existence of a metric class (`Y`).

This dependency is fundamental for governance frameworks. It prevents the generation of "orphan" alerts—alerts that lack a discernible root cause or metric basis. By enforcing a foreign key relationship where the triggering metric (`y`) must reference a valid event process, the system ensures traceability. Every alert raised at the application layer must be traceable back to a specific kernel-level event or derived metric defined in the observability pipeline.

### 4.3.2 Relational Mapping and Instance Data

The implementation of this axiom is realized through the `t_alert_triggered_by` table. The schema enforces a `FOREIGN KEY` constraint on the `y` column, ensuring that it references a valid `id` from the `t_ebpf_event_min_one_attribute` table. This rigid linkage guarantees that the metric triggering the alert is a recognized, compliant event process.

Table 4.2 illustrates this relationship. The `x` column identifies the specific alert class, while the `y` column identifies the originating metric (event class). For example, a `FileQuotaExceededAlert` is causally linked to the `FileOpenEvent` metric.

**Table 4.2: Alert-to-Metric Causality Registry**

| id | x | y |
| :--- | :--- | :--- |
| alt_001 | FileQuotaExceededAlert | evt_001 |
| alt_002 | SuspiciousConnectionAlert | evt_002 |
| alt_003 | UnauthorizedExecAlert | evt_003 |
| alt_004 | MemoryLimitAlert | evt_004 |

*Table 4.2 defines the causal dependency between alert classes (`x`) and their triggering metric classes (`y`). The column `y` acts as a foreign key to the event registry established in Table 4.1, ensuring referential integrity.*

### 4.3.3 Governance Implications

From a governance perspective, this mapping allows security officers to audit the sensitivity of the alerting rules. By querying the join between `t_alert_triggered_by` and `t_ebpf_event_min_one_attribute`, one can rapidly assess which kernel events are instrumented to generate security alerts. If a critical event class, such as `CapabilityCheckEvent` (id: `evt_005`), is absent from the `y` column of the alert table, it indicates a potential gap in the monitoring coverage.

## 4.4 System Call Invocation Contexts

### 4.4.1 Designative Information Content Entities

The `syscall_invoked_by_event` axiom shifts the focus from the process to the information content entity. Specifically, it defines a system call (syscall) as a `cco:DesignativeICE`. Unlike the event processes described in Section 4.2, a syscall is modeled here as a distinct informational payload—a structured entity that designates an action requested by a user-space process.

The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:invokedByEvent some {Y:Class}` establishes that these syscall entities are invoked by event processes. This distinction is vital for granular auditing. It separates the *occurrence* of the event (the process) from the *content* of the request (the syscall). In a forensic investigation, this allows analysts to reconstruct the precise sequence of instructions (syscalls) that were initiated by a specific process event.

### 4.4.2 Relational Schema and Evidence

The `t_syscall_invoked_by_event` table captures this invocation relationship. Similar to the alerting mechanism, the `y` column (the invoking event) is constrained by a foreign key referencing the `t_ebpf_event_min_one_attribute` table. The `x` column represents the syscall class, which is the DesignativeICE being recorded.

Table 4.3 provides a non-exhaustive list of syscall classes and their corresponding invoking events. This data demonstrates that specific events, such as `SocketConnectEvent`, invoke distinct syscalls like the `ConnectSyscall`.

**Table 4.3: Syscall Invocation Event Log**

| id | x | y |
| :--- | :--- | :--- |
| sys_001 | OpenAt2Syscall | evt_001 |
| sys_002 | ConnectSyscall | evt_002 |
| sys_003 | ExecveSyscall | evt_003 |
| sys_004 | MmapSyscall | evt_004 |
| sys_005 | CapsetSyscall | evt_005 |

*Table 4.3 maps syscall classes (`x`) to the event processes (`y`) that invoked them. The foreign key constraint on `y` ensures that every syscall is attributed to a valid, logged event process.*

### 4.4.3 Compliance Validation

Validation of this section involves verifying that the syscall classes listed in column `x` adhere to the standard naming conventions of the target operating system kernel (e.g., Linux kernel syscall tables). Furthermore, the cardinality of the relationship must be examined; while a single event typically invokes one primary syscall, complex events may invoke multiple syscalls. The schema supports this one-to-many relationship, allowing a single `y` value (event ID) to appear multiple times across different rows, corresponding to different `x` values (syscalls).

## 4.5 Syscall Observation Cross-Reference

### 4.5.1 The Observation Framework

The final component of the ontology is defined by the `ebpfevent_observes_syscall_xref` axiom. This axiom formalizes the role of the eBPF event as an observational process. It states that the eBPF event class (`X`) is a process (`bfo:0000015`) that observes a syscall `cco:DesignativeICE`.

This creates a semantic loop: the event process invokes the syscall (Section 4.4) and simultaneously observes it. In the context of eBPF technology, this reflects the reality of tracing programs that attach to hook points in the kernel. The eBPF program (the event process) executes to observe the syscall (the information entity) as it passes through the kernel subsystem. This axiom is essential for defining the "Observation" family in the ontology, categorizing events specifically used for tracing and monitoring as opposed to those used for modification or blocking.

### 4.5.2 Relational Structure and Data

The `t_ebpfevent_observes_syscall_xref` table provides a registry for these observation-capable event classes. It is a simpler structure than the previous tables, containing only the `id` and the event class `x`. However, its semantic weight is significant, as it explicitly tags classes as "observational."

Table 4.4 lists the event classes that are defined as observers within the system. These classes serve as the bridge between the raw kernel activity and the aggregated security metrics.

**Table 4.4: Syscall Observation Event Registry**

| id | x |
| :--- | :--- |
| obs_001 | SyscallTraceEvent |
| obs_002 | AuditLogEvent |
| obs_003 | PerfCounterEvent |
| obs_004 | KprobeEvent |

*Table 4.4 identifies event classes (`x`) that satisfy the definition of an observational process. These classes are capable of observing syscall DesignativeICEs, forming the basis of the kernel-level telemetry data.*

By cross-referencing the observational events listed here with the invocation data in Table 4.3, compliance officers can verify that the system has visibility into the critical syscalls. For instance, if `SyscallTraceEvent` (id: `obs_001`) is active, it implies that the system has the capacity to observe the syscalls listed in Table 4.3.
