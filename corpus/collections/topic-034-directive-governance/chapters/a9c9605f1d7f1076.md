# Chapter 7: Formal Ontology of eBPF Event Attribution and Metric Correlation

## 7.1 Scope and Preamble

This chapter delineates the formal ontological framework governing Extended Berkeley Packet Filter (eBPF) event attribution within secure computing environments. It establishes the requisite structural definitions for kernel-level observability, ensuring that all process entities are rigorously mapped to their designative attributes and causal triggers. The guidelines herein are mandatory for compliance with system-level auditing standards, providing a deterministic schema for correlating low-level system calls with high-level security alerts. Implementers must adhere to the relational constraints defined in the subsequent sections to maintain data integrity and to support forensic analysis.

## 7.2 Event Attribution and Process Definition

The foundational unit of observability within this framework is the eBPF event, formally classified as a process occurring within the kernel space. In accordance with the Basic Formal Ontology (BFO), any entity designated as an eBPF event must satisfy the axiom of being a temporal process (`bfo:0000015`). Furthermore, to ensure that such processes are not merely abstract occurrences but are grounded in observable reality, the ontology mandates that every event process possesses a minimum of one attribute. This attribute is classified as a Designative Information Content Entity (DesignativeICE), serving as the semantic payload that defines the nature of the event for downstream consumers.

The necessity of this attribution cannot be overstated. Without a binding relationship to a DesignativeICE, a process lacks the context required for audit trails and compliance reporting. The DesignativeICE encapsulates the metadata—such as process IDs, user namespaces, or cgroup identifiers—that transforms a raw kernel event into an actionable data point. This relationship ensures that every logged event is self-describing to a degree that satisfies regulatory requirements for traceability.

### 7.2.1 Process Verification
When validating the integrity of the observability pipeline, auditors must verify that for every entry in the event log, a corresponding DesignativeICE exists. The absence of this linkage constitutes a critical failure in the data capture mechanism. The `NetworkConnectionProcess`, for instance, must be associated with attributes that define the source and destination IP addresses, ports, and socket states. Similarly, the `FileSystemAccessProcess` must carry attributes detailing the file path, requested permissions, and the inode of the target file.

## 7.3 Alert Triggering and Metric Causality

Building upon the definition of the event process, the framework defines the conditions under which automated security alerts are generated. An alert is not a spontaneous entity; rather, it is a process that is causally dependent on a specific metric. The ontology formalizes this through the axiom `alert_triggered_by`, which asserts that an alert (Class X) is a process that is triggered by a metric (Class Y). This metric is, in itself, a specific type of eBPF event process, thereby creating a strict dependency chain.

This causal linkage is essential for distinguishing between false positives and genuine security incidents. By mandating that every alert must reference a triggering metric event, the framework enforces a traceable path from the alert notification back to the specific kernel activity that precipitated it. This structure facilitates the "long tail" analysis of security events, allowing investigators to drill down from the alert level to the granular metric data.

### 7.3.1 Metric Thresholds and Alert Logic
The metric referenced in this context serves as the quantitative or qualitative threshold that, when met or exceeded, initiates the alert process. For example, the `AnomalyDetectionAlert` is triggered by the `NetworkConnectionProcess` when specific attributes within that process—such as a high frequency of connection requests to a geographically disperse set of endpoints—exceed the defined baseline. The foreign key constraint ensures that alerts cannot be generated in a vacuum; they must be anchored to a valid, observed event process. This prevents the generation of "orphan" alerts which would otherwise clutter the security dashboard and complicate the incident response workflow.

## 7.4 System Call Invocation by Events

To achieve granular observability, the framework must bridge the gap between high-level process events and the specific system calls that constitute them. This is governed by the axiom `syscall_invoked_by_event`, which classifies a system call (Class X) as a DesignativeICE that is invoked by a specific event process (Class Y). This relationship is critical for deep-dive forensic analysis, as it maps the semantic event to the exact kernel primitive executed.

In this context, the system call is treated as an Information Content Entity because it represents the "intent" or "command" encoded by the process, rather than the execution of the process itself. By defining the syscall as an entity invoked by the event, the ontology allows for the distinct categorization of the *request* (the syscall) separate from the *activity* (the event). This separation is vital for compliance frameworks that require the logging of specific privileged operations, such as `execve` or `mount`, independent of the broader process context.

### 7.4.1 Invocation Traceability
The integrity of the invocation chain is paramount for audit verification. When a `FileSystemAccessProcess` is logged, the corresponding `OpenAtSyscall` provides the technical details of the file access mode (e.g., read-only, write-append). This level of detail is often required by regulatory bodies to verify that access controls were not bypassed. The ontology ensures that the syscall is not merely a property of the event, but a distinct entity that is *invoked by* the event. This distinction allows for complex querying, such as identifying all events that invoked a specific, high-risk syscall, regardless of the event's broader classification.

## 7.5 Event Observation and Syscall Correlation

The final component of the framework addresses the mechanism of observation itself. The axiom `ebpfevent_observes_syscall_xref` defines a class of events (Class X) that are specifically tasked with observing system call designative information. This establishes the eBPF event as an observer or a probe, explicitly linking the event process to the syscall information content entity it captures.

This relationship formalizes the role of eBPF programs as passive observers within the kernel. Unlike standard processes that *perform* actions, these observer events *record* actions. The ontology captures this nuance by stating that the event observes the syscall. This cross-reference is essential for mapping the telemetry data back to the source code or the specific eBPF program responsible for the collection, thereby verifying that the monitoring coverage is comprehensive and unmodified.
