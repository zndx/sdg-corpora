# Chapter 4: Governance Directives, Log Artifacts, and Audit Processes

This chapter delineates the structural relationships between governance directives, system artifacts, and audit processes within the enterprise ontology framework. It provides a formal specification of the control classes that address specific risk categories, the log artifacts that record system events with associated severities, and the audit processes that target these artifacts. The definitions herein are consistent with the Manchester Syntax axioms governing the ontology and are mapped to the underlying relational schema used for persistence and reporting.

## 4.1 Control Directives and Risk Addressal

In the context of information security governance, a Control Directive is defined as a prescriptive instruction intended to mitigate specific threats. The axiom `control_only_addresses_threat_class` establishes that any entity classified as a Control Directive (subclass of `cco:DirectiveICE`) must exclusively address risks belonging to a specific class. This restriction ensures that controls are not ambiguously defined but are tightly coupled to the threat vectors they are designed to neutralize.

The implementation of this axiom within the relational schema utilizes a foreign key constraint to enforce referential integrity. Specifically, the risk class (`y`) addressed by a control must correspond to a valid entry in the log record subclass table. This architecture guarantees that for every control directive defined, there exists a corresponding artifact definition capable of capturing the events relevant to that risk.

### 4.1.1 Relational Mapping of Control Directives

The table `t_control_only_addresses_threat_class` serves as the registry for these governance objects. The primary key (`id`) uniquely identifies the control directive. Column `x` represents the specific class of the control (e.g., InputValidationDirective), while column `y` represents the risk class it addresses (e.g., SQLInjectionLog). The foreign key constraint linking `y` to `t_log_record_subclass(id)` ensures that the control addresses a recognized, loggable threat event.

Table 4.1 details the instantiation of control directives addressing specific threat classes. These entries reflect the deterministic derivation of the ontology slots into the relational model.

| ID (PK) | Control Class (X) | Addressed Risk Class (Y) |
| :--- | :--- | :--- |
| `ctrl_injection_defense` | `InputValidationDirective` | `SQLInjectionLog` |
| `ctrl_xss_defense` | `OutputEncodingDirective` | `CrossSiteScriptingLog` |
| `ctrl_auth_enforcement` | `AuthenticationDirective` | `FailedAuthLog` |
| `ctrl_crypto_management` | `KeyRotationDirective` | `WeakCipherLog` |
| `ctrl_data_disposal` | `SanitizationDirective` | `DataRemanenceLog` |

*Table 4.1: Control Directives and their corresponding addressed threat classes.*

The data in Table 4.1 illustrates the "only" restriction in the axiom. For instance, the `InputValidationDirective` is constrained to address *only* the `SQLInjectionLog` risk class. It cannot, within this strict schema, be semantically linked to unrelated threat classes without violating the subclass axiom. This granularity is essential for automated compliance engines that must map specific technical controls to regulatory requirements.

## 4.2 Log Artifacts and Severity Classification

System artifacts, specifically those generated by logging infrastructure, form the evidentiary basis of security monitoring. According to the axiom `log_record_subclass`, a Log Record is a subclass of `cco:Artifact` that possesses a specific log severity. The ontology posits that the existence of a log record is intrinsically tied to a severity classification, which dictates the urgency and handling of the event.

The relational projection of this axiom introduces a circular dependency with the control directives table, which serves a specific governance purpose. In this schema, the severity of a log record (`y`) is not merely a scalar value (e.g., "High" or "Low") but is functionally mapped to the Control Directive ID that is responsible for addressing that severity level. This design enforces a closed-loop system where the severity of an event is inextricably linked to the control mechanism required to mitigate it.

### 4.2.1 Structure of Log Records

The table `t_log_record_subclass` captures these definitions. The primary key (`id`) identifies the specific log record class. Column `x` denotes the broader artifact class (e.g., `AppSecurityEvent`), while column `y` contains the identifier of the control directive that defines the severity context. The foreign key constraint (`y` references `t_control_only_addresses_threat_class(id)`) ensures that every severity classification is backed by a valid, active control directive.

Table 4.2 presents the log record subclasses mapped to their respective severity contexts (Control Directives).

| ID (PK) | Log Record Class (X) | Severity Context / Control ID (Y) |
| :--- | :--- | :--- |
| `SQLInjectionLog` | `AppSecurityEvent` | `ctrl_injection_defense` |
| `CrossSiteScriptingLog` | `WebSecurityEvent` | `ctrl_xss_defense` |
| `FailedAuthLog` | `IdentityEvent` | `ctrl_auth_enforcement` |
| `WeakCipherLog` | `CryptoEvent` | `ctrl_crypto_management` |
| `DataRemanenceLog` | `StorageEvent` | `ctrl_data_disposal` |

*Table 4.2: Log Record subclasses with severity contexts mapped to Control Directives.*

The mapping demonstrates the axiom `hasLogSeverity some {Y:Class}`. In this implementation, the "class" representing the severity is effectively the Control Directive itself. For example, the `FailedAuthLog` (an `IdentityEvent`) has a severity defined by `ctrl_auth_enforcement`. This implies that the threshold for what constitutes a critical authentication failure is determined by the parameters of the `AuthenticationDirective`. This linkage allows the system to dynamically adjust severity thresholds based on the governing control policy rather than relying on hardcoded static values.

## 4.3 Audit Processes and Artifact Targeting

The final component of this governance triad involves the Audit Process. Defined by the axiom `audit_targets_data_artifact`, an Audit is a subclass of `bfo:0000015` (a Process) that performs an audit action on a `cco:Artifact`. This concept formalizes the review mechanism, ensuring that audit processes are explicitly defined in terms of the artifacts they examine.

Unlike the previous two axioms, which established complex restrictions and cross-references, the audit axiom defines a targeting relationship. The relational schema for `t_audit_targets_data_artifact` is straightforward, consisting of an identifier and the class of the audit process. While the axiom implies a relationship to artifacts, the schema provided focuses on the registration of the audit process classes themselves.

### 4.3.1 Audit Process Registry

The table `t_audit_targets_data_artifact` functions as a registry for valid audit processes within the system. These processes are the mechanisms by which compliance is verified against the control directives and log records defined in Sections 4.1 and 4.2.

Table 4.3 lists the audit process classes defined in the system.

| ID (PK) | Audit Process Class (X) |
| :--- | :--- |
| `audit_input_val` | `InputValidationAudit` |
| `audit_output_enc` | `OutputEncodingAudit` |
| `audit_auth_logs` | `AuthenticationLogAudit` |
| `audit_crypto_keys` | `CryptographicKeyAudit` |
| `audit_storage_san` | `StorageSanitizationAudit` |

*Table 4.3: Audit Process classes targeting specific data artifacts.*

Each entry in Table 4.3 represents a distinct process class (`X`) that inherits from the BFO Process entity. For example, the `InputValidationAudit` is a process specifically designed to target artifacts related to input validation (presumably instances of the `SQLInjectionLog` defined in Table 4.2). The ontology ensures that any process classified as an Audit must target an Artifact, thereby preventing the definition of "empty" audit processes that lack a subject of review.

## 4.4 Integration and Compliance Verification

The integration of these three axiom sets creates a robust chain of evidence and enforcement. The Control Directive (Table 4.1) defines the policy. The Log Record (Table 4.2) captures the state of compliance or violation relative to that policy, with its severity anchored back to the policy ID. The Audit Process (Table 4.3) provides the verification mechanism.

When a compliance officer generates a report, the system queries these tables to verify that:
1.  Every active control has a corresponding threat definition (Foreign Key check on Table 4.1).
2.  Every log event generated is mapped to a severity profile that corresponds to a valid control (Foreign Key check on Table 4.2).
3.  All audit reviews are conducted using registered process classes (Table 4.3).

This structure eliminates ambiguity in the governance framework. By strictly typing the relationships between directives, artifacts, and processes, the ontology ensures that automated compliance tools can reason about the system state with high precision. The "dense" coupling between the severity of a log and the ID of the control directive, as seen in the `t_log_record_subclass` table, is a distinctive feature of this architecture, ensuring that severity is always policy-relative.
