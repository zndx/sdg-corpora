# Chapter 4: Governance Directives, Log Artifacts, and Audit Processes

## 4.1 Scope and Preamble

This chapter delineates the structural dependencies between governance directives, risk artifacts, and audit processes within the enterprise ontology. It establishes the formal relationships between control mechanisms and the specific risk events they mitigate, as well as the evidentiary log records generated during system operations. Furthermore, it defines the audit processes that serve as the primary verification mechanism for these controls. The content herein is grounded in the axiomatic definitions of the `cco`, `sdg`, and `bfo` namespaces, providing a rigorous framework for mapping compliance requirements to technical implementations. Readers should refer to the accompanying data tables to understand the specific instantiation of these axioms within the relational schema.

## 4.2 Control Directives and Risk Addressance

### 4.2.1 Axiomatic Definition

The foundational concept of governance within this framework is defined by the axiom `control_only_addresses_threat_class`. Formally, this axiom asserts that a specific class of Control (X) is a subclass of `cco:DirectiveICE` (Information Control Element) and possesses the property `sdg:addressesRisk` exclusively with respect to a specific Threat or Risk class (Y). In natural language, this relationship is verbalized as: "{X} is something that addresses risk {Y}."

This axiom enforces a strict constraint: a directive control is valid only insofar as it is semantically bound to a specific risk classification. This is not a loose association but a definitional characteristic of the control itself. The control does not merely "mitigate" a risk in a general sense; its very definition as a `DirectiveICE` is contingent upon its specific relationship to the risk class Y. This ensures that governance artifacts are not defined in a vacuum but are always anchored to the threat landscape they are designed to manage.

### 4.2.2 Relational Implementation and Data Manifestation

In the relational projection of this ontology, the axiom `control_only_addresses_threat_class` is materialized as the table `t_control_only_addresses_threat_class`. The structure of this table is designed to capture the class-level definitions of both the Control and the Risk it addresses.

The primary key of this table is the `id` column, which serves as the unique identifier for the specific axiom instance (i.e., the specific Control-Risk pair). The column `x` represents the Control Class (the `DirectiveICE`), while the column `y` represents the Risk Class. A critical referential integrity constraint is enforced herein: the `y` column (Risk Class) acts as a foreign key referencing the `id` of the `t_log_record_subclass` table. This constraint implies that within this schema, a "Risk" is ontologically treated as a subclass of a Log Record. This reflects a data-driven governance model where risks are not abstract concepts but are instantiated as specific, categorizable log events or artifacts.

The following table presents the instantiation of Control Directives and their associated Risk Classes. Note that the Risk Class identifiers (`y`) correspond to identifiers found in the subsequent log record table, enforcing the closed-loop nature of the governance model.

## 4.3 Log Artifacts and Severity Classification

### 4.3.1 Axiomatic Definition

While controls define the intent of governance, the axiom `log_record_subclass` captures the operational reality. This axiom asserts that a Log Record class (X) is a subclass of `cco:Artifact` and possesses the property `sdg:hasLogSeverity` with respect to a Severity class (Y). Verbalized, this reads: "{X} is something that has log severity {Y}."

This axiom bridges the gap between static definitions and dynamic system events. By classifying log records as `cco:Artifact`, the ontology recognizes them as persistent, informational entities produced by the system. The assignment of severity (`sdg:hasLogSeverity`) transforms raw data into structured evidence. The severity classification is not merely a metadata tag but a fundamental property of the log artifact class, determining its processing priority and impact on compliance posture.

### 4.3.2 Relational Implementation and Data Manifestation

The relational schema for this axiom is encapsulated in the table `t_log_record_subclass`. The primary key is the `id` column, representing the unique identifier for the Log Record class. The column `x` holds the Log Record Class name, and the column `y` holds the Severity Class.

The schema enforces a specific, bidirectional constraint through a foreign key: the `y` column (Severity Class) references the `id` of the `t_control_only_addresses_threat_class` table. This creates a structural dependency where the "Severity" of a log event is defined by the "Control" that addresses it. In practical terms, this suggests that severity is not an arbitrary scale but is derived from the governance framework: the severity of a log event is determined by the specific control directive whose scope encompasses that event. For example, a "Failed Login" event has a severity defined by the "Multi-Factor Authentication" control, because that control is the mechanism designed to address the risk represented by that log.

The table below details the Log Record artifacts, their classification, and the Control-derived Severity.

| :--- | :--- | :--- |
| `log_risk_failed_login` | `FailedLoginAttemptArtifact` | `ctrl_auth_01` |
| `log_risk_cleartext_storage` | `UnencryptedDataArtifact` | `ctrl_enc_02` |
| `log_risk_external_scan` | `PortScanDetectionArtifact` | `ctrl_net_03` |

## 4.4 Audit Processes and Artifact Targeting

### 4.4.1 Axiomatic Definition

The final component of the governance triad is the verification mechanism, defined by the axiom `audit_targets_data_artifact`. This axiom asserts that an Audit class (X) is a subclass of `bfo:0000015` (a Process) and holds the property `sdg:auditsControl` over some `cco:Artifact`. In natural language: "{X} is something that audits control artifact."

This axiom formalizes the audit as a distinct process (`bfo:Process`) rather than a static object. Its purpose is explicitly defined as the auditing of control artifacts. This ensures that audit activities are not aimless exercises in data collection but are targeted processes designed to verify the existence, integrity, and efficacy of the artifacts governed by the controls defined in Section 4.2. The audit process is the active agent that interrogates the passive artifacts defined in Section 4.3.

### 4.4.2 Relational Implementation and Data Manifestation

The `t_audit_targets_data_artifact` table materializes this axiom. It is a simpler structure compared to the previous two, consisting of an `id` primary key and a column `x` representing the Audit Process class.

Unlike the previous tables, this schema does not enforce a foreign key constraint within the definition provided. However, the semantic definition implies that the target of the audit (the `cco:Artifact`) must exist within the domain of discourse established by the `t_log_record_subclass` table. The audit process is the consumer of the log artifact data, executing the verification logic required to maintain compliance.

The following table lists the defined Audit Processes. These processes represent the scheduled or event-driven activities that review the log artifacts to ensure the controls defined in Section 4.2 are functioning correctly.
