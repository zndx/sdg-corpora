# Chapter 4: Ontological Mapping of Governance Directives and Audit Artifacts

This chapter delineates the structural relationships between governance directives, risk artifacts, and audit processes within a compliant information system. It provides a formal specification of how control directives address specific risk classes, how log records are classified by severity through those same directives, and how audit processes functionally target data artifacts to verify compliance. The definitions herein are grounded in the OWL ontology axioms governing the `cco`, `sdg`, and `bfo` namespaces, ensuring that the implementation of these concepts adheres to strict referential integrity and semantic consistency.

## 4.1 Directive Governance and Risk Addressal

The foundational element of the governance framework is the Control Directive, formally defined as an instance of `cco:DirectiveICE`. This class represents an immutable instruction or policy mandated by the governing authority to mitigate specific threats. In accordance with the axiom `control_only_addresses_threat_class`, every directive is structurally bound to a specific risk class that it is designed to address. This relationship is not merely associative but is restrictive; a directive of this type may address *only* the risk class specified in its definition.

The semantic binding ensures that governance artifacts are traceable. When a directive is instantiated, it must declare the target risk (`Y`) which it addresses. In the relational projection of this ontology, the risk entity is modeled as a foreign key reference to a log record, establishing a direct link between the policy (the control) and the manifestation of the threat (the log record). This design facilitates automated impact analysis, allowing systems to query which directives are applicable when a specific risk artifact is detected.

Consider the implementation of an `InventoryControlDirective`. This directive exists solely to address the risk of `InventoryMismatchArtifact`. The directive does not apply to financial discrepancies or personnel access logs; its scope is strictly constrained by the axiom to the defined risk class. This constraint prevents scope creep in automated enforcement engines and ensures that audit trails remain coherent.

The `x` column represents the Directive Class, while the `y` column contains the identifier of the Risk Class (Log Record) it addresses. Note that the values in the `y` column must correspond to valid identifiers in the log record subsystem, enforcing the dependency defined in the schema.

The referential integrity implied by this structure dictates that the removal of a risk record (e.g., `LOG-SEC-002`) must be preceded by the decommissioning of the directive addressing it (`DIR-SEC-002`), or the directive must be remapped to a valid, existing risk identifier. This strict dependency is characteristic of high-assurance systems where orphaned controls represent a significant compliance liability.

## 4.2 Artifact Taxonomy and Log Severity

While directives define the intent of governance, the `cco:Artifact` class represents the factual evidence of system state and events. Specifically, we examine the subclass of artifacts defined by the axiom `log_record_subclass`. This axiom asserts that a log record (`X`) is a type of artifact that possesses a specific log severity (`Y`). The severity classification is not an arbitrary string but is derived from the control framework itself.

In this ontology, the severity of a log record is modeled as a reference back to a Control Directive. This circular dependency—where a directive addresses a risk (log record), and that log record has a severity defined by a directive—creates a closed loop of governance. It implies that the severity of an event is determined by the specific control mandate that governs it. For instance, if an `AccessControlDirective` is the governing authority for authentication events, then the severity of a `FailedLoginAttempt` is defined by the parameters of that directive.

This structure allows for dynamic severity adjustment. By modifying the properties of the directive referenced in the `y` slot, the system can globally alter the severity classification of all associated log records without needing to update individual log entries. This is critical for maintaining consistency during regulatory updates, where the definition of "critical" versus "warning" may shift based on external compliance frameworks.

The `x` column denotes the specific Log Record Class, while the `y` column references the ID of the Control Directive that defines its severity. This mapping satisfies the requirement that the artifact has a severity "some" `Y`, effectively linking the observation to the rulebook.

**Table 4.2: Log Record Subclasses and Severity Mappings**

| id | x | y |
| :--- | :--- | :--- |
| LOG-INV-001 | InventoryMismatchArtifact | DIR-INV-001 |
| LOG-SEC-002 | FailedLoginAttempt | DIR-SEC-002 |
| LOG-DAT-003 | ArchiveExpiryEvent | DIR-DAT-003 |
| LOG-NET-004 | CrossZoneTrafficAlert | DIR-NET-004 |
| LOG-CRY-005 | KeyRotationFailure | DIR-CRY-005 |

In this schema, the `LOG-SEC-002` entry (FailedLoginAttempt) derives its severity from `DIR-SEC-002`. If `DIR-SEC-002` is updated to reflect a heightened security posture, all queries assessing the severity of `LOG-SEC-002` instances will automatically reflect this change. This design pattern prioritizes traceability and centralized control over data normalization, ensuring that the interpretation of log data is always anchored to the current governing directives.

## 4.3 Audit Process Verification

The final component of the governance triad is the Audit Process, defined by the axiom `audit_targets_data_artifact`. This class (`X`) is a subprocess of `bfo:Process` (specifically `bfo:0000015`, denoting a processual entity) that functions to verify or audit a control artifact. The audit process is the mechanism by which the organization asserts that the directives defined in Section 4.1 and the artifacts logged in Section 4.2 are operating in accordance with the stated compliance requirements.

An audit process in this context is a distinct computational or procedural workflow. It is not merely a report; it is an active process that targets `cco:Artifact` instances. The axiom specifies that the process audits a "control artifact," which implies that the subject of the audit is the evidence of the control's operation (the log record) rather than the directive itself. This distinction is vital for compliance reporting. Auditors must verify that the controls are *functioning* (evidenced by artifacts), not just that the directives *exist*.

The implementation of an audit process involves the systematic retrieval and validation of artifacts. For example, a `QuarterlyAccessReview` process would target `AccessLogArtifacts` to ensure they align with the `AccessControlDirective`. The process entity encapsulates the logic for this verification, including sampling rates, validation rules, and escalation triggers.

Table 4.3 catalogs the defined Audit Processes within the system. Each process is identified by a unique ID and classified by its specific function (`x`). These processes act as the primary vehicles for compliance assurance, executing the logic required to validate the integrity of the data artifacts described in the previous sections.

**Table 4.3: Audit Processes Targeting Data Artifacts**

| id | x |
| :--- | :--- |
| AUD-REV-001 | QuarterlyAccessReview |
| AUD-INV-002 | AnnualInventoryAudit |
| AUD-DAT-003 | DataRetentionVerification |
| AUD-SYS-004 | ConfigurationDriftAnalysis |
| AUD-SEC-005 | PrivilegedEscalationAudit |

The `QuarterlyAccessReview` (AUD-REV-001), for instance, would systematically query the log records associated with `DIR-SEC-002` to identify anomalies or policy violations. Because the audit process is formally linked to the artifact ontology, automated systems can schedule these processes based on the risk classifications defined in Section 4.1. High-risk artifacts may trigger more frequent audit processes, thereby creating a dynamic feedback loop that prioritizes governance resources based on the current threat landscape.
