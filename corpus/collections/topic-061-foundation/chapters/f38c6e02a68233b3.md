# Chapter 4: Directive Controls, Log Subclasses, and Audit Processes in Compliance Systems

This chapter defines three ontological patterns drawn from directive governance and artifact modeling. The patterns are projected into a minimal relational schema consisting of three tables. The schema supports cross-table queries that resolve control-to-risk addressing, severity classification of log records, and audit targeting of data artifacts.

## 1 Scope and Table Overview

The tables implement the axioms exactly as stated. Primary keys are synthetic identifiers. Foreign keys enforce the directed relationships required by each axiom. All column values are drawn from compliance records typical of disaster-recovery and audit-trail systems.

### 1.1 t_control_only_addresses_threat_class

This table embodies axiom 1. Column id is the primary key. Column y is a foreign key into t_log_record_subclass.id, allowing a reader to retrieve the severity class that a given directive control is permitted to address.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_log_record_subclass(id)
);
```

|----------|--------------------------|---------------|
| ctrl-001 | AccessControlPolicy      | log-003       |
| ctrl-002 | EncryptionAtRest         | log-001       |
| ctrl-003 | NetworkIsolation         | log-002       |
| ctrl-004 | BackupRetentionDirective | log-004       |
| ctrl-005 | IncidentResponsePlan     | log-005       |

### 1.2 t_log_record_subclass

This table embodies axiom 2. Column id is the primary key. Column y is a foreign key into t_control_only_addresses_threat_class.id, closing the permitted-addressing cycle between a log subclass and its controlling directive.

```sql
CREATE TABLE t_log_record_subclass (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_control_only_addresses_threat_class(id)
);
```

### 1.3 t_audit_targets_data_artifact

This table embodies axiom 3. Column id is the primary key. No foreign-key column is present; an audit process instance stands alone yet may be joined by application logic to any control or log record that shares an artifact identifier.

```sql
CREATE TABLE t_audit_targets_data_artifact (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 2 Cross-Join Example

Question: Which log severity class is addressed by the control that is itself referenced by the log record “CriticalErrorLog”, and which audit artifact would be examined if that control were audited?

Step 1. Locate the row in t_log_record_subclass where x = 'CriticalErrorLog'.  
Result: id = log-001, y = ctrl-002.

Step 2. Follow y to t_control_only_addresses_threat_class.  
Result: id = ctrl-002, x = 'EncryptionAtRest', y = log-001.

Step 3. The control EncryptionAtRest addresses the severity class carried by log-001. An auditor would next examine the artifact row whose identifier matches the control’s documented target (here aud-003, EncryptionKeyStore).

Joined row (abridged):  
(log-001, CriticalErrorLog, ctrl-002, EncryptionAtRest, aud-003, EncryptionKeyStore)
