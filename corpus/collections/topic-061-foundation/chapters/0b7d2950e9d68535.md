# Chapter 4: Governance Directives, Log Artifacts, and Audit Processes in the SDG Framework

This chapter delineates the structural relationships between governance directives, system-generated artifacts, and audit processes within the Secure Data Governance (SDG) framework. It provides a formal specification of the ontology axioms governing control mechanisms, the classification of log records, and the procedural targets of audit compliance. The definitions herein are binding for all compliance modules and reporting interfaces referenced in subsequent sections of this handbook.

## 1. Directive Controls and Risk Addressance

The foundational unit of governance within the framework is the Directive Information Control Element (DirectiveICE). This class represents a codified control mechanism designed to mitigate specific security threats or operational risks. Per the governing axiom, a DirectiveICE is formally defined as a class that addresses a risk class exclusively. This relationship is not merely associative but restrictive; the directive is constrained to address only the specific risk class to which it is bound, ensuring a high degree of specificity in the control mapping.

In practical terms, this means that a governance directive cannot be ambiguously defined as addressing "general security." Rather, it must be instantiated with a precise reference to a threat class. This binding ensures that control efficacy can be measured directly against the manifestation of that specific threat within the system logs. The relationship between the directive and the risk is modeled as a unidirectional property where the directive is the subject and the risk is the object.

### 1.1 Control-to-Risk Mapping

The implementation of this axiom requires a rigid mapping structure. When a control is instantiated, it must be linked to a specific threat identifier. This linkage serves as the primary key for all subsequent compliance reporting. For example, an "Encryption Directive" addresses the risk class "Data Exfiltration," whereas an "Authentication Directive" addresses "Unauthorized Access."

The following table illustrates the instantiation of this axiom. It demonstrates how specific control classes (X) are bound to specific threat classes (Y). Note that the threat class identifier (`y`) serves as a foreign key reference to the log record subclass, establishing the dependency between the control definition and the evidence required to verify it.

**Table 1-1: Control and Risk Class Mappings**

| ID | Control Class (X) | Risk Class (Y) |
| :--- | :--- | :--- |
| CTRL-ADM-01 | AccessControlDirective | LOG-THRT-001 |
| CTRL-ADM-02 | DataRetentionDirective | LOG-THRT-002 |
| CTRL-ADM-03 | EncryptionKeyDirective | LOG-THRT-003 |
| CTRL-NET-04 | FirewallFilteringDirective | LOG-THRT-004 |
| CTRL-APP-05 | InputValidationDirective | LOG-THRT-005 |

*Table 1-1 embodies the axiom `control_only_addresses_threat_class`. The primary key is the `id` of the control directive. The column `y` represents the risk class addressed and functions as a foreign key referencing the log record subclass table (`t_log_record_subclass`), ensuring that every defined risk is observable via system artifacts.*

## 2. Log Artifacts and Severity Classification

To validate the efficacy of the directives described in Section 1, the framework relies on `cco:Artifact` entities, specifically system-generated logs. The ontology defines a subclass of artifacts known as the Log Record. This class is distinct in that it possesses a `hasLogSeverity` property. This axiom asserts that any log record serving as evidence for a risk event must possess a severity classification.

The severity classification is not an arbitrary label but is derived from the control context. In this schema, the severity of a log record is determined by the control directive that governs the risk it represents. This creates a feedback loop: the directive defines the risk, and the log record provides the evidence of that risk's manifestation, calibrated by a severity level that references back to the control context.

### 2.1 Severity and Evidence Correlation

The log record acts as the "long tail" of the compliance framework—the persistent, data-heavy evidence generated during operations. The `hasLogSeverity` property allows the governance engine to prioritize alerts and audit trails based on the criticality of the control involved.

For instance, a log record indicating a failure in the "AccessControlDirective" (Table 1-1, ID: CTRL-ADM-01) would carry a severity classification derived from that control's criticality. The schema enforces that the severity value (`y`) must reference a valid control directive ID. This ensures that severity levels are standardized across the enterprise and tied directly to governance policies, rather than being assigned ad hoc by system administrators.

**Table 2-1: Log Record Subclass and Severity Assignments**

| ID | Log Record Class (X) | Severity / Control Reference (Y) |
| :--- | :--- | :--- |
| LOG-THRT-001 | FailedAuthenticationLog | CTRL-ADM-01 |
| LOG-THRT-002 | DataExpiryWarningLog | CTRL-ADM-02 |
| LOG-THRT-003 | KeyRotationFailureLog | CTRL-ADM-03 |
| LOG-THRT-004 | InboundTrafficDenialLog | CTRL-NET-04 |
| LOG-THRT-005 | SQLInjectionAttemptLog | CTRL-APP-05 |

*Table 2-1 embodies the axiom `log_record_subclass`. The column `x` denotes the specific class of the log artifact (e.g., `FailedAuthenticationLog`). The column `y` represents the `hasLogSeverity` property and is constrained as a foreign key referencing the control directive table (`t_control_only_addresses_threat_class`). This structure ensures that the severity of a log event is intrinsically linked to the control directive that addresses the underlying risk.*

## 3. Audit Processes and Control Verification

The final component of the governance triad is the Audit Process. While directives establish policy and logs provide evidence, the audit process provides the verification mechanism. The ontology defines the Audit class as a subclass of `bfo:0000015` (a Process), which possesses the property `auditsControl` targeting `cco:Artifact`.

This axiom formalizes the audit as a distinct temporal process that acts upon the artifacts generated by the system. An audit is not a static document but a processual entity that examines the state of artifacts to verify that the directives (Section 1) are effectively addressing the risks (Section 2).

### 3.1 Audit Targeting and Artifact Scope

The scope of an audit is defined by the artifacts it targets. The axiom `audit_targets_data_artifact` necessitates that any audit process instance must be associated with the review of specific data artifacts. This could be a scheduled process, such as a "Quarterly Compliance Review," or an ad-hoc process, such as a "Forensic Investigation."

The critical distinction here is that the audit targets the *artifact*, not the control directly. The control is verified *through* the artifact. This separation of concerns allows the framework to model audits as independent processes that can be instantiated against various sets of artifacts without modifying the underlying control definitions.

**Table 3-1: Audit Process Targets**

| ID | Audit Process Class (X) |
| :--- | :--- |
| AUD-PROC-001 | QuarterlyAccessControlAudit |
| AUD-PROC-002 | AnnualDataRetentionReview |

| AUD-PROC-004 | NetworkTrafficForensicAudit |

*Table 3-1 embodies the axiom `audit_targets_data_artifact`. The `id` represents the unique instance of the audit process.
