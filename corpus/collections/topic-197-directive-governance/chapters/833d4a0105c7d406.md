# Chapter 4: Formalization of Compliance Observations and Metric Aggregation

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to capture, categorize, and analyze compliance-related data within a secure governance framework. It establishes the axiomatic foundation for transforming raw audit observations into structured Information Content Entities (ICE), ensuring that descriptive claims, regulatory directives, and quantitative measurements are interoperable across disparate compliance domains. The following sections provide a rigorous definition of five core concepts—Outlier Claims, PCI DSS Requirements, Attribute Sets, Measurements, and Aggregations—mapping them to their corresponding relational schemas. This methodology is intended for use by compliance officers, data architects, and systems auditors who require a deterministic, evidence-anchored approach to regulatory reporting and risk management.

---

## 4.2 Outlier Claim Basic

### 4.2.1 Conceptual Definition

In the context of formal audit methodologies, an **Outlier Claim** constitutes the primary unit of descriptive observation. It is defined axiomatically as a subclass of the `cco:DescriptiveICE` (Descriptive Information Content Entity). Unlike prescriptive directives, which mandate behavior, a descriptive claim serves to articulate the state of a specific artifact, process, or configuration as it exists within the observed environment. The identification of an "outlier" implies a deviation from a defined baseline, control point, or expected configuration parameter. This deviation must be documented as a discrete entity to facilitate traceability and remediation workflows.

The ontological assertion that an Outlier Claim is a `DescriptiveICE` ensures that the entity is informational rather than physical. It exists as a datum within the audit record, referencing a real-world state but remaining distinct from it. This distinction is critical for maintaining the integrity of the audit trail; the claim is the *record* of the observation, not the observation itself.

### 4.2.2 Relational Implementation

The persistence of an Outlier Claim is managed through the basic relational schema `t_outlier_claim_basic`. This table serves as the repository for the classification of the observed anomaly. The structure is designed to capture the essential nature of the claim without yet associating it with specific regulatory controls or detailed attribute sets.

The primary key (`id`) ensures that each descriptive claim is treated as a unique, immutable record within the system. The column `x` represents the specific class of the outlier, categorizing the nature of the deviation (e.g., a cryptographic failure, an unauthorized access attempt, or a configuration drift).

**Table 4.1: Basic Outlier Claim Registry**

| id | x |
| :--- | :--- |
| `oc_001` | `UnencryptedTransmissionEvent` |
| `oc_002` | `DefaultCredentialPresence` |
| `oc_003` | `InsecureProtocolUsage` |

*Table 4.1 illustrates the instantiation of the `t_outlier_claim_basic` schema. Each row represents a distinct descriptive information content entity (`x`) identified by a unique audit identifier (`id`). These entries form the evidentiary basis for subsequent regulatory mapping.*

## 4.3 PCI DSS Requirement Mapping

### 4.3.1 Conceptual Definition

While an outlier claim describes *what* has occurred, the **PCI DSS Requirement** mapping establishes *why* it matters within the context of the Payment Card Industry Data Security Standard (PCI DSS). Formally, this concept is defined as a subclass of `cco:DirectiveICE` that maintains a specific object property (`sdg:pciDssRequirement`) linking the directive to a descriptive claim.

This relationship is foundational to compliance auditing. It transforms a neutral technical observation into a regulated finding. By asserting that a Directive (the requirement) necessitates or validates a specific Claim (the observation), the ontology enforces a strict dependency structure. A requirement cannot be fully assessed without the existence of the descriptive claim it governs. This axiom supports the generation of findings reports by linking the "should" (the directive) with the "is" (the outlier claim).

### 4.3.2 Relational Implementation

The schema `t_pci_dss_requirement` operationalizes this linkage. It is imperative to note the referential integrity enforced by this structure: the column `y` is a foreign key that references the `id` from the `t_outlier_claim_basic` table. This constraint ensures that no PCI DSS requirement entry can exist without a corresponding, pre-existing descriptive claim. This reflects the logical flow of an audit: one observes the state (Claim) and then applies the standard (Requirement).

**Table 4.2: PCI DSS Requirement to Claim Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `req_101` | `Requirement_2_2_3` | `oc_001` |
| `req_102` | `Requirement_2_2_4` | `oc_002` |
| `req_103` | `Requirement_4_1` | `oc_003` |
| `req_104` | `Requirement_10_2_3` | `oc_004` |
| `req_105` | `Requirement_4_1_1` | `oc_005` |

*Table 4.2 demonstrates the `t_pci_dss_requirement` schema. Column `x` denotes the specific PCI DSS directive class (e.g., Requirement 2.2.3 regarding encryption), while column `y` validates the directive against a specific outlier claim ID from Table 4.1. This mapping allows auditors to query all requirements associated with a specific technical anomaly.*

## 4.4 Outlier Claim with Attribute Sets

### 4.4.1 Conceptual Definition

To transition from a high-level observation to an actionable audit finding, the system must support granular detail. The **Outlier Claim with Attribute Sets** extends the basic descriptive claim by incorporating the axiom `sdg:hasAttributeSet min 1`. This asserts that the claim is not merely a standalone label but a complex entity possessing one or more defined attributes.

In practice, these attributes represent the metadata necessary for remediation: timestamps, severity scores, host IP addresses, or user identifiers. The ontology dictates that these attribute sets are not loose data points but are structurally linked to the regulatory requirement identified in the previous step. This creates a chain of evidence: the Claim describes the event, the Requirement categorizes the compliance violation, and the Attribute Set provides the forensic details required to fix it.

### 4.4.2 Relational Implementation

The `t_outlier_claim_min_one_attribute` schema introduces a higher level of complexity. It enforces a relationship where the attribute set (`y`) must reference a valid PCI DSS requirement entry (`t_pci_dss_requirement`). This structure implies that the attributes are "about" the requirement in the context of the specific claim. It ensures that the detailed data captured during the audit is directly relevant to the specific compliance control being evaluated.

**Table 4.3: Outlier Claims with Attribute Context**

| id | x | y |
| :--- | :--- | :--- |
| `att_001` | `CipherSuiteDetails` | `req_101` |
| `att_002` | `AdminUserContext` | `req_102` |
| `att_003` | `TLSHandshakeLog` | `req_103` |
| `att_004` | `DatabaseAuditTrail` | `req_104` |
| `att_005` | `CertificateMetadata` | `req_105` |

*Table 4.3 represents the `t_outlier_claim_min_one_attribute` schema. The column `x` defines the class of the attribute set (e.g., `CipherSuiteDetails`), while `y` links this detailed data to the specific requirement ID (`req_101`) defined in Table 4.2. This structure ensures that every granular data point is anchored to a governing compliance directive.*

## 4.5 Measurement Basic

### 4.5.1 Conceptual Definition

While claims and directives are largely qualitative or categorical, **Measurement** introduces quantitative rigor into the governance framework. A Measurement is axiomatically defined as a `cco:DescriptiveICE` that represents a numerical value assigned to an observable property. In the context of compliance, measurements are the raw metrics—such as the number of failed login attempts, the duration of an outage, or the percentage of encrypted traffic—that serve as the basis for statistical analysis.

Measurements differ from outlier claims in that they do not inherently imply a pass/fail status on their own; they provide the scalar data against which thresholds (defined in requirements) are compared. The formalization of measurements as distinct entities allows for the separation of data collection (measurement) from data interpretation (claim generation).

### 4.5.2 Relational Implementation

The `t_measurement_basic` table provides a simplified schema for capturing these quantitative entities. Like the basic claim table, it relies on an `id` for uniqueness and a class descriptor `x`. However, in a full implementation, this table would typically be extended with data properties to store the actual numerical values and units of measure. For the purposes of this ontological mapping, we focus on the classification of the measurement type.

**Table 4.4: Measurement Entity Registry**

| id | x |
| :--- | :--- |
| `meas_001` | `PacketLossPercentage` |
| `meas_002` | `TransactionLatencyMs` |
| `meas_003` | `FailedAuthenticationCount` |
| `meas_004` | `StorageUtilizationRatio` |
| `meas_005` | `PatchComplianceRate` |

*Table 4.4 catalogs the `t_measurement_basic` entities. Each entry (`x`) represents a specific class of quantitative metric. These measurements form the empirical foundation upon which descriptive claims (e.g., "High Latency Detected") are subsequently constructed.*

## 4.6 Aggregation Basic

### 4.6.1 Conceptual Definition

The final concept in this chapter is **Aggregation**. An Aggregation is a `cco:DescriptiveICE` that synthesizes multiple measurements or lower-level claims into a composite score or summary statistic. In governance reporting, aggregations are essential for executive dashboards and risk heatmaps. They answer questions such as "What is the overall security posture of the sector?" or "What is the total risk exposure?"

Axiomatically, the aggregation is treated as a distinct information entity to preserve the provenance of the data. The aggregation entity exists separately from the raw measurements it summarizes, allowing the system to audit how the summary was calculated (e.g., weighted average, maximum value, sum). This abstraction layer is critical for high-level reporting, where the volume of raw data must be condensed into actionable intelligence.

### 4.6.2 Relational Implementation

The `t_aggregation_basic` schema mirrors the structure of the basic measurement and claim tables, emphasizing the classification of the aggregation logic. By storing the aggregation as a specific class (`x`), the framework supports various types of summarization logic—temporal aggregations (e.g., daily averages), spatial aggregations (e.g., per-region totals), or categorical aggregations (e.g., per-control group scores).
