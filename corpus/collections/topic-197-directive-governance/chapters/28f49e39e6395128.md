# Chapter 4: Ontological Structures in Compliance Auditing

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to model compliance artifacts within the Payment Card Industry Data Security Standard (PCI DSS) framework. The content herein defines the necessary Information Content Entities (ICEs) utilized to capture descriptive claims, regulatory directives, and measurement data. It establishes the axiomatic relationships between outlier claims, specific requirement sets, and their subsequent aggregation into audit-ready evidence. The definitions provided are grounded in the Common Core Ontologies (CCO) and are intended to facilitate the rigorous mapping of governance frameworks to machine-readable audit trails.

## 4.2 The Outlier Claim as a Descriptive Entity

The foundational unit of audit evidence is the Outlier Claim, formally defined as a subclass of the Descriptive Information Content Entity (DescriptiveICE). In the context of security governance, an outlier claim represents a declarative statement regarding a specific deviation, anomaly, or exception observed within the controlled environment. Unlike normative claims, which describe expected states, outlier claims document the variance between observed system behaviors and the established baseline.

The ontological definition asserts that the entity {X} is a descriptive information content entity. This classification is critical for audit logging, as it distinguishes subjective observations from objective measurements. The primary key for this entity is its unique identifier, which serves as the anchor for downstream compliance mapping.

**Table 4.1: Basic Outlier Claim Registry**
The following table enumerates distinct outlier claims identified during the preliminary audit phase. Each entry represents a unique class of deviation ({X}) recorded in the governance ledger.

| id | x |
| :--- | :--- |
| oc_001 | UnauthorizedAccessAttempt |
| oc_002 | UnencryptedDataTransmission |
| oc_003 | PrivilegeEscalationEvent |
| oc_004 | ConfigurationDrift |

The registry in Table 4.1 demonstrates the taxonomic breadth of the `t_outlier_claim_basic` structure. The column `x` denotes the specific class of the outlier claim. For instance, `oc_002` represents the class of claims concerning `UnencryptedDataTransmission`. This classification allows auditors to correlate specific log entries with broader categories of non-compliance without necessitating immediate reference to the governing directive.

## 4.3 PCI DSS Requirements as Directives

To operationalize the detection of outliers, audit frameworks must map descriptive entities to prescriptive directives. The PCI DSS Requirement entity functions as a Directive Information Content Entity (DirectiveICE). This axiom asserts that the entity {X} is a directive that specifically references a PCI DSS requirement {Y}. The relationship is hierarchical; the directive ({X}) encapsulates the regulatory mandate, while the slot {Y} references the specific descriptive claim ({X} from the previous section) that the directive aims to govern or detect.

In relational terms, the requirement table is dependent on the outlier claim registry. The foreign key constraint ensures that every regulatory directive is anchored to a specific, defined class of outlier behavior. This structure enforces data integrity by preventing the creation of orphaned compliance requirements that do not correspond to observable phenomena.

**Table 4.2: PCI DSS Requirement Mapping**
The table below illustrates the mapping of specific regulatory directives ({X}) to the outlier claims ({Y}) they are designed to address. The `y` column functions as a foreign key linking the directive to the foundational claim defined in Table 4.1.

| id | x | y |
| :--- | :--- | :--- |
| pci_req_10_2_1 | AuditTrailDirective | oc_001 |
| pci_req_04_1 | EncryptionTransmissionDirective | oc_002 |
| pci_req_08_2_1 | PrivilegeManagementDirective | oc_003 |
| pci_req_02_2 | ConfigurationBaselineDirective | oc_004 |
| pci_req_05_1_2 | AntiMalwareDirective | oc_005 |

As evidenced in Table 4.2, the directive `pci_req_04_1` (EncryptionTransmissionDirective) is directly linked to the outlier claim `oc_002` (UnencryptedDataTransmission). This linkage signifies that the directive exists specifically to prescribe controls against the described outlier. The schema ensures that for every defined risk, there exists a corresponding governance artifact.

## 4.4 Attributed Outlier Claims

While basic outlier claims provide a classification, they lack the granularity required for forensic analysis. The Attributed Outlier Claim extends the basic concept by mandating the presence of an attribute set. Ontologically, this is expressed as {X} being a descriptive information content entity that possesses a minimum of one attribute set {Y}.

In this schema, the attribute set ({Y}) is derived from the PCI DSS Requirement directives. This implies that the specific, attributed claim ({X}) is an instantiation or a specific occurrence that is substantively characterized by its adherence to or violation of a specific requirement directive. The foreign key constraint linking the attribute set to the requirement table ensures that the attributes defining the claim are themselves validated against the regulatory standard.

**Table 4.3: Attributed Claim Instances**
The following table details specific instances of outlier claims ({X}) that have been enriched with attribute sets derived from PCI DSS directives ({Y}). This structure allows the auditor to query not just for an anomaly, but for an anomaly defined by specific compliance parameters.

| id | x | y |
| :--- | :--- | :--- |
| attr_claim_01 | TimestampedFailedLogon | pci_req_10_2_1 |
| attr_claim_02 | CleartextPacketCapture | pci_req_04_1 |
| attr_claim_03 | RootShellSession | pci_req_08_2_1 |
| attr_claim_04 | UnauthorizedServiceModification | pci_req_02_2 |
| attr_claim_05 | HeuristicTrojanDetection | pci_req_05_1_2 |

In Table 4.3, the row `attr_claim_02` represents a specific claim, `CleartextPacketCapture`. This claim is defined by the attribute set found in `pci_req_04_1`. This relationship allows the audit system to filter for `UnencryptedDataTransmission` (the class) specifically where it involves `CleartextPacketCapture` (the attributed instance) governed by the `EncryptionTransmissionDirective`.

## 4.5 Measurement Entities

Compliance auditing requires the quantification of descriptive claims. The Measurement entity represents a specific DescriptiveICE intended to capture the magnitude, frequency, or duration of an observed event. Unlike the claims defined in previous sections, which are categorical, measurements are scalar or vector values derived from system telemetry.

The ontological structure for measurement is straightforward: {X} is a descriptive information content entity. However, in practice, these entities serve as the value nodes for the attributed claims. A measurement provides the evidence that substantiates the existence of the outlier claim. For example, the claim `UnauthorizedAccessAttempt` is substantiated by a measurement of `3` attempts within `60` seconds.

**Table 4.4: Measurement Registry**
The table below catalogs the distinct measurement classes utilized within the audit framework. Each entry ({X}) represents a specific type of data value collected from the environment.

| id | x |
| :--- | :--- |
| meas_001 | FailedLoginCount |
| meas_002 | PacketSizeBytes |
| meas_003 | SessionDurationSeconds |
| meas_004 | ConfigurationHashValue |
| meas_005 | ThreatConfidenceScore |

The registry in Table 4.4 provides the data types for the evidence layer. `meas_001` (FailedLoginCount) provides the quantitative basis for `attr_claim_01` (TimestampedFailedLogon). By standardizing these measurement classes, the audit framework ensures heterogenous data sources can be normalized into a coherent compliance report.

## 4.6 Aggregation Entities

Finally, to support high-level reporting and trend analysis, individual measurements must be synthesized. The Aggregation entity functions as a DescriptiveICE that represents a mathematical or logical combination of multiple measurement instances. Aggregations are essential for determining compliance status over time (e.g., "average failed login attempts per day") or across a fleet of assets.

The axiom defines {X} simply as a descriptive information content entity, but its utility is defined by its role in summarizing the measurement data. Aggregations reduce the noise of high-frequency telemetry into manageable governance metrics.

**Table 4.5: Aggregation Schema**
The following table defines the aggregation logic applied to measurement data to produce compliance metrics.

| id | x |
| :--- | :--- |
| agg_001 | DailyAverageFailedLogins |
| agg_002 | TotalUnencryptedBytes |
| agg_003 | MaxSessionDuration |
| agg_004 | BaselineDeviationIndex |
| agg_005 | MeanThreatConfidence |

Table 4.5 illustrates how raw telemetry is elevated to business intelligence. `agg_001` (DailyAverageFailedLogins) utilizes `meas_001` (FailedLoginCount) to provide a normalized view of access security. This aggregation is the final output typically presented to the audit committee, demonstrating the organization's control effectiveness relative to the PCI DSS requirements outlined in Section 4.3.
