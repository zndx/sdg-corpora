# Chapter 4: Taxonomy of Audit Artifacts and Compliance Metrics

## 4.1 Scope and Preamble

This chapter establishes the formal taxonomy for information content entities utilized within the governance framework, specifically targeting the classification of audit artifacts, regulatory directives, and performance metrics. The definitions provided herein are grounded in the Ontology for Governance and Compliance (OGC) and serve to standardize the semantic representation of data objects across the enterprise architecture. The primary objective is to ensure that all descriptive entities, whether they represent outlier claims, specific regulatory requirements, or aggregated measurements, are structured with sufficient rigor to support automated reasoning and manual audit verification. All entities referenced in the subsequent sections are to be treated as immutable definitions unless a formal change management process is initiated pursuant to Section 9.2 of the Governance Handbook.

## 4.2 Descriptive Information Content Entities (Outlier Claims)

### 4.2.1 Definition and Axiomatic Basis

The foundational unit of audit observation is the Descriptive Information Content Entity (DescriptiveICE). Within the context of anomaly detection and security monitoring, this entity is instantiated as an Outlier Claim. Axiomatically, an Outlier Claim is defined as a subclass of DescriptiveICE. It represents a declarative statement regarding the status of a system component or data point that deviates from the established baseline or expected behavior.

The formulation of an Outlier Claim does not inherently imply a judgment of fault or malicious intent; rather, it denotes a statistical or logical deviation that requires further investigation. The ontology captures this via the `outlier_claim_basic` template, which asserts that the entity {X} is a descriptive information content entity. This classification allows the audit engine to segregate raw descriptive data from prescriptive directives.

### 4.2.2 Implementation and Instances

In practice, the identification of an Outlier Claim is the first step in the incident response workflow. The following table delineates specific instances of Outlier Claims that have been codified within the system registry. These instances represent the canonical types of deviations that the monitoring infrastructure is configured to detect.

The persistence of these records in the central registry ensures that all downstream reporting mechanisms utilize a standardized nomenclature, thereby reducing ambiguity during forensic analysis.

## 4.3 Regulatory Directives and PCI DSS Requirements

### 4.3.1 DirectiveICE and Requirement Mapping

While descriptive entities define *what* has occurred, Directive Information Content Entities (DirectiveICE) define *what must be done* or *how* compliance is measured. A critical relationship exists between the organization's internal governance directives and external regulatory frameworks, specifically the Payment Card Industry Data Security Standard (PCI DSS).

The axiom `pci_dss_requirement` posits that a DirectiveICE {X} is something that satisfies a PCI DSS requirement {Y}. Structurally, this implies that every internal directive designed to enforce compliance must map directly to a specific descriptive claim or requirement defined in the ontology. The relational integrity of this mapping is enforced by a foreign key constraint, ensuring that a PCI DSS requirement cannot exist in isolation from a recognized Outlier Claim or basic descriptive entity.

### 4.3.2 Compliance Mapping Table

The following table illustrates the instantiation of PCI DSS requirements. Each row represents a specific directive class {X} that is linked to a foundational Outlier Claim {Y}. This linkage demonstrates how a high-level regulatory mandate (e.g., regarding access control) is operationalized through the detection of specific descriptive anomalies (e.g., unusual geolocation logins).

**Table 4.2: PCI DSS Requirement Directives (t_pci_dss_requirement)**

| id | x | y |
|---|---|---|
| pcidss_01 | AccessControlMechanism | oc_001 |
| pcidss_02 | DataLeakagePrevention | oc_002 |
| pcidss_03 | CryptographyProtocol | oc_003 |
| pcidss_04 | NetworkAccessControl | oc_004 |
| pcidss_05 | TransmissionMediaSecurity | oc_005 |

*Table 4.2 Notes:*
*   **Primary Key:** `id`
*   **Foreign Key:** `y` references `t_outlier_claim_basic(id)`.
*   **Column `x`:** The Class of the DirectiveICE.
*   **Column `y`:** The ID of the basic Outlier Claim this directive addresses.

For example, the directive `pcidss_01` (AccessControlMechanism) is formally linked to the outlier claim `oc_001` (UnusualGeolocationLogin). This relationship asserts that the Access Control Mechanism is specifically designed to mitigate or monitor the anomaly described in `oc_001`.

## 4.4 Attribute Sets in Complex Claims

### 4.4.1 Granularity and the `hasAttributeSet` Property

As audit artifacts increase in complexity, basic descriptive entities often prove insufficient to capture the nuance of the observed event. To address this, the ontology introduces the concept of the Attribute Set. The axiom `outlier_claim_min_one_attribute` defines a more complex DescriptiveICE {X} that possesses a minimum of one attribute set {Y}.

This structure allows for the decomposition of a complex claim into its constituent properties. For instance, a complex fraud pattern may not be defined by a single metric but by a combination of a directive and specific technical attributes. The relational schema enforces that the attribute set {Y} must reference a valid PCI DSS Requirement directive, thereby grounding the complex claim's attributes in established compliance controls.

### 4.4.2 Complex Claim Registry

The table below documents complex outlier claims that utilize attribute sets. These entries represent advanced detection logic where a single observation is insufficient, and a relationship to a specific directive is required to fully define the claim context.

**Table 4.3: Complex Outlier Claims with Attribute Sets (t_outlier_claim_min_one_attribute)**

| id | x | y |
|---|---|---|
| oc_attr_01 | CrossBorderAnomaly | pcidss_01 |
| oc_attr_02 | BulkTransferAlert | pcidss_02 |
| oc_attr_03 | SelfSignedCertWarning | pcidss_03 |
| oc_attr_04 | UnauthorizedPortBinding | pcidss_04 |
| oc_attr_05 | InsecureChannelTransmission | pcidss_05 |

*Table 4.3 Notes:*
*   **Primary Key:** `id`
*   **Foreign Key:** `y` references `t_pci_dss_requirement(id)`.
*   **Column `x`:** The Class of the complex Outlier Claim.
*   **Column `y`:** The ID of the PCI DSS Requirement directive serving as the attribute set.

In this configuration, the complex claim `oc_attr_01` (CrossBorderAnomaly) is defined by its association with the `pcidss_01` directive. This semantic linkage ensures that when the anomaly is detected, the system can immediately reference the governing AccessControlMechanism to determine the appropriate remediation workflow.

## 4.5 Measurement Artifacts

### 4.5.1 Basic Measurement Definitions

Quantitative analysis forms the evidentiary basis of all audit reporting. A Measurement is a specific type of DescriptiveICE that captures a numerical value corresponding to a physical or virtual property of the system. Unlike outlier claims, which may be categorical or logical, measurements are inherently quantitative.

The axiom `measurement_basic` classifies these entities simply as DescriptiveICEs. This simplicity is intentional; the complexity of a measurement lies in its unit of measure and its data type, not in its taxonomic classification. Measurements serve as the raw inputs for the aggregation processes described in Section 4.6.

### 4.5.2 Standard Performance Metrics

The following table catalogs the standard measurement entities utilized within the governance framework. These definitions are consistent across all reporting modules to ensure uniformity in data collection.

**Table 4.4: Basic Measurement Entities (t_measurement_basic)**

| id | x |
|---|---|
| meas_01 | LatencyMilliseconds |
| meas_02 | PacketLossPercentage |
| meas_03 | ThroughputMbps |
| meas_04 | CpuUtilizationPercent |
| meas_05 | MemoryFootprintGB |

*Table 4.4 Notes:*
*   **Primary Key:** `id`
*   **Column `x`:** The Class designation of the Measurement.

Each entry, such as `meas_01` (LatencyMilliseconds), provides a standardized format for recording performance data. When an audit log records a latency value, it is formally asserting an instance of the `LatencyMilliseconds` class.

## 4.6 Aggregation Protocols

### 4.6.1 Aggregation Logic

While individual measurements provide point-in-time data, Aggregations facilitate trend analysis and summary reporting. An Aggregation is a DescriptiveICE that represents the mathematical combination of multiple measurements (e.g., sum, average, maximum) over a specified time interval.

The axiom `aggregation_basic` defines these entities within the same semantic hierarchy as measurements and claims. This allows the reporting layer to treat a "Daily Average" with the same ontological rigor as a "Single Point Measurement." Aggregations are critical for high-level dashboards and executive summaries, where low-level granularity is abstracted into key performance indicators (KPIs).

### 4.6.2 Aggregation Registry

The table below defines the approved aggregation classes. These are the standard calculations performed during the ETL (Extract, Transform, Load) processes that populate the compliance data warehouse.

**Table 4.5: Basic Aggregation Entities (t_aggregation_basic)**

| id | x |
|---|---|
| agg_01 | DailyTransactionVolume |
| agg_02 | WeeklyFailedAuthCount |
| agg_03 | MonthlyStorageUtilization |
| agg_04 | QuarterlyIncidentSeverityIndex |
| agg_05 | AnnualComplianceScorePercentage |

*Table 4.5 Notes:*
*   **Primary Key:** `id`
*   **Column `x`:** The Class designation of the Aggregation.

For instance, `agg_02` (WeeklyFailedAuthCount) represents a distinct class of information content entity derived from summing individual failed authentication events over a 7-day period. By defining this as a formal class, the system can apply specific retention policies and access controls to this aggregated data distinct from the raw event logs.
