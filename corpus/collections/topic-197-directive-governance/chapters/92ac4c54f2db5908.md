# Chapter 4: Ontological Formalization of Compliance Anomalies and PCI DSS Governance

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required to map descriptive anomalies within information systems to specific regulatory directives, specifically those outlined in the Payment Card Industry Data Security Standard (PCI DSS). The objective is to provide a rigorous, evidence-anchored methodology for classifying information content entities (ICE) as they pertain to audit findings, outlier detection, and compliance measurement. By adhering to the axioms defined in the Common Core Ontologies (CCO) and extending them with specific domain constraints, this chapter ensures that governance frameworks can programmatically verify the structural integrity of compliance reports. The following sections delineate the hierarchical relationships between outlier claims, regulatory requirements, attribute sets, and measurement aggregations, providing a deterministic schema for high-fidelity audit documentation.

## 4.2 Descriptive Information Content Entities (Outlier Claims)

### 4.2.1 Formal Definition
In the context of semantic data modeling for compliance, a foundational entity is the Outlier Claim. Formally defined by the axiom `outlier_claim_basic`, this entity is a subclass of the `cco:DescriptiveICE`. A Descriptive Information Content Entity is defined as an entity that is about some other entity; in this specific application, the Outlier Claim serves as a propositional assertion regarding the deviation of a system state from an expected baseline. Unlike prescriptive directives, which dictate behavior, the Outlier Claim merely describes the existence of an anomaly, such as "Unauthorized Access Attempt" or "Unencrypted Data Transmission," without immediately assigning normative weight until mapped to a requirement.

### 4.2.2 Operational Context and Evidence
The identification of an Outlier Claim is the primary step in the audit lifecycle. It represents the raw signal extracted from log files, network traffic analysis, or access control mechanisms. For a claim to be valid within the ontology, it must be instantiated as a distinct class of observation. The following table illustrates the instantiation of basic outlier claims derived from a hypothetical network security audit. These rows represent the `x` slot (the Class) and a unique identifier `id` for the claim.

**Table 4-1: Basic Outlier Claim Manifestations**

| id | x |
| :--- | :--- |
| `OC-2023-001` | `UnencryptedTransmissionEvent` |
| `OC-2023-002` | `InvalidCertificateChain` |
| `OC-2023-003` | `Non-CompliantCipherSuite` |
| `OC-2023-004` | `RootLoginAttempt` |
| `OC-2023-005` | `StoredCredentialExposure` |

The entities listed in Table 4-1 function as the descriptive anchors for the compliance framework. Each `id` serves as the primary key for subsequent relational mappings, ensuring that every descriptive anomaly is traceable to a specific observation event. The classification of these entities as `cco:DescriptiveICE` allows them to be utilized as objects in further axiomatic relationships, specifically as the range for requirement mappings.

## 4.3 PCI DSS Requirements as Directives

### 4.3.1 Formal Definition
The second axiom, `pci_dss_requirement`, introduces a normative layer to the ontology. Here, we define a class `{X}` as a subclass of `cco:DirectiveICE`. A Directive Information Content Entity differs from a descriptive one in that it prescribes specific behaviors or states. Crucially, this axiom includes the object property `sdg:pciDssRequirement`, which asserts that the directive `{X}` has a requirement relationship with a specific descriptive entity `{Y}`. In this schema, `{Y}` must be an instance of the Outlier Claim defined in the previous section. This relationship formalizes the logic that a specific PCI DSS requirement exists to govern or prevent a specific class of outlier claims.

### 4.3.2 Mapping Directives to Anomalies
The structural integrity of a compliance report depends on the explicit linkage between a regulatory directive and the anomaly it addresses. The foreign key constraint in the relational schema enforces that a PCI DSS Requirement cannot exist in isolation within this context; it must reference a valid `Outlier Claim`. This ensures that governance is evidence-based and that every regulation is tied to a specific, observable risk vector. The following table demonstrates this mapping, where the `y` column references the `id` from the Outlier Claim table.

**Table 4-2: PCI DSS Requirement Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `REQ-PCI-4.1` | `Requirement4.1_Encryption` | `OC-2023-001` |
| `REQ-PCI-4.1` | `Requirement4.1_Encryption` | `OC-2023-003` |
| `REQ-PCI-8.3` | `Requirement8.3_SecureAuth` | `OC-2023-004` |
| `REQ-PCI-2.4` | `Requirement2.4_StrongCryptography` | `OC-2023-002` |
| `REQ-PCI-3.2` | `Requirement3.2_Remediation` | `OC-2023-005` |

In Table 4-2, the `x` column represents the specific PCI DSS directive class (e.g., `Requirement4.1_Encryption`). The `y` column establishes the foreign key relationship to the `t_outlier_claim_basic` table. For instance, `REQ-PCI-4.1` is linked to both `UnencryptedTransmissionEvent` and `Non-CompliantCipherSuite`, indicating that this single requirement governs multiple distinct classes of descriptive anomalies. This structure supports the complexity of real-world compliance environments where one directive may cover a broad set of potential outlier conditions.

## 4.4 Attribute Sets for Outlier Claims

### 4.4.1 Formal Definition
The axiom `outlier_claim_min_one_attribute` refines the descriptive entity by introducing the concept of an AttributeSet. This axiom asserts that a descriptive entity `{X}` (the Outlier Claim) possesses a minimum of one attribute `{Y}`. In the provided relational schema, this is implemented by linking an Attribute Set entity to a PCI DSS Requirement entity. This linkage implies that the specific attributes required to validate a claim are defined by the context of the requirement governing that claim. The `hasAttributeSet` property ensures that an outlier claim is not merely a label but a data-rich assertion containing specific parameters (e.g., IP addresses, timestamps, user IDs) necessary for audit verification.

### 4.4.2 Structural Decomposition
The enforcement of a "min 1" constraint guarantees that no outlier claim enters the compliance database without accompanying metadata. This is critical for audit trails; a claim of "Unauthorized Access" is useless without the attribute of "Source IP" or "Timestamp." The schema links these attributes to the Requirement ID, effectively creating a composite key where the validity of the attribute set is determined by the requirement it serves. The following table details the attribute sets associated with the requirements defined in the previous section.

| `ATTR-SET-003` | `AuthenticationContext` | `REQ-PCI-8.3` |
| `ATTR-SET-004` | `StorageAccessLogs` | `REQ-PCI-3.2` |

In Table 4-3, the `x` column defines the class of the attribute set (e.g., `NetworkFlowAttributes`), while the `y` column references the `id` from the `t_pci_dss_requirement` table. For example, `NetworkFlowAttributes` is linked to `REQ-PCI-4.1`, indicating that to verify compliance with Requirement 4.1 regarding encryption, the auditor must analyze the network flow attributes. This structure enforces a disciplined approach to data collection, ensuring that evidence gathering is strictly scoped to the requirements under review.

## 4.5 Measurement Basic Entities

### 4.5.1 Formal Definition
The `measurement_basic` axiom defines a class `{X}` that is also a subclass of `cco:DescriptiveICE`. While similar in ontological lineage to the Outlier Claim, the Measurement entity serves a distinct functional purpose. Whereas an Outlier Claim asserts the existence of a deviation, a Measurement entity quantifies a specific observable state or value. Measurements are the raw, quantitative data points—such as "Packet Size = 1500 bytes" or "Response Time = 200ms"—that populate the attribute sets described in the previous section. They provide the granular evidence required to substantiate the descriptive claims.

### 4.5.2 Quantitative Evidence Collection
In the execution of a technical audit, measurements are collected continuously via monitoring agents. The ontology treats these measurements as first-class information entities to ensure that every data point is auditable and traceable. The following table presents a set of measurement entities that would typically be extracted during a compliance assessment. These entities represent the `x` slot in the `measurement_basic` axiom.

**Table 4-4: Raw Measurement Entities**

| id | x |
| :--- | :--- |
| `MEAS-001` | `ObservedPacketSize_1500` |
| `MEAS-002` | `ObservedLatency_450ms` |
| `MEAS-003` | `TLS_Version_1.2` |
| `MEAS-004` | `LoginAttempts_Count_5` |
| `MEAS-005` | `FilePermission_644` |

The entities in Table 4-4 (`ObservedPacketSize_1500`, `TLS_Version_1.2`, etc.) represent the atomic units of data. By formalizing these as classes of `DescriptiveICE`, the framework allows for complex querying, such as "Retrieve all measurements associated with `NetworkFlowAttributes` where the value indicates non-compliance." This granular approach is essential for automated compliance tools that must parse vast quantities of log data to identify violations.

## 4.6 Aggregation Basic Entities

### 4.6.1 Formal Definition
The final concept, defined by the `aggregation_basic` axiom, also subclasses `cco:DescriptiveICE`. An Aggregation entity represents a summary or statistical synthesis of multiple measurement entities. While measurements provide raw data points, aggregations provide the high-level metrics necessary for executive reporting and trend analysis. Examples include "Average Latency," "Total Failed Login Count," or "Percentage of Unencrypted Traffic." The distinction between a measurement and an aggregation is critical for governance; while measurements identify specific instances of non-compliance, aggregations identify systemic risk patterns over time.

### 4.6.2 Systemic Risk Analysis
Aggregations are used by auditors and compliance officers to determine the pervasiveness of a control failure. A single measurement of `UnencryptedTransmissionEvent` might be an isolated error, but an aggregation showing `UnencryptedTrafficPercentage > 5%` indicates a systemic control failure requiring remediation. The table below lists aggregation entities that might be generated from the measurements in the previous section.

**Table 4-5: Aggregated Metric Entities**

| id | x |
| :--- | :--- |
| `AGG-001` | `DailyAverageLatency` |
| `AGG-002` | `WeeklyFailedLoginTotal` |
| `AGG-003` | `MonthlyUnencryptedTrafficRatio` |
| `AGG-004` | `QuarterlyIncidentCount` |
| `AGG-005` | `AnnualMeanTimeToRemediate` |

Table 4-5 encapsulates the `x` slot for the `aggregation_basic` axiom. These entities, such as `WeeklyFailedLoginTotal` or `MonthlyUnencryptedTrafficRatio`, are derived from the processing of raw measurements. In a fully implemented semantic database, these aggregation entities would possess properties linking them back to the source measurements, allowing for drill-down analysis from the executive summary level to the specific log event level. This hierarchical structure—from outlier claims to requirements, to attributes, to measurements, and finally to aggregations—provides a comprehensive, vertically integrated view of the compliance posture.
