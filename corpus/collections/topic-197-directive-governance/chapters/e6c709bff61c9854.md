# Chapter 4: Formal Ontology of Compliance Artifacts and Audit Evidence

## 4.1 Scope and Preamble

This chapter establishes the ontological framework necessary for the rigorous classification and management of compliance artifacts within an enterprise governance environment. The primary objective is to define a structured schema for mapping descriptive information content entities (ICE) to regulatory requirements, specifically within the context of the Payment Card Industry Data Security Standard (PCI DSS). The definitions provided herein utilize the Manchester syntax for Web Ontology Language (OWL) axioms to ensure logical consistency and interoperability across audit databases. By anchoring these definitions to a deterministic relational schema, auditors and compliance officers may trace specific assertions from high-level directives down to granular measurement data, ensuring that all evidence is both verifiable and immutable.

## 4.2 Outlier Claim Basic

### 4.2.1 Definition and Axiomatic Structure

The foundational unit of audit evidence is the Outlier Claim Basic. Formally, this concept is defined as a subclass of the `cco:DescriptiveICE` (Descriptive Information Content Entity). In the context of an audit, an outlier claim represents a singular, declarative statement that deviates from expected baselines or standard operating procedures. It is atomic in nature; it does not possess internal attributes within this specific axiom template but serves as the referent for more complex structures.

The axiom for the Outlier Claim Basic is expressed as follows:

**Manchester Syntax:**
```text
Class: {X:Class} SubClassOf: cco:DescriptiveICE
```

**Verbalization:**
{X} is a descriptive information content entity.

This axiom asserts that any entity classified as an Outlier Claim is fundamentally a descriptive artifact. It is a container for information that describes a state of non-compliance or an anomaly within the system. The relational projection of this axiom creates a primary repository for these claims, indexed by a unique identifier.

### 4.2.2 Relational Schema and Instantiation

The corresponding relational schema, `t_outlier_claim_basic`, is designed to store these entities with a unique primary key. This table serves as the root for several foreign key relationships utilized in subsequent sections.

**Table 4.1: Outlier Claim Basic Instances**

| :--- | :--- |

## 4.3 PCI DSS Requirement

### 4.3.1 Definition and Axiomatic Structure

While an outlier claim identifies a specific event or state, it must be mapped to a governing directive to possess regulatory weight. The PCI DSS Requirement axiom defines a class that serves as a directive (`cco:DirectiveICE`) and mandates a specific relationship to a requirement object. This relationship is existential; the directive must satisfy at least one PCI DSS requirement.

The axiom is defined as:

**Manchester Syntax:**
```text
Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}
```

**Verbalization:**
{X} is something that pci dss requirement {Y}.

In this structure, {X} represents the directive or the specific control implementation being audited, while {Y} represents the textual or codified requirement from the PCI DSS framework. Crucially, the schema enforces that the requirement {Y} must exist as a defined entity within the `t_outlier_claim_basic` table. This creates a rigid linkage where a directive cannot exist without a valid, traceable requirement definition.

### 4.3.2 Relational Schema and Dependencies

The `t_pci_dss_requirement` table extends the ontology by linking directives to the basic claims established in Section 4.2. The foreign key constraint ensures that every requirement referenced by a directive corresponds to a valid entry in the `t_outlier_claim_basic` table.

**Table 4.2: PCI DSS Requirement Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `PCI-REQ-001` | Network Security Control Implementation | `OCB-2023-002` |
| `PCI-REQ-002` | Cardholder Data Encryption Policy | `OCB-2023-001` |
| `PCI-REQ-003` | System Component Hardening Directive | `OCB-2023-003` |
| `PCI-REQ-004` | Malware Protection Mechanism | `OCB-2023-004` |

*Table 4.2 details the `t_pci_dss_requirement` schema. Column `x` denotes the Directive class (e.g., the specific policy or control), while column `y` is a foreign key referencing the `id` from `t_outlier_claim_basic`. For instance, the directive "Network Security Control Implementation" (x) is specifically linked to the "Wireless Access Point Without Segregation" claim (y), indicating that this directive addresses the specific outlier defined in the previous table.*

## 4.4 Outlier Claim Min One Attribute

### 4.4.1 Definition and Axiomatic Structure

Complex audit findings often require more than a simple textual description; they possess attributes that provide context, severity, or technical specifics. The Outlier Claim Min One Attribute axiom defines a descriptive information content entity that includes a mandatory attribute set. This axiom enforces cardinality constraints, ensuring that the claim is not atomic but is instead defined by its association with other entities.

The axiom is expressed as:

**Manchester Syntax:**
```text
Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}
```

**Verbalization:**
{X} is a descriptive information content entity.

In this model, the attribute set {Y} is not merely a data property but a reference to another class. Specifically, the schema defines {Y} as a reference to a PCI DSS Requirement. This implies that the defining characteristic of these complex outlier claims is their adherence to or violation of specific regulatory directives. This structure allows for the construction of a "violation matrix" where specific audit events (X) are directly characterized by the requirements they impact (Y).

### 4.4.2 Relational Schema and Linkage

The `t_outlier_claim_min_one_attribute` table implements this relationship. The foreign key constraint links the attribute `y` to the `t_pci_dss_requirement` table, thereby creating a three-tier hierarchy: the Basic Claim (the raw observation), the PCI Requirement (the regulatory definition), and the Attributed Claim (the contextualized audit event).

**Table 4.3: Outlier Claims with Mandatory Attributes**

| id | x | y |
| :--- | :--- | :--- |
| `OCC-ATTR-101` | Critical Segmentation Failure Event | `PCI-REQ-001` |
| `OCC-ATTR-102` | High-Risk Data Exfiltration Attempt | `PCI-REQ-002` |
| `OCC-ATTR-103` | Automated Hardening Validation Failure | `PCI-REQ-003` |
| `OCC-ATTR-104` | Endpoint Protection Service Stop | `PCI-REQ-004` |
| `OCC-ATTR-105` | Quarterly Review Non-Compliance | `PCI-REQ-001` |

*Table 4.3 presents the `t_outlier_claim_min_one_attribute` data. Column `x` identifies the complex audit event, while column `y` references the ID of the PCI DSS Requirement from Table 4.2. For example, the "Critical Segmentation Failure Event" is characterized by the "Network Security Control Implementation" requirement. This structure ensures that every complex claim is anchored to a specific directive requirement.*

## 4.5 Measurement Basic

### 4.5.1 Definition and Axiomatic Structure

To support the descriptive claims with quantitative evidence, the ontology introduces the Measurement Basic concept. This class represents the raw numerical or quantitative data collected during an audit. Like the outlier claim, it is a subclass of `cco:DescriptiveICE`, but its semantic payload is strictly quantitative rather than qualitative or declarative.

The axiom is defined as:

**Manchester Syntax:**
```text
Class: {X:Class} SubClassOf: cco:DescriptiveICE
```

**Verbalization:**
{X} is a descriptive information content entity.

Measurements serve as the "evidence layer" for the claims defined in previous sections. While a claim asserts that a "Wireless Access Point Without Segregation" exists, the measurement provides the specific signal strength, protocol version, or traffic count associated with that access point.

### 4.5.2 Relational Schema and Data

The `t_measurement_basic` table is structurally simple, consisting of an identifier and the measurement class. This simplicity allows for flexibility in the types of data stored, ranging from integer counts to floating-point telemetry values, provided they are serialized as descriptive entities.

**Table 4.4: Basic Measurement Instances**

*Table 4.4 provides examples of the `t_measurement_basic` table. The `x` column contains the serialized measurement data. These entries would typically be linked to the outlier claims via application-level logic, providing the empirical basis for the descriptive assertions made in Sections 4.2 and 4.4.*

## 4.6 Aggregation Basic

### 4.6.1 Definition and Axiomatic Structure

Finally, the ontology must support high-level reporting and trend analysis. The Aggregation Basic axiom defines a class for summarized data points derived from multiple measurements or claims. This is essential for executive reporting and risk scoring, where individual events must be rolled up into composite metrics.

The axiom is defined as:

**Manchester Syntax:**
```text
Class: {X:Class} SubClassOf: cco:DescriptiveICE
```

**Verbalization:**
{X} is a descriptive information content entity.

An aggregation is a descriptive entity that summarizes other information entities. It does not contain raw data but rather a statistical or logical synthesis of data, such as averages, maximums, or compliance percentages.

### 4.6.2 Relational Schema and Reporting

The `t_aggregation_basic` table stores these synthesized entities. Like the measurement table, it utilizes a simple schema to maximize flexibility in the types of aggregations performed.
