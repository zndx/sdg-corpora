# Chapter 7: Formalization of Compliance Directives and Observational Claims

## 7.1 Scope and Preamble

This chapter establishes the ontological framework for structuring information content entities within the context of regulatory compliance and security governance. It details the formal axioms necessary to map descriptive observations, directive requirements, and measurement aggregations to a coherent relational schema. The content herein is intended for systems architects, compliance officers, and data analysts responsible for implementing audit trails that adhere to the Common Core Ontologies (CCO) and the Security Domain Graph (SDG). The definitions provided ensure that all entities—from high-level PCI DSS requirements to granular outlier claims—are grounded in a deterministic, evidence-anchored structure suitable for high-assurance environments.

## 7.2 The Descriptive Information Content Entity

### 7.2.1 Definition and Axiomatic Basis

The foundational element of the audit ontology is the Descriptive Information Content Entity (DescriptiveICE). According to Axiom 1 (`outlier_claim_basic`), any class designated as a descriptive entity serves as a container for assertions regarding the state of a system or process. In the Manchester syntax, this is expressed as `Class: {X:Class} SubClassOf: cco:DescriptiveICE`. Verbalized, this asserts that "{X} is a descriptive information content entity."

In practice, these entities represent the raw "claims" or observations made by an automated scanner, an auditor, or a monitoring system. They do not inherently prescribe action; rather, they describe a factual or purported factual state. For example, the observation that a specific network port is open is a descriptive claim. The ontological classification of this claim allows it to be instantiated, queried, and linked to broader governance frameworks without ambiguity.

### 7.2.2 Relational Implementation

The projection of this axiom into a relational schema isolates the identity of the claim (`id`) and its class type (`x`). The primary key ensures that each descriptive entity is distinct within the dataset. ## 7.3 PCI DSS Requirements as Directives

### 7.3.1 Definition and Axiomatic Basis

While descriptive entities capture the "what" of an observation, directives capture the "what must be." Axiom 2 (`pci_dss_requirement`) formalizes the relationship between a directive class and a specific requirement class within the Payment Card Industry Data Security Standard (PCI DSS). The axiom is defined as `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`.

Verbalized, this structure asserts that "{X} is something that pci dss requirement {Y}." Here, {X} represents the directive information content entity—the formal mandate—while {Y} represents the specific requirement class (e.g., a requirement regarding encryption or access control). This distinction is critical for audit automation; it separates the *rule* from the *implementation* of the rule. The directive acts as the normative anchor against which descriptive observations (Axiom 1) are compared to determine compliance status.

### 7.3.2 Relational Implementation

The relational schema for this axiom introduces a foreign key constraint, linking the directive to the basic descriptive claim defined in the previous section. This enforces the integrity of the compliance mapping: a directive must reference a valid requirement class. ## 7.4 Attribute-Rich Outlier Claims

### 7.4.1 Definition and Axiomatic Basis

Basic descriptive claims (Axiom 1) provide a high-level classification, but effective auditing requires granular detail. Axiom 3 (`outlier_claim_min_one_attribute`) extends the descriptive entity by requiring a minimum of one attribute set. The Manchester syntax is `Class: {X:Class} SubClassOf: cco:DescriptiveICE, sdg:hasAttributeSet min 1 {Y:Class}`.

Verbalized, this asserts that "{X} is a descriptive information content entity" that possesses specific attributes. In this context, {X} is the detailed claim, and {Y} refers to the attribute set class, which often includes metadata such as timestamps, severity scores, or host IP addresses. Crucially, the schema links this detailed claim back to a PCI DSS directive, establishing a traceable chain of evidence from the specific attribute of a finding to the governing requirement.

### 7.4.2 Relational Implementation

The schema for Axiom 3 enforces a dependency on the directive table (`t_pci_dss_requirement`). This ensures that every detailed, attribute-rich claim is justified by a specific compliance directive. ## 7.5 Basic Measurement Entities

### 7.5.1 Definition and Axiomatic Basis

Compliance frameworks rely not only on qualitative observations but also on quantitative data. Axiom 4 (`measurement_basic`) defines the class for these quantitative entities. The axiom is expressed as `Class: {X:Class} SubClassOf: cco:DescriptiveICE`.

Verbalized, "{X} is a descriptive information content entity" specifically representing a measurement. Unlike the "outlier claims" in previous sections, which may be binary or categorical, measurements capture continuous or discrete numerical values (e.g., file size, network latency, encryption key length). These entities form the evidentiary basis for assertions that a system meets or fails specific technical thresholds (e.g., "key length > 2048 bits").

## 7.6 Aggregation of Information Content

### 7.6.1 Definition and Axiomatic Basis

To support high-level reporting and dashboarding, individual measurements and claims must be synthesized. Axiom 5 (`aggregation_basic`) defines the entity responsible for this synthesis. The axiom is `Class: {X:Class} SubClassOf: cco:DescriptiveICE`.

Verbalized, "{X} is a descriptive information content entity" that functions as an aggregation. Aggregations summarize lower-level data points—calculating averages, maximums, or totals—to provide a view of system health or compliance posture over time. For instance, an aggregation might represent the "Average Failed Login Attempts" across all servers in a fleet, derived from multiple instances of the measurement class defined in Axiom 4.

### 7.6.2 Relational Implementation

The table for aggregations mirrors the structure of basic claims and measurements but serves a distinct semantic purpose. It stores the metadata regarding the summary logic applied to the raw data. This separation allows the system to query raw details for forensic purposes while querying aggregations for executive reporting.
