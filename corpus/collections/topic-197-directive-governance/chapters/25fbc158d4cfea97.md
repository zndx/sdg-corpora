# Chapter 4: Formal Classification of Information Content Entities in Compliance Frameworks

## 4.1 Scope and Preamble

This chapter establishes the taxonomic criteria for classifying Information Content Entities (ICEs) within the context of regulatory compliance and audit governance. Specifically, it addresses the formalization of descriptive claims, directive requirements, and measurement observations as prescribed by the Payment Card Industry Data Security Standard (PCI DSS) and related governance frameworks. The objective is to provide a deterministic mapping between natural-language audit findings and a machine-readable ontology, thereby ensuring semantic interoperability between automated compliance tools and human auditors. The following sections detail the structural axioms governing these entities, supported by relational data tables that instantiate the defined classes.

## 4.2 Descriptive Information Content Entities (Outlier Claims)

### 4.2.1 Definition and Axiomatic Basis

In the ontology of audit findings, the primary unit of observation is the Outlier Claim. Formally, this entity is defined by the axiom that the Class {X} is a SubClassOf `cco:DescriptiveICE`. A Descriptive Information Content Entity is distinct from a prescriptive directive in that it asserts a fact about the state of a system or process, rather than mandating a behavior. In the context of security auditing, an Outlier Claim represents a detected deviation from a baseline configuration, a policy violation, or an anomalous system event.

The classification of an entity as a `DescriptiveICE` serves as the foundational step in the audit trail. It signals that the entity contains propositional content describing a specific state of affairs. For the purposes of PCI DSS compliance, these claims often serve as the evidentiary basis for non-compliance reports.

## 4.3 PCI DSS Requirement Directives

### 4.3.1 Definition and Axiomatic Basis

While descriptive entities identify *what* has occurred, directive entities establish the regulatory framework defining *what should* occur. The axiom governing this section posits that Class {X} is a SubClassOf `cco:DirectiveICE` and satisfies the object property `sdg:pciDssRequirement` for some Class {Y}.

This structure creates a formal linkage between a governance directive (the requirement) and the specific descriptive claim it addresses. In practice, this means that every outlier claim or observation must be mappable to a specific control requirement within the PCI DSS framework. The `DirectiveICE` class encapsulates the normative text of the standard, while the relationship to the claim validates the relevance of the audit finding.

### 4.3.2 Relational Mapping and Evidence

The integrity of the compliance audit relies on the traceability between the directive and the observed anomaly. The relational schema enforces this by requiring a foreign key reference to the descriptive entity (the outlier claim) identified in the previous section.

**Table 4.2: PCI DSS Requirement Directives Linked to Claims**

| ID | Class (X) | Requirement Target (Y) |
| :--- | :--- | :--- |
| `req_001` | `AccessControlDirective` | `oc_001` |
| `req_002` | `CryptographyDirective` | `oc_002` |
| `req_003` | `AuditTrailDirective` | `oc_003` |
| `req_004` | `VulnerabilityManagementDirective` | `oc_004` |
| `req_005` | `AuthenticationDirective` | `oc_005` |

In Table 4.2, the `Requirement Target (Y)` column references the ID of the outlier claim. For instance, the `AccessControlDirective` is formally linked to the `UnauthorizedAccessAttempt` claim (`oc_001`). This linkage satisfies the axiom `sdg:pciDssRequirement some {Y:Class}`, ensuring that the directive is semantically bound to the specific context of the observed anomaly.

## 4.4 Attribute Sets for Outlier Claims

### 4.4.1 Definition and Axiomatic Basis

A descriptive claim is insufficient for forensic analysis without a robust set of attributes. The axiom for this section states that Class {X} is a SubClassOf `cco:DescriptiveICE` and possesses the property `sdg:hasAttributeSet` with a minimum cardinality of 1 for Class {Y}.

This requirement mandates that every valid outlier claim must be accompanied by a defined attribute set. These attributes typically include metadata such as timestamps, source IP addresses, user identifiers, or severity scores. The "min 1" constraint ensures that no claim exists in a vacuum; it must be anchored by at least one quantifiable or identifiable data point that substantiates the assertion.

### 4.4.2 Attribute Assignment

The following table illustrates the assignment of attribute sets to the previously defined directive structures. The foreign key constraint ensures that the attribute set is associated with a valid PCI DSS requirement directive, thereby maintaining the chain of evidence from the specific attribute back to the regulatory requirement.

**Table 4.3: Outlier Claims with Mandatory Attribute Sets**

| ID | Class (X) | Attribute Set Reference (Y) |
| :--- | :--- | :--- |
| `attr_001` | `AnnotatedAccessClaim` | `req_001` |
| `attr_002` | `AnnotatedCryptoClaim` | `req_002` |
| `attr_003` | `AnnotatedAuditClaim` | `req_003` |
| `attr_004` | `AnnotatedVulnClaim` | `req_004` |
| `attr_005` | `AnnotatedAuthClaim` | `req_005` |

Here, the `Attribute Set Reference (Y)` column links to the directive ID. For example, `attr_001` represents the class of claims that include specific attributes (e.g., source IP, port number) for the `AccessControlDirective`. This structure satisfies the complex axiom requiring a descriptive entity to possess a minimum of one attribute set, which is instantiated here via the reference to the directive context.

## 4.5 Measurement Entities

### 4.5.1 Definition and Axiomatic Basis

Distinct from categorical claims, Measurement Entities provide quantitative data regarding the state of a system. The governing axiom is identical in structure to the basic descriptive claim: Class {X} is a SubClassOf `cco:DescriptiveICE`. However, the semantic distinction lies in the nature of the content; measurements represent continuous or discrete numerical values rather than categorical assertions.

In the context of technical audits, measurements are critical for establishing compliance with thresholds, such as maximum password age limits, minimum encryption key lengths, or maximum allowed transmission latency. These entities form the quantitative backbone of the audit report.

### 4.5.2 Measurement Instances

The table below defines specific classes of measurement entities utilized in the audit framework.

**Table 4.4: Basic Measurement Entities**

| ID | Class (X) |
| :--- | :--- |
| `meas_001` | `PacketLossRatio` |
| `meas_002` | `KeyExchangeDuration` |
| `meas_003` | `FailedLoginCount` |
| `meas_004` | `DatabaseTransactionLatency` |
| `meas_005` | `DiskUtilizationPercentage` |

Each entry in Table 4.4 represents a specific type of data collection. For instance, `PacketLossRatio` and `DatabaseTransactionLatency` are descriptive entities that convey performance metrics. While they are descriptive, their utility is derived from their numerical value, which is compared against compliance benchmarks.

## 4.6 Aggregation Entities

### 4.6.1 Definition and Axiomatic Basis

Aggregation Entities function as summaries of lower-level measurements or claims. Defined by the axiom Class {X} is a SubClassOf `cco:DescriptiveICE`, these entities synthesize multiple data points into a single representative value, such as an average, maximum, or sum.

Aggregations are essential for high-level reporting and governance dashboards. They allow auditors and compliance officers to assess the overall health of the IT environment without being overwhelmed by granular event logs. Common aggregations include daily averages of system load or weekly totals of security incidents.

### 4.6.2 Aggregation Classes

The following table presents the classification schema for aggregation entities used in the reporting layer.

**Table 4.5: Basic Aggregation Entities**

| ID | Class (X) |
| :--- | :--- |
| `agg_001` | `DailyAveragePacketLoss` |
| `agg_002` | `WeeklyTotalFailedLogins` |
| `agg_003` | `MonthlyPeakLatency` |
| `agg_004` | `QuarterlyMeanDiskUsage` |
| `agg_005` | `AnnualIncidentSeverityIndex` |

These classes (`DailyAveragePacketLoss`, `WeeklyTotalFailedLogins`, etc.) represent the processed output of raw measurements. They are formally classified as `DescriptiveICE` because they describe the state of the system over a defined temporal window, providing the evidence required for trend analysis and long-term compliance monitoring.
