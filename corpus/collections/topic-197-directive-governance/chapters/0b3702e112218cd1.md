# Chapter 4: Ontological Structuring of PCI DSS Compliance Directives and Observational Metrics

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the precise classification of information content entities within a PCI DSS (Payment Card Industry Data Security Standard) compliance environment. The text delineates the structural relationships between descriptive information content entities (ICE), regulatory directives, and observational metrics. It provides the necessary taxonomic definitions to ensure that audit artifacts, anomaly reports, and performance measurements are anchored in a rigorously defined schema. The following sections detail the specific axioms governing outlier claims, compliance requirements, attribute sets, and measurement aggregations, supported by relational data mappings consistent with the enterprise governance model.

## 4.2 Outlier Claim Basic

In the context of continuous monitoring and audit governance, an outlier claim is formally defined as a specific subclass of a descriptive information content entity. As posited by Axiom 1 (`outlier_claim_basic`), any entity classified as an outlier claim functions primarily to characterize a deviation from established operational baselines or security controls. Unlike prescriptive directives, a descriptive ICE serves to articulate the state of a system or the existence of a specific event without mandating a remedial action itself.

The identification of outlier claims is the foundational step in the audit trail. These claims represent the raw observations—such as unauthorized access attempts, configuration drifts, or unencrypted data transmissions—that trigger downstream compliance workflows. To ensure data integrity, each claim must be instantiated as a distinct class within the ontology, providing a clear target for subsequent requirement mapping.

The following table enumerates specific instances of outlier claims identified during the Q2 FY24 audit cycle. These entries represent the `X` slot in the axiom, where each class is asserted to be a subclass of `cco:DescriptiveICE`.

**Table 4.1: Outlier Claim Classifications (t_outlier_claim_basic)**

| id | x |
| :--- | :--- |
| OC-1001 | UnencryptedTransmissionEvent |
| OC-1002 | InvalidAccessAttempt |
| OC-1003 | ConfigurationDriftDetected |
| OC-1004 | StorageVolumeExceeded |
| OC-1005 | VendorCredentialExpiry |

Each entry in Table 4.1 corresponds to a specific class of observation. For instance, `UnencryptedTransmissionEvent` (OC-1001) describes a state where sensitive cardholder data traverses a network in clear text, violating fundamental security principles. The primary key `id` serves as the unique identifier for the claim class, enabling unambiguous reference in higher-level directive structures.

## 4.3 PCI DSS Requirement

Building upon the descriptive definitions of outlier claims, the governance framework introduces the concept of the PCI DSS Requirement. According to Axiom 2 (`pci_dss_requirement`), a requirement is modeled as a subclass of a Directive Information Content Entity (`cco:DirectiveICE`). This entity is distinct from descriptive claims in that it carries normative weight; it prescribes specific controls or behaviors.

The axiom further establishes a relational constraint: a PCI DSS Requirement (`X`) must possess a property `sdg:pciDssRequirement` that references at least one specific Outlier Claim (`Y`). In practice, this means that every regulatory directive is instantiated to address or govern a specific type of outlier observation defined in Section 4.2. The foreign key structure linking the requirement to the claim ensures that compliance mandates are strictly evidence-anchored to observable phenomena.

The relational schema presented below illustrates this binding. The `x` column denotes the specific directive class, while the `y` column establishes the mandatory foreign key reference to the `t_outlier_claim_basic` table. This structure enforces the rule that a directive cannot exist in isolation; it must be a response to a defined claim.

**Table 4.2: PCI DSS Requirement Directives (t_pci_dss_requirement)**

| id | x | y |
| :--- | :--- | :--- |
| DIR-2001 | EncryptionControlDirective | OC-1001 |
| DIR-2002 | AccessControlProtocol | OC-1002 |
| DIR-2003 | ConfigurationManagementStandard | OC-1003 |
| DIR-2004 | CapacityManagementPolicy | OC-1004 |
| DIR-2005 | ThirdPartyVendorPolicy | OC-1005 |

In Table 4.2, the `EncryptionControlDirective` (DIR-2001) is explicitly linked to the `UnencryptedTransmissionEvent` (OC-1001). This mapping formalizes the intent of the directive: to prescribe the necessary controls (e.g., TLS implementation) to mitigate the specific outlier claim described in the previous section. The `NOT NULL` constraint on the `y` column ensures that no directive is drafted without a corresponding subject matter grounded in an observational reality.

## 4.4 Outlier Claim Minimum One Attribute

While the definition of an outlier claim provides the categorical classification of an event, effective governance requires granular detail regarding the attributes of that event. Axiom 3 (`outlier_claim_min_one_attribute`) refines the descriptive ICE by asserting that such an entity must possess a minimum of one attribute set (`sdg:hasAttributeSet`).

This axiom introduces a hierarchical dependency. The attribute set (`Y`) is not merely a property of the claim but is structurally dependent on the PCI DSS Requirement (`X`) that governs the claim. In the relational projection, this is realized by a foreign key constraint where the attribute set references the directive identifier. This design reflects the audit reality that the specific attributes collected for an outlier claim are dictated by the requirements of the governing directive. For example, an access control directive will mandate the collection of specific attributes (such as `source_ip`, `timestamp`, `user_id`) for any invalid access attempt.

The following table details the attribute sets associated with the directives defined in Section 4.2. The `x` column represents the class of the attribute set, while the `y` column references the directive ID (`t_pci_dss_requirement`), thereby enforcing the dependency chain.

**Table 4.3: Outlier Claim Attribute Sets (t_outlier_claim_min_one_attribute)**

| id | x | y |
| :--- | :--- | :--- |
| ATTR-3001 | NetworkFlowAttributeSet | DIR-2001 |
| ATTR-3002 | AuthenticationLogAttributeSet | DIR-2002 |
| ATTR-3003 | SystemConfigAttributeSet | DIR-2003 |
| ATTR-3004 | StorageMetricAttributeSet | DIR-2004 |
| ATTR-3005 | VendorProfileAttributeSet | DIR-2005 |

Consider the entry `ATTR-3002` (`AuthenticationLogAttributeSet`), which references `DIR-2002` (`AccessControlProtocol`). This relationship dictates that when the outlier claim `InvalidAccessAttempt` (OC-1002) is recorded, it must be populated with the attributes defined in `AuthenticationLogAttributeSet`. This structure ensures that data collection is standardized across the enterprise and that all observational data is compliant with the metadata requirements of the governing directive.

## 4.5 Measurement Basic

Distinct from categorical claims and prescriptive directives, the governance framework incorporates quantitative assessments through the concept of Measurement. Axiom 4 (`measurement_basic`) classifies a measurement as a subclass of `cco:DescriptiveICE`. However, unlike the outlier claims which describe discrete events or states, measurements typically represent continuous or scalar values derived from system telemetry.

Measurements serve as the evidentiary basis for evaluating compliance status over time. They provide the quantitative "proof" that a directive is being followed or that an outlier claim is being mitigated. In the context of the ontology, measurements are treated as first-class information entities, allowing them to be archived, queried, and reported alongside other governance artifacts.

The table below presents a catalog of measurement classes utilized within the monitoring infrastructure. These classes define the type of data to be captured, such as latency, throughput, or error rates.

**Table 4.4: Measurement Class Definitions (t_measurement_basic)**

| id | x |
| :--- | :--- |
| MEAS-4001 | TransactionLatencyMeasurement |
| MEAS-4002 | EncryptionStrengthMeasurement |
| MEAS-4003 | FailedLoginCountMeasurement |
| MEAS-4004 | PatchCompliancePercentageMeasurement |
| MEAS-4005 | NetworkThroughputMeasurement |

For instance, `MEAS-4002` (`EncryptionStrengthMeasurement`) provides the quantitative data (e.g., key length in bits) necessary to verify the `EncryptionControlDirective` (DIR-2001). By treating these measurements as descriptive ICEs, the ontology facilitates the automated correlation of quantitative metrics with qualitative compliance requirements.

## 4.6 Aggregation Basic

Finally, to support high-level reporting and strategic oversight, the framework defines the concept of Aggregation. Axiom 5 (`aggregation_basic`) asserts that an aggregation is also a subclass of `cco:DescriptiveICE`. Aggregations represent summaries, roll-ups, or statistical derivations of the base measurements and outlier claims.

Aggregations are critical for executive reporting and periodic reviews (such as the Q2 Shareholder Update). They transform high-volume, granular data into consumable insights, such as daily averages, monthly totals, or risk scores. While they are descriptive in nature, their value lies in their ability to synthesize complex datasets into a format suitable for human decision-making.

The following table lists the aggregation classes currently deployed in the reporting dashboard.

**Table 4.5: Aggregation Class Definitions (t_aggregation_basic)**

| id | x |
| :--- | :--- |
| AGG-5001 | DailyAverageTransactionLatency |
| AGG-5002 | MonthlyFailedLoginSum |
| AGG-5003 | QuarterlyComplianceScore |
| AGG-5004 | WeeklyStorageUtilizationAverage |
| AGG-5005 | AnnualVendorRiskRating |

The entry `AGG-5003` (`QuarterlyComplianceScore`) exemplifies this concept. It is a derived entity that synthesizes data from multiple measurements (e.g., `PatchCompliancePercentageMeasurement`) and outlier claims (e.g., `ConfigurationDriftDetected`) to produce a single indicator of organizational health. As a descriptive ICE, this aggregation is retained within the knowledge base, providing a historical record of performance trends for auditors and regulators.
