# Chapter 4: Ontological Structures for PCI DSS Compliance Reporting

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to represent, audit, and report on Payment Card Industry Data Security Standard (PCI DSS) compliance postures within an enterprise information system. The content herein defines a rigorous framework for mapping regulatory directives to descriptive information content entities, ensuring that governance artifacts are machine-readable and semantically grounded. The principles established are derived from the Common Core Ontologies (CCO) and extended to satisfy specific audit requirements regarding outlier detection, measurement aggregation, and requirement traceability. Professionals utilizing this framework are advised to strictly adhere to the entity definitions and relational constraints provided to ensure the integrity of compliance reporting.

## 4.2 Descriptive Information Content Entities

At the foundational level of the compliance ontology lies the Descriptive Information Content Entity (DescriptiveICE). As defined in the core axiom set, a DescriptiveICE serves as a container for information that describes a state of affairs, a specific observation, or a regulatory definition. In the context of an audit, these entities are not the measurements themselves, but rather the descriptive assertions that categorize and give meaning to raw data.

The primary classification for entities representing specific compliance violations or anomalies is the `outlier_claim_basic`. An outlier claim is a declarative statement asserting that a specific observed condition deviates from the expected baseline or regulatory mandate. This entity is a subclass of `cco:DescriptiveICE`, functioning as the atomic unit of audit evidence. When an automated system detects a potential breach—such as an unauthorized configuration change—it instantiates an outlier claim to formally record this deviation within the governance ledger.

To illustrate the instantiation of these entities, consider the following registry of descriptive claims. Each entry represents a distinct class of observation that has been cataloged during a quarterly audit cycle.

## 4.3 PCI DSS Requirements as Directives

While descriptive entities capture observations, compliance frameworks require a mechanism to link these observations to specific regulatory obligations. This is achieved through the `pci_dss_requirement` axiom. This structure defines a class of entities that function as `cco:DirectiveICE`—information content entities that prescribe specific behaviors or states. Crucially, this axiom establishes a necessary existential restriction: a directive must be associated with at least one specific PCI DSS requirement.

In this relational model, the directive entity (the "X" slot) represents the internal policy or control implementation, while the "Y" slot references the specific descriptive definition of the PCI DSS requirement (e.g., the text of Requirement 1.2.1). This linkage creates a traceability path from the internal governance artifact to the external regulatory standard. The foreign key constraint ensures that no directive can exist without a valid, mapped requirement, thereby enforcing strict compliance alignment.

The following table details the mapping between internal directive classes and their corresponding PCI DSS requirement definitions.

**Table 4.2: Mapping of Directives to PCI DSS Requirements**

| ID | Directive Class (X) | Requirement Definition ID (Y) |
| :--- | :--- | :--- |
| `DIR-FW-001` | `PerimeterFirewallDirective` | `OBS-2023-Q3-001` |
| `DIR-LOG-002` | `AuditLogRetentionDirective` | `OBS-2023-Q3-003` |
| `DIR-WL-003` | `WirelessAccessControlDirective` | `OBS-2023-Q3-004` |
| `DIR-PATCH-004` | `VulnerabilityManagementDirective` | `OBS-2023-Q3-005` |

*Table 4.2 represents the `pci_dss_requirement` axiom. The `x` column identifies the Directive Class, while the `y` column serves as a foreign key referencing the `id` from the `t_outlier_claim_basic` table. This enforces the logical dependency that directives are defined in relation to specific requirement claims.*

## 4.4 Attribute Sets in Outlier Claims

To facilitate granular analysis and remediation, outlier claims must be enriched with contextual metadata. The `outlier_claim_min_one_attribute` axiom extends the basic descriptive entity by mandating the presence of an attribute set. This structure asserts that a valid outlier claim (Class X) possesses a minimum of one attribute set (Class Y), which provides the necessary evidentiary detail (e.g., timestamp, source IP, user ID) to substantiate the claim.

In the context of the relational schema, the attribute set is not merely a property of the claim but is structurally anchored to the directive framework. The schema dictates that the attribute set (Y) is linked to a PCI DSS requirement directive. This design choice implies that the *schema* or *structure* of the evidence collected for an outlier claim is determined by the specific PCI DSS requirement being addressed. For instance, a claim regarding "Unencrypted Transmission" must carry an attribute set compliant with the "Perimeter Firewall Directive."

This hierarchical dependency ensures that data collection for audit purposes is driven by regulatory requirements. The table below demonstrates how specific outlier claims are associated with attribute sets that are, in turn, governed by the directives established in Section 4.3.

**Table 4.3: Outlier Claims with Directive-Defined Attribute Sets**

| ID | Outlier Claim Class (X) | Attribute Set Class (Y) |
| :--- | :--- | :--- |
| `ATTR-SET-100` | `UnencryptedTransmissionEvent` | `DIR-FW-001` |
| `ATTR-SET-101` | `InadequateLogRetention` | `DIR-LOG-002` |
| `ATTR-SET-102` | `UnauthorizedWirelessAccess` | `DIR-WL-003` |
| `ATTR-SET-103` | `UnpatchedSystemVulnerability` | `DIR-PATCH-004` |

*Table 4.3 operationalizes the `outlier_claim_min_one_attribute` axiom. The `x` column defines the class of the descriptive claim, while the `y` column references the Directive ID (`t_pci_dss_requirement`), thereby linking the evidence structure to the regulatory mandate.*

## 4.5 Measurement Entities

Compliance reporting relies heavily on quantitative data to substantiate qualitative claims. The `measurement_basic` axiom defines the fundamental unit of such data. A measurement is a specific type of DescriptiveICE that represents a value assigned to a characteristic of an entity by a measurement procedure. Unlike an outlier claim, which asserts a deviation, a measurement asserts a factual state (e.g., a port is open, a file size is 10MB, a latency is 50ms).

In the audit context, measurements serve as the "ground truth" from which outlier claims are derived. For example, a measurement might record that "Port 22 is observed as open on Server A." If policy dictates that Port 22 must be closed, a subsequent outlier claim is generated. The ontological distinction between the measurement (the fact) and the claim (the interpretation) is critical for maintaining audit integrity and allowing for root cause analysis.

The following registry catalogs the types of measurement entities collected by the governance system.

**Table 4.4: Registry of Measurement Entities**

| ID | Measurement Class (X) |
| :--- | :--- |
| `MEAS-001` | `NetworkPortStatusMeasurement` |
| `MEAS-002` | `EncryptionProtocolStrengthMeasurement` |
| `MEAS-003` | `SystemUptimeDurationMeasurement` |
| `MEAS-004` | `FilePermissionOctalMeasurement` |
| `MEAS-005` | `DatabaseConnectionCountMeasurement` |

*Table 4.4 instantiates the `measurement_basic` axiom. Each row represents a distinct class of data collection activity, all of which are subclasses of `cco:DescriptiveICE`, providing the raw evidentiary basis for compliance reporting.*

## 4.6 Aggregation Entities

While individual measurements are necessary, high-level compliance reporting often requires aggregated views of the data to identify trends and systemic issues. The `aggregation_basic` axiom defines entities that represent the synthesis of multiple measurements into a single descriptive value (e.g., averages, sums, maximums). Aggregations are also DescriptiveICEs, but they are derived from the application of a mathematical or logical function to a set of base measurements.

For the auditor, aggregation entities provide a macro-level view of the security posture. For instance, rather than reviewing 10,000 individual port measurements, an auditor might review a single aggregation entity representing the "Percentage of Systems with Open High-Risk Ports." This abstraction layer is essential for executive reporting and risk scoring.
