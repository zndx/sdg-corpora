# Chapter 7: Formalization of Information Content Entities in PCI DSS Compliance Frameworks

## 7.1 Scope and Preamble

This chapter establishes the ontological foundations for mapping Payment Card Industry Data Security Standard (PCI DSS) requirements to formal information content entities (ICE). It provides a structured methodology for auditors and compliance officers to translate regulatory directives into descriptive data models. The text delineates the hierarchy of descriptive claims, directive requirements, attribute sets, and measurement aggregations necessary for rigorous audit evidence collection. Adherence to the axioms presented herein ensures that compliance artifacts are machine-readable and semantically grounded in the Common Core Ontologies (CCO). This framework is intended for use in governance environments requiring high-fidelity data lineage and automated compliance verification.

## 7.2 Descriptive Information Content Entities

### 7.2.1 Definition and Context

In the context of formal ontology auditing, a Descriptive Information Content Entity (DescriptiveICE) serves as the fundamental unit of propositional data. As defined by the foundational axioms of the Common Core Ontology, a DescriptiveICE is a type of information content entity that is about some entity or state of affairs. Within the scope of PCI DSS compliance, these entities function as the raw "claims" or observations regarding the state of a system's security controls. They do not, in themselves, prescribe action; rather, they describe a condition that may be evaluated against a standard.

The axiom `outlier_claim_basic` posits that any class designated as a descriptive claim is a subclass of `cco:DescriptiveICE`. This classification is critical for audit trails because it segregates observational data from procedural directives. When an auditor identifies a potential security breach or a configuration drift, the formal representation of that observation must be instantiated as a DescriptiveICE. This ensures that the data point is treated as an evidentiary artifact rather than a normative rule.

### 7.2.2 Implementation of Outlier Claims

The identification of outlier claims is the primary mechanism for triggering security alerts. An outlier claim represents a deviation from the expected baseline behavior of a system. For instance, if a database server that typically handles 100 transactions per second suddenly handles 10,000, the event recording this spike is a DescriptiveICE. It describes the state of "High Transaction Volume" without yet asserting whether that state is permissible or malicious.

To maintain data integrity within the audit repository, these claims must be cataloged with unique identifiers. Each entry represents a distinct class of observation that the compliance framework is designed to capture.

## 7.3 Directive ICE and PCI DSS Requirements

### 7.3.1 The Directive Structure

While descriptive entities define *what* is observed, Directive Information Content Entities (DirectiveICE) define *what must be done* or *what is required*. The axiom `pci_dss_requirement` formalizes the relationship between a directive and a specific descriptive claim. Specifically, it states that a DirectiveICE is a subclass of `cco:DirectiveICE` and possesses a `sdg:pciDssRequirement` relationship to a DescriptiveICE.

This relationship is the cornerstone of the compliance mapping. It asserts that for a specific PCI DSS requirement to be satisfied, a specific type of descriptive claim (observation) must be monitored or controlled. For example, PCI DSS Requirement 8.2.1 regarding identification and authentication mandates that users be authenticated. The directive entity representing this requirement would be linked to a descriptive claim regarding "Authentication Success." If the system cannot produce the descriptive claim (e.g., logs showing authentication), the directive is violated.

### 7.3.2 Mapping Requirements to Claims

The relational structure governing this mapping enforces a strict dependency: a requirement cannot exist in isolation; it must be a requirement *about* something. Therefore, the foreign key constraint in the schema ensures that every PCI DSS requirement references a valid, pre-existing outlier claim or descriptive entity. This prevents the creation of "orphan" directives that have no measurable impact on the system's state.

## 7.4 Attribute Sets in Compliance Claims

### 7.4.1 Granularity of Observation

A descriptive claim, while useful, is often insufficiently granular for detailed forensic analysis. To address this, the ontology introduces the concept of attribute sets. The axiom `outlier_claim_min_one_attribute` asserts that a descriptive entity must possess a minimum of one attribute set. An attribute set provides the metadata or parameters necessary to fully contextualize the claim.

For example, the claim `UnusualGeolocationLogin` is semantically meaningful, but for an auditor to act on it, the claim must be accompanied by attributes such as `Timestamp`, `SourceIP`, `UserID`, and `GeoCoordinates`. The axiom enforces the cardinality constraint (`min 1`), ensuring that no claim enters the audit repository without at least one defining characteristic. This prevents "empty" claims that cannot be investigated.

### 7.4.2 Hierarchical Dependency

The relational schema for attribute sets creates a three-layer hierarchy:
1.  **Layer 1:** The Basic Claim (e.g., "Failed Login").
2.  **Layer 2:** The Directive (e.g., "Log Monitoring Requirement").
3.  **Layer 3:** The Attribute Set (e.g., "Time of Failure").

The foreign key structure here references the PCI DSS Requirement table (`t_pci_dss_requirement`). This implies that attributes are defined within the context of a specific requirement's enforcement. While the claim describes the event, and the directive mandates its monitoring, the attribute set defines the *parameters* of that monitoring as required by the directive.

## 7.5 Measurement Entities

### 7.5.1 Quantitative Descriptive Entities

Distinct from claims regarding specific events (outliers), measurement entities represent quantitative data points derived from system monitoring. These are also DescriptiveICEs, as per the `measurement_basic` axiom, but they are characterized by their scalar or vector nature. Measurements are the continuous stream of data that feeds into the generation of outlier claims.

In a governance framework, measurements are the "telemetry" of the system. They include CPU usage, network latency, transaction counts, and disk I/O. While a single measurement rarely constitutes a compliance violation on its own, the aggregation of measurements forms the baseline against which outliers are defined. The ontology treats measurements as first-class entities to ensure that all audit evidence is traceable to a root source data point.

### 7.5.2 Measurement Registry

The registry of measurement entities provides a catalog of acceptable quantitative metrics that the organization captures. This registry is essential for scope definition; it explicitly lists what data is collected, satisfying the "data collection" requirements of various compliance frameworks.

**Table 7.4: Measurement Entity Registry**
This table embodies the `measurement_basic` axiom. It lists the primary key (`id`) and the measurement class (`x`), serving as a controlled vocabulary for system metrics.

| id | x |
| :--- | :--- |
| `MEAS-001` | `NetworkLatencyMs` |
| `MEAS-002` | `ActiveSessionCount` |
| `MEAS-003` | `DiskUtilizationPercentage` |
| `MEAS-004` | `EncryptionKeyLength` |

The entries in Table 7.4, such as `NetworkLatencyMs` and `ActiveSessionCount`, represent the raw data types. These measurements are ingested by the monitoring infrastructure. It is from these measurements that the descriptive claims (Section 7.2) are derived. For example, a spike in `DatabaseTransactionRate` (MEAS-005) might trigger the `ExcessiveFailedAuthenticationAttempts` claim (OC-2024-002) if correlated with error logs.

## 7.6 Aggregation Entities

### 7.6.1 Statistical Summarization

The final concept in this chapter is the aggregation entity. Defined by the `aggregation_basic` axiom, an aggregation is a DescriptiveICE that represents a summary or statistical derivation of multiple measurements or claims. Aggregations are crucial for executive reporting and trend analysis. They transform high-volume, high-frequency data into manageable insights.

Examples of aggregations include "Daily Average CPU Usage," "Weekly Failed Login Totals," or "Monthly Patch Compliance Percentage." In the context of PCI DSS, aggregations are often used to demonstrate ongoing compliance over a reporting period (e.g., "99.9% uptime for the fraud detection system").

### 7.6.2 Aggregation Registry

The relational schema for aggregations is structurally similar to that of basic measurements but semantically distinct. While a measurement represents a point-in-time value, an aggregation represents a value computed over a temporal window or a specific dataset subset.
