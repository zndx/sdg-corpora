# Directive Governance in Organizational Audit Systems

This chapter defines five core ontological patterns for directive governance and demonstrates their instantiation through a normalized relational schema. The patterns address how processes are conducted, how attestations reference evidence, how requirements are satisfied, how verifications produce records, and how controls address threat classes. All examples are drawn from a financial-services audit program conducted in 2018.

## 1 Scope and Schema Overview

The relational representation uses five tables whose columns directly encode the slot types of the source axioms. Primary keys are surrogate identifiers; foreign-key relationships are realized by shared literal values in the x and y columns. Cross-table joins therefore recover the multi-hop chains required by the axioms.

### 1.1 Audit Conducted By

Axiom 1 states that a process is conducted by a person. The table records the responsible individual for each audit process instance. The column id is the primary key; x references the process class.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| acb-001 | InternalControlReview |
| acb-002 | InternalControlReview |
| acb-003 | ThreatAssessmentVerification |
| acb-004 | ComplianceAttestation |
| acb-005 | AccessControlPolicyReview |

### 1.2 Attestation With Supporting Evidence

Axiom 2 states that a process occurs with supporting evidence. The table links each attestation process to its evidence artifact. id is the primary key; x and y are both entity references.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| awe-001 | ComplianceAttestation | AuditReport2018 |
| awe-002 | ComplianceAttestation | SupportingDocs |
| awe-003 | InternalControlReview | AuditReport2018 |
| awe-004 | ThreatAssessmentVerification | RiskRegister |
| awe-005 | AccessControlPolicyReview | PolicyEvidence |

### 1.3 Requirement Only Satisfied By

Axiom 3 states that a directive is satisfied only by a given class. The table enumerates the sole satisfier for each requirement. id is the primary key; x and y are entity references.

```sql
CREATE TABLE t_requirement_only_satisfied_by (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| ros-001 | SecurityRequirement | ThreatAssessmentVerification |
| ros-002 | AccessRequirement | AccessControlPolicyReview |
| ros-003 | DocumentationRequirement | ComplianceAttestation |
| ros-004 | ControlEffectivenessRequirement | InternalControlReview |

### 1.4 Verification Produces Evidence

Axiom 4 states that a process produces evidence. The table records the evidence artifact generated by each verification process. id is the primary key; x and y are entity references.

```sql
CREATE TABLE t_verification_produces_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| vpe-001 | ThreatAssessmentVerification | RiskRegister |
| vpe-002 | InternalControlReview | AuditReport2018 |
| vpe-003 | ComplianceAttestation | SupportingDocs |
| vpe-004 | AccessControlPolicyReview | PolicyEvidence |

### 1.5 Control Only Addresses Threat Class

Axiom 5 states that a directive addresses only a given risk class. The table records the threat class addressed by each control. id is the primary key; x and y are entity references.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| coa-001 | AccessControlPolicyReview | UnauthorizedAccess |
| coa-002 | InternalControlReview | ProcessFailure |
| coa-003 | ComplianceAttestation | RegulatoryBreach |

## 2 Cross-Join Demonstration

To determine which person conducted the verification that produced the evidence satisfying the security requirement, join t_audit_conducted_by, t_verification_produces_evidence, and t_requirement_only_satisfied_by on the shared process identifiers.

- Start with ros-001 (SecurityRequirement satisfied only by ThreatAssessmentVerification).
- Join to vpe-001 (ThreatAssessmentVerification produces RiskRegister).
- Join to acb-003 (ThreatAssessmentVerification conducted by the person recorded for acb-003).

The resulting chain yields the person responsible for the verification step that satisfies the requirement.
