# Chapter 4: Directive Governance Relations in Audit Compliance

This chapter presents five relational tables that instantiate the core axioms of directive governance. The tables encode processes of audit, attestation, requirement satisfaction, verification, and control application, with primary and foreign key references enabling multi-hop queries across governance artifacts.

## 1 Audit Conducted By Relation

Table t_audit_conducted_by embodies AXIOM 1, recording each audit process as a subclass of bfo:0000015 conducted by a person. Column id is the primary key; column x references an audit instance. A reader can join this table on x to t_verification_produces_evidence.x to retrieve the person responsible for a verification step.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 2 Attestation With Supporting Evidence Relation

Table t_attestation_with_supporting_evidence embodies AXIOM 2, capturing an attestation process linked to supporting evidence. Column id is the primary key; column x identifies the attestation and column y is a foreign key to an evidence instance. Joining on y to t_verification_produces_evidence.y yields the originating verification for any attestation.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 3 Requirement Only Satisfied By Relation

Table t_requirement_only_satisfied_by embodies AXIOM 3, expressing that a directive requirement is satisfied exclusively by a designated control. Column id is the primary key; column x references the requirement and column y references the satisfying control. A join on y to t_control_only_addresses_threat_class.x retrieves the threat class addressed by the satisfying control.

```sql
CREATE TABLE t_requirement_only_satisfied_by (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 4 Verification Produces Evidence Relation

Table t_verification_produces_evidence embodies AXIOM 4, linking a verification process to the evidence it produces. Column id is the primary key; column x identifies the verification and column y is a foreign key to an evidence instance. Joining on x to t_audit_conducted_by.x returns the conducting person for the verification that generated a given evidence item.

```sql
CREATE TABLE t_verification_produces_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 5 Control Only Addresses Threat Class Relation

Table t_control_only_addresses_threat_class embodies AXIOM 5, stating that a control addresses only a specified threat class. Column id is the primary key; column x references the control and column y references the threat class. A join on x to t_requirement_only_satisfied_by.y yields every requirement satisfied solely by a control that mitigates a given threat.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 6 Multi-Hop Query Example

To determine the threat class addressed by the control satisfying the requirement linked to attestation ATT-200, first locate the requirement in t_requirement_only_satisfied_by where y equals the control referenced by the attestation evidence path. The evidence EV-300 is produced by VER-600 (t_verification_produces_evidence). VER-600 is conducted under AUD-100 (t_audit_conducted_by). The requirement REQ-400 is satisfied only by CTL-500 (t_requirement_only_satisfied_by). CTL-500 addresses only THR-700 (t_control_only_addresses_threat_class). The joined row is therefore (ATT-200, EV-300, VER-600, AUD-100, REQ-400, CTL-500, THR-700).
