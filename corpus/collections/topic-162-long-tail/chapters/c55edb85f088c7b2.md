# Chapter 4: Entity Classification and Relational Integrity in Facility Control Systems

## 4.0 Scope and Preamble

This chapter establishes the mandatory data ontology and relational schema required for the governance of integrated facility management systems. It defines the structural constraints for descriptive information entities, physical artifacts, and kernel-level system calls. Compliance with these standards ensures data interoperability between physical asset management layers and software-defined control interfaces. The provisions herein apply to all classified entities within the operational database, specifically addressing the mapping of artifacts to postal addresses and the designation of system call return types. Failure to adhere to these relational constraints will result in data integrity exceptions during audit cycles.

## 4.1 Descriptive Information Content Entities (DescriptiveICE)

### 4.1.1 Definition and Standard
The foundational unit of data within the system governance framework is the Descriptive Information Content Entity (DescriptiveICE). As defined by the Common Core Ontologies (CCO), a DescriptiveICE is an entity that is about some other entity. In the context of this technical standard, DescriptiveICE serves as the atomic data type for all descriptive attributes, including string literals, numerical identifiers, and structured text blocks. It is distinct from designative entities, which denote or point to objects, in that DescriptiveICE encapsulates the informational content itself.

The axiom governing this entity class is formalized as follows:
*   **Class:** `DescriptiveICE`
*   **Axiom:** `X` SubClassOf: `cco:DescriptiveICE`

This classification mandates that any data element intended to store descriptive content—such as a formatted address string, a status code description, or a return type definition—must be instantiated as a DescriptiveICE. This ensures a strict separation between the concept of a "thing" and the "description" of that thing.

### 4.1.2 Implementation and Relational Structure
To enforce this standard, the relational schema utilizes a specific table structure, `t_lift_basic`. This table acts as the registry for all descriptive information content entities. The primary key (`id`) serves as the unique identifier for the descriptive entity, while the column `x` represents the class or specific instance of the descriptive content.

The structure is non-complex (`is_complex: false`) and belongs to the observation measurement family. It functions as the lookup table for all higher-level associations. For example, before a physical artifact can be assigned a location, the textual representation of that location must exist as a valid entry in the `t_lift_basic` table.

**Table 4-1: Registry of Descriptive Information Content Entities (t_lift_basic)**

| id | x |
| :--- | :--- |
| desc_ent_001 | PostalAddressString_Type |
| desc_ent_002 | Integer32_ReturnType |
| desc_ent_003 | DeviceStatus_Enum |
| desc_ent_004 | GeoCoordinate_String |
| desc_ent_005 | FirmwareVersion_String |

*Table 4-1 enumerates valid DescriptiveICE instances. The column `x` denotes the specific data class or type definition. These entries are referenced by foreign keys in artifact and system call tables to ensure referential integrity.*

### 4.1.3 Compliance Verification
During system initialization, the governance engine verifies that all entries in `t_lift_basic` conform to the `cco:DescriptiveICE` definition. Any entity lacking descriptive properties or failing to map to a valid information content entity shall be rejected. This verification is critical for downstream processing, as both artifact addressing and system call typing rely on the integrity of these base records.

## 4.2 Artifact Geolocation and Addressing Standards

### 4.2.1 Artifact Definition and Addressing
Physical components within the facility infrastructure, ranging from ventilation control units to sensor arrays, are classified as Artifacts. An Artifact, in this ontology, is a physical object that has been created or modified by an agent. To ensure operational accountability and maintenance compliance, every Artifact must be associated with a specific postal address.

The governing axiom for this relationship is:
*   **Class:** `Artifact`
*   **Axiom:** `X` SubClassOf: `cco:Artifact`, `sdg:hasPostalAddress` some `Y`
*   **Verbalization:** `X` is something that has postal address `Y`

This regulation mandates that the relationship between an Artifact and its location is not merely a loose association but a structural dependency. The postal address (`Y`) must be a valid instance of a DescriptiveICE, formally linking the physical object to its informational descriptor.

### 4.2.2 Relational Mapping and Constraints
The relational schema for this standard is implemented in the table `t_schemaorg_place_address`. This table encodes the "hasPostalAddress" relationship. The column `x` represents the Artifact (the physical entity), while the column `y` represents the Postal Address (the descriptive entity).

A critical foreign key constraint is enforced herein: `y` must reference an existing `id` in the `t_lift_basic` table. This constraint ensures that an Artifact cannot be linked to a non-existent or undefined address string. It enforces the ontology's requirement that the address is an Information Content Entity, preventing the injection of raw, unvalidated data into the location field.

**Table 4-2: Artifact to Postal Address Mapping (t_schemaorg_place_address)**

| id | x | y |
| :--- | :--- | :--- |
| place_001 | ControlUnit_SV24V_Main | desc_ent_001 |
| place_002 | ControlUnit_SV48V_Aux | desc_ent_001 |
| place_003 | Sensor_Array_Temp_Zone1 | desc_ent_004 |
| place_004 | Ventilation_Actuator_Group2 | desc_ent_001 |
| place_005 | PowerDistribution_Unit_Alpha | desc_ent_001 |

*Table 4-2 illustrates the binding of physical Artifacts (`x`) to specific descriptive address entities (`y`). Note that `desc_ent_001` and `desc_ent_004` correspond to the descriptive types defined in Table 4-1. This mapping ensures that every hardware component is auditable against a verified location record.*

### 4.2.3 Operational Implications
For installation and maintenance personnel, this standard implies that the assignment of a location to a device (e.g., "Installation instruction Control Unit for Fire Ventilation") is a database transaction involving two distinct tables. First, the address string must be registered or selected from `t_lift_basic`. Second, the Artifact ID must be updated in `t_schemaorg_place_address` to point to that address ID. This two-step process prevents orphaned location data and ensures consistency across the facility management database.

## 4.3 System Call Designation and Return Typing

### 4.3.1 Designative Information Content Entities
In the context of software-defined controls and kernel interfaces, functions and system calls are categorized as Designative Information Content Entities (DesignativeICE). Unlike descriptive entities, which contain data, designative entities refer to or denote specific processes or functions within the operating system kernel.

The axiom governing this class is:
*   **Class:** `DesignativeICE`
*   **Axiom:** `X` SubClassOf: `cco:DesignativeICE`, `sdg:hasReturnType` max 1 `Y`
*   **Verbalization:** `X` is a designative information content entity

This classification is essential for type safety and interface stability. It explicitly defines that a system call (`X`) must have a designated return type (`Y`), and furthermore, it restricts the cardinality of this relationship to a maximum of one (`max 1`). A system call cannot return multiple conflicting types; it must resolve to a single, defined data structure.

### 4.3.2 Return Type Constraints
The return type (`Y`) of a system call is itself a DescriptiveICE. This recursive dependency reinforces the ontology's hierarchy: the function (Designative) points to a type definition (Descriptive). The `max 1` constraint is enforced at the schema level to prevent ambiguous function signatures. If a system call is recorded as returning both an Integer and a String, the record violates the core axiom and must be rectified.

The relational schema for this axiom is captured in the table `t_syscall_max_one_return`. The column `x` holds the identifier for the system call or function, while `y` holds the identifier of the return type. The foreign key constraint linking `y` to `t_lift_basic(id)` ensures that the return type is a valid, registered descriptive entity.

**Table 4-3: System Call Return Type Designations (t_syscall_max_one_return)**

| id | x | y |
| :--- | :--- | :--- |
| syscall_001 | sys_read_vent_status | desc_ent_003 |
| syscall_002 | sys_get_firmware_ver | desc_ent_005 |
| syscall_003 | sys_actuate_vent | desc_ent_002 |
| syscall_004 | sys_reset_device | desc_ent_002 |
| syscall_005 | sys_log_location | desc_ent_001 |

*Table 4-3 defines the return types for various kernel-level system calls. The `x` column lists the function names (DesignativeICE), while the `y` column references the specific return type (DescriptiveICE) from Table 4-1. For instance, `sys_read_vent_status` returns a `DeviceStatus_Enum` (`desc_ent_003`), ensuring type consistency for the calling application.*

### 4.3.3 Governance and Audit
The `t_syscall_max_one_return` table serves as the primary artifact for software compliance audits. Auditors will verify that:
1.  Every system call exposed to the facility control API has a corresponding entry in this table.
2.  The return type (`y`) is not null and points to a valid `t_lift_basic` record.
3.  No system call ID (`x`) is associated with more than one return type `y` (enforcing the `max 1` cardinality).

Non-compliance with this standard, such as a system call lacking a defined return type or pointing to an invalid descriptor, shall be flagged as a critical vulnerability in the system's safety case, potentially invalidating the compliance certification of the control software.
