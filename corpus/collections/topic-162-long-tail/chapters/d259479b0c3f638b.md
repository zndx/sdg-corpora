# Chapter 12 Standards for Descriptive and Designative Entities in Facility Documentation

This chapter defines the relational projection of three ontology axioms that classify artifacts, descriptive information content entities, and designative information content entities. The projection uses three tables whose primary-key and foreign-key constraints directly encode the subclass and existential restrictions stated in the axioms. All rows satisfy the slot types given by the axioms; cross-table joins therefore reconstruct the original Manchester expressions.

## 1 Axiom 2: Descriptive Information Content Entities

Axiom 2 states that any individual classified under `t_lift_basic` is a `cco:DescriptiveICE`. The table therefore contains only entities that carry descriptive content about facilities or procedures. Column `id` is the primary key. Column `x` holds the class name of the entity.

```sql
CREATE TABLE t_lift_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

Four rows illustrate typical descriptive entities used in county road administration documentation.

| id       | x                          |
|----------|----------------------------|
| desc001  | InspectionProtocol         |
| desc002  | EquipmentCalibrationLog    |
| desc003  | FacilityPostalDescription  |
| desc004  | ComplianceChecklist        |

## 2 Axiom 1: Artifacts Bearing Postal Addresses

Axiom 1 asserts that an artifact may be linked to a postal address via the property `sdg:hasPostalAddress`. The table `t_schemaorg_place_address` materializes this restriction. Column `id` is the primary key. Column `x` references the artifact; column `y` is a foreign key to `t_lift_basic.id` and must contain a descriptive entity that encodes the address.

```sql
CREATE TABLE t_schemaorg_place_address (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_lift_basic(id)
);
```

Six rows record facilities whose addresses are stored as descriptive entities.

| id       | x                    | y       |
|----------|----------------------|---------|
| addr001  | CountyRoadOffice     | desc003 |
| addr002  | DistrictMaintenanceYard | desc003 |
| addr003  | RegionSevenDepot     | desc003 |
| addr004  | BridgeInspectionUnit | desc003 |
| addr005  | SignalShop           | desc003 |
| addr006  | MaterialsTestingLab  | desc003 |

A reader can answer the question “which descriptive entity supplies the postal address of the MaterialsTestingLab?” by joining on `y = desc003` and filtering `x = 'MaterialsTestingLab'`.

## 3 Axiom 3: Designative Entities with Bounded Return Types

Axiom 3 classifies an entity as a `cco:DesignativeICE` that possesses at most one return type. The table `t_syscall_max_one_return` implements the qualified cardinality restriction. Column `id` is the primary key. Column `x` names the designative entity; column `y` is an optional foreign key to `t_lift_basic.id` that supplies the single permitted return type.

```sql
CREATE TABLE t_syscall_max_one_return (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_lift_basic(id)
);
```

Five rows document designative specifications used by laboratory control interfaces.

| id       | x                          | y       |
|----------|----------------------------|---------|
| spec001  | ReadCalibrationValue       | desc002 |
| spec002  | SubmitInspectionResult     | desc001 |
| spec003  | QueryFacilityAddress       | desc003 |
| spec004  | ValidateComplianceItem     | desc004 |
| spec005  | LogEquipmentStatus         | NULL    |

## 4 Cross-Table Query Example

The multi-hop question “Which descriptive entity supplies the postal address referenced by the designative specification QueryFacilityAddress?” is answered by the following join path:

1. Locate `spec003` in `t_syscall_max_one_return` → `y = desc003`.
2. Join `desc003` to `t_schemaorg_place_address` on `y`.
3. The resulting row yields `x = 'RegionSevenDepot'` together with the descriptive entity `desc003`.
