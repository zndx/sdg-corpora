# Chapter 12 Standards of Good Practice—Kernel Information Entities

This chapter specifies the relational representation of three ontological templates that govern descriptive and designative information content entities within kernel documentation schemas. The model comprises exactly three tables whose primary and foreign keys enforce the subclass and existential restrictions stated in the source axioms. All cell values are instances that satisfy the Manchester syntax restrictions; cross-table joins therefore recover the intended multi-hop relations without additional inference rules.

## 1 Scope and table inventory

Section 1.1 presents the single table that realizes the DescriptiveICE axiom. Sections 1.2 and 1.3 present the two tables that realize the Artifact-with-address and DesignativeICE-with-max-one-return axioms, respectively. Each table is preceded by a statement of the axiom it embodies, the key structure, and one example mental join. A worked multi-hop query appears in Section 2.

### 1.1 t_lift_basic

This table embodies AXIOM 2: every row populates a DescriptiveICE. Column id is the primary key; column x holds the class name of the DescriptiveICE. No foreign keys exist.

Example mental join: select the x value for a given id, then use that id as the y value in either of the following tables.

| id | x |
| --- | --- |
| desc_mem_addr | MemoryAddressDescriptor |
| desc_ret_val | ReturnValueDescriptor |
| desc_path | FilePathDescriptor |
| desc_mode | ModeDescriptor |
| desc_size | SizeDescriptor |
| desc_err | ErrorCodeDescriptor |

### 1.2 t_schemaorg_place_address

This table embodies AXIOM 1: every row asserts that an Artifact (column x) hasPostalAddress some DescriptiveICE (column y). Column id is the primary key; column y is a foreign key referencing t_lift_basic.id.

Example mental join: given an Artifact name in x, follow y to obtain the corresponding DescriptiveICE class name from t_lift_basic.

| id | x | y |
| --- | --- | --- |
| addr_kern_01 | KernelModuleVFS | desc_mem_addr |
| addr_kern_02 | KernelModuleVFS | desc_path |
| addr_proc_01 | ProcessImage | desc_mem_addr |
| addr_proc_02 | ProcessImage | desc_size |
| addr_file_01 | FileDescriptorTable | desc_path |
| addr_file_02 | FileDescriptorTable | desc_mode |

### 1.3 t_syscall_max_one_return

This table embodies AXIOM 3: every row asserts that a DesignativeICE (column x) hasReturnType max 1 DescriptiveICE (column y). Column id is the primary key; column y is a foreign key referencing t_lift_basic.id. When y is null the restriction is satisfied by absence of a return type.

Example mental join: given a DesignativeICE name in x, follow y to obtain the return-type DescriptiveICE class name from t_lift_basic, then optionally continue to an address row in t_schemaorg_place_address that shares the same DescriptiveICE.

| id | x | y |
| --- | --- | --- |
| sys_read | SyscallRead | desc_ret_val |
| sys_write | SyscallWrite | desc_ret_val |
| sys_open | SyscallOpen | desc_ret_val |
| sys_close | SyscallClose |  |
| sys_mmap | SyscallMmap | desc_mem_addr |
| sys_stat | SyscallStat | desc_size |
| sys_exit | SyscallExit | desc_err |

## 2 Cross-join demonstration

Question: which DescriptiveICE class describes the return type of the SyscallMmap designative entity, and which Artifact uses that same DescriptiveICE as a postal address?

Walk the keys: locate row sys_mmap in t_syscall_max_one_return (y = desc_mem_addr), locate row addr_kern_01 in t_schemaorg_place_address (y = desc_mem_addr), then read x from t_lift_basic where id = desc_mem_addr.

Resulting joined row:

- syscall: SyscallMmap
- return_type: MemoryAddressDescriptor
- artifact_using_same_descriptor: KernelModuleVFS
