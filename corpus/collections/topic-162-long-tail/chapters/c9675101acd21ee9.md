# Chapter 4: Ontological Classification of Hybrid Infrastructure Assets

## 4.0 Preamble and Scope

This chapter establishes the mandatory ontological framework for classifying hybrid infrastructure assets within the enterprise governance registry. It delineates the structural relationships between physical artifacts, their geospatial descriptors, and software interface definitions. The objective is to ensure data fidelity across the configuration management database (CMDB) by enforcing strict typing constraints on descriptive information content entities (ICE) and designative ICE. Compliance with these classifications is required for all audit reporting and system lineage documentation, pursuant to Governance Framework Directive 14.2.

## 4.1 Descriptive Information Content Entities

### 4.1.1 Definition and Standard of Practice

At the foundational layer of the ontology lies the concept of the Descriptive Information Content Entity (DescriptiveICE). As defined in the core axiom set, a DescriptiveICE serves as the atomic unit for data that describes, qualifies, or constrains other entities within the system. Unlike designative entities, which function as identifiers or pointers, descriptive entities encapsulate the qualitative state or metadata value of an object.

In accordance with the Manchester Syntax axiom `Class: {X:Class} SubClassOf: cco:DescriptiveICE`, any entity classified under this category is recognized solely for its capacity to convey information about a subject. This classification is critical for maintaining the separation of concerns between the *identity* of an asset and its *attributes*. For instance, a specific string representing a postal code or a data structure defining a return type is not the asset itself but a descriptive entity attached to it.

### 4.1.2 Registry Implementation

The registry maintains a distinct table, `t_lift_basic`, to record these foundational entities. The primary key (`id`) serves as the unique reference for the descriptive element, while the column `x` denotes the specific class or instance of the descriptive content. This structure ensures that all descriptive metadata is normalized and referentially intact before being associated with higher-order artifacts or software interfaces.

**Table 4-1: Descriptive Information Content Entity Registry**

| id | x |
| :--- | :--- |
| desc_001 | PostalAddressString |
| desc_002 | IntegerReturnType |
| desc_003 | VoidReturnType |
| desc_004 | PhysicalLocationDescriptor |
| desc_005 | FileDescriptorType |

The data presented in Table 4-1 illustrates the variety of descriptive classes utilized within the system. Note that `desc_001` and `desc_004` represent physical location metadata, whereas `desc_002` and `desc_003` represent software type definitions. These entities act as the "values" in the key-value pairs that constitute the asset's full configuration profile.

### 4.1.3 Compliance Verification

Auditors must verify that no descriptive entity exists in the system without a corresponding entry in the `t_lift_basic` table. Failure to register a descriptive entity—such as an ad-hoc address string or an undefined return type—constitutes a violation of data integrity standards. If a descriptive entity is identified during a scan but is not received within the registry, the asset in question must be flagged for immediate remediation.

## 4.2 Artifact Addressability and Postal Location

### 4.2.1 The Artifact-Address Relationship

The governance framework mandates that all physical artifacts—specifically those classified under `cco:Artifact`—must be linked to a valid postal address. This linkage is governed by the axiom `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`. In natural language, this asserts that for an artifact to be fully registered, it *must* possess a postal address property that points to a valid descriptive entity.

This requirement ensures that the physical footprint of the infrastructure is fully auditable. Whether the asset is a server rack, a field router, or a storage vault, its geospatial coordinates must be captured not as free text, but as a structured reference to a standardized address entity. This facilitates rapid disaster recovery planning and regulatory jurisdiction checks.

### 4.2.2 Relational Mapping and Constraints

The relationship between the artifact and its address is enforced through the `t_schemaorg_place_address` table. This table implements the foreign key constraint `FOREIGN KEY (y) REFERENCES t_lift_basic(id)`, ensuring that the address referenced (`y`) corresponds to a valid entry in the descriptive registry established in Section 4.1.

The primary key (`id`) of this table represents the unique instance of the relationship (i.e., the specific assignment of an address to an artifact). The column `x` represents the artifact instance, while `y` holds the reference to the descriptive address entity. This structure prevents orphaned address records and ensures that address normalization is applied consistently across the enterprise.

**Table 4-2: Artifact-to-Address Mapping**

| id | x | y |
| :--- | :--- | :--- |
| addr_link_01 | ServerRack_AZ04 | desc_001 |
| addr_link_02 | BackupVault_East | desc_004 |
| addr_link_03 | FieldOffice_RTR01 | desc_001 |
| addr_link_04 | DataCenter_Hub2 | desc_004 |

In Table 4-2, the artifact `ServerRack_AZ04` is linked to `desc_001` (PostalAddressString), while `BackupVault_East` utilizes `desc_004` (PhysicalLocationDescriptor). This demonstrates the flexibility of the system: different artifacts may utilize different descriptive classes for their location data, provided those classes are properly defined in the base registry.

### 4.2.3 Audit Implications

During compliance audits, the system will query `t_schemaorg_place_address` to validate that every deployed artifact has a non-null `y` value. Artifacts appearing in the asset inventory but missing a corresponding entry in this table are considered "non-compliant" regarding physical addressability. Furthermore, if the referenced `y` value is deleted or modified in the `t_lift_basic` table without a cascading update, the referential integrity constraint will raise a critical error, halting the synchronization process until the discrepancy is resolved.

## 4.3 System Call Interface Designation

### 4.3.1 Designative Information Content Entities

While Section 4.1 addressed descriptive entities, Section 4.3 focuses on designative entities. Specifically, this section covers the classification of System Calls (Syscalls) as `cco:DesignativeICE`. A Designative Information Content Entity functions as an identifier or a functional pointer within the software architecture. The axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:hasReturnType max 1 {Y:Class}` defines two critical properties: first, the entity is designative (it names a function); second, it possesses a return type relationship with a cardinality of at most one.

The constraint `max 1` is a strict governance rule. It implies that a valid system call definition within this ontology cannot be polymorphic or ambiguous regarding its primary return type in the context of the registry. While a function may logically return different values at runtime, the *definition* of the interface must point to a single, authoritative return type class. This restriction is enforced to simplify static analysis and security auditing, ensuring that every interface has a clearly defined contract.

### 4.3.2 Syscall-Return Type Schema

The `t_syscall_max_one_return` table enforces this strict one-to-one relationship between the system call (`x`) and its return type (`y`). Similar to the artifact schema, the return type (`y`) must reference a valid entry in the `t_lift_basic` table. This linkage ensures that the return type is a recognized, standardized data class (e.g., Integer, Void, or a specific File Descriptor) rather than an arbitrary string.

**Table 4-3: System Call Return Type Assignments**

| id | x | y |
| :--- | :--- | :--- |
| syscall_def_01 | sys_read | desc_002 |
| syscall_def_02 | sys_write | desc_002 |
| syscall_def_03 | sys_open | desc_005 |
| syscall_def_04 | sys_close | desc_003 |
| syscall_def_05 | sys_ioctl | desc_002 |

As evidenced in Table 4-3, `sys_read` and `sys_write` are both mapped to `desc_002` (IntegerReturnType), indicating they return a signed integer representing the count of bytes processed or an error code. Conversely, `sys_close` is mapped to `desc_003` (VoidReturnType), signifying a null or status-only return. The `sys_open` call references `desc_005` (FileDescriptorType), demonstrating the use of complex object types as return values.

### 4.3.3 Governance and Verification

The governance framework utilizes the `t_syscall_max_one_return` table to verify that the kernel interface documentation matches the implemented code. If a system call is introduced into the codebase that attempts to reference a return type ID not present in `t_lift_basic`, the build verification pipeline will fail. Additionally, the `max 1` constraint is validated by ensuring that no single `id` in the `x` column appears with multiple distinct `y` values in a single revision record.

Auditors are required to sample system calls from the production kernel and trace them back to this table. Any deviation—such as a syscall pointing to a deprecated return type descriptor—must be reported as a high-severity finding. The integrity of the software supply chain depends on the accurate mapping of these designative entities to their descriptive counterparts.
