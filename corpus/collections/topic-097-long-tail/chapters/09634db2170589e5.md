## Scope and Preamble

This chapter delineates the formal ontological structures governing the classification of kernel-level Information Content Entities (ICE) within the eBPF syscall subsystem. It provides a rigorous mapping between abstract ontology axioms—expressed in Manchester syntax—and their deterministic projection into relational schemas suitable for audit and compliance verification. The definitions herein are binding for all subsystems utilizing `cco:DesignativeICE` as a base class for syscall instrumentation. Specifically, this document addresses the logical constraints for equivalence, universal restriction, existential subclassing, and security tier stratification. Implementers must ensure that all relational instances adhere to the primary key and foreign key constraints defined in the subsequent sections to maintain referential integrity within the governance framework.

---

## 4.1 Syscall Equivalence within Subsystems

The first axiom establishes a foundational definition for classes that are equivalent to the intersection of a Designative ICE and a specific Syscall Subsystem. In formal ontology, the use of `EquivalentTo` implies a necessary and sufficient condition: a class `X` exists if and only if it is a `cco:DesignativeICE` and it participates in the `sdg:inSyscallSubsystem` relationship with class `Y`. This axiom is critical for defining subsystem-specific primitives that do not leak semantic meaning into other kernel domains.

From a compliance perspective, this axiom ensures that specific syscall classes are strictly bound to their operational context. For example, a class representing a network socket operation is ontologically distinct from a file system operation, even if they share underlying data types. The relational projection of this axiom creates a table where the relationship between the entity (`x`) and the subsystem (`y`) is mandatory and defining.

**Table 4.1: Syscall Equivalence in Subsystem Mapping**
The following table enumerates specific classes that are defined exclusively by their presence within a specific subsystem. The primary key is the identifier (`id`), ensuring each equivalence axiom is unique.

| id | x | y |
| :--- | :--- | :--- |
| `equiv_net_01` | `NetworkSocketDesignator` | `NetworkSubsystem` |
| `equiv_vfs_02` | `VFSNodeDesignator` | `FileSystemSubsystem` |
| `equiv_ipc_03` | `IPCMessageDesignator` | `IPCSubsystem` |
| `equiv_sec_04` | `SELinuxContextDesignator` | `SecuritySubsystem` |

*Table 4.1 Notes:*
*   `x` represents the Class defined by the equivalence.
*   `y` represents the Syscall Subsystem class constraining the definition.
*   The `NOT NULL` constraint on `y` enforces that an equivalence cannot exist without a subsystem context.

In the example of `NetworkSocketDesignator`, the class is not merely a member of the `NetworkSubsystem`; it is *defined* by it. Any audit query seeking instances of `NetworkSocketDesignator` can implicitly restrict its search to the `NetworkSubsystem` without loss of precision. This reduces the computational overhead of compliance scanning by isolating the domain of discourse.

## 4.2 Universal Restriction in Kernel Subsystems

While equivalence defines what a class *is*, universal restriction defines where a class *may* be. Axiom 2 utilizes the `only` constructor (`SubClassOf: ... inSyscallSubsystem only {Y}`). This asserts that any instance of class `X` utilizing the `inSyscallSubsystem` property must relate to an instance of class `Y`. It is a closed-world assumption regarding the relationship: if an `X` exists in a subsystem, that subsystem *must* be `Y`.

This distinction is vital for security governance. It prevents "type leakage" where a privileged syscall designed for one subsystem might be erroneously invoked or mapped within another. For instance, a memory management syscall intended for the virtual memory subsystem must not be valid within the process management subsystem.

**Table 4.2: Syscall Universal Restrictions**
This table records the classes that are universally restricted to specific subsystems. The schema allows for `y` to be nullable in the definition, but in practice, for the restriction to be meaningful, a target subsystem `Y` must be specified to define the boundary.

| id | x | y |
| :--- | :--- | :--- |
| `only_mem_01` | `PageTableOperation` | `MemoryManagementSubsystem` |
| `only_proc_02` | `ProcessExecutionControl` | `ProcessControlSubsystem` |
| `only_hw_03` | `DirectHardwareAccess` | `HardwareAbstractionLayer` |
| `only_time_04` | `SystemClockModifier` | `TimeKeepingSubsystem` |
| `only_audit_05` | `AuditTrailInjection` | `LoggingSubsystem` |

*Table 4.2 Notes:*
*   `x` is the Class subject to the restriction.
*   `y` is the Class defining the exclusive range of the subsystem property.

Consider the `PageTableOperation` class. The axiom `PageTableOperation SubClassOf inSyscallSubsystem only MemoryManagementSubsystem` guarantees that if an auditor finds a reference to a page table operation, it is structurally impossible for it to be linked to anything other than the `MemoryManagementSubsystem`. This provides a strong guarantee for static analysis tools verifying kernel module compliance.

## 4.3 Existential Subclassing of Syscalls

Axiom 3 introduces existential restriction (`some`) via subclassing. The verbalization "{X} is something that in syscall subsystem {Y}" indicates that for every instance of class `X`, there exists at least one relationship to an instance of class `Y` via the `inSyscallSubsystem` property. Unlike universal restriction, this does not preclude `X` from having relationships with other classes, nor does it define `X` exclusively by `Y`. It merely asserts existence.

This axiom is useful for broad categorization and instrumentation. It allows for the definition of generic syscall classes that may span multiple subsystems but are guaranteed to be present in at least one. This is particularly relevant for eBPF programs that hook into generic tracepoints which might be triggered by various subsystems, yet must be classified for monitoring purposes.

**Table 4.3: Syscall Existential Subclassing**
The table below lists classes that are known to manifest within specific subsystems. The `NOT NULL` constraint on `y` ensures that the existential claim is grounded in a specific target class.

| id | x | y |
| :--- | :--- | :--- |
| `sub_read_01` | `GenericReadOperation` | `IOSubsystem` |
| `sub_write_02` | `GenericWriteOperation` | `IOSubsystem` |
| `sub_sync_03` | `CacheSynchronization` | `MemoryManagementSubsystem` |
| `sub_signal_04` | `InterProcessSignal` | `IPCSubsystem` |
| `sub_alloc_05` | `ResourceAllocation` | `ResourceManagementSubsystem` |
| `sub_cap_06` | `CapabilityCheck` | `SecuritySubsystem` |

*Table 4.3 Notes:*
*   `x` represents the broader Class being subclassed.
*   `y` represents the Subsystem where instances of `X` are guaranteed to be found.

For example, `GenericReadOperation` is a class that might apply to files, pipes, or sockets. By asserting it is a subclass of entities in the `IOSubsystem`, we ensure that any read operation is audited under the I/O governance framework, even if the specific implementation details vary across different kernel drivers.

## 4.4 Security Tier Stratification

The final axiom addresses the security classification of syscall entities. Axiom 4 asserts that a class `X` is a subclass of `cco:DesignativeICE` that exists at a specific security tier `Y` (`atSecurityTier some {Y}`). This maps the functional ontology to a security governance model, enabling automated enforcement of access controls and policy restrictions based on the stratification of the syscall.

In high-assurance systems, not all syscalls are created equal. Operations running at Ring 0 (supervisor mode) require vastly different auditing and logging standards than those operating at Ring 3 (user mode) or within a sandboxed environment. This axiom allows the ontology to explicitly encode these tiers, facilitating automated policy generation.

**Table 4.4: Syscall Security Tier Classification**
The following table maps syscall classes to their mandated security tiers. This mapping is essential for generating the "Security Manifest" required for kernel module certification.

| id | x | y |
| :--- | :--- | :--- |
| `tier_01` | `KernelModeHook` | `Tier0_Supervisor` |
| `tier_02` | `UserModeProbe` | `Tier3_Application` |
| `tier_03` | `SandboxedSyscall` | `Tier4_Isolated` |
| `tier_04` | `HypervisorIntervention` | `Tier_Minus1_Hypervisor` |
| `tier_05` | `SecureEnclaveCall` | `Tier_Secure_Enclave` |
| `tier_06` | `DirectMemoryAccess` | `Tier0_Supervisor` |

*Table 4.4 Notes:*
*   `x` is the Class representing the syscall or ICE.
*   `y` is the Security Tier Class defining the privilege level.

The classification of `KernelModeHook` as `Tier0_Supervisor` triggers specific compliance requirements, such as mandatory signed binaries and real-time execution monitoring. Conversely, `SandboxedSyscall` mapped to `Tier4_Isolated` might be subject to rate limiting and strict I/O denial policies. By embedding these tiers directly into the ontology, the system ensures that security posture is not an afterthought but a structural property of the syscall definition itself.
