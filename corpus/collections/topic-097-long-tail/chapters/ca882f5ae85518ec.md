# Chapter 4: Ontological Classification of Kernel Entities and Security Tiers

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for classifying Information Control Elements (ICE) within the eBPF kernel environment. It delineates the structural relationships between system call entities, their respective subsystems, and the security tiers governing their operation. The definitions provided herein are derived from the core ontology axioms governing kernel object interaction and are intended to serve as the authoritative reference for compliance auditing, system hardening, and runtime verification. By rigorously defining these relationships, organizations can ensure that kernel-level extensions adhere to strict architectural boundaries and security mandates.

## 4.2 Equivalence Definitions in Subsystem Contexts

### 4.2.1 Conceptual Overview

The first foundational axiom addresses the precise definition of entity classes through equivalence. In the context of kernel ontology, equivalence is utilized to assert that a specific class of Information Control Elements (ICE) is *identical* to the intersection of the general `cco:DesignativeICE` class and a specific subsystem context. This is not merely a subclass relationship but a definitive characterization: if an entity belongs to the defined class, it must be a Designative ICE operating within the specified subsystem, and conversely, any Designative ICE operating within that subsystem belongs to the defined class.

This distinction is critical for auditability. When a security policy references a class defined by equivalence, it is referencing a closed set of behaviors and properties that are strictly bound to a specific kernel domain. This prevents scope creep where entities might be loosely associated with a subsystem but actually possess characteristics alien to it. For system architects, this axiom provides a mechanism to create "sealed" definitions that guarantee consistency across the kernel surface.

### 4.2.2 Relational Implementation

The equivalence relationship is modeled in the relational schema to enforce strict type checking. The primary key is the identifier `id`, which serves as the unique reference for the equivalence rule. The columns `x` and `y` represent the specific Class being defined and the Subsystem Class it is equivalent to, respectively. This structure ensures that every defined class `x` is inextricably linked to a single subsystem context `y` for the purpose of this equivalence constraint.

| :--- | :--- | :--- |

### 4.2.3 Operational Implications

Consider the entry where `x` is `NetlinkAuditICE` and `y` is `NetlinkSubsystem`. This axiom asserts that the class `NetlinkAuditICE` is exactly equivalent to those Designative ICEs that exist within the `NetlinkSubsystem`. Consequently, any audit tool scanning for `NetlinkAuditICE` instances is effectively scanning for Designative ICEs within the Netlink domain. This eliminates ambiguity in compliance reporting. If a kernel module attempts to register a Designative ICE as `NetlinkAuditICE` but places it outside the `NetlinkSubsystem`, the ontology—and by extension, the validation logic—flags this as a category error. This ensures that the semantic label of the entity matches its structural location within the kernel architecture.

## 4.3 Universal Restrictions in Kernel Subsystems

### 4.3.1 Conceptual Overview

While equivalence defines what a class *is*, the second axiom introduces a universal restriction to define where a class *may* exist. This axiom states that a class `X` is a subclass of `cco:DesignativeICE` subject to the restriction that it may only exist within the syscall subsystem `Y`. In formal ontology, this is a "only" (universal) restriction. It dictates that for any instance of class `X`, all values of the property `inSyscallSubsystem` must be members of class `Y`.

This is a more permissive definition than equivalence but a more restrictive one than simple existence. It allows for the possibility that other entities might exist in subsystem `Y`, but it strictly forbids instances of `X` from existing anywhere else. From a security governance perspective, this is the primary mechanism for enforcing sandboxing and domain isolation. It ensures that specific, potentially dangerous classes of ICEs cannot "leak" into unrelated subsystems where they might violate Least Privilege principles.

The table below embodies the axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:inSyscallSubsystem only {Y:Class}`. The primary key `id` uniquely identifies the restriction rule. The column `x` holds the subclass being restricted, while `y` defines the allowable subsystem. This schema enforces the logical constraint that `x` cannot be associated with any subsystem other than `y`.

**Table 4-2: Universal Restrictions on Subsystem Membership**

| id | x | y |
| :--- | :--- | :--- |
| only_001 | `MemoryManagerICE` | `MMSubsystem` |
| only_002 | `CryptoOperationICE` | `CryptoSubsystem` |
| only_003 | `KeyringAccessICE` | `KeyManagement` |
| only_004 | `SELinuxHookICE` | `SecurityFramework` |
| only_005 | `BPFVerifierICE` | `BPFInfrastructure` |

### 4.3.3 Operational Implications

Examine the restriction defined in `only_002`, where `CryptoOperationICE` is restricted to the `CryptoSubsystem`. This axiom guarantees that a cryptographic operation entity cannot be instantiated within, for example, the `NetlinkSubsystem` or `DeviceDriver` subsystem. Even if an attacker gains the ability to instantiate kernel objects, they are bounded by this ontological constraint. If the system attempts to assign a `CryptoOperationICE` instance to a subsystem other than `CryptoSubsystem`, the constraint is violated. This is particularly relevant for modular kernels where drivers or modules might be loaded dynamically; the ontology serves as a validation layer, rejecting any module that attempts to place restricted entities in unauthorized domains.

## 4.4 Existential Subclassing for Subsystem Membership

### 4.4.1 Conceptual Overview

The third axiom shifts from restriction to requirement via existential subclassing. This axiom asserts that a class `X` is a subclass of `cco:DesignativeICE` and that it must have *some* relationship to a subsystem `Y`. In logical terms, this is a "some" (existential) restriction. It mandates that for every instance of `X`, there must exist at least one value for the property `inSyscallSubsystem` that is a member of `Y`.

Unlike the universal restriction, this axiom does not necessarily forbid `X` from existing in other subsystems (unless combined with other axioms). However, it guarantees that `X` is present in `Y`. This is essential for defining core functionalities that must span multiple domains or ensuring that a specific subsystem always contains a specific type of control element. It is the ontological equivalent of a mandatory dependency.

### 4.4.2 Relational Implementation

The table below embodies the axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:inSyscallSubsystem some {Y:Class}`. The primary key `id` identifies the subclass rule. The columns `x` and `y` represent the subclass and the required subsystem, respectively. The structure enforces that `x` cannot exist without being associated with `y`.

**Table 4-3: Existential Requirements for Subsystem Presence**

| id | x | y |
| :--- | :--- | :--- |
| sub_001 | `FileDescriptorICE` | `VirtualFileSystem` |
| sub_002 | `IPCMessageICE` | `IPCSubsystem` |
| sub_003 | `SyscallEntryICE` | `CoreKernel` |
| sub_004 | `CapabilityCheckICE` | `SecurityFramework` |
| sub_005 | `TimerEventICE` | `TimeKeeping` |

### 4.4.3 Operational Implications

Consider the rule `sub_001`, which requires `FileDescriptorICE` to be present in the `VirtualFileSystem` subsystem. This ensures that any file descriptor entity is fundamentally linked to the VFS. However, because this is an existential restriction, it does not preclude the `FileDescriptorICE` from also being associated with a `NetworkStack` subsystem in scenarios involving socket files. The axiom ensures a baseline of presence: the VFS must be involved. For compliance auditors, this provides a check for "minimum viable presence." If a system component claims to implement file handling but lacks the requisite `FileDescriptorICE` instances within the `VirtualFileSystem` subsystem, the implementation is ontologically incomplete and non-compliant.

## 4.5 Security Tier Assignment

### 4.5.1 Conceptual Overview

The final axiom governs the classification of entities based on their security criticality. It asserts that a class `X` is a subclass of `cco:DesignativeICE` that exists at a specific security tier `Y`. This axiom maps the structural entity to a security classification, enabling policy-driven enforcement based on the sensitivity of the operation. Security tiers typically represent hierarchical levels of trust, privilege, or data sensitivity (e.g., Tier 0 for kernel-land critical operations, Tier 1 for sensitive user-land interfaces, etc.).

By embedding security tiering directly into the ontology, the system architecture moves beyond ad-hoc permission checks to a model where security posture is an intrinsic property of the entity class. This facilitates automated policy enforcement; for instance, a runtime monitor could automatically block any interaction between a `Tier3` entity and a `Tier0` resource based solely on their class definitions.

The table below embodies the axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}`. The primary key `id` uniquely identifies the tier assignment. Column `x` represents the Designative ICE class, and column `y` represents the Security Tier class. This schema links functional entities to their mandated security level.

**Table 4-4: Security Tier Classifications**

| id | x | y |
| :--- | :--- | :--- |
| tier_001 | `HypervisorMgmtICE` | `TierZeroCritical` |
| tier_002 | `UserAuthICE` | `TierOneSensitive` |
| tier_003 | `GenericIOICE` | `TierTwoStandard` |
| tier_004 | `NetworkLoggingICE` | `TierTwoStandard` |
| tier_005 | `DebugInterfaceICE` | `TierThreeRestricted` |

### 4.5.3 Operational Implications

The classification in `tier_001` assigns `HypervisorMgmtICE` to `TierZeroCritical`. This designation triggers the most stringent security controls available in the system. Any instance of `HypervisorMgmtICE` inherits the constraints associated with `TierZeroCritical`, which might include mandatory code signing, strict memory isolation, and real-time audit logging. Conversely, `GenericIOICE` is classified as `TierTwoStandard`, allowing for more flexible handling but subject to standard sandboxing rules. This ontological stratification ensures that security resources are allocated proportionally to the risk profile of the entity, and it provides a clear data model for automated compliance scanners to verify that high-value assets are correctly classified and protected.
