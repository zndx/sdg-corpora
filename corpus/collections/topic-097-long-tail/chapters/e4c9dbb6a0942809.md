# Chapter 4: Formal Classification of Designative ICE within Kernel Subsystems

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the classification of Designative Information Control Elements (ICE) within the context of extended Berkeley Packet Filter (eBPF) kernel subsystems. The objective is to establish a rigorous framework for defining syscall interactions, subsystem containment, and security tier stratification. The definitions provided herein are derived from a set of core axioms that map logical constraints to relational data structures, ensuring consistency across kernel-level audit trails and compliance verification mechanisms. Each section introduces a specific axiom, verbalizes its logical implication, and provides tabular evidence of its application within a controlled environment.

## 4.2 Equivalence in Syscall Subsystems

### 4.2.1 Conceptual Definition

The first foundational axiom addresses the logical equivalence between a specific class of Designative ICE and its containment within a particular syscall subsystem. In formal ontology, equivalence is a strong assertion that requires two conditions to be met simultaneously: an entity must be an instance of the defined class *and* it must possess a specific relationship to the subsystem. This relationship is bidirectional in its implication for classification; if an entity is identified as belonging to Class X, it is axiomatically a Designative ICE located within Subsystem Y, and conversely, any Designative ICE within Subsystem Y that meets the defining criteria of X falls into this classification.

This axiom is critical for defining boundaries where the subsystem context is the sole differentiator for the ICE type. For example, network operations are often strictly defined by their presence within the network subsystem. The Manchester syntax for this axiom is expressed as `Class: {X:Class} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})`. This structure ensures that the classification is not merely a property but a fundamental definition of the entity's existence within the system architecture.

### 4.2.2 Relational Mapping and Evidence

The relational projection of this equivalence axiom creates a schema where the primary key identifies the specific equivalence rule, linking the defined Class (X) to the requisite Subsystem (Y). The constraint `y NOT NULL` enforces the axiom's requirement that the subsystem context is mandatory for the equivalence to hold.

## 4.3 Universal Restriction in Kernel Subsystems

### 4.3.1 Conceptual Definition

While equivalence defines what a class *is*, universal restriction defines what a class is *permitted to be*. The second axiom introduces a restriction on the `sdg:inSyscallSubsystem` property using the logical quantifier "only." This axiom asserts that if an entity belongs to Class X, and it participates in the `inSyscallSubsystem` relationship, the value of that relationship *must* be an instance of Class Y.

The verbalization of this axiom is: "{X} is something that in syscall subsystem {Y}." In practical governance terms, this acts as a constraint mechanism. It does not assert that the entity must be in a subsystem, but rather that *if* a subsystem association exists, it is restricted to a specific domain. This is particularly relevant for kernel modules that may be dormant or abstractly defined without active subsystem binding, yet which must never be erroneously associated with restricted subsystems (e.g., a user-space interface must not map to a kernel-internal memory subsystem).

### 4.3.2 Relational Mapping and Evidence

The schema for this axiom, `t_syscall_only_in_kernel_subsystem`, captures these restriction rules. Unlike the equivalence table, the `y` column is nullable in the SQL definition (though typically populated in the definition of the rule), reflecting that the axiom restricts the *range* of the property rather than asserting its mandatory existence. However, for the purpose of defining the restriction rules, the table is populated with the permitted target classes.

**Table 4.2: Universal Restrictions on Syscall Subsystems**

| id | x (Class) | y (Subsystem) |
| :--- | :--- | :--- |
| only_001 | KernelMemoryICE | MemoryManagementSubsystem |
| only_002 | HardwareInterruptICE | IRQSubsystem |
| only_003 | CryptoOperationICE | CryptoSubsystem |
| only_004 | SELinuxEnforcementICE | SecuritySubsystem |

*Table 4.2 details the universal restrictions. The entry `only_001` formalizes the rule that any `KernelMemoryICE` entity may only be associated with the `MemoryManagementSubsystem`. This prevents misclassification during dynamic analysis where a memory operation might incorrectly appear in an I/O subsystem log.*

## 4.4 Existential Subsystem Inheritance

### 4.4.1 Conceptual Definition

The third axiom shifts from restriction to existential quantification. It asserts that Class X is a subclass of `cco:DesignativeICE` and that there exists at least one relationship to a subsystem Y. The Manchester syntax `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:inSyscallSubsystem some {Y:Class}` utilizes the "some" operator, which implies necessity of existence.

Verbalized as "{X} is something that in syscall subsystem {Y}", this axiom ensures that for an entity to be classified as X, it *must* have a footprint in subsystem Y. This differs from the "only" restriction, which limits possibilities, by actively requiring the presence of the relationship. This is the standard inheritance pattern for active syscall wrappers; a process control ICE is not merely theoretically capable of belonging to the process subsystem—it *must* be instantiated within it to be valid.

### 4.4.2 Relational Mapping and Evidence

The corresponding relational schema enforces that the subsystem reference (`y`) is `NOT NULL`. This structural constraint mirrors the logical axiom: the subclass definition is invalid without the specified subsystem context.

**Table 4.3: Existential Subsystem Inheritance**

| id | x (Class) | y (Subsystem) |
| :--- | :--- | :--- |
| sub_001 | ProcessForkICE | ProcessManagementSubsystem |
| sub_002 | FileDescriptorICE | FileDescriptorSubsystem |
| sub_003 | ThreadSynchronizeICE | ThreadSubsystem |
| sub_004 | TimerExpirationICE | TimerSubsystem |
| sub_005 | KeyManagementICE | KeyringSubsystem |

*Table 4.3 provides evidence of existential inheritance. The record `sub_001` dictates that `ProcessForkICE` is a subclass of Designative ICE that necessarily exists within the `ProcessManagementSubsystem`. This ensures that any audit event identifying a `ProcessForkICE` can be reliably traced back to process management logs.*

## 4.5 Security Tier Stratification

### 4.5.1 Conceptual Definition

The final axiom introduces the dimension of security clearance or privilege level, referred to as the "security tier." This axiom classifies Designative ICE not just by functional subsystem, but by the security tier at which they operate. The logical structure `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}` asserts that Class X exists at Security Tier Y.

This stratification is essential for compliance frameworks that enforce separation of duties or privilege boundaries. It allows auditors to query for all ICEs operating at a specific sensitivity level (e.g., "Ring 0" or "Hypervisor") regardless of their functional subsystem. The verbalization "{X} is something that at security tier {Y}" emphasizes that the security tier is an inherent, existential property of the class itself.

### 4.5.2 Relational Mapping and Evidence

The relational schema `t_syscall_at_security_tier` links the specific ICE class to its mandated security tier. The non-null constraint on `y` ensures that every classified ICE in this context is assigned a definitive security tier, preventing privilege ambiguity.

**Table 4.4: Security Tier Classifications**

| id | x (Class) | y (Security Tier) |
| :--- | :--- | :--- |
| tier_001 | SupervisorModeICE | Ring0_Tier |
| tier_002 | UserModeICE | Ring3_Tier |
| tier_003 | HypervisorCallICE | VMXRoot_Tier |
| tier_004 | SecureMonitorICE | EL3_Tier |
| tier_005 | SystemCallEntryICE | Boundary_Tier |

*Table 4.4 categorizes ICE classes by their security tier. For instance, `tier_001` explicitly places `SupervisorModeICE` at the `Ring0_Tier`. This classification is vital for automated compliance scanners that flag any operation involving `SupervisorModeICE` occurring outside of `Ring0_Tier` contexts as a critical security violation.*
