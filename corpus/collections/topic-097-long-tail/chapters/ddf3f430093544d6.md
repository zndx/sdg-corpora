# Chapter 4: Formal Classification of Syscall Entities within eBPF Security Domains

## 4.1 Preamble and Scope

This chapter establishes the formal ontological framework for classifying Information Control Elements (ICE) within the extended Berkeley Packet Filter (eBPF) kernel subsystem. The primary objective is to define a rigorous, auditable schema for mapping syscall entities to their respective security domains and subsystems. Adherence to these definitions is mandatory for ensuring compliance with kernel-level governance protocols and for maintaining the integrity of runtime security monitoring. The definitions provided herein utilize the Manchester Syntax for Web Ontology Language (OWL) expressions, translated into relational data structures suitable for integration into compliance auditing tools. This specification addresses the logical constraints governing syscall equivalence, universal restriction within kernel subsystems, existential subclassing, and security tier stratification.

## 4.2 Syscall Equivalence in Subsystems

### 4.2.1 Conceptual Definition

The foundational axiom for defining syscall equivalence asserts that a specific class of entities is identical to the intersection of a Designative ICE and a specific Syscall Subsystem. Formally, this is expressed as: `Class: {X:Class} EquivalentTo: cco:DesignativeICE and (sdg:inSyscallSubsystem some {Y:Class})`.

In practical terms, this axiom defines a necessary and sufficient condition. For an entity to be classified as `X`, it must be a Designative ICE, and it must reside within the subsystem `Y`. Conversely, any Designative ICE residing within subsystem `Y` is classified as `X`. This bidirectional implication is critical for automated reasoning engines, as it allows for the unambiguous identification of syscall behaviors without manual intervention. It eliminates ambiguity in audit logs by ensuring that the classification of an entity is strictly bound to its operational context within the kernel.

### 4.2.2 Implementation and Constraints

When implementing this equivalence in a relational database, the primary key serves as the unique identifier for the logical assertion. The foreign key relationships are implicit in the data types; `x` represents the specific class of the syscall entity, while `y` represents the subsystem. The constraint `y NOT NULL` ensures that the equivalence cannot be defined without a valid subsystem context, thereby preventing orphaned or undefined classifications within the registry.

### 4.2.3 Audit Verification

To verify compliance with this axiom, auditors must query the runtime environment to confirm that all instances of `X` are exclusively triggered within the bounds of `Y`. Any deviation—such as a `NetworkSocketBind` operation occurring outside the `NetlinkSubsystem`—constitutes a critical security failure and indicates a potential compromise of the kernel's address space layout or a failure in the syscall table resolution.

## 4.3 Universal Restriction in Kernel Subsystems

### 4.3.1 Conceptual Definition

The second axiom governs the universal restriction of syscall entities. It is formally defined as: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:inSyscallSubsystem only {Y:Class}`. The verbalization of this axiom states: `{X} is something that in syscall subsystem {Y}`.

This axiom introduces a constraint of exclusivity. Unlike the equivalence axiom, which defines identity, this axiom defines a boundary. It asserts that if an entity is a member of class `X`, then its relationship to the `inSyscallSubsystem` property is restricted *only* to the class `Y`. This means that instances of `X` cannot legally or logically exist within any subsystem other than `Y`. This is a powerful construct for enforcing isolation boundaries, ensuring that high-privilege operations cannot be inadvertently migrated to less-secure subsystems.

### 4.3.2 Implementation and Constraints

The relational schema for this axiom tracks the subclass `x` and its permitted subsystem `y`. While the schema definition provided does not explicitly enforce a `NOT NULL` constraint on `y` at the database level, the logical axiom implies that a null value would render the restriction meaningless. Therefore, for all compliance records, `y` must be populated. This table serves as a "Negative Allowlist"; it defines the only valid environment in which `X` may operate.

The following data matrix details the universal restrictions applied to sensitive kernel operations.

| :--- | :--- | :--- |
| U-101 | `MMU_PageTableWalk` | `MemoryManagementUnit` |
| U-102 | `HardwareInterruptAck` | `InterruptController` |
| U-103 | `SystemClockUpdate` | `TimekeepingSubsystem` |
| U-104 | `DirectMemoryAccess` | `DMA_Controller` |

*Table 4.2 Notes:*

### 4.3.3 Security Implications

The enforcement of universal restrictions is paramount for preventing "confused deputy" problems within the kernel. For instance, the `MMU_PageTableWalk` operation (U-101) is restricted solely to the `MemoryManagementUnit`. If a rogue process attempts to invoke this functionality via the `DeviceDriverSubsystem`, the violation of this axiom will trigger an access control violation in the eBPF verifier. This axiom forms the basis for kernel hardening techniques that isolate critical memory management functions from generic device drivers.

## 4.4 Existential Subclassing of Syscalls

### 4.4.1 Conceptual Definition

The third axiom addresses existential subclassing, expressed as: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:inSyscallSubsystem some {Y:Class}`. The verbalization is: `{X} is something that in syscall subsystem {Y}`.

This axiom differs from the universal restriction in that it does not imply exclusivity. Instead, it asserts existence. It states that class `X` is a subclass of Designative ICE that exists in *at least one* instance of subsystem `Y`. This allows for flexibility, acknowledging that while `X` is certainly found in `Y`, it may also appear in other subsystems. This classification is useful for defining broad categories of syscalls that have polymorphic behavior across different kernel components.

### 4.4.2 Implementation and Constraints

In the relational model, this is structurally similar to the equivalence axiom but semantically distinct. The `y` column is mandatory (`NOT NULL`), as the existential claim requires a specific target. However, the absence of a "only" constraint in the axiom means that other rows with the same `x` but different `y` values may exist in the dataset without violating the ontology.

The following table provides a subset of existential subclass mappings, illustrating entities that are known to inhabit specific subsystems without being restricted to them.

**Table 4.3: Existential Subclass Mappings**

| ID | Subclass (X) | Known Subsystem (Y) |
| :--- | :--- | :--- |
| S-201 | `CapabilityCheck` | `LSM_Framework` |
| S-202 | `ResourceQuotaEnforcement` | `CgroupController` |
| S-203 | `NamespaceOperation` | `ProcessNamespace` |
| S-204 | `SocketFiltering` | `NetworkStack` |
| S-205 | `FilesystemMount` | `VFS_Subsystem` |

*Table 4.3 Notes:*
*   **ID**: Unique identifier for the subclass assertion.
*   **Subclass (X)**: The entity being classified.
*   **Known Subsystem (Y)**: A subsystem where the entity is known to reside.

### 4.4.5 Governance and Usage

Existential subclassing is primarily utilized for dynamic observability. When an auditor or monitoring tool queries for instances of `CapabilityCheck` (S-201), this axiom guarantees that they will be found within the `LSM_Framework`. However, it does not preclude the existence of similar checks in other security modules. This axiom is essential for constructing comprehensive audit trails that must account for entities operating across multiple, potentially overlapping domains.

## 4.5 Security Tier Stratification

### 4.5.1 Conceptual Definition

The final axiom defines the security tier stratification of syscall entities. It is formally defined as: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:atSecurityTier some {Y:Class}`. The verbalization states: `{X} is something that at security tier {Y}`.

This axiom maps technical entities to an abstract security classification. It asserts that a given class `X` operates at a specific security tier `Y`. This is crucial for Role-Based Access Control (RBAC) enforcement and for prioritizing audit alerts. The concept of "Security Tier" allows the ontology to separate low-level operational noise (Tier 1) from critical security events (Tier 3).

### 4.5.2 Implementation and Constraints

The relational schema requires a non-null value for the security tier `y`. This ensures that every entity classified under this axiom has a defined security posture. The data types for `x` and `y` are consistent with previous tables, maintaining referential integrity across the ontology.

The table below presents the security tier assignments for critical syscall entities, as defined by the organizational security policy.

**Table 4.4: Security Tier Classifications**

| ID | Entity Class (X) | Security Tier (Y) |
| :--- | :--- | :--- |

| T-302 | `KernelModuleLoad` | `Tier3_Critical` |
| T-303 | `StandardIO` | `Tier1_Public` |
| T-304 | `CryptographicKeyExchange` | `Tier3_Critical` |
| T-305 | `SystemConfigurationWrite` | `Tier2_Restricted` |

*Table 4.4 Notes:*
*   **ID**: Unique identifier for the tier assignment.
*   **Entity Class (X)**: The syscall entity being classified.
*   **Security Tier (Y)**: The assigned security tier level.

### 4.5.3 Operational Impact

Security tier stratification directly influences the behavior of automated monitoring systems. For example, events classified as `Tier3_Critical` (T-302, T-304) trigger immediate alerting and may require manual forensics review. In contrast, `Tier1_Public` events (T-303) may be logged passively for retrospective analysis without generating real-time alerts. This axiom enables the efficient allocation of security resources by filtering entities based on their inherent risk profile.
