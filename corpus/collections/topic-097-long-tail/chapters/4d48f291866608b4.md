# Chapter 4: Ontological Mapping of System Call Interfaces and Security Tiers

## 4.1 Scope and Preamble

This chapter establishes the formal ontological definitions required for the classification and auditing of kernel-level system calls within the eBPF monitoring framework. It delineates the structural relationships between Information Content Entities (ICE), their containment within specific subsystems, and their association with hierarchical security tiers. The specifications provided herein ensure that designative entities are rigorously mapped to their execution contexts, facilitating automated compliance checks and runtime policy enforcement. All definitions adhere to the core ontology axioms governing Designative ICEs and are intended for use by kernel security architects and system validation engineers.

## 4.2 Equivalence in Syscall Subsystems

### 4.2.1 Definition and Specification

The axiom `syscall_equiv_in_subsystem` provides a necessary and sufficient condition for class definition within the kernel ontology. It asserts that a specific class of Designative Information Content Entity (ICE) is equivalent to the intersection of the general class `cco:DesignativeICE` and the restriction that the entity must reside within a specific syscall subsystem.

In formal terms, for a given class $X$ and a subsystem $Y$, $X$ is defined exactly as those entities that are designative and are located in subsystem $Y$. This creates a closed-world definition for the entity $X$, meaning that if an entity is a Designative ICE and it is located in subsystem $Y$, it is necessarily an instance of $X$, and conversely, all instances of $X$ must satisfy these conditions. This axiom is critical for defining subsystem-specific interfaces where the scope of the entity is strictly bounded by the subsystem's domain.

### 4.2.2 Implementation Guidance

When implementing audit rules based on this axiom, the verification engine must confirm that the observed system call maps to a class that is exclusively defined by its subsystem context. For example, a file handle operation is not merely a generic event; it is ontologically equivalent to a Designative ICE specifically within the Virtual File System (VFS) subsystem.

The following table enumerates specific class equivalences derived from this axiom, linking the defined class ($X$) to its requisite subsystem ($Y$).

**Table 4-1: Syscall Equivalence in Subsystem Mappings**

| id | x (Class) | y (Subsystem) |
| :--- | :--- | :--- |
| equiv_001 | VFSOperation | VirtualFileSystem |
| equiv_002 | NetlinkSocketOperation | NetlinkSubsystem |
| equiv_003 | ProcessControlOperation | ProcessManager |
| equiv_004 | DeviceControlOperation | DeviceDriverInterface |
| equiv_005 | KeyringOperation | KernelKeyRetention |

### 4.2.3 Verification Protocol

To validate compliance with `syscall_equiv_in_subsystem`, auditors must verify that no instance of class $X$ manifests outside of subsystem $Y$. Any detection of a `VFSOperation` occurring outside the `VirtualFileSystem` subsystem constitutes a critical ontology violation and suggests a kernel space corruption or a sophisticated rootkit attempting to masquerade entity types.

## 4.3 Universal Restriction in Kernel Subsystems

### 4.3.1 Definition and Specification

The axiom `syscall_only_in_kernel_subsystem` imposes a universal restriction on the class $X$. It asserts that $X$ is a subclass of `cco:DesignativeICE` and that the relationship `sdg:inSyscallSubsystem` holds *only* for instances of the specific subsystem $Y$.

This differs from equivalence by defining a constraint on the range of the subsystem property. While equivalence defines *what* the class is, the universal restriction defines *where* the class is allowed to exist. It dictates that for every instance of $X$, if it is in a subsystem, that subsystem must be $Y$. This prevents the propagation of the entity $X$ into unauthorized or unrelated kernel domains, thereby enforcing strict isolation boundaries.

### 4.3.2 Implementation Guidance

This axiom is utilized for high-security isolation mechanisms. It ensures that sensitive operations, such as those modifying the memory management unit or the scheduler, cannot be inadvertently triggered or referenced by less privileged subsystems. The verbalization "$X$ is something that in syscall subsystem $Y$" implies that $Y$ is the sole permissible environment for $X$.

The relational mapping below identifies classes that are universally restricted to specific subsystems.

**Table 4-2: Universal Subsystem Restrictions**

| id | x (Class) | y (Subsystem) |
| :--- | :--- | :--- |
| only_001 | SchedulerTick | SchedCore |
| only_002 | PageTableModification | MemoryManager |
| only_003 | InterruptHandler | IRQCore |
| only_004 | SELinuxEnforcement | LSMFramework |
| only_005 | BPFVerifierCall | BPFCore |

### 4.3.3 Security Implications

The `syscall_only_in_kernel_subsystem` axiom is foundational for "least privilege" kernel design. By constraining `PageTableModification` to the `MemoryManager`, the ontology ensures that network or device driver subsystems cannot directly invoke memory page table operations. Any cross-subsystem invocation violating this table must be blocked by the runtime security monitor.

## 4.4 Existential Restriction in Syscall Subsystems

### 4.4.1 Definition and Specification

The axiom `syscall_subclass` introduces an existential restriction. It states that class $X$ is a subclass of `cco:DesignativeICE` and that there exists at least one relationship `sdg:inSyscallSubsystem` to the subsystem $Y$.

Unlike the universal restriction (which limits the entity to *only* $Y$), the existential restriction asserts that the entity $X$ *must* be present in subsystem $Y$, but it does not preclude $X$ from also being present in other subsystems. This is appropriate for polymorphic entities or operations that span multiple kernel domains, such as logging or auditing functions that may be triggered by various subsystems but have a primary definition in a specific context.

### 4.4.2 Implementation Guidance

This axiom facilitates the mapping of cross-cutting concerns. For instance, a `SystemLog` event is defined as a Designative ICE that exists in the `AuditSubsystem`. However, the `AuditSubsystem` may receive inputs from the `NetworkSubsystem` or `FileSystem`. The existential restriction anchors the class definition to its primary functional domain while allowing interaction with others.

The following data table illustrates the subclass relationships where the entity $X$ necessarily participates in subsystem $Y$.

| :--- | :--- | :--- |

| sub_002 | FileDescriptorEvent | FileDescriptorTable |
| sub_003 | SignalDelivery | SignalSubsystem |
| sub_004 | UprobeEvent | UprobesSubsystem |
| sub_005 | CgroupOperation | CgroupController |

### 4.4.3 Audit and Compliance

When auditing against `syscall_subclass`, the verification logic confirms that the specific subsystem $Y$ is engaged during the lifecycle of entity $X$. A failure to detect $X$ within $Y$ indicates a broken dependency or a misconfigured kernel environment where the essential subsystem is not loaded or active.

## 4.5 Security Tier Classification

### 4.5.1 Definition and Specification

The axiom `syscall_at_security_tier` classifies entities based on their security privilege level. It asserts that class $X$ is a subclass of `cco:DesignativeICE` and that it exists at a specific security tier $Y$ via the `sdg:atSecurityTier` property.

Security tiers represent hierarchical levels of trust and privilege within the kernel architecture (e.g., Ring 0, Ring 3, or custom hypervisor tiers). This axiom is essential for Mandatory Access Control (MAC) systems, as it provides the ontological basis for determining whether a specific Designative ICE has the clearance to execute or interact with specific kernel resources.

### 4.5.2 Implementation Guidance

Entities classified at higher security tiers (e.g., `HypervisorTier` or `KernelModeTier`) are subject to stricter validation and fewer allowable transitions compared to those at lower tiers (e.g., `UserModeTier`). The axiom "$X$ is something that at security tier $Y$" allows the security framework to filter system calls based on the caller's current context and the target operation's tier requirement.

The table below provides the classification of critical kernel entities according to their requisite security tiers.

**Table 4-4: Security Tier Classifications**

| id | x (Class) | y (Security Tier) |
| :--- | :--- | :--- |
| tier_001 | SyscallEntry | UserBoundaryTier |
| tier_002 | KernelModuleLoad | KernelModeTier |
| tier_003 | Hypercall | HypervisorTier |
| tier_004 | SecureBootCheck | FirmwareTier |
| tier_005 | TEEOperation | TrustedExecutionTier |

### 4.5.3 Enforcement Mechanisms

Enforcement of `syscall_at_security_tier` involves checking the stack frame and privilege registers of the calling process against the tier defined for the target class $X$. For instance, an attempt to invoke `KernelModuleLoad` from a context operating at `UserBoundaryTier` must be rejected, as the axiom dictates that `KernelModuleLoad` is an entity strictly situated at `KernelModeTier`.
