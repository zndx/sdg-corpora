# Chapter 4: Evidence Generation and Control Mapping in Automated Compliance Frameworks

This chapter delineates the structural and semantic requirements for generating, tracing, and validating compliance evidence within automated audit environments. It establishes the formal relationships between laboratory execution processes, the descriptive information content entities (ICEs) they produce, and the regulatory controls they satisfy. The provisions herein specify the ontological mappings required to ensure that every measurement is methodologically sound, traceable to its source, and explicitly aligned with governance frameworks such as NIST SP 800-53.

## 4.1 Laboratory Execution and Evidence Production

The foundational unit of compliance evidence generation is the Laboratory Run (Lab Run). In the context of this framework, a Lab Run is defined as a `bfo:Process` that encompasses the execution of a test suite, a data validation script, or an automated audit procedure. The primary output of this process is not merely a pass/fail status but a structured `cco:DescriptiveICE`. This entity serves as the immutable record of the execution, capturing the state of the system under test at a specific point in time.

The axiom governing this relationship asserts that the Lab Run is the causal agent responsible for the existence of the measurement. Without the process, the descriptive information content does not exist. This distinction is critical for audit trails; it separates the *act* of measurement from the *artifact* produced.

In practice, when the `AutomatedAccessReview_Run_2024Q1` process executes, it generates a specific descriptive ICE. This linkage ensures that any finding can be audited back to the specific execution instance of the review logic, preserving the integrity of the chain of custody.

## 4.2 Provenance and Source Attribution

To satisfy regulatory requirements for data lineage, every descriptive ICE produced by a Lab Run must be attributable to a specific source table or data structure. This concept is formalized by the provenance axiom, which dictates that a descriptive ICE is sourced from a specific table entity. This relationship establishes the ground truth for the measurement, answering the question of *what* data was analyzed.

The schema enforces a strict dependency where the source table (`y`) must correspond to a valid measurement method identifier. This constraint ensures that source attribution is not merely a label but is intrinsically bound to the methodological context in which the source was accessed. It prevents orphaned source references and enforces a closed loop of evidence where the source and the method are co-dependent.

**Table 4.2: Table Provenance Source**

| id | x | y |
| :--- | :--- | :--- |
| `prov_001` | `UserAccessRecord` | `meth_001` |
| `prov_002` | `TransactionLogEntry` | `meth_002` |
| `prov_003` | `ConfigurationSnapshot` | `meth_003` |
| `prov_004` | `CustomerProfileBlob` | `meth_004` |
| `prov_005` | `PatchManifestRecord` | `meth_005` |

For instance, the `UserAccessRecord` (the descriptive ICE) is sourced from a table entity referenced by `meth_001`. This indicates that the provenance of the record is validated only through the specific method associated with that identifier. This rigorous mapping is essential for reconstructing the state of the database during an audit investigation.

## 4.3 Methodological Execution

While provenance identifies the source, the methodological execution axiom defines *how* the source was interrogated to produce the measurement. This relationship asserts that a descriptive ICE is generated via a specific method (`y`). In this framework, the method is treated as a first-class object, representing the algorithm, query, or inspection routine applied to the source.

The relational structure for this axiom introduces a circular dependency with the provenance table: the method (`y`) must reference a valid provenance source ID. This design choice reflects the tight coupling between a data source and the legitimate means of accessing it. A method cannot exist in isolation from the source it is designed to interrogate, and a source cannot be utilized without a valid method. This bidirectional reference ensures that the "Source-Method" pair is treated as a composite unit of analysis within the compliance architecture.

**Table 4.3: Measurement with Method**

| `meth_002` | `TransactionLogEntry` | `prov_002` |

Consider the entry for `meth_001`. It defines that the `UserAccessRecord` was generated via a method that is intrinsically linked to the provenance record `prov_001`. This recursive validation allows the system to verify that the method used to extract the `UserAccessRecord` is the exact method sanctioned for that specific source table, thereby preventing unauthorized analytical procedures.

## 4.4 Regulatory Control Alignment

The ultimate purpose of the evidence generation framework is to demonstrate compliance with specific regulatory controls. This section addresses the mapping of internal directives and findings to the NIST SP 800-53 control catalog. The axiom defines that a Directive Information Content Entity (`cco:DirectiveICE`) is a subclass that implements a specific NIST 800-53 control.

In this schema, the NIST control (`y`) is not a string but a reference to a Lab Run production event. This implies that the control implementation is verified through the execution of the Lab Run. The control is satisfied *because* the Lab Run produced the necessary measurement. This structure anchors the abstract control requirement to concrete physical evidence generated by the system.

**Table 4.4: NIST 800-53 Control Subclass**

| `ctrl_004` | `PrivacyDataHandlingDirective` | `prod_004` |

For example, the `AccessControlPolicyDirective` (the internal policy document or rule set) is mapped to the NIST control requirement satisfied by `prod_001`. By referencing the production ID, the framework provides an auditable link: the directive is compliant because the `AutomatedAccessReview_Run_2024Q1` successfully executed and produced the requisite descriptive ICE.

## 4.5 Column-Level Annotation

Granularity is a key requirement in modern data governance, particularly when dealing with sensitive data types such as PII or PHI. The final axiom addressed in this chapter provides for the annotation of specific columns within the data structures. A descriptive ICE (the annotation) acts as a tag for a specific column (`y`).

Similar to the methodological execution, the column entity (`y`) is referenced via a measurement method ID. This constraint ensures that column tags are not applied arbitrarily to schema definitions but are applied to columns as they are instantiated and measured within a specific methodological context. It binds the semantic tag to the actual data instance observed during the audit run, rather than just a static metadata definition.

**Table 4.5: Column Tag Subclass**
