# Chapter 4: Ontological Mapping of Laboratory Data Lineage and Compliance Controls

This chapter delineates the formal ontological structures required to establish rigorous data lineage, methodological provenance, and regulatory compliance within automated laboratory environments. It provides a systematic examination of the axiom sets governing the generation of Information Content Entities (ICE), the attribution of measurement methods, and the enforcement of NIST 800-53 security controls. The objective is to ensure that all data artifacts produced by laboratory processes are semantically anchored, auditable, and compliant with federal information processing standards.

## 4.1 Process Execution and the Generation of Descriptive Entities

The foundational unit of analysis in any laboratory informatics system is the process execution, formally defined as a `bfo:Process`. In the context of this ontology, a specific class of process, denoted as `{X}`, is axiomatized not merely by its temporal occurrence but by its capacity to produce a `cco:DescriptiveICE`. This relationship establishes the primary link between the physical act of measurement and the digital record that persists thereafter.

The axiom `labrun_produces_measurement` asserts that any instance of class `{X}` is a subclass of `bfo:0000015` (a process) that necessarily produces some `cco:DescriptiveICE`. This is a critical distinction for auditability: a process that fails to produce a descriptive entity is axiomatically incomplete or invalid within the system. The production of this entity serves as the genesis point for the data lineage chain.

To illustrate this, consider a standard High-Performance Liquid Chromatography (HPLC) run. The physical injection and separation of samples constitute the process `{X}`. The output is not merely a voltage signal but a structured `DescriptiveICE`—the chromatogram data—encapsulating the observations. This mapping ensures that every data point in the repository can be traced back to a specific, time-bound execution event.

## 4.2 Methodological Attribution of Measurements

Once a descriptive entity is generated, it is necessary to establish the methodological context of its creation. The axiom `measurement_with_method` posits that a `DescriptiveICE` (the measurement `{X}`) is derived via a specific method `{Y}`. This relationship is essential for reproducibility and validation, as it decouples the data value from the mechanism used to obtain it.

In this schema, `{X}` represents the specific measurement data, while `{Y}` represents the method class. The axiom asserts that `{X}` is a subclass of `cco:DescriptiveICE` and utilizes `sdg:viaMethod` to reference `{Y}`. This structure allows the system to query all measurements derived from a specific method, facilitating broad-scale impact analysis should a method be deprecated or found to be non-compliant.

For instance, a specific set of absorbance values (`{X}`) must be explicitly linked to the "Microplate Reader Method A" (`{Y}`). Without this explicit link, the data exists in a vacuum, rendering scientific reproducibility impossible. The ontology enforces that no `DescriptiveICE` classified as a measurement may exist without this methodological anchor.

## 4.3 Table Provenance and Source Derivation

The integrity of a measurement is contingent upon the provenance of the method definition itself. The axiom `table_provenance_source` addresses this by asserting that a descriptive entity `{X}` (often the method definition or configuration) is sourced from a specific table `{Y}`. This creates a layer of indirection that protects the method's definition from unauthorized alteration and provides a clear audit trail for configuration management.

Here, `{X}` is the entity (such as a method protocol) that is a subclass of `cco:DescriptiveICE`. The slot `sdg:sourcedFromTable` links this entity to its source table `{Y}`. In practice, this means that the parameters defining "Method A" are not hardcoded but retrieved from a specific, version-controlled table within the database. This architecture supports the "single source of truth" principle required in Good Manufacturing Practice (GMP) environments.

The relational implementation of this axiom creates a circular dependency with the measurement method table to ensure referential integrity. Specifically, the method (`y`) referenced in the measurement table must exist as a provenance source here, and conversely, the source table often references the measurement ID to close the loop on lineage.

## 4.4 Regulatory Control Mapping via NIST 800-53

Compliance with federal standards is integrated directly into the data ontology through the `nist80053_control_subclass` axiom. This axiom asserts that a directive information content entity `{X}` (such as a system policy or access control rule) implements or is associated with a specific NIST 800-53 control `{Y}`.

The formalization is expressed as `{X}` SubClassOf: `cco:DirectiveICE`, `sdg:nist80053Control` some `{Y}`. This mapping allows the system to automatically generate compliance artifacts. By querying the ontology, an auditor can retrieve all directives that map to "AU-12" (Audit Record Generation) or "AC-6" (Least Privilege), demonstrating that the laboratory execution environment is governed by codified security requirements.

Crucially, this axiom links the abstract control requirement to the concrete laboratory process. The foreign key structure references the `t_labrun_produces_measurement` table, implying that the control is enforced or triggered during a specific lab run. This grounds high-level compliance mandates in the granular reality of daily operations.

## 4.5 Semantic Annotation of Data Columns

The final structural component involves the semantic annotation of data columns to facilitate automated discovery and interoperability. The `column_tag_subclass` axiom asserts that a descriptive entity `{X}` (a tag or metadata label) annotates a specific column `{Y}` within the measurement schema.

Verbalized as "{X} is something that annotates column {Y}", this axiom allows the system to apply rich semantic context to raw data columns. For example, a tag `PII_Sensitive` can be applied to a column containing `Subject_ID`. This enables automated data loss prevention (DLP) tools to operate effectively without manual inspection of every data table.

The relational schema links the tag to the measurement context. The foreign key references `t_measurement_with_method`, indicating that the column annotation is specific to a particular measurement context or dataset. This prevents ambiguity where a column name might be reused across different tables with different semantic meanings.
