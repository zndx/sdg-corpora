# Evidence-Based Data Lineage in Regulated Laboratory Environments

This chapter establishes the formal ontological framework governing the generation, provenance, and compliance of data within regulated laboratory environments. It details the structural relationships between experimental processes, the information entities they produce, and the regulatory controls governing their usage. The text provides a rigorous examination of how laboratory runs function as processes that yield descriptive information content entities, how those entities derive from specific methods and source tables, and how they are subsequently annotated and governed by NIST 800-53 controls. The objective is to define a deterministic schema for data lineage that satisfies both scientific rigor and auditability requirements.

## 1. Laboratory Runs as Generative Processes

In the context of regulated scientific research, a laboratory run is not merely a temporal event but a distinct ontological process. According to the foundational axiom defined by `labrun_produces_measurement`, a laboratory run (Class X) is a subclass of `bfo:0000015` (a process) that necessarily produces some `cco:DescriptiveICE` (Descriptive Information Content Entity). This relationship establishes the primary output of any experimental activity: the generation of data.

The process entity is defined by its initiation, execution, and termination boundaries. Within these boundaries, the transformation of inputs—reagents, biological samples, or environmental conditions—results in the creation of output data. This output is not the physical sample itself, but the informational record describing the state of that sample. It is imperative to distinguish the physical process from the informational outcome; the process exists in time, whereas the outcome exists as an information content entity.

To illustrate this, consider a standard spectroscopy analysis. The laboratory run involves the physical operation of the spectrometer. The outcome of this run is a dataset representing absorbance values. The ontology dictates that the run *produces* this dataset. Without the process, the specific descriptive entity does not exist. This linkage is the basis for all downstream traceability.

## 2. Measurement Provenance and Methodology

The descriptive information content entities produced by laboratory runs are not generated in a vacuum; they are the result of specific methodologies. The axiom `measurement_with_method` posits that a measurement (Class X) is a subclass of `cco:DescriptiveICE` that is realized `viaMethod` some Class Y. This relationship introduces the concept of instrumental or procedural dependence. The validity of the measurement is intrinsically tied to the method employed.

In technical documentation, the method entity must be defined with sufficient granularity to allow for independent reproduction. This includes the make and model of instrumentation, software versioning, and specific parameter settings (e.g., wavelength, integration time). The axiom asserts that the measurement entity inherits properties from the method entity. If the method is flawed or uncalibrated, the resulting measurement is compromised, regardless of the integrity of the laboratory run process itself.

For instance, a measurement of "pH Level" is only valid if it references the method "Glass Electrode Potentiometry." If the method were "Colorimetric Strip Analysis," the resulting information entity, while potentially describing the same sample, would represent a distinct measurement entity due to the difference in the `viaMethod` relationship. This distinction is critical for data integration and meta-analysis.

## 3. Source Table Derivation and Circular Dependency

In complex data architectures, particularly those involving long-term data retention, measurements are often aggregated or migrated from legacy systems. The axiom `table_provenance_source` addresses this by stating that a descriptive information entity (Class X) is `sourcedFromTable` some Class Y. This establishes a lineage that extends beyond the immediate laboratory run to the storage infrastructure.

This axiom frequently interacts with the methodological axiom in a recursive manner within data pipelines. A measurement may be defined by a method that involves querying a source table, and conversely, a source table may be defined by the measurements it contains. The relational schema reflects this complexity through a circular foreign key constraint: `t_table_provenance_source` references `t_measurement_with_method`, which in turn references `t_table_provenance_source`.

This circularity is not an error but a representation of a tightly coupled data ecosystem where the definition of the data (the measurement) and the container of the data (the table) are interdependent. For example, a "Calculated Concentration" measurement might be derived via a SQL query (Method) that pulls from a "Raw Absorbance" table. The "Raw Absorbance" table itself is defined by the "Raw Absorbance" measurements it houses. Documenting this bidirectional relationship is essential for impact analysis when modifying database schemas or analytical methods.

## 4. Regulatory Control Mapping

Compliance in regulated environments is achieved by mapping technical processes to regulatory frameworks. The axiom `nist80053_control_subclass` formalizes this by asserting that a directive information content entity (Class X) is a subclass of `cco:DirectiveICE` that implements a `nist80053Control` some Class Y. Here, the "Directive" is the specific policy or procedure enacted by the organization, while the "Control" is the standard specification from the NIST Special Publication 800-53.

This relationship transforms abstract regulatory requirements into concrete, executable directives within the laboratory. For example, the NIST control AU-12 (Audit Record Generation) requires the creation of audit records. The corresponding directive within the laboratory might be "Automated Log Retention Policy." The axiom links this directive specifically to the laboratory run process (or the measurement it produces), thereby ensuring that the process is compliant.

The mapping ensures that every laboratory run and resulting measurement is auditable. If a process produces a measurement, and that process is governed by a directive linked to AU-12, the system must demonstrate that the audit trail for that measurement is immutable and complete. This is the mechanism by which "compliance" is operationalized from a legal requirement to a database foreign key constraint.

## 5. Column-Level Annotation and Semantic Tagging

The final layer of the ontological framework concerns the semantic definition of data structures. The axiom `column_tag_subclass` states that a descriptive information content entity (Class X), functioning as a tag, `annotatesColumn` some Class Y. This allows for the application of metadata at the granular level of a database column, rather than the table or row level.

Column tagging is essential for data governance, specifically for identifying sensitive information types (e.g., PII, PHI) or for defining data quality constraints (e.g., "Unit of Measure," "Precision"). The tag is itself an information entity, carrying a vocabulary that standardizes the interpretation of the column's data.

For example, a column named `patient_id` in a measurement table might be annotated by a tag `PHI_Identifier`. This annotation triggers specific handling procedures defined in the security policy (such as access control masking). The ontology ensures that the tag is not merely a comment but a distinct entity with a defined relationship to the column structure. This facilitates automated compliance scanning and data discovery across the laboratory's information infrastructure.
