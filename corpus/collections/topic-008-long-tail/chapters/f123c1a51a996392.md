# Chapter 4: Ontological Classification of Kernel System Calls in Audit Frameworks

## 4.1 Scope and Preamble

This chapter delineates the formal ontological categorization of kernel-level system calls within the context of advanced auditing frameworks, specifically focusing on the `04_ebpf_kernel` family. It addresses the classification of these entities as Designative Information Content Entities (ICE) and rigorously distinguishes between generic designative classes and those subject to active auditing processes governed by specific occurrents. The discussion is grounded in the formal axioms derived from the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO), providing a deterministic schema for mapping kernel behaviors to compliance-ready data structures. This classification is essential for establishing a verifiable chain of evidence in systems requiring high-assurance governance and real-time security monitoring.

## 4.2 Basic Designative Information Content Entities

### 4.2.1 Definition and Semantics

In the context of kernel observability and audit logging, a system call must be formally understood not merely as a software interrupt, but as a specific type of information entity. The foundational axiom for this classification asserts that a system call, denoted as the variable {X}, is a subclass of `cco:DesignativeICE`. A Designative Information Content Entity is defined within the Common Core Ontologies as an entity that conveys meaning or stands for another entity—in this case, the specific function or routine within the kernel space that the system call invokes.

This distinction is critical for audit compliance. By treating the system call as a designative entity, the audit framework separates the *signifier* (the name or identifier of the call used in logs) from the *signified* (the actual execution path within the kernel). This separation allows for the creation of robust, referenceable data tables where the "name" of the system call is treated as a stable, first-class citizen of the information model, independent of the volatile process execution data. The axiom `syscall_basic` establishes this baseline, ensuring that every entity tracked in the audit subsystem is, at a minimum, a recognized designative entity within the system's ontology.

### 4.2.2 Implementation of the Basic Axiom

The implementation of the `syscall_basic` axiom requires the population of a relational structure that links a unique identifier to the class designation of the system call. This structure serves as the master registry for all recognized system calls within the kernel audit scope. It ensures that any subsequent reference to a system call—whether in a security alert, a performance metric, or a compliance report—can be traced back to a canonical definition.

### 4.2.3 Verification and Governance

When auditing a system for compliance with frameworks such as NIST 800-53 or ISO 27001, the integrity of the `t_syscall_basic` table is paramount. Auditors must verify that the `x` values correspond exactly to the system call definitions present in the kernel source code being audited. Any discrepancy between the designative entity listed in this table and the actual kernel symbol table constitutes a failure of the mapping layer and potentially invalidates subsequent security analysis. The "basic" nature of this axiom implies that these entries exist regardless of whether auditing is active; they represent the *potential* for interaction with the kernel, defined ontologically as information content.

## 4.3 Audited System Call Entities

### 4.3.1 The Audit Restriction and Processual Dependence

While the basic classification provides a registry of existing system calls, a security governance framework is primarily concerned with those system calls that are subject to active monitoring. The `syscall_audited_by` axiom introduces a restriction to the basic definition. It asserts that the class {X} is not only a subclass of `cco:DesignativeICE` but is also the object of the property `sdg:auditedBy`, referencing an instance of `bfo:0000015`.

In the Basic Formal Ontology (BFO), `bfo:0000015` denotes a "Process." Therefore, this axiom formally states that the system call is being observed, tracked, or recorded by a specific audit process (such as an eBPF program attached to the kernel tracepoints). This transforms the system call from a static designative entity into a node within a dynamic security graph. The relationship `auditedBy` creates a dependency: the existence of the "audited system call" entity in the compliance model is contingent upon the active execution of the auditing process.

### 4.3.2 Complex Axiom Integration

This axiom is marked as "complex" within the schema metadata due to the intersection of the information entity (the system call) with the occurrent (the audit process). In practice, this means that data populating this table represents a subset of the total system calls—specifically, those deemed security-relevant or operationally critical by the governance policy. For instance, while `sys_getpid` might be a basic designative entity, it may not appear in the audited table if the policy dictates that process ID retrieval is not a security-relevant event. Conversely, `sys_execve` would almost certainly be included, as it represents a critical control point for process execution.

The following table embodies the `syscall_audited_by` axiom. It records system calls that are actively monitored by a BFO Process (the audit mechanism). The primary key is the `id` column, uniquely identifying the audit rule entry. The `x` column holds the class name of the system call subject to this audit relationship. This table effectively filters the broader kernel environment down to the set of observable events required for forensic analysis.

### 4.3.3 Compliance Implications

The data contained within the `t_syscall_audited_by` table serves as the evidence anchor for audit trails. When a forensic investigation is initiated—perhaps following a detected intrusion—the investigator will query the logs generated by the `bfo:0000015` process. The investigator must cross-reference the log entries against this table to confirm that the logged events correspond to sanctioned audit targets. If a system call appears in the logs but is absent from this table, it may indicate "scope creep" in the auditing tools or, more maliciously, the deployment of unauthorized monitoring software. Conversely, if a critical security event occurs (such as a privilege escalation via `sys_setuid`) but the corresponding entry is missing from this table, the organization may be found non-compliant for failing to define adequate monitoring controls. Thus, this table is not merely a technical schema but a legal document defining the boundary of system observability.
