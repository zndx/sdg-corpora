# Chapter 4: Kernel-Level Audit Mechanisms and System Call Taxonomy

## 4.0 Scope and Preamble

This chapter establishes the foundational taxonomy for system calls within the context of kernel-level observability and compliance frameworks. It delineates the structural definitions of system calls as Designative Information Content Entities (DICE) and further classifies their interaction with auditing agents pursuant to the `04_ebpf_kernel` family specification. The objective is to provide a rigorous, evidence-anchored definition of kernel objects to facilitate automated auditing, ensuring that all syscall interactions are traceable to specific process agents. This documentation serves as a normative reference for engineers implementing security controls that rely on precise semantic mapping of kernel primitives.

## 4.1 Foundational Taxonomy of System Calls

### 4.1.1 Definition and Classification

In the context of the formal ontology, a system call is not merely a functional entry point into the kernel space; it is formally categorized as a Designative Information Content Entity (`cco:DesignativeICE`). This classification asserts that the system call serves as a distinct informational entity that designates a specific kernel function or service request. The axiom `syscall_basic` provides the necessary constraint for this classification, asserting that any entity `X` identified as a system call must inherently satisfy the condition of being a designative entity.

This distinction is critical for audit readiness. By treating syscalls as information content entities, the framework allows for the separation of the *concept* of the system call from the *execution* event. The execution is an occurrence, whereas the syscall itself is the designative definition that the execution instantiates. This separation ensures that governance frameworks can reference stable definitions (the `X` in the axiom) rather than transient process states.

To facilitate this, the `t_syscall_basic` table serves as the registry of these designative entities. It catalogs the fundamental system calls that are recognized within the scope of the operating system's interface. The primary key (`id`) ensures referential integrity, while the `x` column holds the canonical designation of the system call class.

## 4.2 Auditing Relationships and Agent Interaction

### 4.2.1 The Auditing Constraint

While the basic taxonomy identifies what a system call *is*, the governance framework must also define *how* it is monitored. The axiom `syscall_audited_by` introduces a restriction that extends the definition of a system call to include an auditing relationship. Specifically, this axiom states that a system call (a subclass of `cco:DesignativeICE`) is audited by some instance of `bfo:0000015` (a Process).

This relationship is pivotal for establishing the chain of custody for kernel events. The entity `bfo:0000015` represents the independent continuant—specifically, the process or agent—responsible for the observation. In practical terms, this maps to the eBPF programs or audit daemons that attach to tracepoints to intercept syscall events. The axiom ensures that for a syscall to be compliant within this framework, it must not exist in a vacuum; it must be structurally linked to an auditor.

The `t_syscall_audited_by` table operationalizes this axiom. It records those system calls that are subject to active monitoring protocols. The schema mirrors the basic registry but implies the existence of the `auditedBy` relationship through the context of the `syscall_audited_by` template.

The entries in Table 4-2 represent a subset of the broader system call interface that requires granular inspection. For example, `sys_execve`, which executes a new program, is a critical control point. By classifying it under `syscall_audited_by`, the framework mandates that any invocation of `sys_execve` must be accompanied by an audit record generated by the observing process (`bfo:0000015`).

### 4.2.3 Verification and Compliance

Compliance with the `04_ebpf_kernel` family requires that the implementation of the audit daemon verifies the consistency between the `t_syscall_basic` and `t_syscall_audited_by` tables. An auditor reviewing the system logs must be able to trace a specific event—say, the execution of `sys_mount`—back to the designative entity in the registry and confirm that the axiom `auditedBy some bfo:0000015` holds true for that event.

If a system call appears in the operational logs but lacks a corresponding entry in the `t_syscall_audited_by` table, this constitutes a deviation from the governance framework. It implies that an information content entity is being utilized without the mandated auditing relationship, potentially creating a blind spot in the security posture. Therefore, maintaining these tables is not merely a data management exercise but a formal requirement for system integrity and auditability.
