# Chapter 4: Ontological Formalization of Kernel Audit Subsystems

## 1. Scope and Governance Framework

This chapter establishes the formal ontological framework for managing system call visibility and auditability within the extended Berkeley Packet Filter (eBPF) subsystem. The provisions herein define the structural requirements for classifying kernel interactions as Designative Information Content Entities and mandate the specific relationships required to bind these entities to auditing processes. The objective is to ensure a deterministic, evidence-anchored mapping between kernel-level events and the security governance frameworks that monitor them. Compliance with these definitions is mandatory for systems requiring high-assurance audit trails, specifically where the integrity of financial information or the containment of system-level threats is paramount.

## 2. Designative Information Content Entities

### 2.1 Definition and Ontological Status

In the context of kernel observability, a system call must be formally recognized not merely as a functional invocation, but as a distinct ontological class. Per the governing axioms, any system call utilized within the audit framework is classified as a subclass of `cco:DesignativeICE` (Designative Information Content Entity). This classification asserts that the system call functions as a "designative" entity—it serves as a stable, information-bearing referent that designates a specific kernel behavior or resource interaction.

The role of the DesignativeICE is to assist the governance framework in fulfilling its monitoring responsibilities by providing a semantically stable identifier for kernel actions. Unlike transient process states, the DesignativeICE represents the immutable definition of the action itself. This distinction is critical for audit integrity; it ensures that the log records refer to the *concept* of the system call (e.g., `open`, `read`), rather than a volatile memory address, thereby guaranteeing the reliability and reproducibility of the audit data.

### 2.2 System Call Classification

To implement this framework, specific system calls are cataloged as instances of the basic designative class. This cataloging process involves mapping the kernel's internal syscall identifiers to the formal ontology. The following table illustrates the instantiation of basic system calls as Designative Information Content Entities. These entries represent the foundational vocabulary of the audit language, devoid of specific audit constraints but essential for the structural integrity of the kernel model.

| id | x |

*Table 2.1 Notes:*
*   **id**: The unique identifier for the designative class record within the governance database.
*   **x**: The specific system call class (e.g., `sys_open`) which is a subclass of `cco:DesignativeICE`. This value represents the formal designation of the kernel function.

### 2.3 Stability and Governance Implications

By defining these entities as `cco:DesignativeICE`, the framework ensures that changes to the kernel implementation do not inadvertently corrupt the audit semantic. If the underlying implementation of `sys_read` is optimized, the designative entity remains constant. This stability is a requirement for maintaining the integrity of historical data. Auditors and compliance officers must verify that the mapping in Table 2.1 aligns with the kernel source headers and that no drift has occurred between the logged identifiers and the formal ontology.

## 3. Audit Binding and Process Relationships

### 3.1 The Audit Relationship

While the basic designation of system calls provides the necessary vocabulary, it does not inherently enforce security monitoring. To satisfy regulatory requirements for containment and surveillance, a subset of designative entities must be explicitly bound to an auditing process. This relationship is formalized through the axiom `sdg:auditedBy some bfo:0000015`.

This axiom asserts that for a system call to be considered "audited," it must be the object of a specific relationship (`sdg:auditedBy`) wherein the subject is a Process (`bfo:0000015`). In practical terms, this means that a specific, active monitoring agent (such as an eBPF program attached to the tracepoints) must exist and be responsible for capturing the execution of that system call. The relationship is not merely passive storage; it requires an active, ongoing process engagement.

### 3.2 Process Integration (bfo:0000015)

The entity `bfo:0000015` refers to a "Process" within the Basic Formal Ontology. In this governance framework, the Process represents the runtime instantiation of the audit logic—typically a daemonized eBPF collector or a security enforcement module running in kernel space. The binding of a DesignativeICE to a Process ensures that there is an accountable agent for every captured event.

This structure allows the organization to define precisely which calls are subject to surveillance. For instance, while `sys_read` may be a basic designative entity, it may not be `auditedBy` a specific process in all contexts. However, high-risk calls such as `sys_execve` or `sys_connect` must be bound to a security process to satisfy containment protocols. The following table details the binding of specific system calls to their designated auditing processes.

**Table 3.1: System Call Audit Bindings (t_syscall_audited_by)**

| id | x |
| :--- | :--- |
| sys_audit_01 | sys_execve |
| sys_audit_02 | sys_connect |
| sys_audit_03 | sys_accept |
| sys_audit_04 | sys_bind |
| sys_audit_05 | sys_mount |
| sys_audit_06 | sys_chmod |
| sys_audit_07 | sys_setuid |

*Table 3.1 Notes:*
*   **id**: The unique identifier for the audit binding record.
*   **x**: The system call class that is the subject of the audit. By virtue of its presence in this table, `x` is asserted to be a subclass of `cco:DesignativeICE` that is also `sdg:auditedBy` an instance of `bfo:0000015`.

### 3.3 Compliance Verification

To verify compliance with this framework, auditors must perform two distinct checks. First, they must confirm that all entries in `t_syscall_audited_by` are valid subclasses of `cco:DesignativeICE` (i.e., they exist in the broader system call ontology). Second, they must validate the runtime existence of the Process (`bfo:0000015`) referenced by the `auditedBy` relationship.

The distinction between the basic entities in Section 2 and the audited entities in Section 3 is critical for the principle of least privilege. Not every system call requires the overhead of active process auditing. By segregating the basic definitions from the audit bindings, the framework allows for a scalable, high-performance kernel environment where only security-relevant events incur the computational cost of active monitoring. This architecture supports the organization's mandate to maintain system performance while ensuring rigorous containment of novel threats and unauthorized execution flows.
