# Chapter 4: Formal Ontology of Kernel Audit Mechanisms

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework governing the classification and attribution of kernel-level system calls within a compliant auditing infrastructure. Pursuant to the requirements for high-assurance environments, the definitions herein align with the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO) to ensure semantic interoperability between low-level kernel events and high-level governance reporting. The text delineates the necessary conditions for a system call to be recognized as a Designative Information Content Entity (ICE) and further specifies the axioms governing its attribution to specific audit processes. This framework is intended for system architects, compliance officers, and security analysts responsible for implementing evidence-anchored monitoring solutions.

## 4.2 Designative Information Content Entities

### 4.2.1 Definition and Axiomatic Basis

In the context of kernel space instrumentation, a system call is not merely a functional interface but a distinct semantic entity classified as a Designative Information Content Entity (`cco:DesignativeICE`). According to the axiom template `syscall_basic`, any class of system call `{X}` is axiomatically a subclass of `cco:DesignativeICE`. This classification asserts that the system call functions as an information entity that "stands for" or designates a specific operational capability within the operating system kernel.

The designation property is critical for audit trails. It transforms a binary memory address into a governance-relevant object. By formalizing system calls under this ontology, the audit framework ensures that every logged event refers to a distinct, categorizable class of entity, rather than an opaque integer value. This approach satisfies the "Paperwork Reduction Act" principles by minimizing the ambiguity of collected data, thereby reducing the burden of downstream interpretation and correlation for auditors.

### 4.2.2 Implementation and Registry

To maintain compliance with this axiom, the audit infrastructure must maintain a registry of recognized system calls. This registry serves as the primary evidence source for verifying that the kernel's exported interface aligns with the documented designative entities. The following table represents a subset of this registry, enumerating specific system call classes that satisfy the `syscall_basic` axiom. Each entry represents a unique class `{X}` that is a subclass of `cco:DesignativeICE`.

**Table 4.1: Registry of Basic Designative System Calls**

| ID | X (Designative Class) |
| :--- | :--- |
| SK-BASIC-001 | `sys_read` |
| SK-BASIC-002 | `sys_write` |
| SK-BASIC-003 | `sys_open` |
| SK-BASIC-004 | `sys_close` |
| SK-BASIC-005 | `sys_stat` |
| SK-BASIC-006 | `sys_fstat` |
| SK-BASIC-007 | `sys_lstat` |

The data presented in Table 4.1 demonstrates the instantiation of the `t_syscall_basic` schema. The primary key `id` provides a unique reference handle for the designative class, while the column `x` contains the standardized identifier for the system call. In accordance with the schema definition, these entities are complex only insofar as they represent a specific class of information content; they do not, in this basic form, imply an active audit relationship. This distinction is vital for separating the *availability* of a kernel feature from the *requirement* to monitor it.

### 4.2.3 Compliance Significance

The classification of a system call as a `cco:DesignativeICE` without further restriction implies that the entity is recognized by the system but not necessarily subject to active monitoring regimes. This distinction allows system architects to define the "baseline" kernel surface. For instance, `sys_read` and `sys_write` are fundamental designative entities present in all standard Linux distributions. Their presence in the registry confirms the kernel's adherence to expected POSIX standards. However, for compliance frameworks requiring strict access control (such as those governing Personally Identifiable Information), mere designation is insufficient. This necessitates the extension of the ontology to include audit relationships, which are detailed in the following section.

## 4.3 Audit Correlation and Process Attribution

### 4.3.1 The Audited By Axiom

While the basic designation of system calls establishes the vocabulary of kernel interaction, governance frameworks require the attribution of these calls to supervisory processes. This requirement is formalized through the axiom `syscall_audited_by`. This axiom states that a system call class `{X}` is not only a `cco:DesignativeICE` but is also the object of the relation `sdg:auditedBy`, which targets some instance of `bfo:0000015` (a Process).

The entity `bfo:0000015` refers to a "process" in the BFO hierarchy—a temporally bounded entity that unfolds in time. In the context of this framework, the process represents the active auditing daemon or kernel trace mechanism (e.g., an eBPF program or an LSM hook) that observes the system call. The axiom `syscall_audited_by` therefore imposes a strict constraint: for a system call to be considered "audited" under this ontology, there must exist a realized process instance that performs the observation. This is not a hypothetical capability but a structural dependency.

### 4.3.2 Regulatory and Structural Implications

This proposed action—classifying a system call as audited—does not impose an information collection burden beyond that required by the underlying audit process. Rather, it validates that the existing State law (or organizational policy) regarding logging is met by the technical implementation. By explicitly mapping the `sdg:auditedBy` relation to `bfo:0000015`, the framework ensures that audit logs are causally linked to a specific, running process. This prevents "orphaned" log entries where data is collected without a responsible, traceable collector.

Furthermore, this classification is a "significant regulatory action" only insofar as it triggers retention policies. If a system call is listed in the `t_syscall_audited_by` table, it implies that the output of that call is subject to archival, review, and potential forensic analysis. Consequently, the selection of entities for this table must be rigorous, limited to those syscalls that touch security-relevant parameters, such as file permissions, process control, or network socket manipulation.

### 4.3.3 Audited System Call Registry

The following table provides the relational instantiation of the `syscall_audited_by` axiom. It lists those designative entities that are actively monitored by a specific audit process. The inclusion of `sys_openat2`, `sys_connect`, and `sys_execve` reflects a security posture focused on file access, network egress, and code execution, respectively.

**Table 4.2: Registry of Audited Designative System Calls**

| ID | X (Audited Designative Class) |
| :--- | :--- |
| SK-AUD-001 | `sys_openat2` |
| SK-AUD-002 | `sys_connect` |
| SK-AUD-003 | `sys_execve` |
| SK-AUD-004 | `sys_mmap` |
| SK-AUD-005 | `sys_ptrace` |
| SK-AUD-006 | `sys_mount` |

The structure of Table 4.2 corresponds to the `t_syscall_audited_by` schema. The `id` column serves as the primary key for the audit record, while `x` denotes the specific subclass of `cco:DesignativeICE` that is being audited. It is evident from the data that these entries represent a subset of the total available system calls (as seen in Table 4.1), filtered for relevance to the security domain.

The presence of `sys_ptrace` and `sys_mount` in this table is particularly noteworthy. These calls are often restricted or heavily monitored because they allow modifications to the process address space and the filesystem layout. By axiomatically binding these calls to an audit process (`bfo:0000015`), the organization ensures that any attempt to debug a process or mount a filesystem is immediately recorded. This satisfies the requirement for "continuous monitoring" as defined in NIST and ISO standards.

### 4.3.4 Verification and Governance

To verify compliance with this chapter, auditors must perform two distinct checks. First, they must validate that the `t_syscall_basic` table accurately reflects the kernel's available system call interface. Second, they must confirm that every entry in `t_syscall_audited_by` has a corresponding, active process in the runtime environment that satisfies the `bfo:0000015` slot. A discrepancy—such as an audited syscall without a running collector—constitutes a violation of the axiom and a failure of the governance framework.

This rigorous, evidence-anchored approach ensures that the technical implementation of kernel auditing is not merely a collection of ad-hoc scripts, but a formally structured system grounded in ontological clarity. It provides the necessary density of evidence required for high-stakes compliance reporting, ensuring that every monitored action is accounted for in both the logical schema and the physical runtime.
