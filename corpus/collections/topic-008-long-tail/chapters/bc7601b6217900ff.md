# Chapter 4: Ontological Foundations of Kernel Audit Frameworks

## 4.1 Scope and Preamble

This chapter establishes the formal ontological distinctions required for the rigorous classification of system calls within an eBPF-enabled kernel audit architecture. It delineates the boundary between basic designative entities and those subject to active auditing processes, providing the semantic scaffolding necessary for compliance verification. The definitions herein are derived from the `04_ebpf_kernel` family of axioms and are intended to guide the implementation of automated governance frameworks. Furthermore, this chapter specifies the relational schema required to map these ontological commitments to persistent storage, ensuring that audit trails are both queryable and semantically valid.

## 1. Basic System Call Designation

### 1.1 Designative Information Content Entities

In the context of kernel-level compliance, a system call must first be understood not as a runtime event, but as a **Designative Information Content Entity** (`cco:DesignativeICE`). This distinction is critical for auditability: the entity represents the *concept* or *designation* of the system call within the controlled vocabulary of the operating system, rather than a specific instance of its execution. By treating the syscall as a `cco:DesignativeICE`, the governance framework establishes a stable referent for policy definitions. This allows security administrators to assert rules against the *class* of actions (e.g., "opening a file") rather than attempting to track transient process states.

The axiom governing this foundational concept is formalized in Manchester syntax as `Class: {X:Class} SubClassOf: cco:DesignativeICE`. This asserts that any class `X` within this domain is fundamentally a designative entity. In practice, this means that the identifier for the system call functions as a distinct informational artifact that stands for the kernel function it designates. This ontological commitment prevents ambiguity in audit logs, ensuring that when a record refers to a specific operation, it references a formally defined class within the information system.

### 1.2 Relational Mapping of Basic Designations

To operationalize this axiom within a relational database, the `t_syscall_basic` table is utilized. This structure serves as the registry for all system call classes that are recognized by the framework as designative entities. The primary key, `id`, ensures a unique identifier for each designation, while the `x` column stores the specific class name (the `X` in the axiom) that inherits from `cco:DesignativeICE`. This table does not imply active auditing; rather, it constitutes the canonical dictionary of operations that the system is capable of recognizing.

The following table embodies **Axiom 2** (`syscall_basic`), illustrating the mapping of specific kernel operations to their designative classes. The primary key `id` serves as the unique surrogate key for the database row, while `x` represents the class name satisfying the subclass condition.

| id | x |
| :--- | :--- |
| basic_sys_001 | SyscallOpen |
| basic_sys_002 | SyscallClose |
| basic_sys_003 | SyscallRead |
| basic_sys_004 | SyscallWrite |
| basic_sys_005 | SyscallStat |

The data presented in Table 1.1 demonstrates the instantiation of the ontology. For instance, the row with `id` `basic_sys_001` asserts that the class `SyscallOpen` is a `cco:DesignativeICE`. This entry provides the semantic grounding for any subsequent audit rules that pertain to file opening operations. Without this foundational entry, an audit trail referencing `SyscallOpen` would lack a valid referent in the ontology, rendering the compliance evidence chain incomplete. It is imperative that all system calls subject to governance be registered in this table prior to the activation of any monitoring policies.

## 2. Audited System Call Relationships

### 2.1 The Audit Process and Dependency

While basic designation establishes the vocabulary of the system, compliance requires the assertion of active monitoring. This is achieved through the introduction of a second, more complex axiom: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`. This axiom extends the basic definition by introducing a necessary condition: the entity must be audited by a process.

In this formalism, `bfo:0000015` refers to a **Process** (as defined by the Basic Formal Ontology). Within the eBPF kernel context, this process represents the runtime execution of the audit logic itself—often a specific eBPF program or a daemon attached to tracepoints. The property `sdg:auditedBy` creates a dependency relationship between the system call class and the auditing process. Consequently, for a class `X` to satisfy this axiom, it is not sufficient for it to merely exist as a designative entity; there must be an active process instance performing the observation. This distinction allows the framework to differentiate between "known" operations and "monitored" operations, a capability essential for least-privilege enforcement and regulatory reporting.

### 2.2 Relational Mapping of Audited Designations

The relational projection of this axiom is captured in the `t_syscall_audited_by` table. While this table shares a similar structure to the basic designation table, its semantic content is significantly richer. The presence of a row in this table signifies that the class `x` is not only a `cco:DesignativeICE` but is also actively linked to an auditing process. The `id` column remains the primary key, ensuring referential integrity within the database schema.

The following table embodies **Axiom 1** (`syscall_audited_by`), listing system call classes that are subject to active monitoring by a kernel process. The primary key `id` uniquely identifies the audit rule, while `x` denotes the class that is both designative and audited.

| id | x |
| :--- | :--- |
| audited_sys_101 | SyscallOpen_Audited |
| audited_sys_102 | SyscallExecve_Audited |
| audited_sys_103 | SyscallConnect_Audited |
| audited_sys_104 | SyscallClone_Audited |

As shown in Table 2.1, the class `SyscallExecve_Audited` (`audited_sys_102`) represents the designation of the execution family of system calls *specifically in the context of being audited*. The existence of this row implies that the `bfo:0000015` process (the auditor) has a defined hook into this specific syscall type. This separation allows for granular control; a system may support `SyscallExecve` as a basic designative entity (Table 1.1) but may only instantiate `SyscallExecve_Audited` within specific security profiles or during certain compliance windows.

### 2.3 Verification and Compliance Implications

The dual-table structure provides a robust mechanism for compliance verification. Auditors can query `t_syscall_basic` to verify the scope of the system's recognized vocabulary and query `t_syscall_audited_by` to verify the active attack surface monitoring. Discrepancies between these datasets—such as a sensitive operation appearing in the basic table but absent from the audited table—constitute immediate findings in a governance assessment.

Furthermore, the reliance on `bfo:0000015` (Process) necessitates that the auditing mechanism itself be treated as a managed asset. If the process terminates or fails to load, the ontological condition `auditedBy some bfo:0000015` is violated, effectively rendering the rows in `t_syscall_audited_by` invalid representations of the runtime state. Therefore, a comprehensive audit framework must include health checks for the auditing process, ensuring that the semantic claims made by the ontology remain true throughout the reporting period. This alignment of data semantics with runtime process state is the hallmark of a mature, evidence-anchored compliance architecture.
