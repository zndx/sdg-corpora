# Chapter 7: Designative Information Content Entities for Syscall Representation

This chapter defines the classification of syscall descriptors under the cco:DesignativeICE hierarchy and specifies their relational projections for audit applications. The treatment is restricted to the axioms syscall_basic and syscall_audited_by. All instances satisfy the stated subclass axioms; column values are restricted to entity references or literals permitted by the slot types.

## 1 Ontological Classification

Axiom syscall_basic states that any class X is a designative information content entity when it functions as a stable referent for a kernel operation. Axiom syscall_audited_by extends the classification by requiring an existential restriction to bfo:0000015, the class of processes. Consequently, every row in the audited table denotes an X that participates in at least one auditing process while remaining a designative information content entity.

### 1.1 Slot Typing and Constraints

Both axioms admit a single slot X of type Class. No data properties are declared; therefore every table contains exactly two columns: an internal identifier and the class reference. Primary-key uniqueness on the identifier column guarantees that each X appears at most once per table.

## 2 Relational Schemas

The deterministic mapping produces two tables. Foreign-key relationships are realized by equi-join on the x column, which holds the shared class reference.

### 2.1 t_syscall_basic

This table embodies axiom syscall_basic. Column id is the primary key. Column x stores the class reference. A reader can retrieve all designative syscall classes by selecting the entire table; no join is required for the unary case.

```sql
CREATE TABLE t_syscall_basic (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id  | x          |
|-----|------------|
| sb1 | sys_open   |
| sb2 | sys_read   |
| sb3 | sys_write  |
| sb4 | sys_close  |
| sb5 | sys_mmap   |
| sb6 | sys_fork   |

### 2.2 t_syscall_audited_by

This table embodies axiom syscall_audited_by. Column id is the primary key. Column x again stores the class reference and serves as the join target to t_syscall_basic. A cross-join on x yields the subset of designative classes that are additionally constrained by an auditing process.

```sql
CREATE TABLE t_syscall_audited_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id   | x          |
|------|------------|
| sa1  | sys_open   |
| sa2  | sys_read   |
| sa3  | sys_write  |
| sa4  | sys_mmap   |
| sa5  | sys_fork   |

## 3 Cross-Join Demonstration

To answer the multi-hop question “which designative syscall classes are subject to process auditing?”, perform an equi-join on column x:

```sql
SELECT b.x
FROM t_syscall_basic b
JOIN t_syscall_audited_by a ON b.x = a.x;
```

Result rows: sys_open, sys_read, sys_write, sys_mmap, sys_fork. The join confirms that each returned class satisfies both axioms simultaneously.
