# Chapter 12: Designative Information Content Entities for eBPF Syscall Audit Trails

This chapter defines two OWL axioms that classify syscall descriptors as designative information content entities and projects those axioms onto a minimal relational schema. The schema supports audit-trail reconstruction through primary-key and foreign-key linkages among processes, auditors, and syscall records.

## 1 Axiom Definitions

### 1.1 Basic Classification
Axiom 2 states that any class X is a designative information content entity when it functions solely as a referent for a kernel operation. No additional restrictions are imposed.

### 1.2 Audited Classification
Axiom 1 extends the same classification by requiring that X is auditedBy at least one instance of bfo:0000015. The auditor relation supplies the necessary temporal and agentive context for compliance verification.

## 2 Relational Projection

Four tables realize the axioms. Primary keys are single-column identifiers. Foreign keys appear in three tables and enable two-hop and three-hop joins.

### 2.1 Processes
The table embodies no ontology axiom directly; it supplies entity references required by the foreign-key columns of the syscall tables. Column process_id is the primary key; all other tables reference it.

| process_id | name          |
|------------|---------------|
| p001       | init          |
| p002       | systemd       |
| p003       | sshd          |
| p004       | auditd        |
| p005       | ebpf_loader   |

### 2.2 Auditors
The table supplies individuals that satisfy the bfo:0000015 restriction in Axiom 1. Column auditor_id is the primary key.

| auditor_id | name             |
|------------|------------------|
| a01        | kernel_tracer    |
| a02        | seccomp_monitor  |
| a03        | bpf_audit_ring   |

### 2.3 Basic Syscall Records
The table directly implements Axiom 2. Column id is the primary key; column x references process_id.

### 2.4 Audited Syscall Records
The table implements Axiom 1. Column id is the primary key; column x references process_id. An implicit link to auditor_id is exercised through join conditions on shared temporal context.

## 3 Cross-Table Query Example

Question: which auditor examined the audited syscall issued by process systemd?

Walk the links: start at t_syscall_audited_by row s103 (x = p002), join t_process on process_id = p002 to confirm name “systemd”, then join t_auditor on the audit context recorded for s103 to obtain auditor_id a01 (“kernel_tracer”).

Result row after two joins:  
id = s103, x = p002, process_name = systemd, auditor_name = kernel_tracer.
