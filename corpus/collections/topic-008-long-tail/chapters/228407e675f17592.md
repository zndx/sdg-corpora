# Chapter 7: Formal Ontology of Kernel Auditing and System Call Designation

## 7.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the classification and auditability of kernel-level system calls within the extended Berkeley Packet Filter (eBPF) ecosystem. The mapping of low-level kernel primitives to upper-level ontology definitions—specifically those grounded in the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO)—is a prerequisite for rigorous compliance reporting and automated governance. The following sections establish the axiomatic definitions for "Designative Information Content Entities" (ICE) as they pertain to system calls, distinguishing between base-level designations and those entities subject to active audit constraints. This formalization ensures that system telemetry is not merely collected as raw data but is instantiated as verifiable, semantically grounded artifacts within a governance framework.

## 7.2 System Calls as Designative Information Content Entities

### 7.2.1 Axiomatic Definition

In the context of kernel observability, a system call is not merely a software interrupt or a transition vector between user space and kernel space; it is formally modeled as a Designative Information Content Entity (`cco:DesignativeICE`). Per the governing axioms, any entity `X` classified as a system call within this ontology must satisfy the condition of being a subclass of `cco:DesignativeICE`.

A Designative ICE is defined as an information content entity that denotes or refers to a specific realizable entity—in this case, the specific function or routine within the kernel that performs a requested action. By formalizing system calls under this class, we establish that the term (e.g., `sys_open`) is a linguistic or symbolic stand-in for the actual process execution. This distinction is critical for audit logs, which must record the *intent* (the designative entity) as distinct from the *execution* (the temporal process).

### 7.2.2 Relational Mapping and Instances

The manifestation of this axiom is captured in the relational schema `t_syscall_basic`. This table serves as the registry for system calls that are defined solely by their designation as information content entities, without the immediate imposition of audit constraints. The primary key (`id`) ensures referential integrity, while the `x` column holds the class name or identifier of the system call.

The following table presents a subset of standard system calls instantiated as Designative ICEs. These entries represent the foundational vocabulary of the kernel interface, categorized strictly by their status as designative entities.

| :--- | :--- |
| basic_001 | sys_read |
| basic_002 | sys_write |
| basic_003 | sys_open |

**Table 7.1: Basic System Call Designations.** This table enumerates instances of the `t_syscall_basic` schema. Each row represents a system call (`x`) that satisfies the axiom `SubClassOf: cco:DesignativeICE`. The `id` provides a unique identifier for the designative record.

### 7.2.3 Compliance Implications

From a governance perspective, the classification of a system call as a basic Designative ICE implies that the entity is recognized within the system taxonomy but is not yet explicitly bound to an audit observer. In a compliance audit, entries derived solely from this table indicate that the system call is *known* to the ontology but may not be actively monitored depending on the policy configuration. This separation allows security architects to delineate between the theoretical set of all available kernel interfaces and the subset that requires granular inspection.

## 7.3 Audited System Calls and Processual Dependencies

### 7.3.1 Axiomatic Definition of Audit Constraints

While the basic designation establishes the existence of a system call, regulatory frameworks often mandate that specific interactions with the kernel be subject to continuous monitoring. This requirement is formalized through the axiom `syscall_audited_by`. This axiom extends the definition of a system call `X` by adding a restriction: `X` must be a `cco:DesignativeICE` AND must be `sdg:auditedBy` some `bfo:0000015`.

In the Basic Formal Ontology, `bfo:0000015` refers to a "Process." Therefore, this axiom asserts a necessary existential dependency: for a system call to be classified as "audited," there must exist a distinct process (the auditor or monitoring agent) that is actively engaged in observing or recording the information content entity. This moves the ontology from a static catalog of terms to a dynamic map of operational dependencies.

### 7.3.2 Relational Mapping and Audit Trails

The relational projection of this axiom is the schema `t_syscall_audited_by`. While the schema structure mirrors the basic table in terms of columns (`id`, `x`), the semantic payload is significantly heavier. The rows in this table represent system calls that are not only designative but are also the active subjects of a processual audit relationship.

The table below enumerates system calls that are typically flagged for auditing in high-security environments due to their potential impact on system integrity and confidentiality.

| id | x |
| :--- | :--- |
| audit_001 | sys_execve |
| audit_002 | sys_connect |
| audit_003 | sys_accept |
| audit_004 | sys_mount |
| audit_005 | sys_umount |
| audit_006 | sys_setuid |
| audit_007 | sys_chmod |

**Table 7.2: Audited System Call Designations.** This table populates the `t_syscall_audited_by` schema. Each row represents a system call (`x`) that satisfies the complex axiom `SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`. The presence of a row in this table implies the existence of a corresponding audit process (`bfo:0000015`) monitoring the call.

### 7.3.3 Governance and Verification

The assertion that a system call is `auditedBy` a process introduces a verifiable chain of evidence for compliance officers. When an automated scanner queries the `t_syscall_audited_by` table, it retrieves the specific set of designative entities that the governance framework has deemed sensitive.

For instance, the inclusion of `sys_mount` (Row `audit_004`) in this table reflects a policy decision that file system mounting events—actions that modify the system's namespace structure—must be traced back to an observing process. If the audit logs for a given time window lack records generated by the auditor process for any `x` listed in Table 7.2, a compliance violation is immediately flagged. This structure ensures that the ontology is not merely a semantic exercise but a functional component of the security architecture, enforcing the requirement that critical designative entities never exist in an unobserved state.
