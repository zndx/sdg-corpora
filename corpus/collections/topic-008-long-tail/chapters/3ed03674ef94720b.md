# Chapter 4: Ontological Foundations of Kernel System Call Auditing

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the classification and governance of kernel-level system calls within the eBPF observability ecosystem. The objective is to define the structural relationships between low-level kernel operations and high-level audit processes, ensuring that all information content entities are rigorously mapped to compliance standards. The discussion herein focuses on the derivation of relational schemas from OWL axioms, specifically addressing the designation of system calls as information entities and their subsequent integration into audit trails. This framework is essential for maintaining data integrity in security-critical environments where kernel observability is mandated by governance protocols.

## 4.2 Designative Information Content Entities

### 4.2.1 Definition and Context

In the context of the Common Core Ontologies (CCO), information content entities are distinct from physical artifacts; they are generically dependent continuents that are about some thing. Within the specific domain of kernel observability (family: `04_ebpf_kernel`), we are concerned with a specific subclass: the Designative Information Content Entity (`cco:DesignativeICE`). A designative entity is one that serves to refer to or identify a specific entity within a system. When applied to the Linux kernel, system calls function as these designative entities. They do not merely represent a function call; they designate a specific, controlled interaction point between user space and kernel space.

The axiom governing this foundational concept is expressed in Manchester syntax as:

**Class: {X:Class} SubClassOf: cco:DesignativeICE**

Verbalized, this axiom asserts: **{X} is a designative information content entity.**

This definition implies that for a system call to be recognized within the audit framework, it must first be classified as a designative entity. This classification is not merely semantic but structural, serving as the primary key for downstream relational mapping. The designation process ensures that the entity is distinct, identifiable, and capable of being subjected to governance mechanisms such as auditing.

### 4.2.2 Relational Projection of Basic System Calls

To operationalize this axiom for technical compliance and database storage, we project the ontological structure into a relational schema. The schema for basic system calls, derived from `template_id: syscall_basic`, isolates the class identifier (`x`) as the primary attribute.

The schema is defined as follows:

```sql
CREATE TABLE t_syscall_basic (
    id VARCHAR(255),
    x VARCHAR(255),
    PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DesignativeICE"],"family":"04_ebpf_kernel","is_complex":false,"template_id":"syscall_basic"}'
```

In this schema, the column `x` represents the specific system call class (e.g., `open`, `read`, `close`). The `id` serves as a unique surrogate key within the compliance database. The primary key constraint on `id` ensures entity integrity, preventing duplicate registration of the same designative entity instance. The `is_complex` flag in the metadata comment indicates that this entity represents a standalone classification without inherent relational dependencies in this specific projection.

For example, the entity `openat2` is cataloged not merely as a function, but as a designated information entity that is subject to tracking. This inventory is a prerequisite for any higher-order governance, as one cannot audit an entity that has not been formally designated within the system ontology.

## 4.3 Audit Process Integration

### 4.3.1 The Audited By Relationship

While the designation of system calls establishes their existence as information entities, compliance frameworks require the ability to trace interactions between these entities and observational processes. This introduces a second layer of complexity: the relationship between the system call and the process that observes it. In formal ontology, this is modeled using the object property `sdg:auditedBy`.

The specific process performing the audit is defined by the Basic Formal Ontology (BFO) as `bfo:0000015`, which denotes a "Process." In the context of eBPF, this process is the execution of a bytecode program attached to a tracepoint or kprobe. The axiom governing this relationship is:

**Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015**

Verbalized, this axiom asserts: **{X} is a designative information content entity that is audited by some process.**

This axiom extends the definition of the system call. It is no longer sufficient for the call to be merely designative; it must now be actively linked to an ongoing process (`bfo:0000015`). This linkage is critical for security audits, as it provides the evidence trail required to verify that a specific kernel interaction was observed, logged, or acted upon by a security monitor.

### 4.3.2 Relational Projection of Audited System Calls

The relational projection of this axiom requires a schema that captures the system call class while acknowledging the complexity introduced by the "audited by" relationship. The schema, derived from `template_id: syscall_audited_by`, maintains the structure of the basic table but is semantically distinct due to the `is_complex` metadata flag and the underlying axiom logic.

The schema is defined as:

```sql
CREATE TABLE t_syscall_audited_by (
    id VARCHAR(255),
    x VARCHAR(255),
    PRIMARY KEY (id)
)
COMMENT '{"bfo_anchor":["cco:DesignativeICE"],"family":"04_ebpf_kernel","is_complex":true,"template_id":"syscall_audited_by"}'
```

Although the column structure appears identical to the basic schema, the `is_complex: true` designation in the comment indicates that the entity `x` in this table is implicated in a relationship with a BFO Process. In a full graph implementation or a more normalized relational model, this would necessitate a foreign key to a process table. However, in this specific projection, the focus remains on the *set of entities* that satisfy the condition of being audited.

The following table enumerates system calls that are currently subjected to active audit processes within the governance framework. These are high-value targets for security monitoring, often involving process creation, memory manipulation, or network interactions.

*Table 4.2: Registry of System Calls Subject to Audit Processes*

The data in Table 4.2 represents the subset of designative entities that satisfy the axiom `SubClassOf: ... sdg:auditedBy some bfo:0000015`. For instance, `execve` is listed because it is a designative entity that is actively monitored by a specific audit process (e.g., an eBPF program attached to the `sys_enter_execve` tracepoint). The presence of `bpf` (the syscall itself) in this list indicates recursive monitoring, where the mechanism used to perform auditing is itself subject to audit controls—a critical requirement for preventing tampering with the observability framework.

## 4.4 Compliance Verification and Schema Consistency

### 4.4.1 Verification of Axiom Adherence

The maintenance of a compliant governance framework requires periodic verification that the data populating the relational tables adheres strictly to the ontological axioms. The distinction between `t_syscall_basic` and `t_syscall_audited_by` is not merely categorization but functional scope.

Entities in `t_syscall_basic` represent the total universe of possible designative interactions. Entities in `t_syscall_audited_by` represent the intersection of that universe with the set of active BFO processes. Therefore, a necessary condition for compliance is that the set of entities in `t_syscall_audited_by` must be a subset of those recognized in the broader ontology (even if the broader ontology is not fully populated in the basic table for the sake of this specific audit scope).

Furthermore, the metadata comment `{"family":"04_ebpf_kernel"}` anchors these tables to a specific technical domain. This ensures that the definitions of "Process" (`bfo:0000015`) are interpreted specifically as kernel-space eBPF execution contexts, rather than generic user-space processes. This specificity is vital for accurate audit reporting.

### 4.4.2 Data Integrity and Governance

The integrity of the audit trail relies on the immutability of the primary keys (`id`) and the consistency of the class names (`x`). Any modification to the `x` value without a corresponding update to the underlying ontology definition constitutes a compliance violation. For example, if an entry for `ptrace` were altered to `ptrace_sys` without a formal axiom update, the audit trail would be severed from the semantic meaning of the "process tracing" capability.

Governance protocols dictate that updates to `t_syscall_audited_by` must be accompanied by evidence of the deployed audit process. This means that for every row in Table 4.2, there must exist a corresponding eBPF bytecode object or configuration artifact that implements the `sdg:auditedBy` relationship. Without this artifact, the row represents a "phantom" audit—a designation without execution—which is a critical failure state in security compliance.

In summary, the rigorous application of the `syscall_basic` and `syscall_audited_by` templates provides the structural backbone for kernel observability. By mapping OWL axioms to deterministic relational schemas, auditors can verify not just the presence of data, but the semantic correctness of the system's security posture.
