# Chapter 4: Ontological Formalization of Kernel System Calls in eBPF Audit Frameworks

## 4.1 Scope and Preamble

This chapter delineates the structural definitions of system calls within the context of kernel observability and compliance auditing. It establishes the foundational axioms governing the designation of information content entities and their subsequent relationship to audit processes. The objective is to provide a rigorous, evidence-based framework for mapping kernel-level interactions to ontological classes, ensuring that audit trails are both semantically grounded and verifiable against formal logic constraints. The definitions herein are essential for architects implementing eBPF-based monitoring solutions who require adherence to high-assurance governance standards.

## 4.2 Designative Information Content Entities in System Call Interfaces

### 4.2.1 The Concept of Designative ICE

In the context of kernel observability, a system call must be understood not merely as a functional invocation of kernel routines, but as a formal information entity. Ontologically, this is categorized as a Designative Information Content Entity (ICE). A Designative ICE is a specific type of information entity that serves to stand for or designate another entity within a system. When a user-space process invokes `sys_open`, the invocation itself is an event, but the definition and structure of `sys_open` within the kernel's interface constitute a Designative ICE. It designates the specific capability and protocol for opening file descriptors.

This distinction is critical for audit compliance. The audit log does not merely record raw binary execution; it records instances of interactions that conform to these designative definitions. By formalizing system calls as instances of `cco:DesignativeICE`, we establish a standardized vocabulary for cross-referencing kernel events with security policies. This allows governance frameworks to assert that a specific observed event is, in fact, an instance of a defined, sanctioned interface, rather than an arbitrary memory jump or exploit.

### 4.2.2 Basic System Call Axiomatization

The fundamental axiom governing this classification asserts that any system call class (`X`) within the scope of this framework is a subclass of `cco:DesignativeICE`. This is expressed in the Manchester syntax as `Class: {X:Class} SubClassOf: cco:DesignativeICE`. This axiom serves as the primary structural constraint for the basic registry of kernel interfaces. It ensures that every syscall monitored by the eBPF probe is ontologically grounded as an information artifact with a specific designation role.

The implication of this axiom is that the system call registry is not a flat list of function pointers, but a hierarchical knowledge structure. For a syscall to be valid within the audit ontology, it must inherit the properties of a Designative ICE. This includes the capacity to be referenced, to be part of a larger documentation set, and to be the subject of information security controls. Without this ontological grounding, an audit log would consist of meaningless integer opcodes; with it, the log becomes a sequence of verified, designated interactions.

### 4.2.3 Verification and Compliance

When deploying eBPF programs to monitor these calls, the verifier ensures that the loaded program references only valid, designated symbols. This technical enforcement mirrors the ontological axiom: the kernel rejects attempts to invoke or monitor entities that do not conform to the `DesignativeICE` structure. Consequently, the compliance officer can assert with high confidence that the "Basic System Call" registry represents a complete and validated set of kernel interfaces, excluding undocumented or rogue entry points that might indicate a rootkit or kernel modification.

## 4.3 Audit Process Integration and System Call Verification

### 4.3.1 The Audit Process as a Processual Entity

To transition from basic definition to active governance, we must introduce the concept of the audit process. In the Basic Formal Ontology (BFO), a process is an entity that unfolds in time and has temporal parts. The audit of a system call is not a static state but a `bfo:0000015` (Process) that involves the observation, recording, and validation of a syscall event. This process is initiated by the eBPF hook upon the execution of a designated system call and terminates when the audit record is serialized to the user-space collector.

The relationship between the system call and the audit process is not merely incidental; it is axiomatic. Certain classes of system calls are defined *specifically* by their relationship to the audit process. This is a critical distinction in security governance. While all syscalls are Designative ICEs, only a subset is formally defined by the requirement that they be "audited by" a specific processual entity. This relationship is captured by the object property `sdg:auditedBy`.

### 4.3.2 Axiomatization of Audited System Calls

The formal axiom for audited system calls extends the basic definition. It states: `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`. This verbalizes to: "{X} is a designative information content entity that is audited by some process." This is a more complex restriction than the basic axiom. It asserts that for a class `X` to exist in this category, there must exist at least one audit process (`bfo:0000015`) that acts upon it.

This axiom allows the governance framework to differentiate between standard operational calls and security-relevant calls. For instance, a simple `sys_getpid` might be a Designative ICE (Axiom 2), but it may not be subject to the `auditedBy` restriction in a standard policy. Conversely, a call like `sys_execve` or `sys_mount` is inherently sensitive and is defined by its relationship to the audit process. The presence of the `auditedBy` property in the class definition mandates that any instance of this class *must* generate an audit trail. Failure to capture an event for a class defined by this axiom constitutes a violation of the ontological structure and, by extension, a compliance failure.

This linkage ensures that any attempt to execute `sys_execve` (which replaces a process's memory image) is inextricably bound to the generation of an audit record. The ontological structure enforces the security policy: the definition of the call *includes* the requirement to be audited.

### 4.3.4 Governance Implications

The separation between the basic system call registry (Table 4-1) and the audited system call registry (Table 4-2) provides a mechanism for "audit by definition." In traditional systems, auditing is often a configuration overlay—a list of rules applied to a pre-existing set of functions. In this ontological approach, the audit requirement is embedded in the definition of the system call class itself. This aligns with the principles of "privacy by design" or "security by design."

For the auditor, this means that verifying compliance involves checking the ontological definitions (the axioms) rather than just runtime configuration files. If the class definition for `sys_connect` includes `sdg:auditedBy some bfo:0000015`, then the absence of log entries for `sys_connect` is a logical contradiction within the system state. It indicates either a failure of the processual entity (the audit daemon crashed) or a bypass of the designative entity (a rootkit hiding the call). Thus, the ontology serves as a rigorous diagnostic tool for forensic analysis and continuous compliance monitoring.
