# Chapter 4: Kernel Interface Classification and Audit Protocols

## 4.1 Scope and Governance Framework

This chapter establishes the mandatory taxonomic framework for the classification of kernel-level system calls within the extended Berkeley Packet Filter (eBPF) governance subsystem. It delineates the ontological distinction between standard interface designations and those entities subject to active process auditing, providing the structural definitions required for compliance verification. The protocols outlined herein are binding upon all kernel modules and user-space agents interacting with the `04_ebpf_kernel` family, ensuring that information content entities are rigorously mapped to their logical and behavioral constraints. Adherence to these classifications is a prerequisite for maintaining the integrity of the audit trail and fulfilling the requirements of the security control matrix.

## 1. Basic System Call Classification

### 1.1 Ontological Foundations of Designative Entities

In the context of kernel architecture and system programming, a fundamental distinction must be drawn between the execution of a process and the informational entity that designates that process. According to the foundational axioms of the Common Core Ontologies (CCO), a specific class of system calls is categorized as a **Designative Information Content Entity** (`cco:DesignativeICE`). This classification asserts that the system call, in its basic form, functions primarily as a signifier or a label—a stable reference point within the kernel's symbol table that designates a specific operation or function without necessarily invoking an external oversight mechanism.

The axiom governing this classification is expressed formally as:
*   **Class:** `{X:Class}` SubClassOf: `cco:DesignativeICE`

This verbalization implies that for any entity `X` falling under this classification, `X` is a designative information content entity. In practical terms, this means the system call serves as a "designator" for a kernel routine. It exists as a data structure within the system namespace, providing the necessary linkage between the user-space invocation and the kernel-space implementation. The "basic" nature of these entities lies in their lack of inherent binding to an audit process; they are defined solely by their capacity to designate an action, rather than their capacity to be monitored by a separate agent.

To ensure consistency across the kernel interface, all basic system calls must be registered within the central governance repository. The following table exhibits a subset of entities that satisfy the axiom for basic designative information content entities. The primary key `id` serves as the unique identifier for this designation within the compliance framework. It is imperative that developers and auditors reference these `id` values when verifying that a system call has been correctly categorized as a basic, non-audited entity within the module's manifest.

### 1.3 Compliance Implications for Basic Entities

When a system call is classified under the `t_syscall_basic` schema, it implies that the default security posture for that interface does not mandate an active audit hook. However, this exemption is not absolute; it applies only to the definition of the entity itself. System integrators must be aware that while `SyscallWrite` is a designative entity, the *data* passed through it may still be subject to filtering. The distinction here is ontological: the *call itself* is the entity being classified. The governance framework requires that no external audit process (`bfo:0000015`) be hard-linked to these classes at the schema level, preserving their status as pure designators.

## 2. Audited System Call Protocols

### 2.1 The Audit Relationship and Process Binding

While basic system calls function as designators, a specific subset of system calls requires the attachment of an oversight mechanism to satisfy security governance requirements. This classification is governed by a more complex axiom which introduces a relational property: `auditedBy`. This axiom asserts that a system call is not only a designative information content entity but is also necessarily the object of an audit action performed by a distinct process.

The formal axiom for this classification is:
*   **Class:** `{X:Class}` SubClassOf: `cco:DesignativeICE`, `sdg:auditedBy` some `bfo:0000015`

Verbalized, this axiom states that `{X}` is a designative information content entity that is audited by some `bfo:0000015` (a Process). This introduces a directed relationship between the system call (the object) and the auditing process (the agent). In this context, `bfo:0000015` refers to the Basic Formal Ontology (BFO) definition of a "process"—an entity that unfolds in time and possesses temporal parts. Consequently, any system call classified under this axiom is intrinsically bound to a temporal, unfolding audit event. It is not merely a name; it is a monitored event trigger.

### 2.2 Registry of Audited Entities

The following table provides the registry for system calls that fall under the audited classification. These entities have been rigorously evaluated and determined to require binding to an audit process. The inclusion of an entity in this table mandates that the kernel module instantiate an eBPF program or a tracepoint attached to the corresponding system call vector, thereby satisfying the `auditedBy` constraint.

**Table 2.1: Registry of Audited System Call Entities (t_syscall_audited_by)**

| id | x |
|---|---|
| sys_audit_01 | SyscallExecve |
| sys_audit_02 | SyscallClone |

| sys_audit_04 | SyscallSetuid |
| sys_audit_05 | SyscallMount |
| sys_audit_06 | SyscallUmount |
| sys_audit_07 | SyscallChmod |

In Table 2.1, the `x` column lists the Classes that satisfy the complex axiom. For example, `SyscallExecve` is listed because the execution of a new program is a critical security-relevant event that must be audited by a process (the eBPF verifier and logger). The relationship `sdg:auditedBy` is materialized by the presence of this entry in the `t_syscall_audited_by` table rather than the basic table. The `id` serves as the foreign key anchor for audit logs, linking the specific invocation of the call to the record generated by the auditing process.

### 2.3 Verification of Audit Integrity

The governance framework requires strict verification that the `auditedBy` relationship is active for all entities listed in Table 2.1. Compliance officers must validate that for every instance of `SyscallMount` or `SyscallSetuid`, a corresponding process entry exists in the runtime audit logs. The ontology dictates that the relationship is existential ("some `bfo:0000015`"), meaning that the existence of the system call entity implies the existence of at least one auditing process.

Failure to maintain this relationship constitutes a violation of the schema constraints. If a system call is defined in the code as a subclass of `cco:DesignativeICE` and invokes the `sdg:auditedBy` property, but no process is actually attached to intercept and log the event, the system is in a state of ontological non-compliance. This discrepancy must be flagged in the audit report as a "Critical Schema Violation."

### 2.4 Security Implications and Governance

The distinction between the basic and audited classifications is not merely academic; it drives the allocation of kernel resources and the enforcement of security policies. Entities in `t_syscall_audited_by` consume additional clock cycles and memory to facilitate the auditing process. Therefore, the classification process must be precise. Over-classifying basic calls as audited can lead to performance degradation and resource exhaustion, while under-classifying sensitive calls (e.g., omitting `SyscallExecve` from Table 2.1) results in blind spots in the security visibility layer.

The governance framework thus treats these tables as the source of truth for eBPF program loading. Only those calls present in `t_syscall_audited_by` shall trigger the loading of the associated audit bytecode. This ensures that the kernel's runtime behavior strictly adheres to the formal definitions provided in the ontology, maintaining a closed loop between the semantic definition of the system call and its operational reality.
