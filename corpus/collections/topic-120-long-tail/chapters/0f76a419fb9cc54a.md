# Chapter 12: Spatial Attribution and Artifact Compliance in Municipal Infrastructure

## 12.1 Scope and Regulatory Context

This chapter establishes the mandatory protocols for the spatial attribution of civic artifacts within the Municipal Infrastructure Registry (MIR). Pursuant to the Infrastructure Governance Act (IGA) 2022, Section 4(c), all physical assets classified as `cco:Artifact` must be rigorously linked to valid postal address entities to ensure auditability and emergency response readiness. The guidelines contained herein define the ontological relationship between artifact classes and their spatial coordinates, providing the deterministic schema required for the central asset database. Compliance with these standards is mandatory for all district managers and registered stakeholders; failure to maintain accurate spatial attribution may result in the suspension of maintenance funding and regulatory non-compliance citations.

## 12.2 Ontological Definition of Spatial Attribution

The foundational concept governing asset registration is the axiom of spatial attribution, formally defined as `schemaorg_place_address`. This axiom asserts a necessary condition for the classification of any physical entity within the municipal domain. Specifically, it dictates that for an entity to be recognized as a valid Artifact (X), it must possess a `sdg:hasPostalAddress` relationship with a defined Address entity (Y).

This relationship is not merely associative but constitutive; the existence of the artifact in the registry is contingent upon the validity of its postal address reference. The Manchester syntax for this axiom is expressed as:

`Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`

In natural language, this verbalization is interpreted as: {X} is something that has postal address {Y}. This constraint ensures that every tracked asset—from static street furniture to mobile emergency units—is geo-located within the standardized postal framework. The implementation of this rule eliminates "orphan" assets—physical objects that consume maintenance resources but lack a verifiable jurisdictional location.

### 12.2.1 Relational Projection and Schema Mapping

To enforce this axiom within the relational database infrastructure, the MIR utilizes a deterministic projection of the ontology into a tabular schema. The table `t_schemaorg_place_address` serves as the validation layer for class-level definitions. It does not store individual asset instances (e.g., "Lamp Post #405"), but rather the *rules* that dictate which classes of artifacts are permitted to associate with which classes of addresses.

The primary key of this table is the unique identifier (`id`), which corresponds to the specific axiom instantiation. The columns `x` and `y` function as foreign keys to the ontology definition tables, representing the Artifact Class and the Address Class, respectively. The structure enforces that `y` cannot be null, guaranteeing that no artifact class is defined without a spatial binding.

For instance, the `TrafficControlCabinet` is explicitly defined as a subclass of artifacts that must possess a `MunicipalRightOfWayAddress`, thereby excluding it from being registered with residential or postal codes.*

## 12.4 Compliance Verification and Audit Protocols

Verification of spatial attribution is conducted through quarterly automated audits. The system queries the `t_schemaorg_place_address` table to generate a compliance report for every asset instance. If an asset instance is found where its class is not listed in column `x` of the axiom table, or if its linked address does not match the class in column `y`, a non-compliance flag is raised.

## 12.5 Implementation Guidelines for Data Entry

Personnel responsible for entering data into the MIR must adhere to the following strict guidelines to ensure consistency with the `schemaorg_place_address` axiom:

1.  **Class Selection:** When defining a new asset, the user must select an Artifact Class (`x`) that exists in the `t_schemaorg_place_address` table. Custom classes are prohibited without a formal ontology change request (OCR).
2.  **Address Binding:** The system will automatically restrict the available Address Classes (`y`) based on the selection of `x`. For example, if `EmergencyResponseUnit` is selected, the system will only allow the selection of an address from the `FacilityGridAddress` class.
3.  **Validation:** Upon saving, the system executes a check: `SELECT COUNT(*) FROM t_schemaorg_place_address WHERE x = [input_class] AND y = [input_address_class]`. If the result is zero, the transaction is rejected.

By adhering to these protocols, the municipality ensures that the digital twin of the city's infrastructure remains robust, queryable, and legally defensible.
