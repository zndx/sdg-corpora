# Chapter 4: Ontological Formalization of Kernel Syscall Auditing Mechanisms

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the identification and auditing of kernel-level system calls within the `04_ebpf_kernel` framework. It establishes the necessary axioms for classifying system calls as Designative Information Content Entities (ICE) and defines the relational constraints binding these entities to their auditing processes. The content herein is intended for systems architects, compliance officers, and security analysts responsible for implementing rigorous governance over extended Berkeley Packet Filter (eBPF) observability programs. By adhering to the axioms defined in Section 4.2, practitioners ensure that kernel telemetry is not merely collected but is semantically anchored to a formal taxonomy, facilitating automated reasoning and high-fidelity audit trail reconstruction.

## 4.2 The Designative Information Content Entity

### 4.2.1 Axiomatic Definition

In the context of kernel observability, a system call must be treated not merely as a functional interrupt or a transition to kernel mode, but as a discrete, semantically grounded entity. The foundational axiom for this classification is derived from the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO).

The axiom asserts that a specific class of system call, denoted as `{X}`, is a subclass of `cco:DesignativeICE`. A Designative Information Content Entity is defined as an entity that stands for or refers to another entity. In the case of syscalls, the call designates a specific intent or function requested by a user-space process (e.g., `open`, `read`, `execve`). Furthermore, this axiom establishes a necessary existential restriction: `{X}` must be audited by some instance of `bfo:0000015` (a Process).

**Axiom 1 (template_id: syscall_audited_by):**
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`
*   **Verbalization:** `{X}` is a designative information content entity.

This formalization ensures that for any syscall class to be valid within the governed system, it must possess an intrinsic property of "being auditable." This is not a contingent feature of the implementation but a necessary condition of the class definition itself.

### 4.2.3 The Auditing Process (bfo:0000015)

The `bfo:0000015` slot in the axiom refers to a BFO "Process." In the implementation of this framework, the Process is realized by the eBPF probe attached to the kernel tracepoints. The ontological requirement that `{X}` is "audited by some" Process necessitates that for every row in `t_syscall_audited_by`, there must be a corresponding, active instrumentation mechanism in the kernel.

If a syscall class is defined in the ontology (i.e., exists in column `x`) but lacks an active auditing process (e.g., the eBPF program is unloaded or the tracepoint is disabled), the system is in a state of ontological violation. This violation indicates a gap between the formal governance model (the axiom) and the physical runtime state. Therefore, compliance audits must verify not only the presence of the row in the registry table but also the operational status of the linked `bfo:0000015` process.

## 4.3 Operational Compliance and Tracepoint Correlation

### 4.3.1 Mapping Designative Entities to Kernel Tracepoints

While Section 4.2 establishes the *existential* requirements for syscall auditing, operational governance requires a precise mapping between the ontological entities (`cco:DesignativeICE`) and the raw kernel tracepoints utilized by the eBPF subsystem. This mapping ensures that the "audited by" relation is technically feasible and correctly instrumented.

This level of granularity is required for high-assurance systems where the mere presence of an audit log is insufficient; the semantic classification of the event must be traceable back to the formal ontology.

### 4.3.2 Verification Protocol

To maintain compliance with the `syscall_audited_by` axiom, the following verification protocol must be executed at regular intervals:

1.  **Schema Validation:** Query the `t_syscall_audited_by` table to ensure all defined `{X}` classes possess a valid `id` and are non-null.
2.  **Runtime Verification:** Confirm that for every entry in `t_syscall_audited_by`, the corresponding tracepoint listed in Table 4.2 is active in the running kernel configuration.
3.  **Axiomatic Consistency:** Verify that no `bfo:0000015` process is auditing a syscall class that is not formally defined as a `cco:DesignativeICE` in the registry. This prevents "orphan" audit data that lacks semantic grounding.

Failure to satisfy any of these conditions constitutes a compliance deviation. For instance, if the `SyscallMount` entity were removed from `t_syscall_audited_by` but the eBPF program continued to log `sys_enter_mount` events, the resulting data would be "non-designative" according to the framework—it would exist as raw data without formal semantic standing, potentially violating data retention policies regarding evidentiary quality.

## 4.4 Summary of Governance Requirements

The integration of the `syscall_audited_by` axiom into the system architecture mandates a strict separation of concerns between the definition of the entity (the syscall class) and the process of observation (the audit). By treating syscalls as `cco:DesignativeICE`, the framework elevates kernel telemetry from a stream of binary events to a structured, queryable knowledge base.

The `t_syscall_audited_by` table acts as the central source of truth for this semantic elevation. It is not merely a configuration file but a materialization of the domain ontology. Consequently, any modification to the system's observability capabilities—such as the addition of new security hooks or the deprecation of legacy syscalls—must begin and end with transactions against this table. This ensures that the system remains formally verifiable and that the audit trail maintains its integrity as a set of Designative Information Content Entities, each rigorously linked to its auditing process.
