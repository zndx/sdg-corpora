# Chapter 7: Ontological Formalization of Kernel Audit Entities

## 7.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the verification of kernel-level information entities within secure computing environments. It addresses the classification of system calls as Designative Information Content Entities (ICE) and their requisite association with auditing processes. The scope is limited to the verification of these entities within eBPF-enabled kernel subsystems, ensuring traceability and compliance with governance mandates. The definitions provided herein are axiomatic, derived from the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO), to support rigorous audit reporting and automated compliance enforcement.

## 7.2 The Designative Information Content Entity (DICE)

### 7.2.1 Axiomatic Definition

The foundational concept for kernel audit verification is the Designative Information Content Entity. Formally, this is defined by the axiom:

**Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015**

In this context, the variable {X} represents a specific class of system call or kernel event. The axiom asserts that for any class X to be recognized within the audit ontology, it must satisfy two necessary conditions:
1.  It must be a subclass of `cco:DesignativeICE`, meaning it is a generically dependent continuant that conveys meaning or designates a specific function within the operating system.
2.  It must participate in the `sdg:auditedBy` relation with at least one instance of `bfo:0000015` (a BFO Process).

This formalism ensures that audit trails are not merely collections of raw data points but are structured records of information content entities that are explicitly defined and monitored by a temporal process. The "designative" nature of the entity implies that the syscall identifier (e.g., `openat`, `execve`) stands for the underlying kernel operation, serving as a semantic bridge between the binary execution and the human-readable audit log.

### 7.2.2 The Process Dependency

The relation `sdg:auditedBy some bfo:0000015` introduces a critical dependency on processual occurrents. `bfo:0000015` denotes a process—an entity that unfolds in time and has temporal parts. In the context of Linux kernel auditing, this process is the execution of the audit daemon (auditd), the eBPF verifier and loader, or the associated tracepoint handlers.

The axiom dictates that a Designative ICE cannot exist in the governance framework without being linked to an active auditing process. This prevents "orphan" data classes—information entities that are defined but not actually monitored—from polluting the compliance schema. It ensures that for every syscall class X defined in the system, there is a verifiable, active mechanism (the process) responsible for capturing its invocation parameters, return codes, and context.

## 7.3 Verification of Network Audit Entities

### 7.3.1 Extension to Network Subsystems

While file system operations provide a clear illustration of the axiom, the governance framework requires equal rigor for network subsystems. The transmission and reception of data packets are governed by specific system calls that must also be classified as Designative Information Content Entities.

In this domain, the "designative" function of the entity refers to the intent to connect, bind, or send data. The `sdg:auditedBy` relation is satisfied by the eBPF programs attached to socket tracepoints (e.g., `sys_enter_connect`, `sys_exit_accept`). The ontological structure remains unchanged: the class X (e.g., `ConnectSyscall`) is a Designative ICE, and it is audited by a process.

### 7.3.2 Compliance and Data Integrity

From a compliance perspective, the verification of the `syscall_audited_by` axiom involves querying the audit logs to ensure that for every critical class X, a corresponding record exists. If a class is defined in the policy (e.g., "All `ConnectSyscall` attempts must be audited"), but the table lacks entries for this class, the axiom is violated, indicating a failure in the auditing process or a gap in the information capture mechanism.

## 7.4 Governance Framework Implications

### 7.4.1 Audit Trail Completeness

The application of the `syscall_audited_by` axiom provides a mathematical basis for audit trail completeness. In traditional systems, "completeness" is often a heuristic. Within this ontological framework, completeness is verifiable: the set of all audit records must be a superset of the intersection of all critical classes X and the set of all processes where `sdg:auditedBy` is active.

If the audit report indicates that `ConnectSyscall` is a critical class (a subclass of `cco:DesignativeICE` requiring monitoring), the absence of rows in `t_syscall_audited_by` where `x = 'ConnectSyscall'` constitutes a formal finding of non-compliance. This elevates the audit report from a descriptive document to an evidence-based verification of the system's state against the formal ontology.

### 7.4.2 Impact on Rights and Service Quality

As noted in regulatory frameworks (such as those governing taxpayer rights or digital service standards), entities have a right to a system that functions accurately and without undue burden. The `syscall_audited_by` axiom directly supports this by ensuring that the monitoring mechanisms (the processes) are tightly coupled to the definitions of the entities they monitor.

By mandating that a Designative ICE *must* be audited by a process, the ontology prevents the implementation of "zombie" monitoring policies—rules that exist in documentation but are not executed by the system. This ensures that the computational overhead of auditing is strictly tied to the generation of verifiable, evidence-anchored data, thereby optimizing system performance while maintaining high assurance levels.
