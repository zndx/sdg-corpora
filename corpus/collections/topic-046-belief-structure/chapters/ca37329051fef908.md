# Chapter 4: Ontological Mapping of eBPF Audit Provenance

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing kernel-level syscall auditing within extended Berkeley Packet Filter (eBPF) environments. It establishes the requisite definitions for designative information content entities as they pertain to system calls, and rigorously defines the audit relationships between these entities and kernel processes. The content herein is intended to serve as a reference framework for compliance officers, system architects, and security analysts responsible for verifying the integrity of audit trails in high-assurance computing environments. All mappings are derived from the Common Core Ontologies (CCO) and the Basic Formal Ontology (BFO), ensuring alignment with upper-level semantic standards.

## 4.2 The Designative Information Content Entity (DICE)

In the context of kernel observability, a system call must be understood not merely as a functional invocation, but as a specific subclass of a Designative Information Content Entity (DICE). According to the axiom `syscall_audited_by`, any class `X` representing a system call is ontologically classified as a `cco:DesignativeICE`. This classification asserts that the entity `X` serves as a signifier or label that designates a specific process or function within the operating system's execution model.

The distinction is critical for audit compliance. While the execution of a syscall is a temporal event, the syscall *class* itself (e.g., `open`, `read`, `write`) is an information entity that persists independently of any single execution instance. By treating these classes as DICEs, the audit framework can attach metadata, provenance data, and governance constraints to the *concept* of the syscall, rather than merely to its transient instances. This allows for the creation of persistent policy rules that apply across all invocations of a specific syscall type.

For example, the class `OpenSyscall` is a designative entity. It refers to the abstract concept of a file opening operation. In an audit report, one must distinguish between the specific event where Process A opened File B (an instance), and the class `OpenSyscall` which is the subject of the governance rule. The axiom `X SubClassOf cco:DesignativeICE` formally anchors this distinction, ensuring that the registry of audited components is populated with stable, referable classes rather than ephemeral event data.

## 4.3 The Audit Relationship and Processual Agents

### 4.3.1 The Role of bfo:0000015

The axiom `sdg:auditedBy some bfo:0000015` introduces the agent responsible for the observation. The entity `bfo:0000015` refers to a `Process`, defined in BFO as an occurrent that has temporal parts and unfolds over time. In the context of eBPF auditing, this Process is the observer—typically a kernel-space probe or a user-space daemon consuming perf buffers.

The ontology dictates that the audit relationship is not merely a passive recording but an active dependency. The Designative ICE (the syscall class) is "audited by" the Process. This implies a directional relationship where the integrity of the audit data is contingent upon the correct functioning and existence of the Process. If the Process (the auditor) terminates or is compromised, the relationship `auditedBy` is severed, effectively breaking the audit chain.

### 4.3.2 The sdg:auditedBy Property

The property `sdg:auditedBy` functions as the semantic link between the syscall class and the auditing process. It is a specific object property that maps the domain of information entities to the range of processes. In a compliance framework, this property must be instantiated for every syscall that falls under the scope of the audit policy.

It is insufficient to simply state that a system is "monitored." The ontology requires explicit declaration of *what* is monitored (the DICE) and *by whom* (the Process). This granularity allows for granular compliance queries, such as "Retrieve all syscall classes audited by Process ID 4022," or "Validate that all critical syscalls are audited by a high-integrity process."

## 4.4 System Call Classification and Audit Mapping

To operationalize these axioms, we must map specific syscall classes to the auditing infrastructure. The following table, `t_syscall_audited_by`, embodies the axiom `syscall_audited_by`. It enumerates specific classes of system calls (X) that are defined as Designative Information Content Entities and explicitly links them to the auditing process via the `auditedBy` relationship.

The primary key `id` serves as a unique identifier for the audit rule, while the column `x` represents the class name of the syscall. The existence of a row in this table constitutes a formal assertion that the syscall class `x` is within the scope of the audit regime.

**Table 4-1: System Call Audit Classification (t_syscall_audited_by)**

| id | x |
| :--- | :--- |
| audit_rule_001 | OpenSyscall |
| audit_rule_002 | CloseSyscall |
| audit_rule_003 | ReadSyscall |
| audit_rule_004 | WriteSyscall |
| audit_rule_005 | SocketBindSyscall |
| audit_rule_006 | ConnectSyscall |
| audit_rule_007 | CloneSyscall |

*Table 4-1 Notes:*
*   **id**: The unique identifier for the audit mapping entry.
*   **x**: The class name of the system call, which is a subclass of `cco:DesignativeICE`.

The data in Table 4-1 indicates that the `OpenSyscall` class is subject to auditing. In a runtime environment, this implies that any kernel invocation matching the signature of `open` or `openat` will trigger the audit logic defined by the associated Process. The inclusion of `SocketBindSyscall` and `ConnectSyscall` demonstrates the application of this ontology to network security monitoring, extending the audit coverage beyond file system operations.

## 4.5 Process Registry and Audit Agents

While the previous table defines *what* is being audited, effective governance requires visibility into *who* is performing the audit. The following table provides a registry of the Process entities (instances of `bfo:0000015`) that act as the auditors. This registry is essential for verifying that the agents referenced in the `auditedBy` relationships are authorized, active, and correctly configured.

**Table 4-2: Kernel Audit Process Registry (t_process_registry)**

| process_id | process_name | execution_context | integrity_level |
| :--- | :--- | :--- | :--- |
| 1001 | kprobe_audit_daemon | kernel_space | high |
| 1002 | trace_collector_v1 | user_space | medium |
| 1003 | net_monitor_ebpf | kernel_space | high |
| 1004 | file_access_logger | user_space | medium |
| 1005 | syscall_filter_agent | kernel_space | critical |

*Table 4-2 Notes:*
*   **process_id**: The unique identifier for the process instance.
*   **process_name**: The human-readable designation of the auditing agent.
*   **execution_context**: Specifies whether the process runs in kernel space (e.g., eBPF program) or user space.
*   **integrity_level**: The assurance level assigned to the process, determining its trustworthiness in handling audit data.

The correlation between Table 4-1 and Table 4-2 allows a compliance officer to trace the lineage of an audit event. For instance, `audit_rule_005` (pertaining to `SocketBindSyscall`) would, in a full implementation, be linked to `process_id` 1003 (`net_monitor_ebpf`). This linkage confirms that the audit obligation is being fulfilled by a high-integrity, kernel-space agent, satisfying the requirements of the `sdg:auditedBy` axiom.

## 4.6 Compliance Verification

Verification of the audit framework involves querying the relational schema to ensure that all critical syscall classes are represented in `t_syscall_audited_by` and that the corresponding auditing processes in `t_process_registry` are operational. A gap analysis should be performed to identify syscall classes that are Designative ICEs but are absent from the audit table, indicating a potential compliance violation.

Furthermore, the ontology mandates that the relationship is "some" `bfo:0000015`. This existential quantification implies that for every audited syscall class, there must exist at least one process performing the audit. If a process in Table 4-2 enters a terminated state, the corresponding rows in Table 4-1 effectively represent orphaned policies. Therefore, the maintenance of these tables is not merely a data entry exercise but a continuous operational requirement to ensure the validity of the audit proof.
