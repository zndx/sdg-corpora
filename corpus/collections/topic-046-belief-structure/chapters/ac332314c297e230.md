# Chapter 4: Kernel Audit Semantics and Designative Entities

## 4.1 Scope and Preamble

This chapter delineates the formal ontological framework governing the identification and auditing of kernel-level system calls within extended Berkeley Packet Filter (eBPF) environments. The primary objective is to establish a rigorous mapping between designative information content entities—specifically, system call invocations—and the auditing processes responsible for their verification. We adhere to the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO) to ensure semantic interoperability across compliance frameworks. The discussion proceeds from the definition of the system call as a designative entity to the relational schema that binds these entities to their respective audit processes.

## 4.2 The Designative Information Content Entity

### 4.2.1 Ontological Foundations

In the context of kernel observability, a system call is not merely a computational instruction; it is an information content entity that designates a specific interaction between user space and kernel space. According to the Common Core Ontologies, such an entity is classified as a `cco:DesignativeICE`. This classification asserts that the system call functions as a signifier or a label that stands for a distinct process or operation within the operating system's execution flow.

The designation is critical for audit trails. It transforms a transient hardware event into a persistent, semantically grounded data point. Without this designative property, audit logs would consist of raw memory addresses or register states devoid of interpretative context. By formalizing the system call as a `cco:DesignativeICE`, we enable the application of governance rules, access controls, and compliance checks that operate on the *meaning* of the event, rather than its binary representation.

### 4.2.2 Class Definition and Subclass Axioms

We define a specific class of entities, denoted here as `{X}`, which represents the set of auditable system calls. The formal axiom governing this class is expressed in Manchester Syntax as:

`Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`

This axiom asserts two necessary conditions for membership in class `{X}`. First, the entity must be a `cco:DesignativeICE`. Second, it must bear the `sdg:auditedBy` relationship to at least one instance of `bfo:0000015`. In BFO, `bfo:0000015` refers to a "Process," specifically an occurrent entity that unfolds in time. Therefore, for a system call to be a member of the audited class `{X}`, it is logically necessary that it is subject to an auditing process.

This structure ensures that the concept of an "audited system call" is not merely a linguistic label but a formally defined category within the ontology. It excludes system calls that are designative but not monitored, or those that are monitored but lack proper designative classification (e.g., raw binary dumps without semantic headers).

## 4.3 The Audit Process Relationship

### 4.3.1 The Auditing Process (bfo:0000015)

The object of the `sdg:auditedBy` relationship is the auditing process itself, formally classified as `bfo:0000015`. In the context of eBPF-based security frameworks, this process is an occurrent that spans the interval from the triggering of the system call to the finalization of the audit record in the user-space ring buffer.

This process is not static; it involves temporal boundaries, a sequence of procedural steps (context capture, filtering, serialization), and a termination state (record emission). The ontological commitment to `bfo:0000015` emphasizes that auditing is an *activity* with a duration, rather than a passive data attribute. It validates that the designative entity `{X}` is actively "processed" by a governance mechanism.

### 4.3.2 Relational Mapping and Schema

The relationship between the designative entity `{X}` and the auditing process is materialized in the relational schema `t_syscall_audited_by`. This table serves as the join index between the static definition of the system call and the dynamic process instances that observe it.

The schema is defined as follows:

```sql
CREATE TABLE t_syscall_audited_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
)
```

In this schema, the column `id` represents the unique identifier for the audit mapping instance, while the column `x` functions as a foreign key reference to the designative entity (the Class `{X}`). The table embodies the axiom `sdg:auditedBy some bfo:0000015` by linking the specific entity `x` to the implicit process context managed by the audit framework.

## 4.4 Compliance Verification and Data Integrity

The integration of ontological axioms into the relational schema facilitates automated compliance verification. By querying the `t_syscall_audited_by` table, auditors can verify that all critical designative entities—those representing high-risk kernel interactions—are properly mapped to an active auditing process.

If a system call exists in the kernel source but is absent from the `x` column of `t_syscall_audited_by`, it constitutes a violation of the subclass axiom `sdg:auditedBy some bfo:0000015`. Such a gap indicates that the entity is a designative information content entity but lacks the requisite process oversight, rendering the system non-compliant with the defined governance framework.

Furthermore, the deterministic derivation of the schema from the ontology ensures that the data model remains synchronized with the conceptual model. As new system calls are introduced into the kernel (e.g., new virtualization primitives), the ontology requires the creation of a corresponding entry in `{X}` and a subsequent row in `t_syscall_audited_by` to maintain the integrity of the audit trail. This closed-loop approach between semantic definition and data storage is essential for high-assurance systems operating under strict regulatory mandates.
