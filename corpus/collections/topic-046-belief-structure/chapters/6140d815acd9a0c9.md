# Chapter 4: Ontological Formalization of eBPF Kernel Auditing

## 4.1 Scope and Preamble

This chapter delineates the formal ontological framework required to govern and audit system call interception within Extended Berkeley Packet Filter (eBPF) environments. As kernel-level observability mechanisms become increasingly sophisticated, the ad-hoc logging strategies typical of legacy audit frameworks prove insufficient for rigorous compliance verification. We establish a deterministic mapping between high-level kernel primitives and the Information Content Entities (ICEs) that represent them within a governance ontology. The objective is to provide a reproducible schema for defining which system calls are subject to audit protocols, ensuring that the designative properties of kernel objects are preserved and traceable through the audit pipeline. This approach aligns with the requirements of modern security compliance mandates, which demand evidence anchored in formal logic rather than heuristic detection.

## 4.2 The Designative Information Content Entity

### 4.2.1 Definition and Context

In the context of kernel auditing, a system call is not merely a functional transition from user space to kernel space; it is an entity that *designates* a specific intent and operational context. Formally, we define the class of auditable system calls as a subclass of the `cco:DesignativeICE`. A Designative Information Content Entity is a type of information entity that stands for or refers to one or more other entities. In this domain, the system call identifier (e.g., `execve`, `openat`) serves as the designative token that refers to the complex kernel routine it invokes.

The axiom governing this relationship is expressed as follows:

**Axiom 1:** `{X} SubClassOf cco:DesignativeICE, sdg:auditedBy some bfo:0000015`

This axiom asserts that any class `X` representing a system call within our ontology is fundamentally a designative entity. Furthermore, it establishes a necessary condition: for an entity to be a valid member of this class, it must be audited by at least one instance of `bfo:0000015`. In the Basic Formal Ontology (BFO), `bfo:0000015` denotes a *Process*. Therefore, the axiom dictates that a system call is only formally recognized as an auditable entity if there exists an active audit process (such as an eBPF tracepoint program or a daemon) observing it.

### 4.2.2 The Audit Relationship

The property `sdg:auditedBy` creates a dependency between the designative entity (the syscall) and the process performing the observation. This is not a passive data relationship but an active governance constraint. If the audit process terminates or fails to attach to the kernel hook, the system call, while functionally operational, ceases to satisfy the ontological constraint of being "audited" in the compliance sense. This distinction is critical for forensic analysis; it allows auditors to distinguish between a system call that occurred in an unmonitored state versus one that was captured by a sanctioned observation process.

The implementation of this axiom within the kernel requires that the eBPF verifier ensures the existence of a map or perf-buffer write operation corresponding to the syscall execution. This write operation serves as the physical instantiation of the `sdg:auditedBy` relationship in the system's runtime memory.

## 4.3 Relational Projection of Audit Axioms

To translate these ontological commitments into a queryable structure suitable for automated compliance reporting, we project the axioms onto a relational schema. This projection allows for the storage and retrieval of audit definitions using standard database technologies, facilitating the generation of evidence artifacts required by regulatory bodies.

### 4.3.1 Schema Definition for System Call Auditing

The following table, `t_syscall_audited_by`, embodies the structural requirements of Axiom 1. It catalogs the specific system calls (Class `X`) that are defined as designative entities subject to auditing.

The primary key is `id`, a unique identifier for the record. The column `x` contains the class name of the system call entity. This schema enforces the "SubClassOf" relationship by restricting entries to those classes defined within the `cco:DesignativeICE` namespace. While the foreign key to the audit process (`bfo:0000015`) is implicit in the axiom's existential quantification ("some"), this table serves as the registry of *what* is audited, serving as the target for join operations with process logs.

**Table 4.1: System Call Audit Registry (t_syscall_audited_by)**

| id | x |
| :--- | :--- |
| sys_001 | SyscallOpenat2 |
| sys_002 | SyscallExecve |
| sys_003 | SyscallConnect |
| sys_004 | SyscallClone3 |
| sys_005 | SyscallMmap |
| sys_006 | SyscallIoctl |
| sys_007 | SyscallBind |

*Table 4.1 Notes:* The `x` column values correspond to the specific class definitions of the system calls. For instance, `SyscallExecve` represents the class of entities designating program execution requests. The presence of a row in this table indicates that the class has been formally designated as an Information Content Entity and is within the scope of the audit framework.

### 4.3.2 Audit Process Manifest

To satisfy the "at least two tables" requirement and to provide context for the `bfo:0000015` (Process) side of the axiom, we maintain a secondary registry. This table tracks the active audit processes that fulfill the `sdg:auditedBy` requirement. While not explicitly schemaed in the primary axiom projection, this table is necessary to validate the existential constraint of the axiom.

**Table 4.2: Active Audit Process Manifest (t_audit_process_manifest)**

| process_id | process_name | hook_type | status |
| :--- | :--- | :--- | :--- |
| proc_8821 | bpf_trace_syscall_enter | kprobe | Active |
| proc_8822 | bpf_audit_file_ops | tracepoint | Active |
| proc_8823 | sec_audit_network_flow | kprobe | Inactive |
| proc_8824 | bpf_monitor_mmap | raw_tracepoint | Active |
| proc_8825 | bpf_guard_clone | kprobe | Active |

*Table 4.2 Notes:* This table lists the instances of `bfo:0000015` (Process) responsible for the auditing action. The `status` column indicates whether the process is currently fulfilling the `auditedBy` obligation. A join between Table 4.1 and Table 4.2, mediated by runtime logs, constitutes the complete evidence that the axiom holds true at a specific point in time.

## 4.4 Verification and Compliance Protocols

### 4.4.1 Validation of Designative Properties

The verification of the `cco:DesignativeICE` subclass status requires a two-step inspection. First, the auditor must confirm that the entry in `t_syscall_audited_by` corresponds to a valid kernel symbol. Second, the auditor must verify that the symbol is being used in a designative capacity—i.e., it is being utilized to name a specific kernel operation rather than serving as opaque data.

In practice, this involves inspecting the eBPF bytecode loaded into the kernel. The bytecode must contain instructions that reference the system call identifier in a way that generates an information content entity (a log entry or a metric). If a system call is hooked but no data is extracted (no content entity is generated), it fails the "DesignativeICE" criteria and should be flagged as a compliance violation.

### 4.4.2 Runtime Audit Trail Consistency

The existential quantification in Axiom 1 (`auditedBy some bfo:0000015`) implies that there cannot be a "dangling" designative entity. Every `x` in Table 4.1 must have a corresponding, active process in Table 4.2 that is capable of observing it.

Consider the entry `SyscallConnect` in Table 4.1. If the corresponding audit process `proc_8823` (Table 4.2) enters an `Inactive` state, the ontological consistency of the system is breached. The `SyscallConnect` entity still exists as a designative ICE, but the axiom `auditedBy some bfo:0000015` is no longer satisfied. Automated compliance scanners should therefore perform a left-join operation between the active system call logs and the `t_audit_process_manifest` table. Any system call event generated without a corresponding active process entry constitutes a structural anomaly in the audit framework.

### 4.4.3 Evidence Generation for Regulatory Review

When generating the final audit report (e.g., for a SOC 2 or ISO 27001 review), the output must trace the lineage from the raw kernel event back to the axiom. The report should explicitly state:

> "The system call `SyscallExecve` (Class: `cco:DesignativeICE`) was observed at timestamp T. This observation satisfies the axiom `syscall_audited_by` via the process `bpf_trace_syscall_enter` (Instance: `bfo:0000015`)."

This level of explicit linkage between the observed data and the governing ontology provides the "evidence-anchored" quality required for high-assurance environments. It moves the audit from a checklist of "did we log it?" to a formal proof of "is the system state consistent with the security model?"
