# Chapter 4: Ontological Specification of Kernel Audit Entities

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework for defining and classifying system call entities within a kernel-level auditing infrastructure. The primary objective is to delineate the structural relationship between information content entities utilized in system calls and the processes responsible for their auditing. The discussion herein is grounded in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), providing a rigorous schema for mapping low-level kernel operations to high-level compliance requirements. Specifically, we examine the axiom that defines a system call class as a subclass of Designative Information Content Entities that are necessarily audited by a specific process. This formalization ensures that audit trails are not merely ad-hoc logs but are structurally integral to the definition of the monitored entities themselves.

## 4.2 The Designative Nature of System Calls

### 4.2.1 Designative Information Content Entities

In the context of kernel instrumentation and security monitoring, a system call must be understood not merely as a jump to a memory address, but as a *Designative Information Content Entity* (cco:DesignativeICE). Within the Common Core Ontologies, a Designative ICE is an entity that conveys meaning or signifies a specific state or action. When a user-space process invokes `open()` or `read()`, it is generating an information artifact that designates an intent to access a resource. This designation is the semantic payload that the auditing infrastructure must capture.

The axiom governing this relationship is expressed as follows:

**Axiom 1:** `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`

This axiom asserts that any class `X` representing a system call is a subclass of `cco:DesignativeICE`. Furthermore, it imposes a necessary existential constraint: for every instance of `X`, there must exist at least one instance of `bfo:0000015` (a Process) that audits it. This creates a hard dependency between the existence of the system call entity and the audit process. In a compliant system, a system call that is not designated to be audited by a process effectively fails to meet the ontological definition of the class `X` within this framework.

### 4.2.2 The Audit Process Constraint

The right-hand side of the axiom introduces the property `sdg:auditedBy` and the object `bfo:0000015`. The term `bfo:0000015` refers to a *Process* in the Basic Formal Ontology—a temporal span during which events occur. In the context of eBPF (extended Berkeley Packet Filter) and kernel tracing, this process is the audit daemon or the trace pipe reader that consumes the event data generated by the kernel.

The constraint `auditedBy some bfo:0000015` utilizes an existential quantifier ("some"). This means that it is insufficient for the audit process to be defined merely as a potentiality; it must be actualized. If a system call fires and no audit process is actively registered to receive or process that event, the system violates the axiom. This ontological rigidity is critical for high-assurance environments where "blind spots" in monitoring are equated with security failures.

## 4.3 Audit Process Instantiation and Verification

### 4.3.1 The Role of the Audit Process (bfo:0000015)

The `bfo:0000015` (Process) referenced in the axiom is the active agent in the auditing framework. While the system call represents the *information* being designated, the audit process represents the *temporal occurrence* of observation. In a technical implementation, this is often realized as a kernel thread or a userspace daemon polling a perf-event buffer or a BPF map.

The ontological linkage ensures that the audit process is not an afterthought. The designative entity (the syscall) and the process (the auditor) are coupled. This coupling prevents configuration drift where a logging daemon might be stopped or disabled without triggering an alert in the ontology management system. If the process terminates, the condition `auditedBy some bfo:0000015` becomes false for subsequent system calls, rendering the system non-compliant with its own formal definition.

The `exec_trace_monitor` handles the security-sensitive execution-related calls. The `audit_status` column provides the operational verification that the BFO process is currently occurring.

### 4.3.3 Verification Protocol

To ensure compliance with the axiom `Class: {X:Class} SubClassOf: cco:DesignativeICE, sdg:auditedBy some bfo:0000015`, the following verification protocol is mandated:

1.  **Ontological Check:** Verify that every entry in `t_syscall_audited_by` is formally defined in the ontology as a subclass of `cco:DesignativeICE`.
2.  **Existential Check:** For every row in `t_syscall_audited_by`, query the runtime environment for at least one corresponding entry in the Active Audit Process Manifest (Table 4.2).
3.  **Process Validation:** Confirm that the `process_id` listed in the manifest corresponds to a running kernel or userspace process with the correct capabilities to read the relevant audit pipes.

Failure to find a corresponding process for a given system call class constitutes a violation of the axiom. In such cases, the system is considered to be in a state of "Semantic De-auditation," where the designative entities exist in isolation from their required observational processes. This state must trigger an immediate alert and, depending on the security policy, a kernel-level enforcement action (such as terminating the offending process or halting the system).

## 4.4 Summary of Axiomatic Compliance

The integration of OWL axioms into kernel auditing frameworks provides a layer of semantic rigor often missing in standard security implementations. By defining system calls as `cco:DesignativeICE`, we acknowledge that they are carriers of intent. By enforcing the `sdg:auditedBy some bfo:0000015` restriction, we ensure that this intent is never expressed without an observer. The tables provided in this chapter serve as both the schema for this definition and the evidence of its implementation.
