# Modeling Directive Subclassing for PCI DSS and HIPAA Compliance

This chapter presents four tables that instantiate OWL axioms for DirectiveICE subclasses. Each table records a binary relation between compliance classes, enabling verification of requirement and safeguard chains through equijoins on class identifiers.

## 1. Axiom Instantiation and Table Structure

The axioms define four distinct relations. Each table uses an opaque surrogate identifier as primary key. Column `x` holds the subclass and column `y` holds the required class filler. Because the filler values are drawn from a shared vocabulary of control classes, rows from different tables can be joined when a `y` value in one table equals an `x` value in another.

### 1.1 PCI DSS Requirement Table

The table `t_pci_dss_requirement` embodies Axiom 1. Its primary key is `id`; no foreign-key columns are declared, yet `y` values serve as join keys to `x` columns in the HIPAA safeguard tables.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.2 HIPAA Physical Safeguard Table

The table `t_hipaa_safeguard_physical` embodies Axiom 2. Its primary key is `id`. Rows may be joined to the PCI DSS table when a physical-control class appears as a `y` filler.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 1.3 HIPAA Technical Safeguard Table

The table `t_hipaa_safeguard_technical` embodies Axiom 3. Its primary key is `id`. Technical-control classes serve as join points to both PCI DSS and administrative-safeguard rows.

### 1.4 HIPAA Administrative Safeguard Table

The table `t_hipaa_safeguard_admin` embodies Axiom 4. Its primary key is `id`. Administrative classes close chains that originate in PCI DSS requirements.


## 2. Cross-Table Query Example

Consider the multi-hop question: which administrative safeguard is reached by following the PCI DSS requirement whose filler is also a technical safeguard filler? The path traverses three tables:

1. Start in `t_pci_dss_requirement` where `y = 'KeyManagement'`.
2. Locate the same value as `x` in `t_hipaa_safeguard_technical`.
3. Follow that row’s `y` into `t_hipaa_safeguard_admin` where `x` matches.

The joined result row is:

req-01 → TransmissionEncryption → KeyManagement → tech-02 → KeyManagement → TransmissionEncryption → (no direct admin match)  
Alternative path using req-03 yields:  
req-03 → AuditLogRetention → LogIntegrityCheck → tech-03 → LogIntegrityCheck → adm-03 → IncidentResponse

Thus the administrative control “IncidentResponse” is reachable from the original PCI DSS requirement in two hops.
