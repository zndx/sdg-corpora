# Compliance Directive Modeling in Relational Data

This chapter defines a four-table relational schema that materializes four OWL axioms for directive information content entities. The schema supports joins on shared class references to answer multi-hop compliance queries for systems that process both payment card and protected health information.

## 1 Table t_pci_dss_requirement

The table embodies axiom 1 by recording each directive class together with its PCI DSS requirement identifier. Column id is the primary key; column y functions as a stable reference that can be matched against y values in the three HIPAA safeguard tables.

| id  | x                        | y     |
|-----|--------------------------|-------|
| p01 | DataAccessControl        | 7.1   |
| p02 | AuditLogging             | 10.2  |
| p03 | EncryptionAtRest         | 3.4   |
| p04 | TransmissionSecurity     | 4.1   |
| p05 | AccessReview             | 7.2   |

## 2 Table t_hipaa_safeguard_physical

The table embodies axiom 2 by associating directive classes with physical HIPAA safeguards. Column id is the primary key; column y supplies the regulatory citation used for equi-joins on class or citation values across tables.

| id  | x                        | y              |
|-----|--------------------------|----------------|
| hp1 | PhysicalSecurityPerimeter| 164.310(a)(1)  |
| hp2 | WorkstationControl       | 164.310(b)     |
| hp3 | DeviceMediaControl       | 164.310(c)     |
| hp4 | AccessControlFacility    | 164.310(a)(2)  |
| hp5 | DataAccessControl        | 164.310(d)     |

## 3 Table t_hipaa_safeguard_technical

The table embodies axiom 3 by linking directive classes to technical HIPAA safeguards. Column id is the primary key; column y holds the citation that participates in cross-table joins on either x or y.

| id  | x                     | y              |
|-----|-----------------------|----------------|
| ht1 | AccessControl         | 164.312(a)(1)  |
| ht2 | AuditLogging          | 164.312(b)     |
| ht3 | IntegrityControl      | 164.312(c)(1)  |
| ht4 | TransmissionSecurity  | 164.312(e)(1)  |
| ht5 | EncryptionAtRest      | 164.312(a)(2)  |

## 4 Table t_hipaa_safeguard_admin

The table embodies axiom 4 by recording directive classes and their administrative HIPAA safeguards. Column id is the primary key; column y provides the citation used for equi-join resolution with the other three tables.

| id  | x                        | y              |
|-----|--------------------------|----------------|
| ha1 | AccessReview             | 164.308(a)(1)  |
| ha2 | WorkforceTraining        | 164.308(a)(5)  |
| ha3 | IncidentResponse         | 164.308(a)(6)  |
| ha4 | DataAccessControl        | 164.308(a)(4)  |
| ha5 | AuditLogging             | 164.308(a)(3)  |

## 5 Cross-table Query Example

To retrieve every technical safeguard that shares a directive class with a PCI DSS requirement, execute the equi-join on column x between t_pci_dss_requirement and t_hipaa_safeguard_technical. For requirement identifier 7.1 the join yields:

- p01 joined with ht1 on DataAccessControl produces the row (p01, DataAccessControl, 7.1, ht1, AccessControl, 164.312(a)(1)).

Extending the same pattern to t_hipaa_safeguard_admin on the identical class value returns the additional row (p01, DataAccessControl, 7.1, ha4, DataAccessControl, 164.308(a)(4)), demonstrating a three-table traversal from a PCI requirement through two distinct HIPAA safeguard families.
