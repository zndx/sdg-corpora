# Regulatory Directive Modeling for Healthcare Payment Systems

This chapter defines four ontological templates that classify instances of cco:DirectiveICE according to their regulatory specializations. The templates are projected directly into four relational tables whose columns correspond to the slot types X and Y. Primary keys ensure unique identification of each directive instance; foreign-key relationships arise when values in the y column of one table match identifiers or x values in another table, enabling multi-hop retrieval across PCI DSS and HIPAA safeguard categories.

## 1. PCI DSS Requirement Classification

Table t_pci_dss_requirement realizes axiom 1. Column id is the primary key. Column x holds the subclass of DirectiveICE; column y holds the referenced PCI DSS requirement class. A reader can join this table to any HIPAA safeguard table on matching y values to retrieve all directives that impose a common control class.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id     | x                          | y            |
|--------|----------------------------|--------------|
| dir001 | NetworkSegmentationPolicy  | PCI-Req-1.1  |
| dir002 | CardholderDataEncryption   | PCI-Req-3.4  |
| dir003 | AccessControlMatrix        | PCI-Req-7.1  |
| dir004 | AuditTrailRetention        | PCI-Req-10.7 |
| dir005 | WirelessAccessRestriction  | PCI-Req-2.1  |

## 1.1 HIPAA Physical Safeguard Classification

Table t_hipaa_safeguard_physical realizes axiom 2. Column id is the primary key. Column x holds the subclass of DirectiveICE; column y holds the referenced physical safeguard class. Values in y may equal x values in t_pci_dss_requirement, permitting a two-table join that links physical facility controls to PCI network requirements.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id     | x                          | y                     |
|--------|----------------------------|-----------------------|
| phy001 | FacilityPerimeterPolicy    | PhysicalAccessControl |
| phy002 | WorkstationLockPolicy      | DeviceAndMediaControl |
| phy003 | VisitorLogProcedure        | PhysicalAccessControl |
| phy004 | ServerRoomBadgeAccess      | PhysicalAccessControl |
| phy005 | MediaDisposalStation       | DeviceAndMediaControl |

## 1.2 HIPAA Technical Safeguard Classification

Table t_hipaa_safeguard_technical realizes axiom 3. Column id is the primary key. Column x holds the subclass of DirectiveICE; column y holds the referenced technical safeguard class. Column y may reference the same control class appearing in t_pci_dss_requirement.y, supporting a join that retrieves technical encryption directives together with their PCI counterparts.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id     | x                           | y                      |
|--------|-----------------------------|------------------------|
| tec001 | UniqueUserIdentification    | AccessControl          |
| tec002 | EncryptionAtRest            | TransmissionSecurity   |
| tec003 | AutomaticLogoffTimer        | AccessControl          |
| tec004 | IntegrityControlHash        | TransmissionSecurity   |
| tec005 | AuditLogIntegrityCheck      | AuditControls          |

## 1.3 HIPAA Administrative Safeguard Classification

Table t_hipaa_safeguard_admin realizes axiom 4. Column id is the primary key. Column x holds the subclass of DirectiveICE; column y holds the referenced administrative safeguard class. Because several y values coincide with y values in the PCI DSS table, a three-table join across t_pci_dss_requirement, t_hipaa_safeguard_technical, and t_hipaa_safeguard_admin yields all directives that share an administrative or technical control class.

```sql
CREATE TABLE t_hipaa_safeguard_admin (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id     | x                              | y                           |
|--------|--------------------------------|-----------------------------|
| adm001 | WorkforceClearanceProcedure    | AccessAuthorization         |
| adm002 | IncidentResponseTeam           | SecurityIncidentProcedures  |
| adm003 | BusinessAssociateAgreement     | BusinessAssociateContracts  |
| adm004 | SanctionPolicy                 | AccessAuthorization         |
| adm005 | ContingencyPlanActivation      | ContingencyOperations       |

## 2. Cross-Table Retrieval Example

Consider the multi-hop question: “Which administrative safeguard directives share the AccessAuthorization control class with a PCI DSS requirement?”  

Begin with t_pci_dss_requirement where y = 'PCI-Req-7.1'. The row (dir003, AccessControlMatrix, PCI-Req-7.1) is obtained. Next locate rows in t_hipaa_safeguard_admin whose y equals a control class that also appears in t_pci_dss_requirement.y or t_hipaa_safeguard_technical.y. The rows (adm001, WorkforceClearanceProcedure, AccessAuthorization) and (adm004, SanctionPolicy, AccessAuthorization) satisfy the condition. The joined result set therefore contains three directive instances linked by the shared control class AccessAuthorization.
