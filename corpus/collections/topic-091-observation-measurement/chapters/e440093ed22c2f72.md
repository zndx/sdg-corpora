# Chapter 4: Regulatory Mapping of Information Control Elements

## 4.1 Scope and Applicability

This chapter delineates the formal ontological mapping between Information Control Element (ICE) directives and specific regulatory obligations defined within the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA). The content herein establishes the structural relationships between abstract control classes and their corresponding compliance requirements or safeguards, providing a deterministic framework for audit verification and governance reporting. All mappings are derived from the core axiom set defined in the governing compliance ontology, ensuring that every directive instance is traceable to a specific regulatory article. The following sections detail these relationships through textual definition, evidentiary context, and relational data representations suitable for integration into enterprise governance architectures.

## 4.2 PCI DSS Requirement Directives

### 4.2.1 Ontological Definition and Context

The class of PCI DSS Requirement Directives represents a specific subset of the broader `cco:DirectiveICE` universe. These directives are formalized interpretations of the mandatory operational steps required to secure cardholder data environments. Under the governing axiom, a PCI DSS Requirement Directive is defined as any entity `X` that subclasses `cco:DirectiveICE` and possesses the property `sdg:pciDssRequirement` linking it to a specific requirement class `Y`.

In practice, this mapping allows an organization to translate high-level regulatory language (e.g., "Install and maintain a firewall configuration") into discrete, implementable directive objects within a compliance management system. The directive serves as the actionable control, while the requirement class `Y` anchors it to the specific paragraph or clause within the PCI DSS standard (v4.0). This bifurcation is critical for automated compliance scanning, where the system must verify that the directive `X` is implemented effectively to satisfy the obligation `Y`.

## 4.3 HIPAA Physical Safeguard Directives

### 4.3.1 Ontological Definition and Context

The HIPAA Security Rule necessitates the implementation of specific physical safeguards to protect Electronic Protected Health Information (EPHI) from unauthorized intrusion and environmental hazards. The ontology defines a HIPAA Physical Safeguard Directive as a class `X` that is a subclass of `cco:DirectiveICE` and is associated via the `sdg:hipaaSafeguard` object property with a Physical Safeguard class `Y`.

This distinction ensures that physical controls—such as facility access restrictions and workstation usage policies—are formally recognized as compliance artifacts. Unlike technical controls, physical safeguards often involve procedural enforcement and physical infrastructure modifications. The axiom `hipaa_safeguard_physical` captures this domain, ensuring that directives regarding locks, security badges, and facility access logs are rigorously mapped to the "Facility Access Controls" and "Workstation Security" standards outlined in 45 CFR § 164.310(a).

## 4.4 HIPAA Technical Safeguard Directives

### 4.4.1 Ontological Definition and Context

Technical safeguards under HIPAA involve the automated mechanisms and technology used to protect EPHI and control access to it. The `hipaa_safeguard_technical` axiom defines a class `X` (DirectiveICE) that implements a technical control `Y` via the `sdg:hipaaSafeguard` property. This covers the broad spectrum of information technology controls, including access control, audit controls, integrity controls, and transmission security.

In the context of the ontology, these directives represent the logical and technical configurations applied to hardware and software. For example, a directive governing unique user identification is not merely a policy statement but a technical implementation of authentication protocols within the information system. The axiom ensures that every technical mechanism deployed is traceable to a specific HIPAA implementation specification, such as "Access Control" or "Audit Controls" found in 45 CFR § 164.312.

## 4.5 HIPAA Administrative Safeguard Directives

### 4.5.1 Ontological Definition and Context

Administrative safeguards are the administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures. The `hipaa_safeguard_admin` axiom defines a class `X` (DirectiveICE) that functions as an administrative instrument linked to a safeguard class `Y` via the `sdg:hipaaSafeguard` property. This encompasses security management processes, assigned security responsibility, workforce training, and contingency planning.

These directives are often procedural or governance-oriented. They define the "who, what, and when" of the security program. For instance, a directive regarding risk analysis is a formalized process requiring periodic assessment of potential risks to EPHI. The ontology treats this administrative process as a distinct class of DirectiveICE, ensuring that governance activities are auditable with the same rigor as technical or physical controls.
