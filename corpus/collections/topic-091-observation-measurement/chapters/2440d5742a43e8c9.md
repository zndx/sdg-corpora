# Chapter 7: Regulatory Mapping of Information Security Compliance Entities

## 7.1 Scope and Preamble

This chapter delineates the formal ontological relationships governing Information Security Compliance Entities (ICE) within the context of prevailing regulatory frameworks. Specifically, it addresses the mapping of directive classes to requirement sets defined by the Payment Card Industry Data Security Standard (PCI DSS) and the safeguard categories established under the Health Insurance Portability and Accountability Act (HIPAA). The content herein provides a structured approach to classifying compliance controls, ensuring that directive implementations are auditable, semantically precise, and aligned with the logical constraints imposed by the underlying ontology. Readers should refer to the accompanying data tables to verify the instantiation of these axioms within a compliant governance framework.

## 7.2 PCI DSS Requirement Mapping

The implementation of PCI DSS controls within an enterprise environment requires a rigorous mapping between internal policy directives and the specific requirements mandated by the standard. The ontological structure for this relationship is defined by the axiom `pci_dss_requirement`. This axiom asserts that a given class (X), representing a specific internal directive or control mechanism, is a subclass of `cco:DirectiveICE` and fulfills a specific PCI DSS requirement (Y).

In practice, this means that for a system to be compliant, the directive class must not only exist as a policy object but must be formally linked to the requirement class it enforces. This linkage creates a traceable path from high-level governance down to technical implementation. For example, a directive regarding network perimeter security must be explicitly tied to the PCI DSS requirement concerning firewall configuration and review.

### 7.2.1 Relational Representation

The following table, `t_pci_dss_requirement`, embodies the axiom described above. The primary key is the `id` column, which serves as the unique identifier for the mapping instance. The column `x` represents the DirectiveICE class (the internal control), while `y` represents the PCI DSS requirement class (the external mandate). The `NOT NULL` constraint on `y` ensures that every directive mapped in this table is associated with a valid regulatory requirement, preventing orphaned controls within the compliance inventory.

| ID | Directive Class (X) | PCI DSS Requirement Class (Y) |
| :--- | :--- | :--- |
| pci-req-001 | NetworkFirewallDirective | ReviewFirewallConfiguration |
| pci-req-002 | VendorAccessPolicy | VendorAccessMonitoring |
| pci-req-003 | CardholderDataStorage | StoredDataEncryption |
| pci-req-004 | SystemLoggingProtocol | AuditTrailRetention |
| pci-req-005 | WirelessAccessControl | WirelessNetworkScanning |

### 7.2.2 Implementation Notes

When auditing against the mappings in Table 7.1, compliance officers must verify that the instance of `NetworkFirewallDirective` (pci-req-001) contains operational parameters that satisfy `ReviewFirewallConfiguration`. This involves checking timestamps on configuration changes against the baseline established in the standard. Similarly, the mapping of `CardholderDataStorage` to `StoredDataEncryption` (pci-req-003) necessitates a technical verification that the storage directives invoke approved cryptographic algorithms.

## 7.3 HIPAA Physical Safeguards

Under HIPAA, Physical Safeguards are operational measures implemented to protect electronic protected health information (ePHI) and the buildings and equipment that house such information. The ontological axiom `hipaa_safeguard_physical` categorizes these measures. It defines a class (X) as a subclass of `cco:DirectiveICE` that specifically enforces a physical safeguard (Y).

These directives often relate to facility access, workstation usage, and device security. The distinction here is the physical nature of the control; unlike technical safeguards which are logical or software-based, physical safeguards involve tangible environmental controls. The formalization of this relationship ensures that physical security policies are not treated as general guidelines but as specific, enforceable directives with distinct regulatory targets.

### 7.3.1 Relational Representation

The table `t_hipaa_safeguard_physical` provides the relational schema for this axiom. The primary key `id` uniquely identifies the physical safeguard mapping. Column `x` denotes the specific directive class responsible for the physical control, and column `y` denotes the type of physical safeguard being enforced. The structure ensures that every physical directive is anchored to a specific HIPAA safeguard definition, facilitating gap analysis during facility inspections.

| ID | Directive Class (X) | Physical Safeguard Class (Y) |
| :--- | :--- | :--- |
| hip-phy-001 | FacilityAccessControl | ContingencyOperations |
| hip-phy-002 | WorkstationSecurityProtocol | PhysicalScreenPlacement |
| hip-phy-003 | MediaDisposalProcedure | DeviceMediaDisposal |
| hip-phy-004 | BuildingEntryLog | AccessValidation |
| hip-phy-005 | HardwareInventoryControl | AssetTracking |

### 7.3.2 Compliance Verification

Verification of the mappings in Table 7.2 requires physical inspection and log review. For instance, the mapping `hip-phy-001` links `FacilityAccessControl` to `ContingencyOperations`. An auditor must confirm that the facility access control systems have documented procedures for emergency access, aligning with the contingency operations safeguard. Furthermore, `hip-phy-003` requires that the `MediaDisposalProcedure` directive includes specific steps for the physical destruction or sanitization of hardware media, ensuring that `DeviceMediaDisposal` is effectively managed.

## 7.4 HIPAA Technical Safeguards

Technical Safeguards under HIPAA involve the technology and the policy and procedures for its use that protect electronic health information and control access to it. The axiom `hipaa_safeguard_technical` formalizes the relationship where a directive class (X) is a `cco:DirectiveICE` that implements a technical safeguard (Y).

This category encompasses access control, audit controls, integrity controls, and transmission security. The ontological distinction here is critical for governance: it separates the policy (the directive) from the technical mechanism (the safeguard). By mapping these explicitly, organizations can automate compliance checks by querying the directive class to ensure the appropriate technical controls are active and configured correctly.

### 7.4.1 Relational Representation

Table `t_hipaa_safeguard_technical` illustrates the implementation of technical safeguards. The `id` column serves as the primary key. Column `x` identifies the directive class (e.g., an access control policy), while column `y` identifies the specific technical safeguard class (e.g., unique user identification). This schema allows security architects to trace a technical configuration back to its governing directive and the specific HIPAA requirement it satisfies.

| ID | Directive Class (X) | Technical Safeguard Class (Y) |
| :--- | :--- | :--- |
| hip-tec-001 | AccessControlMechanism | UniqueUserIdentification |
| hip-tec-002 | EmergencyAccessProcedure | EmergencyAccessProcess |
| hip-tec-003 | AuditControlSystem | ActivityLogReview |
| hip-tec-004 | IntegrityControlProtocol | MechanismToCorruptData |
| hip-tec-005 | TransmissionSecurityPolicy | EncryptionDuringTransmission |

### 7.4.2 Audit and Control Validation

The data presented in Table 7.3 must be cross-referenced with system configurations during an audit. For example, `hip-tec-001` asserts that the `AccessControlMechanism` directive enforces `UniqueUserIdentification`. Auditors must verify that the system does not allow shared accounts and that every user action is attributable to a specific unique identity. Similarly, `hip-tec-005` mandates that the `TransmissionSecurityPolicy` directive results in the active implementation of `EncryptionDuringTransmission`, requiring checks on TLS/SSL configurations across network boundaries.

## 7.5 HIPAA Administrative Safeguards

Administrative Safeguards are administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures to protect electronic health information. These are often the most complex set of safeguards as they involve the workforce and management structure. The axiom `hipaa_safeguard_admin` defines a class (X) as a `cco:DirectiveICE` that enforces an administrative safeguard (Y).

These directives govern workforce security, training, and contingency planning. The formalization of administrative safeguards is essential for establishing a "culture of compliance." By defining these as ontological classes, organizations can integrate HR policies, training modules, and risk management protocols into the same compliance framework used for technical and physical controls.

### 7.5.1 Relational Representation

The table `t_hipaa_safeguard_admin` captures the administrative safeguard mappings. The primary key is `id`. Column `x` represents the administrative directive class, such as a training or security management protocol. Column `y` represents the administrative safeguard class, such as security awareness or authorization supervision. This structure ensures that administrative policies are not merely documented but are formally classified and mapped to regulatory standards.

| ID | Directive Class (X) | Administrative Safeguard Class (Y) |
| :--- | :--- | :--- |
| hip-adm-001 | SecurityManagementProcess | RiskAnalysis |
| hip-adm-002 | WorkforceSecurityPolicy | AuthorizationSupervision |
| hip-adm-003 | InformationAccessPolicy | AccessAuthorization |
| hip-adm-004 | TrainingAndAwarenessProgram | SecurityAwarenessTraining |
| hip-adm-005 | ContingencyPlanProtocol | DataBackupPlan |

### 7.5.2 Policy and Procedure Review

Reviewing the mappings in Table 7.4 involves examining documentation and workforce records. For `hip-adm-001`, the `SecurityManagementProcess` directive must produce evidence of a `RiskAnalysis`, typically in the form of a risk assessment report. The mapping `hip-adm-004` requires the `TrainingAndAwarenessProgram` directive to demonstrate the delivery of `SecurityAwarenessTraining` to all members of the workforce. Auditors should look for attendance logs and training materials that correlate with the specific instances defined in this table.
