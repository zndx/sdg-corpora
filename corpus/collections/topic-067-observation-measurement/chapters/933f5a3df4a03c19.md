# Chapter 4: Ontological Classification of Kernel System Calls for eBPF Auditing Frameworks

## 4.1 Preamble and Scope

This chapter establishes the formal ontological definitions required for the classification of kernel system calls within the context of extended Berkeley Packet Filter (eBPF) auditing and compliance frameworks. The definitions provided herein align with the "04_ebpf_kernel" family of axioms, serving as the foundational schema for automated governance tools. The objective is to map the dynamic behavior of kernel interfaces to static designative information content entities (DesignativeICE), ensuring that security policies, traceability requirements, and subsystem boundaries are rigorously defined. This documentation is intended for systems architects, compliance officers, and kernel developers responsible for implementing observability structures in high-assurance environments.

## 4.2 Basic Designative Entities

### 4.2.1 Definition and Context

At the fundamental layer of the kernel taxonomy, a system call must be formally recognized as a Designative Information Content Entity (DesignativeICE). This classification asserts that the system call is not merely a functional operation but a distinct, named entity within the information architecture of the operating system. The axiom `syscall_basic` posits that any class `X` representing a system call is a subclass of `cco:DesignativeICE`. This distinction is critical for audit logs; it treats the invocation of a system call as the instantiation of a defined concept rather than an opaque event.

In compliance auditing, this allows for the creation of inventories where every kernel interaction is referenced by a stable identifier. For example, the act of reading from a file descriptor is not just an event; it is an instance of the `FileReadOperation` class. By anchoring these entities to the Basic Formal Ontology (BFO) via `cco:DesignativeICE`, we ensure semantic interoperability between distinct monitoring tools and regulatory reporting mechanisms.

## 4.3 Subsystem Equivalence and Classification

### 4.3.1 Logical Containment

The kernel is modularized into distinct subsystems (e.g., networking, file systems, inter-process communication). The axiom `syscall_equiv_in_subsystem` provides a mechanism for defining system call classes based on their exclusive membership within a specific subsystem. Formally, a class `X` is equivalent to the intersection of `cco:DesignativeICE` and the restriction `sdg:inSyscallSubsystem some {Y:Class}`.

This logical structure implies that a system call class `X` is defined *by* its existence in subsystem `Y`. For governance purposes, this allows security architects to apply subsystem-wide policies. If a subsystem is deemed non-compliant or unsafe for specific workloads, all system call classes equivalent to that subsystem can be dynamically blocked or flagged for audit review. This equivalence relation is stronger than a simple property assignment; it is a definitional characteristic of the class `X`.

## 4.4 Return Type Constraints

### 4.4.1 Cardinality and Data Integrity

To maintain data integrity and predictability in kernel-user space communication, system calls must adhere to strict return type definitions. The axiom `syscall_max_one_return` stipulates that a class `X` (a subclass of `cco:DesignativeICE`) is characterized by having a maximum of one return type `Y`.

This constraint, `sdg:hasReturnType max 1 {Y:Class}`, prevents ambiguity in the audit trail. A system call that returns multiple disjoint types would complicate automated parsing and increase the risk of type confusion errors in security monitors. By enforcing a maximum cardinality of 1, the ontology ensures that every invocation of class `X` yields a single, predictable data structure or primitive type `Y`. This is particularly relevant for eBPF programs that inspect return values to determine the success or failure of critical operations, such as privilege elevation attempts or file access checks.

## 4.5 Traceability and Observability

### 4.5.1 Audit Trails and Provenance

In modern security architectures, observability is paramount. The axiom `syscall_traceable` formalizes the relationship between a system call class `X` and the mechanism `Y` capable of tracing it. The axiom states that `X` is a subclass of `cco:DesignativeICE` and is `sdg:traceableBy` some `Y`.

This relationship creates a verifiable chain of evidence. If a specific system call class is defined as traceable by an `eBPFTracepoint` or `AuditDaemon`, the absence of logs for that class constitutes a compliance violation or a system failure. This axiom supports the "defense in depth" strategy by ensuring that critical classes—such as those related to authentication or system configuration—have explicit, mandatory tracing hooks. It transforms the tracing mechanism from an optional add-on to a definitional property of the system call itself.

## 4.6 Security Tier Stratification

### 4.6.1 Privilege Domains

The kernel operates under strict privilege separation. The axiom `syscall_at_security_tier` classifies system calls based on the security tier or privilege ring `Y` in which they operate. The axiom asserts that class `X` (a subclass of `cco:DesignativeICE`) is `sdg:atSecurityTier` some `Y`.

This classification is vital for enforcing the Principle of Least Privilege (PoLP). By identifying which system call classes reside at `Ring0` (kernel mode) versus `Ring3` (user mode), security frameworks can restrict the loading of arbitrary eBPF programs or enforce strict validation on transitions between tiers. Furthermore, this ontology aids in automated threat modeling; any system call class operating at a high security tier that is unexpectedly invoked from a low-privilege context triggers an immediate alert.
