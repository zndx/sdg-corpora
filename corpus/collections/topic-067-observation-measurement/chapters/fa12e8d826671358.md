# Chapter 4: Formal Ontology of Kernel System Calls

This chapter establishes the formal ontological framework governing the classification, behavior, and security attributes of kernel system calls within the eBPF observability architecture. The definitions provided herein are axiomatic, derived from the Manchester syntax of the core ontology, and serve as the basis for automated compliance auditing and runtime verification. Each section details a specific structural constraint or property relation, mapping abstract classes to concrete implementation instances required for system hardening.

## 1. Basic Designative Entities

The fundamental unit of the kernel interface is the system call, formally defined as a Designative Information Content Entity (ICE). This classification asserts that a system call is not merely a function pointer but a distinct, designative entity that conveys specific intent from user space to kernel space. Under Axiom 5 (`syscall_basic`), any entity `X` classified as a system call is, by definition, a subclass of `cco:DesignativeICE`. This serves as the root node for all subsequent property definitions, ensuring that every interaction point inherits the baseline requirements of an information-bearing entity.

In practice, this means that standard file I/O and process manipulation primitives are cataloged not as loose functions, but as registered entities within the global namespace. ## 2. Subsystem Equivalence and Contextual Scope

While the basic axiom establishes existence, Axiom 1 (`syscall_equiv_in_subsystem`) provides the necessary contextual scope by binding a system call to a specific subsystem. The axiom states that a class `X` is equivalent to a `DesignativeICE` only if it exists within the scope of a specific subsystem `Y` (defined by the object property `sdg:inSyscallSubsystem`). This equivalence relation is critical for partitioning the kernel surface, ensuring that calls are not evaluated in isolation but rather as integral components of their respective domains (e.g., VFS, Networking, IPC).

This logical constraint prevents ambiguity in call handling. For instance, a socket operation is distinct from a file operation precisely because of its subsystem classification. ## 3. Return Type Cardinality Constraints

To maintain strict type safety and predictable stack behavior, the ontology imposes cardinality constraints on return values. Axiom 2 (`syscall_max_one_return`) dictates that any system call `X` (being a `DesignativeICE`) must have a return type `Y` with a maximum cardinality of 1. This reflects the hardware and compiler reality that a standard system call invocation returns a single scalar value (typically an integer representing a success code, file descriptor, or error sentinel).

The verbalization of this axiom clarifies that while a call may modify multiple memory structures pointed to by arguments, the direct return channel is singular. ## 4. Traceability and Observability Provenance

In the context of security auditing and runtime monitoring, traceability is a mandatory property. Axiom 3 (`syscall_traceable`) stipulates that a system call `X` must be traceable by some mechanism `Y` (via the property `sdg:traceableBy`). This axiom operationalizes the requirement that kernel functions must expose hook points compatible with tracing frameworks such as eBPF, ftrace, or the audit subsystem.

The property `sdg:traceableBy` links the designative entity to the specific instrumentation class capable of observing its execution. This mapping is crucial for automated governance tools that verify whether a specific syscall can be monitored within a given security context. ## 5. Security Tier Classification

Finally, the ontology enforces a stratified security model through Axiom 4 (`syscall_at_security_tier`). This axiom classifies system calls based on their privilege requirements and potential impact, assigning them to a specific security tier `Y` (via `sdg:atSecurityTier`). This classification allows governance frameworks to apply differential policies; for example, calls at `tier_critical` may require explicit authorization in seccomp profiles, while `tier_standard` calls may be permissive by default.

The designation of a security tier is a static property of the call definition within the ontology, derived from the capabilities it interfaces with. For instance, calls that modify process memory or interact with hardware are typically placed in higher tiers.
