# Chapter 4: System Call Classification and Security Tiering in eBPF Monitoring Architectures

This chapter establishes the formal ontological framework for classifying kernel-level system calls within extended Berkeley Packet Filter (eBPF) monitoring environments. It delineates the axiomatic structure governing Designative Information Content Entities (ICEs), specifically focusing on their subsystem equivalence, return type constraints, traceability, and security tier assignments. The definitions and relational schemas provided herein are intended to serve as the authoritative reference for security architects auditing kernel syscall instrumentation, ensuring that observability pipelines adhere to strict governance and compliance standards.

## 4.1 Designative Information Content Entities (Basic)

The fundamental unit of analysis within the kernel syscall ontology is the Designative Information Content Entity (ICE). In the context of operating system theory, a Designative ICE represents a distinct, semantically stable command or instruction that signifies an intent to the kernel, distinct from the physical execution of that instruction. Under Axiom 5 (`syscall_basic`), any entity classified as a system call is, by definition, a subclass of `cco:DesignativeICE`. This classification is not merely taxonomic; it is a prerequisite for the entity to be recognized by audit logging frameworks and tracing utilities.

For a syscall to be valid within this governance framework, it must first be registered as a Designative ICE. This ensures that the syscall possesses the necessary informational properties to be captured, indexed, and retrieved by compliance monitoring tools. The basic classification axiom asserts that the set of all system calls is a subset of all Designative ICEs. This relationship allows security engineers to apply general information content handling policies to specific kernel interactions.

## 4.2 Subsystem Equivalence and Localization

While the basic classification establishes the nature of the entity, it does not define its operational context. Axiom 1 (`syscall_equiv_in_subsystem`) introduces the concept of subsystem localization. This axiom posits that a system call class (X) is equivalent to a Designative ICE *if and only if* it operates within a specific syscall subsystem (Y). This equivalence is critical for modular auditing, as it allows governance frameworks to isolate failures or anomalies to specific kernel domains (e.g., networking, file systems, inter-process communication).

The logical implication of this axiom is that a syscall cannot exist in a vacuum; its validity as a Designative ICE is contingent upon its membership in a defined subsystem class. This constraint prevents the categorization of "orphan" or undefined kernel calls that lack a subsystem anchor. For compliance officers, this means that any syscall detected in a trace log must be mappable to a subsystem category to be considered valid for audit purposes.

## 4.3 Return Type Cardinality Constraints

In the design of secure and verifiable syscall interfaces, the predictability of output is paramount. Axiom 2 (`syscall_max_one_return`) imposes a structural constraint on system call classes: a valid syscall (X) must have a maximum of one return type (Y). This constraint ensures that the interface contract between user space and the kernel is deterministic. While a syscall may return a complex data structure, it does so via a single return channel or type class, preventing the ambiguity associated with multiple, disparate return vectors.

From a security auditing perspective, this axiom facilitates the automated validation of syscall signatures. If a syscall attempts to return values of two distinct, unrelated type classes (e.g., a file descriptor and a memory address simultaneously as primary returns), it violates this ontological constraint and suggests a potential interface corruption or a fundamental design flaw that could obscure data exfiltration paths.

## 4.4 Audit Traceability and Provenance

A critical requirement for modern governance frameworks is the ability to attribute system actions to specific monitoring agents. Axiom 3 (`syscall_traceable`) formalizes this by stating that a syscall class (X) must be traceable by some tracing agent class (Y). In the context of eBPF, this implies that for a syscall to be compliant, it must be within the scope of an observability program—specifically, an eBPF probe or a compatible tracing utility.

This axiom moves beyond the static definition of the syscall to its dynamic observability. It asserts that a syscall which is theoretically defined but practically invisible to standard tracing agents (due to kernel configuration or lack of instrumentation hooks) fails to meet the criteria for a fully governed Designative ICE. The "traceableBy" relationship ensures that there is a designated, verifiable path for the syscall's execution metadata to flow from the kernel ring to user-space auditing daemons.

## 4.5 Security Tier Assignment

Finally, the ontology addresses the relative privilege and risk associated with different system calls. Axiom 4 (`syscall_at_security_tier`) assigns each syscall class (X) to a specific security tier (Y). This stratification allows governance frameworks to apply differential policies based on the sensitivity of the operation. For instance, syscalls that modify kernel state or interact with hardware are placed at a higher security tier than those that merely read process information.

The assignment of a security tier is a fundamental component of the kernel's defense-in-depth strategy. By categorizing syscalls into tiers (e.g., `SuperUserTier`, `UnprivilegedTier`, `RestrictedTier`), the system can enforce granular access controls and dynamic filtering rules. This axiom ensures that every Designative ICE carries an explicit security classification, facilitating automated policy enforcement and risk scoring during audit log analysis.
