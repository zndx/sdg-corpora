# Audit Process Ontologies in Relational Form

This chapter defines three process classes drawn from an OWL governance ontology and shows how each projects to a fixed relational table. The tables use shared identifier values in the x and y columns to encode subclass and existential restrictions, permitting direct cross-table joins that recover multi-hop provenance chains.

## 1 Ontology-to-Relation Mapping

Each axiom asserts that a process individual belongs to a bfo:Process subclass and participates in a specific relation to another class individual. The corresponding table stores the process identifier in column x and the related individual in column y; the table primary key is an independent surrogate that permits duplicate (x, y) pairs when required by the domain.

### 1.1 Table t_audit_with_findings

The table embodies axiom 1: every row states that the process referenced by x has findings y. Column id is the primary key; columns x and y function as foreign keys into a notional registry of process and finding identifiers, respectively. A reader can join this table to t_verification_produces_evidence on y = x to retrieve the verification step that generated each finding.

| id | x | y |
| id_001 | annual_financial_audit_2023 | finding_control_gap_07 |
| id_002 | annual_financial_audit_2023 | finding_access_violation_12 |
| id_003 | it_security_review_q2 | finding_patch_missing_03 |
| id_004 | it_security_review_q2 | finding_log_retention_05 |
| id_005 | vendor_compliance_audit | finding_contract_clause_09 |

### 1.2 Table t_attestation_with_supporting_evidence

The table embodies axiom 2: every row states that the process referenced by x carries supporting evidence y. Column id is the primary key; x and y again serve as foreign keys. Joining on y to the y column of t_audit_with_findings yields the finding that an attestation directly supports.

| id | x | y |
| id_101 | management_assertion_2023 | evidence_transaction_log_42 |
| id_102 | management_assertion_2023 | evidence_access_review_17 |
| id_103 | board_risk_attestation | evidence_patch_report_08 |
| id_104 | board_risk_attestation | evidence_contract_pdf_11 |
| id_105 | external_auditor_signoff | evidence_log_archive_22 |

### 1.3 Table t_verification_produces_evidence

The table embodies axiom 3: every row states that the process referenced by x produces evidence y. Column id is the primary key; x and y are foreign keys. Joining x to the x column of t_attestation_with_supporting_evidence recovers the attestation that consumed each produced evidence item.

| id | x | y |
| id_201 | automated_control_test | evidence_transaction_log_42 |
| id_202 | automated_control_test | evidence_access_review_17 |
| id_203 | manual_patch_scan | evidence_patch_report_08 |
| id_204 | legal_review | evidence_contract_pdf_11 |
| id_205 | system_log_audit | evidence_log_archive_22 |

## 2 Cross-Join Example

Question: which verification produced the evidence supporting the attestation that references finding_control_gap_07?

Start at t_audit_with_findings where y = finding_control_gap_07; read x = annual_financial_audit_2023.  
Locate the same value in t_attestation_with_supporting_evidence.x; read y = evidence_transaction_log_42.  
Locate the same value in t_verification_produces_evidence.y; read x = automated_control_test.

The joined path is therefore:
annual_financial_audit_2023 → finding_control_gap_07  
annual_financial_audit_2023 → evidence_transaction_log_42 (via attestation)  
automated_control_test → evidence_transaction_log_42 (via verification)
