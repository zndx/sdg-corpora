# Directive Governance Processes: Audits, Attestations, and Verifications

This chapter defines three process classes drawn from the directive governance family and demonstrates their relational encoding. The classes are audit_with_findings, attestation_with_supporting_evidence, and verification_produces_evidence. Each class is projected to a table whose rows contain entity references that satisfy the corresponding OWL axiom. Cross-table joins on these references recover multi-hop chains such as “which verification produced the evidence cited by an attestation that addresses a finding of a given audit.”

## 1. Axiom Definitions and Verbalizations

The three axioms share the BFO root bfo:0000015 (process). Each adds a single existential restriction that links the process to a second class.

- audit_with_findings: any instance X of the class stands in the relation sdg:hasFindings to at least one instance Y.
- attestation_with_supporting_evidence: any instance X stands in the relation sdg:withSupportingEvidence to at least one instance Y.
- verification_produces_evidence: any instance X stands in the relation sdg:producesEvidence to at least one instance Y.

These restrictions are sufficient to generate the three tables that follow. Column x always holds the subject process; column y holds the related class required by the restriction. The primary key id is an opaque surrogate that permits stable reference across tables.

## 2. Relational Tables

### 2.1 t_audit_with_findings

The table embodies axiom 1. Column id is the primary key. Columns x and y are entity references; y is non-null by the existential restriction. A reader can join on y to locate any attestation or verification that addresses the same finding.

```sql
CREATE TABLE t_audit_with_findings (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

### 2.2 t_attestation_with_supporting_evidence

The table embodies axiom 2. Column id is the primary key. Column y references an evidence item that may itself have been produced by a verification (see 2.3). Joining y to the y column of t_verification_produces_evidence recovers the originating verification.

### 2.3 t_verification_produces_evidence

The table embodies axiom 3. Column id is the primary key. Column y contains the evidence item that can be referenced by an attestation. A three-table join (audit → attestation → verification) therefore traces a complete evidence chain from an initial finding to its verification source.

```sql
CREATE TABLE t_verification_produces_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 3. Cross-Join Example

Question: Which verification produced the evidence supporting the attestation that addresses the ClothingPolicyFinding of the SummerTermClubAllocationAudit?

Walk the foreign-key references:

1. Start in t_audit_with_findings where y = 'ClothingPolicyFinding' → row af-001 (x = 'SummerTermClubAllocationAudit').
2. Locate the attestation whose y matches an evidence item linked to that finding context; row ae-001 (y = 'ClubListEvidence').
3. Locate the verification whose y = 'ClubListEvidence' → row ve-001 (x = 'ClubListVerification').

Resulting joined row (conceptual projection):

- audit_id: af-001
- finding: ClothingPolicyFinding
- attestation_id: ae-001
- evidence: ClubListEvidence
- verification_id: ve-001
- verification_process: ClubListVerification

The same pattern applies to any other finding–evidence pair.
