# Chapter 4: Semantic Mapping of Artifacts in Enterprise Data Governance

## 4.1 Scope and Preamble

This chapter delineates the protocols for mapping artifact attributes within the enterprise data model, specifically focusing on the semantic relationships between physical or logical entities and their descriptive properties. The guidelines herein are mandatory for all data stewards and system architects responsible for maintaining the integrity of the `cco:Artifact` subclass hierarchy. The objective is to ensure that every artifact instance is rigorously defined by its provenance, valuation, location, and geospatial coordinates. This specification utilizes the Manchester syntax for ontology definition and projects these semantic structures into relational schemas that enforce data consistency at the database level. Adherence to these mappings is critical for compliance with internal audit standards and external regulatory reporting requirements.

## 4.2 Brand Association and Provenance Tracking

### 4.2.1 Conceptual Definition

The assignment of a brand to an artifact is a fundamental assertion of manufacturing origin and liability. In accordance with the axiom `schemaorg_product_brand`, any entity classified as an Artifact must possess a brand association. This relationship is not merely a label but a structural link that connects the artifact class (`{X:Class}`) to a brand class (`{Y:Class}`). This linkage enables the enterprise to trace product lines through the supply chain, facilitating recall management and warranty validation. The ontology asserts that `{X} is something that has brand {Y}`, establishing a dependency where the existence of the artifact class implies the existence of a brand property.

### 4.2.2 Relational Implementation

The projection of this axiom into the relational model utilizes the table `t_schemaorg_product_brand`. The primary key for this table is the `id` column, which serves as a unique identifier for the brand-class association rule. The column `x` represents the Artifact class, while the column `y` represents the Brand class. The constraint `y VARCHAR(255) NOT NULL` ensures that no artifact class may be entered into the registry without a valid brand designation. This structure supports high-volume data ingestion while maintaining referential integrity, allowing for automated auditing of product catalogs against approved vendor lists.

This mapping implies that any individual instance of an industrial pump introduced into the inventory system must inherit this brand property unless a specific exception is processed through the change management board. The density of this mapping allows for immediate filtering of assets by manufacturer, a requirement for the quarterly compliance reports generated by the Governance Office.

## 4.3 Price Valuation and Financial Reporting

### 4.3.1 Conceptual Definition

Financial transparency regarding asset valuation is governed by the `schemaorg_product_price` axiom. This axiom defines the relationship between an Artifact class (`{X:Class}`) and its associated Price class (`{Y:Class}`). The verbalization, `{X} is something that has price {Y}`, indicates that price is an intrinsic characteristic of the artifact class within the context of the enterprise's pricing strategy. This distinction is vital for separating the concept of a cost (a historical expense) from a price (a current or future value proposition). By defining price at the class level, the organization can establish standard pricing tiers that apply to all instances of a given artifact, reducing the risk of data entry errors in transactional systems.

### 4.3.2 Relational Implementation

The relational schema for this concept is encapsulated in the `t_schemaorg_product_price` table. Similar to the brand mapping, the `id` column functions as the primary key, ensuring a unique index for every price-class definition. The `x` column denotes the Artifact class, and the `y` column denotes the Price class. The `NOT NULL` constraint on the `y` column enforces the business rule that an artifact class cannot exist within the pricing module without a defined valuation class. This table is frequently queried by the ERP (Enterprise Resource Planning) system to generate quotes and invoices, necessitating a highly normalized structure to prevent update anomalies.

**Table 4-2: Artifact-to-Price Class Mappings**

| id | x | y |
| :--- | :--- | :--- |
| price_def_101 | IndustrialPump | Tier1WholesaleRate |
| price_def_102 | OfficeChair | VolumeDiscountPrice |
| price_def_103 | ServerRack | StandardMarketPrice |
| price_def_104 | TransportVehicle | FleetLeaseRate |
| price_def_105 | HandTool | RetailUnitPrice |

As shown in Table 4-2, the `IndustrialPump` class is associated with the `Tier1WholesaleRate` price class. This association dictates the default pricing behavior for all pumps in the catalog. The use of distinct price classes (e.g., `VolumeDiscountPrice` versus `RetailUnitPrice`) allows the financial governance framework to apply complex margin rules without altering the base artifact definition. This abstraction layer is essential for maintaining consistency across different sales channels and geographic regions.

## 4.4 Postal Address and Location Logistics

### 4.4.1 Conceptual Definition

The physical location of an artifact, or the location with which it is associated, is defined by the `schemaorg_place_address` axiom. This axiom links an Artifact class (`{X:Class}`) to a Postal Address class (`{Y:Class}`). The assertion `{X} is something that has postal address {Y}` is critical for logistics, tax calculation, and service delivery. In many jurisdictions, the legal status of an asset is determined by its physical location. Therefore, the ontology must support a rigorous definition of place. This axiom ensures that every relevant artifact class is semantically bound to a standardized address format, facilitating interoperability with global logistics providers and customs agencies.

### 4.4.2 Relational Implementation

The `t_schemaorg_place_address` table provides the relational storage for this axiom. The schema consists of the `id` primary key, the artifact class `x`, and the postal address class `y`. The mandatory nature of the `y` column ensures that location data is never omitted for tracked assets. This table serves as the master reference for validating address strings entered into user interfaces; any address instance must conform to one of the address classes defined in this table. This validation step is a key control in the prevention of shipping errors and the mitigation of fraud.

**Table 4-3: Artifact-to-Address Class Mappings**

| id | x | y |
| :--- | :--- | :--- |
| addr_loc_201 | DistributionCenterA | NorthAmericaFacilityAddress |
| addr_loc_202 | CorporateHeadquarters | HQRegisteredAddress |
| addr_loc_203 | RegionalWarehouse | EUStorageLocation |
| addr_loc_204 | ServiceDepot | FieldServiceUnitAddress |
| addr_loc_205 | RetailOutlet | StorefrontLocationAddress |

Table 4-3 demonstrates the linkage between facility classes and their designated address formats. For example, the `DistributionCenterA` class utilizes the `NorthAmericaFacilityAddress` class. This mapping implies that the specific address attributes (such as street, city, and postal code) for any instance of Distribution Center A must adhere to the formatting rules defined for North American facilities. This is particularly relevant for validating state and province codes against ISO 3166-2 standards during the data entry process.

## 4.5 Geospatial Longitude and Coordinate Precision

### 4.5.1 Conceptual Definition

The final attribute defined in this chapter is the geospatial longitude, governed by the `schemaorg_place_longitude` axiom. This axiom associates an Artifact class (`{X:Class}`) with a Longitude class (`{Y:Class}`). The verbalization, `{X} is something that has longitude {Y}`, provides the necessary semantic framework for precise geolocation. While postal addresses provide a human-readable location, longitude provides a machine-readable coordinate essential for GPS tracking, drone delivery logistics, and spatial analysis. The distinction between the address and the longitude is significant; an address may change due to municipal renaming, but the longitude remains a constant physical coordinate.

### 4.5.2 Relational Implementation

The relational schema for this geospatial data is realized in the `t_schemaorg_place_longitude` table. The structure maintains the pattern of `id` as the primary key, `x` as the Artifact class, and `y` as the Longitude class. The `NOT NULL` constraint on `y` reflects the criticality of coordinate data for the classes that require it. This table is often joined with spatial query engines to visualize asset distribution on geographic information systems (GIS). The precision of the data stored in the `y` column (referenced via the Longitude class) determines the accuracy of these spatial calculations.

**Table 4-4: Artifact-to-Longitude Class Mappings**

| id | x | y |
| :--- | :--- | :--- |
| geo_coord_301 | DistributionCenterA | WGS84LongitudeNegative |
| geo_coord_302 | CorporateHeadquarters | WGS84LongitudePrimeMeridian |
| geo_coord_303 | RegionalWarehouse | WGS84LongitudePositive |
| geo_coord_304 | ServiceDepot | WGS84LongitudeNegative |
| geo_coord_305 | RetailOutlet | WGS84LongitudePositive |

In Table 4-4, the `DistributionCenterA` class is mapped to the `WGS84LongitudeNegative` class. This indicates that the facility is located in the Western Hemisphere. By using class-based definitions for longitude (e.g., positive vs. negative, or specific ranges), the system can enforce business rules such as "Assets in negative longitude zones must use specific shipping carriers." This level of semantic granularity transforms raw coordinate data into actionable business intelligence.
