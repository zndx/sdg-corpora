# Chapter 4: Semantic Attribution of Commercial and Geospatial Properties to Artifacts

## 4.1 Scope and Preamble

This chapter delineates the formal protocols for assigning commercial identifiers and geospatial coordinates to physical artifacts within the enterprise data governance framework. It establishes the axiomatic relationships between artifacts and their associated attributes—specifically brand, price, postal address, and longitude—ensuring data consistency across supply chain management and logistics systems. The following sections provide the ontological definitions for these relationships, supported by relational schema implementations and evidence tables. Compliance with these mappings is mandatory for all entities submitting product data to the central repository.

## 4.2 Brand Attribution (Axiom 1)

### 4.2.1 Axiomatic Definition
The foundational axiom for brand attribution is defined in Manchester syntax as `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasBrand some {Y:Class}`. Verbalized, this asserts that any entity X classified as an Artifact must possess a relationship to a brand entity Y. This relationship is existential; an artifact cannot exist within the system without being attributed to a specific brand or manufacturer. This constraint ensures traceability and enforces vendor accountability within the inventory lifecycle.

### 4.2.2 Implementation Guidelines
In practice, the `sdg:hasBrand` property links a specific product instance (X) to a corporate brand identifier (Y). The relational projection of this axiom creates a foreign key dependency where the artifact identifier references a valid brand registry entry. Data stewards must verify that the brand entity Y exists in the master vendor table before establishing the link.

## 4.3 Pricing Structures (Axiom 2)

### 4.3.1 Axiomatic Definition
The assignment of monetary value is governed by the axiom: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPrice some {Y:Class}`. This posits that an artifact X is characterized by a price Y. Within the ontology, the price Y is treated as a class entity rather than a primitive data type to accommodate complex pricing structures, including multi-currency support, tiered pricing, and historical valuation tracking.

### 4.3.2 Implementation Guidelines
When recording price data, the system enforces a strict non-null constraint on the price entity Y. The relational schema isolates the price attribute to allow for independent auditing of price fluctuations without altering the core artifact definition. It is imperative that the price class Y includes metadata regarding the currency unit and the effective date of the valuation.

## 4.4 Postal Addressing (Axiom 3)

### 4.3.1 Axiomatic Definition
For the purposes of logistics and physical location tracking, the ontology defines the relationship: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`. This axiom asserts that an artifact X, which may represent a facility, a storage unit, or a fixed installation, has a postal address Y. The postal address is modeled as a class to facilitate the parsing of components such as street names, municipal codes, and postal regions.

### 4.3.2 Implementation Guidelines
The `sdg:hasPostalAddress` property is critical for last-mile delivery accuracy and regulatory reporting. The relational structure requires that the address entity Y be distinct from the artifact X, allowing multiple artifacts to reside at a single address or for a single artifact to have multiple functional addresses (e.g., billing vs. physical). Data entry must conform to the ISO 19160 standard for address representation.

## 4.5 Geospatial Coordinates: Longitude (Axiom 4)

### 4.5.1 Axiomatic Definition
To support precision logistics and geospatial analysis, the axiom `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasLongitude some {Y:Class}` is utilized. This defines that an artifact X (typically a location or place) possesses a specific longitude Y. Modeling longitude as a class allows the system to associate metadata, such as the datum (e.g., WGS84) and precision accuracy, directly with the coordinate value.

### 4.5.2 Implementation Guidelines
The `sdg:hasLongitude` property is mandatory for all fixed-location artifacts. The relational schema treats the longitude value Y as a distinct entity to prevent data type ambiguity between floating-point numerics and formatted coordinate strings. Validations must be applied to ensure Y falls within the valid range of -180.0 to +180.0 degrees.
