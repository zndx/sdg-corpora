# Chapter 4: Artifact Attribute Mapping and Schema Governance

## 4.1 Scope and Preamble

This chapter delineates the formal protocols for mapping specific attributes to artifact classes within the enterprise data ontology. It addresses the structural requirements for associating commercial products with brand and price entities, as well as linking physical locations with postal addresses and geospatial coordinates. The guidelines provided herein ensure compliance with the Common Core Ontologies (CCO) framework, specifically anchoring all defined entities to the `cco:Artifact` superclass. Adherence to these mappings is mandatory for maintaining data integrity across supply chain management, logistics, and compliance reporting systems. The following sections provide the axiomatic definition, relational schema implementation, and audit evidence for each attribute mapping.

## 4.2 Brand Association Protocols

### 4.2.1 Axiomatic Definition and Governance
The association of a tangible or digital product to its originating commercial entity is governed by the `schemaorg_product_brand` axiom. In this context, the ontology defines that a specific class of product `{X}` is a subclass of `cco:Artifact` and must possess a specific relationship `sdg:hasBrand` with a brand entity class `{Y}`. This relationship is not merely descriptive but functional; it establishes the provenance and liability chain for the artifact. Verbalized, the axiom asserts: "{X} is something that has brand {Y}". Within the governance framework, this ensures that every inventory item is traceable to a manufacturer or distributor entity, facilitating recall procedures and warranty validation.

### 4.2.2 Implementation and Data Structure
The relational projection of this axiom is realized in the table `t_schemaorg_product_brand`. The primary key `id` serves as the unique identifier for the specific brand assertion. The column `x` references the specific artifact class (the product), while `y` references the brand class. It is imperative that the `y` column is not null, as an artifact without a brand association violates the completeness constraints of the inventory management system.

## 4.3 Price Specification and Valuation

### 4.3.1 Axiomatic Definition and Governance
Financial attribution to artifacts is managed through the `schemaorg_product_price` axiom. This axiom asserts that a product class `{X}`, which is a subclass of `cco:Artifact`, possesses a price attribute defined by the class `{Y}`. The verbalization of this rule is: "{X} is something that has price {Y}". In the context of audit readiness, this mapping separates the physical description of the good from its financial valuation, allowing for currency fluctuations and regional pricing strategies to be modeled without altering the core artifact definition. The `sdg:hasPrice` property acts as a bridge between the physical inventory ontology and the financial ledger sub-systems.

### 4.3.2 Implementation and Data Structure
The schema `t_schemaorg_product_price` enforces the recording of these valuations. The `id` column provides a unique transaction or listing ID. Column `x` denotes the artifact class being priced, and column `y` denotes the price class or value instance. The constraint `NOT NULL` on column `y` ensures that zero-cost or null-value entries are explicitly flagged as errors unless a specific "zero value" class is defined, preventing ambiguity in asset valuation reports.

## 4.4 Geospatial Addressing and Postal Codes

### 4.4.1 Axiomatic Definition and Governance
The physical location of artifacts, specifically those classified as facilities or distribution centers, is governed by the `schemaorg_place_address` axiom. This axiom defines that a place class `{X}`, subclassing `cco:Artifact`, is characterized by `sdg:hasPostalAddress` referencing an address class `{Y}`. The verbalization states: "{X} is something that has postal address {Y}". This mapping is critical for regulatory compliance, particularly regarding jurisdiction determination and tax remittance. It abstracts the full complexity of a postal address into a single relational object, allowing the `cco:Artifact` (the place) to remain distinct from the descriptive string of the address.

### 4.4.2 Implementation and Data Structure
The relational table `t_schemaorg_place_address` captures these linkages. The `id` serves as the primary key for the location record. Column `x` identifies the place artifact (e.g., a specific warehouse or site), while column `y` contains the reference to the postal address class. The non-null constraint on `y` ensures that every registered site in the system has a verifiable physical location for logistics and emergency response planning.

## 4.5 Coordinate Precision and Longitude

### 4.5.1 Axiomatic Definition and Governance
For high-precision logistics and environmental monitoring, the `schemaorg_place_longitude` axiom provides the necessary geospatial granularity. This axiom stipulates that a place class `{X}`, as a subclass of `cco:Artifact`, possesses a longitude attribute defined by class `{Y}`. The verbalization is: "{X} is something that has longitude {Y}". This attribute is essential for automated routing systems, drone delivery protocols, and precise regulatory reporting regarding facility placement relative to restricted zones or environmental boundaries. It complements the postal address by providing machine-readable coordinate data.

### 4.5.2 Implementation and Data Structure
The schema `t_schemaorg_place_longitude` facilitates the storage of these coordinates. The `id` uniquely identifies the coordinate entry. Column `x` references the place artifact, and column `y` references the longitude value class. The `NOT NULL` constraint on `y` enforces the requirement that any place included in geospatial calculations must have a defined longitudinal position.
