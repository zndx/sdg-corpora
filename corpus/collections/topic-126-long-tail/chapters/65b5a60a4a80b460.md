# CHAPTER 4 — ONTOLOGICAL MAPPING FOR ASSET IDENTIFICATION AND GEOSPATIAL COMPLIANCE

## 4.0 SCOPE AND DEFINITIONAL FRAMEWORK

This chapter establishes the mandatory data structures and ontological commitments required for the classification of physical artifacts within the centralized asset management system. It provides the necessary definitions for associating commercial identifiers, financial valuations, and geospatial coordinates with tangible entities. Compliance with these schemas is mandatory for all reporting entities subject to Title 4 of the Governance Framework. The following sections detail the axiomatic structure of four critical relationship types: Brand Association, Price Specification, Postal Address Assignment, and Longitude Verification. Each concept is presented with its formal Manchester Syntax definition, natural language verbalization, and the corresponding relational schema required for database instantiation.

## 4.1 BRAND ASSOCIATION AND ARTIFACT PROVENANCE

### 4.1.1 Axiomatic Definition

The provenance of a physical asset is a primary factor in risk assessment and supply chain auditing. To ensure traceability, the ontology defines a strict relationship between the artifact and its manufacturer or distributor.

*   **Template ID:** `schemaorg_product_brand`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasBrand some {Y:Class}`
*   **Verbalization:** {X} is something that has brand {Y}

This axiom asserts that any entity classified as an Artifact (`cco:Artifact`) must possess a specific relationship to a Brand entity (`sdg:hasBrand`). In this context, {X} represents the specific class or individual instance of the artifact being cataloged, while {Y} represents the commercial brand responsible for its production. This relationship is existential; an artifact cannot exist within the registry without being linked to a valid brand class.

### 4.1.2 Relational Implementation

The projection of this axiom into a relational database schema enforces a one-to-many dependency, where a single brand may be associated with multiple artifacts, but every artifact record must reference a brand. The primary key (`id`) serves as the unique transaction identifier for the association, while `x` and `y` function as foreign keys referencing the Artifacts and Brands tables, respectively.

The following table illustrates the instantiation of this schema, demonstrating the binding of specific asset classes to their corresponding commercial brands.

| :--- | :--- | :--- |
| rel_001 | IndustrialPump_ModX | GlobalFluidics_Corp |

| rel_003 | ControlPanel_V2 | NexGenLogic_Ind |

### 4.1.3 Compliance Verification

Auditors must verify that for every record in the asset inventory, a corresponding entry exists in `t_schemaorg_product_brand`. The `y` column must reference a brand entity that is currently active in the approved vendor list. Any artifact class `x` appearing in the inventory without a corresponding brand relationship is considered non-compliant and must be flagged for immediate remediation.

## 4.2 PRICE SPECIFICATION AND VALUATION PROTOCOLS

### 4.2.1 Axiomatic Definition

Financial accountability requires that every physical artifact be associated with a specific, standardized pricing structure. This association facilitates automated auditing of procurement records and insurance valuations.

*   **Template ID:** `schemaorg_product_price`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPrice some {Y:Class}`
*   **Verbalization:** {X} is something that has price {Y}

This axiom dictates that an Artifact (`cco:Artifact`) is characterized by the possession of a Price (`sdg:hasPrice`). The variable {X} denotes the artifact class, and {Y} denotes the price class. It is critical to note that {Y} is treated as a class within this ontology, representing a standardized price point or pricing tier (e.g., "Standard Rate," "Emergency Surcharge," or a specific monetary value class) rather than a raw floating-point number, ensuring semantic consistency across financial ledgers.

### 4.2.2 Relational Implementation

The relational schema `t_schemaorg_product_price` enforces the linkage between the physical asset and its authorized price point. The `id` column provides the unique index for the relationship. The column `x` references the artifact, and `y` references the authorized price class. This structure prevents the entry of arbitrary or unapproved pricing data by restricting `y` to predefined classes within the financial ontology.

**Table 4.2: Artifact-Price Classification Matrix**

| id | x (Artifact Class) | y (Price Class) |
| :--- | :--- | :--- |
| rel_101 | IndustrialPump_ModX | PriceClass_Tier1_4500_USD |
| rel_102 | SafetyValve_TypeA | PriceClass_Tier2_1200_USD |
| rel_103 | ControlPanel_V2 | PriceClass_Tier3_850_USD |
| rel_104 | SensorArray_Pro | PriceClass_Bulk_500_USD |
| rel_105 | Actuator_Series5 | PriceClass_Tier1_4500_USD |

### 4.2.3 Audit Procedures

During quarterly audits, the system shall cross-reference the `x` values in `t_schemaorg_product_price` against the current procurement log. Discrepancies between the recorded price class `y` and the invoiced amount must be investigated. The use of distinct price classes (e.g., `PriceClass_Tier1_4500_USD`) allows for rapid aggregation of asset values by category without exposing sensitive raw pricing data in lower-level reports.

## 4.3 POSTAL ADDRESS ASSIGNMENT AND LOCATION TRACKING

### 4.3.1 Axiomatic Definition

To facilitate physical inspections and logistical operations, artifacts that represent fixed locations or are assigned to fixed sites must be rigorously linked to postal addresses. This axiom ensures that "Place" entities are grounded in verifiable civic location data.

*   **Template ID:** `schemaorg_place_address`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`
*   **Verbalization:** {X} is something that has postal address {Y}

This axiom asserts that a Place (modeled here as a subclass of `cco:Artifact`) possesses a Postal Address (`sdg:hasPostalAddress`). The subject {X} represents the facility, site, or storage unit, while the object {Y} represents the formal postal address class. This distinction allows for the separation of the physical entity (the building) from its addressing metadata, which may change independently due to municipal renaming or rezoning.

### 4.3.2 Relational Implementation

The table `t_schemaorg_place_address` maintains the binding between the site identifier and the address record. The primary key `id` ensures referential integrity. The column `x` contains the identifier for the Place artifact, and `y` contains the identifier for the Postal Address class. This schema supports one-to-many relationships, allowing a single large facility (e.g., a campus) to possess multiple valid postal address entries (e.g., for different wings or loading docks).

**Table 4.3: Facility-Address Mapping Registry**

| id | x (Place Artifact) | y (Postal Address Class) |
| :--- | :--- | :--- |
| rel_201 | Site_Alpha_Distribution | Address_123_Main_St_Springfield |
| rel_202 | Site_Beta_Manufacturing | Address_456_Industrial_Park_Shelby |
| rel_203 | Site_Gamma_Research | Address_789_Innovation_Dr_Capital |
| rel_204 | Site_Alpha_Distribution | Address_124_Main_St_Springfield |
| rel_205 | Site_Delta_Storage | Address_101_Logistics_Way_Rural |

### 4.3.3 Regulatory Notes

Entities must ensure that the `y` values (Postal Address Classes) are formatted in accordance with ISO 19160-1 standards. The `x` values must correspond to valid facility codes established in the Site Master File. Table 4.3 demonstrates that `Site_Alpha_Distribution` utilizes two distinct address classes, likely representing separate receiving docks, which is a valid configuration under the current schema constraints.

## 4.4 LONGITUDE VERIFICATION AND GEOSPATIAL PRECISION

### 4.4.1 Axiomatic Definition

High-precision location tracking is required for assets subject to movement restrictions or environmental monitoring. While postal addresses provide civic context, geospatial coordinates provide absolute mathematical positioning.

*   **Template ID:** `schemaorg_place_longitude`
*   **Manchester Syntax:** `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasLongitude some {Y:Class}`
*   **Verbalization:** {X} is something that has longitude {Y}

This axiom defines that an Artifact (specifically a Place) is characterized by a specific Longitude (`sdg:hasLongitude`). The subject {X} is the location artifact, and the object {Y} is the longitude coordinate class. By treating longitude as a class rather than a primitive data type, the ontology can associate metadata with specific coordinates (e.g., "Datum: WGS84," "Precision: Centimeter") or group locations into longitudinal zones for regulatory purposes.

### 4.4.2 Relational Implementation

The `t_schemaorg_place_longitude` table records the specific longitudinal coordinate associated with each place artifact. The `id` column serves as the unique record identifier. Column `x` references the Place artifact, and column `y` references the Longitude class. This structure is essential for generating geospatial visualizations and verifying that assets remain within designated permissible zones.

**Table 4.4: Geospatial Longitude Coordinates**

| id | x (Place Artifact) | y (Longitude Class) |
| :--- | :--- | :--- |
| rel_301 | Site_Alpha_Distribution | GeoCoord_W093_15_00 |
| rel_302 | Site_Beta_Manufacturing | GeoCoord_W093_20_30 |
| rel_303 | Site_Gamma_Research | GeoCoord_W077_01_15 |
| rel_304 | Site_Delta_Storage | GeoCoord_W095_40_00 |
| rel_305 | Site_Epsilon_Remote | GeoCoord_W120_30_45 |

### 4.4.4 Data Integrity Standards

The longitude classes listed in column `y` must be derived from verified GPS surveys. Self-reported coordinates are insufficient for compliance. As shown in Table 4.4, the longitude is encoded as a class string (e.g., `GeoCoord_W093_15_00`), which must resolve to a decimal value in the application layer. Any discrepancy between the recorded longitude class and the physical location of the asset identified in {X} constitutes a critical location violation.
