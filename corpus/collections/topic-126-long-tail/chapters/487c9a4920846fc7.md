# Chapter 4: Asset Specification and Geospatial Compliance Protocols

## 4.1 Scope and Preamble

This chapter delineates the mandatory data governance protocols for the classification and specification of physical artifacts and geospatial entities within the enterprise asset management system. It establishes the ontological framework required to ensure data integrity across procurement, logistics, and compliance reporting functions. Adherence to these specifications is critical for maintaining audit readiness and ensuring interoperability between the inventory database and external regulatory bodies. The following sections define the structural relationships between artifacts, their commercial attributes, and their physical locations, providing the necessary schema definitions for implementation.

## 1. Brand Attribution and Artifact Lineage

### 1.1 Ontological Definition

In accordance with the upper-level ontology `cco:Artifact`, every tangible product managed within the system must be explicitly linked to a specific commercial origin. This relationship is governed by the axiom `schemaorg_product_brand`. Formally, this is expressed in Manchester syntax as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasBrand some {Y:Class}`. 

Verbalized, this axiom asserts: **{X} is something that has brand {Y}**. 

This definition mandates that an entity cannot exist as a standalone artifact within the database without a valid association to a Brand class. This constraint prevents the ingestion of orphaned or unverified inventory items, ensuring that every stock-keeping unit (SKU) is traceable to a manufacturer or licensor. The Brand entity ({Y}) functions as a critical control point in supply chain auditing, allowing for rapid filtering of product recalls and warranty validation.

### 1.2 Implementation Guidelines

During the data entry phase, operators must select a valid Brand identifier from the master reference table. The system enforces this by requiring a foreign key validation against the Brand registry prior to the creation of a new Artifact record. For instance, when logging a ventilation control unit, the user cannot merely describe the object; they must associate it with the specific corporate entity responsible for its production. This linkage supports downstream analytics, including market share analysis and vendor performance scoring.

The column `x` represents the Artifact (the product), while the column `y` represents the Brand class. In this relational projection, `y` acts as a foreign key reference to a normalized Brand directory, ensuring referential integrity.

## 2. Pricing Structures and Valuation

### 2.1 Ontological Definition

Financial governance requires that every artifact possess a defined valuation metric to support capitalization and depreciation schedules. The axiom `schemaorg_product_price` formalizes this requirement. The Manchester syntax is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPrice some {Y:Class}`.

Verbalized, this axiom asserts: **{X} is something that has price {Y}**.

In this context, {Y} is not merely a primitive numerical value but is treated as a Price Class instance. This allows the system to distinguish between list price, net price, and discounted price structures without altering the core schema of the Artifact. By treating Price as a class, the ontology supports complex pricing models, including multi-currency representations and time-sensitive pricing tiers, which are essential for international procurement operations.

### 2.2 Audit and Compliance Protocols

When auditing asset registers, inspectors must verify that the Price attribute associated with an Artifact reflects the current book value or the standard unit cost at the time of acquisition. The separation of the Artifact ({X}) from the Price ({Y}) allows for historical price tracking. If the cost of a specific control unit changes, a new Price instance is created and linked to the Artifact, preserving the history of previous valuations for forensic accounting purposes.

Column `y` references the Price class, which encapsulates the specific monetary value and currency code. This structure ensures that price updates are managed as distinct events rather than overwriting historical data, maintaining a strict chain of evidence for financial audits.

## 3. Postal Addressing and Site Identification

### 2.1 Ontological Definition

Logistics and regulatory compliance depend on the unambiguous identification of physical locations where artifacts are installed or stored. The axiom `schemaorg_place_address` defines the spatial relationship between a location and its postal designation. The Manchester syntax is: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y:Class}`.

Verbalized, this axiom asserts: **{X} is something that has postal address {Y}**.

While {X} represents the Artifact or Place entity, {Y} represents the Postal Address class. This distinction is vital for entities that may have multiple valid addresses (e.g., a billing address versus a physical shipping address). By modeling the address as a related class rather than a simple string property, the system can validate addresses against global postal standards and automate the generation of shipping documentation.

### 3.2 Site Verification Standards

For field technicians and compliance officers, the accurate mapping of a Place ({X}) to a Postal Address ({Y}) is a safety-critical requirement. Installation manuals, such as those for fire ventilation systems, mandate that equipment be registered to a specific service location. The ontology ensures that a "Site" entity cannot exist in the database without being anchored to a verified postal address, thereby preventing the deployment of assets to undefined or "ghost" locations.

### 3.3 Relational Schema and Data Mapping

The table `t_schemaorg_place_address` enforces the `schemaorg_place_address` axiom. The `id` column serves as the primary key for the relationship record. Column `x` identifies the specific Place or Site Artifact. Column `y` contains the reference to the Postal Address class instance. This schema supports the requirement that a single site may have multiple address records (e.g., different loading docks) by allowing multiple rows for the same `x` value with distinct `y` values.

## 4. Geospatial Coordinates and Longitude

### 4.1 Ontological Definition

To support high-precision logistics and emergency response planning, the system must capture the geospatial coordinates of all physical assets. The axiom `schemaorg_place_longitude` provides the longitudinal component of this spatial data. The Manchester syntax is defined as: `Class: {X:Class} SubClassOf: cco:Artifact, sdg:hasLongitude some {Y:Class}`.

Verbalized, this axiom asserts: **{X} is something that has longitude {Y}**.

In this axiom, {Y} is treated as a Longitude class. This approach allows for the inclusion of metadata regarding the coordinate system used (e.g., WGS84, NAD83) and the precision of the measurement. For critical infrastructure, such as fire ventilation control units, precise longitude data is often a regulatory requirement for automated dispatch systems and insurance risk assessment.

### 4.2 Geospatial Integrity Checks

The integration of longitude data into the artifact ontology enables automated validation checks. For example, the system can flag inconsistencies where the longitude of an installation site does not match the longitude derived from its associated postal address. This cross-referencing between the `schemaorg_place_address` and `schemaorg_place_longitude` axioms provides a robust mechanism for detecting data entry errors and potential fraud.

### 4.3 Relational Schema and Data Mapping

The following table, `t_schemaorg_place_longitude`, operationalizes the `schemaorg_place_longitude` axiom. The primary key is the `id` column. Column `x` links the record to the Place or Site Artifact. Column `y` references the Longitude class instance. This schema allows for the storage of high-precision floating-point values or specific geodetic string representations, depending on the implementation of the Longitude class.
