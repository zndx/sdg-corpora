# Chapter 4: Formalization of ISO/IEC 27001 Control Mappings and Evidence Verification

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the mapping of organizational directives to ISO/IEC 27001 controls, the generation of compliance evidence, and the verification processes required for audit readiness. It provides a rigorous examination of the relational dependencies between Annex A controls, clause requirements, and attestation protocols. The content herein is designed to assist compliance officers, internal auditors, and information security managers in establishing a traceable, evidence-based governance framework. By defining the precise relationships between directive classes and their corresponding regulatory targets, this chapter ensures that control implementations are not only operationally effective but also verifiable against the strict axioms of the ISO/IEC 27001 standard.

## 4.2 ISO 27001 Annex A Subclassifications

The foundational element of the ISMS (Information Security Management System) architecture is the mapping of internal organizational directives to the specific controls enumerated in ISO/IEC 27001 Annex A. Formally, we define a class of directives that are subclasses of the `cco:DirectiveICE` (Information Control Element) and possess a specific relationship to an Annex A control. This relationship, denoted as `sdg:iso27001AnnexA`, asserts that a given directive is a realization or implementation of a standardized control objective.

In this context, the directive represents the actionable policy or procedure within the enterprise, while the Annex A reference represents the abstract control defined by the standard. The ontological axiom asserts that for a directive to be compliant, it must be a subclass of a DirectiveICE and must be associated with exactly one Annex A control class. This mapping is critical for establishing the "line of sight" between high-level governance mandates and specific technical or administrative controls.

The following data schema illustrates this mapping. The primary key (`id`) represents the unique identifier for the Annex A subclass instance. The column `x` denotes the specific organizational directive (e.g., an Access Control Policy), while `y` denotes the corresponding requirement equivalence class that defines the control's parameters. Note that the foreign key constraint requires that the Annex A control (`y`) must reference a valid Requirement Equivalent ID, ensuring that every control implementation is anchored to a formal requirement specification.

**Table 4.1: Relational Mapping of Annex A Subclasses**

| id | x | y |
| :--- | :--- | :--- |
| annex_a_9_1 | AccessControlPolicy | req_access_control |
| annex_a_8_2 | PrivilegedAccessPolicy | req_asset_mgmt |
| annex_a_12_3 | DataBackupDirective | req_backup_ops |
| annex_a_7_1 | ScreeningPolicy | req_hr_security |
| annex_a_14_2 | SecureDevDirective | req_acquisition |

This mapping demonstrates that the `AccessControlPolicy` (x) is a specific implementation of the control defined by `req_access_control` (y). This structure allows auditors to query the directive and immediately retrieve the governing requirement equivalence, facilitating rapid gap analysis and compliance verification.

## 4.3 Attestation with Supporting Evidence

Once directives are established and mapped to controls, the organization must demonstrate adherence through formal attestation. Attestation is defined as a process (`bfo:0000015`) wherein a responsible entity (such as a CISO or compliance officer) asserts that controls are operating effectively. Crucially, this attestation is not merely a declarative statement; it must be supported by empirical evidence.

The axiom governing attestation stipulates that an attestation class is a process that possesses the property `sdg:withSupportingEvidence`. This property links the attestation act to a specific evidence class or instance. In a mature governance framework, an attestation is considered invalid if it lacks this supporting evidence linkage. This ensures that compliance claims are grounded in verifiable data artifacts, such as logs, screenshots, configuration exports, or third-party audit reports.

The relational schema for attestation highlights this dependency. The attestation record (`id`) describes the process (`x`), which is linked via a foreign key to the Annex A subclass (`y`). This structure enforces the rule that one may only attest to the state of a specific control implementation (the Annex A subclass), and that this linkage must be preserved in the audit trail.

**Table 4.2: Attestation Processes and Evidence Linkage**

| id | x | y |
| :--- | :--- | :--- |
| attest_2023_q4 | QuarterlyAccessReview | annex_a_9_1 |
| attest_2023_q4 | AnnualInventoryAudit | annex_a_8_2 |
| attest_2023_q4 | BackupRestorationTest | annex_a_12_3 |
| attest_2023_q4 | BackgroundVerificationProcess | annex_a_7_1 |
| attest_2023_q4 | CodeReviewAttestation | annex_a_14_2 |

In Table 4.2, the `QuarterlyAccessReview` (x) is the attestation process. It is linked to `annex_a_9_1` (y), indicating that this specific attestation event serves as evidence of compliance for the Access Control Policy. This granular mapping allows the organization to pinpoint exactly which control is being verified by any given attestation activity, reducing ambiguity during external audits.

## 4.4 ISO 27001 Clause Subclassifications

While Annex A provides the catalog of controls, the clauses of ISO/IEC 27001 (e.g., Clause 6 for Planning, Clause 7 for Support, Clause 8 for Operation) prescribe the management system requirements that those controls must satisfy. It is imperative to distinguish between controls (Annex A) and management system clauses. A directive may be implemented to satisfy a specific clause requirement, which in turn mandates the application of certain controls.

The ontology defines a class of directives that are subclasses of `cco:DirectiveICE` and possess the relationship `sdg:iso27001Clause`. This axiom captures the obligation of the organization to meet the systemic requirements of the standard, such as establishing information security roles, conducting risk assessments, or defining management commitment.

The relational representation of clause subclassifications mirrors that of the Annex A mappings but connects to a different dimension of the standard. Here, the directive (`x`) is linked to a requirement equivalence (`y`) that specifies a clause-level obligation. The foreign key constraint ensures that the clause requirement is formally defined within the `t_requirement_equiv_specifies_target` table, maintaining referential integrity across the governance model.

**Table 4.3: Relational Mapping of Clause Subclasses**

| id | x | y |
| :--- | :--- | :--- |
| clause_6_1_1 | InfoSecRolesDirective | req_planning_roles |
| clause_7_5_1 | DocumentedProcedureDirective | req_doc_control |
| clause_8_2 | ThreatIdentificationDirective | req_ops_threats |
| clause_9_1 | MonitoringDirective | req_perf_monitor |
| clause_10_1 | NonConformityDirective | req_improvement |

Table 4.3 illustrates that the `InfoSecRolesDirective` (x) is the organizational realization of the requirement defined in `req_planning_roles` (y), which corresponds to Clause 6.1.1 regarding the assignment of information security roles. By separating clause mappings from control mappings, the organization can verify that it has met both the "what" (Annex A controls) and the "how" (Clause management system processes) of the standard.

## 4.5 Verification Produces Evidence

Verification is the systematic process of checking whether a control is functioning as intended. Unlike attestation, which is a declaration of compliance, verification is an investigative activity. The ontology defines verification as a process (`bfo:0000015`) that `producesEvidence`. This evidence is the output of the verification activity and serves as the input for subsequent attestations.

This axiom establishes a causal chain: the execution of a verification procedure (e.g., a penetration test, a configuration check, or a log review) generates an artifact (e.g., a test report, a pass/fail result). This artifact is then consumed by the attestation process to support a compliance claim. The integrity of this chain is vital; if the evidence produced by verification is not linked to the specific control being verified, the attestation relying on it is fundamentally flawed.

The data structure for verification reinforces this linkage. The verification process (`x`) is linked to the Annex A subclass (`y`), indicating which control is being subjected to verification. This ensures that every piece of evidence generated can be traced back to the specific control implementation it validates.

**Table 4.4: Verification Processes and Evidence Generation**

| id | x | y |
| :--- | :--- | :--- |
| verify_001 | AutomatedConfigAudit | annex_a_9_1 |
| verify_002 | PhysicalAssetCount | annex_a_8_2 |
| verify_003 | RestoreSimulation | annex_a_12_3 |
| verify_004 | EmploymentHistoryCheck | annex_a_7_1 |
| verify_005 | StaticCodeAnalysis | annex_a_14_2 |

In Table 4.4, the `AutomatedConfigAudit` (x) is the verification process. It produces evidence regarding `annex_a_9_1` (y), the Access Control Policy. The output of this audit (e.g., a CSV file of user permissions) constitutes the "evidence" produced. This evidence is subsequently attached to the `QuarterlyAccessReview` attestation identified in Section 4.2, closing the loop between verification, evidence, and attestation.

## 4.6 Requirement Equivalence and Target Specification

The central node in the compliance ontology is the Requirement Equivalent. This concept serves as the bridge between the abstract standard and the concrete operational environment. A Requirement Equivalent is defined as a `cco:DirectiveICE` that `specifies` a control (or clause) and `appliesTo` a specific target within the organization.

The target (`Z`) can be a system, a business unit, a data classification, or a physical location. This tripartite structure—Requirement Equivalent, Specification, and Target—allows for precise scoping of compliance obligations. For example, a requirement equivalent might specify that "Multi-Factor Authentication" is required, but it applies only to the "Production Environment" and not to the "Development Environment."

The relational schema for this axiom is the most complex, serving as a parent table for both Annex A and Clause subclassifications. It defines the unique requirement (`id`), the directive class (`x`) that embodies it, the specific control or clause it specifies (`y`), and the target (`z`) to which it is scoped. The foreign key constraints ensure that the specification (`y`) refers back to a valid Annex A subclass, creating a bidirectional reference that locks the requirement to its implementation.

**Table 4.5: Requirement Equivalence and Target Specification**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| req_access_control | AccessControlRequirement | annex_a_9_1 | HR_System |
| req_asset_mgmt | AssetManagementRequirement | annex_a_8_2 | Production_Database |
| req_backup_ops | BackupOperationsRequirement | annex_a_12_3 | Cloud_Storage_Bucket |
| req_hr_security | HRSafetyRequirement | annex_a_7_1 | Personnel_Records |
| req_acquisition | SecureAcquisitionRequirement | annex_a_14_2 | Supply_Chain_Portal |

Table 4.5 demonstrates the `req_access_control` (id). It is an `AccessControlRequirement` (x) that specifies the `annex_a_9_1` control (y) and applies specifically to the `HR_System` (z). This level of granularity is essential for effective audit management. It allows the organization to state definitively that the HR System is subject to the Access Control Requirement, which is realized by the Access Control Policy, which is verified by the Automated Config Audit, and attested to via the Quarterly Access Review. This end-to-end traceability is the hallmark of a robust, evidence-anchored compliance program.
