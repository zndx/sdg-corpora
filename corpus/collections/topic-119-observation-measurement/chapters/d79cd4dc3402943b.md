# Chapter 7: Ontological Mapping of Spatial Artifacts and Descriptive Claims

## 7.1 Scope and Preamble

This chapter delineates the protocols for mapping physical artifacts to their descriptive information content entities (ICE) within a compliant governance framework. The primary objective is to establish a rigorous data lineage between tangible assets—specifically those classified as Artifacts—and their abstract representations, such as geospatial coordinates and postal addresses. Adherence to the axioms defined herein ensures that spatial data remains auditable, traceable, and semantically consistent across regulatory reporting systems. The following sections provide the formal definitions, relational schemas, and implementation guidelines required to validate these mappings against the established ontology.

## 7.2 Descriptive Information Content Entities

### 7.2.1 Definition and Axiomatic Basis

The foundational unit of data within this framework is the Descriptive Information Content Entity (ICE). Formally defined by the axiom `outlier_claim_basic`, this entity represents any distinct unit of information that describes a state of affairs, a measurement, or an observation. Unlike physical artifacts, Descriptive ICEs are immaterial; they exist as data assertions that require grounding in a specific context to be actionable for compliance purposes.

The axiom asserts that:
**Class: {X} SubClassOf: cco:DescriptiveICE**

Verbalized: {X} is a descriptive information content entity.

In practice, this class serves as the parent type for various data points that will later be attributed to physical locations. It is critical that all Descriptive ICEs be assigned unique identifiers prior to their association with artifacts to prevent referential ambiguity during audit cycles.

### 7.2.2 Implementation and Data Structure

The relational projection of this axiom creates a normalized repository for all descriptive claims. The primary key is the unique identifier (`id`), while the `x` slot denotes the specific class or instance of the descriptive entity.

The following table illustrates the instantiation of Descriptive ICEs used for geospatial and postal recording.

| :--- | :--- |

*Table 7.1 enumerates distinct descriptive entities (x) bound by unique identifiers (id). These records function as the target foreign keys for artifact associations, ensuring that every coordinate or address utilized in the system is formally registered as a Descriptive ICE.*

## 7.3 Geospatial Referencing of Artifacts

### 7.3.1 The Artifact-Coordinate Relationship

To establish physical presence in a digital twin environment, Artifacts must be linked to precise geospatial data. This relationship is governed by the axiom `schemaorg_place_geocoord`, which bridges the physical domain (`cco:Artifact`) with the informational domain (`sdg:hasGeoCoordinates`).

The axiom asserts:
**Class: {X} SubClassOf: cco:Artifact, sdg:hasGeoCoordinates some {Y}**

Verbalized: {X} is something that has geo coordinates {Y}.

This definition mandates that any entity classified as an Artifact must possess a specific relationship to at least one instance of a GeoCoordinate class. This is not merely a data storage requirement but a structural validation rule: an Artifact lacking this link is considered semantically incomplete within the governance model.

### 7.3.2 Relational Mapping and Constraints

The schema derived from this axiom enforces a foreign key constraint linking the Artifact record to the Descriptive ICE registry established in Section 7.2. This structure guarantees that no "orphan" coordinate data can be attached to an Artifact without first being defined as a valid Information Content Entity.

The table below demonstrates the mapping of specific Artifacts (e.g., municipal buildings, inspection sites) to their respective coordinate sets.

**Table 7.2: Artifact-to-Coordinate Mapping**

| id | x | y |
| :--- | :--- | :--- |
| `LOC_HINESBURG_TOWN` | `HinesburgTownHall` | `DESC_COORD_VT_01` |
| `LOC_HINESBURG_CONF` | `ConferenceRoom3rdFloor` | `DESC_COORD_VT_02` |
| `LOC_LAUSANNE_EPFL` | `EPFLInnovationPark` | `DESC_COORD_VT_01` |

*Table 7.2 represents the `t_schemaorg_place_geocoord` schema. The column `x` denotes the Artifact, while column `y` references the `id` from the Descriptive ICE table (Table 7.1). The Foreign Key constraint ensures that only registered coordinate sets (e.g., `DESC_COORD_VT_01`) may be attributed to physical locations.*

## 7.4 Postal Addressing and Administrative Boundaries

### 7.4.1 Administrative Addressing of Artifacts

While geospatial coordinates provide precise physical location, regulatory compliance often requires administrative identification through postal addresses. The axiom `schemaorg_place_address` governs this distinct but complementary relationship. It asserts that an Artifact is an entity that possesses a postal address, which is itself treated as a Descriptive ICE.

The axiom asserts:
**Class: {X} SubClassOf: cco:Artifact, sdg:hasPostalAddress some {Y}**

Verbalized: {X} is something that has postal address {Y}.

This distinction is vital for governance frameworks that must differentiate between "where a thing is" (coordinates) and "where a thing is officially registered" (postal address). In many audit scenarios, such as tax compliance or service jurisdiction, the postal address takes precedence over the geospatial coordinate.

### 7.4.2 Data Integrity and Cross-Referencing

The relational schema for postal addressing mirrors that of geospatial referencing but points to a different subset of Descriptive ICEs—specifically those formatted as postal addresses rather than coordinate sets. The integrity of the system relies on the disjoint nature of these data types; a coordinate set cannot fulfill the requirement for a postal address and vice versa.

The following table provides the linkage between Artifacts and their registered postal addresses.

| `ADDR_LINK_LAUSANNE` | `FlyabilityHQ` | `DESC_ADDR_CH_01` |
| `ADDR_LINK_NY` | `RegionalOfficeUS` | `DESC_ADDR_US_NY` |

*Table 7.3 represents the `t_schemaorg_place_address` schema. The `y` column contains references to postal-specific Descriptive ICEs (e.g., `DESC_ADDR_CH_01`). This separation allows for the maintenance of complex administrative hierarchies where a single Artifact may possess multiple valid descriptive attributes (coordinates and addresses) simultaneously without data collision.*
