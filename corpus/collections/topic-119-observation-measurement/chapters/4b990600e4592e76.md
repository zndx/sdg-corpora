# Chapter 7: Ontological Mapping for Geospatial Asset Compliance

## 7.1 Scope and Preamble

This chapter establishes the protocol for mapping physical artifacts to their descriptive information content entities (ICE) within the centralized compliance database. The objective is to ensure that all geospatial and postal data associated with regulated assets are traceable, verifiable, and structurally bound to their respective physical locations. The guidelines herein follow the strict auditing standards required for regulatory reporting, specifically addressing the integration of coordinate systems and postal addressing schemes into a unified ontology. By adhering to these axioms, the organization ensures that every physical site (Artifact) is inextricably linked to the descriptive claims (DescriptiveICE) that define its spatial and legal boundaries.

## 1. Descriptive Information Content Entities (DICE)

### 1.1 Definition and Axiomatic Basis

In the context of asset governance, a Descriptive Information Content Entity (DescriptiveICE) is defined as any non-material entity that asserts a property, value, or state of affairs regarding a subject. It is not the physical asset itself, but rather the data artifact that describes it. According to Axiom 2, the foundational class structure is established such that the entity {X} is a member of the class `cco:DescriptiveICE`. This distinction is critical for audit trails; it separates the *evidence* (the descriptive claim) from the *object* (the physical artifact).

In practice, these entities serve as the "outlier claims" or data points that require validation during an audit cycle. They are the atomic units of information stored in the database, representing assertions about coordinates, addresses, or other descriptive attributes. The integrity of the entire compliance framework relies on the rigorous management of these entities.

### 1.2 Relational Implementation of Basic Claims

The following table embodies Axiom 2 (`outlier_claim_basic`), which posits that {X} is a descriptive information content entity. The primary key `id` serves as the unique identifier for the specific claim or data record, while the column `x` denotes the class or type of the descriptive entity (e.g., a specific coordinate string or address text). This structure forms the lookup table for all descriptive assertions used in subsequent relational joins.

| :--- | :--- |
| CLAIM_GEO_001 | GeoCoordinateSet_Alpha |

### 1.3 Audit Implications

When an auditor reviews a site record, they are fundamentally reviewing the `t_outlier_claim_basic` entries. If a coordinate is disputed, the `id` of that claim is flagged. Because this table acts as the parent for all specific attribute mappings (geospatial or postal), maintaining referential integrity here is mandatory. Any orphaned records in this table—claims not associated with a physical artifact—must be investigated as potential data anomalies or "ghost" entries that could indicate incomplete decommissioning processes.

## 2. Geospatial Coordinate Integration

### 2.1 Artifact-to-Coordinate Mapping

The physical manifestation of a regulated site is modeled as an `cco:Artifact`. To satisfy regulatory requirements for site location, the ontology defines a relationship between this Artifact and a specific set of GeoCoordinates. Axiom 1 (`schemaorg_place_geocoord`) formalizes this: {X} (the Artifact) is something that has geo coordinates {Y} (the DescriptiveICE).

This relationship is not merely associative but structural. It asserts that the physical existence of the site is spatially defined by the coordinate data provided. In a compliance scenario, this linkage allows the system to query all physical sites within a specific bounding box or to verify that a site's reported location matches the legal description in its permit.

### 2.2 Relational Implementation of Coordinates

The table below embodies Axiom 1 (`schemaorg_place_geocoord`), representing the link between a physical Artifact and its descriptive GeoCoordinates. The primary key `id` uniquely identifies the relationship instance. The column `x` references the physical Artifact (the Place), and the column `y` is a foreign key that references the `id` in the `t_outlier_claim_basic` table, effectively pointing to the specific coordinate data entity. This enforces the constraint that a coordinate cannot exist in the system without being a valid, defined descriptive claim.

| id | x | y |
| :--- | :--- | :--- |
| GEO_LINK_001 | Site_Artifact_882 | CLAIM_GEO_001 |
| GEO_LINK_002 | Site_Artifact_883 | CLAIM_GEO_002 |
| GEO_LINK_003 | Site_Artifact_884 | CLAIM_GEO_003 |
| GEO_LINK_004 | Site_Artifact_885 | CLAIM_GEO_001 |

### 2.3 Verification Protocols

Verification of these mappings requires a two-step process. First, the auditor must validate the accuracy of the content in `t_outlier_claim_basic` (e.g., checking if the latitude/longitude in `CLAIM_GEO_001` is physically correct). Second, the auditor must verify the linkage in `t_schemaorg_place_geocoord` to ensure `Site_Artifact_882` is correctly pointing to `CLAIM_GEO_001` and not a different coordinate set. Errors in the `y` column represent a critical failure in data lineage, potentially causing a site to be mapped to an incorrect location in regulatory visualization tools.

## 3. Postal Address Resolution

### 3.1 Artifact-to-Address Mapping

While geospatial coordinates provide precise physical location data, the Postal Address provides the legal and civic identifier for an Artifact. Axiom 3 (`schemaorg_place_address`) states that {X} (the Artifact) is something that has postal address {Y}. This relationship is essential for correspondence, permit applications, and service delivery.

The distinction between the coordinate and the address is a key feature of this ontology. They are treated as separate descriptive entities (both instances of `cco:DescriptiveICE`) that are linked to the same Artifact. This allows for situations where the postal address may differ from the physical GPS coordinates (e.g., a large facility with a mailing address different from its entry point) without creating data conflicts.

### 3.2 Relational Implementation of Addresses

The following table embodies Axiom 3 (`schemaorg_place_address`), which links the physical Artifact to its Postal Address. Similar to the coordinate schema, the primary key `id` identifies the specific linkage. The column `x` denotes the Artifact, and `y` is a foreign key referencing the `t_outlier_claim_basic` table, specifically pointing to the record containing the postal address string. This structure ensures that address data is treated with the same rigor as coordinate data, maintaining a single source of truth for all descriptive attributes.

| id | x | y |
| :--- | :--- | :--- |
| ADDR_LINK_001 | Site_Artifact_882 | CLAIM_ADDR_001 |
| ADDR_LINK_002 | Site_Artifact_883 | CLAIM_ADDR_002 |
| ADDR_LINK_003 | Site_Artifact_884 | CLAIM_ADDR_003 |
| ADDR_LINK_004 | Site_Artifact_886 | CLAIM_ADDR_001 |

### 3.3 Compliance and Normalization

In the context of regulatory reporting, the `t_schemaorg_place_address` table facilitates the automated generation of mailing lists and legal notices. The foreign key constraint on `y` ensures that only validated, standardized address records are associated with artifacts. For instance, if `CLAIM_ADDR_001` contains the normalized string "10632 Route 116, Hinesburg, VT 05461", multiple artifacts (as seen in `ADDR_LINK_001` and `ADDR_LINK_004`) can share this address if they are co-located. This reduces redundancy and ensures that a change to the master address record propagates correctly to all associated artifacts, a requirement for maintaining accurate contact information under current governance frameworks.
