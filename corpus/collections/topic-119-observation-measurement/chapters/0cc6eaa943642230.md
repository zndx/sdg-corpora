# Chapter 4: Verification of Spatial Artifacts and Descriptive Claims

## 4.1 Scope and Preamble

This chapter delineates the procedural standards for the verification and classification of spatial entities within the enterprise data governance framework. It establishes the mandatory ontological relationships between physical Artifacts and their corresponding Descriptive Information Content Entities (ICE). The guidelines provided herein ensure that all locational data—whether expressed as geodetic coordinates or postal designations—adheres to the strict relational constraints defined in the governing schema. Compliance with these axioms is required for all audit submissions regarding fixed asset management and regulatory reporting.

## 4.2 Descriptive Information Content Entities

### 4.2.1 Ontological Definition

The foundational unit of data within the spatial governance framework is the Descriptive Information Content Entity (DescriptiveICE). Formally defined by the axiom `outlier_claim_basic`, this entity class represents any information content entity that serves to describe a state of affairs, an observation, or a measurement. In the context of this framework, these entities are treated as "claims"—assertions of fact that require validation against physical reality or authoritative sources.

The axiom asserts:
> **{X} is a descriptive information content entity**

Where `{X}` represents the specific class or instance of the information entity. This classification is critical because it segregates raw data (the description) from the physical object (the artifact). By isolating descriptive entities into a dedicated registry, the framework facilitates independent auditing of the data without necessitating the physical inspection of the asset itself.

### 4.2.2 Registry of Basic Claims

All descriptive claims must be registered in the central repository `t_outlier_claim_basic`. This table functions as the primary key source for all subsequent spatial attributions. It ensures that every coordinate set, address string, or boundary description is uniquely identified and typed before it can be associated with a physical location.

The following registry excerpt illustrates the recording of distinct descriptive entities. Note that the `x` column denotes the specific class or instance name of the descriptive content, serving as the data payload for the claim.

**Table 4.1: Registry of Descriptive Information Content Entities**

| id | x |
| :--- | :--- |
| DESC_GEO_001 | GeoCoordinateSet_Hinesburg_Hall |
| DESC_ADDR_001 | PostalAddress_10632_Route_116 |

*Table 4.1 embodies Axiom 2 (`outlier_claim_basic`), where the primary key `id` uniquely identifies the descriptive claim, and `x` represents the entity class. This structure serves as the referential integrity anchor for all spatial artifacts.*

## 4.3 Geospatial Attribution of Artifacts

### 4.3.1 The Artifact-Coordinate Relationship

Physical locations, sites, and facilities are classified as Artifacts within the Common Core Ontologies (CCO). To render these physical entities within a digital system, they must be linked to specific geospatial data. The axiom `schemaorg_place_geocoord` formalizes this requirement by asserting that an Artifact is a subclass of entities that possess specific GeoCoordinates.

The axiom is verbalized as:
> **{X} is something that has geo coordinates {Y}**

In this relational structure, `{X}` represents the Artifact (the place), and `{Y}` represents the DescriptiveICE (the coordinate data) registered in Section 4.2. This relationship is mandatory; an Artifact record cannot be considered compliant without a valid foreign key reference to an established GeoCoordinate claim.

### 4.3.2 Compliance and Verification

During an audit, the verification process involves a two-step check. First, the auditor must confirm the existence of the Artifact record. Second, the auditor must validate that the `y` slot (the GeoCoordinate) references a valid entry in the `t_outlier_claim_basic` table. This prevents "orphan" coordinates—data points that describe a location not tied to a recognized asset—and ensures that every coordinate set is actively utilized.

The following table demonstrates the linkage between specific Artifacts and their respective GeoCoordinate claims. The `y` column contains the Foreign Key constraints referencing the IDs established in Table 4.1.

**Table 4.2: Geospatial Attribution Log**

| id | x | y |
| :--- | :--- | :--- |
| GEO_LINK_01 | Hinesburg_Town_Hall | DESC_GEO_001 |
| GEO_LINK_02 | Vitale_S_Manufacturing | DESC_GEO_002 |
| GEO_LINK_03 | SFPE_Phila_Valley_Chapter | DESC_GEO_003 |

*Table 4.2 embodies Axiom 1 (`schemaorg_place_geocoord`). The primary key is `id`; `x` denotes the Artifact (e.g., Hinesburg_Town_Hall); and `y` is the Foreign Key referencing the descriptive claim (`t_outlier_claim_basic`). This enforces the structural requirement that the Artifact has coordinates.*

## 4.4 Postal Address Attribution of Artifacts

### 4.4.1 Administrative Locators

While geospatial coordinates provide absolute mathematical positioning, regulatory frameworks and logistical operations often require human-readable administrative locators. The axiom `schemaorg_place_address` governs the relationship between an Artifact and its PostalAddress. Similar to the geospatial linkage, this axiom asserts that an Artifact possesses a postal address, which is itself a DescriptiveICE.

The axiom is verbalized as:
> **{X} is something that has postal address {Y}**

This distinction is vital for compliance reporting. Many regulatory bodies, such as tax authorities or emergency services, operate on postal addressing schemas rather than geodetic coordinates. Therefore, the governance framework treats Addresses as a separate class of descriptive claims, subject to their own validation rules (e.g., format checking against postal standards).

### 4.4.2 Dual-Attribution Requirements

In a comprehensive governance environment, a high-value Artifact may require both Geospatial and Postal attributions simultaneously. This dual-attribution ensures that the entity is discoverable both by automated GPS systems and by human-centric delivery networks. The relational schema enforces this by allowing multiple records for the same Artifact `{X}` across the `t_schemaorg_place_geocoord` and `t_schemaorg_place_address` tables, provided they reference valid descriptive claims.

The table below details the assignment of postal addresses to the Artifacts introduced in the previous section.

**Table 4.3: Postal Address Attribution Log**

| id | x | y |
| :--- | :--- | :--- |
| ADDR_LINK_01 | Hinesburg_Town_Hall | DESC_ADDR_001 |
| ADDR_LINK_02 | Vitale_S_Manufacturing | DESC_ADDR_002 |
| ADDR_LINK_03 | SFPE_Phila_Valley_Chapter | DESC_ADDR_003 |

*Table 4.3 embodies Axiom 3 (`schemaorg_place_address`). The structure mirrors the geospatial logic, with `x` as the Artifact and `y` as the Foreign Key referencing a specific PostalAddress claim in `t_outlier_claim_basic`. Note that `DESC_ADDR_003` was implicitly added to the registry to support this linkage, illustrating the dependency of Artifact records on pre-existing descriptive claims.*

## 4.5 Audit Implications and Data Integrity

The strict enforcement of these axioms creates a normalized database environment where no descriptive data exists in isolation, and no physical object exists without a data profile. For the compliance officer, this structure simplifies the detection of anomalies.

For instance, an "orphan" Artifact—an entry in `t_schemaorg_place_geocoord` where the `y` value does not exist in `t_outlier_claim_basic`—indicates a critical referential integrity failure. Conversely, a descriptive claim in `t_outlier_claim_basic` that is not referenced by any Artifact suggests "data drift" or obsolete records that should be purged.

By adhering to the schemas defined in this chapter, organizations ensure that their spatial data is not merely a collection of strings and numbers, but a rigorously defined map of the physical world, anchored in ontological certainty and resistant to data corruption.
