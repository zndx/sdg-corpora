# Corporate Governance Audit Ontologies in Relational Form

This chapter presents five ontological templates that formalize directive governance processes. Each template is realized as a table whose rows contain entity references drawn from corporate board minutes, attendance records, and compliance attestations. Primary-key and foreign-key columns enable cross-table navigation that answers multi-hop queries about verification, conduct, signature, and audit period.

## 1. Requirement Verification Structure

Axiom 1 states that a directive information content entity must be verified by at least one entity. Table t_requirement_min_one_verification implements this requirement by storing the directive identifier in column x and the mandatory verifier in column y. Column id is the primary key; column y functions as a foreign key that must resolve to an entity listed in another governance table.

| id | x | y |
| id | x | y |
| req-001 | BoardMeetingMinutes2020 | AuditCommittee |
| req-002 | AttendanceSlipDec2015 | CompanySecretary |
| req-003 | CourtOrderDec2015 | IndependentDirector |
| req-004 | MeetingNoticeNov2020 | ComplianceOfficer |
| req-005 | CorrectedMinutesNov2020 | BoardPresident |
| req-006 | PrivateLessonSchedule | FacilityManager |

## 2. Audit Conduct Record

Axiom 2 classifies an audit as a process conducted by a person. Table t_audit_conducted_by records the audit identifier in column x. Column id is the sole primary key; the absence of additional columns keeps the table minimal while still allowing x values to serve as join targets in subsequent tables.

| id | x |
| id | x |
| acb-001 | BoardMeetingAudit2020 |
| acb-002 | AttendanceAuditDec2015 |
| acb-003 | CourtConvenedAudit2015 |
| acb-004 | MinutesCorrectionAudit2020 |
| acb-005 | ScheduleComplianceAudit2022 |
| acb-006 | CenterHoursAudit2022 |

## 3. Attestation Signature Requirement

Axiom 3 requires that an attestation process be signed by at least one person. Table t_attestation_min_one_signer stores the attestation identifier in column x. Column id is the primary key; x values are later referenced by tables that record actual signers.

| id | x |
| id | x |
| ams-001 | MinutesAttestationNov2020 |
| ams-002 | AttendanceAttestationDec2015 |
| ams-003 | CourtOrderAttestation2015 |

| ams-005 | HoursVerificationAttestation2022 |

## 4. Attestation Signature Execution

Axiom 4 records that an attestation process is signed by a person. Table t_attestation_signed_by stores the attestation identifier in column x. Column id is the primary key; multiple rows may share the same x value when more than one signer is required.

| id | x |
| id | x |
| asb-001 | MinutesAttestationNov2020 |
| asb-002 | AttendanceAttestationDec2015 |
| asb-003 | CourtOrderAttestation2015 |
| asb-004 | ScheduleAttestation2022 |
| asb-005 | HoursVerificationAttestation2022 |
| asb-006 | MinutesAttestationNov2020 |

## 5. Audit Period Association

Axiom 5 associates an audit process with a defined audit period. Table t_audit_for_period stores the audit identifier in column x and the period identifier in column y. Column id is the primary key; column y acts as a foreign key referencing period entities used elsewhere in the schema.

| id | x | y |
| id | x | y |
| afp-001 | BoardMeetingAudit2020 | November2020 |
| afp-002 | AttendanceAuditDec2015 | December2015 |
| afp-003 | CourtConvenedAudit2015 | December2015 |
| afp-004 | MinutesCorrectionAudit2020 | November2020 |
| afp-005 | ScheduleComplianceAudit2022 | December2022 |
| afp-006 | CenterHoursAudit2022 | December2022 |

## 6. Cross-Table Query Example

To determine which person signed the attestation of the November 2020 corrected minutes that were verified under requirement req-005 and occurred during audit period November2020, perform the following joins. First match t_requirement_min_one_verification.x = "CorrectedMinutesNov2020" to obtain y = "BoardPresident". Next locate the attestation identifier in t_attestation_min_one_signer whose x matches the same directive. Finally join that attestation identifier to t_attestation_signed_by on x and to t_audit_for_period on x = "MinutesCorrectionAudit2020" with y = "November2020". The resulting joined row set contains:

- requirement row: req-005, CorrectedMinutesNov2020, BoardPresident
- attestation requirement row: ams-001, MinutesAttestationNov2020
- signature rows: asb-001, MinutesAttestationNov2020 and asb-006, MinutesAttestationNov2020
- period row: afp-004, MinutesCorrectionAudit2020, November2020

The signer entities referenced by the signature rows therefore satisfy the multi-hop verification path.
