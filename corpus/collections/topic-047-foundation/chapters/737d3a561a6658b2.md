# Chapter 4: Ontological Formalization of Cross-Regulatory Compliance Directives

## 4.1 Scope and Preamble

This chapter establishes the formal ontological mapping for compliance directives within the Information Security Governance framework. It details the structural derivation of regulatory requirements—specifically those pertaining to the Payment Card Industry Data Security Standard (PCI DSS) and the Health Insurance Portability and Accountability Act (HIPAA)—into a unified semantic model. The content herein defines the axiomatic relationships between directive classes, their specified targets, and the implementation of safeguards. It provides the necessary schema definitions and evidentiary data tables required to populate the governance knowledge base, ensuring that all entities adhere to the constraints defined by the `cco:DirectiveICE` upper ontology.

## 4.2 PCI DSS Requirement Axioms

The foundational element of the PCI DSS compliance framework within this ontology is the `pci_dss_requirement` class. This class represents a specific mandate or control objective derived from the Payment Card Industry Data Security Standard. Formally, this axiom asserts that any entity classified as a PCI DSS Requirement is a subclass of `cco:DirectiveICE` (Information Control Element) and necessitates a relationship to a specific requirement class via the object property `sdg:pciDssRequirement`.

In practical governance terms, this mapping allows an organization to trace a specific compliance obligation—such as the requirement to encrypt transmission of cardholder data—to its formal definition within the ontology. The structure ensures that every PCI DSS directive is anchored to a specific control target, facilitating automated audit trails and gap analysis.

## 4.3 Requirement Equivalence and Target Specification

To ensure semantic interoperability between different regulatory frameworks, the ontology employs an equivalence axiom for directive specifications. The `requirement_equiv_specifies_target` axiom defines a class as equivalent to the intersection of `cco:DirectiveICE`, a `sdg:specifies` relationship to a target class, and an `sdg:appliesTo` relationship to a scope class.

This construct serves a critical function in the governance model: it decouples the directive from the implementation. By defining a requirement as equivalent to a directive that specifies a target and applies to a scope, the model supports complex queries such as "Retrieve all directives that apply to 'Cardholder Data Environment' and specify 'Encryption Mechanisms'." Furthermore, the schema enforces a recursive integrity constraint where the specification (`y`) must reference a valid PCI requirement, creating a closed loop of verification.

Table 4-2 illustrates this structure. It maps the equivalence classes to their specific PCI requirement anchors (`y`), defines the object being specified (`y` in the logical sense, mapped here as the target entity), and defines the scope of application (`z`).

## 4.4 HIPAA Physical Safeguards

The HIPAA Security Rule categorizes safeguards into physical, technical, and administrative dimensions. The `hipaa_safeguard_physical` axiom formalizes the physical safeguards within the ontology. This axiom classifies any physical safeguard as a subclass of `cco:DirectiveICE` that enforces a `sdg:hipaaSafeguard` relationship with a specific target class.

Physical safeguards are defined in 45 CFR § 164.310(a)(1) and include measures to control physical access to electronic information systems and the facility in which they are housed. In the context of this ontology, the `hipaa_safeguard_physical` class maps these regulatory measures to the generic `DirectiveICE` structure, allowing for correlation with similar controls in other frameworks (e.g., ISO 27001).

## 4.5 HIPAA Technical Safeguards

Technical safeguards, governed by the `hipaa_safeguard_technical` axiom, address the automated mechanisms used to protect electronic protected health information (ePHI) and control access to it. As defined in 45 CFR § 164.312, these safeguards include access control, audit controls, integrity controls, and transmission security.

The ontology treats these technical safeguards as `DirectiveICE` entities. The axiom asserts that a technical safeguard `X` is a directive that enforces a HIPAA safeguard `Y`. By mapping the `y` slot to the `t_requirement_equiv_specifies_target` table, the ontology explicitly links the technical implementation (e.g., "Unique User Identification") to a requirement specification that may have been defined in the context of PCI DSS or other standards. This facilitates a unified control framework where a single technical control satisfies multiple regulatory obligations.

## 4.6 HIPAA Administrative Safeguards

The final dimension, administrative safeguards, is formalized by the `hipaa_safeguard_admin` axiom. These safeguards, outlined in 45 CFR § 164.308, relate to administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures. These are often the most complex to audit due to their reliance on human behavior and organizational policy rather than rigid hardware or software configurations.

In the ontology, administrative safeguards are modeled similarly to physical and technical safeguards as subclasses of `cco:DirectiveICE`. The relational schema links these administrative actions to the requirement equivalence table, ensuring that policies and procedures are traceable to specific governance targets. For instance, a "Security Awareness Training" program is not merely a document but a directive that applies to a specific target scope defined in the equivalence table.
