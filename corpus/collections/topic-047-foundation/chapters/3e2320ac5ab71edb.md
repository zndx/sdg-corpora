# 4 Directive Governance in Relational Form

This chapter specifies the relational projection of five directive classes under cco:DirectiveICE. The projection uses five tables whose columns directly instantiate the slot types of the source axioms. Primary-key and foreign-key constraints enforce the subclass and equivalence relations stated in each axiom, enabling cross-table joins that recover multi-hop directive specifications.

## 1 Scope and Table Inventory

Five tables are defined. Table t_requirement_equiv_specifies_target is the central equivalence class. Tables t_pci_dss_requirement, t_hipaa_safeguard_physical, t_hipaa_safeguard_technical and t_hipaa_safeguard_admin are its dependent subclasses. All foreign keys reference primary keys of the listed tables only.

## 2 t_requirement_equiv_specifies_target

Axiom 2 states that each instance is an equivalence of cco:DirectiveICE, sdg:specifies and sdg:appliesTo. Column id is the primary key. Column y is a foreign key to t_pci_dss_requirement.id; column z is a non-null class reference to an appliesTo target. A join on y yields the pciDssRequirement filler for any directive instance.

| id | x | y | z |
|----|---|---|---|
| req_001 | AccessControlDirective | pci_001 | NetworkSegment |
| req_002 | AuditLogDirective | pci_002 | TransactionLog |
| req_003 | EncryptionDirective | pci_003 | CardholderData |

## 7 Cross-Join Example

Question: which HIPAA physical safeguard applies to the same directive that specifies PCI DSS requirement pci_001?  
Step 1: select row from t_pci_dss_requirement where id = 'pci_001' yields y = 'req_001'.  
Step 2: select row from t_requirement_equiv_specifies_target where id = 'req_001'.  
Step 3: select row from t_hipaa_safeguard_physical where y = 'req_001' yields x = 'FacilityAccessControl'.  
Joined result row: (pci_001, FirewallConfiguration, req_001, AccessControlDirective, phy_001, FacilityAccessControl).
