# Regulatory Directive Compliance Schema

This chapter specifies the relational encoding of directive instances belonging to cco:DirectiveICE. Five tables materialize the axioms pci_dss_requirement, requirement_equiv_specifies_target, hipaa_safeguard_physical, hipaa_safeguard_technical, and hipaa_safeguard_admin. Primary-key and foreign-key constraints enforce the slot restrictions declared in each axiom, permitting deterministic cross-table retrieval of multi-hop regulatory linkages.

## 1 Scope and Table Organization

The schema supports queries that traverse from a PCI DSS requirement through an equivalence specification to one or more HIPAA safeguard classes. All entity references are drawn from controlled vocabularies of regulatory identifiers. Each table is introduced by a paragraph that identifies the axiom it implements, states its key structure, and supplies one example join path.

### 1.1 t_pci_dss_requirement

This table implements axiom pci_dss_requirement. Column id is the primary key. Column y is a foreign key that must resolve to an instance of t_requirement_equiv_specifies_target. A reader can retrieve the equivalence specification that further qualifies any given PCI DSS requirement by joining on y.

| id                  | x                        | y                       |
|---------------------|--------------------------|-------------------------|
| pci_req_001         | Requirement_1.1          | req_equiv_001           |
| pci_req_002         | Requirement_2.3          | req_equiv_002           |
| pci_req_003         | Requirement_3.4          | req_equiv_003           |
| pci_req_004         | Requirement_4.1          | req_equiv_004           |
| pci_req_005         | Requirement_6.5          | req_equiv_005           |
| pci_req_006         | Requirement_8.2          | req_equiv_001           |
| pci_req_007         | Requirement_12.1         | req_equiv_002           |

### 1.2 t_requirement_equiv_specifies_target

This table implements axiom requirement_equiv_specifies_target. Column id is the primary key. Columns y and z are foreign keys referencing t_pci_dss_requirement and an implicit target class, respectively. The table therefore records the simultaneous specification and applicability constraints required by the equivalence axiom. A reader can obtain both the originating PCI DSS requirement and the target class by joining y to t_pci_dss_requirement.id and z to any safeguard table.

| id            | x                              | y             | z                  |
|---------------|--------------------------------|---------------|--------------------|
| req_equiv_001 | ReqEquivSpec_1                 | pci_req_001   | target_network     |
| req_equiv_002 | ReqEquivSpec_2                 | pci_req_002   | target_access      |
| req_equiv_003 | ReqEquivSpec_3                 | pci_req_003   | target_storage     |

### 1.3 t_hipaa_safeguard_physical

## 2 Cross-Join Demonstration

To determine the administrative safeguard that applies to the target of PCI DSS Requirement_1.1, first locate the equivalence specification whose y column equals pci_req_001 (req_equiv_001). Then locate every row in t_hipaa_safeguard_admin whose y column equals req_equiv_001. The join yields:

- pci_req_001 → req_equiv_001 → hipaa_admin_004 (Incident_Procedures)

The resulting joined row is therefore (pci_req_001, Requirement_1.1, req_equiv_001, target_network, hipaa_admin_004, Incident_Procedures).
