# Chapter 4: Governance Ontology and Relational Compliance Structures

This chapter establishes the formal ontological definitions for key governance concepts—Audit, Requirement, and Attestation—within the context of PCI DSS and general compliance frameworks. It maps these semantic definitions to their corresponding relational schemas, ensuring data integrity and traceability in audit reporting systems. The following sections delineate the axioms governing these entities, providing the necessary structure for implementing compliance controls in a database environment.

## 1. Audit Conducted By

**1.1 Definition and Scope**

In accordance with the governance framework, an AUDIT CONDUCTED BY is defined as a processual entity (bfo:Process) that is executed or overseen by a responsible agent. Specifically, this axiom asserts that any instance of an Audit Class (X) must be associated with a Person (cco:Person) who acts as the conductor or auditor. This relationship ensures accountability and traceability for all audit activities. The definition mirrors the administrative rigor found in regulatory manuals, where the "Reasonable and Prudent Parent Standard" dictates specific decision-making parameters; similarly, the Audit Conducted By standard dictates the necessity of human agency in the audit process.

**1.2 Relational Implementation**

The implementation of this axiom is captured in the `t_audit_conducted_by` table. The primary key (`id`) serves as the unique identifier for the audit class or instance, while the column `x` denotes the specific Audit Class being defined. The structure enforces that every recorded audit is explicitly categorized as a process conducted by a person, satisfying the ontological constraint `sdg:conductedBy some cco:Person`.

## 2. PCI DSS Requirement

**2.1 Directive and Requirement Mapping**

A PCI DSS REQUIREMENT is defined as a Directive (cco:DirectiveICE) that incorporates or references a specific requirement class (Y). This axiom establishes the link between high-level governance directives and the specific compliance requirements mandated by the Payment Card Industry Data Security Standard. In practice, this means that a governing policy document (X) must explicitly map to a technical or operational control (Y). This structure is analogous to the "Health and Human Services" manual entries, where specific titles and chapters (Directives) are inextricably linked to their defining protection standards (Requirements).

**2.2 Schema and Constraints**

The relational schema `t_pci_dss_requirement` enforces a strict dependency between the directive and the requirement definition. The column `x` represents the Directive Class, while `y` represents the Requirement Class. A foreign key constraint ensures that the requirement (`y`) is valid and corresponds to an entry in the `t_requirement_equiv_specifies_target` table, creating a normalized chain of evidence from the directive to its specific implementation targets.

## 3. Requirement Equivalence Specification

**3.1 Complex Class Equivalence**

The REQUIREMENT EQUIV SPECIFIES TARGET axiom provides a granular definition for a Requirement Class (X). It asserts that X is equivalent to the intersection of three conditions: it is a Directive, it Specifies a particular requirement (Y), and it Applies to a specific target (Z). This formalism allows for the precise decomposition of compliance obligations. For instance, a "Foster Care" policy (Directive) is not merely a document but is equivalent to the set of rules that specify safety standards (Y) and apply to foster homes (Z).

**3.2 Relational Structure and Circular Dependency**

The table `t_requirement_equiv_specifies_target` encapsulates this tripartite relationship. The columns `x`, `y`, and `z` correspond to the Directive, the Specification, and the Target, respectively. Notably, the schema includes a circular foreign key reference: the specification (`y`) must reference a valid PCI DSS requirement in `t_pci_dss_requirement`, which in turn references this table. This recursive structure enforces that a requirement cannot exist in isolation; it must be part of a self-referential definition loop that validates both the directive and the specific requirement it entails.

## 4. Attestation Signed By

**4.1 Attestation as a Process**

An ATTESTATION SIGNED BY is a process (bfo:Process) that necessitates the endorsement of a Person (cco:Person). This axiom formalizes the act of attestation, moving it from a vague concept to a distinct entity class within the ontology. In the context of a Board of Regents meeting or a formal corporate filing, an attestation is only valid when it is explicitly signed by an authorized individual, such as a Chair or a Compliance Officer. The signature serves as the bridge between the process of verification and the human agent responsible for it.

**4.2 Data Representation**

The `t_attestation_signed_by` table provides a simple yet critical registry of these attestations. The primary key (`id`) identifies the specific attestation event or class, while `x` denotes the Attestation Class. This table ensures that every attestation recorded in the system is classified as a process requiring a signature, thereby enforcing non-repudiation.

## 5. Attestation with Supporting Evidence

**5.1 Evidence-Based Attestation**

The ATTESTATION WITH SUPPORTING EVIDENCE axiom refines the concept of attestation by requiring that the process (X) be backed by specific evidence (Y). This evidence is typically derived from a PCI DSS Requirement. This structure embodies the principle of "evidence-anchored prose" found in high-quality audit reports; a claim of compliance is insufficient without demonstrable proof. The evidence links the attestation back to the specific technical controls defined in the requirement tables.

**5.2 Foreign Key Relationships**

The `t_attestation_with_supporting_evidence` table links the attestation process to its evidentiary basis. The column `x` identifies the Attestation Class, and `y` identifies the Supporting Evidence Class. The foreign key constraint ensures that the evidence (`y`) corresponds to a valid entry in `t_pci_dss_requirement`, creating a complete audit trail from the human signature (Section 4) through the attestation process down to the specific technical requirement being verified.
