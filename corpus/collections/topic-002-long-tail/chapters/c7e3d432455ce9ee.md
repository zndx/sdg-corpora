# Chapter 4: Governance Directives, Audit Processes, and Attestation Mechanisms

## 4.1 Scope and Preamble

This chapter delineates the structural dependencies between governance directives, audit processes, and attestation protocols within a regulated information security environment. It establishes the ontological relationships between auditable entities, the personnel responsible for conducting audits, and the specific regulatory requirements—such as those defined by the Payment Card Industry Data Security Standard (PCI DSS)—that bind these elements. Furthermore, the chapter details the formal mechanisms of attestation, including the requisite signatories and the evidentiary artifacts necessary to validate compliance. The definitions provided herein are axiomatic, serving as the foundation for the relational data models used in compliance management systems.

## 4.2 Audit Conducted By

The audit function is fundamentally a processual entity (bfo:Process) that requires the agency of a qualified natural person to be instantiated. In formal governance terms, an audit event cannot exist in a vacuum; it is ontologically dependent on the auditor. The axiom `audit_conducted_by` posits that any instance of an audit class is a subclass of a process that is conducted by a specific person (cco:Person). This relationship ensures accountability and traceability, anchoring the audit event to a responsible agent with the authority to inspect and verify.

In practice, this means that the governance framework must maintain a strict record linking every audit engagement to the individual auditor or audit lead. This linkage is not merely administrative but serves as a primary control for independence verification and conflict-of-interest checking. The following table illustrates the instantiation of specific audit events and their necessary binding to the conducting agent.

## 4.3 PCI DSS Requirement Integration

Governance directives are operationalized through their mapping to specific regulatory frameworks. The axiom `pci_dss_requirement` defines a relationship wherein a directive (cco:DirectiveICE) is characterized by its adherence to or inclusion of specific PCI DSS requirements. This is a critical mapping for organizations subject to payment card regulations, as it translates abstract corporate policy into concrete compliance obligations.

The relationship is structured such that a directive class (X) is defined by its possession of a PCI DSS requirement (Y). This requirement (Y) must be formally defined and identifiable within the compliance schema. The complexity of this relationship arises from the need to map high-level governance artifacts (e.g., "Information Security Policy") to granular regulatory controls (e.g., "Requirement 1.2.3").

To maintain data integrity, the relational schema enforces a foreign key constraint where the requirement identifier (Y) must correspond to an entry in the requirements specification table. This ensures that directives are never linked to non-existent or undefined regulatory controls.

**Table 4.2: Directive to PCI DSS Requirement Mapping**

| id | x | y |
| :--- | :--- | :--- |
| DIR-SEC-001 | NetworkSecurityPolicy | PCI-REQ-1.2.1 |
| DIR-SEC-002 | DataEncryptionStandard | PCI-REQ-3.4.1 |
| DIR-SEC-003 | AccessControlProtocol | PCI-REQ-7.1.1 |
| DIR-SEC-004 | VulnerabilityManagementPlan | PCI-REQ-6.1.0 |
| DIR-SEC-005 | LoggingMonitoringProcedure | PCI-REQ-10.1.1 |

*Note: Column `y` references the specific requirement ID. The constraint ensures that `y` exists in the target specification table, preventing orphaned compliance claims.*

## 4.4 Requirement Equivalence and Target Specification

While the previous section maps directives to requirements, the axiom `requirement_equiv_specifies_target` provides a more granular definition of the directive itself. This axiom asserts that a directive class (X) is equivalent to the intersection of three conditions: it is a DirectiveICE, it specifies a particular requirement (Y), and it applies to a specific target system or environment (Z).

This "EquivalentTo" construct is powerful because it defines the directive by its function and scope. A directive is not valid unless it explicitly specifies a requirement and applies it to a tangible target (Z). This structure supports the "long-tail" of compliance governance, where specific technical controls must be mapped to specific infrastructure components (e.g., a firewall rule set applied to the cardholder data environment).

The relational implementation of this axiom involves a circular dependency with the PCI DSS requirement table, reflecting the bidirectional nature of compliance definitions: a directive has a requirement, and that requirement specification, in turn, references the directive to complete the definition of the control environment.

**Table 4.3: Directive Specification and Target Application**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| DIR-SEC-001 | IngressFilterRule | DIR-SEC-001 | PerimeterNetwork |
| DIR-SEC-002 | DatabaseEncryptionAES256 | DIR-SEC-002 | PrimaryCustomerDB |
| DIR-SEC-003 | MFA_Enforcement_IdP | DIR-SEC-003 | ActiveDirectory |
| DIR-SEC-004 | PatchManagement_Windows | DIR-SEC-004 | ServerFarm_Windows |
| DIR-SEC-005 | SIEM_Ingestion_Flow | DIR-SEC-005 | LogAggregationCluster |

*Note: In this schema, `id` represents the unique identifier for the specification equivalence. Column `x` is the directive, `y` is the requirement ID (referencing Table 4.2), and `z` is the target system. The foreign key on `y` ensures the requirement is formally registered in the PCI DSS mapping.*

## 4.5 Attestation Signed By

Attestation is the formal process by which an authorized individual validates the accuracy and completeness of a compliance activity. The axiom `attestation_signed_by` establishes that an attestation is a process (bfo:0000015) that must be signed by a person (cco:Person). This signature serves as the digital or physical manifestation of liability, confirming that the attester has reviewed the underlying evidence and asserts its validity.

In the context of audit trails, the "signed by" property is non-negotiable. It transforms a set of technical logs or configuration states into a legally recognized compliance artifact. The system must record the specific attestation instance (X) and link it irrevocably to the credentials of the signatory. This prevents later repudiation and ensures that a specific human agent is accountable for the compliance claim.

**Table 4.4: Attestation Log and Signatory Authority**

| id | x |
| :--- | :--- |
| ATT-SIG-Q3-2023 | Q3_CIS_Attestation |
| ATT-SIG-ANN-2023 | Annual_SOC2_Report |
| ATT-SIG-PEN-001 | PenetrationTest_Findings_Ack |
| ATT-SIG-VULN-001 | Vulnerability_Scan_Certification |
| ATT-SIG-ACC-001 | User_Access_Review_Certification |

*Note: Column `x` denotes the specific attestation event or document class. The underlying schema links this entry to the personnel record via the `sdg:signedBy` property.*

## 4.6 Attestation with Supporting Evidence

An attestation without evidence is merely a hollow assertion. The axiom `attestation_with_supporting_evidence` mandates that an attestation (X) must be accompanied by supporting evidence (Y). This evidence typically consists of the raw data, screenshots, configuration exports, or audit logs that substantiate the compliance claim.

Crucially, the supporting evidence (Y) must be linked to a specific requirement. This creates a chain of evidence: the Requirement defines the control, the Evidence proves the control is in place, and the Attestation validates the Evidence. The relational schema enforces that the evidence identifier (Y) in the attestation table must reference a valid requirement ID from the PCI DSS requirement table. This ensures that attestations are only supported by evidence that is relevant to the specific regulatory requirement being tested.

**Table 4.5: Attestation Evidence Linkage**

| id | x | y |
| :--- | :--- | :--- |
| ATT-EV-Q3-01 | Q3_CIS_Attestation | PCI-REQ-1.2.1 |
| ATT-EV-Q3-02 | Q3_CIS_Attestation | PCI-REQ-2.2.2 |
| ATT-EV-ANN-01 | Annual_SOC2_Report | PCI-REQ-7.1.1 |
| ATT-EV-PEN-01 | PenetrationTest_Findings_Ack | PCI-REQ-11.3.1 |
| ATT-EV-ACC-01 | User_Access_Review_Certification | PCI-REQ-7.2.1 |

*Note: Column `x` links to the attestation event, while column `y` provides the evidence ID which is mapped to the specific PCI DSS requirement. This structure ensures that every attestation is grounded in verifiable, requirement-specific data.*
