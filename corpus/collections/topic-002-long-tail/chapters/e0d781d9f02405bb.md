# Chapter 4: Formal Verification Mechanisms in PCI-DSS Governance Frameworks

This chapter delineates the formal ontological structures governing the verification of compliance within the Payment Card Industry Data Security Standard (PCI-DSS) domain. It establishes the axiomatic relationships between audit processes, directive requirements, and attestation artifacts, providing a rigorous framework for the classification of governance objects. The content herein is intended for systems architects, compliance officers, and data modelers seeking to implement a high-fidelity representation of regulatory control mechanisms within enterprise knowledge graphs.

## 4.1 Audit Conducted By

In the context of governance frameworks, an audit is formally defined not merely as a review but as a specific temporal process (bfo:Process) that necessitates agency. Axiomatically, the class of Audit is a subclass of processes that are `conductedBy` a `cco:Person`. This distinction is critical for liability and traceability; the audit event cannot exist in a vacuum but must be anchored to a responsible agent possessing the legal standing to perform such verification.

The instantiation of this axiom ensures that every audit record within the system is irrevocably linked to a human operator. This prevents the assignment of audit tasks to automated systems without designated human oversight, thereby maintaining the chain of custody required for regulatory adherence. The following data exhibit illustrates the instantiation of specific audit classes where the conducted-by property is implicit in the class definition, mapped here to their unique identifiers.

**Exhibit 4.1: Audit Class Instances**

| :--- | :--- |

| `AUDIT-2023-Q4-INFRA` | `InfrastructureVulnerabilityAssessment` |

In Exhibit 4.1, the column `x` represents the specific class of the audit event. While the table structure captures the entity identity (`id`) and the class (`x`), the underlying axiom mandates that for any instance of `FinancialControlAudit` or `InfrastructureVulnerabilityAssessment`, there exists a necessary relation `sdg:conductedBy` pointing to an instance of `cco:Person`. This structural constraint enforces the non-automatability of the primary audit signature.

## 4.2 PCI DSS Requirement

The governance of payment card data relies heavily on the precise mapping of organizational directives to regulatory standards. The axiom `pci_dss_requirement` posits that a specific class of directive (`cco:DirectiveICE`) is characterized by the satisfaction of a PCI DSS requirement. Here, the ontology distinguishes between the directive itself (the internal policy or rule) and the external requirement it fulfills.

Formally, if Class `X` is a subclass of `cco:DirectiveICE` and has the property `sdg:pciDssRequirement` with a value of Class `Y`, then `X` is the implementation mechanism for `Y`. This allows the organization to track internal governance artifacts against external compliance mandates. The relational structure implies a dependency where the requirement definition is often further elaborated by an equivalence specification, creating a robust linkage between internal controls and external standards.

**Exhibit 4.2: PCI DSS Requirement Mappings**

| id | x | y |
| :--- | :--- | :--- |
| `DIR-REQ-001` | `DataEncryptionPolicy` | `REQ-EQUIV-001` |
| `DIR-REQ-002` | `AccessControlProtocol` | `REQ-EQUIV-002` |
| `DIR-REQ-003` | `NetworkMonitoringDirective` | `REQ-EQUIV-003` |
| `DIR-REQ-004` | `InformationSecurityPolicy` | `REQ-EQUIV-004` |

In Exhibit 4.2, the `x` column denotes the internal directive class (e.g., `DataEncryptionPolicy`), while the `y` column references the specific requirement specification class. The foreign key constraint (`y` references `t_requirement_equiv_specifies_target`) ensures that every internal directive is mapped to a formally defined requirement specification, preventing orphaned policies within the governance model.

## 4.3 Requirement Equivalence and Target Specification

To achieve a granular level of compliance control, the ontology employs an equivalence axiom for requirement specifications. This axiom asserts that a Class `X` is equivalent to the intersection of a `cco:DirectiveICE`, the act of specifying a requirement (`sdg:specifies`), and the application of that requirement to a target (`sdg:appliesTo`). This tripartite structure forms the core logic of the compliance engine.

This equivalence class serves a dual purpose: it defines what the requirement is (`sdg:specifies`) and where it is enforced (`sdg:appliesTo`). For instance, a directive may specify a firewall rule and apply it to a specific network perimeter. The relational schema for this axiom exhibits a recursive dependency with the PCI DSS requirement table, reinforcing the bidirectional nature of compliance mapping—requirements define directives, and directives instantiate requirements.

**Exhibit 4.3: Requirement Equivalence Specifications**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `REQ-EQUIV-001` | `TransmissionProtectionRule` | `DIR-REQ-001` | `CustomerDataEnvironment` |
| `REQ-EQUIV-002` | `UserAuthenticationStandard` | `DIR-REQ-002` | `ActiveDirectoryRealm` |
| `REQ-EQUIV-003` | `LogRetentionPolicy` | `DIR-REQ-003` | `SIEMInfrastructure` |
| `REQ-EQUIV-004` | `EmployeeClearanceProcess` | `DIR-REQ-004` | `HRDatabase` |

Exhibit 4.3 demonstrates the logical binding. The `x` column represents the specific rule or standard class (e.g., `TransmissionProtectionRule`). The `y` column links back to the internal directive ID (e.g., `DIR-REQ-001`), satisfying the circular reference to `t_pci_dss_requirement`. The `z` column defines the scope of application, such as the `CustomerDataEnvironment`. This structure ensures that compliance is not merely abstract but is grounded in specific, targetable infrastructure or data domains.

## 4.4 Attestation Signed By

While audits and requirements define the *what* and *how* of compliance, attestation provides the *validation* of execution. An attestation is formally modeled as a process (`bfo:0000015`) that is `signedBy` a `cco:Person`. This axiom elevates the attestation from a simple data record to a legally significant event, predicated on the action of a signing agent.

The inclusion of the `signedBy` property within the class definition ensures that any instance of an attestation class carries with it the implicit authority of the signatory. In regulatory contexts, this distinguishes a draft report from a finalized, legally binding submission. The signatory is typically a designated officer or authorized representative whose credentials have been verified within the system's identity management layer.

**Exhibit 4.4: Attestation Class Instances**

| id | x |
| :--- | :--- |
| `ATT-SIGN-2023-01` | `AnnualROCAttestation` |
| `ATT-SIGN-2023-02` | `QuarterlySAQAttestation` |
| `ATT-SIGN-2023-03` | `RemediationCompletionAttestation` |
| `ATT-SIGN-2024-01` | `ExecutiveComplianceCertificate` |
| `ATT-SIGN-2024-02` | `ThirdPartyAssuranceReport` |

The data presented in Exhibit 4.4 categorizes various types of attestations, such as the `AnnualROCAttestation` (Report on Compliance) or the `QuarterlySAQAttestation` (Self-Assessment Questionnaire). By axiomatically binding these classes to the `cco:Person` via the `signedBy` property, the framework guarantees that every entry in this table corresponds to a discrete, accountable event in the physical world, rather than an automated system-generated log entry.

## 4.5 Attestation with Supporting Evidence

The final concept in this governance framework addresses the evidentiary basis of attestation. An attestation is rarely a standalone assertion; it must be substantiated by documentary or empirical proof. The axiom `attestation_with_supporting_evidence` defines a subclass of processes (`bfo:0000015`) that includes the property `sdg:withSupportingEvidence`.

This property links the attestation event directly to the artifacts or requirements it validates. Specifically, the schema links the evidence to a PCI DSS requirement class, creating a closed loop of verification: the requirement exists, the directive implements it, the audit checks it, and the attestation proves it with evidence. This linkage is essential for audit trails and regulatory inquiries, as it allows an investigator to traverse from the final attestation back to the specific control requirement being verified.

**Exhibit 4.5: Attestation Evidence Linkages**

| id | x | y |
| :--- | :--- | :--- |
| `ATT-EVID-100` | `EncryptionValidationAttestation` | `DIR-REQ-001` |
| `ATT-EVID-101` | `AccessReviewAttestation` | `DIR-REQ-002` |
| `ATT-EVID-102` | `VulnerabilityScanAttestation` | `DIR-REQ-003` |
| `ATT-EVID-103` | `PolicyAcknowledgementAttestation` | `DIR-REQ-004` |
| `ATT-EVID-104` | `PenetrationTestAttestation` | `DIR-REQ-003` |

In Exhibit 4.5, the `x` column identifies the specific attestation event class, while the `y` column references the directive ID (e.g., `DIR-REQ-001`) that serves as the evidentiary anchor. The foreign key constraint to `t_pci_dss_requirement` ensures that the evidence cited is valid and exists within the governance framework. For example, the `EncryptionValidationAttestation` is supported by the evidence found in `DIR-REQ-001` (the `DataEncryptionPolicy`), thereby rigorously connecting the assertion of compliance to the defined control.
