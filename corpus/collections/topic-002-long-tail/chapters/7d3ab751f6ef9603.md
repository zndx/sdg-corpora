# Chapter 4: Ontological Formalization of Audit Governance and PCI DSS Compliance

This chapter establishes the formal ontological structures necessary to represent the lifecycle of compliance audits, specifically within the context of the Payment Card Industry Data Security Standard (PCI DSS). The scope of this text is restricted to the precise definition of audit processes, directive requirements, and attestation mechanisms. We employ a dense, axiomatized approach to map these governance concepts to a relational schema, ensuring that every assertion regarding audit conduct, requirement specification, and evidence retention is grounded in a verifiable data structure. The following sections detail the specific axioms governing these relationships, providing the necessary semantic rigor for high-assurance compliance frameworks.

## 4.1 Audit Conducted By

In the governance of information security, the audit is defined not merely as a static report but as an occurrent process—a temporal entity that unfolds over a specific duration. Axiomatically, we define the Audit as a subclass of `bfo:0000015` (Process), which implies it has a beginning and an end and participates in causal relations with other entities. Crucially, the integrity of any audit is predicated on the agency responsible for its execution. The axiom `audit_conducted_by` asserts that every Audit instance must be conducted by a `cco:Person`. This relationship establishes the chain of custody and accountability essential for regulatory adherence.

The distinction between the process (the audit itself) and the agent (the person) is critical. While the audit process encompasses the examination of records, the interviewing of personnel, and the assessment of controls, the `conductedBy` property links this process to a specific legal or functional agent. In compliance frameworks, this linkage prevents the ambiguity of "the audit was performed by the department," instead mandating the identification of a responsible individual. This formalization allows for the automated tracking of auditor conflicts of interest, certification validation, and the segregation of duties.

To illustrate this concept within a relational database context, we map the class `X` (the Audit) to a primary identifier. The following table represents instances of audits where the process is inextricably linked to the ontology of the Person class via the `conductedBy` object property, though the table structure below focuses on the identification of the audit process itself as the entity of interest.

**Table 4.1: Audit Process Instances**

| id | x |
| :--- | :--- |
| AUD-2023-Q3 | Internal_Security_Audit_Q3 |
| AUD-2024-EXT | External_PCI_DSS_Assessment |

The data in Table 4.1 demonstrates the instantiation of the Audit class. Each row represents a distinct process (`x`) identified by a unique URI (`id`). In the broader ontology, each of these `id` values serves as the subject for the `conductedBy` predicate, resolving to a specific `cco:Person` instance. This structure ensures that the audit trail is immutable and that the process is formally recognized as a dependent entity of the auditor.

## 4.2 PCI DSS Requirement

The regulatory landscape governing payment card security is codified in the PCI DSS, which functions as a set of directives. In our ontology, we model these requirements as Information Content Entities (ICE) under the class `cco:DirectiveICE`. The axiom `pci_dss_requirement` formalizes the relationship between a governing directive (`X`) and a specific requirement (`Y`). This relationship is not merely taxonomic but structural; it asserts that the Directive *contains* or *has* the Requirement as a necessary component.

This axiom is foundational for mapping compliance artifacts to regulatory text. When an organization asserts compliance with PCI DSS, they are effectively asserting that their internal controls satisfy the conditions set forth in these `Y` requirement instances. The axiom treats the requirement as a first-class object, allowing for metadata such as versioning, severity, and testing procedures to be attached directly to the requirement entity rather than being embedded in unstructured text.

The relational projection of this axiom requires a foreign key constraint to ensure referential integrity. The requirement (`y`) must point to a valid definition of that requirement, which is modeled in the subsequent section (Axiom 4.3). This dependency enforces the rule that a requirement cannot exist in isolation; it must be part of a defined specification structure.

**Table 4.2: PCI DSS Requirement Directives**

| id | x | y |
| :--- | :--- | :--- |
| DIR-PCI-001 | PCI_DSS_v4.0_Policy | REQ-DEF-001 |
| DIR-PCI-002 | PCI_DSS_v4.0_Network_Security | REQ-DEF-002 |
| DIR-PCI-003 | PCI_DSS_v4.0_Access_Control | REQ-DEF-003 |

In Table 4.2, the column `x` represents the high-level directive (e.g., the PCI DSS v4.0 Policy document), while `y` represents the specific requirement identifier. The foreign key constraint linking `y` to the requirement definition table (detailed below) ensures that every cited requirement is formally defined with its specific targets and parameters.

## 4.3 Requirement Equivalence and Target Specification

To achieve machine-readability in compliance audits, a requirement must be defined not just by its label, but by its logical equivalence to a set of conditions. The axiom `requirement_equiv_specifies_target` provides this definition. It asserts that a Requirement Class (`X`) is equivalent to the intersection of three conditions: it is a `cco:DirectiveICE`, it `specifies` some control or condition (`Y`), and it `appliesTo` some target system or asset (`Z`).

This axiom utilizes the OWL construct `EquivalentTo`, meaning that any entity satisfying the conditions of specifying `Y` and applying to `Z` is recognized as the Requirement `X`. This is a powerful mechanism for dynamic compliance checking. For instance, if a new system is introduced that falls under the definition of `Z` (e.g., "Cardholder Data Environment"), the axiom automatically classifies the relevant requirements as applicable to that system without manual intervention.

The relational schema for this axiom captures the tripartite nature of the definition. The primary key is the requirement ID (`id`), which serves as the anchor for the requirement itself. The column `y` represents the specification (the "what"), and `z` represents the target (the "where"). Notably, the schema includes a recursive foreign key constraint where `y` references the `t_pci_dss_requirement` table. This circular reference creates a tight coupling between the requirement instance and its detailed specification, ensuring that the directive (`X` in Axiom 4.2) and the specification (`Y` in Axiom 4.3) are mutually validating.

**Table 4.3: Requirement Specification and Target Mapping**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| REQ-DEF-001 | Requirement_1_Entity | DIR-PCI-001 | Cardholder_Data_Environment |
| REQ-DEF-002 | Requirement_2_Entity | DIR-PCI-002 | Wireless_Network_Segment |
| REQ-DEF-003 | Requirement_3_Entity | DIR-PCI-003 | Unix_Server_Cluster |
| REQ-DEF-004 | Requirement_4_Entity | DIR-PCI-004 | Central_Log_Server |

Table 4.3 elucidates the specific targets (`z`) for each requirement definition. For example, `REQ-DEF-001` applies specifically to the `Cardholder_Data_Environment`. The column `y` links back to the directive ID in Table 4.2, creating the necessary chain of evidence from the high-level policy document down to the specific technical target.

## 4.4 Attestation Signed By

The culmination of the audit process is the attestation—a formal declaration that the audit findings are accurate and that the subject entity is in a specified state of compliance. The axiom `attestation_signed_by` defines the Attestation as a subclass of `bfo:0000015` (Process), emphasizing that signing is an action occurring in time. It further asserts that this process is `signedBy` a `cco:Person`.

This distinction is vital for non-repudiation. In many compliance frameworks, the difference between a draft report and a final report is solely the presence of a valid signature. By modeling the signature as a process involving a person, we capture the legal gravity of the action. The ontology distinguishes between the *content* of the attestation (the report) and the *act* of attesting (the signing process). This allows the system to track not just who is authorized to sign, but when the signing occurred, which cryptographic keys were used, and whether the signatory's authority was valid at that exact moment.

The relational representation of this axiom is structurally similar to the Audit axiom but serves a different semantic function. Here, the entity `x` represents the Attestation event. This table typically serves as a ledger of all executed attestations, providing a foundation for certificate generation and audit trail reconstruction.

**Table 4.4: Attestation Execution Log**

| id | x |
| :--- | :--- |
| ATT-2023-01 | Q3_Attestation_Event |
| ATT-2024-01 | Annual_Certification_Signing |
| ATT-2024-02 | Remediation_Verification_Signing |
| ATT-2024-03 | Policy_Acknowledgement_Signing |
| ATT-2024-04 | External_Auditor_Conclusion |

The entries in Table 4.4 represent the discrete signing events. Each `id` corresponds to a specific instance where a person applied their credentials to a document or digital artifact. In a full implementation, these IDs would be linked to timestamp records and biometric or cryptographic verification data to ensure the highest level of assurance.

## 4.5 Attestation with Supporting Evidence

An attestation without evidence is merely an opinion; with evidence, it becomes a verifiable assertion of fact. The axiom `attestation_with_supporting_evidence` bridges the gap between the act of signing (Axiom 4.4) and the technical requirements being verified (Axiom 4.2). It asserts that an Attestation (`X`) has `withSupportingEvidence` some Requirement (`Y`).

This axiom implies that the evidence is not an arbitrary document but is intrinsically linked to a specific requirement class. In practice, this means that when an auditor signs an attestation, they are effectively asserting, "I have reviewed the evidence for Requirement Y, and it satisfies the directive." The ontology mandates this link to prevent "rubber-stamping," where an attestation might be applied to a broad set of controls without specific verification for each item.

The relational schema for this axiom links the Attestation instance (`x`) to the specific PCI DSS Requirement (`y`). The foreign key constraint ensures that the evidence cited corresponds to a valid requirement ID defined in the `t_pci_dss_requirement` table. This structure enforces granularity in the audit record, requiring that for every attestation, there must be a traceable path back to the specific regulatory clause it validates.

**Table 4.5: Attestation Evidence Mapping**

| id | x | y |
| :--- | :--- | :--- |
| EVID-001 | ATT-2023-01 | DIR-PCI-001 |
| EVID-002 | ATT-2024-01 | DIR-PCI-002 |
| EVID-003 | ATT-2024-01 | DIR-PCI-003 |
| EVID-004 | ATT-2024-02 | DIR-PCI-001 |
| EVID-005 | ATT-2024-04 | DIR-PCI-005 |

Table 4.5 provides the evidence matrix. For instance, the `Annual_Certification_Signing` (`ATT-2024-01`) is supported by two distinct evidence entries, `EVID-002` and `EVID-003`, which validate `DIR-PCI-002` and `DIR-PCI-003` respectively. This mapping allows compliance officers to query the database for all attestations supporting a specific requirement, or conversely, to generate a report for a specific attestation listing all the requirements it covers. This bidirectional traceability is the hallmark of a mature, audit-ready governance framework.
