# Directive Governance in PCI DSS Attestation Processes

This chapter specifies the relational encoding of five axioms governing audits, requirements, and attestations within PCI DSS compliance. The encoding uses a fixed schema of five tables whose primary and foreign keys directly implement the slot structures of the axioms, enabling deterministic cross-table joins that recover multi-hop relations such as the person who signed an attestation supporting a given requirement.

## 1. Table Structures Derived from Axioms

Each table is introduced by the axiom that determines its columns and constraints. Primary keys identify individual instances; foreign keys enforce the existential restrictions expressed in the Manchester syntax.

### 1.1 t_audit_conducted_by

Axiom 1 classifies an audit process as one conducted by a person; the table therefore stores only the process identifier and the conducting person. The column id is the primary key; x holds the person reference. A reader can join this table on x to any table containing person identifiers to retrieve the responsible individual for each audit instance.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| audit_001 | person_kevin_oneill |
| audit_002 | person_terry_hartle |
| audit_003 | person_amy_smith |
| audit_004 | person_patsy_reddy |
| audit_005 | person_molly_dwyer |

### 1.2 t_pci_dss_requirement

Axiom 2 states that a directive instance stands in the pciDssRequirement relation to a target specification. The table therefore records the directive (x) and the target (y). The column id is the primary key; y is a foreign key referencing t_requirement_equiv_specifies_target.id.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_requirement_equiv_specifies_target(id)
);
```

| id | x | y |
|----|---|---|
| req_001 | directive_pci12_1 | spec_tgt_001 |
| req_002 | directive_pci3_4 | spec_tgt_002 |
| req_003 | directive_pci10_2 | spec_tgt_003 |
| req_004 | directive_pci11_5 | spec_tgt_001 |
| req_005 | directive_pci6_3 | spec_tgt_004 |

### 1.3 t_requirement_equiv_specifies_target

Axiom 3 defines a requirement as equivalent to a directive that both specifies a control and applies to a scope. The table therefore stores the directive class (x), the specification target (y), and the application scope (z). The column id is the primary key; y is a foreign key referencing t_pci_dss_requirement.id.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

| id | x | y | z |
|----|---|---|---|
| spec_tgt_001 | directive_pci12_1 | req_001 | scope_cardholder_data |
| spec_tgt_002 | directive_pci3_4 | req_002 | scope_pan_storage |
| spec_tgt_003 | directive_pci10_2 | req_003 | scope_audit_logs |
| spec_tgt_004 | directive_pci6_3 | req_005 | scope_software_dev |

### 1.4 t_attestation_signed_by

Axiom 4 classifies an attestation process as one signed by a person. The table therefore stores only the attestation identifier and the signing person. The column id is the primary key; x holds the person reference.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| attest_001 | person_kevin_oneill |
| attest_002 | person_patsy_reddy |
| attest_003 | person_molly_dwyer |
| attest_004 | person_terry_hartle |
| attest_005 | person_amy_smith |

### 1.5 t_attestation_with_supporting_evidence

Axiom 5 states that an attestation process is accompanied by supporting evidence in the form of a PCI DSS requirement. The table therefore records the attestation (x) and the evidence reference (y). The column id is the primary key; y is a foreign key referencing t_pci_dss_requirement.id.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

| id | x | y |
|----|---|---|
| attest_001 | attest_proc_001 | req_001 |
| attest_002 | attest_proc_002 | req_002 |
| attest_003 | attest_proc_003 | req_003 |
| attest_004 | attest_proc_004 | req_004 |
| attest_005 | attest_proc_005 | req_005 |

## 2. Cross-Join Demonstration

The following query recovers the signer of an attestation whose supporting evidence satisfies a given PCI DSS requirement. It traverses t_attestation_with_supporting_evidence.y → t_pci_dss_requirement.id, then t_attestation_with_supporting_evidence.x → t_attestation_signed_by.id.

Starting from requirement req_001, the join yields:

- t_attestation_with_supporting_evidence row (attest_001, attest_proc_001, req_001)
- t_attestation_signed_by row (attest_001, person_kevin_oneill)

Result row: (req_001, attest_proc_001, person_kevin_oneill).
