# Chapter 7: Formal Ontology of ISO 27001 Governance and Attestation Protocols

## 1 Scope

This chapter establishes the formal ontological framework governing the mapping of internal directives to the ISO/IEC 27001 information security standard, alongside the protocols for attestation and signatory authority. It delineates the structural relationships between control clauses, annex controls, and requirement specifications, ensuring that governance artifacts are rigorously defined and auditable. Furthermore, it specifies the cardinality constraints for signatory processes, providing a deterministic schema for compliance verification. The provisions herein apply exclusively to the definition and instantiation of security governance objects within the enterprise architecture.

## 2 ISO 27001 Clause Subclassing

### 2.1 Definition and Structural Constraints

The foundational element of the governance framework is the classification of internal directives as subclasses of specific ISO 27001 clauses. A directive is formally defined as a subclass of the standard only when it adheres to the axiomatic structure `iso27001_clause_subclass`. This relationship asserts that a defined entity (X) is a `DirectiveICE` that pertains to a specific ISO 27001 clause (Y). The integrity of this mapping is maintained through a relational dependency where the clause reference (Y) must correspond to a valid requirement equivalence identifier.

This structure ensures that every internal policy or procedure claiming compliance with a specific clause (e.g., Clause 6.1.1 regarding information security roles and responsibilities) is ontologically bound to that clause. The binding is not merely semantic but structural, enforced through foreign key constraints that prevent orphaned references.

### 2.2 Relational Implementation

The implementation of this axiom is captured in the `t_iso27001_clause_subclass` table. The primary key (`id`) serves as the unique identifier for the subclass relationship. The column `x` represents the specific directive class, while `y` represents the ISO 27001 clause class. Critically, the column `y` is constrained by a foreign key referencing the `t_requirement_equiv_specifies_target` table, ensuring that the clause is defined within the context of a specific requirement equivalence.

In the instances presented above, the `AccessControlPolicyDirective` (CS_001) is ontologically linked to the requirement equivalence identified as `REQ_EQ_001`. This linkage ensures that the directive is not an abstract concept but is anchored to a specific, verifiable requirement structure within the governance model.

## 3 Attestation and Signatory Authority

### 3.1 Process Definition and Signatory Binding

Attestation constitutes the formal validation of governance processes, serving as the mechanism by which accountability is established. According to the `attestation_signed_by` axiom, any attestation process (X) is a subclass of `bfo:0000015` (a Process) that must be signed by a `cco:Person`. This axiom establishes the fundamental requirement that processes cannot be considered complete or valid without the explicit association of a human signatory.

This requirement is distinct from the cardinality of signers; it focuses solely on the existence of the relationship. The ontology dictates that the act of signing is an intrinsic property of the attestation process itself. Without this property, the process fails to satisfy the definition of an attestation event within the compliance framework.

### 3.2 Data Representation

The `t_attestation_signed_by` table provides the schema for recording these relationships. Each row represents a specific attestation process instance. The column `x` denotes the specific process class requiring attestation. The table structure is designed to ensure that every entry corresponds to a process that is, by definition, dependent on a signatory actor.

*Table 2: Attestation Signed By Instances*

| id | x |
| :--- | :--- |
| ATT_SIGN_001 | QuarterlyComplianceAuditProcess |
| ATT_SIGN_002 | AnnualRiskAssessmentReviewProcess |
| ATT_SIGN_003 | IncidentResponsePlanSignoff |
| ATT_SIGN_004 | AccessControlGrantingProcess |
| ATT_SIGN_005 | ThirdPartyContractReviewProcess |

The processes listed in Table 2, such as the `QuarterlyComplianceAuditProcess`, are defined by their requirement for a signature. This structural definition facilitates automated compliance checks, ensuring that any workflow instantiated as `ATT_SIGN_001` will trigger a signatory task before completion.

## 4 ISO 27001 Annex A Control Mapping

### 4.1 Operationalizing Annex A Controls

While clauses define the broad requirements of the ISO 27001 standard, Annex A provides the specific control objectives and controls intended for implementation. The `iso27001_annexa_subclass` axiom formalizes the relationship between a directive and an Annex A control. It asserts that a directive (X) is a `DirectiveICE` that pertains to a specific ISO 27001 Annex A control (Y).

This mapping is critical for audit trails, as it connects the high-level policy framework to the granular technical controls specified in Annex A (e.g., A.8.2.1 - Management of privileged access rights). The ontology requires that the Annex A reference (Y) be resolved through a requirement equivalence, ensuring that the control is applied to a specific target within the organization's asset inventory.

### 4.2 Schema and Instances

The `t_iso27001_annexa_subclass` table encodes these mappings. Similar to the clause subclassing table, it relies on a foreign key constraint where `y` references the `t_requirement_equiv_specifies_target` table. This dependency enforces the rule that an Annex A control cannot exist in isolation; it must be part of a requirement specification that targets a specific entity.

*Table 3: ISO 27001 Annex A Subclass Instances*

| :--- | :--- | :--- |
| ANNEX_001 | MultiFactorAuthenticationControl | REQ_EQ_006 |
| ANNEX_002 | SecureDataDisposalProcedure | REQ_EQ_007 |
| ANNEX_003 | MalwareProtectionMechanism | REQ_EQ_008 |
| ANNEX_004 | LoggingConfigurationStandard | REQ_EQ_009 |

For instance, `ANNEX_001` maps the `MultiFactorAuthenticationControl` to the requirement equivalence `REQ_EQ_006`. This entry signifies that the directive implementing multi-factor authentication is formally recognized as satisfying the specific Annex A control objective defined within that requirement equivalence.

## 5 Requirement Equivalence and Target Specification

### 5.1 The Nexus of Directives, Specifications, and Targets

The `requirement_equiv_specifies_target` axiom serves as the central hub in the ontological network. It defines a class (X) as equivalent to a `DirectiveICE` that specifies a particular requirement (Y) and applies to a specific target (Z). This equivalence class resolves the ambiguity often found in compliance frameworks by explicitly linking the directive to both the control it specifies and the entity to which it applies.

This axiom is particularly complex due to its bidirectional relationships. The requirement specified (Y) must reference a valid clause subclass, effectively creating a chain of custody from the Annex A control (or Clause) through the Requirement Equivalence and back to the specific Clause Subclass. This circular dependency ensures that the "specifies" relationship is grounded in a valid clause definition, closing the loop on the compliance definition.

### 5.2 Relational Structure and Data

The `t_requirement_equiv_specifies_target` table implements this logic. It contains columns for the directive (`x`), the specified requirement (`y`), and the target (`z`). The foreign key constraint on `y` mandates that it references an ID in `t_iso27001_clause_subclass`, thereby enforcing the structural link between the requirement and the clause.

*Table 4: Requirement Equivalence Specifies Target Instances*

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| REQ_EQ_001 | LogicalAccessRequirement | CS_001 | InformationSystem |
| REQ_EQ_002 | PersonnelScreeningRequirement | CS_002 | PotentialEmployee |
| REQ_EQ_003 | AssetInventoryRequirement | CS_003 | HardwareAsset |

| REQ_EQ_005 | SupplierEvaluationRequirement | CS_005 | ThirdPartyVendor |

In Table 4, `REQ_EQ_001` defines the `LogicalAccessRequirement`. It specifies `CS_001` (the `AccessControlPolicyDirective`) and applies to the `InformationSystem`. This entry satisfies the axiom by equating the directive to the act of specifying the clause and applying it to a target. Notably, `REQ_EQ_006` also references `CS_001`, demonstrating how multiple requirement equivalences (e.g., for Annex A controls) can specify a single clause subclass, creating a many-to-one relationship that reflects the complexity of real-world compliance mappings.

## 6 Minimum Signatory Constraints

### 6.1 Cardinality in Attestation Processes

While the presence of a signatory is mandatory, the `attestation_min_one_signer` axiom introduces a cardinality constraint to ensure robust governance. It asserts that an attestation process (X) is a subclass of `bfo:0000015` (Process) that must be signed by a minimum of one (`min 1`) `cco:Person`. This constraint prevents the creation of attestation processes that could theoretically be signed by zero actors, which would render the attestation null and void.

This axiom is distinct from the simple "signed by" relationship in that it enforces a quantitative threshold. In the context of automated workflow engines and compliance databases, this constraint acts as a validation rule, blocking the transition of a process to a "completed" state unless at least one signatory event has been recorded.

### 6.2 Implementation and Verification

The `t_attestation_min_one_signer` table captures the instances of processes subject to this constraint. The schema is structurally similar to the basic attestation table but is semantically interpreted by the inference engine to enforce the `min 1` cardinality rule.

The processes listed in Table 5, such as the `SecurityPolicyApprovalProcess` (ATT_MIN_001), represent critical governance events where the absence of a signer would constitute a severe control failure.
