# Chapter 4: Ontological Mapping of ISO 27001 Governance Controls

## Scope

This chapter establishes the formal ontological mappings required to align organizational governance artifacts with the ISO/IEC 27001 information security management standard. The provisions herein define the structural relationships between directive classes, specific ISO 27001 clauses, Annex A controls, and attestation processes. These mappings are intended to facilitate automated compliance auditing and semantic interoperability between regulatory frameworks and internal control systems. The definitions provided are binding for all subsequent data modeling exercises within the governance architecture.

## 4.1 ISO 27001 Clause Subclassifications

The axiom `iso27001_clause_subclass` provides the foundational linkage between a high-level organizational directive and a specific prescriptive clause within the ISO 27001 standard. Formally, this axiom asserts that a Directive Class (X) is a subclass of `cco:DirectiveICE` and possesses the property `sdg:iso27001Clause` with a value restricted to a specific Clause Class (Y). In practice, this allows the governance framework to categorize internal policies not merely by subject matter, but by their specific regulatory authority within the ISO standard.

This relationship is critical for traceability. When a directive is instantiated—for example, an "Access Control Policy"—it must be demonstrably derived from or mapped to a specific clause, such as Clause 9.1.1 (Access control policy). The relational projection of this axiom ensures that every directive instance points unambiguously to the regulatory requirement it fulfills.

The following table instantiates this mapping. The primary key `id` serves as the unique identifier for the mapping instance. Column `x` represents the Directive Class, while column `y` represents the Clause Class. The foreign key constraint on `y` mandates that the Clause Class must correspond to a valid entry in the requirements equivalence table, ensuring referential integrity within the broader ontology.

**Table 4.1: ISO 27001 Clause Subclass Mappings**

| id | x | y |
| :--- | :--- | :--- |
| map_001 | AccessControlPolicy | req_001 |
| map_002 | AssetManagementProcedure | req_002 |
| map_003 | CryptographyStandard | req_003 |
| map_004 | SupplierSecurityPolicy | req_004 |
| map_005 | IncidentMgmtPlan | req_005 |

In the context of the data above, the directive `AccessControlPolicy` is formally defined as satisfying the requirements identified by `req_001`. This structure prevents orphaned directives and ensures that every governance artifact is anchored to a specific regulatory provision.

## 4.2 Attestation and Signatory Authority

Governance frameworks must account for the human element of compliance, specifically the validation of controls through attestation. The axiom `attestation_signed_by` defines a process class (X) that is a subclass of `bfo:0000015` (a Process) and necessitates that the process be signed by a `cco:Person`. This axiom captures the delegation of authority and the non-repudiation of acceptance regarding specific controls or policies.

The instantiation of this axiom transforms abstract compliance activities into auditable events. For example, the process of "Annual Security Review" is meaningless without the explicit sign-off of a designated responsible party. The axiom enforces the ontology's understanding that the process is incomplete and invalid without the `sdg:signedBy` property being populated by a valid Person entity.

The relational schema for this concept, presented in Table 4.2, isolates the process classes that require signature. The primary key `id` uniquely identifies the attestation process type, while `x` denotes the specific Process Class requiring execution. This table acts as a registry of all governance activities that demand human verification.

## 4.3 ISO 27001 Annex A Control Mappings

While clauses define the management system requirements, Annex A provides the detailed catalog of control objectives and controls. The axiom `iso27001_annexa_subclass` maps a Directive Class (X) to a specific Annex A control (Y). This mapping is distinct from the clause mapping in that it deals with the granular implementation of technical or procedural controls (e.g., A.8.2.1, Management of privileged access rights) rather than high-level policy requirements.

This axiom is essential for organizations seeking certification, as auditors must verify that specific Annex A controls are implemented. By defining a Directive Class as a subclass of `cco:DirectiveICE` with the property `sdg:iso27001AnnexA`, the ontology creates a direct line of sight from the operational directive to the specific control objective it satisfies.

Table 4.3 illustrates these mappings. The structure mirrors the clause subclassification, where `id` is the primary key, `x` is the Directive Class, and `y` is the Annex A Control Class. The foreign key constraint on `y` links the control to a requirement specification, ensuring that the Annex A control is properly contextualized within the governance framework.

**Table 4.3: ISO 27001 Annex A Subclass Mappings**

| id | x | y |
| :--- | :--- | :--- |
| annex_001 | PrivilegedAccessProcedure | req_003 |
| annex_002 | MalwareProtectionProtocol | req_001 |
| annex_003 | BackupOperationsPolicy | req_002 |
| annex_004 | SecureDisposalProcess | req_004 |
| annex_005 | LoggingStandard | req_005 |

For instance, the `PrivilegedAccessProcedure` (x) is mapped to the requirement identified by `req_003` (y). This linkage implies that the procedure is the functional realization of the Annex A control objective defined in the referenced requirement.

## 4.4 Requirement Equivalence Specifications

The axiom `requirement_equiv_specifies_target` establishes the equivalence between a Requirement Class (X) and a Directive that specifies a Target (Y) and applies to a Scope (Z). Formally, X is defined as equivalent to the intersection of `cco:DirectiveICE`, the specification of Y, and the application to Z. This axiom serves as the pivot point in the ontology, connecting the abstract requirement to its specific target and scope of application.

This construct allows for precise definition of compliance obligations. A requirement is not merely a string of text but a logical construct asserting that a specific directive applies to a specific target. For example, a requirement might specify that an "Encryption Standard" applies to "Customer Data in Transit." This triple structure (Requirement-Target-Scope) provides the semantic depth necessary for automated compliance queries and gap analysis.

The relational schema for this axiom is presented in Table 4.4. The `id` column serves as the primary key for the requirement instance. Column `x` represents the Requirement Class. Column `y` represents the Target Class (e.g., the specific subclass of a clause or control), and column `z` represents the Scope Class (the entity to which the requirement applies). The foreign key on `y` references the clause subclass table, maintaining the hierarchical integrity of the standard.

**Table 4.4: Requirement Equivalence Specifications**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| req_001 | EncryptionMandate | map_001 | CustomerDatabase |
| req_002 | AssetInventoryRule | map_002 | HardwareInventory |
| req_003 | PrivilegedAccessRule | map_003 | AdminAccounts |
| req_004 | SupplierAuditRule | map_004 | ThirdPartyVendors |
| req_005 | IncidentResponseRule | map_005 | SecurityOperationsCenter |

In this table, `req_001` represents the "EncryptionMandate." It targets the mapping defined in `map_001` (the Access Control Policy mapping) and applies specifically to the `CustomerDatabase`. This granular definition ensures that compliance efforts are directed at the correct assets and processes.

## 4.5 Cardinality Constraints in Attestation

To ensure the validity of governance processes, the ontology must enforce cardinality constraints. The axiom `attestation_min_one_signer` asserts that a Process Class (X) must have a minimum of one (`min 1`) signatory from the class `cco:Person`. This is a stronger constraint than the simple existence of a signatory; it mandates that the process cannot be considered complete or exist in a valid state unless at least one person has executed the signature.

This axiom is particularly relevant for preventing "orphaned" workflows where a process is initiated but never formally approved. It enforces the business rule that delegation of authority is absolute; a process defined by this axiom cannot terminate without human intervention and validation.

Table 4.5 lists the process classes subject to this cardinality constraint. The primary key `id` identifies the constraint instance, and `x` denotes the Process Class. While similar to Table 4.2, this table specifically enforces the *minimum cardinality* rule, distinguishing processes that require *a* signer from those that might allow for batch or automated processing (though in this strict governance framework, human attestation is paramount).

**Table 4.5: Attestation Processes with Minimum Signer Constraints**

| id | x |
| :--- | :--- |
| min_001 | BoardSecurityReview |
| min_002 | DataBreachNotification |
| min_003 | ExceptionApproval |
| min_004 | ContinuityPlanActivation |
| min_005 | ComplianceAuditFinalization |

The processes listed in Table 4.5, such as `BoardSecurityReview`, are critical to the organization's governance posture. The enforcement of the `min 1` constraint ensures that these high-stakes activities cannot bypass the necessary human oversight, thereby maintaining the integrity of the compliance program.
