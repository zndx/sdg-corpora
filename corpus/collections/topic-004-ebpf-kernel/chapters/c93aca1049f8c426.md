# Governance Frameworks: ISO 27001 Directive Mapping and Attestation Protocols

## 1 Scope

This chapter delineates the formal ontological structures governing the integration of ISO/IEC 27001 controls within enterprise information security management systems (ISMS). The provisions herein define the axiomatic relationships between directive classes, specific ISO 27001 clauses, Annex A controls, and the requisite attestation protocols. These specifications apply exclusively to the logical modeling of governance artifacts, ensuring that all directives are traceable to regulatory requirements and that all attestation processes demonstrate verifiable signatory authority. Deviations from these mapping schemas must be explicitly authorized by the Chief Information Security Officer (CISO) and documented in the Governance Exception Register.

## 1 ISO 27001 Clause Subclassification

In the context of the Common Compliance Ontology (cco), specific security directives are frequently modeled as subclasses of the `DirectiveICE` (Information Control Element) class. To maintain regulatory fidelity, it is mandatory that these directives are axiomatically linked to specific clauses within the ISO/IEC 27001 standard. This relationship ensures that a governance artifact is not merely a descriptive policy but a formal implementation of a legal or contractual obligation.

The axiom `iso27001_clause_subclass` posits that a directive class (X) is a subclass of `cco:DirectiveICE` and possesses the property `sdg:iso27001Clause` with a value corresponding to a specific requirement class (Y). This structure enforces a strict hierarchy where the validity of the directive is contingent upon the existence and status of the referenced ISO clause.

For instance, an `AccessControlPolicy` directive must be formally tied to ISO 27001 Clause 9 (Access Control). In this scenario, `AccessControlPolicy` (X) is the directive, and the requirement class referencing Clause 9 serves as the object (Y). This binding facilitates automated audit trails, allowing compliance engines to verify that all organizational directives are anchored to current standard revisions.

## 2 Attestation Signatory Protocols

Governance frameworks must account for the human element of compliance, specifically the authorization and execution of attestation processes. An attestation is formally defined within the ontology as a process that inherits from the Basic Formal Ontology (BFO) process entity (`bfo:0000015`). To be valid, this process must be signed by a natural person acting in a professional capacity.

The axiom `attestation_signed_by` establishes that a class (X), representing the attestation process, is a subclass of `bfo:0000015` and possesses the property `sdg:signedBy` which necessitates the involvement of a `cco:Person`. This axiom prevents the automation of compliance sign-offs without accountable human intervention. It ensures that every assertion of compliance is traceable to an individual with the authority to verify the accuracy of the underlying controls.

Consider the `QuarterlyComplianceReview`. This process is not merely a scheduled task; it is a formal attestation. By applying this axiom, the system mandates that an instance of `QuarterlyComplianceReview` must be associated with a `cco:Person` instance—typically the Compliance Officer or Data Owner—thereby validating the review.

## 3 ISO 27001 Annex A Integration

While clauses provide the high-level requirements for an ISMS, ISO/IEC 27001 Annex A provides a detailed set of control objectives and controls. Governance artifacts often map directly to these specific Annex A controls to demonstrate granular compliance. The axiom `iso27001_annexa_subclass` mirrors the clause subclassification structure but targets the Annex A inventory.

Formally, this axiom states that a directive class (X) is a subclass of `cco:DirectiveICE` and utilizes the object property `sdg:iso27001AnnexA` to reference a specific Annex A control class (Y). This distinction is critical for organizations subject to specific regulatory regimes that mandate explicit adherence to Annex A controls, such as A.9 (Access Control) or A.12 (Operations Security).

For example, a directive governing `CryptographicKeyManagement` would be mapped to Annex A control A.10.1.1. The directive class `CryptoKeyDirective` (X) is linked via the `iso27001AnnexA` property to the class representing A.10.1.1 (Y). This allows the governance framework to generate specific control implementation evidence for external auditors.

## 4 Requirement Specification and Targeting

The core of the governance ontology lies in the precise definition of what a requirement is, what it specifies, and to what entity it applies. The axiom `requirement_equiv_specifies_target` provides a complex equivalence definition that binds these elements together. It asserts that a class (X) is equivalent to the intersection of `cco:DirectiveICE`, the class that specifies some requirement (Y), and the class that applies to some target (Z).

This axiom serves as the "semantic glue" of the framework. It dictates that a valid requirement class must simultaneously be a directive, specify a control (derived from a Clause or Annex A), and be applicable to a specific target (e.g., a system, data set, or personnel group). This tripartite structure eliminates ambiguity in compliance scoping.

For example, consider the requirement `RemoteAccessMFA`. This class is equivalent to being a Directive, specifying the MFA control (Y), and applying to the `RemoteAccessGateway` (Z). Without the "applies to" component (Z), the requirement would be a floating policy without a scope of enforcement. The relational schema implements this by linking the requirement back to the clause/annex definition (via `y`) and explicitly naming the target (via `z`).

## 5 Minimum Signatory Protocols

To further strengthen the integrity of attestation processes, the ontology defines a cardinality constraint regarding signatories. The axiom `attestation_min_one_signer` refines the general attestation definition by stipulating that a process class (X) must have `sdg:signedBy` applied to a minimum of one (`min 1`) `cco:Person`.

This axiom acts as a validation rule within the governance framework. It prevents the creation of "null" or "orphan" attestation processes that have been defined in the system but lack an assigned responsible party. In practice, this ensures that every compliance workflow, from a simple policy review to a complex audit sign-off, has at least one accountable individual designated prior to the workflow's activation.

This constraint is distinct from the simple "signed by" relationship in that it enforces cardinality. While a process *may* have multiple signers (e.g., a Chief Information Officer and a Legal Counsel), this axiom ensures that the lower bound is strictly one. This is critical for automated compliance checks; a workflow engine attempting to transition an attestation to a "Complete" state must verify that the `signedBy` property is populated with at least one valid person instance.
