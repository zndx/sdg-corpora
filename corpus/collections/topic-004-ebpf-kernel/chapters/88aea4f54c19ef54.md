# Chapter 4: Formal Ontology of Governance Directives and Attestation Protocols

## 4.1 Scope and Preamble

This chapter establishes the formal specifications for mapping governance frameworks, specifically ISO/IEC 27001 controls, to a machine-readable ontology. The definitions provided herein are binding for all systems attempting to automate compliance verification, audit reporting, and directive enforcement within the enterprise architecture. The content covers the structural derivation of ISO clauses, the annexation of controls, and the cardinality constraints governing attestation processes. All relational projections are derived deterministically from the cited axioms to ensure referential integrity across the compliance knowledge graph.

## 4.2 ISO 27001 Clause Subclassifications

The integration of statutory requirements into operational directives requires a precise mapping mechanism. Axiom 1 defines the class `iso27001_clause_subclass`, which asserts that a specific directive class (X) is a subclass of `cco:DirectiveICE` and is necessarily associated with a specific ISO 27001 clause (Y). This relationship ensures that any governance artifact instantiated from class X is semantically bound to the regulatory text of clause Y. In practice, this allows the governance framework to trace a technical control directly back to its legal or regulatory mandate without ambiguity.

The following table embodies the axiom `iso27001_clause_subclass`. The primary key is `id`, representing the specific directive instance. The column `y` acts as a foreign key, linking the directive to a requirement specification defined in the equivalence table (Section 4.5), thereby enforcing the constraint that a clause subclass must be validly specified within the broader requirement structure.

## 4.3 Attestation and Signatory Authority

Governance frameworks are ineffective without the verification of execution by authorized agents. Axiom 2, `attestation_signed_by`, formalizes the concept of an attestation process (X) as a subclass of `bfo:0000015` (a Process) which necessitates the involvement of a `cco:Person` via the property `sdg:signedBy`. This axiom captures the legal and procedural requirement that specific actions or documents must be explicitly endorsed by a natural person to be considered valid. It distinguishes automated processes from those requiring human accountability.

The table below represents the relational schema for `attestation_signed_by`. The structure is straightforward, identifying the attestation process instance (`id`) and the class definition (`x`), which implicitly carries the restriction that it must be signed by a person. This serves as a registry for all processes requiring manual sign-off within the system.

## 4.4 ISO 27001 Annex A Control Mapping

While clauses provide the high-level structure of the standard, Annex A provides the detailed control objectives and controls. Axiom 3, `iso27001_annexa_subclass`, extends the `cco:DirectiveICE` class to include directives that are specifically derived from ISO 27001 Annex A controls (Y). This axiom is critical for granular compliance mapping, as it separates general policy directives from those specifically implementing technical or managerial controls listed in the annex. It ensures that the implementation guidance is distinct from the broader clause requirements.

The table `t_iso27001_annexa_subclass` illustrates this mapping. Similar to the clause subclassification, the column `y` references the requirement equivalence table. This enforces the dependency that an Annex A directive is a specific type of requirement that must be formally specified and applied to a target entity.

## 4.5 Requirement Equivalence and Target Specification

The core of the ontology lies in the definition of a requirement as a composite entity. Axiom 4, `requirement_equiv_specifies_target`, defines a class X as equivalent to the intersection of `cco:DirectiveICE`, the specification of a target Y, and the application to a context Z. This equivalence axiom creates a dense, tri-partite relationship: a requirement exists only if it specifies something (Y) and applies to something (Z). This structure prevents the existence of orphaned or abstract requirements that lack actionable context or target.

The table `t_requirement_equiv_specifies_target` is the central hub for these definitions. The foreign key constraint on column `y` references the `t_iso27001_clause_subclass` table, creating a recursive loop where a requirement specifies a clause subclass, which in turn references a requirement. This circularity models the real-world dependency where a specific requirement (the instance) is the implementation of a clause (the type), and the clause is defined by the requirement (the specification).

| :--- | :--- | :--- | :--- |
| req_equiv_001 | AccessControlRequirement | dir_cls_001 | HumanResourceSystem |
| req_equiv_002 | AssetInventoryRequirement | dir_cls_002 | ITAssetDatabase |

| req_equiv_004 | DataCenterAccessRequirement | dir_cls_004 | ServerRoom |

## 4.6 Cardinality Constraints in Attestation Processes

To prevent regulatory gaps, the ontology must enforce quantitative constraints on process execution. Axiom 5, `attestation_min_one_signer`, refines the definition of an attestation process (X) by asserting that it must be signed by a minimum of one (`min 1`) `cco:Person`. This axiom utilizes OWL cardinality restrictions to mandate that no attestation process instance is considered complete or valid unless at least one signatory relationship is fulfilled. It is a guardrail against null or unassigned critical compliance tasks.

The final table, `t_attestation_min_one_signer`, lists the process classes subject to this cardinality constraint. While structurally similar to the general attestation table, the semantic definition of these classes includes the mandatory minimum signer rule, ensuring that any workflow engine instantiating these classes enforces the "at least one" validation rule before allowing process completion.
