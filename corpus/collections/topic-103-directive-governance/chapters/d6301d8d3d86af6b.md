# Chapter 7: Ontological Mapping for Process Traceability and Metrological Compliance

## 7.1 Scope and Preamble

This chapter delineates the procedural axioms governing the integration of process traces, service definitions, and metrological observations within the enterprise governance framework. It establishes the mandatory data structures required to validate the operational status of industrial control systems, ensuring that all process entities are rigorously mapped to their corresponding service contexts and dimensional constraints. The guidelines provided herein are essential for maintaining audit readiness and compliance with the SDG (System Data Governance) interoperability standards. Implementers must adhere strictly to the relational schemas defined to ensure referential integrity across distributed logging infrastructures.

## 7.2 Service Traceability and Operational Binding

### 7.2.1 The Axiom of Trace in Service

The fundamental unit of operational accountability is the `trace_in_service` construct. This axiom formalizes the relationship between a specific process entity (Class X) and the service environment (Class Y) within which it operates. According to the Manchester syntax axiom, Class X is a subclass of `bfo:0000015` (a Process) that participates in the `sdg:inService` relationship with Class Y.

In practical terms, this binding ensures that no process occurs in a vacuum; every operational event must be anchored to a defined service context. This is critical for root cause analysis during compliance audits. If a process fails, the audit trail must immediately identify the service scope to determine if the failure was systemic or localized. The relational projection of this axiom mandates that the service identifier (`y`) must exist as a valid span with a defined status, enforcing a closed-loop verification of service availability.

## 7.3 Span Status Classification

### 7.3.1 The Axiom of Span with Status

While service traceability identifies *where* a process operates, the `span_with_status` axiom defines *how* that operational span is behaving. A span represents a discrete, time-bound segment of a process. This axiom asserts that Class X (a Process) possesses a `sdg:hasSpanStatus` property linking it to Class Y.

The verbalization "{X} is something that has span status {Y}" implies a dynamic state assignment. Statuses are not static attributes but are themselves entities that must be traced back to a service definition, creating a recursive dependency that enhances data fidelity. This structure prevents the use of orphaned status codes; every status must be traceable to a service definition, and every service definition must be associated with a status span. This circular dependency is intentional, designed to enforce mutual existence between the service definition and its current operational state.

### 7.3.2 Status Reporting and Referential Integrity

The implementation of `span_with_status` requires rigorous validation of the foreign key constraints. The status identifier (`y`) must correspond to an existing trace in service. This ensures that status reports are not fabricated but are anchored to legitimate service bindings.

## 7.4 Measurement Equivalence and Dimensional Analysis

### 7.4.1 The Axiom of Measurement Equivalence

To ensure quantitative reliability, the framework employs the `measurement_equiv_with_dim_unit` axiom. This axiom defines a Class X that is equivalent to a `cco:DescriptiveICE` (Information Content Entity) and is characterized by both a dimension (`sdg:hasDimension`) and a unit (`sdg:hasUnit`).

This structure is vital for metrological compliance. It dictates that a measurement is not merely a numerical value but a composite entity comprising the data, the physical dimension being measured (e.g., length, current), and the unit of measure (e.g., meters, amperes). By treating the measurement as an Information Content Entity, the system distinguishes between the physical phenomenon and the recorded data, preserving the semantic layer required for high-fidelity audit logs.

### 7.4.2 Dimensional Constraints and Unit Specification

The relational schema for this axiom links the dimension (`y`) to a valid span status. This constraint implies that the validity of a specific dimensional context is dependent on the status of the operational span. For instance, a measurement of "Voltage" is only valid if the span representing the "Power Circuit" is in an "Active" status.

**Table 7-3: Measurement Definition Registry**
This table embodies the `measurement_equiv_with_dim_unit` axiom. It defines measurements (`x`) by their dimension (`y`) and unit (`z`). The `y` column references `t_span_with_status`, ensuring the dimension is contextually valid.

| id | x (Measurement Entity) | y (Dimension Context) | z (Unit of Measure) |
| :--- | :--- | :--- | :--- |
| `meas-001` | `AirflowVelocityReading` | `sp-status-01` | `MetersPerSecond` |
| `meas-002` | `CoreTemperatureLog` | `sp-status-05` | `Celsius` |
| `meas-003` | `BackupBatteryVoltage` | `sp-status-02` | `VoltsDC` |

In Table 7-3, the `AirflowVelocityReading` is defined within the dimensional context of `sp-status-01` (the active ventilation cycle). The unit is strictly defined as `MetersPerSecond`. This structure prevents ambiguous data entry, such as recording velocity in "FeetPerMinute" without explicitly defining a new measurement entity with the corresponding unit class.

## 7.5 Hierarchical Span Parentage

### 7.5.1 The Axiom of Span with Parent

Complex industrial processes are rarely monolithic; they consist of nested sub-routines and dependent operations. The `span_with_parent` axiom captures this hierarchy by stating that Class X (a Process) has a parent span, Class Y.

This relationship is crucial for impact analysis. If a parent span fails or is suspended, the governance framework must immediately identify all child spans that require termination or suspension. The axiom enforces a tree-like structure where the root nodes are service traces, and the branches are operational spans. The foreign key constraint requires that the parent span (`y`) must be a valid trace in service, ensuring that all hierarchy ultimately resolves to a defined service boundary.
