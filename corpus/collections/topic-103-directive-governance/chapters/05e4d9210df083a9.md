# Chapter 4: Operational Traceability and Status Monitoring in Industrial Control Systems

## 4.1 Scope and Compliance Framework

This chapter delineates the formal ontological structures required for establishing operational traceability and status monitoring within industrial ventilation control units. It provides the axiomatic definitions necessary to map hardware entities to service processes, define hierarchical span relationships, and record measurement data with precise dimensional attribution. Adherence to these protocols is mandated for compliance with IEC 61508 functional safety standards and ensures that all audit trails maintain referential integrity across the control system lifecycle. The following sections define the core data entities and their interrelationships, providing the necessary schema to implement a robust governance framework for safety-critical ventilation infrastructure.

## 4.2 Service Traceability (Axiom: trace_in_service)

### 4.2.1 Conceptual Definition

In the context of industrial automation and safety compliance, the relationship between a physical controller and the process it manages must be rigorously defined. The axiom `trace_in_service` establishes that a specific entity (Class X) is a subclass of a process (`bfo:0000015`) and is actively operating within the context of a service (Class Y). This relationship is not merely associative; it is a definitive assertion of operational responsibility. For a control unit to be considered compliant, it must be explicitly linked to the service process it governs. This linkage serves as the primary anchor for all subsequent status monitoring and measurement activities, ensuring that every signal and state change can be traced back to a defined operational scope.

### 4.2.2 Implementation and Evidence

The implementation of `trace_in_service` requires the generation of unique trace identifiers that bind the hardware instance to the service process. This binding is critical during audit scenarios where the operational status of a specific Control Unit (CU) must be verified against the active ventilation process. For instance, a 24VDC control unit designated for fire ventilation must be traceable to the "Fire Ventilation Service" process. Without this explicit link, the system fails to provide the necessary evidence of functional assignment, rendering the audit trail incomplete.

The following table illustrates the instantiation of the `trace_in_service` axiom. It demonstrates how specific control units (X) are mapped to their respective service processes (Y). The `id` column serves as the primary key for this trace, while the `y` column acts as a foreign key reference to the status span defined in the subsequent section, establishing a bidirectional verification loop.

**Table 4.1: Operational Traceability Mapping (t_trace_in_service)**

| id | x (Control Unit) | y (Service Process) |
| :--- | :--- | :--- |
| TRACE-001 | SV_24V-24A_FireCU | SPAN-STAT-001 |
| TRACE-002 | SV_24V-8A_ComfortCU | SPAN-STAT-002 |
| TRACE-003 | SV_48V-32A_IndustrialCU | SPAN-STAT-003 |
| TRACE-004 | SV_24V-30A_HighCapacityCU | SPAN-STAT-004 |

*Note: The `y` values (SPAN-STAT-*) reference the status span identifiers defined in Section 4.3, ensuring referential integrity.*

### 4.2.3 Compliance Verification

During a compliance audit, inspectors must verify that for every active control unit listed in column `x`, a corresponding valid service process exists in column `y`. Any orphaned trace—where a control unit is listed but the service process is null or invalid—constitutes a critical non-conformance. This structure ensures that hardware deployment is always justified by an active service requirement, preventing "zombie" assets from consuming resources or posing unmonitored risks.

## 4.3 Span Status Definition (Axiom: span_with_status)

### 4.3.1 Conceptual Definition

While `trace_in_service` establishes the operational context, the axiom `span_with_status` defines the state of that operation over a specific temporal span. A span (Class X) is defined as a process that possesses a specific status attribute (Class Y). In this ontology, the status is not treated as a simple string value but as a distinct entity that references the originating service trace. This recursive structure creates a robust dependency where the status of a process is validated by the service trace, and the service trace is, in turn, contextualized by the status span. This mutual dependency prevents the dissociation of a process state from its operational origin.

### 4.3.2 Status Span Logic

The status span represents a continuous interval during which the process maintains a specific state, such as "Active," "Standby," or "Fault." By formalizing this as a class relationship, the system allows for complex querying of state histories. For example, a "Fire Ventilation" process may have a status span of "Active" that is strictly bound to the trace of the fire control unit. This binding ensures that status changes are not arbitrary events but are recorded as distinct, traceable entities within the system's history log.

The table below details the instantiation of status spans. Note the referential integrity constraint: the `y` column must reference a valid `id` from the `t_trace_in_service` table. This enforces the rule that a status cannot exist independently of the service trace it describes.

**Table 4.2: Status Span Registry (t_span_with_status)**

| id | x (Process Span) | y (Service Trace) |
| :--- | :--- | :--- |
| SPAN-STAT-001 | FireVent_Active_Span_01 | TRACE-001 |
| SPAN-STAT-002 | ComfortVent_Standby_Span_01 | TRACE-002 |
| SPAN-STAT-003 | IndustrialVent_Operational_Span | TRACE-003 |
| SPAN-STAT-004 | HighVent_Cyclic_Mode_Span | TRACE-004 |

*Note: The `y` values (TRACE-*) reference the trace identifiers defined in Table 4.1.*

### 4.3.3 Audit Implications

For governance purposes, the `span_with_status` table provides the evidence required to reconstruct the timeline of system operations. Auditors can query this table to determine the exact duration of specific operational states. Furthermore, the foreign key constraint ensures that every status span is attributable to a specific, authorized hardware trace. This eliminates the risk of "ghost" statuses—system states that appear in logs without a corresponding hardware action—which are a common red flag in safety-critical system audits.

## 4.4 Measurement Dimensions and Units (Axiom: measurement_equiv_with_dim_unit)

### 4.3.1 Conceptual Definition

The collection of telemetry data is governed by the axiom `measurement_equiv_with_dim_unit`. This axiom defines a measurement (Class X) as being equivalent to a Descriptive Information Content Entity (`cco:DescriptiveICE`) that possesses both a specific dimension (Class Y) and a unit (Class Z). This tripartite definition is essential for standardizing data across heterogeneous systems. It prevents ambiguity by ensuring that every numerical value recorded by the system is explicitly typed with its physical dimension (e.g., Electric Current, Voltage) and its unit (e.g., Ampere, Volt).

### 4.3.2 Dimensional Integrity

In complex control systems, data ambiguity is a significant source of error. A value of "24" is meaningless without the context of "Volts" or "Amperes." This axiom enforces semantic typing at the data entry level. The measurement entity (X) is inextricably linked to the status span (Y) via a foreign key, ensuring that measurements are always associated with the specific operational state during which they were recorded. The unit (Z) provides the scale necessary for interpretation and regulatory reporting.

The following table demonstrates the recording of measurements within the system. Each row represents a specific data point, its dimensional classification, and the unit of measure. The `y` column links the measurement to the relevant status span, anchoring the data to a specific time and process state.

**Table 4.3: Measurement Log with Dimensional Attributes (t_measurement_equiv_with_dim_unit)**

| id | x (Measurement) | y (Status Span) | z (Unit) |
| :--- | :--- | :--- | :--- |
| MEAS-001 | Current_Load_Reading_01 | SPAN-STAT-001 | Ampere |
| MEAS-002 | Voltage_Input_Reading_01 | SPAN-STAT-001 | Volt |
| MEAS-003 | Current_Load_Reading_02 | SPAN-STAT-002 | Ampere |
| MEAS-004 | Frequency_Output_Reading | SPAN-STAT-003 | Hertz |
| MEAS-005 | Temperature_Sensor_Reading | SPAN-STAT-004 | Celsius |

*Note: The `y` values reference status spans from Table 4.2, ensuring measurements are contextually bound.*

### 4.3.3 Regulatory Reporting

When generating compliance reports, such as those required for safety integrity level (SIL) verification, the system must extract data based on these dimensional attributes. The structure provided by this axiom allows for automated queries such as "Retrieve all Ampere measurements recorded during Fire Ventilation Active spans." This capability is crucial for demonstrating that the system operated within safe parameters during critical events. The explicit definition of units (`z`) further ensures that data aggregation is performed correctly, preventing unit conversion errors that could compromise safety analysis.

## 4.5 Hierarchical Span Relationships (Axiom: span_with_parent)

### 4.5.1 Conceptual Definition

Complex industrial processes are rarely monolithic; they are composed of sub-processes and nested operations. The axiom `span_with_parent` defines a hierarchical relationship where a specific span (Class X) is a subclass of a process and possesses a parent span (Class Y). This structure allows for the decomposition of complex service traces into manageable, auditable components. For example, a "Fire Ventilation" service trace may consist of parent spans such as "System Initialization," "Actuator Activation," and "Status Monitoring."

### 4.5.2 Hierarchical Decomposition

The parent-child relationship defined in this axiom is fundamental to root-cause analysis and system diagnostics. By linking a child span to a parent trace, the system creates a navigable tree of operational events. If a failure occurs in a sub-process, the hierarchy allows engineers to trace the fault up to the main service trace to understand the broader context. Similarly, during an audit, the hierarchy allows for the verification of specific sub-routines within the larger operational workflow.

The table below defines the hierarchical structure of operational spans. The `x` column represents the child span (the specific sub-process), while the `y` column references the parent service trace. This relationship ensures that every operational activity is a recognized component of a higher-level authorized service.

**Table 4.4: Hierarchical Span Dependency (t_span_with_parent)**

| id | x (Child Span) | y (Parent Trace) |
| :--- | :--- | :--- |
| HIER-001 | Actuator_Output_Check | TRACE-001 |
| HIER-002 | Fire_Switch_Monitor | TRACE-001 |
| HIER-003 | Comfort_Mode_Calibration | TRACE-002 |
| HIER-004 | Load_Balancing_Check | TRACE-003 |
| HIER-005 | Emergency_Purge_Sequence | TRACE-001 |

*Note: The `y` values reference the primary trace identifiers from Table 4.1.*

### 4.5.3 Governance and Oversight

From a governance perspective, the `span_with_parent` table provides the structural map of the system's logic. It enables oversight bodies to verify that the control unit's firmware executes the correct sequence of sub-processes. For instance, the "Emergency_Purge_Sequence" (HIER-005) is correctly validated as a child of the "Fire Ventilation" trace (TRACE-001). If this sequence were incorrectly linked to a "Comfort Ventilation" trace, it would indicate a severe logic error or configuration drift, triggering an immediate compliance alert. This hierarchical mapping is therefore a critical control in maintaining the logical integrity of the safety system.
