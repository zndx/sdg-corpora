# Chapter 4: Ontological Formalization of Process Traces and Service States in Industrial Control Systems

## 4.1 Preamble and Scope

This chapter establishes the formal ontological framework required for the precise documentation and auditing of industrial control processes. It addresses the structural necessity of defining process traces, their operational states, and the hierarchical relationships that govern complex system behaviors. The content herein is intended for systems architects, compliance officers, and data engineers responsible for implementing governance frameworks within automated environments. The definitions provided align with the BFO (Basic Formal Ontology) upper-level ontology and are instantiated through relational schemas designed to ensure referential integrity and auditability. Readers are expected to apply these axioms to map real-world operational data—such as ventilation control sequences or power regulation states—into a rigorously defined knowledge graph.

## 4.2 Trace in Service

### 4.2.1 Conceptual Definition

The first foundational axiom required for robust system modeling is the definition of a process trace relative to a specific service context. In formal ontology, a *Trace in Service* is defined as a class of entities (X) that are subclasses of `bfo:0000015` (Process) and participate in the `sdg:inService` relationship with a target class (Y). This relationship asserts that the process is not merely occurring in a vacuum but is operationally bound to a specific service function or infrastructure component.

In the context of industrial auditing, this distinction is critical. A generic process (e.g., "voltage fluctuation") becomes auditable only when it is bound to a service (e.g., "Fire Ventilation Control Unit"). This binding allows for the attribution of responsibility, the allocation of resources, and the application of service-level agreements (SLAs). The axiom ensures that every active process trace recorded in the system logs can be traced back to the service context that necessitates its execution.

### 4.2.2 Relational Implementation

The relational projection of this axiom creates a dependency structure where the existence of a trace is validated by its association with a service span. The table `t_trace_in_service` serves as the primary registry for these bindings. The primary key is the unique identifier of the trace instance, while the foreign key constraint enforces that the referenced service (`y`) must exist as a valid span with a defined status.

This structure prevents the logging of "orphan" processes—events that occur without a valid service context. In compliance scenarios, such as the logging of fire safety events, this ensures that every activation of a ventilation actuator is explicitly tied to a valid, active control service.

### 4.2.3 Compliance Verification

When auditing an installation, such as the SV 24V-24A Control Unit for Fire Ventilation, the verifier must confirm that entries in the event log correspond to entries in `t_trace_in_service`. For instance, if the log indicates a "Fire Ventilation" process initiated at 14:00 hours, there must be a corresponding row where `x` represents that process and `y` references the active service span of the control unit. This linkage is the first step in establishing a chain of custody for operational data.

## 4.3 Span with Status

### 4.3.1 Conceptual Definition

While the previous section defined the binding of a process to a service, it did not define the state of that service. The *Span with Status* axiom provides the necessary state attribution. Formally, this axiom asserts that a class (X), which is a subclass of `bfo:0000015` (Process), possesses a `sdg:hasSpanStatus` relationship with a status class (Y).

This axiom introduces the concept of a "Span"—a temporal segment of the process characterized by a specific condition. Statuses might include "Active," "Idle," "Fault," or "Maintenance." In a regulatory framework, the status span is the unit of analysis for determining system availability and reliability. It is insufficient to know that a service exists; the governance framework requires continuous knowledge of its state to ensure that safety-critical systems (e.g., fire ventilation) are not in a "Fault" state when called upon.

### 4.3.2 Relational Implementation and Circular Dependency

The schema for `t_span_with_status` exhibits a circular dependency with `t_trace_in_service`. This is a deliberate modeling choice reflecting the real-world interdependence of process and state: a process trace exists *in service* of a span, while that span derives its operational meaning from the status of the process.

The table structure requires that the status attribute (`y`) must reference a valid trace ID. This enforces the rule that a status cannot exist in isolation; it must be the status of *something* that is actively in service. This bidirectional referencing creates a robust lock-and-key mechanism in the database, ensuring that process logs and status monitors are perfectly synchronized.

### 4.3.3 Operational Example

Consider a scheduled maintenance window defined in a public notice or meeting minutes. During this window, the status of the "Comfort Ventilation" service must transition to "Maintenance." In the database, this is represented by updating the row in `t_span_with_status` where `id` is `SPN-STAT-200`. The `x` value remains the process span, but the `y` value (the trace reference) might point to a specific maintenance process trace (e.g., `TRC-2024-B`), effectively re-binding the service to a maintenance workflow. This formalization allows auditors to query the system for all spans currently in a "Critical" status and generate compliance reports automatically.

## 4.4 Measurement Equivalence with Dimension and Unit

### 4.4.1 Conceptual Definition

The third axiom addresses the quantification of process variables. In technical systems, raw data is meaningless without standardized context. The *Measurement Equivalence with Dimension and Unit* axiom defines a class (X) that is equivalent to `cco:DescriptiveICE` (Descriptive Information Content Entity) and possesses both a dimension (Y) and a unit (Z).

This axiom formalizes the observation that a measurement is a compound entity. It is not simply a number; it is a value (Information Content Entity) constrained by a physical dimension (e.g., Electric Current, Pressure) and a standardized unit (e.g., Amperes, Pascals). This distinction is vital for interoperability between different subsystems (e.g., a 24VDC ventilation unit communicating with a 48VDC master controller). By explicitly typing the dimension and unit, the system prevents category errors, such as comparing a voltage reading to a pressure reading.

### 4.4.2 Relational Implementation

The table `t_measurement_equiv_with_dim_unit` serves as the catalog for these definitions. Unlike the previous tables, which tracked dynamic process relationships, this table often acts as a registry of valid measurement types or a log of specific observations. The schema enforces that every measurement must be associated with a valid span status (via the foreign key to `t_span_with_status`). This ensures that measurements are always anchored to the operational state of the system—you cannot have a valid voltage reading for a process span that does not exist or has no status.

### 4.4.3 Data Integrity and Audit

In an audit scenario, this table allows for the verification of sensor calibration and data validity. If a control unit specifies a max load of 32A, the auditor can query `t_measurement_equiv_with_dim_unit` for all entries where `x` involves current load and `z` is `Unit_Ampere`. By joining with `t_span_with_status`, the auditor can isolate these readings to specific time spans (e.g., "Fire System Operational"). This provides a granular view of system performance under load, verifying that the `Process_FireVentilation_Main` remained within the `24A/30A/32A` constraints specified in the technical documentation.

## 4.5 Span with Parent

### 4.5.1 Conceptual Definition

Complex industrial processes are rarely monolithic; they are composed of smaller, interacting sub-processes. The *Span with Parent* axiom defines the hierarchical structure of these processes. It asserts that a class (X), a subclass of `bfo:0000015` (Process), has a parent span (Y) via the `sdg:hasParentSpan` relationship.

This hierarchy is essential for root-cause analysis and impact assessment. If a parent process (e.g., "Ventilation Group 1") fails, the axiom dictates that all child spans (e.g., "Actuator 1 Output," "Actuator 2 Output") are implicitly affected. Conversely, a fault in a child span can be traced up to the parent to determine which broader service functionality is degraded. This structure mirrors the physical grouping of devices, such as the grouping of "2 fire ventilation groups" and "2 comfort groups" found in modern control units.

### 4.5.2 Relational Implementation

The table `t_span_with_parent` implements this hierarchy. The foreign key constraint requires that the parent span (`y`) must be a valid trace in service (`t_trace_in_service`). This structural constraint enforces that a child process cannot exist unless it is part of a valid, active service trace. This prevents the creation of "zombie" processes—sub-routines that are running but are not attached to a legitimate parent service.

### 4.5.3 Governance and Impact Analysis

The utility of this hierarchy is most visible during incident response. Suppose an error is detected in `Span_Actuator_Group1_Fire`. By querying `t_span_with_parent`, the system immediately identifies `TRC-2024-A` (Process_FireVentilation_Main) as the parent. The governance framework can then trigger protocols specific to the failure of the main fire ventilation process, rather than treating it as an isolated component fault. Furthermore, this structure supports the configuration of complex control units where multiple groups (e.g., 2 fire groups, 2 comfort groups) must be managed independently yet reported as part of a unified system status.
