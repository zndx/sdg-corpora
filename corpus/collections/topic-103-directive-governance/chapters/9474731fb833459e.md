# Chapter 4: Distributed Tracing Ontology and Compliance Metrics

## 4.1 Scope and Preamble

This chapter defines the formal ontology governing the capture, storage, and reporting of distributed tracing data within regulated high-availability environments. The specifications herein detail the structural relationships between trace entities, service contexts, and dimensional measurements. Adherence to these axioms is mandatory for systems requiring compliance with the System Observability Governance Framework (SOGF). The definitions provided ensure that all generated telemetry data maintains referential integrity and semantic consistency across heterogeneous infrastructure components. Implementers must map internal instrumentation outputs to the relational schemas defined in the subsequent sections to facilitate automated auditing and forensic analysis.

## 4.2 Service Trace Context

### 4.2.1 Conceptual Definition

The foundational unit of observability in a distributed system is the Trace, formally defined as an instance of a process occurring within a specific service boundary. According to the axiom `trace_in_service`, a Trace entity (X) is ontologically a subclass of `bfo:0000015` (a process) that exists *in service* of a Service entity (Y). This relationship establishes the functional context of the trace; a trace cannot exist in a vacuum but must be anchored to the service operation it observes.

In compliance terms, this linkage ensures that every operational workflow recorded by the system is attributable to a defined service component. This is critical for governance, as it allows auditors to map performance degradation or security anomalies directly to specific microservices or functional modules. The "in service" relationship is not merely associative but structural; it enforces that the lifecycle of the trace is bound to the lifecycle of the service context it monitors.

### 4.2.2 Relational Implementation

The implementation of this axiom requires the population of the `t_trace_in_service` table. This table enforces a strict foreign key constraint linking the service context (`y`) to a span status entity, ensuring that the service definition is grounded in an active operational state. The primary key (`id`) serves as the unique identifier for the trace instance, utilized across all downstream telemetry tables.

The following table illustrates the mapping of specific trace instances to their respective service contexts. Note that the `y` column (Service) references a valid span status identifier, satisfying the schema's referential integrity constraints.

## 4.3 Span Status Enumeration

### 4.3.1 Conceptual Definition

While a trace provides the global context for a distributed transaction, the constituent units of work are known as Spans. The axiom `span_with_status` posits that a Span entity (X) is a process (`bfo:0000015`) that *has span status* (Y). The status attribute is a mandatory descriptor of the span's termination state, typically categorizing the outcome as successful, failed, or in progress.

From a governance perspective, the status attribute is the primary indicator of system health and reliability. It allows for the automated calculation of Service Level Objectives (SLOs) and error budgets. The ontology requires that the status itself be a first-class entity linked back to the broader trace context. This circular dependency—where a trace is in service of a status-bearing entity, and a status is linked to a trace—creates a robust chain of custody for telemetry data, preventing orphaned records that could obscure system failures during an audit.

### 4.3.2 Relational Implementation

The `t_span_with_status` table materializes this relationship. The schema dictates that the status entity (`y`) must reference a valid trace identifier (`t_trace_in_service`). This constraint ensures that every status report is explicitly associated with a parent trace, enforcing the hierarchy of the telemetry model.

The table below provides examples of span entities linked to their respective status codes and parent traces. This data structure is essential for root cause analysis, as it isolates specific failures (Status) within the broader context of a transaction (Trace).

| :--- | :--- | :--- |

The `x` column defines the specific unit of work, while `y` represents the status entity which, per the schema constraints, acts as a foreign key to the `t_trace_in_service` table. This linkage ensures that every span is contextually bound to a specific trace instance.*

## 4.4 Dimensional Measurement Equivalence

### 4.4.1 Conceptual Definition

Quantitative observability relies on the precise definition of measurements. The axiom `measurement_equiv_with_dim_unit` establishes that a Measurement entity (X) is equivalent to a `cco:DescriptiveICE` (Information Content Entity) that possesses a specific Dimension (Y) and Unit (Z). This equivalence class ensures that all recorded metrics are semantically typed; a numeric value is not merely a raw integer but a quantified assertion about a specific property of the system.

In this framework, a measurement is valid only if it declares both what is being measured (Dimension) and the scale of measurement (Unit). This distinction is vital for regulatory reporting, where ambiguity in metrics can lead to non-compliance. For instance, reporting latency without specifying the unit (milliseconds vs. microseconds) renders the data analytically useless and potentially misleading. The ontology enforces this by making both `hasDimension` and `hasUnit` mandatory slots.

### 4.4.2 Relational Implementation

The `t_measurement_equiv_with_dim_unit` table captures these constraints. The schema requires that the Dimension (`y`) references a valid span status, grounding the measurement in the operational state of a specific span. The Unit (`z`) is a non-nullable string literal enforcing the definition of the scale.

The following table details measurements associated with the spans defined in the previous section. It illustrates how raw telemetry is converted into structured, compliant data points.

| :--- | :--- | :--- | :--- |
| MEAS-5001 | DbConnectionLatency | SPN-STAT-1001 | Millisecond |
| MEAS-5002 | TokenValidationTime | SPN-STAT-1002 | Microsecond |

The foreign key constraint on `y` ensures that measurements are strictly tied to the status of specific spans.*

## 4.5 Hierarchical Span Parentage

### 4.5.1 Conceptual Definition

Distributed transactions are rarely linear; they consist of nested operations and parallel executions. The axiom `span_with_parent` defines that a Span entity (X) *has parent span* (Y). This parent-child relationship constructs the trace tree, representing the causal chain of events within the system. A child span cannot exist without a parent, mirroring the dependency graph of the underlying software architecture.

For compliance officers, this hierarchy is necessary for reconstructing the sequence of events leading up to an incident. It enables the visualization of call stacks across service boundaries and identifies the precise point of failure (e.g., a database timeout within a payment processing workflow). The ontology treats the parent span as a distinct entity, allowing for the attribution of aggregate metrics (such as total trace duration) to the root span while preserving the granular details of leaf spans.

### 4.5.2 Relational Implementation

The `t_span_with_parent` table formalizes this hierarchy. The schema mandates that the parent span (`y`) references a valid trace identifier (`t_trace_in_service`). This design choice implies that the ultimate parentage of any span is traceable back to the root service context, reinforcing the "in service" relationship defined in Section 4.2.
