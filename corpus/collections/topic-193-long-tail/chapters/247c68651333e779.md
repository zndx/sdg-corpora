# Chapter 4 — Governance Directives and Evidence Structures

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures underpinning the Enterprise Governance Framework (EGF), specifically focusing on the definition, classification, and relational properties of directive information content entities. The provisions herein establish the necessary logical constraints for implementing automated compliance checks within the Governance Audit System (GAS). All definitions are derived from the BFO (Basic Formal Ontology) upper-level structure, utilizing the `cco:DirectiveICE` and `cco:DescriptiveICE` classes to model governance artifacts. The following sections provide a rigorous examination of these concepts, supported by relational data schemas that instantiate the axiomatic constraints required for high-fidelity record-keeping and regulatory reporting.

## 4.2 Basic Directive Entities

### 4.2.1 Conceptual Definition

Per the foundational axioms of the framework, a Directive Information Content Entity (`cco:DirectiveICE`) is defined as any information content entity that prescribes some course of action or modality of behavior. This is distinct from descriptive information, which merely characterizes a state of affairs. In the context of the EGF, all policies, mandates, and procedural requirements are classified as subclasses of `cco:DirectiveICE`. The basic axiom asserts that any entity designated as a Policy (`X`) inherently possesses the characteristics of a Directive.

### 4.2.2 Implementation and Data Structure

The implementation of basic directives within the relational database is governed by the `policy_basic` template. This structure serves as the registry for all governance directives that do not require complex property assertions (such as ownership or scope restrictions) at the primary level of definition. The primary key (`id`) ensures referential integrity, while the `x` column denotes the specific class or instance name of the directive.

The following table illustrates the instantiation of basic directives currently active within the 2024 compliance cycle. The primary key (`id`) serves as the unique identifier for audit trails.

### 4.2.3 Compliance Verification

Auditors must verify that for every entry in `t_policy_basic`, a corresponding textual artifact exists in the Document Management System (DMS). The `id` field must match the DMS metadata tag exactly. Discrepancies between the `x` value (the directive name) and the actual document title constitute a Level 1 finding.

## 4.3 Artifact Governance Scope

### 4.3.1 Conceptual Definition

Certain directives within the framework are designed to govern only specific types of entities. The axiom `policy_only_governs_artifacts` restricts the scope of a directive (`X`) such that it may only govern entities classified as Artifacts (`cco:Artifact`). An Artifact, in this ontology, refers to a physical or digital object produced by some process. This constraint prevents policies from being erroneously applied to abstract concepts or persons where they are not applicable, ensuring legal and operational precision.

### 4.3.2 Implementation and Data Structure

The relational schema for this concept, `t_policy_only_governs_artifacts`, enforces this restriction at the data level. While the schema itself is structurally similar to the basic directive table, the semantic context of the `x` value implies a universal restriction on the `governsScope` object property. The system validates that any entity linked to this policy via a governance relationship is indeed a member of the `cco:Artifact` class.

The table below lists policies that are strictly constrained to govern artifacts. These directives typically pertain to the handling, storage, or disposition of physical media or digital files.

**Table 4.2: Artifact-Specific Governance Policies (t_policy_only_governs_artifacts)**

| id | x |
| :--- | :--- |
| ART-GOV-101 | Physical Media Destruction |
| ART-GOV-102 | Digital Log Archiving |
| ART-GOV-103 | Hardware Asset Disposal |
| ART-GOV-104 | Source Code Versioning |

### 4.3.3 Audit Implications

When reviewing `t_policy_only_governs_artifacts`, the auditor must confirm that the governance scope has not been improperly expanded. For instance, the policy "Physical Media Destruction" (ART-GOV-101) must not be cited as the authority for personnel termination procedures, as a Person is not an Artifact. The ontology constraint `only cco:Artifact` provides a logical fail-safe against such category errors in automated reasoning engines.

## 4.4 Control Ownership and Accountability

### 4.4.1 Conceptual Definition

To ensure operational accountability, the framework mandates that specific Control directives must have an assigned Owner. The axiom `control_min_one_owner` stipulates that any entity classified as a Control (`X`) must possess the property `sdg:hasOwner` with a minimum cardinality of 1, referencing a `cco:Person`. This axiom bridges the gap between abstract governance directives and human responsibility, ensuring that no control exists in a vacuum without explicit stewardship.

### 4.4.2 Implementation and Data Structure

The `t_control_min_one_owner` table catalogs these control directives. While the relational schema provided captures the Control entity (`x`) and its unique identifier (`id`), the enforcement of the ownership constraint is managed through a validation layer that queries the `cco:Person` registry. The presence of a row in this table asserts that the ownership constraint has been satisfied and linked to a valid personnel record.

The following table details the controls currently subject to ownership mandates. Each entry represents a specific directive requiring active human stewardship.

| :--- | :--- |

### 4.4.3 Verification Protocol

During the quarterly audit, the system generates a report for each `id` in `t_control_min_one_owner`, listing the associated `cco:Person` via the `sdg:hasOwner` property. If the query returns a null set or zero owners for any `x`, the control is flagged as "Orphaned." Orphaned controls represent a critical governance failure and must be remediated by assigning a responsible individual immediately.

## 4.5 Enforcement Mechanisms

### 4.5.1 Conceptual Definition

The efficacy of a directive is contingent upon its enforcement. The axiom `policy_min_one_enforcer` formalizes this by asserting that a Policy (`X`) must be enforced by a minimum of one Enforcer (`Y`). In this specific ontological model, the Enforcer slot is projected to a `Claim` entity (specifically, a `cco:DescriptiveICE`). This creates a dependency structure where the validity of the policy is operationalized through a specific claim of enforcement. This recursive linkage ensures that policies are not merely aspirational statements but are anchored to enforceable assertions within the system.

### 4.5.2 Implementation and Data Structure

The table `t_policy_min_one_enforcer` embodies this relationship. The primary key is `id`, representing the Policy. The column `x` holds the Policy entity, while the column `y` holds the ID of the Enforcing Claim. Critically, the schema includes a foreign key constraint linking `y` to the `t_claim_min_one_evidence` table. This enforces referential integrity: a policy cannot claim to be enforced by a non-existent claim.

The data below demonstrates the mapping of Policies to their respective Enforcing Claims. Note that the `y` values correspond to claim identifiers which will be detailed in the subsequent section.

**Table 4.4: Policy-to-Enforcer Mapping (t_policy_min_one_enforcer)**

| id | x | y |
| :--- | :--- | :--- |
| POL-ENF-01 | Password Complexity Mandate | CL-EV-01 |
| POL-ENF-02 | Secure Data Transmission | CL-EV-02 |
| POL-ENF-03 | Audit Log Retention | CL-EV-03 |

### 4.5.2 Structural Dependency

The foreign key constraint (`FOREIGN KEY (y) REFERENCES t_claim_min_one_evidence(id)`) necessitates that for every row in this table, the `y` value must exist as a primary key in the claims table. This structure prevents the creation of circular or dangling enforcement references. It ensures that the "Enforcer" is a valid, registered descriptive information content entity within the governance framework.

## 4.6 Evidence and Claim Support

### 4.6.1 Conceptual Definition

The final component of the governance loop is the evidentiary support for the enforcement claims. The axiom `claim_min_one_evidence` defines a Claim (`X`) as a Descriptive Information Content Entity (`cco:DescriptiveICE`) that must be supported by a minimum of one Evidence item (`Y`). In this schema, the Evidence slot (`Y`) is projected back to the Policy entity (`cco:DirectiveICE`). This creates a mutually reinforcing structure: a Policy is enforced by a Claim, and that Claim is supported by the Policy (or a directive derived from it). This circular dependency models a closed-loop verification system where enforcement claims are grounded in the very directives they authorize.

### 4.6.2 Implementation and Data Structure

The table `t_claim_min_one_evidence` records these claims. The `id` is the Claim ID, `x` is the Claim entity, and `y` is the Evidence ID. The schema mandates that `y` references a valid Policy ID via a foreign key to `t_policy_min_one_enforcer`. This completes the relational circuit: Policy -> Enforces -> Claim -> Supported By -> Policy.

The table below lists the claims that serve as enforcers for the policies listed in Section 4.5. The `y` column references the originating policy, creating the evidentiary link.

### 4.6.3 Relational Integrity and Audit

The relationship between `t_policy_min_one_enforcer` and `t_claim_min_one_evidence` represents a complex governance axiom. The foreign key constraints ensure that:
1.  No Policy can exist without a valid Claim enforcing it (`t_policy_min_one_enforcer.y` is NOT NULL).
2.  No Claim can exist without valid Evidence supporting it (`t_claim_min_one_evidence.y` is NOT NULL).
3.  The Evidence for a Claim must be a registered Policy.
