# Chapter 7: Ontological Foundations of Governance Artifacts and Directives

## 7.1 Scope and Preamble

This chapter establishes the formal ontological structures necessary for the rigorous classification and management of governance artifacts within a regulated environment. The definitions provided herein align with the Information Content Entity (ICE) framework, specifically addressing the intersection of descriptive data, prescriptive directives, and composite artifacts. The purpose of this section is to provide systems architects and compliance officers with a deterministic schema for mapping regulatory requirements to physical and digital documentation. The logical constraints and relational mappings detailed in the subsequent sections are intended to ensure referential integrity across audit databases and metadata repositories.

## 7.2 Descriptive Information Content Entities

### 7.2.1 Conceptual Definition

In the context of information governance, it is critical to distinguish between prescriptive statements, which mandate action, and descriptive statements, which characterize the state of the world. A Descriptive Information Content Entity (DescriptiveICE) is defined axiomatically as a class of entity that is about some subject matter but does not inherently direct behavior. This distinction is foundational for semantic search and automated compliance filtering. By classifying an entity as a DescriptiveICE, the system asserts that its primary function is to represent data, record events, or model reality, rather than to constrain operational parameters.

### 7.2.2 Axiomatic Structure

The axiom governing this classification is expressed as `SubClassOf: cco:DescriptiveICE`. This implies that any instance assigned to this class inherits the properties of the parent Information Content Entity while being semantically typed as "descriptive." This typing is crucial for downstream processing, such as generating audit reports where only descriptive evidence (logs, records, inventories) is required, distinct from policy documents.

Note that the primary key (`id`) serves as the unique identifier for the class definition within the ontology registry.

This formalization allows automated reasoning engines to infer that any instance of `SystemConfigurationRecord` possesses the properties of a descriptive entity, enabling valid queries for "all descriptive records related to system state" without manual keyword matching.

## 7.3 Artifacts and Component Structure

### 7.3.1 Conceptual Definition

Governance frameworks frequently deal with complex documents that serve as containers for regulatory requirements. An Artifact, in this ontology, is not merely a file but a discrete, persisting entity that may possess a mereological structure (i.e., a part-whole relationship). The axiom `equiv_intersect_artifact_with_part` defines a specific class of Artifact that necessarily has a part. This is not a contingent property—it is a defining characteristic. If an entity is a member of this class, it must possess at least one component part.

### 7.3.2 Axiomatic Structure and Relational Integrity

The axiom is formalized as `EquivalentTo: cco:Artifact and (bfo:0000051 some {Y:Class})`. The relation `bfo:0000051` (has part) links the Artifact to a component class. Crucially, the schema enforces a foreign key constraint where the component (`y`) must reference an existing Requirement identifier. This creates a dependency where the existence of the Artifact is structurally validated by the existence of the Requirement it contains. This prevents the creation of "empty" artifact shells in the registry and ensures that every composite artifact is anchored to a specific, defined governance requirement.

### 7.3.3 Implementation and Instances

*Table 7-2 embodies the axiom `equiv_intersect_artifact_with_part`. The primary key is `id`. Column `x` is the Artifact class, and column `y` is the component part. The foreign key constraint ensures that `y` references a valid ID in the `t_requirement_equiv_specifies_target` table, enforcing that the part of the artifact is a valid requirement specification.*

For instance, the `DataRetentionPolicyDocument` is defined as an Artifact that has `req_spec_01` as a part. This structure allows auditors to query the `DataRetentionPolicyDocument` and programmatically decompose it into its constituent requirements (`req_spec_01`). This mereological precision is essential for version control, ensuring that if a requirement is updated, the system can identify all artifacts containing that requirement for impact analysis.

## 7.4 Directives: Authorship and Application

### 7.4.1 Conceptual Definition

A DirectiveICE represents a category of information content that is intended to direct behavior. Unlike descriptive entities, directives are prescriptive. The axiom `directive_authored_and_applies` further refines this by establishing two necessary conditions: a Directive must have an author (`authoredBy`), and it must apply to a specific target (`appliesTo`). This tripartite structure—Entity, Author, Target—forms the basis of accountability within the governance framework. It answers not only what the directive is, but who issued it and what system or process it governs.

### 7.4.2 Axiomatic Structure and Relational Integrity

The axiom is expressed as `EquivalentTo: cco:DirectiveICE and (sdg:authoredBy some {Y:Class}) and (sdg:appliesTo some {Z:Class})`. The relational schema for this axiom introduces a circular dependency with the Requirement table to enforce a tight coupling between high-level directives and specific requirements. Specifically, the `authoredBy` slot (`y`) references a Requirement ID. This implies a semantic constraint where the authority of the Directive is derived from or validated against a specific Requirement. The `appliesTo` slot (`z`) denotes the target class (e.g., a specific IT system, personnel role, or data type).

### 7.4.3 Implementation and Instances

The following table catalogs Directives, linking them to their authoring Requirements and their application targets. This mapping ensures that every prescriptive statement is traceable to a governing requirement and scoped to a specific operational domain.

In this schema, the `EncryptionMandate` (`dir_auth_01`) is authored by `req_spec_01`. This indicates that the mandate exists because of the requirement defined in `req_spec_01`. The directive applies specifically to the `DatabaseCluster`. This level of granularity prevents "scope creep" in compliance enforcement, ensuring that a directive intended for databases is not erroneously applied to endpoints or physical facilities.

## 7.5 Requirements: Specification and Targeting

### 7.5.1 Conceptual Definition

The Requirement class represents the most granular unit of prescriptive governance. It is a specific type of DirectiveICE that not only applies to a target but also *specifies* another entity. The axiom `requirement_equiv_specifies_target` defines a Requirement as an intersection of three conditions: it is a Directive, it specifies something (the method or control), and it applies to a target. This structure allows for the decomposition of complex policies into atomic, verifiable requirements.

### 7.5.2 Axiomatic Structure and Relational Integrity

Formally, the axiom is `EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`. The relational schema enforces a dependency where the `specifies` slot (`y`) must reference a valid Directive ID. This creates a recursive hierarchy where a Requirement specifies a Directive, and that Directive is authored by a Requirement (as seen in Section 7.4). This circular reference is logically consistent in a governance context: a Requirement (e.g., "System must encrypt data") specifies a Directive (the "EncryptionMandate"), and that Directive is in turn validated by the Requirement.

This dense web of relationships ensures that every component of the governance framework is traceable, validated, and contextually bound.
