# Chapter 4: Structural Formalization of Regulatory Directives and Artifacts

This chapter establishes the formal ontological framework required for the precise classification and governance of regulatory documentation within the enterprise architecture. It delineates the structural relationships between descriptive information entities, composite artifacts, and prescriptive directives, ensuring that all compliance materials are auditable and logically consistent. The definitions provided herein are binding for all subsequent data migration efforts and governance reporting cycles. Furthermore, the relational schema mappings presented serve as the authoritative source for the generation of audit trails and compliance verification matrices.

## 1. Descriptive Information Content Entities

In the context of information governance, it is critical to distinguish between prescriptive mandates, which dictate behavior, and descriptive entities, which characterize the state of the world. A Descriptive Information Content Entity (DescriptiveICE) is defined as a subclass of information content entities that are intended to denote, represent, or characterize some aspect of reality without issuing a command or obligation. Unlike directives, descriptive entities do not compel action; rather, they serve as the evidentiary basis upon which compliance is measured.

The axiom `subclass_to_descriptive_ice` formalizes this distinction. It asserts that any entity classified under this hierarchy is fundamentally observational. In practice, this includes audit logs, incident reports, system status summaries, and environmental data records. These entities are passive; they exist to be queried and analyzed, providing the "is" against which the "ought" of regulatory directives is tested.

To illustrate the classification of these entities, consider the following registry of descriptive content types currently utilized within the Federal Information Governance Bureau (FIGB) reporting framework. Each entry represents a class of information that serves a purely descriptive function within the broader compliance architecture.

**Table 1.1: Registry of Descriptive Information Content Entities**

| id | x |
| :--- | :--- |
| desc_entity_01 | ServerAvailabilityLog |
| desc_entity_02 | NetworkTrafficSummary |
| desc_entity_03 | DataBreachIncidentReport |
| desc_entity_04 | UserAccessChronicle |
| desc_entity_05 | QuarterlyFinancialAudit |

The table above encapsulates the `x` slot of the axiom, representing the specific class of the descriptive entity. For instance, the `ServerAvailabilityLog` (id: desc_entity_01) is a descriptive entity because it records the temporal state of server resources without prescribing their configuration. This classification is foundational; it ensures that downstream reporting processes do not mistakenly categorize observational data as regulatory mandates.

## 2. Artifact Composition and Partonomy

Regulatory artifacts are rarely monolithic; they are complex objects composed of multiple distinct parts, each of which may carry its own semantic weight and governance requirements. An artifact, in this ontological framework, is defined as a concrete entity that bears information. The axiom `equiv_intersect_artifact_with_part` provides a rigorous definition for composite artifacts: an entity is classified as a specific type of artifact if and only if it is an instance of `cco:Artifact` and has as a part some specific component `Y`.

This intersection definition implies that mere existence as an artifact is insufficient for classification under specific governance schemas. The entity must possess a specific structural composition. In the context of compliance manuals, this means a "Policy Document" is only recognized as such if it contains specific "Requirement" sections. The partonomy here is strict: the artifact (the whole) contains the requirement (the part), and this relationship is necessary for the artifact to fulfill its defined role in the governance framework.

The following table details specific composite artifacts and their requisite component parts. Note that the `y` column references the identifier of the requirement component, establishing a foreign key relationship that enforces the integrity of the composition. This structure ensures that every artifact listed can be audited not just for its existence, but for its completeness—verifying that it contains the mandatory regulatory components.

**Table 2.1: Composite Artifact and Requirement Partonomy**

| id | x | y |
| :--- | :--- | :--- |
| artifact_001 | PhysicalSecurityManual | req_001 |
| artifact_002 | DataRetentionPolicy | req_002 |
| artifact_003 | AccessControlProcedures | req_003 |
| artifact_004 | IncidentResponsePlan | req_004 |

In the relational schema projected by this axiom, `t_equiv_intersect_artifact_with_part`, the column `y` functions as a foreign key referencing the requirement table. For example, the `PhysicalSecurityManual` (artifact_001) is defined as a valid artifact only by virtue of containing `req_001`. If `req_001` were removed or modified such that it no longer satisfied the constraints of the requirement class, the artifact itself would fail its validation check. This dependency is critical for maintaining the version control and integrity of governance documents.

## 3. Specification and Application of Requirements

The core of the governance framework lies in the definition of Requirements. A Requirement is not merely a suggestion; it is a specific type of Directive Information Content Entity (`cco:DirectiveICE`) that carries the weight of obligation. The axiom `requirement_equiv_specifies_target` establishes the equivalence for a Requirement class: it must be a directive, it must specify some other directive or action (`Y`), and it must apply to a specific target scope (`Z`).

This tripartite structure—Directive, Specification, and Application—ensures that requirements are never vague. A requirement must explicitly articulate what it specifies (the specific protocol or subordinate directive) and the context to which it applies (the target system, personnel group, or data class). This formalism eliminates ambiguity in compliance auditing. An auditor can look at a requirement instance and immediately trace its lineage to the subordinate directive it specifies and the operational target it governs.

The schema for this concept, `t_requirement_equiv_specifies_target`, necessitates that the specification (`y`) refers to a valid directive entry. This creates a chain of authority where high-level requirements specify the precise operational directives needed to achieve compliance.

**Table 3.1: Requirement Specification and Applicability Matrix**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| req_001 | MandatoryEncryptionStandard | dir_001 | FinancialDataClass |
| req_002 | PersonnelVettingProtocol | dir_002 | HR_Department |
| req_003 | ContinuousMonitoringDirective | dir_003 | ServerInfrastructure |
| req_004 | DataPortabilityRequirement | dir_004 | CustomerDatabase |

In Table 3.1, the `MandatoryEncryptionStandard` (req_001) serves as the primary example. It is a directive that specifies `dir_001` (the specific technical directive implementing the encryption) and applies to the `FinancialDataClass`. The foreign key constraint on column `y` ensures that `dir_001` exists within the system as a valid, authored directive. This structure enforces the principle that requirements cannot exist in a vacuum; they must be grounded in executable directives and scoped to tangible targets.

## 4. Directive Authorship and Applicability

While requirements define the high-level obligations, the actual execution of governance is handled by Directives. The axiom `directive_authored_and_applies` defines the operational directive. It asserts that a class `X` is a Directive if and only if it is a `cco:DirectiveICE`, is authored by some entity `Y`, and applies to some target `Z`.

In this specific ontological model, the "authoredBy" slot (`y`) is constrained to reference a Requirement. This reflects a top-down governance flow: the Requirement acts as the authorizing source or the "author" of the operational Directive. The Requirement mandates the existence of a specific action, and the Directive is the embodiment of that action. Consequently, the Directive applies to the specific target (`z`) necessary to fulfill the Requirement.

The relational schema `t_directive_authored_and_applies` enforces a circular dependency with the Requirement table, reinforcing the tight coupling between high-level mandates and operational execution. A Directive cannot exist without being authorized by a Requirement, and a Requirement is incomplete without specifying the Directive it authorizes.

**Table 4.1: Operational Directive Authorship and Scope**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| dir_001 | AES256ImplementationGuide | req_001 | PaymentGateway |
| dir_002 | BackgroundCheckProcedure | req_002 | NewHireWorkflow |
| dir_003 | LogAggregationScript | req_003 | CentralSyslogServer |
| dir_004 | XMLExportModule | req_004 | UserInterfaceAPI |

Reviewing the data in Table 4.1 clarifies the execution flow. The `AES256ImplementationGuide` (dir_001) is the operational directive. It is authored by `req_001` (the `MandatoryEncryptionStandard`), meaning the standard itself generates the requirement for this guide. The guide applies specifically to the `PaymentGateway` (z). This mapping allows compliance officers to verify that for every requirement (e.g., "encrypt financial data"), there exists a corresponding, authored directive (e.g., "use AES-256 on the gateway") applied to the correct asset.

The interplay between Tables 3.1 and 4.1 demonstrates the rigor of the framework. The `MandatoryEncryptionStandard` (req_001) specifies `dir_001`, and `dir_001` is in turn authored by `req_001`. This circular reference is not an error but a validation of the governance chain: the requirement defines the directive, and the directive claims its authority from the requirement. This closed loop ensures that no directive is "orphaned" (without a mandate) and no requirement is "toothless" (without an executing directive).
