# Chapter 4: Ontological Foundations of Governance Artifacts

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework necessary for the classification and management of governance artifacts within the regulatory compliance ecosystem. It delineates the structural relationships between physical and digital artifacts, the directive information content entities (ICEs) that govern them, and the descriptive entities that provide necessary context. The definitions herein are derived from the Core Compliance Ontology (CCO) and the Basic Formal Ontology (BFO), ensuring that all data structures referenced in subsequent audit procedures adhere to a rigorous, machine-readable standard. Professionals utilizing this handbook must ensure that all system inputs conform to the relational schemas provided, as these schemas serve as the validation logic for the central repository.

## 4.2 Artifact Composition and Part-Whole Relations

In the context of compliance documentation, an entity is classified as an Artifact only when it satisfies two simultaneous conditions: it must be a discrete object within the domain of `cco:Artifact`, and it must possess a specific part defined by the `bfo:0000051` (has part) relation. This intersection is critical for the validation of submission packages; a document cannot be registered as a valid Artifact if it lacks the requisite component segments mandated by the governing schema.

The axiom `equiv_intersect_artifact_with_part` formalizes this by stating that Class X (the Artifact) is equivalent to the intersection of the general Artifact class and the class of entities that have some part Y. In practice, this means that when a regulatory body receives a submission, the system does not merely verify that the submission exists; it verifies that the submission *contains* specific, identifiable sub-sections (the Y variable) which are themselves registered entities.

To facilitate the processing of these entities, the following relational schema is applied. The primary key is the unique identifier of the Artifact, while the foreign key establishes a mandatory dependency on the part entity. This structure ensures that an Artifact entry cannot exist in the database without a valid reference to its constituent parts.

| :--- | :--- | :--- |
| ART-SUB-2024-001 | ClinicalSubmissionPackage_V1 | REQ-SAF-7721 |

The foreign key constraint ensures that every part listed in `y` corresponds to a valid entry in the requirements registry.*

## 4.3 The Requirement Class as a Specification Directive

A Requirement within this framework is not merely a textual string; it is a specific subclass of a `cco:DirectiveICE` that performs the action of specification. The axiom `requirement_equiv_specifies_target` defines Class X (the Requirement) as equivalent to a Directive that both `sdg:specifies` a target Y and `sdg:appliesTo` a scope Z. This tripartite structure—Subject, Predicate (Specification), and Object—creates a traceable chain of authority from the high-level requirement down to the specific directive it governs.

This distinction is vital for audit trails. It separates passive descriptive text from active requirements. For an entity to be recognized as a Requirement, it must actively specify another entity. The relational projection of this axiom enforces that the target of the specification (column `y`) must be a valid Directive that has been authored and applied within the system. This creates a recursive validation loop where a Requirement is validated by the existence of the Directive it specifies.

| :--- | :--- | :--- | :--- |
| REQ-SAF-7721 | ElectricalSafetyRequirement | DIR-ENG-101 | PowerSupplyUnit_A |
| REQ-TECH-4402 | TechnicalPerformanceStandard | DIR-SW-202 | FirmwareModule_B |
| REQ-CLIN-9910 | ClinicalEndpointDefinition | DIR-DATA-303 | PatientDatabase_C |
| REQ-AUD-5501 | AuditTrailRetentionPolicy | DIR-OPS-404 | ServerLog_D |

*Table 4.2 embodies the `requirement_equiv_specifies_target` axiom. The `x` column denotes the Requirement class, which acts as the DirectiveICE. The `y` column represents the target Directive being specified, and `z` denotes the scope of application. The foreign key constraint on `y` mandates that the target Directive must exist in the `t_directive_authored_and_applies` table.*

## 4.4 Descriptive Information Content Entities

While directives and requirements prescribe actions or constraints, the governance framework must also accommodate entities that describe the state of the world without prescribing behavior. These are classified under the axiom `subclass_to_descriptive_ice`. Class X is defined as a subclass of `cco:DescriptiveICE`, meaning "X is a descriptive information content entity."

This category encompasses definitions, status reports, metadata annotations, and observational logs. Unlike the Requirement class, a DescriptiveICE does not inherently possess a `specifies` relation that points to a directive. Instead, it serves as the informational bedrock upon which directives may act or upon which requirements are based. The distinction is ontological: Descriptive entities are "about" the world, whereas Directive entities are "to be done" in the world.

The following registry tracks these entities. Note the absence of complex foreign key dependencies in this specific table, reflecting the foundational nature of descriptive data. These entities are often referenced by the `z` (scope) parameters of other tables, grounding the abstract directives in concrete descriptive reality.

| :--- | :--- |
| DESC-001 | DeviceSchematicDiagram |

| DESC-003 | SoftwareVersionHistoryLog |

*Table 4.3 lists instances of the `subclass_to_descriptive_ice` axiom. These entities (column `x`) represent the descriptive layer of the ontology. They provide the necessary context and detail for the operational directives but do not themselves carry prescriptive force.*

## 4.5 Directive Authorship and Application Scope

The final component of the governance framework addresses the provenance and applicability of Directives. The axiom `directive_authored_and_applies` defines Class X (the Directive) as a `cco:DirectiveICE` that is `sdg:authoredBy` some entity Y and `sdg:appliesTo` some scope Z. This axiom closes the loop established in Section 4.3 by defining the properties of the target Directives specified by the Requirements.

Crucially, the schema dictates that the author of a Directive (column `y`) is not necessarily a human agent, but may be another Requirement entity. This formalizes the concept of "derived authorship," where a high-level Requirement (e.g., a safety standard) generates or authors a specific technical Directive (e.g., a voltage limit). This relationship ensures that every Directive in the system is traceable back to a governing Requirement, maintaining the integrity of the compliance chain.

The table below demonstrates this linkage. The `y` column references the ID of the Requirement that authored the Directive, enforcing the circular dependency between the `t_requirement_equiv_specifies_target` table and this table.
