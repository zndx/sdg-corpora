# Chapter 4: Ontological Structuring of Compliance Artifacts and Governance Directives

This chapter delineates the formal ontological structures required to model compliance artifacts, governance directives, and descriptive entities within a high-assurance regulatory framework. It provides a rigorous examination of the axioms governing Information Content Entities (ICEs), specifically focusing on the intersection of artifacts with their constituent parts, the provenance of directives through authorship, and the specification of requirements. The objective is to establish a deterministic schema that supports auditability, traceability, and the automated validation of governance controls. Readers should note that the relational schemas presented herein are derived directly from the Manchester Syntax axioms of the core ontology and are intended for implementation in environments requiring strict data integrity and evidentiary support.

## 1. Descriptive Information Content Entities

In the context of governance frameworks, not all information is prescriptive; a significant portion of the data corpus serves a descriptive function, capturing the state of the world or the history of a system without mandating action. A Descriptive Information Content Entity (DescriptiveICE) is defined axiomatically as a subclass of the broader class of Information Content Entities. Unlike directives, which command behavior, or specifications, which define constraints, a DescriptiveICE is characterized by its "aboutness"—it denotes propositions regarding entities that exist independently of the information entity itself.

The verbalization of the axiom `{X} is a descriptive information content entity` underscores that any instance classified under this category is fundamentally a record. In audit trails and compliance logs, this distinction is critical. If an entity is a DescriptiveICE, it must not be processed by an inference engine as a command. Instead, it serves as evidence. For instance, a system log entry recording a user's access time is a DescriptiveICE because it describes an event; it does not specify that the user *must* access the system at that time.

### 1.1 Schema Implementation and Instances

To implement this concept within a relational database, one must utilize a schema that enforces the classification of entities as descriptive. The table `t_subclass_to_descriptive_ice` serves this purpose. The primary key (`id`) ensures that each descriptive entity is uniquely identifiable, while the column `x` holds the specific class or instance identifier of the DescriptiveICE.

The following table illustrates instances of descriptive entities derived from a hypothetical security monitoring system. These rows represent distinct records that satisfy the axiom of being descriptive information content entities.

These entities function as the evidentiary bedrock for the governance framework, providing the raw data upon which compliance calculations are performed. It is imperative that the system architecture prevents the mutation of these entities into directive classes, thereby preserving the semantic integrity of the audit trail.

## 2. Artifacts and Constituent Part-Whole Relations

Complex regulatory artifacts, such as policy documents or technical manuals, are rarely monolithic; they are aggregates of distinct sections, appendices, and referenced requirements. The ontology formalizes this through the axiom `equiv_intersect_artifact_with_part`, which defines a specific class of Artifact (`X`) as equivalent to the intersection of the general class `cco:Artifact` and the restriction that it must have a part (`bfo:0000051`) some other class (`Y`).

This definition implies that an entity is only recognized as this specific type of Artifact if it possesses the designated part. This is a necessary constraint for document control systems where the validity of a whole document (e.g., a Compliance Policy) depends on the presence of a specific clause (e.g., a Data Retention Requirement). If the part is removed, the entity no longer satisfies the intersection condition and ceases to be an instance of the class `X`.

### 2.1 Relational Mapping of Artifacts

The relational schema for this axiom introduces a foreign key constraint that links the Artifact to its constituent part. Specifically, the column `y` (the part) must reference an existing identifier in the `t_requirement_equiv_specifies_target` table. This structural dependency ensures that an artifact cannot be defined as containing a requirement part unless that requirement itself is formally defined and active within the system.

The table below demonstrates this relationship. The Artifact IDs (column `x`) represent composite documents, while the Part IDs (column `y`) reference specific requirement modules that constitute those documents.

**Table 2.1: Artifact-Part Intersection Relations**

| id | x | y |
| :--- | :--- | :--- |
| ART-101 | InformationSecurityPolicy_v4 | REQ-STD-88 |
| ART-102 | AccessControlProtocol_Gamma | REQ-CTRL-02 |
| ART-103 | DataResidencyManual_EU | REQ-LOC-15 |
| ART-104 | IncidentResponsePlan_Beta | REQ-IR-09 |
| ART-105 | ChangeManagementProcedure | REQ-CM-11 |

In this configuration, `InformationSecurityPolicy_v4` is defined as an Artifact specifically because it includes `REQ-STD-88` as a part. The foreign key constraint enforces referential integrity: one cannot delete `REQ-STD-88` without first addressing the artifacts that depend on it. This structure is essential for maintaining the coherence of governance documentation, ensuring that high-level policies are inextricably linked to the specific requirements that give them substance and authority.

## 3. Governance Directives and Authorship Provenance

Governance frameworks rely on Directives—information entities that prescribe action or mandate states of affairs. The axiom `directive_authored_and_applies` provides a granular definition of a DirectiveICE (`X`) by intersecting it with two properties: it must be authored by some agent or entity (`Y`), and it must apply to some scope or target (`Z`).

This structure facilitates provenance tracking and scope delineation. By axiomatically binding a Directive to its author (`sdg:authoredBy`), the framework creates an immutable chain of responsibility. In regulated industries, knowing *who* or *which authoritative body* issued a directive is as critical as the directive's content. Furthermore, the property `sdg:appliesTo` restricts the directive's domain of influence, preventing the over-application of controls to irrelevant systems or processes.

### 3.1 The Authority Loop and Referential Integrity

The schema for this axiom, `t_directive_authored_and_applies`, contains a critical foreign key constraint: the author (`y`) must reference an entry in `t_requirement_equiv_specifies_target`. This creates a semantic loop where a Directive is authored by a Requirement. This models a common governance pattern where a high-level Requirement (e.g., a law or regulation) acts as the authorizing source for a specific operational Directive. The Directive implements the Requirement, and thus the Requirement is the "author" in an ontological sense.

The table below encodes these relationships. We observe that specific operational directives are authored by broader regulatory requirements.

**Table 3.1: Directives with Authorship and Application Scope**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| DIR-OP-01 | EncryptionProtocol_AES256 | REQ-STD-88 | CustomerPII |
| DIR-OP-02 | PasswordComplexityRule | REQ-CTRL-02 | ActiveDirectory |
| DIR-OP-03 | DataStorageLocation_EU | REQ-LOC-15 | TransactionDatabase |

Here, `EncryptionProtocol_AES256` (the Directive) is authored by `REQ-STD-88` (the Requirement). This linkage ensures that the directive is not an arbitrary instruction but a direct instantiation of a governing requirement. The column `z` further constrains the directive by defining its application target, such as `CustomerPII` or `ActiveDirectory`, ensuring precise governance enforcement.

## 4. Requirements Specification and Target Application

The final component of this ontological chapter addresses the definition of a Requirement itself. The axiom `requirement_equiv_specifies_target` defines a Class (`X`) as equivalent to a DirectiveICE that specifies a target (`Y`) and applies to a context (`Z`). This axiom is recursive in nature, interacting with the previous axioms to form a closed loop of governance definitions.

In this framework, a Requirement is not merely a static text; it is a Directive that actively specifies another entity (often a lower-level directive or a control) and applies to a specific context. This formalization allows the system to treat Requirements as active governance nodes that bridge the gap between abstract mandates and concrete technical controls.

### 4.1 The Requirement Specification Schema

The relational schema `t_requirement_equiv_specifies_target` enforces that every Requirement must specify a target (`y`) and apply to a context (`z`). Furthermore, the target (`y`) is foreign-keyed to the `t_directive_authored_and_applies` table. This completes the loop identified in Section 3: a Requirement specifies a Directive, and that Directive is authored by the Requirement.

This circular reference is not a data anomaly but a feature of the governance model, representing the bidirectional validation of authority. The Requirement mandates the Directive, and the Directive derives its existence from the Requirement.

The following table populates this schema, illustrating how Requirements serve as the bridge between abstract governance needs and specific operational directives.

This structure ensures that every operational directive is both specified by and authored by the governing requirement, creating a robust, redundancy-checked chain of evidence suitable for high-stakes compliance auditing.
