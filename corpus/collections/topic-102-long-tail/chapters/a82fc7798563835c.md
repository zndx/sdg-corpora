# Chapter 4: Governance Frameworks — Evidence, Control, and Audit Protocols

This chapter delineates the structural relationships between governance artifacts, specifically focusing on the ontological dependencies between attestations, controls, risk mitigation, and audit procedures. The definitions provided herein establish a rigorous baseline for compliance management, ensuring that directive governance artifacts are anchored in verifiable evidence and clearly mapped to the threat landscapes they are designed to mitigate. Practitioners must adhere to these axiomatic structures to maintain the integrity of audit trails and to satisfy regulatory requirements for traceability and accountability.

## 1. Attestation with Supporting Evidence

In the context of governance frameworks, an attestation is formally defined as a process—a temporal entity extending through time—that serves to validate the state of compliance against a specified standard. However, the validity of any attestation is contingent upon the existence of corroborating data. An attestation without supporting evidence is merely a declarative statement lacking the empirical weight required for regulatory scrutiny.

The axiom `attestation_with_supporting_evidence` posits that for an attestation (Class X) to be valid, it must be associated with a specific body of supporting evidence (Class Y). This relationship is not merely casual but is constitutive; the attestation is "something that with supporting evidence" Y. In practice, this means that when an entity asserts compliance with a control, they must simultaneously produce the artifact that proves the execution of that control. This linkage prevents the "checkbox compliance" phenomenon where controls are theoretically implemented but never practically executed or recorded.

The following table illustrates instances where specific attestation processes are inextricably linked to the evidence artifacts that sustain them. This mapping is essential for auditors performing validation tests, as it identifies exactly which data objects must be retrieved to substantiate a given attestation.

**Table 1.1: Mapping of Attestations to Supporting Evidence Artifacts**

| id | x (Attestation Process) | y (Supporting Evidence) |
| :--- | :--- | :--- |
| ATST-001 | SOC2TypeIIAttestation | SystemDescriptionEvidence |
| ATST-002 | ISAE3400Report | InternalControlQuestionnaire |
| ATST-003 | VendorComplianceAttestation | PenetrationTestReport |

## 2. Control with Evidence Requirement

While attestations represent the validation of compliance, controls represent the administrative or technical directives designed to enforce it. A control, classified under `cco:DirectiveICE`, is a prescriptive rule or procedure. However, for a control to be auditable, it must explicitly define the evidence it requires. This is formalized by the axiom `control_with_evidence_requirement`, which asserts that a control (Class X) "requires evidence" of a specific type (Class Y).

This distinction is critical for governance architecture. A control that lacks a defined evidence requirement is operationally opaque; it may be followed, but its adherence cannot be proven. By mandating that every control definition includes a slot for the required evidence, the framework ensures that compliance is not just a set of actions but a set of *recorded* actions. The evidence requirement acts as the bridge between the directive (the rule) and the audit trail (the proof).

For example, a directive regarding physical access control is useless if it does not require the retention of visitor logs. The table below details specific control directives and the corresponding evidence artifacts that must be generated to satisfy the control's requirements. This structure allows compliance officers to query the system for all controls that require a specific type of evidence, facilitating efficient audit preparation.

| :--- | :--- | :--- |
| CTRL-REQ-101 | ChangeManagementDirective | ChangeRequestApprovalLog |
| CTRL-REQ-102 | LogicalAccessControl | AccessGrantRevocationRecord |
| CTRL-REQ-103 | DataRetentionPolicy | ArchiveManifest |
| CTRL-REQ-104 | IncidentResponsePlan | IncidentTicketHistory |
| CTRL-REQ-105 | PhysicalSecurityDirective | VisitorLogRegister |

*Table 2.1 represents the axiom that a control directive (x) necessitates the generation of specific evidence (y). The `y` column is mandatory, reflecting the ontological constraint that a control without an evidence requirement is incomplete.*

## 3. Control Only Addresses Threat Class

Governance frameworks must be precise regarding the scope of a control's applicability. The axiom `control_only_addresses_threat_class` introduces a restriction on the object of the `addressesRisk` property. It asserts that a control (Class X) addresses a risk (Class Y) *only* if that risk belongs to a specific threat class.

This "only" restriction (`only`) in the Manchester syntax implies a universal quantification over the risks addressed by the control. If a control is designated as addressing "NetworkIntrusionThreat," it must not be cited as the primary mitigation for "InsiderThreatRisk." This axiom prevents scope creep and ensures that controls are evaluated against the specific threats they were designed to counter. It enforces a strict boundary: the control's efficacy is defined solely within the context of the specified threat class.

In practical terms, this allows risk managers to validate that a specific control, such as a Web Application Firewall (WAF), is not incorrectly mapped to physical security risks. The table below provides examples of controls that are strictly scoped to a single threat class, ensuring that the governance mapping remains logically consistent.

## 4. Control Addresses Risk

Building on the specificity of threat classes, the broader governance requirement is that controls must actively mitigate identified risks. The axiom `control_addresses_risk` utilizes the existential quantifier (`some`), asserting that a control (Class X) "addresses risk" (Class Y). Unlike the "only" restriction, this axiom establishes the positive existence of a mitigation link between a directive and a risk.

This relationship forms the core of the risk-control matrix. Every identified risk within the enterprise risk management framework must be mapped to at least one control via this axiom. The presence of this link validates the control's existence; if a control addresses no risk, it is orphaned and should be deprecated for efficiency.

This distinction allows for granular risk management where specific controls are applied to specific, assessed risks.

## 5. Audit Conducted By

The final component of the governance ontology is the audit process itself. An audit is a process (`bfo:0000015`) that verifies the implementation and effectiveness of controls and the validity of attestations. The axiom `audit_conducted_by` asserts that an audit (Class X) is a process that is "conducted by" a person (`cco:Person`).

This axiom anchors the abstract concept of auditing to the responsibility of a natural person. It ensures that there is always an accountable agent associated with the audit process. In an era of automated scanning and continuous monitoring, this axiom serves as a reminder that the final validation, the "sign-off," is a human activity. The audit is not a self-executing algorithm; it is a rigorous inquiry performed by an agent with professional standing.
