# Governance Artifacts and Evidentiary Structures

This chapter establishes the formal ontological relationships governing audit trails, directive issuance, and evidentiary support within a compliance framework. It delineates the structural dependencies between information content entities and the processes that generate or validate them. The definitions provided herein are axiomatic, intended for implementation in semantic data models and relational database schemas to ensure referential integrity and auditability.

## 1.0 Descriptive Information Content Entities

The foundational unit of any compliance framework is the Descriptive Information Content Entity (DescriptiveICE). In the context of the Common Core Ontologies (CCO), a DescriptiveICE is defined as an information content entity that consists of a set of propositions that describe some entity. Unlike prescriptive entities (which mandate behavior) or representational entities (which denote data structures), descriptive entities serve as the passive record of states of affairs.

In practice, these entities act as the atomic data points for auditability. They are not merely documents but the semantic content within documents that asserts a fact about the world. For a governance framework to be machine-readable and queryable, these entities must be distinct from the processes that produce them.

**Table 1.1: Basic Evidence Classification**
This table embodies Axiom 3 (`evidence_basic`), which classifies entities as subclasses of `cco:DescriptiveICE`. The primary key is `id`, identifying the specific evidence instance, while `x` denotes the class of the descriptive entity.

| id | x |
| :--- | :--- |
| EVID-001 | SystemAccessLog |
| EVID-002 | ConfigurationSnapshot |
| EVID-003 | NetworkFlowRecord |
| EVID-004 | UserProvisioningEntry |

The instances listed in Table 1.1 represent distinct classes of descriptive evidence. A `SystemAccessLog` (EVID-001), for example, is a DescriptiveICE because it contains propositions regarding specific authentication events. By formally typing these records, downstream processes can unambiguously filter and aggregate evidence based on its semantic class rather than its file format.

## 2.0 Audit Processes and Evidence Production

While descriptive entities are the static artifacts of compliance, the Audit Process is the dynamic mechanism that generates them. According to Axiom 1 (`audit_produces_evidence`), an audit is a process (specifically, `bfo:0000015`, a processual entity) that necessarily produces evidence in the form of a `cco:DescriptiveICE`.

This relationship establishes a provenance chain. It is insufficient to store evidence; one must also record the processual context of its creation. In regulatory environments, the validity of evidence often hinges on the legitimacy of the audit process that produced it. If the process is flawed or out of scope, the evidence it produces is often deemed inadmissible.

**Table 2.1: Audit Process Output Registry**
This table embodies Axiom 1 (`audit_produces_evidence`). The primary key `id` uniquely identifies the audit process instance, and `x` represents the specific class of the audit being performed.

| id | x |
| :--- | :--- |
| AUDIT-PROC-101 | QuarterlyAccessReview |
| AUDIT-PROC-102 | AnnualVulnerabilityScan |
| AUDIT-PROC-103 | AdHocIncidentResponse |
| AUDIT-PROC-104 | ThirdPartyComplianceAudit |

For instance, the `QuarterlyAccessReview` (AUDIT-PROC-101) is a processual entity. Its execution results in the generation of access logs and review reports (the DescriptiveICEs). By linking the process ID to the output evidence, auditors can trace any piece of information back to the specific review activity that created it.

## 3.0 Evidence-Backed Claims

A claim in a governance context is an assertion of truth regarding a specific state of compliance. Axiom 5 (`claim_min_one_evidence`) posits that a claim is a subclass of `cco:DescriptiveICE` that must be supported by a minimum of one piece of evidence produced by an audit process.

This constraint enforces the principle of "evidence-based compliance." A claim cannot exist in a vacuum; it must be anchored to a verifiable audit trail. The ontology requires that the supporting evidence (`y`) must be an instance of a process defined in the audit registry (specifically, an entry from `t_audit_produces_evidence`).

**Table 3.1: Compliance Claims and Audit Linkage**
This table embodies Axiom 5 (`claim_min_one_evidence`). The primary key is `id`. Column `x` is the claim class, and column `y` is a foreign key referencing the audit process ID (`t_audit_produces_evidence.id`) that produced the supporting evidence.

| id | x | y |
| :--- | :--- | :--- |
| CLAIM-201 | PrivilegeAccessCompliance | AUDIT-PROC-101 |
| CLAIM-202 | PatchManagementCurrent | AUDIT-PROC-102 |
| CLAIM-203 | DataEncryptionAtRest | AUDIT-PROC-104 |
| CLAIM-204 | IncidentContainmentVerified | AUDIT-PROC-103 |

In Table 3.1, the claim `PrivilegeAccessCompliance` (CLAIM-201) is asserted as true. This assertion is valid only because it is supported by evidence generated during the `QuarterlyAccessReview` (AUDIT-PROC-101). The foreign key constraint ensures that the claim is anchored to a legitimate, defined audit process, preventing the insertion of orphaned or unsupported claims into the governance record.

## 4.0 Directive Governance: Authorship and Application

Directives are prescriptive information content entities that mandate specific actions or states. Axiom 2 (`directive_authored_and_applies`) defines a Directive as an entity that is authored by a specific authority and applies to a specific target. In this ontology, the "author" is not a person but an attestation process, and the directive applies to a target class (`z`).

This structure formalizes the delegation of authority. A directive does not appear spontaneously; it is the output of a governance attestation. Furthermore, its scope is strictly bounded by the class `z` to which it applies, ensuring that directives are not applied arbitrarily to unrelated entities.

**Table 4.1: Directive Issuance and Scope**
This table embodies Axiom 2 (`directive_authored_and_applies`). The primary key is `id`. Column `x` is the directive class. Column `y` is a foreign key referencing the attestation (`t_attestation_with_supporting_evidence.id`) that authored the directive. Column `z` is the target class to which the directive applies.

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| DIR-301 | PasswordComplexityPolicy | ATTEST-401 | CorporateUserAccount |
| DIR-302 | DataRetentionRule | ATTEST-402 | FinancialTransactionRecord |
| DIR-303 | NetworkSegmentationProtocol | ATTEST-401 | ServerSubnet |

Consider the `PasswordComplexityPolicy` (DIR-301). This directive is authored by the attestation process `ATTEST-401`. The foreign key relationship implies that the directive gains its authority from that specific attestation. The directive applies specifically to the `CorporateUserAccount` class (`z`), meaning its prescriptive power is restricted to that domain and does not, for example, apply to service accounts unless explicitly redefined.

## 5.0 Attestation with Supporting Evidence

The attestation is the formal act of validating a state of affairs, often serving as the bridge between evidence and directive. Axiom 4 (`attestation_with_supporting_evidence`) defines an attestation as a process that utilizes supporting evidence. Crucially, the supporting evidence (`y`) in this schema is identified as a Directive.

This creates a recursive governance loop: an attestation produces a directive (Section 4), and that same directive serves as the supporting evidence for the attestation itself. This circular dependency models real-world governance where a policy (directive) is enforced because it has been attested to, and the attestation is valid because it references the policy.

This table embodies Axiom 4 (`attestation_with_supporting_evidence`). The primary key is `id`. Column `x` is the attestation class. Column `y` is a foreign key referencing the directive (`t_directive_authored_and_applies.id`) that serves as the supporting evidence for the attestation.

| id | x | y |
| :--- | :--- | :--- |
| ATTEST-401 | AnnualSecurityCertification | DIR-301 |

In Table 5.1, the `AnnualSecurityCertification` (ATTEST-401) is the process. Its validity is supported by the `PasswordComplexityPolicy` (DIR-301). This linkage ensures that the act of certification is not abstract; it is grounded in the specific directive being certified.
