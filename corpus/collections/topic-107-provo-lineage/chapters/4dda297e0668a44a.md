# Chapter 4: Formalization of Governance Artifacts and Evidence Chains

## Scope and Preamble

This chapter delineates the formal ontological structures governing the creation, management, and interrelation of compliance artifacts within an enterprise information system. It provides a rigorous examination of the axioms defining audit processes, descriptive evidence, compliance claims, governance directives, and attestations. The content is intended to serve as a normative reference for system architects and compliance officers seeking to implement a machine-readable governance framework. The following sections detail the specific class restrictions, object properties, and relational schema mappings required to maintain data integrity and evidentiary chain of custody.

## 4.1 Audit Processes and Evidence Production

The fundamental unit of compliance verification is the audit process. In this ontology, an audit is not merely a procedural checklist but a distinct temporal entity (BFO:0000015) that acts as a generative mechanism. The axiom `audit_produces_evidence` establishes that any instance of an Audit Class must necessarily produce a specific type of artifact: a Descriptive Information Content Entity (DescriptiveICE). This relationship ensures that every audit action is ontologically bound to an output, preventing the existence of "orphan" audit events that lack tangible evidentiary results.

The following table instantiates this axiom. The primary key `id` serves as the unique identifier for the audit instance, while the column `x` represents the specific Audit Class performing the action. The relational structure enforces that the entity described in `x` is a subclass of the process that generates evidence.

## 4.2 Governance Directives: Authorship and Application

Governance directives function as the normative rules that constrain behavior within the system. The axiom `directive_authored_and_applies` defines a Directive Information Content Entity (DirectiveICE) through an equivalence class axiom. This definition mandates that a valid directive must possess two specific characteristics: it must be authored by a specific entity (slot `y`), and it must apply to a specific target domain or scope (slot `z`).

The relational schema for this concept introduces a foreign key constraint linking the author (`y`) to an attestation entity. This dependency creates a formal validation loop: a directive is only valid if it is authored by a recognized attestation authority. The table below illustrates this structure, where the `y` column references identifiers from the attestation table detailed in Section 4.4.

## 4.3 Descriptive Evidence Entities

Evidence in this framework is formalized as a Descriptive Information Content Entity (DescriptiveICE). The axiom `evidence_basic` classifies any entity in slot `x` as a subclass of `cco:DescriptiveICE`. This classification distinguishes raw data or descriptive artifacts from prescriptive documents (like directives) or assertional statements (like claims). DescriptiveICE refers to content that "is about" some portion of reality—such as a log file entry, a system configuration snapshot, or a recorded transaction—without necessarily making a truth claim about it itself.

The table below catalogs instances of these descriptive entities. These are the atomic units of information generated by the audit processes described in Section 4.1 and consumed by claims in Section 4.5.

## 4.4 Attestation and Supporting Evidence

Attestation represents the formal act of validation or verification. The axiom `attestation_with_supporting_evidence` posits that an attestation is a process (BFO:0000015) that carries with it supporting evidence. Crucially, in this schema, the supporting evidence (`y`) required for an attestation is a Directive. This reflects a specific governance logic where an attestation (e.g., a certification or sign-off) is valid only insofar as it is supported by the underlying directive or policy that grants the authority or defines the standard for that attestation.

The table below demonstrates this recursive dependency. The `y` column contains references to the Directive IDs defined in Table 4.2, establishing that the attestation relies on the directive for its legitimacy.

## 4.5 Claims and Evidentiary Support Thresholds

A claim is an assertional statement that requires validation. The axiom `claim_min_one_evidence` defines a Claim as a DescriptiveICE that is supported by a minimum of one evidence item. Unlike the basic descriptive evidence, a claim makes a specific assertion about the state of the world (e.g., "The system is compliant") and therefore requires a foundation in evidence.

The schema enforces a "min 1" cardinality constraint on the `supportedByEvidence` property. In the relational implementation, the `y` column acts as a foreign key referencing the audit process that produced the requisite evidence. This linkage ensures that every claim is traceable back to a specific audit event that generated the supporting proof.
