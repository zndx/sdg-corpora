# Chapter 4: Relational Modeling of Verified Safe Artifacts

This chapter defines the subclass relation of artifacts verified as safe and demonstrates the relation through a four-table schema. The schema supports primary-key and foreign-key navigation sufficient to resolve multi-hop queries on verification events.

## 1. Ontological Foundation

The single axiom employed states that an individual of class X is a subclass of cco:Artifact and stands in the verifiedSafeBy relation to an individual of class Y. All table rows below instantiate this axiom; column values are restricted to the declared slot types (Class or Individual references and typed literals).

### 1.1 Primary and Foreign Key Discipline

Every table declares an explicit primary key. Three tables contain foreign-key columns that reference primary keys of other tables. The foreign-key graph permits direct cross-table joins without additional mapping tables.

## 2. Table Definitions

The following tables realize the axiom in a laboratory compliance system that records verification of eBPF programs submitted for safety review.

t_programs stores candidate artifacts. Its primary key is program_id. The table supplies the X values required by the axiom; a verification record cannot exist without a corresponding program row.

| program_id | name                  | artifact_class     |
|------------|-----------------------|--------------------|
| P001       | packet_filter_v2     | cco:Artifact       |
| P002       | net_monitor_v3       | cco:Artifact       |
| P003       | tracepoint_hook_v1   | cco:Artifact       |
| P004       | cgroup_skb_v2        | cco:Artifact       |

t_verifiers stores the entities that perform verification. Its primary key is verifier_id. The table supplies the Y values required by the axiom.

| verifier_id | name                     | verification_method |
|-------------|--------------------------|---------------------|
| V01         | KernelVerifier_5.15      | static_analysis     |
| V02         | SafetyCert_Lab           | model_checking      |
| V03         | ComplianceEngine_3       | symbolic_execution  |

t_ebpfprogram_verified_safe is the direct projection of the axiom. Its primary key is id. Column x is a foreign key to t_programs.program_id; column y is a foreign key to t_verifiers.verifier_id. A cross-join on x and y yields the verified pair for any given artifact.

| id     | x    | y   |
|--------|------|-----|
| VS001  | P001 | V01 |
| VS002  | P002 | V02 |
| VS003  | P003 | V01 |
| VS004  | P004 | V03 |
| VS005  | P001 | V02 |

t_verification_logs records the temporal outcome of each verification event. Its primary key is log_id. Column verification_id is a foreign key to t_ebpfprogram_verified_safe.id. Joining through this key recovers the originating program, verifier, and result in one traversal.

| log_id | verification_id | timestamp           | result |
|--------|-----------------|---------------------|--------|
| L001   | VS001           | 2024-03-12T09:15:00 | pass   |
| L002   | VS002           | 2024-03-12T10:22:00 | pass   |
| L003   | VS003           | 2024-03-13T14:05:00 | fail   |
| L004   | VS004           | 2024-03-14T08:40:00 | pass   |
| L005   | VS005           | 2024-03-14T11:30:00 | pass   |

## 3. Cross-Join Example

Question: which verifier and result apply to program P001 when verified under record VS005?

Start at t_programs.program_id = 'P001'.  
Follow t_ebpfprogram_verified_safe.x = 'P001' and t_ebpfprogram_verified_safe.id = 'VS005' to obtain y = 'V02'.  
Follow t_verification_logs.verification_id = 'VS005' to obtain result = 'pass'.

Joined row: (P001, packet_filter_v2, V02, SafetyCert_Lab, VS005, pass).
