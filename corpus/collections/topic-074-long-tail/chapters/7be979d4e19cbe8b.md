# Compliance Directive Ontologies Projected to Audit Schemas

This chapter defines five directive classes drawn from an OWL ontology of information-security controls. Each class is realized as a relational table whose rows enumerate concrete X–Y pairs. The tables share value domains in the Y column, enabling cross-table joins that recover multi-hop compliance chains such as “which physical, technical and administrative safeguards simultaneously address a given control objective.”

## 1 Physical HIPAA Safeguards

Table t_hipaa_safeguard_physical embodies axiom 1. Column id is the primary key; columns x and y are foreign-key references to directive subclasses and control objectives respectively. A reader can join on y to locate every safeguard type that addresses the same objective.

```sql
CREATE TABLE t_hipaa_safeguard_physical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 2 Technical HIPAA Safeguards

Table t_hipaa_safeguard_technical embodies axiom 2. Primary key id; x and y again serve as references to directive and objective classes. Joining this table with t_hipaa_safeguard_physical on y yields pairs of physical and technical controls that satisfy an identical objective.

```sql
CREATE TABLE t_hipaa_safeguard_technical (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
```

## 6 Worked Multi-hop Query Example

Question: which ISO 27001 control, PCI DSS requirement and HIPAA administrative safeguard all address the objective LockedServerRoom?

Execution:
1. Select rows from t_iso27001_annexa_subclass where y = 'LockedServerRoom' → iso_a_001.
2. Join t_pci_dss_requirement on the same y → pci_req_002.
3. Join t_hipaa_safeguard_admin on the same y → hs_admin_001.

Resulting joined row: (iso_a_001, A_9_4_2, LockedServerRoom, pci_req_002, Req_7_1, hs_admin_001, AccessReviewProcess).
