# Chapter 4: Regulatory Directives and Control Mapping

## 4.1 Scope and Preamble

This chapter delineates the formal mapping between internal governance artifacts—specifically Information Control Elements (ICE) classified as Directives—and external regulatory frameworks governing data security and privacy. The objective is to establish a traceable lineage from organizational policy (`cco:DirectiveICE`) to statutory and contractual obligations, including the Health Insurance Portability and Accountability Act (HIPAA), the Payment Card Industry Data Security Standard (PCI DSS), and ISO/IEC 27001. The following sections define the ontological relationships wherein a specific Directive serves as the mechanism to satisfy a safeguard, requirement, or control objective. Each section includes a relational schema instantiation demonstrating the binding of the Directive class to the respective regulatory class.

## 4.2 HIPAA Physical Safeguards

The HIPAA Security Rule, codified at 45 CFR § 164.310, mandates "Physical Safeguards" to protect electronic protected health information (ePHI) and related equipment and records from unauthorized intrusion, environmental hazards, and natural disasters. Within the ontology, a Physical Safeguard is defined as a directive that implements specific physical controls. The axiom `hipaa_safeguard_physical` asserts that a Directive (X) is a subclass of `cco:DirectiveICE` and functions as a HIPAA safeguard for a specific physical asset or location class (Y).

Implementation of these safeguards requires a granular assessment of the facility's physical environment. For instance, policies regarding Facility Access Controls must restrict access to authorized personnel only. This is not merely a procedural statement but a binding directive that links the policy document to the physical entity (e.g., "EmergencyAccessPoint" or "WorkstationLocation").

The following table embodies the `hipaa_safeguard_physical` axiom. The primary key `id` uniquely identifies the mapping instance. Column `x` represents the Directive class (the policy or control mechanism), while column `y` represents the Physical Asset class being safeguarded. The `NOT NULL` constraint on `y` ensures that every physical safeguard directive must be associated with a tangible target.

**Table 4-1: Mapping of Directives to HIPAA Physical Safeguards**

| id | x (Directive Class) | y (Physical Asset Class) |
| :--- | :--- | :--- |
| PHYS-001 | FacilityAccessControlPolicy | EmergencyAccessPoint |
| PHYS-002 | FacilityAccessControlPolicy | PhysicalWorkstation |
| PHYS-003 | WorkstationUsePolicy | ElectronicMedia |
| PHYS-004 | DeviceAndMediaControlsPolicy | PortableElectronicMedia |
| PHYS-005 | DeviceAndMediaControlsPolicy | HardwareComponent |

In the context of Table 4-1, the `FacilityAccessControlPolicy` (x) is the directive that governs the `EmergencyAccessPoint` (y). This mapping ensures that during an audit, the existence of the policy can be directly correlated to the security requirement for the physical asset. Similarly, the `WorkstationUsePolicy` governs the usage of `ElectronicMedia`, ensuring that physical handling procedures are anchored to the specific media type defined in the ontology.

## 4.3 HIPAA Technical Safeguards

Pursuant to 45 CFR § 164.312, Technical Safeguards are the automated mechanisms—both hardware and software—used to protect ePHI and control access to it. Unlike physical safeguards, which focus on the tangible environment, technical safeguards address the digital logic and transmission protocols. The ontology defines this relationship via the `hipaa_safeguard_technical` axiom, where a Directive (X) safeguards a specific Technical Process or Data Class (Y).

Organizations must implement technical policies and procedures to allow only authorized persons to access electronic protected health information. This includes the use of unique user identification, emergency access procedures, automatic logoff, and encryption and decryption. The directive here serves as the governance wrapper around the technical implementation.

The table below instantiates the `hipaa_safeguard_technical` schema. The structure mirrors the physical safeguards table but applies to technical domains. The `x` column contains the Directive class (e.g., `AccessControlMechanism`), and the `y` column contains the Technical Class (e.g., `ElectronicProtectedHealthInformation`).

**Table 4-2: Mapping of Directives to HIPAA Technical Safeguards**

| id | x (Directive Class) | y (Technical Class) |
| :--- | :--- | :--- |
| TECH-001 | AccessControlMechanism | ElectronicProtectedHealthInformation |
| TECH-002 | AuditControlMechanism | HardwareConfiguration |
| TECH-003 | IntegrityMechanism | ElectronicMedicalRecord |
| TECH-004 | TransmissionSecurityProtocol | NetworkCommunication |
| TECH-005 | AuthenticationMechanism | WorkstationSession |

As illustrated in row TECH-004, the `TransmissionSecurityProtocol` directive safeguards `NetworkCommunication`. This implies that the directive mandates the use of encryption or other protective measures over open networks. The relational mapping ensures that the technical class `NetworkCommunication` is fully covered by the governance of the `TransmissionSecurityProtocol`.

## 4.4 HIPAA Administrative Safeguards

Administrative safeguards, as defined in 45 CFR § 164.308, are the administrative actions, policies, and procedures to manage the selection, development, implementation, and maintenance of security measures. These safeguards are often the most comprehensive, involving risk analysis, risk management, sanction policies, and information system activity review. The `hipaa_safeguard_admin` axiom formalizes the relationship where a Directive (X) safeguards an Administrative Process or Entity (Y).

A critical component of administrative safeguards is the Security Management Process. This requires the covered entity to implement policies and procedures to prevent, detect, contain, and correct security violations. The directive acts as the enforcement arm of the administrative requirement. For example, a `WorkforceSecurityPolicy` is a directive that safeguards the `WorkforceClearance` process, ensuring that background checks and authorization procedures are rigorously applied.

The following table details the relational schema for administrative safeguards. The `y` column represents the administrative entity or process being protected, such as `SecurityIncidentLog` or `RiskAnalysisReport`.

**Table 4-3: Mapping of Directives to HIPAA Administrative Safeguards**

| id | x (Directive Class) | y (Administrative Entity Class) |
| :--- | :--- | :--- |
| ADMIN-001 | SecurityManagementProcess | RiskAnalysisReport |
| ADMIN-002 | SecurityManagementProcess | RiskManagementStrategy |
| ADMIN-003 | WorkforceSecurityPolicy | WorkforceClearance |
| ADMIN-004 | InformationAccessManagement | AuthorizationEntity |
| ADMIN-005 | SecurityIncidentProcedure | SecurityIncidentLog |

In Table 4-3, the `SecurityManagementProcess` (x) is linked to the `RiskAnalysisReport` (y). This mapping indicates that the directive governs the creation, maintenance, and confidentiality of the risk analysis documentation. By anchoring the directive to the specific document class, the ontology ensures that the administrative artifact is subject to strict version control and access governance.

## 4.5 PCI DSS Requirements

The Payment Card Industry Data Security Standard (PCI DSS) provides a robust framework for organizations that handle cardholder data. Unlike HIPAA, which is structured around safeguards, PCI DSS is organized into specific Requirements (e.g., Requirement 1: Install and maintain a firewall configuration). The `pci_dss_requirement` axiom establishes that a Directive (X) fulfills a specific PCI DSS Requirement Class (Y).

Compliance with PCI DSS requires that all system components and processes be protected according to the specified requirements. The directive within the organization serves as the local implementation of the global standard. For instance, a directive regarding "Wireless Access" must map to "PCI DSS Requirement 1.2.3," which specifically forbids unauthorized wireless networks.

The table below encodes the `pci_dss_requirement` schema. The `x` column refers to the internal `cco:DirectiveICE` class, while the `y` column refers to the specific PCI DSS Requirement class (e.g., `PCI_DSS_Req_2_1`).

**Table 4-4: Mapping of Directives to PCI DSS Requirements**

| id | x (Directive Class) | y (PCI DSS Requirement Class) |
| :--- | :--- | :--- |
| PCI-001 | FirewallConfigurationDirective | PCI_DSS_Req_1_1 |
| PCI-002 | WirelessAccessDirective | PCI_DSS_Req_1_2_3 |
| PCI-003 | VendorDefaultPasswordDirective | PCI_DSS_Req_2_1 |
| PCI-004 | CardholderDataEncryptionDirective | PCI_DSS_Req_3_4 |
| PCI-005 | AntiVirusSoftwareDirective | PCI_DSS_Req_5_1 |

Row PCI-004 demonstrates that the `CardholderDataEncryptionDirective` is the mechanism satisfying `PCI_DSS_Req_3_4` (Render PAN unreadable anywhere it is stored). This relational mapping allows compliance officers to query the ontology and instantly retrieve the internal policy responsible for satisfying a specific external audit question.

## 4.6 ISO/IEC 27001 Annex A Controls

ISO/IEC 27001 is the international standard for Information Security Management Systems (ISMS). Its Annex A lists a comprehensive set of control objectives and controls. The `iso27001_annexa_subclass` axiom defines the relationship where a Directive (X) serves as the implementation for a specific ISO 27001 Annex A Control Class (Y).

Annex A covers diverse areas from access control to cryptography. For an organization to claim conformity to ISO 27001, it must demonstrate that its directives (policies, standards, procedures) effectively implement these controls. The ontology maps the internal directive class to the external control class. For example, an `AccessControlPolicy` directive would map to the Annex A control `A.9.1.1` (Access control policy).

The final table presents the `iso27001_annexa_subclass` schema. The `y` column utilizes standard Annex A nomenclature (e.g., `Annex_A_9_4_1`) to denote the specific control being addressed by the directive in column `x`.

**Table 4-5: Mapping of Directives to ISO 27001 Annex A Controls**

| id | x (Directive Class) | y (ISO 27001 Annex A Class) |
| :--- | :--- | :--- |
| ISO-001 | AccessControlPolicy | Annex_A_9_1_1 |
| ISO-002 | UserAccessManagementDirective | Annex_A_9_2_1 |
| ISO-003 | CryptographyControlDirective | Annex_A_10_1_1 |
| ISO-004 |SecureDisposalPolicy | Annex_A_9_2_7 |
| ISO-005 |LoggingAndMonitoringDirective | Annex_A_12_4_1 |

In Table 4-5, the `CryptographyControlDirective` (x) is the entity responsible for implementing `Annex_A_10_1_1` (y), which concerns policy on the use of cryptography. This mapping is critical for gap analysis; if a specific Annex A control lacks a corresponding entry in this table, the organization has identified a deficiency in its ISMS implementation.
