# Chapter 4: Ontological Mapping of Governance Directives and Metric Emissions

## 4.1 Scope and Preamble

This chapter establishes the formal ontological definitions required to map operational processes to metric emissions and to align governance directives with the Trust Services Criteria (TSC) defined by the American Institute of Certified Public Accountants (AICPA) for SOC2 reporting. The provisions herein detail the structural relationships between process classes, their output metrics, and the categorization of internal control directives across Security and Privacy domains. Compliance with these axioms is mandatory for the accurate generation of automated audit evidence and the maintenance of the governance knowledge graph. The following sections delineate the specific subclass axioms that govern these relationships, supported by relational schema implementations designed to ensure referential integrity and data consistency within the enterprise architecture.

## 4.2 Metric Emission Subclass Axioms

### 4.2.1 Definition and Formalization

In the context of systems observability and continuous auditing, a fundamental requirement is the precise classification of processes that generate quantifiable outputs. The `metric_emission_subclass` axiom provides a formal mechanism to assert that a specific class of process is not merely an isolated activity but is generative in nature, producing a specific class of metric. This axiom is anchored in the Basic Formal Ontology (BFO) through the entity `bfo:0000015`, which denotes a *Process*. By subclassing a process under this axiom, the ontology asserts that the process necessarily participates in the emission of a metric.

The verbalization of this axiom states: *{X} is something that emits metric {Y}*. Here, {X} represents the process class, and {Y} represents the metric class. This relationship is critical for establishing traceability between low-level operational events (the process) and high-level performance indicators (the metric). It ensures that every reported metric is ontologically grounded in a specific, executable process within the system architecture, thereby preventing the existence of "orphan" data points within the audit logs.

### 4.2.2 Operational Context and Examples

Consider a data ingestion pipeline responsible for transferring records from a legacy system to a cloud data warehouse. The process class, `DataIngestionFlow`, is defined as a subclass of `bfo:0000015`. To satisfy the `metric_emission_subclass` axiom, this process must be linked to a metric class, such as `ThroughputBytesPerSec`. This linkage asserts that whenever an instance of `DataIngestionFlow` occurs, it necessarily emits an instance of `ThroughputBytesPerSec`. This formalization allows auditors to query the ontology for all processes contributing to a specific performance report, facilitating root-cause analysis during performance degradation incidents.

Similarly, in the realm of security monitoring, an `AuthAttemptLog` process may be defined. This process captures the event of a user attempting to authenticate. By applying the axiom, we define `AuthAttemptLog` as emitting the metric `FailedLoginCount`. This distinction is vital for compliance reporting, as it differentiates the raw event (the attempt) from the derived measurement (the count), allowing the governance framework to apply distinct retention policies and alerting thresholds to each entity.

## 4.3 SOC2 Security Subclass Axioms

### 4.3.1 Definition and Formalization

The governance of information security requires a rigorous mapping between internal directives and the external criteria against which the organization is evaluated. The `soc2_security_subclass` axiom facilitates this mapping by defining a relationship between a directive class and the SOC2 Security domain. This axiom utilizes the Common Core Ontology (CCO) entity `cco:DirectiveICE`, which represents an Information Control Element (ICE) that is directive in nature—meaning it prescribes a specific course of action or configuration.

Formally, the axiom is expressed as: *{X} is something that for soc2 domain {Y}*. The variable {X} denotes the specific directive class (e.g., a firewall configuration rule or an access control policy), while {Y} denotes the relevant SOC2 domain class, specifically the Security criteria. This subclass relationship ensures that any instance of the directive {X} is automatically classified as relevant to the SOC2 Security domain {Y}, thereby streamlining the evidence collection process during audit engagements.

### 4.3.2 Operational Context and Examples

To illustrate the application of this axiom, consider the directive class `NetworkFirewallPolicy`. In a standard SOC2 audit, the "Security" criterion requires that the system is protected against unauthorized access. By declaring `NetworkFirewallPolicy` as a subclass of `cco:DirectiveICE` and linking it via the `sdg:forSOC2Domain` object property to the `SOC2SecurityDomain`, the organization explicitly encodes the intent of this directive. This semantic tagging allows automated compliance tools to retrieve all firewall configuration changes when testing the "Common Criteria" section of the SOC2 report.

Another example involves the directive class `MFAEnforcementDirective`. Multi-factor authentication is a specific control designed to meet the Security criteria regarding access control. Under this axiom, `MFAEnforcementDirective` is mapped to the `SOC2SecurityDomain`. This mapping ensures that when the directive is enforced—perhaps by a script that disables accounts without MFA—the resulting system state is immediately recognized as satisfying a portion of the SOC2 Security requirements. This ontological structure bridges the gap between policy documentation and technical implementation.

## 4.4 SOC2 Privacy Subclass Axioms

### 4.4.1 Definition and Formalization

While Security focuses on the protection of systems against unauthorized access, the Privacy criterion within the SOC2 framework addresses the organization's handling of personal information. The `soc2_privacy_subclass` axiom mirrors the structure of the security subclass but targets the Privacy domain. It asserts that a specific directive class {X}, which is a subclass of `cco:DirectiveICE`, is implemented for the purpose of satisfying the SOC2 Privacy domain {Y}.

The verbalization remains consistent: *{X} is something that for soc2 domain {Y}*. However, the semantic interpretation shifts to encompass controls related to notice, consent, and the disposal of Personal Identifiable Information (PII). This axiom is essential for organizations subject to the SOC2 Privacy Trust Services Criteria, as it creates a distinct namespace for privacy-related directives, separating them from general security controls to avoid conflation and ensure precise audit scoping.

### 4.4.2 Operational Context and Examples

A practical application of this axiom is the classification of a `CustomerConsentProtocol`. In a privacy-focused governance framework, obtaining and managing user consent is a distinct requirement separate from securing the database where consent is stored. By defining `CustomerConsentProtocol` via the `soc2_privacy_subclass` axiom and mapping it to the `SOC2PrivacyDomain`, the organization clarifies that this directive is specifically aimed at meeting privacy criteria regarding the disclosure of privacy practices to users.

Furthermore, consider the directive class `DataMinimizationRule`. This directive dictates that only data necessary for the stated business purpose should be collected. While related to security (less data means less risk), its primary regulatory driver is privacy. Mapping `DataMinimizationRule` to the `SOC2PrivacyDomain` ensures that during a privacy audit, the evidence gathered focuses on the relevance and necessity of data fields, rather than merely their encryption status. This distinction is crucial for demonstrating compliance with the "Privacy" criteria distinct from the "Security" criteria.
