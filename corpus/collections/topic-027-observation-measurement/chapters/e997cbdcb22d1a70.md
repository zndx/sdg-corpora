# Chapter 4: Ontological Mapping for Automated Compliance Verification

## 4.1 Scope and Preamble

This chapter establishes the formal ontological definitions required for the automated verification of system governance and compliance protocols. It delineates the structural relationships between operational processes, their observable metrics, and the regulatory directives governing Security and Privacy domains within the SOC2 framework. The provisions herein define the necessary subclass axioms that map abstract control requirements to concrete implementation classes. These mappings serve as the evidentiary basis for automated audit trails, ensuring that all system artifacts can be traced back to their governing normative documents. The following sections detail the specific schema definitions, relational constraints, and instance data required to maintain conformance with the established governance architecture.

## 4.2 Metric Emission Subclass Axioms

### 4.2.1 Definition and Structural Requirements

Pursuant to the foundational ontology of Basic Formal Ontology (BFO), specifically the reliance on `bfo:0000015` (Process), this section defines the axiom `metric_emission_subclass`. This axiom asserts that a specific class of operational process (`X`) is, by definition, a subclass of processes that emit a specific type of metric (`Y`). In formal Manchester syntax, this relationship is expressed as `Class: {X:Class} SubClassOf: bfo:0000015, sdg:emitsMetric some {Y:Class}`.

The verbalization of this axiom dictates that `{X} is something that emits metric {Y}`. This distinction is critical for auditability; it separates passive processes from those that generate the telemetry data required for continuous monitoring. The structural integrity of this relationship ensures that for any instance of process `X`, the existence of metric `Y` is a necessary condition, not merely a contingent property. This binding facilitates the automated generation of evidence logs during system operation, as the emission of `Y` serves as a proxy for the successful execution of `X`.

### 4.2.2 Relational Schema and Implementation

The relational projection of this axiom is realized in the database schema `t_metric_emission_subclass`. This table enforces the dependency between the process class and the metric class. The primary key is the unique identifier `id`, which serves as the stable reference for the governance record. The column `x` represents the process class (the emitter), while the column `y` represents the metric class (the emission). The constraint `y VARCHAR(255) NOT NULL` ensures that a process cannot be defined within this subclass without a corresponding metric output, thereby enforcing the ontological requirement at the data layer.

The following table enumerates specific instances of this axiom, mapping critical operational workflows to their required telemetry outputs. These entries reflect the standard operating procedures defined in the System Operations Manual (SOM) v4.2.

### 4.2.3 Compliance Implications

The implementation of the `metric_emission_subclass` axiom allows for automated verification of system observability. During an audit, the compliance engine may query `t_metric_emission_subclass` to identify all required metrics for a given process. If the system logs do not contain an instance of metric `Y` corresponding to the execution of process `X`, a non-conformance flag is raised. This mechanism shifts the audit burden from manual sampling to continuous, deterministic verification.

## 4.3 SOC2 Security Domain Subclass Axioms

### 4.3.1 Definition and Structural Requirements

This section addresses the governance of Information Control Elements (ICE) as they pertain to the Security criteria of the System and Organization Controls (SOC2) framework. The axiom `soc2_security_subclass` defines a class `X` as a subclass of `cco:DirectiveICE` that is specifically designed for a SOC2 Security domain `Y`. The formal Manchester syntax is `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}`.

Verbalized, `{X} is something that for soc2 domain {Y}`. This axiom restricts the scope of the directive `X`, ensuring it is categorically applicable only to the Security domain (often referred to as the "Common Criteria" relating to availability and integrity). By anchoring `X` to `cco:DirectiveICE`, we ensure that the entity is an actionable control directive rather than a passive policy statement. The restriction to the Security domain (`Y`) prevents scope creep and ensures that controls are not misapplied to Privacy or Availability contexts without explicit reclassification.

### 4.3.2 Relational Schema and Implementation

The relational schema `t_soc2_security_subclass` captures these mappings. The table structure consists of the columns `id`, `x`, and `y`. The column `x` contains the identifier for the DirectiveICE class, representing the specific control implementation (e.g., an access control list or an encryption standard). The column `y` contains the SOC2 domain class, specifically constrained here to Security-related domains. The `NOT NULL` constraint on `y` ensures that every directive listed in this table is explicitly bound to a security domain, adhering to the strict segregation of duties required by the compliance framework.

The data presented in Table 4.2 illustrates the binding of specific internal directives to the SOC2 Security domain. These mappings are derived from the Governance Directives Index (GDI) and reflect the current control environment as of the last audit cycle.

### 4.3.3 Audit Verification Protocol

When generating the SOC2 Type II report, the audit system utilizes the `t_soc2_security_subclass` table to populate the "Suitability of Design" narrative. For each directive `x` listed, the system retrieves the test procedures executed against it. Because `x` is axiomatically a subclass of `cco:DirectiveICE`, the system presumes the existence of an executable implementation. The linkage to `y` (SOC2SecurityDomain) allows the report to categorize the evidence under the correct "Security" heading, satisfying the requirement that controls be mapped to the Trust Services Criteria (TSC).

## 4.4 SOC2 Privacy Domain Subclass Axioms

### 4.4.1 Definition and Structural Requirements

While Security controls focus on system integrity and access, Privacy controls govern the handling of Personally Identifiable Information (PII) in accordance with the Privacy Criteria of the SOC2 framework. The axiom `soc2_privacy_subclass` is structurally similar to the Security subclass but operates within a distinct logical domain. It defines a class `X` as a subclass of `cco:DirectiveICE` intended for a SOC2 Privacy domain `Y`. The Manchester syntax is `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}`.

The verbalization remains `{X} is something that for soc2 domain {Y}`, but the semantic instantiation of `Y` is restricted to Privacy classes (e.g., `SOC2PrivacyDomain`). This distinction is vital for maintaining the "Privacy by Design" architecture. It ensures that directives classified under this axiom are subject to review against privacy-specific criteria, such as notice, consent, and data minimization, rather than general security criteria like intrusion detection.

### 4.4.2 Relational Schema and Implementation

The schema `t_soc2_privacy_subclass` enforces the relationship between privacy directives and their target domain. The columns `id`, `x`, and `y` follow the same typing conventions as the security schema. However, the data population of column `y` is restricted to classes representing the Privacy domain. This separation at the relational level prevents logical cross-wiring, where a security directive might inadvertently be cited as satisfying a privacy requirement.

### 4.4.3 Governance and Enforcement

The enforcement of the `soc2_privacy_subclass` axiom is critical during the "Change Management" phase of the software development lifecycle. Any modification to a directive `x` listed in `t_soc2_privacy_subclass` triggers a mandatory Privacy Impact Assessment (PIA). Because the ontology explicitly links `x` to the Privacy domain `y`, the governance framework automatically routes the change request to the Data Privacy Officer (DPO) for approval. This workflow automation is a direct result of the formal ontological classification, ensuring that privacy controls are not altered without appropriate oversight.
