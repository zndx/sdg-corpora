# Chapter 7: Ontological Mapping of Operational Metrics and Compliance Directives

This chapter establishes the formal ontological framework required to map operational telemetry to governance requirements within a SOC2 (System and Organization Controls 2) compliance environment. The scope of this text is restricted to the precise definition of three primary axiom sets: the emission of metrics by specific processes, and the classification of security and privacy directives relative to SOC2 domains. These definitions serve as the structural backbone for automated audit trails, ensuring that every observable data point is traceable to a governing directive and that every directive is grounded in a specific compliance domain.

## 1. Metric Emission Subclasses

In accordance with the Basic Formal Ontology (BFO), a process is an entity that unfolds in time and has temporal parts. However, for the purposes of continuous auditing and real-time compliance monitoring, a process must be rigorously defined not merely by its execution, but by its capacity to generate observable outputs. The axiom `metric_emission_subclass` formalizes this relationship. It posits that a specific class of process (X) is a subclass of `bfo:Process` and is characterized by the emission of a specific metric class (Y).

This distinction is critical for governance frameworks. It separates passive operational activities from active telemetry generation. Without this classification, an audit trail lacks the necessary semantic link between the event occurring and the data recorded. The process is the *cause*; the metric is the *effect*. The ontological assertion ensures that for every instance of Process X, there exists a corresponding instance of Metric Y, providing the evidence required for verification.

### 1.1 Formal Declaration of Metric Emission

We declare that the following processes are formally defined by their capacity to emit the specified metrics. This declaration is pursuant to the `metric_emission_subclass` template, wherein the process class is the subject and the metric class is the object of the emission relation.

The relational schema for this axiom is defined as `t_metric_emission_subclass`. The primary key is the unique identifier (`id`), which serves as the reference for the specific mapping. The column `x` represents the Process Class (the emitter), and `y` represents the Metric Class (the emission). The structure ensures that every process listed is explicitly bound to a metric output, facilitating non-repudiation in log analysis.

**Table 1.1: Metric Emission Subclass Mapping**

| id | x (Process Class) | y (Metric Class) |
|---|---|---|
| emission_001 | `DatabaseBackupExecution` | `BackupSuccessRate` |
| emission_002 | `NetworkIngressFiltering` | `PacketLossRatio` |
| emission_003 | `UserAuthenticationFlow` | `FailedLoginAttempts` |
| emission_004 | `APICreditRateLimiter` | `ThrottleTriggerCount` |
| emission_005 | `SecureKeyRotationProcess` | `KeyAgeDays` |

*Table 1.1 illustrates the instantiation of the metric emission axiom. Each row represents a binding declaration where a specific operational process (e.g., `DatabaseBackupExecution`) is ontologically structured to emit a specific metric (e.g., `BackupSuccessRate`). This mapping is deterministic; if the process occurs, the metric must be emitted.*

### 1.2 Operational Verification

In practice, this ontology allows compliance officers to query the system for all processes that emit a metric relevant to a specific control. For instance, if the control requires monitoring of access attempts, the ontology dictates that `UserAuthenticationFlow` is the only valid process class emitting `FailedLoginAttempts`. This prevents ambiguity in log sources and ensures that monitoring tools are attached to the correct process classes.

## 2. SOC2 Security Directives

The Security criteria within SOC2 require the implementation of logical and physical access controls, safeguarding assets against unauthorized access. To operationalize these criteria within a technical environment, we utilize the `soc2_security_subclass` axiom. This axiom classifies a specific directive (X) as a subclass of `cco:DirectiveICE` (Information Control Element) and stipulates that this directive is designed to satisfy a specific SOC2 Security domain (Y).

A `cco:DirectiveICE` represents a specific, implementable instruction—such as a configuration setting, a policy rule, or a workflow step—rather than a vague high-level policy. By mapping these directives to SOC2 domains, we create a granular chain of evidence. The directive is the mechanism of compliance; the SOC2 domain is the objective of compliance.

### 2.1 Classification of Security Directives

We declare under the provisions of the `soc2_security_subclass` template that the following directives are in conformity with the requirement to address specific SOC2 Security domains. The relational schema `t_soc2_security_subclass` captures this mapping. The primary key (`id`) uniquely identifies the directive instance. Column `x` denotes the specific Directive Class, while column `y` denotes the SOC2 Domain Class it addresses.

This structure enforces the constraint that a security directive cannot exist in a vacuum; it must be explicitly tied to a domain within the SOC2 Trust Services Criteria (e.g., Access Control, System Monitoring).

**Table 2.1: SOC2 Security Directive Mapping**

| id | x (Directive Class) | y (SOC2 Domain Class) |
|---|---|---|
| sec_dir_101 | `MandatoryPasswordRotationDirective` | `AccessControl` |
| sec_dir_102 | `IntrusionDetectionSystemRule` | `SystemMonitoring` |
| sec_dir_103 | `EndpointEncryptionProtocol` | `InformationSecurity` |
| sec_dir_104 | `NetworkSegmentationFirewallRule` | `NetworkArchitecture` |
| sec_dir_105 | `PrivilegedAccessReviewWorkflow` | `RiskMitigation` |

*Table 2.1 provides the normative mapping between internal control directives and the SOC2 Security domains. For example, the `MandatoryPasswordRotationDirective` is a subclass of `cco:DirectiveICE` and is explicitly defined as a measure for the `AccessControl` domain.*

### 2.2 Governance and Enforcement

The utilization of this axiom allows for automated gap analysis. By querying the `t_soc2_security_subclass` table, auditors can verify that for every relevant SOC2 Security domain (e.g., `SystemMonitoring`), there exists at least one Directive Class (e.g., `IntrusionDetectionSystemRule`) that is a subclass of `cco:DirectiveICE`. This satisfies the "evidence of the implementation of controls" requirement standard in Type II SOC2 audits.

## 3. SOC2 Privacy Directives

Distinct from general security, the Privacy criteria of SOC2 focus on the collection, use, retention, disposal, and disclosure of personal information in accordance with the entity's privacy notice. The `soc2_privacy_subclass` axiom mirrors the structure of the security subclass but applies specifically to the handling of Personally Identifiable Information (PII) and privacy rights.

This axiom defines a Directive Class (X) as a subclass of `cco:DirectiveICE` that is specifically designed to satisfy a SOC2 Privacy Domain (Y). This distinction is vital for organizations subject to GDPR, CCPA, or other privacy regulations, as it isolates privacy controls from general security controls, ensuring that privacy-by-design principles are formally encoded in the system architecture.

### 3.1 Classification of Privacy Directives

We declare under the provisions of the `soc2_privacy_subclass` template that the following directives are in conformity with the requirement to address specific SOC2 Privacy domains. The relational schema `t_soc2_privacy_subclass` captures this mapping. The primary key (`id`) uniquely identifies the directive instance. Column `x` denotes the specific Directive Class, and column `y` denotes the SOC2 Privacy Domain Class.

This mapping ensures that privacy directives are not misclassified as general security measures. It enforces a specific relationship where the directive's purpose is strictly bound to privacy domains such as `DataRetention` or `UserRights`.

**Table 3.1: SOC2 Privacy Directive Mapping**

| id | x (Directive Class) | y (SOC2 Privacy Class) |
|---|---|---|
| priv_dir_201 | `DataRetentionSchedulePolicy` | `DataRetention` |
| priv_dir_202 | `RightToAccessRequestHandler` | `UserRights` |
| priv_dir_203 | `ConsentManagementProtocol` | `NoticeAndConsent` |
| priv_dir_204 | `DataAnonymizationDirective` | `DisposalAndDeletion` |
| priv_dir_205 | `ThirdPartyDataTransferAgreement` | `DisclosureAndTransfer` |

*Table 3.1 details the binding of privacy-specific directives to their respective SOC2 domains. The `RightToAccessRequestHandler`, for instance, is a directive class specifically implemented to satisfy the `UserRights` domain, ensuring the system can technically facilitate data access requests.*

### 3.2 Audit Trail Verification

When an auditor reviews the system's adherence to privacy criteria, they utilize the `t_soc2_privacy_subclass` table to trace the implementation of privacy notices into executable code. The axiom confirms that the `ConsentManagementProtocol` is not merely a document, but a `cco:DirectiveICE`—an executable control—mapped to the `NoticeAndConsent` domain. This provides the necessary evidence that privacy commitments are technically enforceable.
