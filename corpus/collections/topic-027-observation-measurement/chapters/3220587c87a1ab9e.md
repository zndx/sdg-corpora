# Chapter 4: Formal Specification of Control Directives and Metric Emissions

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required for the precise definition of compliance mechanisms within automated governance systems. We define the structural relationships between operational processes, their observable metric outputs, and the regulatory directives that govern them. The specifications provided herein are intended to serve as the authoritative schema for mapping internal control objectives to the Trust Services Criteria (TSC) defined by the American Institute of Certified Public Accountants (AICPA), specifically focusing on the Security and Privacy domains. By adhering to the axioms presented in this section, compliance engineers ensure that system artifacts are auditable, semantically rich, and derivatively valid against the governing ontology.

## 4.2 Metric Emission Subclasses

### 4.2.1 Ontological Definition and Process Context

In the context of continuous auditing and real-time monitoring, the ability to trace a specific data point back to its generative process is paramount. We define the concept of a Metric Emission Subclass through the axiom that a specific process class ($X$) is a subprocess that necessarily emits a specific metric class ($Y$). This relationship is grounded in the Basic Formal Ontology (BFO), wherein the emitting entity is classified as a `bfo:Process`—an occurrent that unfolds in time and has temporal parts.

The verbalization of this axiom states: "{X} is something that emits metric {Y}." This implies that the instantiation of process $X$ cannot occur without the concurrent or consequent generation of metric $Y$. For example, a "User Authentication Workflow" (the process) inherently emits an "Authentication Latency Metric" (the metric). This linkage allows auditors to query the ontology for all processes that contribute to a specific Key Performance Indicator (KPI) or, conversely, to identify all metrics generated by a specific compliance-critical workflow.

### 4.2.2 Relational Mapping and Implementation

To implement this axiom within a relational database management system (RDBMS) supporting the governance layer, we utilize a normalized structure that isolates the process class from the metric class. The primary key (`id`) serves as a unique identifier for the specific subclass relationship, ensuring that multiple emission relationships can be defined without redundancy. The foreign key relationships are implicit in the semantic constraints: column `x` must reference a valid class defined within the `bfo:Process` hierarchy, while column `y` must reference a valid class within the `sdg:Metric` hierarchy.

The following table embodies the `metric_emission_subclass` axiom. The primary key is the `id` column, which uniquely identifies the mapping rule. The `x` column represents the process class (the emitter), and the `y` column represents the metric class (the emission), constrained such that `y` cannot be null.

| id | x | y |
|---|---|---|
| ems_001 | IncidentEscalationProcess | MeanTimeToEscalateMetric |
| ems_002 | DataIngestionWorkflow | RecordThroughputVolumeMetric |
| ems_003 | IdentityVerificationSequence | FalsePositiveRateMetric |

### 4.2.3 Audit Verification Protocols

When verifying the implementation of these axioms, auditors must confirm that the system logs for the process identified in column `x` contain data fields corresponding to the definition of the metric in column `y`. For instance, for row `ems_001`, the logs for the `IncidentEscalationProcess` must contain time-stamped data sufficient to calculate the `MeanTimeToEscalateMetric`. A failure to capture this data constitutes a violation of the ontological constraint and a deficiency in the monitoring control environment.

## 4.3 SOC2 Security Domain Directives

### 4.3.1 The DirectiveICE Framework

The Security criteria within the SOC2 framework require that logical and physical access controls are safeguarded against unauthorized access. We model these requirements using the concept of a Directive, specifically an `cco:DirectiveICE` (Information Content Entity). This axiom posits that a directive class ($X$) is defined specifically for the SOC2 Security domain ($Y$).

The verbalization of this axiom is: "{X} is something that for soc2 domain {Y}." In this context, $X$ represents the formal policy, procedure, or technical configuration document, while $Y$ is the target domain, specifically "Security." This classification ensures that governance artifacts are not merely stored as unstructured documents but are typed entities within the ontology, directly linked to the compliance framework they satisfy. For example, a "Firewall Configuration Rule" is a directive that exists specifically to satisfy the "Security" domain criteria regarding access controls.

### 4.3.2 Relational Mapping and Implementation

The relational schema for SOC2 Security directives enforces a strict mapping between the directive artifact and the compliance domain. The table `t_soc2_security_subclass` captures this relationship. The `id` column acts as the primary key, ensuring referential integrity for the specific directive instance. Column `x` holds the identifier for the directive class (e.g., `AccessControlPolicy`), and column `y` holds the reference to the SOC2 domain (e.g., `SOC2_Security`).

The table below embodies the `soc2_security_subclass` axiom. The primary key is the `id` column. The `x` column represents the directive class, and the `y` column represents the SOC2 domain class, which is mandatory (NOT NULL).

| id | x | y |
|---|---|---|
| scs_001 | NetworkAccessControlDirective | SOC2_Security |
| scs_002 | EncryptionAtRestStandardDirective | SOC2_Security |
| scs_003 | PrivilegedUserManagementDirective | SOC2_Security |
| scs_004 | IntrusionDetectionProtocolDirective | SOC2_Security |
| scs_005 | ChangeManagementControlDirective | SOC2_Security |

### 4.3.3 Compliance Validation

Validation of these mappings requires a review of the directive content (defined in `x`) to ensure it explicitly addresses the criteria of the SOC2 Security domain (defined in `y`). For instance, `scs_002` must be reviewed to confirm that the `EncryptionAtRestStandardDirective` specifies cryptographic standards compliant with current industry best practices (e.g., AES-256) to meet the Security criteria. The ontological linkage asserts that this directive *belongs* to the security domain; the audit evidence must substantiate that the content *fulfills* the domain requirements.

## 4.4 SOC2 Privacy Domain Directives

### 4.4.1 Distinguishing Privacy from Security

While Security focuses on the protection of systems against unauthorized access, the Privacy criteria within SOC2 focus on the system's collection, use, retention, disclosure, and disposal of personal information in accordance with the entity's privacy notice and generally accepted privacy principles. We model this distinction using a similar axiom structure where a directive class ($X$) is a subclass of `cco:DirectiveICE` intended for the SOC2 Privacy domain ($Y$).

The verbalization remains: "{X} is something that for soc2 domain {Y}." However, the instantiation of $Y$ shifts to "Privacy." This distinction is critical for multi-tenant systems where data residency and consent management are operationalized. For example, a "Customer Consent Revocation Workflow" is a directive specifically designed to satisfy the Privacy criteria regarding user rights.

### 4.4.2 Relational Mapping and Implementation

The `t_soc2_privacy_subclass` table mirrors the structure of the security table but isolates privacy-related directives to facilitate granular reporting. This separation allows compliance officers to generate domain-specific evidence packages without filtering a monolithic directive table. The `id` serves as the primary key. Column `x` contains the privacy directive class, and column `y` contains the `SOC2_Privacy` domain reference.

The following table embodies the `soc2_privacy_subclass` axiom. The primary key is the `id` column. The `x` column represents the directive class, and the `y` column represents the SOC2 Privacy domain, constrained as NOT NULL.

| id | x | y |
|---|---|---|
| scp_001 | DataRetentionScheduleDirective | SOC2_Privacy |
| scp_002 | ConsentManagementProtocolDirective | SOC2_Privacy |
| scp_003 | CrossBorderDataTransferPolicyDirective | SOC2_Privacy |
| scp_004 | RightToBeForgottenProcedureDirective | SOC2_Privacy |
| scp_005 | AnonymizationStandardDirective | SOC2_Privacy |

### 4.4.4 Evidence Collection and User Rights

Auditors evaluating the rows in this table, such as `scp_004`, must verify the operational existence of the `RightToBeForgottenProcedureDirective`. This involves tracing a hypothetical user request through the system to ensure that the directive is executed effectively—meaning personal data is actually deleted or anonymized from all active databases and backups in accordance with the privacy notice. The ontological assertion links the procedure to the domain; the audit trail links the procedure to the outcome.
