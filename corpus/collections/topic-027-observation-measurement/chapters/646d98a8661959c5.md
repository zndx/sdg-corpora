# Chapter 7: Formal Ontology for SOC2 Governance and Metric Emission

## 7.1 Scope and Preamble

This chapter establishes the formal ontological framework required to map operational processes to compliance controls within a System and Organization Controls 2 (SOC2) audit environment. The text delineates the structural relationships between distinct classes of entities—specifically, the emission of metrics by processes and the application of internal directives to SOC2 trust services criteria. The definitions provided herein align with the Basic Formal Ontology (BFO) upper ontology and the Cybersecurity Core Ontology (CCO), ensuring that governance artifacts are machine-readable and semantically rigorous. The following sections detail the axioms governing `metric_emission_subclass`, `soc2_security_subclass`, and `soc2_privacy_subclass`, providing evidence tables that instantiate these relationships within a hypothetical compliance registry.

## 7.2 Metric Emission Subclasses

### 7.2.1 Axiomatic Definition

In accordance with the `metric_emission_subclass` axiom, a specific class of entity is defined as a process that necessarily emits a metric. The Manchester syntax for this axiom is expressed as `Class: {X:Class} SubClassOf: bfo:0000015, sdg:emitsMetric some {Y:Class}`. This verbalizes to: "{X} is something that emits metric {Y}."

This definition relies on the BFO upper-level entity `bfo:0000015` (Process), which denotes an occurrent that unfolds in time and has temporal parts. For a process to be auditable within the framework, it must be causally linked to a data output—a metric—that serves as the quantitative or qualitative evidence of the process's execution. The relationship `sdg:emitsMetric` is functional in nature; without the emission of {Y}, the entity {X} cannot be classified as a compliant process within this ontology.

### 7.2.3 Audit Implications

The registry in Table 7.1 provides the evidence structure necessary for a SOC2 audit. For instance, the `UserAuthenticationFlow` is not merely a conceptual activity; it is formally defined as a process that *must* emit the `FailedLoginAttemptCount`. If an auditor queries the system logs and finds no record of this metric, the ontological definition is violated, implying a control failure. Similarly, the `DataExfiltrationScan` process is validated only through the presence of the `HighRiskFileTransferVolume` metric. This binding ensures that operational visibility is not optional but is structurally mandated by the class definition of the process itself.

## 7.3 SOC2 Security Domain Subclasses

### 7.3.1 Axiomatic Definition

The governance framework further stipulates that specific internal directives are designed to address SOC2 Security criteria. The axiom `soc2_security_subclass` is defined as `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}`. This verbalizes to: "{X} is something that for soc2 domain {Y}."

Here, {X} represents a subclass of `cco:DirectiveICE` (Internal Control Element Directive). These are the specific, implementable policies or procedures enacted by an organization. The object property `sdg:forSOC2Domain` maps this directive to a specific SOC2 Security domain class {Y}, such as "Access Control" or "System Monitoring." This axiom creates the necessary link between the organization's internal governance artifacts and the external regulatory criteria defined by the American Institute of Certified Public Accountants (AICPA) Trust Services Criteria.

**Table 7.2: SOC2 Security Directive Mapping**

| `sec_map_01` | `LogicalAccessControlDirective` | `CC6.1` |

### 7.3.3 Compliance Verification

The mappings in Table 7.2 demonstrate how the organization satisfies the "Security" principle of SOC2. The `LogicalAccessControlDirective` (x) is explicitly defined as a control intended for the `CC6.1` domain (y), which corresponds to "Logical and Physical Access Controls." By formally defining this relationship in the ontology, the organization automates the traceability of its controls. When an auditor reviews `CC6.1`, the system can automatically retrieve all directives of type {X} that have `sdg:forSOC2Domain` equal to `CC6.1`. This includes the `NetworkSegmentationDirective` and `DataTransmissionEncryptionDirective`, providing a comprehensive, ontology-driven evidence package for that specific criterion.

## 7.4 SOC2 Privacy Domain Subclasses

### 7.4.1 Axiomatic Definition

Distinct from general security, the Privacy trust service criteria require specific handling of personal information. The axiom `soc2_privacy_subclass` follows the same structural pattern as the security subclass but targets a different set of criteria: `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}`. This verbalizes to: "{X} is something that for soc2 domain {Y}."

In this context, while {X} remains a subclass of `cco:DirectiveICE`, the range of the `sdg:forSOC2Domain` property is restricted to classes within the SOC2 Privacy taxonomy (e.g., criteria related to notice, consent, and disposal). This distinction is critical for maintaining the separation of concerns between protecting the system (Security) and respecting the rights of data subjects (Privacy).

### 7.4.2 Relational Implementation

The following table instantiates the `t_soc2_privacy_subclass` schema. It embodies the axiom by listing DirectiveICE classes ({X}) that are specifically authored to satisfy SOC2 Privacy domains ({Y}). The `id` is the unique identifier for the mapping, with `x` and `y` serving as foreign keys to the directive registry and the privacy criteria definitions.

**Table 7.3: SOC2 Privacy Directive Mapping**

| id | x (Directive Class) | y (SOC2 Domain Class) |
| :--- | :--- | :--- |

| `priv_map_02` | `DataSubjectAccessDirective` | `P2.2` |
| `priv_map_03` | `ConsentManagementDirective` | `P1.2` |
| `priv_map_04` | `DataDisposalSanitizationDirective` | `P2.1` |
| `priv_map_05` | `ThirdPartyDataTransferDirective` | `P3.1` |

### 7.4.4 Governance and Enforcement

Table 7.3 illustrates the application of the privacy ontology to operational governance. The `PrivacyNoticeDistributionDirective` is ontologically bound to domain `P1.1` (Privacy Notice and Communication). This binding enforces a semantic constraint: the directive cannot be reclassified or misinterpreted as a security control because its definition inherently includes the property `forSOC2Domain` with the value `P1.1`. Furthermore, the `DataSubjectAccessDirective` maps to `P2.2` (Choices for Data Use), ensuring that the organization's technical and administrative mechanisms for handling user requests are formally linked to the regulatory requirement for choice and consent. This granular mapping allows for precise gap analysis; if the ontology contains a directive for `P3.1` (Third-Party Data Transfer) but the implementation is missing, the discrepancy is immediately evident in the model.
