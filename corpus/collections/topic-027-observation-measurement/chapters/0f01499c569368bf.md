# Chapter 4: Ontological Mapping of GRC Frameworks and Metric Emission

## 4.0 Scope and Preamble

This chapter establishes the formal ontological mappings required to align operational processes with the System and Organization Controls (SOC) 2 Trust Services Criteria. It defines the structural relationships between governance directives, security and privacy domains, and the quantitative metrics emitted during process execution. The provisions herein detail how specific classes of directives are subclassed to target distinct SOC2 domains and how process-oriented entities are axiomatized to emit measurable performance indicators. These definitions serve as the normative basis for automated compliance auditing and continuous monitoring systems.

## 4.1 Metric Emission Subclass Axioms

### 4.1.1 Definition and Formal Structure

In accordance with the Basic Formal Ontology (BFO), a process is defined as an occurrent that unfolds in time and has temporal parts. Within the context of governance frameworks, it is insufficient to merely define the existence of a process; one must formally characterize the output of that process. The Metric Emission Subclass axiom provides a mechanism to link a process class (X) to a specific metric class (Y) that it generates.

The formal axiom is expressed as:
**Class: {X:Class} SubClassOf: bfo:0000015, sdg:emitsMetric some {Y:Class}**

Verbalization: **{X} is something that emits metric {Y}**

This relationship asserts that any instance of class X is necessarily involved in the generation of data corresponding to class Y. This is not a contingent relationship (i.e., it may sometimes emit a metric) but a necessary one (i.e., it always emits the metric by its very definition). This distinction is critical for audit trails where the absence of a metric implies the non-execution of the process.

### 4.1.2 Implementation in Compliance Monitoring

When designing automated governance frameworks, architects must ensure that the data model reflects the dependency between the control activity and the evidence it produces. For example, a "Vulnerability Scanning Process" is ontologically structured to emit a "Severity Score Metric." If the scanning process executes but no metric is recorded, the system flags a logical inconsistency, indicating a potential failure in the logging infrastructure or the process itself.

### 4.1.3 Regulatory Implications

Under the provisions of various regulatory frameworks (e.g., GDPR, HIPAA, SOC2), the ability to demonstrate the execution of a control is paramount. By utilizing the Metric Emission Subclass axiom, organizations move from a checklist-based compliance model to an evidence-based model. Auditors may query the ontology to verify that for every instance of `x` (e.g., a specific access review event), a corresponding instance of `y` (e.g., a numeric count of accounts reviewed) exists. This alignment ensures that the "reasonable and prudent parent standard" of governance is met through rigorous, data-driven verification.

## 4.2 SOC2 Security Domain Subclass Axioms

### 4.2.1 Definition and Formal Structure

The SOC2 framework is predicated on five Trust Services Criteria (TSC): Security, Availability, Processing Integrity, Confidentiality, and Privacy. The Security criterion is foundational, containing the requirements common to all other criteria. To map internal governance directives to this criterion, we employ the SOC2 Security Subclass axiom.

The formal axiom is expressed as:
**Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}**

Verbalization: **{X} is something that for soc2 domain {Y}**

In this structure, class X represents a specific internal directive, policy, or control implementation (subclass of `cco:DirectiveICE`, which denotes an Internal Control Environment directive). Class Y represents the specific SOC2 domain, typically the "Security" criteria category (e.g., CC6.1, CC6.6). This axiom asserts that the directive X exists specifically to address the requirements defined within domain Y.

### 4.2.2 Mapping Directives to Security Criteria

The Security criteria (CC6) generally focuses on the management of system access, the prevention of unauthorized access, and the detection of such attempts. Directives subclassed under this axiom must demonstrate a direct lineage to these specific control points. It is insufficient for a directive to be generally about "security"; it must be ontologically linked to the specific domain object Y within the SOC2 taxonomy.

The following table details directives that are formally subclassed to address the SOC2 Security domain, consistent with the `t_soc2_security_subclass` schema.

| SS-002 | NetworkBoundaryProtectionDirective | SOC2_Security_CC6.6 |
| SS-003 | MalwareDetectionProtocol | SOC2_Security_CC6.7 |
| SS-004 | PrivilegedAccessReviewPolicy | SOC2_Security_CC6.2 |

*Table 4.2 Note: The primary key is `id`. Column `x` denotes the specific directive class, and column `y` denotes the SOC2 Security domain code. This mapping ensures that every directive in `x` is auditable against the specific criteria in `y`.*

### 4.2.3 Compliance Verification

When an auditor evaluates the organization's compliance with SOC2 Security criteria, they will reference the mappings defined in Table 4.2. The auditor must verify that the `LogicalAccessControlDirective` (SS-001) is not only documented but actively enforced. The ontological linkage guarantees that the directive is categorized correctly under the Security domain, preventing "control drift" where a security policy is mistakenly categorized under Availability or Privacy.

Action: Ensure that all internal control documentation is updated to reflect the specific SOC2 domain codes listed in column `y`. Any references to the directive in member communications or governance reports must cite the associated domain to maintain traceability.

## 4.3 SOC2 Privacy Domain Subclass Axioms

### 4.3.1 Definition and Formal Structure

While Security is a prerequisite, the Privacy criterion (CC7) addresses the criteria for the collection, use, retention, disclosure, and disposal of personal information. Distinct from security, which protects against unauthorized access, Privacy concerns the rights of the data subject and the organization's adherence to its privacy notice.

The formal axiom is expressed as:
**Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:forSOC2Domain some {Y:Class}**

Verbalization: **{X} is something that for soc2 domain {Y}**

Although the structure mirrors the Security axiom, the semantic content of class Y changes to reflect the Privacy criteria (e.g., CC7.1, CC7.2, CC7.3). Class X represents directives specifically crafted to handle PII (Personally Identifiable Information) lifecycle management and consent.

### 4.3.2 Mapping Directives to Privacy Criteria

Directives falling under this subclass must address the handling of personal information in accordance with the organization's privacy notice and the criteria set forth by the AICPA. This includes directives on how data is collected, the purposes for which it is used, and how consent is obtained.

### 4.3.3 Governance and Enforcement

The implementation of Privacy directives requires a distinct governance approach compared to Security. While Security directives often rely on technical controls (firewalls, encryption), Privacy directives rely heavily on procedural and legal controls (contracts, notices, consent logs).
