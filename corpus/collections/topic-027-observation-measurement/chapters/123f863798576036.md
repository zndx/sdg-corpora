# Chapter 4: Ontological Mapping of SOC2 Control Frameworks and Metric Emission Processes

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures required to map operational processes to metric emissions and align internal control directives with the Trust Services Criteria (TSC) of the System and Organization Controls (SOC2) framework. In accordance with rigorous governance standards, the definitions provided herein establish a semantic layer between raw operational data and compliance reporting requirements. The objective is to ensure that all assertions regarding system security and privacy are grounded in verifiable, axiomatically defined relationships. By formalizing these mappings, organizations may achieve a deterministic audit trail, wherein every control directive is traceable to a specific domain, and every process is explicitly linked to its observable outputs.

## 4.2 Metric Emission Subclasses

### 4.2.1 Definition and Axiomatic Structure

In the context of continuous monitoring and assurance, a fundamental distinction must be drawn between the operational activity itself and the quantitative data generated by that activity. We define this relationship through the axiom of *Metric Emission*. Formally, this asserts that a specific class of process (*X*) is a subclass of `bfo:Process` (as defined by the Basic Formal Ontology) and holds the property of `sdg:emitsMetric` towards a specific class of metric (*Y*).

This ontological constraint serves a critical function in governance frameworks: it prevents the ambiguity of "orphaned" metrics. Under this axiom, a metric cannot exist as a standalone artifact; it must be the emission of a defined process. This aligns with the evidentiary standards required in audit reporting, where data points must be attributable to a system event or transaction. The verbalization of this axiom is: *{X} is something that emits metric {Y}*.

### 4.2.2 Implementation and Evidence

When implementing this structure within a governance database, the entity class *X* represents the automated or manual procedure (e.g., a log aggregation script, a quarterly access review), while *Y* represents the resulting measurement (e.g., "Failed Login Count," "Access Review Completion Rate"). The integrity of the compliance report depends on the persistence of this relationship. If the process *X* is decommissioned, the validity of the metric *Y* is immediately called into question, triggering an alert in the control environment.

To illustrate the application of this axiom, consider the following data table. This table represents the instantiation of the `t_metric_emission_subclass` schema, documenting the specific processes defined within the information security management system (ISMS) and the corresponding metrics they emit.

As evidenced in Table 4.1, the `LogIngestionProcess` is formally defined as a process that emits the `IngestionLatencyMetric`. This mapping allows auditors to verify that the latency figures reported in the quarterly executive summary are derived from a specific, controlled system activity, rather than ad-hoc queries. The primary key (`id`) ensures that each mapping is unique, while the foreign key structure implicit in the class names allows for joins to broader process taxonomies.

### 4.2.3 Audit Verification

During a Type II examination, auditors will sample instances of *X* to validate the emission of *Y*. For instance, the `VulnerabilityScanningProcess` (em-005) must demonstrate a direct causal link to the `CriticalSeverityCountMetric`. If the scanning process executes but fails to output the metric count, the axiom is violated, indicating a failure in the monitoring subsystem. Therefore, maintaining the relational integrity of Table 4.1 is not merely a data modeling exercise but a compliance requirement.

## 4.3 SOC2 Security Domain Directives

### 4.3.1 Definition and Axiomatic Structure

The second ontological concept addresses the classification of internal directives relative to the SOC2 Security Trust Services Criteria. We define a subclass relationship wherein a specific directive class (*X*) is a subclass of `cco:DirectiveICE` (Information Control Element) and is designated `sdg:forSOC2Domain` for a specific domain class (*Y*).

The `cco:DirectiveICE` entity refers to the specific, implementable control statements—policies, standards, or procedures—that govern the behavior of the system. The `sdg:forSOC2Domain` property links this directive to the relevant SOC2 category, such as "CC6.1" (Logical and Physical Access Controls) or "CC7.2" (System Monitoring). The verbalization of this axiom is: *{X} is something that for soc2 domain {Y}*.

This classification is essential for gap analysis. By asserting that a directive belongs to a specific domain, the organization creates a formal mapping between its internal governance documentation and the external criteria used by certified public accountants (CPAs) to evaluate the system.

### 4.3.2 Implementation and Evidence

The following table provides the relational instantiation of the `t_soc2_security_subclass` schema. It lists the specific directives established by the governance body and maps them to the relevant SOC2 Security domains. This mapping serves as the "Index of Compliance" for the security criteria.

**Table 4.2: Security Directive to SOC2 Domain Mappings**

| id | x (Directive Class) | y (SOC2 Domain Class) |
| :--- | :--- | :--- |
| sec-001 | `LogicalAccessControlDirective` | `SOC2_CC6_1` |
| sec-002 | `SystemMonitoringDirective` | `SOC2_CC7_2` |
| sec-003 | `ChangeManagementDirective` | `SOC2_CC8_1` |
| sec-004 | `IncidentResponseDirective` | `SOC2_CC9_1` |
| sec-005 | `DataTransmissionEncryptionDirective` | `SOC2_CC6_7` |

In Table 4.2, the `LogicalAccessControlDirective` (sec-001) is axiomatically tied to `SOC2_CC6_1`. This means that any evidence gathered for the "Logical Access Control" criteria must be traceable back to this specific directive. The directive acts as the parent node for all associated procedures and evidence artifacts.

### 4.3.3 Governance and Compliance

From a governance perspective, this structure facilitates automated compliance testing. If a query retrieves all directives associated with `SOC2_CC6_1`, the system must return `LogicalAccessControlDirective`. If the system returns a null set, or if the directive has not been populated with implementing procedures, a control deficiency is flagged. Furthermore, this structure supports the "Common Criteria" mapping required by regulators, ensuring that the organization's internal nomenclature (`x`) is strictly aligned with the external standard (`y`).

## 4.4 SOC2 Privacy Domain Directives

### 4.4.1 Definition and Axiomatic Structure

While security directives focus on the protection of infrastructure, privacy directives focus on the handling of Personally Identifiable Information (PII) in accordance with the Privacy Criteria (2017) of the AICPA. The ontological structure mirrors that of the security domain: a directive class (*X*) is a subclass of `cco:DirectiveICE` and holds the property `sdg:forSOC2Domain` for a privacy-specific domain class (*Y*).

The distinction here is the semantic content of *Y*. In this context, *Y* refers to privacy-specific criteria such as "P1" (Notice and Consent) or "P2" (Choice and Consent). The axiom remains: *{X} is something that for soc2 domain {Y}*. However, the instantiation of these classes requires a distinct set of controls that address data subject rights, data minimization, and third-party privacy risks.

### 4.4.2 Implementation and Evidence

Table 4.3 illustrates the `t_soc2_privacy_subclass` schema. It documents the directives that satisfy the Privacy Trust Services Criteria. These directives are critical for organizations subject to GDPR, CCPA, or other privacy regulations, as they provide the formal link between regulatory obligations and the SOC2 audit framework.

**Table 4.3: Privacy Directive to SOC2 Domain Mappings**

| id | x (Directive Class) | y (SOC2 Domain Class) |
| :--- | :--- | :--- |
| prv-001 | `DataCollectionConsentDirective` | `SOC2_P1_NoticeAndConsent` |
| prv-002 | `DataSubjectRightsDirective` | `SOC2_P2_ChoiceAndConsent` |
| prv-003 | `DataDisposalAndRetentionDirective` | `SOC2_P6_Disposal` |
| prv-004 | `DataTransferDirective` | `SOC2_P8_Transfer` |
| prv-005 | `PrivacyIncidentBreachDirective` | `SOC2_P9_Notification` |

Consider the entry prv-002, `DataSubjectRightsDirective`. This directive is axiomatically bound to `SOC2_P2_ChoiceAndConsent`. In practice, this means the directive must contain the procedures by which the organization honors requests for access, deletion, or portability of PII. During an audit, the examiner will review the `DataSubjectRightsDirective` to ensure it adequately addresses the requirements of `SOC2_P2`.

### 4.4.3 Regulatory Alignment

The separation of Security (Table 4.2) and Privacy (Table 4.3) directives into distinct relational tables—despite sharing a common superclass structure—allows for granular reporting. An organization may be fully compliant with Security criteria but still be maturing its Privacy framework. By maintaining these mappings separately, the Chief Information Security Officer (CISO) and the Data Privacy Officer (DPO) can generate targeted reports. The `id` column serves as the unique reference for these controls in the GRC (Governance, Risk, and Compliance) tooling, ensuring that updates to the Privacy Criteria (e.g., updates to the AICPA guide) can be propagated to the relevant *X* classes without disrupting the Security mappings.

## 4.5 Conclusion

The formalization of these three axioms—Metric Emission, SOC2 Security Directives, and SOC2 Privacy Directives—provides the scaffolding for a robust, evidence-based compliance program. The tables included in this chapter represent the minimum required data structure to support such a verification process. It is incumbent upon the governance committee to maintain these tables, ensuring that as new processes are introduced or new directives are authored, they are immediately axiomatized within the framework described herein.
