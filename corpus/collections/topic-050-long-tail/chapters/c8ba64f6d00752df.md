# Chapter 4: Quantitative Evidence and Compliance Metrics in Security Governance

## 4.1 Scope and Framework Applicability

This chapter delineates the formal ontological structures governing the integration of statistical evidence within regulatory compliance frameworks, specifically focusing on the Payment Card Industry Data Security Standard (PCI DSS). The content herein is designed for security architects, compliance auditors, and data governance officers who require a rigorous method for mapping quantitative security metrics to directive controls. We establish a taxonomy where Information Content Entities (ICE) are classified either as prescriptive directives or descriptive observations, linked through deterministic axioms that define baseline rates, evidence correlation, and probabilistic transformations. The following sections provide a detailed analysis of five core axioms, supported by relational data schemas that instantiate these concepts within a controlled audit environment.

## 4.2 PCI DSS Requirements as Directives

### 4.2.1 Ontological Definition
The foundational unit of governance within this framework is the `pci_dss_requirement`. Formally, this concept is axiomatized as a subclass of `cco:DirectiveICE`, which represents prescriptive information entities intended to constrain or guide behavior. The relationship `sdg:pciDssRequirement` links a specific governance control (the subject) to a measurable metric or outcome class (the object).

In practice, this axiom asserts that for a requirement to be auditable, it must be intrinsically bound to a quantifiable metric. This moves the compliance exercise from a binary "pass/fail" checklist to a continuous assurance model. The directive does not merely exist; it *requires* a specific state or performance indicator defined by the target class.

### 4.2.2 Relational Implementation
The implementation of this axiom relies on a primary relational structure where the requirement entity is mapped to a specific metric instance. The foreign key constraint ensures that every PCI DSS requirement is anchored to a valid, pre-defined metric entity, preventing orphaned controls within the governance database.

## 4.3 Lift with Baseline Rate

### 4.3.1 Statistical Context and Axiomatic Structure
To evaluate the efficacy of a security control, auditors must utilize statistical measures that distinguish normal operational noise (baseline) from anomalous security signals. The axiom `lift_with_baseline_rate` defines a subclass of `cco:DescriptiveICE`—an entity describing a state of affairs—possessing the property `sdg:hasBaselineRate`.

"Lift" in this context refers to the ratio of the probability of a security event occurring given the presence of a specific control (or lack thereof) to the baseline probability of that event in the general population. A high lift value indicates a strong correlation between the observed metric and the security outcome. The axiom posits that any descriptive metric claiming to show "lift" must explicitly reference a baseline rate entity. This baseline rate is not merely a numerical value but is modeled as an independent evidence entity (`t_evidence_correlated_with`), allowing the baseline to be audited for its own validity and derivation.

### 4.3.2 Baseline Dependency and Data Lineage
The relational structure for this concept enforces a strict dependency: a lift metric cannot exist without a defined baseline evidence correlation. This prevents the manipulation of security statistics by using undefined or shifting baselines.

The following table demonstrates the registration of lift metrics. Note that the `y` column references the ID of the evidence entity that serves as the baseline.

| id | x | y |
| :--- | :--- | :--- |
| metric_encryption_lift | EncryptionFailureLift | evidence_baseline_cipher |
| metric_access_lift | UnauthorizedAccessLift | evidence_baseline_auth |
| metric_audit_lift | AuditTrailGapLift | evidence_baseline_log |

**Table 4.2:** Definition of Lift Metrics relative to Baseline Evidence (`t_lift_with_baseline_rate`).

Here, `x` denotes the specific lift metric class (e.g., `EncryptionFailureLift`), while `y` acts as a foreign key to the evidence table. This structure ensures that the calculation of lift is always traceable to a specific evidentiary root, satisfying the axiom `X is something that has baseline rate Y`.

## 4.4 Evidence Correlated With

### 4.4.1 The Nature of Evidentiary Correlation
The `evidence_correlated_with` axiom provides the structural mechanism for defining the relationships between disparate data points within a security investigation. It is defined as a `cco:DescriptiveICE` possessing the property `sdg:evidenceCorrelatedWith`.

In the context of the ontology, this axiom is recursive and structural. It asserts that a specific piece of evidence (X) is correlated with another entity (Y). Crucially, the schema dictates that the target of this correlation (Y) must be an instance of a `lift_with_baseline_rate`. This creates a bidirectional semantic link: the evidence provides the empirical basis for the metric, and the metric describes the statistical behavior of the evidence.

### 4.4.2 Establishing the Feedback Loop
This relationship is critical for "evidence-anchored" auditing. It prevents the citation of generic statistical trends without grounding them in specific, observed evidence. For example, a "baseline rate" for authentication failures is not an abstract number; it is derived from `evidence_baseline_auth`, which is explicitly correlated with the `UnauthorizedAccessLift` metric.

The table below encodes these correlations, completing the dependency chain initiated in the previous section.

| id | x | y |
| :--- | :--- | :--- |
| evidence_baseline_cipher | ObservedWeakCipherUsage | metric_encryption_lift |
| evidence_baseline_auth | ObservedFailedLogins | metric_access_lift |
| evidence_baseline_log | ObservedLogGaps | metric_audit_lift |

**Table 4.3:** Correlation of Evidence Entities to Lift Metrics (`t_evidence_correlated_with`).

In this arrangement, `x` represents the raw or processed evidence class (e.g., `ObservedWeakCipherUsage`), and `y` references the lift metric ID. This satisfies the verbalization "{X} is something that evidence correlated with {Y}" and enforces the foreign key constraint back to the lift metrics table, creating a closed loop of verification.

## 4.5 Pignistic Transformation

### 4.5.1 Decision Making Under Uncertainty
When security systems generate alerts or when auditors evaluate incomplete data, they often operate under conditions of uncertainty rather than precise probability. The `pignistic_transformation` axiom introduces a method for converting belief functions—mathematical representations of confidence derived from evidence—into probabilistic distributions suitable for decision-making.

Axiomatically, this is a `cco:DescriptiveICE` that `sdg:hasPignisticTransform`. The "Pignistic Transformation" refers to the specific mathematical operation (often associated with the Dempster-Shafer theory) that bets on the probability of hypotheses. In this governance framework, it ensures that subjective belief or confidence scores are rigorously transformed into objective probabilities before they can influence compliance decisions.

### 4.5.2 Transformation Mapping
The relational schema requires that any entity undergoing a pignistic transformation must be linked to a valid lift metric. This implies that the transformation is applied to the lift metric to normalize it or to convert a confidence score regarding the lift into a hard probability for reporting.

The following table catalogs instances where belief functions regarding security metrics are transformed for reporting.

| id | x | y |
| :--- | :--- | :--- |
| transform_encryption | EncryptionBeliefFunction | metric_encryption_lift |
| transform_access | AccessBeliefFunction | metric_access_lift |
| transform_audit | AuditBeliefFunction | metric_audit_lift |

**Table 4.4:** Pignistic Transformations applied to Lift Metrics (`t_pignistic_transformation`).

In this schema, `x` identifies the belief function or uncertain evidence class, while `y` identifies the target lift metric. This ensures that the output of the transformation (a probability) is strictly tied to the metric being evaluated, maintaining the axiom "{X} is something that has pignistic transform {Y}".

## 4.6 Evidence Independent Of

### 4.6.1 Isolation of Variables
To validate the integrity of a security metric, auditors must frequently demonstrate that specific variables do not influence others, thereby proving that a signal is genuine and not the result of a confounding variable. The `evidence_independent_of` axiom defines a `cco:DescriptiveICE` possessing the property `sdg:evidenceIndependentOf`.

This concept is essential for establishing the "lift" discussed in Section 4.3. If the baseline rate or the observed lift is influenced by an external factor that should be irrelevant (e.g., the time of day for a protocol that should be time-agnostic), the metric is compromised. The axiom formally asserts the independence of evidence X from entity Y.

### 4.6.2 Validating Metric Integrity
The schema links independent evidence to a lift metric. This serves as a constraint or a validation rule: the metric `y` is only considered valid if the independence assertion regarding `x` holds true. For instance, the lift metric for encryption failures should be independent of the specific user agent string, assuming the encryption protocol is universal.

**Table 4.5:** Assertions of Evidence Independence relative to Metrics (`t_evidence_independent_of`).

Here, `x` represents the variable that is asserted to be independent (e.g., `UserAgentString`), and `y` is the metric ID. This structure enforces the axiom "{X} is something that evidence independent of {Y}", ensuring that the metric `y` is not artificially skewed by the factor `x`.
