# Chapter 4: System Call Classification and eBPF Verification Protocols

## 4.1 Scope and Preamble

This chapter establishes the ontological framework governing the classification of kernel-level system calls (syscalls) and the verification of Extended Berkeley Packet Filter (eBPF) programs within a secure operating environment. It delineates the structural relationships between designative information content entities, their respective security tiers, and the auditing mechanisms required to maintain system integrity. The definitions provided herein are binding for all compliance audits, kernel hardening procedures, and security architecture reviews involving the `04_ebpf_kernel` family of components.

## 4.2 Security Tier Stratification

### 4.2.1 Axiomatic Definition
In accordance with the axiom `syscall_at_security_tier`, any entity classified as a Designative Information Content Entity (ICE) must be explicitly mapped to a specific security tier. This mapping is not merely nominal but serves as a functional constraint for kernel execution policies. The relationship asserts that `{X}` is something that at security tier `{Y}`, where `{X}` represents the syscall class and `{Y}` represents the security classification.

This stratification ensures that resource requests originating from user-space are subject to the appropriate privilege checks prior to kernel execution. Failure to correctly map a syscall to its designated tier results in a violation of the Principle of Least Privilege and may lead to unauthorized privilege escalation.

### 4.2.2 Implementation and Compliance
The following table details the requisite mappings for standard file system and process control operations. These entries are derived from the deterministic schema `t_syscall_at_security_tier`, where the primary key `id` ensures referential integrity within the governance framework.

| id | x | y |
| :--- | :--- | :--- |
| ST-101 | Syscall_Open | SecurityTier_UserBoundary |
| ST-102 | Syscall_Mount | SecurityTier_CriticalKernel |
| ST-103 | Syscall_Chmod | SecurityTier_FileSystem |
| ST-104 | Syscall_Kill | SecurityTier_ProcessControl |
| ST-105 | Syscall_Setuid | SecurityTier_PrivilegeEscalation |

**Table 4.1:** System Call to Security Tier Mappings. The column `x` denotes the Designative ICE (the syscall), while `y` denotes the mandatory security tier classification.

### 4.2.3 Audit Implications
Auditors must verify that the kernel's syscall table references the `y` value defined in Table 4.1 for every invocation of entity `x`. Any deviation—such as executing `Syscall_Mount` at `SecurityTier_UserBoundary`—shall be flagged as a Critical Control Failure (CCF).

## 4.3 Subsystem Equivalence and Containment

### 4.3.1 Axiomatic Definition
The axiom `syscall_equiv_in_subsystem` provides a necessary and sufficient condition for syscall classification. It states that a Class `{X}` is EquivalentTo the intersection of a Designative ICE and the property `inSyscallSubsystem` some `{Y}`. In natural language, this defines a specific class of syscalls solely by their membership and operation within a distinct kernel subsystem `{Y}`.

This equivalence relation is critical for modular kernel auditing, as it isolates the functional scope of a syscall. For instance, a network operation is defined not just by its name, but by its existential dependency on the Network Subsystem.

### 4.3.2 Subsystem Containment Matrix
To enforce modular security boundaries, the following equivalence classes have been established. These data points populate the `t_syscall_equiv_in_subsystem` table, linking specific syscall classes to their governing subsystems.

| id | x | y |
| :--- | :--- | :--- |
| SS-201 | Syscall_Bind | Subsystem_NetworkStack |
| SS-202 | Syscall_Listen | Subsystem_NetworkStack |
| SS-203 | Syscall_Accept | Subsystem_NetworkStack |
| SS-204 | Syscall_Socket | Subsystem_NetworkStack |
| SS-205 | Syscall_Sendto | Subsystem_NetworkStack |

**Table 4.2:** Subsystem Equivalence Definitions. Column `x` represents the syscall class, and `y` represents the subsystem class. The `EquivalentTo` axiom dictates that `x` has no meaning outside the context of `y`.

### 4.3.3 Governance Notes
When reviewing kernel logs, compliance officers must ensure that syscalls listed in column `x` are exclusively invoking interfaces provided by the subsystem in column `y`. Cross-subsystem invocation (e.g., `Syscall_Bind` interacting directly with `Subsystem_Graphics`) indicates a kernel space corruption or a rootkit injection attempt.

## 4.4 eBPF Program Verification and Safety

### 4.4.1 Axiomatic Definition
The introduction of programmable packet filtering and tracing via eBPF necessitates a rigorous verification protocol. The axiom `ebpfprogram_verified_safe` governs this domain. It asserts that a Class `{X}` (an eBPF program Artifact) is a SubClassOf `cco:Artifact` and must possess the property `verifiedSafeBy` some `{Y}`.

Verbalized, `{X}` is something that verified safe by `{Y}`. This axiom establishes a dependency relationship where the safety of the executable artifact is contingent upon the validation performed by a verification agent or process `{Y}`.

### 4.4.2 Verification Registry
All eBPF programs loaded into the kernel must be registered in the `t_ebpfprogram_verified_safe` table. This registry serves as the evidence base for compliance checks, ensuring that no unverified code is executing in ring 0.

| id | x | y |
| :--- | :--- | :--- |
| EP-301 | Program_XDP_Firewall_v1 | Verifier_StaticAnalysis_Engine |
| EP-302 | Program_Trace_Sys_Enter | Verifier_JIT_Compliance_Checker |
| EP-303 | Program_Sock_Ops_LB | Verifier_StaticAnalysis_Engine |
| EP-304 | Program_KProbe_HashMap | Verifier_Resource_Limit_Validator |

**Table 4.3:** eBPF Program Verification Status. Column `x` lists the specific program artifact, and `y` identifies the verification mechanism that has validated the program's safety and memory access constraints.

### 4.4.3 Enforcement Standards
The `{Y}` entity (Verifier) must satisfy the requirements of the BPF Virtual Machine specification, specifically regarding loop termination and pointer arithmetic. If a program `{X}` is found in memory but lacks a corresponding entry in Table 4.3, the runtime environment must immediately terminate the process and trigger a kernel panic (oops) to preserve system integrity.

## 4.5 Audit Trails for Designative Entities

### 4.5.1 Axiomatic Definition
To ensure non-repudiation and forensic readiness, specific designative entities are subject to mandatory auditing. The axiom `syscall_audited_by` formalizes this requirement. It states that a Class `{X}` (a Designative ICE) is a SubClassOf `cco:DesignativeICE` and possesses the property `auditedBy` some `bfo:0000015` (a Process).

This axiom creates a hard linkage between the definition of a syscall and the process that observes it. It implies that for `{X}` to exist or be invoked in a compliant system, an audit process must be actively attached and recording the invocation parameters.

### 4.5.2 Auditable Entity Catalog
The following table identifies high-value syscalls that require active auditing by the system monitoring framework. The schema `t_syscall_audited_by` captures these entities.

| id | x |
| :--- | :--- |
| AU-401 | Syscall_Execve |
| AU-402 | Syscall_Ptrace |
| AU-403 | Syscall_Fork |
| AU-404 | Syscall_Vfork |
| AU-405 | Syscall_Clone |

**Table 4.4:** Mandatory Audit Targets. The column `x` lists the Designative ICEs that are subject to the `auditedBy` property. The auditor process (referenced by `bfo:0000015`) is implicit in the system configuration but mandatory for these entries.

### 4.5.3 Forensic Requirements
Data logs generated by the auditing process for entities in Table 4.4 must be retained for a minimum of 365 days and must be immutable. The audit trail must capture the return value (see Section 4.6) and all pointer arguments passed to the syscall.

## 4.6 Return Type Constraints and Cardinality

### 4.6.1 Axiomatic Definition
Type safety is a fundamental component of kernel stability. The axiom `syscall_max_one_return` imposes a cardinality constraint on the return values of syscalls. It asserts that a Class `{X}` (a Designative ICE) is a SubClassOf `cco:DesignativeICE` and has the property `hasReturnType` max 1 `{Y}`.

This constraint `{X}` is a designative information content entity that has a maximum of one return type `{Y}`. This prevents ambiguous return states where a syscall might return varying data types depending on execution flow, which is a common source of exploitation in type-unsafe environments.

### 4.6.2 Return Type Specification
The following table enforces the single-type constraint for critical system operations. The `t_syscall_max_one_return` schema maps the syscall to its singular, defined return type.

| id | x | y |
| :--- | :--- | :--- |
| RT-501 | Syscall_Read | Type_SSizeT |
| RT-502 | Syscall_Write | Type_SSizeT |
| RT-503 | Syscall_Close | Type_Integer |
| RT-504 | Syscall_Exit | Type_Void |
| RT-505 | Syscall_Getpid | Type_PidT |

**Table 4.5:** Syscall Return Type Constraints. Column `x` is the syscall, and `y` is the strictly defined return type. The `max 1` cardinality ensures that `Syscall_Read` cannot return `Type_Integer` under any error condition that bypasses the standard error reporting mechanism (e.g., returning -1 cast as `SSizeT`).

### 4.6.3 Compliance Validation
During the certification phase, the kernel ABI must be tested to ensure that the return type `y` is invariant for all execution paths of syscall `x`. Any polymorphism in return types must be resolved within the definition of `y` (e.g., a union type explicitly defined as `y`), rather than by returning distinct types.
