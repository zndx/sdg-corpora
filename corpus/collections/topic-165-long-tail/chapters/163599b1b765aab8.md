# Governance Frameworks: PCI-DSS Implementation and Audit Evidence

This chapter delineates the formal ontological structures underpinning PCI-DSS compliance frameworks, specifically focusing on the integration of directive information content entities within relational governance models. The scope encompasses the definition of requirement classes, the specification of control targets, and the evidentiary traces necessary for audit verification. By mapping these concepts to a deterministic schema, auditors and compliance officers can ensure that regulatory mandates are not only semantically defined but also operationally instantiated within database management systems.

## 1. PCI-DSS Requirement Mapping

The foundational element of any compliance regime is the formal definition of the requirement itself. Within the ontology, the axiom `pci_dss_requirement` establishes a taxonomic link between a specific governance class and the broader PCI-DSS standard. This relationship posits that a class `X` is a subclass of `cco:DirectiveICE` (Information Content Entity) and maintains a specific relationship `sdg:pciDssRequirement` with another class `Y`.

In practical terms, this axiom allows the organization to categorize internal policies or data objects as specific instantiations of regulatory mandates. For example, a class representing "Network Firewall Configuration" can be formally asserted as a realization of "PCI-DSS Requirement 1." This mapping is not merely semantic; it serves as the primary key for downstream relational integrity, ensuring that every internal control object can trace its lineage to a specific article of compliance.

The relational schema for this concept enforces a foreign key constraint, linking the requirement instance to its equivalent specification. This structure prevents orphaned compliance artifacts; a requirement cannot exist within the system unless it is properly contextualized within a specification-target tuple.

## 2. Requirement Specification and Targeting

While Section 1 established the existence of a requirement, the axiom `requirement_equiv_specifies_target` provides the necessary equivalence definition to operationalize it. This axiom asserts that a class `X` is equivalent to the intersection of three conditions: it is a `cco:DirectiveICE`, it specifies a requirement `Y`, and it applies to a target `Z`.

This tripartite definition is critical for granular governance. It moves beyond the abstract statement of a requirement (e.g., "Encrypt data") to a concrete directive (e.g., "The Database Cluster must encrypt stored cardholder data"). The relational schema captures this by storing the specification ID, the directive class, the requirement ID, and the target asset or system class.

The primary key of this table is the unique identifier for the specification instance. The foreign key constraint on column `y` references the `t_pci_dss_requirement` table, creating a circular dependency that reinforces the tight coupling between a requirement and its specific application. In audit scenarios, this structure allows an examiner to query a target (`Z`) and immediately retrieve all applicable directives (`X`) and the governing requirements (`Y`).

## 3. Control Implementation and Risk Addressal

The implementation of security controls is the mechanism by which requirements are satisfied. The axiom `control_only_addresses_threat_class` formalizes this by defining a class `X` (the control) as a subclass of `cco:DirectiveICE` that addresses a risk `Y`. The use of the "only" restriction (`only`) in the Manchester syntax implies a universal quantification; the control `X` is constrained to address risk `Y` and no other type of risk in this context.

This distinction is vital for risk management frameworks. It ensures that controls are not over-specified or ambiguously defined. If a control is defined as a "Firewall Rule," it must be explicitly linked to the "Network Intrusion" risk class. The relational schema enforces this by linking the control instance directly to the requirement ID, which acts as the proxy for the risk context defined in the previous axioms.

From an audit perspective, this table serves as the control registry. It validates that the organization’s implemented controls (`x`) are formally authorized and designed to mitigate specific compliance requirements (`y`). The foreign key constraint ensures that every control is anchored to a valid PCI-DSS requirement, maintaining the chain of evidence from regulatory text to technical implementation.

## 4. Audit Trails and Evidence Support

Compliance is not static; it requires ongoing verification. The axiom `trace_supports_claim` introduces the concept of an audit trail as a process that supports a descriptive claim. Here, class `X` is a subclass of `bfo:0000015` (a Process) that `supportsClaim` regarding a `cco:DescriptiveICE`.

In the context of a technical audit, a "trace" is a log entry, a system state capture, or a transaction record. The "claim" is typically the assertion that a control is functioning or that a requirement is being met. This axiom bridges the gap between the occurrence of an event (the process) and the interpretation of that event (the descriptive claim).

The relational schema for this concept is deceptively simple, consisting only of an ID and the process class. However, its power lies in its ability to aggregate discrete events into a coherent narrative of compliance. When an auditor reviews a log file (the process instance), they are utilizing this ontological structure to validate that the log entry supports the claim that "Access Control was enforced."

## 5. Attestation and Personnel Sign-off

The final step in the compliance lifecycle is attestation. The axiom `attestation_signed_by` defines the formal act of validation. It asserts that a class `X` (the attestation event) is a subclass of `bfo:0000015` (Process) that is `signedBy` a `cco:Person`.

This axiom moves the compliance verification from the system layer to the human layer. An automated log may indicate that a firewall is active (Section 4), but the attestation is the formal acknowledgement by a qualified individual that the system is in the correct state. This is the legal and procedural binding of the audit process.

The relational schema captures the attestation event. While the schema provided does not explicitly include a column for the "Person" (it only includes `x`), the ontology definition implies the relationship. In a fully expanded implementation, this table would likely join to a personnel directory. However, in this focused schema, the existence of the row in `t_attestation_signed_by` signifies that a process has occurred which satisfies the condition of being signed by a person, thereby closing the audit loop.
