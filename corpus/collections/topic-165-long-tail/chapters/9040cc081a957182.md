# Chapter 7: Formal Ontology of PCI DSS Governance and Audit Verification

This chapter delineates the structural ontology governing Payment Card Industry Data Security Standard (PCI DSS) compliance frameworks. It establishes the formal relationships between regulatory directives, risk mitigation controls, and the evidentiary traces required for rigorous audit verification. The content herein provides a precise, axiom-based definition of compliance artifacts, ensuring that governance frameworks are both machine-readable and legally defensible.

## 7.1 PCI DSS Requirements as Regulatory Directives

The foundational unit of any compliance framework is the requirement itself. Within the context of the Common Core Ontologies (CCO), a PCI DSS requirement is formalized not merely as text, but as a distinct subclass of a Directive Information Content Entity (ICE). The axiom `pci_dss_requirement` posits that a specific class of directive (X) functions as a PCI DSS requirement for a target class (Y). This relationship is critical for automated reasoning engines, as it transforms static regulatory text into a computable constraint that can be validated against system configurations.

In practice, this means that an organization's governance documentation must explicitly map specific control classes to the standardized requirements defined by the PCI Security Standards Council. For example, a directive concerning "Transmission of Cardholder Data" is not a standalone policy; it is an instance of a requirement class that specifically targets "Open, Public Networks." By formalizing this relationship, auditors can trace a specific control implementation back to the high-level mandate it satisfies.

The primary key is `id`, and `y` acts as a foreign key linking to the detailed specification table, ensuring that every requirement is anchored to a specific, defined target.

This mapping ensures that the "Requirement" entity is never treated as an abstract concept but is always tied to a concrete specification ID. This structure prevents the common audit failure where a policy is written but fails to explicitly cite the specific regulatory clause it addresses.

## 7.2 Requirement Specification and Target Equivalence

To achieve granular compliance, a requirement must be rigorously defined in terms of what it specifies and to what entity it applies. The axiom `requirement_equiv_specifies_target` provides an equivalence definition for a Directive ICE. It asserts that a class (X) is equivalent to a directive that specifies some artifact (Y) and applies to some scope (Z). This tripartite structure—Requirement, Specification, and Target—forms the semantic backbone of the governance framework.

For instance, consider the requirement to "Change vendor-supplied defaults." Under this axiom, the requirement class is equivalent to a directive that specifies "System Configuration Parameters" (Y) and applies to "All Network Devices" (Z). This equivalence allows compliance officers to query the ontology for all directives that apply to a specific target (e.g., "Wireless Access Points") and instantly retrieve all relevant specifications and requirements. It eliminates ambiguity regarding the scope of a control.

The table below represents Axiom 4 (`requirement_equiv_specifies_target`), defining a directive class (X) as equivalent to a directive that specifies Y and applies to Z. The primary key is `id`, with `y` referencing the PCI requirement table to create a dependency loop that ensures no requirement exists without a corresponding specification.

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| REQ_SPEC_001 | DataEncryptionDirective | PCI_REQ_001 | CardholderDataEnvironment |
| REQ_SPEC_002 | NetworkAccessDirective | PCI_REQ_002 | InternalNetworkZone |
| REQ_SPEC_003 | AuditTrailDirective | PCI_REQ_003 | SystemLogServer |

The foreign key constraint on column `y` (referencing `t_pci_dss_requirement`) enforces a strict bidirectional relationship. A requirement cannot exist in isolation; it must be the specification of a defined directive. This structure is essential for maintaining the integrity of the compliance matrix during internal audits and external assessments.

## 7.3 Risk Controls and Threat Class Addressal

Effective governance requires not only the definition of requirements but also the explicit mapping of controls to the threat classes they mitigate. The axiom `control_only_addresses_threat_class` refines this by asserting that a Control (X) is a Directive that addresses a Risk (Y). The use of the "only" restriction in the ontology implies a closed-world assumption regarding the control's efficacy: the control is designated to address *only* this specific risk class, preventing scope creep and ensuring precise risk management.

This distinction is vital for risk assessment methodologies (e.g., those required by PCI DSS Requirement 12.1.2). If a "Firewall Configuration" is defined as a control that addresses the risk of "Unauthorized Network Access," the ontology explicitly forbids classifying that same control as the primary mitigation for "Malware Infection" without creating a distinct control instance. This precision forces organizations to deploy defense-in-depth strategies rather than relying on single controls to satisfy broad, undefined threat categories.

The following table captures Axiom 5 (`control_only_addresses_threat_class`), identifying a directive class (X) that exclusively addresses a specific risk class (Y). The primary key is `id`, and `y` references the PCI requirement table to link the control to the specific threat it mitigates.

| id | x | y |
| :--- | :--- | :--- |
| CTRL_001 | CryptographicKeyRotation | PCI_REQ_001 |
| CTRL_002 | TwoFactorAuthentication | PCI_REQ_002 |
| CTRL_003 | ImmutableLogStorage | PCI_REQ_003 |
| CTRL_004 | AutomatedVulnerabilityScanning | PCI_REQ_004 |
| CTRL_005 | AnnualSecurityAwarenessTraining | PCI_REQ_005 |

By linking the control directly to the requirement ID (`y`), the organization maintains a clear line of sight from the technical implementation (the Control) to the regulatory driver (the PCI Requirement). This structure is particularly useful during gap analysis, where missing controls can be identified by searching for requirement IDs that lack corresponding entries in the control table.

## 7.4 Attestation and Authorization Processes

Compliance is not merely a technical state but a legal assertion, verified through the process of attestation. The axiom `attestation_signed_by` formalizes this by defining an Attestation (X) as a Process (bfo:0000015) that is signed by a Person. In the ontology, this moves beyond the concept of a digital signature to define the entire attestation workflow as a distinct process class with specific agency requirements.

This definition is crucial for maintaining the chain of custody in compliance records. An attestation is not valid simply because a document exists; it is valid only if the process of signing—encompassing identity verification, timestamping, and authorization—has been executed by a recognized person (cco:Person). This axiom supports the non-repudiation requirements essential for PCI DSS assessments and SOC 2 audits.

The table below instantiates Axiom 2 (`attestation_signed_by`), categorizing a process class (X) as an attestation signed by a person. The primary key is `id`, serving as the unique identifier for the attestation process within the governance framework.

| id | x |
| :--- | :--- |
| ATT_001 | QuarterlyComplianceReview |
| ATT_002 | AnnualAttestationProcess |
| ATT_003 | IncidentResponseAcknowledgement |
| ATT_004 | PolicyChangeAuthorization |
| ATT_005 | ThirdPartyRiskAcceptance |

These process classes act as the vertices in the audit graph. When an auditor reviews a signed ROC (Report on Compliance), they are verifying an instance of `ATT_002` (Annual Attestation Process). The ontology ensures that this instance is treated as a process with temporal and agency properties, rather than a static document artifact.

## 7.5 Audit Traces and Claim Support

The final pillar of the governance framework is the evidentiary support for compliance claims. The axiom `trace_supports_claim` defines a Trace (X) as a Process that supports a Claim (Descriptive ICE). This distinguishes raw data from "evidence." A system log is merely data; it becomes a "Trace" only when it is identified as a process output that substantiates a specific descriptive claim, such as "All administrative access was logged."

This formalism allows for the construction of complex evidence hierarchies. For example, a claim that "The system is PCI compliant" may be supported by a trace consisting of "Configuration Audit Logs." The ontology explicitly links the process that generated the log to the claim it supports. This is the mechanism by which automated compliance tools validate assertions: by verifying the existence of the trace process and its logical connection to the claim.

In a mature governance environment, the `x` values in this table represent the specific data streams or process outputs that an auditor would request to verify a finding. By defining these as process classes, the ontology accommodates the dynamic nature of log generation and retention policies, ensuring that the "support" for a claim is current and verifiable.
