# Chapter 4: Directive Information Content Entities in PCI DSS Compliance Verification

This chapter specifies five relational tables that realize the listed OWL axioms for directive and descriptive information content entities. The tables support cross-table joins that resolve multi-hop queries over requirements, attestations, and supporting traces within a payment-card data-security audit record.

## 1 Scope and Table Inventory

The schema covers requirement statements, signed attestations, claim-supporting traces, equivalence specifications, and threat-class restrictions. All primary keys are system-generated identifiers. Foreign-key columns enforce the slot restrictions declared in each axiom.

## 1.1 t_pci_dss_requirement

Axiom 1 is embodied by this table. Column id is the primary key. Column y is a foreign key that resolves to the requirement equivalence specification that supplies the target class. A reader can join this table to t_requirement_equiv_specifies_target on y to retrieve the classes that a given directive specifies and applies to.

| id | x | y |

| req-001 | 12.1 | spec-001 |
| req-002 | 12.2 | spec-002 |
| req-003 | 8.2 | spec-003 |
| req-004 | 3.4 | spec-004 |
| req-005 | 10.1 | spec-005 |
| req-006 | 11.4 | spec-006 |

## 1.2 t_requirement_equiv_specifies_target

Axiom 4 is embodied by this table. Column id is the primary key. Columns y and z are foreign keys; y references t_pci_dss_requirement and z references the same table to close the equivalence axiom. A reader can join on y to obtain the directive class and on z to obtain the class to which the directive applies.

| id | x | y | z |

## 1.3 t_attestation_signed_by

Axiom 2 is embodied by this table. Column id is the primary key. The table records processes that are signed by a person; no foreign key is declared because the person slot is an external cco:Person reference. A reader can join attestation rows to requirement rows via an auxiliary link table when tracing who attested a given directive.

## 1.4 t_trace_supports_claim

Axiom 3 is embodied by this table. Column id is the primary key. The table records processes that support a descriptive claim; the claim is an external cco:DescriptiveICE reference. A reader can join trace rows to requirement rows to determine which evidence backs a compliance assertion.

## 1.5 t_control_only_addresses_threat_class

Axiom 5 is embodied by this table. Column id is the primary key. Column y is a foreign key that references t_pci_dss_requirement and restricts the risk class addressed by the control. A reader can join on y to list only those requirements whose addressed threat class satisfies the universal restriction.

| id | x | y |
| id | x | y |
| ctl-001 | Control-12.1 | req-001 |
| ctl-002 | Control-12.2 | req-002 |
| ctl-003 | Control-8.2 | req-003 |
| ctl-004 | Control-3.4 | req-004 |

## 2 Cross-Join Example

To answer “which signed attestation supports the claim for the requirement that specifies target Requirement-12.2 and addresses only the threat class of Requirement-12.1”, first locate spec-002 in t_requirement_equiv_specifies_target where x = Requirement-12.2 and y = req-002. Join t_pci_dss_requirement on id = req-002 to confirm the directive. Join t_control_only_addresses_threat_class on y = req-001 to verify the universal restriction. Finally join the resulting requirement identifier to an external attestation link to retrieve att-001. The joined row yields: requirement 12.2, specification spec-002, control ctl-001, attestation att-001.
