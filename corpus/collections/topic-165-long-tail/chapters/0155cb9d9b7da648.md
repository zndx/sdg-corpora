# Chapter 4: Formal Ontology of PCI DSS Governance and Control Mechanisms

This chapter delineates the formal ontological structures underpinning the governance of Payment Card Industry Data Security Standard (PCI DSS) environments. It provides a rigorous examination of the semantic relationships between regulatory directives, procedural attestations, evidentiary traces, and technical controls. The objective is to establish a deterministic mapping between high-level compliance requirements and their executable implementations within a relational schema, thereby facilitating automated auditing and continuous compliance monitoring. The following sections decompose these concepts into their constituent axiomatic components, supported by data tables that instantiate the theoretical framework.

## 4.1 PCI DSS Requirements as Information Content Entities

The foundational element of the compliance framework is the formal definition of a requirement as an Information Content Entity (ICE). In the context of the ontology, a PCI DSS requirement is not merely a textual string but a distinct class of entity that inherits the properties of a directive. Axiom 1, `pci_dss_requirement`, establishes that a specific requirement class is a subclass of `cco:DirectiveICE` and possesses a necessary relationship to a broader requirement specification.

The Manchester syntax for this axiom is expressed as:
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`

This structure asserts that entity {X} represents a specific compliance mandate which necessitates the existence of a PCI DSS requirement {Y}. This relationship is critical for maintaining traceability between the abstract definition of a control and the specific regulatory clause it satisfies. For instance, a class representing "Data Encryption at Rest" is defined not only by its directive status but by its explicit reference to a PCI DSS article.

The primary key is the unique identifier for the requirement instance, while the foreign key (`y`) establishes a dependency on the requirement specification table, ensuring that no requirement exists in isolation without a regulatory anchor.

## 4.2 Attestation and Signatory Authority

Governance frameworks rely upon the formalization of approval processes. The `attestation_signed_by` axiom defines the procedural act of attestation as a distinct process that necessitates the involvement of a natural person. Axiom 2 is defined as:
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:signedBy some cco:Person`

Here, {X} denotes a class of attestation processes. The axiom utilizes the Basic Formal Ontology (BFO) artifact `bfo:0000015` (Process) to indicate that attestation is an occurrent that unfolds in time, rather than a static entity. The restriction `sdg:signedBy some cco:Person` ensures that the process is agentive; it cannot be executed by an automated system without the delegation of a responsible human agent. This distinction is vital for audit trails, separating automated log generation (a system process) from the formal acceptance of liability (a signatory process).

This table does not require a foreign key to other tables within this specific schema fragment, as the signatory is an external entity (Person), but it serves as a parent table for any evidence logs generated during the attestation event.

## 4.3 Audit Traces and Evidentiary Support

To validate compliance, a governance system must produce artifacts that substantiate claims made by the organization. Axiom 3, `trace_supports_claim`, formalizes the concept of an audit trail as a process that generates or references descriptive information content entities.
`Class: {X:Class} SubClassOf: bfo:0000015, sdg:supportsClaim some cco:DescriptiveICE`

In this axiom, {X} represents the trace or audit process. The object of the relationship is a `cco:DescriptiveICE`, which represents the claim or assertion being supported (e.g., "Firewalls are configured correctly"). This axiom allows the ontology to distinguish between raw data and evidentiary data. A raw log file is merely data; however, a process that aggregates and validates that log file to support a specific compliance claim is a `trace_supports_claim`.

The following table embodies Axiom 3. It catalogs the classes of audit processes (X) designed to support specific descriptive claims. The primary key identifies the trace process. This structure allows auditors to query the system for all processes that support a specific claim type, thereby facilitating the "audit trail" requirement common in standards such as SOC 2 and PCI DSS.

## 4.4 Requirement Specification and Targeting

The core of the governance logic lies in the precise definition of what a requirement dictates and to what entity it applies. Axiom 4, `requirement_equiv_specifies_target`, provides an equivalence definition for a directive that specifies a requirement and applies to a target.
`Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`

This axiom asserts that a class {X} is equivalent to the intersection of three conditions: it is a Directive; it specifies a requirement {Y}; and it applies to a target {Z}. This creates a fully bounded definition of a compliance obligation. For example, a class "Encryption Directive for Cardholder Data" is defined by the fact that it specifies the "Encryption Requirement" and applies to the "Cardholder Data Environment."

## 4.5 Control Implementation and Threat Mitigation

The final conceptual component addresses the operationalization of governance through security controls. Axiom 5, `control_only_addresses_threat_class`, defines a control as a directive that is constrained to address specific risks.
`Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:addressesRisk only {Y:Class}`

This axiom defines {X} as a control class. The use of the `only` (universal restriction) constructor in Manchester syntax is semantically significant: it implies that if an instance of this control addresses a risk, that risk *must* belong to class {Y}. In the context of the provided schema, {Y} is mapped to the PCI DSS requirement identifier. This implies that the risk taxonomy is tightly coupled with the compliance requirement; the control is valid only insofar as it addresses the specific risk defined by that requirement.
