# Chapter 4: Formalizing Compliance Directives and Audit Trails

## 4.1 Scope and Preamble

This chapter establishes the formal ontological structures necessary for mapping regulatory governance to operational information security controls. It details the semantic relationships between compliance directives, specific Payment Card Industry Data Security Standard (PCI DSS) requirements, and the personnel or processes responsible for attestation and evidence generation. The content herein is designed to support auditors, compliance officers, and governance architects in constructing verifiable, machine-readable audit trails. By grounding these concepts in a rigorous axiomatization, we ensure that governance artifacts are not merely descriptive documents but functional components of an enterprise security architecture.

## 4.2 PCI DSS Requirement Mapping

The foundational unit of regulatory compliance within this framework is the directive that explicitly invokes a standard. In formal ontology terms, we define a specific class of directives that are subclasses of the `DirectiveICE` (Information Content Entity) and possess the property of being a PCI DSS requirement. This relationship is not merely associative; it is existential. For a directive to be valid within this class, it *must* reference a specific requirement object.

This mapping allows the organization to query all internal policies that derive their authority from specific external regulations. For instance, an internal policy regarding firewall configuration is not just a document; it is an instance of a class that is semantically bound to PCI DSS Requirement 1.

**Axiom 1:** The class `PCI_DSS_Requirement` is defined as a subclass of `cco:DirectiveICE` that has the property `sdg:pciDssRequirement` linking it to a requirement class. The relational schema below captures this mapping, where the primary key is the directive identifier, and the foreign key establishes the link to the specific requirement specification.

*Table 4.1: PCI DSS Requirement Directives*
| id | x | y |
| :--- | :--- | :--- |
| DIR-2023-001 | NetworkSegmentationDirective | REQ-SPEC-001 |
| DIR-2023-002 | CardDataEncryptionPolicy | REQ-SPEC-002 |
| DIR-2023-003 | AccessControlProtocol | REQ-SPEC-003 |
| DIR-2023-004 | VulnerabilityManagementProcedure | REQ-SPEC-004 |
| DIR-2023-005 | LoggingMonitoringDirective | REQ-SPEC-005 |

In the table above, column `x` represents the internal directive class (the specific policy document or control implementation), while column `y` represents the requirement specification it satisfies. The foreign key constraint ensures that every directive is mapped to a valid, defined requirement specification, preventing orphaned policies.

## 4.3 Requirement Specification and Targeting

While the previous section establishes that a directive *is* a requirement, we must further define what that requirement *does*. In ontology, we use equivalence classes to provide a complete definition. A requirement specification is equivalent to the intersection of three conditions: it is a directive, it specifies a particular PCI DSS requirement, and it applies to a specific target within the infrastructure.

This tripartite definition ensures that requirements are never abstract or floating; they are always anchored to a target (e.g., a database, a network segment, or a role). This is critical for audit scope definition. If a requirement does not specify a target, it cannot be audited effectively.

**Axiom 4:** The class `Requirement_Equiv_Specifies_Target` is equivalent to a `cco:DirectiveICE` that specifies a requirement (`Y`) and applies to a target (`Z`). The relational schema enforces this by linking the requirement specification back to the PCI DSS requirement ID defined in the previous table.

*Table 4.2: Requirement Specifications and Targets*
| id | x | y | z |
| :--- | :--- | :--- | :--- |
| REQ-SPEC-001 | NetworkSegmentationDirective | DIR-2023-001 | CardholderDataEnvironment |
| REQ-SPEC-002 | CardDataEncryptionPolicy | DIR-2023-002 | TransmissionMedia |
| REQ-SPEC-003 | AccessControlProtocol | DIR-2023-003 | PrivilegedUserAccount |
| REQ-SPEC-004 | VulnerabilityManagementProcedure | DIR-2023-004 | ExternalFacingSystem |
| REQ-SPEC-005 | LoggingMonitoringDirective | DIR-2023-005 | SecurityEventLogServer |

Here, the primary key `id` corresponds to the specification identifier. Column `y` acts as a foreign key referencing the directive ID in Table 4.1, creating a bidirectional link between the directive instance and its detailed specification. Column `z` defines the scope of application, ensuring the auditor knows exactly where to look for compliance.

## 4.4 Attestation and Personnel Accountability

Compliance is ultimately a human endeavor. Automated controls must be monitored, and policies must be enforced by individuals with defined authority. The ontology captures this through the concept of attestation. An attestation is a process (a temporal entity) that is signed by a person.

This axiom links the process of verification to the responsible agent. In a legal or regulatory context, this distinguishes between a system event and a verified claim. A log file is a system event; a signed attestation confirming the review of that log file is a governance event.

**Axiom 2:** The class `Attestation_Signed_By` is a subclass of `bfo:0000015` (Process) that involves the property `sdg:signedBy` referencing a `cco:Person`. The relational schema is straightforward, identifying the specific attestation process instance.

*Table 4.3: Attestation Processes*
| id | x |
| :--- | :--- |
| ATT-2023-Q1 | QuarterlyComplianceReview |
| ATT-2023-Q2 | AnnualRiskAssessmentSignOff |
| ATT-2023-Q3 | PenetrationTestAttestation |
| ATT-2023-Q4 | PolicyReviewAttestation |
| ATT-2023-Q5 | IncidentResponsePlanSignOff |

In this table, `id` is the unique identifier for the attestation event, and `x` is the class of the process being attested. While the schema does not explicitly list the person's name in this table (it is handled via the object property in the ontology), the existence of the row implies that a valid person reference must exist for the attestation to hold. This structure supports traceability by allowing the auditor to retrieve the specific "sign-off" event for any given process.

## 4.5 Traceability and Claim Support

The integrity of an audit relies on the ability to trace a conclusion back to raw evidence. We define a "trace" as a process that supports a claim. A claim, in this context, is a `DescriptiveICE`—a statement of fact about the system state. The trace is the mechanism (e.g., a log analysis, a checksum verification) that validates that claim.

This distinction is vital. A claim might be "The system is patched." The trace is the "Vulnerability Scan Report" generated by the scanning process. The ontology formalizes the relationship between the process of generating the evidence and the informational claim it supports.

**Axiom 3:** The class `Trace_Supports_Claim` is a subclass of `bfo:0000015` (Process) that supports a claim (`cco:DescriptiveICE`). The table below catalogs these trace processes.

*Table 4.4: Trace Processes Supporting Claims*
| id | x |
| :--- | :--- |
| TRACE-001 | SystemConfigurationAudit |
| TRACE-002 | AccessLogVerification |
| TRACE-003 | FileIntegrityMonitoring |
| TRACE-004 | NetworkTrafficAnalysis |
| TRACE-005 | EncryptionKeyRotationCheck |

Each row in Table 4.4 represents a process instance (`x`) that generates or validates evidence. By identifying these processes explicitly, the governance framework can automate the collection of support for compliance claims. For example, the `AccessLogVerification` process (TRACE-002) would generate the artifacts necessary to support the claim that "Access controls are functioning as logged."

## 4.6 Control Implementation and Threat Mitigation

Finally, we address the efficacy of controls. A control is a directive implemented to mitigate risk. The ontology imposes a strict condition: a specific control class addresses *only* a specific class of threats. This is a universal quantification (`only`). It implies that if the control `Firewall_Rule` addresses a threat `Inbound_Traffic`, it cannot be said to address `Internal_Malware` unless `Internal_Malware` is a subclass of `Inbound_Traffic`.

This restriction prevents scope creep in control definitions. It forces the architect to define precisely what risk a given control is mitigating. This precision is required for high-assurance environments such as those mandated by PCI DSS.

**Axiom 5:** The class `Control_Only_Addresses_Threat_Class` is a subclass of `cco:DirectiveICE` that addresses a risk (`Y`) such that all addressed risks are of class `Y`. The relational schema links the control to the PCI DSS requirement it serves, which indirectly defines the threat context.

*Table 4.5: Controls and Addressed Threat Classes*
| id | x | y |
| :--- | :--- | :--- |
| CTRL-001 | IntrusionPreventionSystem | DIR-2023-001 |
| CTRL-002 | EndPointEncryptionTool | DIR-2023-002 |
| CTRL-003 | TwoFactorAuthenticationModule | DIR-2023-003 |
| CTRL-004 | AutomatedPatchManager | DIR-2023-004 |
| CTRL-005 | SIEMCorrelationEngine | DIR-2023-005 |

In Table 4.5, column `x` identifies the specific control class (e.g., `IntrusionPreventionSystem`). Column `y` references the PCI DSS Requirement Directive ID from Table 4.1. This foreign key relationship ensures that the control is formally mapped to the regulatory requirement it is intended to satisfy. The "only" constraint in the axiom is enforced logically by ensuring that the control `x` is never associated with a threat class outside the scope defined by the requirement `y`.
