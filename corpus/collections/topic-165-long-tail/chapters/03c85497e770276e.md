# Chapter 7: Directive Governance and Traceability in PCI DSS Audit Records

This chapter defines a five-table relational schema that directly implements five OWL axioms for PCI DSS compliance artifacts. The schema supports multi-table joins that recover requirement targets, signed attestations, supporting traces, and threat-addressing controls from a single audit database.

## 1 Requirement Equivalence and Target Specification

Axiom 4 states that a directive information content entity is equivalent to a class that specifies a target and applies to a further class. Table t_requirement_equiv_specifies_target therefore stores the three slots of the equivalence axiom; column id is the primary key while columns y and z are foreign keys that respectively reference the requirement class and the application target.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

| id          | x                  | y           | z                  |
|-------------|--------------------|-------------|--------------------|
| reqspec-01  | FirewallDirective  | req-01      | NetworkSegment     |
| reqspec-02  | EncryptionRule     | req-02      | CardholderData     |
| reqspec-03  | AccessControlSpec  | req-03      | SystemComponent    |
| reqspec-04  | LoggingMandate     | req-04      | AuditLog           |
| reqspec-05  | VulnerabilityScan  | req-05      | ExternalNetwork    |
| reqspec-06  | PolicyReview       | req-06      | AnnualCycle        |

## 2 PCI DSS Requirement Classification

Axiom 1 classifies an entity as a subclass of DirectiveICE that carries a PCI DSS requirement. Table t_pci_dss_requirement therefore records the two class slots; its primary key id is referenced by t_requirement_equiv_specifies_target.y and by t_control_only_addresses_threat_class.y.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_requirement_equiv_specifies_target(id)
);
```

| id      | x                    | y           |
|---------|----------------------|-------------|
| req-01  | InstallFirewall      | reqspec-01  |
| req-02  | ProtectData          | reqspec-02  |
| req-03  | ProtectSystem        | reqspec-03  |
| req-04  | ProtectLogs          | reqspec-04  |
| req-05  | ScanNetwork          | reqspec-05  |
| req-06  | MaintainPolicy       | reqspec-06  |

## 3 Control Restriction to Threat Class

Axiom 5 asserts that a directive addresses risk only of a given class. Table t_control_only_addresses_threat_class therefore stores the restricted addressesRisk slot; its foreign key y references t_pci_dss_requirement.id so that a control record can be joined directly to its governing requirement.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

| id         | x                    | y      |
|------------|----------------------|--------|
| ctrl-01    | FirewallConfig       | req-01 |
| ctrl-02    | TLSOnly              | req-02 |
| ctrl-03    | RBACMatrix           | req-03 |
| ctrl-04    | ImmutableLog         | req-04 |
| ctrl-05    | QuarterlyScan        | req-05 |

## 4 Signed Attestation Process

Axiom 2 states that a process is signed by a person. Table t_attestation_signed_by therefore records the signed attestation instance; its primary key id serves as the entry point for any subsequent join that recovers the signer.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id           | x                     |

| attest-02    | SAQ-D-Quarterly       |
| attest-03    | ROC-Network-2023      |

## 5 Trace Support for Descriptive Claims

Axiom 3 states that a process supports a descriptive information content entity. Table t_trace_supports_claim therefore records the supporting trace; its primary key id can be joined to attestation or requirement tables to reconstruct evidence chains.

```sql
CREATE TABLE t_trace_supports_claim (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

## 6 Cross-Table Query Example

To recover the signed attestation, requirement target, and supporting trace for the firewall control, the following three-table join is executed:

```sql
SELECT
  c.id AS control,
  r.x AS requirement,
  s.z AS target,
  a.x AS attestation,
  t.x AS trace
FROM t_control_only_addresses_threat_class c
JOIN t_pci_dss_requirement r ON c.y = r.id
JOIN t_requirement_equiv_specifies_target s ON r.y = s.id
JOIN t_attestation_signed_by a ON a.id = 'attest-01'
JOIN t_trace_supports_claim t ON t.id = 'trace-01'
WHERE c.id = 'ctrl-01';
```

The result row is:

control: ctrl-01  
requirement: InstallFirewall  
target: NetworkSegment  
attestation: QSA-Annual-2023  
trace: PacketCapture-2023-11
