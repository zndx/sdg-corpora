# Chapter 4: Relational Projection of DirectiveICE and Claim-Support Axioms in PCI DSS Audit Trails

This chapter presents five tables that instantiate the five supplied OWL axioms as a queryable relational schema. The tables capture PCI DSS requirements, signed attestations, supporting traces, requirement equivalences, and threat-addressing controls. Primary-key and foreign-key constraints enforce the slot restrictions declared in each axiom, enabling multi-table joins that recover the original Manchester restrictions.

## 1 Table Definitions and Axiom Embodiment

### 1.1 t_requirement_equiv_specifies_target
This table directly implements AXIOM 4. Column id is the primary key. Columns y and z are foreign keys; y references t_pci_dss_requirement.id, enforcing the equivalence restriction that every requirement specifies a target only when a corresponding pciDssRequirement assertion exists.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

Example cross-join: given a requirement identifier, retrieve the descriptive target class by joining on y.

### 1.2 t_pci_dss_requirement
This table implements AXIOM 1. Column id is the primary key. Column y is a foreign key referencing t_requirement_equiv_specifies_target.id, materializing the existential restriction sdg:pciDssRequirement some {Y}.

```sql
CREATE TABLE t_pci_dss_requirement (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_requirement_equiv_specifies_target(id)
);
```

Example cross-join: locate every pciDssRequirement instance that participates in an equivalence specification by joining on y.

### 1.3 t_attestation_signed_by
This table implements AXIOM 2. Column id is the primary key. The table records bfo:0000015 processes that are signed by a cco:Person, satisfying the signedBy restriction without additional foreign keys.

```sql
CREATE TABLE t_attestation_signed_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

Example cross-join: correlate an attestation identifier with a requirement trace by joining on shared descriptive identifiers across t_trace_supports_claim.

### 1.4 t_trace_supports_claim
This table implements AXIOM 3. Column id is the primary key. The table records bfo:0000015 processes whose output supports a cco:DescriptiveICE claim, satisfying the supportsClaim restriction.

```sql
CREATE TABLE t_trace_supports_claim (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

Example cross-join: retrieve the attestation that produced a supporting trace by joining attestation identifiers with trace identifiers on common claim values.

### 1.5 t_control_only_addresses_threat_class
This table implements AXIOM 5. Column id is the primary key. Column y is a foreign key referencing t_pci_dss_requirement.id, enforcing the universal restriction that a control addresses only the threat classes declared by the referenced requirement.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id),
  FOREIGN KEY (y) REFERENCES t_pci_dss_requirement(id)
);
```

Example cross-join: given a control identifier, obtain the pciDssRequirement that delimits its admissible threat classes by joining on y.

## 2 Worked Multi-Hop Query Example

Question: which attestation signed by a person supports a claim that is in turn referenced by a control addressing the threat class of requirement REQ-12-3?

Walk the foreign keys:

1. Start at t_control_only_addresses_threat_class row whose y = 'REQ-12-3'.
2. Join t_pci_dss_requirement on id = y to obtain the corresponding x value.
3. Join t_trace_supports_claim on x to obtain the supporting claim identifier.
4. Join t_attestation_signed_by on x to obtain the signed attestation identifier.

Resulting joined row (abbreviated):

control_id = CTL-004, requirement_id = REQ-12-3, trace_id = TR-881, attestation_id = AT-317

The four-table join recovers the complete chain from control to signed attestation in a single deterministic traversal.
