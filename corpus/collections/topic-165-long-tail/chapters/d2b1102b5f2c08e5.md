### 0. Preamble and Scope

This chapter delineates the formal ontological structures underpinning modern compliance governance, specifically within the context of the Payment Card Industry Data Security Standard (PCI DSS). The objective is to provide a precise, axiomatically grounded definition of the relationships between regulatory directives, procedural attestations, evidentiary traces, and risk mitigation controls. The concepts presented herein are derived from a rigorous upper-level ontology, ensuring that governance artifacts are not merely descriptive but are semantically anchored to verifiable logical structures. Readers are advised to consult the accompanying relational schemas to understand the data implementation of these axioms.

---

### 1. PCI DSS Requirements as Directive Information Content Entities

#### 1.1 Axiomatic Definition
The foundational unit of compliance governance is the requirement, formally defined as a subclass of the `Directive Information Content Entity` (DirectiveICE). According to Axiom 1 (`pci_dss_requirement`), a requirement class `{X}` is defined by its relationship to a specific PCI DSS requirement class `{Y}`. This establishes a necessary condition: for an entity to be recognized as a valid governance directive within this framework, it must be explicitly mapped to a standardized PCI DSS requirement.

This relationship is not merely associative but constitutive. The directive derives its normative force from the specification of the requirement. In practical terms, this means that a policy document or configuration standard (the Directive) is only valid insofar as it can be traced back to a specific mandate within the PCI DSS hierarchy.

#### 1.2 Relational Mapping and Circular Dependency
The implementation of this axiom requires a careful understanding of the recursive nature of requirement specification. The schema for `t_pci_dss_requirement` establishes a foreign key dependency on `t_requirement_equiv_specifies_target`. This structure models the equivalence defined in Axiom 4, where a Requirement is equivalent to a Directive that specifies a target and applies to a context.

Consequently, the data model exhibits a circular reference: a PCI DSS Requirement (Table 1) points to a Requirement Specification (Table 4), which in turn references the PCI DSS Requirement instance as the object of its specification. This circularity is intentional and logically sound, reflecting the real-world dependency where a specific control instance validates the abstract requirement, and the abstract requirement defines the parameters of the control.

### 2. The Equivalence of Requirements, Specifications, and Targets

#### 2.1 Axiomatic Definition
Axiom 4 (`requirement_equiv_specifies_target`) provides the necessary semantic expansion for the requirements introduced in Section 1. It posits that a Requirement Class `{X}` is equivalent to the intersection of three conditions: it is a `DirectiveICE`, it `specifies` a target `{Y}`, and it `appliesTo` a context `{Z}`.

This equivalence is critical for auditability. It prevents "orphan" directives that exist in a vacuum. Every valid requirement must explicitly state what it specifies (the specific control or behavior) and the system or environment to which it applies. This tripartite structure—Directive, Specification, Target—forms the atomic unit of governance compliance.

#### 2.2 Relational Mapping
The schema for `t_requirement_equiv_specifies_target` captures this equivalence. The column `y` references the `t_pci_dss_requirement` table, closing the loop established in Section 1. The column `z` represents the target environment or asset class (e.g., Cardholder Data Environment). This structure allows auditors to query a requirement and immediately retrieve its scope (`z`) and its specific instantiation (`y`).

### 3. Attestation Processes and Agent Verification

#### 3.1 Axiomatic Definition
Governance frameworks rely on the integrity of human verification. Axiom 2 (`attestation_signed_by`) defines the class of Attestations as a subclass of `Process` (specifically `bfo:0000015`, a processual entity). The axiom asserts that any such process `{X}` must be `signedBy` a `Person`.

This formalism moves beyond the mere concept of a signature. It classifies the attestation itself as a temporal process—a sequence of actions undertaken by an agent—to validate the state of compliance. The "signature" is the property that links this process to a specific legal/functional agent (the Person), ensuring accountability and non-repudiation.

#### 3.2 Relational Mapping
The table `t_attestation_signed_by` is straightforward but structurally significant. It identifies the process ID (`id`) and the class of the attestation process (`x`). While the schema does not explicitly store the *identity* of the person (the `cco:Person` is the range of the object property in the ontology), the table represents the process instances that are *capable* of being signed. In a full implementation, joins would be effected against a personnel directory, but here we define the attestation processes themselves.

### 4. Audit Trails and Evidentiary Support

#### 4.1 Axiomatic Definition
In the context of an audit, a claim regarding compliance is only as valid as the evidence supporting it. Axiom 3 (`trace_supports_claim`) formalizes the concept of an audit trail. It defines a Trace Class `{X}` as a subclass of `Process` that `supportsClaim` regarding a `Descriptive Information Content Entity` (DescriptiveICE).

A "DescriptiveICE" represents the assertion or the claim (e.g., "The firewall is active"). The "Trace" is the process (e.g., log generation, hash verification) that provides the evidentiary basis for that claim. This distinction is vital for maintaining the integrity of the audit chain: the trace is the *proof*, the descriptive entity is the *statement*.

#### 4.2 Relational Mapping
The `t_trace_supports_claim` table catalogs the trace processes available within the governance framework. Each entry represents a class of activity capable of generating evidence. By populating this table, an organization defines its acceptable methods of proof.

### 5. Risk Addressal and Control Logic

#### 5.1 Axiomatic Definition
The final component of the governance framework is the control mechanism. Axiom 5 (`control_only_addresses_threat_class`) defines a Control Class `{X}` as a subclass of `DirectiveICE` that `addressesRisk` *only* regarding a specific Threat Class `{Y}`.

The use of the universal quantifier ("only") is semantically precise. It implies that the control is scoped exclusively to the threat class `{Y}`. If a control addresses a threat outside of `{Y}`, it violates this specific axiom (or rather, does not fall under this specific subclass definition). This precision prevents scope creep and ensures that controls are tightly coupled to the specific risks they are designed to mitigate.

#### 5.2 Relational Mapping
The table `t_control_only_addresses_threat_class` links specific controls to the PCI DSS requirements they address (which serve as the proxy for the threat class in this schema via the foreign key). This mapping ensures that every control implementation is justified by a specific requirement/threat context.
