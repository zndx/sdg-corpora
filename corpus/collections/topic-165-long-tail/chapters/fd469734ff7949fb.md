# Formal Ontology of Compliance Artifacts: A PCI DSS Governance Framework

This chapter establishes a formal ontological framework for mapping Payment Card Industry Data Security Standard (PCI DSS) requirements to governance artifacts. It delineates the structural relationships between regulatory directives, control mechanisms, and evidentiary traces within a compliance management system. The objective is to provide a rigorous, machine-readable schema that supports automated audit trails and regulatory reporting, ensuring that every control implementation is traceable to a specific requirement and signed off by a responsible agent.

## 1. PCI DSS Requirements as Information Content Entities

In the context of governance frameworks, a PCI DSS requirement is not merely a textual statement but a formal Information Content Entity (ICE) classified under the `cco:DirectiveICE` hierarchy. This classification elevates the requirement from a passive string of text to an active directive that prescribes specific behavior. The axiom `pci_dss_requirement` posits that such a directive is defined by its relationship to a specific requirement class. This relationship is foundational; it asserts that for a governance artifact to be recognized as a valid PCI DSS directive, it must necessarily fulfill the criteria of a requirement class defined within the standard.

This formalization allows compliance engines to infer the nature of an artifact based solely on its class properties. For instance, when a system encounters an entity classified as a PCI DSS requirement, it can immediately infer that this entity is a directive intended to enforce a specific control posture. The relational projection of this axiom creates a dependency between the requirement instance and its equivalent specification, ensuring that no requirement exists in a vacuum—it must point to a defined specification target.

The following table illustrates instances of this axiom, demonstrating how specific requirement classes (X) are mapped to their requirement definitions (Y), which in turn reference specific specification targets.

| id | x | y |
|---|---|---|
| req_001 | FirewallConfigurationDirective | spec_target_001 |
| req_002 | DataEncryptionStandard | spec_target_002 |
| req_003 | AntiVirusMechanism | spec_target_003 |
| req_004 | AccessControlProtocol | spec_target_004 |
| req_005 | MonitoringSystemLog | spec_target_005 |

### 1.1 Directive Inference
The utility of this structure lies in the deductive reasoning capabilities it affords the auditor. By querying the `t_pci_dss_requirement` table, an auditor can verify that all directives loaded into the governance framework are properly anchored to a requirement definition. The foreign key constraint ensures referential integrity; a requirement cannot be entered into the system without a valid specification target, thereby preventing orphaned or unvalidated compliance artifacts from polluting the audit record.

## 2. Specification Equivalence and Target Application

Building upon the basic directive structure, the `requirement_equiv_specifies_target` axiom introduces the concept of equivalence. A requirement is not merely a directive; it is equivalent to the intersection of a directive, a specification, and a target application. This tripartite equivalence is critical for granular governance. It asserts that a PCI DSS requirement (X) is semantically equivalent to a directive that specifies a particular control (Y) and applies to a specific system component (Z).

This axiom resolves ambiguity in compliance mapping. In traditional manual audits, it is often unclear whether a requirement applies to a network segment, a database, or an application. By enforcing the `sdg:specifies` and `sdg:appliesTo` slots, the ontology mandates that every requirement be explicitly bound to a target. This creates a rigid schema where the "specifies" slot (Y) acts as a bridge back to the requirement definition, creating a recursive validation loop that ensures the directive and the specification are mutually consistent.

The relational schema for this concept enforces a circular dependency with the PCI DSS requirement table, ensuring that specifications and requirements are inextricably linked. The table below captures this relationship, showing how directives are mapped to their specific requirements and operational targets.

| id | x | y | z |
|---|---|---|---|
| spec_target_001 | FirewallConfigurationDirective | req_001 | PerimeterNetwork |
| spec_target_002 | DataEncryptionStandard | req_002 | CardholderDataEnvironment |
| spec_target_003 | AntiVirusMechanism | req_003 | EndUserWorkstation |
| spec_target_004 | AccessControlProtocol | req_004 | AuthenticationServer |
| spec_target_005 | MonitoringSystemLog | req_005 | SecurityInformationEventManagement |

### 2.1 Target Application Logic
The `z` slot, representing the target, is of particular interest to risk assessors. It allows for the segmentation of the compliance landscape. By filtering on `z`, an organization can instantly generate a report of all PCI DSS requirements applicable specifically to, for example, the "CardholderDataEnvironment." This capability transforms the ontology from a static dictionary into a dynamic tool for scope management and audit planning.

## 3. Control Logic and Threat Addressal

While requirements define what must be done, controls define how risks are mitigated. The axiom `control_only_addresses_threat_class` formalizes the relationship between a control directive and the specific threat class it is designed to mitigate. This axiom is a SubClassOf restriction, meaning that if an entity is a Control, it *must* address a specific Risk Class. The use of the "only" (`only`) constructor in the Manchester syntax is semantically significant: it implies that the control's purpose is restricted exclusively to addressing the defined threat class.

In practice, this prevents scope creep in control implementation. A control designed to address "Insider Threat" cannot be arbitrarily applied to mitigate "Malware Injection" without reclassification. The ontology enforces a strict mapping where the control (X) addresses the risk (Y), and Y must be a valid PCI DSS requirement ID (as per the foreign key constraint). This ties the operational control layer back to the regulatory requirement layer, ensuring that every mitigating action is traceable to a compliance mandate.

The table below demonstrates this mapping, linking specific control classes to the requirement IDs (threats) they address.

| id | x | y |
|---|---|---|
| ctrl_001 | TwoFactorAuthenticationControl | req_004 |
| ctrl_002 | AES256EncryptionProtocol | req_002 |
| ctrl_003 | HeuristicScanningEngine | req_003 |
| ctrl_004 | StatefulPacketInspection | req_001 |
| ctrl_005 | LogAggregationService | req_005 |

### 3.1 Risk Mitigation Validation
For the compliance officer, this structure serves as a validation matrix. If a risk assessment identifies a vulnerability in "DataEncryptionStandard" (req_002), the system can query `t_control_only_addresses_threat_class` to identify "AES256EncryptionProtocol" (ctrl_002) as the designated mitigating control. If the foreign key link is broken or missing, it indicates a gap in the control framework—a control exists that is not formally mapped to a regulatory threat, rendering it potentially redundant or unauditable.

## 4. Attestation and Agent Responsibility

Governance frameworks rely on the concept of attestation—the formal acknowledgment by a qualified individual that a control or process is operating as intended. The axiom `attestation_signed_by` defines this process as a subclass of `bfo:0000015` (a Process). It asserts that an attestation (X) is a process that is signed by a Person (`cco:Person`).

This distinction is vital for audit trails. It separates the *act* of compliance (the process) from the *agent* of compliance (the person). In legal and regulatory terms, the signature represents the assignment of liability. By modeling attestation as a process with a mandatory `signedBy` property, the ontology captures the workflow of approval. It is not sufficient for a report to exist; it must be a process artifact that carries the digital or physical signature of an authorized agent.

The following table represents instances of attestation processes. Note that the `x` value represents the attestation process itself, which is an instance of a class defined by the axiom.

| id | x |
|---|---|
| attest_01 | QuarterlyReviewAttestation |
| attest_02 | AnnualVulnerabilityAssessmentSignOff |
| attest_03 | PolicyAcknowledgementProcess |
| attest_04 | IncidentResponsePlanApproval |
| attest_05 | PenetrationTestAttestation |

### 4.1 Non-Repudiation and Identity
The `t_attestation_signed_by` table structure implies a separate registry of Persons (not shown here, but referenced via the `cco:Person` class). In a full implementation, the `x` values in this table would serve as the primary keys for linking to a signature table containing timestamps, cryptographic hashes, and user IDs. This ensures non-repudiation. The auditor can verify not just *that* a process was completed, but *who* authorized the completion and when.

## 5. Traceability and Evidentiary Support

The final concept, and perhaps the most critical for audit readiness, is the support of claims through traces. The axiom `trace_supports_claim` defines a Trace (X) as a process that supports a Claim (`cco:DescriptiveICE`). A "Claim" in this context is a statement of compliance (e.g., "All servers are patched"), while a "Trace" is the evidentiary trail (e.g., the patch management logs) that substantiates that claim.

This axiom formalizes the evidence lifecycle. A claim without a supporting trace is an unsubstantiated assertion. By defining the Trace as a `bfo:0000015` (Process), the ontology acknowledges that evidence is often the result of a procedural activity—logging, monitoring, or sampling—rather than a static object. The `supportsClaim` property links the procedural generation of evidence to the descriptive assertion of compliance.

### 5.1 The Audit Chain of Custody
The integration of `t_trace_supports_claim` into the broader schema completes the audit chain. It connects the operational reality (the trace) to the governance assertion (the claim). When an auditor challenges a compliance status, the system retrieves the relevant Trace ID. Because the Trace is modeled as a process, the system can further drill down into the parameters of that process—start time, end time, data sources—to validate the integrity of the evidence. This dense web of relationships, from Requirement to Control to Attestation to Trace, provides a comprehensive, verifiable picture of the organization's security posture.
