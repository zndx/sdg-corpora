# Chapter 7: Formal Ontology of Compliance Directives and Audit Evidence

## 7.1 Scope and Preamble

This chapter establishes the formal ontological framework for mapping compliance directives to specific audit artifacts within a regulated environment. The primary objective is to define the structural relationships between abstract regulatory requirements, concrete control implementations, and the evidentiary traces that substantiate compliance posture. The definitions provided herein utilize the Manchester Syntax for Web Ontology Language (OWL) to axiomatize the relationships between governance artifacts. These axioms are deterministic in nature, projecting to a relational schema that enforces referential integrity across compliance datasets. The following sections detail five core axioms governing PCI DSS requirements, attestation workflows, evidentiary support, requirement specification, and threat mitigation controls.

## 7.2 PCI DSS Requirement Formalization

The foundational unit of regulatory adherence is the PCI DSS Requirement, formally defined as a subclass of the Directive Information Content Entity (ICE). In this framework, a specific class of directive is axiomatized as a PCI DSS Requirement only if it necessitates a specific requirement specification target. This relationship ensures that high-level regulatory mandates are inextricably linked to their granular implementation specifications.

The axiom `pci_dss_requirement` posits that for a class `X` to be considered a PCI DSS Requirement, it must possess a `pciDssRequirement` relationship with a target class `Y`. This structure prevents the existence of orphaned regulatory requirements; every requirement must point to a valid specification target within the system. The relational projection of this axiom enforces that the `y` slot (the requirement target) must exist as a primary key in the specification table, thereby creating a rigid chain of custody from regulation to implementation.

**Table 7.1: PCI DSS Requirement Mapping**
This table embodies the `pci_dss_requirement` axiom, listing the directive classes (`x`) and their corresponding specification targets (`y`). The primary key is `id`, and `y` functions as a foreign key linking to the requirement specification targets.

| id | x | y |
| :--- | :--- | :--- |
| PCI_REQ_001 | NetworkFirewallDirective | REQ_SPEC_TARGET_001 |
| PCI_REQ_002 | DataEncryptionDirective | REQ_SPEC_TARGET_002 |

In practice, the `NetworkFirewallDirective` (PCI_REQ_001) is not merely a static text string but a directive entity that necessitates the specific configuration parameters defined in `REQ_SPEC_TARGET_001`. This mapping allows auditors to query the directive and immediately retrieve the exact specification target that must be verified in the infrastructure.

## 7.3 Attestation and Signatory Authority

Compliance frameworks rely heavily on the concept of attestation—the formal act of validating a process or state. Ontologically, attestation is modeled as a process (specifically, a subclass of `bfo:0000015`, denoting a processual entity) that requires the intervention of an agent. The axiom `attestation_signed_by` formalizes this by asserting that any attestation class `X` must be signed by a `cco:Person`.

This axiom ensures that automated or system-generated logs cannot constitute a valid attestation without the explicit binding of a responsible individual. The `signedBy` property creates a link between the process of attestation and the legal or corporate persona assuming liability for the accuracy of the attested data. In the relational schema, this is represented by a table linking the attestation instance to the class definition of the attestation process itself.

**Table 7.2: Attestation Signatory Records**
This table illustrates the `attestation_signed_by` axiom. The column `x` represents the class of the attestation process (e.g., AnnualComplianceAttestation), which is axiomatically restricted to be signed by a person.

| id | x |
| :--- | :--- |
| ATT_SIGN_01 | AnnualComplianceAttestation |
| ATT_SIGN_02 | QuarterlyReviewAttestation |
| ATT_SIGN_03 | IncidentResponseVerification |
| ATT_SIGN_04 | PolicyUpdateAcknowledgement |
| ATT_SIGN_05 | ThirdPartyAuditValidation |

The record `ATT_SIGN_01` represents the class `AnnualComplianceAttestation`. While the specific instance of the signer (e.g., "John Doe") is managed at the instance level, the class-level axiom dictates that *any* instance of `AnnualComplianceAttestation` must inherit the property of being signed by a person. This constraint is critical for maintaining non-repudiation in audit trails.

## 7.4 Audit Traces and Claim Support

The validity of any compliance claim rests on the existence of supporting evidence. The ontology formalizes evidence through the `trace_supports_claim` axiom. Here, a class `X` (a Trace) is defined as a process that supports a claim, where the claim is a Descriptive Information Content Entity (`cco:DescriptiveICE`). This distinction is vital: the trace is the *act* or *process* of generating or capturing evidence (e.g., a system log generation process), while the claim is the informational content derived from that trace (e.g., "the system was patched").

By axiomatizing the trace as a process (`bfo:0000015`), the framework acknowledges that evidence is dynamic. It involves the temporal occurrence of data collection, storage, and verification. The `supportsClaim` relationship bridges the procedural gap between the raw data generation and the formal assertion of compliance.

**Table 7.3: Trace-to-Claim Relationships**
This table operationalizes the `trace_supports_claim` axiom. The `x` column identifies the specific trace process class responsible for substantiating a descriptive claim.

| id | x |
| :--- | :--- |
| TRACE_SUPPORT_01 | FirewallConfigurationLog |
| TRACE_SUPPORT_02 | CiphertextVerificationReport |
| TRACE_SUPPORT_03 | AccessControlListAudit |
| TRACE_SUPPORT_04 | PhysicalEntryLogReview |
| TRACE_SUPPORT_05 | MalwareScanExecutionTrace |

For instance, `TRACE_SUPPORT_01` corresponds to the `FirewallConfigurationLog` process. This process is the mechanism by which the organization substantiates the claim that "firewalls are configured per standard." The axiom guarantees that without such a process class defined, the claim cannot be formally supported within the ontology.

## 7.5 Requirement Specification and Target Application

The most complex structural definition in this chapter is the `requirement_equiv_specifies_target` axiom. This axiom utilizes an "EquivalentTo" construct, meaning that a class `X` is defined *exactly* by the intersection of three properties:
1.  It is a `cco:DirectiveICE`.
2.  It `sdg:specifies` some target class `Y`.
3.  It `sdg:appliesTo` some scope class `Z`.

This axiom serves as the definitive definition for a requirement specification target. It resolves the ambiguity of what constitutes a "requirement" by asserting that a requirement is *nothing more* and *nothing less* than a directive that specifies a control and applies to a specific target (such as a system, network zone, or data type).

The relational projection of this axiom is significant because it establishes the foreign key dependencies that bind the compliance framework together. The `y` column (the specification) references the PCI DSS requirement defined in Section 7.2, creating a bidirectional link where the PCI requirement points to the target, and the target specifies the PCI requirement.

This table captures the `requirement_equiv_specifies_target` axiom. Column `x` is the requirement class; `y` is the PCI requirement it specifies (referencing Table 7.1); and `z` is the target scope to which it applies.

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| REQ_SPEC_TARGET_001 | PerimeterFirewallControl | PCI_REQ_001 | CardholderDataEnvironment |
| REQ_SPEC_TARGET_002 | TransmissionEncryptionControl | PCI_REQ_002 | PublicNetworkInterface |
| REQ_SPEC_TARGET_003 | RoleBasedAccessControl | PCI_REQ_003 | OperatingSystemLayer |
| REQ_SPEC_TARGET_004 | AutomatedVulnerabilityScanner | PCI_REQ_004 | InternalNetworkSegment |

Consider the record `REQ_SPEC_TARGET_001`. The class `PerimeterFirewallControl` is defined as the directive that specifies `PCI_REQ_001` (NetworkFirewallDirective) and applies to the `CardholderDataEnvironment`. This equivalence ensures that one cannot discuss the `PerimeterFirewallControl` without implicitly referencing both the governing PCI directive and the specific environmental scope.

## 7.6 Control-Threat Addressing

The final axiom, `control_only_addresses_threat_class`, refines the utility of directives by mapping them to the specific risks they mitigate. This axiom asserts that a class `X` (a Control) is a subclass of `DirectiveICE` that addresses a risk `Y`. The use of the "only" restriction (`only`) in the Manchester syntax implies a universal quantification: if this control addresses any risk, it must be an instance of class `Y`.

In the context of the relational schema, `y` references the PCI DSS requirement ID. This design choice models the threat class not as an abstract risk category, but as the specific regulatory requirement that defines the threat mitigation. For example, the threat of "unauthorized network access" is codified in the ontology as the PCI requirement governing firewalls. Therefore, a control addressing this threat is linked directly to that requirement ID.

**Table 7.5: Control-Threat Class Mapping**
This table represents the `control_only_addresses_threat_class` axiom. Column `x` denotes the control class, and `y` denotes the threat class (referenced via the PCI requirement ID).

| id | x | y |
| :--- | :--- | :--- |
| CTRL_THREAT_01 | IngressFilteringRule | PCI_REQ_001 |
| CTRL_THREAT_02 | TLSProtocolEnforcement | PCI_REQ_002 |
| CTRL_THREAT_03 | BiometricAuthenticationSystem | PCI_REQ_003 |
| CTRL_THREAT_04 | SignatureBasedIDS | PCI_REQ_004 |
| CTRL_THREAT_05 | StaticCodeAnalysisTool | PCI_REQ_005 |

The entry `CTRL_THREAT_01` illustrates that the `IngressFilteringRule` control class addresses the threat class defined by `PCI_REQ_001`. By enforcing the foreign key constraint to the PCI requirement table, the ontology ensures that controls are never designed to mitigate undefined or non-compliant threats. Every control must trace back to a ratified regulatory requirement, closing the loop between governance, risk management, and compliance.
