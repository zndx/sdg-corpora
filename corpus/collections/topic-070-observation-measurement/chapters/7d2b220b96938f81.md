# Chapter 4: Ontological Mapping of Compliance Directives and Audit Attestation

## 4.1 Scope and Preamble

This chapter establishes the formal ontological framework required to map regulatory compliance artifacts—specifically those derived from the General Data Protection Regulation (GDPR) and the System and Organization Controls (SOC) 2 framework—into a coherent governance structure. The content herein defines the necessary classes and relationships to model the lifecycle of compliance directives, from their instantiation as legal requirements to their verification through audit processes and personnel attestations. The definitions provided are grounded in the Basic Formal Ontology (BFO) and the Common Core Ontologies (CCO), ensuring that the data structures proposed are suitable for high-assurance environments such as regulatory reporting and automated compliance auditing. Readers should note that the relational schemas presented are deterministic projections of the underlying OWL axioms and must be implemented exactly as specified to maintain referential integrity across the governance knowledge base.

## 4.2 Attestation and Personnel Accountability

### 4.2.1 Conceptual Definition
The foundational unit of governance in any compliance framework is the attestation. Ontologically, an attestation is defined as a process (specifically, a `bfo:0000015` processual entity) that is validated by the action of a specific agent. In this framework, we define the class `AttestationSignedBy` to represent this construct. This class asserts that for any attestation process to be valid, it must be signed by a person (an instance of `cco:Person`). This axiom binds the procedural artifact to the legal or moral agent responsible for its execution, thereby establishing a chain of custody and accountability.

### 4.2.2 Implementation and Data Representation
In practice, the `AttestationSignedBy` class serves as the primary key generator for downstream compliance artifacts. Because the attestation represents the point-in-time validation of a control or directive, unique identification of the attestation event is required. The relational schema for this axiom is restricted to the entity identifier and the class name of the attestation process.

The following table illustrates instances of personnel attestations. Note that the `x` column denotes the specific class of the attestation process (e.g., `DataProcessingAttestation`), while the `id` serves as the immutable reference for this event.

**Table 4-1: Attestation Signed By Instances**

| id | x |
| :--- | :--- |
| ATT-2023-001 | DataProcessingAttestation |
| ATT-2023-002 | AccessControlAttestation |

The integrity of the compliance framework relies on the premise that no directive is considered enacted until a corresponding entry exists in this table, linking the process to a verified human signatory.

## 4.3 Regulatory Directives under GDPR

### 4.3.1 Conceptual Definition
The General Data Protection Regulation (GDPR) imposes specific legal obligations on data controllers and processors. To model these obligations within an ontology, we define the class `GDPRArticleSubclass`. This class is a subclass of `cco:DirectiveICE` (Information Content Entity), representing the textual or codified directive. The axiom asserts that any subclass of this type is something that "gdpr article" a specific regulatory class {Y}.

Crucially, the data model enforces a dependency between the regulatory directive and the attestation process defined in Section 4.2. The foreign key constraint in the schema mandates that a GDPR directive instance must reference a valid attestation ID. This reflects the operational reality that a legal article is not merely abstract text but is instantiated within the organization only when it is actively attested to by a responsible person.

### 4.3.2 Implementation and Data Representation
When populating the `t_gdpr_article_subclass` table, the `y` column must contain the `id` of an attestation from the `t_attestation_signed_by` table. This linkage ensures that every GDPR directive tracked by the system is anchored to a specific accountability event.

**Table 4-2: GDPR Article Subclass Instances**

| id | x | y |
| :--- | :--- | :--- |
| GDPR-ART-17 | RightToErasureDirective | ATT-2023-001 |
| GDPR-ART-25 | DataProtectionByDesignDirective | ATT-2023-002 |
| GDPR-ART-32 | SecurityOfProcessingDirective | ATT-2023-003 |
| GDPR-ART-28 | ProcessorControllerDirective | ATT-2023-004 |

In the table above, the `RightToErasureDirective` (x) is mapped to the attestation `ATT-2023-001` (y). This indicates that the specific interpretation and implementation of Article 17 (Right to Erasure) within this governance framework is formally recorded and signed under the attestation event `ATT-2023-001`.

## 4.4 SOC2 Trust Criteria Integration

### 4.4.1 Conceptual Definition
Parallel to the GDPR framework, many organizations must adhere to the Trust Services Criteria (TSC) defined by the American Institute of Certified Public Accountants (AICPA) for SOC 2 reports. The ontology models this via the `SOC2TrustCriterion` class. Like the GDPR directive, this is a subclass of `cco:DirectiveICE`. The axiom posits that this class represents something that "soc2 trust criterion" a specific class {Y}.

The structural dependency mirrors that of the GDPR directives: a SOC 2 trust criterion is instantiated only when linked to a personnel attestation. This design allows for a unified view of compliance where distinct regulatory regimes (GDPR and SOC2) share a common layer of procedural accountability (the attestation).

### 4.4.2 Implementation and Data Representation
The table below demonstrates how SOC2 criteria are mapped to the attestation records established in Section 4.2. The `y` column, acting as a foreign key, populates with the attestation IDs, thereby enforcing the relationship between the trust criterion and the individual who validated it.

## 4.5 Evidence-Based Attestation

### 4.5.1 Conceptual Definition
A robust compliance framework cannot rely solely on assertions of compliance; it must be evidence-based. The `AttestationWithSupportingEvidence` axiom defines a process (subclass of `bfo:0000015`) that includes the property `sdg:withSupportingEvidence`. This property links the attestation process to a specific class of evidence {Y}.

The relational schema for this axiom introduces a critical dependency: the evidence (`y`) must reference a valid `GDPRArticleSubclass` ID. This constraint enforces a specific hierarchy: evidence is not merely attached to an attestation in a vacuum; it must substantiate a specific regulatory directive (in this schema, a GDPR article). This structure prevents "orphaned" evidence and ensures that every artifact submitted for audit is directly traceable to a legal requirement.

### 4.5.2 Implementation and Data Representation
In the following table, the `x` column represents the specific attestation process class that includes evidence, while the `y` column contains the ID of the GDPR directive that serves as the supporting evidence.

**Table 4-4: Attestation With Supporting Evidence Instances**

| id | x | y |
| :--- | :--- | :--- |
| EVI-PROC-01 | UserDeletionAttestation | GDPR-ART-17 |
| EVI-PROC-02 | AccessReviewAttestation | GDPR-ART-25 |
| EVI-PROC-03 | PenetrationTestAttestation | GDPR-ART-32 |
| EVI-PROC-04 | DPAReviewAttestation | GDPR-ART-28 |

Here, the `UserDeletionAttestation` (x) utilizes `GDPR-ART-17` (y) as its supporting evidence. This indicates that the attestation of the user deletion process is substantiated by the directive and records corresponding to the "Right to Erasure." The foreign key constraint ensures that `GDPR-ART-17` exists in the `t_gdpr_article_subclass` table, maintaining the chain of evidence from the Person -> Attestation -> Directive -> Evidence.

## 4.6 Audit Mechanisms and Control Verification

### 4.6.1 Conceptual Definition
The final component of the governance ontology is the audit mechanism. The `AuditSubclass` axiom defines a process that "audits control" a `cco:DirectiveICE`. This represents the independent or internal review function that examines the directives defined in the previous sections. As a subclass of `bfo:0000015`, the audit is a time-bound process that scrutinizes the state of the information content entities (the directives) to verify their implementation and efficacy.

Unlike the evidence linkage, the audit subclass does not require a foreign key dependency in this specific schema projection, treating the audit class as a high-level categorization of review activities. However, the semantic definition implies that the object of the audit is the `DirectiveICE` (e.g., the GDPR or SOC2 directives).
