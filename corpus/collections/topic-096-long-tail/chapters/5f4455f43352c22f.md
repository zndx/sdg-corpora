# Chapter 4: Formal Ontology of Compliance Directives and Governance Frameworks

## 4.1 Scope and Preamble

This chapter delineates the formal ontological structures governing the definition, jurisdiction, and enforcement of compliance directives within an enterprise information security context. It establishes a rigorous framework for mapping abstract governance artifacts—specifically those aligned with the Payment Card Industry Data Security Standard (PCI DSS)—to concrete operational controls. The discourse herein proceeds from the general definition of a Requirement to the specific instantiation of PCI DSS obligations, culminating in the procedural mechanisms of attestation and enforcement. Readers are advised to consult the accompanying relational schemata to verify the referential integrity of the proposed data structures, ensuring that all foreign key constraints are satisfied prior to implementation in a governance, risk, and compliance (GRC) repository.

## 4.2 Requirement Equivalence and Specification

The foundational unit of governance is the Requirement, formally defined within the ontology as a subclass of the Directive Information Content Entity (DirectiveICE). This concept is not merely a textual label but a logical construct that derives its meaning from two necessary conditions: it must specify a target object, and it must apply to a defined scope. In formal Manchester Syntax, this is expressed as `Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`.

This equivalence axiom ensures that a Requirement cannot exist in a vacuum; it is relationally bound to the object it governs (the `Y` slot) and the context in which it is relevant (the `Z` slot). For instance, a requirement regarding "password complexity" is only valid as a governance object if it specifies a "password policy" and applies to "system users." In a relational database context, this necessitates a structure where the requirement instance is linked directly to the entity it specifies.

The following table embodies the axiom `requirement_equiv_specifies_target`. It illustrates the primary key (`id`) identifying the specific requirement instance, the class definition (`x`), the target specification (`y`), and the scope of application (`z`). The foreign key constraint on column `y` ensures that the target specification corresponds to a valid entry in the PCI DSS requirement registry, maintaining referential integrity across the governance model.

## 4.3 PCI DSS Requirement Subclassing

While the previous section defines the generic structure of a requirement, compliance frameworks often demand domain-specific specialization. The PCI DSS framework introduces a distinct class of obligations that must be formally mapped to the generic directive structure. The ontology defines this via the axiom `pci_dss_requirement`: `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`.

Verbalized, this asserts that `{X}` is something that "PCI DSS requirement" `{Y}`. This creates a critical bidirectional linkage in the data model. The generic Requirement (defined in Section 4.2) specifies a PCI DSS Requirement, and conversely, the PCI DSS Requirement is a type of Directive that references the generic Requirement. This circular dependency is intentional; it allows the governance framework to trace a specific control objective back to a formal regulatory citation while maintaining the properties of the generic directive.

The table below represents the `t_pci_dss_requirement` schema. The primary key (`id`) serves as the unique identifier for the PCI DSS requirement. Column `x` denotes the specific class of the PCI requirement, and column `y` acts as a foreign key referencing the generic requirement ID (`t_requirement_equiv_specifies_target`), thereby instantiating the "pciDssRequirement" relationship.

## 4.4 Policy Jurisdiction and Governance Scope

Moving from specific requirements to broader governance mandates, we define the Policy. A Policy is a high-level DirectiveICE that asserts authority over a specific domain and governs a particular scope. The axiom `policy_equiv_jurisdiction_and_scope` formalizes this: `Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:hasJurisdiction some {Y:Class}) and (sdg:governsScope some {Z:Class})`.

In this structure, the "Jurisdiction" (`Y`) is not merely a legal territory but is modeled as a reference to a specific PCI DSS requirement that grants the policy its regulatory authority. This anchors the policy in evidence-based compliance; the policy exists because a specific requirement demands it. The "Scope" (`Z`) defines the boundary of the policy's application, whether it be a geographic region, a business unit, or a technical architecture.

The table `t_policy_equiv_jurisdiction_and_scope` demonstrates this mapping. The foreign key in column `y` references the `t_pci_dss_requirement` table, establishing that the policy's jurisdiction is derived from that specific requirement. Column `z` defines the operational scope.

## 4.5 Attestation and Procedural Verification

Compliance is not static; it requires verification through processes. The ontology captures this via the concept of Attestation. Defined by the axiom `attestation_signed_by`, we have: `Class: {X:Class} SubClassOf: bfo:0000015, sdg:signedBy some cco:Person`. Here, `bfo:0000015` refers to a Process (a BFO:Process). Thus, an Attestation is a temporal process that culminates in a signature by a responsible natural person.

This distinction is vital for audit trails. It separates the *directive* (the policy or requirement) from the *act of compliance* (the attestation). The ontology ensures that an attestation is not merely a document but a process involving a human agent, satisfying non-repudiation requirements common in audit frameworks.

The table `t_attestation_signed_by` lists instances of these processes. Note that while the schema includes only `id` and `x` (the class of the attestation process), the implicit relationship to a Person is handled at the ontology level. In a full implementation, a separate join table would link this ID to a personnel registry. The rows below represent specific audit events.

## 4.6 Policy Enforcement Mechanisms

Finally, for a directive to be effective, it must possess enforcement capabilities. The ontology defines this via the axiom `policy_min_one_enforcer`: `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:enforcedBy min 1 {Y:Class}`. This utilizes a cardinality constraint (`min 1`), asserting that a valid Policy must be enforced by at least one mechanism or entity.

In the relational projection, the "Enforcer" (`Y`) is modeled as a foreign key referencing a PCI DSS requirement. This implies that the enforcement mechanism is grounded in the specific technical controls mandated by the standard. For example, a "Password Policy" is enforced by the "Secure Authentication" requirement (PCI-REQ-8.3), which in turn may be enforced by technical controls like an Active Directory password filter. This linkage ensures that every high-level policy has a tangible, requirement-based enforcement hook.

The table `t_policy_min_one_enforcer` illustrates these relationships. The `y` column references the `t_pci_dss_requirement` table, identifying the specific regulatory requirement that acts as the enforcement agent for the policy listed in column `x`.
