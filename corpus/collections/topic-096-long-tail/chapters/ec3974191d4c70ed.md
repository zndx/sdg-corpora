# Chapter 4: Ontological Mapping of PCI DSS Governance Structures

This chapter establishes the formal ontological framework required to map PCI DSS (Payment Card Industry Data Security Standard) controls to enterprise governance architectures. It details the structural definitions of directives, requirements, and enforcement mechanisms, ensuring alignment with regulatory standards through a rigorous, evidence-based methodology. The following sections decompose the core axioms governing the relationship between Information Content Entities (ICEs) and their operational targets, providing the necessary schema for automated compliance auditing.

## 1. Requirement Equivalence and Target Specification

The foundational axiom of the governance framework defines a Requirement as a specific subclass of a Directive Information Content Entity (ICE). This entity must satisfy three necessary and sufficient conditions: it must function as a directive, it must explicitly specify a control objective, and it must apply to a defined target scope. In formal ontology terms, this is expressed as the equivalence class `Requirement`, which intersects `cco:DirectiveICE` with the properties `sdg:specifies` and `sdg:appliesTo`.

This structure ensures that every compliance obligation is not merely a textual statement but a formal entity linked to actionable controls and specific environmental targets (e.g., system components, network zones). Administrators must verify that any new requirement introduced into the governance model strictly adheres to this tripartite structure to maintain logical consistency.

### 1.1 Relational Implementation

The following table embodies the axiom `requirement_equiv_specifies_target`. It maps the equivalence class to a relational structure where the primary key (`id`) identifies the specific requirement instance. The column `y` represents the control objective specified, which is foreign-keyed to the PCI requirement registry, while `z` denotes the target scope to which the directive applies.

| Requirement ID | Directive Class (X) | Specifies (Y) | Applies To (Z) |
| :--- | :--- | :--- | :--- |
| `REQ-CTRL-001` | `AccessControlDirective` | `PCI-REQ-8.1.1` | `CardholderDataEnvironment` |
| `REQ-CTRL-002` | `CryptographicDirective` | `PCI-REQ-4.1` | `OpenPublicNetwork` |
| `REQ-CTRL-003` | `LoggingDirective` | `PCI-REQ-10.2.1` | `AuditTrailServer` |
| `REQ-CTRL-004` | `PhysicalAccessDirective` | `PCI-REQ-9.1` | `ServerRoomZone` |
| `REQ-CTRL-005` | `WirelessDirective` | `PCI-REQ-1.2.3` | `GuestWirelessLAN` |

*Table 1.1: Requirement Equivalence and Target Specification*

Action: Ensure that all entries in the governance repository maintain valid foreign key references to the PCI requirement registry and that the target scope (`z`) is accurately classified within the asset inventory.

## 2. PCI DSS Requirement Classification

While the previous section defines the general structure of a requirement, this section addresses the specific classification of entities as PCI DSS requirements. The axiom `pci_dss_requirement` posits that a specific class `X` is a subclass of `cco:DirectiveICE` and possesses the property `sdg:pciDssRequirement`, linking it to a specific requirement class `Y`.

This classification is critical for regulatory reporting. It creates a distinct taxonomic category for obligations that fall under the PCI DSS umbrella, separating them from general corporate policies or local regulatory directives. The verbalization "{X} is something that pci dss requirement {Y}" implies that the entity `X` acts as the realization or instance of the abstract requirement `Y`.

### 2.1 Dependency and Circular Reference

The relational schema for this axiom introduces a circular dependency with the Requirement Equivalence table. The `t_pci_dss_requirement` table links its control objective (`y`) back to the `id` of the requirement equivalence table. This mutual dependency enforces a strict validation rule: a PCI DSS requirement cannot exist without a corresponding directive equivalence definition, and a directive equivalence definition intended for PCI compliance must reference a valid PCI requirement entry.

| PCI Req ID | Class (X) | PCI DSS Requirement (Y) |
| :--- | :--- | :--- |
| `PCI-REQ-8.1.1` | `IdentityManagement` | `REQ-CTRL-001` |
| `PCI-REQ-4.1` | `DataEncryptionStandard` | `REQ-CTRL-002` |
| `PCI-REQ-10.2.1` | `SystemAuditLogging` | `REQ-CTRL-003` |
| `PCI-REQ-9.1` | `SitePhysicalSecurity` | `REQ-CTRL-004` |
| `PCI-REQ-1.2.3` | `WirelessAccessControl` | `REQ-CTRL-005` |

*Table 2.1: PCI DSS Requirement Classification*

Note: The `y` column in this table serves as the bridge to the specific directive definitions in Table 1.1. Any update to the requirement ID in Table 1.1 must cascade to this reference to maintain referential integrity.

## 3. Policy Jurisdiction and Governance Scope

Policies differ from requirements in that they define the overarching governance framework rather than specific control targets. The axiom `policy_equiv_jurisdiction_and_scope` defines a Policy as a Directive ICE that asserts a jurisdiction and governs a specific scope. Jurisdiction refers to the legal or regulatory authority (e.g., EU, US Federal, State-level), while the scope defines the organizational or data boundaries subject to that authority.

This distinction is vital for multi-national organizations. A single technical requirement (e.g., encryption at rest) may fall under multiple policies with different jurisdictions (e.g., GDPR and CCPA). The ontology allows for the mapping of a single directive to multiple governance contexts without duplicating the technical definition.

### 3.1 Jurisdictional Mapping

The table below embodies the `policy_equiv_jurisdiction_and_scope` axiom. The primary key (`id`) represents the unique policy identifier. The column `y` establishes the link to the specific PCI requirement driving the policy, while `z` defines the jurisdictional scope. This structure ensures that technical controls are traceable back to the legal or regulatory frameworks that mandate them.

| Policy ID | Policy Class (X) | PCI Requirement Ref (Y) | Jurisdiction/Scope (Z) |
| :--- | :--- | :--- | :--- |
| `POL-GDPR-001` | `DataProtectionPolicy` | `PCI-REQ-8.1.1` | `EuropeanEconomicArea` |
| `POL-CCPA-001` | `PrivacyRightsPolicy` | `PCI-REQ-4.1` | `CaliforniaState` |
| `POL-NYDFS-001` | `CybersecurityRegulation` | `PCI-REQ-10.2.1` | `NewYorkFinancialSector` |

*Table 3.1: Policy Jurisdiction and Scope*

Action: Review jurisdictional assignments quarterly to ensure that changes in regulatory law (e.g., amendments to the GDPR) are reflected in the `z` column and propagated to the relevant compliance teams.

## 4. Attestation and Signatory Authority

Compliance is not merely a static state but a process of verification. The axiom `attestation_signed_by` defines an Attestation as a subclass of a Process (`bfo:0000015`) that is signed by a Person (`cco:Person`). This formalizes the act of certification, transforming a subjective assessment into an auditable event recorded in the ontology.

In the context of the governance framework, attestation serves as the "seal" of validity for the compliance state. It links the procedural act of verification to a responsible individual, establishing accountability. This axiom is crucial for audit trails, as it separates the automated collection of evidence (a process) from the human validation of that evidence (the attestation).

### 4.1 Attestation Registry

The table `t_attestation_signed_by` implements this axiom. It is a simple registry linking the specific attestation process instance (`id`) to the class of the attestation event (`x`). Unlike other tables in this chapter, it does not link to the requirement tables directly, as attestations may cover multiple requirements or entire policy domains.

| Attestation ID | Attestation Process Class (X) |
| :--- | :--- |
| `ATT-2023-Q3` | `QuarterlyReviewProcess` |
| `ATT-2023-EXT` | `ExternalAuditProcess` |
| `ATT-2023-INC` | `IncidentResponseAttestation` |
| `ATT-2023-ACC` | `AccessControlCertification` |
| `ATT-2023-PEN` | `PenetrationTestSignOff` |

*Table 4.1: Attestation Processes*

Important: While the table defines the process class, the actual signatory (the `cco:Person`) is linked via the object property `sdg:signedBy` at the instance level, which must be resolved in the directory services layer.

## 5. Policy Enforcement Mechanisms

A directive without enforcement is merely advisory. The axiom `policy_min_one_enforcer` stipulates that a Policy (a Directive ICE) must be enforced by a minimum of one Enforcer. This enforcer can be a role (e.g., Chief Information Security Officer), a system (e.g., Automated Compliance Scanner), or an external body. The use of "min 1" in the axiom indicates that enforcement is mandatory; a policy with zero enforcers is invalid within the ontology.

This concept operationalizes the governance framework. It moves the organization from "defining" rules to "implementing" them. By mapping policies to their enforcers, the organization can conduct gap analyses to identify orphaned policies (those defined but not actively enforced) and resource conflicts (a single enforcer overloaded with conflicting policy obligations).

### 5.1 Enforcement Assignment

The table `t_policy_min_one_enforcer` maps the Policy (`x`) to the Enforcer (`y`). The schema dictates that the Enforcer column (`y`) references the PCI Requirement table. This implies a specific design choice: enforcement is modeled as being tightly coupled to the specific technical requirement instance that drives the policy, rather than the high-level policy document itself.

| Enforcement ID | Policy Class (X) | Enforcer Ref (Y) |
| :--- | :--- | :--- |
| `ENF-001` | `CorporateSecurityPolicy` | `PCI-REQ-8.1.1` |
| `ENF-002` | `DataProtectionPolicy` | `PCI-REQ-4.1` |
| `ENF-003` | `AuditGovernancePolicy` | `PCI-REQ-10.2.1` |
| `ENF-004` | `FacilityAccessPolicy` | `PCI-REQ-9.1` |
| `ENF-005` | `NetworkArchitecturePolicy` | `PCI-REQ-1.2.3` |

*Table 5.1: Policy Enforcement Mapping*

Action: Validate that the entity referenced in the `y` column has the operational capacity to enforce the requirement. For example, if `PCI-REQ-8.1.1` references an automated provisioning tool, ensure that tool is active and configured correctly.
