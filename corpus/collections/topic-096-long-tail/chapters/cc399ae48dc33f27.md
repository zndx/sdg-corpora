# Directive Governance Models for PCI DSS Compliance

This chapter defines a minimal relational schema that materializes five OWL axioms governing directive information content entities. The schema supports traceability from PCI DSS requirements through jurisdiction-scoped policies to signed attestations, enabling verification that each policy is enforced by at least one requirement and specifies concrete targets.

## 1 Schema Structure and Axiom Mapping

The five tables implement the supplied Manchester axioms directly. Primary keys are surrogate identifiers; foreign keys encode the existential restrictions and minimum-cardinality constraints expressed in the ontology.

### 1.1 t_requirement_equiv_specifies_target

This table embodies AXIOM 1 by recording the conjunction of cco:DirectiveICE with sdg:specifies and sdg:appliesTo restrictions. Column id is the primary key; columns y and z are foreign keys that respectively reference the requirement being specialized and the target class to which the requirement applies.

| id | x | y | z |
| req_spec_001 | Requirement_12 | pci_req_001 | AccountData |
| req_spec_002 | Requirement_2 | pci_req_002 | NetworkSegment |
| req_spec_003 | Requirement_3 | pci_req_003 | SystemComponent |
| req_spec_004 | Requirement_8 | pci_req_004 | AuthenticationData |
| req_spec_005 | Requirement_10 | pci_req_005 | AuditLog |

### 1.2 t_pci_dss_requirement

This table realizes AXIOM 2, asserting that each directive is a subclass of cco:DirectiveICE and participates in the sdg:pciDssRequirement relation. Column id is the primary key; column y is a foreign key referencing t_requirement_equiv_specifies_target, establishing the bidirectional link required by the axiom pair.

### 1.3 t_policy_equiv_jurisdiction_and_scope

This table materializes AXIOM 3 by capturing the equivalent-class expression that conjoins cco:DirectiveICE with sdg:hasJurisdiction and sdg:governsScope. Column id is the primary key; column y is a foreign key into t_pci_dss_requirement, ensuring every jurisdiction-scoped policy is grounded in an existing requirement.

### 1.4 t_attestation_signed_by

This table implements AXIOM 4, recording the subclass relation to bfo:0000015 together with the sdg:signedBy restriction to cco:Person. Column id is the sole primary key; the absence of foreign keys reflects the axiom’s focus on the attestation process itself.

| id | x |

### 1.5 t_policy_min_one_enforcer

This table satisfies AXIOM 5 by asserting the minimum cardinality restriction sdg:enforcedBy min 1 on cco:DirectiveICE. Column id is the primary key; column y is a foreign key into t_pci_dss_requirement, guaranteeing each policy instance is linked to at least one enforcing requirement.

## 2 Cross-Join Demonstration

A multi-hop query can retrieve the jurisdiction and signed attestation for any given PCI DSS requirement. Consider the question: “Which jurisdiction-scoped policy governs AccountData and is attested by AnnualROC_2023?”

The join path traverses t_requirement_equiv_specifies_target.y → t_pci_dss_requirement.id → t_policy_equiv_jurisdiction_and_scope.y → t_attestation_signed_by.x. The result row is:

- Requirement target: AccountData
- Policy: EU_Merchant_Policy
- Jurisdiction: CardholderDataEU
- Attestation: AnnualROC_2023
