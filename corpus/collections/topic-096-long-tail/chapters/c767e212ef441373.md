# Chapter 4: Governance Frameworks and PCI DSS Compliance Ontology

## 4.1 Scope and Preamble

This chapter delineates the formal ontology underpinning the governance framework for Payment Card Industry Data Security Standard (PCI DSS) compliance. It establishes the axiomatic relationships between regulatory directives, specific control requirements, and enforcement mechanisms within an enterprise information security architecture. The content herein is intended for compliance officers, internal auditors, and information security managers responsible for mapping organizational policies to the PCI DSS standard. The definitions provided utilize Manchester syntax to express logical constraints, ensuring unambiguous interpretation of governance artifacts.

## 4.2 Requirement Equivalence and Target Specification

### 4.2.1 Axiomatic Definition

The foundational unit of the compliance framework is the `RequirementEquivSpecifiesTarget` class. This axiom defines a specific category of governance artifacts that serve three distinct functions: they act as Information Content Entities (ICE), they specify a particular control requirement, and they apply to a defined target system or process.

**Axiom 1:** `Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:specifies some {Y:Class}) and (sdg:appliesTo some {Z:Class})`

In this construct, `X` represents the formal requirement class (e.g., a Two-Factor Authentication Mandate). The slot `Y` refers to the specific PCI DSS requirement being invoked (e.g., Requirement 8.3), while `Z` denotes the operational scope or target asset class (e.g., Remote Access Networks). This tripartite structure ensures that every directive is semantically bound to both a regulatory source and a technical target.

### 4.2.2 Implementation and Audit Evidence

When auditing these entities, the reviewer must verify that the `specifies` slot resolves to a valid requirement identifier and that the `appliesTo` slot references an asset classification currently in scope. The relational projection of this axiom enforces that `y` (the specified requirement) must exist as a primary key in the PCI requirement registry.

**Action:** Ensure that all governance directives in the Document Management System (DMS) contain metadata fields for `RequirementID` and `TargetAsset` that correspond to the values in the schema below.

**Table 4-1: Requirement Equivalence and Target Specification Registry**

| id | x | y | z |
| :--- | :--- | :--- | :--- |
| `REQ_001` | `TwoFactorAuthReq` | `PCI_DSS_8_3` | `RemoteNetwork` |
| `REQ_002` | `EncryptionTransReq` | `PCI_DSS_4_1` | `TransmissionMedia` |

## 4.3 PCI DSS Requirement Subclassing

### 4.3.1 Hierarchical Structure

The `PciDssRequirement` axiom establishes the taxonomic link between a generic class of requirements and the specific PCI DSS standard. It asserts that the subject class `X` is a subclass of `cco:DirectiveICE` and possesses a `pciDssRequirement` relationship to object `Y`.

**Axiom 2:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:pciDssRequirement some {Y:Class}`

Verbalization: `{X} is something that pci dss requirement {Y}`.

This structure allows the ontology to distinguish between a general directive and one specifically mandated by the PCI Security Standards Council. The referential integrity is maintained by linking the `pciDssRequirement` slot (`y`) back to the equivalence definitions established in the previous section. This circular dependency (where the Requirement Equivalence table references the PCI Requirement table and vice versa) models the real-world constraint that a specific PCI requirement (e.g., 8.3) is the semantic fulfillment of a requirement class (e.g., TwoFactorAuthReq).

### 4.3.2 Compliance Verification

Auditors should query this table to trace the lineage of a control. If a control implementation is challenged, one must verify that the class `X` is correctly subclassed under the Directive ICE hierarchy and that its `y` value correctly maps to the originating requirement equivalence record.

**Table 4-2: PCI DSS Requirement Subclass Registry**

| id | x | y |
| :--- | :--- | :--- |
| `PCI_DSS_8_3` | `SecureRemoteAccess` | `REQ_001` |
| `PCI_DSS_4_1` | `DataEncryption` | `REQ_002` |

| `PCI_DSS_9_2` | `PhysicalEntryControl` | `REQ_004` |

*Table 4-2 embodies Axiom 2. The primary key `id` represents the specific PCI DSS requirement identifier. Column `x` is the subclass of the directive, and column `y` is a foreign key referencing the `t_requirement_equiv_specifies_target` table, closing the loop on the requirement definition.*

## 4.4 Policy Jurisdiction and Scope

### 4.4.1 Defining Governance Boundaries

Policies within the framework must explicitly define their legal jurisdiction and operational scope. The `PolicyEquivJurisdictionAndScope` axiom provides the logical structure for these definitions.

**Axiom 3:** `Class: {X:Class} EquivalentTo: cco:DirectiveICE and (sdg:hasJurisdiction some {Y:Class}) and (sdg:governsScope some {Z:Class})`

Here, `X` represents the Policy class (e.g., AccessControlPolicy). The slot `Y` is constrained to the PCI requirement registry, implying that the "jurisdiction" in this technical context is defined by the specific standard requirement being enforced. The slot `Z` defines the scope of governance (e.g., Cardholder Data Environment).

### 4.4.2 Regulatory Mapping

This axiom is critical for multi-national organizations where a single policy must satisfy varying regulatory landscapes. By binding `hasJurisdiction` to the PCI requirement ID, the framework ensures that the policy is strictly interpreted through the lens of that specific compliance mandate.

**Action:** Review all policy documents to ensure the "Jurisdiction" section cites the specific PCI DSS requirement ID (e.g., `PCI_DSS_8_3`) rather than vague geographic terms, unless the ontology is extended to include geographic region classes.

| `POL_002` | `CryptographyPolicy` | `PCI_DSS_4_1` | `PublicNetwork` |

## 4.5 Attestation and Signatory Authority

### 4.5.1 The Attestation Process

Attestation represents the formal acknowledgment of compliance or execution of a directive. The `AttestationSignedBy` axiom defines this as a process (`bfo:0000015`) that must be signed by a person (`cco:Person`).

**Axiom 4:** `Class: {X:Class} SubClassOf: bfo:0000015, sdg:signedBy some cco:Person`

Verbalization: `{X} is something that signed by person`.

This axiom moves the ontology from static definitions (Directives) to dynamic events (Processes). The class `X` represents the specific attestation event instance (e.g., the 2023 Annual ROC Sign-off). The requirement that it be signed by a person ensures non-repudiation and assigns individual accountability.

### 4.5.2 Audit Trail Integrity

For the purposes of this schema, the relational projection focuses on the attestation event itself. The link to the specific person is managed via the object property `sdg:signedBy`, but the table structure below captures the event instance.

**Table 4-4: Attestation Event Registry**

| :--- | :--- |
| `ATT_001` | `QSA_Attestation_Event` |
| `ATT_002` | `InternalAudit_SignOff` |
| `ATT_003` | `Executive_Compliance_Ack` |
| `ATT_004` | `Vendor_Risk_Acceptance` |
| `ATT_005` | `Pen_Test_Review_SignOff` |

*Table 4-4 embodies Axiom 4. The `id` is the unique identifier for the attestation process instance, and `x` is the class of the attestation event. This table records the occurrence of the process defined by the BFO Process anchor.*

## 4.6 Policy Enforcement Mechanisms

### 4.6.1 Mandatory Enforcement

A policy without enforcement is merely advisory. The `PolicyMinOneEnforcer` axiom mandates that any valid policy directive must have at least one designated enforcer.

**Axiom 5:** `Class: {X:Class} SubClassOf: cco:DirectiveICE, sdg:enforcedBy min 1 {Y:Class}`

Verbalization: `{X} is a directive information content entity`.

The `min 1` cardinality constraint on the `enforcedBy` slot ensures that gaps in responsibility are logically impossible within the system. The enforcer (`Y`) is mapped to the PCI requirement registry, implying that the enforcement mechanism is often the control requirement itself or the role responsible for that requirement.

### 4.6.2 Operational Accountability

This structure facilitates automated governance queries. For instance, a system can automatically flag any policy in Table 4-3 that lacks a corresponding entry in Table 4-5 as "Orphaned" or "Non-Enforceable."

**Action:** Conduct a quarterly review of the Enforcement Registry to ensure that for every active Policy ID, there is at least one valid Enforcer ID linked to it.
