# Directive Governance in Infrastructure Audit Systems

This chapter defines five ontological templates for directive governance and realizes each as a relational table. The tables support cross-table queries that trace how controls address risks, how audits are conducted, and how attestations carry evidence and priority.

## 1. Control-Risk Addressing Templates

Two templates capture the distinct semantics of universal versus existential risk addressing by directives. Both tables reference only class-level identifiers; their primary keys therefore serve as stable handles for later joins with process tables.

### 1.1 Universal Risk Addressing

The table `t_control_only_addresses_threat_class` embodies axiom 1. Column `id` is the primary key; columns `x` and `y` are class references with no foreign-key enforcement inside the table.

```sql
SELECT x, y FROM t_control_only_addresses_threat_class;
```

| id | x | y |
| --- | --- | --- |
| ctrl-01 | ENCAInfrastructureDirective | EconomicGrowthBottleneck |
| ctrl-02 | ENCAInfrastructureDirective | ServiceQualityDeficit |
| ctrl-03 | ENCAInfrastructureDirective | MaintenanceBacklogRisk |
| ctrl-04 | ENCAProcurementDirective | CorruptionExposure |

### 1.2 Existential Risk Addressing

The table `t_control_addresses_risk` embodies axiom 3. Column `id` is the primary key; column `y` is required.

```sql
SELECT x, y FROM t_control_addresses_risk;
```

| id | x | y |
| --- | --- | --- |
| ctrl-10 | ENCAFloodDirective | FloodDamageExposure |
| ctrl-11 | ENCAFloodDirective | SupplyChainDisruption |
| ctrl-12 | RoadAssetDirective | PavementDeterioration |
| ctrl-13 | RailSignallingDirective | SignallingFailure |

## 2. Process and Evidence Templates

Three tables record process participation, evidence attachment and priority assignment. Each table’s primary key permits later linkage to the control tables via shared class names.

### 2.1 Audit Personnel Assignment

The table `t_audit_conducted_by` embodies axiom 2. Column `id` is the primary key; column `x` names the audit process class.

```sql
SELECT x FROM t_audit_conducted_by;
```

| id | x |
| --- | --- |
| aud-01 | ENCAComplianceAudit |
| aud-02 | ENCAComplianceAudit |
| aud-03 | ProcurementIntegrityAudit |
| aud-04 | AssetConditionAudit |

### 2.2 Evidence Attachment

The table `t_attestation_with_supporting_evidence` embodies axiom 4. Column `id` is the primary key; column `y` is required.

```sql
SELECT x, y FROM t_attestation_with_supporting_evidence;
```

| id | x | y |

## 3. Multi-Hop Query Example

A compliance officer needs the priority and supporting evidence for the audit of the ENCAFloodDirective. The path traverses three tables:

1. Locate the directive class in `t_control_addresses_risk` (row ctrl-10).
2. Match the same class name in `t_requirement_has_priority` (row req-02) to obtain priority.
3. Match the audit class ENCAComplianceAudit in `t_attestation_with_supporting_evidence` (row att-01) to obtain evidence.

Joined result:

- Directive: ENCAFloodDirective
- Risk addressed: FloodDamageExposure
- Priority: CriticalPriority
- Evidence: SiteInspectionReport2023
