# Directive Governance in Regulatory Compliance Systems

This chapter defines five core ontological patterns for modeling controls, audits, attestations, and requirements within regulatory compliance. Each pattern is realized as a table whose columns directly encode the Manchester OWL axioms. The resulting schema supports cross-table joins that answer multi-hop compliance queries such as “which high-priority controls addressing data-breach risk were attested during an audit conducted by a named person?”

## 1. Table Definitions and Axiom Mappings

### 1.1 Control-Only Addresses Threat Class
Table `t_control_only_addresses_threat_class` embodies Axiom 1 (`control_only_addresses_threat_class`). Column `id` is the primary key. Columns `x` and `y` are class references; `x` denotes a subclass of `cco:DirectiveICE` that addresses risk `y` exclusively. A mental cross-join on `y` with matching values in `t_control_addresses_risk` yields the set of controls that both exclusively and existentially address the same risk class.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x | y |
|----|---|---|
| COT-001 | AnnualDataReview | DataBreachRisk |
| COT-002 | EncryptionMandate | DataBreachRisk |
| COT-003 | AccessLogRetention | UnauthorizedAccess |
| COT-004 | VendorDueDiligence | ThirdPartyRisk |
| COT-005 | IncidentResponsePlan | OperationalDisruption |

### 1.2 Audit Conducted By
Table `t_audit_conducted_by` embodies Axiom 2 (`audit_conducted_by`). Column `id` is the primary key. Column `x` references a subclass of `bfo:0000015` (process) that must be conducted by at least one `cco:Person`. Joining `x` values to `id` columns in attestation or requirement tables links the responsible person to the evidence or priority of the audited control.

```sql
CREATE TABLE t_audit_conducted_by (
  id VARCHAR(255),
  x VARCHAR(255),
  PRIMARY KEY (id)
);
```

| id | x |
|----|---|
| ACB-001 | AnnualComplianceAudit |
| ACB-002 | QuarterlyControlTest |
| ACB-003 | ExternalPenetrationReview |
| ACB-004 | ThirdPartyRiskAssessment |
| ACB-005 | IncidentRootCauseAnalysis |

### 1.3 Control Addresses Risk
Table `t_control_addresses_risk` embodies Axiom 3 (`control_addresses_risk`). Column `id` is the primary key. Column `x` is a subclass of `cco:DirectiveICE`; column `y` (NOT NULL) is the risk class it addresses. The existential restriction permits multiple rows sharing the same `x` but differing `y`, enabling enumeration of all risks mitigated by a single control.

```sql
CREATE TABLE t_control_addresses_risk (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

| id | x | y |

| CAR-001 | EncryptionMandate | DataBreachRisk |
| CAR-002 | AccessLogRetention | UnauthorizedAccess |
| CAR-003 | VendorDueDiligence | ThirdPartyRisk |
| CAR-004 | IncidentResponsePlan | OperationalDisruption |
| CAR-005 | AnnualDataReview | DataBreachRisk |

### 1.4 Attestation With Supporting Evidence
Table `t_attestation_with_supporting_evidence` embodies Axiom 4 (`attestation_with_supporting_evidence`). Column `id` is the primary key. Column `x` references a `bfo:0000015` process; column `y` (NOT NULL) is the evidence class. Joining on `x` with `t_audit_conducted_by.x` yields the person responsible for producing each piece of supporting evidence.

```sql
CREATE TABLE t_attestation_with_supporting_evidence (
  id VARCHAR(255),
  x VARCHAR(255),

  PRIMARY KEY (id)
);
```

### 1.5 Requirement Has Priority
Table `t_requirement_has_priority` embodies Axiom 5 (`requirement_has_priority`). Column `id` is the primary key. Column `x` is a subclass of `cco:DirectiveICE`; column `y` (NOT NULL) is the priority class. Cross-joining `x` with `t_control_addresses_risk.x` surfaces the priority of every control that mitigates a given risk.

```sql
CREATE TABLE t_requirement_has_priority (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

## 2. Cross-Join Demonstration

Question: “List every High-priority control that addresses DataBreachRisk together with the person who conducted the audit that produced supporting evidence for that control.”

Step 1. Join `t_requirement_has_priority` (`x`, `y`) with `t_control_addresses_risk` (`x`, `y`) on `x` where `y = 'DataBreachRisk'` and `t_requirement_has_priority.y = 'High'`.  
Result rows: `EncryptionMandate`.

Step 2. Join the resulting `x` values with `t_attestation_with_supporting_evidence.x` to obtain evidence identifiers.  
Result: `ASE-001` (LogArchive2023Q4).

Step 3. Join `t_attestation_with_supporting_evidence.x` with `t_audit_conducted_by.x` to retrieve the conducting person class.  
Joined row:  
`(EncryptionMandate, High, DataBreachRisk, AnnualComplianceAudit, LogArchive2023Q4, AnnualComplianceAudit)`

The single joined tuple shows that the High-priority control EncryptionMandate, which addresses DataBreachRisk, was attested during the AnnualComplianceAudit conducted by the person class referenced in `ACB-001`.
