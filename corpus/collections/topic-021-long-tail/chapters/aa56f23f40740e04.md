# Chapter 4: Directive Controls for Risk and Requirement Governance

This chapter defines four deterministic templates that classify directive instances according to their risk-addressing and specification properties. Each template is realized as a single relational table whose columns directly encode the Manchester slots. The resulting schema supports cross-table joins that recover multi-hop facts such as “which high-priority requirement specifies a target that is addressed only by a given control class.”

## 1 Template Definitions and Table Projections

### 1.1 Control-Only Threat Restriction
Axiom 1 states that a directive class addresses risk exclusively toward one threat class. The corresponding table therefore stores pairs of class references with no nulls permitted on either column; the synthetic identifier serves solely as primary key and carries no foreign-key semantics.

```sql
CREATE TABLE t_control_only_addresses_threat_class (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255),
  PRIMARY KEY (id)
);
```

Example rows:

| id   | x                              | y                     |
|------|--------------------------------|-----------------------|
| c01  | FireSuppressionDirective       | FireHazard            |
| c02  | ChemicalContainmentDirective   | SpillRisk             |
| c03  | ElectricalIsolationDirective   | ArcFlashThreat        |
| c04  | PressureReliefDirective        | OverpressureEvent     |
| c05  | AccessControlDirective         | UnauthorizedEntry     |

### 1.2 Control-to-Risk Addressing
Axiom 2 relaxes the universal restriction to an existential one, allowing a control to address one or more risks. The table therefore admits multiple rows sharing the same x value while requiring a non-null y.

```sql
CREATE TABLE t_control_addresses_risk (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

Example rows:

| id   | x                              | y                     |
|------|--------------------------------|-----------------------|
| r01  | FireSuppressionDirective       | IgnitionSource        |
| r02  | ChemicalContainmentDirective   | EnvironmentalRelease  |
| r03  | ElectricalIsolationDirective   | ShockHazard           |
| r04  | PressureReliefDirective        | VesselRupture         |
| r05  | AccessControlDirective         | DataBreach            |
| r06  | FireSuppressionDirective       | SmokeDamage           |

### 1.3 Requirement Priority Assignment
Axiom 3 attaches a priority class to any directive that functions as a requirement. The table records the requirement class together with its priority; both columns are non-null.

```sql
CREATE TABLE t_requirement_has_priority (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

Example rows:

| id   | x                                   | y          |
|------|-------------------------------------|------------|
| p01  | QuarterlyInspectionRequirement      | High       |
| p02  | AnnualCalibrationRequirement        | Medium     |
| p03  | IncidentReportingRequirement        | Critical   |
| p04  | TrainingDocumentationRequirement    | High       |
| p05  | EquipmentDecommissionRequirement    | Medium     |

### 1.4 Requirement Equivalence for Specification and Target
Axiom 4 supplies an equivalence axiom that simultaneously captures the specifies and appliesTo relations. The table therefore contains three non-null class columns plus identifier.

```sql
CREATE TABLE t_requirement_equiv_specifies_target (
  id VARCHAR(255),
  x VARCHAR(255),
  y VARCHAR(255) NOT NULL,
  z VARCHAR(255) NOT NULL,
  PRIMARY KEY (id)
);
```

Example rows:

| id   | x                                   | y                              | z                     |
|------|-------------------------------------|--------------------------------|-----------------------|
| e01  | QuarterlyInspectionRequirement      | PressureReliefDirective        | OverpressureEvent     |
| e02  | AnnualCalibrationRequirement        | ElectricalIsolationDirective   | ArcFlashThreat        |
| e03  | IncidentReportingRequirement        | ChemicalContainmentDirective   | SpillRisk             |
| e04  | TrainingDocumentationRequirement    | AccessControlDirective         | UnauthorizedEntry     |
| e05  | EquipmentDecommissionRequirement    | FireSuppressionDirective       | FireHazard            |

## 2 Cross-Table Query Example

To retrieve every high-priority requirement whose specified control addresses a threat that is also restricted by an “only” axiom, the following mental join path is used:

1. Start in t_requirement_has_priority where y = 'High' (rows p01, p04).
2. Join on x to t_requirement_equiv_specifies_target to obtain the control class y and target z.
3. Join the control class to t_control_only_addresses_threat_class on x to confirm the threat class matches z.

Resulting joined row for p01:

QuarterlyInspectionRequirement (High) → PressureReliefDirective → OverpressureEvent (confirmed by c04).

The identical path yields one additional row for p04, confirming two high-priority requirements whose targets are exclusively addressed by the listed controls.
