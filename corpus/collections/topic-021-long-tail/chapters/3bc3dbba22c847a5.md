# Chapter 4: Directive Governance Patterns in Workplace Safety Audit Trails

This chapter presents four ontological templates that formalize how directives address risks, carry priorities, and specify targets. The templates are illustrated with a compact relational schema drawn from workplace safety audit records. The schema supports cross-table joins that recover multi-hop facts such as the priority assigned to a control that addresses a given threat class.

## 1. Core Templates and Their Relational Projections

Four Manchester OWL axioms define the admissible relationships. Each axiom is realized by one table whose columns directly encode the quantified slots. Primary keys are opaque identifiers; columns named x, y, and z hold class references that serve as join keys across tables.

### 1.1 Table t_control_only_addresses_threat_class
This table embodies the universal restriction “addressesRisk only”. Column id is the primary key; columns x and y are class references with no foreign-key enforcement inside the table.

| id  | x                    | y                  |
|-----|----------------------|--------------------|
| c01 | SafetyProtocol       | FireHazard         |
| c02 | EquipmentCheck       | ElectricalRisk     |
| c03 | EmergencyProcedure   | ChemicalSpill      |
| c04 | SafetyProtocol       | ChemicalSpill      |
| c05 | EquipmentCheck       | FireHazard         |

### 1.2 Table t_control_addresses_risk
This table embodies the existential restriction “addressesRisk some”. Column id is the primary key; column y is non-null.

| id  | x                    | y                  |
|-----|----------------------|--------------------|
| c06 | SafetyProtocol       | ElectricalRisk     |
| c07 | EmergencyProcedure   | FireHazard         |
| c08 | EquipmentCheck       | ChemicalSpill      |
| c09 | SafetyProtocol       | ChemicalSpill      |

### 1.3 Table t_requirement_has_priority
This table embodies the existential restriction “hasPriority some”. Column id is the primary key; column y is non-null.

| id  | x                    | y                  |
|-----|----------------------|--------------------|
| r01 | SafetyProtocol       | High               |
| r02 | EquipmentCheck       | Medium             |
| r03 | EmergencyProcedure   | High               |
| r04 | SafetyProtocol       | Medium             |

### 1.4 Table t_requirement_equiv_specifies_target
This table embodies an equivalence axiom combining two existential restrictions. Column id is the primary key; columns y and z are non-null.

| id  | x                    | y                  | z                    |
|-----|----------------------|--------------------|----------------------|
| e01 | SafetyProtocol       | FireHazard         | LaboratoryArea       |
| e02 | EquipmentCheck       | ElectricalRisk     | StorageFacility      |
| e03 | EmergencyProcedure   | ChemicalSpill      | LaboratoryArea       |
| e04 | SafetyProtocol       | ChemicalSpill      | StorageFacility      |

## 2. Cross-Table Retrieval Example

A compliance officer needs the priority of every control that both addresses ChemicalSpill and applies to StorageFacility. The query traverses three tables:

1. Select rows from t_control_addresses_risk where y = 'ChemicalSpill' → yields x values SafetyProtocol and EmergencyProcedure.
2. Join those x values to t_requirement_has_priority on column x → yields priorities High (EmergencyProcedure) and Medium (SafetyProtocol).
3. Join the same x values to t_requirement_equiv_specifies_target on column x where z = 'StorageFacility' → retains only SafetyProtocol.

The resulting joined row is therefore:

SafetyProtocol | ChemicalSpill | Medium | StorageFacility

The same pattern recovers any other admissible combination by substituting different literal values for y or z.
