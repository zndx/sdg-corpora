# Chapter 4: Governance of Temporal Artifacts and Directive Compliance

This chapter delineates the structural compliance requirements governing the publication of artifacts, the specification of directives, and the temporal boundaries of scheduled events within institutional frameworks. It provides a rigorous examination of the ontology governing creative works, information-cognitive entities, and event artifacts, ensuring that all instances adhere to the established relational constraints. The following sections detail the axiomatic relationships between published documents, governing directives, and event schedules, supported by audit data derived from institutional records.

## 4.1 Temporal Anchoring of Creative Works

In the context of information governance, a Creative Work is formally defined as an artifact that is temporally anchored by a specific publication date. This relationship is not merely descriptive but serves as a foundational compliance metric for archival and regulatory purposes. The axiom `schemaorg_creativework_date` posits that for any Artifact {X} to be recognized as a valid record within the system, it must possess a `hasDatePublished` property linking it to a specific temporal instance {Y}.

This dependency ensures that all artifacts are traceable to a specific point in time, facilitating audit trails and version control. In practice, this means that a document such as a "Basic School Calendar" or a "Performance Report" cannot exist in the database as a valid entity without a corresponding date entry. Furthermore, the relational schema enforces a foreign key constraint where the date instance {Y} must reference a valid directive identifier, thereby linking the existence of the artifact to a governing requirement.

The following data table illustrates this relationship for a selection of institutional artifacts. Note that the `y` column, representing the date published, functionally references the requirement identifier that authorized or necessitated the publication.

**Table 4.1: Artifact Publication Records**

| :--- | :--- | :--- |
| CW-2017-01 | Basic School Calendar 2017-2018 | REQ-ORIENT-001 |
| CW-2014-19 | Cool Runnings Issue 19 | REQ-MARATHON-001 |

*Table 4.1 demonstrates the instantiation of the `schemaorg_creativework_date` axiom. The primary key `id` uniquely identifies the creative work, while `x` denotes the artifact class. The column `y` is constrained by the schema to reference a directive requirement, establishing the compliance link between the document and its governing mandate.*

## 4.2 Directive Governance and Specification

The governance framework is predicated on the definition of a Directive as an Information-Cognitive Entity (ICE) that actively specifies a target and applies to a specific scope. The axiom `requirement_equiv_specifies_target` establishes that a Class {X} is equivalent to a `cco:DirectiveICE` if and only if it `specifies` some target {Y} and `appliesTo` some scope {Z}. This tripartite structure is essential for enforcing policy: a directive must have an object (what it specifies), a subject (what it applies to), and an identity (the directive itself).

In the relational model, this structure is captured in `t_requirement_equiv_specifies_target`. The column `x` represents the Directive, while `y` represents the target (which, per the schema, must be a valid Creative Work identifier). Column `z` defines the scope or entity class to which the directive applies. This circular dependency—where the Directive references the Creative Work and the Creative Work references the Directive—creates a robust integrity check preventing orphaned records or unauthorized publications.

For instance, the "Orientation Protocol" directive specifies the "Basic School Calendar" and applies to "Pre-K and K" students. Similarly, a "Funding Mandate" specifies a "Wildlife Survey" and applies to the "Fisheries and Wildlife Division." The table below encodes these governance relationships.

**Table 4.2: Directive Specification and Scope**

| id | x (Directive) | y (Target Creative Work) | z (Scope) |
| :--- | :--- | :--- | :--- |
| REQ-ORIENT-001 | Orientation/Ice Cream Social Protocol | CW-2017-01 | Pre-K and K Students |
| REQ-MARATHON-001 | Comrades Marathon 2014 Rules | CW-2014-19 | Westville Athletic Club Members |
| REQ-GRANT-W39 | Pittman-Robertson Grant W-39-R | CW-2010-PH | Kansas Wildlife & Parks |

| REQ-PHYSIO-001 | Physiotherapist Assessment Directive | CW-2014-19 | Athletes (Brandon Jackson) |

*Table 4.2 operationalizes the `requirement_equiv_specifies_target` axiom. The foreign key constraint on `y` ensures that every directive targets a valid, existing artifact (referencing `t_schemaorg_creativework_date`), while `z` categorizes the applicability of the governance rule.*

## 4.3 Event Temporal Boundaries: Start Times

While creative works represent static artifacts, the ontology also accommodates dynamic entities classified as Events. An Event is a subclass of Artifact that is defined by a specific start time. The axiom `schemaorg_event_starttime` asserts that an Event {X} must have a property `hasEventStartTime` linking it to a temporal instance {Y}. In the context of this governance framework, the start time is not merely a timestamp but a compliance checkpoint regulated by a directive.

The relational schema for `t_schemaorg_event_starttime` links the event artifact to a directive requirement via the `y` column. This implies that the scheduling of an event start time is authorized by a specific directive. For example, the "Ice Cream Social" begins at a time authorized by the "Orientation Protocol." This binding ensures that temporal occurrences are not ad-hoc but are sanctioned extensions of the governing directives.

The following table details the start times for various scheduled events, linking them back to their authorizing directives. The data reflects the precision required in institutional scheduling, where events such as "Physiotherapist Assessments" or "School Kick-Offs" must align with strict temporal windows.

**Table 4.3: Event Start Time Compliance**

| id | x (Event Artifact) | y (Start Time / Directive Ref) |
| :--- | :--- | :--- |

| EVT-START-002 | Back to School Kick-Off | REQ-KICKOFF-002 |
| EVT-START-003 | Brandon Jackson Physio Session | REQ-PHYSIO-001 |
| EVT-START-004 | Pheasant Survey Fieldwork | REQ-GRANT-W39 |
| EVT-START-005 | Comrades Marathon Race Start | REQ-MARATHON-001 |

*Table 4.3 represents the `schemaorg_event_starttime` axiom. The `x` column identifies the specific event instance, while `y` references the directive ID that governs the commencement of that event. This structure ensures that event timelines are auditable against the original directive requirements.*

## 4.4 Event Temporal Boundaries: End Times

Complementing the start time boundary, the governance framework mandates the definition of an event's conclusion. The axiom `schemaorg_event_endtime` specifies that an Event {X} must have a property `hasEventEndTime` linking it to a temporal instance {Y}. This is critical for resource allocation, compliance reporting, and operational security, ensuring that events do not extend beyond their sanctioned durations.

The structure of `t_schemaorg_event_endtime` mirrors that of the start time table, with the `y` column referencing the authorizing directive. This creates a cohesive temporal envelope for every event: the Directive authorizes the Artifact (the Event), which is bounded by a Start Time and an End Time, both of which refer back to the Directive. In the audit data provided below, we observe that events such as the "Barbecue Blast" and "Body Fat Measurements" have strictly defined end times, ensuring that facility usage and personnel availability are managed according to the `cco:DirectiveICE` constraints.
