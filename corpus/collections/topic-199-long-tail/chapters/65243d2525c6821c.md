# Chapter 4: Temporal Anchoring and Directive Compliance in Artifact Governance

## 4.0 Scope and Preamble

This chapter delineates the structural dependencies between published artifacts, governing directives, and temporal events within a compliant information system. We establish the necessity of immutable linkage between creative works and their publication dates, the equivalence of directives to specific governance targets, and the precise bounding of event intervals. The following sections provide a formal analysis of these relationships, instantiated through tabular evidence derived from administrative records, academic reporting, and scheduled institutional events. The objective is to demonstrate how ontological axioms enforce data integrity across distinct domains of governance.

## 4.1 Publication Dating of Artifacts

The foundational axiom of artifact governance asserts that any entity classified as a CreativeWork or Artifact must possess a verifiable publication date. In the context of audit readiness and regulatory compliance, the date of publication is not merely a temporal literal but a governance object linked to the directive that authorized the release. This relationship ensures that the temporal validity of a document can be traced back to a specific requirement or order, preventing retroactive modification of the record without corresponding authority.

The axiom `schemaorg_creativework_date` formalizes this by stating that a Class `X` (the Artifact) has a property `hasDatePublished` pointing to Class `Y`. In the relational projection, this creates a dependency where the date entity (`y`) is actually a foreign key reference to a directive record. This structure enforces the rule that a date cannot exist in isolation; it must be sanctioned by a requirement entry.

Table 4.1 illustrates this concept using data drawn from institutional governance records. This linkage ensures that if the governance status of `REQ-PUB-01` changes (e.g., it is rescinded or superseded), the validity of the publication date is immediately re-evaluated within the system.

## 4.2 Specification and Targeting of Directives

Directives within the governance framework are defined not just by their existence but by their specificity and applicability. The axiom `requirement_equiv_specifies_target` posits that a Class `X` (a Directive) is equivalent to the intersection of three conditions: it is a type of `DirectiveICE`, it `specifies` a particular content element `Y`, and it `appliesTo` a target entity `Z`. This tripartite structure prevents ambiguous directives; every order must explicitly state what it specifies and to whom it applies.

The relational schema for this axiom introduces a circular dependency with the date table. The directive table (`t_requirement_equiv_specifies_target`) contains a column `y` (the specification) which references the date table (`t_schemaorg_creativework_date`). Conversely, the date table references the directive table. This creates a tight coupling where a directive specifies a date, and that date validates the directive.

Table 4.2 presents the directive records corresponding to the artifacts listed in Section 4.1. The `x` column represents the Directive itself, the `y` column references the Date ID (the specification), and the `z` column identifies the organizational target or entity to which the directive applies.

*This table embodies the `requirement_equiv_specifies_target` axiom. The primary key is `id`. Column `y` is a foreign key referencing `t_schemaorg_creativework_date(id)`, creating the specification link. Column `z` defines the scope of applicability.*

| id | x (Directive) | y (Date ID) | z (Target) |
| :--- | :--- | :--- | :--- |
| REQ-PUB-01 | Directive_ILCSWMA_Publication | DT-2018-11 | ILCSWMA_BOARD |

In this configuration, `REQ-PUB-01` (Directive_ILCSWMA_Publication) specifies the date entity `DT-2018-11` and applies to the `ILCSWMA_BOARD`. This structure allows auditors to query the database for all directives applying to a specific target (`z`) and immediately retrieve the specified artifacts or dates (`y`) associated with them. The integrity of the governance model relies on the fact that a directive cannot exist without a specification (`y`), and that specification must be a valid, dated artifact.

## 4.3 Event Start Time Definition

The governance of temporal events requires a distinct semantic treatment compared to static publication dates. An event is an artifact that unfolds over time, and its initiation must be formally declared. The axiom `schemaorg_event_starttime` asserts that an Artifact `X` (the Event) has a property `hasEventStartTime` pointing to Class `Y`.

In this schema, the "Start Time" (`y`) is not a simple timestamp string but a reference to a directive record (`t_requirement_equiv_specifies_target`). This design choice implies that the *start time* of an event is a governed parameter, defined by a specific directive. It prevents the arbitrary alteration of event schedules; changing a start time requires modifying or superseding the underlying directive that defines it.

To determine the actual clock time, the system resolves `REQ-EVT-01` to its specified details (which, as shown in previous sections, includes the linkage to the specific date artifact). This layered approach ensures that event timing is anchored in the same directive framework as static documents.

## 4.4 Event End Time Definition

To complete the temporal bounding of an event, the governance framework must account for its conclusion. The axiom `schemaorg_event_endtime` mirrors the start time logic, asserting that an Artifact `X` has a property `hasEventEndTime` pointing to Class `Y`. Similar to the start time, the end time is a reference to a directive record, ensuring that the duration of an event is a matter of compliance record rather than editable data fields.

This distinction is critical for auditing purposes. It allows for the calculation of event durations based on the difference between the directive defining the start and the directive defining the end. If an event overruns, it is a violation of the directive defining the end time, not merely a logistical issue.

By separating the start and end times into distinct directive references, the ontology supports complex scheduling logic, such as overlapping events or conditional durations, while maintaining a strict referential integrity.
