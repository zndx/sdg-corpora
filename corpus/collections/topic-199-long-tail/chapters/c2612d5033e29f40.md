# Chapter 4: Temporal Governance and Directive Compliance in Artifact Lifecycle Management

## 4.1 Preamble and Scope

This chapter delineates the structural framework for managing temporal and compliance-related metadata within an ontology-driven governance system. The focus is restricted to the precise mapping of artifacts to their publication dates and the enforcement of temporal boundaries on events through directive constructs. The following sections introduce four core axioms that define how CreativeWorks and Events are anchored to temporal directives, ensuring referential integrity across compliance repositories. The definitions provided herein are mandatory for systems processing audit trails and regulatory schedules.

## 4.2 Artifact Publication and Date Anchoring

In the context of digital governance, an artifact does not merely possess a temporal property; it is formally linked to a date entity through a defined subclass relationship. This relationship asserts that any entity classified as a CreativeWork must, by definition, possess a publication date. However, within this ontology, the date is not treated as a primitive literal but as a distinct entity that may itself be subject to governance constraints.

The axiom `schemaorg_creativework_date` establishes that a CreativeWork (X) is a subclass of Artifact and has a date published (Y). This structure ensures that the existence of the artifact is temporally bound. To maintain data consistency, the "date published" slot (Y) must reference an existing directive identifier, enforcing a rule where dates are managed as controlled compliance objects rather than free-text inputs.

**Table 4.1: CreativeWork Date Mapping**
*This table embodies Axiom 1 (`schemaorg_creativework_date`), representing the link between an Artifact and its publication date. The primary key is the `id` of the CreativeWork, while the `y` column serves as a foreign key referencing the Directive that defines the date, ensuring that all temporal points are authorized.*

| id (PK) | x (CreativeWork) | y (Date Published) |
| :--- | :--- | :--- |
| `cw_2023_rpt_a` | `Annual_Audit_Report_2023` | `dir_pub_date_001` |
| `cw_2023_rpt_b` | `Q3_Financial_Summary` | `dir_pub_date_002` |
| `cw_policy_v1` | `Data_Retention_Policy_v1` | `dir_pub_date_003` |
| `cw_manual_x` | `Incident_Response_Manual` | `dir_pub_date_004` |

### 4.2.1 Implementation Notes
When populating the repository, the system must verify that the value inserted into column `y` corresponds to a valid identifier in the directive registry. This prevents the creation of "orphan" dates that lack administrative provenance. For instance, the `Annual_Audit_Report_2023` is linked to `dir_pub_date_001`, indicating that the specific publication moment is governed by directive `001`.

## 4.3 Directive Specification and Target Application

The core of the governance framework lies in the definition of a Requirement. A Requirement is axiomatically defined as a DirectiveICE (Information and Communication Entity) that specifies a target and applies to a particular scope. This tripartite structure—Directive, Target, and Scope—allows for granular control over compliance rules.

The axiom `requirement_equiv_specifies_target` formalizes this by stating that a Requirement (X) is equivalent to a DirectiveICE that specifies some Target (Y) and applies to some Scope (Z). In this schema, the Target (Y) must be an existing CreativeWork, creating a bidirectional enforcement loop: a CreativeWork has a Date (which is a Directive), and that Directive specifies the CreativeWork as its target. This circular reference is intentional, modeling the real-world dependency where a document's validity is contingent upon the directive that publishes it, and the directive's purpose is defined by the document it targets.

**Table 4.2: Requirement and Directive Specification**
*This table embodies Axiom 2 (`requirement_equiv_specifies_target`), defining the directives that govern artifacts. The primary key is the directive `id`. The `y` column is a foreign key to the CreativeWork table, establishing the target of the directive, while `z` defines the organizational scope to which the directive applies.*

| id (PK) | x (Requirement) | y (Target) | z (Scope) |
| :--- | :--- | :--- | :--- |
| `dir_pub_date_001` | `Publication_Directive_Alpha` | `cw_2023_rpt_a` | `Finance_Department` |
| `dir_pub_date_002` | `Publication_Directive_Beta` | `cw_2023_rpt_b` | `Operations_Division` |
| `dir_time_start_01` | `Start_Window_Directive` | `evt_audit_001` | `Server_Farm_East` |
| `dir_time_end_01` | `End_Window_Directive` | `evt_audit_001` | `Server_Farm_East` |
| `dir_pub_date_003` | `Policy_Release_Directive` | `cw_policy_v1` | `Compliance_Office` |

### 4.3.1 Scope and Targeting
The `z` column (Scope) is critical for audit trails. It indicates the organizational domain or jurisdiction to which the directive applies. For example, `dir_pub_date_001` applies specifically to the `Finance_Department`, ensuring that the publication of the `Annual_Audit_Report_2023` is only recognized as valid within that context. Furthermore, the inclusion of temporal directives (`dir_time_start_01`, `dir_time_end_01`) targeting an event (`evt_audit_001`) demonstrates that this requirement structure is not limited to static documents but also governs temporal processes.

## 4.4 Event Start Time Governance

Events are modeled as Artifacts that possess a specific temporal onset. The axiom `schemaorg_event_starttime` asserts that an Event (X) is a subclass of Artifact and has an event start time (Y). Consistent with the treatment of publication dates, the start time is not a raw timestamp but a reference to a governing directive.

This abstraction allows the "start time" to carry metadata, constraints, and authorization levels. By linking the start time to a directive via the foreign key constraint, the system ensures that the event cannot begin until the specific start-time directive has been instantiated and validated. This is particularly relevant in controlled environments where process execution must be explicitly authorized by a governing body.

**Table 4.3: Event Start Time Mapping**
*This table embodies Axiom 3 (`schemaorg_event_starttime`), linking an event to its designated start directive. The primary key is the event `id`, and the `y` column references the directive that authorizes or defines the start time.*

| id (PK) | x (Event) | y (Event Start Time) |
| :--- | :--- | :--- |
| `evt_audit_001` | `Scheduled_System_Audit` | `dir_time_start_01` |
| `evt_maint_002` | `Preventive_Maintenance_Window` | `dir_time_start_02` |
| `evt_review_003` | `Quarterly_Review_Session` | `dir_time_start_03` |

### 4.4.1 Operational Logic
Consider the `Scheduled_System_Audit` (`evt_audit_001`). Its execution is contingent upon `dir_time_start_01`. If the directive is revoked or modified, the link between the event and the start time is severed or updated accordingly. This provides a single point of control for scheduling logic, distributed across the relational layer.

## 4.5 Event End Time Governance

The lifecycle of an event is formally closed by the definition of its end time. The axiom `schemaorg_event_endtime` specifies that an Event (X) has an event end time (Y). Structurally, this mirrors the start time definition, with the end time also serving as a reference to a directive.

By treating the end time as a directive artifact, the framework supports complex temporal logic, such as dependencies where an event cannot end until another directive is satisfied, or where the end time triggers downstream compliance workflows. The relational integrity ensures that an event definition is incomplete without a valid end-time directive, preventing open-ended or undefined process durations in the registry.

**Table 4.4: Event End Time Mapping**
*This table embodies Axiom 4 (`schemaorg_event_endtime`), linking an event to its designated end directive. The primary key is the event `id`, and the `y` column references the directive that authorizes or defines the end time.*

| id (PK) | x (Event) | y (Event End Time) |
| :--- | :--- | :--- |
| `evt_audit_001` | `Scheduled_System_Audit` | `dir_time_end_01` |

### 4.5.1 Temporal Integrity
In the case of `evt_audit_001`, both the start and end times are governed by directives (`dir_time_start_01` and `dir_time_end_01`). As shown in Table 4.2, both directives target the same event (`evt_audit_001`) and apply to the same scope (`Server_Farm_East`). This consistency is enforced by the relational schema, ensuring that the temporal boundaries of the event are tightly coupled to the governance scope of the organization.
