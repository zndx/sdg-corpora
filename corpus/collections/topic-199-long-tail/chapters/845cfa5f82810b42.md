# Chapter 7: Temporal Governance and Compliance Artifacts

## 7.1 Scope and Preamble

This chapter delineates the formal ontology governing the temporal attributes of compliance artifacts within the enterprise governance framework. It establishes the structural relationships between published works, directive requirements, and scheduled events. The definitions provided herein ensure that all audit reports, regulatory filings, and committee meetings are anchored to precise temporal data points, thereby enforcing accountability and traceability. The following sections detail the axioms that define how artifacts possess publication dates, how requirements specify targets, and how events are bounded by start and end times. These concepts are critical for maintaining the integrity of the corporate record and ensuring adherence to regulatory mandates.

## 7.2 Publication Dating of Artifacts

### 7.2.1 Conceptual Definition

In the context of governance records, the provenance of a document is inextricably linked to its publication date. The axiom `schemaorg_creativework_date` formalizes this relationship by asserting that any entity classified as a Creative Work (specifically, a subclass of `cco:Artifact`) must possess a `sdg:hasDatePublished` property. This property does not merely store a literal value; rather, it establishes a relationship to a temporal entity that is itself governed by compliance directives.

This construct ensures that the "date" of a report is treated as a distinct object of governance. By treating the publication date as a first-class citizen within the ontology, the framework allows for the auditing of *when* a document was released, independent of the file system metadata. This distinction is vital for scenarios where publication dates must be retroactively adjusted or verified against external regulatory timelines, such as the filing deadlines mandated by the Sarbanes-Oxley Act or local securities commissions.

### 7.2.2 Relational Implementation

The implementation of this axiom relies on the table `t_schemaorg_creativework_date`. This table serves as a registry linking the Artifact (`x`) to its Date Published (`y`). The structure enforces a foreign key constraint where the Date Published (`y`) must correspond to a valid entry in the requirements table (`t_requirement_equiv_specifies_target`). This circular dependency implies that a date cannot exist without a governing directive, and conversely, a directive regarding a date must target a specific temporal entity.

*Table 7.1: Schema of the Creative Work Date Registry*

| id | x (Artifact) | y (Date Published) |
| :--- | :--- | :--- |
| pub_date_2023_q1 | FinancialReport_Q1_2023 | req_pub_financial |
| pub_date_2023_q2 | FinancialReport_Q2_2023 | req_pub_financial |
| pub_date_audit_23 | AnnualAuditReport_2023 | req_pub_audit |
| pub_date_gov_23 | GovernanceCharter_v2 | req_pub_gov |
| start_time_audit | AnnualAuditMeeting | req_start_audit |

*Note: The `y` column references the requirement ID that authorizes or defines the specific publication date, ensuring that every temporal assertion is backed by a directive.*

## 7.3 Directive Specification and Targeting

### 7.3.1 Conceptual Definition

The core of the governance framework lies in the `requirement_equiv_specifies_target` axiom. This axiom defines a Requirement (or Directive) as an entity that is equivalent to the intersection of three conditions: it is a type of `cco:DirectiveICE`, it `sdg:specifies` a Target, and it `sdg:appliesTo` a Scope. This tripartite structure allows the organization to model complex compliance rules where a directive mandates a specific action (the Target) upon a specific entity (the Scope).

For instance, a directive may specify that a "Publication Date" (Target) must be set for the "Financial Report" (Scope). This separation of Target and Scope allows for the reuse of directives across multiple artifacts. A single "Publication Directive" class can apply to various reports, yet each instance of the directive will specify a unique date target. This modularity is essential for scaling governance controls across a large enterprise with hundreds of distinct reporting obligations.

### 7.3.2 Relational Implementation

The table `t_requirement_equiv_specifies_target` materializes this axiom. The primary key is the `id` of the requirement itself. The column `x` represents the Class of the Directive (e.g., `PublicationDirective`). The column `y` represents the Target of the directive, which, per the schema constraints, must be an identifier found in the `t_schemaorg_creativework_date` table. The column `z` represents the Scope, or the Artifact to which the directive applies.

This structure creates a rigorously enforced chain of custody. To assert that a report has a publication date, one must first create a directive that targets that date and applies to the report. The foreign key constraints prevent orphaned dates or directives that do not reference valid artifacts.

*Table 7.2: Directive Specification and Target Mapping*

| id | x (Directive Class) | y (Target) | z (Scope) |
| :--- | :--- | :--- | :--- |
| req_pub_financial | PublicationDirective | pub_date_2023_q1 | FinancialReport_Q1_2023 |
| req_pub_financial | PublicationDirective | pub_date_2023_q2 | FinancialReport_Q2_2023 |
| req_start_audit | ScheduleDirective | start_time_audit | AnnualAuditMeeting |
| req_end_audit | ScheduleDirective | end_time_audit | AnnualAuditMeeting |
| req_pub_audit | PublicationDirective | pub_date_audit_23 | AnnualAuditReport_2023 |

*Note: The `y` column (Target) references the `id` column of `t_schemaorg_creativework_date`, confirming that the directive targets a specific temporal entity.*

## 7.4 Event Start Time Governance

### 7.4.1 Conceptual Definition

While publication dates mark the release of static artifacts, the governance of dynamic processes requires the definition of event boundaries. The axiom `schemaorg_event_starttime` asserts that an Artifact (specifically an Event) has an Event Start Time. In a rigorous compliance environment, the start time of a meeting, an audit engagement, or a regulatory review period is not merely a calendar invitation; it is a defined attribute of the event artifact that triggers subsequent workflows and obligation periods.

This axiom ensures that the commencement of an event is formally recorded. This is particularly relevant for "Right to be Heard" protocols or stakeholder consultation periods, where the legal validity of the process depends on the precise start time. By modeling this as a relationship between the Event and a Start Time entity, the framework facilitates automated checks against regulatory windows (e.g., ensuring an audit begins within the fiscal year).

### 7.4.2 Relational Implementation

The `t_schemaorg_event_starttime` table captures this relationship. The table links the Event (`x`) to its Start Time (`y`). Consistent with the broader schema design, the Start Time (`y`) is not a simple timestamp string but a reference to a Requirement ID (`t_requirement_equiv_specifies_target`). This design choice implies that the *definition* of the start time is governed by a directive (e.g., "The Audit shall commence at 09:00").

*Table 7.3: Event Start Time Registry*

| id | x (Event) | y (Start Time) |
| :--- | :--- | :--- |
| start_time_audit | AnnualAuditMeeting | req_start_audit |
| start_time_board | BoardMeeting_Q1 | req_start_board |
| start_time_training | ComplianceTraining_2023 | req_start_training |
| start_time_review | RiskReviewCommittee | req_start_review |
| start_time_icebreaker | IceCreamSocial | req_start_social |

*Note: The `y` column references the directive that mandates or defines the specific start time, ensuring temporal alignment with governance schedules.*

## 7.5 Event End Time Governance

### 7.5.1 Conceptual Definition

Complementing the start time, the `schemaorg_event_endtime` axiom defines the termination point of an event artifact. This attribute is essential for calculating duration, enforcing time limits on specific activities, and triggering post-event workflows such as minute finalization or action item distribution. In the context of audit and risk committees, the end time signifies the closure of the deliberative window and the beginning of the recording and ratification phase.

Formalizing the end time allows the system to enforce constraints such as "Meetings shall not exceed 2 hours" or "The consultation period must end by 17:00." By treating the end time as a distinct entity linked to a directive, the organization can manage exceptions and extensions through the formal modification of the underlying requirement, rather than ad-hoc changes to a calendar.

### 7.5.2 Relational Implementation

The `t_schemaorg_event_endtime` table mirrors the structure of the start time table. It links the Event (`x`) to the End Time (`y`). Again, the End Time (`y`) references a Requirement ID, embedding the temporal definition within the directive framework. This ensures that the duration of an event (the interval between start and end) is the result of two intersecting directives, providing a high degree of control and auditability over temporal governance.

*Table 7.4: Event End Time Registry*

| id | x (Event) | y (End Time) |
| :--- | :--- | :--- |
| end_time_audit | AnnualAuditMeeting | req_end_audit |
| end_time_board | BoardMeeting_Q1 | req_end_board |
| end_time_training | ComplianceTraining_2023 | req_end_training |
| end_time_review | RiskReviewCommittee | req_end_review |
| end_time_icebreaker | IceCreamSocial | req_end_social |

*Note: The `y` column references the directive defining the end time, ensuring the event closure is formally authorized.*
