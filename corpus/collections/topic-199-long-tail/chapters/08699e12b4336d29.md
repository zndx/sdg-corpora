# Chapter 4: Governance of Temporal Artifacts and Institutional Directives

## 4.1 Scope and Preamble

This chapter delineates the structural and semantic relationships governing institutional artifacts, specifically focusing on the intersection of published media, regulatory directives, and scheduled events. Within the context of information governance, it is imperative to understand that artifacts—such as calendars, procedural handbooks, and compliance forms—do not exist in a vacuum. Rather, they are anchored to specific temporal points and regulatory frameworks that dictate their validity and operational scope. The following sections detail the ontological commitments required to model these relationships, utilizing a formal schema that binds Artifacts to Directives through precise foreign key constraints. This approach ensures that every instance of a published work or scheduled event is traceable to a governing requirement, thereby maintaining auditability and compliance rigor.

## 4.2 Artifact Publication Dates

The foundational concept in managing institutional records is the attribution of a publication date to a specific Artifact. In the ontology defined herein, an Artifact (denoted as class `X`) is a subclass of `cco:Artifact`. To establish the temporal validity of such an artifact, it must possess the property `sdg:hasDatePublished`, which links it to a specific temporal entity (class `Y`). 

However, in a rigorous governance framework, a "date" is not merely a primitive data type; it is often a reference to a specific directive or compliance milestone. Consequently, the relational schema for this axiom, `t_schemaorg_creativework_date`, establishes a foreign key dependency where the date value (`y`) must reference an existing directive identifier. This design enforces the rule that a publication date cannot exist in isolation; it must be sanctioned by a governing record. The primary key for this table is the unique identifier (`id`), ensuring that each publication event is distinct and immutable.

The following table illustrates the instantiation of this axiom. It records the publication dates for key institutional documents, such as the "Basic School Calendar for 2017-2018." Note that the `y` column (the date published) references a directive identifier, thereby linking the artifact's lifecycle to a specific governance requirement.

**Table 4-1: Artifact Publication Date Registry**

| id | x (Artifact) | y (Date Published / Directive Ref) |
|---|---|---|
| pub_cal_2018 | BasicSchoolCalendar_2017_2018 | dir_spec_cal_pub |
| reg_form_hs | CollegeInHighSchool_Registration | dir_spec_reg_avail |
| handbook_stu | StudentConduct_Handbook | dir_spec_hand_dist |
| audit_rep_q1 | Quarterly_Audit_Report | dir_spec_audit_rel |
| sched_kick | BackToSchool_Kickoff_Schedule | dir_spec_kick_pub |

In the example above, the "Basic School Calendar for 2017-2018" is published according to the parameters defined in directive `dir_spec_cal_pub`. This linkage ensures that the artifact's temporal status is formally controlled and auditable.

## 4.3 Directive Specification and Targeting

While the previous section established *when* an artifact is published, this section addresses *what* governs the artifact and *who* is subject to it. The axiom for `requirement_equiv_specifies_target` defines a class `X` that is equivalent to a `cco:DirectiveICE`. This class is characterized by two essential properties: it must `specify` a target (`Y`) and it must `applyTo` an entity or scope (`Z`).

This structure represents the core logic of compliance governance. A Directive is the active agent of regulation. The `specifies` property links the Directive to a specific target—in this relational model, that target is the publication date or temporal instance defined in the artifact tables. The `appliesTo` property defines the scope, such as a specific department, user group, or organizational unit. 

The relational schema `t_requirement_equiv_specifies_target` serves as the central junction in this data model. Its primary key is `id`. The column `y` (the specified target) contains a foreign key reference back to the `t_schemaorg_creativework_date` table, creating a bidirectional enforcement mechanism: a directive specifies a date, and that date is owned by that directive. The column `z` defines the applicability of the rule.

**Table 4-2: Directive Specification and Applicability Matrix**

| id | x (Directive) | y (Target Specified / Date Ref) | z (Applies To) |
|---|---|---|---|
| dir_spec_cal_pub | PublicationDirective | pub_cal_2018 | DistrictOffice |
| dir_spec_reg_avail | AvailabilityDirective | reg_form_hs | HighSchoolOfficials |
| dir_spec_hand_dist | DistributionDirective | handbook_stu | AllStudents |
| dir_spec_audit_rel | ReleaseDirective | audit_rep_q1 | AuditCommittee |
| dir_spec_kick_pub | AnnouncementDirective | sched_kick | GeneralPublic |

As demonstrated in Table 4-2, the directive `dir_spec_cal_pub` (a Publication Directive) specifies the target `pub_cal_2018` (the publication date of the calendar) and applies to the `DistrictOffice`. This formalism ensures that the act of publishing is not merely a data entry task but a governed action with defined responsibility and scope.

## 4.4 Event Start Times

Institutional governance extends beyond static documents to dynamic occurrences, modeled here as Events. An Event is treated as a subclass of `cco:Artifact`. To define its execution, the ontology utilizes the axiom `schemaorg_event_starttime`, which asserts that an Event (`X`) has an Event Start Time (`Y`).

Consistent with the governance-first approach, the "Start Time" is not a simple timestamp string. Instead, it is modeled as a reference to a Directive. This allows the start time to be conditional, movable, or defined by a complex rule set encapsulated in the directive. The relational schema `t_schemaorg_event_starttime` captures this relationship. The primary key is `id`, identifying the specific start-time instance. The column `y` (the start time) contains a foreign key referencing the `t_requirement_equiv_specifies_target` table. This implies that the start time of an event is dictated by a specific directive record.

Consider the "Orientation/Ice Cream Social" event referenced in institutional planning. Its start time is not merely "6:30 PM" in the database; it is an entity governed by directive `dir_time_orient_start`.

**Table 4-3: Event Start Time Governance**

| id | x (Event Artifact) | y (Start Time / Directive Ref) |
|---|---|---|
| evt_start_orient | OrientationEvent | dir_time_orient_start |
| evt_start_kick | KickoffEvent | dir_time_kick_start |
| evt_start_first | FirstDaySchool | dir_time_first_start |
| evt_start_pto | PTO_GeneralMeeting | dir_time_pto_start |
| evt_start_reg | RegistrationDeadline | dir_time_reg_start |

Table 4-3 shows that the `OrientationEvent` has a start time defined by `dir_time_orient_start`. This abstraction allows the system to link the temporal aspect of the event to the broader compliance framework defined in Section 4.3.

## 4.5 Event End Times

Completing the lifecycle of an institutional event requires the definition of its conclusion. The axiom `schemaorg_event_endtime` mirrors the structure of the start time axiom but applies to the termination of the event. Here, an Event (`X`) has an Event End Time (`Y`).

The relational schema `t_schemaorg_event_endtime` enforces the same constraints as the start time schema. The end time (`y`) is a foreign key referencing a directive in `t_requirement_equiv_specifies_target`. This ensures that the duration and conclusion of an event are as rigorously governed as its initiation. By separating start and end times into distinct tables linked to directives, the model supports complex scenarios where different authorities or rules govern the beginning and end of an event (e.g., an event that starts at a fixed time but ends when a specific condition is met by a directive).

**Table 4-4: Event End Time Governance**

| id | x (Event Artifact) | y (End Time / Directive Ref) |
|---|---|---|
| evt_end_orient | OrientationEvent | dir_time_orient_end |
| evt_end_kick | KickoffEvent | dir_time_kick_end |
| evt_end_first | FirstDaySchool | dir_time_first_end |
| evt_end_pto | PTO_GeneralMeeting | dir_time_pto_end |
| evt_end_reg | RegistrationDeadline | dir_time_reg_end |

In the final example of the "OrientationEvent," the end time is governed by `dir_time_orient_end`. By populating these tables with the specific instances of directives, events, and artifacts, an institution creates a dense, queryable evidence trail. Every date, every duration, and every target is anchored to a directive, satisfying the requirements of high-compliance environments such as audit reporting and regulatory governance.
